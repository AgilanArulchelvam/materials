01 — Extending cicd_pipeline_basics.html's needs: chain with a fourth stage

Adding the eval-gate stage

Start here, before the YAML. Think back to cicd_pipeline_basics.html's factory assembly line — a visual check, then a stress test, then final assembly, each gated on the last. This lab adds a FOURTH station to that same line, positioned after build (a real, deployable artifact now exists) and before deploy: a station that doesn't check whether the part LOOKS right or WORKS in isolation, but whether it performs correctly and fast enough under the exact conditions it'll actually face in production — a full dress rehearsal against real scenarios, not just a functional check.

# .github/workflows/ci.yml — cicd_pipeline_basics.html's 3 stages, # PLUS a new eval-gate stage between build and deploy jobs: lint: # unchanged from cicd_pipeline_basics.html runs-on: ubuntu-latest steps: ["..."] test: needs: lint # unchanged steps: ["..."] build: needs: test # unchanged steps: ["..."] eval-gate: # NEW — this week's checkpoint stage needs: build # will NOT start unless a real artifact was built runs-on: ubuntu-latest steps: - name: Run the eval scenario set against the candidate build # eval_scenario_design.html's set, executed against the just-built image run: run_eval_suite --image namespacelab-api:${{ github.sha }} --out results.json - name: Compute tool-selection accuracy, hallucination rate, p95 latency # tool_selection_and_hallucination_metrics.html + latency_and_tracing_integration.html run: compute_gate_metrics --in results.json --out metrics.json - name: Compare against configured thresholds — BLOCK on any violation run: check_gate_thresholds --in metrics.json --config gate_thresholds.yml # non-zero exit code here fails this JOB, which is what stops deploy # from ever running, via ITS OWN needs: eval-gate below deploy: needs: eval-gate # will NOT run unless every threshold passed runs-on: ubuntu-latest steps: ["blue-green cutover, per backend/cicd_gating_system_design.html"]

Notice this is a direct, mechanical extension of exactly the pattern cicd_pipeline_basics.html already established — eval-gate declares needs: build for the same reason test declared needs: lint: it only makes sense to run once a cheaper, earlier stage has already succeeded, and it needs an actual built artifact to test against, not just source code. deploy then declares needs: eval-gate, which is the ENTIRE mechanism that makes blocking real: if check_gate_thresholds exits non-zero, the eval-gate job itself is reported as failed, and GitHub Actions will not even attempt to start deploy — the exact same hard, mechanically-enforced dependency chain, now extended one link further.

Interview-ready definition: a CI/CD eval gate is a pipeline stage, sequenced after build and before deploy via a hard needs: dependency exactly like cicd_pipeline_basics.html's lint/test/build chain, that runs the full eval scenario set against the just-built candidate artifact, computes tool-selection accuracy, hallucination rate, and p95 latency from that run, and fails its own job (blocking every downstream stage, including deploy) if any individual metric violates its configured threshold. It exists because passing lint, unit tests, and a successful build only proves the CODE runs — none of them can catch a regression in the MODEL's actual behavior, which is exactly the gap this stage is built to close before it ever reaches production.

03 — What actually happens after a real block, and why deploy never even starts

Reading a blocked deploy's postmortem

Start here, before the breakdown. A blocked gate isn't a dead end — it's information. Once you've triggered a block above, the honest next question is the same one a real on-call engineer asks: exactly WHICH metric failed, by how much, and what's the smallest, most targeted next step, rather than a panicked full rollback of unrelated work.

What failedWhat it means concretelyWhat deploy never got to do
Tool-selection precision (a specific tool)Per tool_selection_and_hallucination_metrics.html's confusion-matrix framing — this specific tool is now being called when a different tool was correct, more often than the threshold allowsNever attempted the blue-green traffic-pointer flip at all (per backend/cicd_gating_system_design.html) — the previously-live, already-proven build kept serving 100% of traffic throughout
Hallucination rateA meaningful fraction of the candidate's claims aren't traceable to retrieved context — per tool_selection_and_hallucination_metrics.html's grounding definition, regardless of whether they happen to sound plausibleSame as above — the block happens before deploy is even attempted, so production traffic is never exposed to the regression
p95 latencyThe worst-served 5% of scenario runs exceeded the configured millisecond ceiling — per latency_and_tracing_integration.html's tail-latency argument, this is real even if the AVERAGE looked fineSame as above — no canary traffic percentage is ever increased past 0%

The reason this matters as a genuine "survival exercise" rather than a purely academic one: in each case, the deploy stage's own steps — the blue-green cutover or canary ramp-up from backend/cicd_gating_system_design.html — never execute AT ALL. This is precisely cicd_pipeline_basics.html's fail-fast principle, now applied one stage further downstream: it's far cheaper, and far safer, to catch a regression in an isolated eval run against a candidate build than to catch the same regression after it's already live and affecting real users, which is exactly what an eval gate that runs BEFORE deploy — rather than only monitoring AFTER — is built to guarantee.

Interview-ready definition: a blocked eval gate is a SUCCESS of the pipeline, not a failure of it — the gate did exactly what it was built to do, catching a regression in tool-selection accuracy, hallucination rate, or p95 latency before the candidate build ever reached the deploy stage, meaning the previously-live version continues serving all production traffic, completely undisturbed, for the entire duration of the investigation. The alternative — no gate, or a gate that only monitors production AFTER deploy — means the exact same regression is instead discovered by real users, in production, which is a strictly worse outcome regardless of how quickly a subsequent rollback happens.

Problem 1 · Deciding whether eval-gate should run in parallel with build

A teammate proposes running eval-gate in PARALLEL with build (removing needs: build) to save pipeline time. Using section 1's design and cicd_pipeline_basics.html's Problem 3 reasoning, evaluate this.

Show solution
This proposal is structurally broken, not just a speed/safety trade-off like cicd_pipeline_basics.html's Problem 3 lint/test parallelization question -- it's worse than that, because eval-gate's own steps genuinely DEPEND on build's output existing first. Section 1's eval-gate job runs `run_eval_suite --image namespacelab-api:${{ github.sha }}` -- it needs an actual, already-built, already-pushed image to run the eval scenario set AGAINST. If eval-gate started in parallel with build, that image would not exist yet (build may still be mid-compilation), and the eval run would either fail outright (no image found) or, worse, silently run against a STALE previously-built image with the same tag, producing gate results that don't actually reflect the NEW candidate build at all -- passing or failing the gate based on the wrong artifact entirely. This is a different category of problem from cicd_pipeline_basics.html's Problem 3, which was a genuine trade-off between speed and fail-fast compute savings for two stages that COULD technically run independently (lint and test don't need each other's output, they just chose to be sequenced for cost reasons). eval-gate and build have a hard DATA dependency, not just a stylistic sequencing choice -- needs: build here isn't optional the way needs: lint arguably was for test; it's required for eval-gate to even have a valid, unambiguous target to test against.
Problem 2 · Diagnosing a gate that passes on average but should have blocked

A candidate build passes the eval gate with "92% tool-selection accuracy" reported as a single blended number, safely above an 85% threshold. Two weeks later, the issue_refund tool turns out to have been badly broken the entire time. Using tool_selection_and_hallucination_metrics.html's Problem 2 and Problem 5, what should this gate's threshold logic have looked like instead?

Show solution
This is exactly tool_selection_and_hallucination_metrics.html's Problem 2 and Problem 5 playing out for real: a single blended accuracy number (whether macro- or, more likely here, micro-averaged across many more common, easier tool calls) can comfortably clear an 85% threshold while one specific, possibly high-consequence tool is badly broken, simply because its failures are outnumbered by successes elsewhere in the scenario set. The gate's threshold logic should have checked PER-TOOL precision and recall against PER-TOOL thresholds (per that lab's Problem 5 conclusion) -- section 1's own gate_thresholds.yml config should define a minimum threshold for EACH tool individually, with issue_refund specifically warranting a stricter bar given its financial consequences, and the gate should block if ANY single tool's metric falls below ITS OWN threshold, not merely if the blended average falls below one shared bar. This lab's own section 2 threshold config (a single "min tool-selection precision" slider) is deliberately simplified for the interactive demo -- a real production gate_thresholds.yml would define this per-tool, and recognizing that simplification is itself part of correctly applying tool_selection_and_hallucination_metrics.html's lesson to this specific pipeline.
Problem 3 · Reasoning about what happens to in-flight requests when a gate blocks mid-rollout

Using backend/cicd_gating_system_design.html's canary strategy, what's different about a gate blocking BEFORE any traffic reaches the candidate (this lab's design) versus a hypothetical gate that only runs AFTER a canary has already received 10% of live traffic?

Show solution
In THIS lab's design, the eval-gate stage runs entirely against SIMULATED/scenario-set traffic (eval_scenario_design.html's labeled scenarios), never real user traffic -- if it blocks, ZERO real users were ever exposed to the regression, because deploy (which would start the canary ramp-up at all) never even begins, per section 1's needs: eval-gate dependency. The hypothetical alternative -- a gate that only runs AFTER a canary is already receiving 10% of live traffic -- means by the time ANY gate signal fires, real users have ALREADY been served by the regressed build for however long it took to accumulate enough canary traffic to compute a meaningful metric. Blocking at that point can still stop FURTHER rollout (preventing the canary percentage from increasing past 10%, and triggering a rollback of that 10% back to the old version), but it cannot undo the fact that some real users already experienced the regression during the canary window -- a strictly worse outcome than this lab's pre-deploy gate, even though both are legitimate uses of "gating on thresholds." This is precisely why section 1 placed eval-gate BEFORE deploy (which includes the canary ramp-up) rather than treating canary metrics themselves as the only gate -- a pre-deploy gate against a controlled scenario set catches what it can before ANY real traffic is at risk, while canary-based monitoring (a separate, complementary practice) is a second, later safety net for regressions the eval scenario set didn't happen to cover.
Problem 4 · Designing what happens when the eval-gate stage itself fails to run (not fails its checks)

Suppose the eval-gate stage's run_eval_suite step crashes due to an infrastructure problem (the eval-running service is temporarily down) rather than any actual threshold being violated. Using section 1's needs: mechanism, what happens to deploy, and is that the correct behavior?

Show solution
GitHub Actions' needs: mechanism does not distinguish WHY a job failed -- it only checks whether the job reported success or failure. If run_eval_suite crashes for an infrastructure reason (the eval-running service being down, a network timeout, an out-of-memory crash unrelated to the candidate build's actual quality), the eval-gate job as a whole still reports FAILURE, and deploy's needs: eval-gate gate still refuses to run -- deploy is blocked exactly as if a real threshold had been violated, even though nothing about THIS candidate build's actual quality was ever measured. Is this correct? Yes, and importantly for the same reason a lint tool crashing (rather than reporting a real style violation) should also block test/build in cicd_pipeline_basics.html's original chain: the absence of a PASSING signal is not the same thing as evidence of quality, and treating "the check didn't run" as equivalent to "the check passed" would silently defeat the entire purpose of having the gate at all -- a flaky eval-running service could then become a backdoor that lets EVERY candidate build ship without ever actually being gated, simply by being unreliable enough, often enough. The correct operational response to an infrastructure failure here isn't to change the gating LOGIC (deploy should still be blocked) -- it's to alert whoever owns the eval-running service's reliability separately, and re-run the pipeline once that infrastructure problem is fixed, rather than loosening the gate's fail-closed behavior to work around a temporary outage.
Problem 5 · Writing your own gate_thresholds.yml and justifying each number

Using everything from this week — eval_scenario_design.html's taxonomy, tool_selection_and_hallucination_metrics.html's per-tool framing, and latency_and_tracing_integration.html's percentile reasoning — sketch a realistic gate_thresholds.yml for a customer-support agent with tools lookup_order, get_history, and issue_refund, and justify why issue_refund's thresholds should differ from the other two.

Show solution
tool_selection: lookup_order: { min_precision: 0.90, min_recall: 0.90 } get_history: { min_precision: 0.88, min_recall: 0.90 } issue_refund: { min_precision: 0.98, min_recall: 0.95 } # stricter hallucination: max_rate: 0.05 # stricter than a generic default -- financial-adjacent domain latency: max_p95_ms: 2000 Justification for issue_refund's stricter thresholds, drawing directly on this week's reasoning: tool_selection_and_hallucination_metrics.html's Problem 5 established that per-tool thresholds should reflect the ACTUAL CONSEQUENCE of that tool's misuse, not be uniform across every tool regardless of stakes. A false-positive lookup_order call (the agent looks up the wrong order's status) is annoying but low-consequence -- easily corrected in the same conversation, no lasting harm. A false-positive issue_refund call (the agent issues a refund it shouldn't have, or refunds the wrong order, or the wrong amount) is a genuine financial and trust consequence that's much harder to walk back after the fact -- warranting a meaningfully higher precision bar (0.98 vs 0.90) specifically because the COST of a rare miss is so much higher here, even if the base rate of issue_refund calls is much lower than lookup_order's, per eval_scenario_design.html's own reasoning about why a category needs ENOUGH instances to be trustworthy even when it's naturally rarer than others. The hallucination max_rate (0.05, stricter than a hypothetical generic 0.10 default) reflects the same logic applied to grounding specifically: a hallucinated claim about, say, "your refund has been processed" when it hasn't actually been grounded in a real issue_refund tool result would be a directly harmful, trust-breaking false claim in this domain, not a merely annoying one -- warranting a tighter bound than a lower- stakes, purely informational agent might reasonably accept. The p95 latency threshold (2000ms) is comparatively less domain-specific and more a straightforward UX/SLA call, per latency_and_tracing_integration. html's section 2 reasoning about p95 being the standard, defensible default for a deploy-gate threshold.
