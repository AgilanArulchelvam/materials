01 — What a trace-viewing dashboard actually needs to hold, before any UI code

Designing the dashboard's data shape

Start here, before any UI code. Think about a hospital's patient board — the kind with a row per patient, showing name, room, and status at a glance, where clicking (or walking to) any one patient's room gets you their FULL chart. The board itself doesn't try to show every patient's full chart all at once — that would be unreadable. It shows just enough per row to triage which patient needs attention, and defers the full detail until someone actually clicks in. A trace dashboard needs exactly this two-level structure: a scannable LIST view showing just enough per trace to notice something's wrong, and a DETAIL view (the waterfall, reused directly from opentelemetry_basics.html and instrument_month4_agent.html) that only renders once a specific trace is selected.

Four sample traces make up this dashboard's data, all variations on the exact scenario instrument_month4_agent.html instrumented — the SAME agent, run four different times, with genuinely different outcomes each time (real production traffic never looks identical run to run):

Interview-ready definition: a trace-viewing dashboard's data shape needs exactly two levels: a lightweight per-trace SUMMARY (trace ID, total duration, overall status) cheap enough to render a whole list of at once, and a full per-trace DETAIL (the complete span tree/waterfall) that's only computed or rendered once a specific trace is selected — mirroring database/read_replicas_and_dashboard_caching.html's point that a dashboard's LIST view is itself a distinct, comparatively cheap query pattern from any one trace's full detail view, and shouldn't eagerly fetch or render every trace's full detail just to populate a summary list.

Problem 1 · Diagnosing cap-9954d from the list view alone, before expanding it

Using section 2's dashboard, look at cap-9954d's list-view row WITHOUT expanding it. What can you already conclude, and what can you NOT yet conclude, about why it's slow?

Show solution
What you CAN conclude from the list view alone: this trace's status is OK (no tool_call errors, no injected-failure-retry pattern present) but its duration (2,310ms) is meaningfully higher than the other OK traces (640ms and 1,120ms) -- so something in this specific run took longer than normal, but nothing FAILED outright. This mirrors opentelemetry_ basics.html's Problem 2 distinction exactly: the list view's duration column is closer to a per-trace METRIC-like summary (a single number), while the CAUSE of that number requires the trace's actual span-level detail. What you CANNOT yet conclude from the list view alone: WHICH span inside this trace is responsible for the extra time -- was it plan_task running long, one specific get_order_detail call being slow even though it eventually succeeded, or (as section 1's table actually states) synthesize_answer's LLM call taking unusually long. The list view's single duration number is, by design (section 1), too coarse to localize this -- you have to click into the waterfall (the detail view) to see each span's individual duration and find the one specific span that's inflated, exactly why the dashboard has a detail level at all rather than only ever showing the list.
Problem 2 · Designing a filter this dashboard doesn't have yet

Section 2's dashboard has "All," "Errors only," and "Slow" filters. Design a THIRD filter — "Recovered" (traces where a tool call failed at least once but the trace's overall status is still OK) — and explain exactly which field(s) on each trace this filter would need to check.

Show solution
A "Recovered" filter needs a field this dashboard's summary-level data doesn't currently expose directly: whether ANY span within the trace had a failed attempt, independent of whether the trace's OVERALL status ended up OK or ERROR. Concretely, each trace's summary record would need an additional boolean, something like had_retry: true/false, computed once (when the trace is captured/indexed) by scanning its spans for at least one span with tool.result="error" immediately followed by a sibling span with tool.is_retry=true and tool.result="success" -- exactly the pattern instrument_month4_agent. html's section 2 code produces for cap-7731f specifically. The filter itself would then be: show only traces where had_retry === true AND status === "ok" -- cap-7731f matches (ord-129 failed once, retried, succeeded, overall status OK); cap-9013c does NOT match (ord-114 failed twice and was abandoned, so status is ERROR, not a "recovered" case); cap-8842a and cap-9954d don't match either (no failures at all). This is a genuinely useful filter beyond the two already built, because it answers a different question than "errors only" -- "errors only" finds traces where something is STILL broken, while "recovered" finds traces where the SYSTEM WORKED AS DESIGNED under adversity, which is itself worth being able to review (e.g. to confirm the retry logic is firing at a reasonable rate, not too often or too rarely).
Problem 3 · Explaining why the waterfall is only rendered on click, not eagerly for all 4 traces

Using database/read_replicas_and_dashboard_caching.html's reasoning, why does this dashboard render only the SELECTED trace's waterfall, rather than pre-rendering all 4 traces' waterfalls up front so clicking feels instant?

Show solution
This mirrors read_replicas_and_dashboard_caching.html's core argument almost exactly, just applied to rendering cost instead of query cost: eagerly computing/rendering every trace's FULL detail view (every span, every attribute, every waterfall bar) up front is wasted work for the (likely large majority of) traces a viewer never actually clicks into -- in a REAL system with potentially thousands of recent traces rather than this lab's 4, eagerly rendering every single one's full waterfall would be enormously wasteful compared to rendering only the lightweight list-view summary for all of them and deferring the expensive detail render to the moment (and ONLY the moment) a specific trace is actually selected. This is precisely section 1's two-level data shape argument, now extended to RENDERING cost specifically, not just data-fetching cost: the list view's per-row cost should stay cheap and roughly constant regardless of how many traces exist, while the detail view's (necessarily higher) cost is paid exactly once, exactly when needed -- the same "defer expensive work until it's actually asked for" principle underlying lazy evaluation (python/iterators_and_generators.html), short-TTL caching (this week's own database lab), and now this dashboard's own click-to-expand UI, applied at yet another layer of the same system.
Problem 4 · Comparing cap-7731f and cap-9013c's waterfalls as evidence of different retry-budget outcomes

Expand both cap-7731f and cap-9013c in section 2's dashboard. Using final_multi_agent_workflow.html's Problem 3 (bounded retry budget, abandon after exhausting it), explain precisely what structural difference between their two waterfalls reflects that design decision.

Show solution
cap-7731f's waterfall shows exactly ONE failed span (ord-129's first attempt) immediately followed by exactly ONE retry span that SUCCEEDS -- two spans total for that order, the second one green. cap-9013c's waterfall shows exactly TWO failed spans for ord-114 -- the first attempt AND the retry, BOTH red -- with no third span attempting a second retry. This directly reflects final_multi_agent_workflow.html's Problem 3 design: the retry budget is bounded at exactly one retry (attempt once, retry once, then stop), not unlimited retries until success. cap-9013c's waterfall is the concrete, visual proof that this bound is actually being respected in the instrumented agent's real behavior -- if the agent instead retried indefinitely, cap-9013c's waterfall would show THREE, FOUR, or more attempt spans for ord-114 before either succeeding or giving up, not exactly two. Seeing this bound directly IN THE TRACE DATA, rather than just trusting the code does what Problem 3's solution claimed, is exactly the value a real trace-viewing dashboard adds: instrument_month4_agent.html's Problem 5 extended the instrumentation code to handle this exact double-failure case by setting order.abandoned=True on the retry span rather than opening a third span -- and cap-9013c's waterfall, with precisely two red spans and no third attempt, is that same design decision made visible as a shape you can literally see rather than just reason about from code.
Problem 5 · Designing what "small" should mean for this dashboard as trace volume grows

This lab's dashboard hardcodes exactly 4 sample traces. If the real capstone agent ran thousands of times per day, what would need to change about the LIST view specifically (not the detail/waterfall view) to keep the dashboard usable, and which earlier lab's reasoning directly applies?

Show solution
Two changes, both directly reusing earlier labs' reasoning rather than inventing anything new: (1) Pagination/a bounded time window, not "list every trace ever." This is exactly database/time_series_schema.html's retention/access-pattern argument -- nobody scrolling a trace dashboard actually wants to see literally every trace since the agent's first deployment; they want "recent" traces, bounded to something like the last N or the last hour, with older traces still queryable on demand (e.g. by trace_id or a date filter) but not eagerly loaded into the default list view. (2) The list itself should be served from a source that can handle this volume without competing with production load -- directly database/ read_replicas_and_dashboard_caching.html's own subject: querying "recent traces, most recent first, with duration and status" is exactly the dashboard_aggregate query type that lab routed to a read replica, plus a short-TTL cache on top, since many viewers loading this SAME dashboard within a short window would otherwise trigger redundant identical "give me the last 50 traces" queries. At thousands of traces/day, this stops being an optional optimization and becomes load- bearing -- exactly the threshold read_replicas_and_dashboard_caching. html's section 1 opening analogy (a researcher tying up the register) was describing. What does NOT need to change: the detail/waterfall view's rendering approach (section 2's click-to-expand) stays exactly the same regardless of total trace volume, precisely because Problem 3 established it only ever renders ONE trace's detail at a time -- volume growth affects the LIST view's query cost, not the detail view's per-click rendering cost, which was already designed to be independent of how many traces exist in total.
