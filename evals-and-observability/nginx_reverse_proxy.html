EVALS & OBSERVABILITY LAB · NGINX REVERSE PROXY

One front door, doing the encryption handshake so your app servers never have to.

Nginx sitting in front of your application servers does two related but separable jobs: routing — deciding, based on path or host, which upstream server actually handles a request — and TLS termination — being the ONE place that speaks HTTPS to the outside world, decrypting each request before forwarding it as plain HTTP to whichever app server is behind it. This lab shows a real nginx config for both, and animates exactly where a request's encryption boundary sits.

Routing — path/host decides which upstream server
TLS termination — nginx is the only place that decrypts
Nginx → app server — plain HTTP, safe only on a trusted network

01 — One address the internet knows about, many servers behind it

Routing requests to the right upstream

Start here, before any config. Think about a hotel's front desk. Guests don't know or care which specific floor or wing their room is on — they walk up to ONE desk, say a room number, and the front desk staff (who know the building's actual layout) send them the right direction. The hotel could, in principle, hand every guest a building map and let them wander the halls looking for their room themselves — but centralizing that routing decision at one front desk is simpler, more consistent, and lets the hotel rearrange which rooms are on which floor without guests ever needing to know or care.

Nginx as a reverse proxy is exactly this front desk. It's the one address the outside world sends requests to, and based on the request's PATH or HOST header, it decides which upstream application server should actually handle it — forwarding the request there and relaying the response back to the client, who never needs to know or care how many app servers exist behind nginx, or which one actually answered. This connects directly to systems/load_balancers.html's routing concepts (nginx can itself distribute requests across MULTIPLE identical upstream servers, doing double duty as both a reverse proxy and a load balancer) and Month 2's routing concepts (deciding which handler serves a given path, just one layer earlier — before the request even reaches the application framework's own router).

# /etc/nginx/nginx.conf — routing by path to different upstream services upstream api_service { server 10.0.1.10:8000; server 10.0.1.11:8000; # two instances — nginx load-balances across both } upstream eval_dashboard_service { server 10.0.1.20:8001; } server { listen 80; server_name api.namespacelab.dev; # /api/* goes to the API service location /api/ { proxy_pass http://api_service; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; } # /dashboard/* goes to a completely different upstream service location /dashboard/ { proxy_pass http://eval_dashboard_service; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; } }

Two details worth being precise about. First: proxy_pass is the actual forwarding instruction — it's what makes nginx a REVERSE proxy specifically (a forward proxy sits in front of CLIENTS, hiding who's making a request; a reverse proxy sits in front of SERVERS, hiding which one actually answers — nginx here is doing the latter). Second: proxy_set_header X-Real-IP $remote_addr matters because once nginx is in the middle, the app server would otherwise only ever see connections coming FROM nginx's own IP address, losing the original client's IP entirely — this header explicitly preserves it, which matters for logging, rate limiting, and any per-client logic the app server needs to do.

Interview-ready definition: nginx as a reverse proxy sits in front of one or more application servers and forwards each incoming request to the appropriate upstream based on routing rules — commonly the request's path or host — using proxy_pass, while relaying the upstream's response back to the client. Clients only ever interact with nginx's single public address; which specific upstream server (or which of several identical replicas, doing double duty as a load balancer per systems/load_balancers.html) actually handled the request is invisible to them, exactly the way a hotel's front desk is the single point of contact regardless of which floor a guest's room is actually on.
02 — Why the encryption handshake happens in exactly one place

TLS termination, and why it's centralized

Start here, before the config. Think about a company with one mailroom that opens, scans, and sorts every piece of incoming physical mail before routing it internally as normal, unsealed office memos. Every employee could instead receive their OWN sealed, tamper-evident mail directly and open it themselves — technically more "end-to-end secure" in some abstract sense — but that means every single employee needs to know how to safely verify a sealed envelope, and doing that securely at scale (hundreds of employees, all needing to be trained and equipped to handle sealed mail correctly) is a much bigger operational burden than training ONE mailroom team to do it well, once, centrally.

TLS termination is nginx acting as that mailroom. Nginx holds the TLS certificate and private key, performs the full HTTPS handshake and decryption with the client, and then forwards the now-DECRYPTED request to the app server behind it as plain HTTP. The app server never sees an encrypted byte — by the time a request reaches it, nginx has already done the cryptographic work.

# /etc/nginx/nginx.conf — TLS termination, forwarding plain HTTP internally server { listen 443 ssl; server_name api.namespacelab.dev; ssl_certificate /etc/nginx/certs/api.namespacelab.dev.crt; ssl_certificate_key /etc/nginx/certs/api.namespacelab.dev.key; ssl_protocols TLSv1.2 TLSv1.3; location / { # note: plain http:// here, NOT https:// — nginx already decrypted # the request above; this hop to the app server is unencrypted proxy_pass http://api_service; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-Proto https; # tells the app "the original request WAS https" } } # separate server block: redirect any plain HTTP request to HTTPS server { listen 80; server_name api.namespacelab.dev; return 301 https://$host$request_uri; }

Why centralize TLS at nginx instead of having every app server terminate its own TLS connections? Two concrete reasons. First, certificate management: a real deployment might run many app server instances, possibly across several services — with TLS terminated centrally at nginx, there's exactly ONE place that holds the certificate and private key, one place to renew it, and one place to audit. Managing certificates on every individual app server instance instead multiplies that operational burden by however many instances exist, and makes rotating a compromised key or renewing an expiring certificate a much riskier, more error-prone, multi-machine operation. Second, CPU offload: the TLS handshake and per-request encryption/decryption is genuinely CPU-intensive work. Doing it once, at a layer (nginx) that's built and tuned specifically for this, frees the app servers to spend their CPU budget on actual application logic instead of cryptographic overhead.

Interview-ready definition: TLS termination means nginx (or an equivalent reverse proxy/load balancer) is the ONLY layer that holds the TLS certificate and private key and performs the HTTPS handshake with the client; once decrypted, the request is forwarded to the app server behind it as plain, unencrypted HTTP. This centralizes certificate management (one place to store, rotate, and renew certificates instead of one per app server instance) and offloads the CPU cost of encryption/decryption to a layer designed for it, letting app servers spend their CPU budget on application logic instead. This pattern is safe specifically because nginx and the app servers it forwards to sit on the same trusted internal network — the plaintext hop only ever travels somewhere an external attacker cannot observe.

The trust boundary this depends on: forwarding plain HTTP from nginx to the app server is safe ONLY because that hop stays entirely within a trusted internal network — a VPC, a private subnet, a container network an external attacker has no path onto. If nginx and the app server were instead communicating across the open internet, or across untrusted infrastructure, that plaintext hop would need its own encryption too (often via mutual TLS between nginx and each upstream) — this lab's simplification is a genuinely common, genuinely safe pattern, but only under that specific trusted-network assumption.

Problem 1 · Tracing what happens if X-Forwarded-Proto is forgotten

Section 2's config sets proxy_set_header X-Forwarded-Proto https. If this header were omitted, what would the app server incorrectly believe about the original request, and name one concrete way that could cause a bug.

Show solution
Without X-Forwarded-Proto, the app server has no direct way to know whether the ORIGINAL client request arrived over HTTPS or plain HTTP -- from the app server's own point of view, every request it receives looks identical: a plain HTTP connection from nginx's internal IP, regardless of what the original client actually used. Many web frameworks use exactly this header (or an equivalent) to decide whether to treat the current request as "secure" -- e.g. whether to set the Secure flag on cookies, or whether to redirect a request to HTTPS. Concrete bug: a framework that checks "is this request secure" by looking at its own connection's scheme (which is plain HTTP, since nginx forwarded it that way) would incorrectly conclude the ORIGINAL client connection was insecure, potentially causing it to issue cookies without the Secure flag (making them vulnerable to being sent over a future plain-HTTP connection) or to enter an infinite redirect loop -- the app server redirects "insecure" requests to https://..., the client's browser (which really did use HTTPS) follows the redirect, hits nginx again, gets forwarded to the app server as plain HTTP again, gets redirected again, forever. X-Forwarded-Proto exists specifically to prevent this exact class of bug by telling the app server the truth about the hop it can no longer see directly.
Problem 2 · Comparing nginx's routing role to load_balancers.html's load balancing role

Section 1's upstream api_service block lists TWO server IPs. Using systems/load_balancers.html's concepts, is nginx here acting as a reverse proxy, a load balancer, or both simultaneously? Justify precisely.

Show solution
Both, simultaneously -- and this is worth being precise about because the two roles are conceptually distinct even when the same piece of software (nginx) performs both. The REVERSE PROXY role is the routing decision -- "requests to /api/ go to the api_service upstream, requests to /dashboard/ go to a different upstream" -- deciding WHICH SERVICE handles a request based on path. The LOAD BALANCING role is what happens WITHIN that decision once a service is chosen -- section 1's api_service upstream lists two server IPs, and nginx distributes requests ACROSS those two identical replicas (by default, round-robin), exactly load_balancers.html's core concept: spreading load across multiple interchangeable instances of the same service. The two roles compose cleanly: reverse proxying picks the right SERVICE (dashboard vs api), and load balancing picks the right INSTANCE of that service once chosen. A deployment with only one instance per service would still need the reverse-proxy routing role, but would have nothing to load balance across -- confirming these are genuinely separable concerns that just happen to often be handled by the same nginx instance in a real deployment.
Problem 3 · Deciding whether a specific deployment can safely skip internal TLS

A team runs nginx and their app servers as separate containers on the SAME physical host, communicating over Docker's internal bridge network, never touching the open internet. Using section 3's trust-boundary callout, is section 2's plain-HTTP-after-termination pattern safe here? What would change your answer?

Show solution
Yes, this is a textbook case where section 2's pattern is safe, PROVIDED one additional assumption holds: nothing untrusted has a path onto that Docker bridge network. A container network on a single host is a reasonable example of the "trusted internal network" section 3's callout requires -- an external attacker on the open internet has no direct route onto that internal bridge network at all, so the plaintext nginx-to-app-server hop is never actually exposed to them. What WOULD change the answer: if any additional, less-trusted workload also runs on that same host and shares network access to that bridge network (e.g. a multi-tenant environment where other customers' containers, or even just other, less-audited internal services, could potentially reach that internal network segment) -- then "internal network" no longer implies "fully trusted," and the plaintext hop becomes a real exposure to anything else with access to that segment. This is exactly why real production deployments often still add mutual TLS between nginx and upstream services even on nominally "internal" networks in larger organizations -- the safety of section 2's pattern is a genuine assumption about the network's trust boundary, not a property that holds automatically just because traffic never crosses the public internet.
Problem 4 · Diagnosing a routing config that silently sends dashboard traffic to the API service

A team adds a new location /dashboard/ block to section 1's config, but places it AFTER a broader location / block that proxies everything to api_service. Requests to /dashboard/ unexpectedly reach the API service instead. Using how nginx evaluates location blocks, explain why.

Show solution
Nginx does not simply match location blocks in the order they appear in the file for prefix matches like these -- but the KEY fact that explains this specific bug is nginx's matching precedence: among prefix-match location blocks (the plain `location /path/ { }` form used throughout this lab, as opposed to regex or exact-match forms), nginx selects the LONGEST matching prefix, not the first one written in the file. So if the file genuinely has `location / { proxy_pass http://api_service; }` -- a prefix match of length 1 (just "/") -- and also `location /dashboard/ { proxy_pass http://eval_dashboard_service; }` -- a longer prefix match of length 11 -- the request "/dashboard/x" matches BOTH blocks' prefixes, and nginx correctly picks the LONGER, more specific one (/dashboard/) regardless of which block appears first in the file. Given that this bug is actually observed (dashboard traffic reaching api_service), the more likely real cause is that the `location /` block used a directive that short-circuits location matching entirely for that path space (e.g. a regex `location ~ ^/` matched earlier with higher effective precedence, or the /dashboard/ block has a typo in its path/trailing-slash that makes it not actually match /dashboard/ requests at all -- e.g. `location /dashboard { }` without the trailing slash behaves subtly differently for prefix matching than `location /dashboard/ { }`). The general debugging lesson: when nginx routing behaves unexpectedly, checking WHICH location block nginx actually selected (nginx's own debug logging can show this) is more reliable than reasoning about file order, since prefix-length precedence — not file order — is nginx's real matching rule for this location form.
Problem 5 · Extending the routing config for a WebSocket upgrade

Using backend/websockets.html's concept of a persistent, upgraded connection, what ADDITIONAL nginx directives (beyond section 1's plain proxy_pass) would a location /ws/ block need to correctly proxy a WebSocket connection, and why does a normal HTTP proxy config alone not suffice?

Show solution
A WebSocket connection begins as a normal HTTP request that then UPGRADES to a different protocol via the Upgrade and Connection headers (per backend/websockets.html's own handshake mechanics) -- and critically, once upgraded, the connection needs to stay OPEN and bidirectional for as long as the client stays connected, not be treated as a single request/response cycle the way normal HTTP proxying assumes. Section 1's plain proxy_pass config, by default, does NOT forward the Upgrade/Connection headers nginx itself receives -- it would silently strip them, causing the upgrade handshake to fail and the connection to never actually become a WebSocket at all. The additional directives needed: location /ws/ { proxy_pass http://api_service; proxy_http_version 1.1; # WebSocket requires HTTP/1.1 proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; proxy_read_timeout 3600s; # keep the connection open long-term } proxy_http_version 1.1 is required because WebSocket upgrades are not defined over HTTP/1.0. The Upgrade and Connection header forwarding is what actually lets the handshake complete instead of being silently stripped. And proxy_read_timeout needs to be raised from nginx's normal, much shorter default (meant for ordinary short-lived HTTP requests) to something that accommodates a connection meant to stay open for a long time -- otherwise nginx itself would forcibly close a perfectly healthy, long-lived WebSocket connection just because it looks like an unusually slow ordinary HTTP request. This connects directly to backend/chat_app_at_scale_design.html's concern about long-lived, stateful connections needing fundamentally different handling than typical request/response traffic -- nginx's default config assumes the latter, and needs these explicit overrides to correctly support the former.
