EVALS & OBSERVABILITY LAB · DETERMINISTIC EVALS

Before you ever need a judge, ask whether a rule could have answered it.

Month 4 built an agent whose final answer comes back as validated, structured JSON (final_multi_agent_workflow.html). Month 5 asks the next question: how do you actually check, systematically and repeatably, whether that output is CORRECT? The cheapest, fastest, most trustworthy category of check is a deterministic eval — a check with no randomness and no judgment call, that gives the exact same pass/fail result every single time on the same input. This lab covers the three deterministic check types and shows them running live against a real agent output.

Exact-match — the output equals a known string, byte for byte
Schema validation — the output's SHAPE is checked, not its exact content
Rule-based checks — a specific programmatic property must hold

01 — Three ways to check an answer without ever asking a model to judge it

Exact-match, schema validation, and rule-based checks

Start here, before any code. Think about grading a math worksheet versus grading an essay. For "what is 7 times 8," there's exactly one correct answer — you compare the student's answer to "56" and it's either right or wrong, no interpretation needed. For "does this shape look like a valid geometric proof," you're not checking one exact answer, you're checking that the STRUCTURE follows the required form (a hypothesis, then steps, then a conclusion) even though the specific wording varies. For "did the student show their work by writing at least 3 lines," you're checking one very specific, mechanically verifiable rule, independent of whether the final answer was even correct. All three are things a strict but literal-minded grading assistant could check without understanding math at all — that's exactly the posture a deterministic eval takes toward an agent's output.

Exact-match

Exact-match compares an agent's output to one specific, known-correct expected string, and passes only if they are identical (optionally after a narrow, explicitly-defined normalization step like trimming whitespace or lowercasing). It is the strictest, simplest, and least forgiving of the three checks.

# exact-match: output must equal the expected string exactly def exact_match(output: str, expected: str) -> bool: return output.strip() == expected.strip() exact_match("Paris", "Paris") # True exact_match("paris", "Paris") # False -- case mismatch, exact-match doesn't forgive this

Exact-match is the right tool only when there really is exactly one acceptable answer, expressed exactly one acceptable way — a capital city's name, a specific numeric ID, a fixed classification label from a closed set. It is the WRONG tool the moment there's more than one valid phrasing of a correct answer ("Paris, France" vs "Paris" would both be correct in a chat context, but exact-match against just "Paris" would fail the first).

Schema validation

Schema validation doesn't check the output's exact content at all — it checks that the output's SHAPE conforms to a JSON Schema: the right fields present, the right types, required fields not missing. This is precisely the discipline json_schema_tool_specs.html and final_multi_agent_workflow.html already established for tool call arguments and the agent's final structured answer — schema validation as an eval is that SAME check, now run as a scored test rather than as inline validation before returning a result to a caller.

// the Month 4 agent's final-answer schema, from final_multi_agent_workflow.html { "type": "object", "properties": { "orders_found": {"type": "integer", "minimum": 0}, "orders_summarized": { "type": "array", "items": { "type": "object", "properties": { "order_id": {"type": "string"}, "total": {"type": "number"}, "item_count": {"type": "integer"} }, "required": ["order_id", "total", "item_count"] } }, "orders_omitted": {"type": "array"} }, "required": ["orders_found", "orders_summarized", "orders_omitted"] }

A schema-validation eval doesn't care whether orders_found is 3 or 4 — it cares whether orders_found exists at all, is an integer, and is non-negative. This is deliberately a weaker, more permissive check than exact-match: it can't tell you the agent got the CONTENT right, only that the output is well-formed enough for a downstream system to consume it without crashing.

Rule-based checks

Rule-based checks apply one specific, programmatically-verifiable property to the output — not "does it equal X" and not "does it have the right shape," but "does it satisfy this particular predicate." Common examples: the output must contain a valid ISO-format date; the output must not exceed some token or character budget; the output must not contain a specific banned substring (an internal system prompt fragment leaking, for instance).

# rule-based: output must contain a valid ISO-8601 date import re def contains_iso_date(output: str) -> bool: return re.search(r"\d{4}-\d{2}-\d{2}", output) is not None # rule-based: output must not exceed N tokens (approximated by whitespace split) def within_token_budget(output: str, max_tokens: int) -> bool: return len(output.split()) <= max_tokens

Rule-based checks are the most FLEXIBLE of the three, because the "rule" can be almost anything expressible in code — but that flexibility means each rule is only as good as whoever wrote it thought to check. A rule-based check for "contains an ISO date" says nothing about whether that date is the CORRECT date.

Check typeWhat it verifiesWhat it can't catch
Exact-matchOutput is byte-identical to one known-correct stringAny semantically correct answer phrased differently
Schema validationOutput's structure/types conform to a JSON SchemaWhether the VALUES inside that correct structure are actually right
Rule-basedOne specific programmatic property holds (format, length, forbidden content)Anything the rule wasn't written to check — correctness beyond that one property
Interview-ready definition: a deterministic eval is a check that produces the exact same pass/fail result every time it's run against the same output, with no model call and no subjective judgment involved. Exact-match verifies literal string equality against one expected answer; schema validation verifies structural conformance (fields, types, required keys) to a JSON Schema without checking specific values; rule-based checks verify one explicit, programmatically-expressed property (a format, a length bound, a forbidden substring). All three trade flexibility for reliability — they can only ever check what they were explicitly written to check, but what they DO check, they check with total consistency and zero cost of ambiguity.
02 — From "here's the idea" to a real, runnable test

Writing deterministic eval checks

Start here, before the pytest file. An eval check isn't a philosophical distinction — it's ordinary code, usually wired into a test framework so it can run automatically, in CI, on every change to a prompt or model version. Here is a real pytest-style suite applying all three check types to one sample output from the Month 4 agent's capstone scenario.

# test_agent_deterministic_evals.py import json import re import pytest from jsonschema import validate, ValidationError # the agent's actual final answer for this test case AGENT_OUTPUT = { "period": "2026-07", "orders_found": 4, "orders_summarized": [ {"order_id": "ord-101", "total": 612, "item_count": 3} ], "orders_omitted": [] } FINAL_ANSWER_SCHEMA = { "type": "object", "properties": { "orders_found": {"type": "integer", "minimum": 0}, "orders_summarized": {"type": "array"}, "orders_omitted": {"type": "array"} }, "required": ["orders_found", "orders_summarized", "orders_omitted"] } def test_period_exact_match(): # deterministic: this task's period MUST be exactly "2026-07" -- no other phrasing is correct assert AGENT_OUTPUT["period"] == "2026-07" def test_final_answer_matches_schema(): # schema validation: raises ValidationError on any structural mismatch validate(instance=AGENT_OUTPUT, schema=FINAL_ANSWER_SCHEMA) def test_period_is_valid_iso_month(): # rule-based: the period field must be a valid YYYY-MM string assert re.fullmatch(r"\d{4}-\d{2}", AGENT_OUTPUT["period"]) def test_orders_found_matches_summarized_plus_omitted(): # rule-based: a specific INVARIANT the output must satisfy, not just a shape check total = len(AGENT_OUTPUT["orders_summarized"]) + len(AGENT_OUTPUT["orders_omitted"]) assert AGENT_OUTPUT["orders_found"] == total

Notice the last test: it isn't checking a fixed value or a schema shape at all — it's checking a RELATIONSHIP between three fields that must always hold if the agent's bookkeeping is internally consistent (orders_found should always equal the count of summarized plus omitted orders). This is exactly the kind of invariant a rule-based check is good at catching that neither exact-match nor schema validation would ever notice, since both fields individually pass their own checks even when the relationship between them is broken.

Interview-ready definition: writing a deterministic eval check means expressing a pass/fail condition as ordinary, runnable test code — typically a pytest function ending in an assert, or a schema-validation call that raises on mismatch — so the check can be run automatically and repeatably, the same way any other unit test would run in CI. The valuable checks go beyond superficial shape-matching to verify actual invariants the output must satisfy (like a count field matching the length of the list it's supposed to describe), because those catch classes of bugs that individual field-level checks, run in isolation, would each pass while the output as a whole is still wrong.

Problem 1 · Choosing the right check type for a stated requirement

An eval needs to verify that an agent's output for "what is the capital of France" is correct. A second eval needs to verify that a generated support-ticket summary is under 200 tokens. A third needs to verify that a generated JSON tool call has all required arguments. Match each to exact-match, rule-based, or schema validation, and justify each.

Show solution
"Capital of France" -- exact-match is the closest fit IF the eval normalizes for the small set of acceptable phrasings ("Paris", "Paris, France") ahead of time, since there is genuinely exactly one correct city, just with a few acceptable surface forms. If the system under test is a free-text chat response rather than a constrained single-word answer, a rule-based "output contains the substring Paris" check is often more robust in practice than strict exact-match, since it tolerates the answer being embedded in a full sentence. "Under 200 tokens" -- rule-based. This is precisely the token-budget example from section 1: a specific, programmatically verifiable property (length) that has nothing to do with matching a known string or a JSON structure. "JSON tool call has all required arguments" -- schema validation. This is exactly json_schema_tool_specs.html's discipline: checking that the generated call's arguments object has the right keys and types per its inputSchema, without caring what the SPECIFIC argument values are.
Problem 2 · Explaining why schema validation alone is insufficient

Using section 3's live demo, explain concretely why an agent output can pass schema validation and still be a completely wrong answer. What category of bug does schema validation structurally never catch?

Show solution
Schema validation only checks TYPES and PRESENCE of fields -- it never inspects whether the VALUES inside those correctly-typed fields are actually correct. An output like {"orders_found": 999, "orders_summarized": [], "orders_omitted": []} passes the schema from section 1 perfectly (orders_found is a non-negative integer, both arrays are present) while being wildly, obviously wrong -- claiming 999 orders were found while summarizing zero of them. Schema validation's entire job is structural conformance; correctness of CONTENT is a completely separate question that requires either a rule-based check targeting the specific invariant (section 3's count-invariant check) or, for anything schema/rule checks can't mechanically express, a model-graded eval (model_graded_evals.html) instead. The category of bug schema validation structurally never catches: any bug where the output is well-formed but semantically wrong -- wrong numbers, wrong facts, wrong reasoning -- because "well-formed" and "correct" are orthogonal properties a schema check was never designed to conflate.
Problem 3 · Writing a rule-based check for a new requirement

Write (in pseudocode or real Python) a rule-based check verifying that an agent's output never contains a system-prompt leak — specifically, that it never contains the literal substring "You are an AI assistant" (a common system-prompt opening). Why is this check a poor substitute for actually preventing the leak in the first place?

Show solution
def test_no_system_prompt_leak(output: str): assert "You are an AI assistant" not in output This is a legitimate rule-based check -- a specific, mechanically verifiable property (absence of a known substring). But it's a poor SUBSTITUTE for actually preventing leaks (via prompt design, output filtering before the eval even runs, or permission scoping over what content the model can see) for the same reason a rule-based check is inherently limited per section 1's table: it can only catch EXACTLY the substring it was written to check. A leak phrased even slightly differently ("As an AI assistant, you are..." or a leak of a DIFFERENT part of the system prompt entirely) sails right through this specific check untouched. This check is useful as ONE layer of defense-in-depth -- catching the exact known failure mode it targets, cheaply and reliably -- but treating it as sufficient protection against system prompt leaks in general would repeat the same mistake tool_call_sandboxing.html and permission_scoping.html warned against: a narrow, mechanical check is not a substitute for addressing the underlying cause, only a backstop for one specific known symptom of it.
Problem 4 · Diagnosing a flaky deterministic eval

A team's exact-match eval for a date field sometimes passes and sometimes fails against what looks like the same agent output, run twice. Since exact-match and schema validation are supposed to be perfectly deterministic (same input, same result, every time), what's the most likely explanation, and how would you debug it?

Show solution
The most likely explanation isn't that exact-match itself is nondeterministic -- string comparison is about as deterministic as code gets -- it's that the INPUT isn't actually identical between runs, even though it looks the same at a glance. Common concrete causes: (1) the underlying agent call itself is nondeterministic (temperature > 0, or any sampling), so the "same" prompt genuinely produces slightly different output text each time -- e.g. "2026-07-01" one run and "July 1, 2026" the next, both semantically identical but not byte-equal; (2) trailing whitespace, a stray newline, or invisible unicode characters differing between runs in a way that's invisible when eyeballing the two outputs side by side but fails a literal ==; (3) a timestamp or other non-deterministic field (like a request ID) accidentally included in what's being compared, when only the DATE field was meant to be checked. How to debug it: print or diff the two output strings' raw bytes/repr (not just their printed form) to catch invisible whitespace/unicode differences; check whether the agent call itself uses temperature=0 or some other deterministic decoding setting if bit-for-bit reproducibility of the AGENT'S output (not just the eval logic) is actually required; and narrow the exact-match comparison to ONLY the specific field being tested, not the full raw output, to rule out unrelated fields (like a timestamp) leaking into what's being compared. The eval mechanism itself being "deterministic" only guarantees the CHECK is repeatable given identical input -- it says nothing about whether the agent's own output generation is deterministic, which is usually the real source of apparent eval flakiness.
Problem 5 · Deciding when deterministic evals are NOT enough

A team wants to eval whether a generated customer-support response is "helpful and empathetic in tone." Explain concretely why none of exact-match, schema validation, or rule-based checks can meaningfully evaluate this, and what category of eval this task actually requires.

Show solution
Exact-match fails immediately -- there is no single correct string for "a helpful, empathetic response," since countless different phrasings could equally satisfy that quality. Schema validation is irrelevant -- the response is presumably free text with no meaningful JSON structure to validate in the first place, and even if it were structured, "empathetic tone" isn't a type or presence property any schema can express. Rule-based checks could approximate a few narrow SIGNALS (e.g. "does not contain a curt one-word reply," "is at least N words long," "does not contain an angry-sounding exclamation-heavy phrase") but none of these mechanically-checkable proxies actually verify the real underlying quality being asked about -- a response could satisfy every one of those rules while still reading as cold or dismissive, and a genuinely warm, well-judged response could technically violate one of the proxy rules (e.g. being shorter than the length threshold) while being exactly right. This is precisely the gap model_graded_evals.html exists to fill: "is this response helpful and empathetic" is a genuinely SUBJECTIVE quality judgment that's far easier to recognize than to specify as an exact rule -- exactly the condition under which having a separate LLM call score the output against a rubric becomes the right tool, in place of trying to force a fundamentally qualitative judgment through deterministic checks that were never designed to express it.
