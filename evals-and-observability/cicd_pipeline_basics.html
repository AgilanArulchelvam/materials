EVALS & OBSERVABILITY LAB · CI/CD PIPELINE BASICS

Fail on a typo in three seconds, not on a broken build ten minutes later.

A real CI/CD pipeline runs its stages in a deliberate order: lint first (fast, catches style/syntax issues), then test (runs the eval suite from pytest_evals_practice.html), then build (the multi-stage Docker image from multistage_docker_builds.html). This lab builds a real GitHub Actions-style pipeline config, and animates the exact reason this ordering exists: fail cheap and fast, before ever paying for anything expensive.

Lint — seconds, catches syntax/style before anything else runs
Test — the real eval suite, only runs if lint passed
Build — the multi-stage Docker image, only runs if tests passed

01 — Three stages, each one a real, runnable step

A real pipeline config, stage by stage

Start here, before the YAML. Think about a factory assembly line where the FIRST station is a five-second visual inspection (does this part even look right, before anything is machined into it), the SECOND station is a genuine stress test (does it actually hold weight, which takes a few minutes to run), and only the THIRD station does the expensive final assembly. A part that fails the five-second visual check gets pulled immediately — nobody wastes the stress-test machine's time, let alone the assembly station's, on a part that was visibly wrong from the start. A CI/CD pipeline is this same assembly line, applied to code.

# .github/workflows/ci.yml — three ordered stages, each depends on the last name: CI on: [pull_request] jobs: lint: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Run ruff (style + syntax) run: ruff check . - name: Run mypy (type checking) run: mypy app/ # ~5-15 seconds. Catches typos, unused imports, obvious type errors -- # none of this requires running any actual code. test: needs: lint # will NOT start unless lint succeeded runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Install dependencies run: pip install -r requirements.txt - name: Run the eval suite # exactly pytest_evals_practice.html's suite -- deterministic, # trajectory-based, and rubric checks, against the fixed fixture run: pytest tests/evals/ -v # ~1-3 minutes. Actually imports and runs code -- genuinely more # expensive than lint, but far cheaper than a full image build. build: needs: test # will NOT start unless test succeeded runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Build multi-stage Docker image # exactly multistage_docker_builds.html's two-stage Dockerfile -- # compiles dependencies, then produces the slim runtime image run: docker build -t namespacelab-api:${{ github.sha }} . - name: Push to registry run: docker push namespacelab-api:${{ github.sha }} # ~3-10 minutes. The single most expensive stage -- compiling # dependencies, assembling layers, pushing a real image over the network.

The needs: keyword is what actually enforces the ordering — test declares needs: lint, meaning GitHub Actions will not even START the test job unless the lint job completed successfully; build similarly needs: test. This isn't just a visual ordering in the YAML file — it's a hard dependency the CI runner enforces, so a lint failure genuinely, mechanically prevents the test and build stages from ever running at all, not just from being reported as "also failed."

Interview-ready definition: a CI/CD pipeline's lint/test/build stages are ordered as an explicit dependency chain (needs: in GitHub Actions syntax) rather than run independently in parallel, so that each stage only executes if every earlier, cheaper stage has already succeeded. Lint (style and syntax checks, no code execution) is cheapest and runs first; test (the real eval suite from pytest_evals_practice.html, actually importing and running code) is more expensive and runs second, gated on lint passing; build (compiling and assembling a real Docker image, per multistage_docker_builds.html) is the most expensive stage and runs last, gated on tests passing.
02 — The ordering isn't arbitrary — it's sorted by cost, cheapest first

Why this order: fail fast on cheap checks

Start here, before the reasoning. Think about a restaurant kitchen deciding whether to reject a delivery of ingredients. The FIRST check is a two-second visual glance — is the produce visibly rotten? That check costs almost nothing and catches the most obviously bad deliveries instantly. Only produce that PASSES the glance test gets the more expensive treatment — actually washing, prepping, and cooking with it. Nobody fully cooks a dish with visibly rotten produce just to discover during plating that it was bad — the cheap check happens first specifically so the expensive work never gets wasted on something that was already, visibly, disqualified.

This lab's three stages are sorted by exactly this cost ordering, and each stage catches a genuinely DIFFERENT class of problem that the earlier stage structurally cannot:

StageApproximate costWhat it catchesWhat it CANNOT catch
LintSecondsSyntax errors, style violations, obvious type errors — none of this requires running any code at allWhether the code actually WORKS — a perfectly-styled function with completely wrong logic passes lint cleanly
TestMinutesActual behavioral correctness — the eval suite genuinely runs the code and checks its outputs, per pytest_evals_practice.htmlWhether the code can be correctly PACKAGED and deployed — a test suite can pass while a Dockerfile is subtly broken
BuildMinutes (often the longest)Whether the application actually builds into a deployable artifact — dependency resolution, compilation, image assembly all genuinely happeningNothing "later" exists in this 3-stage pipeline — build is the last gate before an artifact would be ready to deploy

The financial argument for this ordering is concrete, not just aesthetic: if a broken PR has a simple typo (something lint would catch in 5 seconds) but the pipeline instead ran build FIRST (say, 8 minutes) before ever getting to lint, every single broken PR with a trivial typo would cost 8+ minutes of CI compute and wall-clock time before the contributor even learns their PR has a problem — multiplied across however many PRs a team submits per day. Running the cheapest, fastest-failing check FIRST means the overwhelming majority of "obviously broken" PRs get rejected in seconds, and the expensive stages (test, build) only ever run on PRs that have already cleared the cheap bar — genuinely saving both compute cost and, just as importantly, the CONTRIBUTOR's time waiting for feedback.

Cheap-first ordering (this lab's pipeline)

A PR with a typo fails in ~5-15 seconds, at lint. The contributor sees the failure almost immediately and fixes it without ever consuming test or build compute time. Only genuinely lint-clean PRs ever reach the more expensive test stage.

Reversed ordering (build first, hypothetically)

The SAME typo'd PR would sit through an 8-minute build first, THEN fail at a lint stage that could have caught it in seconds — wasting 8 minutes of compute and 8 minutes of the contributor's wait time on a PR that was disqualified from the very first character typed.

Interview-ready definition: ordering a CI/CD pipeline's stages from cheapest/fastest to most expensive — lint, then test, then build — and gating each stage on the previous one's success means an obviously broken PR is rejected as early and as cheaply as possible, rather than only being caught after the pipeline has already paid the cost of the more expensive later stages. This "fail fast" principle isn't about any one stage being more IMPORTANT than another — build failures matter just as much as lint failures — it's about SEQUENCING checks by cost so that expensive compute (and contributor wait time) is never spent validating something a cheap, earlier check would have already rejected.

Problem 1 · Deciding where a new "type check" step belongs

Section 1's lint job already runs both ruff (style) and mypy (type checking) in the SAME job. A teammate proposes splitting mypy into its own separate stage, positioned between lint and test. Using section 2's cost-ordering argument, is this a good idea? What would decide it either way?

Show solution
It depends entirely on mypy's ACTUAL relative cost and failure correlation compared to ruff, not on some fixed rule that "type checking deserves its own stage." If mypy runs in a comparable amount of time to ruff (both genuinely just seconds, neither requiring code execution) and PRs that fail mypy are similarly common to PRs that fail ruff, keeping them together in one "lint" stage is fine and arguably simpler -- section 2's cost-ordering argument cares about the RELATIVE cost between stages, and two checks of similar, small cost gain little from being split into separately-gated stages; splitting them just adds pipeline complexity (another job definition, another needs: dependency) without meaningfully improving fail-fast behavior, since both would already fail in roughly the same few seconds either way. The case FOR splitting would be if mypy were meaningfully slower than ruff in this specific codebase (e.g. a large, complex type-checked codebase where mypy genuinely takes 30-60+ seconds, versus ruff's near-instant style check) -- in that case, section 2's exact reasoning argues for running the CHEAPER check (ruff) first, on its own, so a pure style violation still fails in the fastest possible time, with mypy as a second, slightly more expensive gate before test. The decision criterion is the same one section 2 established generally: order stages (or sub-stages) by actual cost, and only split a combined stage into separate ones when there's a REAL cost difference worth sequencing around -- splitting two equally-cheap checks into separate stages for no reason just adds pipeline bookkeeping without buying any additional fail-fast benefit.
Problem 2 · Tracing what happens to the eval gate from cicd_gating_system_design.html within this pipeline

Using backend/cicd_gating_system_design.html's two-gate design (unit/integration tests, THEN a separate eval-threshold gate), where in section 1's test job would the eval-threshold check specifically belong, and should it be a separate job from pytest tests/evals/?

Show solution
The eval-threshold check belongs INSIDE the same test job, logically AFTER the pytest eval suite step, not as a wholly separate top-level job -- and the reasoning connects both labs precisely. cicd_gating_ system_design.html's section 1 code computed eval_result.pass_rate and compared it against EVAL_THRESHOLD as essentially the SAME step that runs the eval suite (run_eval_suite() returning a pass rate, checked immediately) -- the threshold check is really just an assertion made about the OUTPUT of the eval suite run, not a fundamentally separate kind of work requiring its own build environment, dependencies, or checkout step the way build (a genuinely different kind of work -- compiling a Docker image) does. Concretely, this lab's test job's pytest tests/evals/ -v step already produces the pass/fail signal per-test-case (pytest's own exit code reflects whether all assertions in the suite passed) -- if pytest_evals_practice.html's suite itself encodes the threshold logic as assertions (e.g. asserting the trajectory check's specific behavior directly, per that lab's actual tests), then the test job already IS the eval gate, with no additional job needed at all. If instead the threshold check needs to run as a SEPARATE aggregation step (say, computing pass rate across many individual eval results and comparing to a numeric threshold, closer to cicd_gating_system_design.html's literal code), it should still be an additional STEP within the SAME test job, immediately after the pytest step, rather than a new top-level job -- because it depends directly on that job's own output and doesn't need its own separate checkout/dependency-install overhead that a genuinely separate job (like build) would.
Problem 3 · Designing what should happen if lint and test could theoretically run in parallel instead

A teammate suggests running lint and test in PARALLEL (removing test's needs: lint) to make the pipeline finish faster overall, since most PRs pass both anyway. Evaluate this proposal against section 2's fail-fast argument specifically for the PRs that DON'T pass both.

Show solution
This proposal genuinely improves TOTAL wall-clock time for the common case (a healthy PR that passes both stages) -- running lint and test concurrently instead of sequentially means the healthy-PR pipeline finishes in roughly max(lint_time, test_time) instead of lint_time + test_time, a real speedup. But it directly undermines section 2's fail-fast argument for the LESS common but still important case: a PR with BOTH a lint error and a test failure (or even just a lint error alone) would now consume the FULL test-stage compute cost regardless, since test starts immediately in parallel rather than waiting to be gated on lint's result -- exactly the wasted-compute scenario section 2's dc-compare specifically argued against. The actual trade-off being made: parallelizing optimizes for the COMMON case (healthy PRs) at the direct cost of the fail-fast guarantee for the LESS common case (broken PRs) -- whether this is a good trade depends on the team's actual PR health rate and the relative cost of test compute. If test is cheap and PRs are rarely broken, the proposal is reasonable. If test is expensive (a large, slow eval suite) and lint failures are common (e.g. a team without a pre-commit hook enforcing style locally, so many PRs arrive with trivial lint issues), keeping the sequential needs: lint gate remains the better default, since it's specifically optimizing for minimizing WASTED compute on the PRs most likely to fail early anyway -- which is precisely section 2's whole argument, and a case where "faster in the average case" and "cheaper in the failure case" are genuinely in tension, not the same goal.
Problem 4 · Diagnosing a pipeline where build sometimes runs despite a test failure

A team's pipeline occasionally shows the build stage running even though the test stage's logs clearly show failing assertions. Using section 1's needs: mechanism, name the most likely misconfiguration causing this.

Show solution
The most likely cause: the test job's pytest step (or an equivalent command) isn't correctly propagating a non-zero exit code as the JOB's own failure signal -- e.g. a shell step that runs `pytest tests/evals/ || true` (deliberately swallowing pytest's failure exit code), or a step configured with continue-on-error: true in GitHub Actions syntax, which tells the runner "treat this step's failure as non-fatal to the job." In either case, the test JOB itself reports SUCCESS to GitHub Actions even though the actual pytest run, read by a human in the logs, clearly failed -- and because build's needs: test gate only checks whether the test JOB succeeded (not whether every individual step inside it "looked clean" to a human), build proceeds exactly as if tests had genuinely passed. This is a subtle but common real-world CI misconfiguration, and it's worth naming why it happens innocently: continue-on-error is a genuine, legitimate feature for steps that are ALLOWED to fail (e.g. an optional coverage-upload step that shouldn't block the whole pipeline if a third-party service is briefly down) -- the bug is applying that same flag to the actual eval-suite-running step, which should NEVER be allowed to fail silently. The fix: remove continue-on-error (or the `|| true` pattern) from the actual test-running step specifically, so pytest's real exit code correctly propagates as the job's own pass/ fail signal, restoring build's needs: test gate to actually mean what it's supposed to mean.
Problem 5 · Extending the pipeline with a deploy stage and connecting it to Week 3's earlier labs

Using backend/cicd_gating_system_design.html's blue-green rollout and multistage_docker_builds.html's image, sketch a FOURTH stage, deploy, that would follow this lab's build stage. What does it depend on, and what happens if it fails?

Show solution
deploy: needs: build # only runs if the multi-stage image (this lab's # build stage) was successfully built and pushed runs-on: ubuntu-latest steps: - name: Promote candidate build through the eval gate # exactly cicd_gating_system_design.html's second gate -- # runs the eval suite against THIS candidate image specifically, # separate from (and in addition to) this lab's own test stage run: run_eval_suite --image namespacelab-api:${{ github.sha }} - name: Blue-green cutover # cicd_gating_system_design.html's section 3 mechanism -- # flip the traffic pointer to the newly-built, newly-gated image run: flip_traffic_to namespacelab-api:${{ github.sha }} This deploy stage needs: build specifically (not test directly) because it depends on having an actual, pushed, deployable ARTIFACT to deploy -- the build stage is what produces that artifact; test alone (passing unit/eval tests against source code) doesn't guarantee a deployable image exists yet. Note this deploy stage's OWN internal eval-gate step is a genuinely SEPARATE check from this lab's test stage, even though both run "the eval suite" -- this lab's test stage validates the SOURCE CODE before spending build compute on it (section 2's fail-fast argument), while deploy's own gate, per cicd_gating_system_design.html, validates the actual BUILT CANDIDATE IMAGE specifically, catching any regression introduced during the build/packaging process itself that source-level testing couldn't see (e.g. a dependency version pinned differently in the built image than in the local test environment). If deploy fails -- either the eval gate blocking (per cicd_gating_ system_design.html's blocked-deploy scenario) or the blue-green cutover itself failing -- the PREVIOUS, already-deployed version remains live and fully serving traffic throughout, exactly that lab's core guarantee: because blue-green never tears down the old, known-good version until the new one has proven itself, a deploy-stage failure here costs nothing in terms of production availability, only the time spent building and gating the candidate that ultimately wasn't promoted.
