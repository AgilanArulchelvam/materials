01 — Middleware for what's universal, explicit calls for what isn't

Where instrumentation hooks go in the scaffold

Start here, before adding a single hook. Think about airport security versus a gate agent scanning your boarding pass. Security applies to EVERY passenger, uniformly, before they can go anywhere further into the airport — that's middleware: it wraps every request without any individual route needing to ask for it. The gate agent's scan is different — it's a specific, deliberate check that only makes sense at that one gate, for that one flight. A capstone's instrumentation needs both: request-level middleware for what's true of every request, and explicit calls inside the orchestrator for what's specific to an agent run's internal structure.

# app/observability/middleware.py -- fills the scaffold's second # empty slot (app/observability/), registered in create_app() right # after health.router, per the scaffold's "health first, then # everything else" ordering rule from fastapi import Request from uuid import uuid4 from app.observability.tracer import start_root_span, end_root_span async def tracing_middleware(request: Request, call_next): # UNIVERSAL, every request gets one: a trace_id, a root span, # and its duration -- exactly the shape opentelemetry_basics.html # and latency_and_tracing_integration.html already teach trace_id = request.headers.get("x-trace-id") or str(uuid4()) span = start_root_span(trace_id=trace_id, name=f"{request.method} {request.url.path}") request.state.trace_id = trace_id # orchestrator reads this below response = await call_next(request) end_root_span(span, status_code=response.status_code) response.headers["x-trace-id"] = trace_id return response # registered in create_app(): # app.middleware("http")(tracing_middleware)

Middleware handles the outer boundary — one root span per HTTP request, universally, with zero per-route code needed. But an orchestrated run isn't ONE operation, it's several (per mcp-and-agents/capstone_orchestrator_integration.html section 4's traced example: route, dispatch, dispatch, compose). Those sub-steps need EXPLICIT calls inside the orchestrator itself, because only the orchestrator knows when one agent turn ends and the next begins:

# app/orchestrator/run.py -- Orchestrator.step(), now instrumented. # Explicit child-span calls, nested under the root span middleware # already opened for this request. from app.observability.tracer import start_span, end_span from app.observability.evals import score_run class Orchestrator: async def step(self, run_id, user_message, trace_id): span = start_span(trace_id, parent_span_id=None, name="orchestrator.step") try: tool_name, tool_args = self._route(user_message, state) # one child span PER tool dispatch -- this is what lets the # dashboard's waterfall (section 4) show each tool call # as its own timed, attributable row, not one lump sum tool_span = start_span(trace_id, parent_span_id=span.id, name=f"tool.{tool_name}") tool_result = await self.mcp.call_tool(tool_name, tool_args) end_span(tool_span, attributes={"tool.name": tool_name}) reply = self._render_reply(tool_result) # the eval pass -- see section 2 -- runs as PART of the same # traced run, not a separate offline batch job eval_scores = await score_run(trace_id=trace_id, reply=reply, tool_result=tool_result) end_span(span, attributes={"eval.scores": eval_scores}) return reply except Exception as e: end_span(span, error=str(e)) raise
Interview-ready definition: instrumentation belongs in middleware for what's true of EVERY request regardless of what it does (a trace_id, a root span, overall duration and status), and in explicit calls at the point where a domain-specific boundary actually occurs (one child span per agent turn, one per tool dispatch) — because only the code at that boundary (the orchestrator, not generic middleware) knows where one meaningful unit of work ends and the next begins.
02 — trace_id, spans per step, and a score — never just one of the three

What gets recorded per run

Start here, before assuming "logging the response" is enough. Think about a flight's black box versus a passenger's memory of the flight. A passenger remembers roughly what happened — smooth, then some turbulence, then landed fine. A black box records EVERY instrument reading, continuously, whether or not anything went wrong, precisely because you don't know in advance which flight will need to be investigated. A capstone run needs the black-box version: recorded unconditionally, not only when something looks wrong.

RecordedSourceWhy it's not optional
trace_idGenerated by tracing_middleware, section 1The single key every other record — spans, eval scores — joins back to. Without it, spans and scores are orphaned, unlinkable rows.
Spans per agent turn / tool callExplicit start_span/end_span calls inside the orchestrator, section 1The list-view/detail-view split trace_dashboard_practice.html section 1 designed around requires REAL per-step timing data to populate the detail waterfall — a single "total duration" number can't be decomposed after the fact.
Eval scoresscore_run(...), called as part of the SAME traced step, section 1Per database/eval_results_schema.html's core argument: a score with no trace behind it is untrustworthy. Scoring inline, in the same span tree, keeps the score permanently attached to the exact run that produced it.

Recording all three UNCONDITIONALLY — for every run, not just runs that look interesting or runs that fail — is what makes the dashboard in section 4 show a representative picture rather than a survivorship-biased one. A dashboard that only records failed or slow runs can never answer "what does a NORMAL run look like," which trace_dashboard_practice.html's own sample set (2 OK, 1 slow-but-OK, 1 error) deliberately includes for exactly this reason.

Interview-ready definition: "full instrumentation" for an orchestrated run means recording a trace_id, a span per meaningful sub-step, and an eval score — for every run, unconditionally — not selectively logging only the runs that look noteworthy after the fact, because which runs turn out to matter is exactly the thing you can't know until you already have the data to check.
03 — This week's schema work is not a coincidence

How this data flows to the schema finalized this same week

Start here, before reaching for a second data store. It would be easy to bolt on a lightweight, separate store just for "dashboard data" — a small SQLite file, a JSON log, anything quick. This is exactly the trap database/eval_trace_schema_finalization.html already argued against for eval spans specifically: a second, ad hoc store for what is fundamentally the SAME data (trace_id-linked spans and scores) just means two systems to keep consistent, two query languages, and eventually one going stale relative to the other.

# app/observability/tracer.py -- writes to the SAME database # capstone_schema_finalization_and_indexes.html finalizes this week, # not a separate store async def end_span(span, attributes=None, error=None): span.ended_at = now() await db.execute( """INSERT INTO eval_span (span_id, trace_id, parent_span_id, span_name, started_at, ended_at, attributes) VALUES ($1, $2, $3, $4, $5, $6, $7)""", span.id, span.trace_id, span.parent_span_id, span.name, span.started_at, span.ended_at, json.dumps(attributes or {}), ) async def score_run(trace_id, reply, tool_result): scores = compute_eval_scores(reply, tool_result) # per eval_scenario_design.html await db.execute( """INSERT INTO eval_result (result_id, run_id, eval_type, score, passed, trace_id, evaluated_at) VALUES ($1, $2, $3, $4, $5, $6, $7)""", uuid4(), current_run_id.get(), "capstone_live", scores["overall"], scores["overall"] >= 0.7, trace_id, now(), ) return scores

This is the direct, load-bearing link between this lab and lab 5's schema work: eval_span and eval_result are the SAME tables database/eval_trace_schema_finalization.html designed and database/capstone_schema_finalization_and_indexes.html indexes and migrates this week — this lab's instrumentation is the CODE that writes into that schema at runtime, and lab 5's indexes (e.g. idx_eval_span_trace) are what make the dashboard's own queries (section 4, "load every span for this trace_id") fast rather than a full table scan.

What breaks if this rule is violated: the moment dashboard data lives somewhere other than eval_run/eval_result/eval_span, every query pattern lab 5 indexes for stops applying to it, every CI/CD eval gate cicd_eval_gating_survival_exercise.html built stops seeing it, and the capstone ends up with two silently diverging pictures of "how is this system actually performing" — exactly the failure mode a single source of truth schema is meant to prevent.

Practice problems

Problem 1 · A tool call that errors before a span closes

Section 1's orchestrator code wraps self.mcp.call_tool(...) in a child span, but if that call raises before end_span(tool_span, ...) runs, the span never gets an ended_at. What does this do to the dashboard, and how should the code be fixed?

Show solution
An eval_span row with started_at set but ended_at NULL (or never inserted at all, if the INSERT itself happens inside end_span) is either an invalid row against the schema's NOT NULL constraint on ended_at (lab 5's schema), causing the write itself to fail and the span to silently vanish from the trace entirely, or -- if the schema were laxly built to allow NULL -- a "hung" span the dashboard's waterfall can't compute a duration_ms for, since eval_trace_schema_finalization.html's duration_ms column is a GENERATED column computed from ended_at - started_at, which errors or returns NULL when ended_at is missing. Either way, that trace's waterfall is now incomplete or broken specifically for the failing tool call -- ironically the exact run most worth being able to debug. The fix is a try/finally around the span, not a bare try/except that might skip the end_span call on the error path: tool_span = start_span(trace_id, parent_span_id=span.id, name=f"tool.{tool_name}") try: tool_result = await self.mcp.call_tool(tool_name, tool_args) except Exception as e: end_span(tool_span, attributes={"tool.name": tool_name}, error=str(e)) raise else: end_span(tool_span, attributes={"tool.name": tool_name}) This guarantees every span that STARTS also ENDS, successfully or with an error attribute recorded -- exactly the same "the process must always record an outcome, success or failure, never silence" principle section 2 argues for at the level of whole runs, now applied at the level of one individual span.
Problem 2 · Should eval scoring block the response to the user?

Section 1's code calls await score_run(...) synchronously, inside the same request that returns a reply to the user. What's the trade-off, and is this the right call for a capstone-scale system?

Show solution
The trade-off is response latency versus data completeness. Scoring synchronously means the user's HTTP response doesn't return until compute_eval_scores() finishes -- if that involves an LLM-graded eval (per model_graded_evals.html, itself a real LLM call with its own latency), the user waits for BOTH the actual answer generation AND a separate scoring pass before getting a response, adding real, user-visible latency for something the user never asked for or benefits from directly. The alternative -- scoring asynchronously, e.g. publishing the (trace_id, reply, tool_result) tuple to a queue and letting a separate worker consume it and write the eval_result row afterward -- returns the reply to the user immediately and only delays when eval_result becomes visible in the dashboard, not the user-facing latency at all. For a capstone-SCALE system specifically (low request volume, no strict SLA), synchronous scoring is a reasonable, simpler default -- it avoids standing up a queue and worker for a request volume that doesn't need one, and the extra latency (typically a few hundred ms for a fast deterministic eval per deterministic_evals.html, more for a model-graded one) is tolerable. The asynchronous version becomes the right call once either request volume grows enough that added latency matters, or eval scoring specifically becomes the more expensive of the two paths (a heavyweight model-graded eval suite rather than a handful of deterministic checks) -- exactly the kind of scale-driven trade-off uvicorn_gunicorn_workers.html and the async job queue design already reason about for other expensive side-effects.
Problem 3 · Detecting a missing eval score for a completed run

Design a query against the schema from section 3 (eval_run, eval_result, eval_span) that finds every run with spans recorded but NO corresponding eval_result row — i.e. a run that executed but was never scored, violating section 2's "recorded unconditionally" rule. What would cause this in practice?

Show solution
The query is a LEFT JOIN from distinct trace_ids in eval_span out to eval_result, filtering for no match: SELECT DISTINCT es.trace_id FROM eval_span es LEFT JOIN eval_result er ON er.trace_id = es.trace_id WHERE er.trace_id IS NULL; This finds every trace_id that has span data (meaning the run actually executed, at least partially) but no eval_result row at all (meaning scoring never happened or never completed for it) -- a genuine "instrumentation gap" the dashboard's own health should be checked against periodically, not just used to monitor the CAPSTONE'S health. What causes this in practice, most plausibly given section 1's code: an exception raised INSIDE score_run() itself (a malformed compute_eval_scores() call, a DB write failure on the eval_result INSERT specifically) that isn't caught -- if end_span(span, ...) for the OUTER orchestrator.step() span runs in a try/finally per problem 1's fix but score_run()'s own failure isn't separately guarded, the outer span still closes (looking complete from a tracing perspective) while the eval_result row never gets written. The fix mirrors problem 1's: wrap score_run() in its own try/except that, on failure, still writes SOME eval_result row (even one explicitly marked eval_type= "scoring_failed") rather than leaving a silent gap that this recovery query is the only way to notice after the fact.
