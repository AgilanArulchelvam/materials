01 — What we're testing, and why it's fixtures, not live calls

Setting up the test file

Start here, before any test functions. final_multi_agent_workflow.html's capstone scenario is fully deterministic in its SHAPE even though the underlying agent call isn't: given the scenario ("find orders over $500 from last month, summarize them"), a fixed set of qualifying orders, and one deliberately injected failure on get_order_detail(order_id="ord-129"), we know exactly what a CORRECT run's trajectory and final answer should look like. That means we can write this suite against a captured trajectory + final answer FIXTURE — exactly the recorded, replayable record database/audit_trail_schema.html and this week's eval_results_schema.html both argued for — rather than needing a live, non-deterministic agent call inside every test run.

# test_capstone_agent_evals.py # Testing: mcp-and-agents/final_multi_agent_workflow.html's capstone scenario # "Find all orders over $500 from last month and summarize them." import re import pytest from jsonschema import validate # a captured trajectory from one real run -- the SAME shape # database/eval_results_schema.html's trace_id would point to CAPTURED_TRAJECTORY = [ {"tool": "query_orders", "args": {"start_date": "2026-07-01", "end_date": "2026-07-31", "min_total": 500}, "result": "success"}, {"tool": "get_order_detail", "args": {"order_id": "ord-101"}, "result": "success"}, {"tool": "get_order_detail", "args": {"order_id": "ord-114"}, "result": "success"}, {"tool": "get_order_detail", "args": {"order_id": "ord-129"}, "result": "error", "error_detail": "connection reset"}, {"tool": "get_order_detail", "args": {"order_id": "ord-129"}, "result": "success"}, # the retry {"tool": "get_order_detail", "args": {"order_id": "ord-137"}, "result": "success"}, ] # the agent's final structured answer for this run FINAL_ANSWER = { "period": "2026-07", "min_total": 500, "orders_found": 4, "orders_summarized": [ {"order_id": "ord-101", "total": 612, "item_count": 3}, {"order_id": "ord-114", "total": 780, "item_count": 2}, {"order_id": "ord-129", "total": 511, "item_count": 1}, {"order_id": "ord-137", "total": 945, "item_count": 4} ], "orders_omitted": [], "summary_text": "Found 4 orders over $500 from July 2026, totaling $2,848 across 10 items. All orders were successfully retrieved and summarized." }

Notice this trajectory and final answer are the EXACT scenario walked through interactively in final_multi_agent_workflow.html's section 3 stepper — same order IDs, same injected failure on ord-129, same successful retry. Building this suite against that specific, already-understood scenario means every assertion below can be checked against a run you can already picture step by step, rather than an abstract, unfamiliar example.

Interview-ready definition: a pytest eval suite for an agent is built against captured, fixed fixtures (a recorded trajectory and final answer) rather than live, non-deterministic agent calls inside the test itself — this keeps the SUITE deterministic and fast (no real model calls needed to run the tests routinely, e.g. in CI) while still testing exactly the scenario the agent needs to handle correctly. Live agent calls have their own place (periodic full end-to-end runs, captured as NEW fixtures to test against), but the day-to-day, every-commit test suite runs against recorded fixtures — the same "replay, don't require the original conditions" principle database/audit_trail_schema.html established for debugging, applied here to testing.

02 — First: does the final answer even have the right shape?

Deterministic checks on the final answer

Start with the cheapest, most reliable layer — exactly deterministic_evals.html's discipline, applied directly to FINAL_ANSWER:

FINAL_ANSWER_SCHEMA = { "type": "object", "properties": { "orders_found": {"type": "integer", "minimum": 0}, "orders_summarized": {"type": "array"}, "orders_omitted": {"type": "array"} }, "required": ["orders_found", "orders_summarized", "orders_omitted"] } def test_final_answer_matches_schema(): # schema validation -- structural correctness, per json_schema_tool_specs.html validate(instance=FINAL_ANSWER, schema=FINAL_ANSWER_SCHEMA) def test_period_is_correct(): # exact-match -- there is exactly one correct period for this scenario assert FINAL_ANSWER["period"] == "2026-07" def test_orders_found_matches_summarized_plus_omitted(): # rule-based invariant -- catches silent miscounting total = len(FINAL_ANSWER["orders_summarized"]) + len(FINAL_ANSWER["orders_omitted"]) assert FINAL_ANSWER["orders_found"] == total def test_no_order_summarized_and_omitted_at_once(): # rule-based invariant -- an order can't be BOTH successfully summarized # AND recorded as omitted -- these lists must be disjoint summarized_ids = {o["order_id"] for o in FINAL_ANSWER["orders_summarized"]} omitted_ids = {o["order_id"] for o in FINAL_ANSWER["orders_omitted"]} assert summarized_ids.isdisjoint(omitted_ids)

All four of these run in milliseconds, need no model call, and give identical results every time — exactly deterministic_evals.html's whole point. But notice what none of them check: whether ord-129's data in orders_summarized is actually GROUNDED in a real, successful tool call, versus fabricated after a failure. That's section 3's job.

03 — Second: did the agent actually recover, or did it fake it?

Trajectory check — did it actually recover?

This is the check trajectory_based_evals.html's entire lab built toward, applied concretely here: verify the retry documented in the Month 4 checkpoint actually happened in the trajectory, not just that the final numbers happen to look right.

def test_retried_after_injected_failure(): # the checkpoint requires: "agent completes a 3-step task end-to-end # with one deliberately injected tool failure, and recovers or fails # gracefully." This test verifies the RECOVERY actually happened. failed_calls = [ step for step in CAPTURED_TRAJECTORY if step["tool"] == "get_order_detail" and step["result"] == "error" ] assert len(failed_calls) == 1, "expected exactly one injected failure in this fixture" failed_order_id = failed_calls[0]["args"]["order_id"] # find the index of the failed call, then check for a SUBSEQUENT # successful call to the SAME tool with the SAME order_id -- a genuine retry fail_idx = CAPTURED_TRAJECTORY.index(failed_calls[0]) later_calls = CAPTURED_TRAJECTORY[fail_idx + 1:] retried = any( step["tool"] == "get_order_detail" and step["args"].get("order_id") == failed_order_id and step["result"] == "success" for step in later_calls ) assert retried, f"expected a successful retry for {failed_order_id} after its failure" def test_final_answer_reflects_the_recovered_order(): # cross-checking trajectory AGAINST the final answer -- the order that # failed-then-recovered should appear in orders_summarized, NOT orders_omitted summarized_ids = {o["order_id"] for o in FINAL_ANSWER["orders_summarized"]} assert "ord-129" in summarized_ids, "the recovered order should be summarized, not silently dropped"

The second test is worth pausing on: it deliberately checks the trajectory AND the final answer TOGETHER, verifying they're consistent with each other. This is exactly the class of bug trajectory_based_evals.html's Run B demonstrated — a final answer that LOOKS complete and correct in isolation, but whose data for one specific order has no genuine grounding in the trajectory that supposedly produced it.

Interview-ready definition: a trajectory check for a recovery scenario verifies the ACTUAL SEQUENCE of tool calls contains a genuine failure-then-retry pattern — not just that the final answer's numbers happen to be correct — by finding the failed call, then confirming a subsequent successful call to the same tool with the same arguments exists afterward. Cross-checking the trajectory against the final answer (the recovered order actually appears as summarized, not omitted or missing) catches the specific case where an agent's final output looks complete while the underlying process that should have produced it — the genuine retry — never actually happened.

04 — Third: is the human-readable summary actually usable?

A simple assertion-based quality rubric

The final piece: FINAL_ANSWER["summary_text"] is free text meant for a human reader, not just structured data for a downstream system. A full model-graded eval (model_graded_evals.html) would be the RIGHT tool for genuinely open-ended quality judgment — but for a lightweight Saturday practice suite, a simple assertion-based proxy rubric can catch the most obvious quality failures cheaply, without a judge call:

def test_summary_mentions_the_order_count(): # a minimal proxy rubric check: does the summary text actually state # the number that matters most, rather than being vague? assert str(FINAL_ANSWER["orders_found"]) in FINAL_ANSWER["summary_text"] def test_summary_is_not_suspiciously_short_or_empty(): # a length-floor proxy for "did the model actually say something" assert len(FINAL_ANSWER["summary_text"].split()) >= 10 def test_summary_does_not_silently_omit_a_known_failure(): # since this fixture's run had a failure that WAS recovered, the summary # should read as complete -- no hedging language suggesting a gap the # orders_omitted list doesn't also reflect hedge_phrases = ["could not retrieve", "unable to fetch", "partial results"] if not FINAL_ANSWER["orders_omitted"]: assert not any(phrase in FINAL_ANSWER["summary_text"].lower() for phrase in hedge_phrases), \ "summary hedges about missing data, but orders_omitted is empty -- inconsistent"

Notice the honest framing here: these are RULE-BASED checks wearing a "rubric" label, not a real model-graded eval — they're proxies for quality (mentions the key number, isn't suspiciously terse, doesn't contradict the structured data) rather than a genuine judgment of whether the prose actually reads well. That's a deliberate, appropriate choice for a lightweight practice suite: cheap, fast, zero judge-model cost, catching the most obvious quality regressions — while a REAL production eval suite for this agent would likely add an actual model-graded faithfulness/coherence check on top, per model_graded_evals.html, for the genuinely open-ended quality judgment these proxy rules can't capture.

A trap worth naming directly: calling these three checks a "rubric" is a slight abuse of terminology worth being honest about in an interview — they're deterministic rule-based checks (section 1's deterministic_evals.html category) being used AS A PROXY for quality, not a genuine model-graded rubric. If asked to distinguish them, the correct answer is: these checks are cheap and can catch some obvious regressions, but they cannot assess genuinely subjective quality (tone, clarity of PROSE beyond just containing the right number) the way an actual LLM-as-judge rubric could — see model_graded_evals.html for that layer.

Problem 1 · Writing a new test for a currently-untested requirement

Section 1's fixture asserts query_orders is called before any get_order_detail call — but no test in sections 2-4 actually checks this ordering. Write the pytest test for it, using section 3's index-based approach.

Show solution
def test_query_orders_precedes_detail_fetches(): # a real data dependency, per final_multi_agent_workflow.html section # 2's plan table: get_order_detail's order_ids come FROM query_orders' # result, so query_orders must appear first in the trajectory tools = [step["tool"] for step in CAPTURED_TRAJECTORY] query_idx = tools.index("query_orders") detail_indices = [i for i, t in enumerate(tools) if t == "get_order_detail"] assert all(i > query_idx for i in detail_indices), \ "every get_order_detail call must come after query_orders" This follows exactly the same shape as section 3's test_retried_after_injected_failure -- find a reference index, then assert a property about every OTHER relevant step's position relative to it. It belongs in section 3 (trajectory checks) rather than section 2, because it's checking the SEQUENCE/ordering of tool calls, not any property of the final answer's structure or content.
Problem 2 · Diagnosing which specific test would catch a specific regression

A code change accidentally causes the agent to retry a failed get_order_detail call THREE times before giving up, instead of the intended single bounded retry from loop_termination_logic.html. Would any test in sections 2-4 catch this regression? If not, write one that would.

Show solution
No existing test in sections 2-4 would catch this. test_retried_after_ injected_failure only checks that AT LEAST ONE successful retry exists after a failure -- it says nothing about how MANY attempts preceded that success, so 1 retry and 3 retries both satisfy it equally. None of the deterministic or rubric checks look at retry COUNT at all. A new test that would catch it: def test_retry_count_stays_within_bound(): # loop_termination_logic.html's retry budget: at most 1 retry per # call before either succeeding or moving to orders_omitted tools_and_args = [(s["tool"], s["args"].get("order_id")) for s in CAPTURED_TRAJECTORY] from collections import Counter call_counts = Counter(tools_and_args) for (tool, order_id), count in call_counts.items(): if tool == "get_order_detail": assert count <= 2, \ f"get_order_detail for {order_id} was attempted {count} times, expected at most 2 (1 initial + 1 retry)" This directly tests the loop_termination_logic.html per-call retry BUDGET, a genuinely different property from "did a retry eventually succeed" -- this is exactly the kind of gap Practice Problem 1's pattern (spotting an untested but real requirement) generalizes to: a suite that only checks "did recovery eventually happen" without also checking "was recovery bounded" would silently allow a retry-budget regression to ship undetected, even though the FINAL trajectory still technically contains a successful retry.
Problem 3 · Explaining why this suite tests against a fixture instead of a live agent call

A teammate suggests replacing CAPTURED_TRAJECTORY with an actual live call to the Month 4 agent inside each test, "so we're testing the real thing, not a fake." What's the strongest argument against this for the suite's DAY-TO-DAY use, and where would a live call still be appropriate?

Show solution
The strongest argument against it for day-to-day/CI use: a live agent call reintroduces exactly the non-determinism deterministic_evals.html and this lab's section 1 are both explicitly trying to keep OUT of the test suite itself. If each test run makes a real model call, the suite becomes flaky (different runs might get different trajectories due to the model's own sampling, per model_graded_evals.html's inconsistency failure mode applied to agent behavior generally, not just judges), slow (real model calls take real latency, multiplied across every test run on every commit), and costly (real API calls have real dollar cost, scaled by however many times CI runs the suite per day). A test suite that's flaky for reasons having nothing to do with an actual code regression trains engineers to ignore failures ("oh, it's probably just flaky again"), which defeats the entire purpose of having tests that gate deploys (per eval_results_schema.html's Problem 5 on CI/CD gating). Where a live call IS still appropriate: periodically (e.g. nightly, or specifically when the underlying model/agent version changes) running a SEPARATE process that makes real live agent calls against this same scenario, captures the RESULTING trajectory and final answer, and either (a) runs this exact test suite against that freshly-captured data as an integration-level check, or (b) if it's a known-good run, promotes it to become the NEW fixture data future unit-test runs use. This is exactly observability_pipeline_design.html's trace-capture pipeline doing double duty (per trajectory_based_evals.html's Problem 5) -- a live run's captured trace becomes tomorrow's fixture, keeping the fast, deterministic suite (this lab) and the slower, real-world-validating check (periodic live runs) as two distinct, complementary layers rather than collapsing them into one.
Problem 4 · Extending the suite to fail the whole run on a critical test

Using eval_results_schema.html's CI/CD gating discussion, which ONE test in this suite would you mark as a hard release-blocker if it fails, versus tests that could be "warn but don't block"? Justify your choice.

Show solution
test_retried_after_injected_failure (or its paired test_final_answer_reflects_the_recovered_order) is the strongest candidate for a hard release-blocker. This is because it's directly testing the Month 4 checkpoint's OWN stated bar -- "agent completes a 3-step task end-to-end with one deliberately injected tool failure, and recovers or fails gracefully" -- and a regression here means the agent is silently FABRICATING data instead of genuinely recovering, which is a correctness and trust failure far more severe than, say, test_summary_is_not_suspiciously_short_or_empty failing (a minor prose quality issue that's unpleasant but not actively misleading). Justification using severity: schema validation and the basic exact-match/invariant checks (section 2) catch structural bugs that would likely break DOWNSTREAM consumers outright (a missing field crashes a parser) -- also blocker-worthy, but for a different reason (broken integration, not silent wrongness). The rubric checks (section 4) are explicitly framed as cheap PROXIES, not authoritative quality judgments -- appropriate as "warn, investigate" signals rather than hard blockers, since a false positive (a fine summary that happens to trip a proxy rule) shouldn't block a release on its own. The trajectory fabrication check is the one whose failure means the agent is doing something actively DECEPTIVE -- producing confident, well-formed, plausible-looking output that has no basis in what actually happened -- which is exactly the class of failure a CI/CD gate (per eval_results_schema.html's Problem 5) exists to catch before it reaches production, where a human would have no easy way to detect it after the fact without exactly this kind of trajectory-level check already in place.
Problem 5 · Connecting this whole suite back to the Month 4 checkpoint, explicitly

Restate, in your own words, exactly how this 7-test suite operationalizes final_multi_agent_workflow.html's Month 4 checkpoint ("agent completes a 3-step task end-to-end with one deliberately injected tool failure, and recovers or fails gracefully") as an automated, repeatable check rather than a one-time manual narration.

Show solution
The Month 4 checkpoint, as originally written, asked for a HUMAN to narrate the scenario from memory, cold, in an interview-style setting -- valuable for internalizing the material, but not something that runs automatically or catches a REAL regression in the actual agent code later. This suite is that same checkpoint, translated into code that runs on every commit: "3-step task end-to-end" -> test_query_orders_precedes_detail_fetches (Problem 1) and the schema/invariant tests (section 2) together verify the task's basic SHAPE completed correctly -- query, fetch, synthesize, in the right order, with internally consistent output. "one deliberately injected tool failure" -> the CAPTURED_TRAJECTORY fixture itself encodes this exactly as final_multi_agent_workflow.html's own section 3 stepper does -- one get_order_detail call recorded with result="error". "recovers... gracefully" -> test_retried_after_injected_failure and test_final_answer_reflects_the_recovered_order (section 3) verify the recovery was GENUINE, not just that the final numbers happened to look right -- exactly the trajectory-vs-final-answer distinction this whole lab, and trajectory_based_evals.html before it, existed to make concrete. "...or fails gracefully" -> not directly tested by THIS suite's fixture (which represents the successful-recovery case), but per final_multi_agent_workflow.html's own Practice Problem 3, a parallel fixture representing the "retry also failed, order correctly placed in orders_omitted with a reason" case would need its OWN suite run against it -- this suite as built tests the recovery path; a complete Month 4 regression suite would need a second fixture and a parallel set of assertions for the graceful-failure path, which is a natural, concrete next extension of exactly this pattern. The overall shift: a one-time cold recall becomes a suite that runs on every future code change to this agent, catching a regression the moment it's introduced rather than relying on someone noticing it later in production, or re-deriving the checkpoint from memory being the only time this reasoning ever gets checked at all.
