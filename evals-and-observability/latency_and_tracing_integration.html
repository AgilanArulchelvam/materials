01 — The same trace tree, now with every span's duration as the actual measurement

Span-level vs request-level latency

Start here, before any code. Think about timing a relay race. You can time the WHOLE race, start gun to finish line — that's one number, useful for "did we win." But if you want to know WHY you lost, you need each runner's individual leg time — maybe three of your four runners ran a personal best, and the fourth runner's leg alone cost you the race. The whole-race time and the individual-leg times are both real, both useful, and answer genuinely different questions. Latency in a traced system works exactly the same way.

opentelemetry_basics.html already established that a trace is a tree of spans, each with its own start and end time. Latency measurement is just USING that timing data deliberately, at two different granularities:

GranularityWhat it measuresWhat it answers
Request-levelThe root span's own duration — end-to-end, from the moment the request entered the system to the moment a response left it"How long did the USER actually wait?" — the number that matters for a latency-based SLA or a user-facing p95 target
Span-levelEach individual child span's own duration — one specific unit of work inside the request"WHERE inside a slow request did the time actually go?" — the number that matters for diagnosing WHY the request-level number is high
# extending opentelemetry_basics.html's handle_request example -- # latency is just reading span.duration, which OTel already computes # as end_time - start_time for every span in the tree def handle_request(request): with tracer.start_as_current_span("handle_request") as root_span: with tracer.start_as_current_span("call_database") as db_span: orders = query_orders(request) # db_span.duration is now fixed -- e.g. 210ms with tracer.start_as_current_span("call_llm") as llm_span: summary = summarize(orders) # llm_span.duration is now fixed -- e.g. 480ms return summary # root_span.duration -- e.g. 940ms -- is the REQUEST-LEVEL latency. # db_span.duration and llm_span.duration are SPAN-LEVEL latencies -- # the SAME 940ms, broken down into where it was actually spent.

Nothing new needs to be built to get this — the timing data already exists on every span from the moment opentelemetry_basics.html's nesting model was set up; "latency measurement" is the discipline of actually READING and AGGREGATING that data deliberately, at both the request root (for an SLA/gate number) and per-span (for diagnosis), rather than only ever looking at the root span's duration and treating everything inside it as an opaque black box.

Interview-ready definition: request-level latency is the root span's own duration — how long the user actually waited, end to end — and is the number a latency SLA or a CI/CD gate threshold should be defined against. Span-level latency is each individual child span's own duration, already present in the same trace tree, and is what you read to diagnose WHERE inside a slow request the time went once request-level latency has already told you THAT something is slow. Both live in the exact same trace data structure opentelemetry_basics.html built — latency measurement adds no new instrumentation, it's a deliberate choice of which level of the existing tree to aggregate and alert on.
02 — The average is a summary that erases the exact requests you'd want to investigate

Why percentiles, not averages

Start here, before the math. Think about a restaurant's wait times. If 99 customers wait exactly 5 minutes and 1 customer waits 3 hours (a kitchen disaster on their order), the AVERAGE wait time comes out to about 7 minutes — a number that describes almost nobody's actual experience: the 99 who waited close to 5 minutes, and definitely not the 1 who waited 3 hours. Averages get pulled hard by outliers in one direction but SMOOTH them into invisibility in the reported number — exactly the opposite of what you want when the outlier IS the thing you need to catch.

A percentile instead answers "what's the latency BELOW WHICH X% of requests fall" — and unlike an average, it lets you deliberately choose to look at the TAIL, not the center:

PercentileMeaningWhy it matters
p50 (median)Half of requests are faster than this, half are slowerThe "typical" experience — resistant to outliers unlike a mean, since one 3-hour wait barely moves the median at all
p9595% of requests are faster than this; 5% are slowerThe standard "how bad does it get for a meaningful minority" number most latency SLAs are actually defined against
p9999% of requests are faster than this; only 1% are slowerThe deep tail — at real traffic volume (millions of requests/day), 1% is still thousands of genuinely bad experiences per day, invisible in p50 and often even in p95

Average — smooths the outlier away

99 requests at 200ms, 1 request at 8000ms. Average = (99×200 + 8000)/100 = 278ms. A dashboard showing "278ms average" looks fine — nobody investigating it would guess a request took 8 seconds.

p99 — surfaces exactly what the average hid

The SAME 100 requests, sorted: the 99th value (p99) is the 8000ms request itself. A dashboard showing "p99 = 8000ms" immediately tells you something is badly wrong for your worst-served requests, even while p50 stays a healthy 200ms.

The reason this matters more, not less, as a system scales: at low traffic, a single bad outlier might be a fluke. At real production volume — say a million requests a day — a 1% tail (p99) is ten thousand requests a day experiencing that bad latency, a real, systemic problem worth fixing, not statistical noise. A gate or alert defined only on the average would never surface this at all, because by construction the average is designed to smooth exactly this signal away.

Interview-ready definition: percentiles (p50/p95/p99) are preferred over averages for latency measurement because an average is pulled toward outliers in aggregate but never reveals them individually — a single catastrophic outlier gets diluted into a slightly-elevated mean that still looks acceptable, while a percentile lets you deliberately inspect the TAIL of the distribution (the worst-served 5% or 1%) directly. p50 describes the typical experience; p95 is the standard SLA/threshold number; p99 catches the deep tail that, at real production volume, represents a genuinely large absolute number of bad experiences per day even though it's a tiny percentage — exactly the signal an average is mathematically designed to smooth away.

Problem 1 · Computing p50, p95, and p99 by hand from a small dataset

Given these 20 request-level latencies in ms, sorted: 180, 190, 195, 200, 200, 205, 210, 210, 215, 220, 220, 225, 230, 235, 240, 250, 260, 300, 450, 1200 — compute p50, p95, and p99 using the "nearest-rank" method (index = ceil(percentile × N)).

Show solution
Nearest-rank method: for percentile P and N=20 values, index = ceil(P * N), then read the value at that 1-indexed position in the sorted list. p50: ceil(0.50 * 20) = ceil(10) = 10th value = 220ms p95: ceil(0.95 * 20) = ceil(19) = 19th value = 450ms p99: ceil(0.99 * 20) = ceil(19.8) = 20th value = 1200ms (With only 20 samples, p95 and p99 both land on values near the very top of the sorted list -- this is itself a real, important limitation: with small sample sizes, p99 in particular becomes highly sensitive to literally the single worst observation, which is why percentile estimates from small windows are noisy and why production systems typically compute percentiles over much larger sample counts, often using approximation algorithms like t-digest rather than exact sorting, to get a stable estimate.) For comparison, the mean of these 20 values is (180+190+195+200+200+205 +210+210+215+220+220+225+230+235+240+250+260+300+450+1200)/20 = 5035/20 = 251.75ms -- noticeably pulled up by the single 1200ms outlier, but still nowhere near revealing that a 1200ms request actually happened, exactly section 2's argument made concrete with real numbers: the mean (251.75ms) looks only mildly elevated, while p99 (1200ms) makes the actual worst case fully visible.
Problem 2 · Deciding which percentile a CI/CD gate should actually threshold on

Using section 2's reasoning, would you gate a deploy on p50, p95, or p99 latency — and what's the concrete risk of picking the wrong one?

Show solution
p95 is the standard, defensible default for a deploy gate, and the reasoning is a genuine trade-off between two failure modes, not an arbitrary convention. Gating on p50 is too LENIENT: a regression that specifically makes the slowest 10-20% of requests meaningfully worse (e.g. a new code path that's slow only when a particular cache misses) can leave the MEDIAN completely unchanged, since p50 by definition only reflects the middle of the distribution -- p50 could sail through a gate while a real, user-visible regression ships to a meaningful fraction of traffic. Gating on p99 is too NOISY, especially with the sample sizes a CI/CD eval run typically has available (per Problem 1's finding that p99 gets highly sensitive to individual worst-case observations at small N) -- p99 in a small eval run can swing wildly between runs of the exact SAME code just from a single unlucky slow sample, causing FLAKY gate failures unrelated to any actual regression, undermining trust in the gate. p95 sits at a genuinely useful middle point: sensitive enough to catch a regression affecting a meaningful minority of requests (unlike p50), but stable enough across a reasonably-sized eval run's sample count to avoid p99's flakiness. Many teams DO also track p99 for monitoring/alerting in production (where sample sizes are naturally much larger and the noise problem is smaller), even while using p95 specifically as the CI/CD gate threshold where eval-run sample sizes are typically much smaller.
Problem 3 · Diagnosing a slow request-level p95 using span-level data

A dashboard shows request-level p95 latency jumped from 900ms to 2400ms after a deploy. Using section 1's span-level/request-level distinction, describe the concrete next step to find WHERE the extra 1500ms went, and why request-level data alone can't answer this.

Show solution
Request-level latency alone (the root span's duration) is, by definition, a single aggregate number per request -- it can tell you THAT a request got slower, but has no internal structure to tell you WHERE inside that request the extra time occurred, because it was never broken down into parts in the first place. Answering "where" requires section 1's second granularity: pulling actual TRACES from around the p95-latency requests specifically (not just any traces -- the ones that are actually IN that slow tail) and reading their SPAN-level durations. Concrete next step: query the tracing backend for traces where the root span's duration falls at or above the new p95 threshold, open several of them, and compare each child span's duration against a baseline from BEFORE the deploy. If, say, call_llm's span duration jumped from 400ms to 1900ms specifically while call_database's span duration stayed flat at 200ms, that isolates the regression to whatever changed in the LLM call path during the deploy (a model version change, a prompt length increase, a provider-side slowdown) -- exactly opentelemetry_basics.html's core argument about WHY per-span attributes and nesting matter, now applied specifically to a latency regression instead of a correctness bug. Request-level data alone would have told you "something got 1500ms slower" and stopped there, with zero information about which of potentially many child spans caused it.
Problem 4 · Reasoning about percentile aggregation across services

A candidate proposes computing an overall p95 by averaging each individual service's own p95 (service A's p95 is 200ms, service B's p95 is 300ms, so overall p95 = 250ms). Explain precisely why this is mathematically wrong, using percentiles' actual definition from section 2.

Show solution
Percentiles are NOT linear -- you cannot average them the way you can average a mean, because averaging means literally sums values and divides, while a percentile is a positional statistic (a specific ranked VALUE within a sorted distribution, per Problem 1's nearest-rank method), and averaging two different distributions' RANKED VALUES does not produce the ranked value of their COMBINED distribution. Concretely: service A's p95 (200ms) is the specific 95th-percentile VALUE within service A's own request distribution; service B's p95 (300ms) is the 95th-percentile value within a DIFFERENT distribution entirely. Combining them into one number by simple averaging (250ms) produces a number that isn't the p95 of anything real -- it's not guaranteed to be the 95th-percentile value of A's requests, B's requests, or the two combined. The mathematically correct way to compute an overall p95 across two services: pool ALL individual request latencies from both services into one combined dataset (not the two pre-computed p95 values), sort THAT combined dataset, and compute the 95th percentile of the combined distribution directly -- which requires access to the raw per-request latency data, not just each service's already-summarized p95 number. This is exactly why raw span/trace data (section 1) needs to be RETAINED somewhere queryable, at least in aggregate histogram form, rather than only ever storing pre-computed percentile summaries -- pre-computed percentiles can't be correctly re-aggregated across services or time windows after the fact.
Problem 5 · Connecting latency measurement to the trace pipeline for a CI/CD gate

Sketch (in words) how a CI/CD pipeline stage would compute p95 latency for a candidate deploy using this lab's mechanics plus opentelemetry_basics.html's trace model, and name one thing that must be true about how traces are collected during the eval run for the p95 number to be trustworthy.

Show solution
The pipeline stage: run the full eval scenario set (eval_scenario_ design.html) against the candidate build, with tracing enabled so every scenario's execution produces a real trace (opentelemetry_basics.html's tree) with an accurate root-span duration. Collect every root span's duration across all N scenario runs into one array, sort it, and apply section 2's percentile computation (Problem 1's nearest-rank method, or a production-grade approximation like t-digest at larger N) to get p50/ p95/p99 for this candidate build specifically. Compare the resulting p95 against the configured threshold (per cicd_eval_gating_survival_exercise. html's gate logic) -- block the deploy if it's exceeded. One thing that must hold for this number to be trustworthy: the eval run's SAMPLE SIZE has to be large enough that p95 isn't dominated by noise the way Problem 1 showed p99 becomes at N=20. A scenario set of only 50 scenarios (eval_scenario_design.html's target) gives p95 a nearest-rank index of ceil(0.95*50) = 48 -- meaning p95 is essentially determined by just the 3rd-worst of 50 runs, which is a genuinely noisy estimate that could easily flip between two runs of literally identical code due to normal system jitter alone. A pipeline gating on p95 with this few samples either needs to (a) run each scenario multiple times and pool all the resulting latencies before computing the percentile, substantially increasing the effective N, or (b) accept p95 as a rougher signal at this sample size and pair it with a wider tolerance band or a requirement that a threshold be exceeded across multiple consecutive runs before actually blocking, to avoid a single noisy sample triggering a false block.
