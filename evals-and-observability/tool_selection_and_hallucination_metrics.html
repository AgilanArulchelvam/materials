01 — Not just "right or wrong" — precision, recall, and where each mistake actually happens

Tool-selection accuracy as precision/recall

Start here, before any formula. Think about a hospital triage nurse whose job is to route each incoming patient to the correct department — cardiology, orthopedics, or the ER. "Accuracy" alone (percent of patients sent to the right department) hides two very different kinds of mistake: sending a patient who NEEDED the ER somewhere else (a dangerous miss), versus sending a patient who didn't need the ER to the ER anyway (a wasteful over-caution). A single accuracy number can't tell you which of these is happening, or how often, or between which SPECIFIC pair of departments the confusion keeps occurring. Tool-selection measurement needs exactly this same finer-grained view.

Concretely: every scenario in a labeled eval set (per eval_scenario_design.html) has a known CORRECT tool (or correct sequence of tools). Running the agent against that scenario produces an ACTUAL tool call. Comparing actual against correct, per tool, gives you the standard classification quantities:

# For a given tool T, across all scenarios in the eval set: # True Positive (TP) -- agent correctly called T when T was the right tool # False Positive (FP) -- agent called T when a DIFFERENT tool was correct # False Negative (FN) -- agent did NOT call T when T was actually the right tool precision_T = TP / (TP + FP) # of all the times the agent called T, how often was T actually right? recall_T = TP / (TP + FN) # of all the times T was actually right, how often did the agent call it? # aggregate across every tool -- macro-average treats each tool equally, # regardless of how often it appears in the eval set macro_precision = mean(precision_T for T in all_tools) macro_recall = mean(recall_T for T in all_tools)

Precision and recall diverge specifically because they answer different questions about the SAME confusion. A tool with low precision but high recall is being OVER-called — the agent reaches for it too eagerly, catching every case it's actually needed for (high recall) but also firing it in cases where a different tool was correct (low precision, lots of false positives). A tool with high precision but low recall is being UNDER-called — every time the agent does call it, it's genuinely right (high precision), but it's missing many cases where it should have been called at all (low recall, lots of false negatives). These are opposite failure directions, and a single blended "accuracy" number averages them into invisibility.

Interview-ready definition: tool-selection accuracy is properly measured as per-tool precision (of every call to tool T, what fraction were actually correct) and recall (of every scenario where T was actually correct, what fraction did the agent actually call T for), not as one blended accuracy number — because precision and recall diverge in opposite directions (over-calling vs under-calling a specific tool) that a single number averages into invisibility. A confusion matrix goes one level further, showing exactly WHICH wrong tool gets substituted for which correct one, turning "the agent is 78% accurate at tool selection" into an actionable "the agent confuses lookup_order for get_history specifically, 3 times out of 21 legitimate get_history cases."
02 — Grounding a claim isn't the same as checking if it's plausible

Measuring hallucination rate

Start here, before any technique. Think about fact-checking a news article. A lazy fact-checker just asks "does this sentence SOUND true" — plausible-sounding claims sail through even when fabricated. A real fact-checker instead asks, for every factual claim in the article, "is there an actual SOURCE — an interview transcript, a document, a database record — that this claim can be traced back to?" A claim with no traceable source is flagged, regardless of how confident or fluent it sounds. Measuring hallucination rate in an agent's output requires exactly this second, harder discipline — grounding, not plausibility.

Two structurally different approaches, each with a real trade-off:

ApproachHow it worksTrade-off
Reference-based (grounding check)Extract discrete factual claims from the agent's output, then check each one against the actual retrieved context / tool results the agent had access to. A claim not traceable to any retrieved source is a hallucination.Precise and auditable — you can point to exactly which claim and why. Requires you to actually capture and keep the retrieved context alongside the output (exactly why audit_trail_schema.html's full-fidelity logging matters here).
Reference-free (self-consistency / judge)No ground-truth context is checked directly — instead, sample the model multiple times on the same input and measure how consistent the claims are across samples, or use an LLM judge to assess internal plausibility/consistency without a source document.Works even when no retrieved context exists to check against (e.g. the model reasoning from parametric knowledge). Structurally weaker: a model can be CONSISTENTLY wrong across every sample, and reference-free methods have no way to catch that — consistency is not the same thing as truth.

The reference-based approach is the one worth building first for any agent that retrieves or calls tools before answering, because it's exactly a claim-extraction-then-verification pipeline: (1) extract atomic factual claims from the response (usually via an LLM prompted specifically to decompose an answer into individually-checkable statements), (2) for each claim, search the retrieved context / tool outputs for supporting evidence, (3) mark the claim grounded, contradicted, or unsupported. Hallucination rate is then just the fraction of extracted claims marked unsupported or contradicted:

def hallucination_rate(claims, retrieved_context): unsupported = 0 for claim in claims: # grounded: does retrieved_context actually contain evidence for this claim? if not is_grounded(claim, retrieved_context): unsupported += 1 return unsupported / len(claims) # fraction of claims with no traceable source

The critical distinction this whole approach depends on: is_grounded is checking traceability, NOT plausibility. A claim can be perfectly plausible, even true in the real world, and still count as a hallucination for this specific measurement if the agent never actually retrieved evidence for it — because from the agent's own epistemic position, a plausible-sounding but ungrounded claim and a genuinely false one are indistinguishable failure modes: both mean the agent asserted something it didn't actually verify against what it had access to.

Interview-ready definition: hallucination rate measures the fraction of an agent's factual claims that aren't traceable to actual retrieved context or tool output — reference-based grounding checks extract atomic claims and verify each against the source material the agent actually had, marking a claim a hallucination if it's unsupported or contradicted regardless of whether it happens to be true in the real world, because the failure being measured is the agent asserting something without verification, not the world being wrong. Reference-free methods (self-consistency, LLM-judge plausibility) are a fallback for when no ground-truth context exists to check against, but structurally cannot catch a model being consistently, confidently wrong across every sample.

Problem 1 · Computing precision and recall by hand from a confusion matrix

Using section 1's confusion matrix (lookup_order: 18 correct, 3 false-positive rows where get_history was correct but lookup_order was called; get_history: 14 correct, 1 false positive, 2 false negatives where refund was miscalled for it; refund: 9 correct, 2 false negatives), compute precision and recall for get_history specifically.

Show solution
Reading the matrix precisely: the "Actual: get_history" row shows what happened to the 15 scenarios where get_history was genuinely correct -- 14 landed on the diagonal (correctly called get_history), and 1 landed in the "Predicted: lookup_order" column (a false negative for get_history, and simultaneously a false positive for lookup_order). The "Predicted: get_history" column shows every time the agent actually called get_history -- 14 from its own correct row, plus 3 from "Actual: lookup_order" row (agent wrongly called get_history when lookup_order was correct) and 2 from "Actual: refund" row (agent wrongly called get_history when refund was correct) = 14 + 3 + 2 = 19 total calls to get_history. TP (get_history) = 14 FP (get_history) = 3 + 2 = 5 (called get_history when something else was correct) FN (get_history) = 1 (get_history was correct but something else was called) precision_get_history = TP / (TP + FP) = 14 / (14 + 5) = 14/19 ≈ 0.737 recall_get_history = TP / (TP + FN) = 14 / (14 + 1) = 14/15 ≈ 0.933 Interpretation: get_history is called correctly the large majority of the time it's actually needed (93.3% recall -- rarely missed), but a meaningful fraction of ITS calls are actually mistaken substitutions for lookup_order or refund (73.7% precision -- over-called relative to how often it's truly correct). This is precisely the "high recall, lower precision = over-called" pattern section 1 described.
Problem 2 · Diagnosing why macro-average can hide a badly-performing rare tool

A team reports "macro-average tool-selection precision: 91%" across 5 tools. One of those tools, used in only 2 of 200 scenarios, has 0% precision (every call to it was wrong). Explain precisely how the macro-average can still land at 91%, and why this matters for a CI/CD gate.

Show solution
Macro-average, per section 1's formula, is the unweighted MEAN of each tool's OWN precision -- mean(precision_T for T in all_tools) -- treating every tool equally regardless of how often it actually appears in the eval set. If the other 4 tools each score close to 100% precision (they appear in the other 198 scenarios and are handled reliably), the macro-average is roughly (100 + 100 + 100 + 100 + 0) / 5 = 80%... but if those other 4 tools score, say, 98.75% each, (98.75*4 + 0) / 5 = 79% -- still visibly dragged down. For the number to land at a HIGH 91% despite one 0%-precision tool, the other four would need to average around 113.75%, which is impossible (precision caps at 100%) -- meaning a genuine 0%-precision tool, correctly macro-averaged, could NOT actually produce 91% with only 5 tools total. This is the tell: if a reported 91% macro-average coexists with a genuinely broken rare tool, either the "macro-average" label is wrong (it's actually a MICRO-average, weighted by frequency, where the rare tool's 2 failing calls are diluted into 198 correct ones from other tools and barely move the number at all), or the broken tool wasn't actually included in the average at all. Why this matters for a CI/CD gate specifically: a MICRO-averaged metric (or any metric that implicitly weights by frequency) can pass a gate threshold while a rare-but-critical tool -- imagine issue_refund used rarely but with real financial consequences when wrong -- is silently completely broken, because its failures are outnumbered and diluted by hundreds of correct calls to a common, easy tool like search. A gate that only checks an aggregate number, without also checking each individual tool's own precision/recall against its own threshold (exactly this lab's confusion-matrix per-tool breakdown), can let a genuinely dangerous regression through cleanly.
Problem 3 · Distinguishing a hallucination from an honest "I don't know"

An agent retrieves an order record with no listed delivery date and responds "I don't have a delivery date on file for this order." Using section 2's grounding definition, is this a hallucination? What if instead it responded "It should arrive within 3-5 business days" with no delivery estimate anywhere in the retrieved context?

Show solution
The first response is NOT a hallucination -- it makes no factual claim requiring grounding at all. "I don't have a delivery date on file" is a claim ABOUT THE AGENT'S OWN KNOWLEDGE STATE (that the retrieved context lacks this field), which is itself directly verifiable against the retrieved context (the delivery_date field is indeed absent or null) -- so it passes is_grounded trivially, and correctly so. This is actually the DESIRED behavior section 2 is measuring FOR: an agent that correctly recognizes and states the absence of grounding, rather than fabricating a plausible-sounding answer anyway. The second response IS a hallucination under section 2's definition, and precisely because of the plausibility trap the section warned about: "3-5 business days" is an extremely common, generic shipping estimate -- plausible-sounding, probably even statistically correct much of the time in the real world -- but it has zero support in the actual retrieved context for THIS specific order. claim_extraction would pull out "arrival within 3-5 business days" as an atomic claim, and is_grounded would correctly mark it unsupported, because no field in the retrieved order record actually said this. The claim being independently plausible or even often-true is explicitly irrelevant to this measurement -- section 2's whole point is that grounding checks traceability to the SPECIFIC context the agent had, not real-world plausibility.
Problem 4 · Deciding between reference-based and reference-free hallucination measurement

An agent answers general knowledge questions with no retrieval or tool calls involved at all (pure parametric-knowledge Q&A). Using section 2's table, which hallucination-measurement approach is even AVAILABLE here, and what's the concrete limitation you inherit by using it?

Show solution
Reference-based grounding is not available here at all -- section 2's approach fundamentally requires retrieved context or tool output to check claims AGAINST, and by the problem's own setup, there is none; the agent is answering purely from parametric knowledge with no retrieval step to capture and audit. This immediately forces the reference-free approach: sampling the model multiple times on the same question and measuring claim consistency across samples, or using an LLM judge to assess plausibility without a source document to check against. The concrete limitation inherited: section 2 explicitly named it -- reference-free methods cannot distinguish "consistently correct" from "consistently, confidently WRONG." If the model has a specific parametric misconception (say, a commonly-confused historical date or a plausible-sounding but incorrect technical fact it learned wrong during training), it will likely reproduce that SAME wrong answer across repeated samples with high consistency -- self-consistency measurement would score this as low-hallucination-risk (high agreement across samples) precisely because the model is uniformly, confidently wrong, which is the opposite of what you'd want the metric to report. The only way to actually catch this would be an external, independent ground truth (e.g. cross-checking against a trusted reference source), which is no longer "reference-free" at all -- it's really a reference-based check where the reference is a general knowledge base instead of retrieved-per-request context, an option worth considering as a real mitigation rather than accepting reference-free's blind spot as unavoidable.
Problem 5 · Setting per-tool thresholds vs one blended threshold for a CI/CD gate

Using Problem 2's reasoning, and knowing cicd_eval_gating_survival_exercise.html will need a concrete pass/fail rule, would you gate a deploy on ONE blended tool-selection accuracy threshold, or per-tool precision/recall thresholds? Justify using this lab's own confusion-matrix and macro-vs-micro-average reasoning.

Show solution
Per-tool thresholds, not one blended number -- directly following from Problem 2's demonstration that a single aggregate metric (whether macro- or micro-averaged) can pass comfortably while a specific, possibly high-consequence tool (issue_refund) is badly broken, simply because its failures are outnumbered or averaged away by other tools' successes. A gate that only checks one blended number inherits exactly that blind spot. The concrete gating rule this argues for: define a MINIMUM precision and recall threshold PER TOOL (not necessarily the same threshold for every tool -- a financially consequential tool like issue_refund might warrant a stricter threshold, e.g. 98% precision, than a low-stakes tool like search_knowledge_base, e.g. 85% precision is acceptable), and block the deploy if ANY individual tool's own precision or recall falls below ITS threshold -- not just if the blended average falls below a single bar. This is a direct generalization of database/eval_results_schema.html's own gating example (Q1's per-eval-type pass rate, not one overall pass rate) to tool-selection specifically: the principle in both cases is that an aggregate number is a useful SUMMARY for a dashboard, but a gating DECISION needs the finer-grained, per-category (per-tool, per- eval-type) breakdown, because that's the only view that can't hide one badly broken slice behind many healthy ones.
