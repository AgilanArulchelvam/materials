EVALS & OBSERVABILITY LAB · UVICORN & GUNICORN WORKERS

A sync worker holds a request hostage. An async worker just waits somewhere else for a moment.

Gunicorn's traditional sync workers handle exactly one request at a time — the process is BLOCKED, doing nothing else, for the entire duration of that request, so concurrency comes only from running many worker PROCESSES. Uvicorn workers (run via Gunicorn as a process manager, using Uvicorn's ASGI worker class) handle many concurrent requests inside a SINGLE worker process, using the asyncio event loop this month's Month 1 labs already covered. This lab shows the real Gunicorn commands for both, and works through the actual worker-count heuristics.

Sync workers — one request per process, blocking
Async (Uvicorn) workers — many requests per process, event loop
Worker count depends on CPU-bound vs I/O-bound, per Month 1's GIL labs

01 — One process handling one request at a time, versus one process juggling many

Sync vs async worker models

Start here, before any commands. Think about two different ways a single bank teller could handle customers. Model one: the teller helps ONE customer completely, start to finish — including the slow parts, like waiting for a manager's approval that takes several minutes — before even looking at the next person in line, no matter how long that approval takes. To serve more customers at once, the bank needs to open more TELLER WINDOWS, each staffed by its own teller. Model two: a single teller who, the moment they submit a request that needs a slow manager approval, immediately moves on to help the NEXT customer while that approval is pending, circling back to the first customer the instant their approval comes through. One teller, handling many customers' requests concurrently, by never sitting idle waiting on any single one.

Gunicorn's traditional sync workers are model one. Each sync worker process handles exactly one request at a time, completely blocked for that request's full duration — including any time spent waiting on a slow database query, an external API call, or anything else that isn't pure CPU work. To serve N requests concurrently, a sync-worker deployment needs roughly N separate WORKER PROCESSES, each one a full OS process with its own memory.

Uvicorn workers — Uvicorn's ASGI-compatible worker class, run under Gunicorn as the process manager — are model two, directly building on python/asyncio_fundamentals.html's exact event loop mechanics. A single Uvicorn worker process runs one asyncio event loop, and when a request handler hits an await (a database query, an HTTP call to another service, anything I/O-bound), the event loop doesn't block — it suspends that specific request's coroutine and moves on to service other requests' coroutines that are ready to make progress, coming back to the suspended one once its I/O completes. One process, genuinely handling many concurrent in-flight requests, exactly the way asyncio_fundamentals.html's event loop juggled many coroutines on one thread.

# SYNC workers — Gunicorn's default worker class, no event loop involved # each of these 5 processes can only ever be doing ONE request at a time gunicorn app.main:app --workers 5 --worker-class sync --bind 0.0.0.0:8000 # ASYNC (Uvicorn) workers — Gunicorn manages the PROCESSES, # Uvicorn's worker class runs an asyncio event loop INSIDE each one gunicorn app.main:app --workers 4 --worker-class uvicorn.workers.UvicornWorker --bind 0.0.0.0:8000

Sync worker

One request per process, full stop, for the request's entire duration — even the parts spent waiting on I/O with nothing to do. Concurrency = number of worker PROCESSES. Simple to reason about; a slow request only blocks that one process, not others. But scaling concurrency means spawning more OS processes, each with real memory overhead.

Async (Uvicorn) worker

Many requests per process, interleaved on one asyncio event loop — a request awaiting I/O yields the loop to other pending work instead of blocking it. Concurrency = however many coroutines the event loop can juggle, which for I/O-bound work is often far more than one process could serve under the sync model. But a CPU-bound handler that never awaits blocks the ENTIRE event loop — every other in-flight request in that process stalls too, exactly python/the_gil.html's warning about CPU-bound work starving an event loop.

Interview-ready definition: a sync worker (Gunicorn's traditional model) handles exactly one request per worker process for that request's full duration, including idle time spent waiting on I/O, so achieving concurrency requires running many separate worker processes. An async worker (Uvicorn, run under Gunicorn as the process manager) runs an asyncio event loop inside a single process and handles many requests concurrently by suspending a request's coroutine at each await point and resuming other ready coroutines in the meantime — directly reusing python/asyncio_fundamentals.html's cooperative-scheduling model, now applied at the level of an entire web server's request-handling, not just a single script's coroutines.
02 — The heuristic differs because the two models scale concurrency completely differently

How many workers to run

Start here, before the formula. Back at the bank: the "many teller windows" model (sync) genuinely needs roughly one window per customer being served at once — the number of windows IS the concurrency limit, so the bank sizes it around how many CPUs (tellers) it actually has available to keep busy. The "one multitasking teller" model (async) doesn't need nearly as many tellers, because ONE teller juggling many pending approvals can serve far more customers concurrently than one teller ever could under the first model — adding a second multitasking teller helps mainly for using a SECOND CPU core, not for handling more concurrent waiting.

For sync workers, the common heuristic, straight from Gunicorn's own documentation, is (2 × number_of_cpu_cores) + 1. The reasoning: since each sync worker blocks completely during I/O wait time (not just CPU time), having somewhat MORE workers than CPU cores lets the OS schedule a different worker onto a core while one worker is blocked on I/O rather than actually computing — squeezing a bit of extra overlap out of I/O-bound blocking time, without so many workers that they mostly just contend for the same limited CPU cores. This directly reuses python/the_gil.html's distinction: sync workers scale like separate OS PROCESSES (each with its own Python interpreter, its own GIL, genuinely running in parallel across cores) — the same reasoning that lab gave for why CPU-bound work benefits from multiprocessing over threading.

# sync worker count heuristic: (2 x CPU cores) + 1 # example: a 4-core machine gunicorn app.main:app --workers 9 --worker-class sync # (2 * 4) + 1 = 9

For async (Uvicorn) workers, fewer are usually needed, because a SINGLE worker's event loop can already hold many concurrent I/O-bound requests in flight — the ceiling isn't "one worker per concurrent request" the way sync workers are. A common starting heuristic instead ties worker count to CPU core count directly (often just number_of_cpu_cores, sometimes (2 × cores) + 1 as an upper bound), because each Uvicorn worker is still bound by Python's GIL — one process, one interpreter, and CPU-bound work inside that process still can't run in true parallel across multiple cores within a SINGLE worker. Running one Uvicorn worker per CPU core is what actually gets you real, GIL-bypassing parallelism, exactly python/the_gil.html's multiprocessing argument, while EACH of those per-core workers separately handles high I/O-bound concurrency via its own event loop.

# async worker count heuristic: closer to CPU core count directly # example: same 4-core machine, I/O-bound workload (typical API) gunicorn app.main:app --workers 4 --worker-class uvicorn.workers.UvicornWorker # each of these 4 processes independently handles many concurrent # in-flight requests via its own event loop -- concurrency comes from # the event loop, not from spawning more processes

The deciding factor in both cases is exactly python/the_gil.html's CPU-bound vs I/O-bound split. A workload that's mostly I/O-bound (waiting on a database, waiting on an external LLM API call, waiting on another microservice) benefits enormously from the async model's ability to overlap many waits within one process — this is the common case for a typical backend API. A workload that's genuinely CPU-bound (heavy in-process computation, like image processing or numeric work with no I/O in between) gets comparatively little benefit from more concurrency within one event loop, since a CPU-bound handler blocks the WHOLE loop while it runs — for that workload, more PROCESSES (via multiprocessing, or simply more Uvicorn workers up to the core count) is what actually helps, not a more clever single-process concurrency model.

Interview-ready definition: the sync-worker heuristic (2 × CPU cores) + 1 sizes worker count around overlapping I/O-blocked processes with CPU-available ones, since each sync worker fully blocks during I/O wait. The async-worker heuristic ties worker count closer to CPU core count directly, since a single Uvicorn worker's event loop already provides high I/O concurrency within one process — adding more workers beyond the core count mainly helps CPU-bound work escape the GIL's single-process limitation (per python/the_gil.html), not I/O-bound concurrency, which the event loop already handles. The right number in either case is ultimately a function of whether the workload is I/O-bound (favors fewer, async workers) or CPU-bound (favors more processes, sync or otherwise), not a single universal formula.

Problem 1 · Applying the sync heuristic to a specific machine

A production server has 8 CPU cores. Using section 2's sync-worker heuristic, how many sync workers should it run, and why does the formula add "+1" rather than using exactly 2 × cores?

Show solution
(2 * 8) + 1 = 17 sync workers. The "+1" is a small, deliberate buffer beyond the doubled-core count -- with exactly 2x cores worth of workers, every core could in principle be fully saturated by CPU-bound work from two workers simultaneously scheduled on it, leaving zero slack for the brief moments when a currently-scheduled worker's request needs the CPU to, say, serialize a response, while another I/O-blocked worker becomes ready to run at the exact same instant. The extra +1 worker gives the OS scheduler one additional worker to slot in during exactly that kind of brief overlap, without meaningfully changing the total worker count's memory or resource cost. It is a small empirical safety margin from Gunicorn's own documented guidance, not a value derived from a precise mathematical argument -- the core insight (roughly double the CPU count, to overlap I/O-blocked workers with CPU-available ones) is what matters more than the exact "+1".
Problem 2 · Diagnosing a CPU-bound handler accidentally deployed with async workers

A team deploys a genuinely CPU-heavy endpoint (parsing and transforming a large file, no I/O at all) behind 4 Uvicorn workers. Under load, they observe that ALL requests to that endpoint — even ones that arrived seconds apart — seem to complete in a tight cluster, one after another, rather than overlapping at all. Using section 1's event loop model, explain why.

Show solution
A CPU-bound handler with no await points inside it never yields control back to the event loop -- per section 1's core mechanic, the event loop only gets a chance to switch to a DIFFERENT pending coroutine at an await point; a synchronous, CPU-heavy block of code running inside an async handler runs to completion on that ONE process's single thread before the event loop can service anything else AT ALL, including requests that arrived and were technically "waiting" the entire time. So within any ONE of the 4 Uvicorn workers, if multiple CPU-heavy requests land on it, they execute strictly SEQUENTIALLY, one fully blocking the event loop before the next can even start being processed -- exactly the "tight cluster, one after another" behavior observed, even though from the outside it looks like these 4 processes should provide real concurrency. The fix isn't more Uvicorn workers (that mainly helps I/O-bound work, per section 2) -- it's either moving the CPU-heavy work to a separate process pool (e.g. via asyncio.to_thread or a background worker queue, keeping the event loop itself free to keep servicing other requests) or, if the entire endpoint really is CPU-bound with no I/O to overlap, reconsidering whether sync workers (section 1's dc-compare) or a dedicated multiprocessing-based worker pool is actually the better fit for that SPECIFIC endpoint's workload, even if the rest of the API is genuinely I/O-bound and well-served by the async model.
Problem 3 · Choosing worker counts for a mixed I/O-bound and CPU-bound service

A service has two kinds of endpoints on the same deployment: most are typical I/O-bound API calls (DB reads, external calls), but one specific endpoint does meaningful CPU-bound image processing. Using section 2's reasoning, propose an architecture — not just a worker count — that serves both well.

Show solution
A single worker-count choice can't actually serve both workload shapes well at once -- this is precisely why the right answer is architectural separation, not a compromise number. Run the typical I/O-bound endpoints behind Uvicorn (async) workers, sized near the CPU core count per section 2's I/O-bound heuristic, getting the high I/O concurrency this workload benefits from. For the CPU-bound image processing endpoint specifically, offload that work OUT of the async event loop entirely -- either to a separate process pool (asyncio.to_thread or multiprocessing, keeping the CPU-heavy work off the shared event loop so it doesn't stall unrelated I/O-bound requests, directly avoiding Problem 2's exact bug) or, more robustly at scale, to an entirely separate background job queue/worker fleet (per backend/async_tool_job_queue_design.html's pattern) that the API endpoint enqueues work to and returns a job ID from, rather than processing the image synchronously within the request/response cycle at all. The general principle this illustrates: worker-count heuristics (section 2) answer "how many workers for a GIVEN, roughly uniform workload shape" -- they don't resolve the deeper problem of mixing fundamentally different workload shapes (I/O-bound vs CPU-bound) behind the SAME worker pool. A service with genuinely mixed workloads is usually better served by separating them into different deployments or offloading the CPU-heavy piece elsewhere than by picking one worker count and hoping it works reasonably for both.
Problem 4 · Reasoning about what a crashed sync worker versus a crashed async worker takes down

If one sync worker process crashes mid-request, how many in-flight requests are lost? If one Uvicorn (async) worker process crashes mid-request, how many in-flight requests are lost? Explain the difference using each model's concurrency mechanism.

Show solution
A crashed sync worker loses exactly ONE in-flight request -- per section 1's model, a sync worker was only ever handling one request at the moment it crashed, so exactly that one request fails (typically with a connection reset the client sees), while every OTHER sync worker process is completely unaffected, since each is a fully independent OS process with no shared state. A crashed Uvicorn (async) worker loses potentially MANY in-flight requests at once -- however many coroutines that worker's single event loop happened to be juggling concurrently at the moment of the crash (per section 3's demo, this could be several requests all suspended mid-await simultaneously within one process). This is a real, concrete trade-off of the async model's efficiency: packing many concurrent requests into one process means a single process failure has a larger blast radius than the sync model's "one process, one request" isolation. This is one reason a production async deployment still runs MULTIPLE Uvicorn worker processes (section 2's count ≈ CPU cores) rather than just one -- not only for using multiple CPU cores, but also so a single worker crash doesn't take down every single in-flight request across the entire service at once, only the subset that happened to be on that one worker.
Problem 5 · Connecting worker count to nginx's upstream config

Using evals-and-observability/nginx_reverse_proxy.html's upstream block, which listed 2 separate app server IPs, how does that relate to THIS lab's worker-count decision — are those 2 upstream entries the same thing as 2 Gunicorn workers, or a different layer of scaling entirely?

Show solution
Different, complementary layer of scaling -- worth being precise about the distinction. nginx_reverse_proxy.html's upstream block lists 2 separate MACHINES (or containers) -- 10.0.1.10:8000 and 10.0.1.11:8000 -- each one an entirely separate host running its OWN Gunicorn process (or process manager), which in turn runs its OWN set of workers sized per THIS lab's section 2 heuristics. So the real picture is nested: nginx load-balances across N separate app server INSTANCES (horizontal scaling across machines, per systems/vertical_vs_horizontal_scaling. html), and each of those N instances independently runs however many Gunicorn workers section 2's heuristic recommends for ITS OWN CPU core count. Total request-handling capacity is therefore roughly (number of upstream instances) x (workers per instance), not just one number or the other. This also means the TWO layers get scaled for different reasons and by different mechanisms: adding more upstream instances in nginx's config is how you scale ACROSS machines (more total CPU cores available system-wide, plus redundancy if one whole instance goes down), while tuning the worker count WITHIN one instance (this lab's whole subject) is how you make the BEST use of the cores that single machine already has. Getting one right without the other leaves capacity on the table either way -- e.g. 2 well-tuned app server instances each criminally under-provisioned on workers still underperforms relative to those same 2 instances correctly sized per section 2's heuristics.
