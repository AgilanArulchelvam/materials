01 — The path an agent took is itself evidence, not a discardable detail

Scoring the sequence of steps, not just the final answer

Start here, before any code. Think about a student who gets the right final answer on a math problem, but their work shows they skipped the step where they were supposed to check their answer against the original constraints — maybe they just guessed correctly this time, or copied the answer from somewhere. A teacher grading only the final number would mark it correct. A teacher who actually reads the work would catch that the REQUIRED verification step never happened — and would (correctly) worry that the same student will get the NEXT similar problem wrong, because whatever process got them here wasn't reliable, it just happened to land on the right number this once.

This is exactly the gap trajectory-based evals close for agents. final_multi_agent_workflow.html's capstone scenario had a specific required recovery path: when get_order_detail failed for one order, the agent was supposed to retry it (per loop_termination_logic.html's bounded-retry discipline) before either succeeding or abandoning that order with an explicit orders_omitted entry. A final-answer-only eval checks only whether the returned JSON is correct — it has no visibility into WHETHER the retry actually happened, or whether the agent instead silently fabricated a plausible-looking result for the order that failed, or skipped it without recording why. Both a genuinely-recovered trajectory and a silently-fabricated one could produce an IDENTICAL final JSON blob.

# a trajectory eval checks the SEQUENCE of tool calls, not just the final return value def score_trajectory(trajectory: list[dict], expected_tools: list[str]) -> dict: # trajectory: [{"tool": "query_orders", "args": {...}, "result": "success"}, # {"tool": "get_order_detail", "args": {"order_id": "ord-129"}, "result": "error"}, # {"tool": "get_order_detail", "args": {"order_id": "ord-129"}, "result": "success"}, ...] called_tools = [step["tool"] for step in trajectory] return { "used_required_tools": all(t in called_tools for t in expected_tools), "retried_after_failure": _had_retry_after_error(trajectory), "no_redundant_calls": len(called_tools) == len(set( (s["tool"], tuple(sorted(s["args"].items()))) for s in trajectory )), "step_order_valid": called_tools.index("query_orders") < called_tools.index("get_order_detail") }

Every one of these four checks is asking about the PROCESS, not the outcome — did the agent use the tools it needed to, did it actually retry rather than silently giving up or fabricating, did it avoid wasteful repeated calls, did it call things in a sensible dependency order. An agent could score perfectly on all four of these and still get the final answer wrong (a genuinely correct process applied to bad luck downstream); an agent could ALSO get the final answer completely right while failing every one of these — and it's specifically that second case that final-answer-only evaluation is structurally blind to.

Interview-ready definition: a trajectory-based eval scores the sequence of intermediate steps an agent took — which tools were called, in what order, with what arguments, and how it responded to failures — rather than scoring only the final returned answer. This catches a real class of failure that final-answer-only evals structurally cannot: an agent reaching a correct final answer via an incorrect, unreliable, or lucky path (skipping a required step, fabricating a result instead of genuinely recovering from a failure, or calling tools in an order that happened to work this time but isn't a dependable process for the next similar task).
02 — Naming the frameworks that formalize this for RAG pipelines

DeepEval and Ragas concepts

Start here, before the framework names. Month 3's RAG labs (storage-and-rag/) built a pipeline: retrieve relevant chunks, assemble context, generate an answer. That pipeline has its OWN version of the "right answer, wrong path" problem — a generated answer can happen to be factually correct while being built from retrieved context that was actually IRRELEVANT to the question, which is a real, latent failure even if this specific answer looks fine. DeepEval and Ragas are two widely-used open-source frameworks built specifically to formalize evaluation for RAG and agentic pipelines — you don't need to memorize their APIs, but understanding the CONCEPTS they standardize is directly useful, because those concepts are exactly trajectory-based thinking applied to a RAG pipeline's specific shape.

ConceptWhat it checksConnects to
Retrieval relevanceWere the chunks the retrieval step actually pulled back genuinely relevant to the query — not just superficially similar?storage-and-rag/hybrid_search.html and reranking.html's whole reason for existing — retrieval quality is itself a step worth scoring, not just the final generated answer
FaithfulnessDoes the generated answer only assert things actually supported by the retrieved context, without inventing details the context never contained?Directly analogous to this lab's final_multi_agent_workflow.html fabrication concern — the model asserting something plausible-sounding rather than something the actual retrieved/tool-call evidence supports
Answer relevanceDoes the final answer actually address what the user's ORIGINAL question asked, independent of whether it's faithful to the retrieved context?Catches a subtly different failure: an answer can be perfectly faithful to the context AND still fail to actually answer the question that was asked

Notice these three checks are DELIBERATELY separated rather than folded into one "is the answer good" score — exactly because they can fail INDEPENDENTLY of each other. A RAG pipeline can retrieve irrelevant chunks but still generate a faithful (to those irrelevant chunks) and yet completely unhelpful answer; it can retrieve perfectly relevant chunks and then generate an answer that's unfaithful to them (hallucinating details the context never said); or it can be both faithful and relevant to the retrieved context while never actually addressing what the user asked. Each of these is a DIFFERENT bug, in a DIFFERENT pipeline stage, and collapsing them into one aggregate score — the same trap a final-answer-only agent eval falls into — would hide exactly which stage needs fixing.

Interview-ready definition: DeepEval and Ragas are open-source evaluation frameworks purpose-built for RAG and agentic pipelines, formalizing trajectory-style thinking into named, separately-scored metrics rather than one aggregate "is this good" judgment: retrieval relevance (did the retrieval step pull back genuinely useful context), faithfulness (does the generated answer stick to what that context actually supports, without inventing unsupported claims), and answer relevance (does the final answer actually address the original question). Each metric targets a different pipeline STAGE specifically so failures can be localized to where they actually occurred — retrieval, generation, or the connection between the question and the answer — rather than only being visible as one undifferentiated low score with no clue which stage caused it.

Problem 1 · Writing a trajectory check for a specific requirement

Using section 1's score_trajectory function shape, write a check verifying that the agent never called confirm_booking before a preceding select_seat call in the same trajectory (referencing the sequence from database/audit_trail_schema.html's live replay demo).

Show solution
def confirm_after_select(trajectory: list[dict]) -> bool: tools = [step["tool"] for step in trajectory] if "confirm_booking" not in tools: return True # nothing to check if confirm_booking never happened confirm_idx = tools.index("confirm_booking") # find the LAST select_seat call before this confirm_booking select_indices = [i for i, t in enumerate(tools) if t == "select_seat" and i < confirm_idx] return len(select_indices) > 0 This mirrors section 1's step_order_valid check exactly, just applied to a different required ordering: confirm_booking depends on a seat having been selected first, the same real data dependency react_pattern.html's capital-then-population example established for tool call ordering in general. A trajectory where confirm_booking appears with no PRIOR select_seat call at all would be flagged by this check even if -- through some coincidence -- the confirm call still somehow "succeeded," because the ordering itself is the property being verified, independent of whether the final outcome happened to look fine.
Problem 2 · Explaining why Ragas separates faithfulness from answer relevance

Construct a concrete example where a RAG answer is FAITHFUL to its retrieved context but scores poorly on answer relevance. Why would collapsing both into one score hide this specific failure?

Show solution
Concrete example: a user asks "what's the refund policy for international orders?" The retrieval step, due to a relevance bug, pulls back a chunk about the DOMESTIC refund policy instead (a genuine retrieval failure). The generation step then produces an answer that accurately, faithfully summarizes exactly what that domestic-policy chunk says -- faithfulness is HIGH, because the answer invents nothing beyond what the retrieved context actually said. But the answer never addresses the user's actual question about INTERNATIONAL orders -- answer relevance is LOW, because the response, however faithful to its (wrong) source, doesn't answer what was asked. Why collapsing both into one score hides this: a single "is this answer good" score averaging or blending these two dimensions could land at a middling number that looks like "an okay answer with some minor issues," when the real story is a much sharper diagnosis -- the GENERATION step did its job perfectly (faithful to its input), and the actual bug is entirely upstream, in RETRIEVAL. Separating the metrics tells you exactly where to look (fix retrieval relevance, not the generation prompt) in a way one blended score never could -- this is precisely section 2's point about localizing failures to the STAGE that actually caused them.
Problem 3 · Deciding whether a trajectory eval is even necessary for a given task

A single-tool agent always calls exactly one tool (a calculator) and returns its result directly with no other steps possible. Does this agent need a trajectory-based eval on top of a final-answer eval? Justify using section 1's reasoning about what trajectory evals are FOR.

Show solution
No, or at most minimally -- trajectory-based evals earn their value specifically when there's a MEANINGFUL SEQUENCE OF DECISIONS that could go right or wrong independent of the final answer: which tool to call, in what order, how to respond to a failure. A single-tool agent with exactly one possible tool call and no branching, retry logic, or multi-step dependency has no meaningfully different "wrong path" to a correct answer -- there's only one path available at all, so a correct final answer and a correct trajectory are effectively the SAME fact, not two independent things that could diverge. This connects to section 1's core argument precisely by testing its boundary: trajectory evals matter BECAUSE final-answer-only evaluation can be fooled by multiple different paths converging on the same correct-looking output (Run A's genuine retry vs Run B's fabrication in section 3's demo, both landing on an identical final JSON). Where there is only one possible path to begin with, that specific failure mode structurally cannot occur, so the marginal value of a separate trajectory eval is much lower -- though even here, a MINIMAL trajectory check (did the calculator actually get called, rather than the model just guessing an answer without ever invoking it) still has some value, since "was the tool actually used at all" is itself a trajectory-level question a final-answer eval alone wouldn't directly verify.
Problem 4 · Diagnosing why Run B's final answer looked identical to Run A's

Using section 3's live demo, explain mechanically HOW an agent that fabricates a result instead of retrying can still produce a final JSON answer that's schema-valid and plausible-looking, and why deterministic_evals.html's schema-validation check specifically cannot catch this.

Show solution
Mechanically: nothing about generating a well-formed JSON object requires the VALUES inside it to have come from a genuine, successful tool call. A model asked to "summarize this order" can, in principle, generate a plausible-looking order_id, total, and item_count from its own generative capability -- the same way it can generate any other plausible-sounding text -- without that data having any grounding in an actual successful get_order_detail call. The resulting JSON object passes every structural check deterministic_evals.html's schema validation runs (right fields, right types, required keys present) because schema validation, per that lab's own Problem 2, ONLY checks structure, never whether the VALUES are actually grounded in real data. Why schema validation specifically can't catch this: schema validation has no visibility into PROVENANCE -- it inspects the final JSON object in isolation, with no access to (or interest in) the trajectory that produced it. A fabricated total=511 and a genuinely-fetched total=511 are byte-for-byte identical from the schema validator's point of view -- there's no field in the schema for "was this actually retrieved from a successful tool call." Only a trajectory-based eval, which inspects the SEQUENCE OF TOOL CALLS rather than just their eventual output, can tell the difference -- checking specifically whether a get_order_detail call for that order_id actually appears in the trajectory with a success result, which section 3's Run B trajectory conspicuously lacks.
Problem 5 · Designing a combined eval suite that catches both failure classes

Using everything from this week so far (deterministic, model-graded, and trajectory-based evals), design a complete eval suite for the Month 4 capstone agent that would catch: (1) a malformed final answer, (2) a factually wrong but well-formed summary, (3) fabrication instead of genuine retry. Name which eval type catches each.

Show solution
(1) Malformed final answer -- deterministic (schema validation), per deterministic_evals.html section 1: validate the final JSON against the task's output schema; a missing required field or wrong type fails this check immediately and cheaply, with no model call needed. (2) Factually wrong but well-formed summary (e.g. the total dollar amount for an order is subtly incorrect, or the summary reads coherently but misrepresents what the source order data actually contained) -- this splits across TWO tools depending on what "wrong" means here: if it's a checkable INVARIANT (e.g. orders_found not matching summarized+omitted counts), a deterministic rule-based check catches it cheaply, per deterministic_evals.html section 3's live demo. If it's a more open-ended factual/faithfulness question not reducible to an exact rule (e.g. "does this summary's prose actually reflect what the order contained, without subtly misstating it"), a model-graded eval with a faithfulness-focused rubric (model_graded_evals.html section 1, echoing this lab's faithfulness metric from section 2) is the right tool. (3) Fabrication instead of genuine retry -- trajectory-based eval, exactly per this lab's section 3 live demo: checking the ACTUAL SEQUENCE of tool calls for evidence that a real get_order_detail retry occurred after the injected failure, which neither the deterministic schema check nor a model-graded faithfulness check (both of which only see the FINAL text/JSON, never the trajectory that produced it) has any visibility into at all. The overall lesson this suite makes concrete: no single eval type is sufficient on its own for a real agentic system -- each catches a genuinely different, non-overlapping class of failure, and a suite that only runs one type (however sophisticated) leaves the other failure classes completely uncovered.
