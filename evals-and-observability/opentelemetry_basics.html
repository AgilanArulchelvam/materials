01 — A trace is a tree of spans, not a flat list

Traces and spans — the nesting model

Start here, before any code. Think about a restaurant order. The whole meal — from the moment you sit down to the moment you pay — is ONE experience with a clear start and end. Inside that experience, distinct pieces of work happen: the kitchen prepares your appetizer, then your entrée, and inside "prepare the entrée" there's a further sub-step, "fire the grill." Each of these pieces of work has its own start time, its own end time, and its own PARENT — "fire the grill" happened INSIDE "prepare the entrée," which happened INSIDE "the whole meal." A trace is exactly this: one end-to-end request (the whole meal), decomposed into a TREE of nested spans (kitchen prep, entrée, grill), each span timestamped and aware of which span it happened inside.

Concretely: a trace represents one end-to-end request — a single HTTP call, a single agent invocation — from the moment it starts to the moment it finishes. A trace is composed of spans, and each span represents one unit of work within that request. Spans NEST: a parent span like handle_request can contain child spans like call_database and call_llm, and those children could themselves have their own children. Every span records a start time, an end time (so its duration is just end minus start), a name, and a set of key-value attributes describing what happened — plus a reference to its parent span, which is the ONE piece of data that turns a flat pile of timestamped events into an actual tree.

# real OpenTelemetry-style code — creating a parent span and a nested child span # (this is the actual Python OTel SDK shape, not pseudocode) from opentelemetry import trace tracer = trace.get_tracer("agent-service") def handle_request(request): # the PARENT span — represents the entire request, start to finish with tracer.start_as_current_span("handle_request") as parent_span: parent_span.set_attribute("request.id", request.id) parent_span.set_attribute("request.query", request.query) # a CHILD span, nested inside handle_request — automatically picks up # handle_request as its parent because it's opened while that span is "current" with tracer.start_as_current_span("call_database") as db_span: db_span.set_attribute("db.statement", "query_orders") orders = query_orders(request) db_span.set_attribute("db.rows_returned", len(orders)) # db_span closes here — its duration is now fixed: end_time - start_time # a SECOND child span, also nested directly inside handle_request with tracer.start_as_current_span("call_llm") as llm_span: llm_span.set_attribute("llm.model", "claude-sonnet-5") summary = summarize(orders) llm_span.set_attribute("llm.output_tokens", 142) return summary # parent_span closes here — its duration spans BOTH children plus any # gap between them; it is, by construction, at least as long as its longest child

Two mechanics worth being precise about, because they're exactly what makes this a TREE rather than a flat log of timestamped lines. First: start_as_current_span doesn't just create a span — it also makes that span the "current" one in a thread-local/context-local sense, so any span opened WHILE it's current automatically becomes its child, with no manual parent-ID wiring required in this simple sequential case. Second: a parent span's own reported duration is measured independently of its children — it's just that parent's own start-to-end time — but because the parent's with block wraps the children's, the parent's end time can never be earlier than its last child's end time. A parent is never SHORTER than the longest path through its own children; the whole tree's shape is enforced by nesting, not by any extra bookkeeping.

Interview-ready definition: a trace represents one end-to-end request, composed of nested spans, where each span represents one unit of work — a parent span (e.g. handle_request) can contain child spans (e.g. call_database, call_llm), and those children can have their own children in turn. Every span records a start time, an end time, a name, structured attributes, and a reference to its parent, which is what turns the collection of spans into an actual TREE rather than a flat list of timestamped events — and it's that tree structure, not just the individual timestamps, that lets you answer "where inside this one request did the time actually go."
02 — Going deeper than Week 1's conceptual pass

Metrics vs traces vs logs — what each is for, precisely

Start here, before the table. systems/observability_pipeline_design.html already built the everyday-analogy version of this (a GPS trail for one delivery vs. a dashboard of average delivery time vs. a dispatcher's log entries). This section restates the same three pillars in the exact terms that matter once you're actually writing OpenTelemetry code, not just reasoning about them conceptually — because "traces, metrics, and logs" stops being three vague nouns and becomes three concrete SDK objects (Span, Counter/Histogram, Logger) with genuinely different shapes.

PillarQuestion it answersWhat it's shaped like, concretely
Metrics"How many / how much / how fast, in aggregate?"A number that gets incremented or observed over time — requests_total, llm_call_duration_ms — with no memory of any ONE request's identity once recorded
Traces (spans)"What happened to THIS SPECIFIC request?"A tree of timestamped, named, attributed spans, all sharing one trace_id, causally ordered by parent/child nesting
Logs"What exactly happened at this moment, in detail?"A discrete, timestamped, usually free-text or semi-structured line — one event, described in narrative detail a span's structured attributes alone often don't carry

A span's attributes ARE structured

A span on call_llm might carry llm.model, llm.output_tokens as clean key-value attributes — but it's still fundamentally about ONE call's timing and identity within ONE trace, not an aggregate across every call this service has ever made.

A log line can be equally structured, but isn't a tree

A log line like "[agent-service] WARN retry #1 for get_order_detail(ord-129)" can carry a trace_id for correlation, but it has no PARENT/CHILD relationship to any other log line the way a span has to its parent span — logs are a list, not a tree.

The precise reason none of the three substitutes for the others: a metric like agent_tool_calls_total is, at write time, DELIBERATELY stripped of per-request identity — the moment it's incremented, the specific request that caused the increment is gone, replaced by one bigger number. That's not a limitation to work around, it's the entire mechanism that makes metrics cheap enough to keep for months. A trace's spans, by contrast, keep per-request identity but pay for it — a full span tree is comparatively expensive to store per request, which is exactly why observability_pipeline_design.html's section 3 argued for sampling traces rather than metrics. And a log line sits in between: cheaper than a full span tree, richer in narrative detail than a bare metric, but with no structural tree of its own — a log line about a retry doesn't inherently know it happened "inside" the call_database span unless something (a shared trace_id, or emitting the log AS a span event) explicitly links them.

Interview-ready definition: metrics answer "how many/how much/how fast, in aggregate" — a cheap, always-on number that has already discarded per-request identity at write time. Traces answer "what happened to THIS specific request" — a per-request tree of nested spans, each with its own timing and attributes, expensive enough at real volume that it typically needs sampling. Logs answer "what exactly happened at this moment, in detail" — a discrete, timestamped, often free-text record of one specific event, correlatable to a trace via a shared trace_id but structurally a flat list, not a tree. Each pillar's cheapness/richness trade-off is a direct consequence of how much per-request detail it keeps — the more detail kept, the more it costs, and the more it costs, the shorter you can afford to retain it at full fidelity.

Problem 1 · Writing a 3-level nested span for a concrete scenario

Using section 1's code shape, write the OpenTelemetry spans for: a parent span process_order, containing a child validate_payment, which itself contains a child call_fraud_check_api.

Show solution
with tracer.start_as_current_span("process_order") as order_span: order_span.set_attribute("order.id", order.id) with tracer.start_as_current_span("validate_payment") as pay_span: pay_span.set_attribute("payment.method", order.payment_method) with tracer.start_as_current_span("call_fraud_check_api") as fraud_span: fraud_span.set_attribute("fraud_check.provider", "vendor_x") result = call_fraud_api(order) fraud_span.set_attribute("fraud_check.result", result.verdict) # call_fraud_check_api closes -- its duration is fixed # validate_payment closes -- its duration spans call_fraud_check_api # plus any of its own work before/after that call # process_order closes -- its duration spans validate_payment entirely This is exactly section 1's nesting mechanic one level deeper: call_fraud_check_api is a child of validate_payment (opened while validate_payment is "current"), and validate_payment is a child of process_order for the same reason. The resulting tree has 3 levels, and each span's duration is independently measured but structurally contained within its parent's time window, precisely because each inner span is opened and closed entirely within its parent's `with` block.
Problem 2 · Diagnosing which pillar a specific debugging question needs

A teammate asks: "our p99 latency for call_llm spiked to 4 seconds starting an hour ago — which specific requests were affected, and where in THEIR execution did the extra time go?" Using section 2's table, name which pillar answers which half of this question, and why one alone can't answer both halves.

Show solution
"p99 latency ... spiked ... starting an hour ago" is a METRIC question -- p99 is, by definition, an aggregate statistic computed across many requests' durations, and "spiked starting an hour ago" is a trend observation only possible because metrics are cheap enough to graph continuously over a long window. No trace, by itself, could tell you a trend existed at all -- a single trace only ever describes one request. "which specific requests were affected, and where in THEIR execution did the extra time go" is a TRACE question -- this needs the per-request identity and nested timing metrics deliberately discarded at write time. Once the metric has told you SOMETHING is wrong in aggregate, you'd query traces filtered to slow call_llm spans within that time window, then open one of those specific traces and read its span tree (per section 1's nesting model) to see whether the extra time was in, say, a nested tokenize_prompt child span specifically, versus the call_llm span's own non-child time. Why one pillar can't answer both: the metric was never designed to keep per-request detail (that's the whole reason it's cheap enough to trend over an hour), and a trace was never designed to aggregate across many requests (that's the whole reason it can afford to keep detailed, nested, per-request structure). This is precisely observability_pipeline_design.html's core argument, now demonstrated on a single realistic question that genuinely needs BOTH pillars, each for a different half of the answer.
Problem 3 · Explaining why a parent span's duration isn't just "sum of children"

In section 3's live demo, handle_request's total duration is NOT simply call_database's duration plus call_llm's duration added together. Explain precisely why, using section 1's mechanics.

Show solution
A parent span's duration is measured independently -- it's just that parent span's OWN start time subtracted from its OWN end time, per section 1. Summing the children's durations would only equal the parent's duration in the special case where the children ran back-to-back with literally zero gap between them AND the parent did no work of its own outside those children's spans. In practice this essentially never holds exactly: there's almost always some gap between call_database closing and call_llm opening (the parent span's own code doing something in between -- assembling the query result into a prompt, for instance), and that gap is real time the parent span's duration includes but neither child span accounts for. Additionally, if the parent does ANY work before its first child opens or after its last child closes (setting an initial attribute, or formatting a final return value), that time also counts toward the parent's own duration without belonging to any child span at all. The correct relationship is an INEQUALITY, not an equation: the parent's duration is always greater than or equal to the longest single uninterrupted stretch covered by its children, never less -- because each child is fully nested within the parent's own with block (section 1's structural guarantee) -- but it can exceed the sum of children's durations by any amount, depending on how much of the parent's own, non-child work happened in between.
Problem 4 · Deciding whether a piece of information belongs on a span attribute or a log line

Using section 2's precise distinctions, would you record "the LLM call's token count" as a span attribute or a log line? What about "a free-text explanation of why a retry was triggered, written by the code at the moment it decided to retry"? Justify each.

Show solution
Token count -- span attribute. It's a small, structured, well-typed piece of data (an integer) describing a property of ONE specific span (call_llm) that's genuinely useful to filter/aggregate ON later (e.g. "show me all call_llm spans where output_tokens > 500") -- exactly the kind of structured key-value data section 1's set_attribute calls are for, and exactly the shape a tracing backend can efficiently index and query across many spans. The free-text retry explanation -- log line (or, in OpenTelemetry's actual model, a SPAN EVENT attached to the relevant span, which is a structured way of embedding a log-like narrative moment inside a specific span's timeline). This is narrative, event-like detail -- "what exactly happened, in detail, at this moment" per section 2's table -- rather than a structured, filterable property of the span as a whole. Cramming a long free-text narrative into a span ATTRIBUTE would technically work but misuses the attribute mechanism, which per section 2's design is meant for small, structured, queryable key-value pairs, not prose -- exactly the same category error as trying to answer a metric-shaped question ("how many total retries happened this hour") by reading through individual log lines by hand, when a proper metric counter would answer it instantly.
Problem 5 · Predicting what changes if a child span's tracer call is accidentally left out of the parent's `with` block

Suppose a developer accidentally writes call_llm's span-opening code OUTSIDE handle_request's with block (after it has already closed), rather than inside it. Using section 1's "current span" mechanic, what happens to the resulting trace tree, and why is this a realistic, easy-to-make bug?

Show solution
Because start_as_current_span's parent-assignment relies on which span is "current" at the moment a new span opens (section 1), and handle_request's with block has already exited by the time call_llm's span opens, call_llm would no longer automatically become a CHILD of handle_request. Depending on the SDK's exact default behavior, it would either become a new, unrelated ROOT span of its own trace entirely (its own trace_id, disconnected from handle_request's), or -- if some other span happened to be "current" at that point instead -- a child of whatever THAT span was, silently attaching it to the wrong parent. Either way, the resulting trace tree is now WRONG: querying handle_request's trace_id would no longer show call_llm as part of it at all, even though call_llm genuinely happened as part of serving that same request. This is a realistic, easy-to-make bug specifically because span parenting in most OTel SDKs is IMPLICIT (based on context/current-span state) rather than requiring the developer to explicitly pass a parent span ID every time -- convenient when the nesting matches the code's actual block structure (section 1's normal case), but silently wrong the moment a span-opening call gets moved outside the block it was meant to be nested inside, with no error or warning at all -- the code still runs fine, it just produces a structurally incorrect trace.
