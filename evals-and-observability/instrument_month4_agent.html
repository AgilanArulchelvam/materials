01 — Deciding the span boundaries before writing any wrapper code

What gets wrapped, and why

Start here, before any code. Think about adding mile markers to a road trip you're about to drive, before you start driving. You wouldn't put a marker only at the very start and very end — you'd want one at "left the driveway," one at "merged onto the highway," one at "hit traffic and had to detour," one at "arrived." Each marker tells you WHERE in the trip a specific thing happened, so if someone later asks "where did all the extra time go," you can point at a specific stretch, not just say "somewhere between start and end." Instrumenting an agent with spans is the same idea, decided BEFORE the agent runs: pick the boundaries that will actually matter when someone is debugging a slow or failed run later.

For the Month 4 capstone specifically, per final_multi_agent_workflow.html's own section 2 plan table and section 3 stage tracker, there are exactly four kinds of unit worth their own span: the overall request (the root span, spanning the whole task), the planning step (deciding the 3-step approach), each individual tool call (query_orders, and one get_order_detail call per qualifying order — including the one that fails and its retry, each as its OWN span), and the final synthesis step's LLM call (assembling the structured JSON answer). This maps directly onto opentelemetry_basics.html's nesting model: the root span is handle_capstone_task, and everything else nests inside it, exactly the way call_database and call_llm nested inside handle_request in that lab's section 1.

Interview-ready definition: instrumenting an agent means deciding span boundaries around each genuinely distinct unit of work BEFORE execution — typically one root span for the whole request, one span for planning, one span per tool call (with a failed call and its retry as two separate spans, not one merged span), and one LLM-aware span for any step that calls a model — so that after the run, the resulting trace tree lets you answer "where specifically did time go, and where specifically did something fail" without needing to re-run or guess. The boundaries chosen determine what questions the resulting trace can answer later; too coarse (one span for the whole agent) loses the ability to localize a problem, too fine (a span for every single line of code) buries the signal in noise.
02 — Wrapping the actual capstone agent's code, section by section

Instrumenting the capstone, piece by piece

Starting from opentelemetry_basics.html's exact start_as_current_span pattern, applied to final_multi_agent_workflow.html's actual scenario — the same order IDs, the same injected failure on ord-129, the same retry, that pytest_evals_practice.html's fixture already captured:

# instrumented_capstone_agent.py # wraps final_multi_agent_workflow.html's exact scenario in real spans from opentelemetry import trace from llm_tracing import traced_llm_call # LLM-aware wrapper, per langsmith_or_phoenix.html tracer = trace.get_tracer("capstone-agent") def handle_capstone_task(task): # ROOT span — the whole run gets one trace_id with tracer.start_as_current_span("handle_capstone_task") as root_span: root_span.set_attribute("task.description", task.description) # PLANNING span — nested directly inside the root with tracer.start_as_current_span("plan_task") as plan_span: plan = build_plan(task) # query_orders -> get_order_detail x N -> synthesize plan_span.set_attribute("plan.step_count", len(plan.steps)) # TOOL CALL span #1 — query_orders with tracer.start_as_current_span("tool_call:query_orders") as qo_span: qo_span.set_attribute("tool.name", "query_orders") qo_span.set_attribute("tool.args", str({"min_total": 500, "period": "2026-07"})) orders = query_orders(min_total=500, period="2026-07") # 4 qualifying orders qo_span.set_attribute("tool.result", "success") qo_span.set_attribute("tool.rows_returned", len(orders)) # TOOL CALL span PER ORDER — including the one that fails, then retries for order in orders: with tracer.start_as_current_span(f"tool_call:get_order_detail({order.id})") as od_span: od_span.set_attribute("tool.name", "get_order_detail") od_span.set_attribute("tool.args.order_id", order.id) try: detail = get_order_detail(order.id) # ord-129 raises here, first attempt od_span.set_attribute("tool.result", "success") except TransientError as e: od_span.set_attribute("tool.result", "error") od_span.set_attribute("tool.error_detail", str(e)) # the RETRY gets its OWN span, per loop_termination_logic.html's # "a retry is just another pass through the loop body" with tracer.start_as_current_span(f"tool_call:get_order_detail({order.id})_retry") as retry_span: retry_span.set_attribute("tool.name", "get_order_detail") retry_span.set_attribute("tool.args.order_id", order.id) retry_span.set_attribute("tool.is_retry", True) detail = get_order_detail(order.id) # succeeds this time retry_span.set_attribute("tool.result", "success") # SYNTHESIS span — LLM-aware, captures prompt/completion/tokens/cost with traced_llm_call("synthesize_answer", model="claude-sonnet-5") as llm_span: final_answer = synthesize_final_json(orders) # the structured JSON from final_multi_agent_workflow.html # prompt, completion, input/output tokens, cost all captured # automatically by traced_llm_call, per langsmith_or_phoenix.html root_span.set_attribute("task.orders_found", final_answer["orders_found"]) return final_answer

Notice the retry gets its OWN span rather than being folded into the first attempt's span — this exactly mirrors the trajectory data pytest_evals_practice.html's fixture already recorded as two separate trajectory entries (one "result": "error", one "result": "success" for the same order_id). A trace and a trajectory fixture are, at this point, describing the exact same underlying event sequence — this lab is just making that sequence visible as a real, timed, browsable tree instead of a list of dicts in a test file.

Interview-ready definition: instrumenting an existing agent means inserting start_as_current_span calls (or an LLM-aware equivalent for model calls) around each of the span boundaries decided in section 1, without changing the agent's actual logic — the try/except around get_order_detail still does exactly what it did before, it's now just wrapped so the failure and the subsequent retry each produce their own timed, attributed span, nested correctly inside the tool-call loop, which itself nests inside the root request span — turning a run that previously left only log lines and a final answer into one complete, walkable trace tree.

Problem 1 · Deciding whether the retry should be a child of the failed span or a sibling

Section 2's code opens the retry span AFTER the first get_order_detail span's with block has already caught the exception, nested inside the except block rather than inside the original attempt's span. Using opentelemetry_basics.html's Problem 5 reasoning, is the retry a CHILD of the failed span, or a SIBLING? Justify precisely.

Show solution
Looking at section 2's code carefully: the retry's `with tracer.start_as_current_span(...)` block is written INSIDE the `except` block, which itself is inside the outer `for order in orders:` loop's body -- but the FIRST attempt's span (`od_span`) has already exited its own `with` block by the time the except clause runs (the exception propagated OUT of that with block). So per opentelemetry_basics.html's "current span" mechanic, the retry span's parent is whatever span is CURRENT at the moment it opens -- which is the tool-call loop's enclosing context, not od_span specifically (od_span has already closed). That makes the retry a SIBLING of the failed attempt, not a child -- both nest one level inside handle_capstone_task's tool-call loop, at the same depth, appearing as two separate rows in section 3's waterfall exactly as drawn (bar-129 and bar-129r are siblings, not one nested inside the other). This is a deliberate design choice, not an accident: making the retry a CHILD of the failed attempt would incorrectly suggest the retry only happened "because of" or "as part of" the failed span's own internal work, when actually it's a NEW, independent attempt at the same logical operation. Siblings correctly represent "two separate tries at the same tool call," which is exactly what pytest_evals_practice.html's CAPTURED_TRAJECTORY fixture also represents as two separate list entries rather than one nested structure.

Checklist, using section 3's tree as the source of truth for what "correct" looks like: 1. FAILING case: only the successful retry span exists because the failed attempt's span context manager swallowed the exception before set_attribute ran, erasing evidence the failure ever happened -- exactly the kind of silent data loss trajectory_based_evals.html's Run B scenario warned about, now at the tracing layer instead of the eval layer. 4. The synthesis step's LLM-aware span actually captured prompt/ completion/tokens/cost, not just a generic span with no LLM-specific fields. FAILING case: traced_llm_call was swapped for a plain start_as_current_span by mistake, silently reverting to raw OTel's generic capture -- exactly the gap langsmith_or_phoenix.html's section 1 described.
Problem 3 · Reasoning about what a slow trace would reveal for this specific agent

Suppose a real run of this instrumented capstone agent takes 6 seconds total, and a teammate suspects the retry logic is the culprit. Using section 3's trace tree structure, how would you confirm or rule this out WITHOUT re-running the agent?

Show solution
Open the ALREADY-CAPTURED trace for that specific slow run (per opentelemetry_basics.html's core value: a trace records exactly what happened for ONE specific request, replayable after the fact) and read the durations directly off each span in the waterfall, exactly as drawn in section 3: handle_capstone_task's total duration is the sum of gaps plus whichever child spans ran, per opentelemetry_basics.html's Problem 3 inequality relationship. Specifically check: tool_call:get_order_detail(ord-129) alone (the failed attempt) plus tool_call:get_order_detail(ord-129)_retry (the successful retry) together -- if these two spans combined only account for, say, 800ms of the 6 total seconds, the retry logic is almost certainly NOT the bottleneck, and the teammate's suspicion is ruled out directly from the trace with no new run needed. If instead those two spans combined account for something like 4.5 of the 6 seconds, that's strong evidence the retry (or more likely, the transient failure's own timeout/backoff before the retry even started) IS a major contributor -- and specifically WHICH of the two spans (the failed attempt's own duration vs. a gap before the retry span opens vs. the retry's own duration) pinpoints whether the problem is the failure itself being slow to detect, a delay before retrying, or the retry call itself being slow. This is exactly the "metric flags a trend, trace diagnoses a specific instance" split opentelemetry_basics.html's Problem 2 established, now applied to one real captured trace instead of a hypothetical.
Problem 4 · Explaining why the planning span matters even though it makes no tool calls

Section 1's table gives plan_task its own span even though, per final_multi_agent_workflow.html's section 2, planning makes no tool calls at all. Why is this still worth a dedicated span rather than just being folded into the root span's own "before the first child" time?

Show solution
Per opentelemetry_basics.html's Problem 3, ANY time the root span spends before its first child opens is, by default, invisible as its own named quantity -- it just silently inflates the root span's total duration without a label explaining WHAT that time was spent on. If plan_task were NOT its own span, a slow run's trace would show handle_capstone_task taking longer than the sum of its visible tool-call children, with no way to tell whether that extra time was genuinely spent planning, or was dead time from some other unaccounted-for cause (a slow import, a cold connection pool, etc.) -- exactly the ambiguity that inequality relationship warns about. Giving planning its own explicit span converts an invisible gap into a named, measurable quantity: now a slow run can be diagnosed as "planning took 3 of the 6 seconds" specifically, rather than "3 seconds went somewhere before the first tool call, cause unknown." This connects directly to section 1's core design principle -- span boundaries should be drawn around anything that, if slow, you'd actually want to know about by name later, and "the agent spent an unusually long time deciding its plan" is exactly this kind of question, even though planning itself makes no further tool calls or sub-spans of its own.

with tracer.start_as_current_span(f"tool_call:get_order_detail({order.id})") as od_span: od_span.set_attribute("tool.name", "get_order_detail") od_span.set_attribute("tool.args.order_id", order.id) try: detail = get_order_detail(order.id) od_span.set_attribute("tool.result", "success") except TransientError as e: od_span.set_attribute("tool.result", "error") od_span.set_attribute("tool.error_detail", str(e)) with tracer.start_as_current_span(f"tool_call:get_order_detail({order.id})_retry") as retry_span: retry_span.set_attribute("tool.is_retry", True) try: detail = get_order_detail(order.id) retry_span.set_attribute("tool.result", "success") except TransientError as e2: # per final_multi_agent_workflow.html Problem 3: the # retry budget is exhausted -- record the ABANDONMENT # as its own attribute on THIS span, not a third span retry_span.set_attribute("tool.result", "error") retry_span.set_attribute("tool.error_detail", str(e2)) retry_span.set_attribute("order.abandoned", True) detail = None # this order goes into orders_omitted Difference from the single-failure case: the retry_span's tool.result now reads "error" instead of "success", and a new attribute, order.abandoned=True, is set directly on that SAME retry span rather than opening a third span for a second retry -- because final_multi_agent_workflow.html's Problem 3 established a BOUNDED retry budget (attempt once, retry once, then abandon), not unlimited retries. A trace reader querying for order.abandoned=True spans could now find every order that hit this specific fate directly, and cross- reference it against orders_omitted in the final JSON answer exactly the way pytest_evals_practice.html's test_final_answer_reflects_the_ recovered_order test cross-checked the OPPOSITE (successful-recovery) case.
