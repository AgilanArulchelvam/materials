01 — A span is just a bag of key-value pairs, unless something teaches it what an LLM call IS

The gap: generic spans vs LLM-aware traces

Start here, before any code. Think about the difference between a generic package-tracking system and a system built specifically for tracking restaurant deliveries. The generic tracker knows "package left location A at 2:00pm, arrived at location B at 2:20pm" — useful, but it has no idea WHAT was in the package, whether it was still hot on arrival, or what it cost to make. A delivery-specific tracker, by contrast, was built knowing packages are FOOD ORDERS — it automatically captures the dish, the ingredients, the kitchen prep time, and the price, because someone designed the system around the specific shape of what's actually being tracked, not just "a thing moved from A to B."

Raw OpenTelemetry is the generic tracker. opentelemetry_basics.html's call_llm span is, to the OTel SDK, structurally IDENTICAL to a call_database span — both are just a name, a start time, an end time, and whatever attributes a developer manually thought to call set_attribute for. OpenTelemetry's core spec has no built-in schema for "this span represents an LLM call" — no field it automatically knows means "the prompt," no field it knows means "the completion," no field it knows means "this cost $0.003." Every one of those has to be manually attached, by a human, remembering to do it correctly, on every single call site, with no guarantee of consistency across a codebase.

LangSmith and Arize Phoenix are LLM-specific tracing and observability tools built on top of this same span/trace foundation, but with first-class understanding of what an LLM call actually is. Instrumenting an LLM call with either tool (typically via a decorator or an SDK wrapper around your model client) automatically captures the full prompt sent, the full completion received, input and output token counts, the model name, latency, and — because token counts and model are both known — a computed dollar cost per call, without a developer manually calling set_attribute for each of these individually. The UI on top is ALSO purpose-built: browsing a list of agent runs, drilling into one trace's LLM calls specifically, comparing two prompt variants' completions side by side — none of which a generic OTel-compatible backend (built for arbitrary microservice traces) was designed around.

Interview-ready definition: raw OpenTelemetry is a generic, protocol-level tracing standard — it has no built-in concept of "prompt," "completion," "token count," or "tool call"; every LLM-relevant attribute has to be manually attached to a span's generic key-value attribute bag by a developer. LLM-specific tracing tools like LangSmith and Arize Phoenix add first-class understanding of these concepts on top of that same span/trace foundation: automatically capturing the full prompt/completion pair, token usage, and per-call cost, plus a UI purpose-built for browsing, filtering, and comparing agent traces — rather than a generic backend that treats an LLM call the same as any other timed unit of work.

Nothing about the underlying call changed. What changed is how much of its actual content the tracing layer understood well enough to surface.

LangSmith / Phoenix-style trace

Captured automatically by the LLM-aware wrapper, no manual attribute calls:

LLM call: call_llm duration: 480ms model: claude-sonnet-5 prompt: "Summarize these 4 orders for a July 2026 report: ord-101 ($612, 3 items), ord-114 ($780, 2 items)..." completion: "Found 4 orders over $500 from July 2026, totaling $2,848 across 10 items..." input_tokens: 310 output_tokens: 142 cost: $0.0071

Notice exactly what's missing on the left and present on the right: the raw span has NO record of what was actually asked or what was actually answered — llm.output_tokens is a number a developer chose to track, but the actual PROMPT and COMPLETION text simply aren't there unless someone specifically wrote code to dump them into attributes too (and even then, most teams don't, because raw attribute dumping wasn't designed with prompt-sized text payloads in mind). The right side has all of that, plus a cost figure computed automatically from the token counts and the known per-token pricing for that model — something raw OpenTelemetry has no mechanism to compute at all, because it doesn't know it's looking at an LLM call in the first place.

Problem 1 · Naming exactly which fields a raw OTel span is missing for a given debugging question

A teammate asks: "our LLM cost tripled this week — which specific calls got more expensive, and was it more tokens per call or a higher per-token price?" Using section 1's gap, explain why a raw OpenTelemetry span (with only llm.model and llm.output_tokens set) can partially answer this but an LLM-aware trace answers it completely.

Show solution
Partial answer from the raw span: llm.output_tokens IS present, so you COULD compute "average output tokens per call this week vs last week" and see if that number rose -- this is one real half of the question, and it works because output_tokens happens to be a field this particular raw span was manually configured to track. What the raw span structurally cannot answer: whether the PRICE per token changed (e.g. a silent model swap from a cheaper to a pricier model for some calls) requires knowing model name PER CALL and cross- referencing it against that model's actual per-token pricing -- llm.model is present here, but nothing in raw OpenTelemetry computes cost from it, because raw OTel has no built-in pricing table for any model at all. You'd have to manually join span data against an external pricing sheet yourself, span by span, to reconstruct this. An LLM-aware trace answers the full question directly: cost is already computed per call (section 2's table), so you can directly compare week-over-week cost broken down by model and by token count without any manual join -- exactly the reason section 1 called cost computation a capability raw OpenTelemetry has no mechanism for at all, not just a field nobody happened to set.
Problem 2 · Deciding whether a raw OTel-only setup is sufficient for a given team

A small team's service makes exactly one LLM call per request, with no branching agent logic, and they only ever need to know request latency and error rate. Do they need LangSmith or Phoenix on top of raw OpenTelemetry? Justify using section 1's reasoning about what the LLM-aware layer is actually FOR.

Show solution
Probably not, or only marginally -- LangSmith/Phoenix earn their value specifically when you need to inspect or compare PROMPT/COMPLETION CONTENT, token-level cost, or browse/filter across many LLM-specific traces (section 1's whole argument). A team that only ever needs latency and error rate is asking exactly the kind of question raw OpenTelemetry was already built for -- duration and status are core, generic span fields, no LLM-specific understanding required at all. This directly mirrors trajectory_based_evals.html's Problem 3 reasoning about when a specialized eval type is or isn't worth adding: the extra tool earns its keep when the SPECIFIC gap it closes (here: prompt/ completion/cost visibility) is actually a question you need answered. For a single-call, no-branching service tracking only latency/error rate, that gap is simply not being asked about, so a generic OTel setup plus a basic dashboard is sufficient -- though the moment this team wants to debug WHY a specific request produced a bad answer, or wants to track spend, they'd hit exactly the wall section 1 describes and need the LLM-aware layer at that point, not before.
Problem 3 · Explaining why LangSmith/Phoenix are built ON TOP of spans/traces, not instead of them

Using opentelemetry_basics.html's section 1 nesting model, explain why an LLM-aware trace for call_llm STILL needs to be a span nested inside handle_request, rather than a totally separate kind of record with no relationship to the rest of the request's trace.

Show solution
Because the LLM call didn't happen in isolation -- it happened AS ONE STEP inside a larger request (handle_request), alongside other spans like call_database (opentelemetry_basics.html section 1). If the LLM-aware capture produced a totally disconnected record with no parent relationship, you'd lose the ability to answer questions that require the LLM call's position IN CONTEXT: was this slow LLM call the reason the whole request was slow, or was call_database the bottleneck instead? Did this specific LLM call happen as part of THIS specific user's request, or some other one? This is exactly why LangSmith and Phoenix are built as an ADDITIONAL LAYER of understanding on top of the same span/trace tree structure, not a replacement for it -- the call_llm span still nests inside handle_request exactly as section 1's nesting model requires, still shares the same trace_id, and still has a start time, end time, and parent reference. What's different is that THIS particular span ALSO carries the LLM-specific fields (prompt, completion, cost) an LLM-aware wrapper knows to attach automatically -- the tree structure that makes a trace a trace, per opentelemetry_basics.html section 1's interview-ready definition, is unchanged; only the richness of one node's attributes is enhanced.
Problem 4 · Estimating cost from token counts and pricing, by hand

Using section 2's example call (310 input tokens, 142 output tokens), suppose the model's pricing is $3 per million input tokens and $15 per million output tokens. Compute this call's exact cost, and explain why an LLM-aware tool can automate this while raw OpenTelemetry cannot.

Show solution
Input cost: 310 tokens * ($3 / 1,000,000) = $0.00093 Output cost: 142 tokens * ($15 / 1,000,000) = $0.00213 Total: $0.00093 + $0.00213 = $0.00306, which rounds to roughly $0.0031 -- close to (and illustrating the same order of magnitude as) section 2's displayed $0.0071 figure for a slightly larger example call. Why an LLM-aware tool can automate this and raw OpenTelemetry cannot: computing this number requires knowing (a) both token counts separately (input AND output, since they're priced differently) and (b) a per-model pricing table mapping model name to its specific input/output rates. Raw OpenTelemetry has neither built in -- it has no concept of "this model costs $X per token" at all, per section 1's core point, because pricing is an LLM-domain-specific fact, not a generic tracing concept. An LLM-aware tool ships with (or lets you configure) exactly this pricing table per supported model, so the moment it captures model name + input/output token counts (which it does automatically, per section 1), it can immediately compute cost with no extra instrumentation code required per call site.
Problem 5 · Designing what to instrument first if adopting an LLM-aware tool on an existing OTel setup

A team already has raw OpenTelemetry spans for every service, including several call_llm-style spans across different agents. They're adopting an LLM-aware tool. Using this lab's reasoning, what's the highest-value first step, and why is instrumenting every non-LLM span (like call_database) NOT the priority?

Show solution
Highest-value first step: wrap specifically the LLM call sites (every call_llm-equivalent span across their agents) with the LLM-aware tool's instrumentation, so prompt/completion/token/cost capture becomes automatic for exactly the spans where raw OpenTelemetry was structurally blind per section 1 -- this closes the actual gap the adoption is meant to close, immediately, for the highest-value data. Why call_database and other non-LLM spans are NOT the priority: per section 1's whole argument, raw OpenTelemetry already handles generic, non-LLM spans perfectly well -- duration, name, generic attributes are exactly what it was designed for, and an LLM-aware tool adds nothing NEW for a database call the way it does for an LLM call (there's no "prompt," "completion," or per-token cost concept for a SQL query to begin with). Re-instrumenting call_database spans with the LLM-aware tool would cost migration effort for zero additional capability gained -- the entire value proposition established in section 1 is specifically about the LLM-shaped gap, so effort belongs there first, leaving non-LLM spans exactly as they already are under plain OpenTelemetry.
