EVALS & OBSERVABILITY LAB · MULTI-STAGE DOCKER BUILDS

The compiler that built your app has no business shipping inside it.

A naive Dockerfile installs gcc, dev headers, and every build tool it needs, compiles the app, and ships ALL of that — compiler included — in the final image. A multi-stage build splits this into two genuinely separate stages: one that has the full build toolchain and produces compiled artifacts, and a second, completely separate final stage that starts from a slim base image and copies over ONLY those artifacts — the compiler, the dev headers, the build cache, never make it into the image that actually runs in production.

Stage 1 — build tools, compilers, dev headers, compiles the app
Stage 2 — slim base, copies ONLY the compiled output
1.2GB → 150MB, same app, none of the toolchain shipped

01 — Why the thing that BUILDS your app shouldn't be the thing that RUNS it

Separating build & runtime stages

Start here, before any Dockerfile. Think about a furniture workshop that ships finished chairs to customers. The workshop itself is full of things a customer's living room has no use for — table saws, sanders, sawdust, half-cut lumber, glue clamps. Nobody would ever ship the ENTIRE WORKSHOP to a customer's house just because the workshop is where the chair got built — you ship only the finished chair. A multi-stage Docker build applies exactly this separation to software: the environment that COMPILES your application (full of compilers, dev headers, build caches, package managers) is not the environment that should RUN it in production. Only the finished, compiled result needs to ship.

Concretely, a multi-stage Dockerfile declares two (or more) FROM blocks in the same file, each one a separate, independent stage. The first stage — call it builder — starts from a full-featured base image with a compiler and build tools, installs whatever's needed to compile the application's dependencies (e.g. Python packages with native C extensions, which need gcc to build), and produces compiled artifacts, like Python wheels. The second, FINAL stage starts completely fresh from a minimal base image — no compiler, no dev headers — and uses Docker's COPY --from=builder instruction to pull ONLY the specific compiled artifacts out of the first stage. Everything else in the builder stage — the compiler itself, intermediate build files, package manager caches — simply never exists in the final image, because the final image was never built FROM the builder stage's filesystem, only handed a few specific files copied out of it.

# Dockerfile — a real Python app, two genuinely separate stages # STAGE 1: "builder" — has the full compiler toolchain FROM python:3.12 AS builder RUN apt-get update && apt-get install -y --no-install-recommends \ gcc python3-dev libpq-dev \ # ^ compiler + dev headers needed to build native-extension wheels && rm -rf /var/lib/apt/lists/* WORKDIR /build COPY requirements.txt . # compiles every dependency into a wheel file — gcc runs HERE, in this stage only RUN pip wheel --no-cache-dir --wheel-dir /build/wheels -r requirements.txt # STAGE 2: "runtime" — a completely separate, minimal image # note the fresh FROM — this does NOT inherit anything from "builder" FROM python:3.12-slim AS runtime WORKDIR /app # pull ONLY the compiled wheels out of the builder stage by name COPY --from=builder /build/wheels /wheels RUN pip install --no-cache-dir /wheels/*.whl && rm -rf /wheels # application code, never touched by the build toolchain at all COPY . . # gcc, python3-dev, libpq-dev, the pip cache, apt's package lists -- # NONE of it exists anywhere in this final image. It was never FROM builder. CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0"]

Interview-ready definition: a multi-stage Docker build declares two or more independent FROM blocks in one Dockerfile — an earlier "build" stage that includes the full toolchain needed to compile the application (compilers, dev headers, package managers) and produces compiled artifacts, and a later, separate "runtime" stage that starts fresh from a minimal base image and uses COPY --from=<stage> to pull in ONLY the specific compiled outputs it actually needs. Because the final stage is never built FROM the build stage's filesystem — it only copies a few named files out of it — none of the build stage's toolchain, intermediate files, or caches exist in the image that ships to production, even though that toolchain was absolutely necessary to PRODUCE the artifacts the final image runs.
02 — What a 1.2GB image costs you that a 150MB image doesn't

Shrinking image size, with real numbers

Start here, before the numbers. Think about the difference between mailing someone a fully-stocked toolshed versus mailing them just the one finished birdhouse they asked for. Both technically "contain" the birdhouse. But the toolshed is heavier to ship, costs more, takes longer to arrive, and gives a thief who intercepts the package a lot more to work with than the birdhouse alone would. A bloated Docker image is the toolshed; a multi-stage-built image is just the birdhouse.

Why this difference actually matters in production, beyond just "smaller is tidier":

1.2GB image — what it costs

Slower to docker pull on every deploy and every new node that joins a cluster — at scale, this adds real minutes to rollout time. A larger attack surface: gcc, dev headers, and apt package lists are all things a compromised container could potentially use, and CVE scanners flag vulnerabilities in packages that were never even needed at runtime. Higher registry storage cost and higher network transfer cost, multiplied across every image push and every node pull.

150MB image — what you get back

Pulls in a fraction of the time — meaningfully faster autoscaling and faster rollback if a blue-green flip (per backend/cicd_gating_system_design.html) needs the new image pulled onto fresh nodes quickly. A smaller attack surface — no compiler sitting in a container an attacker might otherwise be able to abuse to build and run malicious code in-place. Lower storage and transfer cost, which compounds across every build in a CI pipeline that publishes many images per day.

Interview-ready definition: shrinking image size via multi-stage builds means excluding an application's build-time-only dependencies (compilers, dev headers, build caches) from the image that actually runs in production, since those dependencies were necessary to PRODUCE the compiled artifacts but serve no purpose at runtime. This matters at scale for three concrete reasons: faster image pulls (directly affecting deploy and autoscaling speed), a smaller attack surface (fewer packages that could contain exploitable vulnerabilities or be abused if the container is compromised), and lower storage/transfer cost, all of which compound across every deploy, every autoscaled node, and every CI build in a real production system.

Problem 1 · Tracing exactly what COPY --from=builder does and doesn't bring across

Section 1's Dockerfile runs COPY --from=builder /build/wheels /wheels in the runtime stage. Precisely: does this instruction also bring gcc, or python3-dev, or the apt package cache into the runtime stage's filesystem? Explain exactly why or why not, in terms of what COPY --from actually does.

Show solution
No -- COPY --from=builder brings across ONLY the specific path named in the instruction (/build/wheels here), copied as files into the runtime stage's own filesystem. It does not "merge" the builder stage's filesystem into the runtime stage, and it does not bring across anything installed elsewhere in the builder stage (gcc, python3-dev, libpq-dev, apt's package lists) unless a COPY --from instruction explicitly names that specific path too. The runtime stage's FROM python:3.12-slim line starts it from a completely fresh, minimal filesystem -- the builder stage's filesystem never becomes the runtime stage's filesystem, or even a layer within it. COPY --from is best understood as "reach into a different, already- built stage and copy specific named files out of it into THIS stage," the same mental model as copying a few files off a USB drive rather than cloning the entire drive. Anything in the builder stage not explicitly named in a COPY --from instruction simply never exists in the runtime stage at all -- which is exactly the mechanism that makes gcc, dev headers, and the apt cache disappear from the final image without any explicit "uninstall" or cleanup step being necessary.
Problem 2 · Deciding whether the app's source code should be COPY'd in the builder or runtime stage

Section 1's Dockerfile does COPY . . (the application's own source code) in the RUNTIME stage, not the builder stage. Would it be functionally wrong to instead copy the source code into the builder stage and then COPY --from=builder it into the runtime stage alongside the wheels? What's the practical downside of doing it that way?

Show solution
It wouldn't be functionally WRONG in the sense of producing a broken image -- the app code would still end up in the runtime stage's filesystem either way, and the final running container would behave identically. But it's a worse design for a concrete, practical reason connected to Docker's LAYER CACHING: Docker caches each instruction's resulting layer, and reuses a cached layer on a later build as long as nothing that instruction depends on has changed. Application source code changes far more often than dependency lists (requirements.txt) do -- during normal development, nearly every commit touches source code but only occasionally touches dependencies. If source code were copied into the builder stage BEFORE the pip wheel compile step, then every single source code change would invalidate Docker's cache for that COPY instruction and everything after it in that stage -- forcing gcc to recompile every dependency's wheel from scratch on every build, even though the dependencies themselves didn't change at all. Keeping COPY requirements.txt + the wheel-building RUN early in the builder stage, and only copying application source code in the RUNTIME stage (or late in the builder stage, after the expensive compile step), means changing application code never invalidates the expensive dependency-compilation layer's cache -- a genuinely faster day-to-day build loop, not just a stylistic preference.
Problem 3 · Estimating the effect of a THIRD stage for test dependencies

A team wants to add pytest and other test-only dependencies (not needed at runtime) to their CI pipeline's build. Using section 1's two-stage structure, would you add these to the existing builder stage, the runtime stage, or a genuinely separate THIRD stage? Justify using this lab's core principle.

Show solution
A separate third stage -- call it "test" -- built FROM builder (so it inherits the compiled wheels and toolchain already present there, avoiding a redundant recompile), that additionally installs pytest and runs the test suite. Neither the existing builder nor runtime stage is the right fit: adding pytest to builder would work mechanically (it's already discarded, so it wouldn't bloat the FINAL image), but it conflates two genuinely different concerns -- "compile the app's real dependencies" and "install tools needed only to verify correctness" -- into one stage, making the Dockerfile harder to reason about and reuse independently (e.g. section 1's builder stage should ideally stay reusable even in a context that never wants to run tests as part of the image build). Adding pytest to runtime would be a direct violation of this lab's entire principle -- pytest has no purpose in a running production container and would bloat the shipped image exactly the way section 2 argued against. A dedicated test stage, built FROM builder (not FROM scratch, and not FROM the slim runtime base, since pytest needs the compiled wheels already present to actually run meaningful tests against the app), lets CI target that ONE stage specifically with `docker build --target test`, run the suite, and then completely discard that stage's image -- never publishing it, never letting pytest anywhere near the actual runtime image that ships. This is the same "each stage exists for exactly one purpose, and only the stages that need to ship actually get published" discipline section 1 established, just extended to a third stage.
Problem 4 · Diagnosing why a multi-stage build failed to shrink the image at all

A team rewrites their Dockerfile with two FROM blocks (looking correct at a glance) but the final image is still 1.1GB — barely smaller than the single-stage version. Looking at section 1's Dockerfile as the correct reference, name the single most likely mistake, and how you'd confirm it.

Show solution
The single most likely mistake: the final stage's FROM line is still pointing at the FULL builder image (or an equivalently large base) instead of a genuinely minimal one -- e.g. `FROM builder AS runtime` instead of `FROM python:3.12-slim AS runtime`. Using the builder stage itself (or inheriting from it) as the runtime stage's base means the runtime stage DOES include the full builder filesystem -- gcc, dev headers, apt caches and all -- with the COPY --from=builder instructions becoming redundant no-ops copying files that were already present. Section 1's whole size reduction depends on the final stage starting completely FRESH from a genuinely minimal base image and then selectively copying files IN, not starting from the large builder image and (implicitly) keeping everything already there. How to confirm it: run `docker history ` on the resulting image and look for layers corresponding to `apt-get install gcc python3-dev libpq-dev` -- per Problem 1's reasoning, those layers should be completely absent from a correctly-built multi-stage image's history, since COPY --from only ever brings across explicitly named paths. If those apt-get layers show up in the final image's history at all, the final stage is inheriting from the wrong base, exactly as suspected -- and the fix is checking that final stage's FROM line points at a slim base image, not at the builder stage or an equivalent full image.
Problem 5 · Designing the Dockerfile for a compiled-binary language instead of Python wheels

Apply section 1's exact same two-stage principle to a Go application instead of Python — Go compiles to a single static binary with no runtime interpreter needed at all. Sketch (in words, referencing section 1's structure) what the builder and runtime stages would each contain, and explain why the runtime stage for Go can be made even smaller than this lab's Python example.

Show solution
Builder stage: FROM golang:1.22 AS builder — a full Go toolchain image with the compiler, WORKDIR set, source code copied in, and `go build -o app .` run to produce a single statically-linked binary (Go, unlike Python's C-extension wheels, typically compiles everything -- including most dependencies -- directly into one self-contained executable, no separate interpreter or shared libraries required at runtime). Runtime stage: FROM a base image that is smaller even than python:3.12-slim -- commonly `scratch` (Docker's literal empty base image, containing nothing at all) or a minimal image like `gcr.io/distroless/static`, then COPY --from=builder /build/app /app, and CMD ["/app"]. This is possible specifically BECAUSE a statically-linked Go binary has no runtime dependency on an interpreter, a package manager, or even a standard C library being present in the final image -- unlike the Python example, where the runtime stage still needs python:3.12-slim itself (a real interpreter, installed via pip) to execute the app at all. The GENERAL principle from section 1 -- final stage contains only what's needed to RUN, copied in from a stage that contained what was needed to BUILD -- is identical; what differs is how minimal "what's needed to run" can get, which depends entirely on whether the compiled language needs a runtime interpreter (Python: yes, needs the interpreter itself) or produces a fully self-contained binary (Go: no interpreter needed at all, enabling an even smaller final image than this lab's Python case).
