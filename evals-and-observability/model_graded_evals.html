Some qualities are easier to recognize than to write a rule for.

deterministic_evals.html's Practice Problem 5 already ran into the wall: "is this response helpful and empathetic" has no exact-match string, no JSON shape, and no single programmatic rule that captures it. Model-graded evals — using a separate LLM call as a judge, scoring an output against a rubric — exist for exactly this gap. But a judge is itself a model, with its own failure modes, not an oracle. This lab covers both halves honestly: how LLM-as-judge works, and the concrete, well-documented ways it goes wrong.

01 — When correctness can't be checked by a rule, ask a second judge

Using an LLM as judge

Start here, before any code. Think about grading a job applicant's writing sample versus grading their typing speed. Typing speed is a number — you time it, done, no judgment involved. But "is this cover letter well-written and persuasive" isn't something you can reduce to a formula ahead of time; instead, you hand it to someone qualified to judge writing, give them a rubric ("clarity, tone, structure, persuasiveness"), and trust their scored judgment — not because it's infallible, but because it's the best available tool for a question that genuinely requires judgment rather than measurement. Model-graded evals apply exactly this idea to LLM outputs: when a quality can't be reduced to an exact-match string, a schema, or a programmatic rule, a SEPARATE LLM call — the "judge" — reads the output (and often the original input and a rubric) and produces a score.

The key structural fact: the judge is a DIFFERENT call from the one that produced the output being evaluated — usually the same or a different model, invoked fresh, with no memory of having generated the answer, given only the rubric and the output to assess. This separation matters: the judge's job is strictly evaluation, not generation, and it should be prompted narrowly enough that its entire task is producing a score plus (ideally) a justification.

# a rubric-based judging prompt for the model_graded_evals task JUDGE_PROMPT = """You are evaluating an AI agent's response for QUALITY, not correctness of facts. ORIGINAL REQUEST: {original_request} AGENT'S RESPONSE: {response} Score the response from 1-5 on each of these dimensions: - Clarity: is the response easy to understand? - Faithfulness: does it accurately reflect only what the source data actually said, without inventing details? - Completeness: does it address everything the request asked for? Respond with ONLY a JSON object: {"clarity": <1-5>, "faithfulness": <1-5>, "completeness": <1-5>, "justification": ""}"""

Notice the judge prompt asks for a SCORE on named dimensions plus a short justification, not a bare "good" or "bad" — this mirrors json_schema_tool_specs.html's discipline of specifying exactly the output shape wanted, applied here to a scoring call rather than a tool call. A justification-free score is much harder to audit later when a human wants to understand WHY the judge rated something the way it did.

Interview-ready definition: a model-graded eval uses a separate LLM call — the judge — to score an output against an explicit rubric, for qualities that are easier to recognize than to specify as an exact rule (coherence, faithfulness to source material, helpfulness, tone). It fills the gap deterministic evals structurally cannot: deterministic checks can only ever verify what they were explicitly programmed to check, while a judge model can assess genuinely open-ended qualitative properties the same way a human reviewer would, at the cost of introducing the judge model's own imperfect judgment as a new, non-deterministic source of potential error into the evaluation itself.
02 — The judge is not a neutral oracle — it has its own predictable biases

Failure modes of model-graded evals

Start here, before trusting a judge score. Think about a human interviewer who unconsciously rates confident-sounding candidates higher regardless of actual answer quality, or who scores the SECOND candidate they see slightly differently than the first purely because of ordering, not merit, or who might rate the exact same answer differently on a good day versus a bad one. None of these make the interviewer useless — but a hiring process that doesn't account for these known biases will systematically produce skewed results. LLM judges have documented, analogous biases, and treating a judge's score as ground truth without accounting for them repeats the same mistake.

Length bias

Judge models have a well-documented tendency to rate longer, more verbose answers higher, independent of actual quality — a concise, correct answer can score lower than a bloated, padded one purely because length reads as "more thorough" to the judge, even when the extra length adds no real information.

Position bias

When a judge compares two candidate answers side by side ("which is better, A or B"), the judge's preference can shift measurably based on which answer is presented FIRST versus SECOND — the same two answers, with positions swapped, can produce a different verdict, revealing that the judgment is partly tracking position rather than purely content.

Inconsistency across repeated judgments

Asking the same judge to score the exact same output twice, in separate calls, does not reliably produce the exact same score — sampling randomness in the judge's own generation means a judge is not a fixed, deterministic function the way deterministic_evals.html's checks are, even when judging literally identical input.

A trap worth naming directly: it's tempting to think "model-graded evals replace deterministic evals" once qualitative judgment is available. They don't — they're for genuinely DIFFERENT questions. A judge should never be asked to verify something a deterministic check could verify more cheaply and more reliably (does this JSON have the right fields? use schema validation). Reserve the judge for exactly the qualities that resist a rule — and even then, treat its score as one noisy signal, not ground truth, mitigated by techniques like averaging across repeated judgments, randomizing presentation order for pairwise comparisons, and using an explicit rubric with named dimensions rather than one vague "rate this 1-10."
Interview-ready definition: model-graded evals have three well-documented failure modes: length bias (favoring longer/more verbose outputs regardless of actual quality), position bias (a pairwise comparison's verdict shifting based on presentation order rather than content alone), and inconsistency (the same judge producing different scores for the identical output across repeated calls, since the judge is itself a non-deterministic model, not a fixed function). None of these make model-graded evals useless — they make them a NOISY, imperfect signal that needs mitigation (randomized ordering, repeated sampling and averaging, explicit rubrics) rather than a ground-truth oracle to be trusted uncritically.

Problem 1 · Choosing between deterministic and model-graded for a stated task

An eval needs to check whether a generated email reply (1) contains a valid unsubscribe link and (2) is polite in tone. Using both this lab and deterministic_evals.html, which check type fits each requirement, and why can't one eval type cover both?

Show solution
"Contains a valid unsubscribe link" -- a rule-based deterministic check (e.g. a regex or URL-parse check that a specific pattern/link is present). This is a mechanically verifiable property with no ambiguity about what counts as satisfying it. "Is polite in tone" -- a model-graded eval. Politeness is exactly the kind of quality section 1 describes: easier to recognize than to specify as an exact rule. There's no regex or schema that reliably captures "politeness" across the space of ways a reply could be worded. Why one eval type can't cover both: they're structurally different kinds of properties. A rule-based check could never meaningfully assess tone (no programmatic rule captures "politeness" in general), and a judge model is comparatively expensive, slower, and non-deterministic -- using it to check "does this contain a specific URL pattern" would be strictly worse than a regex on every axis (cost, speed, reliability) for a property a regex already checks perfectly. The correct eval suite for this task runs BOTH checks, each doing the job it's actually suited for -- this is the same "cheapest sufficient tool" reasoning sql_vs_nosql.html applies to storage engines, just applied here to eval strategy choice.
Problem 2 · Diagnosing a specific judge failure from a described symptom

A team runs a pairwise judge comparison ("is Response A or Response B better") 10 times on the same fixed pair, alternating which response is labeled A vs B each time. Response A (by content, not label) wins 8 times when placed first, and only 3 times when placed second. Name the specific failure mode and what mitigation directly addresses it.

Show solution
This is position bias, and it's diagnosed exactly the way this scenario is constructed to reveal it: the SAME content (by actual substance, not by label) wins far more often when it happens to be presented FIRST (8/times-first) than when presented second (3/times-second) -- a large, systematic swing tied to PRESENTATION ORDER rather than to the content's actual quality, which should be judge-order-independent if the judge were purely evaluating merit. The direct mitigation: run each pairwise comparison TWICE per pair, once with each ordering (A-then-B and B-then-A), and either average the two results or require the same verdict in both orderings before trusting it -- exactly the "randomize/counterbalance presentation order" mitigation section 2 names. If a judge's verdict flips depending purely on which slot a response is placed in, the raw single-ordering verdict isn't trustworthy on its own; the double-ordering check either cancels out the order effect (by averaging) or explicitly surfaces cases where the judge is genuinely uncertain (disagreeing verdicts across orderings), which is itself useful information a single-ordering run would have hidden.
Problem 3 · Redesigning a rubric to resist length bias

Using section 1's judge prompt template and section 3's live demo, rewrite the rubric so it explicitly resists rewarding Candidate B's padding over Candidate A's concision. What specific instruction addition makes the biggest difference?

Show solution
The single highest-leverage addition: explicitly instruct the judge to score CONCISION as its own named dimension, and explicitly warn against conflating length with quality -- e.g. adding a line like: "Concision: does the response convey the necessary information without unnecessary padding or repeated phrasing? A shorter response that says the same thing is NOT worse than a longer one -- do not reward length for its own sake." Naming concision as its OWN scored dimension (rather than leaving it implicit inside "clarity" or "completeness") forces the judge to explicitly reckon with length as a factor it must actively evaluate, rather than letting length bias operate silently in the background the way it does when the rubric only asks for vague, undifferentiated "quality." This mirrors the general principle from json_schema_tool_specs.html of making implicit requirements EXPLICIT in a spec -- an unstated expectation ("don't reward padding") is far more likely to be silently violated than one spelled out as its own named, scored criterion the judge is directly instructed to weigh. This doesn't ELIMINATE length bias (the judge is still an imperfect model, and could still get it wrong) -- but it materially reduces it compared to a rubric that never mentions length or concision at all, which is the realistic bar a rubric redesign can actually clear.
Problem 4 · Reasoning about mitigating judge inconsistency

Using section 2's inconsistency failure mode, propose a concrete mitigation for a team that needs a STABLE score for the same output across multiple eval runs (e.g. for tracking quality trend over time in a dashboard), and explain the trade-off it introduces.

Show solution
The standard mitigation: run the judge call MULTIPLE times (e.g. 3-5 independent calls) on the same output and take the median or average score, rather than trusting any single judge call's result. Since inconsistency comes from the judge's own sampling randomness, averaging across several independent samples smooths out that noise the same way averaging multiple noisy measurements of anything reduces the influence of any one outlier reading. The trade-off: this multiplies the cost and latency of the eval by however many repeated judge calls are used (3-5x more judge-model calls per single scored output), which matters at scale if a suite runs against thousands of outputs regularly. It also doesn't eliminate inconsistency, only reduces its practical impact on the AVERAGED score -- a team still shouldn't treat the averaged number as perfectly precise to the decimal point, just meaningfully more stable than any single raw judge call. A cheaper partial mitigation that doesn't fully solve inconsistency but helps: setting the judge's own sampling temperature to 0 (deterministic decoding) where the judge model supports it, which reduces (though may not fully eliminate, depending on the underlying model's guarantees) run-to-run variance for identical input without needing multiple calls at all -- a real trade between mitigation strength (multi-sample averaging is more robust) and cost (temperature=0 is nearly free by comparison).
Problem 5 · Connecting model-graded evals to permission scoping's least-privilege reasoning

A judge model is given access to call the same tools the agent under evaluation used, "in case it needs to double-check a fact." Using permission_scoping.html's reasoning from Month 4, why is this a design mistake even if it seems helpful?

Show solution
A judge's job, per section 1, is strictly EVALUATION -- reading the original request, the rubric, and the agent's already-produced output, then scoring it. It never needs to independently GENERATE new actions or fetch new data to do that job; everything it needs to score the output is already in front of it (or should be, if the eval was set up correctly with sufficient context). Granting it tool-calling access anyway is exactly the least-privilege violation permission_scoping.html warns about: a component gets capabilities beyond what its actual, stated job requires, purely because those capabilities happened to be convenient or "might help." Concretely, if a judge can call the same tools the agent used, a manipulated or buggy judge prompt (or content the judge reads while "double-checking" a fact, which could itself carry an injected instruction, per prompt_injection_risks.html) now has an actual attack surface it never needed -- it could take real actions (write, delete, external calls) that have nothing to do with producing a score. The correct design keeps the judge strictly read-only over the context it's given, with no tool- calling capability at all, mirroring section 1's own "the judge's job is evaluation, not generation" boundary at the permission level, not just the conceptual level -- least privilege applied at design time again, exactly as final_multi_agent_workflow.html's Problem 4 argued for the agent itself.
