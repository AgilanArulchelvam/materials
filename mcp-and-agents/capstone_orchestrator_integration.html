01 — The decision that breaks or survives multiple workers

Where orchestrator state lives

Start here, before writing a line of orchestrator code. Think about a hotel concierge taking a multi-step request — "book me a table, then a car, then text me the confirmation" — versus a sticky note the concierge keeps at their OWN desk to track progress. If there's only ever one concierge on shift, the sticky note works fine. But the moment the hotel adds a second concierge desk to handle more guests at once, a request that started with concierge A but gets checked on by concierge B is a problem — B has no sticky note, no memory of where A left off. This is exactly the question a stateful orchestrator has to answer before anything else: when uvicorn_gunicorn_workers.html's worker-count heuristics say "run N workers, not one," where does an in-progress multi-turn run's state live so ANY worker can pick up the next step?

The scaffold's app/orchestrator/ package is a Python module inside a FastAPI process — and FastAPI, run under uvicorn main:app --workers 4 (or Gunicorn managing multiple Uvicorn workers, per backend/uvicorn_gunicorn_workers.html), means FOUR separate OS processes, each with its own memory space. An in-process Python dict keyed by run_id works perfectly in local dev (one worker, one process) and breaks silently the moment a second worker exists: request 1 of a multi-turn run lands on worker A, request 2 (same run_id, continuing the same conversation) lands on worker B via round-robin load balancing, and worker B has never heard of that run.

In-process state (dict, per-worker)

Zero network hops per state read/write — fastest possible. Correct ONLY if the deployment guarantees exactly one worker, ever (true for local dev, false for almost any real deployment scaled past a single process). Breaks silently, not loudly: no error, just a "run not found" or a fresh, wrong state, on whichever worker didn't handle the previous turn.

External store (Redis / Postgres, shared)

Every worker reads/writes the same state, so which worker handles which request stops mattering — a real precondition for horizontal scaling. Costs a network round trip per state access, and adds a dependency the scaffold's /readyz check now has to verify (same pattern as the MCP server dependency check in capstone_scaffold_fastapi_mcp.html section 2).

# app/orchestrator/state.py # Redis-backed run state -- any worker can read/write any run_id. # Redis is the right default here specifically because orchestrator # state is short-lived, high-write, and doesn't need SQL's durability # guarantees the way finalized traces/evals do (that's Postgres's job, # per database/eval_trace_schema_finalization.html) -- see problem 1. import json from redis.asyncio import Redis from app.config import get_settings class RunStateStore: def __init__(self, redis: Redis): self.redis = redis async def load(self, run_id: str) -> dict | None: raw = await self.redis.get(f"run:{run_id}") return json.loads(raw) if raw else None async def save(self, run_id: str, state: dict) -> None: # TTL matters: an abandoned run's state shouldn't live forever await self.redis.set(f"run:{run_id}", json.dumps(state), ex=3600) def get_run_state_store() -> RunStateStore: settings = get_settings() redis = Redis.from_url(settings.redis_url) return RunStateStore(redis)
Interview-ready definition: a stateless orchestrator PROCESS with all mutable run state externalized (Redis, or Postgres for anything that must survive a Redis restart) is what makes horizontal scaling of the orchestrator itself possible — any worker, any request, same answer — at the cost of a network round trip per state access; an in-process store is a correctness bug waiting for a second worker, not a valid optimization, unless the deployment topology genuinely guarantees a single process forever.
02 — The thin layer between HTTP and the orchestrator

Wiring the FastAPI route to the orchestrator

Start here, before touching the orchestrator's internals. Think about a restaurant's host stand versus the kitchen. The host takes your name, seats you, and hands your order to the kitchen — the host does NOT cook. Section 4 of capstone_scaffold_fastapi_mcp.html already named this exact split for a hypothetical chat.py router: a thin layer that calls into app/orchestrator/, per fastapi_routing_and_pydantic.html's routing patterns. This section writes that router for real.

# app/routers/chat.py -- new router, registered in create_app() # right after health.router and mount_mcp(app), per the scaffold's # ordering rule (register health first, everything else after) from fastapi import APIRouter, Depends, HTTPException from pydantic import BaseModel from app.orchestrator.run import Orchestrator, get_orchestrator router = APIRouter(prefix="/chat", tags=["chat"]) class ChatRequest(BaseModel): run_id: str | None = None # None => start a new run message: str class ChatResponse(BaseModel): run_id: str reply: str done: bool @router.post("", response_model=ChatResponse) async def chat( req: ChatRequest, orchestrator: Orchestrator = Depends(get_orchestrator), ): # the ENTIRE job of this handler: translate HTTP in, call the # orchestrator, translate its result back to HTTP out -- no # agent logic, no tool-calling logic, lives here try: result = await orchestrator.step(run_id=req.run_id, user_message=req.message) except orchestrator.errors.RunNotFound: raise HTTPException(status_code=404, detail="run_id not found or expired") return ChatResponse(run_id=result.run_id, reply=result.reply, done=result.done)

Notice what is deliberately absent from this handler: no loop, no MCP client calls, no knowledge of which agent handles what. Every one of those decisions belongs to the orchestrator, reached through exactly one call — orchestrator.step(...) — mirroring the same separation dependency_injection.html draws between route handlers and business logic, and the same reasoning capstone_scaffold_fastapi_mcp.html's practice problem 2 used to keep LLM-calling logic out of the MCP tool handler.

Interview-ready definition: a route that "wires in" an orchestrator should be translatable in one sentence — "accept a request shape, call one orchestrator method, return its result shape" — with zero orchestration logic inlined; if a router function needs its own loop or its own branching on agent type, the orchestration logic has leaked into the wrong layer.
03 — The orchestrator is an MCP client, not a re-implementation of one

How the orchestrator dispatches to MCP tools

Start here, before writing the dispatch logic. Think about a project manager who delegates specific tasks to specialists rather than doing every task themselves — the PM's job is deciding WHO does WHAT and WHEN, not replicating each specialist's skill. multi_agent_delegation.html's coordinator does exactly this across sub-agents; this orchestrator does the same thing one layer down, delegating individual actions to MCP tools already registered in the scaffold's app/mcp_servers/ (the ping tool from section 3 of the scaffold, plus whatever real tools — including lab 2's hybrid search tool — get added there).

# app/orchestrator/run.py from dataclasses import dataclass from uuid import uuid4 from mcp import ClientSession from app.orchestrator.state import RunStateStore, get_run_state_store from app.orchestrator.mcp_client import get_mcp_session # thin wrapper around ClientSession @dataclass class StepResult: run_id: str reply: str done: bool class Orchestrator: def __init__(self, store: RunStateStore, mcp: ClientSession): self.store = store self.mcp = mcp # connects to THIS SAME FastAPI process's # /mcp/sse endpoint -- section 3 of the scaffold async def step(self, run_id: str | None, user_message: str) -> StepResult: is_new = run_id is None run_id = run_id or str(uuid4()) state = {"turns": [], "status": "running"} if is_new else ( await self.store.load(run_id) or self.errors.RunNotFound() ) # 1. the orchestrator DECIDES which tool this turn needs -- # real routing logic (classification, a planning agent, # a fixed graph edge per stateful_graphs.html) goes here tool_name, tool_args = self._route(user_message, state) # 2. dispatch through the MCP protocol -- the SAME tools/call # JSON-RPC shape mcp_fundamentals_jsonrpc.html teaches, # NOT a direct Python function call into the tool's code tool_result = await self.mcp.call_tool(tool_name, tool_args) # 3. fold the result back into state and decide if the run is done state["turns"].append({"user": user_message, "tool": tool_name, "result": tool_result}) done = self._is_terminal(state) state["status"] = "done" if done else "running" await self.store.save(run_id, state) return StepResult(run_id=run_id, reply=self._render_reply(tool_result), done=done)

The critical design choice here: the orchestrator calls self.mcp.call_tool(...) — going THROUGH the MCP protocol, exactly as an external MCP client would, even though the MCP server it's calling is mounted in the same process (per the scaffold's SSE-mounting choice). This looks like unnecessary overhead until you consider why: it keeps every tool invocation, whether from this orchestrator or from a future external agent, going through the SAME validated, schema-checked, loggable path — which is exactly what lab 3's instrumentation hooks into in section 2, rather than needing two different instrumentation strategies for "internal" and "external" tool calls.

Interview-ready definition: an orchestrator dispatches to tools by acting as an MCP CLIENT against the MCP server(s) it has access to — including one mounted in its own process — never by importing and calling a tool handler's Python function directly, because doing so bypasses the protocol's schema validation and, downstream, any instrumentation attached to the MCP layer specifically.

What to notice: the orchestrator's own state (state["turns"], state["status"]) persists to the external store BETWEEN dispatch steps, not just at the very end — so if the process crashed mid-run after the search tool call but before the DB tool call, a resumed run (on any worker, per section 1) would see turns: [search_result] already saved and wouldn't have to redo it. This is the practical payoff of externalizing state: partial progress survives a crash, not just a graceful completion.

Practice problems

Problem 1 · Redis vs Postgres for run state

Section 1 chose Redis for in-flight orchestrator state, while database/eval_trace_schema_finalization.html uses Postgres for finalized traces and eval results. Why is this split correct rather than arbitrary — why not put run state in Postgres too, or traces in Redis?

Show solution
The split tracks a real difference in access pattern and durability requirement, not just habit. In-flight run state is: written on every single turn (high write rate), read almost immediately after (low latency need), and DISPOSABLE once the run finishes or times out (a 1-hour TTL is fine, per section 1's state.py). Redis is built exactly for that shape -- an in-memory store with cheap writes and a built-in expiry mechanism, at the cost of weaker durability guarantees (a Redis restart without persistence configured can lose recent writes). Finalized traces and eval results are the opposite shape: written once per completed run (much lower write rate), read later and often in aggregate (dashboard queries scanning thousands of rows, per lab 3), and must NOT be lost -- they're the historical record this capstone's eval/tracing dashboard is built on. Postgres's durability (WAL, ACID transactions) and query capability (joins, aggregates, the indexes built in lab 5) are what that access pattern actually needs, and its higher per-write cost doesn't matter at a much lower write rate. Putting run state in Postgres would work but add unnecessary write latency and lock contention to every single orchestrator turn for a durability guarantee that state doesn't need. Putting finalized traces in Redis would work until the eval/tracing dashboard needed to run a real aggregate query (e.g. "p95 latency across last 1000 runs") that Redis has no native way to do efficiently, and until a Redis restart silently erased data the capstone is supposed to keep.
Problem 2 · Two requests, same run_id, arriving concurrently

Suppose a flaky client retries a request, so two POST /chat calls with the SAME run_id land on two different workers within milliseconds of each other. Walk through what section 1's Redis-backed RunStateStore, as written, does in this case — and whether it's actually safe.

Show solution
As written, it is NOT safe -- this is a classic read-modify-write race. Both workers call store.load(run_id) and get the SAME state (say, turns: [A]). Both independently compute their own next turn, append to their own in-memory copy of turns, and both call store.save(run_id, state) -- whichever save() call happens to run last simply OVERWRITES the other's result. The run ends up with only one of the two turns recorded, and worse, the orchestrator that "lost" may have already returned a reply to its caller claiming success. Two real fixes, both worth knowing: (1) a distributed lock around the load-modify-save sequence, acquired via Redis itself (SET run_id:lock NX with a short expiry, a real, common pattern for exactly this problem) so the second request blocks or fails fast instead of racing; or (2) making the save() step a Redis-native atomic operation -- e.g. representing turns as a Redis LIST and using RPUSH instead of load-full-state/mutate/save-full-state, so there's no window where two workers can both hold a stale copy. Locking is simpler to reason about and works for arbitrary state shapes; the atomic-operation approach is faster and avoids lock contention entirely but requires the state shape to map cleanly onto a Redis primitive, which isn't always true for a state dict with several loosely related fields.
Problem 3 · A tool call that never returns

Section 3's await self.mcp.call_tool(tool_name, tool_args) has no timeout. What specifically goes wrong for the orchestrated run — and for the FastAPI worker serving it — if the underlying MCP tool hangs indefinitely, and what's the fix?

Show solution
Without a timeout, the awaiting coroutine simply never resumes -- the orchestrator's step() call blocks forever, which means the FastAPI request handler that awaited orchestrator.step() also never returns, which means the client's HTTP connection hangs until ITS OWN timeout (or forever, for a client with none configured). Because this is async code, the WORKER PROCESS itself isn't blocked -- other requests on other connections keep being served by the same event loop -- but that one request, and whatever run_id it was progressing, is stuck: its Redis lock (if problem 2's fix is in place) is never released either, meaning a SECOND request against the same run_id would then also hang waiting for that lock. The fix is wrapping the call in asyncio.wait_for() with an explicit timeout, exactly the pattern capstone_scaffold_fastapi_mcp.html's own practice problem 1 used for the readiness check's MCP call: try: tool_result = await asyncio.wait_for( self.mcp.call_tool(tool_name, tool_args), timeout=10.0 ) except asyncio.TimeoutError: tool_result = {"error": "tool_timeout", "tool": tool_name} # still persist state and return a real (if degraded) reply -- # never leave the run silently stuck Critically, a timeout still needs the orchestrator to decide what happens NEXT -- fail the run cleanly, retry once, or fall back to a different tool -- rather than just converting an infinite hang into an exception that crashes the request. The state store's TTL (section 1) is the last line of defense: even a run that gets fully abandoned without a graceful timeout still expires out of Redis eventually rather than leaking memory forever.
