01 — Same tool logic, a different transport wrapper

The same calculator tool, exposed over HTTP+SSE

Start here, before the code. The previous lab's server had two parts that don't change at all — the list_tools/call_tool handlers implementing the actual "add two numbers" logic — and one part that changes completely: how those handlers get connected to a client. Swapping stdio for SSE means swapping out the transport wiring at the bottom of the file; the tool logic itself is untouched, because MCP was deliberately designed so tool implementations don't need to know or care which transport is carrying their messages.

from mcp.server import Server from mcp.server.sse import SseServerTransport from starlette.applications import Starlette from starlette.routing import Route, Mount import mcp.types as types server = Server("calculator-server") # IDENTICAL to the stdio version -- same tool, same schema, same logic. # Nothing about this handler changes when the transport changes. @server.list_tools() async def list_tools() -> list[types.Tool]: return [types.Tool( name="add", description="Add two numbers together", inputSchema={"type": "object", "properties": { "a": {"type": "number"}, "b": {"type": "number"}}, "required": ["a", "b"]}, )] @server.call_tool() async def call_tool(name: str, arguments: dict) -> list[types.TextContent]: if name == "add": return [types.TextContent(type="text", text=str(arguments["a"] + arguments["b"]))] raise ValueError(f"Unknown tool: {name}") # THIS is what actually changes: instead of stdio_server(), the server is # mounted as HTTP routes and run as a persistent web service. sse_transport = SseServerTransport("/messages") async def handle_sse(request): async with sse_transport.connect_sse(request.scope, request.receive, request._send) as (read, write): await server.run(read, write, server.create_initialization_options()) app = Starlette(routes=[ Route("/sse", endpoint=handle_sse), # client opens this to receive server → client messages Mount("/messages", app=sse_transport.handle_post_message), # client POSTs requests here ]) # run with: uvicorn calculator_sse_server:app --host 0.0.0.0 --port 8000 # this process now runs indefinitely as a normal web server, not spawned # per client the way the stdio version was.

Two HTTP endpoints replace the two pipes: GET /sse is the long-lived SSE stream the client opens to RECEIVE server-to-client messages (responses, notifications), and POST /messages is where the client SENDS its JSON-RPC requests as regular HTTP POST bodies. This is the same asymmetric shape as any SSE-based system — one persistent one-directional stream for server→client, and ordinary request/response HTTP for client→server — just carrying MCP's JSON-RPC messages instead of arbitrary event data.

Interview-ready definition: MCP-over-SSE exposes an MCP server as a persistent HTTP service with two endpoints: an SSE stream (typically GET /sse) the client opens to receive server-to-client JSON-RPC messages (responses and notifications), and a POST endpoint (typically /messages) the client uses to send JSON-RPC requests to the server. The tool-serving logic itself — the list_tools/call_tool handlers — is completely unchanged from the stdio version; only the transport layer connecting those handlers to a client differs, which is precisely why MCP separates "what a server does" from "how a client reaches it" as two independent concerns.
02 — Neither transport is strictly better — they fit different situations

stdio vs SSE, the real trade-offs

Start here, before the table. The previous lab ended by noting stdio's constraints (local-only, single-client, tightly-coupled lifecycle) were a genuine FIT for a laptop-local coding assistant, not a limitation. SSE inverts every one of those constraints — and inverting them isn't free; it trades stdio's simplicity for real infrastructure. Neither option is the "advanced" or "correct" one in general; each is the right answer for a different deployment shape.

stdio

Simple: zero infrastructure — no port, no HTTP server, no auth surface to design. Local-only: client and server must run on the same machine (the subprocess relationship requires it). Single-client: the pipes belong to exactly the one process that spawned them. Tightly coupled lifecycle: server dies with its one client, by construction.

SSE / HTTP

Networked: client and server can run on different machines entirely — the server just needs to be reachable at some URL. Multi-client: any number of independent clients can open their own /sse connection to the SAME running server. More infrastructure: needs a real web server process, a port, TLS for anything beyond localhost, and genuine auth (see the gateway design lab later this week) since it's now reachable by more than just its own parent process.

DimensionstdioSSE / HTTP
Where client & server runSame machine, requiredAny machine reachable over the network
How many clients per server instanceExactly one (the spawning process)Any number, concurrently
Server lifecycleSpawned per client, dies with itRuns independently, persists across client connects/disconnects

Best fitLocal dev tools, single-user coding assistantsShared/hosted tool servers, multi-user or multi-agent deployments
What doesn't change either way: the actual message content — JSON-RPC requests, responses, notifications carrying MCP's tools/resources/prompts operations — is identical under both transports, exactly as section 1's unchanged handler code demonstrates. This is a deliberate protocol design choice: MCP defines the MESSAGE layer and the TRANSPORT layer as genuinely separable concerns, so switching transports is a deployment decision, not a rewrite of what the server actually does.
03 — The one capability stdio structurally cannot offer

Multiple clients, one running server

Start here, before running it. The previous lab's Practice Problem 2 established WHY stdio can't support two simultaneous clients — the pipes belong to exactly one spawning parent. SSE's whole point is that this stops being true: the server is just running, independently, at some address, and any client that knows that address can open its own connection.

Interview-ready definition: because an SSE-transport MCP server runs as an independent, persistently-listening HTTP process rather than a per-client spawned subprocess, any number of separate client processes can open their own GET /sse connection to it concurrently, each with its own independent request/response traffic over POST /messages — the server handles each client's JSON-RPC session separately, but all clients are talking to the SAME running server instance and its same in-process state, which is structurally impossible under stdio's one-pipe-pair-per-spawn model. This multi-client capability is exactly what makes SSE (or other networked transports) the right choice once more than one consumer needs to reach the same tool-serving server — the next lab's gateway design builds directly on this, routing many clients' requests across potentially many such servers.

Problem 1 · Choosing a transport for a described deployment

A company wants ONE internal "database query" MCP server that data scientists across the whole org can call from their own individual notebooks/laptops. Which transport fits, and specifically which stdio constraint from section 2's table makes stdio unworkable here?

Show solution
SSE (or another networked transport) fits, not stdio. The specific blocking constraint is stdio's "same machine, required" + "exactly one client per server instance" pairing (section 2's table): stdio requires the client to SPAWN the server as its own local child process, which would mean every single data scientist's notebook/laptop would need to launch and run its OWN independent copy of the database-query server locally -- there would be no single shared server instance at all, just N separate spawned processes, one per user, each independently connecting to the database. That might even work mechanically, but it directly contradicts the stated requirement of "ONE internal server" that people across the org call INTO -- SSE's multi-client, network- reachable model (section 3) is what actually delivers a single shared server that many independent clients on many different machines can all connect to.
Problem 2 · Identifying what genuinely changes vs what doesn't when switching transports

Using section 1's code comparison, list specifically what code changed between the stdio version (previous lab) and the SSE version (this lab), and what stayed byte-for-byte identical. Why does this split matter for a team maintaining both?

Show solution
What stayed identical: the list_tools() and call_tool() handler functions -- the actual tool schema (name "add", the inputSchema, the required fields) and the actual business logic (arguments["a"] + arguments["b"]) are byte-for-byte the same in both versions, per section 1's explicit callout. What changed: everything below that -- how the handlers get wired to a client. The stdio version calls stdio_server() and server.run() against process stdin/stdout pipes inside an asyncio.run(main()) entrypoint. The SSE version instead creates an SseServerTransport, defines HTTP routes (GET /sse, POST /messages via Starlette), and gets run by a separate ASGI server process (uvicorn) rather than being launched directly as __main__. Why this split matters for a team maintaining both: it means the actual tool logic only needs to be written and tested ONCE and can be shared between both transport-specific entrypoints (e.g. as a shared module both a stdio_main.py and an sse_main.py import from), rather than duplicating and maintaining two separate copies of the "add two numbers" logic that could drift out of sync. A bug fix or a new tool added to the shared handler module automatically applies to BOTH transports without being implemented twice -- this is exactly the practical payoff of MCP deliberately separating the message/handler layer from the transport layer, rather than just a theoretical nicety.
Problem 3 · Reasoning about shared state across concurrent clients

Suppose the calculator server is extended with a stateful tool: "remember_number" (stores a number) and "recall_number" (returns whatever was last stored), using a single Python variable in the server process. Under SSE with 3 clients connected simultaneously (section 3), what could go wrong that would never happen under stdio, and why?

Show solution
Under SSE, one client's remember_number call could silently overwrite another client's previously stored value, because a SINGLE shared Python variable in the server process is genuinely shared across every concurrently connected client (section 3's finding: all clients talk to the SAME running server instance and its same in-process state) -- Client A calls remember_number(42), then Client B calls remember_number(99) before Client A calls recall_number(), and Client A gets back 99, not the 42 it stored, with no error or warning that anything unexpected happened. Under stdio, this exact bug is structurally impossible, because each client spawns its OWN separate server subprocess (section 2's "single- client" row) -- there is no OTHER client sharing that process's memory to begin with, so a single unscoped variable behaves exactly like private, per-session state without anyone having to design it that way on purpose. The fix under SSE: state that's meant to be per-client/per-session must be explicitly scoped to a session identifier (e.g. keyed by a session id established when each client connects), rather than stored in a single shared variable -- this is a real design responsibility SSE's multi- client model introduces that stdio's single-client model simply never requires anyone to think about, which is exactly the kind of "more infrastructure" cost section 2's trade-off table gestures at, made concrete.
Problem 4 · Explaining the two-endpoint asymmetry

Section 1's SSE server defines two separate HTTP routes: GET /sse and POST /messages. Why not just use ONE bidirectional endpoint for everything, the way stdio uses one pair of pipes symmetrically?

Show solution
The two-endpoint split exists because plain HTTP (unlike stdio's pipes, or unlike WebSockets) is fundamentally a REQUEST-then-RESPONSE protocol, not a symmetric always-open channel -- a standard HTTP connection doesn't let the server push a message to the client whenever it wants, outside of directly responding to a request that client just made. Server-Sent Events (referenced from backend/sse.html) specifically solves the "server needs to push to the client asynchronously" half of this by keeping ONE long-lived GET connection open that the server can write events into at any time -- but that mechanism is inherently one-directional (server → client only); it was never designed to also carry client → server traffic. So MCP-over-SSE pairs SSE (server → client, via the open GET /sse stream) with ordinary HTTP POST requests (client → server, via POST /messages) to cover both directions, rather than forcing one mechanism to do a job it isn't built for. This is a direct consequence of SSE's underlying mechanics being asymmetric by design (as backend/sse.html covers in general) — MCP-over-SSE doesn't invent a new asymmetry, it inherits the one SSE already has and works around it with a second, ordinary endpoint for the other direction. Stdio's pipes don't need this split because a subprocess's stdin and stdout are already two SEPARATE channels from the start -- one inherently for each direction -- so stdio never had a single- channel symmetry problem to solve in the first place.
Problem 5 · Weighing a migration decision from stdio to SSE

A team's stdio-based MCP server (originally built for one internal tool) is now wanted by a second, unrelated team. Someone proposes "just have the second team's client also spawn its own copy of the same server script" instead of migrating to SSE. What's a real cost of that approach that migrating to SSE would avoid, and when might the "just spawn another copy" approach actually be the more reasonable choice instead?

Show solution
A real cost of "just spawn another copy": if the server holds any state that's meant to be SHARED/consistent across users (a cache, a counter, any resource genuinely meant to represent one canonical source of truth rather than being cheaply/correctly duplicable per-instance), spawning independent copies per client means each copy has its OWN separate, diverging state -- there is no single source of truth anymore, just N independent ones that can silently disagree with each other. It also means N times the resource cost (N separate processes, each holding whatever the server allocates at startup, e.g. a loaded model or an open database connection pool) instead of one shared instance serving everyone, and any operational fix (a bug patch, a config change, monitoring) now has to be applied and verified across N independently running copies instead of one. When "just spawn another copy" is actually reasonable instead: when the server is genuinely STATELESS and cheap to run (e.g. this lab's calculator server holds no state between calls at all -- each add() call is a pure function of its inputs), spawning independent copies costs almost nothing and sidesteps the real infrastructure investment SSE requires (an always-on host, a port, auth, monitoring for a persistent service) for a case where that investment doesn't buy anything real — Problem 1's data-science example specifically differs from this because it explicitly needed ONE canonical server multiple people connect INTO (implying shared state or a shared expensive resource like a live DB connection), not just the same logic run in parallel. The deciding question, in both directions, is the same one section 2's trade-off table points at: does this workload actually need ONE shared, persistent server instance, or would N independent, disposable instances work just as well at lower infrastructure cost?
