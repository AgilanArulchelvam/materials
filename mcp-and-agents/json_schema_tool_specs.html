MCP & AGENTS LAB · JSON SCHEMA TOOL SPECS

A tool's parameters aren't documentation for a human. They're a contract the model calls into.

When a model "calls a tool," what actually happened is: the model generated a JSON object shaped to match a schema you wrote, and your code either trusts that shape or checks it. JSON Schema is how a tool declares exactly which inputs are valid — types, which fields are required, which values are allowed — so a malformed or nonsensical call can be caught before your tool ever runs. This lab builds a real tool spec field by field, then breaks it on purpose to watch validation catch the break.

01 — Every field in the schema is doing a specific job

Anatomy of a tool's JSON Schema

Start here, before any JSON. Think about a form you fill out to book a flight — it doesn't let you type "sometime next month" into the departure date field, and it doesn't let you leave "from which city" blank. The form's STRUCTURE constrains what you're even able to submit, before anyone reads what you wrote. A tool's JSON Schema is that same form, but the one "filling it out" is a language model instead of a person, and the thing checking the submission is code instead of a human clerk.

Here's a real, complete schema for a search_flights tool — the kind an agent would be given so it can call a flight-search API on a user's behalf:

{ "name": "search_flights", "description": "Search available flights between two airports on a given date.", "parameters": { "type": "object", "properties": { "origin": { "type": "string", "description": "IATA airport code the traveler is departing from, e.g. 'SFO'." }, "destination": { "type": "string", "description": "IATA airport code the traveler is arriving at, e.g. 'JFK'." }, "date": { "type": "string", "format": "date", "description": "Departure date, ISO 8601 (YYYY-MM-DD). Omit for 'any date' searches." }, "passengers": { "type": "integer", "minimum": 1, "maximum": 9, "description": "Number of travelers. Most airline APIs cap a single booking at 9." }, "cabin_class": { "type": "string", "enum": ["economy", "business", "first"], "description": "Cabin tier. Defaults to 'economy' if omitted." } }, "required": ["origin", "destination"] } }

Each field here is pulling its own weight, not decoration:

KeywordWhat it actually does
typeDeclares the JSON data type a value must be (string, integer, number, boolean, array, object). A validator rejects a value whose type doesn't match — "passengers": "two" fails immediately against type: integer, regardless of what the string means to a human.
requiredAn array of property names that MUST be present in the arguments object. Note it lives at the object level, not per-field — origin and destination are required, but date, passengers, and cabin_class are optional and can be omitted entirely.
enumAn exhaustive list of the ONLY values a field may take. Anything not in the list — including a plausible-sounding near-miss — fails validation. This is section 2's main subject.
formatA refinement on top of type for string-shaped data that has further structure — "format": "date" means the string must actually parse as a valid ISO 8601 date, not just be any string.
minimum / maximumNumeric bounds. passengers can be any integer, but only within [1, 9] — a value of 0 or 15 fails, even though both are syntactically valid integers.
descriptionThe one field here that validation code never reads at all — it exists purely to help the MODEL decide what to pass, at the moment it's deciding to call the tool. A vague description ("the date") produces worse tool calls than a specific one ("departure date, ISO 8601, omit for any-date searches"), even though both are equally valid JSON Schema.

Notice the split: type, enum, format, minimum/maximum, and required are all read by a VALIDATOR — code that checks a call's arguments against the schema mechanically, with no understanding of what a flight is. description is read by the MODEL, before it ever generates a call, to understand what each field means and what a reasonable value looks like. Both halves matter, but they're doing genuinely different jobs for genuinely different readers.

Interview-ready definition: a tool's JSON Schema specification declares the exact shape of valid arguments for that tool — each parameter's type, which parameters are required versus optional, and any further constraints (enum, format, numeric bounds) on what values are acceptable — plus human/model-readable description fields that guide what the model passes without themselves being enforced by a validator. The schema serves two audiences at once: the model reads descriptions to decide what to generate, and application code reads the structural constraints to verify what the model actually generated before ever executing the tool.
02 — A malformed call gets caught by the schema, before the tool ever runs

Constraining valid inputs via schema

Start here, before the example. Think about a vending machine that physically won't accept a coin shaped wrong, versus one that accepts anything you feed it and only fails later when the mechanism jams trying to dispense with the wrong coin already inside. The first design catches the problem at the door, with a clear, immediate "this doesn't fit" — the second discovers the problem deep inside its own machinery, often in a way that's harder to diagnose and can leave the machine in a broken state. Schema validation is the vending machine's coin slot: it rejects a malformed call at the door, before any of the tool's actual logic runs.

Take section 1's search_flights schema and a model-generated call that's ALMOST right:

// what the model generated: { "origin": "SFO", "destination": "JFK", "cabin_class": "luxury" } // validating against the schema's enum for cabin_class: enum = ["economy", "business", "first"] "luxury" not in enum // FAILS -- "luxury" is not one of the three allowed values ValidationError: 'luxury' is not one of ['economy', 'business', 'first'] at $.cabin_class

Nothing about "luxury" is malformed JSON, and it's not even an unreasonable GUESS — a real airline sometimes markets a "luxury" tier. But this specific API's cabin_class parameter only accepts three exact strings, and "luxury" isn't one of them. Crucially, this check happens before the tool ever executes — the flight-search function is never even called with this input. The validator catches the mismatch at the boundary, the same way type and minimum/maximum would catch "passengers": 15 or "passengers": "two" before either reached the actual search logic.

With schema validation (catch it early)

The malformed call never reaches the tool. The caller gets a precise, structured error — "cabin_class must be one of economy/business/first" — immediately, before any API call, database write, or side effect happens. The failure is caught at the cheapest possible point.

Without schema validation (let it fail inside)

The tool's own code receives "luxury" and either crashes with an unrelated error deep inside (e.g. a KeyError from an internal lookup table that has no "luxury" entry), or — worse — silently does something undefined with it, like defaulting to whatever branch happens to run when no case matches. Either way, the failure surfaces further from its actual cause, and is harder to diagnose.

The key distinction to hold onto: schema validation is not about whether the tool COULD have handled "luxury" gracefully with a fallback — it's about never letting an out-of-contract value reach the tool's logic at all. This is exactly analogous to a database's CHECK constraint or a Pydantic model's field validator (per backend/fastapi_routing_and_pydantic.html): reject invalid data at the boundary, rather than trusting every downstream consumer to independently re-check it.
Interview-ready definition: constraining valid tool inputs via JSON Schema means a model-generated tool call's arguments are checked against the tool's declared schema — types, required fields, and value constraints like enum — BEFORE the tool's own code ever executes. A call violating any constraint (an out-of-enum value, a missing required field, an out-of-range number) is rejected at this validation boundary with a specific, structured error identifying exactly what was wrong, rather than being passed through to the tool where it could fail unpredictably, deep inside logic that was never designed to handle it, or silently produce an undefined result.

Problem 1 · Writing a schema field for a new constraint

The search_flights tool needs a new optional parameter, max_price_usd, which must be a positive number (no upper bound is meaningful, but negative or zero prices make no sense). Write the JSON Schema fragment for this one property.

Show solution
{ "max_price_usd": { "type": "number", "minimum": 0.01, "description": "Maximum total price in USD the traveler is willing to pay. Omit for no price ceiling." } } type: "number" (not "integer") because prices can have cents -- $412.50 is a valid price, and "integer" would reject it. minimum: 0.01 rather than 0 rules out a nonsensical "$0 or negative" price while still allowing any genuinely positive amount -- there's no natural maximum, so no "maximum" key is included at all (omitting a constraint keyword entirely is the correct way to express "no bound here," rather than setting an arbitrarily large maximum). Since this parameter is OPTIONAL, it does NOT get added to the schema's top-level "required" array -- consistent with section 1's cabin_class and date, which are also constrained (enum, format) without being mandatory.
Problem 2 · Diagnosing why "required" alone doesn't fully constrain a field

A teammate argues that listing "origin" in required is enough to guarantee a usable value — no further constraint needed. Using section 1's schema, what call would satisfy required for origin while still being useless to the actual flight-search API?

Show solution
{"origin": "", "destination": "JFK"} An empty string satisfies "required" -- the key "origin" IS present in the arguments object, which is all "required" checks (presence, not content). But an empty string is not a valid IATA airport code, and the flight-search API's own logic would still have to reject or fail on it downstream, exactly the "fails deep inside, not at the boundary" scenario section 2 warned against. This is why real-world schemas often add a "minLength": 1 (or, better, a "pattern" regex constraint like "^[A-Z]{3}$" to require exactly 3 uppercase letters, matching the real IATA code format) alongside "required" -- "required" only guarantees the key exists in the object, it says nothing about whether the VALUE at that key is actually usable. Confusing "the field is present" with "the field is valid" is a common gap in schema design -- required and type/pattern/enum/minimum are answering genuinely different questions ("is it here" vs. "is what's here any good"), and a complete schema needs both where it matters.
Problem 3 · Reasoning about why description doesn't affect validation

Someone proposes fixing the "luxury" cabin_class problem from section 2 by rewriting the description field to be more explicit: "description": "Must be exactly 'economy', 'business', or 'first' -- do NOT use any other value including 'luxury'." — without touching enum at all. Does this actually prevent the malformed call from reaching the tool?

Show solution
No. A more explicit description can genuinely reduce how OFTEN the model generates "luxury" in the first place, since a clearer prompt-like hint at generation time is real signal the model can use -- but it does nothing to VALIDATION. Per section 1's split, description is read only by the model, at generation time, to help it decide what to write; it is never read by a validator, which only checks type/enum/format/minimum/ maximum/required against the actual generated value. If the model generates "luxury" ANYWAY -- despite a well-written description warning against it, which language models can and do sometimes do -- and there's no enum constraint actually present on cabin_class, the malformed call sails straight through to the tool with nothing catching it, reproducing exactly the "fails deep inside, not at the boundary" failure mode from section 2. A better description is a genuinely good idea (it likely reduces the RATE of bad calls), but it is not a substitute for an enforced enum constraint -- the two operate at different points in the pipeline (before generation vs. after generation, before execution) and a robust tool spec needs the enforced constraint regardless of how good the description is.
Problem 4 · Choosing between a loose type and a precise format

The date field is typed as "type": "string", "format": "date" rather than just "type": "string" alone. What's the concrete difference in what gets rejected, and give one example value that the looser schema (string-only) would incorrectly accept?

Show solution
"type": "string" alone accepts ANY string at all -- "hello", "next Tuesday", "2024-13-45" (an invalid month/day), or "03/15/2024" (a valid date, but in the wrong format for this API) would all pass a bare string-type check, since none of them violate "must be a string." Adding "format": "date" layers a further, more precise constraint on top: the string must actually parse as a valid ISO 8601 calendar date (YYYY-MM-DD, with a real month 01-12 and a real day for that month). "2024-13-45" would FAIL this format check (month 13 and day 45 don't exist) even though it fully satisfies "type": "string" -- confirming the value's TYPE is correct but its CONTENT is still garbage. This is exactly the "required guarantees presence, not validity" distinction from Problem 2, generalized: type alone guarantees the right kind of data, but format (or enum, or a regex pattern) is often needed on top of type to guarantee the STRING itself actually represents something usable by the tool, rather than just being technically string-shaped.
Problem 5 · Deciding what belongs in required vs. what belongs in a default

Section 1's schema does NOT list cabin_class in required, and its description says it "defaults to 'economy' if omitted." Why is making a field optional-with-a-default often better tool design than making the model always specify it, and what's the risk of going too far in that direction?

Show solution
Making cabin_class optional-with-a-default means a user question like "find me a flight from SFO to JFK next Tuesday" -- which says nothing about cabin class -- can still produce a clean, valid tool call (omitting cabin_class entirely, letting the API apply its own sensible default) rather than forcing the model to either guess a value it has no actual basis for, or refuse to call the tool at all because a "required" field has no answer available in the conversation. Fewer required fields generally means fewer opportunities for the model to fabricate a plausible-sounding but ungrounded value just to satisfy the schema's required-field constraint -- exactly the kind of forced guessing you want to design away from, not toward. The risk of going too far: making EVERYTHING optional-with-defaults, including fields where a wrong silent default is actually dangerous (imagine "passengers" silently defaulting to 1 when a user actually asked about a family of 4, and the model simply forgot to extract that detail) trades one failure mode for a quieter, arguably worse one -- a call that "succeeds" but does something the user didn't actually intend, with no validation error to catch it, because nothing was technically malformed. The judgment call is per-field: origin/destination have no sensible default (there's no reasonable "assume the traveler meant some particular airport"), so they stay required; cabin_class has one genuinely reasonable default that matches typical user intent when unspecified, so it doesn't. Which fields belong in each category is a real design decision, not something JSON Schema itself can decide for you.
