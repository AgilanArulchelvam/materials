MCP & AGENTS LAB · DETERMINISTIC PARSING

The model's output claiming to be a tool call is just text. Parse it like text that might lie.

react_pattern.html's loop used a regex to pull an action out of the model's raw text — and flagged that a malformed match raises loudly rather than guessing. This lab goes one level deeper: when a model supports native structured tool-calling, its output usually arrives as an actual JSON payload, not text to pattern-match at all — and parsing it should mean a real JSON parser plus schema validation, never regex pattern-matching on the surrounding text. This lab shows exactly where regex breaks on a valid call, and what to do when the JSON itself is malformed.

01 — A JSON parser either succeeds structurally, or it doesn't — a regex just guesses

Strict parsing, not regex-guessing

Start here, before any code. Think about the difference between a customs officer who checks your passport against an actual database record (does this document, structurally and cryptographically, match a real issued passport) versus one who just eyeballs whether it "looks like" a passport — right color, right approximate shape, a photo roughly where a photo should be. The second approach works fine for anything that happens to look normal, and fails in bizarre, hard-to-predict ways the moment something legitimate looks slightly unusual, or something illegitimate happens to look convincingly normal. A JSON parser is the first officer: it checks REAL STRUCTURE. A regex scanning free text for something that "looks like" a tool call is the second.

react_pattern.html's loop parsed a tool call out of freeform text the model generated ("Thought: ... / Action: lookup(...)") using a regex, because the model was producing plain prose with an embedded action, not a dedicated structured field. But when a model supports native tool-calling (the mode most production agent frameworks actually use), the model's API response includes a DEDICATED, already-separated field containing the tool call as real JSON — there's no free text to regex-match against at all, and treating it as if there were is a design mistake, not just a stylistic preference.

# WRONG: regex-scanning for something that looks like a call, # even when the model already gives you a structured field import re match = re.search(r'search_flights\((.*?)\)', model_output_text) if match: raw_args = match.group(1) # now what? this is a STRING, not parsed data # RIGHT: read the structured field the model API already gives you, # then parse ITS argument string with a real JSON parser import json from jsonschema import validate, ValidationError tool_call = response.tool_calls[0] # a dedicated field, not scraped from prose try: arguments = json.loads(tool_call.arguments_json) # REAL JSON parser validate(instance=arguments, schema=SEARCH_FLIGHTS_SCHEMA) # REAL schema check except (json.JSONDecodeError, ValidationError) as e: # section 2 -- this is the expected, handled path, not a crash handle_malformed_call(tool_call, e)

The difference isn't cosmetic. A JSON parser understands nested structure, string escaping, whitespace, and key ordering the way the JSON specification actually defines them — it either successfully parses the ENTIRE structure, or it raises a precise error naming exactly where parsing failed. A regex has no concept of "structure" at all; it matches a pattern of characters, and any input that's semantically identical but shaped even slightly differently — extra whitespace, a different key order, a nested object where the regex expected a flat one — can silently fail to match, with no signal that anything went wrong beyond "the regex didn't match."

Regex extraction (fragile)

Matches a specific TEXTUAL SHAPE the author anticipated. A semantically valid call formatted even slightly differently — different whitespace, a reordered argument, an extra nesting level — can fail to match with no diagnostic beyond "no match." The regex has no model of what JSON actually is; it's pattern-matching characters.

Real JSON parser + schema validation (robust)

Understands actual JSON structure regardless of superficial formatting differences — whitespace, key order, and nesting are all handled correctly because the parser implements the real JSON grammar. A parse failure means the JSON is GENUINELY malformed, not just shaped differently than one regex author anticipated — and a schema check (from json_schema_tool_specs.html) catches everything the JSON grammar itself can't (wrong types, missing fields, bad enum values) with a precise, structured error.

Interview-ready definition: deterministic parsing of a model's tool-call output means feeding the model's structured tool-call payload through an actual JSON parser and validating the result against the tool's JSON Schema — never extracting arguments via regex pattern-matching on raw text when a structured field is available. A JSON parser either successfully parses the full, real structure or raises a precise error naming exactly where it failed; a regex only recognizes the specific textual shapes its pattern was written to anticipate, and silently fails to match anything else, even a call that is semantically perfectly valid.
02 — Not valid JSON, or valid JSON that fails the schema — both are expected, both are recoverable

Handling malformed tool-call output

Start here, before the code. Think about a form-processing clerk who receives a form that's torn, missing a required field, or has "N/A" scrawled where a number should be. A bad clerk either throws the whole stack of forms away because ONE was bad, or forges a plausible-looking value to make the bad form "work." A good clerk sets the bad form aside, writes a specific note about what's wrong with it, and sends it back to whoever submitted it with a chance to fix it — without disrupting processing of every OTHER form in the stack. An agent loop needs to be the good clerk: a malformed tool call is an expected, survivable event, not a reason to crash the entire loop.

There are two genuinely different failure shapes here, and they need different handling:

async def parse_and_validate_call(tool_call, schema: dict) -> dict: # FAILURE SHAPE 1: not valid JSON at all -- the parser itself chokes try: arguments = json.loads(tool_call.arguments_json) except json.JSONDecodeError as e: return { "status": "parse_error", "feedback": f"Your tool call was not valid JSON: {e}. Re-emit it as valid JSON." } # FAILURE SHAPE 2: valid JSON, but it doesn't match the tool's schema try: validate(instance=arguments, schema=schema) except ValidationError as e: return { "status": "schema_error", "feedback": f"Your call was valid JSON but failed validation: {e.message} at {e.json_path}." } return {"status": "ok", "arguments": arguments} # in the agent loop: feed the SPECIFIC feedback back to the model as an # observation, and let it retry -- exactly like an Observation in react_pattern.html outcome = await parse_and_validate_call(tool_call, SEARCH_FLIGHTS_SCHEMA) if outcome["status"] != "ok": transcript += f"Observation: {outcome['feedback']}\n" # model sees exactly what was wrong else: result = execute_tool(outcome["arguments"])

The critical design choice: BOTH failure paths return a structured result describing exactly what went wrong, rather than raising an uncaught exception that would crash the calling loop. That structured feedback then gets fed back to the model as the NEXT observation — the same Thought → Action → Observation mechanism react_pattern.html already established, just with the observation, this time, being "here's specifically why your last call didn't work" rather than a tool's normal result. The model gets a genuine chance to self-correct on its next turn, informed by a precise error rather than silence.

Response to malformed outputWhat happensWhy it's the wrong (or right) default
Crash the whole agent loopOne bad tool call ends the entire session, discarding all prior progressWrong — treats a routine, expected event (the model occasionally generating a bad call) as a fatal, unrecoverable one
Silently guess/coerce a "close enough" valuee.g. treating a missing field as some hardcoded default nobody actually choseWrong — the tool executes with data nobody validated, which can silently do the wrong thing without ever surfacing an error at all
Catch it, return structured feedback, let the model retryThe loop continues; the model's next Thought incorporates specifically what was wrongRight — matches this lab's approach and react_pattern.html's existing Observation mechanism exactly
One more thing this needs: a bound. Retrying forever on a model that keeps generating malformed calls is its own failure mode — this is exactly why loop_termination_logic.html's max-steps cap matters here too, not just for "the task is taking too many steps" in general. A parse/validation retry still counts as a step, so a model stuck generating bad JSON repeatedly still terminates the loop eventually, rather than looping forever on retries that were meant to be a recovery mechanism, not an infinite one.
Interview-ready definition: handling malformed tool-call output means catching both failure shapes — output that isn't valid JSON at all, and output that's valid JSON but fails schema validation — as expected, structured outcomes rather than letting either raise an uncaught exception that crashes the agent loop. The specific error (what failed to parse, or which schema constraint was violated and where) is fed back to the model as its next observation, giving it a genuine chance to self-correct on a subsequent attempt, bounded by the same step/retry limits that prevent any other kind of runaway loop.

Problem 1 · Writing a regex that would break on valid input

Someone writes re.search(r'\{"origin":\s*"(\w+)",\s*"destination":\s*"(\w+)"\}', text) to extract a call, assuming origin always comes first. Give a concrete, valid JSON payload this regex would fail to match, and explain exactly why.

Show solution
{"destination": "JFK", "origin": "SFO"} This is completely valid JSON -- object key order carries no semantic meaning in the JSON specification, so a payload with destination listed BEFORE origin represents the exact same data as one with origin first. But the regex's literal pattern hardcodes the sequence "origin" then "destination" in that specific textual order -- re.search looks for that EXACT character sequence, and a reordered object simply doesn't contain it anywhere in the string, so the match fails silently (returns None), even though the underlying JSON is perfectly parseable and perfectly valid. A real JSON parser (json.loads) would parse either ordering into an identical Python dict, {"origin": "SFO", "destination": "JFK"} == {"destination": "JFK", "origin": "SFO"} evaluates to True -- because a parser operates on the JSON grammar's actual structure (a set of key-value pairs), not a specific textual sequence of characters. This is exactly section 1's point made concrete: any model that happens to generate its JSON with keys in a different order (which is entirely normal and unpredictable across different model providers, prompts, or even different calls from the SAME model) breaks a regex written against one anticipated ordering, for no real reason.
Problem 2 · Distinguishing the two failure shapes in a specific case

A model generates: {"origin": "SFO" "destination": "JFK"} (missing comma between the two key-value pairs). Using section 2's parse_and_validate_call, which failure shape does this hit, and what does the returned feedback actually say?

Show solution
This hits FAILURE SHAPE 1 (parse_error), not failure shape 2. The missing comma between "SFO" and "destination" makes this string malformed at the JSON GRAMMAR level -- json.loads(...) itself raises a json.JSONDecodeError before validation against the schema is ever reached, because there is no valid parsed object yet to check the schema against at all. The code's structure enforces this ordering naturally: the try/except around json.loads() catches this error and returns immediately with status "parse_error", never reaching the second try/except block that validates against the schema. The feedback returned would be something like: "Your tool call was not valid JSON: Expecting ',' delimiter: line 1 column 17 (char 16). Re-emit it as valid JSON." -- note this message is about JSON SYNTAX (a missing delimiter at a specific character position), not about schema semantics (a missing field, a bad enum value) -- because the failure happened before parsing even succeeded, there's no way for the schema validator to have anything meaningful to say about IT yet. This distinction matters for writing good feedback: the model needs to know it's a SYNTAX problem here, not a semantic one, so its retry focuses on fixing JSON grammar (add the comma) rather than reconsidering which values to pass.
Problem 3 · Deciding what to do with a call wrapped in explanatory prose

A model using a plain-text (non-native-tool-calling) interface generates: "Sure, I'll search for that! {"origin": "SFO", "destination": "JFK"} Let me know if you need anything else." — valid JSON, but embedded in surrounding prose rather than isolated. Does section 1's "use a real JSON parser, not regex" advice fully solve this case on its own?

Show solution
Not entirely on its own -- this is a genuinely different sub-problem worth naming explicitly. json.loads() run directly on the ENTIRE string ("Sure, I'll search...") would itself raise a JSONDecodeError, because the full string is not valid JSON -- it's prose WITH a JSON object embedded partway through it. A real JSON parser doesn't magically locate a JSON object floating inside arbitrary surrounding text any more than a regex would; it expects the ENTIRE input it's given to itself be valid JSON. The practical fix in this scenario is architectural, not just about which parsing tool to use: prefer a model interface that returns tool calls in a DEDICATED structured field (native tool-calling, as section 1 recommends) rather than free-form text a call happens to be embedded in at all -- that sidesteps this problem entirely, since there's no prose to extract from in the first place. If a dedicated field genuinely isn't available, a narrow, well-tested extraction step (finding the outermost matching {...} braces, NOT a general-purpose regex trying to also capture the argument structure itself) can isolate the JSON substring first, and json.loads() is then run on exactly that isolated substring, not the surrounding prose -- the JSON PARSING step itself still stays strict and real, it's just preceded by a narrower isolation step whose only job is finding where the JSON starts and ends, not interpreting its contents.
Problem 4 · Reasoning about retry feedback quality

Two implementations both catch a schema validation failure and feed something back to the model. Implementation A's feedback is "Observation: Error - invalid arguments". Implementation B's is "Observation: 'luxury' is not one of ['economy','business','first'] at $.cabin_class". Using react_pattern.html's reasoning about what the model needs to self-correct, why does B give the model a real chance to fix itself and A mostly doesn't?

Show solution
react_pattern.html established that the ENTIRE transcript -- including every Observation -- is the model's only form of memory across loop steps; it has no other way to "know" what happened except what's physically present in the next prompt. Implementation A's feedback tells the model only that SOMETHING was wrong, with zero information about WHAT -- the model's next Thought has no principled way to decide what to change, since "invalid arguments" doesn't distinguish between a bad enum value, a missing field, a wrong type, or an out-of-range number. Left with nothing to go on, the model's most likely next move is either to regenerate an ALMOST identical call (having no signal about what to change) or to guess blindly at what might be wrong, neither of which reliably converges toward success. Implementation B's feedback names the EXACT field ($.cabin_class), the EXACT value that was rejected ('luxury'), and the EXACT set of values that would have been accepted (['economy','business','first']) -- this is precise enough that the model's next Thought can directly reason "cabin_class must be one of those three; the user didn't specify, so I should either omit it (letting the schema's default apply) or pick the closest reasonable match," and generate a corrected call with a real, grounded reason to expect success this time. This mirrors exactly why json_schema_tool_specs.html's ValidationError messages name the specific field and violated constraint rather than just saying "invalid" -- good error feedback is precise enough to be ACTIONABLE by whoever (or whatever) receives it, not just present.
Problem 5 · Applying async_tool_job_queue_design's retry-budget lesson to parsing retries

Using the bounded-retry-then-DLQ pattern from backend/async_tool_job_queue_design.html, what should an agent loop do if a model generates malformed tool-call JSON THREE times in a row for the same logical request, even after receiving section 2's precise feedback each time?

Show solution
The same structural answer as async_tool_job_queue_design's job failures: bound the retries, then stop retrying and surface the failure explicitly rather than looping indefinitely. Concretely, this means tracking a retry count specifically for PARSE/VALIDATION failures on this particular tool-call attempt (separate from, but composed with, the loop's overall max_steps budget from loop_termination_logic.html), and once that count is exhausted -- say, 3 consecutive malformed attempts for the same call -- the loop should stop asking the model to retry THIS specific call and instead do something else entirely: abandon this tool call and let the model reason about an alternative approach in its next Thought, or surface an explicit "I was unable to construct a valid call to search_flights after multiple attempts" message rather than silently looping forever. This mirrors the job queue's dead-letter-queue reasoning directly: a job (here, a tool call) that keeps failing despite retries with feedback is signaling something more fundamentally wrong than a transient, one-off mistake -- continuing to retry it identically, with the SAME kind of feedback that already failed to fix it twice, wastes loop steps and model calls without a principled reason to expect the third attempt succeeds where the first two didn't. Unlike the job queue's DLQ (which preserves a failed job for LATER human inspection), an agent loop's version of this is usually more immediate: surface the repeated failure to whoever is consuming the agent's output right now, since there's no async "worker comes back to it later" step available mid-conversation the way there is for a background job queue.
