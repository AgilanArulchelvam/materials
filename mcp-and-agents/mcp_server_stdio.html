MCP & AGENTS LAB · SERVER OVER STDIO

The server isn't a service you connect to. It's a process your client starts.

The simplest way to run an MCP server has no networking at all: the client launches the server as a subprocess and the two talk over that subprocess's own stdin and stdout, one JSON-RPC message per line. This lab builds a minimal server exposing one tool with a real JSON Schema, then breaks down exactly what "stdio transport" means at the process level — and animates the actual pipe traffic between a spawned client and server.

01 — One tool, registered, with a real schema

A minimal MCP server exposing one tool

Start here, before the code. The previous lab (mcp_fundamentals_jsonrpc.html) established what a tool looks like as JSON — a name, a description, an inputSchema. Building a server means writing the actual code that (1) declares that JSON when asked, and (2) does real work when the tool actually gets called with real arguments. Below is a genuine, runnable-shaped example using the MCP Python SDK's decorator pattern, exposing exactly one tool: a calculator that adds two numbers.

from mcp.server import Server from mcp.server.stdio import stdio_server import mcp.types as types server = Server("calculator-server") # PART 1: declare what tools exist -- called when the client sends tools/list @server.list_tools() async def list_tools() -> list[types.Tool]: return [ types.Tool( name="add", description="Add two numbers together", inputSchema={ "type": "object", "properties": { "a": {"type": "number", "description": "first addend"}, "b": {"type": "number", "description": "second addend"}, }, "required": ["a", "b"], }, ) ] # PART 2: actually execute a tool -- called when the client sends tools/call @server.call_tool() async def call_tool(name: str, arguments: dict) -> list[types.TextContent]: if name == "add": result = arguments["a"] + arguments["b"] return [types.TextContent(type="text", text=str(result))] raise ValueError(f"Unknown tool: {name}") # PART 3: run it over stdio -- this is the transport choice this lab covers async def main(): async with stdio_server() as (read_stream, write_stream): await server.run(read_stream, write_stream, server.create_initialization_options()) if __name__ == "__main__": import asyncio asyncio.run(main())

Notice the shape mirrors exactly the JSON from the previous lab: list_tools returns objects that serialize into the tools/list response's tool descriptions (name, description, inputSchema), and call_tool is what actually runs when a tools/call request with name: "add" arrives — the SDK handles wrapping/unwrapping the JSON-RPC envelope so this code never touches raw JSON-RPC directly, but the same request/response shape from the previous lab is what's flowing underneath.

Interview-ready definition: a minimal MCP server registers its available tools via a list_tools handler (returning each tool's name, description, and JSON Schema inputSchema) and executes them via a call_tool handler (receiving the tool name and arguments dict, returning content back to the client). The SDK translates between this handler-based interface and the underlying JSON-RPC tools/list and tools/call messages from the protocol, so server code is written against a typed function interface rather than raw JSON, even though JSON-RPC is what actually travels over the wire.
02 — No sockets, no ports — just a subprocess's own pipes

stdio transport, mechanically

Start here, before the mechanics. Think about running a command-line calculator program by piping input into it: echo "2 + 2" | calc. The shell isn't opening any network connection to calc — it's just wiring your typed text into calc's own standard input, and whatever calc prints to its own standard output flows back out. stdio transport applies exactly this idea to MCP: no networking stack involved at all, just a program's ordinary input and output streams, repurposed to carry JSON-RPC messages instead of arbitrary text.

Concretely: the MCP client launches the server as a subprocess (e.g. via Python's subprocess.Popen or the equivalent in Node), keeping a handle to that subprocess's stdin and stdout file descriptors. The client writes JSON-RPC request messages to the subprocess's stdin, and reads JSON-RPC response and notification messages from the subprocess's stdout — one complete JSON-RPC message per line, newline-delimited, so each side knows exactly where one message ends and the next begins. This is precisely why it's called "stdio transport" — the transport IS the subprocess's standard input and standard output, nothing more exotic than that.

# roughly what the CLIENT side does to launch and talk to the server above import subprocess, json proc = subprocess.Popen( ["python", "calculator_server.py"], stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True, ) # write one JSON-RPC request, newline-terminated, to the subprocess's stdin request = {"jsonrpc": "2.0", "id": 1, "method": "tools/list"} proc.stdin.write(json.dumps(request) + "\n") proc.stdin.flush() # read one line back from the subprocess's stdout -- that line IS the response response_line = proc.stdout.readline() response = json.loads(response_line) print(response["result"])

Two things make this reliable: one message per line (so readline() always yields exactly one complete JSON-RPC message, never half a message or two concatenated messages), and strict stdout hygiene — the server must never print() anything to stdout that ISN'T a JSON-RPC message, because the client is reading every line of stdout as protocol traffic. Any debug logging the server wants to do has to go to stderr instead, which the client simply doesn't read as protocol data.

The classic stdio bug: a developer adds a stray print("debug: got here") inside the server's tool-handling code, forgetting that stdout is the protocol channel, not a debug console. The client's next readline() gets that debug string instead of the JSON-RPC response it expected, fails to parse it as JSON, and the whole exchange breaks — not because the tool logic was wrong, but because something leaked onto the one channel that was supposed to carry ONLY protocol messages. This is exactly why MCP server implementations are strict about routing all logging to stderr, never stdout.
Interview-ready definition: stdio transport runs the MCP server as a child process launched directly by the client, communicating over that subprocess's own stdin and stdout — the client writes JSON-RPC requests to the server's stdin and reads JSON-RPC responses/notifications from the server's stdout, one newline-delimited message per line, with no network socket involved. This requires strict discipline that stdout carries ONLY protocol messages (anything else, like stray debug prints, corrupts the stream since the client parses every line as JSON-RPC) — which is why server implementations route logging to stderr instead, leaving stdout exclusively for the protocol.

Interview-ready definition: the stdio process boundary is the client-launches-server relationship at the OS level: the client process calls something like subprocess.Popen, which forks and execs the server as a genuine child process, wiring that child's stdin and stdout to pipes the client holds handles to. The client and server are two entirely separate OS processes, with memory isolation between them exactly like any two unrelated processes — the ONLY communication channel between them is the pair of pipes the client set up at spawn time, which is also why stdio-transport MCP servers are inherently single-client: the pipes were created for exactly one parent process, and there is no mechanism for a second, unrelated client to also attach to that same server subprocess.

Problem 1 · Diagnosing a broken stdio server from a symptom

A newly written MCP server works fine when run directly and manually fed input in a terminal, but the moment a real MCP client launches it as a subprocess, every response fails to parse as JSON. The developer swears the JSON-RPC response-building code is correct. What's the most likely cause, using section 2's warning?

Show solution
The most likely cause is that something OTHER than JSON-RPC messages is being written to stdout -- most commonly a stray print() statement (a startup banner, a debug log line, a library that prints its own status messages) that the developer didn't notice because, when run manually in a terminal, a human just visually skims past extra lines without it breaking anything. But the actual MCP client isn't a human skimming output -- per section 2, it calls something like readline() on stdout and attempts to json.loads() EVERY line it receives as a complete JSON-RPC message. Any extra non-JSON line corrupts that parsing, exactly matching the "every response fails to parse" symptom, even though the JSON-RPC- building code itself may be entirely correct -- the bug isn't in what gets built, it's in what ELSE gets written to the same channel. Fix: audit every place the server (and any library it imports) might write to stdout, and redirect all logging/debug output to stderr instead, leaving stdout reserved exclusively for JSON-RPC protocol messages, per section 2's stdout-hygiene rule.
Problem 2 · Explaining why stdio is single-client by construction

A team wants two different client applications to both talk to the same running stdio-transport MCP server instance at the same time. Using section 3's process-boundary explanation, why doesn't this work, and what would they need to change?

Show solution
This doesn't work because a stdio server's stdin/stdout pipes are set up at SPAWN time by the ONE process that launched it (section 3) -- the pipes are a direct, exclusive connection between that specific parent process and that specific child process, not a shared, discoverable channel other unrelated processes can also attach to. A second client application has no way to "also connect" to an already-running server subprocess's stdin/stdout, because those file descriptors were never exposed to anything except the original parent -- there's no listening socket, no address, nothing a second process could discover or dial into even in principle. What they'd need to change: move off stdio transport entirely, to a transport that's actually built around a persistent, addressable service multiple independent clients CAN connect to -- which is precisely what the next lab (mcp_server_sse.html) covers. Under stdio, "supporting two clients" isn't a configuration tweak, it's a different transport model: either each client spawns and owns its OWN separate server subprocess (two independent server instances, not one shared instance), or the server needs to run as a standalone network-addressable service instead of a spawned child process.
Problem 3 · Tracing what breaks if requests aren't newline-delimited

A client sends two JSON-RPC requests to a server's stdin back to back, forgetting to add a newline after the first one, so the server's stdin actually receives one unbroken string containing both request JSONs concatenated. What happens on the server side, and why does this trace back to the "one message per line" rule?

Show solution
On the server side, whatever is reading stdin line-by-line (readline(), per section 2's mechanics) will read past the end of the first JSON object and into the start of the second one before it ever hits a newline character -- because without the newline, there IS no line boundary between the two messages from the reader's point of view. Attempting to json.loads() that concatenated string fails (it's not valid JSON -- two JSON objects back to back with no separator isn't a single parseable value), so the server can't even recover the first request's contents, despite it having been perfectly well-formed JSON on its own. This traces directly back to the "one message per line" rule in section 2: newline-delimiting isn't a stylistic choice, it's the ENTIRE mechanism that lets a reader on either side know where one message ends and the next begins, given that stdin/stdout are just raw byte/character streams with no built-in message-framing of their own (unlike, say, HTTP, which has explicit framing like Content-Length headers). Skip the newline and there's no way to tell "one full request has arrived" from "half a request has arrived so far" without imposing some OTHER framing scheme — which is exactly why every stdio-transport implementation treats the newline as a hard requirement, not an optional nicety.
Problem 4 · Reasoning about lifecycle coupling

If the client process crashes or is force-killed, what happens to the stdio-transport server subprocess it spawned, and why does this differ from what you'd expect from a standalone networked service?

Show solution
In the typical case, the server subprocess dies too (or becomes an orphaned process the OS will eventually reap), because it was launched AS A CHILD of the client process specifically to serve that one client -- its stdin/stdout pipes become invalid the moment the parent that created them is gone, and most process managers/OSes will also send a termination signal to child processes when a parent dies (depending on how the subprocess was spawned and configured). This is a direct consequence of section 3's process-boundary description: the server's entire reason for existing, in the stdio model, is serving the ONE client that spawned it -- there's no independent reason for it to keep running once that relationship is severed. This differs sharply from a standalone networked service (the kind the next lab's SSE transport uses): a persistent HTTP server keeps running regardless of whether any particular client that connected to it is still alive, because its lifecycle was never tied to a specific client process in the first place -- it's an independently running service that clients connect TO, rather than a process a client directly OWNS and spawned. This tight lifecycle coupling (server dies with its one client) is exactly the trade-off section 3's transport-choice framing points toward: stdio is simple and has zero infrastructure to run, but it inherently ties the server's lifetime to one specific client process, which a standalone networked server deliberately avoids.
Problem 5 · Choosing stdio vs a different transport for a described scenario

A team is building a coding assistant that runs entirely on a developer's own laptop and needs to call out to a small set of local file-system tools (read file, list directory, run a lint check) — nothing needs to be reachable from any other machine. Is stdio transport a good fit here, and why?

Show solution
Yes, stdio transport is a strong fit here, precisely because every constraint stdio's design accepts (section 2 and section 3) matches this scenario's actual requirements rather than fighting against them. Stdio's core trade-offs: local-only (no network reachability at all), single-client (tightly coupled to the one process that spawned it, Problem 2), and simple (zero infrastructure -- no port to bind, no HTTP server framework, no auth/network-security surface to reason about). This scenario needs exactly that: the tools ("read file," "list directory," "run a lint check") only ever need to be called by the one coding-assistant process running locally on the SAME laptop as the files being read -- there's no requirement for any OTHER machine or process to reach these tools, and there's exactly one client (the assistant itself) that will ever use them. Reaching for a networked transport (the next lab's SSE, requiring an HTTP server, a port, and real thought about who else might be able to connect to it) here would add real infrastructure and security-surface cost to solve a "multiple remote clients" problem this scenario doesn't actually have -- stdio's constraints aren't a limitation in this case, they're a precise match to what's actually needed, launched fresh each time the assistant starts and torn down cleanly when it exits.
