MCP & AGENTS LAB · MCP FUNDAMENTALS — JSON-RPC

Before any tool gets called, two processes need one shared envelope format to talk in.

The Model Context Protocol (MCP) is a specification for how an AI application (a client) talks to an external server that exposes tools, data, and prompt templates. Underneath all of it is a much older, much simpler wire format: JSON-RPC 2.0. This lab covers the exact shape of a JSON-RPC request, response, and notification, then the three MCP primitives — tools, resources, prompts — that get exchanged using that shape.

01 — One envelope format, three message shapes

JSON-RPC 2.0: request, response, and notification

Start here, before any JSON. Imagine mailing letters back and forth with a pen pal, except every letter you send that expects a reply has a tracking number written on it, and your pen pal writes that exact same tracking number on their reply so you know which of your (possibly several outstanding) letters they're answering. Some letters, though, are just quick postcards — "FYI, I moved" — that don't need a tracking number at all, because you're not expecting or waiting for any reply to them. JSON-RPC 2.0 is exactly this pen-pal protocol, just for two processes instead of two people, and the "tracking number" is called id.

JSON-RPC 2.0 is a lightweight remote procedure call protocol encoded as JSON. Every message includes "jsonrpc": "2.0" to declare the protocol version. There are exactly three message shapes MCP uses constantly:

A request — expects a matching response

{ "jsonrpc": "2.0", "id": 7, "method": "tools/call", "params": { "name": "get_weather", "arguments": { "city": "Lisbon" } } }

Every request has an id (chosen by the sender — often a simple incrementing counter), a method naming the operation being invoked, and optional params carrying arguments for that method. The id is the whole mechanism that makes a later reply identifiable as THIS request's reply, and not some other outstanding request's reply.

A response — success, correlated by the same id

{ "jsonrpc": "2.0", "id": 7, "result": { "content": [ { "type": "text", "text": "18°C, partly cloudy" } ] } }

A response repeats the SAME id the request carried — 7, in this example — so the caller can match it back to the exact request it was waiting on. It carries EITHER a result field (success) OR an error field (failure) — never both, and never neither.

A response — error, same shape, different field

{ "jsonrpc": "2.0", "id": 7, "error": { "code": -32602, "message": "Invalid params: city is required" } }

A notification — no id, no reply expected

{ "jsonrpc": "2.0", "method": "notifications/progress", "params": { "progressToken": "upload-1", "progress": 40 } } // No "id" field at all. The sender fires this and moves on -- it never // waits for, and the receiver never sends, any reply to it.

A notification has the exact same shape as a request — method and optional params — with ONE structural difference: it has no id field. That missing field isn't an oversight, it's the entire signal: the absence of an id tells the receiver "don't bother replying, and if you did reply, I wouldn't have anything to match it against anyway, since I never gave you a tracking number." This is why notifications are called fire-and-forget — the sender dispatches the message and continues immediately, with no correlation mechanism even available to wait on a response. MCP uses notifications for things like progress updates during a long-running tool call, or "the list of available tools just changed" — information worth pushing, but nothing the sender is blocked waiting to hear back about.

Interview-ready definition: JSON-RPC 2.0 defines three message shapes over a shared {"jsonrpc": "2.0", ...} envelope. A REQUEST carries an id, a method, and optional params, and expects exactly one matching RESPONSE — which repeats the same id and carries either a result (success) or an error (failure), never both. A NOTIFICATION has the identical method/params shape as a request but OMITS id entirely, which is precisely what marks it fire-and-forget: no reply is expected, and none could even be correlated back to it since it carries no tracking number in the first place.
02 — Three kinds of things a server can offer a client

Tools, resources, and prompts — the three MCP primitives

Start here, before the JSON. Picture hiring a very capable assistant who arrives with three completely different kinds of things they can offer you: (1) actions they can actually perform on your behalf — booking a table, sending an email — where you tell them what to do and they do it; (2) documents and reference material they already have on hand that you can ask to see — a filing cabinet you can pull from; (3) pre-written templates for common requests you might want to make of THEM later — "use my 'weekly report' template" instead of explaining the same request from scratch every time. MCP formalizes exactly this three-way split as its core primitives: tools, resources, and prompts.

Tools

Functions the model can CALL to take an action or compute something — e.g. run a calculation, hit a real API, write a file. The model decides WHEN to call one and WHAT arguments to pass; the server executes it and returns a result.

Resources

Data the model can READ or reference — e.g. a file's contents, a database row, a config value. Resources are more like a filing cabinet than an action: the client can request one, but nothing gets executed or changed by reading it.

Prompts

Reusable prompt TEMPLATES the server exposes, which the client (or the client's user) can surface and fill in — e.g. a "summarize this document" template with a slot for which document. The server owns the template's wording; the client supplies the specific inputs.

Each primitive has its own list and get/call methods in the MCP spec, all sent as ordinary JSON-RPC requests. A client typically starts a session by calling tools/list, resources/list, and prompts/list to discover what a given server actually offers, before ever calling any of them.

A tool, as JSON

// what tools/list returns, describing ONE available tool { "name": "get_weather", "description": "Get current weather for a city", "inputSchema": { "type": "object", "properties": { "city": { "type": "string" } }, "required": ["city"] } }

A resource, as JSON

// what resources/list returns, describing ONE available resource { "uri": "file:///project/README.md", "name": "Project README", "mimeType": "text/markdown" } // the client later calls resources/read with this uri to fetch the // actual content -- listing and reading are two separate steps

A prompt, as JSON

// what prompts/list returns, describing ONE available prompt template { "name": "summarize_document", "description": "Summarize a document at a given length", "arguments": [ { "name": "document_uri", "required": true }, { "name": "length", "required": false } ] }
Interview-ready definition: MCP defines three core primitives a server exposes to a client. TOOLS are callable functions the model invokes to take action or compute a result, described by a JSON Schema inputSchema the model uses to construct valid arguments. RESOURCES are addressable, read-only data the client can list and fetch by URI — reference material the model can pull into context, not something it executes. PROMPTS are server-defined, reusable prompt templates with named arguments that a client (or its user) can select and fill in, standardizing common requests so they don't need to be reconstructed from scratch each time. All three are discovered via their own list method and invoked via their own call/get/read method, all carried as ordinary JSON-RPC requests over whatever transport the connection uses.

Why fire-and-forget matters: if every single message required a full round trip before the sender could continue, a server streaming 50 progress updates during one long tool call would force the client to synchronously acknowledge each one before the server could send the next — adding real latency for no actual benefit, since the client doesn't need to acknowledge a progress percentage, it just needs to receive it. Making notifications a genuinely distinct, id-less message shape (not just "a request the receiver happens to ignore") means neither side has to allocate any correlation bookkeeping for them at all — there is structurally nothing to correlate.

Problem 1 · Spotting what's wrong with a malformed response

A server sends back: {"jsonrpc": "2.0", "id": 7, "result": {"ok": true}, "error": null}. A teammate says this is fine because error is just null. Is this actually spec-compliant, and why does it matter?

Show solution
This is NOT correctly spec-compliant, even though error is null rather than a populated object. Per section 1, a JSON-RPC response must carry EITHER result OR error -- the field itself should be present only for whichever outcome actually happened, not both fields present with one set to null. Including "error": null alongside a populated "result" blurs a distinction receivers are entitled to rely on structurally (e.g. "if this response has an error key at all, treat it as a failure") -- a naive receiver that checks `if ("error" in response)` rather than `if (response.error)` would incorrectly treat this successful response as a failure, purely because the key exists even though its value is null. The fix is simply to omit the error field entirely on a successful response, exactly as this lab's section 1 examples do -- result-only on success, error-only on failure, no coexistence of both keys regardless of value.
Problem 2 · Deciding request vs notification for a new message type

You're designing a new MCP message: the server wants to tell the client "a new tool just became available, please refresh your tool list." Should this be a request or a notification, and what would break if you picked the other one?

Show solution
This should be a NOTIFICATION. The server isn't asking the client a question it needs an answer to right now -- it's pushing information ("something changed on my end") that the client can act on whenever it gets around to it, with no result the server is waiting to receive back. This matches section 1's notification definition precisely: fire-and- forget information, not a call awaiting a specific reply. If this were instead built as a REQUEST (carrying an id), the server would need to define what a "correct" response even looks like (what result value would the client send back?), and worse, the server would now be implicitly waiting on a reply it doesn't actually need before it could consider the message "done" -- adding pointless coordination overhead for a message that's fundamentally just an announcement. This mirrors exactly the real MCP notification notifications/tools/list_changed, which exists as a genuine notification for this exact reason.
Problem 3 · Distinguishing a tool from a resource for a specific capability

A server can (a) return the current contents of a specific log file, and (b) restart a specific service. Using section 2's definitions, which of these should be modeled as a tool and which as a resource, and what would go wrong modeling them the other way around?

Show solution
Reading the log file's current contents fits RESOURCE: it's read-only data the client can fetch by an identifier (a uri, per section 2's resources/read example) -- nothing about the world changes as a result of reading it, and the client might reasonably fetch it repeatedly without any side effects accumulating. Restarting a service fits TOOL: it's an action with a real side effect in the world (the service actually goes down and comes back up), which matches section 2's tool definition of something the model CALLS to take an action, with actual arguments describing what to do (e.g. which service) and a result describing what happened. Modeling restart-service AS a resource would be actively misleading: a resource read is conventionally assumed to be side-effect-free and safely repeatable (a client or an intermediate cache might re-fetch a resource without a second thought), but "reading" a restart-service resource would actually restart the service every time something merely tried to look at it -- a serious, easy-to-trigger-by-accident foot-gun. Modeling read- log-contents AS a tool would work mechanically (tools CAN be read-only), but it obscures the fact that it has no side effects and forces every client to treat it with the same caution a genuinely stateful tool call deserves, when resources exist specifically to signal "this one's just data."
Problem 4 · Tracing id reuse across concurrent requests

A client sends two requests back to back: id=1 (a slow tool call) and id=2 (a fast one). The server finishes id=2 first and replies, then finishes id=1 later and replies. Explain, using only the id field, how the client knows which reply is which -- and what would go wrong if both requests had reused the same id.

Show solution
The client knows which reply is which purely by reading the id field on each incoming response and matching it against the id it originally sent on the outstanding request it corresponds to -- order of arrival is irrelevant. Even though id=2's response arrives FIRST (because the fast tool call finishes first) while id=1's request was sent FIRST, the client correctly resolves id=2's response to the id=2 request and keeps id=1 marked as still-pending, because id is the only correlation mechanism JSON-RPC provides -- arrival order carries no meaning at all. If both requests had reused the SAME id (e.g. both sent as id=1), the client would have no reliable way to tell which of the two outstanding calls a given id=1 response actually belongs to -- whichever response arrives first would get matched to id=1's pending request (likely incorrectly resolving the wrong call), and the second id=1 response arriving later would either be silently dropped (no pending request left to match it to) or incorrectly matched again, corrupting the client's bookkeeping. This is exactly why every request needs a genuinely UNIQUE id among all currently-outstanding requests -- id isn't just a label, it's the entire correlation mechanism the request/response model in section 1 depends on.
Problem 5 · Designing the id-lifecycle rule for a new client implementation

You're implementing an MCP client from scratch and need a rule for generating request ids. Using this lab's mechanics, write the exact rule (not code) you'd use, and explain why a simple incrementing counter starting at 1 is sufficient, without needing anything fancier like a UUID.

Show solution
Rule: maintain a single counter, starting at 1, incremented by 1 every time the client sends a new request; use the current counter value as that request's id, and never reuse an id that's still outstanding (waiting on a response). A simple incrementing counter is sufficient because id's only job (per section 1 and Problem 4) is to be UNIQUE AMONG CURRENTLY OUTSTANDING requests from THIS client, on THIS connection -- it never needs to be globally unique across different clients, different connections, or different points in time, the way a UUID would guarantee. As long as a given client never has two requests with the same id simultaneously in flight on the same connection, sequential integers satisfy the correlation requirement completely, and they're far cheaper to generate and far easier to read in logs/debugging output than a UUID would be. A UUID would only become necessary if ids needed to be meaningful/unique OUTSIDE the scope of one client's own outstanding-request bookkeeping on one connection -- which JSON-RPC's actual correlation mechanism, as built, simply doesn't require.
