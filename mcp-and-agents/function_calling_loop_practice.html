The tool — calculate
{ "name": "calculate", "parameters": { "type": "object", "properties": { "operation": { "type": "string", "enum": ["add","subtract","multiply","divide"] }, "a": {"type": "number"}, "b": {"type": "number"} }, "required": ["operation","a","b"] } }
The user's question

"A team of 7 people split a $1,240 dinner bill evenly, then each person adds a 18% tip on their own share. What does each person pay in total?"

Why this needs multiple calls

The tip calculation (step 2) needs each person's SHARE (step 1's result) as an input — it cannot be computed until step 1 actually returns, the same hard data dependency react_pattern.html's capital-then-population example established. This question genuinely can't be answered in one call.

max_steps for this run

max_steps = 5 — comfortably above the 3 calls this question actually needs (per_person = 1240 ÷ 7; tip = per_person × 0.18; total = per_person + tip), giving headroom without being so loose it stops functioning as a real safety net.

This setup deliberately includes one imperfection: the model's FIRST attempt at step 2 passes "operation": "percent" — not a valid value in the tool's enum. Predict what should happen when that gets validated, before section 2 shows you.

Problem 1 · Explaining why the "percent" enum failure didn't crash the loop

Using deterministic_parsing.html's two-failure-shape reasoning, which specific failure shape did the step 2 "operation": "percent" attempt hit, and why does the loop's transcript show a corrective Observation rather than an exception?

Show solution
This hits FAILURE SHAPE 2 (schema_error), not failure shape 1. The generated payload {"operation": "percent", "a": ..., "b": ...} is perfectly valid JSON syntactically -- json.loads() would parse it without any error at all. The failure is semantic: "percent" is not one of the values in the operation field's enum (["add","subtract","multiply", "divide"]), so schema validation (json_schema_tool_specs.html) rejects it AFTER a successful parse, not instead of one. The loop's transcript shows a corrective Observation rather than an uncaught exception because this is exactly the structured-feedback path deterministic_parsing.html's parse_and_validate_call establishes: a schema_error result returns specific feedback ("'percent' is not one of ['add','subtract','multiply','divide'] at $.operation") that gets appended to the transcript as the next Observation, giving the model a genuine, precise reason to retry with a valid operation name on its next Thought -- rather than the whole loop crashing on a bad enum value the same way json_schema_tool_specs.html's live demo showed a "luxury" cabin_class getting caught before ever reaching a tool.
Problem 2 · Tracing exactly which max_steps budget this specific run consumes

This lab's question needs 3 successful tool calls, but step 2's first attempt failed validation and had to retry. Using loop_termination_logic.html's reasoning, does the failed attempt at step 2 count against max_steps = 5, and how many total loop iterations does this full run actually consume?

Show solution
Yes -- per loop_termination_logic.html's own Practice Problem 5, a parse/ validation-failure retry is just another iteration of the SAME loop body, so it consumes one unit of the max_steps budget exactly like a successful tool call does. This run's full iteration count: step 1 (per_person calculation, succeeds first try) = 1 iteration; step 2's FAILED "percent" attempt = 1 iteration; step 2's CORRECTED retry with a valid operation = 1 more iteration; step 3 (final total, succeeds) = 1 iteration; plus one final iteration where the model emits its Final Answer instead of another action = 1 iteration. Total: 5 iterations used out of the max_steps = 5 budget. This is a genuinely useful trace to notice: this run finishes with ZERO steps to spare, entirely because of ONE validation failure along the way -- if the model had gotten operation wrong a second time too, this run would have hit max_steps_exceeded before ever reaching a Final Answer, despite the underlying task only strictly needing 3 tool calls. This is exactly why loop_termination_logic.html's Practice Problem 1 argued for setting max_steps meaningfully ABOVE the typical-case step count, not merely equal to it -- a cap set at exactly 3 for this task would have left zero room for even one recoverable mistake.
Problem 3 · Reasoning about what the model actually "sees" going into step 3

By the time the model generates its step 3 tool call, what EXACTLY is in its prompt — and using react_pattern.html's statelessness reasoning, explain why the failed "percent" attempt from step 2 is still part of that prompt even though it never executed.

Show solution
By step 3, the model's prompt is the ENTIRE running transcript accumulated so far: the original question, step 1's Thought/Action/ Observation (per_person = 177.14), step 2's FAILED attempt (Action: calculate(operation="percent", ...), Observation: the schema validation error naming exactly what was wrong), step 2's CORRECTED retry (Action: calculate(operation="multiply", a=177.14, b=0.18), Observation: 31.89), and now the model is being asked to generate its next step from all of that combined history. Per react_pattern.html's core statelessness point -- each call to the model is a fresh, independent request with no built-in memory between calls -- the failed "percent" attempt has to be PHYSICALLY PRESENT in the transcript for the model to have any awareness it ever happened at all, even though that specific attempt never actually executed against the real tool. This might look wasteful (why keep a failed attempt around?) but it's exactly what lets the model avoid repeating the SAME mistake -- if the failed attempt and its corrective feedback were silently dropped from the transcript instead of retained, the model would have no way to "remember" it already tried "percent" and been told that's invalid, and could plausibly generate the exact same wrong enum value again on a later, unrelated call to the same tool.
Problem 4 · Deciding what should happen if execute_tool itself raised, not validation

Suppose step 1's calculate(operation="divide", a=1240, b=0) call passes schema validation (0 is a valid number) but the actual execution raises a division-by-zero error INSIDE the tool. Is this the same failure shape as the "percent" enum case, and how should the loop's Observation differ?

Show solution
No -- this is a genuinely different failure point than either of deterministic_parsing.html's two shapes (which are both about PARSING/ VALIDATING the call itself, before execution). This is an EXECUTION-time failure: the call was syntactically valid JSON AND passed schema validation (a=1240, b=0 are both legitimate numbers -- nothing in this tool's schema declares b must be nonzero, since JSON Schema's numeric constraints don't naturally express "not equal to zero" the way enum or minimum/maximum do), but the underlying operation itself is mathematically undefined once it actually runs. The loop should handle this the same STRUCTURAL way as deterministic_parsing.html's two failure shapes, even though it's a third, distinct kind of failure: catch the exception explicitly (never let an uncaught ZeroDivisionError crash the whole loop), and feed a specific, actionable Observation back -- "Observation: Error - division by zero (a=1240, b=0)" -- rather than crashing or silently returning some placeholder value like 0 or null that the model might mistake for a real result. This mirrors react_pattern.html's own Practice Problem 5, which established exactly this pattern (wrap the tool call, feed the error back as an Observation) for a lookup tool finding no results -- the same posture generalizes cleanly to a calculator tool hitting an undefined operation. The deeper lesson: schema validation catches malformed CALLS, but it cannot catch every way a syntactically and structurally valid call might still fail once it actually runs -- execution-time error handling is a separate, additional layer the loop still needs on top of schema validation, not a replacement for it.
Problem 5 · Designing the loop's exit condition for this specific question

Once step 3 successfully computes the final total ($209.03), what specifically should the model's NEXT generated output look like for the loop to terminate via the done signal rather than continuing toward max_steps? Write the actual shape.

Show solution
Following loop_termination_logic.html's exact mechanism, the model's next output should contain "Final Answer:" instead of another Action -- concretely, something like: Thought: I now have per_person ($177.14), the tip on that share ($31.89), and the total per person ($209.03). I have everything needed to answer the original question. Final Answer: Each of the 7 people pays $209.03 in total (a $177.14 share of the bill plus an $31.89 18% tip on their own share). The loop's termination check (loop_termination_logic.html's "if 'Final Answer:' in model_output: return ...") fires the moment this specific string appears in the model's output -- at this point the loop has used 5 of its 5 max_steps budget (per Problem 2's trace), so this Final Answer needs to arrive on EXACTLY this iteration for the run to terminate via the done signal rather than via max_steps_exceeded. This is a genuinely tight margin worth noticing: if the model had instead generated one more unnecessary tool call here (say, re-verifying the arithmetic with a redundant call) before finally emitting its Final Answer, THIS run would have hit max_steps_exceeded with a correct answer sitting one step away but never reached -- a concrete illustration of why loop_termination_logic's Problem 1 argued for headroom above the typical case, and why an unnecessary extra step (echoing react_pattern.html's Problem 4 on ReAct's adaptivity not always paying off) has a real cost measured in exactly this kind of margin.
