MCP & AGENTS LAB · STATEFUL GRAPHS

An agent's workflow isn't one long script — it's a graph of states, and the path through it depends on what happens.

Both the ReAct loop and Plan-and-Solve have an implicit control flow. Modeling that flow EXPLICITLY as a graph — nodes as states, edges as conditional transitions — makes the workflow inspectable, debuggable, and resumable in a way a bare loop or a linear plan isn't. This lab builds a concrete customer-support agent graph and animates a real request taking a specific conditional path through it.

01 — The workflow itself becomes a diagram, not just a mental model

Modeling agent workflows as state machines

Start here, before any diagram. A vending machine is a genuinely simple state machine: it's in exactly one state at a time (idle, coin-inserted, dispensing, out-of-stock), and a specific EVENT (inserting a coin, pressing a button, running empty) causes a well-defined TRANSITION to exactly one next state — never two states at once, and never a transition that isn't explicitly defined for the current state. You've already seen this idea applied to a network connection in the Month 2 WebSocket lifecycle lab (CONNECTING → OPEN → CLOSING → CLOSED) — a connection is always in exactly one of those states, and specific events move it to the next one.

An agent's workflow can be modeled the exact same way, just with richer states: instead of "idle / dispensing," a state might be "classify the user's intent" or "escalate to a human," and instead of "coin inserted," a transition might be triggered by "the classification step returned billing" rather than a physical event. The core idea carries over unchanged — the agent is always in exactly one node of the graph, and a specific transition, chosen based on what just happened, moves it to the next one.

Interview-ready definition: modeling an agent workflow as a stateful graph means representing the workflow as a directed graph where each NODE is a distinct step or state the agent can be in (e.g. "classify intent," "handle billing," "escalate"), and each EDGE is a transition between two states, often conditional on the output of the state the edge leaves from. At any point during execution, the agent occupies exactly one node — the same fundamental state-machine property as a WebSocket connection's lifecycle states — and the specific path taken through the graph for a given run is determined dynamically by which conditional edges fire, not fixed in advance.
02 — A concrete example graph: a customer support agent

Nodes, edges, and explicit conditional transitions

Start here, before the code. Below is a real, concrete graph for a customer support agent: a request always starts at classify_intent, which conditionally branches to exactly ONE of three next nodes depending on what the classification found, and every path eventually reaches generate_response before the workflow ends.

Notice classify_intent has exactly THREE outgoing edges, each with a different condition attached — the agent takes exactly ONE of them per run, never zero and never more than one, based on what the classification step's own output actually was. This is the graph-native way of expressing what would otherwise be a chain of nested if/elif statements — but represented as data (nodes and edges) rather than buried inside procedural code, which is exactly what makes it inspectable as a standalone diagram, the way this SVG itself is one.

# the graph as data -- nodes are functions, edges are conditional routes def classify_intent(state: dict) -> dict: intent = classify(state["message"]) # e.g. an LLM call or classifier model state["intent"] = intent return state def route_after_classify(state: dict) -> str: # this function IS the conditional edge -- it decides which node is next if state["intent"] == "billing": return "handle_billing" elif state["intent"] == "technical": return "handle_technical" else: # angry, unclear, or anything not confidently classified return "escalate_to_human" GRAPH = { "classify_intent": {"fn": classify_intent, "router": route_after_classify}, "handle_billing": {"fn": handle_billing, "next": "generate_response"}, "handle_technical": {"fn": handle_technical, "next": "generate_response"}, "escalate_to_human": {"fn": escalate_to_human, "next": None}, # terminal -- hands off, no response generated here "generate_response": {"fn": generate_response, "next": None}, # terminal -- workflow ends } def run_graph(start_node: str, state: dict): node = start_node while node is not None: entry = GRAPH[node] state = entry["fn"](state) # run this node's step node = entry["router"](state) if "router" in entry else entry["next"] return state

The state dictionary itself (state["intent"], and whatever each node adds to it) is exactly what carries information FORWARD through the graph from one node to the next — this is the "state" a stateful graph is named for: not just "which node am I in," but the accumulated data that travels along with the execution as it moves node to node, available to every subsequent node's logic and to whichever conditional router decides the next edge.

Interview-ready definition: in a stateful agent graph, nodes are steps that transform a shared state object, and edges are transitions between nodes — either fixed (always go to the same next node) or conditional (a router function inspects the current state and returns which of several possible next nodes to visit). The graph's structure makes branching logic an explicit, inspectable part of the workflow's DEFINITION rather than logic buried inside a monolithic function — the same request can take genuinely different paths through the SAME graph depending on what earlier nodes produced, exactly the way classify_intent's three outgoing edges route to three different sub-flows depending on the classification result.

Problem 1 · Identifying the state-machine invariant a bad implementation violates

A buggy version of route_after_classify is rewritten so that, for intent == "billing", it returns BOTH "handle_billing" and "handle_technical" (e.g. by mistakenly appending both to a list and the executor calling both). Which core state-machine property from section 1 does this violate, and using the WebSocket lifecycle analogy, why is it a real bug rather than just extra work being done?

Show solution
This violates the property section 1 calls out explicitly: at any point, the agent should occupy EXACTLY ONE node, never two at once -- the same invariant a WebSocket connection maintains by always being in exactly one of CONNECTING/OPEN/CLOSING/CLOSED, never two simultaneously. Running both handle_billing AND handle_technical means the workflow has effectively forked into two concurrent executions from what was supposed to be a single conditional branch point. Why this is a real bug, not just wasted work: handle_technical will now run against a request that was actually a billing issue, potentially producing an irrelevant or actively wrong technical-support response that then flows into generate_response alongside (or instead of) the correct billing response -- depending on how the executor combines two "next node" results, this could silently overwrite the correct output, produce two conflicting responses, or corrupt the shared state object if both nodes write to overlapping keys. A state machine's exactly-one-state-at-a-time property isn't a stylistic preference -- it's what makes the SYSTEM's behavior predictable and traceable to a single path through the graph; violating it means you can no longer reason about "what happened" as one coherent sequence of node visits.
Problem 2 · Tracing what a NEW intent value does to the existing graph

The classifier is upgraded to also detect a new intent category, "refund_request", but section 2's route_after_classify code is left unchanged. Using the code exactly as written, what node does a "refund_request" classification actually route to, and is that necessarily wrong?

Show solution
Tracing route_after_classify exactly as written: intent == "billing" is False (it's "refund_request"), intent == "technical" is also False, so execution falls through to the else branch, which returns "escalate_to_human" -- the catch-all case section 2 documents as handling "angry, unclear, or anything not confidently classified." Whether this is "wrong" depends entirely on intent: if refund requests genuinely need human judgment (policy exceptions, fraud review), routing them to escalate_to_human might be exactly the RIGHT temporary behavior until a dedicated handle_refund node is added -- the else branch is explicitly designed to catch cases the graph doesn't yet have a specific node for, which is a reasonable safety default rather than a crash. But if refund requests are common and mostly routine, silently escalating every single one to a human is a real product/cost problem masquerading as correct behavior, since nothing in the code or the graph structure signals that this case is being handled by the DEFAULT branch rather than a purpose-built one -- someone reading only the graph diagram (section 2's SVG) would have no way to tell "refund_request" wasn't an intentional design decision to route through escalation specifically. This is exactly why a stateful graph's node/edge structure needs to be kept in sync with whatever's actually producing the classifications feeding into it -- the graph doesn't automatically know about new possible states of its own inputs.
Problem 3 · Explaining why escalate_to_human has no outgoing edge to generate_response

In section 2's graph, escalate_to_human's "next" is None — unlike handle_billing and handle_technical, which both route to generate_response. Why is this the correct structural choice, not an oversight?

Show solution
handle_billing and handle_technical are sub-flows where the AGENT still owns producing the final reply -- it gathers whatever information it needs and then generate_response formats and returns an actual answer to the user, which is why both routes correctly to that shared exit node. escalate_to_human is structurally different: its entire job is to hand the conversation OFF to a human agent -- the automated workflow's involvement ends at the handoff itself, not at producing a response, because the actual response (whatever the human eventually says) isn't something this graph generates or even has visibility into. Routing escalate_to_human to generate_response anyway would be actively misleading -- it would suggest the automated system is still going to produce the reply, when the whole point of escalating is that it should NOT. Setting "next": None here correctly marks escalate_to_human as its own terminal node -- the workflow legitimately ends there, just via a different kind of ending (a handoff) than handle_billing and handle_technical's ending (a generated response). A graph can have more than one kind of "done," and modeling that explicitly, rather than forcing every path through the same exit node, is exactly the kind of nuance a diagram like section 2's makes visible at a glance.
Problem 4 · Comparing a stateful graph to a bare ReAct loop for this exact task

Could the customer-support routing in section 2 have been implemented as a ReAct loop instead (the model deciding, via Thoughts, which "tool" — handle_billing, handle_technical, escalate — to call next)? What does the explicit graph give you that a bare ReAct loop over the same three functions wouldn't?

Show solution
Mechanically, yes -- nothing stops you from exposing handle_billing, handle_technical, and escalate_to_human as tools and letting a ReAct loop (react_pattern.html) decide which one to call based on a Thought reasoning about the classification. Both approaches can PRODUCE the same routing decision for a given request. What the explicit graph gives you that the bare loop doesn't: the full set of POSSIBLE paths through the workflow is visible and inspectable as a static artifact -- section 2's SVG diagram, or the GRAPH dictionary itself -- before any request ever runs, the same reviewability advantage plan_and_solve_pattern.html's Problem 3 describes for approval gates. A ReAct loop's possible behaviors are only ever implicit in what the model COULD choose to do at each Thought -- there's no artifact you can point at and say "here are all the paths this workflow can take" the way the graph literally IS that artifact. This matters concretely for this specific use case: a customer support workflow is exactly the kind of system where a team wants to audit "what are all the ways a request can be handled" (for compliance, QA, or just onboarding a new engineer) without needing to enumerate every possible model reasoning trace to reconstruct it -- the graph makes that audit a matter of reading the diagram, not guessing at model behavior. The trade-off is the graph's routing logic (here, a plain if/elif on a classification label) is less flexible than letting a model reason freely about ambiguous cases -- exactly the kind of case-by-case nuance ReAct's Thought step handles naturally and a rigid router function does not.
Problem 5 · Reasoning about resumability, a property loops don't get for free

A request reaches handle_billing, and the process crashes before generate_response runs. Using section 2's run_graph structure, what would need to be true about how state is stored for this workflow to be resumable from exactly where it left off, rather than restarted from classify_intent?

Show solution
For resumability, the CURRENT node name and the current state dictionary (everything accumulated so far -- the classification result, whatever handle_billing had already written into state before the crash) both need to be persisted somewhere DURABLE -- e.g. written to a database or a durable queue -- after each node completes, not just held in the crashed process's in-memory variables the way section 2's run_graph loop does by default (its `node` and `state` local variables vanish entirely when the process dies). With that persistence in place, resuming means: on restart, look up the last successfully completed node and its resulting state for this request, set `node = "generate_response"` (the node AFTER the last completed one, per GRAPH["handle_billing"]["next"]) and `state` to the persisted value, then continue the same while loop from there -- rather than re-running classify_intent and handle_billing from scratch, which would be wasteful at best (re-doing completed work) and actively wrong at worst if handle_billing had a side effect (e.g. actually issuing a partial refund) that shouldn't happen twice, the same double-execution risk the database CRUD lab's idempotency-key lesson covers for retried requests generally. This is precisely the practical advantage an EXPLICIT graph representation provides over an implicit control flow buried in a function: because the workflow's progress is expressible as "which node, plus what state," that's a natural, serializable checkpoint to persist -- a bare while-loop or a deeply nested chain of function calls has no equally clean equivalent to snapshot and resume from, since "where you are" in that case is smeared across the call stack rather than being one clean, explicit value.
