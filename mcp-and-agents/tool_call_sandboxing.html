MCP & AGENTS LAB · TOOL CALL SANDBOXING

A tool call executing on an agent's behalf shouldn't be able to touch whatever it wants.

prompt_injection_risks.html established that an agent can be tricked into WANTING to do something harmful. Sandboxing is the layer underneath that: even if an agent decides (correctly or via injection) to call a tool with dangerous arguments, sandboxing constrains what that tool call is physically CAPABLE of touching — a "read file" tool restricted to one directory, a code-execution tool run with no network access. This lab builds a concrete allowlist-checking wrapper and shows exactly where an out-of-bounds request gets stopped.

01 — Not "will the agent behave," but "what CAN the tool physically reach"

Isolating what a tool call can touch

Start here, before any code. Think about giving a new employee a building keycard. You could hand them a master key that opens every door in the building, trusting them to only ever use it on the doors relevant to their job — or you could issue a keycard programmed to open ONLY the specific doors their job actually requires, so that even if they're confused, careless, or someone tricks them into trying the wrong door, the door itself simply doesn't open. Sandboxing a tool call is the second approach applied to software: instead of trusting the AGENT's judgment about which files to read or which hosts to contact, you constrain the TOOL's actual reach so that even a compromised or confused agent can't get a tool to do something outside its intended boundary.

This is a genuinely different layer of defense than the ones prompt_injection_risks.html discussed. That lab's mitigations (delimiting untrusted content, instructing the model to treat it as data-only) try to stop the agent from ever WANTING to do something harmful in the first place. Sandboxing doesn't try to stop that at all — it assumes the agent's decision-making might fail (via injection, a bug, or a bad tool call the model generates for entirely mundane reasons) and asks instead: even if the agent DOES try to do something harmful, what is the tool itself physically capable of reaching?

/etc/passwd — outside the boundary, unreachable regardless of what the agent asks for
~/.ssh/id_rsa — outside the boundary, unreachable regardless of what the agent asks for

Two concrete forms this takes, both with the same underlying principle: a read-file tool restricted to a specific directory — no matter what path an agent's tool call requests, the tool refuses to read anything outside its allowed directory tree, full stop, independent of whether the request came from a legitimate need or an injected instruction. And a code-execution tool run inside an isolated container or process with no network access — even if an agent is tricked into generating code that tries to exfiltrate data over the network, the sandboxed execution environment has no network interface to exfiltrate anything over, making the attempt fail at the OS/container level regardless of what the code itself contains.

Interview-ready definition: tool call sandboxing constrains what a tool invocation is CAPABLE of touching — filesystem paths, network destinations, other system resources — independent of what the calling agent's decision-making process asked for. Where prompt injection mitigations try to prevent an agent from being tricked into requesting something harmful, sandboxing assumes that request might arrive anyway (from injection, a bug, or an honest mistake) and enforces a hard boundary at the point of EXECUTION, so a request outside that boundary fails regardless of why it was made.
02 — A concrete allowlist check, before the tool ever runs

A sandboxing wrapper, concretely

Start here, before the code. The mechanism is a checkpoint at a doorway: before a tool call's requested path is ever handed to the actual file-reading code, a wrapper function checks that path against an allowlist of permitted directories. If the requested path resolves to somewhere inside an allowed directory, the wrapper lets the real tool run. If it resolves to anywhere else — even via a clever relative path like ../../etc/passwd — the wrapper rejects the request before the real file-reading code ever executes.

import os ALLOWED_DIRECTORIES = [ "/data/reports", "/data/uploads", ] def sandboxed_read_file(requested_path: str) -> dict: # resolve to an ABSOLUTE, canonical path first -- this is the step that # defeats "../../etc/passwd"-style traversal tricks, since os.path.realpath # collapses ".." segments and symlinks down to the actual target path # BEFORE any comparison against the allowlist happens real_path = os.path.realpath(requested_path) # check the RESOLVED path against every allowed directory -- a path is # only permitted if it is genuinely INSIDE one of these trees, not # merely if its unresolved string happens to start with the right prefix is_allowed = any( real_path == allowed or real_path.startswith(allowed + os.sep) for allowed in ALLOWED_DIRECTORIES ) if not is_allowed: # REJECTED before the real file-reading code ever runs -- # this return happens instead of ever calling open() return {"status": "denied", "error": f"'{requested_path}' resolves outside the sandbox boundary"} # only reached if the path passed the allowlist check with open(real_path, "r") as f: return {"status": "success", "content": f.read()}

Notice the order of operations is what makes this actually enforce a boundary: os.path.realpath resolves the path FIRST, collapsing any .. traversal or symlink indirection down to where the path genuinely points — and only THEN is the resolved path compared against the allowlist. A naive version that checked the allowlist against the raw, unresolved string (e.g. just checking whether the requested string starts with "/data/") could be defeated by a request like /data/reports/../../etc/passwd, which starts with the right prefix as a raw string but resolves to something entirely outside the sandbox once collapsed.

The exact same pattern extends to a code-execution tool, just with a different resource being constrained: instead of checking a filesystem path against an allowlist of directories, the sandbox is the execution ENVIRONMENT itself — running submitted code inside a container or subprocess launched with no network interface attached and a read-only or entirely separate filesystem, so there is no allowlist check to bypass at all, because the capability (reaching the network, writing outside a scratch directory) simply doesn't exist inside that environment regardless of what the code tries to do.

TRY THE SANDBOXED READ TOOL
Interview-ready definition: a sandboxing wrapper enforces a resource boundary by resolving a tool call's requested resource (a filesystem path, in this example) to its canonical, fully-resolved form BEFORE comparing it against an allowlist — closing off traversal tricks that could otherwise make an out-of-bounds request look, as a raw unresolved string, like it satisfies the allowlist. The check happens as a gate strictly before the tool's real operation (e.g. open()) ever runs, so a rejected request never reaches the underlying resource at all, rather than being caught by an error thrown by that resource afterward.

Problem 1 · Explaining why the allowlist check must happen AFTER path resolution

Section 2's code calls os.path.realpath() before checking the allowlist, not after. Write a concrete request that would incorrectly pass a NAIVE version of the check (comparing the raw, unresolved string against the allowlist), and explain why resolving first closes that gap.

Show solution
A concrete request that defeats a naive raw-string check: requested_path = "/data/reports/../../etc/passwd". As a raw STRING, this literally starts with "/data/reports" -- a naive check doing something like requested_path.startswith("/data/reports") would see this string, confirm the prefix matches, and incorrectly allow it. But the path this string actually POINTS TO, once ".." segments are resolved (each ".." moves up one directory), is /etc/passwd -- completely outside both allowed directories. Resolving first with os.path.realpath() converts the request to what it ACTUALLY resolves to on the filesystem (following ".." and any symlinks) BEFORE the string comparison ever happens, so the allowlist check is comparing against the true destination, not against a string that merely happens to start with the right characters. This is the general lesson: any check comparing untrusted input against a boundary needs to operate on the FULLY NORMALIZED form of that input, because there are often multiple different string representations that all resolve to the same (or a different, unintended) actual target -- checking the raw, un-normalized string is checking the wrong thing.
Problem 2 · Sandboxing a network-capable tool, not just a file-reading one

Using section 1 and 2's reasoning, sketch (in words, not full code) how you'd sandbox a tool that makes outbound HTTP requests on the agent's behalf, so it can only reach a specific allowlist of hostnames. What's the equivalent of "resolve before comparing" for a hostname, given DNS exists?

Show solution
The structural shape is identical to section 2's file-path wrapper: a wrapper function intercepts the tool's requested URL BEFORE the actual HTTP request is made, extracts the hostname, and checks it against an ALLOWED_HOSTNAMES allowlist (e.g. ["api.internal-service.com", "data.trusted-partner.com"]) -- rejecting the request before any network call happens if the hostname isn't on the list. The DNS-specific version of "resolve before comparing": a naive check might compare the REQUESTED hostname string against the allowlist and stop there, but an attacker-controlled DNS response (or a hostname that LOOKS like an internal service via a clever subdomain trick, e.g. "api.internal-service.com.evil.com") could resolve to a completely different, unintended IP address than the allowlist author expected -- the equivalent of the "../../etc/passwd" trick, but for network destinations instead of filesystem paths. A more robust version resolves the hostname to its actual IP address and checks THAT against a range of allowed IPs/CIDR blocks (or, more simply, still checks the exact hostname string but rejects anything that isn't an EXACT match, not merely "starts with" or "contains" the allowed name, closing off the subdomain-trick variant of the same underlying "the raw string looks right but resolves somewhere else" problem section 2 solved for filesystem paths).
Problem 3 · Deciding what the tool should return on a denial, connecting to loop_termination_logic

Using loop_termination_logic.html's reasoning about feeding failures back into the transcript rather than crashing, what should sandboxed_read_file return when a request is denied, and why does that choice matter for how the agent loop continues?

Show solution
Section 2's code already gets this right: it returns a structured dict ({"status": "denied", "error": "...resolves outside the sandbox boundary"}) rather than raising an uncaught exception or crashing the whole process. This mirrors deterministic_parsing.html and loop_termination_logic.html's shared posture from earlier this month -- a failure inside one tool call is fed back into the transcript as the next Observation, letting the model's NEXT step decide how to proceed (try a different, in-bounds path, explain to the user why it can't access that file, or give up gracefully) -- rather than the sandbox violation taking down the entire agent loop. Why this matters specifically for sandboxing: if a denial instead raised an unhandled exception that crashed the loop, an attacker (or an injected instruction) could use a SANDBOX VIOLATION ITSELF as a denial- of-service vector -- deliberately requesting an out-of-bounds path not because they expect it to succeed, but specifically to crash the agent and disrupt whatever legitimate task it was in the middle of. A structured "denied" result that flows back into the loop exactly like any other tool observation closes that off -- the sandbox boundary protects the RESOURCE, and the structured-failure-handling pattern protects the LOOP's own availability, two different things that both need to hold.
Problem 4 · Distinguishing sandboxing from permission scoping

This week's next lab, permission_scoping.html, also restricts what a tool can do. Using this lab's "what a tool call can physically TOUCH" framing, articulate the genuine difference between sandboxing and permission scoping — are they the same mechanism with different names, or two different layers?

Show solution
They're two different, complementary layers, not the same mechanism under different names. Sandboxing (this lab) constrains WHAT RESOURCES a tool call can physically reach at the point of execution -- a filesystem boundary, a network allowlist, a container with no outbound access -- independent of who is calling it or what they're authorized to do; it's enforced at the resource/execution layer, below the application's own notion of identity or permission. Permission scoping (next lab) constrains WHICH OPERATIONS a specific tool or agent is even ALLOWED to attempt in the first place, based on least-privilege identity -- e.g. a calendar tool granted calendar:read but not calendar:delete never even has the DELETE capability wired up for it to attempt, regardless of whether the underlying resource would have allowed a delete if asked. This is enforced at the authorization/capability layer, ABOVE the resource itself. Concretely, they can fail independently of each other: a tool could be correctly scoped (only has calendar:read permission, so it would never even generate a delete call) but still be UNSANDBOXED (if it also had a file-read capability with no directory allowlist, it could read any file on the system its process can access) -- correct permission scoping doesn't imply the resource-level boundary was ever enforced. Symmetrically, a perfectly sandboxed file-read tool (restricted to /data/reports) could still be handed to an agent that has NO business reading files at all -- sandboxing the resource doesn't substitute for deciding, at the permission layer, whether this tool should be reachable by this agent in the first place. Real systems need both layers, each catching a different kind of over-broad access.
Problem 5 · Reasoning about a sandbox that's technically correct but too permissive

A team sets ALLOWED_DIRECTORIES = ["/"] (the entire filesystem root) for a read-file tool, reasoning "the allowlist check is implemented correctly, so we're sandboxed." Is this a real sandbox? What's actually wrong with it?

Show solution
The CHECK is implemented correctly (path resolution happens before comparison, exactly as section 2 specifies), but the boundary it enforces is functionally no boundary at all -- every possible resolved path on the entire filesystem is, trivially, "inside" an allowlist of ["/"], so the allowlist check will never actually deny anything. This is a real, common trap: the MECHANISM can be technically sound (correctly resolving paths, correctly comparing against the configured list) while the CONFIGURATION of that mechanism provides zero actual isolation, because "the entire filesystem" isn't a meaningfully constrained boundary. The deeper lesson: sandboxing's security value comes specifically from the allowlist being NARROW -- scoped tightly to exactly what the tool legitimately needs (echoing permission_scoping.html's least-privilege principle, applied here to resources instead of operations). A correctly -implemented check with an overly broad allowlist gives a false sense of security ("we have sandboxing!") without providing the actual protection sandboxing exists to provide -- section 1's whole motivating scenario (an agent tricked into requesting something harmful) is completely unmitigated if "harmful" and "allowed" overlap entirely because the allowlist was never actually scoped down from "everything." The fix isn't a different mechanism -- it's configuring the SAME mechanism with directories that reflect what this specific tool actually needs, nothing more.
