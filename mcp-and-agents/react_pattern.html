MCP & AGENTS LAB · REACT PATTERN

A model that thinks, acts, looks at what happened, then thinks again — out loud, every step.

ReAct (Reason + Act) is the pattern behind most tool-using agent loops: instead of trying to answer in one shot, the model interleaves explicit reasoning with tool calls, one step at a time, reading each result before deciding what to do next. This lab builds the loop, worked by hand on a real question, then animates the exact transcript it produces.

Thought — what does the model reason next
Action — a tool call it decides to make
Observation — the result fed back in

01 — Reasoning and acting, interleaved, not separated

The core loop: Thought → Action → Observation

Start here, before any code. Think about how you'd actually answer "what's the population of the capital of France?" if you didn't already know the answer cold. You wouldn't silently work it out and blurt a final number — you'd reason out loud in stages: "first I need to know the capital of France" (thought), so you'd look it up (action), see "Paris" come back (observation), then think again: "now I need Paris's population" (thought), look THAT up (action), see "~2.1 million" come back (observation), and only THEN give your final answer. Each step depends on what the previous lookup actually returned — you couldn't have planned the second lookup before seeing the first result, because you didn't yet know what city to look up.

That's exactly what ReAct does with a language model driving the loop: at each step, the model produces a Thought (its reasoning about what to do next), then an Action (a tool call, chosen based on that reasoning), then receives an Observation (the tool's actual result) — which becomes the input to the NEXT thought. The loop repeats until the model decides it has enough information to produce a Final Answer instead of another action.

Worked example, in full, for "What's the population of the capital of France?" using a single lookup(query) tool:

Thought 1: I need to find the capital of France before I can find its population. Action 1: lookup("capital of France") Observation 1: Paris Thought 2: Now I know the capital is Paris. I need its population next. Action 2: lookup("population of Paris") Observation 2: approximately 2.1 million (city proper) Thought 3: I now have both facts I need to answer the original question. Final Answer: The capital of France is Paris, which has a population of approximately 2.1 million people.

Notice Action 2 could not have been planned before Observation 1 arrived — the model didn't know to look up "population of Paris" until the first lookup told it the capital WAS Paris. This is the defining property of ReAct: each action is chosen in light of what actually happened in the previous step, not decided in advance as part of some larger plan. The plan_and_solve_pattern lab covers exactly the alternative — committing to a full plan up front — and works through why that trade-off cuts the other way.

Interview-ready definition: ReAct (Reason + Act) is an agent pattern that interleaves explicit reasoning steps (Thoughts) with tool invocations (Actions) and their results (Observations) in a single repeating loop — Thought → Action → Observation, repeated until the model emits a Final Answer instead of another action. Each Thought is conditioned on the most recent Observation, meaning the model's next action is chosen adaptively, in response to what it just learned, rather than committed to ahead of time.
02 — Parse the model's output, run the tool, feed the result back in, repeat

Implementing a basic ReAct loop

Start here, before the code. Mechanically, a ReAct loop is a text-generation loop wearing a strict format: the model is prompted to always produce its next step as "Thought: ... / Action: tool_name(args) / " and then STOP — the calling code parses that action out, actually executes the tool, appends the result as "Observation: ..." to the running transcript, and calls the model again with the whole transcript so far as its prompt. The model never "sees" the tool run — it only ever sees text, some of which happens to be an observation that was inserted by code, not generated by the model itself.

SYSTEM_PROMPT = """You solve problems using this exact loop, one step at a time: Thought: <your reasoning about what to do next> Action: lookup(<query>) (then STOP -- wait for an Observation before continuing) Once you have enough information, instead of another Action, write: Thought: <final reasoning> Final Answer: <your answer> """ def parse_action(model_output: str): # real parsing -- pull the tool name and argument out of the model's # own text, e.g. "Action: lookup(\"population of Paris\")" match = re.search(r'Action:\s*(\w+)\((.*)\)', model_output) if not match: return None tool_name, raw_arg = match.group(1), match.group(2).strip('"') return {"tool": tool_name, "arg": raw_arg} def react_loop(question: str, tools: dict, max_steps: int = 6) -> str: transcript = f"Question: {question}\n" for step in range(max_steps): # STEP 1: prompt the model with everything so far -- it produces the # next Thought and either an Action or a Final Answer model_output = call_model(SYSTEM_PROMPT + transcript) transcript += model_output # STEP 2: check whether the model decided it's done if "Final Answer:" in model_output: return model_output.split("Final Answer:")[-1].strip() # STEP 3: parse the Action out of the model's own generated text action = parse_action(model_output) if action is None: raise ValueError(f"Model output didn't match the expected format:\n{model_output}") # STEP 4: actually execute the tool -- this is real code running, # not something the model does itself result = tools[action["tool"]](action["arg"]) # STEP 5: feed the observation back into the transcript, then loop transcript += f"Observation: {result}\n" raise RuntimeError("Exceeded max_steps without a Final Answer")

Two details carry real weight here. First, max_steps is not decoration — without a hard cap, a model that never converges on a Final Answer would loop indefinitely, a failure mode the Week 3 loop-termination-logic topic will formalize much further. Second, the ENTIRE transcript (every prior Thought/Action/Observation) is re-sent as the prompt on every single step — the model has no persistent memory of the loop between calls; its only continuity is whatever text is physically in the prompt each time it's called again.

Interview-ready definition: a basic ReAct loop repeatedly (1) prompts the model with the full transcript so far, formatted to elicit a Thought followed by either an Action or a Final Answer, (2) checks for a Final Answer and returns it if present, (3) otherwise parses the requested tool call out of the model's own generated text, (4) actually executes that tool call in application code, and (5) appends the result as an Observation onto the transcript before looping back to step 1 — bounded by a maximum step count to guarantee termination even if the model never emits a Final Answer.

Problem 1 · Tracing what changes if the first lookup returns something unexpected

Suppose lookup("capital of France") had returned "Paris (disputed — some sources cite Versailles historically)" instead of a clean "Paris". Using section 1's loop, what would Thought 2 need to do differently, and why couldn't this have been anticipated at Thought 1?

Show solution
Thought 2 would need to reason about the ambiguity itself before proceeding -- e.g. deciding to treat "Paris" as the intended answer for a population lookup (since Versailles is not the modern capital), or explicitly asking a follow-up lookup to resolve which interpretation is correct, rather than blindly assuming the first lookup returned a single, clean value. This couldn't have been anticipated at Thought 1 because Thought 1 was reasoning about what to look up NEXT, not about what the result of that lookup would contain -- the model has no way to know in advance whether Observation 1 will be clean or ambiguous, since it hasn't happened yet. This is exactly the property section 1 calls out: each Thought is conditioned on the most recent Observation. A model running ReAct handles this kind of surprise gracefully because its NEXT reasoning step naturally incorporates whatever the tool actually returned, ambiguous or not -- whereas a plan committed to in advance (the plan_and_solve_pattern lab's approach) would have no natural point to revise its strategy mid-execution without an explicit re-planning step, since the plan was fixed before any observation existed to reveal the ambiguity.
Problem 2 · Diagnosing a parsing failure

Using section 2's parse_action regex (r'Action:\s*(\w+)\((.*)\)'), what happens if the model generates "Action: lookup population of Paris" — no parentheses at all — instead of the expected "Action: lookup(\"population of Paris\")"? Walk through the loop's actual behavior.

Show solution
The regex requires literal parentheses containing the argument -- with no parentheses present at all, re.search finds no match, so parse_action returns None. Back in react_loop, the code explicitly checks "if action is None: raise ValueError(...)" -- so the loop raises an exception and stops, rather than silently guessing what the model might have meant or crashing with some unrelated, harder-to-diagnose error deeper in the tool-execution step. This is a deliberate design choice worth noticing: the loop treats a malformed Action as a HARD failure rather than trying to fuzzy-parse around it. A more permissive design might try several regex patterns or ask the model to retry in-loop, but the version here fails loudly and immediately with the exact malformed text included in the error message -- which is far easier to debug than silently misinterpreting "lookup population of Paris" as, say, a tool named "lookup" with no arguments, or worse, matching it against a different tool name accidentally. Whether to fail loudly (as here) or retry automatically is a real design decision the Week 3 "deterministic parsing of model output" topic goes into in more depth -- but failing loudly is the safer default in a lab specifically trying to teach you what "malformed model output" looks like.
Problem 3 · Reasoning about why the full transcript is re-sent every step

Section 2's loop re-sends the ENTIRE transcript (every prior Thought/Action/Observation) as the prompt on every single call to call_model. Why can't the loop instead just send the single most recent Observation each time, to save tokens?

Show solution
The model itself has no memory between calls -- each call to call_model is a fresh, independent request with no built-in continuity from the previous call (this is the same statelessness property covered in systems/stateless_vs_stateful.html, now showing up at the level of a single model call rather than a whole service). If the loop only sent the most recent Observation, the model would have no way to know WHY that observation matters, what the original question was, or what it already concluded in Thought 1 -- it would be reasoning from a single disconnected fact with zero context, unable to even remember that it was in the middle of a multi-step lookup at all. The full transcript IS the model's only form of memory across the loop's steps -- every Thought, Action, and Observation the model needs to "remember" has to be physically present in the next prompt, because nothing else persists between calls. This does mean token usage grows with every step (a real cost, and part of why max_steps in section 2 matters for cost control too, not just termination), but truncating the transcript risks the model losing track of the original question or earlier reasoning entirely -- exactly the token-budget-vs-completeness trade-off the storage-and-rag token_budget_management lab covered for conversation history generally, now applying specifically to an agent loop's own working transcript.
Problem 4 · Comparing ReAct's adaptivity to a scenario where it doesn't help

A task requires exactly 3 independent lookups that don't depend on each other at all (e.g. "what are the capitals of France, Japan, and Brazil?" — each lookup is unrelated to the others' results). Does ReAct's step-by-step adaptivity provide any real benefit here compared to just deciding all 3 actions upfront?

Show solution
Not much, and this is a genuinely useful edge case to notice. ReAct's core advantage -- letting each action be informed by the PREVIOUS observation -- only pays off when a later action's parameters or choice actually depend on an earlier result. Here, none of the 3 lookups depend on each other's outputs at all: "capital of Japan" doesn't need to know what "capital of France" returned. Running them one at a time through a full Thought/Action/Observation cycle each still WORKS, but it pays the cost of 3 separate round trips to the model (3 full re-sends of a growing transcript, per Problem 3) to accomplish something that gains nothing from being sequential and adaptive. This is precisely the kind of task where Plan-and-Solve's upfront approach -- or better, recognizing the 3 lookups are independent and could be dispatched in parallel rather than sequentially at all -- would be strictly more efficient, since there's no genuine information dependency forcing them to happen one after another. ReAct isn't wrong here, it's just not buying you anything: its adaptivity is a real advantage specifically when later steps genuinely depend on earlier results (like this lab's capital-then-population example, where the second lookup's query literally can't be known until the first resolves) -- and a comparatively unnecessary overhead when they don't.
Problem 5 · Designing for a tool call that returns an error, not a result

Section 2's loop assumes tools[action["tool"]](action["arg"]) always succeeds and returns a usable result. Using the graceful-error-handling reasoning from mcp_client_basics.html, how should the loop change to handle the lookup tool raising an exception (e.g. the query matched nothing)?

Show solution
The tool call should be wrapped in explicit error handling, and -- this is the key move -- the ERROR itself should be fed back into the transcript as the Observation, rather than letting the exception crash the whole loop: try: result = tools[action["tool"]](action["arg"]) transcript += f"Observation: {result}\n" except ToolError as e: transcript += f"Observation: Error - {e}\n" This mirrors mcp_client_basics.html's core lesson exactly: a tool call failing is an expected, recoverable outcome in an agentic loop, not a reason to crash the entire process. By feeding "Observation: Error - no results found for query" back into the transcript instead of raising, the NEXT Thought the model generates gets to see that the lookup failed and can react accordingly -- rephrasing the query, trying a different tool, or concluding it can't answer and saying so honestly in a Final Answer -- exactly the self-correcting behavior an agent loop needs to survive routine, expected failures along the way rather than dying on the first one. Treating a failed Observation as just another kind of Observation (rather than a special crash case) is what keeps the loop uniform and robust.
