SYSTEM DESIGN LAB · MCP GATEWAY DESIGN

One agent, dozens of tool servers. Something has to decide which one answers.

A real agentic deployment doesn't talk to one MCP server — it talks to a database server, a search server, a calendar server, a dozen others, each possibly built and owned by a different team. An MCP gateway is the single front door that routes each request to the right backend server, centralizes auth and per-client permissions, and — like any front door under enough traffic — needs to scale horizontally itself. This lab builds all three, at the same bar as backend/rate_limiter_design.html and systems/caching_layer_design.html.

01 — One address for the client, many addresses behind it

Routing requests to multiple agents/MCP servers

Start here, before any diagram. Imagine calling a large company's single support phone number instead of needing to somehow know the direct line for billing, technical support, and shipping separately. You dial one number; a receptionist (or an automated menu) listens to what you actually need and transfers you to whichever department can handle it. You never had to learn three different phone numbers, and the company is free to reorganize which team handles what without your phone number ever changing.

An MCP gateway is exactly this receptionist, for agents. Instead of a client (an LLM-driven agent) needing to know the address of every individual MCP server it might need — a database-query server, a search server, a calendar server — it connects to ONE gateway address. The gateway inspects each incoming request (specifically, which tool is being called, per the mcp_fundamentals_jsonrpc lab's tools/call shape) and forwards it to whichever backend MCP server actually implements that tool, based on a routing table the gateway maintains.

# a simplified gateway routing table -- maps tool name to backend server ROUTING_TABLE = { "query_database": "http://db-mcp-server:8001", "search_documents": "http://search-mcp-server:8002", "create_event": "http://calendar-mcp-server:8003", } async def handle_gateway_request(request: dict) -> dict: if request["method"] == "tools/call": tool_name = request["params"]["name"] backend_url = ROUTING_TABLE.get(tool_name) if backend_url is None: return {"jsonrpc": "2.0", "id": request["id"], "error": {"code": -32601, "message": f"No server handles tool '{tool_name}'"}} return await forward_to_backend(backend_url, request) # tools/list is special: the gateway must MERGE every backend's tool # list into one combined list, so the client sees ALL available tools # as if they came from a single server elif request["method"] == "tools/list": return await merge_all_backend_tool_lists(request)

Notice tools/list needs special handling: a client asking "what tools exist?" should see ONE combined list spanning every backend the gateway fronts, not just the tools of whichever single server happens to answer first. The gateway is genuinely aggregating multiple servers' catalogs into one presented surface, not merely forwarding one request to one destination.

Interview-ready definition: an MCP gateway routes each incoming request to the correct backend MCP server based on which tool (or resource/prompt) the request targets, using a routing table mapping capability names to backend addresses — giving clients a single address to connect to regardless of how many actual servers exist behind it. Because a gateway fronts MULTIPLE servers, discovery operations like tools/list require the gateway to aggregate every backend's individual catalog into one merged response, rather than simply forwarding to a single destination the way a routing decision for tools/call does.
02 — One place to get security right, instead of N places to get it wrong

Auth and permission scoping at the gateway layer

Start here, before the argument. Imagine a large office building where EVERY individual room has its own separate lock, its own separate guest sign-in sheet, and its own separate rule about who's allowed in — set up independently by whoever happens to run that room, with zero coordination between rooms. Compare that to a building with ONE front desk: everyone checks in once, gets a badge that's scoped to exactly the rooms they're allowed into, and every room simply trusts a badge that reads "access: floor 3 only." The second design doesn't just look tidier — it's the only one where a security audit can actually answer "who can get into what" by looking in ONE place.

Centralizing auth at the gateway means: the CLIENT authenticates ONCE, to the gateway — not separately to every individual backend MCP server it might end up calling. The gateway then decides, per client, which TOOLS that client is permitted to invoke (a client's identity might be scoped to "can call search_documents and create_event, but NOT query_database" — a real per-client permission boundary), and either forwards or rejects each request based on that scope, before it ever reaches a backend server at all.

# centralized auth + permission check, BEFORE routing (section 1) CLIENT_PERMISSIONS = { "client-mobile-app": {"search_documents", "create_event"}, "client-admin-tool": {"search_documents", "create_event", "query_database"}, } async def authorize_and_route(request: dict, api_key: str) -> dict: client_id = verify_api_key(api_key) # ONE auth check, at the gateway, done once if client_id is None: return {"error": {"code": -32001, "message": "Unauthenticated"}} tool_name = request["params"]["name"] allowed = CLIENT_PERMISSIONS.get(client_id, set()) if tool_name not in allowed: return {"error": {"code": -32002, "message": f"'{client_id}' not permitted to call '{tool_name}'"}} return await handle_gateway_request(request) # section 1's routing, only reached if authorized

Per-server auth (no gateway)

Every individual MCP server implements its own auth check, its own permission model, possibly its own bugs — a client that shouldn't have access to query_database is only blocked if THAT specific server's team remembered to enforce it correctly. A security audit means reviewing N separate implementations, and a permission change means updating N separate places.

Centralized gateway auth

One auth check, one permission model, enforced BEFORE a request ever reaches any backend server — a backend server can even trust "if this request reached me, the gateway already verified it's allowed," simplifying every individual server's own code. A security audit or a permission change happens in exactly one place.

Interview-ready definition: centralizing auth and per-client tool permissions at the gateway layer means clients authenticate once against the gateway, and the gateway enforces a per-client permission scope (which specific tools/resources/prompts a given client is allowed to invoke) before routing any request to a backend server — rather than requiring every individual backend server to independently implement its own auth and permission logic. This is architecturally cleaner because it produces exactly ONE place where security policy is defined, audited, and updated, and it lets backend servers be written more simply, trusting that any request reaching them has already been authenticated and authorized upstream.
03 — The front door becomes the bottleneck once enough traffic arrives

Scaling the gateway horizontally

Start here, before the diagram. Section 1 and 2 gave the gateway a genuinely important job — EVERY request from EVERY client passes through it, for both routing and auth. That's exactly what makes it a single point of load, and eventually a single point of failure, if it's only ever one process: once traffic grows past what one gateway instance can handle, the fix is the same one covered all the way back in Month 1's systems/vertical_vs_horizontal_scaling.html and systems/load_balancers.html — run MANY gateway instances behind a load balancer, rather than trying to make one instance infinitely powerful.

This immediately raises the exact question the Month 1 stateless/stateful lab and Month 3's replication lab both dealt with: where does the routing table and the per-client permission data (sections 1 and 2) actually LIVE, if there are now multiple gateway instances? If each instance kept its own private in-memory copy, a permission change (revoking a compromised client's access, adding a new backend server) would need to somehow be pushed to EVERY instance — and any instance that missed the update would keep enforcing the old, stale policy. The fix mirrors the rate limiter lab's distributed-counter lesson exactly: routing tables and permissions belong in a shared external store (a config service, a database, a fast cache like Redis) that every gateway instance reads from, NOT duplicated separately in each instance's own memory — this is precisely what makes the gateway instances stateless (per systems/stateless_vs_stateful.html) and therefore safe to scale horizontally by simply adding more of them.

Interview-ready definition: scaling an MCP gateway horizontally means running multiple identical gateway instances behind a load balancer rather than growing one instance's capacity indefinitely, exactly mirroring the general horizontal-scaling pattern — this eliminates the gateway as a single point of failure and lets throughput scale by adding instances. The prerequisite this imposes is that the gateway instances must be STATELESS with respect to routing tables and per-client permissions: that data has to live in a shared external store every instance reads from (not duplicated in each instance's private memory), otherwise different instances can enforce different, inconsistently-updated policies for the same client — the same shared-state problem the rate limiter design lab's distributed counter solved, now applied to routing/auth data instead of a request count.

Problem 1 · Diagnosing a routing gap

A client calls a tool named send_email, but no backend server currently registers that tool with the gateway. Using section 1's code, what does authorize_and_route actually return, and why is this a BETTER failure mode than the gateway silently dropping the request?

Show solution
Using section 1's handle_gateway_request logic, ROUTING_TABLE.get("send_email") returns None (no entry registered for that tool name), so the gateway returns a proper JSON-RPC error response: {"error": {"code": -32601, "message": "No server handles tool 'send_email'"}} -- correlated back to the client's original request id, per the JSON-RPC fundamentals lab's error-response shape. This is a better failure mode than silently dropping the request because a dropped request gives the CLIENT no signal at all about what happened -- it would simply hang waiting for a response that's never coming (or eventually time out with no diagnostic information), leaving a developer to guess whether the problem was a network issue, a crashed server, or simply a typo'd/unregistered tool name. A proper JSON-RPC error response tells the client (and whoever's debugging it) EXACTLY what went wrong -- "no server handles this specific tool" -- immediately and unambiguously, which is precisely the kind of graceful, structured failure the later mcp_client_basics lab covers handling on the client side.
Problem 2 · Reasoning about auth check ordering

Section 2's authorize_and_route checks authentication AND permission BEFORE calling section 1's handle_gateway_request (routing). What would go wrong, specifically, if this order were reversed — route first, check permissions after the backend already responded?

Show solution
Reversing the order would mean the gateway forwards a request to a real backend MCP server -- causing that server to actually EXECUTE the tool call, with whatever real side effects that entails (a database query actually runs, a calendar event actually gets created, an email actually gets sent) -- BEFORE ever checking whether the calling client was even permitted to invoke that tool in the first place. Discovering "actually, this client wasn't allowed to do that" only after the action already happened is far too late to matter: you can reject the RESPONSE on its way back to the client, but you can't un-execute a side effect that already occurred on the backend. This is exactly why section 2's code structure checks authentication and permission strictly BEFORE section 1's routing/forwarding step, not after -- the whole architectural value of centralizing auth at the gateway (a request that reaches a backend server can be trusted to have already been authorized) depends entirely on that check happening first, on the gateway's side, before any backend ever sees the request at all. Checking permissions after the fact doesn't centralize anything meaningful -- it just adds a pointless extra step after the real damage (or at minimum, the real unauthorized action) is already done.
Problem 3 · Comparing per-server auth duplication to a real bug scenario

In a per-server-auth world (no gateway), the query_database server's team ships a bug that accidentally allows an unauthenticated request through. Using section 2's comparison, what's the actual blast radius of this bug under each architecture (per-server auth vs. centralized gateway auth), and why do they differ?

Show solution
Under PER-SERVER AUTH (no gateway): the blast radius is scoped to exactly the query_database server's own auth bug -- other servers (search, calendar) have their OWN independent auth implementations that are unaffected by this specific bug, so this is a real but contained vulnerability limited to one backend. However, the actual risk here is systemic, not just this one instance: N independently-implemented auth systems means N independent chances for exactly this kind of bug to occur, and section 2 already noted a security audit has to separately review every one of them to find and fix each one -- this bug in query_database's team's code is a symptom of that broader N-implementations risk, not a one-off. Under CENTRALIZED GATEWAY AUTH: there is no per-server auth implementation at all for query_database's team to introduce a bug INTO -- auth is enforced once, upstream, at the gateway, before any request reaches query_database's server. This doesn't mean the gateway's OWN single auth implementation can never have a bug (it still could) -- but it means there is exactly ONE place such a bug could exist, rather than N independently-written, independently-buggy places, which directly matches section 2's "one place to audit/fix" argument. The comparison isn't "centralized auth is bug-proof" -- it's that centralizing reduces the SURFACE AREA where such a bug could be introduced from N independent implementations down to one shared, more heavily-scrutinized one.
Problem 4 · Diagnosing an inconsistent-policy bug under horizontal scaling

A team scales their gateway to 3 instances behind a load balancer, but each instance loads its routing table and permissions from a local config file at startup, into its own private memory. An admin revokes a compromised client's access. Using section 3's reasoning, what can go wrong, and what's the fix?

Show solution
What goes wrong: revoking the compromised client's access updates whatever the admin directly changed (say, one instance's local config file, or a central file that gets pushed out asynchronously) but does NOT automatically and atomically update all 3 instances' independent in-memory copies of the permission data -- exactly the failure mode section 3 warns about. Depending on round-robin routing (or whichever load-balancing algorithm is in use), the compromised client's next request might land on an instance that HASN'T yet picked up the revocation, and that instance -- still holding the old, stale permission data in its own private memory -- would incorrectly continue allowing the very access that was supposed to have just been revoked. This is a genuinely dangerous inconsistency for a SECURITY-relevant setting specifically, since the whole point of the revocation was to immediately cut off access, not "cut off access on however many of 3 instances happened to reload their config file since the change." The fix, per section 3: routing tables and permissions must live in a SHARED EXTERNAL STORE (a database, a config service, a fast cache like Redis) that every gateway instance reads from directly at request time (or via a short-TTL cache with a deliberately bounded staleness window), rather than each instance loading its own private, independently-stale copy at startup. This makes the gateway instances properly stateless with respect to this data -- a permission change becomes visible to every instance immediately (or within a small, known bound), regardless of which instance happens to be loaded from a file versus already running, which is exactly the property in-process-memory storage cannot provide across multiple instances.
Problem 5 · Weighing gateway-level caching against auth freshness

To reduce load on the shared permissions store from Problem 4's fix, someone proposes each gateway instance cache permission lookups for 5 minutes instead of querying the shared store on every single request. Using this lab's reasoning (and the freshness-vs-speed framing from backend/system_design_review_month3_cold.html), is this a reasonable trade, and what would you want to know before deciding?

Show solution
This can be a reasonable trade, but it reintroduces a BOUNDED version of exactly the staleness risk Problem 4 flagged, and whether it's acceptable depends entirely on how tolerant this specific system is of that bounded delay -- precisely the "freshness vs speed" trade-off the Month 3 cold- review lab covered for caching layers, search autocomplete, and RAG, now showing up again in a security-relevant context here. What matters before deciding: (1) how sensitive is a permission REVOCATION specifically -- a 5-minute window where a just-revoked, potentially compromised client can still successfully call tools is a real, concrete security exposure, not a hypothetical one, and the "5 minutes" number needs to be chosen based on how much damage is tolerable in that window for the actual tools being gated, not picked arbitrarily for convenience; (2) whether the cache can be invalidated PROACTIVELY on a revocation event (e.g. the admin action that revokes access also actively pushes an invalidation to every gateway instance's cache, rather than passively waiting out the TTL) -- this hybrid approach gets most of the query-load reduction benefit while removing the worst of the staleness risk for the specific case (revocation) that actually matters most; (3) whether GRANTS (adding permissions) and REVOKES (removing permissions) should even use the same caching policy -- a stale GRANT that hasn't propagated yet just means a legitimate request gets incorrectly rejected for a few minutes (annoying, but safe), while a stale REVOKE means an request that SHOULD be rejected gets incorrectly allowed (a real security gap) -- these two directions of staleness have very different risk profiles even though naive TTL caching treats them identically.
