MCP & AGENTS LAB · LOOP TERMINATION LOGIC

Every loop needs an exit. An agent loop needs three: done, exhausted, and timed out.

react_pattern.html's loop already had a max_steps cap and checked for a Final Answer — this lab formalizes both as first-class termination mechanisms, adds a wall-clock timeout as an independent third safety net, and works through what makes each one necessary: a model that never converges needs a step cap; a model that converges too slowly in wall-clock time (one slow tool call can burn a whole budget) needs a timeout that doesn't care how many steps have run.

Explicit done signal — the model says "I'm finished"
Max steps — a hard cap, independent of what the model says
Timeout — wall-clock, independent of step count entirely

01 — Two different questions: "is the model done?" and "has it gone on too long?"

Max steps and explicit done signals

Start here, before any code. Think about giving someone directions with two independent safety nets: "keep walking until you reach the blue door" (a clear, self-reported completion condition) AND "but if you've walked more than 20 blocks, stop and call me regardless" (a hard cap that doesn't care whether they FEEL close to the blue door or not). The first trusts the walker's own judgment about when they're done. The second exists specifically for the case where that judgment is wrong, or the blue door doesn't exist at all — a genuinely different failure to guard against.

An agent loop needs exactly this pair, and they answer genuinely different questions. The explicit done signal is the model's own report that it has enough information to answer — react_pattern.html's "Final Answer:" check is exactly this. The max-steps cap is a hard limit that terminates the loop regardless of what the model says, specifically covering the case where the model NEVER produces a done signal — looping indefinitely, calling tool after tool, never quite deciding it has enough.

async def agent_loop(question: str, tools: dict, max_steps: int = 8) -> dict: transcript = f"Question: {question}\n" for step in range(1, max_steps + 1): model_output = await call_model(transcript) transcript += model_output # MECHANISM 1: explicit done signal -- the model itself reports it's finished if "Final Answer:" in model_output: return {"status": "done", "steps_used": step, "answer": model_output.split("Final Answer:")[-1].strip()} action = parse_action(model_output) # deterministic_parsing.html result = await execute_tool(tools, action) transcript += f"Observation: {result}\n" # MECHANISM 2: max_steps -- fires ONLY if the loop reaches here, meaning # step max_steps completed without ever hitting the done-signal return above return {"status": "max_steps_exceeded", "steps_used": max_steps, "answer": None}

Notice the two mechanisms are checked at genuinely different points and never conflict: the done-signal check happens INSIDE the loop body, every single iteration, immediately after each model call — it can fire as early as step 1. The max-steps cap is structural: it's simply the loop's own for bound, and it only ever "fires" in the sense that the loop exits its for statement normally, having never hit the early return for a done signal. A well-behaved model that converges quickly never comes close to max_steps; a model that never converges is caught by it regardless.

MechanismWhat triggers itWhat it protects against
Explicit done signalThe model itself emits "Final Answer:" instead of another actionNothing on its own — this is the NORMAL, successful exit path, not a safety net
Max stepsThe loop completes max_steps iterations without ever hitting a done signalA model that never converges — keeps calling tools indefinitely, never deciding it has enough information
Interview-ready definition: loop termination via explicit done signals and max steps means an agent loop exits through exactly one of two paths: the model itself reports completion (e.g. emitting a Final Answer instead of another tool call), which is the loop's normal, intended exit — or the loop reaches a hard-coded maximum step count without ever receiving that signal, which is a safety net specifically for a model that never converges. The two checks are independent and layered: the done-signal check runs every iteration and can fire immediately; the max-steps cap is a structural bound on the loop itself that only matters when the done signal never arrives.
02 — A single step can hang forever, no matter how low the step count is

Timeout handling

Start here, before the code. Section 1's max_steps guards against too MANY steps. It does nothing at all about a single step that never returns — imagine step 3 out of 8 calls a tool that hits a hung network connection to a third-party API that simply never responds. The loop is sitting at step 3, well under its cap of 8, technically "on track" by the step-count metric, but stuck forever anyway. This is a genuinely different failure mode from an unconverging model — the number of steps was never the problem; the WALL-CLOCK TIME one particular step is taking is.

A timeout is a wall-clock safety net, independent of step count entirely — it bounds how long the loop (or any single step within it) is allowed to run in real time, regardless of how many or how few steps have executed.

import asyncio async def agent_loop_with_timeout(question: str, tools: dict, max_steps: int = 8, step_timeout_seconds: float = 15.0, total_timeout_seconds: float = 60.0) -> dict: transcript = f"Question: {question}\n" loop_start = time.monotonic() for step in range(1, max_steps + 1): # TOTAL timeout -- independent of step count, checked every iteration if time.monotonic() - loop_start > total_timeout_seconds: return {"status": "timed_out", "steps_used": step - 1, "answer": None} try: # PER-STEP timeout -- catches a SINGLE hung tool call, even at step 1 of 8 model_output = await asyncio.wait_for(call_model(transcript), timeout=step_timeout_seconds) except asyncio.TimeoutError: return {"status": "step_timed_out", "steps_used": step - 1, "answer": None} transcript += model_output if "Final Answer:" in model_output: return {"status": "done", "steps_used": step, "answer": model_output.split("Final Answer:")[-1].strip()} action = parse_action(model_output) try: result = await asyncio.wait_for(execute_tool(tools, action), timeout=step_timeout_seconds) except asyncio.TimeoutError: return {"status": "step_timed_out", "steps_used": step, "answer": None} transcript += f"Observation: {result}\n" return {"status": "max_steps_exceeded", "steps_used": max_steps, "answer": None}

Two DIFFERENT timeouts are layered here, and they're not redundant: step_timeout_seconds bounds any SINGLE model call or tool call, catching a hang inside one step regardless of overall progress. total_timeout_seconds bounds the WHOLE loop's wall-clock duration, catching the case where every individual step technically completes within its own budget, but there are enough of them (or they're each just slow enough) that the cumulative time is still unacceptable — a scenario max_steps alone wouldn't catch if the step cap were generous.

MechanismWhat it measuresWhat it catches that the others don't
max_stepsCount of loop iterationsA model that never converges — regardless of how fast each individual step is
step_timeoutWall-clock time of ONE stepA single hung tool call or model call — even at step 1 of 8, long before max_steps would ever fire
total_timeoutWall-clock time of the ENTIRE loopCumulative slowness across many technically-within-budget steps — a scenario max_steps alone wouldn't catch if the cap were generous
Why this has to be a SEPARATE mechanism, not folded into max_steps: step count and wall-clock time measure genuinely different things, and a loop can be pathological on either axis independently. A loop stuck at step 3 of 8 forever (one hung call) never exhausts max_steps at all — nothing about the step-count cap would ever trigger, because the loop simply never reaches step 4. Only a timeout, measuring real elapsed time rather than iterations completed, catches this specific failure.
Interview-ready definition: timeout handling adds a wall-clock safety net to an agent loop, independent of step count: a per-step timeout bounds how long any single model call or tool call is allowed to run before being treated as failed, and a total-loop timeout bounds the loop's entire cumulative wall-clock duration regardless of how many steps have executed. This catches a failure mode max_steps cannot — a single step (or the sum of many technically-fast steps) hanging or running unacceptably long in real time, even when the number of steps completed is well within the step cap.

Problem 1 · Choosing a max_steps value and justifying it

A task typically needs 2-4 tool calls to complete. Why would max_steps = 6 be a more defensible choice than either max_steps = 3 or max_steps = 50?

Show solution
max_steps = 3 risks cutting off LEGITIMATE, successfully-converging runs that happen to need slightly more steps than the typical case -- if the task "typically" needs 2-4 calls, a cap of exactly 3 would already be too tight for some fraction of normal, non-pathological runs (anything needing the full 4), forcing them to terminate via max_steps_exceeded even though they were making genuine progress toward a real answer, not looping pathologically at all. This is a real cost: a cap set too low converts some SUCCESSFUL runs into failures for no reason related to the model actually malfunctioning. max_steps = 50 is too loose to serve as a meaningful safety net at all -- a model that's genuinely stuck in a non-converging pattern would burn through 50 full model+tool round trips (real latency and real cost, per this month's discussion of token/step costs) before the cap ever intervened, which defeats much of the point of having a cap in the first place: catching a runaway loop reasonably QUICKLY, not merely eventually. max_steps = 6 sits meaningfully above the typical 2-4 range (giving genuine, well-behaved runs real headroom to occasionally need a couple more steps than usual without being wrongly cut off) while still being low enough that a truly non-converging model is caught after a bounded, reasonably small number of wasted round trips rather than after dozens. The right number is task-specific, not universal, but the underlying principle -- set the cap meaningfully above typical usage, not merely possible usage -- generalizes.
Problem 2 · Diagnosing which mechanism fires in a specific trace

Using section 2's agent_loop_with_timeout, a run reaches step 4 of max_steps=8, and step 4's tool call has been running for 20 seconds against a step_timeout_seconds=15.0 budget, with total_timeout_seconds=60.0 and only 35 seconds of total elapsed time so far. Which mechanism fires, and why not the others?

Show solution
The PER-STEP timeout fires -- step 4's tool call has been running 20 seconds against a 15-second step_timeout_seconds budget, so asyncio.wait_for(execute_tool(...), timeout=15.0) raises asyncio.TimeoutError once 15 seconds elapse, well before it reaches the actual 20-second mark, and the loop returns {"status": "step_timed_out", ...}. Why not max_steps: only 4 of the 8 allotted steps have been used -- nowhere near exhausted, so the for-loop's bound was never going to be the thing that ends this run. Why not total_timeout: only 35 seconds of the 60-second total budget have elapsed -- the total-timeout check (per section 2's code, evaluated at the START of each loop iteration) would not have fired yet even if it were checked again after this step, since 35 < 60. This trace is a clean illustration of section 2's core point: the per-step timeout is what catches THIS specific failure (one step hanging) precisely because it's checking something max_steps and total_timeout are both blind to -- how long ONE step, specifically, has been running -- independent of how many steps have run overall or how much cumulative time has passed.
Problem 3 · Explaining why total_timeout is checked at the top of the loop, not just once

Section 2's code checks time.monotonic() - loop_start > total_timeout_seconds at the TOP of every iteration, not just once before the loop starts. Why does it need to be inside the loop body at all?

Show solution
A single check made ONCE before the loop starts would only ever see elapsed time = 0 (the loop hasn't run yet) -- it could never detect that the loop has since been running for, say, 65 seconds across several completed steps, because that time genuinely hasn't passed yet at the moment a pre-loop check would run. The total timeout is measuring CUMULATIVE wall-clock time across potentially many steps, which is fundamentally a quantity that only grows AS the loop executes -- it has to be re-evaluated at multiple points DURING execution to have any chance of catching the threshold being crossed. Checking it at the top of every iteration (section 2's actual placement) means: after step 1 completes, before starting step 2, ask "has the loop's total elapsed time now exceeded the budget?" -- and same again before step 3, step 4, and so on. This is the only placement that can actually catch "the loop has been running too long in total," since the condition being checked (cumulative elapsed time) is itself a moving target that changes with every completed step, unlike max_steps (a fixed number decided before the loop even starts) or step_timeout (scoped to one single step's own duration, checked via wait_for around that one call, not by re-polling a clock).
Problem 4 · Deciding what happens after a step_timed_out result

Using the graceful-degradation reasoning from deterministic_parsing.html and mcp_client_basics.html, should a "step_timed_out" result always mean the whole agent session ends with no answer? What's a better default?

Show solution
Not necessarily, and treating it as an automatic hard stop repeats the same mistake those two labs warned against for a DIFFERENT failure type: a single tool call timing out is a specific, localized failure (this particular tool, this particular call, timed out) -- not evidence the entire task is unanswerable. A better default mirrors deterministic_parsing.html's malformed-output handling almost exactly: treat the timeout as an Observation fed back into the transcript ("the last tool call timed out after 15s and did not return a result") and let the model's NEXT Thought decide how to proceed -- try a different tool, retry once with a longer budget if that's a reasonable option, or explicitly tell the user "I wasn't able to complete this because a lookup timed out" rather than silently returning nothing at all. The important caveat: this "let the model try again" response should itself still be bounded by max_steps and total_timeout -- a timeout recovering into "just try again" without any additional limit could still spiral into repeated timeouts eating the entire step/time budget. Whether to hard-stop immediately on any timeout or attempt one bounded recovery is a real design decision that depends on how expensive retrying is and how tolerant the specific task is of extra latency -- but "always hard-stop with zero recovery attempt" throws away exactly the kind of self-correction opportunity react_pattern.html and deterministic_parsing.html both argued for elsewhere in this same loop.
Problem 5 · Connecting termination logic to the retry-budget lesson from deterministic_parsing

deterministic_parsing.html's Practice Problem 5 argued a parse-failure retry loop needs its own bounded retry count, separate from but composed with max_steps. Using THIS lab's mechanisms, sketch how a parse-retry count and max_steps interact — does a parse-retry attempt consume a "step," or is it accounted separately?

Show solution
The cleanest design treats each parse-retry attempt as consuming one iteration of the SAME loop -- i.e., a step where the model generates malformed output, gets corrective feedback per deterministic_parsing.html, and generates again on the NEXT loop iteration is just another pass through this lab's for-loop body, incrementing step exactly the same way a successful tool call would. This has a genuinely useful property: it means max_steps automatically serves as an implicit upper bound on parse retries too, without needing a wholly separate counter -- a model stuck generating malformed JSON repeatedly still terminates via max_steps eventually, exactly as deterministic_parsing.html's Practice Problem 5 required, because those retries are steps like any other and step count is already being tracked and capped. Where a SEPARATE, tighter counter still earns its keep: if you want to abandon a specific tool call after, say, 3 consecutive parse failures specifically (rather than letting the model burn most of its ENTIRE max_steps budget retrying the same malformed call over and over before moving on to anything else), a dedicated per-call retry counter -- checked and reset independently of the loop's overall step count -- lets you fail that ONE call fast and let the model try a different approach with most of its step budget still intact, rather than discovering only at max_steps that the whole session is out of steps because one call kept failing. The two counters aren't redundant: step count bounds the WHOLE session as a blunt backstop; a per-call retry counter bounds how much of that session budget any SINGLE call is allowed to consume before the loop gives up on it specifically and moves on.
