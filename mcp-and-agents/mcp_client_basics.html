01 — Connect, discover, call, receive — in that order

A client that calls the server's tool

Start here, before the code. Think about calling a restaurant you've never ordered from before. You don't just blurt out "one large pizza" the moment someone picks up — you first find out what they actually offer (their menu), THEN place an order using the exact terms their menu uses (their sizes, their toppings), and THEN wait for confirmation of what you're actually getting. An MCP client follows the same three-step discipline: connect, discover (tools/list), then call (tools/call) — never assuming in advance what a server offers or how its tools are named.

Below is a real client using the MCP Python SDK, connecting to the exact stdio calculator server built two labs ago in mcp_server_stdio.html.

from mcp import ClientSession, StdioServerParameters from mcp.client.stdio import stdio_client async def main(): server_params = StdioServerParameters( command="python", args=["calculator_server.py"], # the exact server from mcp_server_stdio.html ) # STEP 1: connect -- this spawns the server subprocess (previous lab, section 3) async with stdio_client(server_params) as (read, write): async with ClientSession(read, write) as session: await session.initialize() # STEP 2: discover -- ask the server what it actually offers, never assume tools_response = await session.list_tools() print("Available tools:", [t.name for t in tools_response.tools]) # -> Available tools: ['add'] # STEP 3: call -- with real arguments matching the tool's inputSchema result = await session.call_tool("add", arguments={"a": 7, "b": 35}) # STEP 4: receive -- the actual result, ready to use for content in result.content: print("Result:", content.text) # -> Result: 42 if __name__ == "__main__": import asyncio asyncio.run(main())

Notice session.call_tool("add", arguments={"a": 7, "b": 35}) is the client-SDK-level call that, underneath, sends exactly the tools/call JSON-RPC request from the mcp_fundamentals_jsonrpc lab — {"method": "tools/call", "params": {"name": "add", "arguments": {"a": 7, "b": 35}}} — and result.content unwraps the matching response's result field. The SDK's job, on both the client and server side, is exactly this translation between a typed function-call interface and raw JSON-RPC — the client code here never touches a JSON-RPC envelope directly, but that's precisely what's traveling underneath every one of these calls.

Interview-ready definition: a minimal MCP client follows a strict connect → discover → call → receive sequence: it establishes a session with a server (spawning it as a subprocess for stdio, or opening an SSE connection for a networked server), calls list_tools() to discover what's actually available rather than assuming a fixed tool set, then calls call_tool(name, arguments) with arguments matching that tool's inputSchema, and finally reads the result content back out of the response. Discovery-before-call matters architecturally, not just stylistically — it's what lets a client work against ANY MCP server without being hard-coded to one specific server's tool set, the same discovery principle the gateway design lab's tools/list aggregation depends on.
02 — The happy path is the easy half of this lab

Handling server errors gracefully

Start here, before the code. Go back to the restaurant analogy: if you order something not on the menu, a good restaurant tells you clearly ("we don't have that, but we do have X") rather than the kitchen just silently catching fire. A well-behaved MCP client needs the same posture toward a server's JSON-RPC error responses — from the mcp_fundamentals_jsonrpc lab, a response carries EITHER result OR error, and a client that only ever checks for result will crash, hang, or silently misbehave the instant a server legitimately returns an error instead.

# calling the tool with a BAD argument -- "a" is missing entirely try: result = await session.call_tool("add", arguments={"b": 35}) for content in result.content: print("Result:", content.text) except McpError as e: # the SDK raises this from a JSON-RPC error response, e.g.: # {"jsonrpc":"2.0","id":3,"error":{"code":-32602, # "message":"Invalid params: 'a' is a required property"}} print(f"Tool call failed ({e.error.code}): {e.error.message}") # -> Tool call failed (-32602): Invalid params: 'a' is a required property # The client keeps running -- this is a HANDLED, expected outcome, # not an unhandled crash. # a well-behaved client can go further: use the error to decide what to # do next, rather than just logging and stopping async def call_tool_safely(session, name, arguments): try: return await session.call_tool(name, arguments=arguments) except McpError as e: if e.error.code == -32602: # invalid params return {"error": f"Bad arguments for {name}: {e.error.message}"} elif e.error.code == -32601: # method/tool not found return {"error": f"Tool '{name}' does not exist on this server"} else: raise # genuinely unexpected -- let it propagate rather than swallow it silently

Two distinct failure modes are worth separating: arguments that don't match the schema (error code -32602, "Invalid params" — the client's fault, correctable by fixing the call) versus a tool that simply doesn't exist (error code -32601, "Method not found" — a discovery/naming mismatch, not a bad-arguments problem). Handling both the same generic way ("something went wrong, give up") throws away information the error response is specifically providing; a well-behaved client uses the error CODE to decide what recovery, if any, actually makes sense.

Graceful handling

Catches the error, reads its code/message, decides on a specific next step (retry with corrected arguments, tell the user, fall back to a different tool) — the client keeps running and the failure is a handled, expected branch in its logic.

No error handling

An unhandled exception propagates up and crashes the client (or an agent loop built on top of it), often mid-conversation — one malformed tool call from the model becomes a full outage instead of a single recoverable step.

Interview-ready definition: a well-behaved MCP client wraps every call_tool invocation in explicit error handling that distinguishes error TYPES by their JSON-RPC error code (e.g. -32602 invalid params vs -32601 method not found) rather than treating every failure identically, and decides a specific recovery action per type — rather than letting a raised exception propagate unhandled and crash the calling code. This matters especially in an agentic context: a tool call's arguments are often generated by a model, which can produce malformed or invalid arguments; a client that crashes on the first such error turns one recoverable, expected failure mode into a full outage of whatever loop or application the client is embedded in.

Problem 1 · Explaining why discovery has to happen before calling

A developer writes a client that skips list_tools() entirely and just directly calls session.call_tool("add", ...), assuming the server has an "add" tool because that's what their OWN server happens to expose. What breaks if this client is later pointed at a DIFFERENT MCP server?

Show solution
If pointed at a different server that doesn't happen to expose a tool named exactly "add" (a different naming convention, a genuinely different tool set, or "add" existing but with a differently-shaped inputSchema), the call fails with a -32601 "method/tool not found" error (section 2) or a -32602 "invalid params" error if the name matches but the schema doesn't -- either way, a call the developer assumed would "just work" fails, and because they skipped discovery entirely, there's no code path that even checked whether the assumption was valid before acting on it. This is exactly why section 1 frames discovery as a REQUIRED step, not an optional nicety -- list_tools() is what makes a client genuinely general-purpose, able to work against ANY MCP server's actual current tool set rather than a specific server's tool set hard-coded into the client's assumptions at write time. Skipping it doesn't save meaningful work (list_tools() is cheap), but it does silently couple the client to one specific server's implementation details, which is precisely the kind of coupling MCP's discovery mechanism exists to avoid -- the same principle the gateway design lab's tools/list aggregation depends on: clients are expected to ask what's available, not assume it.
Problem 2 · Distinguishing which error code applies to a scenario

A client calls session.call_tool("substract", arguments={"a": 5, "b": 2}) — note the typo, "substract" instead of "subtract." Using section 2's two error codes, which one does the server return, and why does distinguishing it from the OTHER error code matter for how the client should respond?

Show solution
The server returns -32601 (method/tool not found), NOT -32602 (invalid params) -- the arguments {"a": 5, "b": 2} are perfectly well-formed for whatever a "subtract" tool would expect; the actual problem is that no tool named "substract" (the typo) exists on this server at all. The server's list_tools() response simply never included that name, so routing/dispatch fails before argument validation would even be reached. Why the distinction matters for the client's response: -32601 signals a NAMING/DISCOVERY problem -- the fix is checking the actual tool name via list_tools() (Problem 1's point) or correcting a typo, not adjusting the arguments being passed. -32602 would instead signal an ARGUMENTS problem -- the tool name was found and matched, but the arguments didn't satisfy its inputSchema, meaning the fix is correcting the ARGUMENTS, not the name. A client (or an agent built on top of one) that treated both error codes identically -- e.g. always retrying with "fixed" arguments -- would retry forever on a -32601 typo error, since no amount of argument-fixing addresses a tool name that doesn't exist; only checking and correcting the NAME would actually resolve it. This is exactly section 2's point about using the error CODE to decide the specific recovery action, rather than treating every failure as the same generic "something went wrong."
Problem 3 · Designing recovery for an agent loop, not just a single call

An agent loop calls tools based on arguments an LLM generates. The LLM calls add with {"a": "seven", "b": 35} — a string where a number was required. Using section 2's call_tool_safely pattern, sketch what the loop should do with the resulting error, rather than just logging it and stopping.

Show solution
This produces a -32602 "invalid params" error (the tool exists, but "a" fails the inputSchema's {"type": "number"} constraint) -- section 2's call_tool_safely would catch this and return a structured {"error": "Bad arguments for add: ..."} rather than crash. What the LOOP should do with it, specifically: feed that structured error message BACK to the LLM as the "result" of its tool call (in whatever role the loop uses for tool results, per the conversation_turns schema from the agent_memory_schemas lab -- a tool-role turn, but with an error in tool_result instead of a success value), and let the model see exactly what went wrong ("Bad arguments for add: 'a' must be a number, got string 'seven'") so it can generate a CORRECTED tool call on its next turn -- e.g. retrying with {"a": 7, "b": 35}. This treats the error as useful information routed back into the loop's normal flow, not a reason to halt the loop entirely. This is exactly the kind of design this month's later system-design- review-cold lab and the loop-termination-logic topic (Week 3) will formalize further -- but the core idea already applies here: a single malformed tool call from a model is an extremely common, expected failure mode in agentic systems (models are not perfectly reliable at producing schema-valid arguments), and a client/loop that treats it as recoverable input rather than a fatal crash is what actually makes a multi-step agent loop robust enough to complete a task despite occasional bad calls along the way.
Problem 4 · Deciding when NOT to catch an error

Section 2's call_tool_safely re-raises the exception (raise with no arguments) for any error code other than -32601 or -32602. Why not catch and swallow EVERY possible error, returning a generic {"error": "something went wrong"} for anything unexpected too?

Show solution
Swallowing every possible error uniformly would hide genuinely different classes of problems behind one indistinguishable message, which defeats the entire point section 2 makes about using error codes to choose a SPECIFIC recovery action. -32601 and -32602 are deliberately singled out because they have KNOWN, sensible recovery paths (fix the tool name; fix the arguments) that make sense to handle automatically, often even by feeding the message back to a model to self-correct (Problem 3). An error code the code doesn't explicitly recognize might be something like a server-side internal error, an authentication failure from the gateway design lab's auth layer, or a genuinely new failure mode nobody anticipated when this handling code was written -- none of which have an obvious "just retry with corrected input" fix, and blindly returning a generic error message for all of them risks the calling code (or a model reading that message) attempting an inappropriate "fix" that doesn't actually address the real problem, or worse, silently continuing in a broken state. Re-raising unrecognized errors instead surfaces them loudly -- to logs, to monitoring, to a human -- rather than quietly downgrading every unknown failure into the same bland, uninformative message. This mirrors a broader principle worth stating explicitly: catching and handling SPECIFIC, anticipated failure modes is good defensive design; catching and silently normalizing EVERY possible failure mode, known or not, often trades a loud, fixable bug for a quiet, harder-to-diagnose one -- the kind of blanket except-and-continue pattern that tends to hide real problems rather than solve them.
Problem 5 · Connecting client error handling to the transport it's running over

Everything in this lab assumes the server is reachable and responds — but the underlying transport can also fail entirely (e.g. the stdio server subprocess crashes outright, or an SSE connection drops mid-session). Is that the SAME kind of failure as a JSON-RPC error response, and should a client handle it the same way?

Show solution
No -- these are genuinely different failure categories, and conflating them leads to worse error handling, not better. A JSON-RPC error response (section 2's -32601/-32602 examples) is the server successfully receiving, processing, and REPLYING to a request -- the reply just happens to be "here's why this failed" instead of "here's your result." The protocol worked correctly; the requested OPERATION failed in a well-defined, structured way the client can parse and reason about. A transport-level failure (the stdio subprocess crashing, an SSE connection dropping) is different in kind: there is no JSON-RPC response at all, because the underlying channel carrying JSON-RPC messages is itself gone -- the previous lab's stdio mechanics and this lab's SSE transport both depend on that channel staying alive, and if it doesn't, the client's readline() call (stdio) or SSE event stream (SSE) simply never receives anything, or raises a connection-level exception distinct from McpError entirely (e.g. a BrokenPipeError, a network timeout). A genuinely robust client handles BOTH, but with different recovery logic: JSON-RPC errors (section 2) get handled per error CODE, often feeding the message back into an agent loop for self-correction (Problem 3). Transport failures need different recovery entirely -- e.g. detecting the subprocess died and deciding whether to respawn it (stdio), or detecting a dropped SSE connection and attempting to reconnect (SSE) — neither of which is meaningfully "fixable" by changing the tool call's arguments the way a -32602 error is. Treating a crashed subprocess the same way as a bad-arguments error (e.g. trying to "retry with corrected arguments" against a server that no longer exists) would be a category error -- the client needs to distinguish "the operation failed" from "the connection itself is gone" before it can pick an appropriate response to either.
