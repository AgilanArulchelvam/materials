MCP & AGENTS LAB · MULTI-AGENT DELEGATION

One agent trying to do everything is a bottleneck wearing a single hat. Split the hats.

A complex task often decomposes naturally into distinct sub-tasks that benefit from different specializations — one agent good at finding sources, another good at writing prose. Multi-agent delegation formalizes this: a coordinator breaks a task apart, hands each piece to a specialized sub-agent, and combines their results. This lab builds a real "research and summarize" example end to end, then animates the coordinator dispatching and merging.

Coordinator — breaks the task apart
Sub-agents — specialized, dispatched (often in parallel)

01 — Different sub-tasks, different specialists, one coordinator tying it together

A coordinator handing off subtasks

Start here, before any code. Think about a newsroom editor assigning a story: the editor doesn't personally go interview sources AND write the final copy AND fact-check it — they break the story into pieces, hand "go get quotes from these three people" to a reporter and "turn this into a polished 800-word piece" to a writer, then combine what comes back into the published article. The editor's actual skill is knowing HOW to break the story apart and WHO should get which piece — not necessarily being the best reporter or the best writer themselves.

Multi-agent delegation applies this exact structure to agentic systems: a coordinator agent receives a complex task, decomposes it into distinct subtasks, dispatches each subtask to a specialized sub-agent built (or prompted) specifically for that kind of work, and then combines whatever the sub-agents return into a single final result. Concretely, for a "research and summarize" task on some topic:

Task: "Research and summarize recent developments in fusion energy." Coordinator's decomposition: Subtask A -> research_agent: "Find 3-5 credible recent sources on fusion energy developments." Subtask B -> writer_agent: "Write a 150-word summary from the sources research_agent finds." Dispatch order matters here: B genuinely depends on A's output (the writer needs sources to summarize) -- so unlike section 3's fully independent case, these two subtasks run sequentially, not in parallel. Coordinator combines: takes research_agent's source list AND writer_agent's summary, packages them together as the final deliverable (a summary WITH citations, not just a summary).

Notice the two sub-agents here have genuinely different jobs, not just an arbitrary split of the same work — research_agent is good at finding and evaluating sources; writer_agent is good at turning source material into readable prose. Neither would necessarily do the OTHER'S job as well; the value of delegation comes specifically from routing each subtask to whichever specialist is actually suited to it, exactly the way the newsroom editor routes reporting and writing to different people rather than expecting one person to be excellent at both.

Interview-ready definition: multi-agent delegation is a pattern where a coordinator agent decomposes a complex task into distinct subtasks and dispatches each one to a specialized sub-agent built or prompted for that specific kind of work, then combines the sub-agents' results into a single final output. The coordinator's own core competency is decomposition and integration — deciding what the subtasks are, which specialist should handle each, and how to merge what comes back — rather than performing every subtask itself, mirroring how a human coordinator (an editor, a project lead) routes work to specialists rather than doing every specialist's job personally.
02 — Real code: a coordinator function calling specialized sub-agent functions

Implementing a simple delegator + sub-agent

Start here, before the code. Mechanically, each "sub-agent" here is just a function (or a full model call with its own specialized prompt) that does one well-scoped job and returns a result — the coordinator is the function that calls them in the right order, with the right inputs, and assembles what they return. Nothing about this REQUIRES separate models or separate infrastructure; the essential structural idea is separation of concerns between decomposition/orchestration (coordinator) and specialized execution (sub-agents), which can be implemented at any scale from simple Python functions up to fully independent deployed services.

async def research_agent(topic: str) -> list: # specialized: good at finding and evaluating sources, nothing else prompt = f"Find 3-5 credible recent sources on: {topic}. Return as a list of (title, url)." response = await call_model(prompt, tools=[web_search_tool]) return parse_sources(response) async def writer_agent(topic: str, sources: list) -> str: # specialized: good at turning source material into readable prose prompt = f"Write a 150-word summary of {topic} using only these sources: {sources}" response = await call_model(prompt) return response.text async def coordinator(task: str, topic: str) -> dict: # STEP 1: decompose -- decide what subtasks this task breaks into # STEP 2: dispatch -- call each sub-agent with the right inputs, in the # right order (sequential here, since writer_agent NEEDS research_agent's # output -- section 3 shows a case where subtasks CAN run in parallel) sources = await research_agent(topic) summary = await writer_agent(topic, sources) # STEP 3: combine -- the coordinator's own job, not delegated to either sub-agent return { "summary": summary, "sources": sources, }

The coordinator here never itself calls web_search_tool or writes prose directly — its entire job is orchestration: deciding sub-agents exist for this task, calling them with the right arguments in the right order, and assembling the final dict. This separation is what makes each piece independently improvable — research_agent's prompt or tools can be refined without touching writer_agent at all, and vice versa, because neither depends on the other's internal implementation, only on the shape of data passed between them.

Interview-ready definition: a simple delegator implementation is a coordinator function that (1) decomposes a task into an explicit set of subtasks, (2) calls each corresponding specialized sub-agent function with the right inputs — in whichever order their actual data dependencies require — and (3) combines the sub-agents' return values into the task's final result, without performing any sub-agent's specialized work itself. Each sub-agent is independently a well-scoped function (or model call with its own dedicated prompt/tools) responsible for exactly one kind of work, letting each be developed, tested, and improved in isolation from the others.

What to notice: in sequential mode, writer_agent doesn't even START until research_agent's sources are available — it structurally can't, since its prompt requires them as input. Problem 1 · Deciding whether a task is worth decomposing at all

A task is "translate this one sentence into French." Should a coordinator decompose this into sub-agents, or handle it directly? Using section 1's reasoning, justify your answer.

Show solution
This task should be handled directly, with no delegation at all -- it's a single, atomic unit of work that doesn't naturally decompose into genuinely DIFFERENT kinds of specialized work the way "research and summarize" does (finding sources vs. writing prose are different skills; translating one sentence is just... translating one sentence). Section 1's newsroom analogy is instructive here: an editor doesn't split "write one short caption" into a reporting subtask and a writing subtask -- that split only makes sense when a task genuinely has multiple distinct specialties it benefits from, and a one-sentence translation doesn't. Forcing decomposition onto a task that doesn't need it adds pure overhead -- the coordination logic (deciding subtasks, dispatching, combining results) costs extra model calls and latency without providing any of delegation's actual benefit (routing to genuinely better-suited specialists), since there's no meaningful specialization gap for a single- sentence translation to exploit. This mirrors react_pattern.html's Problem 4 lesson about ReAct's adaptivity not paying off on tasks that don't need it: an architectural pattern's cost should be paid only when its benefit is actually available to be captured.
Problem 2 · Diagnosing a coordinator that dispatches in the wrong order

A buggy coordinator calls writer_agent(topic, sources) BEFORE research_agent(topic) has actually returned — passing an empty or placeholder sources value. Using section 2's code, what actually happens, and why is this a genuinely different kind of bug than the plan_and_solve_pattern lab's plan-staleness problem?

Show solution
writer_agent would receive an empty (or garbage placeholder) sources list and generate its summary prompt as "Write a 150-word summary of {topic} using only these sources: []" -- the model would either produce a summary with no actual grounding in real sources (likely hallucinating content, since it was explicitly told to use sources that don't exist), or refuse/hedge because it has nothing to summarize. Either way, the final combined result section 2's coordinator returns would be substantively broken -- a summary that isn't actually derived from research_agent's findings at all, defeating the entire point of delegating the research subtask in the first place. This differs from plan_and_solve_pattern.html's plan-staleness problem in an important way: that lab's issue was an early PLAN STEP's assumption becoming outdated relative to what a LATER step actually discovered mid- execution -- a timing/adaptivity problem. This bug is simpler and more fundamental: it's a straightforward DATA DEPENDENCY violation -- the coordinator's own code called writer_agent before the data it structurally needs (sources, an actual function parameter) existed at all. This isn't about adapting to unexpected results; it's about the coordinator failing to respect an ordering constraint that was already fully knowable in advance from section 2's function signatures alone (writer_agent's second parameter is literally named sources and is used directly in its prompt) -- a straightforward implementation bug, not a fundamental limitation of the delegation pattern itself.
Problem 3 · Choosing sequential vs. parallel dispatch correctly

A coordinator has three subtasks: "find sources on topic A," "find sources on topic B," and "write a combined summary of both." Which of the three should be dispatched in parallel, which must wait, and why — using section 3's distinction?

Show solution
"Find sources on topic A" and "find sources on topic B" should be dispatched in PARALLEL -- neither depends on the other's output at all (finding sources on topic A doesn't require or benefit from knowing anything about topic B's sources), exactly the genuinely-independent case section 3's parallel mode demonstrates. Dispatching them sequentially here would be pure wasted time -- there's no data dependency forcing the wait, so making them wait on each other anyway just makes the whole task take longer for no benefit, the same "you're not gaining anything by being sequential when nothing requires it" point react_pattern.html's Problem 4 made about independent ReAct lookups. "Write a combined summary of both" MUST wait for both source-finding subtasks to complete first -- it structurally needs BOTH sets of sources as input (a combined summary of A and B can't be written knowing only one), so it cannot start until both parallel subtasks return, even though those two subtasks themselves don't depend on each other. This is a common real shape for delegation: a "fan out" of independent subtasks followed by a "fan in" step that depends on ALL of them completing -- correctly identifying which subtasks can run in parallel (no shared data dependency between them) versus which have to wait (this coordinator's combining step depending on both fan-out results) is exactly the judgment call a coordinator's decomposition logic has to get right for delegation to actually be efficient rather than just correct.
Problem 4 · Handling a sub-agent that fails

Using the graceful-error-handling principle from mcp_client_basics.html and the retry/DLQ reasoning from backend/async_tool_job_queue_design.html, what should section 2's coordinator do if research_agent raises an exception (e.g. its web search tool times out)?

Show solution
The coordinator should not let research_agent's exception simply propagate up uncaught and crash the whole delegation flow -- exactly the graceful-error-handling principle mcp_client_basics.html established for individual tool calls, now applied one level up, to an entire sub-agent invocation. A reasonable approach: try: sources = await research_agent(topic) except ToolTimeoutError as e: # option 1: retry with backoff (async_tool_job_queue_design's # pattern, applied to a sub-agent call instead of a queued job) sources = await retry_with_backoff(research_agent, topic) # option 2: degrade gracefully -- proceed without sources, but # tell writer_agent (and ultimately the user) that no sources # were found, rather than silently proceeding as if sources=[] # were a normal, successful result # option 3: fail the whole task explicitly, returning a clear # error rather than a broken or misleadingly empty summary Which option is right depends on the task's tolerance for partial failure -- but ALL three are meaningfully better than either crashing uncaught or (as Problem 2's bug does) silently proceeding with garbage input as if nothing went wrong. The key shared idea across all three options: a sub-agent's failure is treated as a real, expected outcome the coordinator's logic explicitly accounts for, exactly the same posture mcp_client_basics.html argued for at the level of a single MCP tool call -- multi-agent delegation doesn't get to skip this just because the "tool call" here happens to be an entire sub-agent rather than a single function.
Problem 5 · Comparing multi-agent delegation to a single agent using multiple tools

Section 1's "research and summarize" task could also be done by ONE agent with access to both a search tool and no special writing constraints, reasoning through the whole thing itself via a ReAct loop. What does splitting it into two SEPARATE sub-agents actually buy you that a single capable agent with the right tools wouldn't already provide?

Show solution
A single sufficiently capable agent with the right tools genuinely CAN accomplish the same end result -- multi-agent delegation isn't the only way to solve this task, and for a simple enough version of it, a single ReAct loop (react_pattern.html) calling a search tool and then reasoning its way to a summary might be entirely sufficient, echoing Problem 1's point that decomposition isn't free and shouldn't be applied reflexively. What separate sub-agents specifically buy, when the task justifies it: (1) each sub-agent can have a NARROWER, more specialized prompt/context -- research_agent's entire prompt and context can be focused purely on source evaluation without also needing instructions about prose style, and vice versa for writer_agent, which can reduce the surface area for either to get confused about competing objectives within one prompt; (2) each sub-agent is independently testable, improvable, and swappable -- you can upgrade or fine-tune JUST the research capability without touching the writer at all, which section 2 already noted as a benefit of the separation; (3) sub-agents can genuinely run in PARALLEL when their subtasks are independent (section 3), something a single sequential ReAct loop fundamentally cannot do since it only ever takes one action at a time; and (4) for larger, more complex tasks with many distinct specialties (not just two), a single agent's context and reasoning can become genuinely overloaded trying to hold every specialty's considerations at once, whereas delegation keeps each specialist's context scoped to just its own job. The trade-off is real added complexity -- orchestration logic, inter-agent data-passing, and coordination failure modes (Problem 2, Problem 4) that a single agent simply doesn't have to deal with -- which is exactly why "does this task actually need multiple specialists" (Problem 1) is the right question to ask before reaching for delegation by default.
