01 — What the client agent discovers before it plans anything

The MCP server's DB query tools

Start here, before the plan. This week's capstone reuses everything Week 1 already established about MCP servers (mcp_server_stdio.html, mcp_fundamentals_jsonrpc.html): a server process exposes a small set of tools via tools/list, each with a name, description, and a JSON Schema for its parameters (json_schema_tool_specs.html, Week 3). For this scenario, the server exposes two DB query tools — nothing more elaborate is needed, and per event_sourcing_vs_crud.html's "simpler is the right default" reasoning from earlier this week, a minimal, correctly-scoped tool surface beats an overbuilt one.

// tools/list response from the DB-query MCP server { "tools": [ { "name": "query_orders", "description": "Query orders by date range and minimum total.", "inputSchema": { "type": "object", "properties": { "start_date": {"type": "string", "format": "date"}, "end_date": {"type": "string", "format": "date"}, "min_total": {"type": "number", "minimum": 0} }, "required": ["start_date", "end_date", "min_total"] } }, { "name": "get_order_detail", "description": "Fetch full line-item detail for one order ID.", "inputSchema": { "type": "object", "properties": { "order_id": {"type": "string"} }, "required": ["order_id"] } } ] }

Per permission_scoping.html (this same week), the agent invoking these tools holds only orders:read — it was never granted any write or delete scope, because summarizing orders is genuinely all this task requires. Per tool_call_sandboxing.html, query_orders is itself scoped server-side to only the orders table — it has no path to touch any other table even if asked. Neither of this week's security mechanisms is incidental here — this capstone is deliberately reusing them, not just the earlier weeks' mechanics.

Interview-ready definition: an MCP server exposing DB query tools advertises a small, precisely-scoped set of tools via tools/list — each with a JSON Schema constraining exactly what arguments it accepts — so a connecting agent can discover what's available and what's required before ever attempting a call, with the server itself enforcing both the schema (rejecting malformed calls before execution) and, per this week's security labs, the resource boundary and permission scope each tool call is subject to.

Problem 1 · Tracing exactly which max_steps budget this run consumes

Using loop_termination_logic.html's reasoning, suppose this scenario returns 4 qualifying orders from query_orders, and one of the 4 get_order_detail calls fails once before succeeding on retry. How many total loop iterations does this run consume, and what would be a defensible max_steps value for it?

Show solution
Counting iterations the same way function_calling_loop_practice.html's Problem 2 did: 1 (query_orders) + 4 (one get_order_detail call per qualifying order, counting only the SUCCESSFUL final attempt for the 3 that worked first try) + 1 (the FAILED get_order_detail attempt for the 4th order, which still counts as its own iteration per loop_termination_logic.html's Practice Problem 5 -- a retry is just another pass through the same loop body) + 1 (the retry that succeeds) + 1 (final synthesis/Final Answer step) = 8 iterations total. A defensible max_steps for this task: something like 12-14 -- following loop_termination_logic.html's Practice Problem 1 reasoning directly (set the cap meaningfully ABOVE the typical case, not merely equal to it), this task's typical-case count is 8 (as just computed, including one recoverable failure), so a cap of exactly 8 would leave ZERO room for a SECOND unlucky failure on a different order, and a cap like 3-4 would cut off the task before even the first order's detail fetch completed. 12-14 gives headroom for one or two more failures than this particular run happened to hit, without being so loose (50+) that a genuinely runaway loop would burn excessive real cost before the cap ever intervened.
Problem 2 · Validating the final JSON answer against a schema

Using json_schema_tool_specs.html's validation discipline, sketch a JSON Schema for this task's final structured answer (fields for the qualifying order count, a list of order summaries, and any orders that failed to fetch and had to be omitted). Why does the schema need a field for failed/omitted orders specifically?

Show solution
{ "type": "object", "properties": { "period": {"type": "string"}, "min_total": {"type": "number"}, "orders_found": {"type": "integer", "minimum": 0}, "orders_summarized": { "type": "array", "items": { "type": "object", "properties": { "order_id": {"type": "string"}, "total": {"type": "number"}, "item_count": {"type": "integer"} }, "required": ["order_id", "total", "item_count"] } }, "orders_omitted": { "type": "array", "items": { "type": "object", "properties": { "order_id": {"type": "string"}, "reason": {"type": "string"} }, "required": ["order_id", "reason"] } } }, "required": ["orders_found", "orders_summarized", "orders_omitted"] } The orders_omitted field is required specifically because of THIS lab's own deliberately-injected-failure scenario: if the get_order_detail call that failed had eventually been abandoned rather than successfully retried (a real possibility loop_termination_logic.html's timeout/ max_steps mechanisms exist to bound), silently returning orders_summarized with only 3 of the 4 qualifying orders -- with no mention that a 4th existed and was dropped -- would be actively misleading to whoever reads the final answer, understating the real total. This directly mirrors deterministic_parsing.html and react_pattern.html's shared insistence on surfacing failures explicitly rather than silently absorbing them -- the structured JSON answer needs its OWN field for "here's what we couldn't get and why," not just a silently-shorter list.
Problem 3 · Deciding what "fails gracefully" means if the SAME order fails twice

The checkpoint says the agent should "recover or fail gracefully." Using async_tool_job_queue_design.html's dead-letter-queue reasoning and loop_termination_logic.html's retry-budget point, what should happen if a SPECIFIC order's get_order_detail call fails on both its first attempt AND its retry?

Show solution
This is exactly the scenario a per-call retry budget (distinct from the overall max_steps budget) exists for, per loop_termination_logic.html's Practice Problem 5: rather than retrying this SAME order indefinitely (burning the whole session's step budget chasing one stubborn failure) or letting the entire task fail just because one order's detail fetch is having a bad day, the correct "fails gracefully" behavior is to ABANDON that specific order after a bounded number of attempts (e.g. 2, mirroring a tight per-call retry cap rather than the looser overall max_steps), record it in orders_omitted (Problem 2's schema field) with a reason like "get_order_detail failed twice, abandoned," and CONTINUE processing the remaining orders rather than treating one order's persistent failure as reason to fail the entire task. This mirrors async_tool_job_queue_design.html's dead-letter-queue logic almost exactly, just synchronous rather than queued: a job (here, one order's detail fetch) that can't succeed after a bounded number of attempts gets set aside rather than retried forever or silently dropped without a trace -- its failure is preserved (in orders_omitted) for later inspection, while the rest of the task's progress isn't held hostage to that one failure. "Recovers" describes the case where a retry succeeds (this lab's actual live-demo scenario); "fails gracefully" describes this case, where recovery genuinely isn't possible within a reasonable budget, and the honest, partial answer with a clearly marked omission is the correct final output -- not a crash, and not a silently incomplete answer with no indication anything was missing.
Problem 4 · Applying this week's permission scoping to a subtly different tool request

Suppose, mid-task, an injected instruction inside one order's notes field (a real possibility if order notes come from customer-submitted text) tries to redirect the agent to call a hypothetical delete_order tool. Using this week's permission_scoping.html and prompt_injection_risks.html together, trace what happens.

Show solution
This is precisely system_design_review_month4_final_cold.html's section 3 scenario, replayed inside this capstone's own concrete task. Even if the injected instruction in the order notes fully succeeds at manipulating the agent's reasoning into WANTING to call delete_order (i.e. even assuming prompt_injection_risks.html's mitigations -- content delimiting, data-only instructions -- were bypassed), the call still has to pass permission_scoping.html's authorize_tool_call check before executing. Per section 1's setup, this agent's grant is exactly {"orders:read"} -- it was never granted any write or delete scope, because summarizing orders is genuinely all this task's job requires. "orders:delete" (or whatever scope delete_order would require) is not in {"orders:read"}, so the call is DENIED before any deletion occurs, regardless of how convincingly the agent was manipulated into generating it. The broader point this problem is testing: this capstone's own tool surface was deliberately kept minimal (section 1's two read-only query tools) and its agent deliberately scoped to read-only access -- not as an afterthought, but as this week's actual security lesson APPLIED to this specific task's design. A well-scoped agent for "summarize orders" never has delete_order reachable at all in the first place, which is a stronger, earlier defense than relying on a permission check to correctly deny a dangerous call that a more broadly-scoped agent COULD have generated -- least privilege, applied at design time, not just as a runtime check.
Problem 5 · Explaining why this capstone's synthesis step has no tool call

Section 2's plan table marks step 3 (synthesis) as "no tool call." Using deterministic_parsing.html's and this month's schema-validation discipline together, what specifically validates that step's OUTPUT if no tool is executing it, and why is that check still necessary even without a tool involved?

Show solution
Step 3 doesn't call a tool because it isn't fetching new information -- it's ASSEMBLING information the agent already has (from steps 1 and 2's tool results, now sitting in the transcript) into the final structured answer. But "no tool call" doesn't mean "no validation needed" -- the model's generated JSON output for the final answer still has to be checked against Problem 2's schema using the SAME json.loads()-then- validate discipline deterministic_parsing.html established for tool call arguments, just applied to the FINAL output instead of an intermediate tool call's arguments. This is necessary for exactly the same reason schema validation matters anywhere else this month: a model generating "structured JSON" is still generating TEXT that is supposed to parse as valid JSON matching a specific shape -- it can still emit malformed JSON, omit a required field like orders_omitted, or put a string where the schema expects a number, exactly the same failure modes json_schema_tool_specs.html and deterministic_parsing.html catalogued for tool call arguments. If this final-answer validation is skipped just because "it's the last step, not a tool call," a caller consuming this agent's output downstream (another service parsing this JSON programmatically, not a human reading prose) would have no guarantee the output is actually well-formed -- the entire reason Week 3 pushed toward structured JSON output in the first place was to make the final answer machine-consumable, and an unvalidated final JSON blob only nominally achieves that.
