01 — Never start drawing boxes before you know what you're solving for

Requirements gathering

Start here, before any box on a whiteboard. Think about the difference between a hotel's single front desk and a hotel with one unmarked door per department (housekeeping, room service, maintenance, billing) that a guest has to somehow discover on their own. The front desk works because ONE trained person (or system) knows every department, can verify who you are once, and routes your request without you needing fifty different phone numbers memorized. That's the pitch for a gateway — but a real interview never starts by drawing the front desk. It starts by asking: how many guests, how many departments, what happens if housekeeping doesn't pick up?

Here the prompt is: "Design a gateway that fronts multiple MCP servers/tools for an enterprise multi-agent system." Before touching capacity numbers, pin down what "design a gateway" is actually asking for.

Functional requirements

  • Routing — every incoming tools/call request (per mcp-and-agents/mcp_fundamentals_jsonrpc.html's JSON-RPC shape) reaches the correct downstream MCP server, keyed by tool name.
  • Auth/authz per tool — not just "is this caller authenticated," but "is THIS specific agent, on behalf of THIS specific user, allowed to call THIS specific tool" — a much finer grain than the single-tenant auth mcp_gateway_design.html assumed.
  • Rate limiting — per agent, per team, and possibly per downstream tool (a slow tool needs its own ceiling independent of how much headroom the gateway itself has), reusing backend/rate_limiter_design.html's token-bucket design rather than reinventing it.
  • Tool schema registry/discovery — agents need to discover which tools exist and their JSON schemas (per mcp-and-agents/json_schema_tool_specs.html) without every MCP server being queried directly on every agent startup.
  • Audit logging — enterprise-grade: every tool call, who invoked it, on whose behalf, what arguments, what came back — for compliance review, not just debugging.
  • Graceful degradation — a single slow or dead downstream MCP server must not take down calls to every OTHER tool.

Interview-ready definition: requirements gathering for an enterprise MCP gateway means separating what it must DO (route by tool name, authorize per-tool per-caller, rate-limit, expose a schema registry, audit-log every call, and degrade gracefully when one downstream tool misbehaves) from how it must PERFORM under load (call volume, latency budget, consistency tolerance, availability target) — and getting the interviewer to confirm or correct concrete numbers for the latter BEFORE any capacity estimation, since every number in section 2 is derived directly from these assumptions.
02 — Every number below is derived, not guessed

Capacity estimation

Start here, before the math. Capacity estimation is just Fermi estimation with an engineering purpose: start from a small number of assumptions you can defend (users, request rate, payload size), and multiply your way to storage and throughput numbers that tell you whether you're building something that fits on one machine or needs to be distributed from day one. The value isn't precision — it's knowing whether the answer is "megabytes" or "terabytes," because that decides the entire architecture.

Throughput

# From requirements: ~150 tool calls/sec sustained, 5x burst = 750/sec peak # Gateway must be provisioned for PEAK, not average -- this is the # single most common capacity-estimation mistake to call out loud peak_qps = 750 # calls/sec at burst # Each gateway instance, doing routing + authz + rate-limit check # (no heavy compute, mostly a hash lookup + a permission check), # can reasonably sustain ~2,000 req/sec before p99 latency degrades # -- this number itself would come from a load test in practice, # but is a defensible assumption to state and move on from qps_per_instance = 2000 instances_needed = peak_qps / qps_per_instance # = 0.375 # round up AND add headroom for one instance failing (N+1, or N+2 # for a fleet this small) -- 3 instances minimum, not 1
Read the number, don't just compute it: 750 QPS needs less than one instance mathematically — but the gateway is now a single point of failure for every agent in the company (non-functional requirement: 99.95% availability), so the REAL instance count is driven by fault tolerance, not raw throughput. Three small instances behind a load balancer beats one large one purely because a single-instance gateway violates the availability requirement regardless of how much spare capacity it has.

Payload size and bandwidth

# Typical tool call: JSON-RPC request + response # request: tool name, arguments (avg ~2KB for a moderately complex # tool call -- e.g. a search query with filters) # response: tool result (avg ~8KB -- e.g. a handful of DB rows or # search results; some tools return much more, so this is a median, # not a max) avg_request_bytes = 2_000 avg_response_bytes = 8_000 avg_roundtrip_bytes = avg_request_bytes + avg_response_bytes # 10KB peak_bandwidth = peak_qps * avg_roundtrip_bytes # 750 * 10KB = 7.5MB/sec = 60Mbps # trivial for a modern NIC -- bandwidth is NOT the bottleneck here. # this is worth stating explicitly: it tells the interviewer you know # WHERE the actual constraint is (connection count / CPU for authz # checks / downstream latency), not just reciting a formula

Audit log storage

# Every tool call gets ONE audit record: caller, tool, args (or a hash # of args if they're large/sensitive), result status, timestamp, latency # ~500 bytes per audit record, generously avg_audit_record_bytes = 500 calls_per_day = 150 * 86400 # sustained qps * seconds/day = ~13M calls/day audit_bytes_per_day = calls_per_day * avg_audit_record_bytes # ~6.5GB/day audit_bytes_per_year = audit_bytes_per_day * 365 # ~2.4TB/year # compliance retention is often 1-7 years for enterprise audit trails -- # at 7 years that's ~17TB. This is squarely "needs a columnar/log- # oriented store with tiered storage (hot recent data, cold archived # data)," not "fits in the gateway's own Postgres instance."

Tool schema registry size

num_tools = 400 avg_schema_bytes = 3_000 # a JSON schema per json_schema_tool_specs.html, typically a few KB registry_size = num_tools * avg_schema_bytes # 1.2MB total # TINY. This tells us the entire schema registry fits comfortably # in memory on every gateway instance -- caching it locally (refreshed # on a TTL or push-invalidated on change) is not just possible, it's # the obviously correct design. Section 3 builds on exactly this.
Interview-ready definition: capacity estimation here means deriving five numbers from the requirements: peak QPS (750, driven by burst not average), instance count (driven by availability, not raw throughput, once you compute that peak QPS is trivially low), bandwidth (60Mbps — cheap, not the bottleneck), audit log growth (~2.4TB/year, driving a columnar/tiered storage choice), and schema registry size (~1.2MB — small enough to cache fully in memory on every instance). The exercise isn't the arithmetic — it's using each number to make or justify a concrete design decision in section 3.
03 — What the numbers above actually buy you

Architecture

Start here, before the diagram. An enterprise gateway is really three small, mostly-independent decisions stacked on top of mcp_gateway_design.html's routing table: (1) where auth/authz checks happen relative to routing, (2) how the schema registry stays fresh without hammering every MCP server on every agent startup, and (3) how a slow downstream tool is prevented from starving requests meant for a different, healthy tool.

1 — Auth/authz at the gateway, not per MCP server

Every downstream MCP server could re-implement its own auth check, but that means 60 teams independently maintaining 60 authorization implementations — a compliance and consistency nightmare. Instead, the gateway is the SINGLE enforcement point: it authenticates the calling agent (service identity, not end-user session, since agents call on behalf of users but authenticate as themselves), then checks a per-tool permission grant (agent X may call tool Y) against a permissions store, BEFORE the request is ever routed downstream. Downstream MCP servers trust the gateway's signed, short-lived token rather than re-checking permissions themselves — the same "verify once at the edge, trust downstream" pattern backend/auth_jwt_oauth2.html established for JWTs, now applied at tool-call granularity instead of per-HTTP-request granularity.

2 — Schema registry: cached, not queried live

Section 2's math showed the full registry is ~1.2MB — small enough that every gateway instance holds the ENTIRE registry in memory, refreshed on a short TTL (e.g. 30 seconds) or push-invalidated when an MCP server registers/updates a tool. This means an agent's tools/list discovery call never touches a downstream MCP server directly — it's served entirely from the gateway's local cache, which is both faster (no downstream round trip) and more resilient (a downstream MCP server being briefly unreachable doesn't break discovery for tools it doesn't even own).

3 — Isolating a slow/failing downstream tool

The single most important non-functional property: one misbehaving MCP server (slow, timing out, erroring) must not degrade calls to every OTHER tool. Three mechanisms, layered:

  • Per-backend connection pools — each downstream MCP server gets its own bounded connection pool (backend/connection_pooling.html's pattern, applied per-backend instead of per-database); one server's slow responses can only exhaust ITS OWN pool, not a shared one.
  • Per-backend timeouts — a tool call to a known-slow server gets a tighter or looser timeout than the gateway default, configured per tool, not globally.
  • Circuit breaker per backend — after N consecutive failures/timeouts to one MCP server, the gateway trips a breaker and fails fast (returns an error immediately) for that server for a cooldown window, rather than letting every new request queue up waiting on a server that's already down.
Interview-ready definition: the architecture centralizes auth/authz and schema discovery at the gateway edge (verify once, cache the schema registry entirely in memory since it's small), and isolates failure per downstream backend using per-backend connection pools, timeouts, and circuit breakers — so that request volume and failure blast radius are both scoped to ONE MCP server at a time, never to the gateway or its other backends as a whole.
04 — Every design choice above has a real cost. Say it out loud.

Every trade-off should trace back to a specific number or requirement from sections 1–2, not a general engineering instinct.

Now defend the design yourself

Practice problems

Work each one out before expanding the solution. Treat these as interviewer follow-ups.

Problem 1 · Defending the availability-driven instance count

Section 2 computed that 750 peak QPS needs less than one gateway instance mathematically, yet the design uses three. An interviewer pushes back: "isn't that over-provisioned?" How do you respond?

Show solution
No -- the instance count in this design was never driven by throughput, and saying so explicitly is the strong answer. Throughput math (peak_qps / qps_per_instance) answers "how much CPU/connection capacity do I need," which here is genuinely small. But the non-functional requirement was 99.95% availability, and a SINGLE instance -- no matter how much spare capacity it has -- cannot meet an availability target, because any one deploy, crash, or node failure takes the entire gateway down for every agent in the company. Three instances (N+2 over a minimum of N=1) is the smallest fleet that tolerates a single instance failure without dropping below full capacity, and is sized for FAULT TOLERANCE, not load. The over-provisioning read is backwards: this is the gateway being correctly sized against a requirement (availability) that throughput math alone doesn't capture at all. A gateway sized ONLY from QPS math, ignoring availability, would be the actual mistake here.
Problem 2 · Extending the design for a tool with 50MB responses

One new tool (a document-export tool) returns responses averaging 50MB, not section 2's assumed 8KB. Walk through which of section 2's numbers change, and whether anything in the architecture (section 3) needs to change as a result.

Show solution
Bandwidth is the number that changes materially. If even a small fraction of the 750 peak QPS is this new tool -- say 10 calls/sec of the 750 -- that alone is 10 * 50MB = 500MB/sec just for this one tool, dwarfing the ~7.5MB/sec section 2 computed for the ENTIRE rest of the system combined. That's no longer "trivial for a modern NIC" -- it's a genuine bandwidth and buffering concern, and it means this tool's traffic needs to be treated as a distinct case, not folded into the general roundtrip-bytes assumption. Architecturally, two things follow. First, this tool almost certainly should NOT be synchronous through the gateway the way section 4's default assumes -- a 50MB payload is a strong signal this belongs in the async tool invocation path (job ID + polling/webhook, per async_tool_job_queue_design.html), both to avoid holding a gateway connection open for the transfer duration and because a response that large is a reasonable proxy for "this tool takes real, non-trivial time to produce its result" even if it happens to be fast today. Second, its per-backend connection pool (section 3) should likely be sized and timed out separately from other backends -- a shared timeout tuned for 8KB JSON responses would incorrectly kill legitimate 50MB transfers. Audit logging also needs a tweak: logging the full 50MB response body per section 2's "~500 bytes per audit record" assumption breaks immediately -- the audit record for this tool should log a hash/pointer to the result, not the payload itself, exactly the parenthetical section 2 flagged for "large/sensitive" args.
Problem 3 · Choosing what a stale schema cache should never be allowed to do

Section 3 caches the tool schema registry with a 30-second TTL. A tool's schema changes to make a previously-optional argument REQUIRED. During the TTL window, an agent using the stale cached schema calls the tool without that argument. What should happen, and where should the failure surface?

Show solution
The call should fail, but it must fail at the DOWNSTREAM MCP server's own request validation, not be silently accepted -- and this is exactly why caching the schema for DISCOVERY purposes (what tools.list returns to agents) is safe under section 3's eventual-consistency assumption, while the gateway must never treat its cached schema as authoritative for VALIDATION. If the gateway tried to validate the request against its own stale cached schema before forwarding it, it would incorrectly accept a request missing the now-required argument, and the failure would surface downstream anyway (worse: possibly as a confusing runtime error inside the tool's own logic rather than a clean validation error). The correct design: the gateway's cached schema is used ONLY for what section 3 said -- serving discovery/tools.list quickly -- while the actual downstream MCP server remains the source of truth for request validation on every call, cache-staleness or not. This is a direct instance of the general principle non-functional requirements already drew a line around in section 1: routing/permission data can tolerate staleness, but anything where staleness produces an incorrect ALLOW (validating a request that shouldn't pass) needs a stronger guarantee than a cache with a TTL provides.
Problem 4 · Reasoning about audit log durability vs. gateway latency

The non-functional requirements state the gateway must add under 15ms p99 overhead, and that audit logs must never be silently dropped. If audit writes are synchronous (the gateway waits for the audit record to be durably written before returning the tool result to the agent), does this design meet both requirements simultaneously? What would you change if it doesn't?

Show solution
Not necessarily, and this is a genuine tension worth naming rather than hand-waving past. A fully synchronous audit write -- gateway blocks until the audit record is durably committed before responding to the agent -- directly adds the audit store's own write latency on top of the routing/authz overhead, and if that store is a general-purpose durable database under load, that alone could threaten the 15ms budget, especially at the tail (p99), where a single slow write is exactly what blows through a tight latency budget. The practical resolution real systems use: write the audit record to a LOCAL, fast, durable buffer synchronously (e.g. an in-process write- ahead log or a local append-only file, both fast and durable at the single-node level) as the ONE synchronous step, then asynchronously forward from that buffer to the actual audit log store (the columnar/ tiered store section 2's 2.4TB/year estimate was sized for). This keeps the "never silently dropped" guarantee -- the record survives a gateway crash because it hit durable local storage before the response was returned -- while decoupling the SLOW part (writing to the shared audit store, batching, indexing) from the gateway's response path entirely. This is the same "durable-write-then-async-propagate" shape section 2 of chat_app_at_scale_design.html used for message delivery, and the same batching principle distributed_telemetry_ingester_design.html applies to spans -- durability and low latency aren't actually in conflict once you separate "committed somewhere durable" from "propagated to its final destination" into two different steps.
