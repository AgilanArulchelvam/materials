01 — Throughput answers "how much"; percentile latency answers "how bad, for whom"

What to measure under load

Start here, before running any load tool. Think about a single toll booth versus the whole highway during rush hour. Watching ONE car pass through tells you the booth works. It tells you nothing about what happens when a thousand cars arrive in the same ten minutes — does the booth process them at a steady rate (throughput), and for the unlucky driver stuck behind a jam, how long do THEY actually wait (the tail of the latency distribution, not the average)? A load test exists specifically to answer the second question, which no single-request integration test can.

MetricWhat it answersWhere it comes from in this capstone
Throughput (req/s)How many completed requests the system sustains per second at a given concurrency levelCount of successful POST /chat responses per second, measured by the load generator itself
p50 latencyThe typical request's experienceRoot span duration, per evals-and-observability/latency_and_tracing_integration.html section 1 — the SAME span data this week's dashboard already records
p95 latencyWhat the worst-served 5% of users experience — the number most real SLAs are actually defined againstSame root span data, aggregated across the load test's full request set
p99 latencyThe deep tail — invisible in an average, and often invisible in p50 tooSame source; this is the number most likely to reveal a bottleneck an average completely hides
Error rateWhether the system fails OPEN (returns errors fast) or fails BAD (hangs, times out, or returns wrong data) under saturationNon-200 responses and timeouts from the load generator, cross-checked against eval_span rows with no matching eval_result — a load-induced version of backend/capstone_debugging_integration_issues.html's silent instrumentation gap
# Reading percentile latency out of the SAME span data # latency_and_tracing_integration.html already collects -- load # testing doesn't need new instrumentation, it needs a new WORKLOAD # to run that instrumentation against. import numpy as np def summarize_load_test(root_span_durations_ms: list[float]) -> dict: arr = np.array(root_span_durations_ms) return { "p50": np.percentile(arr, 50), "p95": np.percentile(arr, 95), "p99": np.percentile(arr, 99), "max": arr.max(), "count": len(arr), }
Interview-ready definition: a load test's job is to plot throughput AND percentile latency against increasing concurrency on the same timeline — the interesting result is never a single number, it's the SHAPE of the curve: throughput that plateaus while latency keeps climbing is the universal signature of a saturated bottleneck, and knowing where that plateau begins is the entire point of running the test at all.
02 — A realistic ramp, against a realistic request mix

Designing the load test

Start here, before pointing a tool at the system. Two design mistakes make a load test's results meaningless: hammering ONE endpoint with identical requests (real traffic is never uniform — some requests hit the search tool, some don't, some are multi-turn continuations of an existing run_id), and jumping straight to maximum concurrency instead of ramping (a sudden step function tells you the system fell over, but not WHERE the knee in the curve actually was).

# load_test.py -- ramping concurrent users against a realistic mix # of the three capstone request shapes, using locust-style semantics import random REQUEST_MIX = [ (0.5, "new_chat_with_search"), # new run_id, needs hybrid_search (0.3, "continue_existing_run"), # existing run_id, loads prior state (0.2, "new_chat_no_search"), # new run_id, tool-free reply ] class CapstoneUser: async def one_request(self, client): r = random.random() cumulative = 0 for weight, shape in REQUEST_MIX: cumulative += weight if r <= cumulative: return await self._send(client, shape) async def ramp(target_concurrency: int, step_seconds: int = 30): # ramp concurrency in steps, holding each step steady long enough # to reach equilibrium (a few seconds of warm-up noise at the # START of each step should be discarded, not counted) for concurrency in range(10, target_concurrency + 1, 10): await hold_concurrency(concurrency, duration=step_seconds) yield collect_metrics_for_step(concurrency)
Design choiceWhy it matters
Weighted request mix, not one endpointThe orchestrator's real bottleneck (per section 3) may only appear under a MIX — e.g. continue_existing_run requests contend on the same Redis keys as new runs, a contention pattern a search-only load test would never surface
Ramp in steps, hold each step, discard warm-upA single jump to max concurrency conflates "the system is at capacity" with "the system is still warming up (cold caches, cold connections)" — holding steady and discarding the first few seconds of each step isolates steady-state behavior
Run against a realistically-sized datasetPer database/capstone_capacity_estimation_practice.html's growth assumptions — load-testing hybrid search against 50 documents when production has 500,000 will completely hide an index-scaling bottleneck that only appears at real volume
Measure the DATABASE side effects too, not just responsesExactly capstone_integration_testing.html section 3's "assert on the response AND the resulting trace/eval records" rule, applied under load — a system that returns fast 200s while silently dropping eval_result writes under contention is failing in the worst possible way: looking healthy while it isn't
Interview-ready definition: a well-designed load test ramps concurrency in discrete, held steps against a WEIGHTED mix of the system's real request shapes, discards each step's warm-up period, and measures both response-side and database-side outcomes at every step — a flat spike to max concurrency against one endpoint tells you the system broke, not where or why.
03 — Four real candidates, each with its own signature in the data

Reading results to find the actual bottleneck

Start here, before assuming "it's just slow." Every one of this capstone's major components is a plausible bottleneck, and each one leaves a DIFFERENT fingerprint in throughput/latency data — the skill this section teaches is matching the fingerprint to the cause, not guessing.

CandidateSignature under loadHow to confirm
Orchestrator serializing on shared stateThroughput plateaus early; p95/p99 latency grows roughly LINEARLY with concurrency even while CPU usage stays low — the system is waiting on a lock, not doing workCheck Redis lock wait time directly (per mcp-and-agents/capstone_orchestrator_integration.html problem 2's SET NX lock) — if lock acquisition time dominates a request's total latency at high concurrency, this is confirmed
Search index (hybrid search)Latency grows specifically on the new_chat_with_search request shape from section 2's mix, while new_chat_no_search stays flat — an isolated, shape-specific slowdown rather than a system-wide oneCompare per-span latency (not just root span) for the hybrid_search span specifically, per latency_and_tracing_integration.html section 1's span-vs-request-level distinction — if that ONE span's p95 is climbing while others stay flat, the index is the bottleneck
A synchronous downstream MCP callThroughput caps at a suspiciously round number close to (worker_count × 1/average_call_duration) — a classic signature of a blocking call inside code that should be concurrentCheck whether the suspect tool's call is properly awaited inside an async handler versus accidentally using a blocking (non-async) client library, which would serialize an entire worker's event loop behind ONE slow call — the exact hazard capstone_orchestrator_integration.html problem 3's missing-timeout bug is a cousin of
DB writes for tracing/evalResponse latency (what the USER sees) stays flat even as concurrency rises, but the GAP between response time and eval_result write time (per capstone_dashboard_integration.html's async-vs-sync scoring trade-off) grows — the user-facing path is fine, the observability path is falling behindTrack write latency to eval_span/eval_result separately from response latency; if scoring is fire-and-forget (async, per that lab's own practice problem 1), a growing queue backlog here is invisible to users but means the DASHBOARD is increasingly showing stale or incomplete data under load
The trap this table is built to avoid: "throughput dropped, so add more workers" is the wrong conclusion if the actual bottleneck is a SHARED resource (a lock, a single index, a single DB connection pool) — more workers just means more processes contending for the same choke point, and can occasionally make p99 WORSE by adding more contention without adding more real capacity. Confirming WHICH component saturated first, per this table, always comes before choosing a fix.

Now design the fix, not just the finding

Practice problems

Problem 1 · The knee in the curve moved after a fix — did it actually help?

After identifying the orchestrator's Redis lock as the bottleneck (section 3, candidate 1), a teammate replaces the lock with capstone_orchestrator_integration.html problem 2's atomic-operation fix (RPUSH instead of load/mutate/save). Re-running section 4's ramp, throughput now plateaus at a HIGHER concurrency, but p99 latency at that new plateau is still climbing sharply. Is this fix "working," and what would you check next?

Show solution
Partially working, and the two numbers are telling two different things -- worth separating rather than treating "did it help" as one yes/no question. The fact that the PLATEAU moved to a higher concurrency is real evidence the lock was genuinely part of the original bottleneck: removing lock-wait time let the system sustain more simultaneous work before throughput capped out, exactly the predicted effect of candidate 1's fix in section 3. But p99 still climbing sharply AT the new, higher plateau means something else is now the binding constraint -- the fix didn't remove ALL contention, it moved the ceiling higher and revealed the NEXT bottleneck underneath it, which is the normal, expected outcome of fixing one bottleneck in a multi-component system (the "whack-a-mole" nature of performance work: removing the tightest constraint just exposes the next-tightest one, it rarely means "the system is now fully unconstrained"). What to check next: re-run section 3's whole table of candidates against the NEW plateau's traffic pattern -- is p99 now driven by the search index at higher concurrency, by DB write contention on eval_span (candidate 4, since more successful requests now mean more write volume than before), or by something the RPUSH change itself introduced (e.g. a single Redis list growing large enough that RPUSH's own performance degrades, which the atomic- operation fix's own trade-off notes in capstone_orchestrator_ integration.html problem 2 already flagged as a condition on it "mapping cleanly onto a Redis primitive"). The right conclusion is "the fix worked AND surfaced a new binding constraint," not simply "the fix didn't work" or "the fix is done."
Problem 2 · Designing a load test that would catch section 3's DB-write candidate

Section 3's fourth bottleneck candidate (DB writes for tracing/eval) is specifically dangerous because user-facing latency can stay flat while it happens — the load test's THROUGHPUT and RESPONSE-latency numbers alone would miss it entirely. What would you add to section 2's load test design to actually catch this candidate, and why wouldn't the design as originally written catch it?

Show solution
Section 2's load test, as designed, measures exactly two things: the load generator's own view of response latency/throughput, and (per its own "measure the database side effects too" row) an assertion that database writes happened at all -- but neither of those, on their own, catches a write pipeline that is falling BEHIND without failing outright. A queue of unwritten eval_result rows that grows throughout the load test, but eventually drains after the test ends, would show "eval_result rows exist for every trace_id" as TRUE by the time anyone checks, while completely missing that the writes were significantly delayed DURING the test -- which is precisely the dashboard-staleness problem this candidate describes. What to add: track write LATENCY (time between a run finishing and its eval_result row actually landing, not just whether it eventually lands), sampled continuously throughout the ramp rather than checked once at the end -- essentially running latency_and_tracing_integration .html's own percentile-latency treatment against the SCORING pipeline, not just the user-facing request pipeline, as its own separate timeline. Concretely: log a timestamp when score_run() is CALLED and compare it against eval_result.evaluated_at once written, computing p50/p95/p99 of that GAP across the load test's duration, plotted against concurrency exactly like section 4's simulator does for user-facing latency. A gap that grows with concurrency, even while user-facing p95 stays flat, is the specific, otherwise-invisible signature this candidate produces -- and is exactly the kind of result a load test that only watches the response path would never surface, which is the whole reason this problem is worth practicing deliberately rather than assuming "the response was fast" is sufficient evidence the whole system is healthy.
