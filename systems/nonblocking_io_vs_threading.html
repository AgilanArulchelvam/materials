SYSTEMS FUNDAMENTALS LAB · CONCURRENCY MODEL SELECTION

Concurrent connections, CPU cores, and simplicity all pull in different directions.

Async I/O, threading, and multiprocessing all "do concurrency" — but they solve genuinely different bottlenecks, and picking the wrong one either wastes engineering effort or hits a wall at scale. This lab builds the decision framework with real numbers: what an OS thread actually costs, what an asyncio Task actually costs, and the C10K problem that made the difference matter in the first place.

01 — Why this question exists at all

The C10K problem: why async I/O wins at scale

Start here, before any code. Imagine a hotel where every single guest, no matter how quietly they're sleeping, requires their own dedicated staff member standing outside their door all night just in case they need something. That's absurd at 10 guests and catastrophic at 10,000 — you'd need 10,000 staff, most of them doing nothing but occupying payroll and hallway space. A sane hotel instead has a small night crew and a system of call buttons: when a guest actually needs something, a button lights up, and whichever free staff member is nearest handles it. The staff count scales with actual simultaneous activity, not total guests.

The C10K problem (coined in the late 1990s: "can a single server handle 10,000 concurrent connections?") is exactly this. A naive server design gives every connection its own OS thread that blocks waiting for that connection's next byte — the "dedicated staff member per door" model. At a few hundred connections this is fine. At 10,000 mostly-idle connections (a realistic number for a chat server, a long-polling API, or persistent websockets), you'd need 10,000 OS threads sitting around mostly idle, and the sheer overhead of that many threads — memory footprint, scheduler overhead from context-switching between them — becomes the actual bottleneck, even though almost none of them are doing real work at any given moment.

Async I/O is the call-button system: one thread, one event loop, and a much cheaper per-connection bookkeeping cost (a small data structure the loop tracks, not an entire OS thread with its own stack). The loop only "wakes up" a connection's handler when there's actually something to do — new data arrived, a write buffer drained — so idle connections cost almost nothing while they wait.

Interview-ready definition: the C10K problem refers to the scalability limits of a thread-per-connection server architecture once concurrent connection counts reach roughly ten thousand or more — the fixed per-thread memory and OS scheduling overhead dominates system resources even when the vast majority of connections are idle. Async I/O (event-loop-based, non-blocking) architectures solve this by handling many connections on a single thread with near-constant per-connection overhead, since idle connections consume no thread and require no context switch while waiting.
02 — Putting real numbers on the tradeoff

What a thread costs vs. what an asyncio Task costs

An OS thread needs its own call stack reserved up front — typically roughly 1–8 MB of stack space by default (the exact default varies by OS and can be tuned down, but it's reserved per thread regardless of how much is actually used), plus kernel-side bookkeeping and the CPU cost of the OS scheduler context-switching between threads. An asyncio Task, by contrast, is just a Python object tracking a paused coroutine's state — on the order of a few kilobytes, with no separate OS-level stack and no OS-level context switch, because the switching happens entirely inside your single-threaded event loop.

03 — A different bottleneck entirely

When multiprocessing wins: CPU-bound work

Async I/O and threading both solve the same category of problem — lots of waiting, cheaply. Neither helps when the bottleneck is actual computation: image processing, numeric simulation, parsing large payloads, running a machine learning inference pass. In CPython, all Python-level threads (and all coroutines running in one event loop, which is single-threaded by definition) are bound by the GIL for CPU-bound work — only one can execute Python bytecode at a time, regardless of how many exist.

Multiprocessing sidesteps this entirely by using separate OS processes, each with its own Python interpreter and therefore its own independent GIL. Splitting a CPU-bound workload across N processes on an N-core machine can deliver close to an N-times speedup, something neither async I/O nor plain threading can ever provide for genuinely CPU-bound work in CPython.

04 — When the "better" tool is the wrong choice

When plain threading is still the right call

Async I/O wins at scale, but scale isn't free — every function in the call path needs to be async def, every library you call needs an async-compatible version (or a wrapped executor call), and debugging a stalled event loop is a different, less familiar skill than debugging a stalled thread. For a small, fixed number of I/O-bound tasks — say, five to twenty concurrent API calls in an internal script or a lightly-loaded background job — plain threading.Thread gets nearly all of the benefit (the waits still overlap) with dramatically less code complexity and no need to rewrite your entire call stack as async.

# Plain threading: simple, correct, entirely adequate for ~10 concurrent I/O calls from concurrent.futures import ThreadPoolExecutor import requests urls = ["https://api.example.com/a", "https://api.example.com/b", ...] # ~10 URLs with ThreadPoolExecutor(max_workers=10) as pool: results = list(pool.map(requests.get, urls)) # No event loop, no async/await threaded through every function — just works.

The moment that number grows into the hundreds or thousands, or the service needs to hold many long-lived idle connections (websockets, SSE, long polling), the thread overhead from Section 2 starts to actually matter, and that's the signal to reach for async I/O instead — not "async is always better," but "async is better once the connection count makes per-thread overhead the bottleneck."

Problem 1 · Chat server

You're building a chat server that needs to hold open up to 50,000 simultaneous websocket connections, most of them idle at any given moment (users not actively typing). Which approach, and why?

Show solution
Async I/O. This is the textbook C10K scenario: tens of thousands of mostly-idle, long-lived connections. Thread-per-connection would require 50,000 OS threads reserving 1-8MB of stack space each — tens of gigabytes of memory just for idle connections, plus severe OS scheduler overhead. An event loop tracks each connection as a lightweight Task costing a few KB, and only does work when a connection actually has something to send or receive.
Problem 2 · Batch image processing

You need to resize and compress 200,000 uploaded images as fast as possible on a 16-core machine. Which approach, and why not the alternatives?

Show solution
Multiprocessing. This is purely CPU-bound work with no I/O waiting to overlap. Async I/O gives zero benefit here — there's no waiting to hide, just computation, and it all runs on one thread anyway. Threading also gives no real speedup because the GIL means only one thread executes Python bytecode at a time. Multiprocessing, with one process per core (up to ~16 worker processes), gets each its own interpreter and GIL, achieving close to a 16x speedup by genuinely parallelizing the CPU work.
Problem 3 · Internal reporting script

You write a script that runs nightly, calling 8 different internal APIs to build a report, then emails it. Total run time matters a little but not critically. Which approach, and why might "the theoretically best" option be the wrong practical choice here?

Show solution
Plain threading (e.g. ThreadPoolExecutor with 8 workers). Async I/O could technically do this too and might shave a small amount of overhead, but for only 8 I/O-bound calls in a one-off nightly script, the added complexity of threading async/await through the whole codebase, choosing async-compatible HTTP libraries, etc. isn't worth it. This is precisely the "simplicity outweighs asyncio's added complexity" case — the theoretically most scalable tool is not automatically the right engineering choice when the scale doesn't demand it.
Problem 4 · Mixed workload

A web service handles incoming API requests (I/O-bound: mostly waiting on a database) but one specific endpoint does heavy CPU-bound data transformation before responding. How would you architect the concurrency here?

Show solution
Use async I/O for the main request-handling path (it's the dominant workload and benefits from cheap, high concurrency on database-bound requests), but offload the CPU-bound endpoint's heavy transformation to a separate process pool (e.g. via a ProcessPoolExecutor submitted from within the async handler, or a background worker queue like Celery/RQ) rather than running it inline on the event loop's single thread. Running heavy CPU work directly inside an async handler would block the entire event loop for every other concurrent request during that computation — combining the two wrong ways can be worse than picking either one consistently.
Problem 5 · Justifying against a skeptical interviewer

An interviewer pushes back: "Why not just always use async I/O for everything — isn't it strictly better than threading?" Give a concise rebuttal.

Show solution
No — async I/O is better specifically for high-concurrency I/O-bound workloads, not universally "better." It requires an async-compatible ecosystem end-to-end (every blocking call in the path must be replaced or offloaded, or it silently freezes the entire event loop — see the asyncio fundamentals lab's blocking-call trap), adds cognitive overhead (async/await threaded through the whole call stack), and provides zero benefit for CPU-bound work (still limited to one thread of Python execution) or for small, simple I/O workloads where thread overhead was never the bottleneck in the first place. The right choice depends on where the actual bottleneck is: connection count and per-connection overhead point to async; raw computation points to multiprocessing; a small number of I/O waits with a premium on simplicity points to plain threading.
Problem 6 · Estimating the threading ceiling

Using the ~1-8MB-per-thread figure from this lab, roughly how much memory would 5,000 thread-per-connection workers reserve for stack space alone, and what does that tell you about where the C10K problem actually bites?

Show solution
At the low end (~1MB/thread): ~5GB. At the high end (~8MB/thread): ~40GB — just for reserved stack space, before counting any actual per-connection application state, socket buffers, or the OS's own per-thread bookkeeping. This tells you the wall isn't purely about CPU capacity to handle 5,000 connections' worth of traffic — it's specifically the FIXED, mostly-wasted overhead of committing a full thread stack to every connection regardless of how idle it is, which is exactly the inefficiency async I/O's few-KB Tasks are designed to eliminate.
