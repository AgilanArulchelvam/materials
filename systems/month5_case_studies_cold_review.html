Chat app at scale, re-derived

Do this before opening anything below. Set a timer for 6-9 minutes. Sketch the architecture on paper or narrate it out loud, exactly as if a live interviewer were listening and could ask a follow-up at any moment.

Prompt — attempt cold first

Without looking anything up, design connection management, delivery guarantees, and horizontal scaling for a chat app:

  • Why does a chat app break the "any server can answer any request" assumption a typical stateless HTTP API relies on?
  • Name the three delivery guarantee levels and explain, precisely, why "exactly-once" is hard to guarantee at the transport layer — and what real systems actually build instead.
  • A message from a user on server A needs to reach a user connected to server B. Walk through the mechanism that makes this possible without server A knowing which specific server B holds that connection.
  • What single architectural property does that mechanism depend on, and what's a concrete way it could go wrong under real production conditions?
Reveal the answer (only after you've actually attempted it)
WHY STATELESSNESS BREAKS: a typical HTTP API's statelessness means no server holds anything specific to any one client between requests, so a load balancer can route any request to any server interchangeably. A chat app breaks this because each online user holds one persistent, long-lived WebSocket connection to exactly ONE specific server process -- that server, and only that server, has the actual in-memory socket handle needed to push a message to that user. There is no way for a DIFFERENT server to reach that connection directly. DELIVERY GUARANTEES: at-most-once (send once, never retry -- risks silent loss, never duplicates), at-least-once (retry whenever delivery is uncertain -- guarantees eventual arrival, but may deliver more than once), and exactly-once (arrives precisely once, always). Exactly-once is hard at the transport layer because a sender can never be perfectly certain whether an unacknowledged send genuinely failed or simply lost its ACKNOWLEDGMENT on the way back -- from the sender's point of view, both look identical (silence), so the sender cannot distinguish "must retry" from "must not duplicate." Real systems approximate exactly-once by combining reliable at-least-once delivery (retry whenever uncertain) with a client-generated idempotency key (database/crud_done_right.html's pattern) that lets the receiver recognize and discard a duplicate -- producing an exactly-once USER EXPERIENCE on top of an honestly at-least-once mechanism underneath. CROSS-SERVER DELIVERY: a pub/sub backplane (commonly Redis pub/sub) that every server connects to. Each server SUBSCRIBES to channels for the users it personally has connections to. Any server needing to deliver a message PUBLISHES to the recipient's channel unconditionally, with no knowledge of which specific server is subscribed to it. This converts "route this message to the right SERVER" (a problem server A has no way to solve on its own) into "publish to the right CHANNEL" (a problem server A can always solve, because channel names are just a known convention, e.g. user:{user_id}) -- the backplane, not application code, handles the actual server-to-server routing. WHAT THIS DEPENDS ON, AND WHERE IT BREAKS: the backplane itself becomes a new critical dependency and potential bottleneck -- every cross-server message now flows through it. A concrete failure mode: if the pub/sub backplane itself falls behind or drops a message under load, a message can be silently lost between publish and the recipient server's subscription callback firing, with NEITHER server aware anything went wrong -- this is exactly why delivery guarantees (the previous bullet) have to be enforced on TOP of the backplane, via application-level acknowledgment and retry, not assumed for free just because the backplane exists.
What "re-derive cold" is testing: whether you can explain WHY exactly-once is fundamentally hard (not just recite the three levels), and whether "pub/sub backplane" connects to the concrete reframing — routing to a server becomes publishing to a channel — rather than staying a buzzword.

CI/CD eval gating, re-derived

Do this before opening anything below. Same rules: timer, full attempt, no peeking until you're done.

Prompt — attempt cold first

Without looking anything up, design a CI/CD pipeline that gates deploys on eval thresholds, not just tests:

  • What can passing unit/integration tests NOT tell you about a model-backed system that an eval-based gate specifically closes?
  • Where does the eval gate sit relative to ordinary lint/test/build stages, and why there specifically?
  • Name the two deploy strategies that make rollback fast, and explain precisely what "fast" means for each — what operation actually happens when you roll back?
  • What's the concrete cost difference between an automated rollback triggered by a failed gate versus a manual rollback, beyond just "manual is slower"?
Reveal the answer (only after you've actually attempted it)
WHAT TESTS CAN'T TELL YOU: unit/integration tests verify the CODE runs correctly — the right functions get called, no exceptions are thrown, types line up. They say nothing about whether the MODEL'S BEHAVIOR -- answer quality, trajectory correctness, hallucination rate, cost per call -- has regressed, because none of that is a code-correctness property at all; a candidate build can pass every unit test while its prompts, retrieval, or a swapped model version make its actual answers measurably worse. An eval-based gate closes exactly this gap by running the SAME kind of eval suite (deterministic, model-graded, trajectory- based) against every candidate build as a genuinely separate, second check. WHERE IT SITS: after ordinary tests, as an ADDITIONAL gate -- not a replacement for lint/test/build's own ordering (cicd_pipeline_basics. html's fail-fast argument still applies: don't spend eval-suite compute on a build that doesn't even pass its unit tests yet). The eval gate runs once a candidate build genuinely exists and has already cleared cheaper checks, comparing the eval pass rate (or a specific critical eval) against a configured threshold, and blocking promotion to production if it's not met. TWO DEPLOY STRATEGIES AND WHAT "FAST" MEANS: blue-green deployment keeps TWO complete environments running -- the old, currently-live version and the new candidate -- and "rollback" is purely a TRAFFIC-POINTER FLIP back to the environment that was already fully running and already proven; no rebuilding, no redeploying, just re-pointing traffic. Canary releases instead route only a SMALL percentage of traffic to the new version while the majority stays on the old one; "rollback" here means routing that small percentage back to 0%, which is also fast because the new version was never fully promoted to begin with -- pulling back is a routing change, not a reconstruction. AUTOMATED VS MANUAL ROLLBACK COST: automated rollback triggers the instant a failure signal appears (a failed eval gate, a bad post-deploy metric) with NO human in the loop at all. Manual rollback adds two separate delays stacked on top of each other: a human first has to NOTICE the problem (a detection delay that doesn't exist for an automated trigger watching the signal directly), and only then DECIDE and EXECUTE the rollback (a decision-and-execution delay on top of the mechanical rollback time itself, which is the same whether triggered by a human or automatically). The automated path eliminates both added delays entirely, not just the mechanical portion.
What "re-derive cold" is testing: whether you can name the SPECIFIC gap between test-passing and eval-passing (not just "evals are also good to have"), and whether you can explain rollback speed as a concrete OPERATION (a traffic-pointer flip) rather than a vague "it's just faster."

Nginx reverse proxy, re-derived

Do this before opening anything below. Same rules: timer, full attempt, no peeking until you're done.

Prompt — attempt cold first

Without looking anything up, design an nginx reverse proxy sitting in front of several backend services:

  • What does nginx's routing table actually map, and what real config directive expresses it?
  • Where does TLS termination happen, and why is it centralized at the proxy rather than handled independently by each backend service?
  • Precisely where does encryption stop, and what does that imply about the network segment between nginx and an app server?
  • Why does that implication matter operationally — what has to be true about that segment for terminating TLS at the proxy to be a safe design choice at all?
Reveal the answer (only after you've actually attempted it)
ROUTING TABLE: nginx's routing maps URL PATHS (or hostnames) to specific UPSTREAM backend addresses -- a `location /api/orders/ { proxy_pass http://orders-service:8080; }` block routes any request under that path prefix to the orders service, while a different location block routes a different path to a different backend, all behind one single public front door / domain. WHY CENTRALIZED TLS TERMINATION: nginx accepts the incoming HTTPS connection, does the actual TLS handshake and certificate validation ONCE, at the edge, then forwards the now-decrypted request to the appropriate backend over HTTP (or a separately-terminated internal connection). Centralizing this at one place means certificate management, cipher configuration, and TLS version support are handled in exactly ONE location instead of independently -- and potentially inconsistently, with some services running outdated or misconfigured TLS -- across every single backend service. WHERE ENCRYPTION STOPS: encryption stops at nginx itself -- the connection from the CLIENT to nginx is encrypted (HTTPS), but the connection from nginx to the actual APP SERVER is typically plain HTTP, unencrypted. This implies the network segment between nginx and the app servers carries genuinely unencrypted traffic. WHY THIS IS OPERATIONALLY SAFE ONLY CONDITIONALLY: terminating TLS at the proxy is a safe design choice ONLY if that internal nginx-to- app-server segment is a TRUSTED, PRIVATE network -- typically inside the same VPC or a network no untrusted party can observe traffic on. If that internal network were exposed or shared with untrusted parties, the plaintext hop between nginx and the app server would leak exactly the data TLS was supposed to protect, meaning "TLS termination at the edge" is not free -- it's a deliberate trade of end-to-end encryption for centralized management, valid specifically because (and only because) the internal network segment is assumed trustworthy.
What "re-derive cold" is testing: whether "TLS terminates at the proxy" connects to the concrete consequence (an unencrypted internal hop) and its precondition (a trusted internal network), rather than staying an isolated fact about where a certificate lives.

Sharding & replication for eval data, re-derived

Do this before opening anything below. Same rules: timer, full attempt, no peeking until you're done.

Prompt — attempt cold first

Without looking anything up, apply Month 3's sharding and replication concepts to eval_result data specifically:

  • Name three candidate shard keys for eval_result, and for each, describe the query pattern it makes fast versus the one it forces to fan out across every shard.
  • Which shard key actually wins for this workload, and why — what's the dominant real-world query this data serves?
  • Should eval data use synchronous or asynchronous replication? Justify using what actually happens if a follower falls behind for each option.
  • What's the concrete risk of an uneven/hot shard specifically for eval data, using your chosen shard key?
Reveal the answer (only after you've actually attempted it)
THREE CANDIDATE SHARD KEYS: - run_id: fast for "get every result from THIS run" (a single-shard query, since one run's results all share one run_id) -- but "how has test case tc-882 performed across the last 10 runs" (querying ACROSS runs) has to fan out across every shard, since different runs' results land on different shards. - dataset_id: fast for "get every result ever produced against THIS dataset" -- but a single eval_run's results (which typically span many test cases from possibly multiple datasets, or at minimum aren't naturally grouped by dataset_id alone) may not co-locate cleanly, and cross-run trend queries for one test case still fan out. - time period (e.g. the run's started_at, bucketed by week/month): fast for "show me everything from the last 7 days" (a time-range dashboard query) -- but "all results for run X" or "all results for test case Y over its full history" both potentially span multiple time-based shards if the run/test-case's history crosses a shard boundary. WHICH KEY WINS AND WHY: run_id wins, because the DOMINANT real-world access pattern for eval data is "give me everything from THIS run" -- that's what a CI/CD gate queries (compute pass rate for run X), what a developer investigating a specific failed run queries, and what dashboard views showing "the latest run's results" query. Cross-run trend queries (per test case, over time) DO have to fan out under this choice, but they're a comparatively rarer, less latency-sensitive analytical query (typically viewed on a dashboard, not blocking a CI/CD gate decision) -- a reasonable trade to make explicitly, optimizing the hot path (single-run lookups) at the cost of the cold path (cross-run trend analysis). SYNC OR ASYNC REPLICATION: asynchronous. Eval results are written once after a run completes and are read frequently afterward but never require the absolute latest write to be visible on every replica instantly -- a CI/CD gate reading a few hundred milliseconds of replication lag behind the primary write is a non-issue, since the write that matters (this run's results) either fully happened moments ago or didn't; there's no financial-transaction-style correctness requirement here. Synchronous replication would force every write to wait for follower acknowledgment before returning, adding real latency to every eval-result write for a durability guarantee this workload doesn't actually need enough to pay for -- exactly the "sync for correctness- critical, async for latency-sensitive-but-tolerant-of-lag" trade-off Month 3's replication lab established generally. HOT SHARD RISK WITH run_id: an uneven shard key would concentrate a disproportionate share of writes/reads onto one shard. With run_id specifically, the risk isn't uniform value distribution (run_ids are typically well-distributed, e.g. UUIDs) but TEMPORAL concentration -- if a CI/CD pipeline runs many eval suites back-to-back during a busy release window, and the shard key hashes run_id in a way that happens to cluster recently-created run_ids onto the same shard (a real risk with some naive hash-and-modulo schemes on sequential or time-correlated IDs), that shard becomes a hot spot exactly when write AND read volume are both highest -- during an active release crunch, precisely the worst time for a bottleneck to appear.
What "re-derive cold" is testing: whether you can name the ACTUAL dominant query pattern (not just list shard key options) and use it to justify a specific choice, and whether the sync-vs-async replication answer connects to a concrete tolerance for lag rather than a memorized rule.

Practice problems

Work each one out cold before expanding the solution. These reason across all four designs at once.

Problem 1 · Connecting TLS termination to the eval gate's rollback strategy

A blue-green rollback (section 2) flips traffic from the new environment back to the old one. Using section 3's nginx design, where does that traffic flip actually happen mechanically, and why does centralizing TLS termination at nginx make this flip simpler than if each backend terminated its own TLS?

Show solution
The traffic flip happens at nginx's own upstream configuration -- the proxy_pass / upstream block that currently points to the "green" environment gets updated to point back at "blue" instead (or an nginx config reload, or an upstream group weight change if using a more dynamic routing setup). Because TLS termination happens ONCE at nginx (section 3), the client-facing TLS session is completely unaffected by this flip -- clients keep talking to the same public endpoint with the same certificate the whole time; only the INTERNAL routing decision (which upstream nginx forwards decrypted traffic to) changes. If each backend instead terminated its own TLS independently, a blue-green flip would need to ensure BOTH environments have valid, correctly configured certificates for the same public hostname simultaneously (since either could receive traffic at flip time), and any TLS-related bug or misconfiguration specific to the "blue" environment's own certificate handling would only surface at the exact moment traffic flips back to it -- a new failure mode section 3's centralized approach eliminates entirely, since nginx's own TLS configuration doesn't change at all during a blue-green rollback; only which backend receives the already-decrypted request changes. This is a concrete instance of section 3's "centralizing TLS reduces surface area" argument, now applied specifically to why it also makes ANOTHER system's (the eval gate's) rollback mechanism simpler.
Problem 2 · Reasoning about the pub/sub backplane's own scaling need

Using section 1's pub/sub backplane design and section 4's sharding reasoning, would you shard the pub/sub backplane the same way you'd shard eval_result (by an ID field)? Why or why not?

Show solution
No -- and the reason exposes a real difference in what each system is optimizing for. eval_result sharding (section 4) is chosen around a QUERY pattern -- which reads need to be fast and single-shard versus which are acceptable to fan out. A pub/sub backplane's core operation is different in kind: it's not being QUERIED by an arbitrary key at all, it's routing PUBLISH events to whichever servers are SUBSCRIBED to a specific channel (user:{user_id}, per section 1) at delivery time -- there's no "give me all messages across many channels" query pattern analogous to eval_result's "eval results across many runs" trend query that section 4 needed to weigh a shard key against. If a pub/sub backplane needs to scale beyond one instance's capacity, the actual mechanism (in a real system like Redis Cluster) is closer to CONSISTENT HASHING of the channel key itself (user_id) across nodes, specifically to keep each channel's publish/subscribe traffic on ONE node so a publish never needs to fan out to multiple nodes to find the right subscriber -- which is actually MORE similar to section 4's run_id choice (optimize for single-key operations, accept that cross-key aggregate queries are rare and can be slower) than it might first appear, just applied to a fundamentally different operation (routing a live event) rather than a stored, queryable table.
Problem 3 · Diagnosing a false sense of safety from async replication

A team argues "our eval_result data uses async replication (section 4), so a primary database failure loses zero data, since read replicas have a full up-to-date copy." Using section 4's own definition of asynchronous replication, what's wrong with this claim specifically?

Show solution
This claim conflates "async replication happens quickly, most of the time" with "async replication guarantees zero data loss on primary failure" -- and section 4's own definition of asynchronous replication directly contradicts the second half. Async replication means the PRIMARY acknowledges a write as successful WITHOUT waiting for any follower to confirm it has received that write -- by construction, there is always some window, however small under normal conditions, where a write exists on the primary but has NOT yet reached a follower. If the primary fails during exactly that window -- a write was accepted, the client was told "success," but the write had not yet replicated to any follower when the primary went down -- that write is genuinely lost when a follower is promoted to become the new primary, because the new primary's data is only as current as the last write it actually received, not the last write the OLD primary accepted. This exact scenario is the well-known trade-off async replication makes deliberately: lower write latency (no waiting for follower ACKs) in exchange for a real, non-zero risk of losing the most recent writes on an unplanned primary failure -- section 4's justification for choosing async for eval_result specifically was that THIS particular risk (losing a few of the very latest eval writes, in the rare event of a primary crash at exactly the wrong moment) is an acceptable trade for eval data, not that the risk doesn't exist. The team's claim is confusing "we accepted this trade because the consequence is tolerable here" with "the trade-off doesn't apply to us," which is a real, dangerous misunderstanding if repeated for a workload where losing the latest writes actually IS unacceptable (e.g. financial transaction data, where synchronous replication's cost is worth paying specifically to avoid this scenario).
Problem 4 · Designing a new case study that combines two of these designs directly

Sketch, in words, what would have to change in the CI/CD eval gate design (section 2) if the system being gated were the CHAT APP itself (section 1) — specifically, what would the eval SUITE need to test that a typical single-turn agent eval suite wouldn't, given the chat app's stateful, multi-turn, cross-server nature?

Show solution
A typical eval suite (deterministic, model-graded, trajectory-based, per Month 5 Week 1) is usually built and run against SINGLE-turn or single-session interactions -- it doesn't inherently exercise section 1's specific concerns (cross-server delivery, connection handoff, backplane-mediated routing) at all, because those are INFRASTRUCTURE properties of the chat app, not properties of any one model response's quality. Gating a chat app deploy on evals would need the suite EXTENDED with scenarios that specifically probe section 1's guarantees: (1) a multi-turn scenario where the two turns are deliberately routed through DIFFERENT chat server instances (simulating a user's connection being handled by server A, then reconnecting and landing on server B after a network blip), verifying conversation context/state was actually retrievable rather than silently lost when the connection moved servers -- this tests whether shared conversation state (not just in-memory per-server state) was correctly designed; (2) a delivery-guarantee scenario that deliberately introduces a simulated backplane hiccup (section 1's own "concrete failure mode") and verifies the at-least-once + idempotency-key mechanism actually prevents both silent loss AND visible duplication on the receiving client; (3) a load/concurrency scenario verifying a message from a server-A user to a server-B user still arrives correctly under realistic concurrent connection churn (users connecting/disconnecting rapidly), not just in a clean, static two-server test. None of these are properties a standard single-turn quality eval (does the RESPONSE content make sense) would ever exercise, because they're about whether the INFRASTRUCTURE correctly preserves conversation continuity and delivery guarantees across the exact stateful, multi-server complexity section 1 introduced -- exactly the kind of gap a naive "just reuse the existing eval suite" approach to gating a NEW kind of system would miss entirely.
Problem 5 · Full synthesis — writing your own end-to-end trace for a failure scenario

Write (in words) a full trace, using all four designs, for this scenario: a candidate build's eval gate FAILS specifically on p95 latency (not accuracy or hallucination rate) after a deploy. Trace what happens at each of the four systems, and identify precisely which system's OWN behavior is actually responsible for triggering the block.

Show solution
A full trace: the candidate build completes its eval run (the eval scenario set, executed against the new build) and every result lands in the SHARDED eval_result table (section 4), sharded by run_id so this run's full result set is queryable from a single shard. The CI/CD eval gate (section 2) then queries that run's results -- computing not just pass/fail rates but also the run's aggregate p95 request-level latency (a metric this synthesis assumes was captured via traces during the eval run itself, per Month 5's tracing labs) -- and compares it against the configured p95 threshold. p95 exceeds the threshold; the gate blocks promotion. Per section 2's rollback strategy, since this is a BLOCKED promotion rather than a live rollback of an already-promoted build, the mechanism is simpler than a full rollback -- the candidate build simply never gets its traffic-pointer flip (blue-green) or its traffic percentage increase (canary); the currently-live, already-proven build keeps serving 100% of traffic throughout, untouched. Nginx (section 3) and the chat server's connection/backplane machinery (section 1) are NOT involved in this trace at all, and that's the point worth naming explicitly: the eval gate operates entirely BEFORE any live traffic (which nginx routes and the chat server serves) ever reaches the candidate build, exactly synthesis section 5's own callout about the eval gate not sitting in the live per-message path. WHICH SYSTEM IS ACTUALLY RESPONSIBLE: the eval gate (section 2) is the system whose OWN behavior triggers the block -- it's the one comparing a measured value against a configured threshold and making the block/promote decision. The sharded eval_result table (section 4) is merely where the DATA the gate needs already lives, queryable fast specifically because of the run_id shard key choice; it doesn't make any decision itself. Correctly attributing WHICH component made the decision versus which merely supplied data to it is exactly the kind of precision a system design interview is testing when it asks "walk me through what happens" rather than just "does it work."
