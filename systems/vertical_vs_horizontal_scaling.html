SYSTEMS FUNDAMENTALS LAB · VERTICAL VS HORIZONTAL SCALING

Growing a system is a choice between one bigger machine and more machines that share the work.

Both directions add capacity. Only one of them removes your single point of failure — and that safety isn't free. This lab walks through why vertical scaling hits a wall, what horizontal scaling actually demands from your application (statelessness, load balancing, partitioning), and the concrete cost and complexity price you pay for each.

01 — Two directions, one goal

The core idea: growing without breaking

Start here, before any diagrams. Imagine a small bakery that's outgrown its kitchen. There are two ways to fix that: knock down a wall and build a much bigger kitchen in the same spot, or open a second bakery location across town and split the customers between both. Both solve "we can't keep up with demand" — but they behave completely differently when a health inspector shuts one kitchen down, or when rent goes up, or when you need a third location next year.

That's the entire idea behind vertical and horizontal scaling:

  • Vertical scaling ("scale up") — the bigger-kitchen approach. Give one machine more resources: more CPU cores, more RAM, a faster disk. The system is still fundamentally one thing, just a beefier version of itself.
  • Horizontal scaling ("scale out") — the second-location approach. Add more machines, all doing the same job, and spread the incoming work across them. The system becomes a team instead of an individual.

Both directions genuinely add capacity — more requests handled per second. But they diverge sharply once you ask two follow-up questions that this lab is built around: "what happens when one part breaks?" and "how far can this actually grow?" Vertical and horizontal answer both questions completely differently, and that difference is what the rest of this lab digs into.

02 — Why "just get a bigger server" runs out of road

Vertical scaling limits: single point of failure & hardware ceiling

Start here, before any code. If your entire bakery is one building, and that one building floods, you have zero bakeries — not "a smaller bakery," zero. That's the first problem with vertical scaling, and it has nothing to do with how big or powerful that one building is. The second problem shows up later: even if the building never floods, there's only so big a single kitchen can physically get before you literally run out of things to buy that make it bigger.

Single point of failure (SPOF)

A single point of failure is any one component whose failure takes down the entire system — not just part of it. When you scale vertically, your one powerful server is a single point of failure, no matter how much RAM or how many CPU cores you give it. Bigger doesn't mean less fragile; it just means the same one point of failure can now do more work before it goes down.

The mechanism, precisely: it doesn't matter that the server has 128GB of RAM or 16 CPU cores — a power supply failure, a disk failure, a kernel panic, or even a routine reboot for a security patch takes the entire service down, for every single client, at the same moment. Vertical scaling makes the server more capable; it does nothing to make it less singular. The only way to remove a single point of failure is to stop having only one of that thing — which is a fundamentally horizontal move (redundant, interchangeable copies), not a vertical one.

The hardware ceiling

Even setting failure aside, vertical scaling runs into a second, harder wall: there is a biggest machine you can currently buy. CPUs have a maximum number of cores before manufacturing gets exotic and absurdly expensive. RAM has a maximum a single motherboard can address. Network cards have a maximum throughput. At some point "buy a bigger one" isn't a budget question anymore — it's a "no such product exists yet" question.

Why this matters: the hardware ceiling means vertical scaling is a strategy with a built-in expiration date — it can absolutely be the right first move (it's simple, and there's nothing to coordinate), but it cannot be the long-term plan for a system that needs to keep growing indefinitely. Horizontal scaling doesn't have this ceiling in the same way: instead of needing one impossible machine, you need N ordinary, easy-to-buy machines, and N can keep growing.
03 — What "just add more machines" actually demands

Horizontal scaling requirements: statelessness, load balancing, partitioning

Start here, before any code. Opening a second bakery location sounds simple until you actually try it: a customer who ordered a custom cake at Location A can't just walk into Location B and expect them to know about it, unless you've written that order down somewhere both locations can see. Someone also has to decide which customers go to which location so neither one gets overwhelmed while the other sits empty. And if you're storing a million customer records, you probably don't want every location keeping a full copy of all of them.

Those three problems — "remembering things across locations," "deciding who goes where," and "splitting up what each location is responsible for" — map exactly onto the three things horizontal scaling requires from a real system: statelessness, load balancing, and partitioning.

Requirement 1 — Statelessness

If server A remembers "this customer is mid-checkout" only in its own local memory, and the customer's very next request happens to land on server B instead, server B has no idea any of that happened. For horizontal scaling to work, any given request must be answerable by any server in the group — which means servers can't keep request-specific memory (like login sessions or shopping carts) sitting locally in their own process. That per-request memory has to live somewhere every server can reach — typically a shared database or cache like Redis — not inside any one server.

request 1: login
request 2: view cart
The failure mode, precisely: a stateful server behind a load balancer works fine right up until a request that depends on earlier state gets routed to a server that never saw that earlier request — then it looks like the user was randomly logged out or their cart emptied, and the bug is maddening to reproduce because it depends entirely on which server the load balancer happened to pick. This is why "make the app stateless" is usually the very first real engineering work required before horizontal scaling can work at all — it's not a nice-to-have, it's a precondition.

Requirement 2 — Load balancing

Once you have multiple interchangeable servers, something has to decide which server handles each incoming request. That's a load balancer — it sits in front of the server pool and picks a target using some algorithm. A few common ones:

AlgorithmHow it picksWeakness
Round robinCycles through servers in order: 1, 2, 3, 1, 2, 3…Ignores how busy each server actually is right now

Requirement 3 — Partitioning (sharding)

Load balancing splits up requests. Partitioning (also called sharding) splits up data. If your dataset is too large for one database server to hold — or too much write traffic for one server to handle — you split the data itself across multiple database servers, each owning a slice, usually decided by something like hash(user_id) % number_of_shards.

PARTITION USERS ACROSS 3 SHARDS BY hash(user_id) % 3
Each user id is hashed and routed to exactly one shard — that shard is the only one that ever needs to be asked about that user.
Why this matters: partitioning is what lets horizontal scaling apply to data, not just to compute — without it, every server in your horizontally-scaled fleet would still need to talk to the same single, ever-growing database, which becomes its own single point of failure and its own hardware ceiling. The trade-off: once data is partitioned, a query that needs data from multiple shards (like "find all orders across all users this week") becomes genuinely harder — it has to gather results from several shards and combine them, instead of asking one database one question.
04 — There is no free direction

Cost, complexity, and failure-mode trade-offs

Start here, before the numbers. The bigger-kitchen approach is simple to reason about — there's only one kitchen, one set of keys, one thing that can go wrong. The multi-location approach is safer against any single disaster, but now someone has to manage staffing across locations, keep their inventories in sync, and figure out which location a delivery driver should go to. Neither approach is just "better" — they trade different kinds of risk and effort for each other.

Vertical scaling

  • Complexity: low — it's still one system, nothing to coordinate
  • Cost curve: cheap at first, then rises steeply — the biggest instances cost far more than proportionally more capacity
  • Failure mode: total outage — one fault takes down 100% of traffic
  • Ceiling: hard — bounded by the biggest machine that exists to buy

Horizontal scaling

  • Complexity: higher — needs statelessness, a load balancer, often partitioning, and monitoring across many machines
  • Cost curve: roughly linear — 2x the machines is close to 2x the cost, all the way up
  • Failure mode: partial degradation — losing one of ten machines costs ~10% capacity, not the whole system
  • Ceiling: soft — bounded mainly by budget and coordination overhead, not by hardware limits
COST TO DOUBLE CAPACITY — SAME WORKLOAD, TWO STRATEGIES
Why this matters: the vertical cost curve bends upward because CPU/RAM pricing isn't linear at the high end — the jump from a 32-core to a 64-core instance costs much more than double, since fewer manufacturers can even build that chip. The horizontal cost curve stays close to a straight line because each additional machine is an identical, mass-produced unit — but that flatter cost line is bought with the ongoing complexity cost of running a distributed system: coordination, monitoring, and the statelessness/load-balancing/partitioning work from Section 3.

Choosing between them isn't binary in practice

Most real systems don't pick one direction forever — they scale vertically first (it's cheap and simple while traffic is small), and switch to horizontal once either the hardware ceiling gets close, or the single point of failure becomes an unacceptable business risk. Many systems end up doing both: a horizontally-scaled fleet of moderately-sized (not maximally huge, not minimally small) machines, because the sweet spot for cost-per-unit-of-capacity is rarely at either extreme.

Practice problems

Problem 1 · Spotting the single point of failure

A company runs their entire checkout flow on one very large database server, but has 20 identical, load-balanced web servers in front of it. Is this system horizontally scaled? What's the single point of failure, if any?

Show solution
The web tier is horizontally scaled -- 20 interchangeable servers behind a load balancer means losing one costs about 5% of capacity, not an outage. But the database is a single, unreplicated server, so it IS a single point of failure: if that one database goes down, all 20 web servers become useless, since none of them can complete a checkout without it. Horizontal scaling has to be applied to every layer that matters -- scaling only the web tier doesn't remove the SPOF sitting one layer below it.
Problem 2 · Why this specific bug appears

A team adds a second web server and a load balancer in front of both. Users start reporting that they get logged out randomly, seemingly at random times, only some of the time. What's the most likely cause, and what's the fix?

Show solution
Almost certainly a statefulness bug: login sessions are being stored in each web server's local memory. When a user's login request lands on server A, server A remembers them -- but if their NEXT request gets routed by the load balancer to server B, server B has never seen that session and treats them as logged out. It looks "random" because it depends entirely on which server the load balancer happens to route to each time. Fix: move session storage out of each server's local memory into a shared store both servers can read from -- a shared database or a cache like Redis -- so any server can answer "is this user logged in?" identically. This is exactly the statelessness requirement from Section 3.
Problem 3 · Choosing a load balancing algorithm

Two servers sit behind a load balancer. Server A mostly handles quick, sub-10ms requests. Server B occasionally receives requests that take 4 seconds to process (a slow report-generation endpoint). Would round robin or least-connections distribute load more fairly here? Why?

Show solution
Least-connections is the better fit. Round robin would keep sending every other request to server B regardless of how backed up it already is, since round robin has no idea how busy a server currently is -- it just cycles in order. Least-connections actively avoids sending new requests to a server that's already tied up with a long-running request, since that server's active-connection count stays elevated for the whole 4 seconds. That said, least-connections isn't perfect either: it only sees connection COUNT, not how expensive each connection actually is, so it can still be fooled by, say, one connection that's unusually slow but the server has few others.
Problem 4 · Partitioning trade-off

A social app partitions its user data across 8 database shards by hash(user_id) % 8. A new feature needs to show "the 10 most recent posts from anyone in the world," sorted by time, across all users. Why is this query harder now than it would be with a single, unpartitioned database?

Show solution
Because "anyone in the world" spans all 8 shards, and no single shard has enough information to answer the question alone -- each shard only knows about the posts from the slice of users hashed onto it. The application now has to query all 8 shards for their own top 10 recent posts, then merge and re-sort those 80 results down to the true global top 10 in application code (this pattern is called a "scatter-gather" query). A single unpartitioned database could have answered this with one ORDER BY ... LIMIT 10 query. This is the direct cost of partitioning: queries that only ever touch one shard's data (like "get user X's own posts") stay fast and simple, but queries that need a global view get meaningfully more expensive and complex.
Problem 5 · Vertical first, or horizontal first?

A brand-new startup with 200 total users is deciding how to run their backend. Would you recommend they start with vertical or horizontal scaling? What would make you change that recommendation later?

Show solution
Start vertical: at 200 users, the complexity cost of statelessness, load balancing, and partitioning almost certainly isn't worth paying yet -- a single reasonably-sized server is simpler to build, deploy, and debug, and is very unlikely to hit a hardware ceiling at that scale. Vertical scaling is also easy to reverse or upgrade incrementally as traffic grows. Reasons to revisit that decision later: (1) approaching the practical hardware ceiling (traffic growth suggests they'll need a machine bigger than what's available soon), (2) the business risk of a single point of failure becomes unacceptable (e.g. paying customers, an SLA, real revenue at stake during downtime), or (3) cost -- if they're paying for a huge vertical instance sized for peak traffic that mostly sits idle, several smaller horizontally-scaled machines that can be added or removed with demand may end up cheaper.
