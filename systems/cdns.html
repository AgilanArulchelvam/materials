SYSTEMS FUNDAMENTALS LAB · CDNs

A CDN's entire job is to put a copy of your content physically closer to the person requesting it.

Every network request has a speed-of-light floor — data can only travel so fast, and a round trip from Tokyo to a single origin server in Virginia takes real, unavoidable time no matter how powerful that server is. A Content Delivery Network sidesteps this by keeping copies of content at edge locations scattered around the world, so "closest copy" replaces "the one true copy" for most requests. This lab animates the hit/miss decision an edge node makes on every request, and the origin fallback path when it doesn't already have what's needed.

01 — Distance is the whole problem

What a CDN caches, and why geographic proximity matters

Start here, before any diagrams. Imagine a bakery in New York that ships its famous bread to customers all over the world, one loaf at a time, from a single oven. A customer in Tokyo waits days for that loaf to travel — not because the bakery is slow, but because the physical distance is real and shipping takes time no matter how the bakery organizes its kitchen. The obvious fix: open small satellite kitchens in Tokyo, London, and Sydney that already have a batch of the same bread ready to hand out locally, refreshed periodically from the original recipe. Customers near a satellite kitchen get their bread almost instantly; the original NY oven becomes the backup for anything the satellite kitchens don't have on hand.

A Content Delivery Network (CDN) is that network of satellite kitchens for web content. It consists of many edge servers (also called "points of presence" or PoPs) distributed geographically close to end users, each holding cached copies of content that would otherwise have to be fetched from a single origin server far away. CDNs are especially effective for content that's the same for everyone and doesn't change often: images, videos, CSS/JS bundles, downloadable files — collectively "static" or "static-ish" content. They're a poor fit for content that's different per-request or per-user (a live database query result specific to one logged-in user's dashboard), though modern CDNs increasingly cache dynamic content too, with careful cache-key design.

Interview-ready definition: a CDN is a geographically distributed network of proxy servers (edge servers / PoPs) that cache copies of origin content close to end users, reducing latency by shortening the physical (and network-hop) distance a request has to travel, and reducing load on the origin server since most requests are served from an edge cache without ever reaching it. The core trade-off a CDN makes is trading storage (paying to keep copies in many places) for latency (getting content to users faster) and origin load reduction (protecting the source of truth from being hit by every single request).

Why "physically closer" isn't just a nice-to-have

Network latency has a hard physical floor: light in fiber-optic cable travels at roughly two-thirds the speed of light in a vacuum, and a round trip from, say, Sydney to a server in Virginia covers roughly 16,000 km one-way — tens of milliseconds of unavoidable travel time before the server has even started processing the request, doubled for the round trip. No amount of origin-server optimization removes that floor; the only way to reduce it is to reduce the DISTANCE, which is exactly what placing an edge server in or near Sydney does. This is why CDN performance gains are largest for geographically distant, latency-sensitive traffic, and smallest for traffic that's already close to the origin.

02 — The decision every single request makes

Cache hit vs miss, and the origin fallback

Start here, before the demo. Back at the satellite kitchen: a customer walks in asking for a specific loaf. If that exact loaf is sitting on the shelf, ready to go — that's a cache hit, and the customer is served immediately, no contact with the original NY bakery needed. If it's NOT on the shelf (maybe it's a rare specialty order, or the shelf copy expired and got thrown out), the satellite kitchen has to call the original bakery, get a fresh copy, hand it to the customer, AND keep a copy on the shelf for the next person who asks — that's a cache miss with an origin fallback.

Cache hit

The edge server already has a valid (non-expired) copy of the requested content. It serves the response directly to the user — fast, and the origin server is never contacted for this request at all.

Cache miss

The edge server does NOT have a valid copy (never cached it, or its copy expired). It must forward the request to the origin server, wait for the response, serve it to the user, AND store a copy locally so the next request for the same content is a hit.

Notice the pattern: the FIRST request for any given piece of content is always a miss (nothing to serve yet), which triggers the origin fetch and populates the cache. Every SUBSEQUENT request for that same content, as long as the cached copy hasn't expired, is a hit — served entirely from the edge, without the origin server even being aware the request happened. This is why CDNs dramatically reduce origin load in aggregate: for popular content requested by thousands of nearby users, only the very first request (per edge location, per expiration cycle) ever reaches the origin.

Why edge servers don't cache forever: every cached item has a TTL (time-to-live) after which it's considered stale and must be re-fetched from the origin on the next request, even if the cached bytes are still sitting right there. This exists because origin content DOES change eventually (a new image gets uploaded, a bug fix ships), and without an expiration mechanism, edge servers could serve permanently outdated content forever with no way to know it's wrong. Click "Expire the cached copy" above to see the very next request become a miss again, exactly as if the TTL had naturally elapsed.
Interview-ready definition: a cache hit occurs when an edge server can satisfy a request entirely from its local cached copy, without contacting the origin. A cache miss occurs when the edge server lacks a valid cached copy (either never cached, or expired past its TTL) and must forward the request to the origin server, then cache the response before returning it to the client. The hit ratio (hits / total requests) is the standard metric for CDN effectiveness — a higher hit ratio means less origin load and more requests served at edge-server latency rather than origin-server latency.
03 — "There are only two hard things in computer science"

Cache invalidation as a hard problem

Start here, before the mechanism. The old programmer joke goes: "there are only two hard things in computer science: cache invalidation, naming things, and off-by-one errors." It's funny because it's true — but WHY is invalidation specifically hard? Back at the satellite bakery: suppose the original NY bakery changes its sourdough recipe today. Every satellite kitchen around the world is still happily handing out the OLD recipe's loaves, because nobody told them to throw out their shelf stock. The bakery can shout "new recipe!" as loud as it wants — that message has to physically reach every single satellite kitchen, and until it does, customers everywhere are unknowingly eating stale bread.

Concretely, a CDN has two basic strategies, and both have real costs:

StrategyMechanismThe hard trade-off
TTL-based expiration (passive)Content is simply considered stale after a fixed time, then re-fetched on next requestSet the TTL too long, and stale content lingers after a real update; set it too short, and you lose most of the caching benefit (frequent re-fetches from origin)
Active invalidation (purge)The origin explicitly tells every edge server "throw out your copy of X right now"Requires reaching every single edge location (potentially hundreds worldwide) reliably and near-instantly — a distributed coordination problem, not a local one. A purge request that fails to reach even one edge location leaves that location serving stale content indefinitely, undetected, until its TTL eventually elapses anyway.

This is exactly why cache invalidation is genuinely hard, not just tedious: it's a distributed consistency problem. The origin has one true, current version of the content, but that truth has to propagate to an unknown, geographically scattered set of caches, each of which may be serving stale data to real users for an unpredictable window of time until it catches up — and there's no way to instantaneously and reliably guarantee every copy everywhere updates at once, especially under real-world conditions like network partitions, edge server outages, or purge requests silently failing.

The mechanism behind the difficulty, made concrete: if you have 200 edge locations, an origin update requires 200 separate "please purge this" messages to succeed for the world to be consistent. If even one of those messages is dropped, delayed, or arrives at an edge server that's temporarily unreachable, that ONE location keeps serving the old version — and there's often no built-in mechanism telling the origin "hey, edge #147 never got the memo." Compare this to updating a single database row, which is one atomic operation on one machine — cache invalidation is the same conceptual update, fanned out across many independent machines with no shared transaction wrapping them together.

In practice, teams manage this by combining both strategies: reasonably short TTLs as a safety net (so staleness self-heals within a bounded, known window even if active purging fails silently), plus active purge/invalidation APIs for urgent updates (a security fix, a legal takedown) where waiting for a TTL to elapse isn't acceptable. Some systems also use versioned URLs (e.g. style.v2.css or a content hash in the filename) to sidestep invalidation entirely for immutable assets — since the URL itself changes when the content changes, the old URL's cached copy being "stale forever" is harmless, because nothing references that URL anymore anyway.

Interview-ready definition: cache invalidation is the problem of ensuring that once origin content changes, all cached copies of that content (potentially scattered across many geographically distributed edge servers) stop being served as if they were current — either by expiring on a TTL, or by an explicit purge signal reaching every relevant cache. It is fundamentally hard because it is a distributed consistency problem: propagating a single source-of-truth change to an unbounded, independently-operating set of caches cannot be made instantaneous or perfectly reliable, so real systems accept a bounded staleness window (via TTLs) as a deliberate trade-off rather than pursuing unattainable perfect real-time consistency.

Problem 1 · What belongs on a CDN

A web app serves (a) its compiled JavaScript bundle, (b) a logged-in user's personal notification count, and (c) a marketing video on its homepage. Which of these are good CDN candidates, and which isn't, and why specifically?

Show solution
(a) JavaScript bundle: excellent CDN candidate. It's identical for every user, changes only on deploys (infrequently, and can be versioned via a content hash in the filename), and is requested extremely often -- exactly the profile that benefits most from edge caching. (c) Marketing video: excellent CDN candidate for the same reasons, plus video is large, so the latency and bandwidth savings from serving it from a nearby edge location (rather than one origin server) are especially significant. (b) Notification count: a POOR CDN candidate in its naive form, because it's different for every single user and changes frequently (in real time, potentially) -- caching it at the edge would either require an impractically short TTL (defeating the caching benefit) or risk showing users a stale, wrong count. This kind of per-user, frequently-changing data is usually left uncached or handled with more sophisticated per-user cache-key strategies rather than simple CDN edge caching.
Problem 2 · Hit ratio and origin load

An edge server receives 10,000 requests for the same image over one hour, and the image's TTL is 10 minutes (so it's fetched fresh from origin once per 10-minute window as long as requests keep arriving). Assuming requests are spread evenly across the hour, roughly how many of those 10,000 requests actually reach the origin server?

Show solution
One hour = 60 minutes = 6 windows of 10 minutes each (since the TTL is 10 minutes, the cached copy needs re-fetching once per window, assuming at least one request arrives in each window to trigger the miss). In each 10-minute window, the FIRST request is a miss (triggers an origin fetch and re-populates the cache), and all subsequent requests in that same window are hits. With 6 windows total, that's roughly 6 origin fetches out of 10,000 total requests. Hit ratio = (10,000 - 6) / 10,000 = 99.94% -- the origin server is protected from over 99.9% of the traffic this single popular image generates, which is the core value proposition of a CDN at scale: origin load scales with the NUMBER OF DISTINCT TTL WINDOWS elapsed, not with the number of requests.
Problem 3 · TTL trade-off, concretely

A news site sets a 24-hour TTL on its homepage HTML to maximize cache hit ratio. A breaking news story needs to appear on the homepage within minutes. What goes wrong, and what's the fix that doesn't mean abandoning caching entirely?

Show solution
What goes wrong: with a 24-hour TTL, any edge server that already has a cached copy of the homepage will keep serving the OLD version for up to 24 hours after the breaking news is published on the origin -- readers hitting that edge server won't see the new story until the TTL naturally expires, which could be nearly a full day late for a time-sensitive story. Fix: use active cache invalidation (a purge request) to explicitly tell all edge servers "the homepage has changed, discard your cached copy now" at the moment the breaking story is published, rather than waiting for the 24-hour TTL to elapse naturally. This preserves the caching benefit for the other 23 hours and 55 minutes of normal operation (long TTL = high hit ratio = low origin load) while still allowing near- immediate updates when genuinely needed, at the cost of the added complexity and reliability risk of the purge mechanism itself (as covered in section 3 -- a purge that fails to reach even one edge location leaves that location stale until ITS TTL eventually elapses).
Problem 4 · Versioned URLs as an invalidation dodge

Explain how naming a CSS file app.a1b2c3.css (where a1b2c3 is a hash of the file's contents) instead of just app.css avoids the need for active cache invalidation entirely when the CSS changes.

Show solution
When the CSS content changes, its content hash changes too, which means the FILENAME itself changes (e.g. app.a1b2c3.css becomes app.d4e5f6.css). The HTML page referencing this file is updated to point at the new filename/URL. Because it's a genuinely different URL, there's no "stale cached copy of the SAME URL" problem to solve -- the old URL (app.a1b2c3.css) can be cached with an extremely long or even infinite TTL, since its content by definition can never change (any change would produce a different hash and thus a different URL). Old cached copies under the old URL become irrelevant, not wrong, once nothing links to that URL anymore. This completely sidesteps active invalidation for this asset: instead of telling every edge server "your copy of X is now wrong, discard it," you simply stop referencing the old URL and start referencing a new one that no edge server has seen yet (which is then a normal first-request cache miss, not an invalidation).
Problem 5 · Diagnosing a stale-cache bug report

A company deploys a critical bug fix to their website's JavaScript, purges the CDN cache globally, and confirms the fix works when they test it. Two days later, a small number of users in one specific region report still seeing the old buggy behavior. What's the most likely explanation, tying back to why cache invalidation is described as a "hard" problem rather than just an inconvenient one?

Show solution
Most likely explanation: the global purge request did not actually reach every single edge server -- specifically, the edge location(s) serving that particular region either missed the purge message (network issue, that edge server being temporarily unreachable or under maintenance at the moment the purge was broadcast, etc.) or the purge silently failed there without any visible error to the deploying team. This is exactly the mechanism section 3 describes: a purge isn't one atomic operation, it's a fan-out of many independent messages to many independently-operating machines, and there is often no built-in guarantee (or even visibility) that every single one succeeded. The company's origin and MOST edge locations are consistent and correct, but one location silently diverged -- and it will keep serving the old, buggy JavaScript until either a manual re-purge targets it specifically, or its normal TTL eventually elapses and it re-fetches from origin on its own. This is precisely why relying solely on active purges (with no TTL safety net at all) is risky: an infinite TTL with a failed purge means that stale copy could persist indefinitely with no self-healing mechanism.
