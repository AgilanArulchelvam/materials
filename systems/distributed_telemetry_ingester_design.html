01 — What "ingest telemetry at scale" is actually asking

Requirements gathering

Start here, before any pipeline diagram. Think about the difference between a small-town post office, where the postal worker personally sorts every letter into the right bin as it arrives, versus a regional mail-sorting FACILITY, where trucks dump tens of thousands of pieces of mail per hour onto conveyor belts, and the sorting itself happens downstream, in batches, by machines built for volume — because no single person could sort that fast, and the trucks can't be kept waiting at the loading dock while sorting happens. A tracing SDK emitting spans from one service, going straight into a database, is the postal worker. A distributed telemetry ingester is the regional facility: accept fast, buffer, and let sorting (storage, indexing) happen downstream at whatever pace it can sustain.

The prompt: "Design a distributed ingestion pipeline for traces/spans/metrics at scale." This builds directly on opentelemetry_basics.html's span/trace model — a trace is a tree, a span is a node — so the vocabulary is assumed, not re-taught here.

Functional requirements

  • Ingestion API — services push spans/metrics to the ingester over a well-defined protocol (commonly gRPC or HTTP, per backend/grpc.html and backend/http1_vs_http2.html's trade-offs), without blocking the emitting service's own request path.
  • Durability under burst — a traffic spike (a deploy, an incident causing retry storms) must not drop spans outright or crash the ingester.
  • Sharding by trace ID — all spans belonging to the same trace must eventually be groupable together for a single trace view, per trace_dashboard_practice.html's dashboard needs.
  • Sampling — at scale, storing every single span is often neither affordable nor useful; the system needs a principled way to keep a representative and USEFUL subset.
  • Downstream storage — spans/traces need to be queryable (by trace ID, by service, by time range, by latency) for the dashboards trace_dashboard_practice.html already built, and metrics need to be queryable as time series for latency_and_tracing_integration.html's percentile work.

Non-functional requirements — numbers to pin down out loud

Interview-ready definition: requirements gathering for a telemetry ingester means separating the emitting service's need (ack fast, under 5ms, and never block the caller's actual request) from the pipeline's own needs (durably buffer bursts, shard for queryability, sample to control volume, and route to storage suited for the query pattern) — and confirming concrete numbers (request rate, spans/request, retention) before any capacity math, since ingestion latency and storage volume pull the design in different directions and the numbers decide how hard each pull actually is.
02 — From request rate to storage over a year, step by step

Capacity estimation

Start here, before the math. The whole estimation chain here is one multiplication after another: requests → spans → bytes → bytes/sec → bytes/day → bytes/year, with ONE additional lever (the sampling rate) that can shrink the final number by an order of magnitude or more. Working the chain WITHOUT sampling first, then applying sampling, is what makes sampling's cost impact legible rather than just asserted.

Spans per second

requests_per_sec = 20_000 spans_per_request = 15 spans_per_sec = requests_per_sec * spans_per_request # 300,000 spans/sec # This is the number that decides everything downstream. 300K spans/sec # is squarely "needs a distributed, horizontally-scaled ingestion tier," # not "a single process reading a socket."

Bytes per second, before sampling

# A span: trace_id, span_id, parent_id, service name, operation name, # start/end timestamps, status, a handful of key-value attributes # (per opentelemetry_basics.html's span shape) -- ~500 bytes average, # serialized (protobuf, which OTel uses natively, is compact) avg_span_bytes = 500 raw_bytes_per_sec = spans_per_sec * avg_span_bytes # 300,000 * 500 = 150,000,000 B/sec = 150MB/sec raw_bytes_per_day = raw_bytes_per_sec * 86400 # ~13TB/day # 13TB/day, UNSAMPLED, for 14 days of hot retention alone = ~180TB. # This is the number that makes sampling non-optional, not a nice-to-have # -- storing every span at this volume is a real, large infrastructure # cost, and most of those spans are for requests that were completely # unremarkable (fast, successful, boring).

Bytes per second, after sampling

# A defensible sampling target for a system this size: keep 100% of # traces that are SLOW (p95+) or ERRORED, and a flat 2% of everything # else ("boring" traffic) -- this is a simplification of section 4's # tail-based sampling, previewed here just for the storage math error_or_slow_fraction = 0.03 # ~3% of traces are slow/errored -- keep ALL of these boring_sample_rate = 0.02 # keep 2% of the remaining 97% effective_keep_rate = error_or_slow_fraction + (1 - error_or_slow_fraction) * boring_sample_rate # = 0.03 + 0.97 * 0.02 = 0.0494 -- keep ~5% of all spans sampled_bytes_per_day = raw_bytes_per_day * effective_keep_rate # ~13TB * 0.05 = ~650GB/day hot_storage_14d = sampled_bytes_per_day * 14 # ~9.1TB -- a very different, very buildable number
Read the number, don't just compute it: sampling took hot storage from ~180TB to ~9TB — a 20x reduction — while DELIBERATELY keeping 100% of the traces most likely to matter for debugging (slow, errored). This is the entire argument for tail-based sampling over naive uniform sampling: uniform 5% sampling would have thrown away 95% of the rare error traces along with 95% of the boring ones, exactly the traces an on-call engineer needs most.

Ingestion tier sizing

spans_per_sec = 300_000 # A single ingestion node, doing minimal work (validate, batch, write # to the durable queue) can reasonably sustain ~15,000 spans/sec spans_per_node = 15_000 nodes_needed = spans_per_sec / spans_per_node # = 20 nodes # plus headroom for burst (deploys, retry storms can 3-5x this # instantaneously) -- provision for ~2.5x sustained, so ~50 ingestion # nodes, horizontally scaled behind a load balancer, each stateless
Interview-ready definition: capacity estimation here chains four numbers: spans/sec (300K, from request rate × spans/request), raw bytes/day (~13TB, before any sampling — the number that justifies sampling as a REQUIRED cost control, not optional), sampled bytes/day (~650GB, after a tail-based-style keep rate that preferentially retains slow/errored traces), and ingestion node count (~50, sized with burst headroom, not just sustained average). The 20x reduction from sampling is the single most important number in the whole estimate — it's what turns an unbuildable 180TB hot-storage requirement into a buildable 9TB one.
03 — Accept fast, buffer durably, sort downstream

Architecture

Start here, before the diagram. The whole pipeline is the mail-sorting-facility analogy made literal: an ingestion tier that does almost nothing except accept and batch (the loading dock), a durable queue that survives the ingestion tier or storage tier having a bad day (the conveyor belt with buffer capacity), and a storage tier split by query pattern (the actual sorting, done by machines built for the specific kind of mail).

1 — Ingestion API: batch client-side, ack fast

The SDK on each service does NOT send one network call per span — per section 1's 5ms ack budget, that would be both wasteful and slow. Instead, per latency_and_tracing_integration.html's instrumentation pattern, the SDK buffers spans locally and flushes a BATCH (e.g. every 100 spans or every 1 second, whichever comes first) to the ingestion tier. The ingestion tier's job is deliberately minimal: validate the batch's shape, append it to the durable queue, and ack — no parsing individual spans for content, no sampling decisions, no storage writes on this path. This is exactly why it can hit a 5ms p99 ack: it's doing the least possible work before durability is achieved.

2 — Durable queue, partitioned by trace_id

A Kafka-like append-only log sits between ingestion and everything downstream. Partitioning by trace_id (hash the trace ID to a partition) — not by service name or random round-robin — guarantees every span belonging to the SAME trace lands in the SAME partition, which means a single consumer reading one partition sequentially can assemble a complete trace without needing to coordinate with consumers reading other partitions. This is the load-bearing sharding decision the prompt calls for: it turns "reassemble a trace scattered across arbitrary consumers" into "read one partition in order."

3 — Storage split: time-series vs. columnar

Time-series storeColumnar store
What it holdsAggregated metrics: request counts, latency percentiles, error rates, bucketed by timeFull-fidelity sampled traces: every span, every attribute, individually queryable
Query pattern"p99 latency for service X over the last hour" — range scans over time, pre-aggregated"show me trace abc123" or "show me every trace with a DB span over 500ms" — point lookups and ad-hoc filtering across columns
Why not one store for bothA time-series store is optimized for compact storage of NUMERIC aggregates over time and fast range queries, not for storing structured, high-cardinality span attributes. A columnar store is optimized for the opposite: flexible, ad-hoc filtering across many attribute columns, but is comparatively wasteful for something as simple as "the p99 over the last hour," which the time-series store answers in a pre-aggregated single read. Splitting them lets each be tuned for what it's actually good at, matching database/time_series_schema.html's reasoning for choosing a time-series shape in the first place.
Interview-ready definition: the architecture accepts spans through a thin, stateless ingestion tier that batches and acks fast (meeting the 5ms budget by doing minimal work before durability), buffers them in a durable queue partitioned by trace_id (so trace reassembly never requires cross-partition coordination), and splits storage into a time-series store for aggregated metrics/percentiles and a columnar store for full-fidelity sampled traces — because those two query patterns (range-aggregate vs. ad-hoc point lookup) are different enough that one store optimized for both would do neither well.
04 — The lever that turns an unaffordable system into an affordable one

Sampling strategies: head-based vs. tail-based

Start here, before the trade-off table. Imagine a security guard deciding which cars to search at a checkpoint. A HEAD-based strategy decides at the moment each car arrives, with no information about what's actually in the trunk — e.g. "search every 20th car," a coin flip made before anything is known. A TAIL-based strategy waits until AFTER observing something about the car (it's swerving, the driver seems nervous) and decides based on that — which requires holding every car briefly before deciding, but catches the genuinely suspicious ones a blind 1-in-20 rule would mostly miss.

Head-based samplingTail-based sampling
When the decision is madeAt the START of a trace (often at the root span, before any child spans exist) — e.g. "sample 5% of traces, decided by a coin flip on trace_id"AFTER the full trace has completed — decision can use the trace's actual outcome (errored? slow? which service?)
Cost/complexityCheap and simple — no buffering needed, each service independently applies the same deterministic rule (e.g. hash trace_id, keep if below threshold) and gets a consistent answerRequires buffering ALL spans of a trace somewhere until the trace is judged complete, THEN deciding — real memory/time cost, and "is this trace complete yet" is itself a nontrivial question (per opentelemetry_basics.html's trace-as-a-tree model, a trace is "done" only once its root span closes)
What it's good atUniformly representative sampling of NORMAL traffic — good for overall volume/pattern trendsGuaranteeing you never lose the RARE, high-value traces (errors, outliers) — exactly section 2's 20x storage reduction relied on this
What it's bad atBy construction, samples errors and slow traces at the SAME low rate as everything else — a rare 0.1%-of-traffic bug could be sampled out entirely and never observedMore expensive to run (buffering, decision latency) and adds a processing stage between ingestion and storage

Section 2's estimate used a tail-based-flavored rule (100% of slow/errored, 2% of the rest) precisely because head-based sampling cannot express "always keep the interesting ones" — a coin flip made before the trace exists structurally cannot know whether that trace is about to fail. The realistic production answer, and what most tracing backends actually implement: a HYBRID — a cheap head-based rate as a coarse volume control (so an ingestion tier isn't overwhelmed even before any sampling decision), combined with tail-based logic downstream (in the sampler stage of section 3's diagram) that can still override and retain any trace matching an "interesting" rule, even one head-based sampling would have dropped.

Interview-ready definition: head-based sampling decides whether to keep a trace at its start, cheaply and without needing to buffer anything, but cannot condition on the trace's eventual outcome — so it samples rare, important traces (errors, outliers) at the same low rate as routine traffic. Tail-based sampling decides after the trace completes, which requires buffering the trace's spans until then, but can guarantee errored or slow traces are always kept — directly enabling the large storage reduction section 2 relied on. Production systems typically combine both: a coarse head-based rate to bound ingestion volume, plus tail-based logic downstream to retain anything that later proves interesting.

What to notice: the ingestion tier keeps accepting and acking at its normal fast rate throughout — it never blocks the emitting services, because its only job is to append to the queue, and the queue can absorb a burst far faster than it can be written far beyond what downstream consumers (samplers, storage writers) can keep up with. Consumer LAG grows temporarily and drains back down once the burst passes — that lag, not a dropped span or a slow ingestion ack, is where backpressure actually shows up in this design.
Now defend the design yourself

Practice problems

Work each one out before expanding the solution. Treat these as interviewer follow-ups.

Problem 1 · Justifying trace_id partitioning over round-robin

An interviewer asks: "why not just round-robin spans across queue partitions for better load balancing, instead of partitioning by trace_id?" What's the answer, and what would round-robin break?

Show solution
Round-robin partitioning would break the property section 3's design depends on: that a single consumer reading ONE partition sequentially can assemble a complete trace without coordinating with any other consumer. If spans were round-robined, the 15 spans belonging to one trace (per section 1's average) would be scattered across up to 15 different partitions, and reassembling that trace into the tree opentelemetry_basics.html describes would require EVERY consumer to somehow know about and communicate with every other consumer, or require a separate join/reassembly stage that reads across all partitions -- reintroducing real coordination complexity that trace_id-based partitioning was specifically designed to avoid. The load-balancing concern is real but secondary and solvable a different way: as long as there are meaningfully more distinct trace_ids than partitions (true at 300K spans/sec across many concurrent traces), hashing trace_id to a partition still distributes load roughly evenly across partitions in aggregate, even though any ONE trace's spans all land in the same partition. You get both properties -- even load distribution AND colocated trace spans -- because the unit of partitioning (trace_id) is high-cardinality enough that hashing it still spreads load well; round-robin would only be strictly necessary if trace_id had low cardinality or a skewed distribution, which isn't the case here.
Problem 2 · Reconciling the 5ms ack budget with tail-based sampling's need to see the whole trace

Section 1 requires the ingestion API to ack the emitting service in under 5ms. Section 4's tail-based sampling requires waiting until a trace is COMPLETE (which could be seconds, for a trace with a slow downstream call) before deciding to keep or drop it. Explain why these two requirements don't actually conflict, given section 3's architecture.

Show solution
They don't conflict because they apply to two DIFFERENT points in the pipeline, and section 3's architecture deliberately keeps them decoupled. The 5ms budget applies ONLY to the ack from the ingestion tier back to the emitting service -- i.e. "I have durably received and queued your batch of spans." It says nothing about how long it takes for those spans to be FULLY PROCESSED (sampled, stored, made queryable) downstream. The emitting service's request path is unblocked the moment the ingestion tier acks the batch write to the durable queue -- which, per section 3, is a cheap append operation, achievable well under 5ms because it does essentially no processing. Tail-based sampling happens entirely AFTER that ack, as a downstream consumer (the "Tail Sampler" stage in section 3's diagram) reading from the durable queue at its own pace, buffering spans per trace_id until each trace is judged complete, then deciding keep/drop. This is exactly why the durable queue exists as a separate stage rather than the ingestion tier doing sampling inline: it lets the FAST, latency-critical path (accept and durably queue) be architecturally separate from the SLOW, correctness-critical path (wait for a full trace, then decide). A design that tried to make the ingestion tier itself wait for trace completion before acking would violate the 5ms budget on any trace with a slow span -- which is precisely the case tail-based sampling most wants to observe. Decoupling ack-time from sampling-decision-time is what makes both requirements simultaneously satisfiable.
Problem 3 · Recomputing storage if retention doubles

Compliance now requires 28 days of hot trace retention instead of 14. Using section 2's sampled daily rate (~650GB/day), what's the new hot storage requirement, and does this change any architectural decision from section 3?

Show solution
Straightforward scaling of section 2's number: 650GB/day * 28 days = ~18.2TB, roughly double the original ~9.1TB (exactly what doubling the retention window should do to a roughly constant daily ingest rate). Whether this changes section 3's architecture depends on what "hot" means operationally, which is worth stating explicitly rather than just recomputing the number. At ~9TB, a single well-provisioned columnar store cluster is comfortably sufficient. At ~18TB, it likely still is -- this is not yet the kind of jump (section 2's earlier 180TB unsampled number, for contrast) that forces a fundamentally different storage tier. But it's a reasonable trigger to introduce TIERING within "hot" itself: e.g. the most recent 7 days on faster, more expensive storage (SSD-backed, optimized for the freshest and most frequently queried data -- most trace lookups are for recent incidents), and days 8-28 on a slightly cheaper tier with slightly higher query latency tolerance. This is the same hot/cold tiering instinct enterprise_mcp_agent_gateway_design.html applied to audit logs, now applied within the "hot" retention window itself rather than only at the hot/cold boundary -- a good interview answer recognizes that "double the number" doesn't automatically mean "double the infrastructure," and asks whether the SHAPE of the storage tier itself should change before just provisioning 2x more of the same thing.
Problem 4 · Diagnosing a trace that's missing spans in the dashboard

A user reports that trace_dashboard_practice.html's dashboard shows a trace with only 3 of its expected 15 spans. Using this lab's pipeline (sections 1-4), list at least three distinct points in the pipeline where spans could have been lost or excluded, and how you'd distinguish which one happened.

Show solution
At least three genuinely distinct causes, each diagnosable differently: 1. SAMPLING excluded them intentionally (section 4). If tail-based sampling judged this trace "boring" (fast, no errors) at the 2% keep rate, only a SUBSET of spans might have been retained if sampling were applied per-span rather than per-trace -- which is itself a design bug worth catching: section 4's sampling should be a per-TRACE decision (keep all 15 spans or none), never per-span, precisely to avoid this exact "partial trace" outcome. If spans are missing due to sampling misconfigured as per-span, that's diagnosable by checking whether ANY of the missing spans belonged to error/slow child operations (which a correct per-trace tail sampler would have force-kept). 2. QUEUE partition lag or a consumer failure (section 3). If the tail sampler consumer reading trace_id's partition crashed or fell behind before all 15 spans for this trace had arrived in the queue, it might have judged the trace "complete" prematurely (e.g. on a timeout) and made its keep/drop decision before the remaining spans arrived. This is diagnosable by checking consumer lag metrics and timeout configuration for the sampler stage around the time this trace was emitted. 3. Ingestion tier or client-side batching drop (sections 1, 3). If the emitting service's SDK batches and flushes locally before sending, an ungraceful shutdown or crash of that specific service instance between buffering a span and flushing the batch would lose exactly those unflushed spans -- diagnosable by checking whether the missing spans all originate from ONE particular service instance, and whether that instance had a crash/restart logged around the relevant timestamp. The general diagnostic principle: missing spans that are randomly distributed across services points at sampling (1); missing spans clustered by TIME point at a downstream consumer issue (2); missing spans clustered by SERVICE INSTANCE point at a client-side/ingestion issue (3) -- three different signatures for three different root causes, each requiring a different fix.
