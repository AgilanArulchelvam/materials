01 — Three genuinely different questions, not three names for the same thing

Collecting traces, metrics, and logs at scale

Start here, before any diagrams. Imagine investigating why a specific delivery arrived late. Three completely different kinds of evidence could help, and none of them substitute for each other. A GPS breadcrumb trail of exactly this ONE package's journey — which truck, which route, how long at each stop — tells you what happened to THIS delivery specifically. A dashboard of "average delivery time this week across all packages" tells you whether lateness is a one-off or a systemic trend, but says nothing about any single package. A dispatcher's handwritten log entries ("3:14pm — truck 12 reported a flat tire near the warehouse") capture specific NOTEWORTHY events as they happened, in plain language, without needing to be tied to one specific package's journey or aggregated into a number. Traces, metrics, and logs are exactly this trio, applied to software.

Traces

A trace tracks ONE request's entire path through a distributed system — every service it touched, in order, with timing for each hop. A trace is composed of spans: each span represents one unit of work (one service handling one part of the request), and spans nest to show which work happened inside which other work — a parent span for the overall request, child spans for each downstream call it made. Traces answer: "for THIS specific slow or failed request, exactly where did the time go, or exactly where did it break?"

Metrics

A metric is an aggregated numeric measurement over time — request count per minute, p99 latency, error rate, CPU utilization. A metric deliberately throws away per-request detail in exchange for a cheap, always-available, easy-to-graph-and-alert-on NUMBER. Metrics answer: "is the system healthy right now, and has this specific number been trending in a concerning direction?" — a question no single trace could answer, because a single trace only ever describes ONE request, never the aggregate pattern across millions of them.

Logs

A log is a discrete, timestamped record of one specific event, usually free-text or semi-structured — "user 4471 login failed: invalid password," "cache eviction triggered for key X," "worker pool scaled from 4 to 8." Logs answer: "what specifically happened, in this service, at this moment, in enough narrative detail to understand a one-off event" — the same posture database/audit_trail_schema.html already established for tool calls specifically, generalized here to every service in a distributed system, not just one agent's tool calls.

Traces

Per-request, structured, causally ordered. Answers "where did THIS request's time go." Expensive to store in full for every request at high volume — often sampled.

Metrics

Aggregated, numeric, cheap. Answers "is the system healthy, and what's the trend." Cannot explain any ONE request's specific behavior — it only ever shows the aggregate.

Logs

Per-event, narrative, unstructured or semi-structured. Answers "what specifically happened here." Not inherently tied to one request's full cross-service path the way a trace is.

Why you need all three, not just one: metrics alone tell you error rate spiked at 2:14pm, but not WHICH request or WHY. Traces alone would require capturing full detail on every single request forever to catch a rare failure — prohibitively expensive at real scale, per section 3's storage argument below. Logs alone give you narrative detail about specific events but no structured, causally-ordered path connecting "the database call in service B" to "the API call in service A that triggered it," and no cheap way to see the AGGREGATE trend across millions of requests the way a metric's single number does instantly. Each pillar's weakness is exactly the other two's strength — that's not a coincidence, it's why all three exist as separate, complementary systems rather than one system trying to do all three jobs.

Interview-ready definition: the three pillars of observability are traces (a structured, causally-ordered record of one request's path through a distributed system, composed of nested spans, answering "where did THIS request's time go or break"), metrics (aggregated numeric measurements over time, cheap to store and graph, answering "is the system healthy and what's the trend"), and logs (discrete, timestamped, narrative records of specific events, answering "what exactly happened here, in this service, at this moment"). No single pillar substitutes for the other two — each is optimized for a genuinely different question, and a real observability system needs all three, correlated together (often via a shared trace ID present in the metrics and logs emitted during that trace), not just whichever one was easiest to add first.

03 — Observability data is time-series data, at a volume that punishes naive storage

Storage and query design for observability data

Start here, before the schema. database/time_series_schema.html already established the core shape this section needs: time-series data is write-heavy, append-only, almost always queried by a recent time range, and grows without bound if you never prune it. Traces, metrics, and logs are ALL fundamentally time-series data — every span has a start time, every metric is a value observed AT a point in time, every log line has a timestamp — just at a volume that dwarfs most "normal" time-series workloads like the sensor-reading example that lab used, because a single busy service can emit thousands of spans, metric points, and log lines per SECOND.

This means the retention and downsampling strategy time_series_schema.html built for sensor data applies directly, with the same underlying trade-off: keep full-fidelity raw data for a bounded RECENT window (where debugging value is highest), and age older data into a coarser form rather than deleting it outright or keeping everything forever at full detail.

The sampling point for traces deserves its own emphasis, because it's a decision time-series metric data never has to make: since metrics are ALREADY aggregated at write time, there's no "which requests do we skip" question for a metrics pipeline — the aggregation itself is the compression. But a full, unsampled trace for every single request, kept even briefly, is often the single most expensive part of an observability pipeline's storage bill at real scale — which is why most production tracing systems SAMPLE (keep, say, 1% of normal-latency traces in full detail, while keeping closer to 100% of traces that were slow or errored, since those are disproportionately the ones worth having later).

Interview-ready definition: observability data at scale is fundamentally time-series data — write-heavy, timestamped, almost always queried by a recent time range — and inherits time_series_schema.html's retention/downsampling discipline directly: keep raw, full-fidelity data (individual spans, individual log lines) for a bounded recent window where debugging value is highest, and age it into progressively coarser aggregate forms (or discard it) beyond that window, rather than retaining everything at full detail indefinitely. Traces additionally require a SAMPLING decision at write time — since capturing every span of every request is rarely affordable at real scale — typically biased toward keeping a higher fraction of slow or errored traces, since those are disproportionately the ones a later investigation will actually need.

Problem 1 · Choosing which pillar answers a specific on-call question

An on-call engineer gets paged: "error rate for the agent service jumped from 0.1% to 4% starting at 2:14am." Walk through which pillar (trace, metric, or log) they'd use at each stage of investigating this, in order.

Show solution
Stage 1 -- the PAGE ITSELF is a metric-driven alert: error_rate_percent crossing a threshold is exactly the kind of aggregated, cheap-to-monitor number metrics exist for. No trace or log could have triggered this alert efficiently -- you'd need to aggregate across every individual request to compute a rate, which is precisely what a metric already did for you continuously. Stage 2 -- having been alerted, the engineer needs to find SPECIFIC failing requests to investigate. They'd query traces filtered to errored status within that time window (2:14am onward) -- this narrows from "error rate is elevated" (a percentage, no specifics) down to actual concrete trace_ids they can drill into. Stage 3 -- for ONE specific failing trace, they'd look at its spans to see WHERE in the request it failed (which service, which span), then pull the LOGS emitted by that specific service around that span's timestamp (correlated via trace_id, per section 2's demo) to read the actual narrative detail -- an error message, a stack trace, specific context a span's structured timing data alone wouldn't carry. The pattern: metrics trigger and characterize the alert (something is wrong, in aggregate), traces localize it to specific requests and specific services within those requests, logs explain the SPECIFIC narrative reason once you've narrowed down to where to look. Each stage needs a DIFFERENT pillar because each is answering a different, narrower question than the last.
Problem 2 · Explaining why full-fidelity trace retention for months doesn't scale

Using database/time_series_schema.html's storage-savings reasoning (Problem 2 there), estimate why a service handling 500 requests/second, each generating an average of 8 spans, would make "keep every span at full detail for 6 months" an unreasonable default. Roughly how many spans would that be?

Show solution
500 requests/sec * 8 spans/request = 4,000 spans/second. 4,000 * 60 * 60 * 24 = 345,600,000 spans/day. 345,600,000 * ~182 days (6 months) ≈ 62.9 BILLION spans. Even at a modest few hundred bytes per span (span ID, parent ID, service name, timestamps, a handful of key-value attributes), 63 billion rows is an enormous, expensive-to-query, expensive-to-store dataset -- easily reaching multiple terabytes even with reasonably compact encoding, before accounting for indexing overhead. This is exactly time_series_schema.html's Problem 2 arithmetic (full-year raw sensor data vs. a tiered retention policy) applied at trace-pipeline scale -- except traces are typically MUCH higher volume per unit time than a sensor-reading workload, since every single request across potentially many concurrent users generates its own full set of spans, whereas a sensor emits readings on a comparatively slow, fixed schedule. This is precisely why section 3 argues for BOTH a short raw-retention window (days, not months) AND sampling at write time for traces specifically -- neither retention alone nor sampling alone is doing the full job here; sampling controls the volume that gets written in the first place, and short retention controls how long even the sampled volume sticks around at full detail before aging out or being discarded.
Problem 3 · Diagnosing a system that only implemented metrics

A team's observability setup is metrics-only (no tracing, no structured logs). They can see "p99 latency for the checkout service is 4.2 seconds" but cannot answer "why is THIS specific slow checkout request slow." Using section 1's reasoning, explain precisely why metrics alone cannot answer the second question, even in principle.

Show solution
Metrics are, by construction, AGGREGATED -- the entire point of a metric like p99 latency is that it deliberately discards per-request identity and detail in exchange for a single cheap, always-available number describing the distribution across MANY requests. Once that aggregation has happened, there is no way to recover which specific request(s) contributed to the tail, what path THAT SPECIFIC request took through the system, or which downstream call was actually slow for it -- that information was never retained in the first place, not merely hard to query. This isn't a query-design limitation that a cleverer metrics query could work around; it's a structural property of what a metric IS (an aggregate, not a per-request record) that makes "why was THIS one request slow" fundamentally the wrong kind of question to ask of a metrics-only system. Answering it requires a trace -- a per-request, causally-ordered record of exactly the spans and timing THIS SPECIFIC request generated, which metrics-only systems never captured because they were never designed to answer per-request questions at all. This is exactly section 1's core argument: each pillar is suited to a genuinely different QUESTION, and a system missing one pillar isn't just "missing some nice-to-have data," it's structurally unable to answer the category of question that pillar exists to answer, no matter how the available data is queried.
Problem 4 · Deciding a sampling strategy for a cost-constrained trace pipeline

A team can only afford to store 2% of all trace volume at full detail. Using section 3's sampling reasoning, design a sampling rule that's smarter than a flat "keep a random 2% of everything," and explain what it would miss even so.

Show solution
A smarter rule: sample differently based on the trace's OUTCOME rather than uniformly at random. Keep 100% of traces that errored or exceeded some latency threshold (these are disproportionately the ones worth having when investigating an incident later, per section 3's own reasoning), and sample only a small fraction (perhaps well under 2%, to make room for the always-kept slow/errored traces within the same overall budget) of normal, fast, successful traces, since those are individually much less likely to ever be looked at again. Concretely: if 0.5% of traffic errors or is slow, keeping 100% of THOSE plus a random ~1.5% of the remaining 99.5% normal traffic still lands close to the 2% overall storage budget, while making the traces that actually GET kept far more likely to be useful later than a flat random 2% sample would be -- a flat random sample would, by construction, keep mostly boring, fast, successful traces (since those are the overwhelming majority of traffic) and might easily miss a rare, specific error pattern entirely if it happened to fall outside the random 2% draw. What this smarter rule would still miss: it can't help with an incident type that isn't visible as an ERROR or LATENCY OUTLIER at the trace level -- e.g. a request that "succeeded" (no error, normal latency) but returned subtly WRONG data (a correctness bug rather than a performance/error bug). Since this rule's outcome-based sampling only biases toward errors and slowness, a correctness bug hiding in an otherwise normal-looking trace has the same low chance of being sampled as any other normal trace -- this is a real, remaining gap that outcome-based sampling doesn't close, and is part of why deterministic and model-graded EVALS (deterministic_evals.html, model_graded_evals.html) exist as a separate mechanism for catching correctness issues that observability sampling alone isn't designed to surface.
Problem 5 · Connecting trace_id correlation to trajectory-based evals

Using trajectory_based_evals.html's reasoning about scoring an agent's sequence of tool calls, explain how a trace's spans could serve as the actual DATA SOURCE a trajectory-based eval reads from, rather than the eval needing its own separate instrumentation.

Show solution
trajectory_based_evals.html's score_trajectory function needs exactly the information a trace's spans already capture: which tool/operation was invoked, in what order, with what arguments, and what the outcome was (success, error, retried). If the agent service is instrumented so that every tool call becomes its own SPAN (a child span of the overall request's trace, per section 1's span-nesting model) -- with attributes like tool name, arguments, and result status attached to that span -- then a trajectory-based eval doesn't need to build or maintain any separate logging mechanism at all; it can simply query the trace for that request's trace_id and read the ordered sequence of tool-call spans directly as its trajectory data. This is a genuinely practical convergence, not just a coincidence: the SAME instrumentation that section 2's live demo shows generating spans for observability purposes (debugging a slow or failed request) is ALSO, for free, exactly the raw material a trajectory-based eval needs to score whether the agent's process was correct. A well-instrumented system gets both benefits from one investment; a system that only instruments for observability (spans, but no eval layer reading them) or only for evals (custom trajectory logging, disconnected from the trace pipeline) is duplicating effort that a shared trace-based approach would have avoided. This is exactly why Week 2's roadmap topic ("instrument the Month 4 agent with tracing... verify traces capture tool calls end-to-end") matters beyond pure debugging value -- the same traces double as eval infrastructure.
