A load balancer is the one decision-maker standing between every request and which server actually handles it.

Once you have more than one server, something has to decide, for every single incoming request, exactly which one gets it — and that choice has real consequences: uneven load, wasted capacity, or requests routed to a server that's already dead. This lab builds three real routing algorithms you can watch make that decision live, then adds the failure-detection layer that keeps them from routing into a hole.

01 — The job before the algorithms

What a load balancer does, and why

Start here, before any diagrams. Picture a busy restaurant with one host stand and several servers working the floor. Customers don't get to pick their own server — the host at the front makes that call for every single party that walks in, using some rule: maybe alternating who gets the next table, maybe sending people to whichever server currently has the fewest tables, maybe always sending a specific regular customer to the same server who already knows their order. Take the host away, and customers would have to guess which server is free themselves — some servers would get overwhelmed while others stood idle, and a customer might even walk up to a server who just went home sick.

A load balancer is that host stand, sitting in front of a pool of interchangeable servers. Every incoming request arrives at the load balancer first — never directly at a server — and the load balancer decides, using one of a small number of well-known algorithms, exactly which server actually handles it. This single design choice is what makes horizontal scaling usable: without something making that routing decision, having 10 servers instead of 1 doesn't automatically mean anything gets easier.

Interview-ready definition: a load balancer is a component (hardware appliance, software process, or managed cloud service) that sits between clients and a pool of backend servers, distributing incoming requests across that pool according to a configured algorithm. It typically also performs health checking — continuously verifying which backend servers are actually able to serve traffic — so it only ever routes to servers known to be alive. Load balancers can operate at different layers of the network stack: Layer 4 (transport layer — routes based on IP/port, faster, doesn't inspect request content) or Layer 7 (application layer — routes based on HTTP headers, cookies, or URL path, slower but far more flexible, e.g. routing /api/* to one pool and /static/* to another).

Why this isn't just "spread the load evenly"

It's tempting to assume the goal is simply "give every server the same number of requests" — but that's often the wrong goal entirely. A request that takes 4 seconds to process and a request that takes 4 milliseconds both count as "one request," yet they cost wildly different amounts of server time. The three algorithms in the next section make genuinely different trade-offs about what "balanced" even means, and picking the wrong one for your traffic pattern can leave one server drowning while its neighbors sit idle, even though every server "received its fair share" by request count.

02 — Three different definitions of "fair"

Round-robin vs least-connections vs IP-hash

Start here, before the demo. Back at the restaurant: the host could alternate strictly in order (table 1 gets server A, table 2 gets server B, table 3 gets server A again, regardless of how busy each server currently is) — that's round robin. Or the host could actually glance at the floor and send the next party to whichever server currently has the fewest tables to manage — that's least connections. Or the host could recognize a specific regular customer and always send them to the same server who remembers their usual order — that's IP hash. All three are "fair" by some definition; they just disagree about which one matters.

Round robin

Cycles through servers in a fixed order: 1, 2, 3, 1, 2, 3… Every server gets an equal count of requests over time, regardless of how expensive each one turns out to be.

Least connections

Sends each new request to whichever server currently has the fewest active connections right now. Naturally avoids piling more work onto a server that's already tied up.

IP hash

Hashes the client's IP address to deterministically pick the same server every time that same client connects — trading load evenness for session stickiness.

Round robin — the failure mode of ignoring cost

Round robin's blind spot: it has no idea how expensive a request actually is. If server B happens to receive a request that takes 4 seconds to process while servers A and C keep receiving quick sub-10ms requests, round robin keeps sending B its "fair share" every third request regardless — piling more slow work onto an already-backed-up server, purely because it's B's turn in the rotation.

Least connections — the failure mode it doesn't fully solve

Least connections is a real improvement — it actively avoids sending new work to a server that's visibly tied up — but it only sees connection count, not how expensive each connection actually is. A server holding one unusually slow request looks "less busy" (by count) than a server holding three fast ones, even if the slow request is consuming far more CPU. It's a good heuristic, not a perfect one.

IP hash — trading balance for memory

IP hash deliberately gives up perfect load distribution in exchange for a property neither of the other two algorithms provide: the same client reliably lands on the same server, every time. This matters when a server has built up local, unshared state about that specific client — most commonly a stateful session cache — and losing that stickiness would mean the next request from that client has to start from scratch on a different server, exactly the statelessness problem covered in the vertical-vs-horizontal-scaling lab.

Why this matters: IP hash is often described as "a workaround," and that's basically accurate — the better long-term fix is usually to make servers stateless (moving session data to a shared store, as covered in the statelessness lab) so any algorithm can be used freely. But IP hash remains a genuinely useful stopgap, or a deliberate choice when session affinity has real value (e.g. a WebSocket connection, which needs to stay pinned to one server for its entire lifetime regardless of load-balancing strategy).
The trap in choosing IP hash blindly: IP hash can badly concentrate traffic when many clients share one apparent IP address — for example, an entire office or university behind a single NAT gateway. Every request from that shared IP hashes to the exact same server, so that one server can become badly overloaded while the rest of the pool sits comparatively idle. This is a classic "load balancer looks correctly configured, but real-world traffic breaks the assumption behind it" interview scenario.

03 — Routing decisions are only as good as what you know

Health checks and failover

Start here, before the demo. Going back to the restaurant host one more time: what if a server quietly walked off the floor — sick, or just gone — and the host kept sending new tables their way anyway, because nobody told the host? Every one of those customers would sit down and simply never get served. The host needs some way of actually noticing a server is gone, not just assuming the roster from this morning is still accurate.

A health check is the load balancer periodically asking each backend server some version of "are you still there and working?" — often a lightweight HTTP request to a dedicated endpoint like /health that responds quickly if the server is genuinely able to handle real traffic. If a server fails enough consecutive health checks in a row, the load balancer marks it unhealthy and stops routing new requests to it — this automatic response is called failover. When the server starts passing health checks again, it's added back into rotation.

The tuning trade-off: how fast should failover be?

Health checks run on an interval (e.g. every 5 seconds) and typically require a small number of consecutive failures before declaring a server unhealthy (e.g. 3 in a row) — not just one. This threshold is a deliberate trade-off, not an arbitrary default:

SettingToo aggressive (fails fast)Too lenient (fails slow)
Check intervalWastes server resources on constant health-check trafficSlow to detect a real outage — requests keep failing longer
Failure thresholdA single slow response (a GC pause, a brief network blip) wrongly pulls a healthy server out of rotation — a "flapping" serverA genuinely dead server keeps receiving traffic for longer, and those requests all fail for real users
Why this matters in practice: pulling a server out of rotation too eagerly (on a single missed health check) causes "flapping" — a perfectly fine server gets kicked out over one slow response, then added back, then kicked out again, destabilizing the whole pool's effective capacity. Requiring several consecutive failures absorbs brief hiccups (a garbage-collection pause, one dropped packet) while still catching genuine, sustained outages within a reasonable time. There is no universally correct threshold — it's tuned against how costly a false failover is versus how costly a slow real failover is for that specific service.
Interview-ready definition: a health check is a periodic, lightweight probe (often an HTTP GET to a dedicated endpoint) the load balancer sends to each backend to determine liveness. Failover is the automatic removal of an unhealthy backend from the active routing pool once it fails a configured number of consecutive checks, and its automatic re-addition once it starts passing again. This combination is what allows a load-balanced, horizontally-scaled system to survive individual server failures without manual intervention — directly addressing the single-point-of-failure problem: losing one of N servers now costs roughly 1/N of capacity, not a full outage, precisely because the load balancer stops sending traffic to the dead one almost immediately.

Problem 1 · Picking the right algorithm

A service handles two very different kinds of requests on the same servers: quick sub-5ms API calls, and occasional file-export jobs that take 30+ seconds. Which load-balancing algorithm from this lab handles this mixed workload best, and why do the other two struggle with it specifically?

Show solution
Least connections is the best fit of the three. It actively avoids routing new quick requests to a server that's currently tied up with a 30-second export job, because that server's active-connection count stays visibly elevated for the job's whole duration. Round robin struggles here specifically because it has no concept of request cost -- it will cheerfully route the next quick request to whichever server is "due" in the rotation, even if that server is in the middle of a 30-second export, creating unnecessary queuing delay for a request that should have been instant. IP hash struggles for an unrelated reason: it isn't optimizing for load at all, it's optimizing for session stickiness. Since this mixed workload has nothing to do with client identity, IP hash would route based on client IP regardless of which servers happen to be busy with exports, so a client could easily get pinned to a server that's currently backed up.
Problem 2 · The NAT trap

A company switches their load balancer to IP hash so users stay pinned to the same server for their WebSocket connections. A week later, one server is consistently at 90% CPU while the other three sit around 15%. What likely happened, and what's a fix that keeps the stickiness property?

Show solution
Likely cause: a large number of the company's users are behind a shared NAT gateway (e.g. a big office, university, or corporate VPN) and all appear to the load balancer as the same IP address. IP hash deterministically routes every request from that one apparent IP to the same server, so all of those users -- however many there actually are behind that NAT -- pile onto a single backend, while genuinely distinct IPs spread normally across the other three. A fix that keeps stickiness without this specific failure mode: switch to a stickiness mechanism based on something more granular than raw IP, such as a session cookie the load balancer sets and reads (cookie-based session affinity). This still pins an individual USER's session to one server, but no longer collapses an entire NAT'd population down to a single hash bucket, since the cookie is unique per browser/session rather than shared across everyone behind the same gateway.
Problem 3 · Trace round robin by hand

A pool has 3 servers (A, B, C) behind a round-robin load balancer, currently positioned to send the next request to B. 7 requests arrive back to back. Write out which server handles each of the 7, in order.

Show solution
B, C, A, B, C, A, B Round robin simply continues cycling in fixed order from wherever it left off -- it does not reset or consider load. Starting at B: B, C, A (one full cycle), then B, C, A again (second cycle), then B for the 7th request, picking back up exactly where the cycle would naturally continue.
Problem 4 · Health check threshold tuning

A team sets their load balancer to mark a server unhealthy after just ONE failed health check, checked every 2 seconds. Within a day, they notice servers are being pulled out of rotation and re-added dozens of times, even though no server has actually crashed. Diagnose the problem and propose a fix.

Show solution
This is a classic "flapping" problem caused by an overly aggressive failure threshold. A single missed health check can happen for reasons that have nothing to do with the server being genuinely broken -- a brief garbage-collection pause, one dropped network packet, a momentary CPU spike from an unrelated request. With a threshold of 1, ANY of these transient blips is enough to yank a perfectly healthy server out of the pool, and then it gets added back once the next check succeeds, only to potentially flap again on the next transient blip. Fix: require several consecutive failures (commonly 2-3) before declaring a server unhealthy, not just one. This absorbs brief, harmless hiccups while still detecting genuinely sustained outages within a reasonable time (with checks every 2 seconds and a threshold of 3, a real outage is still caught within about 6 seconds -- a small cost for much more stable routing behavior).
Problem 5 · Layer 4 vs Layer 7 routing decision

A company wants to route all requests to /api/v2/* to a new server pool running updated code, while everything else keeps going to the old pool — as a gradual migration. Can a Layer 4 load balancer do this? Why or why not, and what's needed instead?

Show solution
No, a Layer 4 load balancer cannot do this. Layer 4 operates at the transport layer, making routing decisions based only on IP address and port -- it has no visibility into the HTTP request itself, including the URL path. From a Layer 4 balancer's perspective, a request to /api/v2/foo and a request to /home look identical: both are just TCP packets to the same IP and port. This requires a Layer 7 load balancer, which operates at the application layer and can inspect the actual HTTP request -- reading the URL path (or headers, cookies, etc.) and routing /api/v2/* to the new pool while sending everything else to the old pool. This path-based routing capability is exactly why Layer 7 load balancers, despite being slower than Layer 4 (more data to inspect per request), are the standard choice whenever routing needs to depend on anything about the request's content rather than just where it's addressed to.
