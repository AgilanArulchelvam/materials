SYSTEMS FUNDAMENTALS LAB · STATELESS VS STATEFUL SERVICES

A stateless service could forget you existed between two requests and nothing would break.

The latency & scaling lab mentioned statelessness as one requirement for horizontal scaling to work cleanly — this lab goes deep on that idea specifically: what "state" actually means for a service, why forgetting everything between requests is a feature rather than a bug, and where that memory has to live instead.

stateless: any server can answer any request
stateful: request 2 must land on the same server as request 1

01 — Memory that outlives a single request

What "state" means for a service

Start here, before any code. Picture a coat-check counter versus a self-serve locker room. At a coat-check counter, the same attendant who took your coat has to be the one who gives it back — they're holding your ticket number in their head. In a self-serve locker room, you get a key; ANY employee walking by could let you into locker #14 because the information ("locker 14 is yours") lives on the key itself, not in any one employee's memory.

State, for a service, is any data from a previous request that a later request depends on — and that isn't included in the later request itself. A stateless service keeps no such memory between requests: every request arrives with everything the server needs to fully handle it, and the server retains nothing about it afterward. A stateful service keeps memory in the process itself — an in-memory session, a cached computation tied to one specific connection, a variable that changes based on request history.

# STATEFUL — server remembers who's logged in, in its own memory logged_in_users = {} # lives in THIS process's RAM def handle_login(session_id, user): logged_in_users[session_id] = user # stored HERE, on this one server def handle_request(session_id): user = logged_in_users.get(session_id) # only works if THIS server saw the login # STATELESS — every request carries its own proof of identity def handle_request(request): user = verify_jwt(request.headers["Authorization"]) # self-contained, any server can do this
SAME TWO REQUESTS, TWO ARCHITECTURES
Interview-ready definition: state, in a service context, is any information persisted across requests inside the service's own process or local storage such that a later request's correct handling depends on it. Statelessness means no such server-local persistence exists between requests — each request is self-describing and independently satisfiable — while statefulness means at least one required piece of context is held in server-local memory or storage instead of arriving fresh with each request.
02 — The direct mechanism, not just a rule of thumb

Why stateless services scale horizontally more easily

Start here, before any code. A self-serve locker room can add more staff on a busy day instantly — any new employee can help any customer, because nobody needs to "remember" anything, the locker key already has everything encoded. A coat-check counter can't do that as cleanly: a new attendant who just started their shift has no idea which coat belongs to ticket #42, because that memory lives in the PREVIOUS attendant's head, not on the ticket.

Horizontal scaling (from the latency & scaling lab) means adding more identical server instances and spreading traffic across them with a load balancer. That only works cleanly if any instance can correctly handle any request — which is exactly what statelessness guarantees. If a server holds session data in its own memory, the load balancer either has to force every request from a given user onto that SAME server forever (called "sticky sessions" or "session affinity") — which caps scaling and means one server crashing wipes out every session pinned to it — or requests get routed unpredictably and users get logged out or lose data mid-flow.

ADD/REMOVE SERVERS — WATCH REQUEST ROUTING
StatelessStateful (in-process session)
Load balancingSimple round-robin — any server worksNeeds sticky sessions — a request must revisit its original server
Adding a new server mid-trafficImmediately usable for any requestCan only take NEW sessions — existing ones stay pinned elsewhere

Interview-ready definition: stateless services scale horizontally more easily because request-to-server assignment becomes a pure load-balancing problem with no correctness constraint — any healthy instance can serve any request, so instances can be added, removed, or replaced at any time without coordinating which one "remembers" what. Statefulness introduces an affinity requirement (sticky sessions) that couples specific requests to specific instances, which directly undermines the flexibility horizontal scaling depends on and turns instance failure into data loss instead of a routing non-event.
03 — Statelessness doesn't mean the data vanishes

Where state has to live if the service is stateless

Start here, before any code. A stateless coffee shop cashier doesn't personally remember your loyalty points — but the points still exist, tracked on a card system anyone at the register can look up. Making the CASHIER stateless didn't delete the loyalty program; it just moved that memory somewhere shared and lookup-able by any cashier.

A service being stateless never means the application has no state at all — user sessions, shopping carts, and business data are real and must persist somewhere. It means that memory is pushed out of the application server's own process and into a system built specifically to hold shared state, which every server instance can reach identically.

External session store

Redis / Memcached holding session data by session ID — any app server reads/writes the same shared store, so no server needs its own memory of who's logged in.

Database

Durable business data (orders, user profiles, cart contents) — the actual system of record, queried fresh on every request that needs it.

The client itself

A signed JWT or encrypted cookie carries identity/claims directly in the request — no server-side lookup needed at all for that piece of state.
# the app server itself holds nothing between requests — # it's a stateless computation layer over externally-stored state def handle_add_to_cart(request): user_id = verify_jwt(request.headers["Authorization"]) # state lives in the token redis.rpush(f"cart:{user_id}", request.json["item_id"]) # state lives in Redis return {"status": "ok"} # nothing about this request is remembered by THIS process once it returns
Interview-ready definition: in a stateless architecture, application state is externalized to purpose-built shared stores — a distributed cache or session store (e.g. Redis) for ephemeral session data, a database for durable business data, or the client's own request payload (tokens, cookies) for identity claims — so that every stateless compute instance reads and writes the same shared source of truth rather than keeping any of it in local process memory.
04 — Not every system can be stateless

When stateful is unavoidable — and how it's handled anyway

Start here, before any code. A live phone call can't be "reconnected to any operator" mid-sentence without someone catching up on the conversation first — the connection itself carries irreplaceable in-flight context. Some systems are like that: the state IS the ongoing interaction, not just a record you can look up.

Databases, WebSocket connections, long-running streaming sessions, and some real-time multiplayer or collaborative-editing systems are inherently stateful — the state can't be trivially externalized without losing what makes them fast or even meaningful. The common mitigations: databases embrace statefulness deliberately and add replication/failover instead of trying to be stateless; WebSocket-based systems often use sticky routing plus a fast recovery/reconnect path; and some systems minimize the surface area of what's stateful, keeping only the truly connection-bound piece in memory while pushing everything else (auth, profile data, history) to stateless externalized stores.

SystemWhy it's statefulTypical mitigation
Relational databaseIs the system of record — its entire job is durable, consistent memoryReplication, leader/follower failover, not "made stateless"
WebSocket / live connection serverThe open TCP connection itself is tied to one processSticky routing at the load balancer + fast client reconnect logic
In-memory game/collab sessionReal-time state changes faster than a shared store could keep upShard by session/room, keep session data as the ONLY stateful piece, externalize everything else
Interview framing that matters: the goal is rarely "make literally everything stateless" — it's minimizing what's stateful to the smallest necessary surface, and being deliberate about it. A well-designed system is explicit about exactly which component holds state and why, rather than accidentally accumulating in-memory state in what was supposed to be a disposable, horizontally-scaled compute layer.

Practice problems

Work each one out before expanding the solution.

Problem 1 · Spot the state

An API server stores "requests remaining this minute" per API key in a local Python dictionary to implement rate limiting. Is this service stateless or stateful? What breaks if you add a second server instance behind a load balancer?

Show solution
Stateful — the rate-limit counters live in that one process's local memory, not anywhere externally shared. With two instances behind a load balancer, each server tracks its OWN counter independently. A client could get routed to server A for 50 requests (fine, under the limit there) and server B for another 50 (also fine THERE), totaling 100 requests despite a supposed limit of, say, 60 — the rate limit is silently ~2x too permissive because neither server knows what the other has counted. The fix is externalizing the counter to a shared store like Redis (often using INCR with a TTL) so every instance reads and writes the same count.
Problem 2 · Sticky sessions tradeoff

A team enables sticky sessions (session affinity) on their load balancer instead of externalizing session storage. Traffic is uneven: 80% of active users happen to be pinned to Server 3. What operational problem does this cause that a stateless design wouldn't have?

Show solution
Uneven load distribution that the load balancer CAN'T fix by shifting traffic — sticky sessions force those users to keep hitting Server 3 specifically, regardless of how overloaded it gets, because that's where their session data lives. A stateless design has no such constraint: the load balancer could freely redirect any of those users to a less-loaded server on their very next request, since any server can serve any request identically. Sticky sessions trade scaling flexibility for the convenience of not externalizing session state.
Problem 3 · Where does state go?

You're converting a stateful "shopping cart in server memory" design to a stateless one. List two different valid places the cart data could live instead, and one tradeoff of each.

Show solution
Option 1 — External store (e.g. Redis, keyed by user_id or cart_id): fast, shared across all servers, but adds an external dependency and network hop; if Redis is unavailable, cart operations fail even though the app servers themselves are healthy. Option 2 — Client-side (encoded in a signed cookie or local storage, synced to the server on checkout): removes the server-side dependency entirely for browsing, but has size limits, is harder to update transactionally across multiple tabs/devices, and needs careful signing to prevent tampering with prices or item IDs. Option 3 — Database directly: durable and simple to reason about, but higher latency per cart mutation than an in-memory cache, since it's usually not optimized for the same access pattern.
Problem 4 · Identify the mitigation

A collaborative document-editing service keeps the live, actively-edited document state in the memory of whichever server process is hosting that document's editing session, for speed. What's the risk if that server crashes, and name one mitigation from this lab.

Show solution
Risk: any edits not yet persisted to durable storage are lost when that process crashes, and every client connected to that session gets disconnected simultaneously since the in-memory session state (and likely the live connections themselves) died with the process. Mitigation: this is a case where full statelessness isn't practical (the lab's Section 4) — the realistic approach is minimizing what's stateful (keep only the live edit buffer in memory, periodically flush/checkpoint it to a durable store) plus fast reconnect logic on the client so a crash means "reconnect and replay from the last checkpoint," not permanent data loss. Sharding sessions across servers also limits the blast radius of any single crash to just the sessions hosted on that one instance.
Problem 5 · Stateless vs stateful in an interview scenario

An interviewer asks: "Is a database server stateless or stateful, and does that mean databases can't scale horizontally?" Answer both parts precisely.

Show solution
A database server is inherently stateful — its entire purpose is durable memory of data across requests, which is the opposite of statelessness by definition. This does NOT mean databases can't scale horizontally — it means they scale horizontally using different techniques suited to stateful systems: read replicas (multiple copies serving reads, one primary handling writes), sharding (partitioning data across multiple database instances by key), and consensus/replication protocols to keep copies consistent. It's harder and has more failure modes than scaling a stateless compute layer (no simple "any instance handles any request"), but "stateful" and "can't scale horizontally" are not the same claim — they just require fundamentally different scaling strategies.
