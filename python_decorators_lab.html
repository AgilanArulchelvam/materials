A decorator is just a function that swaps another function out for a wrapped version.

No new syntax magic is happening — @decorator above a function is 100% equivalent to reassigning the function name to whatever the decorator returns. Once that's concrete, decorator factories, functools.wraps, lru_cache, partial, and stacking order all become predictable instead of mysterious.

01 — The mechanism, de-mystified

How a decorator wraps a function

@my_decorator written above def greet(): ... is exactly this, in one line:

greet = my_decorator(greet)

The decorator is just a regular function. It receives the original function as an argument, defines a new inner function (the "wrapper") that does something extra, and returns that wrapper. The name greet in your module now points at the wrapper — the original function still exists, but only the wrapper (which holds a reference to it in its closure) can reach it.

def my_decorator(func): def wrapper(*args, **kwargs): print("before the call") result = func(*args, **kwargs) # the original function, called from inside the closure print("after the call") return result return wrapper @my_decorator def greet(name): return f"Hello, {name}!" greet("Ada") before the call after the call → "Hello, Ada!"
WATCH THE CALL FLOW THROUGH THE WRAPPER
callergreet("Ada")
wrapper (this is what "greet" now IS)print("before the call")
original greet, reached via closurereturn f"Hello, {name}!"
Key insight: after decoration, the name greet no longer refers to the function you wrote — it refers to wrapper. The original function object still exists in memory, kept alive only because wrapper's closure holds a reference to it (this is the same closure mechanism from the scoping lab).
02 — Adding a configuration layer

Decorators with arguments (decorator factory)

A plain decorator takes one argument: the function. If you want @repeat(3) — a decorator that itself takes arguments — you need one more layer: a factory function that takes your config and returns a real decorator.

def repeat(times): # layer 1: the factory — takes YOUR arguments def decorator(func): # layer 2: the real decorator — takes the function def wrapper(*args, **kwargs): # layer 3: the wrapper — takes the call's arguments for _ in range(times): result = func(*args, **kwargs) return result return wrapper return decorator @repeat(3) def wave(): print("👋") wave() 👋 👋 👋

@repeat(3) above def wave() unfolds to wave = repeat(3)(wave) — repeat(3) runs first and returns decorator, then decorator(wave) runs and returns wrapper. times stays alive in wrapper's closure, exactly like the counter example from the closures lab.

THREE LAYERS, THREE DIFFERENT ARGUMENT TYPES
1 · repeat(3) — receives YOUR configcaptures times=3 in a closure, returns decorator
2 · decorator(wave) — receives the FUNCTIONcaptures func=wave, returns wrapper
3 · wrapper(*args, **kwargs) — receives the CALL's argumentsloops range(times), calling func() each time
03 — Fixing an identity problem

functools.wraps and why it matters

The wrapper function is a brand-new function object with its own __name__, __doc__, and other metadata — none of it copied from the original. After decorating, tools that introspect functions (debuggers, help(), documentation generators) see the wrapper's identity, not the real one.

def my_decorator(func): def wrapper(*args, **kwargs): return func(*args, **kwargs) return wrapper @my_decorator def greet(name): """Say hello to someone.""" return f"Hello, {name}!" greet.__name__ → 'wrapper' 😬 lost its real name greet.__doc__ → None 😬 lost its docstring

The fix: decorate the wrapper itself with @functools.wraps(func), which copies __name__, __doc__, __module__, and more from the original onto the wrapper.

from functools import wraps def my_decorator(func): @wraps(func) # copies metadata from func onto wrapper def wrapper(*args, **kwargs): return func(*args, **kwargs) return wrapper greet.__name__ → 'greet' ✓ correct now greet.__doc__ → 'Say hello to someone.' ✓ correct now
WITHOUT vs WITH functools.wraps

✗ without @wraps

greet.__name__'wrapper'
greet.__doc__None
greet.__module__'decorator_module'
help(greet)shows wrapper's signature

✓ with @wraps(func)

greet.__name__'greet'
greet.__doc__'Say hello to someone.'
greet.__module__'__main__'
help(greet)shows greet's real signature
Rule of thumb: every wrapper you write should be decorated with @functools.wraps(func) — it costs one line and prevents confusing bugs in stack traces, docs, and any code that inspects __name__.
04 — A decorator that remembers results

functools.lru_cache

@lru_cache wraps a function so that calls with arguments it's seen before return instantly from a cache instead of recomputing. "LRU" (Least Recently Used) means once the cache is full, the oldest unused entry gets evicted to make room.

from functools import lru_cache @lru_cache(maxsize=3) def slow_square(n): print(f"computing {n}**2...") return n ** 2 slow_square(4) computing 4**2... → 16 (cache MISS — actually ran) slow_square(4) → 16 (cache HIT — no print, instant)
CALL slow_square(n) AND WATCH THE CACHE (maxsize=3)
DetailBehavior
Cache keyBuilt from the function's arguments — must be hashable (no lists/dicts as args)
maxsizeOldest unused entry evicted once full; maxsize=None means unbounded
Great forPure functions (same input always → same output), especially recursive ones like Fibonacci
Bad forFunctions with side effects, or that depend on mutable/changing state
05 — Pre-filling arguments

functools.partial

partial isn't a decorator — it's a factory that takes a function plus some arguments, and returns a new callable with those arguments already locked in. Calling the new callable only requires whatever arguments weren't fixed.

from functools import partial def power(base, exponent): return base ** exponent square = partial(power, exponent=2) # exponent is now permanently 2 cube = partial(power, exponent=3) # a separate, independent callable square(5) → 25 (same as power(5, exponent=2)) cube(5) → 125 (same as power(5, exponent=3))
partial() BUILDS A NEW CALLABLE WITH SOME ARGS FROZEN
frozen inside the partial objectexponent = 2
supplied at call timebase = (whatever you pass)
Try: square(5) → power(5, exponent=2) → 25

This is common for adapting a general function to a specific callback signature — e.g. giving a UI callback a pre-configured handler without writing a whole new def and without losing introspection the way a lambda sometimes does.

06 — Multiple decorators, one function

Stacking decorators — order of application

Stacked decorators apply bottom-up (closest to the function first), but execute top-down at call time. Think of it as wrapping presents: the last box you put on is the first one someone opens.

@decorator_a @decorator_b def func(): ... # exactly equivalent to: func = decorator_a(decorator_b(func)) # ^applied FIRST (closest to func) # ^applied SECOND, wraps the already-wrapped result
@upper THEN @exclaim, STACKED ON shout()
@exclaim @upper def shout(): return "hello"
exclaim wrapper (applied 2nd / outermost — runs FIRST)adds "!"
upper wrapper (applied 1st / innermost — runs SECOND)uppercases result
shout() — the original function — runs LAST (deepest)return "hello"
Build order vs. run order: Python builds the wrapper chain bottom-up when the module loads (upper wraps shout first, then exclaim wraps that result). But when you actually call the decorated function, execution starts at the outermost layer and works inward — so the decorator written closest to def runs its logic last on the way in, first on the way out.

Problem 1 · Basic wrapping
def loud(func): def wrapper(*args, **kwargs): return func(*args, **kwargs).upper() return wrapper @loud def greet(name): return f"hi {name}" print(greet("sam")) print(greet.__name__)
Show solution
HI SAM wrapper greet is called through wrapper, which calls the real greet() then uppercases its result. But greet.__name__ shows 'wrapper', not 'greet' — no functools.wraps was used, so the wrapper's own identity leaked through.
Problem 2 · Decorator factory math
def multiply_result(factor): def decorator(func): def wrapper(*args, **kwargs): return func(*args, **kwargs) * factor return wrapper return decorator @multiply_result(10) def add(a, b): return a + b print(add(2, 3))
Show solution
50 add = multiply_result(10)(add). multiply_result(10) returns decorator with factor=10 captured in its closure. decorator(add) returns wrapper. Calling add(2, 3) runs wrapper, which computes add(2,3)=5, then 5 * factor = 50.
Problem 3 · Missing functools.wraps in practice
def timer(func): def wrapper(*args, **kwargs): print(f"running {func.__name__}") return func(*args, **kwargs) return wrapper @timer def process(): """Process the data.""" return 42 help(process)
Show solution
Help on function wrapper in module __main__: wrapper(*args, **kwargs) help() shows wrapper's own signature and has no docstring — process's real signature "process()" and its docstring "Process the data." are both hidden because timer never used @functools.wraps(func) on wrapper. Note that the print("running process") line still works, because func.__name__ is read from the ORIGINAL func object inside the closure — that's unaffected by wraps. It's process.__name__ (the outer, reassigned name) that's wrong.
Problem 4 · lru_cache with recursion
from functools import lru_cache calls = 0 @lru_cache(maxsize=None) def fib(n): global calls calls += 1 if n < 2: return n return fib(n - 1) + fib(n - 2) fib(10) print(calls)
Show solution
11 Without caching, naive recursive fib(10) would make hundreds of calls (exponential blowup, ~177 calls). With lru_cache, each distinct n from 0 to 10 is computed exactly once and reused for every repeat request — so calls increments exactly 11 times (once per unique n in 0..10).
Problem 5 · partial vs lambda
from functools import partial def greet(greeting, name): return f"{greeting}, {name}!" hello = partial(greet, "Hello") print(hello("Ada")) print(hello.func, hello.args)
Show solution
Hello, Ada! ('Hello',) partial(greet, "Hello") locks in the FIRST positional argument (greeting). hello("Ada") supplies the remaining one (name). partial objects expose .func (the original function) and .args (the frozen positional args) — useful for introspection in a way a lambda wrapping the same logic wouldn't give you as cleanly.
Problem 6 · Stacking order
def bracket(func): def wrapper(*args, **kwargs): return f"[{func(*args, **kwargs)}]" return wrapper def star(func): def wrapper(*args, **kwargs): return f"*{func(*args, **kwargs)}*" return wrapper @bracket @star def word(): return "hi" print(word())
Show solution
[*hi*] word = bracket(star(word)). star is applied first (innermost), so it wraps the raw "hi" into "*hi*" first. bracket is applied second (outermost), so it wraps THAT result: "[*hi*]". Reading top-to-bottom in the source gives you outside-to-inside in the final nesting.
Problem 7 · Combo: factory + wraps + stacking
from functools import wraps def retry(times): def decorator(func): @wraps(func) def wrapper(*args, **kwargs): last_error = None for attempt in range(times): try: return func(*args, **kwargs) except ValueError as e: last_error = e raise last_error return wrapper return decorator attempts = 0 @retry(3) def flaky(): """Fails twice, then succeeds.""" global attempts attempts += 1 if attempts < 3: raise ValueError("not yet") return "success" print(flaky()) print(flaky.__name__)
Show solution
success flaky flaky = retry(3)(flaky). Calling flaky() runs wrapper, which tries func() up to 3 times, catching ValueError each time. attempts goes 1 (fails), 2 (fails), 3 (succeeds) — all within ONE call to flaky() during its retry loop, so it returns "success" on the third internal attempt. flaky.__name__ correctly shows 'flaky', not 'wrapper', because @wraps(func) was applied to wrapper inside decorator.
