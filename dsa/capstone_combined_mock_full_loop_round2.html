ROUND 1 — DSA · FULL LENGTH · 30:00
30:00

Prompt: The eval/tracing dashboard (evals-and-observability/capstone_dashboard_integration.html) needs to render a waterfall view of a run's spans — given a flat list of (span_id, parent_span_id, started_at, duration_ms) records for one trace_id, reconstruct the span TREE (parent_span_id null = root) and compute, for every span, its "self time" — the span's own duration minus the total duration of its direct children (the time spent in that span NOT accounted for by any sub-span). Design the algorithm, state its time complexity, and handle the edge case of a span whose ended_at was never recorded (per backend/capstone_debugging_integration_issues.html's silent-gap bug category).

This is a full round: work through the tree-building step, the self-time computation, a complexity proof, and the missing-ended_at edge case unprompted — not a sketch.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Builds a parent → children adjacency map in one O(n) pass before computing anything, rather than repeatedly scanning the flat list per span
  • Computes self-time via a single bottom-up (or top-down accumulate-and-subtract) traversal, O(n) total, and states why it's not O(n²)
  • Raises the missing-ended_at case UNPROMPTED and proposes a concrete handling (exclude from self-time math with a flagged "incomplete" state, not a crash or a silent zero)
  • Names what a NEGATIVE self-time value would mean (children's total duration exceeds the parent's — a real bug worth surfacing, not silently clamping to zero)
Weak answer
  • Recomputes each span's children by rescanning the full flat list per span (O(n²)) with no adjacency map
  • Never proves or states the complexity, just asserts "should be fast"
  • Missing ended_at either crashes the whole computation or is silently treated as duration 0 with no flag
  • Never considers that self-time could come out negative, or what that would mean
Show reference approach (only after your timer ends AND you've self-graded)
Step 1: one O(n) pass over the flat span list builds a dict from parent_span_id -> list of child span_ids (and a separate dict from span_id -> the span's own record), exactly the adjacency-list representation trees_and_binary_search_trees.html builds from a flat edge list. The root is whichever span has parent_span_id = None, matching eval_span's own schema definition in database/capstone_schema_finalization_and_indexes.html section 1. Step 2: self-time for a span = its own duration_ms minus the SUM of its direct children's duration_ms (not all descendants -- only direct children, since a grandchild's time is already excluded from the child's own self-time separately). Computing this for every span requires, for each span, summing its direct children's durations -- which the adjacency map from step 1 makes O(1) amortized per span (iterate each span's children list once), giving O(n) total across the whole tree, not O(n) per span (which would be the O(n^2) weak answer). No traversal ORDER actually matters here since each span's self-time only depends on its OWN direct children, not on any recursive aggregate from further down -- worth stating explicitly, since it's a genuinely simpler case than a full bottom-up tree DP would suggest at first glance. The missing ended_at edge case (unprompted, per the strong rubric): per capstone_schema_finalization_and_indexes.html section 1, duration_ms is a GENERATED column computed from ended_at - started_at -- a span with no ended_at (exactly backend/capstone_debugging_ integration_issues.html section 4's silent instrumentation-gap bug, here showing up as a data-quality problem for THIS algorithm to handle) has a NULL duration_ms. Silently treating NULL as 0 would make that span's self-time massively NEGATIVE-looking once its children's real durations are subtracted from a zero. The correct handling: exclude spans with NULL duration_ms from self-time computation entirely, mark them "incomplete" in the rendered waterfall, and -- since the row exists but never closed -- this is itself useful DIAGNOSTIC information for the dashboard to surface, not just an error to hide. Negative self-time in general (also unprompted, per the strong rubric): if it occurs on a span WITH a valid duration_ms, it means the children's total reported duration exceeds the parent's -- structurally impossible for correctly-nested spans, and a strong signal of either clock skew between processes recording started_at/ended_at, or an overlapping-siblings bug in the tracing instrumentation itself. This should be surfaced as a data-integrity warning on the dashboard, never silently clamped to zero, since clamping would hide a real instrumentation bug behind a plausible-looking zero.
ROUND 2 — SCHEMA DESIGN · FULL LENGTH · 35:00
35:00

Prompt: The capstone needs a new capability: rate-limiting per client, tracked as "how many agent_runs has this client started in the last 60 seconds." Design the schema addition from scratch, out loud — where does client identity live, what table(s) track the rolling count, what index makes a rate-limit CHECK cheap on every single request, and how would you migrate this into the existing finalized schema (database/capstone_schema_finalization_and_indexes.html) without a write-blocking lock on tables that already hold production data. Then discuss whether this data belongs in Postgres at all, or whether it's actually a better fit for Redis given the access pattern.

This is the full version of a genuinely new schema decision, not a restatement of the existing finalized schema — the round tests whether you can apply the SAME reasoning method (query pattern first, then index; access pattern first, then storage choice) to something you haven't seen designed for you already.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • States the actual query first ("count runs for client X in the last 60s") before proposing any table or index
  • Recognizes this is a HIGH-FREQUENCY, short-lived counter — structurally similar to orchestrator run state, not to durable trace history — and explicitly revisits capstone_orchestrator_integration.html problem 1's Redis-vs-Postgres reasoning to argue for Redis (e.g. a sliding window counter) over a new Postgres table
  • If arguing FOR Postgres, names a real index that would serve the query (composite on client_id + started_at) and acknowledges the write-amplification cost on every single request
  • Proposes a concrete, additive, non-locking migration if Postgres is chosen, per capstone_schema_finalization_and_indexes.html section 3's CREATE INDEX CONCURRENTLY rule
Weak answer
  • Jumps to a new Postgres table with no discussion of the access pattern driving that choice
  • Never revisits the Redis-vs-Postgres reasoning already established elsewhere in the capstone, treating this as an unrelated decision
  • Proposes an index but never names the specific query it serves
  • Migration plan doesn't mention lock behavior on tables with existing data
Show reference approach (only after your timer ends AND you've self-graded)
The query pattern first, stated precisely: "given client_id X, how many agent_run rows were started in the last 60 seconds" -- a SLIDING WINDOW count, checked on every single incoming request (the rate limiter has to run BEFORE the request is allowed to proceed, so this query sits directly on the hot path of every request, not in a background job). That access pattern -- checked on literally every request, needs to be fast, and the underlying data (a rolling 60-second window) is disposable and constantly expiring -- is structurally identical to capstone_orchestrator_integration.html problem 1's argument for Redis over Postgres for run state: high write/read rate, no durability requirement beyond the current window, and a natural expiry. The strong answer applies that SAME reasoning here rather than defaulting to "add a table" out of habit. A concrete Redis-native implementation: a sorted set per client_id, keyed by request timestamp (ZADD on each new run, ZREMRANGEBYSCORE to evict anything older than 60s, ZCARD to get the current count) -- O(log n) per operation, no schema migration needed at all, and no write-blocking lock risk on any existing table. If a candidate argues FOR Postgres instead (a legitimate answer if they want a durable audit trail of rate-limit events, not just live enforcement): the query "count runs for client X since time Y" wants a composite index on (client_id, started_at) -- equality filter on client_id first, range filter on started_at second, exactly the same composite-index-ordering rule capstone_schema_finalization_and_indexes .html section 2 already established for idx_tool_call_name_time. The migration would be a straightforward CREATE TABLE (new, empty, no lock concern) plus CREATE INDEX CONCURRENTLY on the new table's own column, following section 3's "safe to run against a live table" rule -- though since this is a brand new table, CONCURRENTLY isn't strictly required here (only existing, populated tables need it), which is itself worth stating to show the migration-safety reasoning is actually understood, not just pattern-matched. What separates a strong live answer from a merely correct one: recognizing this ISN'T a fresh decision -- it's the SAME decision capstone_orchestrator_integration.html problem 1 already made, now being re-derived for a new feature, and saying so explicitly ("this has the same shape as run state, so I'd make the same call") is exactly the kind of connected reasoning a real interviewer is listening for across a whole loop, not just within one round.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Clarifies requirements and re-derives capacity estimation with real numbers before drawing anything, exactly as thoroughly as it would be done first thing in a fresh loop
  • Separates the three candidate causes (compute, I/O, lock/contention) into DISTINCT, checkable diagnostics rather than one vague "the index is slow"
  • Names a genuinely different fix for each of the three causes, not one generic "add more resources" answer for all three

  • Never connects back to the load-testing lab's own diagnostic framework, re-deriving everything from scratch less rigorously under time pressure
Show reference approach (only after your timer ends AND you've self-graded)
High-level architecture: identical to Round 1's mock reference answer -- FastAPI + orchestrator + MCP tools + hybrid search + eval/tracing dashboard, per this week's own backend/capstone_architecture_ documentation.html worked example. A strong answer draws this correctly and quickly here, since it's now the SECOND time reproducing it -- if it's slower or shakier than Round 1's version was, that's itself useful signal about how well the architecture actually got internalized versus memorized for one specific round. The three-way diagnosis, which is the actual point of this round: COMPUTE bottleneck: the fusion/ranking math (RRF or weighted combination, per hybrid_search.html) itself becomes the limiting factor as query volume rises -- diagnosable by watching CPU utilization on the process hosting the index climb toward saturation WHILE p95 latency rises, with no corresponding rise in I/O wait time. Fix: the fusion computation is typically cheap per-query (bounded by top_k, not corpus size), so a genuine compute bottleneck here more likely means too much work happening PER query (e.g. re-scoring far more candidates than top_k actually needs) -- the fix is tightening the candidate set BEFORE fusion, not adding raw compute. I/O bottleneck: the underlying index storage (disk-backed vector index or inverted index) can't serve lookups fast enough at the current query rate -- diagnosable by disk I/O wait time or, for an in-memory index, whether the corpus has grown past available RAM and started paging. Fix: this is exactly storage-and-rag/capstone_hybrid_search_ integration.html section 2's "where the index lives" trade-off, revisited under load -- an embedded, in-process index that was fine at low query volume may need to move to a separate, horizontally scalable search service once I/O becomes the binding constraint, trading network-hop latency for the ability to add more index replicas. Lock/contention bottleneck: concurrent queries are serializing on a shared resource INSIDE the index implementation itself (e.g. a global read lock around an in-memory data structure that technically allows concurrent reads but is implemented with an overly coarse lock) -- diagnosable by the SAME signature capstone_load_testing.html section 3 gives for the orchestrator's Redis lock: latency growing while CPU and I/O both stay comparatively low, because requests are WAITING, not working. Fix: this is a code-level concurrency bug in the index implementation, not a capacity problem -- profiling exactly where the lock is held and either narrowing its scope or replacing it with a lock-free / reader-writer-lock-friendly data structure fixes it without adding any new infrastructure at all. What separates a strong live answer from a merely correct one: treating "the index is slow under load" as three DIFFERENT hypotheses requiring three DIFFERENT diagnostic signals and three DIFFERENT fixes, rather than one vague diagnosis -- exactly capstone_load_ testing.html section 3's entire point, that different bottlenecks leave different fingerprints and matching the fingerprint to the cause is the actual skill, not guessing "just scale it."

Show reference approach (only after your timer ends AND you've self-graded)
No single "correct" answer by design, but a strong worked example using backend/capstone_debugging_integration_issues.html's own silent instrumentation gap as the source material: "The hardest bug this week was an idempotency fast-path in the orchestrator that returned a cached reply for a retried request WITHOUT calling score_run() -- meaning the response looked completely normal, 200 status, sensible reply, but no eval_result row ever landed for that trace_id. I found it because our smoke test specifically checks the database, not just the response -- exactly the 'assert on the response AND the resulting records' rule from capstone_integration_testing.html -- and it started failing intermittently, only on retried requests. I isolated it by grepping every return statement inside step() and checking whether each one was downstream of the score_run() call or upstream of it -- found the early-return sitting above it. The fix was moving trace initialization to the very top of the function so no future early-return could bypass it. To verify it was the actual root cause and not just a patch: I reproduced the original failure by reverting the fix, confirmed the smoke test failed the same way, reapplied the fix, and confirmed it passed -- not just 'the code looks right now.' Last week's Round 4 asked for a design decision; this week's asks for a bug story — if the second one felt noticeably harder to make specific and concrete, that's a sign the skill trained was "tell this one story well" rather than "generate a specific, honest answer to whatever's actually asked," a meaningfully different and more fragile skill.
