STATION 1 — DSA · 12:00

Prompt: The orchestrator can route a request through multiple tool chains, each with a different estimated latency cost. Given a directed weighted graph of tool-to-tool transitions (edge weight = expected latency in ms), find the CHEAPEST total-latency path from a start tool to a goal tool. All weights are non-negative. State your algorithm, its complexity, and what would break if a weight could be negative.

Builds on dsa/graphs_bfs_dfs.html's traversal foundation, now with weighted edges — the standard shortest-path-with-non-negative-weights problem, applied to routing cost instead of an abstract graph.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Names Dijkstra's algorithm specifically, not BFS (which only works for unweighted or uniform-weight graphs) and not a brute-force path enumeration
  • Describes the mechanism correctly: a min-priority-queue keyed by current best-known distance, greedily finalizing the closest unvisited node each step
  • States complexity correctly with a binary heap: O((V + E) log V)
  • States unprompted why Dijkstra breaks with negative weights (a node can be "finalized" too early, before a cheaper path through a later negative edge is discovered) and names Bellman-Ford as the correct alternative
Weak answer
  • Proposes plain BFS, which only finds the fewest-EDGES path, not the cheapest-WEIGHT path
  • Can't state the priority-queue mechanism precisely, or forgets nodes should only be finalized once
  • Gets the complexity wrong or can't justify it
  • Doesn't know why negative weights break Dijkstra, or names no alternative algorithm
Show reference approach (only after your timer ends AND you've self-graded)
Dijkstra's algorithm is the correct tool here, not BFS -- BFS finds the path with the FEWEST EDGES, which is only equivalent to cheapest-weight when every edge has equal weight. With genuinely different latency costs per edge, BFS can return a path that's "shortest" in hop count but far from cheapest in total latency. Mechanism: maintain a min-priority-queue of (distance, node) pairs, seeded with (0, start). Repeatedly pop the node with the smallest current known distance, and if not already finalized, finalize it and relax all its outgoing edges -- for each neighbor, if distance[current] + edge_weight is less than the neighbor's currently known distance, update it and push the improved (distance, neighbor) pair onto the queue. Stop when the goal node is popped and finalized (or the queue empties). Each node is finalized exactly once, and the greedy choice (always expanding the currently-cheapest frontier node next) is provably correct precisely BECAUSE all weights are non-negative -- a node's distance can never improve after being finalized, since any alternative path would have to go through an already-more-expensive node first. Complexity: with a binary heap for the priority queue, O((V + E) log V) -- each edge can trigger one push/relax (E log V total) and each node is popped and finalized once (V log V total). Why negative weights break it, the key unprompted insight: Dijkstra's correctness relies on finalizing a node the FIRST time it's popped with the current minimum distance, on the assumption no cheaper path could appear later. A negative-weight edge violates this -- a path through a later negative edge could make an already-finalized node's true shortest distance LOWER than what was locked in, but Dijkstra has no mechanism to revisit a finalized node. Bellman-Ford is the correct algorithm for graphs with negative weights (as long as there's no negative CYCLE): it relaxes every edge V-1 times, tolerating the possibility that a shorter path is discovered late, at the cost of worse complexity, O(V * E) instead of O((V + E) log V).

A strong position: AGAINST a full switch to event sourcing for agent_run's status field specifically, in favor of a scoped hybrid -- keep the mutable current-state row (CRUD) for fast reads, and ADD a separate append-only status_transition log alongside it (exactly this week's own audit-trail pattern from Tuesday) rather than replacing CRUD entirely. The cost of full event sourcing here: every read of "what's this run's current status" would require replaying all prior events for that run_id to derive current state (or maintaining a materialized snapshot that's kept in sync, which reintroduces a mutable row anyway) -- for a field checked FREQUENTLY (dashboard polling, the orchestrator's own state machine), this is real added latency and complexity for no benefit, since the current status is exactly the kind of simple, frequently-read field CRUD is well suited for. The genuine benefit event sourcing offers -- a complete history of every transition, useful for debugging "why did this run fail" post hoc -- is achievable WITHOUT paying event sourcing's read-path cost for the whole entity: a separate, append-only status_transition_log table (run_id, old_status, new_status, transitioned_at), written alongside every CRUD update to agent_run.status, gives the same audit value as full event sourcing while keeping current-state reads cheap and simple. The scoped conclusion, which is what separates a strong answer from a merely correct one: event sourcing and CRUD aren't a strict either/or for a whole entity -- the right question is WHICH FIELDS OR CONCERNS actually benefit from an event log (here: the transition history, for debugging) versus which benefit from simple mutable state (here: current status, for fast frequent reads), and applying each pattern where it fits rather than picking one architecture for the entire schema.

Design how you'd serve this efficiently at global scale — where does a CDN fit, what gets cached at the edge versus origin, and how do you handle a documentation update propagating to viewers without a long stale-content window?

Directly reuses systems/cdns.html's territory. Name the specific caching and invalidation mechanism, not just "put it behind a CDN."

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Recognizes this content is an ideal CDN candidate: static, globally distributed readers, infrequent writes — exactly the read-heavy/write-rare profile a CDN edge cache is built for
  • Names a concrete cache-control strategy: long TTL at the edge (since content changes rarely) paired with an explicit invalidation trigger on publish, not just waiting out the TTL
  • Distinguishes edge cache invalidation (a push, on-demand purge of the specific changed asset) from a naive short-TTL-everywhere approach, which would sacrifice cache hit rate for freshness it doesn't usually need
  • Names origin's role explicitly: source of truth, only hit on a cache miss or post-purge, not on every request
Weak answer
  • Says "put it behind a CDN" with no cache-control specifics
  • Proposes a short TTL everywhere to stay safe, without recognizing the hit-rate cost for content that changes rarely
  • No invalidation mechanism named for handling an actual content update
  • Doesn't distinguish edge cache from origin at all
Show reference approach (only after your timer ends AND you've self-graded)
This content is close to an ideal CDN use case: static (no per-request computation needed), read by a globally distributed audience, changes infrequently -- exactly the profile cdns.html identifies as the strongest fit for edge caching, versus dynamic, personalized, or frequently-changing content that benefits far less. Cache-control strategy: a LONG TTL at the edge (hours to a day, since documentation updates are infrequent and don't need second-level freshness) rather than a short TTL that would force frequent origin re-fetches for content that rarely changes -- a short TTL here would sacrifice cache hit rate (more origin trips, more latency for readers far from origin) for a freshness guarantee nobody actually needs at that granularity. The invalidation mechanism that makes a long TTL safe: an explicit PURGE triggered on publish -- when the documentation is updated, the publish pipeline issues a cache invalidation request to the CDN for that specific asset's path, forcing the next request to bypass the stale edge copy and re-fetch from origin, rather than waiting out the long TTL. This is the standard "long TTL + active purge on write" pattern that gets both high cache hit rate (99%+ of the time, nothing changed, so serve from edge) AND fast propagation on the rare occasions something does change, without the two goals fighting each other the way a short-TTL-only strategy would. Origin's role, stated explicitly: origin is hit only on an edge cache MISS (first request after a purge, or a request from a region with no warm edge cache yet) -- it is the source of truth but not on the hot path for the vast majority of requests, exactly the "origin serves cache misses, not every request" principle systems/cdns.html establishes and this week's earlier Postgres-vs-cache stations have reinforced in different contexts.

Prompt: The capstone's database layer wraps every transaction in a context manager for automatic commit/rollback. Explain exactly what Python calls on a context manager object, in what order, including what happens on the happy path versus when an exception is raised inside the with block.

Directly reuses python/context_managers.html's territory. Cold — name the actual dunder methods and their exact contract, not just "with handles cleanup."

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Names __enter__ and __exit__ specifically, and states __enter__'s return value is what gets bound to the as variable
  • States __exit__'s exact signature: it receives exception type, value, and traceback (all None on the happy path)
  • States the return-value contract precisely: if __exit__ returns a truthy value, the exception is SUPPRESSED; if falsy (including implicit None), the exception propagates normally after __exit__ runs
  • Applies this to the transaction case: __exit__ commits on the happy path (exc_type is None) and rolls back when an exception occurred, then typically returns falsy so the original error still propagates to the caller
Weak answer
  • Says "with calls enter and exit" without naming the actual dunder methods or their signatures
  • Doesn't know __exit__ receives exception info, or can't state what happens if no exception occurred
  • Doesn't know the return-value-suppresses-exception contract, or gets it backwards
  • Can't connect the mechanism to the concrete commit/rollback behavior asked about
Show reference approach (only after your timer ends AND you've self-graded)
A context manager implements two dunder methods: __enter__(self) and __exit__(self, exc_type, exc_value, traceback). On entering a `with obj() as x:` block, Python calls obj.__enter__(), and whatever it RETURNS is bound to `x` -- __enter__'s return value is what the `as` clause captures, not the context manager object itself (though they're often the same object, by convention). On leaving the block -- whether normally or via an exception -- Python calls obj.__exit__(exc_type, exc_value, traceback). On the HAPPY PATH (no exception raised inside the block), all three arguments are None. If an exception WAS raised inside the block, those three arguments carry the actual exception's type, instance, and traceback, giving __exit__ full visibility into what went wrong before deciding what to do about it. The return-value contract, precisely: if __exit__ returns a truthy value, Python treats the exception as HANDLED and SUPPRESSES it -- execution continues after the with block as if nothing happened. If __exit__ returns a falsy value (including the implicit None from a function with no explicit return), the original exception PROPAGATES normally after __exit__ finishes running. This is a commonly missed detail: forgetting to explicitly return False (or nothing) in a custom __exit__ is fine, but explicitly and accidentally returning True would silently swallow every exception raised inside the block, which is almost never the intended behavior for cleanup code. Applied to the transaction case asked about: __enter__ starts the transaction (e.g. BEGIN) and typically returns the connection or cursor. __exit__ checks exc_type -- if it's None (happy path), issue COMMIT; if it's not None (an exception occurred inside the block), issue ROLLBACK instead. Critically, __exit__ then returns falsy (or nothing), so the ORIGINAL exception still propagates to the caller after rollback completes -- the context manager cleans up the transaction state but does not swallow the actual error, which the caller still needs to see and handle.
