Prompt: The eval dashboard needs to continuously track the K slowest tool calls seen so far, as a live stream of (tool_name, latency_ms) pairs arrives (potentially millions of calls, K is small, e.g. 20). Design a data structure and algorithm that maintains this top-K set with O(log K) insertion per new call, without ever storing all seen calls.

This is dsa/heaps_from_scratch.html's territory, applied to a streaming top-K problem — a heap of BOUNDED size, not the unbounded heap the dedicated lab builds from scratch. State which heap type (min or max) and why.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Picks a MIN-heap of bounded size K, not a max-heap — and can explain precisely why (the min-heap's root is the SMALLEST of the current top-K, making it the correct comparison point to decide whether a new element belongs)
  • States the algorithm: if the heap has fewer than K elements, push the new call. Otherwise, compare the new call's latency to the heap's root (current minimum of the top-K); if larger, pop the root and push the new call
  • States complexity precisely: O(log K) per call (bounded by K, not by total stream size N), O(K) space total — never O(N) for either
  • Names the follow-up unprompted: retrieving the current top-K in SORTED order requires draining/sorting the heap, O(K log K), a separate cost from maintaining it
Weak answer
  • Picks a max-heap, or can't clearly justify the min-heap choice
  • Proposes storing all N calls and sorting/selecting the top-K at the end, which violates the "never store all seen calls" constraint
  • States complexity in terms of N (total stream size) instead of K (the bounded heap size)
  • Doesn't distinguish "maintaining the top-K set" from "retrieving it in sorted order" as separate costs
Show reference approach (only after your timer ends AND you've self-graded)
A MIN-heap bounded to size K is the correct structure -- the counterintuitive part worth stating explicitly: to track the K SLOWEST (largest latency) calls, you use a MIN-heap, not a max-heap, because the heap's ROOT needs to be the smallest value currently in your top-K set, so you can cheaply compare each new arrival against "the weakest member of the current top-K" and decide whether it displaces it. A max-heap's root would be the LARGEST of the top-K, which tells you nothing useful about whether a new, smaller-than-max call still belongs in the set. Algorithm: for each incoming (tool_name, latency_ms), if the heap has fewer than K elements, push it unconditionally (still building up to K). Once the heap has exactly K elements, compare the new call's latency to the heap's root (the current minimum of the top-K): if the new latency is LARGER than the root, pop the root and push the new call (it displaces the current weakest member of the top-K); if smaller or equal, discard the new call without touching the heap at all -- it doesn't belong in the top-K. Complexity: each push or pop on a heap of size K costs O(log K) -- critically, this is bounded by K, the small constant, NOT by N, the total stream length, which is exactly what makes this approach scale to a "potentially millions of calls" stream: total space used is O(K) at all times, regardless of how many calls have streamed through, and per-call cost never grows as the stream grows. The unprompted follow-up, worth naming: the heap itself is NOT sorted internally (only the root is guaranteed to be the minimum) -- retrieving the current top-K AS A SORTED LIST requires either draining the heap via repeated pop (destroying it, O(K log K)) or copying and sorting a snapshot (also O(K log K)), which is a separate, occasional cost distinct from the O(log K) per-call maintenance cost, and shouldn't be conflated with it when stating overall complexity.

Prompt: The eval_result table has grown past what a single Postgres instance comfortably serves. Propose a sharding key for horizontally partitioning this table, and defend your choice against the two most common queries: "get all results for run X" and "get the average score for tool Y over the last week across all runs."

Directly reuses database/sharding_and_partitioning.html's territory. A sharding key that serves one query well can make another expensive — name that trade-off explicitly.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Proposes sharding by run_id (or a hash of it) and explains it keeps "all results for run X" a SINGLE-SHARD query — the common, hot-path case
  • Explicitly names the cost: "average score for tool Y over the last week across ALL runs" now becomes a SCATTER-GATHER query across every shard, since results for tool Y are spread across many different run_ids
  • Proposes a mitigation for the scatter-gather cost: a separate, periodically-refreshed rollup/aggregate table (not sharded the same way, or replicated) that pre-computes per-tool aggregates, so the expensive cross-shard query becomes rare rather than eliminated entirely
  • States why sharding by tool_name instead would be worse: it would make "all results for run X" (a run touches MANY tools) the expensive scatter-gather query instead, and that query is likely far more frequent (looked up per run, constantly) than the aggregate one
Weak answer
  • Picks a sharding key with no analysis of which query it helps or hurts
  • Doesn't recognize that ANY sharding key makes at least one access pattern cross-shard
  • No mitigation proposed for the query that becomes expensive under the chosen key
  • Doesn't compare the chosen key against the alternative to justify why it's the better trade-off
Show reference approach (only after your timer ends AND you've self-graded)
Shard by run_id (or a hash of run_id for even distribution across shards) -- this is the right default because "get all results for run X" is almost certainly the HOTTER, more frequent query (checked every time a run's results are viewed, likely on the orchestrator's own hot path per this week's earlier stations) and sharding by run_id makes it a single-shard lookup: every eval_result row for a given run lives on exactly one shard, determined by hashing run_id. The explicit cost: "average score for tool Y over the last week across ALL runs" now touches every shard, since results for tool Y are scattered across however many different run_ids happened to produce them, hashed to different shards essentially at random. This becomes a SCATTER-GATHER query -- fan out to every shard, run a partial aggregate on each, then combine the partial results -- which is materially more expensive and more operationally complex than a single-shard query, exactly sharding_and_partitioning.html's own warning that a sharding key is a trade-off, not a free win. Mitigation: rather than accepting scatter-gather on every dashboard load for per-tool aggregates, maintain a separate, periodically refreshed rollup table (tool_name, week_bucket, avg_score, call_count) computed by a background job that DOES do the scatter-gather, but only once per refresh interval rather than once per dashboard view -- the same "precompute the expensive aggregate, don't recompute it live on every read" instinct Monday's caching station already established, now applied at the sharding layer instead of the caching layer. Why sharding by tool_name would be the worse choice: it would flip which query is cheap and which is expensive. "All results for run X" would become the scatter-gather query, since a single run typically invokes MANY different tools, each potentially on a different shard -- and that query is checked far more often (per run view) than the per-tool aggregate is (per dashboard summary load), making tool_name a worse sharding key for this specific access-pattern mix even though it might look equally reasonable in the abstract.
STATION 3 — SYSTEM DESIGN · 14:00
14:00

Prompt: The eval/tracing dashboard's read load has grown to the point where dashboard queries are competing with the orchestrator's own writes on the primary Postgres instance. Design a read-replica setup to relieve this: what replicates, how does replication lag affect dashboard correctness, and how would you detect a replica falling dangerously far behind?

Directly reuses systems/replication.html and database/read_replicas_and_dashboard_caching.html's territory. Name the specific lag-detection mechanism, not just "add replicas."

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Proposes async streaming replication: primary handles all writes, one or more replicas continuously apply the write-ahead log and serve dashboard reads
  • Names the correctness implication explicitly: replicas are EVENTUALLY consistent, not immediately — a dashboard read right after a write could miss that write if it lands on a lagging replica, and this is acceptable ONLY because dashboard reads already tolerate staleness (tied back to Monday's caching discussion)
  • Proposes a concrete lag-detection mechanism: comparing replica's replayed WAL position (or a last-applied-timestamp) against the primary's current position, alerting when the gap exceeds a threshold
  • States what to do about a badly lagging replica: route reads away from it (remove from the read pool) rather than serving increasingly stale data silently
Weak answer
  • Says "add read replicas" with no mechanism for how replication actually works
  • Doesn't mention eventual consistency or any correctness implication of replica lag at all
  • No concrete lag-detection method proposed
  • No response defined for what happens when a replica IS found to be lagging badly
Show reference approach (only after your timer ends AND you've self-graded)
Async streaming replication is the standard fit: the primary handles every write (orchestrator inserts, updates) and continuously streams its write-ahead log to one or more replicas, which replay it to stay in sync. The dashboard's read queries get routed to a replica instead of the primary, freeing the primary to focus on write throughput -- exactly read_replicas_and_dashboard_caching.html's own architecture. The correctness implication, stated explicitly because it's the part most often glossed over: async replication means replicas are EVENTUALLY consistent, not synchronously consistent with the primary -- there's a real window (typically milliseconds, but unbounded in the worst case under load) where a write has committed on the primary but hasn't yet been replayed on a given replica. A dashboard read hitting that replica immediately after the write could miss it entirely. This is acceptable specifically because dashboard reads were already established (Monday's caching station) to tolerate staleness -- the same underlying trade-off, now showing up at the replication layer instead of the cache layer. Lag detection, concretely: Postgres exposes each replica's replay position (how far it's gotten through the WAL) which can be compared against the primary's current WAL position -- the difference, typically reported as either a byte offset or converted to a time estimate, IS the replication lag. A monitoring job periodically checks this gap against a threshold (e.g. 5 seconds of lag) and alerts when exceeded, the same threshold-and-alert pattern this week's earlier system-design stations (Monday's caching TTL, Tuesday's least-connections) keep reusing in different contexts. Response to a badly lagging replica: remove it from the active read pool (stop routing dashboard queries to it) until it catches up, rather than silently continuing to serve increasingly stale data -- serving SOME requests from the primary temporarily (accepting the extra write-contention cost) is a better trade than serving dashboard users data that's, say, ten minutes stale without any indication of it.

Prompt: The capstone wraps every tool-call function with a @retry_on_timeout decorator. Explain exactly what happens, mechanically, when Python parses and executes a decorated function definition — including why a decorator that forgets functools.wraps silently breaks introspection.

Directly reuses python/decorators.html's territory. Cold — trace the actual mechanism, not just "decorators wrap functions."

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • States the desugaring precisely: @decorator def f(): ... is exactly equivalent to defining f normally, then rebinding the name f to decorator(f) — the decorator runs at DEFINITION time, not call time
  • Explains that the decorator typically returns a new wrapper function that closes over the original, and it's THAT wrapper which the name f now refers to everywhere
  • States precisely what breaks without functools.wraps: the wrapper function has its OWN __name__, __doc__, and signature, distinct from the original — introspection tools, debuggers, and help() now see the wrapper's generic identity instead of the original function's
  • functools.wraps's actual mechanism: it copies the original function's metadata (__name__, __doc__, __module__, etc.) onto the wrapper, so introspection sees through the wrapping
Weak answer
  • Says "a decorator wraps a function" without the precise definition-time rebinding mechanism
  • Doesn't know decorators run at DEFINITION time, not call time
  • Can't explain specifically what functools.wraps fixes, or what breaks without it
  • No mention of __name__/__doc__ or introspection at all
Show reference approach (only after your timer ends AND you've self-graded)
The exact desugaring: writing @retry_on_timeout def call_tool(): ... is precisely equivalent to: def call_tool(): ... call_tool = retry_on_timeout(call_tool) This runs at MODULE IMPORT / DEFINITION time, not when call_tool is later invoked -- the decorator function (retry_on_timeout) is called exactly once, immediately after the original function object is created, and whatever it RETURNS is what the name `call_tool` gets rebound to from that point forward. Every subsequent call to call_tool() is actually calling whatever retry_on_timeout returned, not the original function body directly (unless the decorator happens to return the original unchanged, which a retry decorator would not -- it needs to return a wrapper that adds retry logic around the original call). Concretely, retry_on_timeout typically looks like: def retry_on_timeout(fn): def wrapper(*args, **kwargs): # retry logic, then eventually: return fn(*args, **kwargs) return wrapper The returned `wrapper` closes over the original `fn` via a closure, and it's THIS wrapper function object that `call_tool` now refers to everywhere in the codebase. What breaks without functools.wraps: `wrapper` is a genuinely different function object from the original -- it has its OWN __name__ (literally the string "wrapper"), its own __doc__ (None, since wrapper has no docstring), and its own signature. Anything that introspects call_tool after decoration -- help(call_tool), call_tool.__name__, a debugger showing the function's identity, or automatic API documentation generation -- now sees "wrapper" instead of "call_tool", which is confusing and can break tooling that relies on accurate function metadata (e.g. a framework that registers routes or tools by inspecting __name__). functools.wraps(fn) applied inside the decorator (as @functools.wraps(fn) on the wrapper definition) copies fn's __name__, __doc__, __module__, and a few other metadata attributes onto wrapper after it's defined, so introspection sees through the wrapping and reports the ORIGINAL function's identity, even though the actual object being called is still the wrapper with its added retry logic.
