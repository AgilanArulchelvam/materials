STATION 1 — DSA · 15:00
15:00

Prompt: The eval dashboard needs to flag pairs of tool calls whose combined latency exceeds a per-run budget. Given an array of tool-call latencies (in ms) for one run and a target budget, determine whether ANY two distinct calls sum to exactly the budget — and if the interviewer pushes further, return the actual pair. Then generalize: what changes if you need ALL such pairs, not just one?

This is the classic two-sum shape, applied to a run-latency-budget framing instead of an abstract array. State the brute-force approach first, then the hash-map optimization, with complexity for both.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • States the brute-force O(n²) approach briefly, then moves to the O(n) hash-map approach without being prompted to optimize
  • Correctly handles the single-pass hash-map trick: check for budget - current in the map BEFORE inserting current, avoiding using the same element twice
  • Extends cleanly to "all pairs" and states the complexity change (still O(n) with a multi-value map, or O(n log n) if pairs must be returned in sorted order)
  • Names the edge case of duplicate latencies explicitly (two calls with the identical latency value summing to the budget)
Weak answer
  • Only produces the O(n²) nested-loop approach and doesn't reach for a hash map unprompted
  • Inserts into the map before checking, risking counting one element against itself
  • Can't articulate the change needed to return ALL pairs, not just one
  • Never mentions the duplicate-value edge case
Show reference approach (only after your timer ends AND you've self-graded)
Brute force: for every pair (i, j) with i < j, check whether latencies[i] + latencies[j] == budget -- O(n^2) time, O(1) space. Fine to state first as a baseline, but should not be the final answer. Hash-map approach, O(n) time, O(n) space: iterate once, maintaining a set of latencies seen so far. At each element x, check whether (budget - x) is already in the set -- if so, that's a valid pair, found in O(1) average lookup. Only AFTER checking, insert x into the set. Checking before inserting is what prevents a single element from being paired with itself when budget happens to equal 2x for some x in the array. Generalizing to ALL pairs: instead of a set, use a dict from latency value -> count of occurrences seen so far. At each x, if (budget - x) is in the dict, emit count[(budget - x)] pairs ending at this index, then increment count[x]. Still O(n) time overall (each element processed once), O(n) space for the dict. If pairs must be returned in a specific SORTED order, an O(n log n) sort of the final pair list is a small additional cost layered on top, not a change to the core algorithm. Duplicate-value edge case: if two DIFFERENT calls both have latency 250ms and budget is 500ms, they form a valid pair -- the count-based dict approach above handles this correctly (each occurrence is tracked separately), whereas a plain set-based existence check for the "all pairs" variant would silently under-count or mishandle this case, which is exactly why the strong answer upgrades from a set to a count map once the problem generalizes past "any one pair."
STATION 2 — SCHEMA DESIGN · 12:00
12:00

Prompt: Model a schema for storing multi-turn conversation history for the capstone's agent: each conversation has an ordered sequence of messages, each message has a role (user/assistant/tool), content, and a timestamp, and you need to efficiently answer "give me the full ordered message history for conversation X" and "how many conversations has this user had in the last 7 days." Sketch tables, keys, and the normal form you're targeting.

Directly reuses database/conversation_history_schema.html's territory — the point today is producing the standard shape cleanly and explaining your indexing choices, not inventing something novel.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Two tables: conversations (conversation_id PK, user_id FK, started_at) and messages (message_id PK, conversation_id FK, sequence_number or created_at, role, content)
  • Names the index that makes "full ordered history for conversation X" a cheap indexed range scan: composite on (conversation_id, sequence_number)
  • Names a second index or query plan for "conversations per user in last 7 days": composite on (user_id, started_at)
  • States 3NF explicitly and explains why role/content live on the message row, not a separate lookup table (no redundancy to normalize away)
Weak answer
  • Puts all messages in one JSON blob column on the conversation row, making per-message queries impossible without full deserialization
  • No explicit ordering column, relying on insertion order or timestamp granularity that could collide
  • Never proposes an index for either stated query
  • Can't state which normal form the design targets or why
Show reference approach (only after your timer ends AND you've self-graded)
Two tables, 3NF: `conversations` (conversation_id PK, user_id FK, started_at, status) and `messages` (message_id PK, conversation_id FK, sequence_number, role, content, created_at). An explicit sequence_number column beats relying on created_at alone, since two messages could share a timestamp at millisecond granularity under load -- exactly conversation_history_schema.html's own reasoning for an explicit ordering column over implicit insertion order. Query 1 ("full ordered history for conversation X") wants a composite index on (conversation_id, sequence_number) -- equality filter on conversation_id, range/order on sequence_number, giving a single indexed range scan instead of a full table scan plus sort. Query 2 ("conversations per user in last 7 days") wants a composite index on (user_id, started_at) on the conversations table -- equality on user_id, range on started_at, the same "equality-column-first, range-column-second" composite-index ordering rule this repo's indexing labs establish repeatedly. Why 3NF here: role and content are attributes of the MESSAGE itself, not of some separable entity referenced by multiple messages -- there's no redundancy to normalize away by pulling them into a lookup table, unlike, say, a `tool_name` that genuinely repeats across many rows and might warrant its own table if it grows attributes of its own (description, owner). Correctly recognizing when NOT to over-normalize is as much the skill as recognizing when to normalize.
STATION 3 — SYSTEM DESIGN · 18:00
18:00

Prompt: Sketch, at a high level, how you'd add a caching layer in front of the capstone's eval/tracing dashboard so repeated dashboard loads for the same time window don't re-run expensive aggregation queries against Postgres every time. Cover what gets cached, the cache key shape, invalidation strategy, and where the cache physically lives.

Directly reuses systems/caching_layer_design.html and database/read_replicas_and_dashboard_caching.html's territory. Name the 3-4 right components and their responsibilities — full capacity estimation isn't the point today.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • States the cache key precisely (e.g. hash of query params: time window, filters, aggregation type) rather than "cache the response"
  • Picks a cache location (Redis, in-process LRU, or a CDN edge cache) and justifies it against the read pattern (many readers, one underlying query)
  • Names a concrete invalidation strategy: TTL-based expiry for a rolling time window is a legitimate default, explicitly justified rather than assumed
  • Identifies the staleness trade-off explicitly: dashboard data can tolerate being slightly stale (unlike, say, an account balance), which is WHY caching is acceptable here
Weak answer
  • Says "add a cache" with no key shape, no location, no invalidation policy
  • Picks a cache location with no justification tied to the actual read/write pattern
  • No invalidation strategy stated, or an obviously wrong one (never expires, requiring manual clearing)
  • Doesn't address staleness at all — treats caching as risk-free
Show reference approach (only after your timer ends AND you've self-graded)
Cache key: a deterministic hash of the query's actual parameters -- time window (bucketed to, say, the nearest minute so nearby requests share a key), filter set (agent_id, tool_name, etc.), and aggregation type (p50/p95 latency, failure rate). Bucketing the time window is what turns "everyone hitting the dashboard right now" into a small number of shared cache keys instead of one unique key per request. Cache location: Redis, sitting between the dashboard API and Postgres -- read_replicas_and_dashboard_caching.html's own reasoning: the underlying aggregation query is expensive and the same window gets requested by many concurrent dashboard viewers, so a shared, centralized cache serves all of them from one computed result rather than recomputing per viewer. An in-process LRU would only help a single server instance, not a horizontally scaled dashboard API with multiple replicas behind a load balancer. Invalidation: TTL-based expiry (e.g. 60 seconds) rather than event-driven invalidation, because dashboard data is explicitly NOT required to be real-time-accurate to the second -- a short TTL naturally refreshes the aggregate periodically without needing to track every underlying write that could affect it, which would be substantial added complexity for a dashboard, not an account balance. The staleness trade-off, stated explicitly: caching is safe and appropriate here specifically BECAUSE a dashboard viewer seeing data that's 30-60 seconds stale is an acceptable cost -- this is the same class of decision as read_replicas_and_dashboard_caching .html's read-replica-lag discussion, and naming why staleness is tolerable HERE (versus a system where it wouldn't be, like a payment balance) is what separates a considered answer from "caching is always good."
STATION 4 — PYTHON FUNDAMENTALS · 8:00
8:00

Prompt: Explain the GIL: what it actually protects, why a CPU-bound multi-threaded Python program doesn't get faster on more cores, and why an I/O-bound one often does benefit from threading anyway. Then answer: would you use threads, processes, or asyncio for the capstone's tool-call dispatch layer, and why?

Directly reuses python/the_gil.html's territory. This is a cold, verbal-style question — no code required, just a precise explanation under a short clock.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • States precisely what the GIL protects: only one thread executes Python bytecode at a time within one process, preventing races on CPython's own reference-counting internals
  • Explains why CPU-bound threaded code doesn't parallelize: threads still take turns holding the GIL, so compute-heavy work serializes regardless of thread count
  • Explains why I/O-bound code benefits: the GIL is released during blocking I/O calls, letting other threads run while one waits on the network or disk
  • Gives a clear, justified recommendation for the tool-call dispatch layer (asyncio or threads for I/O-bound tool calls; multiprocessing only if a tool itself does CPU-bound work)
Weak answer
  • Says "Python can't do multithreading" without the more precise "can't parallelize CPU-bound Python bytecode" distinction
  • Can't explain WHY I/O-bound code still benefits from threads despite the GIL
  • Recommends multiprocessing for an I/O-bound dispatch layer without recognizing the unnecessary overhead of separate processes for I/O-wait-dominated work
  • No mention of asyncio as an alternative to threads for I/O concurrency
Show reference approach (only after your timer ends AND you've self-graded)
What the GIL protects: CPython's own internal reference-counting scheme, used for memory management, is not thread-safe by itself -- the GIL is a single lock that ensures only ONE thread executes Python bytecode at any instant, which incidentally also serializes all Python-level computation across threads within one process. Why CPU-bound threaded code doesn't get faster: since only one thread can be running Python bytecode at a time regardless of core count, four threads doing pure computation on a 4-core machine still take turns through the GIL -- there's no wall-clock speedup, and often a slight SLOWDOWN from the overhead of the GIL being repeatedly acquired and released as threads switch. Why I/O-bound code benefits anyway: CPython releases the GIL around blocking C-level I/O calls (socket reads, file reads, time.sleep) specifically so other threads can run Python code WHILE one thread is blocked waiting on the OS. A thread waiting on a network response isn't holding the GIL during that wait, so other threads make real progress -- this is why a thread pool genuinely speeds up an I/O-bound workload despite the GIL, and why "the GIL means Python threading is useless" is an overstatement that misses this distinction entirely. For the capstone's tool-call dispatch layer specifically: tool calls are dominated by I/O wait (network calls to external APIs, database queries) rather than CPU-bound computation, so asyncio (or a thread pool, if the underlying client libraries aren't async-native) is the right choice -- it gets the I/O-bound concurrency benefit without the memory and startup overhead of separate OS processes. Multiprocessing would only be justified if a specific TOOL itself does heavy CPU-bound work (e.g. local embedding computation) that needs to bypass the GIL entirely to use multiple cores -- a genuinely different bottleneck than dispatch concurrency.
