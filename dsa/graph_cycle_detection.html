DATA STRUCTURES & ALGORITHMS LAB · GRAPH CYCLE DETECTION

Detecting a cycle is really asking one question: "can I get back to somewhere I haven't finished with yet?"

A "visited" boolean is not enough to detect a cycle in a directed graph — you need a THIRD state, because "currently being explored" and "fully explored and safe" are genuinely different things. This lab animates the exact color transitions (white → gray → black) that make that distinction visible, contrasts it against the simpler parent-tracking trick undirected graphs get to use instead, and shows precisely what breaks when you try to topologically sort a graph that has a cycle.

01 — Three states, not two

Cycle detection in a directed graph — visited / in-progress / done

Start here, before any code. Imagine you're reading a stack of reference books, and book A tells you "see book B for more detail," so you set A down half-read and open B. If B then tells you "see book A," you're in trouble — not because you've read A before (you have, that's normal for cross-references), but because you're being sent back to a book you set down and never finished, while it's still open on your desk. That's a cycle. If instead B said "see book C," and C referenced a totally different, already-fully-read book D, that's completely fine — D is closed, finished, filed away; going back to it isn't a loop, it's just reuse.

This is exactly why a directed graph needs three states per node during DFS, not just "visited or not":

White (unvisited): haven't started exploring this node yet Gray (in-progress): currently on the DFS call stack — exploration started but not finished Black (done): this node and everything reachable from it has been fully explored

The cycle check is precise: while exploring a node's neighbors, if you find a neighbor that is gray, you've found a cycle — you've looped back to a node that's still "open" on the call stack above you. If you find a neighbor that's black, that's completely safe — it's a legitimately finished, separate branch you're simply revisiting via a different path (this is called a "cross edge" or "forward edge," not a cycle).

def has_cycle_directed(graph): WHITE, GRAY, BLACK = 0, 1, 2 color = {node: WHITE for node in graph} def dfs(node): color[node] = GRAY # entering — mark in-progress for neighbor in graph[node]: if color[neighbor] == GRAY: return True # hit a node still on OUR OWN call stack — cycle! if color[neighbor] == WHITE and dfs(neighbor): return True color[node] = BLACK # leaving — fully explored, safe forever after return False return any(dfs(node) for node in graph if color[node] == WHITE)

Exactly where the two examples diverge: both graphs share the same nodes and start the same way. The WITH-cycle graph has edge C→A; the WITHOUT-cycle graph instead has C→D (D being a separate, already-black node, or a fresh white one). In the cycle case, when DFS reaches C and looks at A, A is still gray (it's the very root of the current call stack, never finished) — cycle detected immediately. In the no-cycle case, C's neighbor is either white (fine, just recurse deeper) or black (fine, already fully explored elsewhere) — never gray, so DFS finishes cleanly with no cycle reported. Interview-ready definition: a directed graph contains a cycle if and only if a DFS traversal encounters a "back edge" — an edge from the current node to an ancestor still on the active recursion stack (colored gray). Tracking three states (white/unvisited, gray/in-progress, black/finished) rather than a simple visited boolean is what distinguishes a genuine back edge (cycle) from a safe cross edge or forward edge to an already-completed subtree.
02 — Two states are enough, plus one extra piece of memory

Cycle detection in an undirected graph — parent tracking

Start here, before any code. In an undirected graph, every edge is automatically a two-way street: if A is connected to B, then when you're standing at B, "A" shows up as one of your neighbors too — even though you just walked from A to B a moment ago. If a plain visited-check ran here, it would immediately (and wrongly) scream "cycle!" the instant you looked back at the node you came from, because that node is, of course, already visited. You need to explicitly ignore "the edge I just walked in on" — which means remembering who your parent is in the DFS tree, so you can tell "I'm looking at the same edge backwards" apart from "I've found a genuinely different way back to an ancestor."

def has_cycle_undirected(graph): visited = set() def dfs(node, parent): visited.add(node) for neighbor in graph[node]: if neighbor == parent: continue # skip the edge we just arrived through — not a cycle if neighbor in visited: return True # reached an already-visited node some OTHER way — cycle if dfs(neighbor, node): return True return False return any(dfs(node, None) for node in graph if node not in visited)

Interview-ready definition: an undirected graph contains a cycle if and only if a DFS traversal reaches an already-visited node through an edge OTHER than the one connecting it to its immediate parent in the DFS tree. Because every undirected edge is traversed from both endpoints, the parent must be explicitly excluded from the "is this a cycle" check, or the trivial back-and-forth along the same edge would be misreported as one.
03 — The classic interview trip-up, explained precisely

Why undirected needs parent-tracking but directed doesn't

Directed graph

Edge A→B is a ONE-WAY relationship. There is no automatic edge B→A just because A→B exists. So when DFS is standing at B, "A" does not appear in B's neighbor list unless someone explicitly added a B→A edge — and if they did, that genuinely IS a separate edge representing a real second connection, worth flagging. There's no "trivial immediate bounce-back" to filter out, because directed edges don't create one.

Undirected graph

Edge {A,B} is stored as BOTH "B is a neighbor of A" and "A is a neighbor of B" — it's the same single edge represented from both ends. So when DFS walks from A to B, B's neighbor list automatically contains A again, not because of some separate second connection, but because it's literally the identical edge looked at backwards. Without excluding the parent, this manufactures a false cycle on every single edge in the entire graph.

Put differently: in a directed graph, "gray" (in-progress) is the specific signal that only fires on a genuine cycle, because reaching a gray node requires a real second directed edge pointing back into the current path. In an undirected graph, merely being "visited" fires on both real cycles AND the trivial same-edge-backwards case, so an additional filter (parent-exclusion) is required to tell them apart. The three-color scheme directed graphs use isn't even necessary for undirected graphs — "visited or not" plus "who's my parent" is sufficient there, since undirected DFS has no equivalent notion of a cross edge to a separately-finished branch: any already-visited non-parent neighbor in an undirected graph is unconditionally a cycle.

The mistake this section exists to prevent: applying the undirected parent-tracking trick to a directed graph (or vice versa) silently gives wrong answers. Using plain visited-tracking (no gray/black distinction) on a directed graph will report false cycles on perfectly legitimate cross edges — e.g. two different tasks that both depend on the same already-finished third task. Using the three-color scheme unnecessarily on an undirected graph works but does more bookkeeping than needed, since undirected graphs never have the "safe revisit via a black node" case that the black color exists to permit — any revisit of a non-parent visited node is a cycle, always.
04 — Ordering constraints that only make sense without cycles

Topological sort, and why it specifically requires no cycles

Start here, before any code. Think of a list of college courses with prerequisites: "Calc II requires Calc I," "Linear Algebra requires Calc I," "Diff Eq requires Calc II and Linear Algebra." A topological sort produces a valid order to take all these courses in, such that every prerequisite comes before the course that needs it. This is only possible in a Directed Acyclic Graph (DAG) — directed, and specifically with NO cycles.

The algorithm (DFS-based): run DFS, and each time a node finishes (turns black — all its dependencies are fully processed), push it onto the FRONT of the result list. Because a node only finishes after everything it depends on has already finished, this guarantees prerequisites end up earlier in the final order.

def topological_sort(graph): WHITE, GRAY, BLACK = 0, 1, 2 color = {node: WHITE for node in graph} result = [] def dfs(node): color[node] = GRAY for neighbor in graph[node]: if color[neighbor] == GRAY: raise ValueError("graph has a cycle — no valid topological order exists") if color[neighbor] == WHITE: dfs(neighbor) color[node] = BLACK result.insert(0, node) # finished nodes go to the FRONT for node in graph: if color[node] == WHITE: dfs(node) return result
COURSE PREREQUISITES — VALID DAG, WATCH THE ORDER BUILD

Edges mean "must come before": Calc I → Calc II, Calc I → Linear Algebra, Calc II → Diff Eq, Linear Algebra → Diff Eq.

WHAT BREAKS: ADD ONE EDGE TO CREATE A CYCLE (Diff Eq → Calc I)

Concretely: if "Diff Eq requires Calc II and Linear Algebra" ALSO had "Calc I requires Diff Eq" tacked on (perhaps by data-entry error), you'd have Calc I → Calc II → Diff Eq → Calc I, a cycle. Ask yourself: what course would you take FIRST? Calc I needs Diff Eq done first, but Diff Eq needs Calc II done first, which needs Calc I done first — there is no valid starting point, because every course in the cycle is waiting on another course in the same cycle. This isn't a limitation of the algorithm; it's a genuine logical contradiction in the input, and topological sort's cycle-detection check exists precisely to catch and report it rather than produce a nonsensical or infinite-looping "order."

Interview-ready definition: a topological sort produces a linear ordering of a directed acyclic graph's vertices such that for every directed edge u→v, u appears before v in the ordering. It is defined ONLY for DAGs because a cycle creates a set of mutually-dependent nodes with no valid "first" node to place — attempting the DFS-based algorithm on a cyclic graph will detect a gray-node revisit (the same back-edge signal used for cycle detection) and must abort, since no correct ordering can exist.

Problem 1 · Directed graph — spot the cycle

Directed edges: A→B, B→C, C→D, D→B. Starting DFS from A, trace the color of each node when C is being explored and its neighbor D is examined, then when D is explored and its neighbor B is examined. Is there a cycle? Which edge is the "back edge"?

Show solution
DFS order: A (gray) -> B (gray) -> C (gray) -> D (gray). At this point: A=gray, B=gray, C=gray, D=gray (all still on the active call stack, none have finished yet). Exploring D's neighbor B: B is GRAY (still on the call stack, entered before D and not yet finished) -> CYCLE DETECTED. The back edge is D->B: it points from the current node (D) back to an ancestor (B) that is still open/in-progress on the DFS call stack. Note C was never re-examined as part of the cycle -- the cycle is specifically B -> C -> D -> B, and D->B is the edge that closes the loop.
Problem 2 · Directed graph — NOT a cycle (cross edge)

Directed edges: A→B, A→C, B→D, C→D. Trace DFS from A (visiting B's subtree fully before starting C). When C examines its neighbor D, what color is D, and why is this NOT a cycle even though D was already visited?

Show solution
DFS from A: A(gray) -> B(gray) -> D(gray) -> D finishes, D(black) -> B finishes, B(black) -> back to A, now explore C: C(gray) -> examine C's neighbor D. D is BLACK at this point (fully finished via the A-B-D branch, popped off the call stack already). Since D is black, not gray, this is NOT a cycle -- it's a "cross edge": a legitimate second way to reach an already-fully-processed node from a completely different branch. D being reachable two different ways (via B and via C) is normal graph structure (e.g. D could be "final exam" that both "Course B" and "Course C" lead into) -- it only becomes a cycle if you loop back to a node that is still OPEN (gray), not one that's already closed (black).
Problem 3 · Undirected graph — the parent-exclusion trap

Undirected edge A-B only (just one edge, two nodes, no cycle). Trace what happens WITHOUT parent-tracking (i.e. treating any already-visited neighbor as a cycle), starting DFS from A. What false result do you get, and how does tracking the parent fix it?

Show solution
Without parent-tracking: DFS visits A, marks A visited. Looks at A's neighbors: B. B is not visited, recurse into B, mark B visited. Now inside B, look at B's neighbors: A. A IS already visited -> falsely reports a cycle! This is wrong -- there's only one edge here, A-B, and you can't have a cycle with just one edge (a cycle needs at least 2 edges in an undirected graph, forming an actual loop back to the start via a DIFFERENT path). The "problem" is that B's neighbor list contains A only because the single A-B edge is stored symmetrically (undirected), not because there's a second real connection. With parent-tracking: when recursing into B, we pass parent=A. Inside B, when checking neighbor A, we see A == parent and skip it entirely (the "continue" in the algorithm). No cycle reported -- correct.
Problem 4 · Topological sort, worked fully

Tasks and dependencies: "wash dishes" has no prerequisites. "dry dishes" requires "wash dishes." "put away dishes" requires "dry dishes." "cook dinner" requires "put away dishes" (need clean pots). Produce one valid topological order, and explain in one sentence why the order isn't unique in general (though it happens to be forced here).

Show solution
Edges: wash -> dry, dry -> putaway, putaway -> cook. This is actually a straight chain (each node has exactly one predecessor and one successor), so there is exactly ONE valid order here: wash dishes, dry dishes, put away dishes, cook dinner. In general, topological order is NOT unique whenever two or more nodes have no dependency relationship between them at all (neither one requires the other, directly or transitively) -- in that case either relative order is valid, and a topological sort algorithm is free to output either one depending on iteration order. This particular example happens to be a pure chain with no such independent pairs, which is why its topological order is forced to be unique.
Problem 5 · Diagnose the broken topological sort

A build system has tasks: compile → link, link → test, test → package, and (added by mistake) package → compile. Explain concretely, using the gray/black states, exactly which DFS call detects this is unsortable, and why "just run the tasks in the order compile, link, test, package anyway" is not a safe fallback.

Show solution
DFS from compile: compile(gray) -> link(gray) -> test(gray) -> package(gray). Now package examines its neighbor: compile. Compile is GRAY (it's the very root of this DFS call, still open on the stack, never finished) -> cycle detected at the edge package -> compile. "Just run them in the listed order anyway" is unsafe because the cycle represents a genuine logical contradiction, not just an inconvenient ordering: package explicitly requires compile to have ALREADY happened again after packaging, which is impossible to satisfy in a single linear run. Silently ignoring the cycle and running compile, link, test, package once would produce a package step whose declared prerequisite (a fresh compile) never actually re-ran -- exactly the kind of stale-build bug topological sort's cycle check exists to catch at build-config time, before any task is actually executed.
