STATION 1 — DSA · 13:00
13:00

Prompt: The capstone's schema-cold-defense tool represents index ranges as a binary search tree for fast lookup. Given the root of a binary tree, determine whether it's a VALID binary search tree — every node's value must be strictly greater than all values in its left subtree and strictly less than all values in its right subtree, not just greater/less than its immediate children.

This is dsa/bst_mechanics.html's core invariant, tested as a validation problem instead of an insert/delete walkthrough. State the naive wrong approach first (checking only immediate children), then the correct one, with complexity.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Explicitly names the common wrong approach (checking only left.val < node.val < right.val locally) and why it fails on a deeper counterexample
  • Proposes the correct approach: recursive validation carrying a (low, high) valid-range bound down the tree, tightening it at each step
  • States the complexity correctly: O(n) time (visits each node once), O(h) space for recursion stack where h is tree height
  • Handles the edge case of duplicate values explicitly (does the BST definition being used allow equal values, and on which side)
Weak answer
  • Only checks immediate parent-child relationships, missing violations from a non-adjacent ancestor
  • Can't produce a concrete counterexample showing why the local-only check is wrong
  • Never states space complexity or forgets the recursion stack contributes to it
  • Doesn't address how duplicates should be handled
Show reference approach (only after your timer ends AND you've self-graded)
The wrong approach, worth naming explicitly: checking only that node.left.val < node.val < node.right.val at every node LOCALLY misses violations from non-adjacent ancestors. Counterexample: a root of 10, with a left child of 5, and that left child has a RIGHT child of 15 -- locally, 5 < 10 checks out and 5 < 15 checks out, but 15 is in the root's LEFT subtree and must be less than 10, which it isn't. A purely local check misses this entirely. Correct approach: recursive validation carrying a (low, high) bound that TIGHTENS as you descend. Start with (-infinity, +infinity) at the root. At each node, check low < node.val < high; recurse left with (low, node.val) as the new bound, and recurse right with (node.val, high). This correctly propagates every ancestor's constraint down the tree, not just the immediate parent's. Complexity: O(n) time -- each node visited exactly once. O(h) space for the recursion call stack, where h is tree height -- O(log n) for a balanced tree, O(n) worst case for a completely unbalanced one (exactly the imbalance tree_rotations_and_balancing.html's rotation logic exists to prevent). Duplicate handling: the STRICT inequality (low < node.val < high, not <=) is the standard BST convention this repo's own bst_mechanics .html uses -- equal values are typically disallowed or, if allowed, consistently routed to one side (e.g. duplicates go right) and the bound check adjusted accordingly (low <= node.val < high or similar, stated explicitly rather than left ambiguous). A strong answer states which convention it's assuming rather than leaving it implicit.
STATION 2 — SCHEMA DESIGN · 11:00
11:00

Prompt: The capstone needs an audit trail: every time an admin changes a client's rate-limit setting, record who changed it, the old value, the new value, and when. Design the schema so this history is queryable ("show me every change to client X's rate limit, in order") without ever mutating or deleting a historical record.

Directly reuses database/audit_trail_schema.html's territory — an append-only pattern, distinct from the mutable-row pattern most CRUD tables use.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Proposes a dedicated, append-only rate_limit_audit table — never UPDATE or DELETE, only INSERT
  • Records old_value, new_value, changed_by, changed_at, and client_id explicitly, not a single opaque "diff" blob
  • Names the index that serves "changes for client X, in order": composite on (client_id, changed_at)
  • Explicitly distinguishes this from the mutable clients table itself, which holds only the CURRENT rate limit — the audit table is a separate, additive log, not a replacement for current state
Weak answer
  • Proposes storing history by adding versioned columns directly on the clients table (rate_limit_v1, rate_limit_v2...), which doesn't scale
  • Allows UPDATE on audit rows, defeating the purpose of an audit trail
  • No explicit old/new value columns — just says "log the change" without a concrete shape
  • Never proposes an index for the stated query
Show reference approach (only after your timer ends AND you've self-graded)
A dedicated `rate_limit_audit` table, append-only by convention (no application code path ever issues UPDATE or DELETE against it, and ideally enforced at the database permission level too): audit_id PK, client_id FK, old_value, new_value, changed_by (admin user id), changed_at. Every change to a client's rate limit produces exactly one new row here -- the table only ever grows. The `clients` table itself keeps a single mutable `rate_limit` column holding the CURRENT value -- this is intentional and correct, not a design flaw: current-state lookups (the hot path, checked on every request per Monday's rate-limiting discussion elsewhere in this repo) stay a simple single-row read, while historical "who-changed-what-when" queries go to the separate audit table, which is a much colder, less frequent access pattern. Conflating the two into one mutable table with embedded history (versioned columns, or a JSON array of past values) breaks both: current-state lookups get slower as history grows, and structured historical queries (filter by admin, by date range) become painful string/JSON parsing instead of simple indexed columns. The query ("changes for client X, in order") wants a composite index on (client_id, changed_at) -- equality filter on client_id, range/ order on changed_at, the same composite-index-ordering pattern this week's other schema stations keep reusing because it recurs constantly in real systems: audit_trail_schema.html's own worked example follows exactly this shape. What makes this genuinely audit-grade rather than just a change log: never allowing UPDATE or DELETE on existing rows is the actual guarantee an audit trail exists to provide -- a "history" table that can be silently edited after the fact isn't a trustworthy audit trail at all, regardless of what columns it has.
STATION 3 — SYSTEM DESIGN · 16:00
16:00

Prompt: The capstone's FastAPI app is being scaled to three replicas behind a load balancer. Pick a load balancing strategy (round robin, least connections, or consistent hashing) and justify it, given that most requests are stateless tool-call dispatches but a small fraction are long-lived streaming responses. Then explain what changes if a future version needs sticky sessions.

Directly reuses systems/load_balancers.html's territory. Name the trade-off between strategies explicitly, not just a single pick with no reasoning.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Recognizes round robin is fine for the stateless majority but can imbalance load when a minority of requests (streaming) hold connections much longer than average
  • Proposes least-connections as a better default given the mixed request-duration profile, and explains WHY (accounts for actual in-flight load, not just request count)
  • Explicitly separates "load balancing strategy" from "session affinity" — sticky sessions are an orthogonal concern layered on top, not a replacement for the LB algorithm
  • States what sticky sessions would require concretely: a consistent hash on client/session id, or a shared session store so any replica can serve any client without needing affinity at all
Weak answer
  • Picks round robin with no justification, or without noticing the streaming-request imbalance risk
  • Conflates load balancing strategy with session stickiness as though they're the same decision
  • No concrete mechanism proposed for how sticky sessions would actually work
  • Doesn't mention the shared-session-store alternative to stickiness at all
Show reference approach (only after your timer ends AND you've self-graded)
Round robin distributes requests evenly by COUNT, blind to how long each request actually holds a connection -- fine when every request takes roughly the same time, but this workload explicitly isn't uniform: most requests are short stateless dispatches, a minority are long-lived streaming responses that occupy a connection (and a worker) far longer. Round robin can send a disproportionate share of those long-lived streams to the same replica by chance, leaving it doing more actual work than its "equal share" of request COUNT would suggest -- a real imbalance round robin's algorithm has no visibility into. Least-connections is the better default here specifically because it tracks ACTUAL in-flight load per replica and routes new requests to whichever replica currently has the fewest open connections -- naturally self-correcting for the mixed-duration profile, since a replica holding several long streaming connections will show a higher active-connection count and receive fewer NEW requests until those streams complete. This is load_balancers.html's own stated trade-off: round robin is simpler and stateless for the LB itself, least-connections requires the LB to track connection state per backend but handles uneven request durations correctly. Sticky sessions, kept explicitly separate: session affinity (routing the SAME client to the SAME replica across requests) is a different axis entirely from load distribution strategy -- you can run least-connections AND sticky sessions together. The concrete mechanism: either a consistent hash on a client/session identifier (so the same client consistently maps to the same replica without a central lookup), or -- the architecturally cleaner alternative -- moving session state OUT of the replica entirely into a shared store (Redis, echoing this week's earlier orchestrator-state discussion), so ANY replica can serve ANY client's request without needing affinity in the first place. A strong answer names the shared-store option as the preferred long-term fix, since sticky sessions reintroduce a single point of failure per client (if that one replica goes down, the client's session is disrupted) that a shared store avoids entirely.

Prompt: Explain the difference between an iterator and a generator in Python, and why a generator is memory-efficient for streaming the capstone's eval-trace records from a large export file. Then: what does yield actually do to a function's execution model that a normal return doesn't?

Directly reuses python/iterators_and_generators.html's territory. Cold, verbal-style — precise mechanism, not just "generators are lazy."

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • States the iterator protocol precisely: an object implementing __iter__ and __next__, raising StopIteration when exhausted
  • States that a generator IS an iterator, but one created via a function containing yield (or a generator expression) rather than a hand-written class
  • Explains the memory win precisely: a generator produces one value at a time on demand, never materializing the full sequence in memory, versus reading the whole export file into a list first
  • Explains yield's actual mechanism: it suspends the function's execution and local state (a real, resumable stack frame), returning control to the caller, and resumes exactly where it left off on the next next() call — a normal return destroys the frame permanently
Weak answer
  • Says "generators are lazy" or "iterators are things you can loop over" without the precise protocol
  • Doesn't state that generators ARE iterators (a specific implementation of the protocol), treating them as an unrelated concept
  • Memory-efficiency explanation is vague ("uses less memory") without contrasting against materializing a full list
  • Can't explain what happens to the function's execution state between yields — treats yield as "like return but multiple times" with no mention of frame suspension
Show reference approach (only after your timer ends AND you've self-graded)
The iterator protocol: any object implementing __iter__ (returning the iterator itself) and __next__ (returning the next value or raising StopIteration when exhausted) is an iterator -- this is the mechanism every `for` loop in Python is built on under the hood. A generator is an iterator, specifically one produced by a function containing at least one `yield` statement (or a generator expression, `(x for x in ...)`). Calling a generator function doesn't run its body immediately -- it returns a generator OBJECT that already satisfies the iterator protocol, and the body only executes incrementally as `next()` is called on it. Memory efficiency, precisely: reading a large export file into a list first (`records = [parse(line) for line in file]`) materializes EVERY record in memory simultaneously before processing begins. A generator (`for line in file: yield parse(line)`) produces exactly ONE parsed record at a time, on demand -- memory usage stays constant regardless of file size, versus scaling linearly with record count for the list version. This is the exact trade-off worth naming for a large eval-trace export: the generator version can stream an arbitrarily large file with flat memory usage. What `yield` actually does to execution, the mechanism a strong answer states explicitly: unlike `return`, which destroys the function's stack frame permanently and hands a single value back to the caller, `yield` SUSPENDS the function's execution mid-body -- its entire local variable state, its current position in the code, and its call stack frame are preserved, paused, exactly where the yield statement fired. Control returns to the caller with the yielded value. The NEXT call to `next()` on that generator resumes execution from that exact paused point, with all local state intact, continuing until the next yield or the function actually returns (which raises StopIteration). This resumable-frame mechanism is what makes a generator fundamentally different from a function that just returns a list -- it isn't "returning multiple times," it's a genuinely different execution model where the function's state persists across calls.
