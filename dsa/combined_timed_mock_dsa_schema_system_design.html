How this mock works

Start here, before starting any timer. Think about a relay race versus a single runner doing four different events back to back. A relay race hands off a baton between four DIFFERENT runners, each specialized for their leg — no individual runner has to reorient. A decathlete, by contrast, is ONE person who has to go from the 100m sprint (explosive, seconds-long, all adrenaline) to the long jump (technical, patient, a completely different body mechanic) to the shot put (raw strength, no running at all) — and the actual skill decathlon training targets isn't "get better at sprinting" in isolation, it's minimizing the dead time and mental fumbling in the TRANSITION between events. A real system design interview loop is a decathlon, not a relay: you are one person, going from a DSA whiteboard problem straight into a schema design question straight into a full system sketch, often within the same hour, with no specialist handoff.

This mock has four stations. Each one is deliberately SHALLOW relative to its dedicated lab — the depth already exists in dsa/graphs_bfs_dfs.html, database/normalization_3nf_and_er_modeling.html, and the Week 1 design mocks. What this lab adds is the CLOCK and the FORCED SWITCH: each station has a visible countdown, and the moment it hits zero, you move on — finished or not — exactly like a real loop where the next interviewer doesn't care that you were 90% done with the last one.

How to actually use this lab: work each station for real, on paper or in your own head, using the timer below as a hard stop — not a suggestion. Resist the urge to peek at a station's solution before your own timer runs out; the entire point is training the decision of WHEN to stop optimizing one answer and move to the next, which you can only practice by actually running out of time sometimes.
STATION 1 — DSA · 12:00
12:00

Prompt: Given a directed graph representing tool dependencies in an agent's plan (an edge A → B means tool A must run before tool B), determine whether the plan can be executed at all — i.e., detect whether the dependency graph contains a cycle — and if it can, produce one valid execution order.

This is dsa/graph_cycle_detection.html's cycle detection combined with a topological sort, applied to an agent-planning context instead of an abstract graph — recognizing the SHAPE of a familiar problem under a new label, fast, is exactly the skill being tested. Sketch your approach (DFS with a recursion-stack set, or Kahn's algorithm via in-degree tracking) and its complexity before your timer runs out.

Show reference approach (only after your timer ends)
Two standard approaches, either is a strong answer: 1. DFS with a three-color scheme (white/gray/black), per graph_cycle_detection.html: a node in the current recursion stack ("gray") that's revisited means a back edge, hence a cycle. If DFS completes with no back edge found, the plan is executable; the topological order is the REVERSE of DFS finish order (append each node to the order as it's popped/finished, then reverse). 2. Kahn's algorithm: compute in-degree for every node, push all 0-in-degree nodes onto a queue, repeatedly pop a node, append it to the order, and decrement its neighbors' in-degrees, pushing any that reach 0. If the final order has fewer nodes than the graph, a cycle exists among the unvisited remainder. Both are O(V + E) time, O(V) space. Kahn's is often preferred in an agent-planning context specifically because the ORDER it produces falls out naturally as a byproduct of the cycle check itself (no separate reverse step), and it generalizes cleanly to "give me ALL tools currently unblocked" at any point in execution -- relevant if tools can be dispatched in parallel whenever their dependencies are satisfied, which is a realistic elaboration of this exact problem.
STATION 2 — SCHEMA DESIGN · 10:00
10:00

Prompt — no ramp-up, go straight from graphs to tables: Model a schema for tracking agent tool-call results (an agent run produces an ordered sequence of tool calls, each with arguments, a result, a latency, and a success/failure status), where you need to efficiently answer "what's the failure rate of tool X over the last 24 hours" and "show me the full ordered call sequence for run Y." Sketch the tables, keys, and which normal form you're targeting.

Directly reuses database/normalization_3nf_and_er_modeling.html's modeling approach and database/eval_results_schema.html's "a score with no trace behind it is untrustworthy" shape, now for tool calls instead of eval scores. Sketch entities and foreign keys before your timer runs out — full DDL isn't the point, the entity/relationship shape is.

Show reference approach (only after your timer ends)
Core entities, in 3NF: an `agent_runs` table (run_id PK, agent_id, started_at, status) and a `tool_calls` table (call_id PK, run_id FK, sequence_number, tool_name, arguments JSON, result JSON, latency_ms, status, called_at). The ordered-sequence requirement is satisfied by sequence_number + an index on (run_id, sequence_number) -- retrieving run Y's full ordered call sequence is one indexed range scan, exactly eval_trace_schema_finalization.html's reasoning for why an explicit ordering column beats relying on insertion order or timestamp granularity alone. The failure-rate query ("tool X's failure rate over 24h") wants an index on (tool_name, called_at) at minimum, and at real scale would benefit from a separate aggregated rollup table (tool_name, hour_bucket, call_count, failure_count) maintained incrementally rather than scanning raw tool_calls on every dashboard load -- the same read-optimization instinct database/read_replicas_and_dashboard_caching.html applied to eval dashboards, now applied to tool-call failure rates. A strong answer explicitly names WHY 3NF here (no redundant tool metadata duplicated per call row -- if tool_name needs a description or owner, that belongs in a separate `tools` table, not repeated on every tool_calls row) and flags the aggregation table as an intentional, justified DEVIATION from strict normalization for read performance, not an oversight.
STATION 3 — SYSTEM DESIGN · 15:00
15:00

Prompt — now zoom all the way out, from one table to a whole system: Sketch, at a HIGH level (no deep capacity estimation — that's Week 1's dedicated mocks), how you'd architect a service that takes the tool-call data from Station 2's schema and exposes a real-time "which tools are currently failing above threshold" alerting signal to on-call engineers, at a scale of ~5,000 tool calls/sec.

This deliberately compresses systems/distributed_telemetry_ingester_design.html's ingestion-pipeline shape and systems/observability_pipeline_design.html's alerting concerns into a 15-minute sketch — the goal is naming the right 3-4 components and their responsibilities, not a full mock.

Show reference approach (only after your timer ends)
A strong 15-minute sketch names roughly four components without going deep on any one: (1) an ingestion path that receives tool-call completion events (success/fail + latency) and writes them somewhere durable fast, mirroring distributed_telemetry_ingester_design.html's "accept fast, buffer durably" shape rather than writing directly and synchronously to the Station 2 schema on the hot path; (2) a streaming aggregation layer that maintains a rolling per-tool failure-rate window (e.g. failures in the last 5 minutes / total calls in the last 5 minutes, per tool_name) incrementally, rather than re-querying the full tool_calls table on every check; (3) a threshold evaluator that compares each tool's rolling rate against a configured threshold and fires an alert on crossing it, with de-duplication so a tool stuck above threshold doesn't re-alert every second; (4) the durable Station 2 schema itself as the system of record for post-incident investigation (the full ordered call sequence), explicitly NOT on the alerting hot path -- alerting reads from the fast in-memory rolling aggregate, not from a database query, echoing observability_pipeline_design.html's "the dashboard's query path and the alerting path are not the same path" distinction. The interview skill being tested at THIS station specifically is naming the RIGHT four boxes and their responsibilities under real time pressure, then explicitly deferring capacity estimation ("I'd want to work out exact node counts the way I did in Monday's telemetry ingester design, but at a sketch level: five thousand calls/sec is squarely 'needs a horizontally-scaled ingestion tier, not a single process' ") rather than trying to cram a full capacity-estimation pass into 15 minutes at the cost of never reaching component 4.
STATION 4 — DSA FOLLOW-UP · 8:00
8:00

Prompt — jump back to DSA thinking, cold, right after system design: Station 3's threshold evaluator needs to maintain, per tool, a rolling window of the last 5 minutes of call outcomes to compute a failure rate cheaply. Design the data structure that lets you add a new outcome AND evict outcomes older than 5 minutes, both in O(1) amortized time.

This is deliberately the HARDEST switch in the mock: from 15 minutes of high-level system boxes, straight back into precise data-structure reasoning, with zero transition time. Notice the mental gear-change required — that's the point, not the algorithm itself.

Show reference approach (only after your timer ends)
A queue (deque) of (timestamp, outcome) pairs plus two running counters (total_count, failure_count) is the standard answer -- this is a sliding-window-over-a-stream pattern, structurally the same shape as big_o_and_linked_lists.html's discussion of amortized O(1) operations on a deque. On each new outcome: append it to the back of the deque and increment total_count (and failure_count if it's a failure) -- O(1). Before computing the current rate, evict from the FRONT of the deque any entries older than 5 minutes, decrementing total_count/failure_count for each evicted entry -- this eviction step is O(1) AMORTIZED, not O(1) worst-case per call, because in the worst case many stale entries could be evicted in one pass, but each individual entry is only ever pushed once and evicted once across its entire lifetime, so the total eviction work across N calls is bounded by O(N), giving O(1) amortized per call over any sequence of operations -- the exact amortized-analysis argument big_o_and_linked_lists.html walks through for dynamic array resizing, now applied to a time-based eviction window instead of a capacity-based one. failure_rate = failure_count / total_count is then an O(1) read at any point, no need to iterate the deque itself. The follow-up worth anticipating: what if calls arrive out of order (network delay, distributed sources)? A strict monotonic-timestamp assumption breaks -- the practical fix in a real distributed system is bucketing into fixed time buckets (e.g. per-second counts in a circular buffer of 300 buckets for a 5-minute window) rather than a raw per-event deque, which tolerates minor out-of-order arrival within a bucket at the cost of per-second rather than per-event granularity -- a real trade-off worth naming even under an 8-minute clock.
The actual skill this mock trains

Reflection: handling context-switching under time pressure

Start here, before reading the list below. Notice what just happened, if you ran the stations for real: Station 3 asked you to hold FOUR fuzzy, half-finished component boxes in your head and talk about them at a high level, deliberately avoiding precision. Station 4, immediately after, demanded the opposite — one precise, fully-specified data structure with a proven complexity bound. Anyone who tried to answer Station 4 with Station 3's "sketch it loosely, we'll come back" energy would give a genuinely bad answer, and anyone who tried to answer Station 3 with Station 4's "get every detail exactly right" energy would run out of time before naming the fourth component.

What actually helps, station to station

  • Name the mode change out loud, even to yourself. "Okay, this is a schema question now, not a graph question" — a two-second explicit reset is cheaper than the 90 seconds of fumbling that happens when your brain is still halfway solving the last problem while you start talking about the new one.
  • Match your precision level to the station's actual ask. Station 1 and Station 4 want a specific, correct, complexity-bounded answer. Station 3 wants the right FOUR BOXES and their responsibilities, explicitly deferring depth ("I'd work this out the way enterprise_mcp_agent_gateway_design.html did, but at sketch level here"). Applying Station 1's precision bar to Station 3 is a real, common failure mode — you'll only get through two boxes.
  • Let go of an unfinished station on the clock, deliberately. The clock hitting zero on Station 1 mid-proof is not a failure of Station 1 — it's success at the actual skill, which is not carrying that unfinished thread into Station 2's very different demands. A real loop's next interviewer has no idea (and doesn't care) that you were 90% done with the last one.
  • Use the PREVIOUS station's artifact when a later one legitimately calls back to it — but don't force a connection that isn't there. Station 3 legitimately builds on Station 2's schema; Station 4 legitimately builds on Station 3's threshold evaluator. That's real continuity, not context bleed — the skill is distinguishing "this station actually depends on the last one" from "I'm just still thinking about the last one."
The failure mode this mock is built to surface: not knowing less about graphs, schemas, or system design than you do in the dedicated labs — it's discovering, under a clock, that you're still mentally "in" Station 2's normalization argument three minutes into Station 3's high-level sketch, and that costs you the fourth component you never got to name. The fix isn't more DSA practice or more schema practice — both already exist at full depth elsewhere in this repo. The fix is running THIS exact drill again until the mode-switch itself stops costing visible time.

Practice problems

These aren't new technical problems — they're about the switching itself. Work through them honestly.

Problem 1 · Diagnosing your own slowest transition

Run all four stations again, timing yourself honestly. Which transition (1→2, 2→3, or 3→4) took the longest to "arrive" at the new station's mode of thinking — not to solve the problem, just to stop thinking about the previous one? Why that specific transition, and not the others?

Show solution
There's no single correct answer here -- the value is in the honest self-diagnosis, not a specific outcome. But a common pattern worth checking for: the 2→3 transition (schema into system design) is often the SLOWEST for people who default to precision-first thinking, because Station 2 rewards getting a specific detail exactly right (is this 2NF or 3NF? which column is the foreign key?), and that same instinct actively HURTS in Station 3, where spending the first three minutes trying to nail exact table names or column types instead of naming the four architectural boxes is precision applied at the wrong altitude. The 3→4 transition (system design back into DSA) is often slow for the opposite reason -- people who just spent 15 minutes deliberately staying high-level have to consciously downshift back into "no, actually prove this data structure's complexity bound now," and the instinct to stay comfortably vague, which just worked for 15 minutes, is now the wrong instinct entirely. If you noticed a consistent slow transition across multiple runs of this mock, that's real, actionable signal -- it tells you which DIRECTION of altitude change (zooming in vs. zooming out) costs you more, which is more useful than knowing "I'm slow at system design" in the abstract, because the deficit here isn't depth (you have dedicated labs for that) -- it's the specific muscle of changing altitude quickly in one particular direction.
Problem 2 · Simulating an interviewer follow-up that forces a switch back mid-station

Real loops sometimes don't wait for your timer — an interviewer interrupts Station 3's system design sketch with "hold on, walk me back through how Station 2's schema would actually store the rolling window data you just mentioned." Practice answering this cold: reconcile Station 3's in-memory rolling window (Station 4's deque/bucket structure) with Station 2's durable schema. Are they the same storage, or genuinely different, and why?

Show solution
They are genuinely DIFFERENT storage, serving different purposes, and conflating them is the wrong answer here -- recognizing that distinction under a surprise interruption is exactly the skill this problem is testing. Station 4's rolling window (a deque or bucketed circular buffer) is an EPHEMERAL, in-memory structure living inside the threshold evaluator process itself, optimized for O(1) amortized add/evict and existing ONLY to answer "what's the current failure rate right now" cheaply and continuously -- it is explicitly NOT meant to be durable; if the evaluator process restarts, rebuilding the last 5 minutes of window state from Station 2's durable tool_calls table (a simple range query on called_at) is perfectly acceptable, because 5 minutes of catch-up is a small, bounded cost. Station 2's schema, by contrast, is the durable system of record -- every tool call, indefinitely retained (subject to whatever retention policy applies), queryable for the FULL ordered call sequence of any run, used for post-incident investigation, audit, and historical analysis -- none of which the ephemeral rolling window structure is built for or even capable of. The right answer to the interviewer's interruption is naming this split explicitly: "the rolling window is a derived, ephemeral, in-memory VIEW computed from the same stream of events that also gets durably persisted to Station 2's schema -- they're two different consumers of the same underlying event stream, not the same storage doing double duty." This is the same "hot path vs. system of record" split systems/observability_pipeline_design.html draws between a dashboard's live view and its durable backing store, and recognizing that pattern quickly, even mid-interruption, is a genuinely strong signal in a real loop.
