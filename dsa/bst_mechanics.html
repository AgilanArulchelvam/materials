A binary search tree is a phone book that reorganizes itself every time you insert a name.

The entire BST property is one sentence — everything in a node's left subtree is smaller, everything in its right subtree is bigger — but that one sentence is what turns "search" into a series of coin-flip-like eliminations instead of a linear scan. This lab walks every comparison the algorithm makes, node by node, for insert, search, delete (including the messy two-children case), and all four traversal orders.

01 — One rule, applied recursively

The BST property: left < node < right

Start here, before any code. Picture a "guess my number" game where after every guess you're told "higher" or "lower." Each answer eliminates roughly half the remaining possibilities. A binary search tree bakes that exact elimination strategy into its shape: at every node, comparing your target against that node's value tells you which entire subtree can be skipped — you never have to look at it.

Formally: for every node N in a binary search tree, every value in N.left's subtree is strictly less than N.value, and every value in N.right's subtree is strictly greater. This must hold recursively at every node, not just the root — a node two levels down still has to be smaller than its grandparent if it sits in the grandparent's left subtree.

class Node: def __init__(self, value): self.value = value self.left = None self.right = None # Valid BST: Invalid — 9 violates the property: # 8 8 # / \ / \ # 3 10 3 10 # / \ \ / \ \ # 1 6 14 1 6 14 # / \ / \ # 4 7 4 9 ← 9 > 8, but it's in the LEFT # subtree of the root. Even though # 9 > 6 locally is fine, it breaks # the property relative to the root.
Interview-ready definition: a Binary Search Tree is a binary tree satisfying the invariant that for every node, all keys in its left subtree are less than the node's key and all keys in its right subtree are greater — applied recursively at every node, not merely at the root — which enables search, insert, and delete to each discard one entire subtree per comparison rather than examining every element.
02 — Descending until you find the gap

Insert — watch the comparison-by-comparison descent

Inserting a new value means walking from the root, comparing at each node, and following "go left" / "go right" exactly like a search — until you fall off the tree into a None slot. That empty slot is where the new node attaches.

def insert(root, value): if root is None: return Node(value) # found the gap — attach here if value < root.value: root.left = insert(root.left, value) # recurse left elif value > root.value: root.right = insert(root.right, value) # recurse right return root
INSERT — LIVE DESCENT, NODE BY NODE
Enter a value and click Insert — each comparison against the current node will be spelled out here before the tree moves on.
Cost of insert: the number of comparisons equals the depth at which the new node lands — O(h) where h is the tree's height. In a balanced tree h ≈ log₂(n); in a degenerate (chain-shaped) tree h can be n. This is the seed of why balancing matters, covered in the next lab.
03 — Same descent, different question

Search — watch it eliminate half the remaining tree each step

Start here, before any code. This is the "guess higher or lower" game made literal: at each node you ask "is my target smaller, bigger, or equal?" A "smaller" answer means you can ignore that node's entire right subtree forever — not skip it for now, discard it completely from consideration, along with everything beneath it.

def search(root, target): if root is None: return False # fell off the tree — not present if target == root.value: return True # found it elif target < root.value: return search(root.left, target) # entire right subtree eliminated else: return search(root.right, target) # entire left subtree eliminated

04 — Three genuinely different cases

Delete: leaf, one child, and the two-children case

Start here, before any code. Deleting a leaf is like removing a name with no cross-references — just erase it. Deleting a node with one child is like removing a person from an org chart when they have exactly one direct report — promote that report into their spot. Deleting a node with two children is trickier: you can't promote both children into one slot, so instead you find the next larger value in the tree (called the in-order successor — the smallest value in the right subtree), copy that value into the node being deleted, and then delete the successor from where it originally was (which is guaranteed to be an easy leaf-or-one-child case).

def delete(root, target): if root is None: return None if target < root.value: root.left = delete(root.left, target) elif target > root.value: root.right = delete(root.right, target) else: # found the node to delete if root.left is None: return root.right # 0 or 1 child (right) — promote it if root.right is None: return root.left # 1 child (left) — promote it successor = find_min(root.right) # TWO children: smallest value in right subtree root.value = successor.value # copy successor's value up root.right = delete(root.right, successor.value) # remove the now-duplicate successor return root
DELETE — PICK A CASE TO WALK THROUGH
CaseWhat happensWhy it's correct
Leaf (0 children)Just remove it; parent's pointer becomes NoneNothing referenced it, no property to preserve
One childSplice out the node — parent now points directly to the childThe child (and its subtree) already satisfies the BST property relative to the grandparent, since it did relative to the removed node
Two childrenCopy in-order successor's value up, then delete the successor (a leaf or one-child case) from the right subtreeThe successor is the smallest value greater than the deleted node — placing it there preserves left < node < right everywhere
Why the successor (not just "either child"): the in-order successor is specifically the smallest value in the right subtree — guaranteed to have no left child itself (if it did, that left child would be even smaller, contradicting "smallest"). That guarantee is exactly what makes deleting the successor always reduce to the easy leaf-or-one-child case, never recursively triggering another two-children deletion. An in-order predecessor (largest in the left subtree) would work equally well by the mirror argument — either choice is valid, just be consistent.
05 — Four ways to visit every node

In-order, pre-order, post-order, level-order traversal

Start here, before any code. Think of the tree as a family tree you need to read aloud in different orders: youngest-to-oldest within each branch (in-order), "announce the parent before their kids" (pre-order), "announce the kids before their parent" (post-order), or "read across each generation, left to right" (level-order). Same tree, same nodes — the order you visit them in changes what the sequence is useful for.

06 — Shape matters as much as content

Why an unbalanced BST degrades to O(n)

All the O(log n) claims above assumed a roughly balanced tree — one where each subtree is about half the remaining nodes. Nothing in the basic insert algorithm enforces that. If you insert values that are already sorted (1, 2, 3, 4, 5...), every new value is larger than everything before it, so every node gets attached as the right child of the previous one. The "tree" becomes a straight line — structurally identical to a linked list.

INSERT SORTED VALUES — WATCH THE TREE COLLAPSE INTO A CHAIN
Tree shapeHeightSearch/Insert/Delete
Perfectly balancedO(log n)O(log n) — each comparison halves the remaining candidates
Degenerate (sorted-order insertion)O(n)O(n) — identical to searching a linked list, one comparison eliminates only ONE node, not half the tree
Interview-ready definition: a plain BST's O(log n) time complexity is a claim about a balanced tree of height h ≈ log₂(n); the operations are actually O(h) in general, and insertion order alone determines h — sorted or adversarial insertion order can produce h = n, degrading every operation to O(n). Self-balancing variants (AVL, Red-Black trees) exist specifically to guarantee h stays O(log n) regardless of insertion order, which is the subject of the next lab.

Problem 1 · Validate the BST property

Tree: root=10, left child=5, right child=15. Node 5's right child is 12. Is this a valid BST? Explain using the recursive property, not just local comparisons.

Show solution
No, invalid. Node 12 is in the LEFT subtree of the root (10), because it descends from 5, which is root.left. But 12 > 10, violating the property that EVERY value in the root's left subtree must be less than 10. Locally, 12 > 5 looks fine (12 correctly sits to the right of 5) — but the BST property is recursive relative to ALL ancestors, not just the immediate parent. This is exactly the kind of subtle violation interviewers test for with a "validate BST" question: you must track a valid (low, high) range that narrows as you descend, not just compare each node to its direct parent.
Problem 2 · Trace an insert

Starting from an empty tree, insert in this order: 50, 30, 70, 20, 40, 60, 80, 35. Draw (or describe) the resulting tree shape, and state its height.

Show solution
50 / \ 30 70 / \ / \ 20 40 60 80 / 35 Height = 3 edges from root to the deepest node (35), i.e. 4 levels. This is a well-balanced tree for 8 nodes — log2(8) = 3, so height 3-4 is expected for a balanced shape. Each insert compares against ancestors: e.g. 35 vs 50 (smaller, go left), vs 30 (bigger, go right), vs 40 (smaller, go left), lands as 40's left child.
Problem 3 · Delete a leaf and a one-child node

Using the tree from Problem 2, describe what changes when you delete 20 (a leaf), and separately (starting fresh from the same tree) what changes when you delete 60 (which has no children — wait, check: does 60 have a child in that tree)? If it doesn't, explain what "one child" would look like using node 80 instead if 80 had only a left child of 75.

Show solution
Delete 20 (leaf): 30's left pointer simply becomes None. Nothing else changes — 20 had no children to reattach anywhere. 60 in that tree is also a leaf (70's left child, no children of its own) — deleting it sets 70.left = None, same as the leaf case above. One-child example instead: if 80 had a single left child 75 (no right child), deleting 80 means splicing it out — 70.right = 75 (75 gets promoted directly into 80's old spot). 75 keeps whatever subtree it had; the BST property still holds because 75 < 80 was already true, and 75 is still correctly positioned as > 70 in 70's right subtree.
Problem 4 · Two-children deletion, fully worked

Using the tree from Problem 2 (50 root, 30/70 children, 20/40/60/80 grandchildren, 35 under 40), delete the root, 50. Walk through finding the successor and the final tree shape.

Show solution
50 has two children (30 and 70) — the two-children case. In-order successor = smallest value in the RIGHT subtree (rooted at 70). Walk left from 70: 70 -> 60 (60 has no left child) -> successor = 60. Copy 60's value into the root: root.value becomes 60. Delete 60 from its original spot (70's left child) — 60 is a leaf there, so 70.left becomes None. Resulting tree: 60 / \ 30 70 / \ \ 20 40 80 / 35 Verify the property still holds: 60's left subtree (30,20,40,35) are all < 60. 60's right subtree (70,80) are all > 60. Valid.
Problem 5 · Predict the traversal outputs

For the tree: root=8, left=3 (children 1, 6), right=10 (right child 14, whose left child is 13). Write the in-order, pre-order, and post-order sequences.

Show solution
In-order (left, node, right): 1, 3, 6, 8, 10, 13, 14 Pre-order (node, left, right): 8, 3, 1, 6, 10, 14, 13 Post-order (left, right, node): 1, 6, 3, 13, 14, 10, 8 Note in-order produces perfectly ascending sorted order (1,3,6,8,10,13,14) — this is guaranteed for ANY valid BST, which is exactly why in-order traversal is the standard way to extract sorted data from one.
Problem 6 · Why sorted insertion is the worst case

Explain, in terms of comparisons made, why inserting n already-sorted values one at a time into an empty BST takes O(n²) total time, even though each individual insert is "just" a descent.

Show solution
Inserting sorted values 1, 2, 3, ..., n one at a time: each new value is larger than every existing value, so it always becomes the right child of the current rightmost node. Inserting the k-th value requires walking k-1 existing nodes (all chained to the right) before finding the None slot. Total comparisons across all n inserts: 0 + 1 + 2 + ... + (n-1) = n(n-1)/2 = O(n²) for the whole sequence of insertions, even though the claimed per-operation cost was "O(h)" — because h itself grows to k-1 for the k-th insert in this specific degenerate case, rather than staying at O(log k). This is the concrete mechanism behind "an unbalanced BST degrades to O(n) per operation."
