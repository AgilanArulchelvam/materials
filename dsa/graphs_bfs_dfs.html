DATA STRUCTURES & ALGORITHMS LAB · GRAPHS: BFS & DFS

A graph is just nodes and connections — and the ONLY thing that changes between BFS and DFS is which end of a list you pull from.

BFS and DFS are, in code, almost identical: both maintain a "frontier" of nodes to visit and a "visited" set, and both loop while the frontier is non-empty. The single line that differs — pop from the front (queue) versus pop from the back (stack) — is the entire reason one explores level-by-level and the other plunges deep down one path first. This lab shows that frontier changing shape, item by item, live, on the same graph both algorithms share.

01 — How do you even store "connections"?

Adjacency list vs adjacency matrix

Start here, before any code. Imagine you're modeling a city's friendships. You could keep, for every person, a short personal list of "who I'm friends with" — that's an adjacency list. Or you could keep one giant spreadsheet with every person as both a row and a column, and mark a cell "yes" if those two people are friends — that's an adjacency matrix. The spreadsheet lets you instantly answer "are Alice and Bob friends?" by checking one cell, but if the city has a million people and each person only has ~200 friends, you're storing a trillion mostly-empty cells just to represent 200 million actual friendships.

A graph is formally just a set of vertices (nodes, V) and edges (connections between them, E). Everything else — directed/undirected, weighted/unweighted, cyclic/acyclic — is a property layered on top of that basic shape.

Adjacency list

A dictionary/array where each vertex maps to a list of its neighbors. Space: O(V + E) — you only pay for edges that actually exist. Checking "are A and B connected?" costs O(degree of A) — you scan A's neighbor list. This is the default choice for almost every real graph, because real graphs are sparse (E is much closer to V than to V²).

Adjacency matrix

A V×V grid where matrix[i][j] = 1 (or a weight) if an edge exists from i to j. Space: O(V²) regardless of how many edges actually exist. Checking "are A and B connected?" is O(1) — one array lookup. Worth it only when the graph is dense (close to every pair connected) or when O(1) edge-existence checks matter more than memory.

Interview-ready definition: an adjacency list represents a graph as a mapping from each vertex to a collection of its adjacent vertices, using O(V + E) space; an adjacency matrix represents it as a V×V boolean or weighted grid using O(V²) space regardless of edge count. The choice is a space/time trade-off governed by graph density: sparse graphs (E ≈ V) favor adjacency lists, dense graphs (E ≈ V²) make the matrix's fixed O(V²) cost less wasteful and its O(1) edge queries more valuable.
02 — Four independent axes

Directed vs undirected, weighted vs unweighted

Start here, before any code. A two-way street is an undirected edge — if you can drive from A to B, you can also drive from B to A along the same road. A one-way street is a directed edge — a Twitter "follow" is directed too (you following someone doesn't mean they follow you back). Separately, weighted just means each connection has a "cost" attached — a road has a distance, a flight has a price — versus unweighted, where every edge just means "connected," full stop, with no notion of one connection costing more than another.

PropertyMeaningReal-world example
DirectedEdge A→B does NOT imply B→ATwitter follows, task dependencies (A must finish before B)
UndirectedEdge {A,B} works both waysFacebook friendships, road networks (two-way streets)
WeightedEach edge carries a cost/distance/capacityFlight prices, road distances, network bandwidth
UnweightedEdges only encode "connected or not""Who follows whom" (just the relationship, not its strength)
Why this matters for algorithm choice: BFS finds the shortest path by edge count in an unweighted graph — but that stops being true the instant edges have different weights, because BFS has no concept of one edge "costing more" than another. A 1-edge path with weight 100 looks identical to BFS as a 1-edge path with weight 1. Weighted shortest-path needs a different algorithm entirely (Dijkstra's, covered in a later lab) that specifically accounts for accumulated edge weight, not just hop count.
03 — Level by level, using a queue

Breadth-First Search — watch the queue change, live

Start here, before any code. Picture dropping a stone in a pond: the ripples spread outward one ring at a time — everything 1 step away lights up before anything 2 steps away does. That's BFS. It explores the graph in expanding "rings" outward from the start node, which is exactly why, in an unweighted graph, the FIRST time BFS reaches any node is guaranteed to be via the shortest possible path (fewest edges) to it — you can't skip a ring.

Mechanically: BFS keeps a queue (first-in-first-out) of nodes waiting to be explored. It pops the FRONT of the queue, looks at that node's unvisited neighbors, marks them visited and pushes them to the BACK of the queue, and repeats until the queue is empty. Because new neighbors always go to the back, all of "ring 1" gets fully processed before any of "ring 2" is even looked at.

from collections import deque def bfs(graph, start): visited = {start} # mark as visited THE MOMENT it enters the queue, queue = deque([start]) # not when it's dequeued — prevents duplicate enqueues order = [] while queue: node = queue.popleft() # FIFO: pop from the FRONT order.append(node) for neighbor in graph[node]: if neighbor not in visited: visited.add(neighbor) queue.append(neighbor) # push new neighbors to the BACK return order

Interview-ready definition: Breadth-First Search explores a graph outward in order of distance (edge count) from the source, using a FIFO queue to ensure every node at distance d is dequeued and its neighbors examined before any node at distance d+1 is processed. In an unweighted graph, this guarantees the first time a node is reached is via a shortest path, making BFS the standard algorithm for unweighted shortest-path and "minimum number of hops" problems.
04 — One path, all the way down, using a stack

Depth-First Search — watch the stack change, live

Start here, before any code. Now picture exploring a maze by always taking the first unexplored turn and committing to it fully, only backtracking when you hit a dead end — you might tunnel far away from the start before ever circling back to try a different branch near the entrance. That's DFS. Same graph, same nodes, but instead of exploring in rings, it charges down one path as deep as it can go, then backtracks.

Mechanically: DFS keeps a stack (last-in-first-out) — or, equivalently, uses the call stack via recursion, which is the same idea in disguise. It pops the node most recently pushed, explores it, and pushes its unvisited neighbors. Because the most recently pushed neighbor is explored NEXT (not the oldest one waiting), DFS naturally follows one branch all the way to a dead end before backtracking to try the next one.

# Iterative, explicit stack — mirrors the animation below exactly def dfs_iterative(graph, start): visited = set() stack = [start] order = [] while stack: node = stack.pop() # LIFO: pop from the BACK (top of stack) if node in visited: continue # may have been pushed twice — skip if already done visited.add(node) order.append(node) for neighbor in reversed(graph[node]): if neighbor not in visited: stack.append(neighbor) # Recursive version — the call stack IS the stack, implicitly def dfs_recursive(graph, node, visited=None, order=None): if visited is None: visited, order = set(), [] visited.add(node) order.append(node) for neighbor in graph[node]: if neighbor not in visited: dfs_recursive(graph, neighbor, visited, order) return order

The one-line difference, made concrete: on the exact same graph, BFS visits A, then ALL of A's direct neighbors, then all of THEIR unvisited neighbors — expanding outward in rings. DFS visits A, then dives into ONE neighbor, then ONE of that neighbor's neighbors, potentially reaching a node several hops away before ever touching a node that's only 2 hops away in a different direction. Run both labs above from the same start node and compare the visit-order lists directly — same graph, same start, genuinely different orders, purely because of pop-front vs pop-back.

When DFS is the right tool (and BFS isn't)

DFS is preferred when you need to explore a full path before deciding anything about it — cycle detection (next lab), topological sort (next lab), finding connected components, or exhaustively searching all paths (maze-solving, backtracking puzzles like Sudoku). BFS is preferred specifically when "shortest path" or "minimum steps" is the actual question — DFS can find *a* path, but offers no guarantee it's the shortest one, since it commits fully to one branch before backtracking rather than exploring proportionally to distance.

Interview-ready definition: Depth-First Search explores as far as possible along each branch before backtracking, implemented via an explicit stack (LIFO) or equivalently via recursion (the call stack). Unlike BFS, DFS provides no shortest-path guarantee in general graphs, but its natural "fully explore this branch before trying another" behavior makes it the standard tool for cycle detection, topological sorting, and exhaustive path/backtracking search.
05 — Not "just memorize O(V+E)"

Deriving O(V + E) by counting, against this exact graph

Both BFS and DFS are O(V + E). Instead of asserting that, let's count against the lab's running example graph: 6 vertices (A, B, C, D, E, F) and 7 edges.

VERTEX WORK
6 enqueues + 6 dequeues
Every vertex is added to the visited set and pushed onto the frontier exactly ONCE (the visited-check prevents re-adding it), and popped off exactly once. That's a constant amount of work per vertex → O(V) total across the whole run.
EDGE WORK
7 edges, each checked once
When a vertex is popped, the algorithm loops over ITS neighbor list. Summed across all vertices, that's exactly the total size of every adjacency list combined — which is 2×E for an undirected graph (each edge appears in two lists) or E for directed. Each edge is examined a constant number of times → O(E) total.

So the total work is (a constant amount of vertex bookkeeping) × V, plus (a constant amount of edge-checking) × E — added together, not multiplied, because vertex processing and edge scanning are two separate passes over two separate totals, not nested loops over each other. That sum is, by definition, O(V + E). Concretely for THIS graph: 6 vertices worth of enqueue/dequeue overhead, plus 7 edges worth of neighbor-scanning overhead — the step-through logs above will show exactly 6 "dequeue" lines and (in an undirected reading) up to 14 total neighbor-checks (7 edges × 2 directions), matching this derivation exactly.

ClaimWhy, mechanically
Each vertex is enqueued/pushed exactly onceThe visited-check happens BEFORE adding to the frontier, so a vertex can never be queued twice — this is what makes the "once per vertex" claim exact, not approximate
Each edge is examined a constant number of timesAn edge (u,v) is looked at when u is popped (scanning u's neighbor list) and, if undirected, again when v is popped — a fixed small constant, not something that grows with graph size
Total timeO(V) [vertex bookkeeping] + O(E) [edge scanning] = O(V + E)
Why this is NOT O(V × E) or O(V²): a common mistake is assuming that because you loop over vertices AND loop over their edges, the two costs multiply. They don't, because the inner "loop over edges" isn't repeated V times per vertex — each vertex's neighbor list is scanned exactly once, and the SUM of all neighbor-list lengths across every vertex equals the edge count (or twice the edge count for undirected graphs), not V times the edge count. The work is additive across the single combined pass, not multiplicative.

Problem 1 · Space cost, concretely

A social graph has 10,000 users, and on average each user follows 50 others (directed edges). Roughly how many total entries would an adjacency list store, versus how many cells an adjacency matrix would need? Which representation is clearly the right choice here, and why?

Show solution
Adjacency list: ~10,000 vertices x 50 average out-edges each = ~500,000 total (vertex, neighbor) entries stored. That's O(V + E) with E = 500,000. Adjacency matrix: 10,000 x 10,000 = 100,000,000 cells, REGARDLESS of how many follows actually exist -- because the matrix always allocates space for every possible pair, not just the ones that are actually connected. Adjacency list is overwhelmingly the right choice: 500K entries vs 100M cells is a 200x difference, and the vast majority of those 100M matrix cells would just store "0" (not following). This graph is extremely sparse -- each user connects to 50 out of 10,000 possible others, so E (500K) is nowhere close to V^2 (100M). Sparse graphs are the textbook case for adjacency lists.

Problem 3 · Trace DFS by hand, same graph

Same graph as Problem 2 (A-B, A-C, B-D, C-D, C-E, D-F). Using the iterative stack version with neighbors pushed in the order given (not reversed), trace DFS from A and give the visit order. Contrast it with BFS's order from Problem 2.

Show solution
Stack starts: [A] Pop A. Not visited -> visit A. Push unvisited neighbors B, C: stack=[B,C] Pop C (top of stack/LIFO). Not visited -> visit C. Push D, E: stack=[B,D,E] Pop E (top). Not visited -> visit E. No unvisited neighbors: stack=[B,D] Pop D (top). Not visited -> visit D. D's neighbors are B, C, F -- C is visited, B is not yet visited (still sitting on the stack), F is unvisited. Push unvisited: B, F -> stack=[B,B,F] (B appears twice because it was pushed once already and gets pushed again here before either copy has been popped -- this is exactly why the iterative version checks "if visited: continue" on pop, to safely discard stale duplicate entries). Pop F (top). Not visited -> visit F. No new neighbors: stack=[B,B] Pop B (top). Not visited -> visit B. Its neighbors A, D both visited: stack=[B] Pop B again. Already visited -> skip (continue). Problem 4 · Picking the right algorithm

You need to find the minimum number of button presses to get from level 1 to level 20 in a game, where pressing a button takes you to one of several other levels (an unweighted directed graph of level transitions). Should you use BFS or DFS, and what specifically about the problem tells you that?

Show solution
BFS. The phrase "minimum number of button presses" is a minimum-hop-count question in an UNWEIGHTED graph (each press costs the same "1 step", regardless of which button) -- that combination is the exact signature of a shortest-path-by-edge-count problem, which BFS solves by construction because it explores in expanding rings of distance from the start. DFS would find *a* sequence of presses that reaches level 20, but offers no guarantee it's the shortest one -- it might tunnel down a long chain of transitions before ever trying a shorter route, since it commits fully to one branch before backtracking. You'd have to explore every possible path and compare lengths to guarantee a minimum with DFS, throwing away its main efficiency advantage.
Problem 5 · Directed graph, one-directional reachability

A directed graph has edges A→B and B→C (one-way only). Is C reachable from A? Is A reachable from C? Explain why a directed edge doesn't give you the reverse connection "for free," and how this changes what a BFS/DFS starting from C alone would discover.

Show solution
C is reachable from A: following A->B->C, yes, 2 edges get you there. A is NOT reachable from C: there is no edge C->B or C->A (or any edge at all) pointing back the way we came, because A->B and B->C are directed edges that only encode "you can go this direction," not "these two nodes are mutually connected." A directed edge is fundamentally a one-way relationship, like a Twitter follow -- A following B doesn't create B following A as a side effect. A BFS or DFS starting from C, using C's outgoing edges only, would discover NOTHING beyond C itself in this graph (C has no outgoing edges here) -- it would report C as an isolated component from that direction, even though C is very much reachable from elsewhere. This is exactly why "is the graph connected" and "is every node reachable from node X" are different, direction-sensitive questions in a directed graph, unlike in an undirected graph where reachability is always symmetric.
