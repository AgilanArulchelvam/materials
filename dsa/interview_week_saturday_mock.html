STATION 1 — DSA · 9:00
9:00

Prompt: The orchestrator needs to detect, in a live stream of (tool_a, tool_b, timestamp) call-adjacency events, the first moment a genuine dependency CYCLE appears among tools that have ever been chained together — without ever re-scanning the full history from scratch on each new event. Design an online (incremental) cycle-detection algorithm: what state do you maintain, what happens on each new edge, and what's the amortized cost per event?

This combines Monday's graph-cycle-detection territory with a genuinely harder constraint: INCREMENTAL detection under a live stream, not a one-shot check on a static graph. The naive answer (re-run full cycle detection after every edge) is O(V+E) per event — the strong answer needs to beat that.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Names the naive approach (full DFS/Kahn's cycle check after every new edge) and explicitly states its cost, O(V+E) per event, as the baseline to beat
  • Proposes a Union-Find (disjoint set) based incremental approach for the common case, and correctly identifies its real limitation for DIRECTED graphs (Union-Find naturally detects cycles in undirected graphs; a directed cycle needs a different check)
  • Proposes the correct directed-graph approach: maintain reachability incrementally, and a new edge (u → v) creates a cycle if and only if v can already reach u — checkable via a bounded traversal from v, or via incrementally maintained reachability sets/a topological order that gets locally repaired
  • States the honest complexity trade-off: incremental cycle detection in general directed graphs doesn't have a simple O(1) amortized answer like Union-Find gives for undirected graphs — a real strong answer says so explicitly rather than overclaiming a clean bound
Weak answer
  • Proposes only the naive full-rescan approach with no attempt at an incremental improvement
  • Applies Union-Find directly to the directed case without noticing it doesn't correctly detect directed cycles
  • Claims an incorrect O(1) amortized bound for the general directed case without justification
  • Doesn't distinguish the directed-cycle detection problem from the undirected one at all
Show reference approach (only after your timer ends AND you've self-graded)
Baseline to beat: re-running a full DFS or Kahn's-algorithm cycle check from scratch after every new edge costs O(V + E) per event -- for a live stream, that's the naive answer, correct but not incremental. Why Union-Find alone doesn't solve this: Union-Find (disjoint set with path compression and union by rank) gives near-O(1) amortized cycle detection, but ONLY for UNDIRECTED graphs -- adding edge (u, v) creates a cycle iff find(u) == find(v) already. For a DIRECTED graph (tool A must run before tool B is directional), two nodes being in the same undirected-connected-component does NOT mean a directed cycle exists -- this is the key distinction a strong answer must name explicitly, since applying Union-Find naively to a directed adjacency stream gives WRONG answers (false positives on cycles that aren't actually directed cycles). Correct approach for the directed case: a new edge (u -> v) creates a cycle if and only if v can ALREADY reach u through existing edges -- if v could already reach u, then adding u -> v closes a loop: u -> v -> ... -> u. So on each new edge, the check reduces to "is there already a path from v to u?" -- a single BFS/DFS from v, bounded by the CURRENT graph's size, not the full historical edge count. This correctly detects the cycle at the moment it's created, but its cost per event is O(V + E) in the worst case too, UNLESS reachability is maintained incrementally (e.g. a reachability matrix updated incrementally, which trades O(V^2) space and update cost for O(1) per-query reachability checks -- a real engineering trade-off, not a free win). The honest complexity statement, which is what actually separates a strong answer here: incremental cycle detection in general directed graphs does NOT have a simple, universally-cheap amortized bound the way undirected Union-Find does -- the best practical approaches (incremental topological-order maintenance, or bounded reachability checks) have real costs that depend on graph structure and how frequently cycles must be detected versus how large the graph grows. A strong answer states this honestly -- "the naive per-event reachability check beats full re-scan by bounding the search to the CURRENT graph rather than re-deriving order from nothing, but I would NOT claim O(1) amortized here without qualification, unlike the undirected Union-Find case" -- rather than confidently overclaiming a bound that doesn't actually hold for the general directed problem. Recognizing the limits of your own claimed complexity is itself a signal a real interviewer is listening for, especially at this difficulty tier.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer

  • Names the concrete query the normalized design serves that JSON can't serve efficiently: "failure rate for tool X across ALL runs" requires scanning and filtering INSIDE every JSON blob (no usable index) versus a simple indexed query on a proper tool_calls table

  • Closes with the actual decision criterion, not just a list of pros/cons: "the normalized design costs one extra join for the single-run read case, in exchange for indexed cross-run queries and cheap partial updates — and cross-run tool analytics is a real, frequent access pattern for this system, so the join cost is worth paying"
Weak answer
  • Dismisses the JSON alternative without acknowledging its genuine advantage for the single-run read case
  • Can't name a SPECIFIC query that breaks down under the JSON design, stays abstract ("normalization is just better")
  • Doesn't mention the write-amplification cost of updating a JSON blob
  • No clear final decision criterion — just restates "normalization has trade-offs" without landing on why THIS system favors it
Show reference approach (only after your timer ends AND you've self-graded)
Concede the true part first, because a defense that pretends the challenge has no merit is less credible, not more: yes, a JSON array of tool calls on agent_run genuinely does mean fewer joins for reading ONE full run's tool call sequence in a single row fetch -- that's a real, honest advantage of the JSON approach, worth naming before defending against it. The query that breaks down under JSON, stated concretely: "failure rate for tool X across ALL runs in the last 24 hours" -- with tool calls normalized into their own table, this is a simple indexed query: WHERE tool_name = X AND called_at > now() - interval, using the (tool_name, called_at) composite index this week has built repeatedly. With tool calls buried inside a JSON array on agent_run, this same query requires scanning EVERY agent_run row, parsing its JSON, and filtering entries inside each blob -- no standard B-tree index can serve "find all JSON array entries across all rows matching tool_name = X" efficiently, since the index would need to be on the ARRAY CONTENTS, not the row itself. This is exactly the cross-run analytics query the eval dashboard needs constantly (this week's own Thursday sharding station discussed exactly this query), and it's precisely the kind of query normalization exists to make cheap. The write-side cost, equally concrete: updating a single tool call's status from "running" to "complete" mid-run, with the normalized design, is a single indexed UPDATE on one tool_calls row. With the JSON design, it requires reading the ENTIRE agent_run.tool_calls array, finding and modifying the one relevant entry in application code, and rewriting the WHOLE JSON blob back -- for a run with many tool calls, this is real, avoidable write amplification on every single status update, of which there are many per run. The closing decision criterion, which is what a strong answer must land on explicitly rather than trailing off: the normalized design costs exactly one extra JOIN for the single-run read case, which is a small, bounded, indexed cost -- in exchange for making cross-run analytical queries (this system's actual, frequent access pattern, not a hypothetical one) efficient AND making individual tool-call updates cheap instead of write-amplified. Given that this system genuinely needs both of those things regularly, the one-join cost is the correct trade to accept -- which is a fundamentally different, more defensible answer than "normalization is always better," because it's grounded in THIS system's actual query mix rather than a general rule.

STATION 4 — PYTHON FUNDAMENTALS · 5:00
5:00

Prompt: The orchestrator holds a long-lived Python process handling many runs over hours. Explain CPython's memory model precisely: reference counting versus the generational garbage collector, why BOTH exist rather than just one, and what specifically a reference CYCLE is and why refcounting alone can't reclaim it.

Directly reuses python/cpython_internals.html and python/memory_and_scoping.html's territory. Five minutes, cold — the hardest and final Python station of the week.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • States reference counting precisely: every object has a count of references to it; the count increments on assignment/passing, decrements when a reference goes out of scope or is reassigned; the object is freed IMMEDIATELY when the count hits zero
  • Explains precisely why refcounting alone is insufficient: a reference CYCLE (object A references B, B references A, and nothing outside the cycle references either) means neither object's count ever reaches zero, even though both are genuinely unreachable garbage from the program's perspective
  • States what the generational garbage collector does: periodically scans for groups of objects that reference each other but are unreachable from any root (a variable, the stack, a global), and reclaims cycles that pure refcounting misses
  • Explains the "generational" part specifically: objects are grouped by age (generations 0, 1, 2), young objects are collected far more frequently than old ones, based on the empirical observation that most objects die young — this is a real performance optimization, not an arbitrary detail
Weak answer
  • Says "Python has garbage collection" without describing refcounting as the PRIMARY mechanism at all
  • Can't explain what a reference cycle actually is or why it specifically defeats refcounting
  • Doesn't know the GC exists specifically to catch what refcounting misses — treats it as a redundant or unrelated second system
  • No mention of generations, or can't explain why age-based collection frequency makes sense
Show reference approach (only after your timer ends AND you've self-graded)
Reference counting, CPython's PRIMARY memory reclamation mechanism: every object carries an integer count of how many references point to it. Assigning a reference, passing an object to a function, or storing it in a container increments the count; a reference going out of scope, being reassigned, or explicitly deleted decrements it. The moment an object's refcount hits zero, CPython frees it IMMEDIATELY -- not on some later sweep, but synchronously at the point the count reaches zero. This is why refcounting gives Python its characteristic immediate, deterministic cleanup for the vast majority of objects (e.g. a local variable's object is freed the instant the function returns and nothing else references it). Why refcounting alone is insufficient -- the reference cycle problem, stated precisely: consider object A with an attribute referencing object B, and B with an attribute referencing back to A. If nothing OUTSIDE this pair references either A or B, both are genuinely unreachable garbage -- the program can never reach them again through any variable, the stack, or a global. But each one still has a refcount of at least 1 (A is referenced by B, B is referenced by A), so neither count EVER reaches zero through refcounting alone -- the memory leaks, permanently, unless something else intervenes. What the generational garbage collector does: periodically, it scans for groups of objects that reference each other in a way that makes them collectively unreachable from any ROOT (a local variable, the call stack, module globals) -- essentially, it can detect cycles where the total refcount within the group only comes from OTHER members of the same group, none from outside it. When it finds such a cycle, it reclaims the whole group, which refcounting structurally cannot do on its own. Why "generational" specifically, the mechanism-level detail that separates a strong answer from a merely correct one: CPython buckets objects into generations (0 = youngest, up to 2 = oldest) based on how many collection cycles they've survived. Generation 0 is collected far more often than generation 1, which is collected far more often than generation 2. This is a deliberate performance optimization based on the empirical "generational hypothesis" -- most objects that become garbage do so shortly after creation (a temporary list, a short-lived loop variable), so scanning young objects frequently catches most garbage cheaply, while objects that have survived several collections are statistically likely to live much longer, so scanning them as often would be wasted work. For a long-lived orchestrator process specifically, this matters concretely: long-lived state (connection pools, caches) should settle into an older generation and get scanned rarely, while short-lived per-request objects get reclaimed quickly in generation 0 -- exactly the profile a long-running server process should expect and benefit from.
