01 — Counting, not guessing

Deriving time complexity by counting operations

Start here, before any code. Imagine you're looking for a friend's name in a phone book. If the book is in no particular order, you might have to check every single page before you find them (or confirm they're not there) — double the pages, double your worst-case effort. That relationship between "how big the input is" and "how much work you do" is all Big-O measures. It doesn't care if you're a fast reader or a slow reader (that's like CPU speed) — it cares about the shape of how effort scales as the phone book gets bigger.

To derive Big-O for real: write the operation as code, then count how many times its dominant operation runs as a function of input size n, then drop constants and lower-order terms — because for large enough n, only the fastest-growing term matters.

def find_max(items): # n = len(items) best = items[0] # 1 operation for x in items: # runs n times if x > best: # 1 comparison, EVERY iteration best = x return best # total work ≈ 1 + n comparisons → drop the constant → O(n)

Interview-ready definition: Big-O notation describes an asymptotic upper bound on the growth rate of an algorithm's resource usage (time or space) as input size n approaches infinity, expressed by keeping only the highest-order term and discarding constant factors and lower-order terms — because those are the terms that dominate the count once n is large, regardless of hardware.
02 — Same algorithm, different luck

Best, average, and worst case — and when they diverge

Start here, before any code. Think about searching for your keys in a messy room. Best case: they're right on the table by the door — found instantly. Worst case: they're in the very last drawer you check, in the very last room. Average case: somewhere in the middle, statistically. The algorithm — "check drawers one by one" — never changed; only where the keys happened to be changed how much work you did.

For linear search specifically: best case is O(1) — the target is the first element. Worst case is O(n) — the target is last, or absent entirely, so every element gets checked. Average case is also O(n) (specifically ~n/2 comparisons for a random position) — the constant factor differs from worst case, but dropping constants means both are described as O(n). These cases diverge most dramatically for algorithms like quicksort: average case O(n log n), but a worst case of O(n²) if the pivot choice is consistently bad (e.g., always picking the first element on already-sorted input).

Why "average case" isn't just optimism: interviewers care about worst case by default because it's a guarantee — average case describes typical behavior but says nothing about the ceiling. A system that's O(1) on average but O(n) worst case can still have catastrophic tail latency if an adversarial or unlucky input triggers that worst case.
03 — Contiguous memory vs. scattered nodes

Singly vs. doubly linked lists, and the trade-off vs. arrays

Start here, before any code. An array is like a row of numbered parking spaces — to find space #7 you can walk straight there because you know exactly how far #7 is from #0. A linked list is like a scavenger hunt — each clue (node) tells you where to find the next one, but only the next one. You can't jump to the 7th clue without following all six before it.

An array stores elements in contiguous memory, so any index can be computed directly (base_address + index * element_size) — O(1) random access. But inserting or deleting in the middle requires shifting every subsequent element, O(n). A singly linked list stores each value alongside a pointer to the next node — no contiguous memory required, so inserting/deleting at a known position is O(1) once you're there (no shifting), but reaching that position requires walking from the head, O(n), and there's no way to go backward. A doubly linked list adds a prev pointer to each node, enabling O(1) backward traversal and O(1) deletion given only a reference to the node (no need to track its predecessor separately) — at the cost of extra memory per node and more pointers to keep consistent.

class Node: # singly linked def __init__(self, value): self.value = value self.next = None class DNode: # doubly linked def __init__(self, value): self.value = value self.next = None self.prev = None

Interview-ready definition: a linked list trades O(1) random access (which arrays have via direct address computation) for O(1) insertion/deletion at known positions without shifting — because nodes are independently allocated and connected only by pointers, not laid out contiguously. A doubly linked list additionally trades memory (one extra pointer per node) for O(1) deletion given a node reference and bidirectional traversal.

def reverse(head): prev = None curr = head while curr: nxt = curr.next # save before we overwrite it curr.next = prev # flip the pointer backward prev = curr curr = nxt return prev # prev is now the new head
The classic reversal bug: if you set curr.next = prev before saving nxt = curr.next, you've just overwritten your only path forward — the rest of the list becomes unreachable. Save the forward pointer first, always.

Problem 1 · Counting operations
def has_duplicate(items): for i in range(len(items)): for j in range(i + 1, len(items)): if items[i] == items[j]: return True return False

Derive the Big-O by counting comparisons as a function of n = len(items).

Show solution
O(n²) For i=0, j ranges over n-1 values. For i=1, j ranges over n-2 values. ... Total comparisons ≈ (n-1) + (n-2) + ... + 1 = n(n-1)/2 = (n² - n)/2. Dropping the constant factor (1/2) and the lower-order term (-n/2) leaves the highest-order term: O(n²).
Problem 2 · Best vs worst case

A function checks if a list is sorted by comparing each adjacent pair and returning False the moment it finds an out-of-order pair. What's the best case and worst case, and what input triggers each?

Show solution
Best case: O(1) — the very first pair (items[0], items[1]) is already out of order, so it returns False immediately. Worst case: O(n) — the list IS fully sorted (or only the very last pair is out of order), forcing every adjacent pair to be checked before concluding True (or finding the violation at the end).
Problem 3 · Array vs linked list choice

You're building a browser's back/forward history where you constantly add new pages, occasionally jump back several pages, but never need to jump to an arbitrary numbered position. Would a doubly linked list or an array serve better, and why?

Show solution
Doubly linked list. The access pattern is purely sequential (forward/back one or a few steps at a time via prev/next pointers), never "give me page #47 directly" (which is where arrays' O(1) random access would matter). Meanwhile, inserting a new page after the current one, or truncating forward history when a new page is visited, is O(1) with pointer rewiring instead of O(n) array shifting.
Problem 4 · Reverse a linked list, trace it
def reverse(head): prev = None curr = head while curr: nxt = curr.next curr.next = prev prev = curr curr = nxt return prev

Trace this on the list 1 → 2 → 3 → None. What is prev after each loop iteration, and what's the final returned head?

Show solution
Iteration 1: nxt=2, node 1's next -> None, prev=1, curr=2. List so far: 1->None Iteration 2: nxt=3, node 2's next -> 1, prev=2, curr=3. Chain so far: 2->1->None Iteration 3: nxt=None, node 3's next -> 2, prev=3, curr=None. Chain: 3->2->1->None Loop ends (curr is None). Returns prev = node 3. Final list: 3 -> 2 -> 1 -> None — fully reversed, O(n) time, O(1) extra space.
Problem 5 · Delete a node given only its reference

In a SINGLY linked list, you're handed a reference to a node in the middle (not the head, not the tail) — but you have no reference to the list's head and no way to find the predecessor. Can you delete this node in O(1)? If not directly, what could you do instead, and does it work if the node is the last one?

Show solution
You cannot truly delete it (unlink it from its predecessor) in O(1) without a predecessor reference — singly linked nodes have no "prev" pointer, and finding the predecessor requires walking from the head, O(n). The common trick: copy the NEXT node's value into this node, then point this node's `next` to skip over the next node (this.value = this.next.value; this.next = this.next.next). This fakes a deletion of "this" node in O(1) by actually deleting the node after it. This does NOT work if the given node is the last node — there's no next node to copy from, so the predecessor must be found the normal O(n) way (or the structure needs to be a doubly linked list, where prev is already known).
Problem 6 · Delete a middle node, trace the pointer rewiring

List: 10 → 20 → 30 → 40 → None. Delete the node holding 30 (you have a reference to its predecessor, the node holding 20). Write the single line of pointer rewiring, and explain why this is O(1) once the predecessor is known but O(n) to get there from the head in the general case.

Show solution
prev.next = prev.next.next # i.e. node(20).next = node(40) The node holding 30 is now unreferenced by anything reachable from head (node 20 points straight to node 40), so it becomes garbage. This single pointer reassignment is O(1) — no shifting, no copying. BUT: finding "the node holding 20" (the predecessor of the target) required walking from head — 10 -> 20 — which is O(k) where k is the position, worst case O(n). This is the key nuance: the REWIRE is O(1), the WALK to find the predecessor is what makes deletion-by-value O(n) overall in a singly linked list. If you already hold a reference to the predecessor (as this problem states), the rewiring step itself is O(1).
Problem 7 · Reverse edge cases: empty and single-node

Using the reverse(head) function from Problem 4, trace what happens when head = None (empty list), and separately when the list has exactly one node (5 → None). Does the algorithm need special-casing for either?

Show solution
Empty list (head = None): curr = None immediately, so `while curr:` never executes. The function returns prev, which is still None. Correct — an empty list reversed is still empty. No special-casing needed. Single node (5 -> None): Iteration 1: nxt = curr.next = None. curr.next = prev (None) -- node 5 now points to None (unchanged, it already pointed to None). prev = curr (node 5). curr = nxt (None). Loop ends. Returns prev = node 5. Result: 5 -> None, identical to the input — correct, since reversing a single element changes nothing. No special-casing needed either: the general while-loop logic handles both edge cases for free, which is a sign of a well-designed iterative algorithm.
