A heap is a tree that lives inside a plain array — no pointers, just index arithmetic.

A binary heap looks like a tree when you draw it, but it's implemented as a flat array where a node's children are found with pure arithmetic on its index — no left/right pointers anywhere. 01 — A shape rule, stored without any pointers

Min-heap vs max-heap, and the array trick that avoids pointers entirely

Start here, before any code. Picture a company org chart with one very specific extra rule: every manager must earn LESS than everyone who reports to them, all the way down (a "min-heap" org chart) — or, for a max-heap, every manager earns MORE than their reports. Critically, this rule says nothing about how siblings compare to each other, or how a niece compares to an uncle — only along direct manager-to-report lines. That's the heap property: weaker than "fully sorted," but strong enough to guarantee one very useful fact — the CEO (the root) is always the minimum (or maximum) of the entire organization.

The clever part: a heap is a complete binary tree (every level full except possibly the last, which fills left-to-right with no gaps) — and a complete tree's shape is so predictable that you can store it in a flat array and compute parent/child relationships with pure arithmetic, no pointers needed at all:

For a node at array index i:
parent(i) = (i - 1) // 2  ·  left_child(i) = 2i + 1  ·  right_child(i) = 2i + 2

Why this works: in a complete binary tree filled left-to-right level by level, node i's two children are ALWAYS at exactly 2i+1 and 2i+2 — this isn't a coincidence, it falls directly out of "complete" meaning no gaps. Compare that to a general binary tree (like a BST), which needs an actual .left / .right pointer per node because its shape is arbitrary and unpredictable — a heap's shape is so constrained that the position IS the pointer.

Min-heap

Every parent ≤ both children. The root (index 0) is always the SMALLEST element in the entire heap. Used for: priority queues where "lowest priority number = served first" (e.g. Dijkstra's algorithm, task schedulers), or a running minimum.

Max-heap

Every parent ≥ both children. The root is always the LARGEST element. Used for: heap sort (repeatedly extract the max to build a descending sequence), or a running "top-k largest" tracker.

Interview-ready definition: a binary heap is a complete binary tree satisfying the heap property (min-heap: every parent ≤ its children; max-heap: every parent ≥ its children), stored as a flat array where a node at index i has parent at (i-1)//2, left child at 2i+1, and right child at 2i+2. Completeness (no gaps except possibly at the end of the last level) is exactly what makes this pointer-free array encoding valid — an arbitrary (non-complete) binary tree cannot be encoded this way without wasting array space on absent nodes.
02 — New element enters at the bottom, then earns its way up

Insert — sift-up (bubble-up), animated swap by swap

Start here, before any code. A new hire joins the min-heap org chart at the very bottom (the array's next open slot — completeness demands new elements go there, not anywhere convenient). If that new hire earns LESS than their brand-new manager, that violates the min-heap rule — so they swap places with their manager. Now compare again against the NEW manager (their former manager's manager), and keep swapping upward until either they hit someone who earns even less than them, or they reach the very top.

def sift_up(heap, i): while i > 0: parent = (i - 1) // 2 if heap[i] < heap[parent]: # min-heap: child smaller than parent — violation heap[i], heap[parent] = heap[parent], heap[i] # swap i = parent # continue checking from the new position else: break # heap property restored — stop
INSERT A VALUE — WATCH SIFT-UP SWAP STEP BY STEP
Interview-ready definition: sift-up (bubble-up) restores the heap property after appending a new element to the end of the array by repeatedly comparing it against its parent (at index (i-1)//2) and swapping upward while the heap property is violated, terminating as soon as a valid parent is found or the root is reached. Because a heap's height is O(log n), sift-up performs at most O(log n) swaps.
03 — Root removed, last element promoted, then demoted back down

Extract — sift-down (bubble-down), animated swap by swap

Start here, before any code. Extracting the minimum means removing the CEO (the root) — but you can't just leave an empty seat at the top. The standard trick: take the very LAST employee in the array (the most recently added, at the bottom-right of the tree) and temporarily promote them to CEO, then let them "prove" they deserve it by repeatedly comparing against their new children and swapping down with whichever child is smaller, until either they're smaller than both children, or they've sifted all the way to a leaf position.

def sift_down(heap, i, size): while True: left, right = 2*i + 1, 2*i + 2 smallest = i if left < size and heap[left] < heap[smallest]: smallest = left if right < size and heap[right] < heap[smallest]: smallest = right if smallest == i: break # both children are >= current — heap property restored heap[i], heap[smallest] = heap[smallest], heap[i] # swap with the SMALLER child i = smallest # continue checking from the new position
EXTRACT THE MIN — WATCH SIFT-DOWN SWAP STEP BY STEP
The one detail people forget: sift-down must compare against BOTH children and swap with whichever is SMALLER (for a min-heap), not just the left child. Swapping with the larger child, or always picking left, can leave the smaller child still violating the heap property relative to its new parent — the algorithm must specifically find min(left, right) among existing children before deciding whether/where to swap.
Interview-ready definition: sift-down (bubble-down) restores the heap property after replacing the root with the heap's last element by repeatedly comparing the node against both its children and swapping with the smaller one (min-heap) if it violates the heap property, continuing from the new position until no children violate it or a leaf is reached. Like sift-up, this takes at most O(log n) swaps since it traces at most one root-to-leaf path.
04 — Why O(log n) per operation, and the surprising O(n) build

Deriving the complexity — and why heap-build isn't O(n log n)

Both sift-up and sift-down trace a single path from one level of the tree to another — sift-up from a leaf toward the root, sift-down from the root toward a leaf. A complete binary tree with n nodes has height exactly ⌊log₂ n⌋ (each level roughly doubles the node count of the previous one, so the number of levels needed for n nodes grows logarithmically). Since each sift operation does at most one comparison-and-possible-swap per level, and there are O(log n) levels, each operation is O(log n) — not by assertion, but because that's literally the count of levels a single root-to-leaf (or leaf-to-root) path can have.

The surprising part: building a heap from n arbitrary elements is O(n), not O(n log n)

The naive assumption is "n inserts, each O(log n), so building a heap is O(n log n)." That's true if you insert one at a time via sift-up. But there's a smarter way — heapify — that starts from an arbitrary array and calls sift-down on every NON-leaf node, working from the bottom of the tree upward (from the last non-leaf node back to the root). This turns out to be O(n), and here's the intuitive reason why:

def heapify(arr): n = len(arr) # start at the last NON-LEAF node — leaves need no sift-down, they have no children for i in range(n // 2 - 1, -1, -1): sift_down(arr, i, n)

Most nodes in a heap are near the bottom, and sift-down from near the bottom does almost no work. Half of all nodes are leaves (0 levels to sift down through — instantly done). A quarter of all nodes are one level above the leaves (at most 1 swap). An eighth are two levels up (at most 2 swaps). In general, the number of nodes at height h from the bottom is roughly n / 2^(h+1), and each of THOSE nodes costs at most h swaps to sift down. Multiplying and summing across all levels:

Total work ≈ Σ (n / 2^(h+1)) × h  for h = 0 to log₂n
This sum converges to a constant multiple of n — NOT n log n — because the number of nodes that could possibly need the FULL log n swaps shrinks exponentially (there's only ONE root), while the nodes that dominate by COUNT (the leaves and near-leaves) each do almost no work.

The intuitive takeaway (no rigorous proof needed for an interview): in "insert one at a time" building, EVERY element potentially sifts up through O(log n) levels, because at insertion time the heap can already be tall. In bottom-up heapify, the vast majority of elements (leaves and near-leaves) are already close to their final resting depth and need little to no sifting — only the few nodes near the root, of which there are exponentially fewer, ever pay the full O(log n) cost. The asymmetry between "many cheap operations" and "few expensive ones" is what collapses the total from O(n log n) down to O(n).
Interview-ready definition: a single heap insert or extract-min/max operation costs O(log n), bounded by the heap's height, since sift-up and sift-down each traverse at most one root-to-leaf path. Building a heap from n arbitrary elements via bottom-up heapify (calling sift-down on each non-leaf node from the last internal node up to the root) costs O(n) total, not O(n log n), because the summed cost across all levels — weighted by how many nodes sit at each level and how far each can sift — converges to a constant multiple of n, since the overwhelming majority of nodes are near the bottom where sift-down does little to no work.

Problem 1 · Index math by hand

For a node at array index 5, compute its parent, left child, and right child indices. Then verify: if the array is [1, 3, 2, 7, 8, 4, 9], is the node at index 5 (value 4) correctly positioned relative to its computed parent under the min-heap property?

Show solution
parent(5) = (5-1)//2 = 4//2 = 2 left_child(5) = 2*5+1 = 11 right_child(5) = 2*5+2 = 12 Array has only 7 elements (indices 0-6), so indices 11 and 12 are out of bounds -- node 5 (value 4) is a LEAF, it has no children. That's expected and fine. Checking the min-heap property against its parent: parent index = 2, array[2] = 2. Is array[5]=4 >= array[2]=2? Yes, 4 >= 2 -- the min-heap property holds here (parent <= child).
Problem 2 · Trace sift-up by hand

Min-heap array: [1, 3, 2, 7, 8]. Insert 0 (append to the end, then sift up). Show each comparison and swap, and the final array.

Show solution
Append 0: array = [1, 3, 2, 7, 8, 0], new element at index 5. Sift up from index 5: parent(5) = (5-1)//2 = 2. array[2] = 2. Is array[5]=0 < array[2]=2? Yes -- swap. array = [1, 3, 0, 7, 8, 2]. Now i = 2. parent(2) = (2-1)//2 = 0. array[0] = 1. Is array[2]=0 < array[0]=1? Yes -- swap. array = [0, 3, 1, 7, 8, 2]. Now i = 0. i = 0 is the root -- loop ends (no parent to compare against). Final array: [0, 3, 1, 7, 8, 2]. Two swaps total, matching the height of the tree at that path (root is 2 levels up from index 5).
Problem 3 · Trace sift-down by hand

Min-heap array: [1, 3, 2, 7, 8, 9]. Extract the min (remove index 0, move the LAST element (9) to index 0, shrink the array, then sift down). Show each comparison and swap.

Show solution
Remove array[0]=1 (this is the returned minimum). Move last element (9) to index 0, shrink array: array = [9, 3, 2, 7, 8], size = 5. Sift down from index 0: left(0)=1, right(0)=2. array[1]=3, array[2]=2. Smallest of {array[0]=9, array[1]=3, array[2]=2} is array[2]=2 -- smallest = index 2. smallest(2) != i(0) -- swap. array = [2, 3, 9, 7, 8]. i = 2. left(2)=5, right(2)=6. Both >= size(5) -- no children exist (index 2 is a leaf in this 5-element array). smallest stays i(2) -- loop ends. Final array: [2, 3, 9, 7, 8]. Returned value: 1 (the original minimum). One swap total.
Problem 4 · Why swap with the SMALLER child specifically

Min-heap sift-down at index 0: array = [10, 2, 3]. If sift-down incorrectly always swapped with the LEFT child regardless of which is smaller, trace what would happen here and explain why it produces an invalid heap.

Show solution
Correct behavior: left(0)=1 (value 2), right(0)=2 (value 3). Smaller of the two children is array[1]=2. Swap 10 and 2: array = [2, 10, 3]. Check: is this a valid min-heap? array[0]=2 <= array[1]=10 yes, array[0]=2 <= array[2]=3 yes. Valid. Incorrect "always swap left" behavior: swap array[0]=10 with array[1]=2 regardless (this happens to be the same swap here since left already was smaller) -- but consider array = [10, 3, 2] instead. Always-swap-left would swap 10 and 3: array = [3, 10, 2]. Check: array[0]=3 <= array[2]=2? NO -- 3 > 2, heap property VIOLATED at the root versus its right child, and the algorithm would incorrectly stop here (thinking root vs one checked child was enough), leaving an invalid heap. This is exactly why sift-down must find the minimum of BOTH children before deciding whether and where to swap -- checking only one child can miss a violation on the other side.
Problem 5 · Build vs insert-one-at-a-time cost

You have 1000 unsorted numbers and need to build a heap from them once, with no further inserts afterward. Compare the total cost of (a) inserting all 1000 one at a time via sift-up, versus (b) placing them all in an array and running bottom-up heapify. Which is asymptotically better, and does the difference actually matter here in practice?

Show solution
(a) Insert one at a time: each of the 1000 inserts costs O(log n) in the worst case (the heap is already close to full size for most of the inserts), giving a total of O(n log n) = O(1000 * log2(1000)) = O(1000 * ~10) = O(10,000) comparisons in the worst case. (b) Bottom-up heapify: O(n) = O(1000) total, roughly 10x fewer worst-case comparisons than (a) for this size. Asymptotically, (b) is strictly better -- O(n) beats O(n log n) for any n large enough to matter. In PRACTICE, for n=1000 the constant-factor difference is real but not dramatic (thousands of comparisons either way is fast on modern hardware) -- the O(n) vs O(n log n) gap becomes far more consequential as n grows into the millions or billions, which is exactly why library implementations (e.g. Python's heapq.heapify) always use the bottom-up approach rather than looping insert calls when building from a known, complete initial dataset.
