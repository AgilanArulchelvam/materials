A hash map is an array wearing a disguise — the "magic" is just arithmetic that turns a key into an index.

Every hash map is, underneath, a plain array (the "bucket array") plus a function that converts any key into an array index. This lab computes that arithmetic live — hash(key) % table_size, shown as real numbers — then deliberately forces two keys into the same bucket so you can watch a collision get resolved two different ways: chaining (a linked list per bucket) and open addressing (probing to the next free slot). 01 — Turning anything into a number, reliably

Hash function properties: deterministic, uniform distribution

Start here, before any code. Imagine a coat-check counter at a huge venue with exactly 8 numbered racks. The attendant needs a rule for which rack to hang your coat on, using only your name — and that rule needs two properties: (1) if you come back later and give the same name, they need the SAME rack every time (otherwise they can never find your coat again), and (2) the rule shouldn't send everyone named with a common first letter to the same rack, or that one rack would be overflowing while others sit empty. Property 1 is determinism. Property 2 is uniform distribution.

A hash function takes a key (a string, a number, any hashable value) and produces an integer — the "hash code." A hash map then takes that integer modulo the table size to get an actual array index that's guaranteed to be in bounds. This lab uses a simple polynomial rolling hash for strings, the same basic idea Python, Java, and most languages use under the hood (with more sophistication for security and distribution quality):

def simple_hash(key: str) -> int: h = 0 for ch in key: h = h * 31 + ord(ch) # 31 is a small prime — spreads bits well, cheap to compute return h def bucket_index(key: str, table_size: int) -> int: return simple_hash(key) % table_size # modulo brings any integer into [0, table_size)

Interview-ready definition: a hash function maps keys of arbitrary type to a fixed-size integer range, and a well-behaved one for hash-table use is deterministic (identical input always yields identical output) and approximately uniform (dissimilar keys are unlikely to map to the same bucket after taking the result modulo the table size). Cryptographic hash functions add a third property (irreversibility) that hash tables don't need; hash-table hash functions optimize purely for speed and distribution quality, not security.
02 — Two keys, one bucket — now what?

Collision handling: chaining vs open addressing

Start here, before any code. Back at the coat check: no matter how good the attendant's rule is, with enough coats and only 8 racks, eventually two different people's names WILL map to the same rack — this is unavoidable once you have more possible keys than buckets (the pigeonhole principle, guaranteed, not just likely). The question is what the attendant does next. One option: hang a second coat on the SAME hook, so that rack now holds a little list of coats — this is chaining. Another option: if rack 3 is full, walk to rack 4, then rack 5, until an empty one is found — this is open addressing.

Chaining

Each bucket holds a small linked list (or dynamic array) of ALL keys that hashed there. Insert: hash, then append to that bucket's list. Lookup: hash, then linearly scan that bucket's list for the matching key. Never "runs out of room" — buckets can grow arbitrarily, though a very long chain degrades that bucket's lookups toward O(chain length).

Open addressing (linear probing)

Every bucket holds AT MOST one key. On collision, probe forward (bucket+1, bucket+2, ... wrapping around) until an empty slot is found. Lookup: hash, then walk forward the same way, comparing keys, until you find a match or hit a genuinely empty slot (which means "not present"). Deletions need special handling — a "tombstone" marker, not a true empty slot, or probing chains would incorrectly break early.

Interview-ready definition: a collision occurs when two distinct keys hash to the same bucket index. Chaining resolves this by storing a secondary structure (typically a linked list) per bucket holding all colliding keys. Open addressing resolves it by probing according to a deterministic sequence (linear, quadratic, or double hashing) to find an alternative empty slot in the same array, requiring the table to always have free capacity and requiring tombstones (not true deletion) to keep probe sequences intact after a removal.
03 — When "mostly full" becomes a performance problem

Load factor and resizing / rehashing

Start here, before any code. Back at the coat check one more time: with 8 racks and only 2 coats, collisions are rare — plenty of empty racks to spread out across. But once you're checking in your 30th coat with only 8 racks, EVERY new coat collides with something, chains get long, and finding any specific coat means checking racks (or scanning long lists) one by one. The venue's fix: get more racks, and re-sort every existing coat onto the new, bigger rack layout. That's exactly what a hash map's resize operation does.

Load factor = (number of stored keys) / (number of buckets). Most hash map implementations resize (commonly doubling the bucket count) once load factor crosses a threshold — typically around 0.7. Resizing means allocating a bigger bucket array and re-hashing every existing key into it, because the modulo (hash % table_size) changes when table_size changes — a key's bucket index is NOT portable across different table sizes.

Why re-hashing is unavoidable, not just "extra work": a key's bucket index is hash(key) % table_size. Change table_size from 4 to 8, and nearly every key's index changes too (e.g. hash=13: 13%4=1, but 13%8=5 — a completely different bucket). There is no way to "keep the old positions" after a resize — every single existing key must be re-inserted into the new, larger array. This is exactly why resize is an O(n) operation (touching all n existing keys) even though any INDIVIDUAL insert is normally O(1) — but because resizes happen rarely (only when crossing the threshold, and each resize roughly doubles capacity), the COST of resizing, spread out ("amortized") over all the inserts that happen between resizes, still averages out to O(1) per insert.
Interview-ready definition: load factor is the ratio of stored elements to bucket count, and it is the key signal for when to resize a hash table — as it approaches 1 (or a configured threshold below 1), collision frequency and chain/probe length grow, degrading average-case performance. Resizing allocates a larger bucket array (commonly double the size) and re-hashes every existing key into it, since bucket indices are a function of table size and are not preserved across a resize. Despite resizing being O(n), the amortized cost per insertion across the table's lifetime remains O(1), because resizes become exponentially less frequent as the table grows.
04 — Constructing the failure on purpose

Why average-case O(1) degrades to worst-case O(n)

Every complexity claim about hash maps — O(1) insert, lookup, delete — is an AVERAGE-case claim that assumes reasonably uniform distribution. It is possible to construct a pathological input where every single key collides into the same bucket, and this section builds exactly that, so the O(n) worst case isn't an abstract warning but something you can watch happen.

PATHOLOGICAL INPUT — EVERY KEY FORCED TO COLLIDE (CHAINING)

These 5 keys were specifically chosen because hash(key) % 8 is identical for all of them — every insert collides with everything already there.

ScenarioWhat happens to bucket 3's chainLookup cost for the last-inserted key
Well-distributed keysEach bucket gets ~1 key on average (n keys / 8 buckets)O(1) — scan a chain of length ~1
Pathological (all same bucket)Every single key lands in ONE bucket — a chain of length nO(n) — must scan the entire chain, exactly like a linked list search

This is the mechanism, not just an assertion: with all n keys sharing one bucket, the hash table has degenerated into exactly one linked list wearing a hash-table costume. Lookup now means walking that one chain from the front, comparing keys one by one — indistinguishable in cost from searching an unsorted linked list. This is also precisely why some languages' hash-table implementations (e.g. Java's HashMap since Java 8) convert an unusually long chain into a balanced tree internally, capping this specific worst case at O(log n) instead of O(n) — a mitigation, not a full fix, since it only helps once a chain has already grown suspiciously long.

Real-world relevance — hash flooding attacks: if an attacker can predict or influence a service's hash function (e.g. a web server hashing form-parameter names into a dictionary), they can deliberately submit thousands of keys engineered to all collide, forcing every bucket lookup toward O(n) and effectively causing a denial-of-service through algorithmic complexity alone — no buffer overflow or memory exhaustion required, just degraded average case turned into guaranteed worst case. This is why many languages now randomize their hash seed per process (Python's PYTHONHASHSEED, for instance) — so an attacker can't predict which keys will collide without also knowing that process's random seed.
Interview-ready definition: a hash table's O(1) average-case time complexity for insert/lookup/delete assumes keys are distributed roughly uniformly across buckets by the hash function. Worst-case O(n) arises when a hash function or an adversarially chosen input set causes many or all keys to collide into the same bucket, degenerating that bucket's chain (or open-addressing probe sequence) into a linear structure that must be scanned entirely — a failure mode independent of the table's average behavior and exploitable in security contexts if the hash function's collision behavior is predictable to an attacker.

Problem 2 · Chaining vs open addressing trade-off

A system needs to guarantee it never allocates memory unpredictably at insert-time (a hard real-time constraint), and deletions are extremely rare. Which collision strategy fits better, and which specific property of the OTHER strategy would violate the real-time constraint?

Show solution
Open addressing fits better here. Its collision resolution (probing to another slot in the SAME pre-allocated array) does not require any new memory allocation at insert time -- it's just arithmetic and array writes within already-reserved space. Chaining would violate the constraint: appending to a bucket's linked list (or growing a bucket's dynamic array) typically requires allocating a new node or reallocating the bucket's backing array, and allocation timing is exactly the kind of unpredictable-latency operation a hard real-time system needs to avoid. Since deletions are rare here, open addressing's usual weak point (tombstone bookkeeping on delete) barely matters, making it a clean fit on both counts.
Problem 3 · Load factor and resize trigger

A hash table has 6 buckets and a resize threshold of load factor 0.75. After inserting the 4th key (no deletions), does it resize? Show the load factor calculation, and state the new bucket count if a resize (doubling) is triggered.

Show solution
Load factor after 4th key = keys / buckets = 4 / 6 = 0.6667 0.6667 < 0.75 (the threshold) -- no resize yet after the 4th key. It would resize after the 5th key: 5/6 = 0.8333, which crosses 0.75. At that point, doubling gives a new bucket count of 12, and all 5 existing keys get re-hashed with % 12 instead of % 6 -- an O(5) = O(n) one-time cost for that resize, immediately followed by continued O(1) average-case inserts until the next threshold crossing.
Problem 4 · Why re-hashing can't be skipped

A key K has hash(K) = 29. In a 4-bucket table, what index does it occupy? After resizing to 8 buckets, what index would it occupy? Explain concretely why simply copying K from its old array slot into the same-numbered slot in the new, bigger array would be incorrect.

Show solution
In a 4-bucket table: 29 % 4 = 1 (29 = 7*4 + 1) -- bucket 1. In an 8-bucket table: 29 % 8 = 5 (29 = 3*8 + 5) -- bucket 5. Simply copying K from old-slot-1 into new-slot-1 would be WRONG: K's correct home in an 8-bucket table is bucket 5, not bucket 1. If you naively preserved old slot numbers, a subsequent lookup for K would compute hash(K) % 8 = 5, look in bucket 5, find it empty, and incorrectly report K as not present -- even though it's sitting right there in bucket 1. This is exactly why resize must ITERATE every existing key and recompute hash(key) % new_table_size for each one individually, rather than just reallocating a bigger array and copying old contents over positionally.
Problem 5 · Constructing a pathological worst case

Explain, in your own words, how an attacker who knows a server uses simple_hash from section 1 with a FIXED, non-randomized table size could deliberately degrade that server's hash map to O(n) per operation, and why randomizing the hash seed per process defends against this.

Show solution
If the attacker knows the exact hash function and the table size (or can infer it), they can offline-compute many candidate keys and select only the ones whose hash(key) % table_size all produce the SAME bucket index -- exactly like this lab's section 4 pathological example. Submitting a large batch of such keys (e.g. as form field names, JSON object keys, or URL query parameters that get inserted into a server-side hash map) forces every one of them into a single bucket's chain, so every subsequent lookup or insert touching that bucket costs O(chain length) = O(n) instead of the expected O(1) -- with enough colliding keys, this can consume enough CPU time per request to constitute a denial-of-service. Randomizing the hash seed per process means the attacker can no longer precompute colliding keys offline, because hash(key) now depends on a secret random value chosen fresh when the server process started -- different every time the server restarts, and unknown to anyone outside the process. The SAME keys that collided against one seed will very likely NOT collide against a different random seed, which removes the attacker's ability to prepare a universal colliding key set in advance.
