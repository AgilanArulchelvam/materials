How this loop works, and why it's not the Week 1 mock again

Start here, before starting any timer. Think about the difference between four short sprints on a track versus one actual marathon. Four sprints test whether you can explosively reset between very different distances. A marathon tests something else entirely: whether your form, focus, and decision quality HOLD UP once fatigue is real — mile 20 is a different problem than mile 2, even though the running motion itself never changed. combined_timed_mock_dsa_schema_system_design.html was the sprints: four stations of 8-15 minutes, explicitly testing the SWITCH between modes. This lab is the marathon: four FULL rounds at realistic interview-length time budgets (30-45 minutes each, roughly 2.3 hours total, exactly what an onsite loop with a lunch-adjacent behavioral round actually costs), testing whether your depth and judgment survive being the FOURTH thing you've done today, not just the first.

The four rounds also add one the Week 1 mock never touched: a behavioral / capstone-walkthrough round (Round 4). A real loop for anyone building something like this capstone almost always includes a round where you talk through your own project's decisions out loud, under questioning — a fundamentally different skill from solving a fresh problem, and one worth training deliberately rather than assuming it "just happens."

ROUND 1 — DSA · FULL LENGTH · 30:00
30:00

Prompt: The capstone's orchestrator (mcp-and-agents/capstone_orchestrator_integration.html) needs to detect when a chain of tool calls has entered a redundant loop — the same tool called with the same arguments more than k times within the current run, which almost always signals the orchestrator is stuck rather than making progress. Design a data structure and algorithm that, given a live stream of (tool_name, args_hash) pairs as they occur, detects this condition in O(1) amortized time per call, and explain what the orchestrator should do once it fires.

Unlike Week 1's 12-minute cycle-detection station, this is a FULL round: work through the full solution, a complexity proof, and at least one edge case (what if args_hash collides for two genuinely different argument sets?) before your timer runs out — not just a sketch of the approach.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Names a hash map keyed on (tool_name, args_hash) → count, with O(1) expected lookup/increment
  • States the amortized complexity claim precisely and defends it (not just "it's fast")
  • Raises the hash-collision edge case UNPROMPTED and proposes a fix (e.g. storing full args alongside the hash for a final equality check on collision)
  • Names a concrete recovery action once the loop fires — not just "detect it," but what the orchestrator DOES next
Weak answer
  • Proposes rescanning the full call history on every new call (O(n) per call, no amortized argument at all)
  • Treats "detect the loop" as the entire problem, with no answer for what happens after detection
  • Never mentions hash collisions unless directly asked
  • Complexity claims are asserted, not derived from the actual operations performed
Show reference approach (only after your timer ends AND you've self-graded)
A hash map from (tool_name, args_hash) -> call_count, updated on every tool dispatch inside the orchestrator's step() loop (per mcp-and-agents/capstone_orchestrator_integration.html section 3, right where self.mcp.call_tool(...) is invoked). On each call: compute the key, increment its count, and check against threshold k. Both the hash and the increment are O(1) expected time (standard hash map behavior), giving O(1) amortized per call across the whole run -- no rescanning of prior calls needed, since the running count IS the full history's answer already folded in. The collision edge case, worth raising unprompted: args_hash is a hash of the tool arguments, and two DIFFERENT argument sets can collide to the same hash (a real, if rare, possibility for any fixed-width hash). A naive implementation using args_hash alone as the map key would incorrectly count two genuinely different calls as "the same redundant call." The fix: store the actual arguments (or a reference to them) alongside the count, and on a hash match, do a final equality check against the STORED arguments before incrementing -- this is exactly the standard hash-map collision-handling pattern hash_maps_from_scratch.html builds from first principles, now applied at the application layer instead of inside the hash map's own implementation. What the orchestrator does once the threshold fires (the part a weak answer skips): this is a genuine STOP signal, not a warning to log and continue -- per mcp-and-agents/loop_termination_logic.html's "done signals vs hard step caps vs wall-clock timeouts" framing, a redundant- call loop is a fourth, distinct termination condition worth its own explicit check, and firing it should end the run with a clear diagnostic reply ("this run appears stuck calling the same tool repeatedly and has been stopped") rather than either silently continuing (risking runaway cost) or crashing with an unhandled exception (losing the chance to persist a clean, explainable failure state via the orchestrator's own state store).
ROUND 2 — SCHEMA DESIGN · FULL LENGTH · 35:00
35:00

Prompt: Design the FULL capstone schema from scratch, out loud, as if this were your first time being asked — agent runs, tool calls, traces/spans, and eval results, plus the relationships between all four. Cover normalization decisions, which columns need indexes and why (name the actual query pattern each index serves), and one deliberate denormalization you'd justify for read performance. Then walk through how you'd migrate this schema safely if it already had production data.

This is the full version of what database/eval_trace_schema_finalization.html and database/capstone_schema_finalization_and_indexes.html already built — the round tests whether you can reconstruct and defend that reasoning from scratch, under time pressure, not whether you remember the exact column names.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Names all four entities and their relationships (1:N run→tool_calls, run→spans via trace_id, result→spans via trace_id) without prompting
  • Ties every proposed index to a SPECIFIC query pattern ("lookup by trace_id" → index on trace_id), not a generic "index the foreign keys"
  • Names one real denormalization (e.g. a rollup/aggregate table) and explicitly justifies it as an intentional trade-off, not an oversight
  • Describes an additive, backward-compatible migration with a rollback plan
Weak answer
  • Jumps straight to CREATE TABLE statements with no discussion of query patterns driving the design
  • Indexes every column "to be safe" with no cost/benefit reasoning (write cost, storage cost)
  • Treats normalization as a fixed rule rather than a trade-off against the read patterns established earlier in the same answer
  • Migration plan involves dropping/recreating a table with existing data, no rollback mentioned
Show reference approach (only after your timer ends AND you've self-graded)
The full reference schema and its index rationale live in database/capstone_schema_finalization_and_indexes.html section 1-2 -- this round is testing whether you can reconstruct that reasoning live, so re-deriving it here in brief: four tables (agent_run, tool_call, eval_span, eval_result), each index justified by a named query pattern (idx_eval_span_trace for "all spans for one trace_id," idx_tool_call_run for "full ordered call sequence for one run," a composite index on (tool_name, called_at) for "failure rate for tool X over time"), one denormalized rollup table for dashboard read performance (explicitly NOT normalized, with the trade-off stated out loud), and an additive CREATE TABLE + CREATE INDEX migration with a symmetric DROP TABLE rollback -- the exact pattern eval_trace_schema_finalization.html walks through for eval_span specifically. What separates a strong live answer from a merely correct one: SAYING the query pattern before proposing the index, in that order ("we need to look up all spans for a trace fast, so index on trace_id" -- not "index on trace_id, because... lookups I guess"), and explicitly naming denormalization as a deliberate, justified trade-off rather than something you back into apologetically when asked "why did you duplicate that column." A real interviewer is listening for the REASONING PROCESS as much as the final schema shape.

ROUND 4 — BEHAVIORAL / CAPSTONE WALKTHROUGH · 30:00
30:00

Prompt: Walk through this capstone as if presenting it to a hiring panel: what it does, the hardest technical decision you made while building it (pick a real one — e.g. Redis vs Postgres for orchestrator state, embedded vs separate-service search index, sync vs async eval scoring), why you made that call over the alternative, and what you'd do differently with more time. Expect follow-up questions that probe for genuine understanding versus a rehearsed script — answer as if being pushed on specifics.

This round is deliberately LAST, right after the heaviest technical round — talking clearly and specifically about your own decisions is measurably harder when you're tired than when you're fresh, which is exactly why real loops often place a behavioral round late rather than first.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Picks ONE specific decision, not a vague "there were many trade-offs"
  • States the alternative that was rejected AND the actual reason, not just "I chose X because it's better"
  • Survives a follow-up ("what would break if you'd chosen the alternative?") with a concrete, specific answer
  • Names a genuine limitation or thing they'd change, not a humble-brag disguised as a weakness
Weak answer
  • Generic, rehearsed-sounding language that could apply to any project ("I focused on scalability and best practices")
  • Can't name what the rejected alternative actually was, only that "other options were considered"
  • Follow-up questions expose that the reasoning wasn't actually understood, just memorized
  • "Weakness" answer is not a real limitation (e.g. "I work too hard")
Show reference approach (only after your timer ends AND you've self-graded)
There's no single "correct" answer here by design -- this round tests YOUR actual capstone decisions, not a canned script. But a strong worked example, using this week's own labs as the source material: "The hardest call was choosing Redis over Postgres for in-flight orchestrator run state. I considered keeping everything in Postgres for consistency with the eval/trace schema, but run state is written on every single turn and is fully disposable once a run completes -- Postgres's durability guarantees would have added write latency to every turn for a guarantee that state doesn't actually need, per the access-pattern argument in capstone_orchestrator_integration.html's first practice problem. The real cost of that choice: two requests racing on the same run_id from different workers can corrupt state if you're not careful -- I had to add a Redis-native lock to avoid a read-modify-write race, which is a failure mode Postgres's transactions would have handled for free. Given more time, I'd benchmark whether the lock's overhead under real concurrent load actually beats what Postgres transactional writes would have cost." What makes this a strong template to imitate: it names the SPECIFIC alternative (Postgres), the SPECIFIC reasoning (access pattern: write-heavy, disposable, latency-sensitive), the SPECIFIC cost of the choice made (the race condition, and the real fix required), and a SPECIFIC, non-defensive thing they'd reconsider with more time -- every clause is checkable against the actual work, which is exactly what survives a skeptical follow-up question and what a rehearsed, generic answer cannot survive.
The skill this loop trains that no single round can

Reflection: stamina and context-switching across a full loop

Start here, before reading the list below. Week 1's mock trained the SWITCH between modes, isolated, at a length short enough that fatigue was never really a factor. This loop trains something a short mock structurally cannot: whether your Round 3 deep-dive is as sharp as your Round 1 answer, and whether your Round 4 behavioral answers are as specific and honest after 110 minutes of technical rounds as they'd be first thing in the morning. This is not the same skill as fast mode-switching — a marathon runner's mile-20 form and a sprinter's start-block explosiveness are different trained capacities, and a real onsite loop tests the marathon one.

What actually helps, round to round, across a long loop

  • Notice fatigue as data, not as an excuse. If Round 3's deep-dive was genuinely thinner than Round 1's answer would have been, that's real signal about pacing and energy management — worth addressing directly (shorter, more frequent context-resets between rounds; explicitly re-reading the prompt before diving in even when tired) rather than dismissing as "I just wasn't sharp today."
  • Protect the LAST round deliberately — it's structurally the most vulnerable. Round 4's behavioral answers require specific, honest recall, which is measurably harder when tired than solving a fresh technical problem is (technical problems have external structure to lean on; behavioral answers require you to generate the structure from memory). Treat the transition into Round 4 with MORE deliberate reset effort, not less, precisely because it's easy to assume "it's just talking, I'll coast."
  • Use short breaks like a real loop would give you, not like a study break. A 5-minute gap between rounds, not a 30-minute one — the goal is training performance under the ACTUAL conditions of a real loop, and an unrealistically generous recovery window between rounds defeats the purpose of training stamina at all.
  • A rubric you self-graded honestly across all four rounds is a better signal than "I think it went fine." Look at your four grade selections together, in order — a strong/strong/mixed/weak pattern, read left to right, IS the stamina curve this lab measures, more precisely than any single round's grade alone.
The failure mode this loop is built to surface: not a gap in DSA knowledge, schema knowledge, system design knowledge, or communication skill — each of those has a dedicated lab elsewhere in this repo, and Week 1's mock already trained the mode-switch between them. What this loop surfaces is specifically whether depth and precision HOLD UP under cumulative fatigue across a realistic loop length — a distinct, trainable capacity that only shows up when you actually run all four full rounds back to back, honestly, without shortening them because a shorter version feels more comfortable.

Problem 1 · Comparing this loop's Round 1 against Week 1's DSA station, cold

You've now done both combined_timed_mock_dsa_schema_system_design.html's 12-minute DSA station and this lab's 30-minute DSA round, on different problems but the same general skill area. What did the extra 18 minutes actually buy — was it more depth on the same core idea, or room for edge cases and follow-ups the short version structurally can't fit?

Show solution
Most honestly, it's the latter more than the former -- the CORE insight in both cases (recognize a known pattern -- cycle detection via DFS/Kahn's in Week 1, a hash-map-with-collision-handling counter here -- and apply it) is roughly the same size of idea and doesn't actually take 30 minutes to STATE. What the extra time buys is everything AROUND the core insight that a 12-minute station has to cut for time: a full complexity proof rather than an assertion, at least one edge case raised unprompted (the hash collision case here), and a concrete answer for "what happens after detection" rather than stopping at "detection" as if that were the whole problem. This is a genuinely useful thing to notice about real interview rounds generally: a short round often rewards recognizing the pattern FAST and stating the approach confidently, while a full-length round punishes stopping there and rewards treating the initial insight as the START of the answer, not the end of it. Conflating the two -- bringing Week 1's "get to the approach fast and move on" energy into a 30-45 minute round -- reads as thin and underprepared, exactly the kind of mismatch this lab's rubrics are built to catch.
