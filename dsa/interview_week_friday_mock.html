STATION 1 — DSA · 10:00
10:00

Prompt: Same tool-dependency graph as earlier this week, weighted by latency — but now the orchestrator has a hard constraint: a plan can use AT MOST K tool-to-tool transitions (hops) end to end. Find the cheapest-latency path from start to goal using AT MOST K edges. Plain Dijkstra no longer directly applies — why not, and what's the correct approach?

This combines Wednesday's shortest-path station with a hop-count constraint, requiring a genuinely different technique — a Bellman-Ford-style relaxation bounded by K rounds, or a DP over (node, hops-used). State the state space and transition precisely.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Explains WHY Dijkstra breaks: its greedy finalize-once guarantee assumes no constraint on path length, so it can commit to a cheap-but-long path early and never revisit it under the new hop budget
  • Proposes a DP formulation: dist[node][hops] = cheapest cost to reach node using exactly (or at most) hops edges, filled by relaxing all edges K times (Bellman-Ford bounded to K rounds)
  • States the transition precisely: dist[v][h] = min(dist[v][h], dist[u][h-1] + weight(u,v)) for every edge (u, v)
  • States complexity correctly: O(K · E) time, O(V · K) space — and explicitly contrasts it with unbounded Dijkstra's O((V+E) log V)
Weak answer
  • Tries to bolt a hop counter onto Dijkstra without recognizing the greedy finalize-once guarantee is what actually breaks
  • Can't state a precise DP state and transition, stays vague ("track hops somehow")
  • Gets the complexity wrong or can't derive it from the proposed approach
  • Doesn't recognize this is structurally a bounded Bellman-Ford / DP problem, tries to force a heap-based approach that doesn't actually solve the constraint
Show reference approach (only after your timer ends AND you've self-graded)
Why Dijkstra breaks: its correctness relies on finalizing each node ONCE, at the moment it's popped with the current minimum distance, and never revisiting it -- this is valid when there's no constraint on path length, because any alternative path would have to be at least as expensive. But under a hop-count budget, the CHEAPEST overall path to a node might use MORE hops than the path Dijkstra would greedily finalize first (which only optimizes for cost, blind to hop count) -- so a node's "best" distance now depends on BOTH cost and hops used, a two-dimensional state Dijkstra's single-value finalization can't represent. Correct approach: dynamic programming over the state (node, hops used). Define dist[v][h] = the cheapest cost to reach node v using EXACTLY h edges (or, alternately, at most h -- either formulation works with a small adjustment). Base case: dist[start][0] = 0, dist[v][0] = infinity for all v != start. Transition: for h from 1 to K, for every edge (u, v) with weight w, dist[v][h] = min(dist[v][h], dist[u][h-1] + w) -- this is exactly Bellman-Ford's relaxation step, bounded to run only K rounds instead of V-1 rounds. The answer is min over all h from 0 to K of dist[goal][h]. Why this is really "bounded Bellman-Ford," worth stating explicitly: Bellman-Ford's V-1 relaxation rounds exist to guarantee correctness for ANY path length up to V-1 edges (the longest possible simple path). Here, the problem ITSELF bounds path length to K, so running exactly K rounds of the same relaxation logic directly encodes the hop constraint, rather than being an arbitrary truncation. Complexity: O(K * E) time -- K rounds, each relaxing every edge once. O(V * K) space for the full dist table (or O(V) if only the previous round's row is kept, since each round only depends on the one before it). Worth contrasting explicitly against unbounded Dijkstra's O((V + E) log V): this approach is asymptotically worse when K is large (approaching V), but for a genuinely bounded K (a realistic orchestrator hop limit, likely small), K * E can be significantly cheaper in practice, and more importantly, it's the approach that's actually CORRECT under this constraint, which Dijkstra alone is not, regardless of speed.
STATION 2 — SCHEMA DESIGN · 8:00
8:00

Prompt: Design a schema for storing per-minute p50/p95/p99 latency percentiles for every tool, going back 90 days, where old data (past 7 days) can be safely stored at coarser granularity (hourly rather than per-minute) to save space. How do you model the granularity change without two completely separate, hard-to-query table shapes?

Directly reuses database/time_series_schema.html's territory, now with the added wrinkle of a granularity downgrade over time — a genuinely harder version of the standard time-series rollup pattern.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • Proposes ONE table shape (tool_name, bucket_start, bucket_size, p50, p95, p99, sample_count) where bucket_size is itself a column (1 minute or 60 minutes), not two separate table schemas
  • Explains the downgrade mechanism: a background job aggregates the per-minute rows older than 7 days into hourly rows (recomputing percentiles is non-trivial — flags this explicitly, see below) and deletes the now-redundant fine-grained rows
  • Names the real percentile-recomputation problem unprompted: you CANNOT simply average p95 values across 60 one-minute buckets to get an accurate hourly p95 — percentiles don't compose that way — and proposes either storing enough raw samples to recompute properly, or accepting approximate downsampling as a documented trade-off
  • Names the index that keeps both granularities queryable together: composite on (tool_name, bucket_start)
Weak answer
  • Proposes two entirely separate tables (per-minute and hourly) with no unifying shape, making a 90-day query across the boundary awkward
  • Doesn't recognize that averaging percentiles across buckets is mathematically wrong
  • No concrete downgrade/aggregation mechanism described, just "roll it up somehow"
  • No index proposed for the range queries this schema needs to serve
Show reference approach (only after your timer ends AND you've self-graded)
One unified table shape: `tool_latency_buckets` (tool_name, bucket_start, bucket_size_minutes, p50, p95, p99, sample_count) -- bucket_size_minutes is a real column (1 for fresh per-minute data, 60 for downgraded hourly data), not two separate schemas. This lets a single query across a 90-day window return a mix of fine and coarse rows without a UNION across differently-shaped tables, and the caller can treat bucket_size_minutes as just another filterable/ groupable column. The downgrade mechanism: a scheduled background job, run daily, finds per-minute rows older than 7 days for each tool, groups them into hourly buckets, computes new hourly percentile rows, inserts those, and deletes the now-redundant per-minute rows for that window -- time_series_schema.html's own rollup pattern, now framed explicitly as a granularity DOWNGRADE rather than just an aggregation. The real problem, worth surfacing unprompted because it's the part most answers miss: percentiles do NOT compose by simple averaging. Averaging 60 one-minute p95 values does NOT give an accurate hourly p95 -- p95 is a property of the full underlying DISTRIBUTION of samples in that hour, and a naive average of per-minute p95s can be meaningfully wrong, especially if latency is bursty (a few very slow minutes get diluted by averaging with many fast ones). Two honest options: (1) store enough raw sample data (or a sketch/histogram structure like a t-digest) alongside the per-minute rows to allow TRUE percentile recomputation at rollup time, at some storage cost; or (2) accept that the downgraded hourly percentiles are APPROXIMATE, document this explicitly, and ensure nothing downstream treats a 90-day-old p95 as precisely as accurate as a fresh one. Either is a legitimate answer -- what's NOT legitimate is silently averaging percentiles and presenting the result as exact. Index: composite on (tool_name, bucket_start) serves both "give me tool X's latency over the last 90 days" (equality filter, range scan) and naturally returns rows in chronological order regardless of which bucket_size_minutes each row happens to have, since the downgrade process preserves bucket_start as the true point in time each bucket represents.

The deep-dive, the actual point of this station: when a new document is added to the hybrid search index WHILE a query is in flight, does that query see the new document? A newly added document becomes visible to the NEXT query issued after the write completes, not retroactively to queries already in progress -- this is eventual consistency at QUERY granularity, a narrower and more forgiving version of the eventual consistency already established for read replicas (Thursday) and caching (Monday) this week. Why this is acceptable for search specifically, the justification a strong answer states explicitly: a search result being one query-cycle stale (missing a document added microseconds ago) has essentially no real-world cost -- nobody notices or is harmed by a document not yet being searchable for the few milliseconds between being written and the next query cycle picking it up. This is the same class of justified staleness-tolerance this week has invoked repeatedly (dashboard caching, replica lag) applied to a new context, and naming the PATTERN explicitly ("this is the same kind of trade-off as Monday's caching station, now at the search-index layer") is exactly the connected, whole-system reasoning a real interviewer listens for across a loop.
STATION 4 — PYTHON FUNDAMENTALS · 5:00

Prompt: Explain how Python's descriptor protocol makes @property work under the hood — what __get__ and __set__ actually do, and why a plain instance attribute assignment doesn't go through them but a class-level descriptor does. Tie this to CPython's attribute lookup order.

Directly reuses python/cpython_internals.html and python/classes_and_dunders.html's territory. Five minutes, cold — this is the hardest Python station of the week so far.

Self-grading rubric — grade BEFORE reading the reference approach
Strong answer
  • States the descriptor protocol precisely: any object implementing __get__ (and optionally __set__/__delete__) defined on a CLASS controls attribute access for instances of that class
  • States that @property is syntactic sugar for creating a descriptor object (with __get__ calling the getter function, __set__ calling the setter) and assigning it as a CLASS attribute
  • Explains the attribute lookup order correctly: Python checks the type's __dict__ (and its MRO) for a DATA descriptor (has both __get__ and __set__) FIRST, before checking the instance's own __dict__ — a data descriptor takes priority over an instance attribute of the same name
  • States why this matters for @property specifically: since it's a data descriptor, self.x = value always goes through the property's __set__, even though instances normally store attributes directly in their own __dict__
Weak answer
  • Says "@property makes a method look like an attribute" without describing the underlying descriptor mechanism
  • Doesn't know what __get__/__set__ actually are or when Python calls them
  • Doesn't know the class-attribute-descriptor-takes-priority-over-instance-dict lookup order, or gets it backwards
  • Can't connect the mechanism back to CPython's actual attribute resolution process
Show reference approach (only after your timer ends AND you've self-graded)
The descriptor protocol: any object that defines __get__(self, obj, objtype) and, optionally, __set__(self, obj, value) or __delete__, and is itself stored as a CLASS attribute (not an instance attribute), becomes a descriptor -- Python's attribute lookup machinery calls these methods instead of returning the descriptor object directly. @property is exactly a convenient way to construct a descriptor: `@ property def x(self): ...` creates a property object (whose __get__ calls the decorated getter function) and binds it to the name `x` on the CLASS. If a corresponding `@x.setter` is defined, the property object's __set__ is wired to call that setter function instead. The attribute lookup order, precisely, and the part most answers get wrong or skip: when Python evaluates `instance.x`, it does NOT simply check instance.__dict__ first. It first checks type(instance).__mro__ for `x` -- if found AND it's a DATA descriptor (defines both __get__ and __set__), that descriptor's __get__ is called immediately, taking priority over anything in instance.__dict__. Only if no data descriptor is found does Python fall back to instance.__dict__, and only if THAT also fails does it fall back further to a non-data descriptor or plain class attribute. This data-descriptor-takes-priority rule is precisely why @property works reliably: a property is a data descriptor (has both __get__ and __set__), so it INTERCEPTS attribute access even for an instance that might otherwise have tried to store an attribute of the same name directly in its own __dict__. Why `self.x = value` goes through __set__ specifically, tying it together: for an ORDINARY instance attribute (no descriptor involved), `self.x = value` simply inserts "x" into instance.__dict__ directly -- no interception happens. But because a property named `x` is a data descriptor living on the CLASS, Python's attribute-SETTING machinery checks for a data descriptor FIRST here too, finds the property's __set__, and calls it (running the setter function) INSTEAD of writing directly into instance.__dict__ -- which is exactly what lets a property run validation or side-effect logic on assignment, something a plain instance attribute structurally cannot do.
