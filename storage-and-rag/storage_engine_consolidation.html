02 — Commit to an answer before revealing the reasoning

Three sample workloads — pick which engine(s) fit

For each scenario below, click the engine (or engines) you'd pick BEFORE opening the reasoning. There's no scoring here — the value is entirely in having actually committed to an answer first, the same discipline the system design review, cold lab used for re-deriving designs from nothing.

Scenario 1

A financial ledger system needs to record individual transactions (deposits, withdrawals, transfers) and, far more often, needs to fetch a SINGLE account's current balance and recent transaction history — fast, and with a strong guarantee that a read never sees a torn or inconsistent write. There is no analytics or vector-search requirement here at all.

Reveal the reasoning (only after you've picked)
Row-store (B-tree) is the clear fit. Every access pattern described here is textbook OLTP: single-account, whole-record reads and writes ("this account's balance," "this transaction"), needing strong consistency guarantees on individual records, at high frequency. Row-store keeps a whole record's data contiguous, which is exactly what makes fetching one account's full state fast and what makes atomic single-row (or small, related-row) writes -- backed by real transactions -- straightforward. Columnar would actively hurt here: this workload needs whole records, not narrow scans across millions of rows for a handful of columns -- the opposite of columnar's strength, and reconstructing one account's full row from a columnar layout means stitching together data from many separate column regions, adding cost for no benefit given this access pattern. HNSW and IVF are irrelevant -- there's no vector similarity search requirement anywhere in this scenario at all, so neither approximate- nearest-neighbor technique applies.
Scenario 2

A BI dashboard aggregates millions of historical sales rows to compute rolling metrics — total revenue by region by quarter, average basket size by product category — refreshed a few times per day, not in real time. The underlying table has 40+ columns (customer notes, shipping metadata, payment details) but each dashboard query only ever touches 2-4 of them.

Reveal the reasoning (only after you've picked)
Columnar is the clear fit. This is the textbook OLAP shape from the btree_vs_columnar lab: millions of rows scanned, but only 2-4 of 40+ columns needed per query. Columnar storage lets each aggregation query read only the bytes belonging to those 2-4 columns' contiguous regions, skipping the other 36+ columns entirely -- versus row-store, which would force reading every row's FULL width (all 40+ columns) for every row scanned, roughly a 10-20x I/O penalty for the identical logical query, purely from physical layout. Row-store would technically still "work" (it can answer the same SQL query) but would be dramatically slower and more I/O-expensive at this scale and column-width, which is exactly the OLAP-on-row-store performance trap the btree_vs_columnar lab's Problem 3 walks through. The "refreshed a few times per day, not real time" detail also reinforces columnar being a good fit -- this workload doesn't need the fast single-row write path row-store is built for, and periodic batch refreshes match columnar's natural bulk-write pattern well. HNSW and IVF don't apply -- there's no vector similarity search in this scenario, only structured aggregation over relational columns.
Scenario 3

A semantic search feature lets users find product descriptions similar in meaning to a free-text query, across a catalog of 10 million products. The product catalog changes continuously throughout the day (new products added, old ones removed) as inventory turns over, and the team has generous memory budget on dedicated search infrastructure, prioritizing search quality (finding genuinely the most relevant products) over minimizing memory footprint.

Reveal the reasoning (only after you've picked)
HNSW is the better fit here, and the scenario is specifically constructed to point that way on two separate stated constraints. First, "the catalog changes continuously throughout the day" favors HNSW's naturally incremental insertion (new vectors slot directly into the graph, no separate retraining step) over IVF's need for an upfront k-means clustering step that isn't naturally incremental -- IVF would require periodic re-clustering to avoid centroids drifting stale relative to a constantly-changing catalog, an operational cost this scenario's continuous-churn description makes more painful than it would be for a more static dataset. Second, "generous memory budget... prioritizing search quality... over minimizing memory footprint" directly matches HNSW's profile from section 1's table: generally better recall, at the cost of a higher memory footprint from storing explicit graph edges -- exactly the trade this scenario says the team is willing to make. IVF would be the better answer if the constraints were flipped (memory- constrained, batch-updatable catalog, recall requirements looser) -- this is a genuinely close call in the abstract, which is why the scenario leans on BOTH stated constraints (continuous updates AND memory-not-a-priority) to point toward HNSW specifically, rather than leaving it ambiguous. Row-store and columnar don't apply at all here -- neither is a vector-similarity technique, and "find descriptions similar in MEANING" is fundamentally a nearest-neighbor-over-embeddings problem, not a relational query.

Problem 1 · A workload that needs two engines at once, not one

An e-commerce platform needs both (a) fast single-order lookups for its checkout/order-status pages, and (b) a nightly analytics job computing revenue trends across all historical orders. Using the reasoning from Scenario 1 and Scenario 2 above, what's the actual recommendation, and why is picking just ONE engine for both the wrong answer?

Show solution
The recommendation is to run BOTH a row-store (for the OLTP checkout/ order-status path) and a separate columnar store (for the OLAP nightly analytics job), not to pick one engine and force both workloads onto it -- this is the exact same reasoning as the btree_vs_columnar lab's "why you can't just pick one and be done" callout, and it directly mirrors Scenario 1 (row-store fit) and Scenario 2 (columnar fit) being DIFFERENT scenarios in this very consolidation lab for a reason: they represent genuinely different access-pattern shapes that no single storage layout serves equally well. Picking only row-store for both: checkout/order-status stays fast, but the nightly analytics job pays the OLAP-on-row-store I/O penalty from Scenario 2's reasoning -- reading full row widths across millions of historical rows for aggregations that only need a few columns -- and worse, that heavy nightly scan can degrade the SAME database's live checkout traffic by competing for disk I/O and cache, exactly the "slowing down the live checkout service" symptom described in the btree_vs_columnar lab's own Problem 3. Picking only columnar for both: the nightly analytics job would be fast, but checkout/order-status lookups -- which need EVERY column of ONE specific order, fast -- would pay columnar's reconstruction cost (stitching one row together from many separately-stored column regions) on every single checkout page load, which is exactly the wrong shape for columnar's strengths. The standard real-world answer is what the btree_vs_columnar lab already named: row-store as the OLTP system of record, with a periodic ETL/ export feeding a separate columnar store for analytics -- two engines, each doing the job it's actually built for.
Problem 2 · Distinguishing IVF's and HNSW's failure modes when picking for a hybrid scenario

A vector search feature over 10 million vectors needs to run on a memory-constrained edge device (not a generous server), but ALSO needs reasonably good recall since it's the only search mechanism available (no fallback to a bigger server). Is this scenario closer to Scenario 3's answer, or does it push toward IVF instead? Explain the tension.

Show solution
This scenario deliberately conflicts with itself in the same way a real constrained environment often does, and the honest answer is that it pushes toward IVF specifically BECAUSE of the memory constraint, even though the recall requirement alone (considered in isolation) would lean toward HNSW the way Scenario 3 did. The reasoning: Scenario 3 explicitly stated "generous memory budget... prioritizing quality over memory footprint" -- the memory constraint was explicitly relaxed, which is what let HNSW's higher memory cost be a non-issue. Here, the memory constraint is explicitly NOT relaxed (edge device, memory-constrained) -- which is precisely the condition under which section 1's table names IVF as the better fit (lower memory footprint, no per-vector graph edges to store), even though this comes at some real recall cost relative to HNSW. The "reasonably good recall, no fallback" requirement doesn't override the hard memory constraint -- it instead becomes a tuning problem WITHIN IVF rather than a reason to switch to HNSW: raising nprobe (searching more clusters per query) directly improves IVF's recall at the cost of more query-time computation (not more baseline memory, which is the constraint that actually can't be violated here) -- a real, usable lever precisely because the memory ceiling, not the compute budget, is the binding constraint in this version of the scenario. This is the kind of distinction a system-design interview specifically probes for: not "which engine is better in general" but "which constraint in THIS version of the problem is actually binding, and which trade-off knob is still available to spend."
Problem 3 · Justifying a hybrid IVF+HNSW choice

The IVF lab mentioned that some production systems combine IVF and HNSW — IVF for coarse partitioning, a small HNSW graph within each cluster for fine navigation. Explain, using both labs' trade-off reasoning, why this combination might beat using either technique alone at very large scale (e.g. 500 million vectors).

Show solution
At 500 million vectors, pure HNSW's memory cost becomes a real constraint even with a "generous" budget -- storing explicit multi-layer graph edges for every one of 500 million vectors is a large, direct multiplier on total memory versus IVF's leaner per-vector overhead (just a cluster assignment). Pure IVF alone, meanwhile, pays its structural recall cost (missing near-boundary neighbors, from the ivf_indexing lab's section 2) across a much larger dataset, where more total clusters and more total boundary regions mean more opportunities for that specific failure mode to matter. The hybrid approach uses each technique where it's cheapest to apply: IVF's coarse clustering does the EXPENSIVE part of narrowing 500 million vectors down to a manageable candidate set cheaply, in roughly O(k) time against k centroids, exactly as the ivf_indexing lab's Problem 4 describes -- this step doesn't require per-vector graph memory at all, just k centroids. Then, WITHIN each of the (comparatively small) selected clusters, a small HNSW graph gives the fine-grained recall benefit HNSW is good at, but only needs to be built and stored per-cluster rather than across the full 500-million-vector dataset -- so the "expensive per- vector graph memory" cost of HNSW is paid at a much smaller scale (one cluster's worth of vectors) rather than the full dataset's scale. This is the same "use the cheap technique for the coarse pass, the more expensive/higher-quality technique for the fine pass" pattern that shows up throughout systems design (e.g. a first coarse filter followed by a more expensive re-ranking step) -- neither technique alone is forced to pay its worst-case cost across the ENTIRE dataset.
