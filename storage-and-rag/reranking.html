STORAGE & RAG LAB · CHUNKING & HYBRID SEARCH

Retrieval finds a big pile of plausible answers fast. Re-ranking looks closer, at only a few.

Fast retrieval (dense, BM25, or hybrid) is deliberately approximate — it has to scan a huge index quickly, so it can't afford to look too closely at any one candidate. Re-ranking is the second pass: a slower, more accurate model that looks at the query and each candidate TOGETHER, but only across the small shortlist retrieval already narrowed things down to. This lab animates the funnel — many candidates in, a small precise top-K out — and works through exactly why the re-ranker has to be a different kind of model.

01 — Cheap and broad first, expensive and narrow second

Re-ranking as a second-pass refinement step

Start here, before any architecture. Imagine hiring for a role with 2,000 applicants. Nobody conducts a full, careful, in-depth interview with all 2,000 people — that would take forever. Instead, a fast first pass (scanning resumes for basic keyword/qualification matches) narrows 2,000 down to maybe 20 plausible candidates quickly and cheaply. THEN, and only then, a much more careful, more expensive process — an actual interview, where the interviewer looks closely at each specific candidate's answers in context — gets applied, but only to those 20, not all 2,000. The expensive step is affordable specifically because it only ever runs on the small shortlist the cheap step already produced.

Re-ranking applies exactly this two-stage structure to search. The first stage — retrieval (dense embedding search, BM25, or the hybrid combination of both from earlier this week) — scans the FULL index and returns a larger candidate set (e.g. the top 50-100) cheaply and quickly, prioritizing speed and scale over precision. The second stage — re-ranking — takes ONLY that smaller candidate set and runs a more expensive, more accurate scoring pass over it, reordering (and often further truncating) it down to a small, precise top-K (e.g. the top 5-10) that actually gets used — sent to the LLM, or shown to the user. The re-ranker never touches the full index; it only ever operates on the shortlist retrieval already produced.

# The two-stage shape, end to end def search_with_reranking(query, full_index, final_k=5): # stage 1: fast, broad retrieval over the FULL index candidates = retrieve(query, full_index, top_n=50) # cheap, approximate # stage 2: slow, precise re-ranking over ONLY those 50 candidates rescored = [(doc, cross_encoder_score(query, doc)) for doc in candidates] rescored.sort(key=lambda pair: -pair[1]) return rescored[:final_k] # the small, precise top-K that actually gets used
Interview-ready definition: re-ranking is a second-pass refinement step in a retrieval pipeline: an initial retrieval stage (dense, sparse, or hybrid) cheaply scans the full index and returns a larger candidate set, and a re-ranking stage then applies a more expensive, more accurate scoring model to ONLY that smaller candidate set to reorder (and typically truncate) it into a small, precise final result. This staged structure exists because the more accurate scoring approach is too expensive to run against the entire index directly — it's only affordable when applied to the much smaller shortlist the first stage already narrowed things down to.
02 — Why the re-ranker can't just be "the same model, but better"

Bi-encoder vs cross-encoder: why re-ranking needs a different architecture

Start here, before the diagrams. Imagine two ways to judge how well a job candidate matches a role. Method one: separately summarize the candidate into a short profile, and separately summarize the role into a short profile, then compare the two summaries — fast, and you can pre-write a candidate's profile once and reuse it against many different roles. Method two: sit the candidate down WITH the actual role's hiring manager and have a real conversation where each side responds to the specific details of the other — much more accurate, since it can catch subtle fit signals the two independent summaries would flatten away, but it's expensive and has to happen fresh, in real time, for every single candidate-role pairing — you can't "pre-compute" a real conversation in advance.

Bi-encoder (used in initial retrieval)

Query → Encoder → query vector
↓ compared via cosine similarity ↓
Document → Encoder → doc vector

Query and document are embedded separately, by the same encoder, with no interaction between them. Document embeddings can be computed once, offline, and reused for every future query — this is exactly what makes large-scale fast retrieval possible.

Cross-encoder (used in re-ranking)

[Query + Document] fed in TOGETHER → Encoder → relevance score

Query and document are concatenated and processed together, in one pass, so the model can directly attend to how specific words/phrases in each relate to the other. This produces a more accurate relevance judgment, but the score is meaningless until you already know the SPECIFIC query — it cannot be precomputed for a document in isolation.

This architectural difference is exactly why re-ranking has to be a two-stage pipeline rather than "just use the cross-encoder for everything." A bi-encoder embeds the query and each document independently — critically, this means every document's embedding can be computed ONCE, offline, ahead of any query, and stored in an index; at query time, only the QUERY needs to be embedded fresh, and it's compared against millions of precomputed document vectors via fast similarity search. A cross-encoder needs both the query AND the specific document present simultaneously to produce a score — there's no way to precompute "how relevant is this document" without already knowing what it's being compared against, since the model's entire mechanism is built around directly attending across the two inputs together. Running a cross-encoder against every document in a million-document index, for every query, would require millions of full model inferences per query — computationally infeasible at that scale, which is exactly why it's only ever applied to retrieval's small shortlist.

Interview-ready definition: a bi-encoder embeds the query and each document independently into a shared vector space, with no interaction between them at encoding time — this independence is precisely what allows document embeddings to be precomputed once and reused across every future query, making bi-encoders the right architecture for fast retrieval over large indexes. A cross-encoder instead processes the query and a specific document TOGETHER in a single forward pass, allowing it to directly attend to fine-grained interactions between them for a more accurate relevance score — but this score cannot be precomputed, since it requires the specific query at inference time, which makes cross-encoders computationally affordable only on a small candidate set rather than an entire index, and is the direct architectural reason re-ranking must be a second stage applied after retrieval, not a replacement for it.

Problem 1 · Explaining precisely why cross-encoder scores can't be precomputed

Someone suggests: "just precompute cross-encoder relevance scores for every document against a large set of common queries, and cache them, the same way bi-encoder document embeddings are precomputed." Explain specifically what breaks about this compared to bi-encoder precomputation.

Show solution
Bi-encoder precomputation works because a document's EMBEDDING is a property of the document alone -- it doesn't depend on any particular query, so it's computed once and reused against every future query via a separate, fast similarity comparison at query time. A cross-encoder score, by contrast, is not a property of the document alone at all -- it's a joint function of the SPECIFIC query-document PAIR, produced by feeding both into the model together in one pass. There is no "cross-encoder embedding of just the document" to precompute, because the model's entire mechanism (attending across query and document together) requires both inputs simultaneously to produce any score at all. Precomputing scores against a "large set of common queries" doesn't actually solve this -- it only covers the specific finite set of queries chosen in advance, and real user queries are effectively unbounded and frequently novel (a query nobody typed before, phrased in a way not in the precomputed set, gets no cached score at all). This differs fundamentally from bi-encoder document embeddings, which are useful against EVERY possible future query without needing to know any of them in advance, precisely because the document embedding step never involved a query to begin with. This is the structural reason cross-encoders stay confined to a small, query-time-only shortlist rather than being precomputed like bi-encoder embeddings.
Problem 2 · Tracing what a re-ranker can catch that retrieval missed

A query is "database with strong consistency guarantees, not eventual." A retrieved document (ranked 15th by the bi-encoder) discusses "a database offering configurable consistency, including strict linearizability for critical operations." Explain, using section 2's architecture difference, why a cross-encoder might rank this document much higher than the bi-encoder did.

Show solution
The bi-encoder embeds the query and this document completely independently, with no direct interaction between them at embedding time -- its similarity score reflects how close their two INDEPENDENT vector summaries land in the embedding space overall, which can be diluted by everything else in the document unrelated to consistency, and by the fact that "strong consistency, not eventual" (query) and "strict linearizability" (document) are related concepts but not phrased with obvious surface-level similarity that an independent summary necessarily preserves strongly. A cross-encoder processes the query and this specific document TOGETHER in one pass, allowing it to directly attend to the fact that "strict linearizability" is a specific, strong technical instantiation of "strong consistency guarantees, not eventual" -- a fine-grained semantic connection that requires directly relating specific phrases in the query to specific phrases in the document, exactly the kind of interaction a bi-encoder's separate-embedding-then-compare approach is structurally less able to capture as precisely. This is a concrete instance of section 2's core claim: the cross-encoder's joint processing can surface relevance signals that got diluted or missed when the query and document were only ever compared as two independently-computed summaries.
Problem 3 · Choosing retrieval and re-ranking candidate-set sizes under a latency budget

A cross-encoder pass takes roughly 8ms per query-document pair, and the total pipeline (retrieval + re-ranking) has a 150ms latency budget, of which retrieval itself reliably takes about 20ms. What's the maximum number of candidates retrieval can hand to the re-ranker without blowing the budget, and what does this reveal about why retrieval can't just return everything?

Show solution
Remaining budget for re-ranking: 150ms - 20ms (retrieval) = 130ms. At 8ms per candidate (assuming candidates are scored sequentially, a reasonable simplifying assumption for this estimate), 130ms / 8ms ≈ 16 candidates is roughly the maximum the re-ranker can process within budget. (In practice, cross-encoder scoring is often batched/parallelized to some degree, which would raise this number somewhat, but the underlying cost-per-candidate constraint still directly caps how large a candidate set is affordable — batching doesn't make the cost disappear, just amortizes it.) This reveals exactly why retrieval can't simply return "everything plausibly relevant" or the entire index: the re-ranker's per-candidate cost is the binding constraint on candidate-set size under any real latency budget, and that cost is fixed by the cross-encoder's architecture (section 2) — it can't be avoided by better engineering, only worked around by giving the re-ranker fewer candidates to score. This is precisely why retrieval's job is to be a cheap, imperfect FILTER down to a size the re-ranker can actually afford (here, roughly 16), not to independently guarantee finding every possible good answer on its own — the re-ranker's job is to add precision within that constrained candidate budget, not to fix a retrieval stage that returned too little or too much.
Problem 4 · Diagnosing a re-ranking pipeline that isn't improving results

A team adds a cross-encoder re-ranking stage to their pipeline, but measured result quality barely improves. On investigation, retrieval's top-50 candidates for a large fraction of queries don't actually contain the truly best-matching document at all — it's sitting at rank 80+ in retrieval's own ranking, well outside what gets passed to the re-ranker. Is this a re-ranking bug? What's actually wrong, and what does it reveal about the pipeline's overall dependency structure?

Show solution
This is not a re-ranking bug -- the re-ranker is doing exactly what it's designed to do (accurately reordering whatever candidate set it's given), but it can only reorder documents that were HANDED to it in the first place. If the truly best-matching document never makes it into retrieval's top-50 (it's sitting at rank 80+, outside the shortlist the re-ranker ever sees), no amount of re-ranking accuracy can recover it -- the re-ranker has no visibility into candidates it was never given, the same structural limitation an RRF fusion step has with respect to its own inputs. What's actually wrong is upstream, in retrieval's RECALL: retrieval itself is failing to surface the best document within its own top-50 for a meaningful fraction of queries, likely due to retrieval-stage issues (bi-encoder embedding quality, chunking choices, or too small a top_n cutoff at the retrieval stage) rather than anything about re-ranking. This reveals the pipeline's overall dependency structure precisely: retrieval's job is to guarantee (with high probability) that the truly best documents are SOMEWHERE within the candidate set it hands off; re-ranking's job is to accurately ORDER whatever it's handed. The two stages have genuinely different failure modes and different fixes -- improving re-ranking accuracy cannot compensate for a retrieval recall problem, and the fix here is investigating and improving retrieval's top_n cutoff and/or embedding quality, not tuning the re-ranker further.
Problem 5 · Explaining why bi-encoder retrieval is still necessary even with a great cross-encoder

If cross-encoders produce more accurate relevance scores than bi-encoders, why not skip bi-encoder retrieval entirely and just run the cross-encoder against every document in the index directly? Give the specific reason, not just "it would be slow."

Show solution
The specific reason ties directly back to section 2's architecture difference: a cross-encoder score requires the query and a SPECIFIC document to be processed together in a single model pass, which means running it against every document in the index would require one full model inference PER DOCUMENT, PER QUERY -- for a million-document index, that's a million full model forward passes for every single query, with none of that work reusable across different queries (since nothing about a cross-encoder's computation can be precomputed independently of the query, per section 2). This isn't just "slow" in a vague sense -- it's a fundamentally different computational shape than bi-encoder retrieval, which does ONE query-side computation plus a fast vector similarity search against ALREADY-precomputed document embeddings, letting it scale to large indexes because the expensive per-document work (embedding) was already done once, offline, before any query ever arrived. Bi-encoder retrieval remains necessary specifically to convert "score every document against this query" (computationally infeasible for a cross-encoder at index scale) into "score only these ~50 documents against this query" (computationally very feasible for a cross-encoder) -- it's not that bi-encoders are simply "good enough" on their own, it's that they perform the specific structural job (cheap, precomputable, scale-to-the-full-index filtering) that a cross-encoder architecturally cannot perform at all, regardless of how much compute you're willing to spend on it, since its accuracy comes precisely from the per-pair joint processing that also makes it impossible to precompute or scale to millions of documents per query.
