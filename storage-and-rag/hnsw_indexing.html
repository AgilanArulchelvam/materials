HNSW searches a haystack by parachuting in from above, not walking every row.

A Hierarchical Navigable Small World graph is a stack of graphs layered on top of the same set of vectors — sparse and long-range at the top, dense and fine-grained at the bottom. A search starts at the sparse top layer, takes big jumps toward the target, then drops down a layer and repeats with finer and finer steps. This lab animates that descent directly, and connects it to why HNSW trades a small chance of missing the true nearest neighbor for a massive speedup over brute-force exact search.

01 — A stack of graphs, not one flat graph

Hierarchical Navigable Small World graphs — the layered idea

Start here, before any graph theory. Imagine finding a specific street address in an unfamiliar country, using three different maps of increasing detail. The first map shows only major highways connecting a handful of big cities — from wherever you start, you can jump enormous distances fast, landing you in roughly the right city. The second map, once you're in the right city, shows the major roads within it — fewer huge jumps, more moderate ones, narrowing toward the right neighborhood. The third map shows literally every street in that neighborhood — small, precise steps until you're standing at the exact address. You never once needed a map showing every street in the entire country; you only needed that much detail in the tiny final neighborhood.

An HNSW graph is built the same way, as a stack of graph "layers" over the same underlying set of vectors. The top layer contains only a small, sparse subset of all the stored vectors, connected by relatively few edges spanning long distances in the vector space — this is the "highway map," built for covering huge ground in very few hops. Each layer below adds back more of the vectors and more, shorter edges, getting progressively denser, until the bottom layer (layer 0) contains every single vector in the entire index, densely connected to its true nearest neighbors — the "every street" map. A vector's presence in upper layers is decided randomly at insert time (with exponentially decreasing probability the higher the layer), which is exactly why upper layers end up naturally sparse without anyone explicitly curating which vectors belong there.

# Roughly how layer membership is decided at insert time import random, math def assign_layer(level_multiplier=1.0): # exponential decay: each higher layer is exponentially less likely # -- this is WHY the top layer ends up sparse "for free" return int(-math.log(random.random()) * level_multiplier) # most vectors: assign_layer() returns 0 -> layer 0 only (the base layer) # far fewer vectors: returns 1 -> also inserted into layer 1 # vanishingly few: returns 2, 3, ... -> present in the sparse top layers too
Interview-ready definition: HNSW (Hierarchical Navigable Small World) is a multi-layer graph index for approximate nearest-neighbor search, where each layer is a proximity graph over a subset of the stored vectors — the top layer is sparse with long-range edges for fast coarse navigation, and each layer down is progressively denser, with layer 0 containing every vector and its true nearest-neighbor edges. Layer membership is assigned randomly per vector at insert time with exponentially decreasing probability per layer, so the pyramid shape (sparse top, dense bottom) emerges naturally rather than being explicitly constructed.
02 — The crux of the whole topic

Descending through layers: a search, animated

Start here, before running the demo. Back at the three maps: you don't start by scanning the street-level map for your destination — you start on the highway map, find the entry point closest to your goal, and only switch to a more detailed map once you've gotten as close as that current map lets you. HNSW search works identically: start at a single fixed entry point in the TOP layer, greedily move to whichever neighbor (of the current node, using only that layer's edges) is closer to the query vector than the current node is, and keep doing that until no neighbor at this layer is closer — that's "locally optimal" for this layer. At that point, drop down one layer, keep the same current-best node as the new starting point, and repeat the greedy walk using that layer's (denser) edges. Continue descending until you're greedily walking layer 0, the densest layer, which gives the final, most precise answer.

Notice what just happened: the search never examined most of the 24 vectors. It took a few big jumps at the sparse top layer to get roughly in the right neighborhood of the vector space, then refined with smaller and smaller jumps as it dropped through progressively denser layers — exactly mirroring the highway-map-to-street-map narrowing. Each layer's greedy walk only compares the query against the CURRENT node's direct neighbors at that layer, never the whole dataset, which is the entire source of HNSW's speed.

Interview-ready definition: HNSW search begins at a fixed entry point in the top (sparsest) layer and performs a greedy walk — repeatedly moving to whichever neighbor at the current layer is closer to the query than the current node, until no neighbor improves the distance — then descends one layer, using the best node found as the new starting point, and repeats. This continues until the greedy walk completes at layer 0, the densest layer containing every vector, which produces the final approximate nearest-neighbor result. Each layer's walk only examines the current node's local neighbors, never the full dataset, which is the structural reason HNSW search is sublinear in the number of stored vectors rather than scanning all of them.
03 — What's traded away, and what's paid for it

Approximate vs exact nearest neighbor, and the build/query trade-off

Start here, before the numbers. Imagine being asked "who in this stadium of 50,000 people is closest in height to exactly 5'11"?" One way to answer with certainty: measure every single person and compare all 50,000 heights — guaranteed correct, but it takes forever. A faster way: walk through a few strategically chosen sections first, narrow down to the section that looks closest, then only carefully check people within that section — almost certainly gets you someone very close to correct, in a tiny fraction of the time, but there's a real (small) chance the true closest person was standing in a section you never checked closely.

Exact nearest-neighbor search (brute force) compares the query vector against every single stored vector, computing a real distance to each one, and returns the true closest match — guaranteed correct, but the cost scales linearly with the number of stored vectors (O(n) per query). At millions or billions of vectors, this becomes far too slow for any interactive or high-throughput use case; a single query touching every vector doesn't scale the way an index that can skip most of the dataset does.

Approximate nearest-neighbor (ANN) search, which is what HNSW provides, sacrifices the guarantee of finding the EXACT true nearest neighbor in exchange for dramatically fewer distance comparisons per query — because the greedy layered walk only ever examines a small, local neighborhood at each step, there's a real (usually small, tunable) chance it settles into a "locally good enough" answer that isn't the globally best one, the same way the stadium search could miss the true closest person if they happened to be in a section that got skipped. This trade — accepting a small, controllable chance of imperfect results for a massive speedup — is the entire premise of ANN indexing, and it's the right trade for almost every real embedding-search use case, where "one of the very closest matches" is functionally as useful as "the single mathematically closest match."

More layers / connections per node

Better recall (closer to the true nearest neighbor), faster queries once built. But: slower to build the index (more edges to compute and insert), and more memory to hold all those extra edges — every node stores references to more neighbors across more layers.

Fewer layers / connections per node

Cheaper to build, less memory. But: worse recall (more likely to settle into a locally-good-but-not-globally-best answer), and each layer's greedy walk has fewer good paths to follow, which can also slow convergence per query in practice.

The concrete trade-off knobs: HNSW's two main build-time parameters are M (max connections per node per layer) and ef_construction (how thoroughly the graph is searched while inserting each new node, i.e. build-time recall effort). Both knobs trade the SAME resources against each other: higher M and ef_construction → better recall and often faster queries, at the cost of slower index builds and more memory to store the denser graph. A separate query-time parameter, ef_search, lets you trade query latency for recall AFTER the index is already built — searching more candidates per layer at query time costs more time but improves the odds of finding the true nearest neighbor, without requiring a full rebuild.
Interview-ready definition: HNSW trades the guarantee of exact nearest-neighbor search for approximate results found via a layered, greedy graph walk that only examines a small local neighborhood at each step — this is what makes HNSW query time roughly logarithmic rather than linear in dataset size, at the cost of a small, tunable probability of missing the true nearest neighbor. Build time, memory footprint, query speed, and recall are all coupled through the same parameters (M, ef_construction, ef_search): pushing any one of them toward "better" (more connections, more thorough construction/search) costs more of the others, so there is no free-lunch configuration — only a choice of where on that trade-off curve a given workload needs to sit.

Problem 1 · Explaining why the top layer is sparse without anyone designing it that way

Section 1's insert-time code assigns each vector a maximum layer via an exponentially-decaying random draw. Explain concretely why this alone is enough to guarantee the pyramid shape (sparse top, dense bottom) without any explicit rule saying "put fewer vectors in layer 2."

Show solution
Because the layer-assignment draw is exponential, the probability of a given vector being assigned to layer L drops off exponentially as L increases -- most vectors draw layer 0 only, a much smaller fraction also qualify for layer 1, an even smaller fraction for layer 2, and so on. Since every vector that qualifies for layer L is ALSO inserted into every layer below L (a vector present at layer 2 is also present at layer 1 and layer 0, not layer 2 alone), each layer above the base is automatically a strict subset of the layer below it, and that subset shrinks exponentially with height purely as a side effect of the random draw's probability curve. No explicit curation step ("pick which 5 vectors go in the top layer") is needed -- the sparse-top, dense-bottom shape falls out mechanically from one simple per-vector random decision made independently at insert time, which is also why HNSW doesn't need to be rebuilt from scratch to maintain that shape as vectors are added incrementally over time.
Problem 2 · Tracing what happens if the entry point's layer-2 neighbors are all far from the query

Suppose the fixed entry point at layer 2 happens to be geometrically far from the query vector, and none of its direct layer-2 neighbors improve on that distance (the greedy walk terminates immediately, after zero hops, at the entry point itself). Does the search still work? What does this reveal about the entry point's role?

Show solution
The search still proceeds -- it just descends to layer 1 immediately, using the (possibly still-distant) entry point as the starting node for layer 1's greedy walk, and continues from there. It's not broken, but this scenario is exactly the mechanism behind HNSW's imperfect recall: if the layer-2 walk gets "stuck" early at a locally-optimal-but-globally- distant node, every layer below inherits that same starting disadvantage, and the final layer-0 result may end up settling near where the walk got stuck rather than near the true global nearest neighbor. This reveals that the entry point (and the quality of the walk at the TOP layer specifically) matters disproportionately -- a bad early decision compounds through every layer below it, since each layer's walk only starts searching from wherever the layer above left off, rather than re-examining the whole space fresh at each layer. This is part of why build-time parameters like ef_construction (how thoroughly each layer is searched while the graph is being built) directly affect recall: a more thoroughly-connected graph gives the greedy walk more escape routes at each layer, reducing the odds of getting stuck exactly like this.
Problem 3 · Choosing HNSW parameters for two different products

Product A is a real-time typeahead search-as-you-type feature where sub-10ms query latency matters far more than perfect recall. Product B is an offline nightly batch job computing high-quality nearest-neighbor recommendations, where build time and query latency barely matter but recall quality directly affects revenue. How would you tune M / ef_construction / ef_search differently for each?

Show solution
Product A (typeahead, latency-critical, recall-tolerant): favor LOWER M and ef_construction (faster, cheaper index, less memory) and a LOWER ef_search at query time (fewer candidates examined per layer, faster queries) -- accepting a higher chance of a slightly-not-optimal suggestion is a completely acceptable trade for keeping every keystroke feeling instant, especially since typeahead results are inherently approximate/forgiving to the end user already (they're going to keep typing if the first suggestion isn't quite right). Product B (offline batch, recall-critical, latency-tolerant): favor HIGHER M and ef_construction (denser graph, better long-run recall, even though the index takes longer and more memory to build -- both acceptable since this runs offline overnight) and a HIGHER ef_search at query time (examine more candidates per layer, since query latency isn't the binding constraint here, and better recall directly improves recommendation quality and therefore revenue). This is a clean example of the SAME three knobs being tuned in opposite directions because the two products sit at different points on the recall/build-cost/query- latency trade-off curve described in section 3 -- there's no universally "correct" HNSW configuration, only the one that matches a given workload's actual constraints.
Problem 4 · Why HNSW query cost is sublinear, stated precisely

Explain, structurally (not just "it's a graph"), why HNSW's query cost scales roughly O(log n) with the number of stored vectors while brute-force exact search scales O(n).

Show solution
Brute-force exact search's O(n) cost comes directly from its mechanism: it computes one distance calculation per stored vector, so doubling the number of stored vectors exactly doubles the work, with no way to skip any of them without risking missing the true nearest neighbor. HNSW's roughly-O(log n) cost comes from the layered structure itself: at each layer, the greedy walk only examines a small, roughly constant number of candidates (the current node's direct neighbors at that layer) before either converging or moving to the next layer -- the work done AT EACH LAYER doesn't grow with total dataset size, only with each node's fixed connection count (M). What DOES grow (slowly) with dataset size is the NUMBER of layers needed for the pyramid to taper from "a handful of nodes at the top" down to "every node at the bottom" -- and because each layer holds an exponentially decreasing fraction of the vectors below it (section 1), the number of layers needed grows only logarithmically with total vector count. Roughly constant work per layer times logarithmically-many layers gives roughly O(log n) total query cost -- fundamentally different scaling behavior from brute force's linear per-vector cost, which is the entire reason HNSW remains fast at vector counts where brute force becomes impractical.
Problem 5 · Diagnosing a recall complaint from production

A team reports their HNSW-backed semantic search "used to return great results in testing but recall has visibly degraded in production, even though they haven't changed M or ef_construction." What's a plausible explanation that doesn't involve those two build-time parameters, and how would you confirm it?

Show solution
A plausible explanation not involving M or ef_construction: the QUERY-time parameter ef_search was left low (or defaulted low) for production, likely to minimize latency under real production traffic volume, whereas testing may have used a higher ef_search (more thorough per-layer search) without the team realizing that knob differs from the build-time parameters and needed separate tuning for production load. Since ef_search controls how many candidates are examined per layer AT QUERY TIME (independent of how the index was built), a lower production ef_search directly and immediately explains a recall regression with no change to the underlying graph structure at all -- the exact same index, queried less thoroughly, produces measurably worse results. To confirm: compare the ef_search value actually configured in the production query path against what was used during testing/evaluation; if production is meaningfully lower, temporarily raising it (accepting the added query latency) and re-measuring recall on the same queries should recover most or all of the lost recall, confirming ef_search as the cause rather than anything about the index's construction.
