01 — A vector alone can't answer "which documents, and from when?"

Storing embeddings alongside metadata: a real schema

Start here, before any schema. Imagine a library that only shelved books by their exact physical dimensions — height, width, thickness — with no title, no author, no subject label anywhere on the spine. You could technically find "books shaped like this one," but you could never ask "give me books shaped like this one, published after 2020, in the science section." The vector alone (the "shape") answers the SIMILARITY question. Everything else — category, timestamp, source, permissions — has to live somewhere too, or the system can only ever answer "what's similar," never "what's similar AND relevant to this specific context."

A real vector DB row (or document, depending on the store) needs both: the raw embedding, AND structured metadata columns that describe what the embedding represents.

ColumnTypePurpose
iduuid / bigint (PK)Primary key for the row itself
embeddingvector(768)The actual embedding — a fixed-length array of floats, dimension matching the embedding model used
chunk_texttextThe source text this embedding represents (needed to actually show/use the retrieved content, not just its vector)
categorytext / enume.g. "electronics", "support-docs", "legal" — used for metadata filtering
source_doc_iduuid (FK)Which parent document this chunk came from — for citation and dedup
created_attimestampWhen this chunk was indexed — for recency filtering/sorting and staleness checks
access_scopetext / jsonWhich users/roles/tenants can see this chunk — a real, common production requirement
-- Postgres + pgvector, as a concrete example CREATE TABLE document_chunks ( id uuid PRIMARY KEY DEFAULT gen_random_uuid(), embedding vector(768) NOT NULL, chunk_text text NOT NULL, category text NOT NULL, source_doc_id uuid REFERENCES documents(id), created_at timestamptz NOT NULL DEFAULT now(), access_scope jsonb NOT NULL DEFAULT '{}' );

Why not JUST the vector: without category, there's no way to answer "search only within electronics" without either searching everything and hoping the results happen to be electronics (unreliable), or maintaining a completely separate index per category (operationally heavier, and doesn't compose when a query needs to filter on MULTIPLE metadata fields at once). Without access_scope, a multi-tenant RAG system has no way to prevent one tenant's search from surfacing another tenant's private documents — a real security requirement, not a nice-to-have. The vector answers "how similar," the metadata columns answer everything else a real query needs to also be true.

Interview-ready definition: a vector database schema pairs a fixed-dimension vector column (the embedding, used for similarity search) with structured metadata columns (category, timestamp, source, access control, and any other queryable attribute) describing what that embedding represents. The vector column alone can only ever answer "what's most similar to this query" — metadata columns are what let a real system answer the compound question "what's most similar to this query, AND satisfies these other constraints," which is what nearly every production retrieval query actually needs.
02 — Same query, same metadata constraint, two different orders of operations

Metadata filtering: pre-filter vs post-filter, animated

Start here, before running the demo. Imagine searching a huge warehouse for "the red item closest in size to this sample" but you ALSO only care about items in aisle 3. One approach: walk directly to aisle 3 first, then compare sizes only among what's there. The other approach: find the closest-sized items across the ENTIRE warehouse first, then check afterward which of those top matches happen to be in aisle 3 — and if none of them are, you get nothing useful, even though aisle 3 definitely has red items, just not ones that happened to make the initial top-K cut.

Pre-filtering narrows the candidate set by metadata BEFORE running vector search — e.g. "only search within category = 'electronics'," then run the similarity search purely over that narrowed subset. Post-filtering does the reverse: run vector search first over the FULL dataset, get the top-K most similar results, THEN filter those results by the metadata constraint afterward.

Pre-filter

More efficient when the constraint is selective (electronics is a small slice of the dataset) — vector search only ever runs over the already-narrowed candidate set. Requires the index itself to support filtered search (not every ANN index does this cheaply — filtering has to be pushed INTO the search, not bolted on after).

Post-filter

Simpler to implement — any vector index works, since filtering is just a plain post-processing step on the returned results. But if too many of the top-K matches get filtered out (e.g. the true top 3 similar items are ALL non-electronics), the caller can end up with fewer than k results, or even zero, despite genuinely relevant electronics items existing further down the unfiltered ranking.

Interview-ready definition: pre-filtering applies metadata constraints before vector similarity search runs, restricting the search to only the qualifying subset — more efficient when the constraint is selective, but requires the underlying index structure to support filtered search natively. Post-filtering runs similarity search first over the full unfiltered dataset, then discards non-matching results afterward — simpler to implement against any index, but risks returning fewer than k results (or missing genuinely relevant matches entirely) when the metadata constraint excludes a large fraction of the true top-ranked candidates.
03 — Connecting back to Week 1: which index for which configuration

Indexing strategy for the vector column

Start here, before the table. Week 1 covered HNSW (graph-based, sub-linear query, higher memory) and IVF (cluster-based, requires a training step, different recall/speed profile) as two ANN index families. Choosing between them for a real vector column isn't abstract — it depends directly on this week's schema decisions: how often the data changes, how large the dataset is, and whether filtering needs to be pushed into the index itself.

ConfigurationBetter fitWhy, connecting to Week 1
Frequent inserts, streaming new documents (e.g. a live RAG corpus)HNSWHNSW supports incremental insertion without a full rebuild (this week's hnsw_from_scratch lab, section 3) — new chunks can be added to the graph as they arrive. IVF's cluster assignments are trained on a snapshot of the data; a large enough distribution shift after training degrades recall until retrained.
Very large dataset, memory-constrainedIVFIVF stores vectors grouped into clusters with much lighter per-vector overhead than HNSW's multi-layer graph edges — the Week 1 ivf_indexing lab's memory/training trade-off. HNSW's graph structure (every point's edges across however many layers it participates in) costs meaningfully more memory per stored vector.
Metadata pre-filtering required, filter is highly selectiveDepends on DB support — often IVF-family with partitioning, or HNSW variants with filtered search supportNot every ANN index supports pushing a metadata filter INTO the search efficiently. Some vector DBs partition IVF clusters by a metadata field directly (e.g. one IVF index per category), making pre-filtered search a matter of only searching the relevant partition's index — a design choice this week's schema section 1 supports directly via the category column.
Read-heavy, dataset relatively stable, latency-criticalHNSWHNSW's query-time cost (Week 1 lab: roughly O(log n)) tends to be faster and more consistently low-latency than IVF once both are well-tuned, at the cost of the memory and build-time trade-offs above (this week's hnsw_from_scratch section 3's insertion-order and build-cost discussion).
Interview-ready definition: choosing an ANN index type for a vector column is a workload-shape decision, not a universal "which is better" choice — HNSW favors workloads with frequent incremental inserts and latency-critical reads (at higher memory cost per vector), while IVF favors very large, memory-constrained, or filter-partitionable datasets (at the cost of a training step and periodic retraining as data distribution shifts). This decision connects directly back to Week 1's HNSW and IVF labs — the same M/ef_construction/ef_search and nlist/nprobe trade-off knobs from those labs are exactly what gets tuned once an index type is chosen for a real schema like this one.

Problem 1 · Designing a schema for a concrete multi-tenant use case

A RAG system serves multiple companies (tenants) from one shared vector database, and one tenant's documents must NEVER be searchable by another tenant. Using section 1's schema, what column(s) are load-bearing for this requirement, and where does the enforcement actually have to happen — at query time in application code, at the database/index level, or both?

Show solution
The load-bearing column is section 1's access_scope (or a simpler dedicated tenant_id column, which is really a more specific version of the same idea) -- every stored chunk needs an explicit, queryable record of which tenant it belongs to. Enforcement has to happen at BOTH levels, not just one, and this is the actual point being tested. If enforcement only happens in application code (e.g. the app filters returned results by tenant_id AFTER getting them back from the vector search), that's exactly section 2's post- filter pattern applied to a security boundary instead of a convenience filter -- and it inherits post-filter's exact weakness: if vector search returns its top-K results and NONE of them happen to belong to the requesting tenant, the app-layer filter correctly returns nothing, but the vector search itself still SCANNED and ranked another tenant's data internally, and a bug in the app-layer filtering step (missed once, anywhere in the codebase) means a full cross-tenant data leak with no safety net. Enforcement should be pushed into the query itself (pre-filtering by tenant_id, section 2's pre-filter pattern) so that vector search never even considers another tenant's rows as candidates -- the database/index layer, not just application code, should be the actual boundary. This is a case where pre-filtering isn't just a performance choice, it's the difference between a real security boundary and an easily-bypassable convenience filter.
Problem 2 · Predicting when post-filter returns fewer than k results

A dataset of 10,000 chunks is 2% "legal" category (200 chunks) and 98% everything else. A query asks for the top 10 most similar chunks WITHIN category="legal", using post-filtering with an initial unfiltered top-50 candidate pull. Under what condition does this return fewer than 10 results, and how would you fix it without switching to pre-filtering?

Show solution
This returns fewer than 10 results if fewer than 10 of the initial unfiltered top-50 candidates happen to be in the "legal" category. Given legal is only 2% of the dataset, the EXPECTED number of legal chunks in a random top-50 slice would be roughly 1 (50 * 0.02), though similarity search isn't random sampling -- if legal chunks happen to also be semantically close to this specific query, more than the base rate could appear. But in the likely case where the query isn't specifically legal-flavored, pulling only 50 unfiltered candidates and hoping 10 of them are legal is a real, probable failure -- there just may not BE 10 genuinely top-similar legal chunks within the first 50 overall matches. Fix without switching to pre-filtering: pull a much larger unfiltered candidate set before filtering -- e.g. request the top 500 or 1000 unfiltered candidates instead of 50, then filter down to legal-only and take the top 10 of THOSE. This raises the odds that enough legal-category chunks appear somewhere in the larger initial pull, at the direct cost of more compute spent on vector search (a bigger initial top-K pull is more expensive) and more post-processing -- which is exactly section 2's efficiency trade-off made concrete: post-filtering's fix for low-hit-rate categories is "search more broadly first," which is precisely the extra cost pre-filtering avoids by never considering the other 98% of the dataset as candidates in the first place.
Problem 3 · Choosing HNSW vs IVF for a described workload

A support-ticket search system ingests roughly 5,000 new tickets per day (continuous, not batched), holds about 2 million vectors total, and needs sub-50ms search latency. Using section 3's table, which index type fits better, and what would concern you about the other choice?

Show solution
HNSW fits better here. Two of section 3's criteria point the same direction: continuous, frequent inserts (5,000/day, not a periodic batch) favor HNSW's support for incremental insertion without a full rebuild, and the sub-50ms latency requirement favors HNSW's typically faster, more consistent query-time cost once tuned. What would concern you about IVF here: IVF's clusters are trained on a snapshot of the data at some point in time. With 5,000 new vectors arriving daily, the data distribution IVF's clusters were trained on starts drifting from the CURRENT actual data distribution immediately, and this drift compounds every day post-training -- eventually new tickets may not map well to any existing cluster centroid, degrading recall for exactly the newest, potentially most relevant tickets. Fixing this would require periodic retraining (recomputing cluster centroids against the current full dataset), which is itself a real operational cost and a source of temporary index unavailability or a live-vs-stale- index cutover complexity that HNSW's incremental-insert model avoids needing at all for this specific workload shape.
Problem 4 · Diagnosing a pre-filter that made things slower, not faster

A team switches from post-filtering to pre-filtering expecting a speedup, but query latency gets WORSE. The metadata filter they're applying matches 95% of the dataset (nearly everything qualifies). Using section 2's reasoning, explain why pre-filtering didn't help here, and what property of the filter actually determines whether pre-filtering helps at all.

Show solution
Pre-filtering's efficiency benefit (section 2's dc-compare) comes from narrowing the candidate set BEFORE the expensive similarity search runs -- but that benefit is proportional to how SELECTIVE the filter actually is. A filter matching 95% of the dataset barely narrows anything at all -- vector search still has to effectively operate over almost the entire dataset either way, so pre-filtering provides almost none of its intended benefit. Worse, pre-filtering can add its OWN overhead on top of that: depending on how the index implements filtered search, evaluating the metadata predicate against (or integrating it into) the ANN index's search process can itself carry real cost -- for example, if the index has to check the metadata condition at every node/cluster it visits during the graph walk or cluster scan, rather than being able to use a pre-built, efficient structure specifically optimized for that filter. When the filter barely narrows anything, that added filtering overhead can exceed whatever savings come from touching slightly fewer candidates, producing a net slowdown -- exactly the symptom described. The property that determines whether pre-filtering helps: SELECTIVITY -- how small a fraction of the dataset the filter actually admits. Highly selective filters (a rare category, a narrow time window) are where pre-filtering earns its efficiency advantage (section 2's dc-compare: "more efficient when the constraint is selective"); filters that admit nearly everything gain little or nothing from pre-filtering and can, as here, actually lose to simple post-filtering, which has no extra per-candidate filtering overhead built into the search itself.
Problem 5 · Designing for a filter whose selectivity varies by query

A system's queries sometimes filter by a rare category (0.5% of data) and sometimes by a common one (60% of data), depending on the user. Using Problems 2 and 4's findings together, would you hardcode either pre-filter or post-filter for this system, or design something else? Sketch the approach.

Show solution
Hardcoding either strategy is the wrong call here, precisely because Problems 2 and 4 show the two strategies' relative merits flip depending on filter selectivity -- pre-filtering wins decisively for the rare 0.5% category (Problem 4's logic in reverse: a highly selective filter is exactly where pre-filtering's narrowing benefit is largest), while for the 60%-of-data category, pre-filtering barely narrows anything and risks the exact overhead-without-benefit problem Problem 4 diagnosed -- post-filtering, or a large-enough unfiltered top-K pull (Problem 2's fix), is likely simpler and just as fast for that case. A better design: compute or estimate the filter's SELECTIVITY at query time (e.g. maintain a rough per-category row count, cheap to keep updated) and branch the query strategy based on it -- below some selectivity threshold (say, filter matches under ~10% of the dataset), use pre-filtering; above that threshold, use post-filtering (or an unfiltered top-K pull sized generously enough per Problem 2's fix). This is a genuinely common real-world pattern in production vector databases and query planners more broadly (the same idea underlies a relational query planner choosing between an index scan and a full table scan based on estimated selectivity) -- the "right" filtering strategy isn't fixed per system, it's a per-query decision informed by how selective THIS query's filter actually is, and treating it as a single global choice is the mistake this problem is pointing at.
