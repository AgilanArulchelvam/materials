01 — Two fundamentally different ways to decide "relevant"

Dense embedding search vs sparse BM25

Start here, before any formulas. Imagine two different librarians helping you find a book. The first librarian has read every book and understands what each one is ABOUT — ask for "something about overcoming adversity" and they'll point you to a book that never uses those exact words but is clearly about that theme. The second librarian hasn't read the books, but has a perfect index of every word that appears in every book and how often — ask for a book containing the exact phrase "ISBN 978-0-13-468599-1" and they'll find it instantly, something the first librarian's thematic understanding is no help with at all.

Dense embedding search represents each document (or chunk) as a dense vector — a fixed-length list of numbers capturing its semantic meaning, produced by an embedding model. A query is embedded the same way, and documents are ranked by embedding similarity (typically cosine similarity) to the query. Because the comparison happens in a learned semantic space, dense search finds conceptually related results even with little or no literal word overlap — the "first librarian." Sparse search, and specifically BM25 (the standard modern implementation of classic TF-IDF-style scoring), represents documents and queries as sparse vectors over the vocabulary — mostly zeros, with a nonzero weight for each term that actually appears. BM25 scores a document highly when it contains the query's exact terms, weighted by how rare those terms are across the whole collection (a rare term matching is a stronger signal than a common one) and how densely they appear in that document relative to its length — the "second librarian."

# BM25, conceptually: score a document by summing a per-term contribution # for every query term the document actually contains def bm25_score(query_terms, doc, corpus_stats): score = 0 for term in query_terms: if term not in doc.terms: continue # BM25 contributes NOTHING for a term that's simply absent idf = inverse_document_frequency(term, corpus_stats) # rarer term = higher weight tf = term_frequency(term, doc) # how often it appears here score += idf * saturate(tf, doc.length) # diminishing returns per repeat return score

Dense embedding search

Good at: conceptual/semantic similarity, paraphrases, synonyms, "meant the same thing but said it differently." Weak at: exact identifiers, rare technical terms, codes/IDs that carry no semantic meaning of their own.

Sparse search (BM25)

Good at: exact keyword/term matches, codes, product IDs, rare or technical vocabulary. Weak at: matching a relevant passage that expresses the same idea with completely different words.

Interview-ready definition: dense embedding search ranks documents by semantic similarity between learned dense vector representations of the query and each document, making it strong at conceptual/paraphrase matches but weak at exact literal matches on terms with little semantic content (IDs, codes, rare tokens). BM25 (sparse search) ranks documents by a term-frequency-based scoring function over the literal vocabulary, weighting rarer terms more heavily and applying diminishing returns to repeated terms — making it strong at exact keyword matches but blind to relevant content that shares no vocabulary with the query at all.

Pick a query and run both searches to compare what each one surfaces.
Failure mode 1 — dense misses the exact code: the query "error code E4471-B retry" contains a specific alphanumeric code. A dense embedding model has likely never seen "E4471-B" in training in any meaningful semantic context — it has no learned meaning, so the embedding for a document containing it looks about as similar to the query as any other vaguely error-related document. BM25, however, treats "E4471-B" as a rare, highly-weighted term (inverse document frequency is high for a code that appears in very few documents) and finds the one document containing it almost instantly, ranking it far above semantically-similar-but-code-lacking documents.
Failure mode 2 — BM25 misses the paraphrase: the query "why does my payment keep failing" shares almost no vocabulary with a document titled "Troubleshooting recurring transaction declines," even though they're clearly about the same underlying issue. BM25 scores near zero — there's no term overlap for it to score against. Dense search, however, embeds both the query and that document into the same conceptual neighborhood (payment failure / transaction decline are semantically close), and ranks that document highly despite the near-total absence of shared words.
Interview-ready definition: dense search and BM25 fail in structurally opposite, complementary ways: dense search's semantic embedding has no special mechanism for surfacing rare literal tokens with little inherent meaning (codes, IDs), so exact-match queries can rank the correct document low or miss it; BM25's term-overlap scoring has no mechanism for recognizing that two different vocabularies describe the same concept, so paraphrased or synonym-heavy queries can score the correct document near zero. Because the two failure modes are largely independent — a query that breaks one often doesn't break the other — combining their rankings recovers cases that either method alone would miss.
03 — Combining two rankings into one, without needing comparable scores

Combining both via reciprocal rank fusion (RRF)

Start here, before the formula. Imagine two judges scoring a competition on totally different scales — one judge scores out of 10, the other scores out of 100 — and you need one final ranking. Averaging their raw scores would be misleading (a 7/10 and a 70/100 look identical numerically but came from different scales entirely). A more robust approach: ignore the raw scores completely and just look at each judge's RANKING — who they placed 1st, 2nd, 3rd — then combine the rankings themselves, rewarding whoever consistently ranked well across both judges.

Reciprocal rank fusion does exactly this for combining dense and BM25 results, which is important because their raw scores are NOT directly comparable — dense similarity scores and BM25 scores live on completely different, incompatible numeric scales, so simply adding them together would be meaningless. RRF instead uses each result's RANK (1st, 2nd, 3rd...) in each ranked list, converting it to a score via 1 / (k + rank) (with a small constant k, commonly 60, that dampens the impact of very high ranks) and summing that reciprocal-rank score across all the lists a document appears in. A document that ranks well in EITHER list gets a meaningful boost; a document that ranks well in BOTH gets boosted twice, landing near the top of the fused result.

# Reciprocal Rank Fusion, k=60 (a common default) def reciprocal_rank_fusion(dense_ranked, sparse_ranked, k=60): scores = {} for rank, doc_id in enumerate(dense_ranked, start=1): scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank) for rank, doc_id in enumerate(sparse_ranked, start=1): scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank) # a doc in BOTH lists accumulates score from both terms -- doesn't # need a comparable raw score from either search, only its RANK return sorted(scores.items(), key=lambda x: -x[1])
RRF FUSION — SEE BOTH FAILURE-MODE DOCUMENTS RECOVERED

A query where dense search ranks doc E4471 low (no semantic signal for the code) but BM25 ranks it 1st, while another doc ranks well in dense but not sparse. Watch the fused ranking recover both.

Interview-ready definition: reciprocal rank fusion combines multiple ranked result lists (e.g. dense and BM25) into one fused ranking by summing each document's reciprocal-rank contribution (1/(k+rank)) across every list it appears in, rather than combining raw scores directly — this sidesteps the problem that dense similarity scores and BM25 scores are on incomparable scales, since rank position is a scale-independent signal both methods produce. A document that ranks well in only one list still gets meaningfully boosted, which is exactly the mechanism by which hybrid search recovers both failure modes from section 2: the exact-match document BM25 alone would rank first stays highly ranked in the fusion even though dense search barely noticed it, and vice versa for the paraphrase-matched document.

Problem 1 · Predicting BM25's score for a term that never appears

Looking at section 1's bm25_score pseudocode, what does BM25 contribute to a document's score for a query term that appears ZERO times in that document? What does this reveal about BM25's fundamental limitation?

Show solution
Exactly zero -- the code explicitly checks `if term not in doc.terms: continue`, skipping that term's contribution entirely rather than assigning any partial credit. BM25 has no notion of "this document is somewhat related to this term even though the term itself never appears" -- its entire scoring mechanism is built around literal term presence, so a term's absence contributes nothing, positive or negative, beyond simply not adding to the score. This reveals BM25's fundamental limitation directly: it has no mechanism for recognizing conceptual relatedness in the absence of shared vocabulary. A document that is a near-perfect semantic match for the query but happens to use zero of the query's literal terms scores identically (near zero) to a document that has nothing at all to do with the query -- BM25 cannot distinguish between "irrelevant" and "relevant but phrased completely differently," which is exactly the paraphrase failure mode demonstrated in section 2.

Problem 3 · Explaining why raw scores aren't just averaged instead

Someone proposes simplifying hybrid search by just averaging the raw dense cosine-similarity score and the raw BM25 score for each document, instead of using RRF. What specifically goes wrong with this approach?

Show solution
Dense cosine similarity and BM25 scores live on fundamentally different, incompatible numeric scales -- cosine similarity is typically bounded between -1 and 1 (often clustering in a narrow band like 0.7-0.95 for "relevant" results in practice), while BM25 scores are unbounded and can range anywhere from 0 to double digits or higher depending on term rarity, document length, and the specific corpus statistics. Averaging two numbers from different scales directly means whichever score happens to have the larger typical MAGNITUDE (often BM25's, since it's unbounded) will dominate the average almost regardless of the other score's actual relative meaning within its own scale -- a mediocre BM25 score of 8 could easily outweigh a near-perfect dense similarity of 0.95, not because it's actually more relevant, but purely because of a scale mismatch that has nothing to do with relevance. This is exactly the problem RRF sidesteps by discarding raw scores entirely and working only with RANK POSITION within each list -- rank 1 means the same thing (the single best result according to that method) regardless of what raw score produced it, making ranks directly combinable across methods in a way raw scores from different scoring functions never are without careful, corpus-specific normalization that RRF avoids needing at all.
Problem 4 · Choosing when hybrid search is worth the extra infrastructure

A product's search queries are almost entirely natural-language questions from end users ("how do I reset my password"), with essentially no exact codes, IDs, or technical jargon ever appearing in real queries. Is hybrid search still clearly worth the added infrastructure (maintaining both a dense index and a BM25 index, plus fusion) over dense search alone?

Show solution
The case for hybrid search is meaningfully weaker here, though not necessarily zero. Hybrid search's core value proposition (section 2) is recovering BM25's exact-match strength for queries dense search would otherwise miss -- codes, IDs, rare technical terms. If real user queries are overwhelmingly natural-language and essentially never contain exact identifiers, the specific failure mode BM25 exists to catch (dense missing an exact code match) may simply not occur often in this product's actual query distribution, meaning the added cost of maintaining a second index and a fusion step may not be earning its keep proportional to its operational cost. That said, "essentially no exact codes" is a claim worth verifying with real query logs rather than assuming -- and BM25 also helps with rare but non-code technical vocabulary (a specific error message string, a specific setting name) that a dense model may not have learned a distinct embedding for if it was underrepresented in training data. A reasonable answer weighs this against the product's actual measured query patterns rather than deciding purely from the stated assumption -- and notes that if the answer is "probably not worth it right now," it's a decision worth revisiting if the query distribution changes (e.g. the product adds a technical support surface where users paste in error codes).
Problem 5 · Diagnosing why hybrid search still missed a relevant result

A team ships hybrid search with RRF, but a specific query still fails to surface a genuinely relevant document. On investigation, that document didn't appear in EITHER the dense top-50 or the sparse top-50 candidate lists that were fused. Is this an RRF fusion bug? What's actually going on, and what does it reveal about RRF's dependency on its inputs?

Show solution
This is not an RRF fusion bug -- RRF can only combine and re-rank documents that appear in at least one of the input ranked lists it's given. If a document never made it into EITHER the dense top-50 or the sparse top-50 candidate set to begin with, RRF has no rank information for it at all and therefore cannot include it in the fused output, regardless of how relevant that document actually is. RRF's job is combining rankings, not independently discovering documents neither underlying search method surfaced. This reveals that RRF's output quality is fundamentally bounded by the RECALL of its inputs -- if both the dense and sparse retrieval steps individually fail to surface a genuinely relevant document within their own top-k candidate sets (perhaps k=50 is too small, or both methods happen to score this specific document poorly for method- specific reasons unrelated to each other), fusion cannot rescue it, since there's nothing to fuse. The fix here isn't touching the RRF logic itself -- it's investigating why NEITHER underlying retrieval method surfaced the document within its candidate window (too small a k for each method's initial retrieval, or a chunking/embedding issue specific to that document), since RRF's entire premise depends on at least one of the two methods finding the right answer somewhere within the list it hands to fusion.
