01 — Not accuracy, not precision — specifically, overlap with the true top-k

What "recall" means precisely, here

Start here, before any numbers. Imagine asking two research assistants to find your 5 closest friends by how often you've talked in the last year. One assistant checks EVERY single contact you have — slow, but guaranteed correct. The other assistant uses a fast shortcut — skims a much smaller set of likely candidates — and comes back quickly with their own list of 5. Recall, in this context, asks one specific question: of the 5 people the slow-but-guaranteed-correct assistant would have found, how many did the fast assistant's list ALSO include?

Concretely: brute-force search over a query returns the TRUE top-k nearest neighbors — by definition, since it exhaustively checks every vector (this week's day-1 lab). An approximate index (HNSW-style, day-2 lab) returns its OWN top-k, found via the greedy layered walk, which may or may not exactly match brute force's list. Recall@k is the fraction of brute force's true top-k that ALSO appears in the approximate index's returned top-k.

WORKED EXAMPLE — TRUE TOP-5 VS APPROXIMATE TOP-5
Brute force (true): 31742891
HNSW (approx): 3174289155

Brute force's true top-5 is [3, 17, 42, 8, 91]. HNSW's approximate top-5 is [3, 17, 8, 55, 91] — 4 of the 5 true neighbors (3, 17, 8, 91) appear in HNSW's list; only 42 is missing, replaced by 55 (a node HNSW's greedy walk found instead, close but not actually in the true top-5). Recall@5 = 4/5 = 80%.

# recall@k for a single query def recall_at_k(true_neighbors, approx_neighbors): true_set = set(true_neighbors) approx_set = set(approx_neighbors) return len(true_set & approx_set) / len(true_set) print(recall_at_k([3,17,42,8,91], [3,17,8,55,91])) 0.8 # 80% recall@5, matching the worked example above # recall over a full benchmark: run many queries, average per-query recall def benchmark_recall(queries, brute_force_index, approx_index, k=10): scores = [] for q in queries: true_top_k = brute_force_index.search(q, k) approx_top_k = approx_index.search(q, k) scores.append(recall_at_k(true_top_k, approx_top_k)) return sum(scores) / len(scores) # average recall@k across all queries
Interview-ready definition: recall@k measures what fraction of the TRUE top-k nearest neighbors (as determined by exhaustive brute-force search) an approximate index's own returned top-k actually contains, averaged across many benchmark queries. It is not the same as precision or accuracy in the classification sense — it specifically measures OVERLAP between two ranked result sets of the same size k, and it exists as a metric specifically because approximate indexes (this week's HNSW-style build) trade a small, measurable chance of missing true neighbors for dramatically faster query time — recall quantifies exactly how much of that trade is actually being paid.
02 — Not a single query — many, averaged, on a real-sized set

Run the benchmark: recall vs brute force on a 10,000-vector set

Start here, before running it. A single query's recall (section 1's worked example) is a data point, not a benchmark. A real benchmark runs MANY queries against the SAME dataset and index, computes recall@k for each one independently, then averages — because any one query could get lucky or unlucky, but the average across dozens or hundreds of queries is a genuinely representative measure of how well-tuned the approximate index actually is.

SIMULATED BENCHMARK — 10,000-VECTOR SET, 30 QUERIES, k=10

Each run simulates 30 queries against a 10,000-vector dataset, comparing brute-force ground truth to an HNSW-style index's approximate top-10 for each query, exactly as benchmark_recall above does. Results vary slightly run to run — like a real benchmark would.

Interview-ready definition: a recall benchmark runs a representative sample of real queries against both the ground-truth brute-force index and the approximate index being evaluated, computes recall@k for each query independently, and reports the AVERAGE — a single query's recall is noisy and not representative on its own, so credible recall numbers always come from averaging over a meaningful query sample (dozens to hundreds of queries, ideally reflecting the actual query distribution the production system will see), not a single spot-check.
03 — Below 90%? Here's exactly what moves the number

Confirming the ~90% recall target — and what to tune if you're below it

Start here, before the table. A recall benchmark that comes back below target isn't a dead end — it's a diagnostic pointing at specific, known knobs. Every one of these knobs trades query speed (or build time/memory) for recall, echoing the exact trade-off curve from the Week 1 hnsw_indexing lab and this week's hnsw_from_scratch lab — there's no free-lunch setting, only a choice of where on that curve to sit.

KnobDirection to raise recallWhat it costs
ef_searchIncrease — examine more candidates per layer at query timeQuery latency, immediately, per query — no rebuild needed, this is a query-time-only knob
M (max connections per node)Increase — denser graph, more paths for greedy search to find true neighborsBuild time and memory (more edges to store per node, across every layer that node participates in) — requires a rebuild
Number of layers / level_multiplierIncrease — taller pyramid, more graduated descent, less chance of getting stuck earlyBuild time and memory, similar to M, plus insertion cost — requires a rebuild (this week's hnsw_from_scratch lab, section 1)
ef_constructionIncrease — more thorough search while building each node's connectionsBuild time specifically (slower index construction) — requires a rebuild, but doesn't add query-time cost

The fastest, cheapest fix to try FIRST is almost always ef_search, precisely because it's the only knob in this table that doesn't require rebuilding the index — it's read at query time, so raising it and re-running the benchmark is a matter of minutes, not a full re-index. If recall is still short of target even after raising ef_search substantially, that's the signal to consider the build-time knobs (M, layers, ef_construction), which cost more to iterate on but can fix recall problems that ef_search alone can't — for instance, if the graph structure itself is too sparse to ever reach certain true neighbors regardless of how thoroughly it's searched at query time.

Interview-ready definition: when a benchmarked HNSW-style index falls short of a recall target, the fix is tuning one or more of its trade-off knobs (ef_search, M, layer count, ef_construction) toward "more thorough" — each knob trades away either query latency (ef_search, the query-time-only, no-rebuild-required knob) or build time/memory (M, layers, ef_construction, all requiring a rebuild) in exchange for higher recall. There is no single "correct" configuration — only a configuration that hits the specific recall/latency/memory point a given workload actually needs, discovered by iterating the cheapest-to-adjust knob (ef_search) first before reaching for the more expensive, rebuild-requiring ones.

Problem 1 · Computing recall@k by hand for a new example

Brute force's true top-6 for a query is [5, 12, 19, 23, 31, 44]. An HNSW-style index returns [5, 12, 99, 23, 31, 7]. Compute recall@6 by hand, showing the set intersection.

Show solution
True set: {5, 12, 19, 23, 31, 44}. Approx set: {5, 12, 99, 23, 31, 7}. Intersection: {5, 12, 23, 31} -- 4 elements shared. 19 and 44 are missing from the approximate result (replaced by 99 and 7, neither of which is in the true top-6). Recall@6 = |intersection| / |true set| = 4 / 6 ≈ 0.667, or about 66.7%. This is below the 90% target from section 3 -- section 3's tuning table is exactly what you'd reach for next to try to close this specific gap.
Problem 2 · Explaining why recall is computed per query and averaged, not computed once globally

Someone proposes simplifying the benchmark: instead of running 30 separate queries and averaging their individual recall@k scores, just run ONE large query with k=300 and compute recall@300 once. Why doesn't this give an equivalent, valid recall measurement?

Show solution
This conflates two genuinely different things: recall@k for ONE query with a large k, versus the AVERAGE of recall@k across MANY different queries each with a realistic k. A production system's actual query pattern is many different queries, each asking for a modest k (e.g. top 10) -- section 2's benchmark_recall function is built to mirror exactly that real usage pattern, averaging per-query recall over queries that resemble what the system will actually see. A single query with k=300 measures something different: how well the approximate index finds a much LARGER neighborhood around one specific point in the vector space, which doesn't necessarily generalize to how well it performs across queries scattered throughout different regions of that space. The approximate index's recall can genuinely vary by region -- a densely-populated area of the embedding space might have excellent local graph connectivity and high recall, while a sparser region might have gaps that hurt recall specifically there. Averaging many DIFFERENT queries' recall@k (section 2's actual approach) captures that regional variation; one giant query at one point in the space doesn't -- it's measuring a different, less representative thing, even though both produce "a recall number."
Problem 3 · Diagnosing which knob to raise given a described failure pattern

A benchmark shows recall@10 stuck at 65% even after raising ef_search from 10 all the way to 500 (a huge increase, with query latency now noticeably worse) — recall barely moved. Using section 3's table, what does this suggest about where the actual problem lies, and what would you try next?

Show solution
This suggests the bottleneck isn't how THOROUGHLY each layer is being searched at query time (which is exactly what ef_search controls) -- it suggests the underlying GRAPH STRUCTURE itself may be too sparse or poorly connected to reach certain true neighbors AT ALL, regardless of how much query-time search effort is thrown at it. Raising ef_search lets the greedy walk examine more candidates per layer, but if the true nearest neighbors are structurally unreachable from the walk's actual path (too few edges, or a poorly-connected region of the graph, per this week's hnsw_from_scratch lab's insertion-order and M discussion), no amount of additional query-time search effort recovers what the graph structure itself never wired in as a reachable path. What to try next: the BUILD-time knobs from section 3's table -- specifically raising M (more connections per node, giving the greedy walk more paths per layer, per hnsw_from_scratch section 2) and/or raising ef_construction (a more thorough search during insertion means each node's neighbors are chosen more accurately in the first place, per the Week 1 hnsw_indexing lab's build-time trade-off discussion). Both require a full rebuild of the index, unlike ef_search -- but this symptom (recall plateauing despite a large ef_search increase) is precisely the signal that distinguishes a query-time-search problem from a graph-structure problem, and only the build-time knobs fix the latter.
Problem 4 · Weighing the ef_search-vs-M trade-off for a specific deployment

A team is below the 90% recall target. Raising ef_search alone would get them to 90% but at 3x current query latency. Raising M alone (via a rebuild) would also get them to 90%, but at a 40% increase in index memory and a one-time multi-hour rebuild. The system is latency-critical (sub-50ms) but has ample memory headroom and can tolerate an offline rebuild window. Which would you choose, and why?

Show solution
Raise M via a rebuild, not ef_search, given these specific constraints. The deciding factor is which resource the system actually has slack in: this system is explicitly latency-critical (sub-50ms), so a 3x query latency increase from raising ef_search is a direct hit to the constraint that matters most here -- even if 3x still technically stays under 50ms in absolute terms, it's eating directly into the system's most protected resource for no reason when an alternative exists. Meanwhile, the system explicitly has "ample memory headroom" and can tolerate an offline rebuild window -- both of M's costs (memory, one-time rebuild time) land squarely on resources this system has been described as having slack in. This is exactly the point of section 3's table laying out knobs with DIFFERENT cost shapes rather than presenting "raise some HNSW parameter" as one undifferentiated fix -- ef_search and M solve the same recall problem but spend genuinely different resources to do it, and the "right" choice depends entirely on which resource a given deployment can actually afford to spend. A team without memory headroom or without an acceptable rebuild window, facing the identical recall shortfall, would reasonably make the opposite choice -- there's no universal answer, only a match between the available knobs' cost shapes and this specific system's actual constraints.
Problem 5 · Explaining a sharding trade-off out loud (the Month 3 checkpoint's second half)

The Month 3 checkpoint (below) asks you to explain a sharding trade-off out loud, in addition to the recall benchmark. Using this week's engine (a vector index over a growing dataset), sketch: what would sharding the vector index across multiple machines actually require, and what's the concrete trade-off versus keeping it on one machine?

Show solution
Sharding a vector index means splitting the dataset (and its index structure) across multiple machines instead of keeping the whole thing on one -- necessary once the dataset genuinely exceeds what one machine's memory can hold, or once query throughput exceeds what one machine can serve, echoing the exact scaling motivation from the Month 1 sharding_and_partitioning lab, now applied to a vector index rather than a relational table. What it requires: (1) a shard key / partitioning strategy -- e.g. hash- based (spread vectors roughly evenly by some hash of their ID) or semantic (cluster similar vectors onto the same shard, which can improve per-shard search quality but risks uneven shard sizes if some semantic regions are much denser than others); (2) each shard runs its OWN HNSW-style index over only its slice of the data; (3) at query time, the query has to FAN OUT to every shard (or a relevant subset, if the partitioning is semantic and the query can be routed to only the shards likely to contain good matches), each shard returns its own local top-k, and a final merge step combines all shards' results into one global top-k -- this fan-out-then-merge pattern mirrors exactly the cross-shard query pattern from the Month 1 sharding lab. The concrete trade-off: sharding buys the ability to scale past a single machine's memory/throughput ceiling, at the cost of query complexity (every query now touches multiple machines instead of one, adding network round-trips and merge overhead) and, for the fan-out approach, POTENTIALLY WORSE recall per query if any individual shard's local index is itself approximate -- errors can compound slightly across shards, though the fan-out-and-merge step recovers much of this since each shard's local top-k still gets globally re-ranked at merge time. This is the same fundamental "solves the true bottleneck at the cost of new complexity" pattern that showed up in Month 2's rate-limiter cold-review lab discussing the shared-counter bottleneck -- horizontal scaling never comes free, it trades one problem (a single machine's ceiling) for a different, more distributed set of problems (coordination, network cost, merge logic).
