01 — Same fusion algorithm, now behind a protocol boundary

Exposing hybrid search as an MCP tool

Start here, before writing the tool definition. Think about a library's reference desk versus letting patrons wander the stacks themselves. Handing an agent RAW access to the vector index and the keyword index (two separate systems, two separate query APIs) is like letting it wander the stacks — it has to know the layout. Wrapping both behind ONE reference desk — "ask a question, get back the best-fused answer" — is what an MCP tool does: it collapses hybrid_search.html's two-index, RRF-fusion machinery behind a single schema the orchestrator (per mcp-and-agents/capstone_orchestrator_integration.html section 3) can call exactly like it calls any other tool.

# app/mcp_servers/search_tool.py -- registered alongside example_server.py's # "ping" tool, in the SAME capstone_mcp Server instance from the scaffold from mcp.types import Tool, TextContent from app.mcp_servers.example_server import capstone_mcp from app.services.hybrid_search import run_hybrid_search # protocol-agnostic logic, # same separation as the # scaffold's problem 2 SEARCH_TOOL_SCHEMA = Tool( name="hybrid_search", description="Search the capstone's document corpus using blended dense (vector) and sparse (keyword) retrieval, RRF-fused.", inputSchema={ "type": "object", "properties": { "query": {"type": "string", "description": "Natural-language search query"}, "top_k": {"type": "integer", "minimum": 1, "maximum": 20, "default": 5}, "dense_weight": {"type": "number", "minimum": 0, "maximum": 1, "default": 0.5}, }, "required": ["query"], }, ) @capstone_mcp.call_tool() async def call_tool(name: str, arguments: dict) -> list[TextContent]: if name == "hybrid_search": results = await run_hybrid_search( query=arguments["query"], top_k=arguments.get("top_k", 5), dense_weight=arguments.get("dense_weight", 0.5), ) # structured JSON back as text content, per json_schema_tool_specs.html's # convention -- the orchestrator parses this, not a human return [TextContent(type="text", text=json.dumps(results))] if name == "ping": return [TextContent(type="text", text="pong")] raise ValueError(f"Unknown tool: {name}")

Note the schema constrains dense_weight to [0, 1] and top_k to a small bounded range — the same defensive schema design json_schema_tool_specs.html taught for search_flights's cabin_class enum, now protecting against a malformed or adversarial call requesting, say, top_k: 100000 and blowing the context budget section 3 works within.

Interview-ready definition: exposing hybrid search as an MCP tool means the fusion algorithm's implementation detail (RRF, weighted linear combination, whichever hybrid_search.html covers) stays entirely behind the tool's schema boundary — callers supply a query and a few bounded knobs, never index internals — which is exactly what lets the orchestrator treat this tool identically to any other MCP tool it dispatches to.
02 — Embedded vs a separate service, the real trade-off

Where the index lives relative to the FastAPI process

Start here, before deciding. Think about keeping a reference book on your own desk versus walking down the hall to the library. Keeping it on your desk (embedded) is instant but means every desk needs its own copy, and updating one copy doesn't update the others. Walking to the library (a separate service) means everyone shares ONE up-to-date copy, at the cost of a walk every time. realtime_rag_engine_design.html already worked through this exact trade-off for a freshness-critical RAG system; this section applies it specifically to the capstone's single FastAPI process.

Embedded index (in-process)

The vector/keyword index loads into the same process as the FastAPI app — no network hop per search. Fast, but N running workers (per uvicorn_gunicorn_workers.html) means N in-memory copies of the index, each consuming its own RAM, and a new document ingested has to somehow reach every worker's copy, not just one.

Separate search service

One index, one service, called over HTTP/gRPC from every FastAPI worker — ingestion updates ONE place and every worker sees it immediately. Costs a network round trip per search call, and adds a new dependency /readyz must check, same as section 1's Redis dependency in the orchestrator lab.

FactorEmbeddedSeparate service
Per-query latencyLowest — no network hop+network RTT, but often still <50ms for a co-located service
Memory costMultiplied by worker countPaid once, shared
Freshness after ingestStale until every worker reloads (see realtime_rag_engine_design.html's "not yet indexed" window)Fresh the moment the one shared index updates
Right choice whenCorpus is small/static, single-worker or dev deploysCorpus is large, updates frequently, or multiple workers/services need the same index

For this capstone specifically: the scaffold's own dependency table (section 4 of capstone_scaffold_fastapi_mcp.html) already assumes a database layer arrives once Week 2's schema work lands (lab 5, this same week) — and a corpus that supports the capstone's own eval/tracing dashboard content is exactly the kind of thing that gets updated out-of-band, not embedded and baked into each worker's memory. The separate-service model is the better default here, with the MCP tool from section 1 calling out to it rather than holding the index directly.

Interview-ready definition: an embedded index trades freshness and memory efficiency for raw per-query speed and simplicity, correct for small/static/single-worker deployments; a separate search service trades a network hop for a single shared, immediately-fresh index visible to every caller — the same in-process-vs-external trade-off mcp-and-agents/capstone_orchestrator_integration.html draws for orchestrator state, applied here to a search index instead.
03 — Fused results are not automatically usable context

How fused results get merged into the orchestrator's context

Start here, before assuming "return the top 5" is sufficient. A search result list and an LLM's context window are not the same shape — a ranked list of (doc_id, score) pairs has to become actual TEXT, budgeted against a token limit, before generation can use it. This is where hybrid search's output meets the orchestrator's context-assembly step.

# app/orchestrator/context.py -- called from run.py's step() after a # hybrid_search tool call returns, before composing the final reply def merge_into_context(search_results: list[dict], token_budget: int = 2000) -> str: # results arrive PRE-RANKED by RRF fusion (hybrid_search.html) -- # this function's only job is fitting them into a token budget, # not re-ranking them again chunks = [] used = 0 for r in search_results: # rough token estimate; a real implementation uses the model's # own tokenizer, not len(text) // 4 est_tokens = len(r["text"]) // 4 if used + est_tokens > token_budget: break # stop merging, don't truncate mid-chunk -- a half a # sentence is worse than one fewer full chunk chunks.append(f"[source: {r['doc_id']}, fused_score={r['score']:.3f}]\n{r['text']}") used += est_tokens return "\n\n".join(chunks)

Two details worth naming explicitly, because both are easy to skip and both cause real bugs: results are budgeted in RANK ORDER, not truncated arbitrarily, so the highest-fused-score result is never the one cut for space; and each chunk keeps its doc_id attached in the merged text, so a later eval pass (lab 3's dashboard) can trace a generated answer back to which specific search result it came from — the same provenance link database/eval_results_schema.html requires between a score and its trace.

Interview-ready definition: merging search results into context means converting a ranked list into a token-budgeted string WITHOUT re-ranking (fusion already decided order) and WITHOUT silently truncating mid-chunk — stopping at the last chunk that fully fits is what keeps the context both within budget and internally coherent.

Practice problems

Problem 1 · A search call that returns zero results

Section 1's hybrid_search tool returns an empty result list for a query with no matches. What should the orchestrator (from capstone_orchestrator_integration.html) do with an empty tool result, and what's wrong with silently proceeding to generation as if nothing happened?

Show solution
Silently proceeding is the most common real bug in RAG-backed agents: the LLM generating the final reply has no signal that search came back empty, so it often "helpfully" fabricates an answer that sounds grounded but isn't -- a classic hallucination triggered specifically by missing context rather than by the model being asked something unanswerable. The orchestrator needs to treat an empty result list as a distinct, checkable branch in its routing logic (section 3 of the orchestrator lab's _route/_is_terminal methods), not just an empty string that flows through unchanged. Two reasonable responses, both better than silence: (1) have the orchestrator's merge_into_context step produce an explicit marker -- e.g. "[No search results found for this query]" -- included in the prompt sent to the model, so the model is EXPLICITLY told context is missing rather than inferring it from absence; or (2) have the orchestrator's routing logic branch on empty results and either retry with a broadened query (fewer/no filters, a rephrased query) or return a reply that honestly states no relevant information was found, rather than calling the generation step at all. Option 2 is stronger when the capstone's eval/tracing dashboard (lab 3) needs to distinguish "search found nothing, correctly reported" from "search found something, generation ignored it" as two different failure modes worth separate eval metrics.
Problem 2 · Choosing dense_weight per query type

Section 1's schema exposes dense_weight as a caller-supplied parameter, defaulting to 0.5. Should the orchestrator ever pass a value other than the default, and if so, based on what?

Show solution
Yes -- a fixed 0.5 for every query wastes information the orchestrator often already has. hybrid_search.html's own failure-mode demo shows dense (vector) retrieval winning on QUERIES ABOUT MEANING/PARAPHRASE (a question worded very differently from the source text but semantically close) and sparse (BM25/keyword) retrieval winning on queries containing EXACT TERMS THAT MATTER LITERALLY -- an error code, a proper noun, a specific field name. A well-built orchestrator can cheaply classify which regime a given query falls into (e.g. a simple heuristic: does the query contain a quoted string, an identifier-looking token, or a capitalized proper noun not at the sentence start? lean sparse-heavy; otherwise lean dense-heavy) and pass a correspondingly skewed dense_weight rather than always defaulting to an even blend. The risk of over-engineering this: a classifier that's wrong half the time is worse than a fixed 0.5 default, because it introduces inconsistent, hard-to-debug retrieval quality instead of one uniformly mediocre-but-predictable behavior. The practical middle ground most real systems land on is exactly what hybrid_search.html's RRF fusion already provides -- a reasonably weight-INSENSITIVE default that performs acceptably across query types -- with per-query weight overrides reserved for cases with strong, cheap, high-confidence signal (e.g. the query literally contains an ID pattern matching a known schema field).
Problem 3 · Index staleness after a document update

Section 2 recommends a separate search service for this capstone. A document gets updated in the underlying store, and a search five seconds later still returns the OLD version. Is this necessarily a bug, and how would you reason about whether it's acceptable?

Show solution
Not necessarily a bug -- it depends entirely on the freshness SLA the system commits to, which is precisely the question realtime_rag_engine_design.html poses and answers concretely for a continuously-updating corpus: define an explicit "not yet indexed" window (e.g. "updates are searchable within 10 seconds, worst case") rather than either promising instant consistency (expensive, often unnecessary) or leaving the window undefined (a support the search system silently just... does). To reason about whether 5 seconds is acceptable here: check what INGESTS the update into the separate search service. If it's an async background indexing job (the common, cheaper pattern -- write to the primary store, then asynchronously re-embed and re-index), a few seconds of staleness is an inherent, expected property of that architecture, not a bug -- the fix is DOCUMENTING the window, not eliminating it (eliminating it usually means synchronous re-indexing on every write, which trades ingest latency for read freshness, often the wrong trade for a capstone with a low update rate). If instead the system's stated contract promises immediate consistency and 5 seconds violates that contract, then yes, it's a real bug -- most likely a missing or too-infrequent index refresh cycle, or a caching layer in front of the search service serving a stale response past its intended TTL.
