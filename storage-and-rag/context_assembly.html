01 — No framework, no magic — just concatenation with clear boundaries

Assembling chunks + instructions + history into a prompt

Start here, before any code. Imagine handing someone a single sheet of paper before a meeting, and that sheet has to contain everything they need: the ground rules for how to behave in the meeting, a few reference documents relevant to the topic, the notes from earlier in the conversation, and finally, the actual question being asked right now. If you just typed all of that onto the page with no headers, no separators, no visual distinction between sections, the reader would have a hard time telling where the reference documents end and your actual question begins. A framework doesn't solve this problem for you — it's still just organizing text on a page. The organizing itself is what makes the difference.

Without a framework, context assembly is literally building one big string via concatenation, with each section clearly delimited so the model can distinguish "this is an instruction," "this is retrieved reference material," and "this is what you're actually being asked" from each other. A common, simple approach uses distinct markers — XML-style tags, markdown headers, or clear labeled sections — around each part, since the model reads the final assembled string as one undifferentiated block of text and relies entirely on these textual cues to tell the parts apart.

# the literal string-building, no framework involved def assemble_prompt(system_instructions, retrieved_chunks, history, user_question): parts = [] parts.append(f"<system>\n{system_instructions}\n</system>") for i, chunk in enumerate(retrieved_chunks): parts.append(f"<context source='{chunk.source}'>\n{chunk.text}\n</context>") for turn in history: parts.append(f"<{turn.role}>{turn.content}</{turn.role}>") parts.append(f"<question>{user_question}</question>") return "\n\n".join(parts) # the final, literal prompt string sent to the model
Interview-ready definition: context assembly, done without a framework, is the direct construction of one final prompt string by concatenating clearly delimited sections — system instructions, retrieved context chunks (each marked off so the model can tell where one chunk ends and the next begins, and ideally which source each came from), conversation history, and the current user question — typically using explicit textual markers (XML-style tags, markdown headers, or labeled sections) since the model has no structural awareness of the prompt beyond the literal text it reads. The delimiters exist specifically to prevent the model from confusing a retrieved chunk's content with an instruction, or blending two adjacent chunks together as if they were one continuous passage.
02 — The same four sections, in a different order, is a different prompt

Ordering and prioritization decisions

Start here, before the specifics. Imagine giving someone directions right before they walk into an important meeting. If you list five pieces of advice and the meeting starts the instant you finish talking, they're much more likely to remember and act on the LAST thing you said than the first — recency matters for what stays freshest in mind. Prompt assembly has an analogous effect: many language models show measurably stronger attention to content positioned near the END of a long prompt, closer to where generation actually begins, than to content buried earlier — a recency effect on what actually gets used, not just what's technically present.

Where does retrieved context go?

Placing retrieved context near the END of the prompt — closer to the user's question, right before generation starts — tends to get more attention from many models than burying it near the very start, ahead of the instructions and history. This is a direct consequence of the recency effect: content closest to where the model begins generating tends to be weighted most heavily.

How do you order multiple chunks?

When several retrieved chunks are included, their relative order matters too — a common approach places the MOST relevant chunk last (closest to the question, benefiting most from the recency effect), with less relevant chunks earlier. Some systems instead put the most relevant chunk first for readability; there's a genuine trade-off here, not a universal rule, and it's worth testing empirically for a specific model and prompt structure rather than assuming one order is always correct.

Interview-ready definition: ordering and prioritization in context assembly is the decision of where each section sits in the final prompt string, driven substantially by the observation that many models attend more strongly to content positioned near the end of a long prompt (closer to where generation begins) than content earlier in it — a recency effect. This motivates placing retrieved context and the current question later rather than earlier in the assembled prompt, and, when multiple chunks are retrieved, often ordering them so the most relevant chunk sits closest to the question rather than furthest from it — though the "most relevant last" convention is a common default, not a universal law, and is worth validating empirically against the specific model in use.

Problem 1 · Explaining what breaks without clear delimiters

Someone assembles a prompt by just concatenating the system instructions, two retrieved chunks, and the user question with a single space between each, no tags or headers at all. What specifically goes wrong, and give a concrete example of a failure this could cause.

Show solution
Without delimiters, the model has no textual signal for where one section ends and the next begins — from its point of view, it's reading one continuous, undifferentiated block of text. Concretely: if the system instructions end with "...always answer in a formal tone" and the first retrieved chunk begins with "Refunds are processed within 5-7 days", concatenated with just a space, the model may have no reliable way to distinguish "always answer in a formal tone. Refunds are processed..." as two SEPARATE, unrelated pieces of information versus one continuous instruction that happens to mention refunds — in the worst case, the model might even treat part of a retrieved chunk's content as if it were an instruction to follow, or blend two adjacent chunks together as if they were one continuous passage from a single source, misattributing which chunk a fact came from. This is exactly why section 1 emphasizes explicit delimiters (XML-style tags, markdown headers, or clearly labeled sections) rather than plain concatenation — the delimiters are not cosmetic, they're the entire mechanism by which the model can tell "this part is an instruction to follow" apart from "this part is reference material to draw from" apart from "this part is the actual question I'm being asked right now."
Problem 2 · Choosing where to place context given the recency effect

A team currently assembles prompts in this order: retrieved context, then system instructions, then conversation history, then the user's question. Using section 2's reasoning, is this ordering a reasonable default? What would you change, and why?

Show solution
This ordering places retrieved context FIRST, furthest from the question and furthest from where generation actually begins — which runs directly against section 2's core reasoning that content closer to the end of the prompt tends to receive more attention from many models (the recency effect). Retrieved context is often exactly the material you most want the model to actually USE when answering, so burying it at the very front, ahead of instructions and history, is a reasonable candidate for why a RAG system's answers might underuse context it was technically given. A change more aligned with section 2's reasoning: move retrieved context to sit closer to the question — e.g. instructions first (as the overall frame), then history, then retrieved context, then the question last. This keeps instructions upfront (still fully read, just not competing for the recency-favored position) while giving context and the question themselves the positions closest to generation, where they're most likely to be weighted heavily. As section 2 notes, this isn't a universal law — but the CURRENT ordering (context first) is specifically the version section 2's reasoning argues against, since it puts context furthest from, rather than closest to, the position that tends to get the most attention.
Problem 3 · Ordering three chunks with different relevance scores

Retrieval returns three chunks with relevance scores 0.91, 0.74, and 0.58. Using the "most relevant chunk closest to the question" convention from section 2, in what order should they appear in the assembled prompt (listing them in the order they'd be concatenated)?

Show solution
In concatenation order (first to last, ending closest to the question): chunk with score 0.58, then chunk with score 0.74, then chunk with score 0.91 — placing the HIGHEST-relevance chunk (0.91) LAST among the chunks, immediately before the question, since that's the position closest to generation and therefore, per the recency-effect reasoning in section 2, most likely to receive strong attention. The lowest-relevance chunk (0.58) is still included (it made the cut from retrieval and presumably has SOME value, or it wouldn't be in the context at all), but it's placed furthest from the question among the three, since it's the least essential per that ranking, and the positions closer to the question are effectively the most valuable "real estate" reserved for the more relevant material.
Problem 4 · Diagnosing why the model answered from an outdated retrieved chunk

A RAG system retrieves both an old, outdated policy document and a newer one that supersedes it (both are genuinely relevant to the query in a keyword/semantic sense — retrieval can't tell which is "current," only which matches). The old, outdated chunk is placed first in the assembly; the newer, correct one is placed last, closest to the question. The model answers using the newer document. Explain this outcome using section 2, then explain what would likely change if the order were reversed.

Show solution
This outcome is consistent with section 2's recency-effect reasoning: the newer, correct chunk is positioned closest to the question, in the position many models tend to weight most heavily, which plausibly contributes to the model favoring it over the outdated chunk positioned earlier and further from the question. This isn't a guarantee — the model could still make this choice based on content alone (e.g. explicit "as of [date]" language in the newer document) — but the POSITIONING is a real contributing factor per this lab's reasoning, not just the content. If the order were reversed (outdated chunk placed last, closest to the question; correct chunk placed first, furthest away), section 2's reasoning predicts a real risk of the OPPOSITE outcome — the model favoring the outdated chunk specifically because of its more favorable position, even though the newer chunk is the objectively correct source. This is exactly why chunk ORDER, not just chunk SELECTION, is a real lever in context assembly: retrieval decided which two chunks made the cut, but assembly's ordering decision can measurably influence which of two conflicting, equally-retrieved chunks the model actually leans on when they disagree — a distinct failure mode from retrieval recall or precision, and one assembly-level ordering choices can make better or worse.
Problem 5 · Debugging a prompt that silently dropped the user's actual question

A team's assemble_prompt function (section 1's pattern) has a bug: under a specific code path, the function returns early after appending the retrieved-chunk sections, before the loop that appends conversation history and the final question ever runs. What does the actual string sent to the model look like, and why is this a particularly dangerous bug to have shipped silently?

Show solution
The actual string sent to the model would contain the system instructions and the retrieved context chunks, but NOTHING about the conversation history or, critically, the user's actual current question — the model receives a prompt that never asks it anything at all. Depending on how the model handles a prompt with no explicit question, it might generate a generic response, try to summarize the provided context unprompted, or produce something that looks superficially plausible but has no relationship to what the user actually asked. This is a particularly dangerous bug to have shipped silently because the FAILURE MODE isn't a clean error — the model doesn't refuse or throw an exception when handed a prompt missing its question, it just generates SOME output, and that output can look coherent and confident even though it's not actually answering anything the user asked. This is exactly why section 3's callout emphasizes printing and reading the literal final assembled string as a debugging step: a bug like this (an early return, a section silently missing from the concatenation) is invisible if you only look at the FUNCTION's logic in isolation — reading the actual output string directly would immediately reveal that the question section is missing, in a way that inspecting the assemble_prompt code path-by-path might not, especially if the buggy early-return path is only hit under specific conditions that aren't obviously wrong when reading the code.
