01 — Two ways to lay the same table out on disk

Row-oriented vs column-oriented layout

Start here, before any diagrams. Imagine a spreadsheet of orders, one row per order, columns for id/customer/amount/date/status. Now imagine two totally different ways to physically photocopy that spreadsheet onto a stack of paper. Method one: photocopy it exactly as it looks — row 1 in full, then row 2 in full, then row 3 in full, and so on. To read one entire order, you flip to one page and it's all right there. Method two: instead, make one long sheet per COLUMN — a sheet listing every order's id in sequence, a separate sheet listing every order's customer name in sequence, a separate sheet for every amount, and so on. To read one entire order now, you have to go find that order's line on EVERY sheet. But if you only wanted "every amount, to compute a total," method two hands you exactly one sheet with nothing else on it — no names, no dates, no statuses mixed in.

That's the literal difference between row-oriented storage and column-oriented (columnar) storage. A row-oriented engine (the on-disk format behind most traditional relational databases — Postgres, MySQL's default engine) physically stores each row's full set of column values contiguously on disk: row 1's id, name, amount, date, status all sit next to each other, then row 2's full set right after, and so on. A columnar engine (Parquet files, ClickHouse, most modern data-warehouse / analytics engines) stores each COLUMN's values contiguously instead: every row's amount sits together as one long run of bytes, separate from every row's status, separate from every row's date.

Row-oriented layout on disk

Each row's columns are stored together, one row after another.

Columnar layout on disk

Each column's values are stored together, one column after another.

Interview-ready definition: row-oriented (row-store) layout physically stores all column values belonging to one row contiguously on disk, so a single row is one contiguous chunk of bytes; column-oriented (columnar) layout physically stores all values belonging to one column contiguously instead, so a single column across every row is one contiguous chunk of bytes, and reconstructing one full row requires stitching together a value from each column's separate storage region. Same logical table, same total bytes — the physical arrangement is the only thing that differs, and that arrangement determines which access pattern is cheap and which is expensive.
02 — Counting exactly what a query has to touch

Byte-counting a real query: 2 columns out of 8

Start here, before the numbers. Back at the photocopied spreadsheet: if you need "every order's amount and date, nothing else," method one (row-by-row photocopies) forces you to read every single page front to back, because amount and date are mixed in among six other columns you don't need on every page. Method two (one sheet per column) hands you exactly two sheets — the amount sheet and the date sheet — and you never even glance at the other six sheets' worth of paper.

This is the entire reason columnar storage exists. Disk (and network, for cloud storage) I/O is the dominant cost for large scans, and I/O cost is driven by how many bytes physically get read off disk — not by how many bytes the query logically cares about. In a row-store, reading a query that needs 2 of 8 columns still requires reading every row's FULL width (all 8 columns' worth of bytes) for every row scanned, because the storage engine can't skip the other 6 columns without skipping the whole row — they're physically interleaved together on the same disk pages. In a columnar store, that same query reads only the 2 columns' worth of bytes, full stop; the other 6 columns physically live somewhere else entirely and are never touched.

Scaled up, this is the difference the roadmap topic is pointing at: reading column X across 1,000,000 rows in columnar format touches only column X's data — roughly (1,000,000 × width of column X) bytes, full stop. In row format, the same read touches every row's FULL width even though only 1 of 8 columns was wanted — roughly (1,000,000 × width of ALL 8 columns) bytes, because the storage engine has no way to extract one column's value without first reading the row page it's embedded in. If each row is 80 bytes wide and the wanted column is 10 bytes wide, columnar reads 10MB; row-oriented reads 80MB for the exact same logical question — an 8x I/O difference driven purely by physical layout, not by anything about the query itself.

Interview-ready definition: columnar storage wins on I/O for queries that touch few columns across many rows because physical bytes read scale with (columns actually needed) × (rows scanned), not with (all columns) × (rows scanned) — the storage engine can seek directly to and stream only the needed columns' contiguous regions. Row-oriented storage cannot do this: because columns are physically interleaved per row, reading even one column requires reading each row's full width off disk, since there is no way to separate one column's bytes from the rest of that row's bytes without reading the row itself.
03 — The layout choice is a bet on the workload

Why columnar wins for OLAP, row-oriented wins for OLTP

Start here, before the trade-off table. Think about two completely different jobs at a retail company. One person's whole job is: "pull up THIS ONE customer's THIS ONE order — every detail about it, right now, because they're on the phone asking about it." Another person's whole job is: "compute the average order value, by month, across every order placed in the last two years — I don't care about any single order's shipping address or customer notes, just the amounts and the dates, for millions of rows." These are structurally opposite access patterns, and each maps cleanly onto one of the two storage layouts.

OLTP (Online Transaction Processing) is the first job: a live application reading and writing whole, individual records — "fetch this exact order," "update this user's address," "insert this new order." Each operation needs EVERY column of ONE row, and needs it fast, often as part of a transaction that also writes back. Row-oriented storage is built for exactly this: one row is one contiguous chunk on disk, so fetching or updating a whole record is a single localized read/write, not bytes scattered across many separate column regions that all have to be located and stitched together.

OLAP (Online Analytical Processing) is the second job: analytical queries that scan millions of rows but only touch a handful of columns — aggregations, averages, group-bys, trends over time. "Average order value by month" needs only 2 columns (amount, order_date) out of a wide orders table that might have 20+ columns (shipping address, customer notes, payment metadata, and so on). Columnar storage is built for exactly this: scan only the 2 needed columns' contiguous regions across all rows, and never touch the other 18+ columns' bytes at all — which, at millions of rows, is the difference between a query that finishes in seconds and one that doesn't.

OLTP → row-oriented

Whole-row reads/writes, low latency per operation, frequent single-record transactions. Row-store keeps a whole record contiguous, so touching one record is cheap regardless of how many columns the table has.

OLAP → columnar

Wide-scan, narrow-column aggregations over millions of rows. Columnar keeps each column contiguous, so a query can skip every column it doesn't need, which is the entire I/O saving at scale.

Why you can't just pick one and be done: this is exactly why real systems often run BOTH — an OLTP row-store (Postgres, MySQL) as the system of record handling live application traffic, and a separate OLAP columnar store (or columnar export) for analytics/BI/reporting, often fed by periodic ETL from the OLTP database. Trying to run heavy analytical aggregation queries directly against a row-oriented production database is a common real-world performance trap: each aggregation query ends up reading every column of every row it scans, competing for the same disk I/O the live application needs for its own whole-row OLTP queries.

Problem 1 · Computing the byte savings directly

A table has 10 columns, each averaging 12 bytes, for a 120-byte row width. A query needs exactly 1 column (12 bytes) across 5,000,000 rows. How many bytes does a row-oriented engine have to read versus a columnar engine, and what's the ratio?

Show solution
Row-oriented: has to read every row's FULL width even though only 1 of 10 columns is needed, because columns are physically interleaved per row. That's 120 bytes/row × 5,000,000 rows = 600,000,000 bytes (≈572 MB). Columnar: reads only the wanted column's contiguous region across all rows. That's 12 bytes/row × 5,000,000 rows = 60,000,000 bytes (≈57 MB). Ratio: 600,000,000 / 60,000,000 = 10x — which is exactly the column count (10 columns total, 1 needed). This isn't a coincidence: the I/O ratio between row-oriented and columnar for an N-of-M-column query is roughly M/N, since row-oriented always pays for all M columns regardless of how many are actually needed, while columnar pays only for the N columns actually touched.
Problem 2 · Choosing a layout for a stated workload

A checkout service needs to insert a new order row and immediately read back that exact order (all columns) to render a confirmation page, thousands of times per minute, each one a separate customer's separate order. Which layout fits, and why would the other layout actively hurt here?

Show solution
Row-oriented fits. This is a textbook OLTP access pattern: single-row writes immediately followed by single-row, whole-record reads, repeated at high frequency across many independent rows. Row-store keeps each order's full set of columns contiguous, so both the insert and the immediate full-row read are single, localized operations. Columnar would actively hurt here for two separate reasons. First, reads: reconstructing one full order (all columns) from a columnar layout means locating and stitching together that order's value from EVERY column's separately-stored region — the opposite of the "read just 2 columns" benefit columnar provides; here ALL columns are needed, which is columnar's worst case. Second, writes: columnar formats are typically optimized for bulk, batched writes (append a large chunk to each column's region at once), not fine-grained single-row inserts arriving continuously — inserting one row at a time into a columnar layout is comparatively awkward and often requires buffering/batching machinery that a row-store simply doesn't need for the same workload.
Problem 3 · Diagnosing a slow analytics query on the wrong engine

A team runs "total revenue by region, last 12 months" directly against their production Postgres (row-oriented) orders table, which has 30 columns and 200 million rows. The query takes 40 seconds and is also slowing down the live checkout service. Explain both symptoms using what this lab covered.

Show solution
The 40-second query time: the aggregation only logically needs 2 of 30 columns (amount, region) but Postgres's row-oriented storage forces it to read every row's FULL 30-column width for all 200 million rows it scans, since it can't extract just those 2 columns without reading each row they're embedded in. That's roughly 15x more bytes read off disk than a columnar engine would need for the identical logical query (2 of 30 columns) — this is precisely the OLAP-on-row-store performance trap described in section 3. The slowdown to the live checkout service: that 40-second scan is consuming real disk I/O and buffer-cache pages on the SAME database instance that the OLTP checkout traffic (single-row inserts/reads) is also competing for. The two workloads are fundamentally different shapes — the analytics query wants to stream huge sequential column ranges, checkout wants fast localized single-row access — and running both against one row-oriented instance means the analytics scan's heavy I/O directly degrades the latency-sensitive OLTP traffic sharing the same disk and cache. The fix (as section 3 states) is to route this kind of analytical query to a separate columnar store or warehouse, fed by periodic export/ETL from the OLTP database, rather than running it directly against production.
Problem 4 · Reasoning about writes, not just reads

This lab mostly discusses read/scan cost. Explain, in your own words, why columnar storage is comparatively awkward for frequent single-row writes, using the physical layout described in section 1.

Show solution
In columnar layout, one logical row's values are physically scattered across N separate column regions (one per column) rather than living together in one place. Inserting a single new row means appending one new value to EACH of those N separate contiguous regions -- N separate small writes to N separate physical locations, rather than one single contiguous write the way a row-store handles it (append one new 120-byte chunk in one place). At low write volume this overhead is tolerable, but at high-frequency single-row inserts, columnar engines typically buffer incoming rows in memory and periodically flush them as a single BATCHED write across all columns at once, rather than performing N tiny separate writes per incoming row -- which adds complexity (a write buffer, a flush/compaction process) that a row-store's naturally-contiguous single-row write simply doesn't need. This is the mechanical reason columnar formats are generally paired with bulk-load/batch-append write patterns (ETL jobs, periodic ingestion) rather than the continuous single-row write pattern of a live OLTP application.
Problem 5 · A mixed workload that doesn't cleanly fit either bucket

A product needs BOTH fast single-order lookups (thousands/minute, OLTP-shaped) AND a live dashboard aggregating revenue trends across all orders (OLAP-shaped), and both need to reflect data that's at most a few minutes old. Propose an architecture, referencing the trade-off from section 3.

Show solution
Neither a single row-store nor a single columnar store alone cleanly serves both shapes well, which is exactly the trade-off section 3 flags. A reasonable architecture: keep a row-oriented database (Postgres) as the system of record handling the OLTP single-order lookups/writes, and continuously (or on a short interval, e.g. every 1-5 minutes) stream or replicate changes into a separate columnar store (via change-data- capture / CDC, or a lightweight incremental ETL job) that the dashboard queries against instead of hitting the OLTP database directly. This satisfies the "few minutes old" freshness requirement (short replication lag) while keeping the two fundamentally different access patterns physically separated onto the storage layout each is suited for -- fast whole-row OLTP access stays on row-store, wide-scan narrow- column aggregation stays on columnar, and neither workload's I/O pattern competes with or degrades the other on shared disk/cache resources the way running both directly against one row-oriented instance would (as in Problem 3).
