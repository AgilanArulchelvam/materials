A document lands. Seconds later, someone's query needs to be able to find it.

Everything in storage-and-rag/ so far — hybrid_search.html, hnsw_indexing.html, reranking.html, context_assembly.html — assumed a mostly-static corpus you index once and query many times. 01 — "Real-time" is a latency number, not a vibe. Pin it down.

Requirements gathering

Start here, before any pipeline diagram. Think about the difference between a library that reprints its entire card catalog once a year (every book added since the last printing is simply unfindable until the next one) versus a library where the front desk clerk, the moment a new book is shelved, immediately writes one new card and slots it into the existing catalog drawer — no reprinting, no waiting for the next batch. A traditional RAG pipeline that rebuilds its vector index nightly is the annual reprint. A real-time RAG engine is the clerk: every new or updated document gets folded into the EXISTING searchable index within seconds, not at the next scheduled rebuild.

The prompt: "Design a RAG engine that serves low-latency queries over a corpus with near-real-time updates." This builds directly on storage-and-rag/hybrid_search.html (combining keyword and vector search) and hnsw_indexing.html (the ANN index structure itself) — both assumed here, not re-taught.

Functional requirements

  • Ingestion pipeline — new/updated documents are chunked (per chunking_semantic_and_windowed.html / chunking_parent_child.html), embedded, and made searchable.
  • Freshness SLA — a document must be findable in query results within a bounded, small window after ingestion — this is THE defining constraint of this lab, and needs a real number.
  • Hybrid retrieval at query time — combining keyword and vector search per hybrid_search.html, plus reranking per reranking.html.
  • Generation integration — retrieved chunks feed an LLM's context window, per context_assembly.html and token_budget_management.html.
  • Updates and deletes — not just new documents; an existing document's content can change or be removed, and stale content must stop being retrieved promptly.

Non-functional requirements — numbers to pin down out loud

Interview-ready definition: requirements gathering for a real-time RAG engine means treating "real-time" as a concrete freshness SLA (here, 5 seconds p95 from ingestion to retrievable) rather than a qualitative goal, and separating that from the SEPARATE query-time latency budget (800ms p95 for retrieval + generation) — the two numbers pull on different parts of the system (index-update path vs. query path) and get conflated if not stated explicitly, which is exactly the mistake this lab's capacity estimation and architecture sections are structured to avoid.
02 — Docs/sec, index size, and where the 800ms actually goes

Capacity estimation

Start here, before the math. Two separate capacity questions live in this system, and conflating them is a common mistake: how much WORK the ingestion path does per second (embedding + indexing throughput), and how much SPACE the resulting index occupies plus how the 800ms query budget gets spent. Work both chains separately.

Query embedding (~100ms) → hybrid vector+keyword retrieval across sharded index (~150ms) → cross-encoder reranking of top-K per reranking.html (~80ms) → LLM generation over assembled context (~470ms, the dominant cost — matching rag_qa_system_design.html's finding that generation, not retrieval, usually dominates end-to-end latency).

Interview-ready definition: capacity estimation here produces three numbers that each justify a specific design decision: burst embedding throughput (~2,000 chunks/sec, requiring ~7 embedder replicas — justifying horizontal scaling of the embedding step specifically for burst, not average, load), index size (~740GB, too large for one machine's memory at HNSW's overhead multiplier — justifying a sharded vector index), and the 800ms latency budget breakdown (generation dominates at ~470ms, echoing rag_qa_system_design.html — meaning retrieval-side optimizations have a hard ceiling on how much they can move the total).
03 — Two paths, two different consistency requirements, one shared index

1 — Incremental index updates, not periodic rebuild

HNSW (per hnsw_indexing.html) supports incremental insertion natively — new vectors can be added to an existing graph without rebuilding it from scratch, unlike some ANN structures (e.g. certain IVF configurations per ivf_indexing.html) that are cheaper to query but more expensive to update incrementally. This is the central reason HNSW, not IVF, is the right index choice for THIS specific system: the 5-second freshness SLA is structurally incompatible with any index strategy whose update path is "periodically rebuild the whole thing." Each new chunk is embedded and inserted directly into its shard's live HNSW graph, typically within a second or two of ingestion — comfortably inside the 5-second budget.

2 — The "not yet indexed" window

Between a document being ingested and its chunks finishing embedding + insertion, there IS a window — bounded by the 5-second SLA — where a query that should retrieve it won't. This is not a bug to eliminate; it's an explicit, bounded consistency trade-off (eventual consistency, per section 1's non-functional requirements) that every real-time system with an indexing step has. The design goal isn't "never let this window exist" — it's "keep the window short and bounded, and make sure nothing downstream assumes zero latency here."

3 — Deletes and updates: tombstone, don't rewrite in place

An update is modeled as a delete of the old chunks plus an insert of new ones, not an in-place vector mutation — HNSW graphs are not efficiently mutated in place once built. Deletes are handled via TOMBSTONING (marking a chunk ID as deleted in a fast-lookup side structure) rather than immediately removing it from the graph, because removing a node from an HNSW graph while preserving its navigability properties is expensive; the query path checks the tombstone set and filters deleted results out post-retrieval, with a periodic background compaction pass that actually rebuilds affected graph regions to reclaim space.

4 — Context assembly under the generation budget

Retrieved, reranked chunks feed the LLM exactly per context_assembly.html and token_budget_management.html: a fixed token budget for context (leaving room for the system prompt, conversation history, and the model's own output), with reranking (section 2's 80ms step) existing specifically to make sure the chunks that DO fit in that budget are the most relevant ones, not just the top-K by raw vector similarity.

Interview-ready definition: the architecture is two paths sharing one index: an ingestion path that embeds and incrementally inserts each new chunk directly into a sharded HNSW graph (chosen specifically because HNSW supports true incremental updates, unlike rebuild-oriented index structures), and a query path that embeds the query, retrieves hybrid results, reranks, and generates within the 800ms budget. Deletes/updates use tombstoning with background compaction rather than expensive in-place graph mutation, and the "not yet indexed" window between ingestion and searchability is an explicit, bounded eventual-consistency trade-off — not an error condition.

Problem 1 · Justifying HNSW over IVF for this specific system

An interviewer asks: "IVF indexes are often faster to query than HNSW at similar recall — why didn't you choose IVF here?" Answer using section 1's specific requirements, not a general index comparison.

Show solution
The answer has to be anchored to section 1's 5-second freshness SLA, not a generic "HNSW vs IVF" comparison, because query speed alone isn't the deciding factor for THIS system. IVF indexes partition the vector space into clusters (per ivf_indexing.html) and are often faster to query, but adding new vectors well after the clusters were built can degrade cluster quality over time, and IVF implementations often lean more heavily on periodic re-clustering/rebuilding to maintain good recall as the corpus evolves -- exactly the "periodic full rebuild" option section 4 explicitly rejected as incompatible with a 5-second freshness requirement. HNSW, by contrast, supports genuinely incremental graph insertion as its native update model (section 3), which is what lets a new chunk go from "ingested" to "in the live, queryable graph" in roughly a second or two -- comfortably inside the SLA -- without needing to wait for or trigger any full-index operation. If section 1's freshness SLA were instead "nightly rebuild is acceptable" (a genuinely different set of requirements), IVF's query-time speed advantage would become the dominant consideration and could well win that trade-off instead. The correct interview answer names the SPECIFIC requirement (freshness SLA) that made incremental-update support the deciding property, rather than asserting HNSW is unconditionally better.
Problem 2 · Recomputing the burst embedder count under a tighter freshness SLA

Product now wants a 2-second freshness SLA instead of 5 seconds, with the same burst rate (500 docs/sec, 2,000 chunks/sec) and the same per-embedder throughput (300 chunks/sec). Does the embedder replica count from section 2 need to change? What else in the pipeline might need to change that pure throughput math wouldn't reveal?

Show solution
The raw REPLICA COUNT for embedding throughput doesn't actually need to change from section 2's ~7 -- that number was sized to keep up with 2,000 chunks/sec of SUSTAINED burst arrival rate, which is a throughput requirement independent of the SLA's time window. 7 embedders handling 2,000 chunks/sec keeps the QUEUE of pending chunks from growing unboundedly regardless of whether the freshness target is 2s or 5s -- throughput determines whether you keep up with arrival rate at all, not how fast an individual chunk moves through the pipeline once accepted. What DOES need scrutiny is the total pipeline LATENCY per chunk end-to- end -- embedding time, network hops, HNSW insertion time, and any queueing delay if the embedders are momentarily saturated. At 5 seconds of budget, a chunk sitting in a queue for 1-2 seconds during a burst before an embedder picks it up is tolerable. At a 2-second budget, that same queueing delay alone could consume the entire SLA, even with throughput nominally "keeping up" on average -- this is the classic gap between AVERAGE throughput sufficiency and TAIL latency sufficiency that raw throughput math doesn't surface. The real fix under a tighter SLA is provisioning embedders with MORE headroom above the sustained burst rate specifically to keep queueing delay low (e.g. sizing for 1.5x the 2,000 chunks/sec burst rather than exactly 1x), and possibly prioritizing embedding requests by arrival order with a tighter timeout alert if any chunk's queue wait threatens the 2-second budget on its own -- exactly the kind of p95/tail-focused reasoning distributed_telemetry_ingester_design.html's ingestion tier sizing used for burst headroom, now applied to a latency SLA instead of a pure throughput target.
Problem 3 · Handling a query that arrives during the "not yet indexed" window for a CRITICAL update

Section 4 accepts the not-yet-indexed window as a bounded, tolerable trade-off for general documents. Suppose one specific use case is "a user just corrected a factual error in a document, and a query asking about that exact fact must never return the STALE (pre-correction) answer, even briefly." Does section 3's design as-is satisfy this, and if not, what would you add?

Show solution
Section 3's design as-is does NOT satisfy this stronger requirement, and it's important to recognize why: the "not yet indexed" window (section 1's eventual consistency) bounds how long it takes for a document to become retrievable, but it says nothing about actively INVALIDATING the OLD, now-incorrect version during that same window. Under section 3's tombstone-based update model, the old chunks get tombstoned and new chunks get inserted -- but if tombstoning itself isn't instantaneous and synchronous with the update request, a query landing in the gap could retrieve the STALE chunk (not yet tombstoned) instead of just failing to find the NEW one, which is a meaningfully worse failure mode than section 4 explicitly signed up for ("briefly unfindable" is very different from "confidently wrong"). The fix: this specific requirement needs the DELETE half of an update to be synchronous and immediate (tombstone the old chunk ID in the fast-lookup side structure BEFORE returning success on the update request, blocking briefly rather than being eventually consistent), while the INSERT half of the new content can remain on the normal eventual-consistency path from section 1. This is a legitimate, narrower SLA than the system's general one -- "never serve known-stale content" is a stronger, synchronous guarantee than "eventually become findable," and the two don't have to move at the same speed. A good interview answer recognizes that a single system can reasonably offer DIFFERENT consistency guarantees for different operations (tombstone-on- delete: synchronous; insert-on-create: eventually consistent within 5s) rather than assuming the whole pipeline must use one uniform consistency model everywhere.
Problem 4 · Reconciling sharding with the 150ms retrieval slice of the latency budget

Section 2's ~740GB index needs sharding, and section 4 flagged that shard fan-out risks eating into the 150ms retrieval budget as shard count grows. If the corpus later grows 5x (to ~3.7TB, needing proportionally more shards), what specifically breaks first, and what's the mitigation?

Show solution
What breaks first is tail latency at the retrieval step specifically, via the classic "slowest shard" problem: a query that fans out to EVERY shard and waits for all of them to respond is only as fast as its SLOWEST responding shard, and as shard count grows (5x the data, likely somewhere near 5x the shard count to keep each shard's in-memory size manageable), the probability that AT LEAST ONE shard is having a momentarily slow moment (GC pause, a noisy neighbor process, a cold cache) on any given query goes UP, not down -- more shards queried per request means more chances for one of them to be the tail. This is a structural property of fan-out-and-wait-for-all designs, not something that improves just by adding more hardware per shard. The mitigation used in practice: query only a RELEVANT SUBSET of shards rather than all of them when possible (e.g. if shards are partitioned along a dimension correlated with the query, like recency or document category, a query can sometimes skip shards known to be irrelevant) -- but the more general and reliable fix is setting a per-shard timeout shorter than the overall 150ms slice and proceeding with whatever shards HAVE responded once that sub-timeout is hit (a "partial fan-out" tolerance), accepting slightly reduced recall on the rare query that hits a genuinely slow shard, in exchange for a hard ceiling on retrieval latency regardless of shard count. This is the same fundamental trade-off structure as the availability-vs-consistency choices elsewhere in this lab: 100% correctness (wait for every shard, always) is being deliberately traded for a bounded latency guarantee, exactly the same kind of explicit, defensible trade-off section 4 asked for rather than an unstated assumption.
