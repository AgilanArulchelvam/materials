01 — One random draw per point, decided at insert time

Layer assignment, from the actual formula

Start here, before any code. Imagine a lottery where most tickets only win a small local prize, a much smaller fraction wins a regional prize, and a vanishingly small fraction wins the national prize — and crucially, winning the national prize means you ALSO automatically win the regional and local prizes too. That's exactly how a new point's presence across HNSW's layers is decided: one random draw, at the moment the point is inserted, decides the HIGHEST layer that point will participate in — and it also participates in every layer below that, all the way down to layer 0.

The real formula (used in the original HNSW paper, simplified slightly here) draws from an exponential distribution:

import random, math def assign_max_layer(level_multiplier=1.0): # level_multiplier ("mL" in the paper) controls how quickly the # probability of reaching a higher layer decays -- a common choice # is 1 / ln(M), where M is the max-connections-per-node parameter. r = random.random() # uniform draw in [0, 1) return int(-math.log(r) * level_multiplier) # Run this once per NEW point as it's inserted -- not once for the whole # dataset. Each point's max layer is decided independently, at insertion # time, and never recomputed afterward. for _ in range(10): print(assign_max_layer(level_multiplier=0.36)) 0 0 1 0 0 2 0 0 1 0 # roughly: ~70% of points land at layer 0 only, ~22% also reach layer 1, # ~6% also reach layer 2, and so on -- decaying fast.

Why -log(r) specifically: r is uniform between 0 and 1, so it's close to 1 most of the time and close to 0 rarely. -log(r) flips that: it's close to 0 (small) most of the time, and grows large only rarely — exactly the "most points get a small max layer, a few get a large one" shape the pyramid structure needs. The level_multiplier just stretches or compresses that curve — a smaller multiplier means fewer points reach high layers at all, a taller, narrower pyramid.

LIVE LAYER-ASSIGNMENT DRAW — RUN IT 500 TIMES, SEE THE DISTRIBUTION
Interview-ready definition: HNSW layer assignment draws each new point's maximum participating layer from an exponentially-decaying random distribution (typically floor(-ln(uniform_random()) * level_multiplier)), computed once at insertion time. A point assigned max layer L is inserted into layer L and every layer below it, never layers above L. Because the distribution decays exponentially, most points land at layer 0 only, with exponentially fewer points reaching each successively higher layer — this single per-point random decision is the entire mechanism that produces HNSW's sparse-top, dense-bottom pyramid shape, with no separate curation step required.
02 — Greedy search down, then wire in M edges per layer

Insertion: how a new point actually gets wired into the graph

Start here, before the pseudocode. Think about joining a new city to an existing highway-and-street road network. You don't get to just teleport in and declare yourself connected to whichever roads you like — you approach from the existing network, following the best road you can find that gets you close to where you actually are, layer by layer of road detail, and once you're in the right neighborhood, you build a small number of new direct connections to your closest actual neighbors. That's insertion.

The real algorithm, simplified but mechanically faithful:

def insert(graph, new_point, M=4, entry_point=None): max_layer = assign_max_layer() # section 1's random draw if entry_point is None: # first point ever inserted graph.set_entry_point(new_point, max_layer) return current_layer = graph.top_layer() current_best = entry_point # PHASE 1: greedy-descend from the top layer down to max_layer + 1, # WITHOUT connecting anything yet -- just finding a good starting # point for the layer where this new point actually starts inserting. while current_layer > max_layer: current_best = greedy_search(graph, current_layer, new_point, current_best) current_layer -= 1 # PHASE 2: from max_layer down to 0, greedy-search AND connect -- # at each layer the new point actually participates in, find its # M nearest neighbors (via the same greedy walk) and wire in real, # bidirectional edges to them. while current_layer >= 0: neighbors = greedy_search_k_nearest(graph, current_layer, new_point, current_best, k=M) for neighbor in neighbors: graph.add_edge(current_layer, new_point, neighbor) # bidirectional current_best = neighbors[0] # closest neighbor found, carried down a layer current_layer -= 1 if max_layer > graph.top_layer(): graph.set_entry_point(new_point, max_layer) # this point becomes the new top-layer entry

Two phases, and the split matters: phase 1 (layers above the new point's max layer) only searches for a good starting position — the new point doesn't exist at those layers, so nothing gets connected there. Phase 2 (max_layer down through layer 0) is where the point actually joins the graph — at every layer from its assigned max down to the base, it gets wired to its M nearest neighbors AT THAT LAYER specifically (neighbors can differ layer to layer, since each layer only contains a different subset of points). This is exactly why a point's connections get denser the further down you go: at layer 0 every point participates, so there's a much richer set of true near neighbors to connect to than at a sparse upper layer.

Interview-ready definition: HNSW insertion has two phases. First, greedily descend from the graph's current top layer down to just above the new point's randomly-assigned max layer, using each layer's existing edges purely to find a good entry point for the next phase — no new connections are made here. Second, from the max layer down through layer 0, at each layer greedily find the new point's M nearest neighbors (M being a tunable build-time parameter) and wire real bidirectional edges to them, carrying the best-found neighbor down as the starting point for the next layer's search. The new point only exists in the graph from its assigned max layer downward — never above it.

Notice the pattern once you've run through all 14: the layer-0 label ends up with every single point wired into it, densely connected. Layer 1 has noticeably fewer. Layer 2, if it has anything at all, has barely one or two — exactly the exponential-decay shape from section 1's distribution, now visible as an actual constructed graph rather than a claim about probabilities.

Early insertions (graph mostly empty)

The first few points have very little existing structure to search or connect against — greedy search barely has anywhere to go yet, and early points can end up with outsized influence on the graph's initial shape purely by being first.

Later insertions (graph well-populated)

By the time later points are inserted, there's a rich existing graph to greedy-search through at every layer, so their M nearest-neighbor connections are found more precisely — this is part of why HNSW graph quality can depend on insertion ORDER, not just final point count.

Interview-ready definition: HNSW is built incrementally, one point insertion at a time, not computed as a single global batch operation — each new point runs the full two-phase insertion algorithm (section 2) against whatever graph structure already exists from all PRIOR insertions. This is a structural property, not an implementation detail: it's exactly why HNSW supports efficient online/streaming inserts of new vectors into an already-built index (unlike some index structures that require a full rebuild to add data), and also why insertion order can measurably affect the resulting graph's quality, since each point's neighbor search only ever sees the graph as it existed at that point's own insertion time.

Problem 1 · Tracing a single insertion by hand

A graph currently has a top layer of 2. A new point draws max_layer = 1. Using section 2's two-phase algorithm, describe exactly what happens at layer 2, then at layer 1, then at layer 0 — which phase is each layer part of, and does the new point get any edges at layer 2?

Show solution
Layer 2: this is PHASE 1 (current_layer=2 > max_layer=1), since the graph's top layer (2) is above the new point's assigned max layer (1). Greedy search runs at layer 2 purely to find a good starting point for layer 1 -- the new point gets NO edges at layer 2, because it doesn't exist at layer 2 at all (its max layer caps its participation at 1). Layer 1: this is where PHASE 2 begins (current_layer=1 is now <= max_layer=1). The new point greedy-searches layer 1 (starting from wherever phase 1 left off) to find its M nearest neighbors AT layer 1, and gets real bidirectional edges wired to them here. Layer 0: still PHASE 2, continuing downward. The new point greedy- searches layer 0 (starting from the best node found at layer 1) for its M nearest neighbors at layer 0, and gets wired in there too. Net result: the new point ends up with edges at layer 1 and layer 0 only -- never layer 2 -- exactly matching its randomly-assigned max layer of 1.
Problem 2 · Why phase 1 doesn't create edges, stated precisely

Someone suggests: "phase 1 is wasted work — just skip straight to the new point's max layer and start connecting immediately, using a random existing node as the entry point." What breaks if you did this?

Show solution
Phase 1 isn't wasted work -- it's what makes the M nearest-neighbor search in phase 2 actually accurate. Its whole job is narrowing down, via the SAME greedy layered descent search used everywhere else in HNSW, to a good starting position -- a node already reasonably close to the new point -- before phase 2's nearest-neighbor search even begins. If you instead started phase 2 from a RANDOM existing node instead of one found via phase 1's greedy descent, the greedy search within phase 2's own layer could easily get stuck in a "locally good enough" pocket of the graph that's actually far from the new point's true nearest neighbors -- exactly the same "entry point matters disproportionately" failure mode covered in the Week 1 hnsw_indexing lab's Practice Problem 2, except now happening at INSERT time instead of query time. A bad starting point at insertion doesn't just produce one bad search result -- it produces a permanently badly-connected node baked into the graph structure itself, since the new point's actual edges get chosen based on wherever this flawed search happened to end up. Phase 1's descent is specifically what keeps insertion-time search quality comparable to query-time search quality, rather than treating them as different problems.
Problem 3 · Predicting the effect of level_multiplier on graph shape

Using section 1's formula (floor(-ln(r) * level_multiplier)), would DOUBLING level_multiplier make MORE or FEWER points reach layer 2 and above, compared to the default? Explain using the formula's structure, not just intuition.

Show solution
Doubling level_multiplier makes MORE points reach layer 2 and above. Since -ln(r) is a fixed random quantity for a given draw r, multiplying it by a LARGER level_multiplier produces a LARGER result before the floor() is applied -- so for the exact same random draw r, a bigger level_multiplier pushes the computed max_layer value higher, on average, across many draws. Concretely: if -ln(r) = 0.8 for some draw, a level_multiplier of 0.36 gives floor(0.8*0.36)=floor(0.288)=0, landing that point at layer 0 only. The same draw with level_multiplier=0.72 gives floor(0.8*0.72)=floor(0.576)=0 still -- but for a draw with -ln(r)=1.5, multiplier 0.36 gives floor(0.54)=0, while multiplier 0.72 gives floor(1.08)=1, now reaching layer 1. Across many draws, a larger multiplier systematically shifts the whole distribution of computed max layers upward, meaning more points end up qualifying for layer 1, 2, and beyond -- a taller, less sharply-tapered pyramid, with a denser (and more expensive to build/store) upper layer, trading build cost/memory for potentially better search quality via a richer top-layer structure to navigate.
Problem 4 · Diagnosing a graph with an unusually tall, sparse structure

A team's HNSW build ends up with 6 layers for only 2,000 points, and query performance is worse than expected, with unusually long build times. Using sections 1 and 2, what parameter would you suspect first, and what would you check?

Show solution
Suspect level_multiplier being set too high for this dataset size first. Section 1's formula means a larger level_multiplier systematically pushes more points into higher layers (Problem 3's finding) -- 6 layers for only 2,000 points is an unusually tall pyramid for that few points; a well-tuned build for 2,000 points would typically only need 2-3 layers to taper correctly from "sparse top" down to "every point at layer 0." What to check: the actual level_multiplier value used, and whether it was copied from a configuration tuned for a MUCH larger dataset (the paper's recommended default, 1/ln(M), is dataset-size-independent by formula, but some implementations expose it as a directly-tunable knob that can accidentally be set too high). A too-high multiplier means more points participate in more layers than necessary for a dataset this small -- each of those extra layer-memberships means extra edges to build (slower construction, exactly matching the "unusually long build times" symptom) and extra graph structure to traverse per query without a proportional recall benefit at this data scale (mirroring the "unusually long build times" and worse-than-expected query performance symptoms together) -- essentially paying HNSW's build/memory cost of a much bigger dataset's optimal shape without getting a bigger dataset's benefit from it.
Problem 5 · Comparing this lab's build to a full rebuild-from-scratch approach

Some ANN index types require rebuilding the ENTIRE index from scratch to add new vectors (recomputing global structure over the whole dataset). Using section 3's incremental-insertion demo, explain concretely why HNSW avoids this, and name one real operational advantage that follows from it.

Show solution
HNSW avoids full rebuilds because insertion (section 2) is defined entirely in terms of the NEW point and the graph AS IT CURRENTLY EXISTS -- it never needs to look at or recompute anything about points that were already inserted and already have their own edges. Each insertion is a bounded, local operation: draw a max layer for just this one point, greedy-search down through the EXISTING graph, wire in M new edges at each participating layer. Section 3's demo shows this directly -- points 2 through 14 are each inserted against whatever graph points 1 through (n-1) already built, with no step that goes back and recomputes anything about the earlier points' own edges. Real operational advantage that follows: a production vector database using HNSW can accept new documents/embeddings continuously, in real time, as they arrive (e.g. a user uploads a new document to a RAG corpus), without taking the index offline or scheduling a batch rebuild job that reprocesses the entire existing dataset. An index type that required a full rebuild on every new insert would force a choice between staleness (batch up new vectors and rebuild periodically, meaning new data isn't searchable until the next rebuild) or an expensive, disruptive full-recompute on every single write -- HNSW's incremental insertion structurally avoids having to make that trade-off at all.
