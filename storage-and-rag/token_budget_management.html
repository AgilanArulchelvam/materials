The context window is a fixed-size box. Everything you want to put in it has to fit.

An LLM's context window has a hard maximum number of tokens — not characters, not words, tokens, the model's own sub-word units. Every piece you want present at generation time — system instructions, retrieved chunks, conversation history, and room left over for the model's own output — has to share that one fixed budget. This lab builds a live token estimator, then a budget bar that fills up exactly the way a real prompt does, and shows precisely what gets cut when it overflows.

01 — A rough ruler, because you rarely have the real tokenizer on hand

Estimating token counts for a context window

Start here, before any formulas. Imagine packing a moving truck without a scale — you don't know the exact weight of every box, but you know roughly "a box this size is about this heavy," so you can estimate whether everything will fit before you actually try to load it. Token budgeting works the same way: running the model's real tokenizer on every candidate piece of text before deciding what to include is often too slow or simply unavailable at the point in your pipeline where you're making these decisions, so you lean on a quick, good-enough heuristic instead — accurate enough to plan with, even though it isn't exact.

A token is the actual unit a language model reads and writes in — not a character, and not quite a word either. Modern tokenizers (like BPE — byte-pair encoding — variants) build a vocabulary of common sub-word pieces, so a single English word might be one token ("the") or split across two or three ("unbelievably" → "un" + "believ" + "ably"). Because exact tokenization depends on the specific model's vocabulary, the standard rough heuristic for English text is: ~4 characters per token, or equivalently ~0.75 words per token (roughly 3 tokens per 4 words). Neither is exact — both are planning estimates, useful specifically because they're cheap to compute without invoking a real tokenizer at all.

# the rough heuristic — good enough for planning, not for billing def estimate_tokens_by_chars(text): return round(len(text) / 4) # ~4 characters per token, English prose def estimate_tokens_by_words(text): words = text.split() return round(len(words) / 0.75) # ~0.75 words per token

Where the heuristic breaks: code and non-English text

The ~4-characters-per-token ratio is specifically an English prose average — it drifts noticeably for other kinds of text, and a real tokenizer's actual behavior on these cases can differ substantially from the heuristic's prediction.

Code

Source code tends to tokenize less efficiently than prose per character — punctuation-heavy syntax ({}, (), ::, =>), camelCase/snake_case identifiers, and indentation whitespace often each consume their own token or split into multiple sub-word pieces, so a 400-character code snippet can easily cost noticeably more than the ~100 tokens the ÷4 heuristic would predict.

Non-English text

Many tokenizer vocabularies are trained on English-majority corpora, so languages that are underrepresented in that training data — or that don't use whitespace to separate words at all, like Chinese or Japanese — often tokenize far less efficiently per character. A given non-English passage can cost 2-3x (or more) the tokens the English-tuned ÷4 heuristic would estimate for the same character count.

Interview-ready definition: a token is the actual sub-word unit a language model's tokenizer encodes and decodes, typically produced by a byte-pair-encoding-style algorithm over a fixed vocabulary — not equivalent to a character or a whole word. Because running the real tokenizer isn't always convenient or available, the standard planning heuristic for English prose is ~4 characters per token (equivalently ~0.75 words per token); this ratio is an approximation that measurably breaks down for token-dense text like source code (punctuation and identifiers tokenize less efficiently per character) and for non-English text (especially languages underrepresented in the tokenizer's training vocabulary, or without whitespace-delimited words), where the real token count can run meaningfully higher than the heuristic predicts.
02 — The budget is fixed. Something has to give when demand exceeds it

Strategies for staying under budget

Start here, before the list. Imagine packing a single carry-on bag for a trip where you'd genuinely like to bring twice as much as it can hold. You don't just refuse to pack — you make deliberate trade-offs: some things get left behind entirely, some bulky items get compressed into smaller packing cubes, and you prioritize what you're most likely to actually need over what's merely nice to have. Staying under a token budget requires exactly this kind of deliberate triage, not a hope that everything will simply fit.

StrategyWhat it doesCost of using it
TruncationCut text off at a hard limit — e.g. keep only the first/last N tokens of a chunk or messageSimple and fast, but can cut off mid-sentence or drop the actually-important part of a long passage
SummarizationReplace older content with a shorter summary that preserves the gist (the subject of the next lab)Costs an extra LLM call to produce the summary, and summaries can lose specific details irreversibly
Relevance prioritizationRank retrieved chunks by relevance score and keep only the top-scoring ones within budgetRequires already having a relevance score (e.g. from retrieval/re-ranking) to rank against
Dropping low-priority contextDefine an explicit priority order across context TYPES (e.g. system instructions > current question > top retrieved chunks > older history) and drop from the bottom upRequires deciding that priority order in advance — a design decision, not something the budget itself tells you

These strategies are not mutually exclusive — a real pipeline typically combines several: relevance prioritization decides which retrieved chunks are worth including at all, truncation handles anything still too long once selected, and summarization specifically targets conversation history, which tends to be the fastest-growing, lowest-density part of the prompt as a conversation goes on.

Interview-ready definition: staying under a token budget requires an explicit strategy for what to cut when total content exceeds the available window: truncation (hard-cutting text at a length limit, cheap but potentially destructive to meaning), summarization (compressing older content into a shorter gist via an extra LLM call, trading compute cost and some information loss for space), relevance-based prioritization (ranking candidate content by a relevance score and keeping only the top-scoring items), and priority-tiered dropping (defining in advance which categories of context — system instructions, current question, retrieved chunks, older history — are least essential and cutting those first). Real pipelines typically combine these rather than relying on just one.
03 — Four sections competing for one fixed-width bar

The context window budget bar, live

Start here, before the demo. A context window doesn't have one owner — it has to simultaneously hold the system prompt (instructions for how the model should behave), retrieved chunks (the RAG context pulled in for this specific question), conversation history (prior turns of the exchange), and it has to leave room at the end for the model's own output tokens, since generation also consumes the same shared budget. What gets cut, in order: the system prompt and reserved output space are treated as non-negotiable — the model needs its instructions, and generation needs somewhere to write to, so those two are never the first things sacrificed. Between retrieved chunks and conversation history, the demo above cuts from the lowest-priority end of conversation history first (the oldest turns), then, if still over budget, drops the lowest-relevance retrieved chunks — mirroring the "prioritize more relevant chunks over less relevant ones, drop low-priority context first" strategy from section 2. A production system's actual cut order is a real design decision, not a law of nature — but SOME explicit order has to exist, or the overflow behavior is undefined.
Interview-ready definition: a context window's token budget is shared across every section that must be present at generation time — system prompt, retrieved context, conversation history, and reserved space for the model's own output — and because the total is fixed while the demand from these sections grows over a long conversation, some explicit policy must determine what gets truncated, summarized, or dropped when total demand exceeds the budget. Treating this as an afterthought (no defined cut order) risks silently dropping the system prompt's instructions or truncating mid-generation output space, both of which are typically far more damaging than losing some lower-priority older conversation history.

Problem 1 · Estimating tokens by hand with the ÷4 heuristic

A retrieved chunk of English prose is 1,840 characters long. Using the ~4-characters-per-token heuristic, estimate its token count. If your context window has a hard limit of 400 tokens reserved for retrieved chunks, does this single chunk fit on its own?

Show solution
1,840 characters / 4 characters per token ≈ 460 tokens. This single chunk, estimated at ~460 tokens, does NOT fit within a 400-token budget reserved for retrieved chunks on its own -- it would need to be truncated, or a different (shorter, or more relevant) chunk would need to be selected instead, or the per-chunk budget would need to be reconsidered. This is exactly the kind of quick, no-tokenizer- required estimate the heuristic exists for: deciding "does this roughly fit" before committing to including it, without needing to invoke the actual model tokenizer just to make that call.
Problem 2 · Explaining why a code-heavy chunk breaks the heuristic's assumption

A retrieved chunk is a 800-character Python function. The ÷4 heuristic estimates ~200 tokens. A real tokenizer run against the actual model reports 265 tokens. Explain specifically why the heuristic under-estimated here, tying your answer back to section 1.

Show solution
Section 1 specifically calls out that the ~4-characters-per-token ratio is an ENGLISH PROSE average, and that source code tokenizes less efficiently per character than prose -- punctuation-heavy syntax (parentheses, colons, brackets, operators), camelCase/snake_case identifiers that often split across multiple sub-word tokens, and indentation whitespace all tend to consume more tokens per character than ordinary English sentences do, where common words often map to a single token each. The 800-character Python function landing at 265 real tokens instead of the heuristic's predicted 200 is a direct instance of this drift: 800/4 = 200 assumes prose-like token density, but code's higher proportion of punctuation and split identifiers pushes the real count meaningfully higher (265 tokens implies a real ratio closer to ~3 characters per token here, not 4). This is exactly why section 1 frames the ÷4 heuristic as a rough PLANNING estimate rather than something to rely on for a hard, precise budget cutoff when the content in question is code or other non-prose text.
Problem 3 · Choosing a strategy for a specific overflow scenario

A chat assistant's conversation history has grown to 40 turns and is now, on its own, larger than the entire remaining token budget after the system prompt and current retrieved chunks are accounted for. The user's most recent 3 messages are clearly still relevant to the current question; turns 1-10 are about a completely different topic the user has since moved on from. Which strategy (or combination) from section 2 fits best here, and why not just truncate the oldest N tokens blindly?

Show solution
The best fit is a combination of relevance prioritization and summarization (or outright dropping) applied specifically to the OLDER, now-irrelevant portion of history, rather than blind truncation by token count. Since turns 1-10 are described as being about a completely different topic the user has since moved on from, they carry very little value toward answering the CURRENT question -- this is exactly the "drop low-priority context first" strategy from section 2, where "priority" here is determined by topical relevance to the current turn, not just recency. Blind truncation by raw token count (e.g. "just cut the oldest N tokens") happens to work out reasonably well in THIS specific scenario only because the least-relevant content also happens to be the oldest -- but that's a coincidence of this example, not something truncation guarantees in general. If the irrelevant turns were somewhere in the MIDDLE of the conversation instead of at the start, blind oldest-first truncation would cut the wrong content (or the right content for the wrong reason), while a relevance-based approach would still correctly identify and drop the actually-irrelevant turns regardless of where they fall in the sequence. The most recent 3 messages, described as clearly still relevant, should be prioritized to stay in full rather than being caught in either truncation or summarization.
Problem 4 · Diagnosing a budget bar that silently dropped the system prompt

A team's RAG pipeline has a bug: under heavy load with long conversation histories, the assembled prompt sometimes truncates the SYSTEM PROMPT itself to make room, because their truncation logic just cuts from the end of the final concatenated string once it exceeds the token limit, with no awareness of which section is which. What breaks, and what's the fix, tying back to section 3?

Show solution
What breaks: if the system prompt happens to be placed near the end of the final concatenated string (or if the truncation logic simply doesn't distinguish between sections at all and just chops off whatever ends up at the tail once the limit is hit), a long enough conversation history can push the truncation point back far enough to eat into the system prompt itself -- silently removing the model's core behavioral instructions (tone, format constraints, safety guardrails, whatever the system prompt was responsible for) with no error or warning, since from the truncation logic's point of view it's just "characters past the limit," not "the instructions the model absolutely needs." The fix, directly from section 3's budget bar: the system prompt (and reserved output space) need to be treated as NON-NEGOTIABLE sections that are reserved and protected BEFORE anything else is allocated budget, not truncated as an undifferentiated tail of one long string. Concretely, this means computing the system prompt's token cost first, subtracting it (and the reserved output allowance) from the total budget up front, and only then deciding how much of the REMAINING budget retrieved chunks and conversation history are allowed to consume -- with cuts applied specifically to those lower-priority sections, never to the system prompt. This requires the assembly logic to be section-aware (know which tokens belong to which category) rather than treating the final prompt as one opaque string to truncate blindly.
Problem 5 · Reasoning about the reserved output space trade-off

A model has a 8,000-token total context window. A team reserves 1,500 tokens for the model's output. Why does under-reserving this (e.g. reserving only 200 tokens) risk a real failure mode, and why does over-reserving it (e.g. reserving 6,000 tokens) also have a real cost? What does this reveal about reserved output space being just another competing section in the budget bar?

Show solution
Under-reserving (e.g. only 200 tokens reserved for output): if the model's genuinely correct, complete answer would naturally run longer than 200 tokens -- a detailed explanation, a multi-step answer, a longer piece of generated code -- the model's output gets cut off mid-generation once it hits the hard context-window ceiling, producing a visibly truncated, incomplete response. This is a direct, user-facing failure mode, not a subtle one: the answer just stops. Over-reserving (e.g. 6,000 of 8,000 tokens reserved for output, leaving only 2,000 for everything else): this squeezes the INPUT side of the budget -- system prompt, retrieved chunks, and conversation history now have to fit in a much smaller remaining space, which directly increases how aggressively section 2's strategies (truncation, summarization, dropping low-priority context) need to be applied, potentially degrading answer quality by feeding the model less relevant context than it could have had, purely because output space that may not even end up being fully used was reserved upfront and made unavailable to input. This reveals exactly what section 3 is illustrating: reserved output space isn't a special, budget-exempt category -- it's one more section competing for the same fixed total, with a real trade-off in both directions. Sizing it correctly means estimating (often from the specific task's typical response length) roughly how much output is actually needed, not defaulting to either extreme.
