01 — Four stages, strictly sequential, each depending on the previous one's output

The retrieval + generation pipeline, end to end

Start here, before the diagram. Imagine asking a research assistant a question they don't already know the answer to. They don't just start talking — they first figure out what to search for (turning your question into search terms), then go look through the library for the specific relevant sources (not the whole library, just what's actually relevant), then organize what they found into something they can reason from, and only THEN do they actually compose an answer, informed by what they found rather than pulled from memory alone. A RAG Q&A system runs the exact same four-step shape, mechanically.

The four stages, concretely: (1) embed the question — the user's natural-language question is passed through the same embedding model used to embed the document chunks, producing a query vector in the same vector space. (2) vector search — that query vector is compared against the indexed chunk vectors (via the dense/HNSW/IVF/hybrid techniques from earlier this month) to retrieve the top-K most similar chunks, each with a similarity score. (3) assemble context — exactly the mechanics from the context_assembly lab: the retrieved chunks, system instructions, and the question get concatenated with clear delimiters into one final prompt string, ordered per that lab's recency-effect reasoning. (4) generate — the assembled prompt is sent to the LLM, which produces the final answer grounded in the retrieved context rather than purely from its own training-time knowledge.

Interview-ready definition: a retrieval-augmented generation Q&A pipeline is a strictly sequential four-stage process: embedding the user's question into the same vector space as the indexed documents, searching that index for the top-K most similar chunks, assembling those chunks with instructions and the question into one delimited prompt string, and generating a final answer from that assembled prompt. Each stage's output is the next stage's required input — the pipeline cannot skip or reorder stages, which is precisely why its total latency (section 3) is the SUM of each stage's individual latency rather than something that can be collapsed by running stages concurrently.
02 — "I don't have good information about this" beats a confident wrong answer

Handling low-confidence retrieval

Start here, before the mechanism. Imagine asking that same research assistant a question completely outside their library's coverage — say, a question about a competitor's internal policies they have no documents on at all. A good research assistant tells you plainly "I don't have anything on that" rather than skimming the closest-sounding document they DO have and confidently answering as if it were relevant, just because it was the best match available among a bad set of options. The vector search stage always returns SOMETHING — even irrelevant chunks get some similarity score — so the pipeline needs an explicit check for whether what it found is actually good enough to answer from, not just whatever happened to score highest.

The mechanism is a similarity-score threshold check: after retrieval returns its top-K chunks with similarity scores, the system compares the TOP score against a minimum threshold. If even the best-matching chunk falls below that threshold, the system has good evidence that nothing genuinely relevant was found — retrieval finding "the least-bad option" is not the same as retrieval finding a genuinely relevant match. In that case, the correct behavior is to have the system explicitly say it doesn't have good information on this question, rather than assembling a prompt from weakly-related chunks and letting the LLM generate a confident-sounding answer anyway.

SIMILARITY-SCORE THRESHOLD CHECK — TWO QUERIES, ONE PASSES, ONE DOESN'T
Why this matters more than it might seem: without a threshold check, EVERY query gets an answer assembled from whatever chunks scored highest, even if none of them are actually relevant — the LLM, given weakly-related context and no signal that the context is weak, will often still generate something that reads as confident and specific, because generating fluent, plausible-sounding text is exactly what it's good at, independent of whether the underlying context actually supports the claim. This is a direct hallucination risk introduced at the RETRIEVAL layer, not the generation layer — the fix belongs in the pipeline's retrieval-confidence check, not in trying to prompt the LLM into being more careful after the fact.

Above threshold — proceed normally

Top chunk's similarity score clears the minimum bar. The pipeline proceeds to context assembly and generation as normal, grounded in genuinely relevant retrieved material.

Below threshold — decline gracefully

Even the best-matching chunk falls short of the threshold. The system skips generation-from-weak-context entirely and returns an explicit "I don't have good information about this" response instead, rather than gambling on a low-relevance chunk.

Interview-ready definition: handling low-confidence retrieval means explicitly checking the similarity score of the retrieval stage's best result against a minimum threshold before proceeding to generation — if even the top-ranked chunk falls below that threshold, the system has evidence that nothing genuinely relevant exists in the index for this query, and the correct behavior is to return an explicit "insufficient information" response rather than assembling a prompt from weakly-related chunks and risking a fluent, confident-sounding but ungrounded (hallucinated) answer. This check exists specifically because vector search always returns its top-K results regardless of whether any of them are actually good matches — a low top score is a real, available signal that the pipeline should not simply discard by proceeding as if retrieval had succeeded.
03 — Four sequential stages, one of them dominates the total

Latency budget across the pipeline

Start here, before the numbers. If you time each of the four pipeline stages individually, one of them will almost always dwarf the other three combined — and knowing WHICH one, and why, changes where you'd actually spend engineering effort if this pipeline felt too slow. Optimizing a stage that's already a small fraction of total latency, even by a lot, barely moves the total; optimizing the dominant stage moves it a lot.

WHERE DOES THE TIME ACTUALLY GO?
Embed query Vector search Assemble context LLM generation

StageTypical latencyWhyParallelizable?
Embed query~20-40msOne short text embedded through a (usually small) embedding model — a single forward passSequential — search needs the query vector first
Vector search~10-50msAn approximate nearest-neighbor lookup (HNSW/IVF) over a pre-built index — sub-linear by designSequential — needs the query vector from stage 1
Assemble context~5-15msPure string concatenation and formatting — no model inference involved at allSequential — needs the retrieved chunks from stage 2
LLM generation~800-3000ms+Full autoregressive generation, token by token, of the entire answer — by far the most compute-intensive stepSequential by nature (each token depends on the previous), and dominates the total regardless
What's actually parallelizable, and what isn't: within a SINGLE query, these four stages are fundamentally sequential — each one's output is a required input to the next, so there's no way to run embedding and generation concurrently for the same request. What IS parallelizable: handling multiple DIFFERENT queries concurrently (the pipeline for query A and the pipeline for query B don't depend on each other at all), and, within stage 4 specifically, streaming the generated answer token-by-token back to the user as it's produced rather than waiting for the full response — this doesn't reduce total generation time, but it reduces PERCEIVED latency, since the user sees output starting almost immediately instead of waiting for the entire answer to finish generating first.
Interview-ready definition: a RAG pipeline's total latency is the sum of four sequential stages (embed, search, assemble, generate), each depending on the previous stage's output — but LLM generation typically dominates total latency by a wide margin (often 10-50x any other single stage), since it involves full autoregressive token-by-token generation from a large model, versus the comparatively cheap embedding lookup, index search, and string concatenation in the other three stages. Because the stages are strictly sequential within one request, latency optimization efforts are best directed at the dominant stage (e.g. streaming tokens to reduce perceived latency, or using a faster/smaller generation model) rather than the three earlier stages, whose combined latency is typically a small fraction of the total even before any optimization.

Problem 1 · Tracing why the pipeline can't reorder or skip stages

Someone proposes: "let's run vector search and context assembly at the same time to save latency, since they're both fast anyway." Explain specifically why this isn't possible, using section 1's pipeline structure.

Show solution
Context assembly's input is the SET OF RETRIEVED CHUNKS -- it literally cannot begin until vector search has finished and produced that output, since assembly's whole job (per the context_assembly lab) is concatenating those specific retrieved chunks, with their specific text and source labels, into the prompt string. There's nothing for assembly to assemble until search has returned results. This is a hard data dependency, not merely a convention -- it's not that running them concurrently is unsafe or discouraged, it's that assembly has no valid input to operate on until search completes. This is exactly section 1's point about the pipeline being strictly sequential: each stage's output is a REQUIRED input to the next stage, which is a fundamentally different situation from two independent tasks that merely happen to both be fast and could, in principle, run at the same time. The fact that both stages are individually fast (section 3's table: ~10-50ms for search, ~5-15ms for assembly) doesn't change this -- speed and independence are separate properties, and only independence would make concurrent execution possible.
Problem 2 · Choosing a similarity threshold given a concrete score distribution

A team observes that for queries genuinely covered by their knowledge base, the top retrieved chunk's similarity score is almost always above 0.75. For queries clearly outside their knowledge base's coverage, the top score is almost always below 0.55. Where would you set the threshold, and what happens to queries that happen to score between 0.55 and 0.75?

Show solution
A reasonable threshold sits somewhere in the observed gap between the two clusters -- e.g. around 0.60-0.65 -- since that range separates the two observed populations (in-domain queries clustering above 0.75, out-of-domain queries clustering below 0.55) reasonably cleanly, with some margin on either side rather than setting the threshold exactly at either cluster's edge. Queries landing in the 0.55-0.75 gap are the genuinely ambiguous case -- this is real, unavoidable uncertainty rather than a sign the threshold was chosen badly: a single scalar threshold can't perfectly separate "good match" from "bad match" for queries whose true relevance is itself somewhat ambiguous. Where exactly to draw the line WITHIN that gap is a real trade-off: a threshold near the low end of the gap (e.g. 0.58) accepts more borderline queries as "confident enough to answer," risking occasionally answering from a genuinely weak match (a false accept); a threshold near the high end (e.g. 0.72) rejects more borderline queries as "not confident enough," risking occasionally declining to answer a question the system actually had decent information for (a false reject). This is the same precision/recall- style trade-off that shows up whenever a single score threshold is used to make a binary decision -- there's no threshold value that eliminates both kinds of error simultaneously, only a choice of which kind of error to accept more of.
Problem 3 · Calculating the effect of a latency optimization on each stage

Given roughly: embed 30ms, search 30ms, assemble 10ms, generate 1800ms (total ≈1870ms). A team cuts vector search latency in HALF (to 15ms) via a better index. Separately, another team cuts generation latency by just 20% (to 1440ms) via a faster model. Compare the two teams' impact on TOTAL pipeline latency, and explain what this reveals about where optimization effort should go.

Show solution
Team 1 (search 30ms → 15ms, a 50% reduction on that stage): new total = 30 + 15 + 10 + 1800 = 1855ms. Reduction from original 1870ms: only 15ms, about a 0.8% reduction in TOTAL latency, despite HALVING the search stage's own latency. Team 2 (generation 1800ms → 1440ms, just a 20% reduction on that stage): new total = 30 + 30 + 10 + 1440 = 1510ms. Reduction from original 1870ms: 360ms, about a 19.3% reduction in TOTAL latency, from a proportionally SMALLER percentage improvement to its own stage than Team 1 achieved. This directly demonstrates section 3's core point: because generation dominates total latency (1800 of 1870ms, ~96% of the total in this example), even a modest percentage improvement to generation swamps a much larger percentage improvement to any of the other three stages, purely because of how much of the total each stage represents to begin with. This is a concrete instance of Amdahl's-law-style reasoning: optimizing a component that's a small fraction of the total, no matter how effectively, bounds how much total improvement is even possible -- the search stage's ENTIRE latency (30ms) is a hard ceiling on how much total time IT could ever save, regardless of optimization technique, while generation's dominant share means proportionally modest improvements there yield much larger total-latency wins.
Problem 4 · Diagnosing a system that hallucinates despite having a threshold check

A team has a similarity-score threshold check per section 2, and it correctly rejects clearly out-of-domain queries. But it still occasionally produces confident, wrong answers for queries that ARE technically covered by the knowledge base, just poorly — the top chunk scores 0.68 (above their 0.60 threshold), but the chunk only tangentially relates to the actual question asked. What's the limitation of a single top-score threshold check being exposed here, and what would help?

Show solution
The limitation being exposed: a single top-score threshold only checks whether SOMETHING scored reasonably well -- it says nothing about whether that best-scoring chunk is actually a GOOD, on-target match for the SPECIFIC question, versus merely the best available option among a generally weak field of candidates. A chunk that's "tangentially related" can genuinely clear a 0.60 threshold (similarity scores are continuous, not binary "relevant vs irrelevant"), while still being a poor basis for a confident, specific answer to the particular question asked -- the threshold check (section 2) is a coarse, real, but incomplete signal, not a guarantee of true relevance. What would help: additional signals beyond just the raw top score -- for example, checking the SCORE GAP between the top chunk and the next-best chunks (a lone chunk scoring 0.68 with everything else far below might indicate a narrow, possibly-coincidental match rather than strong topical coverage), using a re-ranking step (from earlier this month's re-ranking lab) to get a more precise relevance judgment via cross-encoder scoring rather than trusting the bi-encoder's retrieval score alone, or having the generation step itself be explicitly instructed and evaluated on whether it can ACTUALLY answer the specific question from the provided context versus only tangentially-related material -- essentially, pushing part of the "is this actually sufficient" judgment into a stage with more context than a single scalar similarity number can carry. The core lesson: a threshold check is a real, useful, cheap first filter, not a complete solution to low-confidence retrieval on its own.
Problem 5 · Designing for 10x query volume

This pipeline needs to handle 10x its current query volume. Using section 1's sequential structure and section 3's latency breakdown, is the fix "make each of the four stages individually faster," or something else? What's the actual lever for handling more TOTAL volume versus making each individual request faster?

Show solution
These are two genuinely different problems, and the fix for 10x VOLUME is not the same as the fix for reducing any single request's LATENCY. Making each of the four stages individually faster (section 3's optimization discussion) reduces how long ONE request takes end to end -- it doesn't, by itself, change how many requests the system can handle concurrently. Handling 10x volume is primarily a horizontal-scaling and concurrency problem: since each individual query's pipeline (embed → search → assemble → generate) is independent of every OTHER query's pipeline (this lab's section 3 "what's parallelizable" callout notes exactly this -- different queries' pipelines don't depend on each other), the lever for volume is running many of these independent pipelines concurrently, across multiple embedding-model replicas, multiple generation-model replicas/instances, and a vector index that can serve concurrent read queries -- not making any single pipeline's four sequential stages individually faster. The generation stage specifically, being both the slowest AND the most compute-intensive (typically running on GPU infrastructure), is usually the first capacity bottleneck under increased volume -- meaning the 10x-volume question is substantially about "how many concurrent generation requests can the LLM serving infrastructure handle," which is a capacity/replica-count question, distinct from "how fast is any one generation call," which is the section 3 latency question. Both are real design considerations, but they point to different fixes: replica count and concurrency for volume, per-stage speed for individual- request latency.
