STORAGE & RAG LAB · CHUNKING & HYBRID SEARCH

Search on the small piece. Hand the LLM the whole neighborhood.

Small chunks make retrieval precise — a tight, specific span of text matches a specific query well. But that same small chunk often lacks the surrounding context an LLM needs to actually use it. Parent-child chunking resolves the tension by searching on small child chunks, then returning their larger parent chunk instead. This lab animates that exact "zoom out" — a query matches a small child, then the system swaps in its parent before the LLM ever sees it.

01 — Two different chunk sizes, doing two different jobs

Small chunks for retrieval, larger chunks for context

Start here, before any diagrams. Imagine a library's card catalog. Each index card is short — a title, an author, maybe one line of subject description — deliberately terse so you can flip through hundreds of them fast and find the exact card that matches what you're looking for. But nobody hands you the index card and calls it done — once you've found the RIGHT card, you walk over and pull the entire BOOK it points to, because the index card alone was never meant to contain enough to actually read and understand the subject. The card's job is precise matching; the book's job is providing enough context to actually be useful.

Parent-child chunking applies this same split to document retrieval. A document is chunked twice, at two different sizes: child chunks are small (a sentence or two, or a small paragraph) and exist specifically to be embedded and searched — their small size makes them precise, closely matching a narrow query without a lot of unrelated surrounding text diluting the embedding. Parent chunks are larger (a full section, or several child chunks' worth of surrounding text) and exist specifically to be RETURNED to the LLM once a search finds a relevant child — the parent gives the LLM the fuller context the tiny child chunk alone never had room for. Critically, only the CHILD chunks get embedded and searched; the parent is retrieved by reference (via a parent ID stored alongside each child), not by a separate similarity search of its own.

# Roughly how a parent-child index is built and queried def build_index(document): parents = chunk(document, size=1000) # large, for context index = [] for parent_id, parent_text in enumerate(parents): children = chunk(parent_text, size=150) # small, for matching for child_text in children: index.append({ "embedding": embed(child_text), # only the CHILD is embedded "child_text": child_text, "parent_id": parent_id, # pointer back to the larger parent }) return index, parents def query(q, index, parents): best = max(index, key=lambda c: cosine_similarity(embed(q), c["embedding"])) # the match happened on the small child -- but we RETURN the parent return parents[best["parent_id"]]
Interview-ready definition: parent-child chunking indexes and embeds small "child" chunks for precise retrieval matching, while storing a pointer from each child to a larger "parent" chunk (or the full section/document it belongs to) that is returned to the LLM instead of the child once a match is found. The search step operates entirely on the small, precise child embeddings; the context-delivery step swaps in the larger parent by reference, without a second similarity search — decoupling "what gets matched" from "what gets returned" lets each be sized for the job it's actually doing.

Interview-ready definition: the parent-child retrieval flow performs similarity search exclusively against child chunk embeddings, then — once the best-matching child is identified — resolves that child's stored parent_id and returns the parent chunk's full text to the generation step instead of the child. This means retrieval precision is governed entirely by the small child chunks (which is why they're kept small and specific), while the answer quality the LLM can produce is governed by the larger parent chunk's context (which is why it's kept large enough to be self-sufficient) — the two chunk sizes are tuned independently for these two different jobs.
03 — Why not just pick one chunk size?

When parent-child beats flat (single-size) chunking

Start here, before the trade-off. The obvious question: why not just use one chunk size everywhere? Because a single chunk size is forced to be good at both matching AND context-sufficiency at once, and those two goals pull in opposite directions. Small chunks are great at precise matching but often too thin on context for the LLM to use well. Large chunks give the LLM plenty of context but dilute the embedding with lots of surrounding, possibly irrelevant text, making retrieval LESS precise — a large chunk's embedding is an average-ish summary of everything in it, which can drown out the one sentence that actually matched the query.

Flat chunking, small chunks everywhere

Great retrieval precision — each chunk's embedding closely reflects one specific idea. But each returned chunk, alone, often lacks enough surrounding context for the LLM to use it well — pronouns with no antecedent, conclusions with no stated setup.

Flat chunking, large chunks everywhere

Plenty of context in every returned chunk. But retrieval precision suffers — a large chunk's embedding blends multiple ideas together, so a narrow query may fail to surface the chunk containing its actual answer, or surface it ranked lower than it should.

ApproachRetrieval precisionContext sufficiency
Flat, small chunksHigh — narrow, specific embeddingsLow — matched chunk often lacks context
Flat, large chunksLow — diluted, blended embeddingsHigh — plenty of surrounding text
Parent-childHigh — search operates on small childrenHigh — LLM receives the larger parent

Parent-child chunking is the right call specifically when this tension is real for a given document type: technical documentation, legal text, or narrative content where a small span often can't stand alone but a whole document is too much to embed precisely. It's LESS necessary when documents are already short enough that a single chunk covers them fully (no parent/child split needed — one chunk IS both), or when chunks are naturally self-contained regardless of size (e.g. structured FAQ entries, where each entry is already a complete question-answer unit at almost any reasonable chunk size).

The real cost: parent-child chunking isn't free — it requires storing and maintaining two chunking granularities per document (more preprocessing, more storage for the parent text even though only children are embedded), and the parent-lookup step adds a small amount of retrieval-path complexity compared to "just return what matched." This is worth it exactly when the precision-vs-context tension described above is real for the document type; for already-short, already-coherent documents, the added complexity buys little.
Interview-ready definition: parent-child chunking beats flat (single-size) chunking whenever small standalone chunks lack sufficient context for an LLM to use well, but chunks large enough to provide that context would dilute retrieval precision if embedded directly — by decoupling the searched unit (small child) from the returned unit (larger parent), it achieves both high retrieval precision and high context sufficiency simultaneously, at the cost of maintaining two chunking granularities and an extra parent-lookup step in the retrieval path.

Problem 1 · Tracing exactly what gets embedded vs what gets returned

In section 1's build_index/query code, is the parent chunk's text ever passed to an embedding function? Walk through exactly what gets embedded and what gets returned, and explain why this matters for retrieval precision.

Show solution
No -- the parent chunk's text is never embedded. Looking at build_index, the embed() call happens only on child_text inside the inner loop; parent chunks are stored in the `parents` list purely as retrievable text, referenced later by parent_id, with no embedding computed for them at all. The similarity search in query() only ever compares the query's embedding against child embeddings (`c["embedding"]`, which was always computed from a child chunk) -- the parent is looked up ONLY after the best-matching child has already been identified, via a plain list index into `parents`, not a second similarity search. This matters for retrieval precision because it means the entire matching process operates exclusively on small, focused child chunks -- the parent's larger, more diluted content never has a chance to out-compete or under-compete anything in the similarity ranking, since it was never a candidate in that ranking to begin with. This is exactly what keeps parent-child chunking's retrieval precision as good as flat small chunking's (section 3's table) while still returning large-chunk context.
Problem 2 · Predicting what happens if two children under different parents both match well

A query's top-3 matching child chunks belong to 3 DIFFERENT parents (not 2 children under the same parent). What does the system return, and what does this reveal about how parent-child interacts with "return top-k results"?

Show solution
The system returns 3 separate parent chunks -- one per matched child, since each child's parent_id points to a different parent. This is a direct, correct extension of the single-match case described in section 2: retrieving top-k results under parent-child chunking means resolving EACH of the k matched children to ITS OWN parent independently, not picking one "best" parent overall. If two of the top-k matched children had instead belonged to the SAME parent, a well-implemented system would typically deduplicate and return that parent only once (there's no value in handing the LLM the same parent text twice), but with 3 genuinely different parents, the correct behavior is 3 distinct parent chunks handed to the LLM. This reveals that parent-child chunking composes normally with top-k retrieval -- it doesn't collapse multiple independent good matches into one, it just changes what "a match" resolves to (a parent instead of a child) after the ranking step has already run on children. The one added consideration a real implementation needs is de-duplicating parents when multiple top-k children happen to share one, so the LLM's context isn't padded with redundant repeated text.
Problem 3 · Choosing parent-child vs flat chunking for a stated document type

A company's internal wiki has two very different document types: (a) a 40-page technical architecture doc with dense, interdependent sections, and (b) a simple FAQ page where each entry is a self-contained question and 2-sentence answer. Would you apply parent-child chunking to both, one, or neither? Justify per document type.

Show solution
Apply parent-child chunking to (a), the 40-page architecture doc, but NOT to (b), the FAQ page -- these two document types sit on opposite sides of exactly the tension section 3 describes. For (a): dense, interdependent technical sections are precisely the case where a small chunk (a sentence or two about "the retry mechanism") likely depends on surrounding context (what system is being described, what triggers the retry, what happens after) to be usable by an LLM at all -- but embedding a whole large section directly would dilute the embedding across many sub-topics within that section, hurting retrieval precision for narrow queries. Parent-child directly resolves this: small children for precise matching, the full section as parent for context. For (b): each FAQ entry is already a small, SELF-CONTAINED unit -- the question and its 2-sentence answer together already form a complete, coherent idea with no dependency on surrounding entries. There's no context-insufficiency problem to solve (an FAQ answer doesn't need "parent" context beyond itself), so introducing a parent-child split here would add real complexity (two chunking passes, parent storage, a lookup step) for essentially no benefit -- flat, single-size chunking (one chunk per FAQ entry) is already both precise AND self-sufficient.
Problem 4 · Diagnosing a parent-child system returning too little useful text

A team implements parent-child chunking, but users still report that answers feel like they're missing context. On investigation, parent chunks are only slightly larger than child chunks (children: 100 tokens, parents: 150 tokens). What's the likely issue, and what's the fix?

Show solution
The likely issue is that the parent chunk size wasn't set large enough to meaningfully solve the context problem parent-child chunking exists to address -- a parent only 50 tokens larger than its child barely qualifies as "zooming out" at all; it's still close to the same narrow span of text, just marginally padded. Section 1's whole premise is that the parent should be sized to actually contain the surrounding context the LLM needs (a full section, or several children's worth of text) -- a parent that's only 1.5x the child size doesn't meaningfully deliver on that promise, so users experiencing the same "missing context" symptom flat small chunking would produce isn't surprising. The fix: meaningfully widen the gap between child and parent size -- e.g. children around 100-150 tokens (kept small and precise for matching) but parents sized to a full logical section, often several hundred to over a thousand tokens, enough to contain the setup, the detail, and any immediately relevant surrounding explanation a reader would need. The exact right parent size is document-dependent (tied to how documents are naturally structured into sections), but "only slightly bigger than the child" defeats the purpose of having two separate sizes in the first place.
Problem 5 · Explaining why parent-child doesn't need a second similarity search

Someone proposes: "after finding the best-matching child, why not ALSO run a similarity search over just the candidate parent chunks, to double-check the parent is actually relevant?" Explain why this extra step is typically unnecessary, tying your answer back to how parent_id linking works.

Show solution
It's typically unnecessary because the parent's relevance is already established INDIRECTLY and reliably through the child: since the parent is defined as the larger section the matched child was chunked FROM (the parent_id link in section 1's code is set at chunking time, not at query time), the parent chunk by construction CONTAINS the very text that matched the query well enough to win the similarity search. There's no scenario where a child scores as the best match but its parent is somehow irrelevant to the query -- the parent's relevance is inherited directly from containing the specific span that already proved itself relevant. Running a second similarity search over parent embeddings would also reintroduce exactly the precision problem parent-child chunking was built to avoid (section 3): a large parent's embedding is diluted across its full content, so directly comparing the query against parent embeddings could rank a genuinely relevant parent LOWER than its own precise child ranked it, undermining the whole point of matching on children in the first place. The parent_id lookup being a simple, deterministic pointer resolution (not a second search) is precisely what keeps the precision benefit of child-based matching intact all the way through to what gets returned.
