01 — The engine's search function, version 2

v1 → v2: adding hybrid scoring to the retrieval stage

Start here, before any code. Recall the hybrid_search lab's core example: a dense embedding model can miss an EXACT error code because it's reasoning about meaning, not literal string matching, while a keyword method like BM25 catches the exact code instantly but misses a paraphrase that means the same thing in different words. Neither retrieval method alone is strictly better — they fail on different kinds of queries. v2 of this engine's search function runs BOTH scoring methods against the SAME candidate set and combines them, rather than picking one.

# v1 -- day 1/2's engine: cosine similarity only def search_v1(query_vec, index, top_k=10): return index.knn_search(query_vec, k=top_k) # brute-force or HNSW, from days 1-2 # v2 -- add BM25 keyword scoring, combine via reciprocal rank fusion def search_v2(query_text, query_vec, index, bm25_index, top_k=10, candidate_k=50): dense_results = index.knn_search(query_vec, k=candidate_k) # day 1/2's cosine/HNSW search sparse_results = bm25_index.search(query_text, k=candidate_k) # BM25 keyword scoring # reciprocal rank fusion: combine by RANK position, not raw score # (dense cosine scores and BM25 scores live on completely different # numeric scales -- RRF sidesteps needing to normalize them) fused_scores = {} for rank, doc_id in enumerate(dense_results): fused_scores[doc_id] = fused_scores.get(doc_id, 0) + 1 / (60 + rank) for rank, doc_id in enumerate(sparse_results): fused_scores[doc_id] = fused_scores.get(doc_id, 0) + 1 / (60 + rank) ranked = sorted(fused_scores.items(), key=lambda x: x[1], reverse=True) return [doc_id for doc_id, _ in ranked[:top_k]]

The change from v1 to v2 is structural, not cosmetic: v1's search function takes one input (the query vector) and calls one thing (the index). v2 takes both a query VECTOR and the raw query TEXT, calls two independent retrieval systems, and adds a fusion step that neither system needed on its own. This mirrors exactly the hybrid_search lab's reciprocal rank fusion mechanics — the difference here is it's wired directly into THIS engine's actual retrieval function, sitting right on top of the HNSW/brute-force index from days 1-2, rather than shown as an isolated concept.

Interview-ready definition: hybrid search applied to a real retrieval engine means running dense vector search (the engine's existing HNSW/brute-force cosine index) and sparse keyword search (BM25) independently against the same query, then combining their result rankings — typically via reciprocal rank fusion, which combines by each result's RANK position in each list rather than trying to normalize two incompatible raw score scales. The point isn't replacing the vector index built on days 1-2 — it's adding a second, differently-failing retrieval signal alongside it, so queries that expose either method's individual blind spot still surface the right result.
02 — The engine's search function, version 3

v2 → v3: adding a re-ranking pass on top of hybrid retrieval

Start here, before any code. Recall the reranking lab's core distinction: the bi-encoder used for retrieval (v1/v2's cosine similarity and BM25) is cheap enough to run against the ENTIRE index, but that cheapness comes from encoding the query and each document SEPARATELY and comparing the results — it never lets the query and a specific document actually interact while being scored. A cross-encoder re-ranker is more expensive per pair (so it only runs on the small candidate set retrieval already narrowed down to) but scores the query and document TOGETHER, in one pass, producing a more precise relevance judgment.

# v3 -- add a cross-encoder re-ranking pass over v2's fused candidates def search_v3(query_text, query_vec, index, bm25_index, reranker, top_k=10, candidate_k=50, rerank_pool=20): fused_candidates = search_v2(query_text, query_vec, index, bm25_index, top_k=rerank_pool, candidate_k=candidate_k) # cross-encoder scores (query, doc) pairs TOGETHER -- expensive per # pair, which is exactly why it only runs on rerank_pool candidates # (e.g. 20), never the full index (that's what v1/v2 narrowed down for) rerank_scores = [ (doc_id, reranker.score(query_text, get_doc_text(doc_id))) for doc_id in fused_candidates ] rerank_scores.sort(key=lambda x: x[1], reverse=True) return [doc_id for doc_id, _ in rerank_scores[:top_k]]

Notice the shape of the pipeline that's now emerged across v1 → v2 → v3: each version doesn't replace the previous one, it WRAPS it. v3 calls v2, which calls v1's underlying index plus BM25. This is exactly the "narrowing funnel" pattern from the reranking lab — a large candidate pool (v1/v2, cheap per item, applied broadly) progressively narrows to a small, precisely-ordered final result (v3, expensive per item, applied only to survivors) — never the other way around.

Interview-ready definition: re-ranking applied to a real retrieval engine is a final narrowing stage layered on top of whatever retrieval (dense, sparse, or hybrid) already produced a candidate set — a cross-encoder scores each candidate against the query jointly, rather than via separately-precomputed embeddings, producing a more accurate but more expensive-per-item relevance judgment. It's structurally always the LAST stage precisely because its cost doesn't scale to the full index the way v1/v2's retrieval does — it depends on retrieval having already done the cheap work of throwing away the obviously-irrelevant majority of the dataset first.

Problem 1 · Explaining reciprocal rank fusion's scale-independence

Section 1's RRF formula uses 1 / (60 + rank) based on each result's POSITION, not its raw score. Why does this matter given that cosine similarity scores range roughly 0-1 while BM25 scores are unbounded and can be, say, 8.3 or 15.7?

Show solution
If fusion tried to combine raw scores directly (e.g. simply adding a cosine score of 0.82 to a BM25 score of 11.4), the BM25 score would completely dominate the sum purely because of its numeric scale, not because it's actually a more reliable relevance signal -- a document that BM25 barely favors could still outscore a document dense search strongly favors, purely as an artifact of the two scores living on wildly different numeric ranges. Fixing this by normalizing both scores to a common scale is possible but fragile -- it requires knowing or estimating each method's typical score distribution, which can shift across query types. RRF sidesteps the whole problem by using each result's RANK POSITION (1st, 2nd, 3rd, ...) instead of its raw score. Rank position is already on the same "scale" (an integer index) regardless of what scoring function produced it -- the top BM25 result and the top dense result both contribute the same 1/(60+0) fusion score, regardless of whether the underlying BM25 score was 11.4 or 6.2, or the underlying cosine score was 0.82 or 0.61. This is exactly why RRF is the standard fusion method for combining retrieval signals that don't share a comparable numeric scale -- it only requires that each method can RANK its own results, not that the two methods' scores mean the same thing numerically.
Problem 2 · Predicting v2's behavior on a pure-paraphrase query

A query is a pure paraphrase with zero shared vocabulary with the correct document (e.g. asking "what happens when a network call takes too long" about a document that only ever says "connection timeout"). Would v2 (hybrid) retrieve the correct document better, worse, or about the same as v1 (cosine only) for this specific query? Explain using RRF's mechanics.

Show solution
About the same as v1, and specifically NOT worse. For a query with literally zero shared vocabulary with the target document, BM25 (a keyword-overlap-based method) would likely rank that document low or not retrieve it into its own candidate_k list at all -- BM25 has nothing lexical to match on. But RRF's fusion step only ADDS scores together from whichever lists a document actually appears in; a document that dense search ranks highly (rank 0, contributing 1/60 ≈ 0.0167) but BM25 either ranks very low or doesn't surface at all (contributing 0 from that list) still gets dense search's own contribution intact, undiminished by BM25's absence. So v2 doesn't actively hurt a pure-paraphrase query relative to v1 -- the dense signal that v1 already relied on for exactly this kind of query still contributes fully to v2's fused score. What v2 adds is a SEPARATE retrieval path that can rescue cases dense search misses (exact codes, rare terms); it doesn't remove or dilute the cases dense search already handled well. This is the key property that makes hybrid search a safe default rather than a trade-off you have to choose sides on: it doesn't sacrifice one method's strengths to gain the other's.
Problem 3 · Justifying why re-ranking runs on rerank_pool=20, not all of candidate_k=50

Section 2's search_v3 re-ranks only 20 candidates even though v2 fused from a pool of 50 per method. Using the reranking lab's cost-shape reasoning, why not just re-rank all 50 (or more) to be safer?

Show solution
Because the cross-encoder's cost is paid PER (query, document) pair, scoring 50 candidates costs 2.5x what scoring 20 does, with no shortcut -- unlike v1/v2's retrieval, a cross-encoder can't precompute anything about a document ahead of time, since its whole value proposition (per section 2 and the Week 2 reranking lab) is scoring the query and document TOGETHER, which by definition can't happen until the specific query arrives. Re-ranking more candidates is a direct, linear increase in query-time latency and compute cost, unlike widening candidate_k in v1/v2's dense/BM25 retrieval, which is comparatively cheap per extra candidate. The actual trade-off: rerank_pool controls how much you trust the FUSED ranking from v2 to already contain the true best results somewhere in its top N, versus how much re-ranking latency you're willing to pay to correct v2's ordering mistakes. Setting rerank_pool too small (e.g. 5) risks the true best result sitting at fused rank 8 and never even reaching the re-ranker to get properly promoted -- re-ranking can only reorder candidates it's given, it can't rescue documents excluded from its input pool entirely. Setting it too large erodes the whole point of having a cheap retrieval stage in front of an expensive one. 20 (or whatever value is chosen) is a deliberate middle point on that curve, not an arbitrary number.
Problem 4 · Diagnosing a v3 regression that v2 didn't have

A team ships v3 and finds that for one specific query, the CORRECT document, which v2 ranked #2, is completely absent from v3's final top-10 output. v1 and v2 both had it in their top 3. What's the most likely explanation, using section 2's pipeline structure?

Show solution
The most likely explanation is a rerank_pool cutoff problem, not a cross-encoder scoring error. Look at search_v3's structure: it calls search_v2 with top_k=rerank_pool (e.g. 20) BEFORE re-ranking even begins -- if the correct document happened to fall just outside that initial rerank_pool cutoff in v2's fused ranking for THIS query (even though it was described as ranking #2 in a different, presumably larger, top-k view), the re-ranker never even sees it as a candidate to score, and no amount of cross-encoder accuracy can promote a document that was never in its input set. More precisely, re-read the given scenario: if v2's own top-10 output had it at #2, and rerank_pool is set to something >= 10 (which it should be, since the final top_k it needs to output is itself 10), this specific failure mode wouldn't apply -- so the real diagnostic question is confirming rerank_pool's actual configured value versus top_k, and checking whether rerank_pool was accidentally set smaller than top_k (a configuration bug: re-ranking a POOL smaller than the number of results the caller ultimately wants returned structurally guarantees some final-output slots get filled by whatever v2 candidates happened to survive, even ones the cross-encoder never got a chance to evaluate against the correct document). The general lesson: a wrapped pipeline (v3 wraps v2 wraps v1) can fail at any stage's BOUNDARY -- the interface between stages (how many candidates pass from one to the next) is often where a subtle regression actually lives, not necessarily inside any one stage's own scoring logic.
Problem 5 · Choosing which version to ship for a given latency budget

A product has a hard 50ms retrieval budget. v1 takes ~8ms, v2 takes ~15ms, v3 takes ~140ms (cross-encoder inference dominates). The product handles a mix of exact-code lookup queries and natural-language paraphrase queries. What would you ship, and what would you tell the team about the trade-off?

Show solution
v3 is disqualified outright -- 140ms blows the 50ms budget by nearly 3x, and re-ranking's cost (section 2's table: "expensive per pair, bounded only by pool size") doesn't have an easy way to shrink further without gutting rerank_pool so small it stops being useful (Problem 3's trade-off). This isn't a "tune it a little" situation, it's a hard disqualification given this specific budget. Between v1 and v2: v2 (~15ms) still comfortably fits the 50ms budget, and given the product explicitly handles BOTH exact-code lookups (where v1's dense-only search is known to sometimes miss exact matches, per section 1's framing) AND natural-language paraphrase queries (where BM25 alone would struggle), v2's hybrid fusion directly addresses the actual query mix described, at a small (~7ms) cost increase over v1. Ship v2. What to tell the team: the choice not to ship v3 isn't "re-ranking is bad" -- it's that re-ranking's cost shape (per-pair, not amortizable) makes it a poor fit for a HARD real-time latency budget specifically, regardless of quality gains. If ranking QUALITY for this product later proves insufficient with v2 alone, the honest paths forward are: loosening the latency budget for this specific query type, re-ranking asynchronously and only for a slower "more results" follow-up UI action rather than the initial response, or using a smaller/faster re-ranker model -- not silently shipping v3 and hoping 140ms goes unnoticed.
