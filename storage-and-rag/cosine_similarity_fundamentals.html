01 — Two vectors, one number describing how alike they point

Cosine similarity, the actual arithmetic

Start here, before any code. Imagine two people pointing flashlights into a dark room. If both flashlights point in almost exactly the same direction, the beams overlap almost entirely — very similar. If one points north and the other points due south, the beams share nothing — completely dissimilar. It doesn't matter whether one flashlight is a small keychain light and the other is a massive spotlight (different "strengths," i.e. different magnitudes) — what cosine similarity measures is purely the ANGLE between the two beams, not how bright either one is. That's the entire idea: cosine similarity ignores vector length and measures only direction.

Concretely, for two vectors a and b: compute their dot product (multiply each corresponding pair of components and sum the results), then divide by the product of their magnitudes (each vector's own length, computed via the Pythagorean-style square-root-of-sum-of-squares). Dividing by the magnitudes is exactly what removes "how long is this vector" from the answer, leaving only "which way does it point."

import numpy as np def cosine_similarity(a, b): dot = np.dot(a, b) # sum of elementwise products mag_a = np.linalg.norm(a) # sqrt(sum(a_i^2)) mag_b = np.linalg.norm(b) # sqrt(sum(b_i^2)) return dot / (mag_a * mag_b) a = np.array([1.0, 2.0, 0.0]) b = np.array([2.0, 4.0, 0.0]) # same direction as a, just longer print(cosine_similarity(a, b)) 1.0 # identical direction -> perfect similarity, despite different magnitude

The result ranges from -1 (pointing in exactly opposite directions) through 0 (perpendicular — no directional relationship at all) to 1 (pointing in exactly the same direction). For text/document embeddings specifically, values cluster mostly in the 0-to-1 range in practice, since embedding models rarely produce genuinely opposite-pointing vectors for real text — but the formula itself supports the full -1-to-1 range.

Interview-ready definition: cosine similarity between two vectors is their dot product divided by the product of their magnitudes — equivalently, the cosine of the angle between them. It measures directional similarity only, deliberately ignoring each vector's length/magnitude, which makes it the standard similarity metric for embeddings, where a document's embedding "direction" carries the semantic meaning and its magnitude is often just an artifact of the encoding process rather than a meaningful signal.

Interview-ready definition: brute-force nearest-neighbor search computes the exact similarity score (here, cosine similarity) between the query vector and EVERY vector in the dataset, with no shortcuts or precomputed structure — then sorts all scores and takes the top-k. It's the ground-truth baseline every approximate method (HNSW, IVF) is measured against for recall, precisely because it can never miss the true top-k results — it examines everything.
03 — The exact arithmetic that makes this a real bottleneck

Why brute force breaks at real scale — worked out in full

Start here, before the numbers. The 6-vector demo above ran instantly — of course it did, cosine similarity against 6 vectors is nothing. The entire point of this section is to take the SAME arithmetic and actually multiply it out at a scale a real production vector database would face, so the bottleneck isn't just asserted, it's derived.

Each cosine similarity computation between a query and one stored vector of dimension d costs roughly O(d) work: d multiplications for the dot product, plus d more for each magnitude (magnitudes can be precomputed once at insert time and cached, but the dot product itself is unavoidable per query). Comparing a query against n stored vectors costs O(n·d) total — and that's for ONE query.

# A real, common embedding size: 768 dimensions (e.g. many sentence-transformer models) n = 10_000_000 # 10 million stored vectors d = 768 # embedding dimensionality multiply_adds_per_query = n * d print(f"{multiply_adds_per_query:,} multiply-adds, per single query") 7,680,000,000 multiply-adds, per single query # ~7.68 BILLION multiply-add operations -- for ONE query against this dataset. # And this entire computation repeats again, from scratch, for every new query.

7.68 billion multiply-adds per query is not a rounding error — even on modern hardware capable of billions of floating-point operations per second, doing this for every single query, especially under real production query volume (hundreds or thousands of queries per second), means the CPU/GPU work scales linearly with BOTH the size of the dataset and the number of queries. Double the dataset, double the cost per query. Double the query volume, double the total cost again. Brute force has no mechanism to avoid comparing against vectors that are obviously going to be irrelevant — it treats every stored vector as equally worth checking, every time.

n = 10, d = 768 → 7,680 multiply-adds

Small dataset (this lab's demo, n=6)

Brute force is not just acceptable, it's the RIGHT choice — building any index at all would be pure overhead for a dataset this small. The 6-vector demo above never needs anything smarter.

10M+ vectors, production query volume

7.68 billion multiply-adds per query, repeated per query, at real QPS, is the exact wall that motivates tomorrow's lab: an index structure (HNSW) that examines a small, sublinear fraction of the dataset instead of literally all of it.

Interview-ready definition: brute-force nearest-neighbor search has query-time complexity O(n·d), where n is the number of stored vectors and d is the embedding dimensionality — every query re-examines the entire dataset, with cost growing linearly in both dataset size and query volume. At realistic production scale (millions to billions of vectors, hundreds/thousands of embedding dimensions, sustained query traffic), this becomes computationally impractical for interactive latency, which is precisely the motivation for approximate nearest-neighbor index structures like HNSW and IVF — this week's actual engine build.

Problem 1 · Computing cosine similarity by hand

Compute the cosine similarity between a = [3, 0] and b = [0, 4] by hand, showing the dot product and both magnitudes. What does the result tell you geometrically?

Show solution
Dot product: (3*0) + (0*4) = 0. Magnitude of a: sqrt(3^2 + 0^2) = sqrt(9) = 3. Magnitude of b: sqrt(0^2 + 4^2) = sqrt(16) = 4. Cosine similarity: 0 / (3*4) = 0. Geometrically, a points straight along the x-axis and b points straight along the y-axis -- they are perpendicular (90 degrees apart). A cosine similarity of exactly 0 corresponds to a 90-degree angle, confirming this directly: perpendicular vectors share no directional overlap at all, regardless of their individual lengths (3 and 4 here).
Problem 2 · Why magnitude gets divided out, concretely

Vector a = [1, 1] and vector c = [10, 10]. Compute cosine similarity(a, c). Then explain in one sentence why a much "louder"/larger-magnitude embedding doesn't automatically win in cosine similarity ranking the way it might in a raw dot-product ranking.

Show solution
Dot product: (1*10)+(1*10) = 20. Magnitude of a: sqrt(2) ≈ 1.414. Magnitude of c: sqrt(200) ≈ 14.14. Cosine similarity: 20 / (1.414 * 14.14) ≈ 20/20 = 1.0 -- identical direction, perfect similarity, despite c being 10x "longer" than a in every component. The reason: dividing by the product of both magnitudes exactly cancels out any pure scaling of either vector. If you used raw dot product instead (no division), a vector with a much larger magnitude would tend to produce a larger dot product against almost anything, purely because its components are bigger numbers -- which would bias "similarity" toward large-magnitude vectors regardless of whether they actually point in a semantically similar direction. Cosine similarity's normalization step is specifically what prevents magnitude from masquerading as relevance.
Problem 3 · Working out the O(n·d) cost for a different dataset size

A dataset has 500,000 vectors at 1536 dimensions (OpenAI's text-embedding-3-large size). How many multiply-adds does one brute-force query cost? If the service handles 200 queries per second, how many total multiply-adds per second is that?

Show solution
Per query: n * d = 500,000 * 1,536 = 768,000,000 (768 million) multiply-adds. At 200 queries/second: 768,000,000 * 200 = 153,600,000,000 (about 153.6 billion) multiply-adds per second, sustained. This is a genuinely large, continuous compute load -- and it scales linearly with BOTH numbers independently: doubling either the dataset size or the query rate doubles this total, with no way to "cache" your way out of it the way you might cache a repeated identical query, because in practice most queries are at least somewhat different from each other.
Problem 4 · Diagnosing when brute force is actually still the right call

A team has 50,000 vectors, gets about 2 queries per second, and query latency isn't especially latency-sensitive (a 200ms response is fine). Should they build an HNSW index, or is brute force still the right choice? Justify using this lab's O(n·d) reasoning.

Show solution
At n=50,000 and, say, d=768: 50,000 * 768 ≈ 38.4 million multiply-adds per query -- trivial for modern hardware, almost certainly well under a few milliseconds even unoptimized, comfortably inside a 200ms budget. At only 2 QPS, the sustained load is tiny (under 100 million multiply-adds per second total). Brute force is very plausibly still the right call here. Building an approximate index like HNSW isn't free -- it costs engineering complexity, build time, memory for the graph structure, and introduces the recall trade-off from this week's later labs (section 3 of the HNSW lab: approximate results, not guaranteed-exact ones). When brute force already comfortably meets the latency and throughput requirements, as it does here, adding an ANN index trades away guaranteed-correct results and adds real system complexity for a performance benefit the workload doesn't actually need. This is a genuine engineering judgment call: "can brute force handle this" should be checked BEFORE reaching for an index, not skipped in favor of always building the more sophisticated option.
Problem 5 · Precomputing magnitudes as a partial optimization

Section 3 notes stored-vector magnitudes can be precomputed once at insert time and cached. Does this change the O(n·d) complexity of brute-force search? What part of the per-query cost does it actually remove, and what part remains untouched?

Show solution
No, it does not change the asymptotic O(n·d) complexity -- it's a real, worthwhile constant-factor optimization, not a change in scaling behavior. What it removes: recomputing each STORED vector's magnitude (a sqrt-of-sum-of-squares over d dimensions) on every single query -- without caching, that's redundant O(d) work per stored vector per query, even though a stored vector's magnitude never changes after it's embedded. Precomputing it once at insert time and storing it alongside the vector means each query only needs to compute the QUERY vector's own magnitude once (O(d), a single one-time cost per query, not per stored vector) plus its magnitude for the query itself. What remains completely untouched: the dot product between the query and EVERY stored vector, which is still O(d) work per stored vector, and there are still n stored vectors to compare against. That dot product cannot be precomputed ahead of time because it depends on BOTH the query and the stored vector together -- it doesn't exist until a specific query arrives. So the per-query cost drops from roughly 3 passes of O(d) work per stored vector (dot product + two magnitudes) to roughly 1 pass of O(d) work per stored vector (dot product only, plus one query-magnitude computation done once) -- a real, meaningful constant-factor speedup, typically close to 2-3x, but the total cost is still O(n·d), still linear in dataset size, and still the bottleneck this week's index structures exist to actually break out of.
