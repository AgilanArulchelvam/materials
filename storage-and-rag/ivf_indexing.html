IVF's whole trick: sort vectors into neighborhoods first, then only knock on nearby doors.

An Inverted File index partitions every stored vector into k clusters ahead of time, each with a centroid summarizing where it sits. At query time, instead of comparing against every vector in the dataset, IVF first finds the few closest cluster centroids to the query, then only searches the vectors INSIDE those clusters — skipping the rest of the dataset entirely. This lab animates that skip directly, and compares IVF against HNSW on the trade-offs that actually decide which one to reach for.

01 — Sort first, search later

Inverted File index: partitioning into clusters ahead of time

Start here, before any math. Imagine organizing a huge warehouse of loose items by first walking through and grouping everything into a handful of labeled bins — "kitchen stuff," "office stuff," "sports stuff" — based on which bin each item most resembles. This grouping happens ONCE, upfront, before anyone ever comes looking for anything. Later, when someone asks "where's the closest thing to a tennis racket," you don't search the whole warehouse — you look at which BIN "tennis racket" would belong to, walk straight to that bin (and maybe one or two neighboring ones, in case the ideal item landed in an adjacent bin), and only look through what's physically inside those bins.

An Inverted File (IVF) index does exactly this to a set of vectors. Before any queries run, a clustering algorithm (typically k-means) partitions all n stored vectors into k clusters, where every vector is assigned to whichever cluster's centroid (the mean position of all vectors currently in that cluster) it's closest to. This is an iterative process — assign vectors to the nearest centroid, recompute each centroid as the average of its assigned vectors, reassign, repeat — until the assignments stabilize. The result is a set of k centroids, each one a single vector summarizing "roughly where this whole cluster of vectors sits" in the embedding space, plus a lookup structure ("inverted file" — hence the name) mapping each cluster to the list of vector IDs that belong to it.

# Roughly what IVF's build step does (k-means clustering) def build_ivf_index(vectors, k): centroids = initialize_random_centroids(vectors, k) for iteration in range(20): # until assignments stabilize clusters = {i: [] for i in range(k)} for v in vectors: nearest = argmin(distance(v, c) for c in centroids) clusters[nearest].append(v) centroids = [mean(cluster) for cluster in clusters.values()] # each cluster's vector IDs are stored in an "inverted list" keyed by cluster id -- # this upfront training step is the cost IVF pays before it can ever answer a query return centroids, clusters
Interview-ready definition: an IVF (Inverted File) index partitions all stored vectors into k clusters via k-means clustering, computed once upfront as a training/build step, producing k centroids (each the mean position of its cluster's vectors) and an inverted list mapping each cluster to its member vector IDs. This upfront partitioning is what lets query time skip most of the dataset: rather than comparing the query against every vector, IVF only needs to compare it against the k centroids first, then search within a small number of the closest clusters.
02 — Skipping most of the dataset, on purpose

Searching nearby clusters vs the whole dataset, animated

Start here, before the demo. Back at the warehouse: someone asks for the closest match to "tennis racket." You don't walk to the "kitchen stuff" bin at all — you already know, just from the query itself, which one or two bins are even plausible candidates, and every other bin gets skipped without a second glance. IVF search works identically: given a query vector, first compute its distance to all k centroids (a cheap comparison — there are only k of them, far fewer than n total vectors), then pick the nprobe closest centroids (a tunable parameter, usually a small number like 1-20), and search ONLY the vectors belonging to those nprobe clusters — every vector in every other cluster is skipped entirely, never compared against the query at all.

Notice exactly what got skipped: two full clusters' worth of vectors were never compared against the query at all — not "compared and rejected," but never examined in the first place. This is the entire IVF speedup: instead of n distance comparisons (brute force) or a graph walk (HNSW), IVF pays k centroid comparisons plus (n/k × nprobe) vector comparisons within the selected clusters — dramatically less than n when k and nprobe are chosen well, since only a small fraction of the total clusters get searched.

The boundary problem: because clusters are drawn as hard regions with a centroid at the center, a query vector sitting right near the EDGE of its own cluster's boundary — closer, in reality, to a neighboring cluster's member vector than to some vectors deep inside its own cluster — can miss its true nearest neighbor if that neighbor's cluster isn't among the nprobe closest centroids searched. This is IVF's core recall risk: a true nearest neighbor sitting just across a cluster boundary from the query gets skipped entirely, not almost-found — it's structurally invisible to a search that never looks inside that cluster at all. Raising nprobe (searching more clusters per query) directly reduces this risk, at the direct cost of more vector comparisons and slower queries.
Interview-ready definition: IVF search computes the query's distance to all k cluster centroids, selects the nprobe closest centroids, and searches only the vectors within those selected clusters, skipping every vector in every unselected cluster entirely. This trades completeness for speed: a true nearest neighbor located near a cluster boundary, in a cluster that wasn't among the nprobe selected, can be missed structurally — not approximately found, but never examined — which is IVF's specific mechanism for approximate (not exact) results, distinct from HNSW's greedy-walk-can-get-stuck mechanism for the same approximation trade-off.
03 — Two different approximation strategies, two different trade-off shapes

IVF vs HNSW: when each is preferred

Start here, before the table. Both IVF and HNSW answer the same underlying question — "find the approximate nearest neighbors of this query vector, fast" — but they get there via genuinely different mechanisms, and that difference in mechanism is exactly what drives when each is the better real-world choice. IVF's mechanism is "sort everything into neighborhoods upfront, then only check the plausible neighborhoods." HNSW's mechanism is "build a navigable graph and walk toward the answer, layer by layer." Neither is universally better — they trade different resources.

IVF — simpler, more memory-efficient

Requires an upfront training/clustering step (k-means) before the index is usable at all — you can't incrementally build it one vector at a time the way HNSW allows. Storage is comparatively lean: just the vectors, their cluster assignment, and k centroids — no per-vector graph edges to store. Can miss neighbors sitting near a cluster boundary, as shown above.

HNSW — no training step, generally better recall

Vectors can be inserted incrementally with no separate upfront clustering phase — each insert just assigns layers and wires up graph edges immediately. Generally achieves better recall than IVF at comparable speed, but is more memory-hungry: every node stores explicit edges to its neighbors across multiple layers, which costs more than IVF's flat cluster-assignment-plus-centroids structure.

In practice, many production vector databases (FAISS, Milvus) offer BOTH, and some even combine them — IVF for the coarse first-pass partitioning, with a small HNSW graph built within each cluster (or over the centroids themselves) for finer navigation. This is a direct acknowledgment that the two techniques' strengths are complementary rather than strictly competing: IVF's cheap coarse filtering plus HNSW's better fine-grained recall, layered together.

Interview-ready definition: IVF and HNSW are both approximate-nearest-neighbor techniques trading exactness for speed, but via different mechanisms with different resource profiles: IVF requires an upfront k-means training step and trades some recall (missing near-boundary neighbors) for a simpler, more memory-efficient structure and cheap incremental query cost via the nprobe knob; HNSW requires no training step, generally achieves better recall via its layered graph, but at the cost of higher memory usage from storing explicit multi-layer graph edges per vector. The choice between them is a real engineering trade-off between memory budget, whether vectors arrive incrementally or in a batch, and how much recall the workload actually needs — not a strictly-better-or-worse comparison.

Problem 1 · Tracing the boundary-miss scenario concretely

A query vector's true nearest neighbor sits in cluster C, very close to the boundary it shares with cluster D. The query itself lands geometrically just inside cluster D's region. With nprobe=1, does the search find that true nearest neighbor? Walk through why or why not.

Show solution
No, it does not find it, and this is exactly the structural boundary problem section 2 describes. With nprobe=1, the search computes the query's distance to all k centroids, finds that cluster D's centroid is closest (since the query landed inside D's region), and searches ONLY the vectors physically assigned to cluster D. The true nearest neighbor lives in cluster C -- a different cluster, assigned there because IT was closer to C's centroid than D's centroid during the k-means build step, even though geometrically it happens to sit very close to the query (which is on the other side of the boundary). Since only cluster D gets searched, cluster C's vectors -- including this true nearest neighbor -- are never examined at all. The search returns whatever the closest vector WITHIN cluster D happens to be, which is provably not the global true nearest neighbor in this scenario. Raising nprobe to 2 (searching the 2 nearest centroids instead of just 1) would very likely fix this specific case, since cluster C's centroid is presumably the second-closest to a query sitting right on the C/D boundary -- which is exactly why nprobe is the knob used to trade query cost for recall in section 3's comparison table.
Problem 2 · Choosing nprobe and k under stated constraints

A team has 50 million vectors and needs sub-50ms query latency, but their recall requirements are relatively loose (returning one of the top-20 nearest neighbors is acceptable, not just the single closest). Would you lean toward a smaller or larger nprobe, and a smaller or larger k (cluster count)? Justify both.

Show solution
nprobe: lean SMALLER. Loose recall requirements (top-20 acceptable, not just the single true nearest) mean the team can tolerate more boundary misses than a strict top-1 requirement would allow -- a smaller nprobe searches fewer clusters per query, which directly reduces query latency, and the loosened recall bar is exactly the condition under which that trade is worth making. k (cluster count): lean LARGER, given 50 million vectors specifically. More clusters means each individual cluster holds fewer vectors on average (roughly n/k per cluster), so searching a FIXED nprobe number of clusters touches fewer total vectors as k grows -- which is what keeps per-query latency low at large n. The trade-off is that a much larger k also means a more expensive k-means training step at build time (more centroids to converge) and slightly more centroid-comparison overhead per query (comparing against k centroids instead of a smaller k) -- but at 50M vectors with a hard 50ms latency ceiling, keeping each cluster's vector count manageable via a larger k is usually the dominant consideration, since the centroid-comparison cost (proportional to k) is far cheaper than the in-cluster vector-comparison cost (proportional to n/k × nprobe) at this scale.
Problem 3 · Choosing between IVF and HNSW for a stated scenario

A startup is running on a memory-constrained single server, ingests new document embeddings continuously throughout the day (not in periodic batches), and cares more about not running out of memory than about squeezing out the last few percentage points of recall. Which index would you recommend, and what specifically about their constraints drives the choice?

Show solution
Lean toward IVF, though with a real caveat about the continuous- ingestion constraint. The memory-constrained, recall-is-not-critical profile matches IVF's strengths directly from section 3's table: lower memory footprint (no per-vector graph edges to store) is exactly what a memory-constrained single server needs, and "don't need the last few percent of recall" is exactly the condition under which IVF's boundary- miss weakness is an acceptable cost. The caveat: IVF's upfront k-means training step is normally NOT naturally incremental, which conflicts with "ingests new embeddings continuously throughout the day." In practice this is handled by periodically re-training/re-clustering the index in the background (e.g. nightly, or whenever enough new vectors have accumulated to risk the existing centroids becoming stale relative to the new data's distribution), while new vectors are assigned to their nearest EXISTING centroid in the interim without waiting for a full re-cluster. This is a real operational cost IVF imposes that HNSW's naturally-incremental inserts avoid -- naming this trade-off explicitly (not just picking IVF and stopping) is what separates a complete answer from a partial one here.
Problem 4 · Explaining why IVF's centroid comparison is cheap

Explain concretely why comparing a query against all k centroids is cheap even when k is reasonably large (say, k=10,000 for a 50-million-vector dataset), and why this step doesn't reintroduce the same cost problem IVF is trying to avoid.

Show solution
Comparing against k=10,000 centroids means exactly 10,000 distance computations -- a real cost, but a FIXED, small cost that does not scale with the total dataset size (50 million vectors) at all, only with k, which the index designer chooses independently of n. 10,000 distance comparisons is trivially fast on modern hardware (a small fraction of a millisecond for typical embedding dimensions), and critically, it stays exactly that cheap even if the dataset grows from 50 million to 500 million vectors -- as long as k doesn't also grow, the centroid- comparison step's cost is flat. This does NOT reintroduce brute-force's cost problem because brute-force cost scales with n (every stored vector gets compared), while the centroid-comparison step scales with k, a number chosen to be far smaller than n specifically so this step stays cheap regardless of how large the underlying dataset becomes. The actual work that scales with n happens only within the nprobe selected clusters (roughly n/k vectors each), which is the whole point of clustering in the first place: it converts one expensive O(n) comparison into one cheap O(k) comparison plus a cheap O(n/k × nprobe) comparison, and as long as k is chosen well relative to n, that sum is dramatically smaller than n.
Problem 5 · Distinguishing IVF's failure mode from HNSW's

Both IVF and HNSW can return a wrong (non-true-nearest) answer. Explain, precisely, the DIFFERENT mechanism by which each one fails — don't just say "both are approximate."

Show solution
IVF's failure mechanism is a PARTITIONING failure: the true nearest neighbor exists somewhere in the dataset, but it was assigned to a cluster that the query's nprobe-selected centroids didn't include, so it is structurally never examined at all during that query -- not approximately compared and rejected, but completely skipped, as walked through in Problem 1. The failure is about WHICH REGION of the vector space gets searched at all. HNSW's failure mechanism is a LOCAL-OPTIMUM failure in the greedy walk: every vector IS reachable in principle (the graph connects the whole dataset across its layers), but the greedy walk at some layer can converge to a node that looks locally best (no direct neighbor at that layer is closer to the query) even though a globally closer vector exists elsewhere in the graph, reachable only via a path the greedy walk didn't take because it never looks more than one hop ahead. The failure is about the WALK STRATEGY getting stuck, not about entire regions being excluded from consideration the way IVF's unsearched clusters are. Concretely: IVF's failure is "we never looked there at all"; HNSW's failure is "we looked, but our step-by-step local decisions led us somewhere merely good instead of globally best." Both produce the same observable symptom (a non-optimal result), but the underlying reason -- and therefore the fix -- differs: IVF's fix is raising nprobe (search more regions); HNSW's fix is raising ef_search or improving graph connectivity (give the walk more chances to escape a local optimum).
