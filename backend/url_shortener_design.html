A monotonic counter and base62 sidestep hash collisions entirely — a true hash-based scheme cannot.

Everything about a URL shortener is a lookup problem wearing an encoding costume: given a long URL, produce a short, unique code; given that code, get the long URL back, fast, forever. This lab builds the base62 encoding scheme by hand with real arithmetic, designs the read-heavy storage layer around it, and works through exactly why counter-based IDs avoid the collision-handling problem that hash-based short codes can't avoid.

01 — Turning a big number into a short string

The hashing/encoding scheme for short codes

Start here, before any math. Think about how a car odometer works, except instead of only 10 digits (0-9) per wheel, imagine each wheel had 62 possible symbols: the ten digits 0-9, the 26 lowercase letters, and the 26 uppercase letters. With 62 symbols per "digit" instead of 10, you can represent much larger numbers in far fewer characters — exactly the property you want for a short code that still needs to be unique across potentially billions of URLs.

Base62 encoding converts an ordinary base-10 integer (like an auto-incrementing database ID) into a string using that 62-character alphabet, via the same repeated-division-and-remainder process you'd use to convert to any other base by hand.

ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ" # 62 chars def encode_base62(n: int) -> str: if n == 0: return ALPHABET[0] digits = [] while n > 0: n, remainder = divmod(n, 62) digits.append(ALPHABET[remainder]) return "".join(reversed(digits))
WATCH THE ACTUAL DIVISION/REMAINDER STEPS
Interview-ready definition: base62 encoding represents an integer using a 62-symbol alphabet (0-9, a-z, A-Z) instead of the usual 10, by repeatedly dividing the number by 62 and recording each remainder as a symbol, then reading the remainders in reverse order — the same positional-numeral-system logic as converting to binary or hex, just with a larger alphabet. Because 62^6 already exceeds 56 billion, a 6-7 character base62 code comfortably covers a URL shortener's entire ID space for years of sustained growth.
02 — A workload that is almost entirely reads

Storage & lookup design

Start here, before any schema. A phonebook is written once per entry and read constantly, by many different people, for a long time afterward — nobody re-edits a listing every time someone looks up a number. A URL shortener has exactly that shape: each short code is written ONCE (when created) and then read an enormous number of times afterward, every time someone clicks the short link. This "write once, read a million times" pattern is the single most important fact shaping the storage design.

The core schema is deliberately simple: a single key-value mapping, short_code → long_url, indexed on short_code (the primary lookup key, since every redirect request looks up by code, never the reverse). Because the workload is so overwhelmingly read-heavy and each lookup is a single-key point read (no joins, no range scans), this maps extremely well onto a cache in front of a key-value or relational store: a redirect service checks a fast in-memory cache (e.g. Redis) first, and only falls through to the durable backing store on a cache miss.

Why this matters: popular short links (a viral tweet's link, a marketing campaign URL) get looked up disproportionately often — a classic hot-key access pattern that caching handles gracefully (the same handful of keys stay warm in the cache, absorbing nearly all the read traffic) while a naive "hit the database on every request" design would concentrate enormous, avoidable load on the exact same few rows.
Interview-ready definition: a URL shortener's storage layer is a simple key-value schema (short_code → long_url, plus metadata like creation/expiry timestamps) optimized around an extremely read-heavy access pattern — each mapping is written once and read repeatedly. This makes it a textbook fit for a read-through cache (checking a fast in-memory store first, falling back to a durable database on a miss), since the workload's read:write ratio is enormous and individual lookups are simple single-key point reads with no need for joins or range queries.
03 — Why counters sidestep a problem that hashing creates

Handling collisions and scale

Start here, before comparing approaches. Imagine two different ways to assign locker numbers at a gym: (1) a manager keeps a running tally and hands out locker 1, then 2, then 3, guaranteeing every number is used exactly once, by construction — or (2) each member's locker number is computed by hashing their name, and occasionally two different people's names hash to the same number, requiring an awkward "sorry, try a different locker" negotiation. Both eventually assign unique lockers, but only one of them can NEVER produce a duplicate in the first place.

Counter + base62 (this design)

An auto-incrementing ID is guaranteed unique by the database itself (or a distributed ID generator like Snowflake, for multi-node setups). Base62-encoding a unique number ALWAYS produces a unique string — encoding is a deterministic, reversible bijection, not a lossy hash. Collisions are structurally impossible.

True hash-based (e.g. MD5/SHA of the URL, truncated)

Hashing the long URL and truncating to a few characters CAN produce the same short code for two different long URLs (a collision), because hashing is a many-to-one mapping — you must detect this (check if the code is already taken by a different URL) and handle it (rehash with a salt, append a disambiguator, retry) every single time.

The scale wrinkle: a single auto-incrementing counter is easy on one database instance, but becomes a coordination bottleneck across multiple write nodes. The standard fix is to pre-allocate non-overlapping ID ranges to each node (node A gets IDs 1-1,000,000, node B gets 1,000,001-2,000,000, etc.) or use a structured distributed ID scheme (like Twitter's Snowflake) that embeds a node identifier directly into the generated ID — both preserve "no two nodes ever generate the same ID" without needing a single shared counter that all writes must serialize through.
Interview-ready definition: counter-based short code generation sidesteps collision handling entirely because it relies on a uniqueness guarantee (an auto-incrementing or distributed-unique ID) BEFORE encoding, and base62 encoding is a deterministic bijection — every distinct input integer maps to a distinct output string, with no possibility of two different inputs colliding on the same output. True hash-based schemes (hashing the URL itself and truncating the result) have no such guarantee, since hashing is fundamentally a many-to-one mapping compressed into a fixed-width output, making some collision rate mathematically inevitable at scale and requiring explicit detection-and-retry logic on every write.

Problem 2 · Capacity planning

Roughly how many unique short codes can a 6-character base62 string represent? Is that enough for a service issuing 10 million new short links per day for 10 years?

Show solution
62^6 = approximately 56.8 billion unique 6-character codes. 10 million/day * 365 days * 10 years = about 36.5 billion links over that period. 56.8 billion comfortably covers this with room to spare (roughly 1.5x headroom), though a real design would likely still plan for 7 characters (62^7 ~= 3.5 trillion) for a larger safety margin as growth assumptions change, since resizing an established encoding scheme later is disruptive.
Problem 3 · Why hashing needs collision handling and counters don't

Explain, in terms of the mathematical properties of the two approaches, precisely why a counter+base62 scheme can never produce a collision, while a truncated-hash scheme fundamentally can.

Show solution
Counter + base62: base62 encoding is a BIJECTION between integers and base62 strings up to a given length -- every distinct integer maps to exactly one distinct string, and no two distinct integers ever map to the same string. Since the ID itself is already guaranteed unique (by the database's auto-increment or a distributed unique-ID generator) BEFORE encoding, and the encoding step introduces no new collisions, the final short code is guaranteed unique by construction. Truncated hash: a hash function maps an effectively unlimited input space (all possible URLs) down to a FIXED, much smaller output space (e.g. 6 base62 characters = ~56.8 billion possible outputs). By the pigeonhole principle, once you have more distinct URLs than possible output codes, at least two different URLs MUST map to the same code -- and even before that theoretical limit, hash collisions can occur well earlier due to how hash functions distribute outputs. This is an inherent property of compressing an unbounded space into a bounded one, not an implementation bug, which is exactly why collision detection and retry logic is mandatory for any hash-based scheme but structurally unnecessary for a counter-based one.
Problem 4 · Multi-node ID generation

A single-database auto-increment counter works fine at low scale. Why does this become a problem once the service needs multiple write-capable database nodes, and name one concrete fix.

Show solution
A single shared auto-increment counter requires every write, regardless of which node received the request, to coordinate through that one counter to get the next ID -- this becomes a serialization bottleneck and a single point of contention (and failure) as write volume grows across multiple nodes, defeating much of the point of having multiple write nodes in the first place. Fix: pre-allocate disjoint ID ranges to each node (node A issues IDs from 1-1,000,000, node B from 1,000,001-2,000,000, and so on, each node incrementing independently within its own range), or use a structured distributed ID scheme like Snowflake, which encodes a timestamp, a node identifier, and a per-node sequence number directly into each generated ID -- guaranteeing global uniqueness without any node needing to coordinate with any other node on every single ID generation.
Problem 5 · Caching a read-heavy workload

Explain why a URL shortener's access pattern is an especially good fit for caching, using the concept of read:write ratio, and describe what happens on a cache miss.

Show solution
Each short_code -> long_url mapping is written exactly ONCE at creation time, but can be read an essentially unbounded number of times afterward -- every single click on that short link is another read of the exact same row. This gives an extremely lopsided read:write ratio (often many thousands or millions of reads per write), which is precisely the condition under which a cache pays off enormously: a small, frequently- accessed subset of "hot" short codes can live in fast in-memory cache and absorb the vast majority of traffic, while the durable backing store handles the comparatively rare writes and occasional cache misses. On a cache miss (the requested short_code isn't currently cached, perhaps because it's rarely used or was just evicted), the redirect service falls through to the durable backing store, looks up the mapping there, returns the redirect to the client, AND typically writes the result back into the cache so the next request for that same code is a cache hit.
