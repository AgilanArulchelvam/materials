01 — Every one of these bugs passed its own lab's unit tests

Why seam bugs are a different animal than logic bugs

Start here, before opening a debugger. Think about four musicians who each nailed their individual part in separate practice rooms, then play together for the first time and it falls apart — not because anyone forgot their notes, but because the TIMING between parts, never exercised until this moment, was wrong. Nobody's part has a bug in isolation. The orchestrator's routing logic works. The hybrid search tool's fusion math works. The dashboard's rendering works. capstone_integration_testing.html exists specifically because none of that proves the pieces agree with each other about ORDER, SHAPE, and WHO IS RESPONSIBLE FOR WHAT — and this week's "fix integration issues" checklist item is what happens once that suite starts actually surfacing where they don't.

Three categories cover almost every seam bug this capstone can produce, and each one below is built around a specific real seam from Weeks 1-2's labs:

CategoryThe seamWhy unit tests miss it

The pattern to internalize: every seam bug in this lab is a case where two components each did EXACTLY what their own author intended, and the bug lives entirely in the gap between those two correct-in-isolation intentions. Debugging a seam bug is therefore never "find the broken function" — it's "find the two components' disagreeing ASSUMPTION about the other," which is why the isolate-root-cause step below always starts by writing down each side's assumption explicitly, not by single-stepping through one component's code.

Bug 1 — the dashboard reads state mid-write

RACE CONDITION
Orchestrator worker A
— writes run:abc123 →
Redis
← reads run:abc123 —
Dashboard poller

How you'd actually notice it

capstone_integration_testing.html's own suite would not catch this directly — its test_full_orchestrated_run_produces_reply_and_records test runs one request start to finish and only checks the FINAL state, after everything settled. What surfaces this bug is production-shaped: the dashboard occasionally shows a run's status flipping from "running" to "done" and back to "running" within the same few seconds, or shows a turns list that's shorter than the reply the user actually received — a reader that's polling faster than the writer's read-modify-write cycle can complete. The tell in the logs: two RunStateStore.save() calls for the SAME run_id land within milliseconds of each other, and the dashboard's read timestamp falls between them.

How you'd isolate root cause

This is exactly the race capstone_orchestrator_integration.html's own practice problem 2 already named for two orchestrator workers racing on the SAME write — the dashboard reintroduces the identical hazard from the READ side. Confirm it by adding a short, deliberate delay inside RunStateStore.save() in a test environment and firing a dashboard poll during that window — if the poll observes a state object with some fields updated and others stale (an impossible intermediate state that was never actually saved as a whole), that confirms the reader is seeing a write in progress rather than atomic before/after snapshots.

# BEFORE -- the dashboard's poller, reading raw state mid-flight # app/observability/dashboard_feed.py async def get_run_snapshot(run_id: str, store: RunStateStore) -> dict: # reads whatever RunStateStore.load() returns, right now, no matter # WHEN "now" happens to land relative to an in-flight save() call state = await store.load(run_id) return {"run_id": run_id, "status": state["status"], "turns": state["turns"]} # AFTER -- state.save() writes atomically to a NEW key, then flips a # pointer -- readers always see either the fully-old or fully-new # state, never a value drawn from mid-write # app/orchestrator/state.py async def save(self, run_id: str, state: dict) -> None: payload = json.dumps(state) # SET is already atomic at the single-key level in Redis -- the # actual bug was never "SET is non-atomic," it was that the OLD # code let a reader observe a state dict PARTIALLY constructed # in Python before the SET call, if load-mutate-save spanned an # await point. Fixing it means the full new state object is # built BEFORE any I/O, then written in one atomic SET: await self.redis.set(f"run:{run_id}", payload, ex=3600)

The real fix has two parts, and naming both is what separates a strong debugging answer from a lucky one: first, confirm the state object being serialized is fully built in memory before any await — a Python dict mutated across an await point can be read half-updated by an unrelated coroutine on the same event loop, a subtler variant of the classic race even without a second process involved; second, apply capstone_orchestrator_integration.html problem 2's actual fix (a Redis SET NX lock around the full load-modify-save sequence) for the WRITER side, since the reader can only ever be as consistent as the writer's own atomicity guarantee.

Interview-ready definition: a read-side race at a seam is usually a write-side atomicity problem wearing a read-side symptom — before changing the reader, confirm the writer actually produces one atomic transition per logical update; a reader polling a value that's never guaranteed to be a complete, consistent snapshot will always eventually observe a torn state, no matter how the reader itself is written.

Bug 2 — the search tool's shape drifted from what the orchestrator expects

SCHEMA MISMATCH
hybrid_search tool
returns list[dict] with "text" key →
Orchestrator._render_reply()
reads "content" key →
KeyError, swallowed

How you'd actually notice it

This one is sneaky specifically because it doesn't crash loudly — storage-and-rag/capstone_hybrid_search_integration.html section 3's merge step reads each result's ranked content to build the context window, and if that read is inside a broad try/except (common, since a single malformed result shouldn't kill an entire run), a KeyError gets caught, logged at a level nobody's watching, and the orchestrator silently falls back to composing a reply with ZERO retrieved context. The user gets a plausible-sounding but ungrounded answer. What actually surfaces it: capstone_integration_testing.html's empty-search-results test (problem 1 in that lab) would catch a variant of this if extended to assert on REPLY CONTENT, not just status code — but the more direct signal is a spike in a hallucination-rate eval metric (tool_selection_and_hallucination_metrics.html) with no corresponding drop in search-tool error rate, which is the specific fingerprint of "the tool succeeded, but its result was silently unusable downstream."

How you'd isolate root cause

Write down each side's assumption explicitly, per section 1's rule. The search tool's actual MCP response (check the tool's own schema, not the orchestrator's assumption about it) returns each result as {"doc_id": ..., "score": ..., "text": ...}. The orchestrator's merge code, written independently, assumes {"content": ..., "relevance": ...} — plausible-sounding field names that were never actually cross-checked against the tool's real schema, because the orchestrator lab was built and tested against a hand-written mock response, not the real tool's actual output.

# BEFORE -- app/orchestrator/run.py, the merge step, silently # swallowing the mismatch inside a broad except def _render_reply(self, tool_result: dict) -> str: context_chunks = [] for r in tool_result.get("results", []): try: context_chunks.append(r["content"]) # KeyError -- real key is "text" except KeyError: pass # swallowed -- no log, no signal return self._compose(context_chunks) # silently composes from an EMPTY list # AFTER -- match the tool's REAL schema (verified against # storage-and-rag/capstone_hybrid_search_integration.html section 1's # actual return shape, not a hand-written assumption), and fail LOUD # on a genuine mismatch instead of silently degrading def _render_reply(self, tool_result: dict) -> str: context_chunks = [] for r in tool_result.get("results", []): if "text" not in r: logger.error("hybrid_search result missing 'text' key: %r", r) continue # skip THIS result, but LOUDLY, and keep going context_chunks.append(r["text"]) if not context_chunks and tool_result.get("results"): # results existed but NONE were usable -- structurally different # from "search legitimately found nothing," and should be # reported as its own eval_span attribute (schema_mismatch) logger.error("all hybrid_search results were unusable -- schema mismatch suspected") return self._compose(context_chunks)

The durable fix is not just correcting the key name — it's removing the SILENT swallow. A schema mismatch between two components should be as loud as possible the first time it happens, not quietly degrade into a worse but still-200-status-code answer. The best long-term fix, worth naming as the actual engineering answer beyond the patch: define the tool's response shape as a shared Pydantic model imported by BOTH the tool handler and the orchestrator, so a real field rename becomes a type error caught at development time, not a runtime KeyError caught nowhere.

Interview-ready definition: a schema mismatch at a seam is a sign the two sides never shared a single source of truth for the contract between them — the fix is never just "correct the field name," it's making the shape impossible to silently disagree on again, typically by having both sides import one shared model rather than each independently guessing the other's shape.

Bug 3 — a code path skips score_run() entirely

SILENT GAP
Orchestrator.step() early-return
bypasses →
score_run()
never called →
eval_result row never written

How you'd actually notice it

capstone_dashboard_integration.html section 1's interview-ready definition is explicit: "full instrumentation... for every run, unconditionally." This bug is exactly the violation of that rule — a code path exists (say, a fast-path in Orchestrator.step() that returns immediately when the state store reports the run is already done, an idempotency guard against duplicate client retries) that returns a valid StepResult WITHOUT ever reaching the score_run(...) call. The response looks completely normal. What surfaces it: exactly the assertion capstone_integration_testing.html section 3 insists on — checking the DATABASE, not just the response — a smoke test or integration test that does SELECT * FROM eval_result WHERE trace_id = $1 after a request and finds nothing, even though the HTTP response was 200 with a normal-looking reply body.

How you'd isolate root cause

Grep every return statement inside Orchestrator.step() and check whether each one is downstream of the score_run(...) call or upstream of it — this is a purely mechanical check once you know to look for it, but easy to miss during a code review that reads top-to-bottom and doesn't specifically enumerate every exit point.

# BEFORE -- app/orchestrator/run.py, an idempotency fast-path added # LATER than the original instrumented step() from # capstone_dashboard_integration.html section 1 -- and added by # someone who didn't realize instrumentation lived further down async def step(self, run_id: str | None, user_message: str) -> StepResult: is_new = run_id is None run_id = run_id or str(uuid4()) existing = await self.store.load(run_id) if not is_new else None if existing and existing["status"] == "done": # idempotency guard: a retried request for an already-finished # run just re-returns the cached reply -- BUT this return # happens BEFORE the trace_id / score_run() call below, # so a retried request produces ZERO eval_result rows return StepResult(run_id=run_id, reply=existing["last_reply"], done=True) trace_id = start_trace() # ... route, dispatch, compose ... eval_scores = await score_run(trace_id=trace_id, reply=reply, tool_result=tool_result) return StepResult(run_id=run_id, reply=reply, done=done) # AFTER -- the fast-path still short-circuits the EXPENSIVE work # (routing, tool dispatch), but instrumentation happens on EVERY # reachable return, including this one -- scoring a cache hit is # cheap and worth doing, or at minimum a lightweight "cache_hit" # eval_span attribute gets recorded so the dashboard can tell the # two cases apart rather than seeing a silent gap in the data async def step(self, run_id: str | None, user_message: str) -> StepResult: is_new = run_id is None run_id = run_id or str(uuid4()) existing = await self.store.load(run_id) if not is_new else None trace_id = start_trace() # trace starts BEFORE any early-return, no exceptions if existing and existing["status"] == "done": await record_span(trace_id, "cache_hit", attributes={"run_id": run_id}) return StepResult(run_id=run_id, reply=existing["last_reply"], done=True) # ... route, dispatch, compose ... eval_scores = await score_run(trace_id=trace_id, reply=reply, tool_result=tool_result) return StepResult(run_id=run_id, reply=reply, done=done)

The general lesson worth stating explicitly: this bug class is created by ADDING a new early-return to an already-instrumented function later, without re-reading the whole function's control flow first. It's not that anyone forgot instrumentation existed — it's that a new exit point was added without checking whether it sits upstream or downstream of it. The durable defense against this class, worth naming in review: any function with instrumentation should have that instrumentation attached as close to the TOP of the function as structurally possible (start the trace first thing, per the AFTER version), so it becomes nearly impossible for a later `return` to bypass it — versus instrumentation attached near the bottom, which every future early-return silently escapes.

What a response-only smoke test would miss, concretely: capstone_integration_testing.html section 4's smoke test explicitly checks eval_span, not just response status — this exact bug is why that design choice matters in practice, not just in principle. A version of the smoke test checking only response.status_code == 200 would pass on every single retried request through the broken fast-path, while the eval pipeline's actual promise (a score for every run) silently failed for every one of them.

Problem 1 · A partial index that silently stopped being used

database/capstone_schema_finalization_and_indexes.html's idx_agent_run_running is a partial index (WHERE status = 'running'). A teammate changes the orchestrator to use a NEW status value, "in_progress", alongside the existing "running" for a subset of runs, without updating the index. Nothing crashes. What's the seam-level symptom this produces, how would you notice it days later rather than immediately, and what's the fix?

Show solution
The symptom is purely a PERFORMANCE regression, not a correctness one, which is exactly why it's the kind of bug that survives days before anyone notices: the ops query "find long-running, still-active orchestrator runs" (idx_agent_run_running's whole purpose, per the schema lab section 2) still returns CORRECT results either way -- an index only affects how fast a matching query runs, never whether the answer is right, so no test asserting on RESULTS would ever fail. What actually breaks is that the WHERE status = 'running' partial index no longer covers the "in_progress" rows at all, so a query looking for all currently-active runs (if written to check both status values) falls back to a full sequential scan for the in_progress subset while still using the index for the "running" subset -- a mixed, silently-degraded plan that gets slower in proportion to how much of agent_run's total history the "in_progress" status accumulates, per capstone_schema_finalization_and_indexes.html problem 2's own reasoning about why a partial index's write-overhead advantage depends entirely on staying small. How you'd notice it days later: not from a failing test (results are correct) but from an ops-facing symptom -- the "find stuck runs" query, part of on-call tooling, gets slower over time as more historical in_progress rows accumulate outside the index's coverage, until someone runs EXPLAIN ANALYZE on it (per the schema lab section 4) and sees a Seq Scan where an Index Scan used to appear, or notices the query's latency climbing on a dashboard that tracks internal tooling performance -- a genuinely easy thing to miss unless someone is specifically watching for index-usage drift after a status-value change, which is why "did this change touch any column referenced in a WHERE clause of an existing index" is worth being a standing review question, not just a one-time check. The fix: either normalize on ONE status value for the active state (rename in_progress back to running everywhere, simplest and safest if the two values were never meant to mean different things), or, if they genuinely are meant to be two distinct active substates, widen the partial index's WHERE clause to WHERE status IN ('running', 'in_progress') so both subsets stay covered -- decided by asking capstone_schema_finalization_and_indexes.html section 2's own question again: what's the REAL query pattern this index needs to serve, now that the set of "active" values changed.
Problem 2 · A trace_id that doesn't match between two tables

A dashboard query joining eval_result and eval_span on trace_id (per capstone_schema_finalization_and_indexes.html's idx_eval_span_trace) starts returning zero rows for a subset of recent runs, even though both tables individually show rows for those runs existing. Given that eval_result.trace_id and eval_span.trace_id are populated by two DIFFERENT call sites in the orchestrator's instrumentation code, what's the most likely seam-level cause, and how would you confirm it without guessing?

Show solution
The most likely cause is that the two call sites are no longer using the SAME trace_id value -- e.g. start_trace() generates a fresh trace_id, that value is correctly threaded into every record_span() call, but a LATER code change refactored score_run()'s call site to generate its own id (perhaps via a different helper, or by reusing run_id instead of trace_id by an easy-to-make copy-paste mistake) instead of receiving the same trace_id as a parameter. Both tables get populated correctly in isolation -- eval_span rows all share one trace_id, eval_result rows all have SOME trace_id -- but the two values no longer match for the affected runs, so the join predicate trace_id = trace_id fails silently for exactly those rows even though every individual row is otherwise well-formed. How to confirm without guessing: pull one affected run's data from both tables directly (not through the join) -- SELECT trace_id FROM eval_span WHERE ... for that run's known span, and SELECT trace_id FROM eval_result WHERE run_id = ... for the same run -- and compare the two trace_id STRINGS byte-for-byte. If they differ, that's definitive confirmation of exactly this bug, not a hypothesis. Then grep every call site that either generates a trace_id or receives one as a parameter (start_trace(), record_span(), score_run()) and check which ones are threading the SAME variable through versus which one independently generates or substitutes a different id -- this is the same "write down each side's real assumption, don't guess" isolation method section 1 established, applied to a join key instead of a JSON field name. The fix is always structural, not a data patch: change the diverging call site to accept trace_id as an explicit required parameter (never optional, never internally regenerated), so a future refactor can't silently reintroduce the same drift.
