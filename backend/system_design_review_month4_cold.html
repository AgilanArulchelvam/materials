01 — Cold recall, no notes

MCP gateway design, re-derived

Do this before opening anything below. Set a timer for 5-8 minutes. On paper or out loud, answer every bullet below as if you were in an actual interview, with nobody to check your work until you're done.

Prompt — attempt cold first

Without looking anything up, sketch an MCP gateway design:

  • What does the gateway's routing table actually map, and why does tools/list need special handling that tools/call doesn't?
  • Why does centralizing auth at the gateway reduce security surface area, specifically — not just "make it tidier"?
  • What has to be true about a gateway instance before you can safely run several of them behind a load balancer?
  • Walk through what breaks if a permission revocation only updates one gateway instance's local memory.
Reveal the answer (only after you've actually attempted it)
ROUTING TABLE AND tools/list: the routing table maps tool (or resource/ prompt) names to the backend MCP server address that actually implements each one -- so a client sends every request to ONE gateway address, and the gateway forwards tools/call requests to whichever specific backend owns the named tool. tools/list needs special handling because it's not a routing decision at all -- it's a DISCOVERY query, and the gateway has to MERGE every backend's individual tool catalog into one combined list so the client sees all available tools as if they came from a single server, rather than only seeing whichever one backend happened to answer first. WHY CENTRALIZING AUTH REDUCES SECURITY SURFACE AREA: with per-server auth, N independently-implemented auth/permission checks means N independent chances for a bug to slip through -- a security audit has to review every one of them separately, and a permission change has to be pushed to every one of them separately. Centralizing auth at the gateway means there is exactly ONE place authentication and per-client permission scope is enforced, before a request ever reaches any backend server -- backend servers can even trust that anything reaching them was already authorized, simplifying their own code. This isn't "auth becomes bug- proof" -- it's that the surface area for such a bug shrinks from N independent implementations to one. WHAT MUST BE TRUE BEFORE SCALING HORIZONTALLY: the gateway instances must be STATELESS with respect to routing tables and per-client permissions -- that data has to live in a shared external store every instance reads from (a database, a config service, a fast cache), not duplicated in each instance's own private memory. This mirrors Month 1's stateless/ stateful lesson and the rate limiter's distributed-counter lesson exactly: if each instance kept its own private copy, a policy change would need to somehow reach every instance, and any instance that missed the update would keep enforcing stale policy. WHAT BREAKS ON A STALE REVOCATION: if a permission revocation updates only ONE gateway instance's local memory (or a config file that only some instances have re-read), the compromised client's next request might land -- via round-robin or whatever the load balancer's algorithm is -- on an instance that HASN'T picked up the revocation yet, and that instance would incorrectly continue allowing access that was supposed to have just been cut off. This is a genuinely dangerous inconsistency specifically because it's security-relevant: the whole point of a revocation is immediate effect, not "cut off on however many instances happened to reload since the change."
What "re-derive cold" is testing: whether you can explain WHY centralizing auth actually reduces risk (fewer independent implementations, not just tidiness), and whether you connect "must be stateless" to a CONCRETE consequence (a stale revocation on one instance) rather than reciting "stateless" as a buzzword with no mechanism behind it.
02 — Cold recall, no notes

Async tool job queue design, re-derived

Do this before opening anything below. Same rules: timer, full attempt, no peeking until you're done.

Prompt — attempt cold first

Without looking anything up, sketch an async tool job queue design:

  • Walk through the enqueue → worker → result-store flow. What exactly makes the caller's path non-blocking?
  • Trace the exact backoff delays across several failed attempts, and explain what happens once MAX_ATTEMPTS is hit.
  • Name the two distinct problems a dead-letter queue solves.
  • Name at least two backpressure strategies, and describe a scenario where applying the wrong one makes things worse.
Reveal the answer (only after you've actually attempted it)
ENQUEUE -> WORKER -> RESULT-STORE FLOW: a slow tool call is represented as a job (tool name, arguments, a generated job ID) written to a queue rather than awaited directly in the caller's request path. The caller returns IMMEDIATELY with a job ID once the job is written to the queue -- it never waits for the actual work to happen. A separate, independently- running worker process dequeues jobs on its own schedule and actually executes them, writing the result to a results store the caller (or a later poll) reads from afterward. What makes the caller's path non- blocking specifically: the enqueue operation itself (writing to the queue) is fast and returns right away -- the SLOW part (actually running the tool) happens entirely on the worker's own timeline, decoupled from the original request. BACKOFF DELAYS AND MAX_ATTEMPTS: using delay = BASE_DELAY_SECONDS * (2 ** (attempts - 1)) with BASE_DELAY_SECONDS=2: after attempt 1 fails, wait 2s; after attempt 2 fails, wait 4s; after attempt 3 fails, wait 8s -- doubling each time. Once attempts reaches MAX_ATTEMPTS (commonly 4), the job stops retrying and moves to the dead-letter queue instead of attempting a 5th time -- the retry budget is bounded, not infinite. TWO PROBLEMS A DLQ SOLVES: first, it stops a permanently-failing job (malformed payload, deleted resource, invalid input -- not something retrying fixes) from consuming worker retry capacity forever, freeing that capacity for jobs that CAN succeed. Second, it avoids silently dropping the failed job -- its full payload and failure history are preserved intact for later human inspection, so if the root cause turns out to be fixable, the job can be reprocessed rather than being unrecoverably lost. BACKPRESSURE STRATEGIES AND THE WRONG-STRATEGY TRAP: (1) reject new enqueue requests past a queue-depth threshold -- simple, predictable, but pushes the "what now" decision back to the caller; (2) throttle/slow the producer -- couples producer speed to queue depth, which can cascade upstream; (3) scale workers horizontally to increase drain rate. The trap: scaling workers does NOT help when the actual bottleneck is an EXTERNAL, FIXED constraint -- e.g. a third-party API's hard rate limit that doesn't budge no matter how many workers are asking it for work. Adding more workers in that specific scenario can make things WORSE, since more workers just means more requests contending for the same fixed-rate resource, likely triggering more rate-limit errors and feeding back into the retry logic, compounding the problem rather than solving it.
What "re-derive cold" is testing: whether you can name the EXACT exponential-backoff arithmetic (not just "it retries with backoff"), articulate BOTH problems a DLQ solves (most people only remember one), and correctly identify a scenario where "just add more workers" is the wrong answer rather than always assuming more capacity helps.
03 — Neither system was designed to run alone

How the gateway and the job queue actually connect

Start here, before the diagram. Section 1 and 2 each stand on their own as designs — but in a real agentic deployment, they're not two unrelated systems sitting side by side. They're two adjacent stages of the SAME request's journey: a client's request arrives at the gateway, the gateway routes it to whichever agent (or backend MCP server) handles that capability, and if that agent decides a particular tool call is slow enough to warrant it, THAT agent is the one enqueueing a job into the queue — the gateway itself never touches the queue directly.

The key architectural point: the gateway's job (section 1) ends the moment it has routed the request to the correct agent — it has no opinion about whether that agent's tool calls are fast or slow, and it does not itself enqueue anything. The DECISION to enqueue (section 2's if tool_name in SLOW_TOOLS check) is made by the AGENT, downstream of the gateway, using exactly the same handle_tool_call logic backend/async_tool_job_queue_design.html already specified. The gateway routing a request and an agent enqueueing a job are two separate concerns, cleanly separated — the gateway would work identically whether or not any backend agent used a job queue internally at all.

A trap worth naming directly: it's tempting to think the gateway itself should own retry/backoff/backpressure logic for slow tool calls, since section 1's gateway already sits in the critical path of every request. But retries, backoff, and the dead-letter queue are all about managing the LIFECYCLE of one specific tool call's EXECUTION — something the gateway has already handed off responsibility for once it routes the request downstream. Making the gateway also own job-queue semantics would blur a clean separation of concerns into one component doing two structurally different jobs (routing/authz vs. async execution management), which is exactly the kind of unnecessary coupling that makes each piece harder to reason about, test, and scale independently.
Interview-ready definition: in a real agentic deployment, the MCP gateway and the async tool job queue are adjacent, cleanly separated stages of one request's journey rather than independent systems: the gateway authenticates the client and routes the request to the correct downstream agent based on which tool is being called, and — only once the request has already reached that agent — the agent itself decides, using its own slow-tool check, whether a given tool call should be enqueued for async execution rather than awaited inline. The gateway has no visibility into or responsibility for queue internals (retries, backoff, the dead-letter queue, backpressure); the queue and its workers have no visibility into or responsibility for routing and auth. Each system scales and fails independently of the other, which is the direct architectural payoff of keeping the two concerns separate rather than merging them into one component.

Problem 1 · Diagnosing where a permission check belongs when a job is enqueued

A client's request to call a slow tool is authorized by the gateway, routed to the correct agent, and the agent enqueues it as a job (section 2). Minutes later, a worker dequeues the job and executes it. Does the worker need to re-check the client's permissions at execution time? Why or why not?

Show solution
In the architecture section 3 describes, no -- the worker does not need to independently re-check permissions, because authorization already happened once, upstream, at the gateway (section 1), BEFORE the request was ever routed to the agent that decided to enqueue it. By the time a job exists in the queue at all, it represents a tool call that was already authorized -- the queue and its workers are downstream of that decision, not a separate entry point a client could reach directly to bypass the gateway's auth check. This mirrors section 1's own "backend servers can trust a request that reaches them was already authorized" argument, extended one hop further: just as an MCP backend server doesn't need its own auth logic because the gateway already enforced it, a queue worker doesn't need its own permission check because the AGENT that enqueued the job only got to make that decision because ITS request had already passed the gateway's auth check. The one caveat worth naming: this chain of trust depends on there being no way to enqueue a job DIRECTLY into the queue, bypassing both the gateway and the agent -- if the queue had some other entry point reachable without going through the gateway first, THAT path would need its own authorization check, since the "already authorized upstream" assumption would no longer hold for jobs arriving that way.
Problem 2 · Reasoning about what happens if the queue is at capacity when an agent tries to enqueue

Using section 2's backpressure reasoning and section 3's connection diagram, what should the AGENT do if its attempt to enqueue a job is rejected because the queue is past its depth threshold? Does this failure ever need to propagate back through the gateway to the original client?

Show solution
The agent should treat the rejection as a real, structured outcome to reason about -- not silently retry the enqueue call in a tight loop (mirroring async_tool_job_queue_design's own Practice Problem 5, and the same graceful-degradation posture deterministic_parsing.html and mcp_client_basics.html both established elsewhere this month). A reasonable response: the agent surfaces "the system is currently at capacity for this kind of request, please try again shortly" as part of its own response, or attempts a bounded retry with backoff before giving up. Whether this needs to propagate back through the gateway to the client: yes, eventually -- the gateway's job (section 1) was only to ROUTE the original request to this agent; it has no ongoing role in the agent's internal handling of that request afterward, so the gateway itself does nothing special here. But the CLIENT still needs to find out the request couldn't be completed -- that response travels back along the same path the original request came in on (agent's response -> back through whatever return path the gateway's request/response cycle uses -> to the client), simply because that's the only path connecting the client to the agent at all. The gateway doesn't need to UNDERSTAND that a queue rejection happened somewhere downstream -- it's just forwarding a response back, the same as it would for any other response from that agent, authorized or not.
Problem 3 · Comparing the two systems' approaches to horizontal scaling

Both the gateway and the job queue's worker pool can be scaled horizontally. Using section 1's statelessness requirement and section 2's backpressure table, explain one genuine similarity and one genuine difference in HOW each system scales.

Show solution
SIMILARITY: both scale by adding more independent, identically-capable instances rather than growing one instance's capacity indefinitely -- more gateway instances behind a load balancer (section 1), more worker instances draining the same shared queue (section 2's "scale workers horizontally" backpressure strategy). Neither system tries to make ONE instance handle unbounded load; both lean on Month 1's horizontal- scaling pattern. DIFFERENCE: what each additional instance NEEDS to scale correctly differs. Gateway instances must be stateless with respect to routing tables and permissions specifically because MULTIPLE clients could hit DIFFERENT gateway instances for DIFFERENT requests at the same moment, and all of them need to enforce the exact same, current policy -- inconsistency here is a security problem (section 1's stale-revocation scenario). Worker instances, by contrast, don't need to share nearly as much state with each other at all -- each worker mostly just needs to be able to dequeue an independent job, execute it, and write its own result; workers aren't coordinating policy decisions with each other the way gateway instances are. Also critically: section 2 already flags that scaling WORKERS specifically fails to help when the bottleneck is an external, fixed-rate dependency (Problem 4 of the async job queue lab) -- there's no equivalent "external fixed-rate constraint" limiting how much scaling gateway instances helps, since the gateway's own routing/auth work doesn't depend on a third-party rate limit the way tool execution sometimes does. The two systems scale via the same general PATTERN, but the actual bottleneck each one runs into as it scales is genuinely different.
Problem 4 · Spotting a design that merges the two systems' responsibilities incorrectly

A candidate proposes: "let's just have the gateway maintain the job queue directly, since it's already the single front door for every request anyway." Using section 3's separation-of-concerns argument, what's the risk of this design?

Show solution
This merges two structurally different responsibilities into one component, which section 3's warning callout flags directly. The gateway's entire job (section 1) is ROUTING and AUTHORIZATION -- fast, per-request decisions that need to happen before a request reaches any backend. The job queue's entire job (section 2) is managing the LIFECYCLE of long-running, asynchronous work -- retries, backoff, dead- letter handling, backpressure -- which unfolds over a completely different timescale (seconds to minutes, not the sub-request-latency scale routing operates on). Concretely, folding queue ownership into the gateway means: every gateway instance (recall section 1's requirement that gateway instances be stateless and horizontally scaled independently) would now ALSO need to coordinate queue state, worker assignment, and retry bookkeeping -- coupling the gateway's scaling behavior to the queue's, when section 3 specifically valued that the two currently scale independently. It also means a bug or overload in queue-management logic could now destabilize the GATEWAY itself -- the single front door every request passes through for routing and auth -- rather than staying contained to a separate component whose failure doesn't take down request routing for the entire system. "It's already the front door" is true but doesn't imply "so it should own everything downstream of the front door too" -- the value of keeping them separate is exactly that a queue-side problem stays a queue-side problem, and a gateway-side problem stays a gateway-side problem, rather than either one being able to take the other down.
Problem 5 · Writing your own cold-recall connection question for a third system

Using the same "how do these systems actually connect" framing as section 3, write ONE cold-recall question (not the answer) that tests how the MCP gateway would need to connect to database/audit_trail_schema.html's logging schema — this same week's DB design topic — if every tool call routed through the gateway needed to be logged for replay/debugging.

Show solution
A reasonable connection question, following section 3's shape (specific enough to force a real design decision, not so open-ended a vague answer can dodge it): "The gateway (section 1) sits in front of every tool call in the system, and the audit trail schema needs a row logging every tool call's inputs, outputs, and status. Where in the gateway's own request flow -- BEFORE routing, AFTER a backend responds, or both -- would you insert the audit-log write, and why does logging only 'before' or only 'after' each lose something the schema needs? Does the audit log write need to be synchronous with the gateway's response to the client, or could it be handled the way section 2's job queue handles slow work -- asynchronously, off the critical request path?" The value of writing this yourself: it forces connecting THIS lab's gateway-request-flow reasoning to a genuinely different system (a logging schema, not another system-design lab) using the same "trace one request's actual journey through multiple components" method section 3 modeled -- rather than treating "system design" and "database design" as two disconnected weekly tracks that happen to both exist this month. The "synchronous vs async" sub-question specifically echoes section 2's own core lesson (don't block a fast path on slow, non-critical work) applied to a new concern (audit logging) that section 2 never actually covered.
