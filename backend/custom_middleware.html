BACKEND & APIS LAB · CUSTOM MIDDLEWARE

Middleware registered first wraps outermost — it runs first going in, and last coming back out.

Middleware sits between the raw incoming request and your route handler, able to inspect or modify both the request on the way in and the response on the way out. The mental model that trips people up in interviews is ordering: middleware layers nest like an onion, and the layer closest to the outside is the FIRST one registered — not the last.

01 — Two different levels to intercept a request

BaseHTTPMiddleware vs. pure ASGI middleware

Start here, before any code. Imagine a building with a front desk (simple, easy to staff, handles most routine visitor logging) versus a full security checkpoint with equipment that can inspect literally anything about a person as they pass through, at the cost of being more complex to build and operate correctly. Both "intercept everyone entering," but at very different levels of control and complexity.

BaseHTTPMiddleware is FastAPI/Starlette's simpler, higher-level way to write middleware: you write a single async function that receives the request and a call_next function, do something before calling call_next(request), and do something with the response it returns. Pure ASGI middleware operates one level lower — directly against the raw ASGI scope/receive/send interface that Starlette itself is built on, giving full control (including over streaming request/response bodies) at the cost of noticeably more boilerplate.

# BaseHTTPMiddleware -- simpler, most common choice from starlette.middleware.base import BaseHTTPMiddleware class TimingMiddleware(BaseHTTPMiddleware): async def dispatch(self, request, call_next): start = time.monotonic() response = await call_next(request) # runs everything INSIDE this layer duration = time.monotonic() - start response.headers["X-Process-Time"] = str(duration) return response app.add_middleware(TimingMiddleware)
# Pure ASGI middleware -- lower level, full control class TimingASGIMiddleware: def __init__(self, app): self.app = app async def __call__(self, scope, receive, send): if scope["type"] != "http": return await self.app(scope, receive, send) start = time.monotonic() await self.app(scope, receive, send) # NOTE: modifying headers here is harder -- you must wrap `send` # itself to intercept the outgoing response message before it's sent.

Interview-ready definition: BaseHTTPMiddleware is a Starlette convenience class that wraps the lower-level ASGI protocol into a simple "receive a request, call the next layer, receive a response, return it" async function — sufficient for the large majority of middleware use cases (logging, timing, header injection). Pure ASGI middleware implements the raw scope/receive/send callable interface directly, offering finer-grained control (including over streaming bodies and non-HTTP protocols like WebSockets) at the cost of more manual plumbing.
02 — The order that trips everyone up at least once

Middleware ordering: the onion model

Start here, before the demo. Picture wrapping a gift in three layers of paper, one at a time: brown paper first, then patterned paper, then a ribbon last. To UNWRAP it, you go in the exact reverse order — ribbon first, then patterned paper, then brown paper. The LAST thing you wrapped is the FIRST thing you unwrap. Middleware nests exactly like this: whichever middleware you register FIRST ends up as the OUTERMOST layer, wrapping everything registered after it — so it's the first thing the request touches, and the last thing the response touches on the way back out.

The interview trip-up, stated plainly: "the first middleware you add runs first" is true only for the INBOUND leg. On the way back OUT, order reverses completely — the first-registered (outermost) middleware is the LAST to see the response. If middleware order matters for correctness (e.g. an auth-check middleware must run before a middleware that logs the authenticated user's ID), get this backwards and you'll either log garbage or block requests that should have passed.
Interview-ready definition: ASGI middleware layers nest in the order they are registered, forming a call stack: the first-registered middleware becomes the OUTERMOST wrapper, meaning it is the first to process an incoming request and the last to process the outgoing response, while the most-recently-registered middleware sits closest to the route handler (innermost) — first to hand off to the actual route, and first to receive its raw response back. This "last in, first out on the way back" behavior is a direct consequence of each middleware literally calling the next one and only continuing its own code after that call returns.
03 — What middleware is actually good for

Logging, timing, and header injection

Start here, before any code. Airport security doesn't care what your specific reason for flying is — it applies the exact same screening to every single traveler, regardless of destination. Middleware is the same idea for HTTP requests: instead of adding logging code to every single route handler individually (and inevitably forgetting one), you write it once as middleware and it applies uniformly to every request that passes through the app.

Request-side interception

Reading headers before the route runs (extracting a request ID, validating an API key format), starting a timer, logging the incoming method/path — anything that needs to happen BEFORE the route sees the request.

Response-side interception

Adding a computed header (like X-Process-Time), logging the final status code, compressing the body — anything that needs the ALREADY-COMPUTED response to act on.

class RequestIDMiddleware(BaseHTTPMiddleware): async def dispatch(self, request, call_next): request_id = str(uuid.uuid4()) request.state.request_id = request_id # attach BEFORE the route runs response = await call_next(request) response.headers["X-Request-ID"] = request_id # attach AFTER the route runs return response
Why this matters in practice: because every request flows through the same layers in the same order, middleware is the natural place for cross-cutting concerns that would otherwise mean copy-pasting the same few lines into every route — request ID tagging for tracing, structured access logging, response compression, and CORS handling are all textbook middleware use cases precisely because they apply uniformly and have nothing to do with any single route's specific business logic.

Problem 1 · Predicting inbound order

A team registers middleware in this order: CORS, then Logging, then RateLimit. On an INCOMING request, which middleware's code runs first, before the route handler?

Show solution
CORS runs first. The first middleware registered becomes the OUTERMOST layer, so it's the first thing an incoming request touches -- the request flows CORS -> Logging -> RateLimit -> route handler, in registration order, on the way in.
Problem 2 · Predicting outbound order

Using the same registration order (CORS, Logging, RateLimit), which middleware's response-handling code runs LAST, after the route handler has already produced a response?

Show solution
CORS runs last on the way out. The order reverses completely for the outbound leg: the response flows route handler -> RateLimit -> Logging -> CORS, meaning the FIRST-registered middleware (CORS) is the LAST to see and potentially modify the response, since it was the outermost wrapper and its own code only resumes after everything inside it (including the route) has already returned.
Problem 3 · A real ordering bug

A team writes an AuthMiddleware that rejects unauthenticated requests, and a LoggingMiddleware that logs `request.state.user_id` (set by AuthMiddleware). They register LoggingMiddleware first, then AuthMiddleware. What breaks, and why?

Show solution
LoggingMiddleware, being registered first, is the OUTERMOST layer -- it runs and tries to read request.state.user_id BEFORE control has even reached AuthMiddleware (which is inside it), because AuthMiddleware hasn't run yet at that point in LoggingMiddleware's own pre-call_next code. If LoggingMiddleware tries to read user_id before calling call_next(request), that attribute doesn't exist yet -- AuthMiddleware, being the inner layer, only sets it once IT runs, which happens only after LoggingMiddleware has already called call_next(). The fix is to register AuthMiddleware first (making it outermost) so it runs and sets user_id before LoggingMiddleware (now the inner layer) gets a chance to read it -- registration order needs to reflect this "who needs to run before whom" dependency directly.
Problem 4 · BaseHTTPMiddleware vs ASGI middleware choice

You need to build a middleware that proxies and streams large file uploads without ever buffering the entire request body in memory. Which approach — BaseHTTPMiddleware or pure ASGI middleware — fits, and why?

Show solution
Pure ASGI middleware. BaseHTTPMiddleware's higher-level abstraction historically works by buffering the request/response body to present it as a simple in-memory object to your dispatch function, which is exactly the problem for large file uploads -- it defeats the purpose of streaming and can exhaust memory on big payloads. Pure ASGI middleware operates directly on the receive/send callables, letting you forward chunks of the body as they arrive without ever holding the whole thing in memory at once, which is the entire point of a true streaming proxy.
Problem 5 · Timing middleware placement

You want X-Process-Time to reflect ONLY the time your own application code takes (route handler + any inner middleware), excluding any time spent in an outer rate-limiting middleware that might delay requests before they even reach yours. Should your timing middleware be registered before or after the rate limiter?

Show solution
Register the timing middleware AFTER the rate limiter (making timing the INNER layer, closer to the route). Since the first-registered middleware is outermost, registering rate-limiting first means it wraps everything else -- any delay it introduces happens before control ever reaches the timing middleware's start-the-clock code. If timing were registered first (outermost) instead, its clock would start before the rate limiter even runs, incorrectly including the rate limiter's delay in the reported process time.
