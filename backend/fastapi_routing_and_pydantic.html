BACKEND & APIS LAB · FASTAPI ROUTING & PYDANTIC

A route signature is a contract — FastAPI reads your type hints and enforces them before your code ever runs.

FastAPI's whole design centers on one idea: describe the shape of a request using ordinary Python type hints and Pydantic models, and the framework will parse, validate, and reject bad input automatically — then use that exact same description to generate interactive API docs. This lab covers where each piece of a request comes from, how Pydantic V2 validates it, and what the generated OpenAPI docs are actually built from.

01 — Where does each piece of the request come from?

Path, query, and body parameters

Start here, before any code. Think about a restaurant reservation line: "Table 12, party of 4, note: window seat please." "Table 12" identifies exactly WHICH resource you mean — that's like a path parameter, baked into the URL itself and always required. "Party of 4" is an optional filter or modifier tacked onto the request — that's a query parameter, usually optional, usually simple. "Window seat please, also here's our full anniversary request form with six fields" is a larger, structured payload that doesn't fit cleanly into a URL — that's the request body, used for anything more complex than a few short values.

FastAPI decides where each function parameter comes from using a simple set of rules based on your type hints and the route's path template: a parameter whose name matches a {placeholder} in the path is a path parameter; a simple-typed parameter (str, int, bool, etc.) that ISN'T in the path is a query parameter; and a parameter typed as a Pydantic BaseModel is parsed from the request body as JSON.

from fastapi import FastAPI from pydantic import BaseModel app = FastAPI() class UserCreate(BaseModel): name: str email: str @app.get("/users/{user_id}") async def get_user(user_id: int, include_deleted: bool = False): # user_id -> PATH param (it's in "{user_id}" in the route) # include_deleted -> QUERY param (?include_deleted=true), simple type, not in path return {"user_id": user_id, "include_deleted": include_deleted} @app.post("/users") async def create_user(payload: UserCreate): # payload -> BODY param (its type is a Pydantic BaseModel) # parsed from the raw JSON request body, and VALIDATED against UserCreate return {"created": payload.name}

Path params

Identify a specific resource. Always required — the URL wouldn't match the route at all without it. GET /users/{user_id}

Query params

Filter, sort, or paginate. Usually optional with a default. GET /users?active=true&limit=20

Body params

Structured payload for creating/updating something. Parsed as JSON into a Pydantic model. POST /users {"name": "Ada"}

Interview-ready definition: FastAPI infers a parameter's source (path, query, or body) from its type hint and whether its name appears in the route's path template — path parameters are extracted from the URL path itself and are always required, query parameters come from the URL's query string and are typically optional, and any parameter typed as a Pydantic BaseModel is parsed and validated from the request body's JSON payload. This inference is what lets a route's function signature double as both its parsing logic and its documented contract.
02 — Enforcing the contract before your code runs

Pydantic V2 validators and Field() constraints

Start here, before any code. Imagine airport security: nobody gets to the gate (your actual route handler) without passing through a checkpoint that verifies their ID, checks their bag dimensions, and confirms nothing prohibited is inside. Pydantic is that checkpoint — it inspects the incoming JSON against your model's declared fields and types, rejects anything that doesn't conform, and only lets validated, correctly-typed data through to your function body. Your route handler never has to defensively check "is this actually a string?" or "did they forget the email field?" — by the time your code runs, that's already guaranteed.

Beyond basic types, Pydantic's Field() lets you attach constraints — minimum/maximum length, numeric ranges, regex patterns — directly onto a field declaration, and @field_validator lets you write arbitrary custom validation logic.

from pydantic import BaseModel, Field, field_validator class UserCreate(BaseModel): name: str = Field(min_length=1, max_length=50) age: int = Field(ge=0, le=130) email: str = Field(pattern=r"^[^@]+@[^@]+\.[^@]+$") @field_validator("name") @classmethod def no_leading_space(cls, v: str) -> str: if v != v.strip(): raise ValueError("name cannot have leading/trailing whitespace") return v
SIMULATE PYDANTIC VALIDATION LIVE

This form validates against the UserCreate model above using the exact same rules Pydantic would enforce — including the error message FORMAT Pydantic actually produces.

Interview-ready definition: Field() attaches declarative constraints (length, numeric bounds, regex patterns, defaults) directly to a Pydantic model field, while @field_validator allows arbitrary custom validation logic that runs during model construction. When validation fails, Pydantic raises a ValidationError containing a structured list of every failing field, the failure type, and a human-readable message — FastAPI automatically catches this and returns it as a 422 Unprocessable Entity response, so invalid data never reaches your route handler's body.
03 — Composing models, and shaping what goes back out

Nested models and response models

Start here, before any code. A shipping label doesn't just have a flat list of fields — it has a "ship to" address block and a separate "return address" block, each with their own street/city/zip structure nested inside. Pydantic models nest the same way: a field can simply be typed as another BaseModel, and Pydantic will recursively validate the nested object's own fields using its own rules.

class Address(BaseModel): street: str city: str zip_code: str = Field(pattern=r"^\d{5}$") class UserCreate(BaseModel): name: str address: Address # nested model — validated recursively # incoming JSON: # {"name": "Ada", "address": {"street": "1 Infinite Loop", "city": "Cupertino", "zip_code": "95014"}} # if address.zip_code were "9501" (4 digits), Pydantic reports the error at # path "address -> zip_code", not just "address" -- nesting is fully validated.

The response side works the other way: a response model declared on the route (@app.get("/users/{id}", response_model=UserOut)) tells FastAPI to filter and re-validate whatever your function returns against a DIFFERENT model than the input one — most commonly to strip sensitive fields (like a hashed password) that exist on your internal object but should never be serialized back to the client.

class UserOut(BaseModel): id: int name: str # NOTE: no "hashed_password" field here, even though the internal # User object has one -- response_model filters it out automatically. @app.get("/users/{user_id}", response_model=UserOut) async def get_user(user_id: int): user = db.get_user(user_id) # has .id, .name, .hashed_password return user # FastAPI serializes ONLY the UserOut fields
Why this matters: the input model and the response model are deliberately different types precisely because "what a client is allowed to send" and "what a client is allowed to receive back" are different contracts — a request model might require a plaintext password, while a response model must never echo any form of it back.
04 — The same type hints, reused as documentation

Automatic OpenAPI docs generation

Start here, before any code. Imagine if a form's printed instructions were generated automatically FROM the form itself, guaranteed to always match exactly what the form actually accepts — no separate document that quietly goes stale the moment someone adds a field. That's what FastAPI's docs generation is: instead of hand-writing separate API documentation, FastAPI inspects your route decorators, function signatures, and Pydantic models at import time and builds a complete OpenAPI (formerly "Swagger") schema from them — then serves that schema as an interactive UI at /docs.

That single generated openapi.json schema then powers TWO separate interactive doc UIs FastAPI ships automatically: Swagger UI at /docs (try-it-out forms for every route) and ReDoc at /redoc (a cleaner reference-style layout). Nobody writes either page by hand — both are rendered client-side purely from the schema.

Interview-ready definition: FastAPI generates an OpenAPI 3.x schema automatically at startup by introspecting each route's path, HTTP method, parameter types (path/query/body), and any Pydantic models used for request/response bodies — including their field constraints and nested structure. This schema is exposed as JSON at /openapi.json and rendered as interactive documentation at /docs (Swagger UI) and /redoc (ReDoc), meaning the documentation can never drift out of sync with the actual API, since both are generated from the exact same source of truth as the validation logic itself.

Practice problems

Problem 1 · Classifying parameters

Given the route @app.get("/posts/{post_id}/comments") with signature def list_comments(post_id: int, page: int = 1, page_size: int = 20), classify each parameter as path or query, and explain why.

Show solution
post_id is a PATH parameter -- its name matches "{post_id}" in the route template, so FastAPI extracts it directly from the URL and it's always required (there's no way to hit this route without it). page and page_size are QUERY parameters -- they're simple types (int) and their names don't appear anywhere in the path template, so FastAPI reads them from the query string (e.g. ?page=2&page_size=50). Both have defaults, so they're optional; a client can omit them and get page=1, page_size=20.
Problem 2 · Predicting a validation error

Given age: int = Field(ge=0, le=130), a client POSTs {"age": -5}. What HTTP status code does FastAPI return, and roughly what does the error body contain?

Show solution
FastAPI returns 422 Unprocessable Entity. The response body contains a "detail" array with one entry describing the failure: the field location (["body", "age"]), a message like "Input should be greater than or equal to 0", and the error type (e.g. "greater_than_equal"). This structured format is exactly what Pydantic's ValidationError produces, and FastAPI translates it directly into the JSON response -- the route handler's code never even runs, because validation fails before the function body executes.
Problem 3 · Response model filtering

A route returns an internal User object with fields id, name, email, and hashed_password. The route is declared with response_model=UserOut, where UserOut only has id and name. What ends up in the actual JSON response, and why is this useful beyond just "cleaner output"?

Show solution
Only id and name appear in the response JSON -- email and hashed_password are silently dropped, because response_model tells FastAPI to serialize the return value strictly through the UserOut schema, not through whatever attributes the internal object happens to have. This matters for more than tidiness: it's a genuine SECURITY boundary. If a developer later adds a new sensitive field to the internal User object (say, a password reset token) and forgets to update every route, this mechanism means the field is excluded by default rather than accidentally leaked -- you have to deliberately add it to the response model for it to ever be serialized back to a client.
Problem 4 · Nested validation error paths

Using the Address/UserCreate nested model example from this lab, a client sends {"name": "Ada", "address": {"street": "1 Loop", "city": "Cupertino", "zip_code": "950"}}. Where, specifically, does Pydantic report the error, and what does that reveal about how nested model validation works?

Show solution
Pydantic reports the error at the location ["body", "address", "zip_code"] -- a full path down through the nesting, not just a generic "address is invalid" message. This reveals that nested BaseModel fields are validated RECURSIVELY: Pydantic doesn't just check that "address" is a dict-shaped object, it fully validates address as its own Address model instance, applying that model's own Field() constraints (the 5-digit zip_code pattern) to its own sub-fields, and any failure bubbles up with a precise path showing exactly which nested field failed and why.
Problem 5 · Why docs can't go stale

A teammate adds a new required field to a request model but forgets to update any documentation. Explain why the Swagger UI at /docs will still be accurate anyway.

Show solution
Because there IS no separate documentation to forget to update -- the Swagger UI isn't hand-written prose that lives independently of the code, it's rendered client-side entirely from the OpenAPI schema, which FastAPI regenerates automatically every time the app starts by introspecting the actual route signatures and Pydantic models currently in the code. Adding a required field to the model changes what FastAPI introspects, which changes the generated openapi.json, which changes what Swagger UI renders -- there's no manual sync step to skip, because the "documentation" and the "validation logic" are reading from the exact same source (the model definition itself).
Problem 6 · Custom validator vs Field constraint

You need to enforce that a "confirm_password" field exactly matches a "password" field on the same model. Can this be expressed with a simple Field() constraint alone? If not, what Pydantic V2 feature is needed and why?

Show solution
No, a plain Field() constraint can't express this, because Field() constraints only see the SINGLE field they're attached to (its own value) -- they have no visibility into other fields on the same model. Comparing password and confirm_password requires access to the whole model's data at once. This needs a model-level validator -- in Pydantic V2, @model_validator (mode="after") runs once the whole model has been constructed and has access to all fields simultaneously, so it can check self.password == self.confirm_password and raise a ValueError if they differ, which Pydantic will surface as a normal validation error.
