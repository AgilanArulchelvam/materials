01 — Five sections, each answering a question no other section answers

What sections a good architecture doc has

Start here, before opening a blank document. Think about the difference between a map and a travel diary. A travel diary (most READMEs) tells you what happened, in the order it happened — useful, but you have to read the whole thing to find anything specific. A map (an architecture doc) is organized by QUESTION: where am I, how do I get from A to B, what's the fastest route, what roads are closed. A good architecture doc is structured the same way — five sections, each answering one question a reader actually has, not a narrative of how the system was built.

SectionQuestion it answersWhat goes wrong if it's missing
Context / goalsWhat is this system FOR, and what does it explicitly NOT need to do?A reader can't judge whether a design decision was reasonable without knowing what it was optimizing for — "why Redis for run state" only makes sense against the stated goal "low-latency, disposable, high-write" from mcp-and-agents/capstone_orchestrator_integration.html section 1
Component diagramWhat are the pieces, and how do they connect?Without this, every other section is describing parts of a whole the reader can't picture — the single highest-leverage section, covered in depth in section 2
Data flowWhat actually happens, in order, for the system's core use case?A diagram shows STRUCTURE but not SEQUENCE — without a walked-through data flow, a reader can't tell whether step 3 happens before or after step 5, or what triggers what
Key design decisions, with rationaleWhy THIS choice over the real alternative?Undocumented decisions get silently "fixed" by a future reader who doesn't know they were deliberate — exactly the failure dsa/capstone_combined_mock_full_loop.html Round 4's rubric is built to catch when someone can't defend a choice under questioning
Known limitations / future workWhat's honestly still broken or unaddressed?A doc that only describes what works reads as either dishonest or unaware — and this section is exactly where systems/capstone_load_testing.html's actual bottleneck findings belong, not buried in a chat log
Interview-ready definition: a good architecture doc is organized around the questions a NEW reader actually has (what is this, how do the pieces connect, what happens when, why this design, what's still broken) — not a chronological account of how it was built. If a section could only be understood by someone who already watched the system get built, it belongs in a changelog, not the architecture doc.
02 — Boxes and arrows are necessary, never sufficient

Drawing a component diagram that actually communicates

Start here, before drawing a single box. Think about a subway map versus a street map of the same city. A street map shows every road at true scale — accurate, but useless for "how do I get from here to there," because it doesn't distinguish a fast express line from a local one that stops everywhere. A subway map deliberately DISTORTS geography to make the thing that actually matters — which lines are fast, where you transfer — immediately visible. A good architecture diagram makes the same trade: it isn't a literal picture of file layout, it's a picture of the distinctions that actually change how a reader should reason about the system.

Distinction a real diagram must showWhy "just boxes and arrows" hides it
Synchronous call vs. asynchronous / fire-and-forgetA solid arrow that looks identical whether the caller BLOCKS waiting for a reply or moves on immediately hides exactly the trade-off evals-and-observability/capstone_dashboard_integration.html's own practice problem 1 debates for score_run() — a reader can't reason about latency impact without knowing which arrows block
In-process call vs. a real network hopAn in-process Python function call and an HTTP or MCP protocol call to a different service both look like "A talks to B" in a naive diagram, but only one of them can time out, retry, or fail independently — capstone_orchestrator_integration.html section 3's deliberate choice to dispatch to the co-located MCP server AS IF it were remote (through the protocol layer, not a direct import) is invisible unless the diagram marks that edge as a protocol call, not a plain function call
Which component owns which piece of stateIf two boxes both "talk to" a database-shaped box with no further detail, a reader can't tell that Redis and Postgres serve genuinely different roles (ephemeral run state vs. durable trace/eval history, per capstone_orchestrator_integration.html problem 1) — ownership needs its own visual distinction, not just a generic "data" arrow
Practical conventions worth adopting for every diagram in this doc: solid arrow = synchronous call, caller blocks for a reply dashed arrow = asynchronous / fire-and-forget, caller proceeds thick border = a real network hop (HTTP, MCP protocol, DB wire protocol) thin border = in-process call (regular Python function call) color grouping = which subsystem owns this component (app-layer, MCP tools, storage, observability)
Interview-ready definition: a component diagram is doing its job when a reader who has never seen the code can correctly answer "if this box goes down, what breaks, and does the caller notice immediately or eventually" — which requires the diagram to distinguish blocking from non-blocking calls and in-process from networked calls, not just show that two things are connected.
03 — This repo's own capstone, documented for real

Worked example: this capstone's architecture doc

Start here, before writing your own from scratch. Applying section 1's five sections to the actual system Weeks 1-2 built.

Context / goals

The capstone is a chat-driven agent service: a client sends a message, an orchestrator decides which tools to call (including a hybrid search tool over a document corpus), composes a reply, and every run is fully traced and scored for later inspection via a dashboard. Explicit non-goals: this is not a multi-tenant SaaS product (no auth/billing layer), and it does not need to support real-time streaming responses — the interaction model is request/response per turn, per backend/capstone_scaffold_fastapi_mcp.html's original scope.

Component diagram

See section 4 below for the full interactive diagram — summarized here: a FastAPI app (capstone_scaffold_fastapi_mcp.html) exposes POST /chat, which calls a stateless orchestrator (mcp-and-agents/capstone_orchestrator_integration.html) backed by Redis for in-flight run state. The orchestrator dispatches to MCP tools — including hybrid search (storage-and-rag/capstone_hybrid_search_integration.html) — mounted in the same process but reached through the real MCP protocol layer, not a direct function call. Every step is instrumented (evals-and-observability/capstone_dashboard_integration.html), writing traces, spans, and eval scores into Postgres per the finalized schema (database/capstone_schema_finalization_and_indexes.html), which a separate dashboard reads.

Data flow (the core use case: a new chat message)

  1. Client POST /chat with no run_id — a new run
  2. The route (thin, per capstone_orchestrator_integration.html section 2) calls orchestrator.step()
  3. The orchestrator starts a trace, routes the message to a tool decision, and dispatches to hybrid_search over the MCP protocol
  4. The search tool queries its index and returns fused, ranked results
  5. The orchestrator composes a reply from the results, saves run state to Redis, and calls score_run() — writing spans and an eval score to Postgres
  6. The route returns the reply and run_id to the client

Key design decisions, with rationale

  • Redis for run state, Postgres for traces/evals — access pattern split (high-write/disposable vs. low-write/durable), per capstone_orchestrator_integration.html problem 1.
  • The orchestrator calls its own co-located MCP server through the protocol, not a direct import — keeps every tool call, internal or external, on one instrumentable, schema-validated path, per that lab section 3.
  • Eval scoring happens inline, in the same traced step — a score with no trace behind it is untrustworthy, per capstone_dashboard_integration.html section 1.

Known limitations / future work

  • Load testing (systems/capstone_load_testing.html) found the orchestrator's Redis lock becomes the binding constraint above roughly 140 concurrent users — the atomic-operation fix from capstone_orchestrator_integration.html problem 2 raises this ceiling but doesn't eliminate contention entirely.
  • The three integration bug classes fixed in backend/capstone_debugging_integration_issues.html (state races, schema drift between tool and orchestrator, silent instrumentation gaps on new early-return paths) are exactly the class of bug most likely to recur as new code paths get added — worth a standing review checklist, not a one-time fix.
  • No authentication or multi-tenancy — explicitly out of scope per the stated goals, but the first thing that would need designing before any real deployment beyond this capstone's own scope.
What separates this from a README: every claim above is traceable to a specific lab and, where relevant, a specific practice problem — "why Redis" isn't asserted, it's pointed at the actual reasoning that produced the decision. A reader who wants to go deeper always has somewhere concrete to go; a reader who just wants the shape gets it from the five sections alone.

Practice problems

Problem 1 · Adding a new component: a response cache

Suppose the capstone adds a response cache in front of the orchestrator — identical (run_id, message) pairs within a short window return a cached reply without re-invoking the orchestrator at all. Where does this box go in section 4's diagram, what kind of edges does it need (per section 2's conventions), and what does it change about the data flow section 3 walked through?

Show solution
Placement: between the FastAPI route and the orchestrator -- the cache needs to intercept a request BEFORE it reaches the orchestrator (a cache hit should skip orchestrator.step() entirely, not just skip part of it), so the route now has a conditional edge: check the cache first, and only call the orchestrator on a miss. This is a real structural change to the diagram, not just a new box floating nearby -- the existing solid edge from route to orchestrator becomes a solid edge from route to cache, with a NEW conditional solid edge from cache to orchestrator only on a miss, and a new solid edge from cache directly back to the route on a hit (bypassing the orchestrator, Redis, and the MCP tool layer entirely for that request). Edge type: solid and thick-bordered if the cache is a separate service (e.g. a real Redis-backed cache, a genuine network hop, matching section 2's "network hop" convention) -- or solid and thin-bordered if it's an in-process LRU cache inside the FastAPI app itself. This is exactly the kind of distinction section 2 argues a real diagram must make explicit, since the two choices have completely different failure modes (an in-process cache is invisible to other workers, exactly capstone_orchestrator_integration.html section 1's stateless-orchestrator argument working in reverse -- a per-worker cache would give DIFFERENT workers different cache-hit behavior for the same request). What changes in the data flow: step 2 in section 3's walkthrough ("the route calls orchestrator.step()") becomes "the route checks the cache; on a hit, skip to step 6 with the cached reply; on a miss, proceed as before" -- and critically, a cache hit means NO new trace or eval_result gets written for that turn (since the orchestrator, where instrumentation lives, per capstone_dashboard_integration.html section 1, never runs) -- worth flagging explicitly as a NEW known limitation in the doc's final section: cached responses are invisible to the eval/tracing dashboard unless the cache layer gets its own, separate instrumentation hook, echoing exactly the "instrumentation near the top of the function, not the bottom" lesson from backend/capstone_debugging_integration_issues.html section 4, now applied one layer higher in the stack.
