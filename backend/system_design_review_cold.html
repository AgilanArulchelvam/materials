01 — Cold recall, no notes

URL shortener design, re-derived

Do this before opening anything below. Set a timer for 5-8 minutes. On paper or out loud, answer every bullet in the prompt below as if you were in an actual interview, with nobody to check your work until you're done. Resist the urge to peek at the answer partway through — a half-attempt you bail out of early trains recall much less effectively than a full attempt you complete imperfectly.

Prompt — attempt cold first

Without looking anything up, sketch the URL shortener:

  • What's the short-code encoding scheme, and what alphabet/length does it use?
  • What's the storage schema — what columns, what's the primary lookup key?
  • How do you handle collisions between two different long URLs generating the same short code?
  • Is this workload read-heavy or write-heavy, and how does that shape the design?
Reveal the answer (only after you've actually attempted it)
ENCODING SCHEME: base62 encoding (alphabet 0-9, a-z, A-Z — 62 characters) applied to an auto-incrementing integer ID. A new long URL gets the next ID from a counter (a DB auto-increment column, or a distributed ID generator like Snowflake if sharded across multiple DB nodes), and that ID is base62-encoded via repeated division/remainder into the short code string. A 6-character base62 string covers 62^6 ≈ 56.8 billion unique codes — comfortably enough for a service issuing tens of millions of new links per day for years. STORAGE SCHEMA: intentionally almost trivial, because the workload is a pure key-value lookup, not a relational one: short_code (PK, indexed) | long_url | created_at | expires_at (nullable) The primary (and often ONLY) lookup pattern is "given short_code, return long_url" — a single indexed point lookup. This is exactly the shape a key-value store (Redis, DynamoDB) or a simple indexed relational table handles well; there's little need for joins or complex relational structure. COLLISION HANDLING: base62-encoding a UNIQUE integer is a deterministic bijection — every distinct integer maps to exactly one distinct base62 string and vice versa, so encoding a genuinely unique ID can never collide with another genuinely unique ID's encoding. This is why counter+base62 is preferred over hashing the long URL directly: a truncated hash of the URL is a many-to-one mapping, so two different long URLs CAN hash to the same short code, requiring detect-and-retry collision-handling logic on every write. Counter-based IDs sidestep that problem entirely, structurally, not just probabilistically. READ VS WRITE: overwhelmingly read-heavy. Every short link, once created, gets looked up (redirected) far more times than it was ever written — often by orders of magnitude. This shapes the whole design toward optimizing reads: aggressive caching of hot short_code → long_url mappings (e.g. an in-memory cache or CDN edge cache in front of the DB), and accepting that writes (creating a new short link) can be comparatively slower and less optimized, since they're rare relative to reads.
What "re-derive cold" is testing: not whether you memorized the base62 arithmetic verbatim, but whether you can reconstruct WHY counter+base62 was chosen over hashing, and connect the read-heavy workload shape to the caching decisions that follow from it — the reasoning chain, not the trivia.
02 — Cold recall, no notes

Rate limiter design, re-derived

Do this before opening anything below. Same rules: timer, full attempt, no peeking until you're done.

Prompt — attempt cold first

Without looking anything up, sketch the rate limiter:

  • Name at least two algorithms and explain the concrete difference between them (not just names).
  • What specific flaw does fixed window have that sliding window fixes?
  • Why does running the rate limiter across multiple server instances break a naive, per-instance implementation?
  • What does an atomic, shared implementation actually look like?
Reveal the answer (only after you've actually attempted it)
ALGORITHMS: token bucket and sliding window (fixed window is a third, usually presented as the naive baseline both others improve on). - Token bucket: a bucket holds up to `capacity` tokens, refills at a steady `rate` (e.g. 1 token/second), and every request consumes one token. If the bucket is empty, the request is rejected. This naturally allows short bursts (spend the whole bucket at once) while still enforcing a long-run average rate (the refill rate). - Sliding window: counts requests within a continuously moving lookback window (e.g. "the last 60 seconds, right now," not "this fixed 60-second bucket"), so the count at any instant reflects a true rolling window rather than a fixed, resettable one. FIXED WINDOW'S FLAW: a fixed window resets its count at a hard boundary (e.g. exactly on the minute). A client can send the full limit right before the boundary and the full limit again right after — e.g. 5 requests at 9:00:59 and 5 more at 9:01:00, 10 requests in about 1 real second, while each individual 60-second bucket still shows exactly 5, technically satisfying the rule as literally written. Sliding window looks back continuously from the current moment, so it would see all 10 requests within its 60-second lookback and correctly reject the excess — there's no clock-aligned boundary to exploit. WHY MULTIPLE INSTANCES BREAK A NAIVE IMPLEMENTATION: if each server instance keeps its own local, in-memory counter, a client hitting 3 different instances behind a load balancer effectively gets 3x the intended limit — each instance only sees and limits its own slice of that client's traffic, with no shared knowledge of the other instances' counts. Even a shared external store (e.g. Redis) isn't automatically safe: a naive GET-check-SET sequence run from multiple instances at nearly the same moment is a race condition — two instances can both GET the same pre-increment count, both see it under the limit, and both allow a request that together should have been rejected. WHAT AN ATOMIC IMPLEMENTATION LOOKS LIKE: the check-and-increment has to happen as a single atomic operation against the shared store, not as separate read-then-write steps in application code. E.g. Redis's INCR (atomically increments and returns the new value in one operation) or a Lua script executed atomically inside Redis that checks the current count against the limit and increments it in one indivisible step — eliminating the window where two instances could both read a stale pre-increment value.
What "re-derive cold" is testing: whether you can name the actual race condition (not just say "it needs to be distributed"), and whether you know WHY atomicity — not just "using Redis" — is the thing that fixes it. "We put it in Redis" without INCR or a Lua script is still broken.
03 — Cold recall, no notes

Notification service design, re-derived

Do this before opening anything below. Same rules: timer, full attempt, no peeking until you're done.

Prompt — attempt cold first

Without looking anything up, sketch the notification service:

  • Synchronous vs queue-based fan-out — what's the actual difference, and which do you pick?
  • What happens when a single delivery attempt to one channel fails? Walk the full retry sequence.
  • Why does a dead-letter queue exist instead of just dropping a permanently-failing message?
  • Why can't email, push, and SMS just receive "the same string"?
Reveal the answer (only after you've actually attempted it)
SYNCHRONOUS VS QUEUE-BASED FAN-OUT: synchronous fan-out has the producer (e.g. the order service) directly call each channel handler in sequence, waiting for each to finish before calling the next — a slow or down channel (e.g. a flaky SMS vendor) delays every channel after it and keeps the producer's own request open the whole time. Queue-based fan-out has the producer publish the event ONCE to a message broker (Kafka, SQS, RabbitMQ); each channel handler independently subscribes and pulls its own copy whenever it's ready. The producer's job ends the instant it publishes — it never waits on any handler. Queue-based is the correct default: it decouples the producer's latency/availability from every downstream channel's latency/availability. RETRY SEQUENCE ON FAILURE: exponential backoff, not instant or fixed-interval retry. Attempt 1 fails → wait ~1s → attempt 2 fails → wait ~2s → attempt 3 fails → wait ~4s, doubling each time, up to a max attempt count (commonly 3-5). This spaces retries out enough to let a transient failure (a momentary provider blip) clear, instead of hammering an already-struggling provider in a tight loop. After the max attempt count is exhausted, the message moves to a dead-letter queue rather than being retried forever or discarded. WHY A DLQ EXISTS: it solves two problems simultaneously. First, it stops the message from consuming retry-worker capacity forever — some failures are PERMANENT (a malformed payload, a deleted account, an invalid phone number), not transient, and no amount of retrying fixes a data problem. Second, it avoids silently dropping the message — the full payload, recipient details, and failure history are preserved intact for human inspection, so if the root cause turns out to be fixable (e.g. a phone number formatting bug), the DLQ'd messages can be reprocessed and delivered late, rather than being unrecoverably lost. WHY CHANNELS CAN'T SHARE ONE STRING: each channel has its own format, transport, and hard constraints. Email needs a full HTML template with a subject line and often a legally-required unsubscribe footer, sent via SMTP or an email API. Push needs a short title+body plus a structured deep-link payload, capped at a few KB, sent via APNs/FCM. SMS is plain text only, capped at 160 characters per segment, sent via a telephony API like Twilio. Sending one raw HTML email body as an SMS blows the character limit instantly; sending the same body as a push payload blows the payload size cap. Each channel needs its own rendering of the same underlying logical notification, and each has genuinely different failure modes (bounces vs expired tokens vs invalid numbers) that must be tracked independently, not as one aggregate success/failure flag.
What "re-derive cold" is testing: whether you can actually name the exponential backoff formula (roughly doubling, capped attempts) rather than gesturing at "it retries a few times," and whether you can articulate the TWO distinct problems a DLQ solves — most people only remember one.
04 — The question interviewers actually care about

What breaks first at 10x scale, across all three

Start here, before the table. "Design X" is only half the interview. The other half is almost always "now imagine X is 10x more successful than you designed it for — what falls over first, and why?" This question tests whether you understand your OWN design's actual bottleneck, not just whether you can draw the boxes. A design that "works" at the scale you sketched it for but that you can't reason about under load is, in a real interview, treated as a design you don't actually understand.

SystemPrimary bottleneck at 10xWhy, specifically
URL shortener KV store read throughput / hot-key contention The workload is overwhelmingly read-heavy, and popular short links follow a power-law distribution — a small number of viral links receive a disproportionate share of all traffic. At 10x scale, those specific "hot" keys can exceed what even a well-provisioned single cache node or DB shard can serve, regardless of how well the overall system scales horizontally, because the load isn't evenly distributed across keys — it's concentrated on a handful of them.
Rate limiter The shared counter store itself becomes the bottleneck Correct distributed rate limiting requires every instance to check against ONE shared, atomically-updated counter (e.g. Redis INCR). At 10x request volume, that shared store now has to handle 10x the atomic increment operations, on the same central resource that every other request across every instance must also serialize through — the very mechanism that makes rate limiting correct under concurrency is also a single chokepoint that doesn't scale away just because you add more application servers.
Notification service Fan-out amplification and retry-storm risk Each single logical event fans out to multiple channel handlers, so 10x more events means 10x more fan-out work across every channel simultaneously — not a 10x increase in one place, but roughly 10x increase in N places (email queue, push queue, SMS queue) at once. Worse, if a downstream provider (e.g. an email vendor) can't absorb 10x traffic and starts failing, EVERY failing send schedules a retry with backoff — at 10x volume, that's 10x the messages re-queuing and re-attempting, which can produce a thundering-herd "retry storm" that hits the already-struggling provider even harder right as it's trying to recover, a self-reinforcing failure the original design didn't have to reckon with at 1x scale.
The pattern across all three: in each case, the bottleneck at 10x is NOT "we need more servers" — it's a specific shared resource or distribution-shape problem that horizontal scaling of the application layer alone doesn't fix: a hot key inside a KV store, a single atomic counter every request must serialize through, and a retry mechanism that amplifies under exactly the conditions (a struggling downstream provider) it's supposed to handle gracefully. Recognizing "which shared resource does NOT scale linearly with request count" is the actual skill being tested by "what breaks at 10x."
Now work through it yourself

Practice problems

Work each one out before expanding the solution. These go one level past the cold-recall prompts above — they ask you to reason ACROSS the three designs, not just reproduce one.

Problem 1 · Applying the URL shortener's hot-key fix to a different system

The standard fix for the URL shortener's hot-key problem is an in-memory or CDN-edge cache in front of the KV store for popular codes. Would the same fix help the rate limiter's shared-counter bottleneck at 10x scale? Why or why not?

Show solution
No, and the reason exposes a real conceptual difference between the two bottlenecks. The URL shortener's hot key is a READ-heavy problem: the same long_url is being read over and over, and caching a read is safe because the value doesn't need to change on every access — you can serve a slightly stale cached copy and it's still correct (a URL redirect target essentially never changes after creation). The rate limiter's shared counter is fundamentally a WRITE problem: every single request has to both READ the current count AND ATOMICALLY increment it, and the entire correctness of the rate limiter depends on that count being exactly right at every instant — that's the whole point of the atomicity requirement covered in section 2. Caching a rate-limit counter would mean serving a stale, already-outdated count, which directly reintroduces the race condition the atomic store was built to prevent (two instances both checking a stale cached count, both seeing "under limit," both allowing a request that together exceeds it). Caching helps read-heavy, rarely-changing data; it actively breaks a write-heavy, must-be-exactly-current counter.
Problem 2 · Comparing failure isolation across all three designs

Rank the URL shortener, rate limiter, and notification service by how badly a SINGLE COMPONENT failure (e.g. one downstream dependency going down) cascades through the rest of the system, and justify the ranking.

Show solution
Best isolated → worst isolated: URL shortener, then notification service, then rate limiter (worst). URL shortener: a single failed lookup affects only that one request — one user gets a broken redirect. There's no fan-out and no shared mutable state that a failure corrupts for OTHER requests; each lookup is independent. Notification service: a failure in ONE channel (e.g. the email provider going down) is explicitly isolated by design — per-channel retry queues mean an email outage's growing backlog doesn't consume the SMS or push queues' capacity, and each channel's DLQ is separate. Failure is contained to that one channel, though within that channel, a bad enough outage can still cause a retry storm as covered in section 4. Rate limiter: worst isolation, because EVERY request across every instance and every client depends on the SAME shared counter store being available and fast. If that shared store goes down or becomes slow, it doesn't just degrade one feature — it potentially blocks or corrupts the gating logic for literally all traffic through the system, since the rate limiter sits in the critical path of every request it protects. A single shared dependency with system-wide reach is inherently the worst-isolated failure mode of the three.
Problem 3 · Choosing what to over-provision given a fixed budget

You're told to expect 10x growth over the next year but can only proactively harden ONE of the three systems' bottlenecks ahead of time due to limited engineering time. Which would you prioritize, and what's your reasoning?

Show solution
There's no single universally "correct" answer here — this is a judgment call an interviewer wants you to REASON about, not a fact to recall — but a defensible answer: prioritize the rate limiter's shared counter store, because of problem 2's finding: it's the worst-isolated of the three, sitting in the critical path of every request, so its failure mode has the largest blast radius. Hardening options include sharding the counter store by client ID (so no single node has to absorb 100% of the atomic-increment traffic), or accepting a slightly relaxed correctness model (e.g. a short-lived local cache with periodic reconciliation) that trades perfect precision for surviving 10x load without becoming a single chokepoint for all traffic. An equally defensible alternative answer: prioritize the URL shortener's hot-key problem, on the reasoning that it's the cheapest and most mechanical fix (add a cache layer) with the most predictable payoff, so it's the best use of limited engineering time even if its failure mode is less severe — "harden the cheap, well-understood fix first" is a legitimate prioritization strategy too. What matters in an interview setting is naming a real trade-off (blast radius vs. cost/certainty of the fix) and reasoning about it explicitly, not landing on one "right" system.
Problem 4 · Spotting a design that silently conflates two of the three bottleneck types

A candidate says: "for the rate limiter at 10x scale, I'd just add a caching layer in front of Redis, same as I would for the URL shortener's hot keys." What's wrong with this answer, and what should the candidate have said instead?

Show solution
This is exactly the mistake identified in Problem 1: it applies a read-heavy caching fix to a bottleneck that is fundamentally a write/ atomicity problem, not a read problem. A cache in front of the rate limiter's counter would mean requests reading a POSSIBLY STALE count — which reintroduces the exact race condition (two instances both seeing an outdated "under limit" count and both allowing traffic that together exceeds it) that using an atomic shared store was meant to eliminate in the first place. The fix isn't wrong because caching is bad in general — it's wrong because it was copy-pasted from a different bottleneck SHAPE without noticing the shapes don't match. What the candidate should have said instead: since the counter's correctness depends on atomicity, not just availability, the actual 10x-scale fixes have to preserve atomicity while spreading load — e.g. sharding the counter keyspace across multiple Redis instances (by client ID or API key, so no single instance absorbs all traffic), using a purpose-built distributed rate-limiting service, or relaxing to an approximate/eventually-consistent counting scheme ONLY if the product can tolerate slightly imprecise limits in exchange for surviving load — a conscious trade-off, not an accidental one introduced by treating this like a caching problem.
Problem 5 · Cold re-derivation of a fourth system, using the same recall method

Using the exact same "prompt, attempt cold, then reveal" structure from sections 1-3 of this lab, write the prompt (not the answer) you'd use to cold-test yourself on a system you haven't designed yet this month: a URL shortener's close cousin, a "paste bin" / pastebin-style service. What 3-4 questions would you ask yourself?

Show solution
A reasonable cold-recall prompt for a pastebin service, following the same shape as this lab's three prompts (specific enough to force a real design decision, not so open-ended that a vague answer can dodge it): "Without looking anything up, sketch a pastebin service: - What's the ID/short-link scheme for a new paste, and does the same counter+base62 reasoning from the URL shortener apply here, or does something about pastebin change that calculus? - Where does the actual PASTE CONTENT get stored -- in the same relational row as the metadata, or somewhere else -- and why? (Hint: think about typical paste size vs typical URL length.) - Does this workload skew read-heavy like the URL shortener, or does write volume matter more here? What's actually different about who creates pastes vs who reads them? - What expiration/deletion behavior does a pastebin need that a URL shortener usually doesn't, and how does that change the schema?" The value of writing your OWN prompt like this (rather than just being handed one) is that it forces you to first identify which parts of a familiar design (URL shortener) genuinely transfer to a new but similar system, and which parts don't -- e.g. paste CONTENT is typically much larger than a URL, which pushes toward storing it in blob storage (S3) with only a reference in the relational/KV row, a divergence a lazy "it's basically the same as the URL shortener" answer would miss entirely.
