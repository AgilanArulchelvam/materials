01 — A schema both sides already agree on

Protocol Buffers as the wire format

Start here, before any schema. Imagine two people who've agreed in advance on a very specific form: "field 1 is always your name, field 2 is always your age, field 3 is always your email." Once both sides have that form memorized, you don't need to write "name:", "age:", "email:" on every single submission — you can just send the values in the agreed field-number order, and the other person already knows what each one means. JSON is like re-writing the field labels every single time; protobuf is like both sides having already memorized the form.

A .proto file defines a message schema with explicit field numbers, and a compiler generates code in whatever language you're using to serialize/deserialize messages matching that schema. Both the client and server compile the SAME .proto file, so both sides know exactly what field number 1 means without ever needing to transmit the word "name" over the network.

// user.proto message User { string name = 1; int32 age = 2; string email = 3; }

Why protobuf is smaller — mechanically

Field names ("name", "age", "email") are NEVER transmitted — only small integer field-number tags plus a wire-type byte, then the raw value bytes. Integers are varint-encoded (small numbers use fewer bytes), and there's no repeated punctuation (quotes, colons, braces, commas) at all.

Why JSON is larger — mechanically

Every single field name is spelled out as a literal string, in full, on every single message — "name", "age", "email" cost real bytes each time, even though both sides already "know" the schema at the application level. JSON is also text-based, so even numbers are stored as their full decimal digit characters, not compact binary.

The trade-off this buys you: protobuf's compactness costs you human-readability — you cannot open a protobuf message in a text editor and read it the way you can with JSON; you need the .proto schema and a decoder to make sense of the bytes at all. This is a genuine debugging cost, which is part of why REST/JSON remains dominant for public-facing APIs where ad-hoc inspection (curl, browser devtools, Postman) matters a lot.
Interview-ready definition: Protocol Buffers (protobuf) is a binary serialization format where a shared .proto schema assigns each field a small integer number; messages on the wire contain only those field numbers (as compact tags) and their raw values — never the field names themselves — combined with variable-length integer encoding for numeric fields. This produces meaningfully smaller payloads than JSON for the same logical data, at the cost of the format no longer being human-readable without the schema, and requiring both client and server to compile and stay in sync with that same schema.
02 — Four different shapes of "call a function on another machine"

Unary vs streaming RPCs — all 4 types

Start here, before any diagrams. A phone call and a walkie-talkie conversation are structured completely differently, even though both are "talking to someone remotely." A phone call is one question, one answer, done. A walkie-talkie exchange might be one person continuously narrating updates while the other just listens, or both people talking back and forth freely whenever they each have something to say. gRPC gives you all of these shapes as first-class options, not just the simple phone-call one.

The detail worth remembering about bidirectional streaming: the two streams (client-to-server and server-to-client) are fully independent — neither side has to wait for a message on one stream before sending on the other, and message counts on each side don't need to match at all. This is possible specifically because gRPC runs over HTTP/2, whose multiplexed streams already support exactly this kind of independent, simultaneous flow in both directions.
Interview-ready definition: gRPC supports four RPC shapes built directly on HTTP/2 streams: unary (single request, single response — functionally like a normal function call), server-streaming (single request, a stream of responses over time), client-streaming (a stream of requests over time, single final response), and bidirectional-streaming (independent streams of requests and responses flowing in both directions simultaneously, with no fixed correspondence between message counts on each side).
03 — Efficiency isn't free, and REST isn't just "the old way"

When gRPC beats REST, and when it doesn't

Start here, before the table. A race car is objectively faster than a family sedan, but you wouldn't daily-drive a race car to pick up groceries — it needs premium fuel, specialized maintenance, and a place to actually go fast. gRPC's efficiency gains are real, but they come with real requirements (schema compilation, less casual debuggability, weaker browser support) that make it the wrong tool for plenty of common jobs.

Where gRPC genuinely wins

Internal service-to-service communication in a microservices architecture, where both sides are your own code (so schema coordination is easy), traffic volume is high enough that payload size and serialization speed actually matter, and you want strongly-typed contracts enforced by generated code rather than hand-maintained documentation.

Where REST/JSON is still the better call

Public-facing APIs consumed by many unknown third-party clients (JSON is universally parseable, curl-able, and human-readable without special tooling), browser-based clients calling your API directly (native browser gRPC support is limited — usually needs a proxy like gRPC-Web), and anywhere ad-hoc debuggability matters more than shaving bytes off the wire.

The interview trap, stated plainly: "gRPC is just strictly better and faster" is the wrong takeaway. It's better along specific, measurable axes (payload size, streaming ergonomics, contract strictness) that matter most for internal, high-volume, same-organization traffic — and it's actively worse along other axes (browser-native support, human debuggability, ecosystem ubiquity) that matter most for public APIs. The right answer to "gRPC or REST?" is almost always "it depends on who's calling this API and how often," not a blanket preference.
Interview-ready definition: gRPC is generally preferred for internal, high-throughput, same-organization service-to-service communication where both endpoints can share a compiled schema and streaming or strict typing add real value; REST with JSON remains preferred for public or browser-facing APIs where universal client compatibility, human-readability, and ad-hoc debuggability outweigh the bandwidth and serialization-speed advantages gRPC provides.

Problem 1 · Why field numbers instead of names

Explain concretely, in terms of actual bytes on the wire, why a protobuf message encoding {"user_id": 42} is smaller than the equivalent JSON, even though both "represent the same information."

Show solution
The JSON version must literally spell out the string "user_id" as UTF-8 bytes (7 characters plus surrounding quotes and a colon) every single time the field appears, because JSON has no separate schema -- the field name IS the only thing identifying what the value means. Protobuf instead assigns "user_id" a small integer field number (say, field 1) once, in the shared .proto schema that both sides already compiled against -- so on the wire, only a compact tag byte encoding "field 1, wire type varint" plus the value 42 (itself varint-encoded, likely 1 byte for a small number) needs to be sent. The English name "user_id" never travels over the network at all; it only exists in the schema file both sides already have. This is the core mechanical reason protobuf payloads shrink relative to JSON -- eliminating repeated field-name strings, not just switching text to binary.
Problem 2 · Picking the right RPC type

A service needs to let a client upload a very large file in small chunks, and only needs one final confirmation once the whole file has been received and validated. Which of the 4 RPC types fits, and why not the others?

Show solution
Client-streaming fits: many requests (the file chunks, sent over time) resulting in exactly one final response (the confirmation), which matches this scenario precisely. Unary doesn't fit because it only allows ONE request message -- you'd have to buffer the entire file into a single message before sending, defeating the purpose of chunked upload (memory pressure, no progress feedback, inability to handle files larger than a single message size limit). Server-streaming doesn't fit because it's the reverse shape -- one request, many responses -- which is backwards from "many chunks in, one confirmation out." Bidirectional-streaming COULD technically work (it's the most general shape) but is unnecessary complexity here -- the client never needs to receive a stream of responses back during the upload, only a single confirmation at the end, so client-streaming's simpler, more specific contract is the better fit and better documents the actual intent to anyone reading the .proto file.
Problem 3 · Recognizing where gRPC is the wrong choice

A team wants to expose a brand-new public API that any third-party developer, including ones building simple browser-based dashboards with plain JavaScript, can call directly. Should this API be built with gRPC? Explain the concrete obstacles.

Show solution
Building this as a plain gRPC API is a poor choice. Two concrete obstacles: (1) browsers cannot make native gRPC calls the way they can make a fetch() call to a REST/JSON endpoint -- gRPC relies on HTTP/2 trailers and framing details that browser fetch/XHR APIs don't expose, so direct browser gRPC requires an intermediate proxy layer (gRPC-Web) translating between what the browser can actually send and true gRPC, adding real infrastructure complexity; (2) third-party developers benefit enormously from being able to just curl an endpoint, read a JSON response in a browser tab, or use universally available HTTP tooling without needing to obtain and compile a .proto schema first -- a public API's value is partly its accessibility to unknown, varied clients, which is exactly REST/JSON's strength and exactly where gRPC's binary, schema-dependent format creates friction. REST/JSON (possibly documented via OpenAPI) is the better fit here.
Problem 4 · Bidirectional streaming message independence

In a bidirectional-streaming RPC powering a live chat feature, does the server need to send exactly one response for every one request the client sends? Explain why or why not.

Show solution
No. Bidirectional streaming's defining property is that the two streams (client-to-server and server-to-client) are fully independent -- there is no requirement that message counts match, or that a response corresponds to any particular request. In a chat scenario, the client might send 3 messages while the server, independently, pushes 7 messages from other users during that same window -- there's no 1:1 pairing at all. This is fundamentally different from unary or the other streaming types, which do have a fixed request/response cardinality (1:1, 1:many, or many:1). Bidirectional streaming is the one shape where both directions genuinely run on their own independent schedules, which is exactly why it's the right fit for chat-like, freely-flowing communication rather than any request-triggers-response pattern.
Problem 5 · Debuggability trade-off in practice

A team migrates their internal service-to-service API from REST/JSON to gRPC/protobuf and later complains that they can no longer quickly inspect request/response payloads with curl during incident debugging. Was this an unforeseeable side effect, or an inherent trade-off they should have anticipated?

Show solution
This is an inherent, well-known trade-off, not an unforeseeable surprise. Protobuf's entire size advantage over JSON comes specifically from NOT being human-readable text -- the field names are gone, numeric values are binary-encoded, and there's no plain-text structure to eyeball. Losing curl-and-eyeball debuggability is the direct, unavoidable cost of gaining that compactness; you cannot have both "smaller than JSON" and "as readable as JSON" from the same format, because the readability is precisely what protobuf strips out to save space. The team's mistake wasn't choosing gRPC -- for high-volume internal service-to-service traffic it's often a reasonable choice -- it was likely not investing in the standard mitigations upfront: tools like grpcurl (which can decode gRPC calls if given the schema or with server reflection enabled), structured logging of decoded payloads at the application layer, or a debugging proxy that decodes traffic using the .proto files. The debuggability cost is real and should be planned for before migrating, not discovered afterward.
