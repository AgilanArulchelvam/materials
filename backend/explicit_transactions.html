BACKEND & APIS LAB · EXPLICIT TRANSACTIONS

BEGIN opens a door. COMMIT locks it shut. ROLLBACK pretends it was never opened.

Autocommit mode quietly wraps every single statement in its own implicit transaction — which works fine until an operation needs more than one statement to make sense. This lab walks through the exact semantics of BEGIN, COMMIT, and ROLLBACK; builds an animated savepoint demo showing a partial rollback that undoes only part of an open transaction; and ends with the canonical money-transfer example proving, side by side, why multi-step operations that must succeed or fail together need an explicit transaction boundary around them.

01 — What BEGIN, COMMIT, and ROLLBACK actually do

BEGIN / COMMIT / ROLLBACK semantics

Start here, before any SQL. Think about editing a shared document with "track changes" and a big "accept all" / "reject all" button. The moment you start typing, you're in a draft state — your edits are visible to you, but the document's official, shared version hasn't changed yet. Click "accept all" and every edit you made since you started becomes permanent, visible to everyone. Click "reject all" instead, and the document snaps back exactly to how it looked before you touched it — as if you'd never opened the editor at all. An explicit database transaction is that same draft-then-decide model, applied to writes against a database.

By default, most database connections run in autocommit mode: every single SQL statement is automatically its own implicit transaction, committed the instant it finishes. That's fine when each statement stands alone. It breaks down the moment two or more statements need to be treated as a single unit of work — which is exactly what explicit transactions are for.

BEGIN; -- or START TRANSACTION; opens a new transaction, ending autocommit for what follows UPDATE accounts SET balance = balance - 50 WHERE id = 1; UPDATE accounts SET balance = balance + 10 WHERE id = 1; COMMIT; -- makes both UPDATEs permanent and visible to everyone else, together -- ...or, instead of COMMIT: ROLLBACK; -- discards BOTH UPDATEs entirely, as if neither one ever ran

Precisely: BEGIN opens a new transaction — every statement that follows is provisional, visible to the connection that made it but not yet durably recorded or visible to other transactions. COMMIT makes every change made since BEGIN permanent in one atomic step — durably written to disk and now visible to other transactions reading the same rows. ROLLBACK discards every change made since BEGIN, in full — the affected rows return to exactly their pre-BEGIN state, with no partial effect left behind, regardless of how many statements ran in between.

Interview-ready definition: BEGIN (equivalently START TRANSACTION) suspends autocommit and opens a transaction boundary; every statement afterward is provisional until explicitly resolved. COMMIT durably and atomically applies every change made since BEGIN, making it permanent and visible to other transactions. ROLLBACK discards every change made since BEGIN in its entirety, returning affected rows to their exact pre-BEGIN state — there is no such thing as "partially" committing or rolling back a plain transaction with no savepoints; it is all-or-nothing by definition.
02 — A middle ground between "undo everything" and "undo nothing"

Nested transactions, in practice: SAVEPOINT

Start here, before the SQL. Picture writing a long email with several paragraphs. You get to paragraph 4, realize it's garbage, and want to delete just that paragraph — not undo your way back through paragraphs 1, 2, and 3 as well. A savepoint is exactly that: a bookmark you drop partway through your work so that if something later goes wrong, you can rewind to JUST that bookmark, not all the way back to a blank page.

A common misconception is that databases support true "nested transactions" — a BEGIN inside another BEGIN, each with its own independent commit/rollback. Most databases don't actually work that way. What they offer instead is SAVEPOINTS: named markers you can drop at any point inside a single top-level transaction, and later roll back to, undoing only the work done after that marker while leaving everything before it — including the still-open outer transaction — completely intact.

BEGIN; UPDATE inventory SET qty = qty - 1 WHERE sku = 'A100'; -- step 1 SAVEPOINT sp1; -- bookmark dropped here UPDATE inventory SET qty = qty - 1 WHERE sku = 'B200'; -- step 2 -- something goes wrong here (e.g. B200 is actually out of stock) ROLLBACK TO SAVEPOINT sp1; -- undoes ONLY step 2 UPDATE inventory SET qty = qty - 1 WHERE sku = 'C300'; -- step 3, a substitute item COMMIT; -- commits step 1 AND step 3 together; step 2 never happened

The critical distinction: ROLLBACK TO SAVEPOINT sp1 is NOT the same as ROLLBACK. A full rollback discards everything since BEGIN. A rollback to a savepoint discards only what happened after that specific savepoint was set — step 1 (the A100 update) survives, uncommitted but preserved, and the transaction stays open, free to keep going with more statements and eventually commit normally.

Not the same as rolling back the whole transaction: if step 2 fails and you call a FULL ROLLBACK instead of ROLLBACK TO SAVEPOINT sp1, you lose step 1 as well — the entire transaction is discarded and you'd have to start completely over, re-running even the parts that were fine. A savepoint exists specifically to avoid that: undo-this-part-only, without losing earlier work still sitting in the same open transaction.
Interview-ready definition: most relational databases don't support true nested transactions with independently commit/rollback-able sub-transactions; instead they offer SAVEPOINT, a named marker inside a single top-level transaction. ROLLBACK TO SAVEPOINT <name> undoes only the statements executed after that savepoint was set, while preserving everything before it and keeping the outer transaction open — giving you a middle ground between committing everything and discarding everything, useful for scenarios like "try a sub-step, and if it fails, back out just that sub-step and try an alternative, without losing the work done earlier in the same transaction."
03 — Two statements that must live or die together

Wrapping multi-step operations atomically: the money transfer

Start here, before the demo. Imagine physically handing someone $100 in cash. There's no in-between state where the money has left your hand but hasn't yet arrived in theirs — it's one motion. Now imagine that same transfer as two separate mail packages: one package removes $100 from your account statement, a second separate package adds $100 to theirs. If the first package arrives and the second gets lost in the mail, $100 has simply vanished from existence — not stolen, not misdelivered, just gone, with no record of where it went. That's exactly the failure mode two unwrapped, independently-autocommitted UPDATE statements create.

Transferring $100 from account A to account B requires two statements:

UPDATE accounts SET balance = balance - 100 WHERE id = 'A'; -- debit UPDATE accounts SET balance = balance + 100 WHERE id = 'B'; -- credit

These two statements MUST happen together as a single atomic unit, or not at all. If the debit succeeds and commits on its own, and then the credit fails for any reason (a dropped connection, a constraint violation, the process crashing), the $100 that left A is simply gone — it was never conditionally reserved, it was permanently subtracted the instant that first UPDATE committed under autocommit. Wrapping both statements in BEGIN ... COMMIT makes them one indivisible operation: if the credit fails, the whole transaction (including the already-run debit) rolls back, and A's balance is restored as if nothing had been attempted.

Without a transaction

Each UPDATE is its own autocommit transaction. The debit commits immediately and permanently. When the credit then fails, there is nothing left to roll back — the debit already happened for real. Result: $100 has permanently vanished from the system, a real, unrecoverable-without-manual-intervention data integrity bug.

With a transaction

Both UPDATEs happen inside one BEGIN...COMMIT boundary. The debit is only provisional until COMMIT. When the credit fails, the whole transaction rolls back — including the already-run debit — so A's balance is restored exactly. Result: either both changes land, or neither does. The total is correct at every observable moment.

Interview-ready definition: wrapping a multi-step operation in an explicit transaction (BEGIN ... COMMIT) makes those steps atomic — they succeed or fail as a single indivisible unit. Without that boundary, each statement is its own autocommit transaction, so a failure partway through a logically-multi-step operation leaves some statements permanently applied and others not, an inconsistent partial state that has to be manually detected and repaired (or, worse, goes unnoticed). This is precisely why the canonical money-transfer example always debits one account and credits another inside a single transaction — the two writes are only meaningful together.

Problem 1 · Tracing a BEGIN/UPDATE/UPDATE/COMMIT-or-ROLLBACK sequence

A row starts at balance = 400. The sequence runs: BEGIN; UPDATE ... SET balance = balance - 50; UPDATE ... SET balance = balance - 25; ROLLBACK;. What is the final value of balance, and what would it have been if the last statement were COMMIT instead?

Show solution
With ROLLBACK: balance ends at 400, exactly where it started. Both UPDATEs ran and, within the open transaction, temporarily moved the value to 350 then 325 -- but ROLLBACK discards every change made since BEGIN in full, so the row reverts to its pre-BEGIN value of 400 as if neither UPDATE had ever executed. No partial effect (e.g. only the first UPDATE surviving) is possible with a plain rollback and no savepoints. With COMMIT instead: balance ends at 325 (400 - 50 - 25), and that value becomes permanent and visible to every other transaction reading that row from that point on.
Problem 2 · Tracing a savepoint partial-rollback sequence by hand

A row starts at qty = 10. The sequence runs: BEGIN; UPDATE ... SET qty = qty - 2; SAVEPOINT sp1; UPDATE ... SET qty = qty - 3; ROLLBACK TO SAVEPOINT sp1; UPDATE ... SET qty = qty - 1; COMMIT;. Predict the exact final committed value of qty, and explain which statements' effects actually survived.

Show solution
Final committed value: qty = 7. Trace: qty starts at 10. The first UPDATE (-2) runs before the savepoint, bringing qty to 8 -- this is the "before sp1" work. SAVEPOINT sp1 bookmarks this point (qty=8). The second UPDATE (-3) runs AFTER the savepoint, bringing qty to 5 -- but ROLLBACK TO SAVEPOINT sp1 undoes ONLY this second UPDATE, since it's the only statement that ran after the bookmark. qty reverts to 8 (the value at the savepoint), not to 10 (the value at BEGIN). The transaction is still open at this point, so a THIRD UPDATE (-1) then runs against that restored value of 8, bringing qty to 7. COMMIT makes 7 permanent. The -2 UPDATE's effect survived (it ran before the savepoint). The -3 UPDATE's effect was entirely undone (it ran after the savepoint and was rolled back to it). The -1 UPDATE's effect survived (it ran after the rollback-to-savepoint, as new work in the still-open transaction).
Problem 3 · Quantifying the money-transfer bug

Account A has $500 and Account B has $300 (total $800). Someone runs the two-statement $100 transfer as two separate autocommit statements (no transaction). The debit succeeds and commits. The credit then fails and is never retried. Precisely quantify what's wrong with the resulting state.

Show solution
After the failure: Account A = $400 (500 - 100, the debit committed for real), Account B = $300 (unchanged, the credit never landed), so the new total in the system is $700 -- exactly $100 less than the $800 that existed before the operation started. That $100 isn't sitting anywhere recoverable in the database; it was subtracted from A permanently the instant the debit's autocommit transaction committed, and never added anywhere else. This is a genuine, silent data integrity bug: nothing in the system flags an error state (both individual statements "succeeded" or predictably failed on their own terms), yet $100 has permanently vanished from the books. Fixing it after the fact requires manual reconciliation -- someone has to notice the total doesn't match, dig through logs, and manually credit A or otherwise account for the missing $100, which a database transaction would have prevented from ever happening in the first place.
Problem 4 · What "atomic" guarantees, and what it does NOT

A teammate says "since our transfer is wrapped in BEGIN...COMMIT, it's atomic, so we don't need to worry about a concurrent reader seeing a half-finished transfer." Is that reasoning correct? What exactly does atomicity guarantee, and what separate concern is being conflated with it here?

Show solution
The reasoning is subtly wrong, or at least imprecise, depending on the isolation level in use. Atomicity ONLY guarantees all-or-nothing execution from the transaction's own point of view: either every statement inside the BEGIN...COMMIT block takes effect, or none of them do -- there's no partial-completion outcome for the transaction itself. Atomicity says nothing on its own about what a DIFFERENT, concurrently-running transaction is allowed to observe WHILE the first transaction is still in progress (i.e., after the debit UPDATE has run inside the transaction but before COMMIT). That's the separate concern of ISOLATION -- a different one of the four ACID properties -- and whether a concurrent reader can see the debited-but-not-yet-committed intermediate state depends on the isolation level (e.g. Read Uncommitted would allow a dirty read of that in-progress state; Read Committed or stronger would not). Atomicity guarantees the transfer resolves as all-or-nothing eventually; it does not, by itself, guarantee that no one else can see it mid-flight -- that's what isolation levels are for, and it's a separate lever from the BEGIN/COMMIT/ROLLBACK mechanics covered in this lab.
Problem 5 · Designing a transaction boundary around an external API call

An order-checkout flow needs to: (1) reduce inventory for the purchased item, (2) call an external payment provider's API to charge the customer's card, and (3) insert a new row into an `orders` table marking the order as paid. Where should the transaction boundary (or boundaries) go, and specifically, why should you generally NOT hold a single open database transaction across the external payment API call?

Show solution
You generally should NOT wrap the external payment API call inside the same open database transaction as the inventory update and order insert, even though all three steps are logically part of one checkout. The core reason: a network call to an external service can be slow, or hang, or time out unpredictably -- and a database transaction that's still open holds locks on whatever rows it has already touched (e.g. the inventory row) for its entire duration. Holding those locks open while waiting on a slow or stalled third-party network call blocks every other transaction that needs those same rows, for however long that external call takes -- turning an external latency problem into a database-wide contention problem, and risking the database server's own connection/lock timeout limits being hit for reasons that have nothing to do with the database itself. A more robust design: call the payment provider FIRST, outside any open database transaction, and only once you have a definitive success/failure result back, open a short-lived transaction that atomically updates inventory AND inserts the paid order row together (steps 1 and 3, wrapped together since those two DB writes do need to succeed or fail as a unit). If the payment call fails, you simply never open that transaction at all -- no compensating rollback needed, since nothing was written yet. This also raises a related real-world wrinkle worth naming: what if the payment succeeds but the subsequent short DB transaction then fails for an unrelated reason (e.g. a constraint violation) -- since you can't roll back an external payment charge with a SQL ROLLBACK, this class of problem typically needs a separate reconciliation/retry mechanism (e.g. an idempotent order-creation retry, or a compensating refund), which is a different pattern than the plain BEGIN...COMMIT covered in this lab, but grows directly out of not being able to hold a DB transaction across a call the database has no control over.
