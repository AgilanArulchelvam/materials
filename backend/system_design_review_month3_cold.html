01 — Cold recall, no notes

Caching layer design, re-derived

Do this before opening anything below. Set a timer for 5-8 minutes. On paper or out loud, answer every bullet below as if you were in an actual interview, with nobody to check your work until you're done.

Prompt — attempt cold first

Without looking anything up, sketch a caching layer design:

  • Write-through vs write-back — what's the actual mechanical difference, and what does each trade away?
  • Walk through LRU eviction on a full cache when a new key needs a slot.
  • Why is perfect cache consistency fundamentally in tension with the reason a cache exists?
  • What's the actual write path for write-through, step by step?
Reveal the answer (only after you've actually attempted it)
WRITE-THROUGH VS WRITE-BACK: write-through writes to the cache AND the underlying database SYNCHRONOUSLY, as one logical operation, before the write is considered complete — the cache and the source of truth are never out of sync, but every write pays the database's full write latency, so caching doesn't speed up writes, only reads. Write-back writes to the cache immediately and returns, then asynchronously flushes to the database later (e.g. on a timer or when a slot needs evicting) — writes are fast, but there's a window where the cache holds data the database doesn't have yet, and a cache node failure during that window means real, unrecoverable data loss unless there's a separate durability mechanism (e.g. a write-ahead log) backing it. LRU EVICTION: Least Recently Used tracks, for every cached key, when it was last accessed (read or write) — typically via a doubly-linked list where the most-recently-used key sits at the head and the least-recently- used sits at the tail, with a hash map for O(1) key lookup into that list. When a new key needs a slot in a full cache: the tail (least recently used) entry is evicted, the new key is inserted at the head, and every access (hit) also moves that key to the head — this is why LRU needs O(1) operations for both "move to head" and "evict from tail," which is exactly what the linked-list-plus-hashmap combination provides. WHY CONSISTENCY IS IN TENSION WITH THE POINT OF CACHING: a cache exists specifically to serve reads FASTER than the source of truth can, by keeping a copy that doesn't require hitting the database every time. Perfect consistency would require every cache read to first verify against the database that its copy is still current — but that verification IS a database round trip, which defeats the entire purpose of having a cache in the first place. This is why real caching systems accept some amount of staleness (via a TTL, invalidation-on-write, or similar) rather than pursuing perfect consistency — the trade-off is structural, not a limitation of any particular implementation. WRITE-THROUGH'S WRITE PATH: (1) client issues a write, (2) the application writes to the cache, (3) the application ALSO writes to the database, waiting for that write to be acknowledged, (4) only after BOTH succeed does the write return success to the client. If the database write fails, the write-through cache entry must be rolled back or invalidated too — otherwise the cache would hold a value the database never actually persisted, silently reintroducing the inconsistency the synchronous approach was meant to avoid.
What "re-derive cold" is testing: whether you can name the actual FAILURE MODE each strategy accepts (write-back's data-loss window, write-through's write-latency cost) rather than just labeling them "fast" and "safe" — and whether you can articulate why consistency and cache speed are structurally opposed, not just "sometimes in tension."

Search autocomplete design, re-derived

Do this before opening anything below. Same rules: timer, full attempt, no peeking until you're done.

Prompt — attempt cold first

Without looking anything up, sketch a search autocomplete design:

  • Why a trie, specifically, over other data structures? What does descending it character by character actually retrieve?
  • Why does sub-100ms latency force precomputed rankings instead of scoring at query time?
  • What mechanism handles typo tolerance, and how does it actually work?
  • What happens at each trie node beyond just "is this a valid word ending"?
Reveal the answer (only after you've actually attempted it)
WHY A TRIE: a trie (prefix tree) stores strings character by character along paths from the root, so that ALL strings sharing a common prefix share the same path down to where they diverge — meaning "find every completion of the prefix the user has typed so far" is just "descend the trie one node per typed character, then collect everything in the subtree below wherever you land." This is structurally the exact operation autocomplete needs: the user's partial input IS a prefix, and the trie's entire organization is built around prefix-sharing. A hash map or sorted list would require scanning or re-filtering the ENTIRE dataset for every keystroke to find prefix matches; a trie's descent means each keystroke only costs the traversal of one more node, and the candidate set naturally narrows as more characters are typed. WHY SUB-100MS FORCES PRECOMPUTED RANKING: scoring every completion by some live signal (e.g. current popularity, personalization) at the exact moment a query hits the server, especially across potentially thousands of matching completions for a short prefix, is real compute work that competes directly against the latency budget on every single keystroke. Precomputing and caching a ranked completion list per prefix (or per trie subtree) ahead of time means the query-time path is just "read the already-sorted top-K list" — O(1)-ish lookup instead of live scoring — which is what actually makes sub-100ms achievable at real query volume, since every keystroke a user types fires a new request. TYPO TOLERANCE MECHANISM: edit distance (Levenshtein distance) — the minimum number of single-character insertions, deletions, or substitutions needed to turn one string into another. Rather than requiring an EXACT prefix match in the trie, the system tolerates completions within a small edit-distance threshold (e.g. 1-2 edits) of the typed prefix, catching common typos (transposed letters, one wrong character, a missing character) without requiring the user to correct themselves before seeing any suggestions. WHAT'S AT EACH TRIE NODE: beyond a boolean "is this a complete word here," each node typically also stores (or has fast access to) the precomputed top-K ranked completions for everything in its subtree — this is exactly what makes the precomputed-ranking point above concrete: the ranking isn't computed separately from the trie, it's attached directly to the trie structure itself, at the node representing each possible prefix.
What "re-derive cold" is testing: whether you can explain WHY a trie fits this problem (prefix-sharing structure matching prefix-based queries) rather than just naming it as the "correct" data structure, and whether you connect the sub-100ms constraint causally to precomputation rather than treating them as two unrelated facts.
03 — Cold recall, no notes

RAG Q&A system design, re-derived

Do this before opening anything below. Same rules: timer, full attempt, no peeking until you're done.

Prompt — attempt cold first

Without looking anything up, sketch a RAG-backed Q&A system:

  • Name all four pipeline stages, in order, and explain why they must run strictly sequentially.
  • What's the similarity-score threshold check for, and what problem does it solve that retrieval alone can't?
  • Which stage dominates total latency, and by roughly how much? What does that imply for where to optimize?
  • What's the actual lever for handling 10x query volume, versus making one request faster?
Reveal the answer (only after you've actually attempted it)
FOUR STAGES, IN ORDER: (1) embed the question — pass the user's question through the same embedding model used on the document corpus, producing a query vector in the same vector space; (2) vector search — compare that query vector against the indexed chunk vectors (via dense/HNSW/hybrid retrieval) to get the top-K most similar chunks with similarity scores; (3) assemble context — concatenate the retrieved chunks, system instructions, and the question into one delimited prompt string, ordered with recency-effect reasoning (retrieved context and the question placed near the end); (4) generate — send the assembled prompt to the LLM, which produces an answer grounded in the retrieved context. They're strictly sequential because each stage's output is a REQUIRED input to the next — assembly literally has nothing to assemble until search returns results, and generation has no prompt to run on until assembly finishes. This is a hard data dependency, not a convention. SIMILARITY-SCORE THRESHOLD CHECK: vector search ALWAYS returns its top-K results, even when nothing in the corpus is actually relevant to the query — a low top score is real, available evidence that nothing genuinely relevant was found, but retrieval alone has no built-in way to say "I found nothing good," it always reports "here's what scored highest," even if everything scored low. The threshold check compares the top result's score against a minimum bar; if even the best match falls short, the system explicitly returns "I don't have good information about this" rather than assembling a prompt from weakly- related chunks and risking a fluent, confident-sounding but ungrounded (hallucinated) answer. This is a retrieval-layer fix, not a generation- layer one — it has to happen before assembly, not by hoping the LLM "notices" weak context on its own. DOMINANT STAGE: generation, typically by 10-50x any other single stage (roughly 800-3000ms+ versus ~20-50ms each for embed/search/assemble). Because the four stages are strictly sequential, total latency is the SUM of all four — and because generation is such a large fraction of that sum, optimization effort belongs there (streaming tokens to reduce PERCEIVED latency, or a faster/smaller generation model), not on the three comparatively cheap earlier stages, where even a large percentage improvement barely moves total latency (an Amdahl's-law-style effect). 10X VOLUME LEVER: NOT "make each stage faster" — that's a per-request LATENCY fix, a different problem from handling more TOTAL volume. Since each query's full pipeline is independent of every OTHER query's pipeline, the actual lever for volume is horizontal scaling and concurrency: more embedding-model replicas, more generation-model replicas/instances, and a vector index that serves concurrent reads — running many independent pipelines in parallel across replicas, not speeding up any single pipeline's four sequential stages. Generation, being both the slowest and most GPU-compute-intensive stage, is usually the first capacity bottleneck under increased volume.
What "re-derive cold" is testing: whether you can name the exact FAILURE the threshold check prevents (confident hallucination from weak context, not just "bad results"), and whether you keep the "faster per request" question and the "more total volume" question genuinely separate — they're commonly conflated, and interviewers notice when they aren't.
04 — The question that connects all three of this month's designs

Data freshness vs response speed, across all three

Start here, before the table. Month 2's cold review compared "what breaks at 10x traffic" across three backend systems. This month's three designs share a different, equally real tension: each one trades DATA FRESHNESS (how current the information it returns is) against RESPONSE SPEED (how fast it can return anything at all) — and each one resolves that trade-off differently, in a way that reveals what each system actually optimizes for.

SystemFreshness vs speed trade-offWhy, specifically
Caching layer Explicitly accepts staleness (via TTL or write-back's async flush) in exchange for read/write speed Section 1's core finding: perfect consistency requires a database round trip on every read, which defeats the purpose of caching entirely. The cache's whole existence is a deliberate bet that slightly-stale-but-fast beats always-current-but-slow for the specific read pattern it serves — freshness is the resource being spent to buy speed.
Search autocomplete Precomputed rankings are stale by construction, refreshed periodically, not per-request Section 2's core finding: sub-100ms latency is only achievable because rankings are computed AHEAD OF TIME and cached at the trie-node level, not scored live per keystroke. This means autocomplete rankings reflect popularity/relevance data from whenever they were last recomputed, not the literal current instant — a deliberate, structural staleness accepted specifically because live per-keystroke scoring cannot hit the latency target at all, not just "hits it slower."
RAG Q&A system The opposite trade: freshness of the RETRIEVED CONTEXT matters more than speed, and the system pays generation's large latency cost specifically to stay grounded in current source documents Unlike the other two, RAG's four-stage pipeline doesn't sacrifice freshness for speed — retrieval happens fresh, per query, against the current index (Section 3), and the dominant latency cost (generation) exists precisely because the system insists on reasoning over freshly-retrieved, current context rather than relying on a model's stale training-time knowledge. If RAG cached whole ANSWERS the way the caching layer caches data, it would reintroduce exactly the staleness problem RAG's retrieval step exists to avoid.
The pattern across all three: the caching layer and search autocomplete both deliberately trade freshness AWAY to buy speed — staleness is the accepted cost of a fast response. The RAG system does the opposite: it pays a large latency cost (generation) specifically to stay grounded in fresh, per-query-retrieved information rather than accepting the "staleness" of relying purely on the LLM's frozen training-time knowledge. Recognizing which direction a given system trades freshness for speed — and why — is exactly the kind of cross-system reasoning "compare trade-offs across all three" is testing for.

Practice problems

Work each one out before expanding the solution. These reason ACROSS the three designs, not just reproduce one.

Problem 1 · Applying the caching layer's TTL idea to RAG

Someone proposes caching full generated ANSWERS in the RAG system (keyed by question text) with a TTL, the same way the caching layer caches database rows, to cut generation latency for repeated questions. What breaks, and what's actually safe to cache instead?

Show solution
What breaks: caching the full generated answer reintroduces exactly the staleness problem the RAG system's fresh-per-query retrieval exists to avoid (section 4's finding). If the underlying document corpus changes -- a policy gets updated, a document gets corrected -- a cached answer keyed only on question TEXT has no way to know its retrieved context is now stale, and will keep confidently serving an outdated answer until the TTL expires, exactly the kind of confident-wrong-answer risk the similarity-threshold check in section 3 is specifically designed to prevent at the RETRIEVAL layer -- caching the final answer bypasses that protection entirely, since the threshold check never re-runs on a cache hit. What's safer to cache: the QUERY EMBEDDING itself (computing an embedding for the same repeated question text is a pure function of the text and the embedding model, so it's safe to cache/reuse as long as the embedding model hasn't changed), or perhaps the retrieved CHUNK IDs for an identical query with a short TTL that's explicitly tied to how often the corpus actually changes -- but even then, re-running the generation step fresh each time (rather than caching its output) keeps the answer responsive to any recent corpus changes that retrieval just picked up. This mirrors the caching layer's own lesson (section 1): caching something is only safe when you've deliberately decided how much staleness is acceptable for THAT specific piece of data -- caching a final generated answer wholesale skips that deliberate choice for the one place (grounding in current documents) this system was built specifically not to compromise on.
Problem 2 · Comparing autocomplete's precompute strategy to RAG's real-time retrieval

Autocomplete precomputes rankings ahead of time to hit its latency target; RAG computes retrieval fresh per query. Both have real latency constraints. Why can't RAG adopt autocomplete's precompute strategy for its retrieval stage?

Show solution
The key structural difference: autocomplete's precomputed rankings are keyed on a bounded, enumerable set of PREFIXES (finite strings up to some reasonable length) that can be computed once and reused across every user who types that same prefix -- the query space is small and repetitive enough that precomputing "the answer for every possible prefix" is tractable. RAG's retrieval stage is keyed on the QUERY VECTOR of an essentially unbounded space of possible natural-language questions -- there's no finite, enumerable set of "every question a user might ask" to precompute retrieval results for. Precomputing would require guessing in advance which questions will be asked, which is fundamentally different from precomputing every possible PREFIX (a small, literally enumerable alphabet-based space) of a search box. This is exactly why RAG's stage 2 (vector search, section 3) has to run a REAL search per query against the index rather than a lookup into a precomputed table the way autocomplete's trie nodes work -- the two systems' query spaces have fundamentally different cardinality, so a strategy that works beautifully for one (precompute everything) is simply inapplicable to the other.
Problem 3 · Choosing where to over-invest given a fixed staleness budget

You're told the business can tolerate slightly stale data almost everywhere EXCEPT one place: users must never see a search suggestion or a RAG answer that references a product that's been discontinued in the last hour. Which of the three systems needs the SHORTEST staleness window as a result, and what would you change about it?

Show solution
Both search autocomplete AND the RAG system are directly implicated by this constraint (the caching layer is a supporting layer underneath both, not a user-facing surface on its own, so it inherits whichever constraint the system built on top of it imposes) -- but autocomplete's PRECOMPUTED rankings (section 2) are the harder one to fix quickly, because by design its whole latency strategy depends on NOT recomputing per request. Shortening its staleness window to "under an hour" means the precomputation/refresh job itself has to run far more frequently than a typical autocomplete deployment would default to, which is a real infrastructure cost (recomputing rankings across the whole trie structure on a much tighter cycle) that section 2's original design didn't have to account for. RAG's retrieval (section 3) is comparatively easier to fix for this specific constraint: since it already searches the index FRESH per query, the fix is really just "make sure the vector index itself reflects discontinued-product removals within the hour" (a corpus- update-pipeline problem, not a per-query retrieval-latency problem) -- retrieval was never precomputed staleness the way autocomplete's rankings are, so the discontinued-product freshness requirement mostly falls on how fast the underlying document corpus and its index get updated, not on changing retrieval's own query-time behavior. What to change: for autocomplete specifically, either move discontinued- product filtering OUT of the precomputed ranking step and into a fast, small, always-fresh filter applied at query time on top of the (still stale-by-design) precomputed candidates -- keeping the speed benefit of precomputation for the bulk of ranking while patching in freshness only where it's actually required -- or accept a shorter, more expensive refresh cycle if the discontinued-product list changes rarely enough that a targeted post-filter isn't worth building separately.
Problem 4 · Spotting a design that silently reintroduces a solved staleness problem

A candidate says: "for the RAG system's latency, I'd just add a write-through cache in front of the vector search stage, same idea as the caching layer lab." What's wrong with copy-pasting write-through specifically here?

Show solution
Write-through (section 1) is a strategy for keeping a CACHE and a DATABASE synchronized on WRITES -- it solves "how do I keep a read cache current when the underlying data changes," at the cost of paying full database write latency on every write. But RAG's vector search stage (section 3) isn't primarily a write-heavy path being read repeatedly the way a caching-layer use case is -- it's a READ path (search) over an index that changes relatively rarely (when documents are added or updated) compared to how often it's QUERIED. Applying "write-through" to it doesn't map cleanly: there's no natural "write path" at query time to keep synchronous with anything, since a search query doesn't write anything to the index at all. What the candidate likely means, stated correctly, is something more like caching REPEATED IDENTICAL QUERY VECTORS' retrieval results (a read-cache-with-TTL pattern, not write-through) -- but even that, per Problem 1's finding, has to be scoped carefully (cache retrieved chunk IDs with a TTL tied to corpus update frequency, not the full generated answer) to avoid quietly serving stale, ungrounded results past the point where the source documents changed. The deeper mistake being tested here: reaching for a memorized caching STRATEGY NAME without checking whether its actual mechanics (synchronizing a cache against WRITES) match the shape of the problem at hand (a read-heavy stage with infrequent underlying updates) -- exactly the kind of copy-paste-without- checking-the-shape mistake Month 2's cold review flagged for the rate limiter/URL-shortener caching mismatch, showing up again here in a new context.
