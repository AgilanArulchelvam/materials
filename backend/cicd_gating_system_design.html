BACKEND & APIS LAB · SYSTEM DESIGN — CI/CD GATING SYSTEM

Passing the tests was never the whole bar. Passing the evals is.

A normal CI pipeline blocks a deploy when unit tests fail. A CI/CD pipeline for an LLM-backed system needs a SECOND, independent gate: the same eval suite pytest_evals_practice.html built, run against a candidate build, blocking the deploy if eval scores fall below a threshold — even when every unit test passed cleanly. This lab designs that gate end to end, animates a build that passes tests but fails evals getting blocked before production, and works through automated vs. manual rollback strategy on failure.

01 — Why "the tests pass" isn't the same claim as "the model is still good"

Gating deploys on test/eval thresholds

Start here, before any pipeline diagram. Think about a driving test that only checks whether the car starts, the headlights work, and the seatbelt clicks — every one of those checks can pass on a car whose driver has never actually learned to parallel park or merge onto a highway safely. Those mechanical checks are necessary (a car that doesn't start shouldn't be on the road at all) but they say NOTHING about whether the driver is actually competent at driving. A real driving test needs a SECOND, behaviorally-focused evaluation on top of the mechanical checklist — and only passing BOTH means the car is actually safe to put on the road.

A CI/CD pipeline for an LLM-backed system has exactly this two-layer structure. Unit and integration tests are the mechanical checklist: does the code import without errors, does the API return a 200, does the database migration apply cleanly. These are necessary — a build that fails them should never ship — but they say nothing about whether the MODEL'S BEHAVIOR is still acceptable. A candidate build can pass every unit test while its underlying prompt change or model swap has quietly made its answers worse, its tool-call reliability worse, or its cost per request far higher. That's exactly the gap pytest_evals_practice.html's eval suite — deterministic checks, trajectory checks, rubric-based checks — was built to catch, and a CI/CD pipeline for this kind of system needs to run that SAME suite as its own gate, with its own pass/fail threshold, separate from and in addition to ordinary tests.

# deploy_pipeline.py — two independent gates, both must pass # reuses pytest_evals_practice.html's exact suite as the second gate def run_deploy_pipeline(candidate_build): # GATE 1 — ordinary tests. Necessary, but says nothing about model quality. test_result = run_pytest_suite(candidate_build, suite="unit_and_integration") if not test_result.passed: return block_deploy("unit/integration tests failed", test_result) # GATE 2 — the eval suite, exactly pytest_evals_practice.html's suite, # run against THIS candidate build specifically eval_result = run_eval_suite(candidate_build, suite="capstone_agent_evals") EVAL_THRESHOLD = 0.90 # e.g. 90% of eval checks must pass if eval_result.pass_rate < EVAL_THRESHOLD: return block_deploy( f"eval pass rate {eval_result.pass_rate:.0%} below threshold {EVAL_THRESHOLD:.0%}", eval_result ) # both gates cleared — safe to proceed to rollout return promote_to_production(candidate_build)

Two design details matter here, both directly connected to earlier labs. First: the eval gate reuses the SAME suite pytest_evals_practice.html built against a fixed, recorded fixture — deterministic schema checks, the trajectory check verifying a genuine retry (not a fabrication), and rubric checks — so the CI gate isn't inventing new criteria, it's running the exact same, already-understood bar every candidate build has to clear. Second: the threshold is a NUMBER (0.90 above), not a binary "all evals must pass" — because a single flaky eval or a marginal regression in one edge case shouldn't necessarily block every deploy forever, but a build whose overall eval quality has genuinely regressed should. Where that threshold is set is itself a real design decision, revisited in this section's practice problems.

Interview-ready definition: gating deploys on eval thresholds means running the SAME kind of eval suite deterministic_evals.html, trajectory_based_evals.html, and pytest_evals_practice.html built — not just ordinary unit/integration tests — against every candidate build as a second, independent CI gate, blocking promotion to production if the eval pass rate (or a specific critical eval) falls below a defined threshold. This exists because passing unit tests only proves the CODE runs correctly; it says nothing about whether the MODEL'S BEHAVIOR — answer quality, trajectory correctness, cost — has regressed, which is exactly the gap an eval-based gate is designed to close before a regression ever reaches real users.

03 — What happens when a bad build gets through anyway

Rollback strategy on failure

Start here, before the diagram. Think about renovating one bathroom in a house you still live in, versus renovating the ENTIRE house before moving your family in. If you renovate incrementally and something's wrong (a leaking pipe), you can just move back into the OLD, still-fully-functional bathroom immediately — no rebuild needed, just switching back to what already worked. If instead you tore out the whole house and are living in the half-finished new one, "rolling back" means actually rebuilding the old house from scratch, which takes real time you don't have during an emergency. Rollback strategy is exactly this choice, made in advance: do you keep the OLD, known-good version standing and ready, or do you only have the NEW version and have to reconstruct the old one if something goes wrong?

Automated rollback keeps the previous known-good version fully deployed and ready — often via blue-green deployment (two complete, identical production environments, "blue" and "green"; traffic points at whichever is currently live, and a rollback is just flipping that pointer back to the other one, typically in seconds) or canary releases (the new version receives a small percentage of real traffic first — e.g. 5% — while the vast majority still hits the old, proven version; if the canary's metrics or evals look bad, that 5% gets routed back and the rollout never expands further). Both approaches share the same underlying idea: the OLD version is never actually torn down until the new one has proven itself, so "rollback" is a fast, low-risk traffic-routing change, not a rebuild.

Manual rollback, by contrast, typically means someone has to notice the problem, decide to roll back, and then actually execute a slower process — redeploying a previous build from scratch, restoring a database backup, or otherwise reconstructing the old state rather than just flipping back to it. This is slower for two independent reasons: the HUMAN decision loop (noticing, deciding, initiating) and the MECHANICAL rebuild time, versus automated rollback's near-instant traffic-routing flip triggered the moment the eval gate (or a post-deploy monitoring signal) detects a problem.

Manual rollback instead requires a human to notice, decide, and then execute a slower reconstruction of the old state, adding both a human decision-loop delay and a mechanical rebuild delay on top of however long the failure took to even notice in the first place.

Problem 1 · Setting a defensible eval threshold

Using section 1's EVAL_THRESHOLD = 0.90, argue for why this shouldn't be set to exactly 1.0 (100% of evals must pass), and separately why it shouldn't be set arbitrarily low (like 0.50). What real trade-off is the threshold balancing?

Show solution
Not 1.0: a real eval suite, per pytest_evals_practice.html's own suite design, includes some checks closer to "soft signal" than "hard invariant" -- a rubric-based quality check, for instance, can have legitimate run-to-run variance even for a genuinely GOOD build (model outputs aren't perfectly deterministic). Requiring literally 100% pass rate means a single flaky or borderline eval -- not a real regression -- blocks EVERY deploy indefinitely, which trains the team to either ignore the gate's failures (defeating its purpose) or delete the flakiest evals just to unblock shipping (actively making the suite worse over time). Not 0.50: this would let a build through even if roughly HALF its eval checks fail, which per section 1's whole argument defeats the purpose of having a gate at all -- a build failing half its trajectory and schema checks has a genuine, serious regression, not noise. The real trade-off: false positives (blocking a genuinely fine build because of eval flakiness, which erodes trust in the gate and pressures teams to bypass it) versus false negatives (letting a genuinely regressed build through because the bar was set too low). A threshold like 90% is a defensible middle ground -- tight enough to catch a real regression (most evals failing) while tolerant of the occasional flaky check a well-designed suite should mostly avoid in the first place.
Problem 2 · Deciding which failure should block harder than the aggregate threshold

Using pytest_evals_practice.html's specific tests (test_final_answer_matches_schema, test_retried_after_injected_failure), should EVERY eval count equally toward the 90% aggregate threshold, or should some failures block the deploy regardless of the overall pass rate? Justify with a concrete example.

Show solution
Some failures should block UNCONDITIONALLY, regardless of aggregate pass rate -- specifically, deterministic schema-validation failures like test_final_answer_matches_schema. If the candidate build's final JSON answer doesn't even match the expected schema, that's not a "quality regression" in the same category as a slightly-worse rubric score -- it means DOWNSTREAM CONSUMERS of this agent's output will literally fail to parse the response, an unconditional break regardless of how well everything else scores. Treating this the same as one soft rubric point among many, averaged into a 90% threshold, could let a build with a genuinely broken output schema through as long as enough OTHER evals compensated in the aggregate -- clearly wrong. By contrast, test_retried_after_injected_failure (the trajectory check) is a reasonable candidate for the AGGREGATE threshold rather than an unconditional block -- a build that fabricates instead of retrying on ONE specific injected-failure fixture is a real regression worth counting, but it's closer to a quality signal than an unconditional correctness break the way a malformed schema is. The general design principle: split the eval suite into "hard gates" (any single failure blocks, no averaging) for invariants whose failure means the system is structurally broken, and "aggregate-threshold" checks for softer quality signals where some noise is tolerable -- a distinction directly mirroring deterministic_evals.html's split between schema validation (structural, binary) and rubric-based quality checks (softer, graded).
Problem 3 · Choosing between blue-green and canary for a specific scenario

A team is deploying a change to the Month 4 capstone agent's prompt that they believe improves quality but haven't been able to fully validate with offline evals alone (some failure modes only show up under real, varied production traffic). Would blue-green or canary better fit this rollout, and why?

Show solution
Canary fits better here. Blue-green is a full, instant cutover -- once you flip the traffic pointer, 100% of real traffic hits the new version immediately, which is a poor fit when the whole premise is "we're not fully confident offline evals caught every failure mode, and want real traffic to help validate that." A canary release deliberately exposes the new version to only a SMALL percentage of real traffic first (e.g. 5%), letting the team observe real-world eval/metric signals on that slice before deciding whether to expand the rollout -- directly suited to exactly the stated uncertainty ("offline evals alone weren't sufficient"). Blue-green's strength is elsewhere: when the team IS confident (offline evals and tests both cleared per section 1's gates) and just wants the fastest possible cutover with an instant rollback option if something unexpected happens post-deploy -- not a gradual, traffic-percentage- based validation process. The two aren't mutually exclusive either -- many real systems canary FIRST (small percentage, validate) and only then do a full blue-green-style cutover to 100% once the canary's metrics look clean, getting graduated validation AND a fast full cutover once confidence is established.
Problem 4 · Tracing why the eval gate needs its OWN fixture, not live traffic

Using pytest_evals_practice.html's section 1 reasoning about captured fixtures vs. live calls, explain why the CI eval gate should run against a FIXED, recorded fixture (like the capstone agent's captured trajectory) rather than live production traffic, even though live traffic would in some sense be more "realistic."

Show solution
Per pytest_evals_practice.html's own section 1 interview-ready definition, a suite built against captured, fixed fixtures keeps the SUITE itself deterministic and fast -- the exact property a CI gate needs. A gate that instead evaluated against live, non-deterministic production traffic would have two serious problems specific to the CI/CD context: first, it couldn't run BEFORE a deploy at all, since "live traffic against the candidate build" requires the candidate build to already be receiving real traffic -- defeating the entire point of gating deploys BEFORE they reach production (section 1's core goal). Second, even if you could somehow route a slice of live traffic to a not-yet-promoted candidate, results would vary run to run purely from which real queries happened to arrive, making "did the pass rate cross the threshold" partly a function of random traffic composition rather than a repeatable, comparable signal across every candidate build a team ships. A fixed fixture, evaluated identically against every candidate build, gives an apples-to-apples comparison -- build A and build B are judged against the EXACT SAME scenario, isolating whatever changed in the build itself as the only variable. Canary releases (section 3) are the correct place for real, live-traffic-based validation -- but that happens AFTER the offline eval gate has already been cleared, as a second, complementary validation layer, not a replacement for the fixture-based CI gate.
Problem 5 · Designing what happens when a canary's evals fail mid-rollout

A canary release sends 5% of live traffic to a new build. After an hour, an automated system running pytest_evals_practice.html-style trajectory checks against SAMPLES of that 5% traffic detects a pass rate below threshold. Design what should happen next, using this lab's rollback reasoning.

Show solution
The correct automated response, per section 3's canary mechanics: route that 5% back to the proven previous version IMMEDIATELY -- this is exactly canary's "seconds, not minutes" rollback speed table entry, because the previous version was NEVER torn down; the canary was always just a small, reversible traffic slice on top of it. The rollout simply never expands past its current (or reverts to zero) percentage, and no rebuild or redeploy is needed -- purely a traffic-routing change. Beyond the immediate rollback, two more things should happen, both connecting to earlier labs: (1) the specific failing trajectory samples should be captured and preserved -- exactly database/audit_trail_ schema.html's "replay, don't require the original conditions" principle -- so engineers can inspect precisely which real production inputs triggered the eval failures, not just see an aggregate "pass rate dropped" alert with no specifics. (2) The canary rollout should be marked BLOCKED at this specific traffic percentage rather than silently retried at the same percentage later -- the eval gate failing during a canary is exactly as serious a signal as it failing during the pre-deploy CI gate (section 1), and should require the same kind of explicit human review and a NEW candidate build (with a fix) before canarying again, not an automatic retry that could re-expose real users to the same regression a second time.
