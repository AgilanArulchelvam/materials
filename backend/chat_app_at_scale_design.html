BACKEND & APIS LAB · SYSTEM DESIGN — CHAT APP AT SCALE

A million open sockets don't care which server happens to be holding them.

A typical HTTP API is stateless: any server can answer any request, because nothing about "who's connected" persists between requests. A chat app breaks that assumption entirely — every online user holds open a long-lived, stateful WebSocket connection (per backend/websockets.html) to ONE specific server, and that server has to somehow deliver a message from a user on a completely different server. This lab designs connection management at scale, works through delivery guarantees, and builds the pub/sub backplane that lets any server reach any connected user.

Persistent connections — stateful, long-lived, one per online user
At-least-once + idempotency — the practical path to exactly-once
Redis pub/sub backplane — any server can reach any connected user

01 — Why "any server can handle any request" stops being true

Connection management at scale

Start here, before any architecture. Think about the difference between a mail carrier delivering a letter (a one-shot interaction — drop it off, done, the carrier owes the recipient nothing further) versus a phone operator on a decades-old switchboard holding open a physical circuit between two callers for the ENTIRE duration of their call. The mail carrier model scales trivially — any carrier can deliver any letter, no memory required between deliveries. The switchboard model doesn't: whichever operator physically plugged in that circuit is the one holding it open, and the call literally cannot continue if that specific operator's board goes down, no matter how many OTHER operators are sitting idle right next to them.

A typical stateless HTTP API is the mail carrier: any app server behind nginx_reverse_proxy.html's load balancer can answer any request, because nothing persists between one request and the next — this is exactly why horizontal scaling (systems/vertical_vs_horizontal_scaling.html) is comparatively easy for stateless services. A chat app's WebSocket connections are the switchboard: per backend/websockets.html, when a user opens the app, they establish ONE persistent, long-lived, bidirectional connection to ONE specific server, and that connection stays open — often for hours — as long as the user stays online. That server now holds real STATE (which user is connected, on which specific TCP connection) that no other server has any direct access to.

# the state a chat server holds for every currently-connected user # this in-memory map is exactly the "switchboard operator's board" -- # it exists ONLY on this one server process, for exactly these connections class ChatServer: def __init__(self): self.connections = {} # user_id -> WebSocket connection object, LOCAL to this process async def on_connect(self, user_id, ws): self.connections[user_id] = ws # PROBLEM: no other server process knows this mapping exists at all async def send_to_user(self, user_id, message): ws = self.connections.get(user_id) if ws: await ws.send(message) else: # user isn't connected to THIS server -- but might be connected # to a DIFFERENT one. This server has no way to know, on its own. pass

This is precisely why a chat app's connection-management challenge is fundamentally different from a normal stateless API's scaling challenge — and connects directly to evals-and-observability/uvicorn_gunicorn_workers.html's worker models: a WebSocket connection needs a worker (or event loop coroutine) that stays alive and dedicated to it for the connection's ENTIRE lifetime, not the short request/response cycle a typical async worker is optimized to cycle through quickly. Holding hundreds of thousands of long-lived connections open concurrently is itself a real capacity question (how many open sockets can one server/event loop hold before running out of memory or file descriptors), separate from and in addition to section 3's cross-server routing problem.

Interview-ready definition: connection management at scale for a chat app means each currently-online user holds one persistent, stateful WebSocket connection (per backend/websockets.html) to exactly ONE specific server process, and that server — not the load balancer, not any other server — is the only one with a direct handle to that connection. This breaks the assumption typical stateless HTTP services rely on (any server can answer any request) and introduces two distinct new challenges: how many long-lived connections a single server can hold open concurrently (a capacity/resource question), and how a message from a user on a DIFFERENT server ever reaches a user whose connection lives elsewhere (section 3's routing problem) — neither of which exists for a stateless request/response API.
02 — What "the message got delivered" actually promises, and what it costs to promise more

Message delivery guarantees

Start here, before the definitions. Think about handing a letter to three different kinds of couriers. Courier A promises "I'll try to deliver this once — if something goes wrong along the way, I won't retry, and I definitely won't deliver it twice" (at-most-once: the letter might just never arrive). Courier B promises "I will absolutely make sure this gets delivered, and if I'm not 100% sure the first attempt worked, I'll just deliver it again to be safe" (at-least-once: the letter WILL arrive, but the recipient might get two identical copies). Courier C promises "this will arrive exactly once, no more, no less, guaranteed" — which sounds strictly better than both, but requires the courier to somehow coordinate with the recipient in a way real, unreliable networks make genuinely hard to guarantee absolutely.

GuaranteeWhat it promisesThe real cost
At-most-onceA message is delivered zero or one times — never duplicatedSimplest to implement (send once, no retry), but messages can be silently LOST on any failure — unacceptable for a chat app where a lost message is a real user-visible bug
At-least-onceA message is delivered one or MORE times — never lostRequires retrying on any uncertainty (timeout, ack not received), which means the SAME message can genuinely arrive twice — the receiving side must handle duplicates itself
Exactly-onceA message is delivered exactly one time — never lost, never duplicatedGenuinely hard to guarantee end-to-end in a distributed system with unreliable networks — in practice, almost always APPROXIMATED, not truly guaranteed at the network/transport level

Exactly-once is hard for a structural reason, not just an engineering-effort reason: in a distributed system, a sender can never be perfectly certain whether a message it sent was received and processed, or was lost, or was received and processed but the ACKNOWLEDGMENT was what got lost on the way back (the exact ambiguity database/crud_done_right.html's idempotency-key section built its entire "retry, but the client can't tell success from failure" scenario around). Given that fundamental uncertainty, a sender that wants to guarantee "never lost" has no choice but to retry when uncertain — which mechanically means at-least-once, with the very real possibility of duplicates, is really the only guarantee that can be TRULY enforced at the transport layer without additional coordination.

# the actual pattern real chat systems use: at-least-once delivery # + idempotency, exactly database/crud_done_right.html's mechanism, # applied here to chat messages instead of payment charges async def send_message(sender_id, recipient_id, message_id, body): # message_id is a CLIENT-GENERATED idempotency key, one per logical # message -- reused across retries of the SAME send attempt, # exactly crud_done_right.html's "one key per logical operation" rule existing = await db.get_message_by_id(message_id) if existing: # this exact message was already processed -- retry, not a new message. # return the already-stored result, don't re-deliver, don't re-store. return existing # genuinely new message_id -- store it (this is the durability point; # once stored, at-least-once redelivery to the recipient is safe to retry) await db.insert_message(message_id, sender_id, recipient_id, body) await deliver_to_recipient(recipient_id, message_id, body) # may be retried; safe return {"message_id": message_id, "status": "delivered"}

This is the practical resolution real chat systems use: implement genuinely reliable AT-LEAST-ONCE delivery (retry aggressively whenever delivery confirmation is uncertain, since losing a chat message is a real bug), then use a client-generated message_id as an idempotency key so that any DUPLICATE delivery caused by a retry gets recognized and deduplicated — either by the server before storing (as above) or by the client, which can simply ignore a message it's already rendered once. The end result, from the USER's point of view, looks and feels like exactly-once delivery — no lost messages, no visible duplicates — even though the underlying mechanism is honestly at-least-once with deduplication, not a true, structurally-guaranteed exactly-once transport.

Interview-ready definition: at-most-once delivery risks silent message loss but never duplicates; at-least-once delivery guarantees a message eventually arrives but may deliver it more than once; exactly-once delivery — arriving precisely once, always — is genuinely hard to guarantee at the transport layer in a distributed system, because a sender can never be perfectly certain whether an unacknowledged send failed or merely lost its acknowledgment on the way back. In practice, systems approximate exactly-once by implementing reliable at-least-once delivery (retry whenever uncertain) combined with idempotency — a client-generated message ID, exactly database/crud_done_right.html's idempotency-key pattern, that lets the receiving side recognize and discard a duplicate delivery — producing an exactly-once USER EXPERIENCE built on top of an honestly at-least-once mechanism.
03 — The actual hard part: server B has a message for a user connected to server A

Horizontal scaling of stateful connections

Start here, before the diagram. Back at the switchboard: imagine now there are MULTIPLE switchboard buildings across town, each with its own set of operators and its own set of physical circuits, with no direct wires between the buildings themselves. If a call needs to reach someone whose circuit is held by an operator in a DIFFERENT building, the operator who received that request has no way to reach them directly — unless every building is ALSO connected to some shared, central coordination system that every operator can both announce things to and listen for things on.

This is exactly section 1's connection-state problem, now made concrete: if user A is connected to server 1 and user B is connected to server 2, and user A sends B a message, server 1 receives that message but has NO direct connection to user B at all — self.connections in section 1's code is a purely LOCAL, in-process map, invisible to every other server. The standard solution is a pub/sub backplane — commonly Redis pub/sub — that every chat server connects to. When server 1 needs to deliver a message to user B, it doesn't try to find server 2 directly; it PUBLISHES the message to a channel (often keyed by user ID or a shard of user IDs), and EVERY server SUBSCRIBES to the channels for users currently connected to it. Server 2, having subscribed to user B's channel because B is connected to it, receives the published message and delivers it over ITS OWN local WebSocket connection to B.

# pub/sub backplane pattern -- every chat server connects to the SAME # Redis instance, publishing to and subscribing from user-scoped channels class ChatServer: def __init__(self, redis_client): self.connections = {} # local WebSocket connections, same as section 1 self.redis = redis_client # SHARED backplane, every server connects to this same Redis async def on_connect(self, user_id, ws): self.connections[user_id] = ws # subscribe to a channel scoped to THIS user -- only messages meant # for them will ever be published here await self.redis.subscribe(f"user:{user_id}", self._on_pubsub_message) async def _on_pubsub_message(self, channel, message): # fires when ANY server (including a different one) publishes to a # channel THIS server is subscribed to -- i.e. one of ITS local users user_id = channel.split(":")[1] ws = self.connections.get(user_id) if ws: await ws.send(message) async def send_to_user(self, user_id, message): # don't check local self.connections at all -- ALWAYS publish. # whichever server actually holds this user's connection (maybe # this one, maybe a different one) will receive it via subscribe. await self.redis.publish(f"user:{user_id}", message)

The key design shift from section 1's broken code: send_to_user no longer even CHECKS whether the recipient is connected to this local server — it always publishes to the backplane, unconditionally, and relies on whichever server actually holds that user's connection (subscribed to that exact channel) to pick it up and deliver it locally. This decouples "which server received the send request" from "which server holds the recipient's connection" entirely — any server can now deliver to any connected user, regardless of which one physically holds the socket, which is precisely what horizontal scaling of stateful connections requires and what a purely local, in-memory connection map (section 1) could never provide on its own.

Interview-ready definition: horizontal scaling of stateful WebSocket connections is hard specifically because each server only has a direct handle to the connections it personally accepted — unlike a stateless API, there's no way for server B to hand off work to server A's exact in-memory state. The standard fix is a pub/sub backplane (commonly Redis pub/sub) that every server connects to: each server subscribes to channels for its own locally-connected users, and any server needing to deliver a message publishes to the recipient's channel unconditionally, without needing to know or care which specific server actually holds that user's connection. This converts "route this message to the right SERVER" into "publish to the right CHANNEL," letting the backplane — not application code — handle the actual cross-server routing.

Problem 1 · Deciding what happens if the recipient isn't connected to ANY server

Section 3's send_to_user always publishes to Redis, unconditionally. If the recipient is currently offline — not connected to ANY server — what happens to the published message, and what does this imply needs to exist ALONGSIDE the pub/sub backplane for a real chat app?

Show solution
Redis pub/sub, by its own core mechanics, only delivers a published message to subscribers that are ACTIVELY subscribed at the moment of publish -- there's no built-in persistence or replay. If the recipient is offline, no server is subscribed to their channel at all, and the published message is simply gone -- not queued, not stored, not delivered later when they reconnect. This is precisely why section 3's pub/sub mechanism ALONE cannot be the complete message delivery story for a real chat app: it solves the "route to whichever server currently holds this connection" problem, but it structurally cannot solve "hold this message until the recipient reconnects," because pub/sub has no concept of a message existing independent of an active subscriber. What needs to exist alongside it: exactly section 2's durable storage step -- db.insert_message() in section 2's code -- which persists every message to a real database BEFORE attempting delivery, independent of whether the recipient is currently online. A real chat app's actual flow is: (1) durably store the message (this succeeds regardless of recipient online status), (2) attempt real-time delivery via the pub/ sub backplane IF the recipient is currently connected somewhere, and (3) if not currently connected, the recipient's client fetches undelivered messages from the durable store directly on their NEXT reconnect, rather than depending on pub/sub to have somehow held onto it. Pub/sub handles the "already online" fast path; durable storage handles the "offline, deliver eventually" case pub/sub structurally cannot.
Problem 2 · Reasoning about a user connected to TWO servers simultaneously (multiple devices)

A real user often has the chat app open on both their phone and their laptop at once — two separate WebSocket connections, potentially to two DIFFERENT servers. Using section 3's channel design (user:{user_id}, one channel per user, not per connection), would both devices receive a new message? Would you need to change the channel design, and if so, how?

Show solution
With section 3's design exactly as shown, BOTH devices would correctly receive the message, even without any changes -- and it's worth understanding precisely why. Redis pub/sub delivers a published message to EVERY currently-subscribed subscriber, not just one -- it's genuinely a broadcast mechanism, not a queue that a single consumer drains. If the phone's server and the laptop's server are both subscribed to the same user:{user_id} channel (because on_connect subscribes per CONNECTION, and this user currently has two active connections, quite possibly on two different servers), a publish to that channel reaches BOTH subscribing servers, and each independently delivers it to its own locally-held connection -- phone gets it, laptop gets it, exactly the multi-device behavior a real chat app needs. The one subtlety worth naming: if BOTH of this user's connections happen to land on the SAME server (not two different ones), that one server would subscribe to user:{user_id} potentially twice (once per on_connect call) -- section 3's code as written doesn't show connection- level deduplication of subscriptions, which in a real implementation would need self.connections to map to a LIST of connections per user (not a single WebSocket), and _on_pubsub_message would need to iterate and send to ALL of that user's local connections, not just one. This is a real, concrete extension needed on top of section 3's simplified single-connection-per-user model, but the core channel design (one channel per user, any number of subscribing servers/connections) already supports it structurally without redesign.
Problem 3 · Diagnosing a message duplicated across a server crash and reconnect

Server 2 (holding Bob's connection) crashes mid-delivery, after publishing an ack back but before Bob's client confirms receipt. The client, uncertain whether the message reached Bob, retries the send. Using section 2's mechanism exactly, trace what happens and confirm no duplicate message is shown to Bob.

Show solution
Trace it through section 2's exact code: the client's retry carries the SAME message_id as the original attempt (per crud_done_right.html's "one key per logical operation, reused across retries" rule, restated in section 2). When the retry's send_message() call runs, its very first step is db.get_message_by_id(message_id) -- and because the ORIGINAL attempt already completed db.insert_message(message_id, ...) before the crash (the durable-storage step happens BEFORE the delivery attempt in section 2's ordering), that lookup finds the message ALREADY EXISTS. The function returns the existing stored result immediately, WITHOUT calling insert_message again and WITHOUT calling deliver_to_recipient again -- no second publish to the pub/sub backplane happens at all for this retry. So Bob never sees a duplicate, PROVIDED the crash happened after insert_message completed (which the scenario states -- "after publishing an ack," implying storage had already succeeded). If instead the crash had happened BEFORE insert_message completed, the retry's get_message_by_id lookup would correctly find nothing, and the retry would proceed as a fresh attempt -- also correct, just a different branch of the same idempotency check. Either way, the message_id lookup is what prevents the duplicate, exactly the same mechanism crud_done_right.html's idempotency_keys table provided for payment retries, now protecting against a duplicate CHAT MESSAGE instead of a duplicate charge.
Problem 4 · Estimating the connection-count challenge from section 1 at real scale

A chat app has 500,000 concurrently online users, spread across 50 server instances (10,000 connections per server on average). Using section 1's reasoning and evals-and-observability/uvicorn_gunicorn_workers.html's worker model discussion, would sync workers or async (Uvicorn) workers be the better fit for holding these connections, and why?

Show solution
Async (Uvicorn) workers, clearly, and for a reason that goes beyond uvicorn_gunicorn_workers.html's usual I/O-bound-API argument. A sync worker (per that lab's section 1) is fully blocked handling exactly ONE thing at a time -- there is no way for a single sync worker process to hold 10,000 concurrent WebSocket connections open simultaneously at all, since "holding a connection open" for a sync worker would mean that worker is permanently occupied by just that ONE connection. Achieving 10,000 concurrent connections under the sync model would require roughly 10,000 separate OS processes per server -- utterly impractical, both in raw OS resource terms (10,000 processes' worth of memory overhead) and because that number has nothing to do with uvicorn_gunicorn_workers.html's CPU-core-based sync heuristic at all, which assumes workers are occupied by short-lived, CPU-competing work, not indefinitely by one long-held socket. An async worker's single event loop, by contrast, can hold many thousands of suspended, idle WebSocket connections concurrently with comparatively little overhead per connection -- each idle connection is just a suspended coroutine waiting on the next incoming message, consuming memory but no CPU while idle, exactly the model uvicorn_gunicorn_workers.html's section 1 established for I/O-bound work. 10,000 connections per server is a realistic number specifically BECAUSE the async model was chosen -- this is precisely why real chat systems are built on async/event-loop-based servers (or their equivalent in other languages, like Go's goroutines or Erlang's lightweight processes) rather than a thread- or process-per-connection sync model, which simply cannot reach this kind of per-server connection density.
Problem 5 · Designing what happens to Alice's channel subscription when she disconnects

Section 3's on_connect subscribes to user:{user_id}. What needs to happen when a user disconnects (closes the app, loses network), and what specifically goes wrong for FUTURE messages to that user if this step is forgotten?

Show solution
On disconnect, the server needs to explicitly UNSUBSCRIBE from that user's channel (a corresponding on_disconnect that mirrors on_connect, calling self.redis.unsubscribe(f"user:{user_id}") and removing the entry from self.connections) -- this is not automatic just because the WebSocket connection itself closed; the Redis subscription is a SEPARATE piece of state that has to be explicitly torn down. If this step is forgotten, two related problems compound over time. First, an immediate correctness bug: _on_pubsub_message would still fire for this now-stale subscription on a future publish to user:{user_id}, and self.connections.get(user_id) would return None (or worse, a reference to an already-closed WebSocket object) -- the code as shown in section 3 handles the None case gracefully (the `if ws:` check), but attempting ws.send() on an already-closed connection object could raise an exception that needs separate handling, not something this simplified code accounts for. Second, and more insidious at scale: every server that a user has EVER connected to, across their entire session history, accumulates a permanent, never-cleaned-up subscription to that user's channel if disconnection is never handled -- meaning a single active user could, over enough reconnects across enough different servers (e.g. every time a mobile client's connection drops and reconnects, possibly landing on a different server per nginx_reverse_proxy.html's load balancing), end up with subscriptions lingering on many stale servers simultaneously, each one needlessly receiving and discarding every message meant for that user forever. This is a genuine, gradually-worsening resource leak -- exactly the kind of "someone eventually has to clean this up explicitly" problem database/crud_done_right.html's soft-delete forgotten-filter bug illustrated in a different context: state that isn't automatically torn down when its owning event ends has to be torn down explicitly, or it just accumulates.
