01 — Fixtures that build a real, disposable system, not a mock of one

Test structure for an async FastAPI app calling MCP tools

Start here, before writing a single test function. Think about a dress rehearsal versus a table read for a play. A table read tests each actor's LINES in isolation, sitting around a table — useful, but it never confirms the lighting cue actually fires when the actor hits their mark, or that the prop is where the actor expects it. A dress rehearsal runs the ENTIRE production, start to finish, with everything wired together — the only way to catch problems that only exist at the SEAMS between pieces, not inside any one piece. Integration tests are the dress rehearsal: unit tests (the table read) already exist elsewhere for the orchestrator's routing logic and the search tool's fusion math individually — this lab is specifically about the seams.

# tests/conftest.py -- shared fixtures for the whole integration suite import pytest import pytest_asyncio from httpx import AsyncClient, ASGITransport from main import create_app from app.orchestrator.state import RunStateStore from fakeredis.aioredis import FakeRedis # in-memory Redis, real Redis protocol @pytest_asyncio.fixture async def test_db(): # a REAL Postgres instance -- per section 2, this is deliberately # NOT mocked, since the schema/index behavior itself is part of # what this suite needs to exercise honestly from app.db import create_test_database, drop_test_database db = await create_test_database() # runs migrations fresh, per lab 5 yield db await drop_test_database(db) # torn down after EVERY test -- no # cross-test state leakage @pytest_asyncio.fixture async def run_store(): # fake, in-memory Redis -- fast, no external service needed for CI, # but speaks the real Redis wire protocol so RunStateStore's actual # code runs unmodified against it (see section 2's trade-off table) fake_redis = FakeRedis() yield RunStateStore(fake_redis) @pytest_asyncio.fixture async def client(test_db, run_store): app = create_app(db=test_db, run_store=run_store) async with AsyncClient(transport=ASGITransport(app=app), base_url="http://test") as ac: yield ac

Three deliberate choices worth naming: the app is built via create_app(db=test_db, run_store=run_store), matching the scaffold's own create_app() factory function (per capstone_scaffold_fastapi_mcp.html section 2) rather than importing the module-level app singleton — this is what makes DEPENDENCY INJECTION of test doubles possible at all, the same reasoning dependency_injection.html gives for why routes should never construct their own dependencies directly. httpx.AsyncClient with ASGITransport drives real ASGI request/response cycles against the app in-process — no actual network socket, but every layer of FastAPI's routing, middleware (including lab 3's tracing middleware), and dependency resolution genuinely runs. And test_db tears down after every single test, preventing one test's leftover rows from silently making a LATER test pass or fail for the wrong reason.

Interview-ready definition: integration test fixtures should construct the REAL application object (via its actual factory function, not a stripped-down substitute) wired to REAL or REALISTIC dependencies (a real test database, a protocol-faithful in-memory Redis) — the goal is exercising the actual seams between components, which a fixture built from hand-rolled stand-ins for the app itself cannot do, no matter how carefully the stand-ins are written.
02 — Every dependency is a separate, deliberate decision

Mocking vs. real MCP calls, decided per dependency

Start here, before mocking everything for speed or nothing for realism. Both extremes are wrong for the same reason: a suite that mocks EVERYTHING tests nothing but your mocks agreeing with your assumptions about the real systems, and a suite that mocks NOTHING is slow, flaky against external services, and expensive to run on every commit. The right call is made per-dependency, weighing what that specific dependency's role in the seam actually is.

DependencyMock or real?Why
The database (test_db)Real (ephemeral test instance)The seam being tested — whether writes actually land per lab 5's schema, whether indexes serve the queries they're built for — cannot be verified against a mock without simply re-asserting the mock's own hard-coded behavior back at itself
Redis (run_store)Real protocol, fake backend (fakeredis)The orchestrator's actual Redis client code runs unmodified — the seam between RunStateStore and Redis is genuinely exercised — without requiring a real Redis process in CI
The MCP server (search tool, ping)Real (mounted in-process, per the scaffold)Whether the orchestrator's calls actually reach the MCP protocol layer and get correctly routed to a tool handler IS the seam mcp-and-agents/capstone_orchestrator_integration.html section 3 designed — mocking this away tests nothing about that design decision
An external LLM API call (inside a tool's logic)MockedGenuinely external, slow, costs real money per call, and non-deterministic — none of which this suite needs to verify; a fixed, canned response is sufficient since the LLM's own output quality is evals-and-observability/'s concern, not integration testing's
# Mocking ONLY the genuinely external dependency -- the LLM call # inside the summarization tool -- while everything else stays real from unittest.mock import AsyncMock, patch @pytest.mark.asyncio async def test_chat_with_mocked_llm(client): with patch("app.services.summarization.call_llm", new=AsyncMock(return_value="a fixed, canned summary")): response = await client.post("/chat", json={"message": "summarize the Q3 report"}) assert response.status_code == 200

Notice the mock is patched at the NARROWEST possible point — app.services.summarization.call_llm, the specific external call — rather than mocking the whole tool, the whole orchestrator, or the whole MCP layer around it. This preserves the real seam (orchestrator → MCP protocol → tool handler → service layer) while only removing the one piece that's genuinely external and non-deterministic, exactly the "protocol-agnostic service module" separation capstone_scaffold_fastapi_mcp.html's own practice problem 2 argued for.

Interview-ready definition: the mock-vs-real decision for each dependency in an integration test should be made by asking "is THIS dependency part of the seam I'm trying to verify?" — internal seams (orchestrator↔MCP, app↔database, app↔Redis) should stay real or protocol-faithful, while genuinely external, slow, costly, or non-deterministic dependencies (a real LLM API, a real third-party service) should be mocked at the narrowest point that still exercises everything around them.
03 — One real request, asserted on twice: the response AND the side effects

The end-to-end scenario, in full

Start here, before writing the assertions. A unit test typically asserts on ONE thing: a function's return value. An integration test for this capstone needs to assert on TWO categories of outcome, because a full orchestrated run produces two kinds of result — the reply returned to the caller, AND the durable records (trace, spans, eval score) it's supposed to leave behind in the schema lab 5 finalized. A test that only checks the response and never checks the database is blind to exactly the kind of bug lab 3's practice problem 1 covers: a span that starts but never closes, silently.

# tests/test_capstone_e2e.py import pytest @pytest.mark.asyncio async def test_full_orchestrated_run_produces_reply_and_records(client, test_db): # 1. ARRANGE: nothing extra needed -- the fixtures already gave us # a real app, a real (empty) test database, a real MCP server # mounted, and a fake-but-protocol-faithful Redis # 2. ACT: one real request through the full stack -- # FastAPI route -> orchestrator -> MCP tool dispatch -> # hybrid_search tool -> instrumentation -> response response = await client.post("/chat", json={ "message": "what does the capstone scaffold's readiness endpoint check?" }) # 3. ASSERT on the RESPONSE -- the user-visible contract assert response.status_code == 200 body = response.json() assert "run_id" in body assert len(body["reply"]) > 0 trace_id = response.headers["x-trace-id"] # set by tracing_middleware, lab 3 section 1 # 4. ASSERT on the SIDE EFFECTS -- did this run actually get recorded # the way lab 3's instrumentation and lab 5's schema promise? spans = await test_db.fetch( "SELECT span_name, ended_at FROM eval_span WHERE trace_id = $1", trace_id ) assert len(spans) >= 2 # root span + at least one tool-call span assert all(s["ended_at"] is not None for s in spans) # NO span left hanging open -- problem 1, lab 3 eval_result = await test_db.fetchrow( "SELECT score, passed FROM eval_result WHERE trace_id = $1", trace_id ) assert eval_result is not None # recorded UNCONDITIONALLY -- lab 3 section 2's rule # checked here, not just asserted in prose assert eval_result["score"] is not None

This single test exercises the ENTIRE integration surface this week's five prior labs built: the FastAPI route (lab wiring), the orchestrator's dispatch (lab 1), the search tool (lab 2), the tracing and eval instrumentation (lab 3), and the schema it all writes into (lab 5) — one failing assertion here pinpoints exactly which SEAM broke, in a way no single lab's own isolated tests could.

What a response-only test would miss: a version of this test that only checked response.status_code == 200 and "reply" in body would happily PASS even if the tracing middleware silently failed to write spans, or if score_run() raised and was swallowed somewhere — the user would still get a normal-looking reply, while the capstone's entire observability promise quietly failed underneath it. This is exactly why "assert on the response AND the resulting trace/eval records" is stated as a requirement, not a nice-to-have.
04 — One fast, repeatable check before every deploy

Structuring this as a repeatable smoke test

Start here, before treating section 3's test as the only thing that matters. A full integration suite (many scenarios, many edge cases) is valuable but too slow to run before every single deploy. A SMOKE TEST is a small, fast subset — does the system even come up and handle the most basic real request — run as a final gate, exactly the role cicd_eval_gating_survival_exercise.html's eval-gate stage plays for output quality, now applied to structural correctness.

tests/ ├── conftest.py # section 1's fixtures ├── unit/ # fast, isolated -- orchestrator routing logic, # fusion math, individual index query plans ├── integration/ │ ├── test_capstone_e2e.py # section 3's full scenario, plus variants # (tool failure, empty search results, etc.) │ └── test_schema_writes.py # targeted: does each table get written # correctly in isolation from a full run └── smoke_test.py # SECTION 4: the minimal pre-deploy gate, # run separately, run fast, run always

Not exhaustive -- that's what integration/ is for. # This just needs to be FAST and CATCH A TOTALLY BROKEN DEPLOY. response = await client.post("/chat", json={"message": "ping"}) assert response.status_code == 200 trace_id = response.headers["x-trace-id"] row = await test_db.fetchrow("SELECT 1 FROM eval_span WHERE trace_id = $1 LIMIT 1", trace_id) assert row is not None

The smoke test deliberately duplicates a SMALLER version of section 3's assertion rather than importing or calling it — smoke tests trade thoroughness for speed and independence; if section 3's larger integration file changes shape, the smoke test shouldn't break as a side effect of an unrelated refactor.

Problem 1 · Testing the empty-search-results case from lab 2

Write the integration test (structure, not full code needed) that verifies storage-and-rag/capstone_hybrid_search_integration.html's practice problem 1 fix — the orchestrator explicitly handling an empty search result rather than silently proceeding to generation. What would this test's arrange/act/assert look like, and what's the one dependency that MUST stay real for this specific test to mean anything?

Show solution
Arrange: seed the test database (or the search index/service, if mocked at that boundary specifically) so that a chosen query is GUARANTEED to return zero hybrid_search results -- e.g. querying for a term that matches nothing in the test corpus at all. Act: POST /chat with that query, exactly like section 3's scenario, through the real client fixture. Assert: this is the interesting part, and where it differs from section 3's happy-path test. Two things to check: (1) the RESPONSE should reflect problem 1's chosen fix explicitly -- e.g. the reply text contains an honest "no relevant information found" message rather than a suspiciously confident-sounding fabricated answer with no grounding; and (2) the EVAL RECORD for this run should reflect the same thing -- e.g. eval_type or an attribute on the eval_span marking this as an "empty_search" case, so the dashboard (lab 3) can actually distinguish this failure mode from a normal successful run, per problem 1's own solution in the hybrid search lab. The dependency that MUST stay real here: the search tool/index itself (or a faithful stand-in that genuinely returns zero results for the chosen query), NOT mocked to directly return an empty list. If the test mocks call_tool("hybrid_search", ...) to return [] directly, it never actually verifies that a REAL, no-match query against the REAL index produces an empty result in the first place -- it only verifies the orchestrator's handling of a hypothetical empty list, which could pass even if the real search tool never actually returns an empty list for ANY query (a bug in the search tool's own empty-result path would go completely undetected). This is exactly section 2's "is this dependency part of the seam being tested" question, applied here: the search-returns-empty behavior IS part of what this specific test needs to verify, so it can't be the mocked piece.
Problem 2 · A flaky test caused by fixture teardown order

Section 1's test_db fixture drops the test database after every test. A teammate reports that test_capstone_e2e.py passes reliably alone but fails intermittently when run as part of the FULL suite alongside other test files. What's the most likely cause given the fixture scope shown in section 1, and how would you confirm it?

Show solution
The most likely cause is a fixture SCOPE mismatch -- section 1's fixtures, as written, use pytest_asyncio's default function scope (a fresh test_db and run_store per individual test function), which should actually PREVENT this exact symptom if scope is correctly function-level throughout. So the realistic culprit is that a scope was accidentally widened somewhere -- e.g. test_db or run_store redefined with scope="session" or scope="module" in a conftest.py closer to the failing test file, intending to speed up the suite by reusing one database across many tests, but breaking test isolation in the process: an earlier test in the same session leaves rows behind (or a stale trace_id) that a LATER test's assertions accidentally match against, producing a pass or fail that depends on WHICH OTHER TESTS ran first and in what order -- the classic signature of shared, insufficiently-isolated test state, and exactly why "fails only in the full suite, passes alone" is such a strong diagnostic signal for this specific class of bug. To confirm: run the suite with pytest's -p no:randomly (or whatever disables test-order randomization, if a plugin like pytest-randomly is in use) to get a STABLE failure order, then bisect by running smaller and smaller subsets of tests before test_capstone_e2e.py until the minimal reproducing subset is found. Separately, grep the test directory's conftest.py files for any scope= argument on a fixture touching the database or Redis, since that's the concrete code change most likely to explain this exact symptom, and would show up immediately once specifically looked for rather than being obvious from the failure alone.
Problem 3 · Deciding where a test for lab 5's partial index belongs

Should a test verifying that database/capstone_schema_finalization_and_indexes.html's idx_agent_run_running partial index is actually used by the query planner (via EXPLAIN) live in tests/unit/, tests/integration/, or the smoke test — and why?

Show solution
tests/integration/, specifically NOT unit and NOT the smoke test, for two separate reasons that are each individually sufficient. Not unit: verifying an EXPLAIN plan requires a real database with real (or realistically-shaped, per capacity_estimation_practice.html's volume assumptions) data and a real query planner making a real cost- based decision -- there is no meaningful way to unit-test this against an isolated function or a mock, since the thing being tested IS the interaction between the database engine, its statistics, and the schema, not any single function's logic in isolation. This is a seam-level concern by definition, which is exactly what integration tests exist for. Not the smoke test: an index-usage check is valuable but not part of "is this deploy catastrophically broken" -- the smoke test's whole design point (section 4) is staying fast and minimal, catching total failures (won't start, can't reach the DB, MCP unreachable) before every deploy. A missing or unused index degrades PERFORMANCE, it doesn't break correctness or availability -- a real distinction worth keeping the smoke test's gate focused on. It belongs in the full integration suite instead, run on a slower cadence (e.g. nightly, or on every merge to main rather than every single deploy attempt), exactly the same reasoning that separates a fast CI lint/test/build stage from a slower, more thorough nightly suite in most real pipelines.
