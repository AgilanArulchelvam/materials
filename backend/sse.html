BACKEND & APIS LAB · SERVER-SENT EVENTS

SSE is just a plain HTTP response that never says it's finished writing.

Server-Sent Events are the simplest possible answer to "the server needs to push updates to the client" — a single long-lived HTTP response, streamed as plain text in a specific line-based format, reusing the ordinary HTTP request/response model instead of upgrading to a whole new protocol. This lab shows the real text/event-stream wire format frame by frame and works through exactly when one-directional streaming is enough, and when it genuinely isn't.

01 — One HTTP response, kept open forever

The text/event-stream wire format

Start here, before any wire format. Think of a sports radio broadcast versus a phone call: the broadcast is a single, continuous, ONE-directional stream that the station just keeps transmitting — listeners tune in and receive updates for as long as they stay tuned, but they never talk back over that same channel. SSE is exactly that: the server opens a response and simply never finishes writing to it, streaming new chunks of data down that same still-open connection whenever it has something new to send.

Technically, an SSE connection is a normal HTTP request whose response has Content-Type: text/event-stream and is never fully closed by the server. The browser's EventSource API keeps reading from that streaming response and parses out individual events as plain, line-based text — no binary framing, no separate protocol upgrade, just HTTP doing something HTTP was already capable of (a response body doesn't have to be small or fully known in advance).

THE REAL SSE WIRE FORMAT
data: {"price": 41.20, "ticker": "ACME"}\n\n data: {"price": 41.35, "ticker": "ACME"}\n\n data: this line and\ndata: this line join into one message\n\n
The framing detail that trips people up: a single SSE event is terminated by a BLANK line — that is, two consecutive newlines (\n\n), not one. A single data: line followed by just one newline is NOT yet a complete event; the parser keeps buffering until it sees the blank line. Multiple consecutive data: lines before that blank line are joined together (with a newline between them) into a single multi-line event's data — this is how SSE lets you stream multi-line text as one logical message.
Interview-ready definition: Server-Sent Events use the text/event-stream MIME type over a single, deliberately never-closed HTTP response; the server writes plain-text events using a simple line-based field format (field: value\n), with a blank line (\n\n) marking the end of each individual event. Multiple data: lines before that terminating blank line are concatenated into one multi-line message — this text-based, HTTP-native framing is what lets SSE work over ordinary HTTP/1.1 or HTTP/2 without any protocol upgrade or special handshake.
02 — Not just data — id, event, and retry each solve a real problem

id:, event:, and retry: fields

Start here, before the demo. A live sports score feed needs more than just "here's a number" — it needs a way to say WHAT KIND of update this is (a score change vs a red card vs the game ending), a way for a client that just reconnected after a dropped WiFi signal to say "catch me up from where I left off," and a way for the server to hint how patiently the client should wait before trying to reconnect at all. Those three needs map directly onto SSE's three optional fields.

WATCH id, event & retry FIELDS PARSED FROM A LIVE STREAM
id: 101 event: score-update data: {""home"": 2, "away"": 1} id: 102 event: score-update data: {"home": 2, "away"": 2} // client-side reconnection: browser automatically sends this header on // reconnect, using the LAST id: value it saw -- no app code required Last-Event-ID: 102
FieldWhat it's for
data:The actual payload of the event — one or more lines, joined if repeated
id:A resumption checkpoint — the browser remembers the last id seen and automatically sends it back as a Last-Event-ID header if the connection drops and reconnects, letting the server resume from where it left off instead of replaying everything
event:Names the event type (default is a generic "message" if omitted), letting client code register different handlers per event type instead of parsing every payload the same way
retry:Tells the browser how many milliseconds to wait before automatically attempting reconnection if the connection drops — a server-controlled backoff hint
Why this matters in practice: automatic reconnection with resumption via id:/Last-Event-ID is built directly into the browser's EventSource API with zero application code required — this is a genuinely underrated feature. A WebSocket, by contrast, gives you no built-in reconnection or resumption logic at all; you have to hand-write reconnect-with-backoff and any "catch me up on what I missed" logic yourself.
Interview-ready definition: beyond the required data: field, SSE supports id: (a checkpoint value the browser automatically echoes back as a Last-Event-ID header on reconnection, enabling server-side resumption), event: (a named event type letting client code dispatch different handlers per type instead of parsing every message uniformly), and retry: (a server-specified reconnection delay in milliseconds). Automatic reconnection and resumption via these fields are handled natively by the browser's EventSource API, requiring no custom client-side reconnect logic.
03 — Don't reach for bidirectional when you only need one direction

SSE vs WebSockets — when one-directional is genuinely enough

Start here, before the table. If you only ever need a radio broadcast (server → client, continuously, with the client never talking back over that same channel), building a full two-way phone line is unnecessary complexity — more protocol overhead, more server-side connection state to manage, and a client API with more surface area than the problem actually calls for. The right question isn't "which is more powerful" (WebSockets, unambiguously) — it's "does this specific feature actually need the client to push data back over the same connection."

SSE fits well

Live score updates, stock ticker feeds, server-side progress notifications for a long-running job, live log tailing, real-time notifications/activity feeds — all cases where the server has updates to push, and the client's only "communication back" need (if any) is handled fine by occasional separate normal HTTP requests, not the same streaming channel.

WebSockets are actually needed

Live chat (client sends messages just as often as it receives them), multiplayer games (constant bidirectional state), collaborative editing (every keystroke from every participant needs to flow both ways), or any case where the client needs to send data back over the SAME live connection frequently and with low latency, not via separate requests.

The trap in defaulting to WebSockets "to be safe": reaching for a WebSocket for a feature that's genuinely one-directional (say, a live notification badge) adds real, avoidable cost: you lose SSE's free automatic reconnection/resumption and have to hand-roll it, you take on a stateful bidirectional connection your server has to manage even though the client-to-server direction is never actually used, and — for the common "just push updates to the client" case — you gain no real capability you needed in the first place. Picking SSE when it's sufficient is not a lesser choice; it's the simpler tool correctly matched to a simpler problem.
Interview-ready definition: SSE is the correct choice when data only needs to flow server-to-client and the client's own communication needs (if any) are well served by ordinary, separate HTTP requests rather than the same streaming channel — it trades away bidirectionality for genuine simplicity, native browser reconnection with resumption, and reuse of plain HTTP infrastructure. WebSockets are necessary specifically when the client must also push data back frequently and with low latency over that SAME persistent connection — a requirement SSE's one-directional design cannot satisfy at all, regardless of how it's configured.

Problem 1 · Parsing the raw wire format by hand

Given this raw stream, how many distinct SSE events does it contain, and what is each one's data? "data: A\ndata: B\n\ndata: C\n\n"

Show solution
Two distinct events. A blank line (\n\n) marks the end of an event, so: Event 1: two consecutive "data:" lines ("A" and "B") appear before the first blank line — these get JOINED into one multi-line event whose data is "A\nB" (joined with a newline between them, per the SSE spec's handling of repeated data: fields within one event). Event 2: the single "data: C" line, terminated by its own blank line, is a separate, second event with data "C". The key parsing rule: it's not the NUMBER of data: lines that determines event count, it's the number of blank-line terminators — everything between one blank line and the next belongs to the same event, however many data: lines it contains.
Problem 2 · Reconnection without application code

A client's WiFi drops for 3 seconds during an active SSE stream with `id:` fields present, then reconnects. What happens automatically, with zero application code, and what does the server need to support to make this useful (not just automatic)?

Show solution
Automatically, with no application code: the browser's EventSource implementation detects the dropped connection and, after the retry: delay (or a browser default if none was specified), automatically issues a new HTTP request to reconnect -- and critically, it automatically includes a Last-Event-ID header set to the value of the last id: field it successfully received before the drop. For this to be USEFUL (not just automatically reconnecting and starting over), the SERVER needs to actually read that Last-Event-ID header on the new incoming request and resume the stream from the appropriate point -- e.g. re-sending any events the client missed while disconnected, using the id as a checkpoint into whatever backing store or event log the server maintains. The automatic reconnection is free; the actual GAP-FREE resumption requires the server to be written to honor Last-Event-ID deliberately -- a server that ignores this header will reconnect successfully but simply resume the live stream from "now," silently dropping whatever happened during the disconnect.
Problem 3 · Choosing SSE over WebSockets, justified

A team is building a feature where users get a small red badge count update whenever they receive a new notification (likes, comments, follows). A teammate suggests WebSockets "since it's more powerful and future-proof." Argue for SSE instead.

Show solution
The notification badge feature is a textbook one-directional case: the server has updates to push (new notification counts), and the client never needs to send anything back over that SAME channel -- any action the user takes in response (clicking to view notifications, marking as read) is naturally its own separate, ordinary HTTP request/API call, not something that needs to ride back over a live push channel. "More powerful" is true but irrelevant here — WebSockets' bidirectional capability is capability this feature will never use, and "future-proof" is a weak argument for taking on real, immediate costs (implementing manual reconnect-with-backoff logic that SSE gets for free via EventSource, managing bidirectional connection state server-side that's only ever used in one direction) against a hypothetical future need that may never materialize. If a genuinely bidirectional real-time need appears later, that's the point to introduce WebSockets for THAT feature specifically — not to pre-emptively add complexity to a feature that is, today, simply and completely one-directional.
Problem 4 · A genuinely wrong SSE choice

A team builds a collaborative document editor (like Google Docs) using SSE for the server-to-client updates, and separate individual HTTP POST requests every time a user types a character to send their edits to the server. What problem does this design run into that SSE cannot fix?

Show solution
Sending a separate HTTP POST request per keystroke is fundamentally the wrong shape for this problem, and no amount of SSE optimization on the receiving side fixes it — SSE only ever addresses the server-to-client half. Each individual POST carries full HTTP request overhead (headers, a new (or pooled) connection, TLS overhead if applicable) for what is conceptually a tiny, extremely frequent update — this adds real latency per keystroke and puts significant unnecessary load on the server handling what could be a continuous low-overhead stream instead of thousands of discrete request/response round trips. A WebSocket (or a client-streaming/bidirectional gRPC-style channel) would let the client push each edit over an already-open, low-overhead persistent connection instead of paying full HTTP request setup for every keystroke, while ALSO receiving other collaborators' edits over the same connection with much lower latency than juggling two entirely separate communication mechanisms. This is precisely the scenario — frequent, low-latency, genuinely bidirectional communication — where SSE's one-directional design is the wrong tool, no matter how well the server-to-client half is implemented.
Problem 5 · Why SSE needs no protocol upgrade

WebSockets require an HTTP upgrade handshake to switch to a different wire protocol entirely. Why doesn't SSE need anything similar?

Show solution
SSE doesn't need a protocol upgrade because it never actually leaves HTTP -- it's simply an ordinary HTTP response with a specific content type (text/event-stream) that the server chooses not to finish writing right away, streaming additional text over time instead of sending the full body at once and closing. HTTP has ALWAYS supported responses of unknown or arbitrarily large length via chunked transfer encoding (or, under HTTP/2, its native stream framing) -- SSE is really just a convention for how to FORMAT the text within an already-ordinary, already-supported kind of streaming HTTP response, plus a client-side API (EventSource) that knows how to parse that specific text format as it arrives. WebSockets, by contrast, needed the upgrade specifically because its FRAMING is fundamentally different from HTTP's — after the handshake, the connection stops being HTTP messages entirely and starts being WebSocket frames, a different wire format that needs both sides to explicitly agree to switch into. SSE never changes what protocol is being spoken at all — it's HTTP, formatted a specific way, from start to finish.
