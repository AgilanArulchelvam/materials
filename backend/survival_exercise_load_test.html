01 — Not the same question as "how fast is one request"

What load testing actually measures for a streaming service

Start here, before any tooling. Think about stress-testing a restaurant two completely different ways. One way: how fast can the kitchen produce a single dish, over and over, back to back — that's throughput for quick, self-contained transactions, and it's what a typical HTTP load test measures (requests per second, latency per request). The other way: how many tables can the restaurant simultaneously seat and keep occupied, each one lingering for an hour, before it runs out of chairs, staff attention, or floor space — that's a completely different question, about how many things can be held open AT ONCE, not how fast any one of them gets served.

A normal HTTP load test (hammering a REST endpoint) measures requests per second and per-request latency, because each request is quick and self-contained — it arrives, gets handled, and is gone. A streaming service's load test has to measure something structurally different: concurrent connection count — how many WebSocket or SSE connections can the service hold open AT THE SAME TIME, for realistic durations, without connections failing, memory climbing unboundedly, or the server refusing new connections.

DimensionTypical HTTP load testStreaming service load test
Primary metricRequests per second, p50/p95/p99 latencyMaximum concurrent open connections sustained without failure
Connection lifetimeMilliseconds — open, respond, closeMinutes to hours — deliberately held open
What actually gets exhaustedCPU/thread time per requestFile descriptors, connection pool slots, per-connection memory — resources that accumulate the LONGER connections stay open, not just how often new ones arrive
A "passing" run looks likeHigh req/sec at low latency, sustainedN concurrent connections held open for the full test duration with zero unexpected drops

This distinction matters because a tool or test plan built purely around "hit this endpoint N times per second" will systematically under-test a streaming service — it might never even attempt to hold more than a handful of connections open simultaneously, since a normal HTTP load generator's whole model is open-request-close-repeat, not open-and-hold. The streaming architecture integration lab covered why WebSockets and SSE both involve connections that are deliberately kept open far longer than a typical request — that's exactly the property this kind of load test has to stress.

Interview-ready definition: load testing a streaming (WebSocket/SSE) service measures concurrent connection capacity — how many long-lived connections the service can hold open simultaneously, for realistic durations, without dropping existing connections or refusing new ones — rather than requests-per-second, which is the wrong metric for a service whose defining property is holding a connection open rather than completing it quickly. The resources under real pressure in a streaming load test (file descriptors, pool slots, per-connection memory) accumulate with concurrent OPEN connections over time, not with request arrival rate, which is why a load test designed around throughput alone will miss the failure modes that actually matter for this kind of service.
02 — Actually opening (and holding) thousands of connections

A real connection-flooding script

Start here, before the code. To measure how many tables a restaurant can seat at once, you don't ask one customer to eat very fast — you actually seat many customers at once and see when the restaurant runs out of chairs. Load testing a streaming service works the same way: you need a script that actually opens many connections concurrently and, critically, HOLDS them open (doesn't immediately close them), because the failure modes this lab cares about only show up once a large number of connections are simultaneously alive, not just simultaneously opened-and-closed.

A simple asyncio-based flooding script does exactly this — open N WebSocket connections concurrently, keep each one alive with periodic pings, and track how many stay open successfully versus how many fail:

import asyncio import websockets async def hold_one_connection(conn_id: int, url: str, results: dict): try: async with websockets.connect(url) as ws: results["opened"] += 1 # hold the connection open, sending a lightweight ping periodically # so it doesn't look idle/abandoned to the server or any proxy while True: await ws.send(f'{{"type": "ping", "conn_id": {conn_id}}}') await asyncio.sleep(15) # realistic keep-alive interval, not a tight loop except Exception as e: results["dropped"] += 1 results["errors"].append(str(e)) async def flood(url: str, num_connections: int): results = {"opened": 0, "dropped": 0, "errors": []} # launch all connections CONCURRENTLY, not one after another -- # sequential opening would never actually stress "N open at once" tasks = [hold_one_connection(i, url, results) for i in range(num_connections)] await asyncio.gather(*tasks, return_exceptions=True) return results # ramp up in stages, checking results at each stage -- # don't jump straight to 10,000, since that tells you almost nothing # about WHERE things start failing for n in [100, 1000, 5000, 10000]: asyncio.run(flood("ws://localhost:8000/ws/chat/room1", n)) # inspect results["dropped"] and results["errors"] before ramping further

Two design choices in that script matter more than they look: launching every connection concurrently via asyncio.gather (not a sequential loop, which would never produce a real spike of simultaneously-open connections), and holding each one open with a periodic keep-alive rather than connecting and immediately disconnecting (a connect-and-drop loop tests connection SETUP throughput, a completely different thing from concurrent connection CAPACITY). A production-grade version of this exact idea is what a tool like Locust provides out of the box, with built-in ramp-up scheduling, live metrics, and a web UI for watching results as the test runs — but the asyncio script above is exactly what Locust (or any such tool) is doing underneath for a WebSocket target.

03 — Same symptom, three different root causes

Common causes of dropped connections under load, and how to tell them apart

Start here, before the diagnosis. Imagine your car won't start, and there are three completely different possible reasons: the battery is dead, the fuel tank is empty, or the starter motor itself is broken. All three produce a similar surface symptom ("it won't start"), but each has a distinct, checkable signal that tells you which one it actually is — the dashboard lights don't come on at all (battery), the engine cranks but doesn't catch (fuel), or you hear a click but no crank (starter). Diagnosing "connections are dropping under load" works the same way: the same broad symptom can come from at least three genuinely different root causes, each with its own distinct error signature.

File descriptor limits

Every open socket (every WebSocket or SSE connection) consumes one operating-system file descriptor, and every process has a ceiling on how many it's allowed to hold open at once — the ulimit -n value, often defaulting to a surprisingly low number (1024 on many systems) unless explicitly raised. Once a process hits that ceiling, it cannot open any MORE file descriptors — new connection attempts fail outright, and depending on how the accepting code handles the error, existing connections may also start failing if the process can't even open descriptors for other internal operations (like writing a log line) anymore.

# Checking and raising the file descriptor limit ulimit -n # 1024 <- the default ceiling on many systems, often far too low # for a service meant to hold thousands of concurrent connections ulimit -n 65536 # raise it for the current shell/process # the actual OS-level error when the ceiling is hit: # OSError: [Errno 24] Too many open files

Exhausted connection pools

This is a different resource entirely from OS file descriptors: it's the application-level database connection pool covered in the connection_pooling.html lab from earlier this month. Every incoming WebSocket connection that needs to touch the database (say, to persist a chat message) borrows a connection from that pool for the duration of its query, then returns it. Under a flood of concurrent streaming connections, if each one holds onto its borrowed DB connection for longer than expected (or if the pool size was sized for typical HTTP request volume, not this many simultaneous streaming clients each occasionally needing a DB connection), the pool runs out of available slots, and any NEW request needing a database connection blocks or times out waiting for one to free up — even though the OS-level sockets and file descriptors are completely fine.

Memory pressure

Each open connection isn't free even when it's idle — the server keeps some in-memory state per connection (buffers, the connection object itself, any per-connection application state like "which chat room is this socket subscribed to"). At a few hundred or even a few thousand connections this is negligible, but at tens of thousands of concurrent connections, the CUMULATIVE per-connection memory overhead can genuinely approach or exceed the process's available memory, causing the OS to start killing the process (an OOM kill) or the server to slow to a crawl under garbage-collection/paging pressure well before any explicit "connection refused" error appears.

Failure modeWhat you'll seeHow to confirm it's THIS one
File descriptor limitOSError: [Errno 24] Too many open files, new connections refused outright, existing ones sometimes also failingCheck ulimit -n against the actual concurrent connection count the server is holding; the failure count tracks closely against hitting that exact ceiling
Connection pool exhaustionTimeouts specifically on operations that touch the database (not on the streaming connection itself), e.g. TimeoutError: QueuePool limit exceededThe WebSocket/SSE connections themselves stay open and healthy; only DB-dependent operations inside them start failing or hanging
Memory pressureGradual slowdown across the whole process, then an OOM kill (process dies entirely) or the OS starts swapping heavilyWatch process memory (RSS) climb roughly linearly with concurrent connection count over the course of the ramp, well before the fd or pool limits are hit
The trap: all three failure modes can produce a vague, generic symptom like "some clients report their connection dropped" if you're only watching client-side behavior. The actual root cause is only visible from SERVER-side signals — the specific exception type and where in the stack it originates, the OS-level fd count, the connection pool's own metrics, and process memory over time. Diagnosing "which one is it" without server-side logs and metrics is close to guessing; this is exactly why observability (structured logging with the specific exception, and basic resource metrics) has to exist BEFORE you run a load test, not be added afterward once something breaks.
Interview-ready definition: the three most common causes of dropped connections under load for a streaming service are (1) OS-level file descriptor exhaustion — the process hits its ulimit -n ceiling on open sockets, surfacing as OSError: Too many open files; (2) application-level connection pool exhaustion — a database connection pool sized for typical request volume runs out of available slots under many concurrent streaming clients, surfacing as pool timeout errors specifically on DB-touching operations, with the streaming connections themselves staying healthy; and (3) memory pressure — cumulative per-connection state across tens of thousands of open connections approaches available process memory, surfacing as gradual slowdown followed by an OOM kill rather than an explicit connection-refused error. Each has a distinct server-side signature, which is why diagnosis requires server-side observability, not just observing that clients are disconnecting.

Problem 1 · Diagnosing from a specific error message

During a load test ramping toward 8,000 concurrent WebSocket connections, the server logs start showing OSError: [Errno 24] Too many open files at around connection #4,096, and new connection attempts start being refused outright, while all previously-open connections keep working fine. Which of the three failure modes is this, and what's the fix?

Show solution
This is file descriptor exhaustion. The specific error (Errno 24, "Too many open files") is the OS-level signal for exactly this failure mode, and the fact that it hits at a specific, round-ish number (4,096 is a very common default/soft ulimit value, or half of a 8192-ish limit combined with other fds the process already had open for logs, listening sockets, etc.) rather than climbing gradually is consistent with hitting a hard ceiling rather than a resource degrading progressively. The fact that EXISTING connections keep working is also consistent -- the process already holds those file descriptors; it's only NEW open() calls (new incoming connections) that fail once the ceiling is hit. Fix: raise the process's file descriptor limit before running the service under this kind of load -- ulimit -n 65536 (or an appropriate higher value based on expected peak concurrency) in the process's startup environment, not just in an interactive shell that won't apply to how the service is actually deployed (e.g. in a systemd unit file's LimitNOFILE= setting, or the container/orchestrator's ulimit configuration if containerized).
Problem 2 · Distinguishing pool exhaustion from fd exhaustion

At 3,000 concurrent chat connections, clients report messages aren't being saved (though the chat connection itself stays open and messages still broadcast to other users in the room in real time). Is this more likely file descriptor exhaustion or connection pool exhaustion? Justify using the specific symptom.

Show solution
Connection pool exhaustion, not file descriptor exhaustion -- and the key diagnostic detail is exactly what's stated: the WebSocket connection itself stays open and healthy (messages still broadcast live to other users), while only the DATABASE-touching part of the operation (saving the message) is failing. If this were file descriptor exhaustion, the WEBSOCKET connections themselves (which are also just file descriptors) would be failing to open or would be getting dropped -- fd exhaustion doesn't selectively spare the socket layer while breaking only DB writes, because sockets and DB connections both consume file descriptors from the SAME OS-level pool of them. The pattern here -- streaming layer fine, only DB-dependent operations failing/timing out -- is specifically what happens when the application- level connection pool (a fixed number of DB connection slots, sized based on some assumption about concurrent DB usage) runs out of available slots under 3,000 concurrent chat connections each occasionally needing one to persist a message. The fix is either increasing pool size (with awareness of the underlying database's own max-connections ceiling) or reducing how long each borrowed connection is held per operation, not touching the OS file descriptor limit at all -- that's the wrong lever for this specific symptom.
Problem 3 · Reading a memory-pressure symptom correctly

A load test shows the server's process memory climbing steadily and roughly linearly as concurrent connections ramp from 1,000 to 20,000, with no explicit error messages at any point — until the process is suddenly killed by the OS partway through the ramp to 25,000. What failure mode is this, and why does it look so different from the fd-exhaustion case in Problem 1?

Show solution
This is memory pressure culminating in an OOM (out-of-memory) kill. It looks structurally different from fd exhaustion because the underlying resource behaves differently: file descriptors are a HARD, discrete ceiling (ulimit -n) that either has room or doesn't -- hitting it produces an immediate, specific error (Errno 24) the moment the ceiling is crossed, with no gradual warning beforehand from the OS itself. Memory is a SOFT, continuous resource that degrades gradually as it's consumed -- there's no single "memory ceiling reached" error from the kernel the way there is for file descriptors; instead the OS silently allows memory use to climb (each additional connection's buffers, connection object, and per-connection app state adding a small, roughly constant amount) right up until the process either can't allocate any more and crashes on its own, or the OS's out-of-memory killer decides to forcibly terminate the process to protect the rest of the system -- which is exactly the "suddenly killed" behavior described here, with no graceful error message from the application's own code, because the process didn't get a chance to log one before being killed externally. The practical implication: memory pressure needs to be caught via PROACTIVE monitoring (watching RSS/process memory climb during the ramp, well before it's exhausted) rather than reactive error handling, since by the time the symptom is "the process got killed," there's no clean error to catch or handle -- the fix has to happen earlier, either by reducing per-connection memory footprint or by capping the maximum concurrent connections the service will accept before that ceiling is ever approached.
Problem 4 · Designing a staged ramp and explaining why it beats a single big jump

A teammate proposes load testing by immediately opening 20,000 concurrent connections in one shot, reasoning "if it survives 20,000, we're done, and if it doesn't, we know we have a problem." What's lost by skipping the staged ramp (100 → 1,000 → 5,000 → ...) from section 2?

Show solution
Jumping straight to 20,000 tells you PASS or FAIL at 20,000, but not WHERE in that range things actually start breaking, nor WHICH failure mode is responsible -- and this lab's whole diagnostic section depends on being able to correlate a failure with a specific concurrency level and a specific server-side symptom. If the single-jump test fails, you're left knowing only "something broke somewhere between 0 and 20,000 connections," which could be fd exhaustion at 4,096, pool exhaustion at 9,000, memory pressure starting around 15,000, or some combination overlapping and compounding each other -- with no way to tell which, since all the resource pressure arrived at once. A staged ramp (100 → 1,000 → 5,000 → 10,000...) with server-side metrics checked at EACH stage isolates roughly where each failure mode's threshold sits: if 5,000 succeeds cleanly but 10,000 shows Errno 24 specifically, you've narrowed the fd ceiling to somewhere between those two numbers, with a clean error signature pointing at exactly which resource it was. This is the same reasoning as binary-searching for a bug rather than guessing at the whole range at once -- staged, observed ramping turns "it broke somewhere" into "it broke at approximately N connections, and here's the specific error that tells us why."
Problem 5 · Confirming schema and migrations hold up under the same load test

The Week 4 survival exercise checkpoint also says to "confirm schema + migrations hold up." Concretely, what would you actually check here, connecting this back to the migrations lab from earlier this week?

Show solution
This means running the SAME load test against a database that has already had the week's Alembic migrations applied (e.g. the notification_delivery_log table with its JSONB provider_response column, or the "add last_login to users" example), and confirming two separate things under real concurrent load, not just correctness in isolation: 1. The migrated schema performs acceptably under the SAME concurrency this lab is stress-testing -- e.g. does the notification_delivery_log table's indexing hold up when thousands of concurrent connections are each writing delivery-attempt rows simultaneously, or does write contention on that table become its own bottleneck alongside (or instead of) the three connection-level failure modes covered in section 3? This is a genuinely different question from "does the migration run correctly once" -- a migration can be structurally correct and still perform poorly under concurrent write load if, say, a needed index was missed. 2. The migration's REVERSIBILITY doesn't get invalidated by data written during the load test -- if the load test itself writes a large volume of new rows using the post-migration schema, running downgrade() (as covered in Problem 5 of the migrations lab) afterward should still behave predictably, not fail or silently corrupt the freshly-written load-test data. This is a practical check that the migration's downgrade() path was genuinely tested, not just written and assumed to work, before treating it as safe to deploy.
