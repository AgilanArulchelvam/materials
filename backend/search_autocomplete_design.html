01 — A tree shaped exactly like the words it stores

Tries: building one, then searching it character by character

Start here, before any code. Imagine a dictionary organized not alphabetically on a shelf, but as a physical maze: you enter at the front door, and the FIRST letter of the word you're looking for is a hallway choice — go left for "c," go right for "d." Down the "c" hallway, the SECOND letter is another set of doors. Keep following letter by letter, and you end up in a room representing the complete word, with everything reachable from that room being every word that shares that same prefix. Someone looking for anything starting with "ca" just walks to the "ca" junction and explores everything past it — they never need to revisit the front door or any other hallway.

A trie (prefix tree) is exactly this maze, built as a tree structure: each node represents one character, and a path from the root down to some node spells out the prefix formed by the characters along that path. A node is marked as the END of a real word if some complete word ends exactly there. Building a trie means inserting each word one character at a time, following existing nodes where they already exist and creating new ones only where a path doesn't yet exist — words sharing a common prefix automatically share the same nodes for that prefix, which is the structural reason tries are so well suited to prefix search in the first place.

# Roughly how a trie node and insertion work class TrieNode: def __init__(self): self.children = {} # char -> TrieNode self.is_word_end = False def insert(root, word): node = root for ch in word: if ch not in node.children: node.children[ch] = TrieNode() # new hallway/door node = node.children[ch] node.is_word_end = True # mark the room as a complete word

Notice exactly what happened: the search walked only 2 hops (c → a) to reach the node representing the prefix "ca," then explored ONLY the subtree hanging beneath that node — never touching "dog" or "do" at all, since those words don't share the "ca" prefix and therefore live in a completely different branch of the tree. This is the entire mechanism behind why prefix search on a trie is fast: cost scales with the LENGTH of the prefix typed plus the number of matching completions, not with the total number of words stored.

Interview-ready definition: a trie (prefix tree) stores a set of strings as a tree where each root-to-node path spells out a prefix, and nodes marking the end of a real word are flagged explicitly — words sharing a prefix automatically share the nodes for that prefix. A prefix search descends the trie one character at a time following the query's characters, then performs a traversal (e.g. DFS) of the subtree rooted at the node where the prefix ends, collecting every word-ending node found — this makes prefix search's cost proportional to the prefix length plus the number of matches, not the total dictionary size.
02 — Sub-100ms per keystroke, at massive scale, means you can't compute live

Ranking suggestions and the latency budget

Start here, before the trade-offs. Imagine a restaurant host who, instead of memorizing which tables are typically requested most, had to re-survey every single table's status from scratch every time someone walked in and asked "table for two?" That would be accurate, but far too slow for a busy Friday night — a good host instead keeps a running mental model of what's popular and available, updated periodically, so they can answer instantly without re-deriving everything on the spot for every guest.

Autocomplete has a brutal latency constraint: a response needs to land well under 100ms per keystroke, or the UI feels laggy and defeats the entire point of "auto"-completing as someone types. At real product scale — potentially many millions of queries per second across all users combined, all typing different prefixes at different moments — traversing a live trie and re-ranking candidates on every single keystroke, for every user, is exactly the kind of repeated, predictable computation that's far cheaper to precompute and cache than to compute fresh on each request. A common real design: periodically (e.g. from a batch job processing recent query logs) compute and cache the TOP completions for every prefix that's actually been searched, so that a live request becomes a cheap cache lookup by prefix string rather than a live tree traversal plus a ranking computation.

# Precomputed top-K completions per prefix, refreshed periodically # (e.g. hourly, from query-frequency logs) -- NOT computed per request def precompute_top_completions(query_log, top_k=5): prefix_to_ranked = {} for prefix in all_prefixes_seen(query_log): candidates = completions_for(prefix) ranked = sorted(candidates, key=lambda c: -c.historical_frequency) prefix_to_ranked[prefix] = ranked[:top_k] return prefix_to_ranked # cached in a fast key-value store, e.g. Redis def handle_keystroke(prefix, cache): return cache.get(prefix, []) # O(1) cache lookup, not a live trie search
TYPE A PREFIX — SUGGESTIONS RANKED BY POPULARITY, NOT ALPHABET

Notice the ranking above isn't alphabetical — "care" outranks "card" and "cat" even though "car" comes first alphabetically among words sharing the "ca" prefix, because "care" has a higher historical popularity/frequency in the (simulated) query log. Ranking by historical popularity/frequency — how often each completion has actually been searched by real users in the past — is the standard approach, since it directly optimizes for "what is the user most likely to actually want," which alphabetical order has no relationship to at all.

Interview-ready definition: autocomplete's sub-100ms-per-keystroke latency requirement, combined with massive query volume, makes live per-request computation of ranked completions impractical at scale — the standard design instead precomputes and caches the top-K completions for each prefix (refreshed periodically from query-frequency logs, e.g. via a batch job), turning each live request into a fast cache lookup rather than a live trie traversal plus ranking pass. Suggestions are ranked by historical popularity/frequency (how often that completion has actually been searched before), not alphabetically, since frequency directly reflects what users are statistically most likely to want next.
03 — What happens when the prefix itself has a typo in it

Handling typos and fuzzy matches

Start here, before edit distance. A pure trie/prefix match has a hard requirement: every character typed must exactly match a real path in the tree. Type "resturant" instead of "restaurant" and a literal trie walk falls off the tree entirely at the missing "a" — no completions found, even though a human reading "resturant" instantly understands what was meant. Autocomplete needs some tolerance for this, since typos are extremely common, especially on mobile keyboards.

The standard mechanism for measuring "how close" two strings are is edit distance (specifically Levenshtein distance): the minimum number of single-character insertions, deletions, or substitutions needed to turn one string into the other. "resturant" and "restaurant" have an edit distance of 1 — inserting a single "a" turns one into the other. A fuzzy-tolerant autocomplete can allow candidates within a small edit distance (e.g. 1 or 2) of the typed prefix to still surface as suggestions, rather than requiring an exact prefix match.

EDIT DISTANCE, CONCRETELY

"cat" vs "cot": one substitution (a → o) turns one into the other — edit distance 1. "kitten" vs "sitting": edit distance 3 (substitute k→s, substitute e→i, insert g).

Interview-ready definition: edit distance (Levenshtein distance) between two strings is the minimum number of single-character insertions, deletions, or substitutions required to transform one string into the other — it's the standard mechanism for measuring how "close" a typo'd input is to an intended word. Autocomplete systems use it to tolerate small typos by allowing candidates within a small edit-distance threshold of the typed input to still surface, rather than requiring a literal exact-prefix trie match, at the cost of needing to search a wider (fuzzy) candidate space than a pure exact-prefix trie walk would.
The scale tension: computing true edit distance between a query and every candidate word is more expensive than a plain trie walk (it's a small dynamic-programming computation per candidate pair, not a single character-by-character tree descent), so production autocomplete systems typically restrict fuzzy matching to a bounded neighborhood (e.g. only checking candidates within edit distance 1-2, or precomputing common typo variants alongside the correctly-spelled term) rather than fuzzy-matching the ENTIRE dictionary against every keystroke — this keeps typo tolerance from blowing the same sub-100ms latency budget that motivated precomputing rankings in section 2 in the first place.

Problem 1 · Tracing a trie build and search by hand

Insert the words "app", "apple", "apply" into an empty trie, in that order. How many total nodes exist after all three insertions (excluding the root), and which nodes are marked as word-ends?

Show solution
"app" creates 3 nodes: a -> p -> p, with the second "p" node marked as a word-end (completing "app"). "apple" shares the "app" prefix entirely (a, p, p already exist from the first insertion), so it only needs 2 NEW nodes: l -> e, with the "e" node marked as a word-end (completing "apple"). Total nodes so far: 5 (a, p, p, l, e). "apply" shares "appl" with the existing path (a, p, p, l all already exist -- the "l" node was created during "apple"'s insertion), so it only needs 1 NEW node: y, marked as a word-end (completing "apply"). Total nodes: 6 (a, p, p, l, e, y). Word-end nodes: the second "p" (app), the "e" under l (apple), and the "y" under l (apply) -- three word-end markers total. This demonstrates the trie's core space efficiency: three words sharing long common prefixes needed only 6 total character nodes, not 3+5+5=13 nodes a naive independent-storage approach would need, because "app" and "appl" were each built once and reused by every word sharing that prefix.
Problem 2 · Explaining why precomputation is the right call, quantitatively

A product serves 2 million autocomplete keystrokes per second at peak, and each live trie-walk-plus-ranking computation takes roughly 3ms of CPU time. Explain concretely why precomputing top completions per prefix (section 2) is close to mandatory here, not just a nice-to-have optimization.

Show solution
At 2 million keystrokes/second and 3ms of CPU time per live computation, the AGGREGATE CPU-time demand is 2,000,000 * 0.003 = 6,000 CPU-seconds of work needed EVERY SECOND just to serve live computation for this one feature -- meaning the system would need roughly 6,000 CPU cores running flat out, permanently, just for autocomplete ranking alone, even before accounting for network overhead, other backend work, or traffic spikes above the stated "peak" number. This is an enormous, likely cost-prohibitive amount of dedicated compute for a single feature, especially one where the underlying data (word/prefix popularity) doesn't meaningfully change millisecond to millisecond. Precomputing top completions per prefix converts this from "6,000 cores of live computation, every second, forever" into "an O(1) cache lookup per keystroke (sub-millisecond) plus a periodic batch job (e.g. hourly) that does the expensive ranking work ONCE per prefix, not once per individual keystroke that happens to hit that prefix." Since the same popular prefixes get typed by many different users constantly, the batch job's one-time cost is amortized across an enormous number of live requests that each just read the cached, already-computed answer -- this is precisely the scale of savings that makes precomputation close to mandatory rather than a nice-to-have here.
Problem 3 · Diagnosing a staleness problem from precomputed rankings

A team precomputes top completions per prefix once per day. A completely new, suddenly-trending search term starts getting typed heavily mid-day but doesn't appear in autocomplete suggestions until the next day's batch run. Is this a bug? What's the actual trade-off being made, and how would you address it without abandoning precomputation entirely?

Show solution
This isn't a bug -- it's the direct, expected consequence of the precompute-and-cache design described in section 2: cached rankings are only as fresh as the last batch run that computed them, so anything that becomes popular AFTER that run genuinely won't be reflected until the NEXT run, by design. This is the real trade-off precomputation makes: trading some ranking freshness/recency for a massive reduction in live per-request compute cost (Problem 2) -- there's no way to get both perfectly live rankings AND the compute savings of precomputation simultaneously; some staleness window is inherent to the approach. Addressing it without abandoning precomputation: shorten the batch refresh interval for prefixes with unusually high recent query velocity (refresh trending prefixes more often, e.g. every few minutes, while leaving stable/rarely-changing prefixes on the daily cycle) -- this targets the actual pain point (fast-moving trends) without paying the full live-computation cost for the entire dictionary. Another common approach: maintain a small, fast "trending now" overlay computed on a much shorter cycle (or even a lightweight streaming counter) that gets blended with the daily-batch base ranking at serve time, giving new trends a path to surface quickly without re-architecting the whole precomputation pipeline.
Problem 4 · Choosing an edit-distance threshold under a latency constraint

A team is deciding whether to allow fuzzy matches within edit distance 1, or edit distance 3, of the typed prefix. What does raising the threshold from 1 to 3 cost, concretely, and why does section 3's "scale tension" callout matter here?

Show solution
Raising the allowed edit distance from 1 to 3 dramatically increases the number of dictionary candidates that fall within the fuzzy-match neighborhood of any given typed prefix -- edit distance 1 only catches single-character typos (one wrong/missing/extra letter), while edit distance 3 catches far more garbled inputs, which means far MORE candidate words need to be checked (or precomputed as typo variants) for every possible prefix, since the "close enough" neighborhood around any given string grows sharply as the allowed distance increases (roughly exponentially with the alphabet size and distance, in the worst case for brute-force checking). This directly matters for section 3's scale tension: computing true edit distance is more expensive per comparison than a trie walk, so checking against a much larger candidate set (because the threshold is looser) at the same per-keystroke latency budget is a real cost increase, risking blowing the sub-100ms budget the whole system is built around. In practice this pushes toward a threshold like 1-2 (catching the large majority of realistic single-typo mistakes) rather than something as loose as 3, and toward precomputing common typo variants for popular terms specifically, rather than fuzzy-matching the live query against the full dictionary at request time regardless of threshold.
Problem 5 · Combining all three mechanisms into one design decision

A user types "aple" (missing a "p", intending "apple"). Walk through, mechanism by mechanism, why a well-designed autocomplete system still surfaces "apple" as a suggestion despite the typo, tying together the trie, ranking, and edit-distance concepts from this lab.

Show solution
A pure literal trie walk on "aple" fails structurally partway through: following a -> p -> l finds no "l" child under the second "p" node in a trie that only contains "apple" (a -> p -> p -> l -> e) unless "aple" happens to also be a stored word -- the walk falls off the tree with no completions found via exact prefix matching alone, exactly as section 3 describes. This is where edit distance comes in: "aple" is edit distance 1 from "apple" (one character, a "p", was deleted) -- well within a typical fuzzy-match threshold like 1-2. A well-designed system, upon failing (or in parallel with) the exact trie walk, checks nearby fuzzy-match candidates within that edit-distance threshold and finds "apple" as a strong candidate despite the missing letter. Once "apple" (and any other typo-tolerant candidates) are identified, RANKING still applies exactly as in section 2 -- if multiple fuzzy candidates are found near "aple" (say, "apple" and some rarer word also within edit distance 1), they get ordered by historical popularity/frequency, not alphabetically or by edit distance alone, so the far more commonly searched "apple" would be ranked above an obscure edit-distance-1 alternative. And for latency, this fuzzy-lookup path itself benefits from precomputation too: common typo variants of popular terms (like "aple" -> "apple") are often precomputed and cached directly, the same way exact-prefix completions are, rather than computing live edit distance against the whole dictionary on every fuzzy-triggering keystroke.
