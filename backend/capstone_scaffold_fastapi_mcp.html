01 — Decide the shape before writing a single route

Project structure

Start here, before any code. Think about the difference between moving into an empty house and just piling boxes wherever you first set them down, versus deciding room-by-room what goes where BEFORE unpacking a single box — kitchen things in the kitchen, even if the kitchen is still empty on day one. A capstone scaffold is exactly the second approach: the directories below are mostly EMPTY or near-empty right now, but their existence and names commit to where things will live in Weeks 2–3, so nothing has to be reorganized later once real code starts filling them in.

capstone/ ├── main.py # FastAPI app entrypoint -- section 2 ├── app/ │ ├── __init__.py │ ├── routers/ # HTTP route groups (health, chat, admin) │ │ └── health.py │ ├── orchestrator/ # EMPTY for now -- Week 2 slot, see section 4 │ │ └── __init__.py │ ├── mcp_servers/ # MCP server(s) this backend hosts -- section 3 │ │ ├── __init__.py │ │ └── example_server.py │ ├── observability/ # EMPTY for now -- Week 2 slot, see section 4 │ │ └── __init__.py │ └── config.py # settings, env vars ├── tests/ │ └── test_health.py ├── pyproject.toml └── .env.example

Four directories, four responsibilities, deliberately kept separate: routers/ owns HTTP surface area (per backend/fastapi_routing_and_pydantic.html's routing patterns), mcp_servers/ owns the MCP server(s) this backend hosts or proxies to (per mcp-and-agents/mcp_server_stdio.html / mcp_server_sse.html), orchestrator/ is an intentionally EMPTY slot for the agent/orchestration logic Week 2 will fill in, and observability/ is an intentionally EMPTY slot for the tracing/eval hooks Month 4–5 already built and Week 2 will wire in.

Interview-ready definition: a scaffold's job is to commit to the SHAPE of a system — where each kind of code will eventually live — before most of that code exists, using empty-but-present directories as explicit placeholders rather than letting structure emerge ad hoc as features get added. This matters specifically for a capstone spanning multiple weeks: Week 2's "wire the orchestrator in" task should mean "fill in app/orchestrator/," not "figure out where orchestration code should even go."
02 — Health and readiness before a single real feature

The FastAPI app

Start here, before any business logic. Think about a new employee's first day: before they're handed any real work, someone checks that their badge opens the door and their laptop actually boots — trivial checks, but checks that would be a genuine problem to skip, because every subsequent thing depends on them silently working. A service's health and readiness endpoints are the same idea: before the capstone does anything interesting, it needs to be provably "the process is up" (liveness) and separately "the process is up AND ready to serve real traffic" (readiness) — two different questions, and conflating them is a common, costly mistake in real deployments.

# main.py from fastapi import FastAPI from app.routers import health from app.config import get_settings def create_app() -> FastAPI: settings = get_settings() app = FastAPI( title="Capstone Agent Backend", version="0.1.0", ) # health/readiness FIRST -- every other router gets registered after this, # so even a broken feature router still leaves health checks reachable app.include_router(health.router) # orchestrator and MCP routers get registered here in Week 2 -- # see section 4 for exactly what goes here and why it's still empty now return app app = create_app()
# app/routers/health.py from fastapi import APIRouter from pydantic import BaseModel router = APIRouter(tags=["health"]) class HealthResponse(BaseModel): status: str # LIVENESS: "is the process running at all?" -- should almost never fail; # if it does, the process itself is broken (crashed event loop, deadlock) # and the orchestrator (k8s, etc.) should restart the whole container @router.get("/healthz", response_model=HealthResponse) async def liveness(): return HealthResponse(status="alive") # READINESS: "is the process ready to serve REAL traffic?" -- checks actual # dependencies (can it reach its MCP server? its DB, once one exists?). # A process can be ALIVE but NOT READY (e.g. still starting up, or a # dependency is temporarily down) -- exactly the distinction # systems/load_balancers.html draws for why LBs check readiness, not # just liveness, before routing traffic to an instance @router.get("/readyz", response_model=HealthResponse) async def readiness(): # Week 2: check MCP server connectivity, DB connectivity, etc. here. # For now, ready == alive, since there's nothing else to depend on yet. return HealthResponse(status="ready")
Interview-ready definition: liveness answers "is this process running and not deadlocked" and should almost never fail short of the process itself being broken; readiness answers "is this process currently able to correctly serve a real request" and CAN legitimately fail temporarily (a dependency is down, startup isn't finished) without the process itself needing to be killed and restarted. Conflating the two — using one endpoint for both — means a load balancer either routes traffic to an instance that's up but can't actually serve requests, or an orchestrator restarts a perfectly healthy process just because one downstream dependency blipped.
03 — Connect the protocol you already know, don't re-learn it

Wiring in an MCP server

Start here, before any MCP-specific code. This section assumes mcp-and-agents/mcp_fundamentals_jsonrpc.html's JSON-RPC message shape, mcp_server_stdio.html's stdio transport, and mcp_server_sse.html's SSE transport as already-understood prerequisites — this section is purely about the WIRING: how an MCP server ends up reachable from this FastAPI app, not what MCP fundamentally is.

# app/mcp_servers/example_server.py # A minimal MCP server exposing ONE example tool, using the SSE # transport (per mcp_server_sse.html) so it can be mounted directly # into the same FastAPI app rather than run as a separate process from mcp.server import Server from mcp.types import Tool, TextContent capstone_mcp = Server("capstone-tools") @capstone_mcp.list_tools() async def list_tools() -> list[Tool]: # per json_schema_tool_specs.html's schema shape -- real tools get # added here as Weeks 2-3 build them out return [ Tool( name="ping", description="Trivial example tool -- confirms the MCP server is reachable end to end", inputSchema={"type": "object", "properties": {}}, ) ] @capstone_mcp.call_tool() async def call_tool(name: str, arguments: dict) -> list[TextContent]: if name == "ping": return [TextContent(type="text", text="pong")] raise ValueError(f"Unknown tool: {name}")
# Mounting it into the FastAPI app -- goes in main.py's create_app(), # right where section 2 left the comment for it from mcp.server.sse import SseServerTransport from app.mcp_servers.example_server import capstone_mcp def mount_mcp(app: FastAPI) -> None: sse_transport = SseServerTransport("/mcp/messages") @app.get("/mcp/sse") async def handle_sse(request): async with sse_transport.connect_sse(request) as (read, write): await capstone_mcp.run(read, write, capstone_mcp.create_initialization_options()) # then, in create_app(): # mount_mcp(app) # right after app.include_router(health.router)

Why SSE over stdio for this scaffold specifically: stdio (per mcp_server_stdio.html) is the right transport when an MCP server is spawned as a subprocess by its client (common for local dev tools), but this capstone's MCP server needs to be reachable over HTTP from the SAME FastAPI process that serves everything else — SSE is the transport built for exactly that shape, and it's what lets the readiness check in section 2 eventually verify "is my own MCP server actually responding" as one of its real dependency checks.

Interview-ready definition: wiring an MCP server into a FastAPI backend means mounting the MCP server's transport (SSE, for an in-process HTTP-reachable server) as additional routes on the same FastAPI app, alongside the ordinary REST routes — the MCP server and the REST API are two DIFFERENT protocols served by the SAME process, not two separate services, which is exactly why this scaffold's app/mcp_servers/ directory sits next to app/routers/ rather than as a wholly separate deployable unit.

05 — A scaffold that doesn't run is not a scaffold

Verify the scaffold works

Start here, before moving to Week 2. A skeleton that "looks right" but has never actually been run is worse than no skeleton at all — it hides broken imports, missing dependencies, and wiring mistakes until Week 2, when there's real feature code layered on top and every bug is harder to isolate. This checklist is the literal verification pass: run it now, on the scaffold exactly as built in sections 1–3, before adding anything else.

# from the capstone/ directory uv venv && source .venv/bin/activate # or your preferred env tool uv pip install -e . # run it, per uvicorn_gunicorn_workers.html's dev-mode invocation uvicorn main:app --reload --port 8000 # in a second terminal: curl http://localhost:8000/healthz # expect: {"status": "alive"} curl http://localhost:8000/readyz # expect: {"status": "ready"} curl http://localhost:8000/mcp/sse # expect: an open SSE connection, not a 404/500
What "done" means for this lab specifically: every box above checked, on THIS machine, today — not "the code looks like it should work." The entire value of scaffolding before building real features is catching wiring problems (a missing dependency, a transport misconfiguration, an import cycle between app/orchestrator/ and app/mcp_servers/) while the codebase is still small enough that the cause is obvious, rather than three weeks from now when the same bug is buried under real feature code.

Problem 1 · Making readiness actually check the MCP server

Section 2's /readyz currently just returns "ready" unconditionally. Extend it to genuinely check that the MCP server mounted in section 3 is reachable and responsive, and explain what status code and body it should return if the MCP server is NOT responding.

Show solution
A real readiness check needs to actually EXERCISE the dependency, not just check that the mounting code ran without erroring at startup -- those are different failure modes. A reasonable implementation calls the MCP server's own list_tools() handler directly (in-process, since it's mounted in the same app) with a short timeout, and reports failure if it raises or times out: async def readiness(): try: tools = await asyncio.wait_for(capstone_mcp_list_tools_handler(), timeout=2.0) mcp_ok = len(tools) >= 0 # just confirming it responded at all except Exception: mcp_ok = False if not mcp_ok: raise HTTPException(status_code=503, detail={"status": "not_ready", "reason": "mcp_server_unreachable"}) return HealthResponse(status="ready") The status code matters: 503 Service Unavailable, not 500 Internal Server Error -- a 503 tells a load balancer or orchestrator "temporarily don't route traffic here, but don't kill the process," which is exactly readiness's semantic per section 2's liveness/readiness distinction. A 500 would incorrectly suggest the PROCESS itself is broken (liveness's concern), which could trigger an unnecessary restart even though the FastAPI process itself is perfectly healthy -- only its MCP dependency is temporarily down. This is precisely why the two checks need to stay semantically distinct even as readiness grows more dependencies over Weeks 2-3 (DB connectivity, external API reachability): every new dependency check added to /readyz should return 503 on failure, never crash the liveness check or the process itself.
Problem 2 · Deciding where a new "summarize_document" tool's logic should live

Week 2 needs to add a real tool, summarize_document, that calls an LLM to summarize a document fetched from the capstone's storage. Using section 1's directory structure, where does the LLM-calling logic itself live — inside app/mcp_servers/ alongside the tool registration, or somewhere else? Justify it.

Show solution
The tool REGISTRATION (the @capstone_mcp.call_tool() handler that MCP clients invoke) belongs in app/mcp_servers/, exactly where ping lives -- that's the MCP-protocol-facing surface, and section 3 established this directory as owning "the MCP server(s) this backend hosts." But the actual LLM-calling logic (constructing the prompt, calling the model, parsing the response) should NOT be written inline inside that handler -- it belongs in a separate, protocol-agnostic module (e.g. app/services/summarization.py, a new directory this problem's answer correctly identifies as missing from section 1's initial tree) that the MCP tool handler calls into as a thin wrapper. The reasoning: MCP is one INTERFACE to this capability, but almost certainly not the only one Weeks 2-3 will want -- the orchestrator in app/orchestrator/ may also want to call summarization logic directly, without going through the MCP protocol layer at all, for an internal agent step that doesn't need to be exposed as an externally-callable tool. If the summarization logic is written INSIDE the MCP handler, reusing it from the orchestrator means either duplicating the logic or having the orchestrator call itself through its own MCP server -- an unnecessary protocol round-trip for an in-process call. Keeping business logic (services/) separate from protocol-facing wrappers (mcp_servers/, routers/) is the same separation-of-concerns instinct dependency_injection.html applies to route handlers vs. business logic, now applied to MCP tool handlers specifically -- the MCP handler's job is translating between MCP's protocol shape and a plain Python function call, nothing more.
Problem 3 · Diagnosing why /mcp/sse returns a 404 after adding a second router

A teammate adds a new chat.py router (per section 4) and, after registering it in create_app(), the previously-working /mcp/sse endpoint from section 3 starts returning 404. Using section 2's ordering comment ("health/readiness FIRST... every other router gets registered after this"), what's the most likely cause, and how would you confirm it?

Show solution
The most likely cause is a route path COLLISION or an ordering mistake introduced by where mount_mcp(app) got called relative to the new router registration -- most plausibly, the new chat.py router was registered using a prefix or a catch-all path that happens to shadow /mcp/sse, or mount_mcp(app) was accidentally moved to run AFTER something that already returns a response for that path pattern (e.g. a catch-all 404 handler or a wildcard route defined too early). FastAPI matches routes in REGISTRATION order for overlapping patterns, so an earlier-registered broad route (e.g. an accidentally-added @app.get("/{path:path}") catch-all in the new router, a realistic mistake when someone's first pass at a router uses a wildcard for flexibility) can intercept a request before FastAPI ever reaches the more specific /mcp/sse route registered afterward. To confirm: check the actual registration order in create_app() -- verify mount_mcp(app) still runs, and specifically look for any newly added route in chat.py with a wildcard or overly broad path parameter that was registered BEFORE mount_mcp(app) in the function body. FastAPI also exposes app.routes (a list, in registration order) that can be printed/inspected directly to see the exact order and patterns being matched -- checking that list is a faster diagnostic than guessing from the code, since it shows FastAPI's actual matching order rather than requiring you to mentally trace the registration sequence. This is exactly why section 2's comment calling out registration order matters explicitly: as more routers get added in Weeks 2-3, ORDER becomes a real, easy-to-violate invariant, not just a style preference.
