BACKEND & APIS LAB · STREAMING ARCHITECTURE INTEGRATION

Two streaming protocols, one service, and the middleware that wasn't built for either of them.

Chat needs bidirectional messaging — that's a WebSocket. Live notifications only need to flow one way, server to client — that's SSE. A real product often needs both, served by the same backend, but neither fits the request/response shape that rate limiting and error-handling middleware were designed around. This lab wires all four previous weeks' pieces together — WebSockets, SSE, rate limiting, and custom middleware — into one coherent picture, and is explicit about exactly where the seams don't line up.

01 — Same backend, two different jobs

Combining WebSockets and SSE in one service

Start here, before any code. Think of a hotel front desk that does two unrelated things: it runs an intercom line to your room for two-way calls with the concierge (you can ring them, they can ring you, either direction, any time), and it also has a lobby announcement speaker that only ever broadcasts outward — "checkout is at 11am," "the pool is closed for cleaning" — that you never talk back into. Both systems are run by the same front desk staff and the same building wiring, but they're fundamentally different channels serving different needs. Forcing the lobby announcements through the two-way intercom, or vice versa, would be over-engineering one and under-serving the other.

That's the real shape of "combine WebSockets and SSE in one service." It does not mean picking one protocol and using it for everything. It means recognizing that different features have different communication shapes, and building one backend that serves each feature over the protocol that actually matches it:

  • Chat needs true bidirectional, low-latency messaging — a user sends a message, another user's client needs to receive it instantly, and either side can initiate at any moment. This is exactly what the WebSockets lab covered: a single HTTP request upgrades via 101 Switching Protocols into a full-duplex connection where both sides can speak whenever they want.
  • Live notifications ("your export finished," "you have a new comment") only ever flow one direction: server to client. The client never needs to push anything back over that same channel — if the user wants to react, that's a completely separate normal HTTP POST. This is exactly the shape the Server-Sent Events lab covered: a long-lived HTTP response with Content-Type: text/event-stream, one direction only, with automatic client-side reconnection built into the browser's EventSource API.

The trap: using WebSockets for everything "because it's more powerful" is a real anti-pattern here. The notification feed never needs the client to send anything back over that channel — building it as a WebSocket anyway means carrying the operational cost of a bidirectional connection (more complex reconnection logic, a connection that can be misused to send unexpected client→server traffic, no built-in EventSource reconnection) for a feature that never uses the "bidirectional" half of what it's paying for.
Interview-ready definition: combining WebSockets and SSE in one service means recognizing that different features within the same product have genuinely different communication shapes — bidirectional-and-interactive versus one-way-and-broadcast — and serving each over the protocol that matches it, from the same backend process and deployment. It is not "pick one streaming protocol for the whole app"; a single FastAPI (or any ASGI) service can expose a @app.websocket route for chat and a separate StreamingResponse-based SSE route for notifications simultaneously, because they're just two different endpoint types on the same running application.
02 — One consistent shape, no matter which protocol carried it

Normalizing the schema for streamed data

Start here, before any code. Imagine getting mail from three different senders, each using a completely different envelope format: one hand-writes the date in the corner, one stamps it on the back, one doesn't include a date at all and expects you to infer it from the postmark. Sorting and processing that mail means writing separate handling logic for each sender's quirks. Now imagine every sender instead used the exact same envelope template — return address here, date there, tracking number there — regardless of what's actually inside. Sorting becomes trivial: you always know where to look, no matter who sent it or what the letter says.

A chat message and a notification are structurally different payloads — one has a sender and room ID, the other has a user ID and a notification type — but consumers on the client side (and any shared logging/monitoring code on the server side) benefit enormously from every streamed event, regardless of which protocol or feature produced it, sharing one consistent outer envelope. The inner payload varies; the outer shape does not.

// Consistent envelope shape -- same three top-level keys for every event, // whether it arrived over the WebSocket or the SSE stream { "type": "chat.message", // or "notification.export_ready", etc. "timestamp": "2026-08-19T14:03:21Z", "payload": { "room_id": "room_42", "sender": "alex", "text": "be there in 5" } } // A notification event -- DIFFERENT payload shape, SAME envelope { "type": "notification.export_ready", "timestamp": "2026-08-19T14:04:02Z", "payload": { "user_id": "u_991", "export_id": "exp_113", "download_url": "https://.../exp_113.csv" } }

Without this, every client-side consumer needs special-case parsing logic per event type before it can do even the most basic thing — log it, route it to a handler, or figure out when it happened. With the envelope, one small piece of dispatch code handles literally everything the stream will ever emit, present or future:

# One dispatcher, regardless of how many event "type" values exist def handle_event(raw_json): event = json.loads(raw_json) handler = HANDLERS.get(event["type"]) # dict lookup, not a growing if/elif chain if handler: handler(event["payload"], event["timestamp"]) else: log_unknown_event_type(event["type"]) # forward-compatible: new types don't crash old clients

Interview-ready definition: a normalized event envelope is a consistent outer shape — typically {type, timestamp, payload} — applied to every event a streaming service emits, regardless of which feature or protocol produced it. The type field lets a single generic dispatcher route events without bespoke per-type parsing; the timestamp field is always in the same place for logging, ordering, and client-side "time since" display; and the payload field is where feature-specific structure is free to vary. This decouples the transport (WebSocket vs SSE) and the event's specific shape from the consumer's dispatch logic, which only ever needs to understand the envelope, not every payload variant that has ever existed or will exist.
03 — Middleware built for one request, applied to a connection that never ends

Wiring rate-limiting and error middleware into streaming connections

Start here, before any code. Picture a bouncer at a club whose entire job is designed around "check ID, let one person in, done" — that model works great for a steady stream of individual customers. Now imagine a customer who, once let in, never leaves and instead keeps a permanently open tab running all night. The bouncer's per-person check-at-the-door model has nothing to say about "how much should this one customer, who's been inside for six hours, be allowed to keep ordering" — that's a genuinely different kind of gate, checked on a different rhythm, not at the door but continuously, or per-order, for as long as the customer stays.

The custom middleware lab covered BaseHTTPMiddleware's core shape: wrap call_next(request), do something before, do something with the single response that comes back after. That model assumes a request has a beginning, an end, and exactly one response — which is exactly what a WebSocket or SSE connection does NOT have. A streaming connection is opened once and then may stay open for minutes or hours, sending an unbounded number of individual messages (WebSocket) or events (SSE) over that single connection's lifetime. call_next() either never returns (the connection is still open) or, if it did return, the "request" would already be over — there's no clean point to run typical after-the-response middleware logic mid-stream.

This is the specific complication the roadmap calls out: rate limiting and error-handling middleware, as built for typical request/response traffic, don't cleanly apply to a long-lived streaming connection. The fix isn't to abandon rate limiting or error handling for streams — it's to apply them at different points than "wrap the single response":

Rate limiting a normal HTTP request

Checked once, at the top of the middleware stack, before the route handler runs. One request, one check, one decision (allow or 429). The rate limiter design lab's token bucket or sliding window logic runs exactly once per request.

Rate limiting a streaming connection

Has to happen at TWO different points instead: (1) at connection-open time — should this client be allowed to open a new WebSocket/SSE connection at all right now — and (2) per-message or per-event, continuously, for the entire lifetime of the now-open connection, since a single connection can otherwise emit unlimited messages once it's past the door.

# Rate limiting applied at BOTH points for a WebSocket connection @app.websocket("/ws/chat/{room_id}") async def chat_socket(websocket: WebSocket, room_id: str, user_id: str): # (1) connection-open check -- same idea as a normal request's rate limit, # but gating whether the CONNECTION is allowed to open at all if not await connection_rate_limiter.allow(user_id): await websocket.close(code=1008, reason="rate limited") return await websocket.accept() async for message in websocket.iter_text(): # (2) PER-MESSAGE check -- the connection is open, but each individual # message still has to pass its own rate-limit gate if not await message_rate_limiter.allow(user_id): await websocket.send_json({"type": "error", "payload": {"reason": "slow down"}}) continue # drop this message, but do NOT close the connection over it await broadcast_to_room(room_id, message)

Error-handling middleware has a related mismatch. In the request/response model, BaseHTTPMiddleware can catch an unhandled exception from the route handler, log it, and return a clean 500 response — there's exactly one response to shape. Inside a streaming handler, an unhandled exception happens mid-connection, potentially after hundreds of messages have already been sent successfully. There's no single "the response" left to intercept and reshape; the practical pattern is a try/except wrapped directly around the per-message or per-event loop body inside the handler itself, so one malformed message or one downstream failure closes cleanly (or sends an in-band {"type": "error", ...} event over the still-open connection) without necessarily tearing down the whole connection or crashing the server process.

Why this matters in practice: teams that bolt generic BaseHTTPMiddleware-style rate limiting onto a WebSocket route often find it either does nothing useful (it ran once, at connection-open, and then every subsequent message on that same connection sails through unlimited) or breaks the connection outright (some middleware implementations assume a request finishes quickly and time out or interfere with a connection that's deliberately meant to stay open for a long time). The fix is always to move the per-unit-of-work check INSIDE the handler's own message loop, not to keep stacking generic HTTP middleware around a route that isn't really "one request" anymore.
Interview-ready definition: standard ASGI middleware wraps a single request/response cycle via call_next(), which doesn't map cleanly onto a streaming connection that has one open event but many subsequent messages over an unbounded lifetime. Rate limiting a streaming connection therefore requires two separate checks: an open-time check (should this client be allowed to establish a new connection right now, analogous to a normal per-request check) and a per-message/per-event check running continuously inside the connection's own read loop (since a single already-open connection can otherwise emit unlimited traffic). Error handling follows the same pattern — a try/except around the per-message loop body inside the handler, rather than a wrapper around one response, since there is no single response object left to intercept once the connection has been open and streaming for a while.

Problem 1 · Choosing WebSocket vs SSE for a new feature

A product team wants to add a "live collaborative cursor" feature (see other users' cursors move in real time on a shared document) to the same app that already has chat (WebSocket) and notifications (SSE). Which protocol fits the cursor feature, and why?

Show solution
WebSocket, for the same reason chat uses it: live cursor positions are genuinely bidirectional -- every connected client needs to both SEND its own cursor position continuously AND RECEIVE every other client's cursor position continuously, in real time, with neither direction being clearly "primary." This is the same full-duplex shape as chat, just with cursor coordinates instead of text messages as the payload. SSE would not fit here: SSE is one-way (server to client only), so a client would need some SEPARATE channel just to send its own cursor updates up to the server, at which point you're already running two channels to do one job that a single WebSocket does cleanly in one. The deciding question is always the same: does this feature need the CLIENT to push data over this same channel, not just receive it? If yes, WebSocket; if the client-side is purely passive receiving, SSE is the simpler, lighter-weight fit.
Problem 2 · Spotting a missing envelope field

A teammate's streaming event looks like this: {"kind": "chat.message", "data": {...}} — no timestamp anywhere. What breaks downstream because of this, concretely?

Show solution
Without a timestamp in the envelope, any consumer that needs to know WHEN an event happened has no reliable source for it. Concretely: a client rendering "sent 2 minutes ago" under a chat message either has to fall back to the time it happened to RECEIVE the event client-side (wrong if there was any network delay, reconnection, or buffering delay between the server producing the event and the client receiving it) or has to reach into the feature-specific payload and hope there's a timestamp buried in there under some inconsistent key name per event type. Server-side, anything doing ordering, deduplication, or "replay events since X" (e.g. reconnection logic asking "catch me up on everything since my last seen event") has no consistent field to sort or filter on across different event types -- it would need type-specific logic to find A timestamp inside each payload shape, which is exactly the special-casing a normalized envelope exists to avoid. The fix is simply adding "timestamp" as a top-level, always-present envelope field, set once, server-side, at the moment the event is actually produced.
Problem 3 · Diagnosing unlimited per-connection traffic

A chat service has rate limiting correctly applied via BaseHTTPMiddleware to all normal REST endpoints, and it also checks the rate limiter once when a WebSocket connection is first opened. In production, a single misbehaving client opens one connection and then sends 50,000 messages per second over it, and nothing stops them. What's missing, precisely?

Show solution
The connection-open check ran exactly once and only gates whether a NEW connection is allowed to be established -- it says nothing about how much traffic is allowed to flow over a connection that's already open. Once past that one check, the client is inside an open WebSocket loop (`async for message in websocket.iter_text()`), and nothing in that loop is re-checking the rate limiter per message. The BaseHTTPMiddleware rate limiting on REST endpoints is irrelevant here too -- WebSocket traffic after the initial upgrade handshake never goes through the normal HTTP middleware stack again; it's a different framing protocol entirely on the same TCP connection. The fix is exactly the missing second gate from this lab: a per-message rate-limit check INSIDE the message-receiving loop itself, e.g. calling `message_rate_limiter.allow(user_id)` on every single message before processing it, and either dropping the message (with an in-band error event) or, for a sufficiently abusive client, closing the connection outright if it keeps exceeding the per-message limit repeatedly.
Problem 4 · Handling a mid-stream error without killing the connection

Inside the notification SSE generator, one particular notification's payload fails to serialize to JSON (a bug in a new notification type someone just shipped). What should happen to the stream, and why is "let the exception propagate and close the connection" usually the wrong answer here?

Show solution
The exception should be caught locally, around JUST that one event's serialization/yield, not allowed to propagate up and tear down the whole generator/connection. If it's allowed to propagate, the entire SSE response terminates -- every OTHER, perfectly healthy notification this user would have received for the rest of that connection's lifetime is now lost too, and the client's EventSource will have to reconnect (with whatever delay/backoff that involves) to resume receiving anything at all, all because of one bad payload unrelated to the rest of the stream. The better pattern: wrap the per-event serialization/yield in a try/except inside the generator's loop, log the malformed event server- side for debugging, optionally skip it (or emit a minimal fallback "something went wrong with one notification" event), and continue the loop so every subsequent healthy notification still reaches the client uninterrupted. This mirrors the DLQ instinct from notification service design -- isolate and preserve the failure for later investigation rather than letting it take down healthy, unrelated work alongside it.
Problem 5 · Designing the envelope for a third, future event type

Six months from now, the team adds a third streaming feature: "typing indicators" (someone is typing in a chat room). Using the envelope pattern from this lab, sketch what that event would look like, and explain why adding it requires zero changes to any EXISTING client-side dispatch code.

Show solution
A typing indicator event, in the same envelope shape: { "type": "chat.typing", "timestamp": "2026-08-19T14:05:10Z", "payload": { "room_id": "room_42", "user_id": "alex", "is_typing": true } } Existing client-side dispatch code needs zero changes because the dispatcher (from section 2) was written as a lookup against event["type"] -- HANDLERS.get(event["type"]) -- with a fallback branch for unrecognized types, rather than an if/elif chain hardcoded to the two types that existed when it was written. Adding "chat.typing" to the HANDLERS dict on the client side (whenever the client team gets around to actually building UI for it) is additive: old clients that haven't been updated yet simply hit the "unknown type" fallback branch and safely ignore or log it, rather than crashing or misparsing it as some other event type. This forward-compatibility is the entire practical payoff of paying for a normalized envelope up front -- new event types are additive, not breaking, for every consumer that was written against the envelope contract rather than against specific payload shapes.
