BACKEND & APIS LAB · SQLALCHEMY ASYNC

The engine owns the connections. The session owns your transaction. Neither one is the other.

SQLAlchemy's async layer looks like the sync API with await sprinkled on top, but underneath it, the engine's connection pool and asyncio's event loop have to cooperate at every single database round trip. This lab builds up async engine and session setup, contrasts Declarative ORM models against raw Core tables for the same schema, and animates exactly what happens to your coroutine — and to every OTHER coroutine — the instant await session.execute(...) hits the network.

01 — Two different objects, two different jobs

AsyncSession and async engine setup

Start here, before any code. Think of a restaurant. The engine is the restaurant's fixed set of parking spaces out back and the valet staff who manage them — a shared, reusable resource pool that exists for the whole night, handed out to whichever car (connection) needs one at the moment, then taken back when that car's business is done. A session is a single table's dining experience for one party — it starts when they sit down, tracks everything they order and eat during that one visit, and ends (the check is settled, the transaction is committed or rolled back) when they leave. The valet lot is shared infrastructure across the whole restaurant; a table's dining session belongs to exactly one party, for exactly one visit.

The async engine, created with create_async_engine(...), manages a pool of database connections opened over an async-capable driver. It does NOT represent a transaction or hold application state — it's purely connection plumbing: opening connections, keeping a pool of them warm and ready, handing one out when work needs to happen, and returning it to the pool afterward.

from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession # the engine manages a POOL OF CONNECTIONS -- it is not a transaction, # it is not a session, it has no idea what your application logic is doing engine = create_async_engine( "postgresql+asyncpg://user:pass@localhost/mydb", pool_size=10, # keep up to 10 connections warm in the pool max_overflow=5, # allow 5 more temporarily under heavy load echo=False, ) # a sessionmaker is a FACTORY for sessions -- create it once, reuse it # everywhere, rather than constructing AsyncSession(engine) by hand each time async_session_factory = async_sessionmaker(engine, expire_on_commit=False) async def do_work(): # AsyncSession as an async context manager: borrows a connection from # the engine's pool, opens a transaction, and guarantees cleanup # (commit/rollback + returning the connection to the pool) on exit async with AsyncSession(engine) as session: # ... do queries here, all within ONE logical transaction ... await session.commit() # equivalently, and more commonly, via the factory: async with async_session_factory() as session: # ... same thing, but the factory carries shared config ... await session.commit()

Interview-ready definition: the async engine manages a pool of reusable, async-capable database connections and knows nothing about application-level units of work — it exists for the lifetime of the process. An AsyncSession represents a single unit-of-work / identity map scoped to one logical transaction: it checks out a connection from the engine's pool on first use, tracks every object it has loaded or modified during that transaction (so the same row loaded twice returns the same Python object), and releases the connection back to the pool when the transaction ends via commit, rollback, or the async with block exiting. Many sessions are created and discarded, cheaply, over the engine's much longer lifetime — you create the engine once per application, and a new session per unit of work (often per request).
02 — Same table, two completely different ways to describe it

Declarative models vs Core, side by side

Start here, before any code. Imagine describing a filing cabinet two ways. One way: "here's a Folder class — every folder object has a name and a list of documents inside it, and you interact with folders as things, calling methods on them, comparing whether two folder objects are 'the same folder.'" The other way: "here's the literal blueprint of the cabinet — drawer dimensions, label positions, exactly what goes in column 3 row 2 — with no notion of a 'Folder object' at all, just the raw physical layout you can read and write directly." Both describe the identical filing cabinet. One gives you objects with identity and behavior; the other gives you precise, direct control over the physical structure with nothing in between.

SQLAlchemy lets you define the exact same database table either way. Declarative (the ORM style, SQLAlchemy 2.0 syntax) defines a Python class whose attributes map to columns, using Mapped[...] type annotations and mapped_column(...). Core defines the same table directly against a MetaData object using Table(...) and Column(...), with no Python class and no object identity at all — just table and column definitions you build SQL expressions against.

Declarative ORM (2.0 style)

from sqlalchemy import String from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column class Base(DeclarativeBase): pass class User(Base): __tablename__ = "users" id: Mapped[int] = mapped_column(primary_key=True) email: Mapped[str] = mapped_column(String(255), unique=True) is_active: Mapped[bool] = mapped_column(default=True) # User is a real Python class. Rows come back as User instances # with attribute access, identity, and (optionally) relationships.

You get objects: user.email, object identity within a session (load the same row twice, get the same Python object back), and relationships to other mapped classes. This is what most application code — the code that reads like a domain model — reaches for.

Core (Table + MetaData)

from sqlalchemy import MetaData, Table, Column, Integer, String, Boolean metadata = MetaData() users_table = Table( "users", metadata, Column("id", Integer, primary_key=True), Column("email", String(255), unique=True), Column("is_active", Boolean, default=True), ) # No class. No objects with identity. Rows come back as plain Row # tuples/mappings -- you work directly with columns and SQL expressions.

You get raw rows, not objects — no identity map, no Python-side object graph, no relationship loading. In exchange, you get precise control over exactly what SQL gets generated, with none of the ORM's bookkeeping overhead.

Both definitions above describe the literal same users table in the database — same columns, same types, same constraints. Reach for Core when you're doing bulk operations (inserting or updating thousands of rows where per-object overhead matters), need precise control over exactly what SQL gets generated, or simply don't need Python object identity at all (a reporting query that just needs rows, not domain objects). Reach for Declarative for the majority of application code — anywhere you're working with entities as objects, navigating relationships, or want the identity map's guarantee that the same row loaded twice in one session is the same Python object.

Interview-ready definition: Declarative and Core are two APIs over the same underlying SQL expression language, not two different databases or two different sets of capabilities — a Declarative model's table is, underneath, a Core Table object that SQLAlchemy generates for you from the class definition. Declarative adds a mapped Python class, object identity within a session (the identity map), and relationship navigation on top of that Core table; Core alone gives you the table and column definitions with no object layer, returning plain rows. Choosing between them is a choice about how much object-oriented bookkeeping you want, not a choice about what SQL can be expressed.
03 — Same intent, different verbs

Async query execution patterns

Start here, before any code. Ordering food at a counter (sync) means you stand there and wait — nothing else happens for you until your order is ready, you're physically occupying that spot the whole time. Ordering food via an app that texts you when it's ready (async) means you place the order, walk away and do something else, and come back only once notified — the KITCHEN takes the same amount of time either way, but what YOU are able to do while waiting is completely different. await session.execute(...) is the "walk away and get notified" version of exactly the same database round trip.

Sync APIAsync equivalent
session.query(User).filter(User.id == 1).all() (legacy 1.x style)Not available — async sessions don't support the legacy .query() API at all
session.execute(select(User).where(User.id == 1)).scalars().all()await session.execute(select(User).where(User.id == 1)), then .scalars().all() on the result — .scalars() itself is NOT awaited, only execute() is
Blocks the calling thread until the DB respondsSuspends the coroutine at the await; the thread is free to run other coroutines during the wait
from sqlalchemy import select # SYNC version -- blocks the thread for the full round trip def get_user_sync(session, user_id: int) -> User | None: result = session.execute(select(User).where(User.id == user_id)) return result.scalar_one_or_none() # ASYNC version -- same query, same result shape, but the execute() # call is awaited, so this coroutine yields control during the round trip async def get_user(session: AsyncSession, user_id: int) -> User | None: result = await session.execute(select(User).where(User.id == user_id)) return result.scalar_one_or_none() # fetching MULTIPLE rows: .scalars() unpacks Row objects into # plain model instances; .all() materializes the full list async def get_active_users(session: AsyncSession) -> list[User]: result = await session.execute(select(User).where(User.is_active == True)) return result.scalars().all()
The mistake this trips people into: mixing sync and async is not a style choice, it's a hard runtime failure. A synchronous create_engine("postgresql://...") (no +asyncpg) paired with AsyncSession raises immediately, because AsyncSession requires an async-capable driver underneath to actually hand back awaitables. Conversely, calling the legacy session.query(...) API on an AsyncSession doesn't work at all — it isn't wired up for that surface; you must use await session.execute(select(...)) instead. And forgetting the await in front of session.execute(...) doesn't crash loudly — it hands you a coroutine object instead of a result, and calling .scalars() on a coroutine fails with an AttributeError that looks nothing like "you forgot to await."
Interview-ready definition: async query execution in SQLAlchemy 2.0 uses the same select()-construct API as sync code — build a Select statement, pass it to session.execute(...), and unwrap the returned Result with .scalar_one_or_none(), .scalars().all(), or similar. The only structural difference is that execute() itself must be awaited on an AsyncSession, because it performs actual network I/O against the database driver; the result-unwrapping methods that follow (.scalars(), .all(), .scalar_one_or_none()) operate on the already-fetched Result object in memory and are NOT themselves awaited.
04 — The centerpiece: where does control actually go during a DB wait?

The lifecycle of an async query, animated

Start here, before the animation. When you place that food-app order and walk away, you don't just stand frozen next to the counter waiting for your phone to buzz — you go do something else entirely, like answering a different phone call, and you only come back to the food counter once notified. The kitchen (the database) doesn't know or care what you're doing during that wait; it just does its work and produces a result when it's ready. The interesting part isn't the kitchen — it's what YOU, specifically, get to do with your own attention during the gap.

This is precisely what happens to a coroutine at await session.execute(select(...)). It is the SAME cooperative scheduling mechanism from the event loop lab (python/asyncio_fundamentals.html) — a single-threaded event loop, coroutines voluntarily yielding at await, another ready task getting a turn during the wait — just applied specifically to database network I/O instead of generic I/O like asyncio.sleep() or an HTTP call.

WATCH THE EVENT LOOP DURING A DATABASE ROUND TRIP

Task A runs await session.execute(select(User)...). Task B is a completely unrelated coroutine — handling a different incoming request — that becomes ready to run during Task A's wait.

1Task A (application code) calls await session.execute(select(User).where(...)).
2The coroutine hands the query to the async DB driver, which sends it over the socket. The instant that send happens, Task A hits its await and suspends — control returns to the event loop scheduler, NOT to the database.
3The event loop sees Task A is now waiting on I/O (not ready to resume yet) and looks for other ready work. Task B is ready — the loop switches to it.
4Meanwhile, on the database side (a separate machine, working independently the whole time): the query is parsed, the rows are fetched, and the result is serialized back onto the socket.
5The socket becomes readable. The event loop notices this I/O-ready event and resumes Task A exactly where it left off — right after the await — with the result object now available.
6Application code continues: result.scalars().all() runs in memory, no further I/O needed. Task A finishes.
Task B: handling a different incoming request — parses a JSON body, validates a couple of fields, and prepares a response, entirely on CPU. It makes real progress ONLY during the window while Task A is suspended waiting on the DB socket.
Click to step through exactly what the event loop does at each stage of the await.
The detail worth memorizing: at the moment of await, control returns to the event loop scheduler — not to the database, not nowhere. The database is a completely separate process on a separate machine, making progress on its own regardless of what Python is doing. The await boundary is purely about what the SINGLE THREAD running your Python process is allowed to do next: sit idle and do nothing (wasteful), or go run some other ready coroutine (what actually happens). This is why a single Python process using an async DB driver can serve hundreds of concurrent in-flight queries with a single thread — nobody is blocked waiting; everybody is just taking turns during each other's I/O gaps.
Interview-ready definition: the async query lifecycle is the same cooperative-scheduling model taught in the event loop lab, applied to database I/O specifically: application code calls await session.execute(...), the coroutine sends the query to the driver and immediately suspends at the await, the event loop notices Task A is now blocked on I/O and schedules a different ready task in its place, the database independently finishes processing and makes the result available on the socket, and the event loop — polling for I/O readiness — resumes the ORIGINAL coroutine exactly where it suspended once that socket is readable. No new thread is spawned and no busy-waiting occurs; the single thread is simply never idle while other ready work exists.

Problem 1 · session.query vs session.execute across sync/async

Trace what happens when a developer writes await session.query(User).filter(User.id == 1).all() against an AsyncSession. What actually goes wrong, and what should they have written instead?

Show solution
This fails, and not in an obvious way at first glance. AsyncSession does not implement the legacy session.query(...) API at all -- that surface is part of the older 1.x ORM query interface, and the async session was built against the 2.0-style select() + execute() API from the start. Depending on the exact SQLAlchemy version, this either raises an AttributeError (no .query method) or, in some transitional setups, returns something that isn't awaitable in the way the developer expects -- either way, "await" in front of it is a symptom of trying to force the old pattern onto an object that was never designed to support it. The correct version: result = await session.execute(select(User).where(User.id == 1)) users = result.scalars().all() Note precisely which call gets awaited: execute() performs the actual network round trip and must be awaited. scalars() and all() run against the already-fetched Result object in memory and are never awaited themselves.
Problem 2 · Mixing sync and async engines/sessions

What breaks, concretely, if you construct an AsyncSession using an engine created with plain create_engine("postgresql://...") instead of create_async_engine("postgresql+asyncpg://...")? What about the reverse — using a sync Session with an async engine?

Show solution
AsyncSession + sync engine: this fails, typically at construction or at first use, because AsyncSession expects the engine's underlying DBAPI driver to support async operations (returning awaitables from execute calls, using an async network driver like asyncpg under the hood). A plain create_engine(...) wires up a SYNCHRONOUS driver (like psycopg2) that blocks the calling thread and has no notion of "await" at all -- there's no coroutine for AsyncSession to await, so the abstraction simply doesn't line up. SQLAlchemy raises an error rather than silently degrading to blocking behavior. Sync Session + async engine: also breaks, for the mirror-image reason -- a sync Session expects to call driver methods that return results directly, not coroutines that need to be awaited. Handed an async engine's async-driver connections, it would receive coroutine objects where it expects real values, and has no await point in its own synchronous call stack to actually drive them to completion. The rule: the engine's driver (asyncpg vs psycopg2, indicated by the +asyncpg / +psycopg2 in the connection string) and the session type (AsyncSession vs Session) have to match -- they are two halves of the same async-or-sync commitment, not independently swappable pieces.
Problem 3 · Why the event loop can serve another request during a DB wait but not during CPU-bound work

Explain precisely why await session.execute(select(User)) lets another coroutine make progress during the wait, while a slow, purely CPU-bound computation (e.g. hashing a large file in a loop) inside a coroutine does NOT let anything else run during it.

Show solution
The distinguishing factor is whether there is an actual await point where control can be voluntarily handed back to the event loop. await session.execute(...) sends the query over the network socket and then suspends -- the Python interpreter is not doing anything during the wait for the database to respond, so it is free to go run other ready coroutines on that same single thread. The database itself makes progress independently, on a separate machine/process, using its own resources -- Python's single thread isn't "waiting" in the sense of being occupied, it is genuinely idle with respect to that task and available for other work. A CPU-bound loop (hashing a large file) has no await point anywhere in it -- it is a straight-line synchronous computation that occupies the ONE thread the event loop runs on for its entire duration. There is nothing for the event loop to "notice is ready" during that loop, because the loop never voluntarily yields control back -- cooperative scheduling only works at explicit await boundaries, and a tight CPU-bound loop simply never reaches one. This is the same blocking-call trap from the event loop lab (time.sleep() freezing everything) applied to computation instead of an obvious blocking call -- the fix there is the same too: asyncio.to_thread() or a process pool to move the CPU-bound work off the event loop's single thread entirely.
Problem 4 · Declarative vs Core for a given scenario

A nightly batch job needs to update a last_synced_at timestamp on 2 million rows in a users table, based on a join against an external sync log, with no need to ever construct a Python User object for any of those rows. Should this use Declarative ORM objects or Core? Why?

Show solution
Core is the better fit here. Loading 2 million rows as full Declarative User objects (each with its own identity-map entry, attribute tracking, and potential relationship loading machinery) is pure overhead when the job never actually needs a Python object for any of those rows -- it only needs to run a bulk UPDATE. Core lets you build a precise users_table.update().values(last_synced_at=...).where(...) statement (or an update-from-join construct) that generates exactly the SQL needed and executes it as a single bulk operation, with no per-row Python object materialization at all. This matches the general rule: Core fits bulk operations, precise control over generated SQL, and scenarios with no need for object identity; Declarative fits code working with individual entities as objects, navigating relationships, and needing the identity map's guarantees -- none of which this batch job needs.
Problem 5 · Tracing the async query lifecycle animation

In the lifecycle animation above, at the exact moment Task A's coroutine suspends after sending its query to the driver, where does control go? Name the one thing that must be true for Task B to actually make progress during that window.

Show solution
Control goes to the event loop scheduler -- not to the database, and not nowhere. The event loop is the single-threaded dispatcher that owns the one thread Python is running on; when Task A suspends at its await, the event loop is free to look at its set of ready tasks and pick a different one to run. The one thing that must be true for Task B to make progress: Task B must already be registered with the event loop as a task (e.g. via asyncio.create_task(), or as a separate request handler the async web framework is already running) AND it must not itself be blocked waiting on something that isn't ready yet. If Task B were, say, also waiting on its own database query that hasn't resolved, the loop would move on to look for yet another ready task instead -- the loop always picks from whatever IS ready, never blocks trying to force a specific task to run. This is exactly the same "loop picks whichever task is ready, never sits idle" model from the event loop lab's cooperative scheduling animation -- nothing here is unique to databases specifically, it is generic async I/O scheduling pointed at a database socket instead of, say, an HTTP client or asyncio.sleep().
