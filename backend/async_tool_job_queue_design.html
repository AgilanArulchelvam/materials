SYSTEM DESIGN LAB · ASYNC TOOL JOB QUEUE DESIGN

An agent that blocks on a slow tool call is an agent that can only do one thing at a time.

Some tool calls are slow — a long-running data export, a video render, a batch API call to a rate-limited third party. Instead of an agent thread sitting idle waiting for one of these, this lab builds the pattern of enqueueing the call and letting a separate worker pick it up: the queue itself, retrying failed jobs with backoff into a dead-letter queue, and what to do when jobs arrive faster than workers can drain them — at the same bar as backend/rate_limiter_design.html and backend/notification_service_design.html.

01 — Don't wait on the slow thing, hand it off

Queueing tool calls for async execution

Start here, before any code. Think about dropping off a roll of film at a photo shop instead of standing at the counter waiting for it to be developed. You hand it over, get a claim ticket, and go do something else — a separate person in the back actually does the developing, on their own schedule, and you come back later (or get a call) when it's ready. You were never blocked standing at the counter the whole time it took to develop.

An agent facing a slow tool call can use exactly this pattern instead of blocking: rather than await-ing a call that might take minutes, it enqueues a job describing the work (which tool, what arguments) and immediately continues — free to handle other requests, or to tell the user "working on it, I'll have results shortly." A separate worker process, running independently, picks jobs off the queue and actually executes them, writing the result somewhere the original caller (or a later poll) can retrieve it.

# enqueueing side -- the agent's request-handling path, never blocks on the slow work async def handle_tool_call(tool_name: str, arguments: dict) -> dict: if tool_name in SLOW_TOOLS: # e.g. "generate_video_report", "run_batch_export" job_id = str(uuid4()) await queue.enqueue({ "job_id": job_id, "tool_name": tool_name, "arguments": arguments, "status": "queued", "attempts": 0, }) return {"job_id": job_id, "status": "queued"} # returns IMMEDIATELY, no blocking return await execute_tool_directly(tool_name, arguments) # fast tools run inline, unchanged # worker side -- a SEPARATE process, running continuously, independent of any request async def worker_loop(): while True: job = await queue.dequeue() # blocks HERE, not in the agent's request path result = await execute_tool_directly(job["tool_name"], job["arguments"]) await results_store.set(job["job_id"], {"status": "done", "result": result}) # caller polls (or gets notified) for the result later async def get_job_result(job_id: str) -> dict: return await results_store.get(job_id) or {"status": "queued"}

Interview-ready definition: queueing tool calls for async execution means a slow tool invocation is represented as a job (tool name, arguments, a generated job ID) written to a queue rather than awaited directly in the request path, letting the caller return immediately with a job ID it can poll or be notified against. A separate, independently-running worker process dequeues jobs and actually executes them, writing results to a store the caller reads from later — decoupling "accepting the request" from "doing the slow work" so that one slow tool call never blocks the agent's ability to handle anything else in the meantime.
02 — Failures happen; retrying forever isn't the answer, dropping silently isn't either

Handling failures & retries in the queue

Start here, before the code. This is the exact retry-and-dead-letter-queue pattern from backend/notification_service_design.html, applied here to tool-call jobs instead of notification deliveries. A job can fail for reasons that have nothing to do with whether it was a good idea to try — a downstream API rate-limited the worker, a transient network blip, a momentary resource shortage. Retrying with exponential backoff (waiting longer between each successive attempt) gives a transient failure room to resolve itself without hammering an already-struggling downstream system.

MAX_ATTEMPTS = 4 BASE_DELAY_SECONDS = 2 async def process_job(job: dict): try: result = await execute_tool_directly(job["tool_name"], job["arguments"]) await results_store.set(job["job_id"], {"status": "done", "result": result}) except ToolExecutionError as e: job["attempts"] += 1 if job["attempts"] >= MAX_ATTEMPTS: # exhausted retries -- move to the dead-letter queue, don't retry forever await dead_letter_queue.push({**job, "final_error": str(e)}) await results_store.set(job["job_id"], {"status": "failed", "error": str(e)}) else: # exponential backoff: 2s, 4s, 8s, ... before this job is eligible again delay = BASE_DELAY_SECONDS * (2 ** (job["attempts"] - 1)) await queue.enqueue_delayed(job, delay_seconds=delay)
A JOB THAT FAILS, RETRIES WITH BACKOFF, THEN LANDS IN THE DLQ
Job moved to the DEAD-LETTER QUEUE after exhausting MAX_ATTEMPTS — preserved intact for inspection, no longer consuming worker retry capacity.

The dead-letter queue solves the same two problems here that it solved for notifications: it stops the worker pool from looping on a job that can never succeed (freeing capacity for healthy jobs), and it preserves the failed job's full payload and failure history instead of silently discarding it, so a human can inspect why it failed and potentially reprocess it once the underlying cause is fixed.

Interview-ready definition: a job queue handles failures by retrying a failed job a bounded number of times with exponential backoff — waiting progressively longer between attempts so a transient failure has room to resolve without amplifying load on a struggling downstream dependency — and, once a job exhausts its retry budget, moving it to a dead-letter queue rather than retrying indefinitely or dropping it silently. The DLQ preserves the job's full payload and failure history for later human inspection or manual reprocessing, which is what makes bounded retries a safe default rather than a way of quietly losing failed work.
03 — What happens when jobs arrive faster than workers can drain them

Backpressure handling

Start here, before the meter. A sink with the faucet running faster than the drain can empty it will overflow eventually, no matter how big the sink is — the only real fixes are slowing the faucet, widening the drain, or deliberately refusing more water once the sink is nearly full. A job queue faces the identical problem: if producers enqueue jobs faster than workers can process them, the queue's backlog grows without bound unless something actively pushes back.

ApproachWhat it doesTrade-off

Do nothing (unbounded queue)Accept every job regardless of backlog sizeNot actually a solution — the backlog grows without bound, memory/storage eventually exhausts, and jobs queued now may not run for hours
Why "just accept everything" isn't actually safe: an unbounded queue doesn't fail loudly when overwhelmed — it fails quietly, by growing. Every accepted job LOOKS successful ("job_id: queued") right up until someone notices results aren't coming back in any reasonable time, or the queue's storage backend runs out of capacity and fails in a much less controlled way. Rejecting new jobs past a depth threshold turns an eventual, uncontrolled failure into an immediate, controlled one — the caller finds out RIGHT NOW that the system is overloaded, rather than discovering it much later when a job that "succeeded" at enqueue time never actually completes.
Interview-ready definition: backpressure handling means a job queue actively signals or resists accepting more work once its backlog reaches a threshold it can't drain in a reasonable time, rather than growing unboundedly — concretely, by rejecting new enqueue requests past a depth threshold, throttling the producer's rate of new jobs, or (within limits) scaling workers to increase drain rate. The alternative — accepting every job regardless of backlog — isn't actually safer, since it just delays and obscures the moment of failure rather than preventing it, converting an immediate, diagnosable rejection into a much harder-to-diagnose, unbounded resource exhaustion later.

Problem 1 · Deciding which tool calls belong in the queue at all

Section 1's code checks if tool_name in SLOW_TOOLS before deciding to enqueue rather than execute inline. Why not just queue EVERY tool call, even fast ones, for consistency?

Show solution
Queueing every tool call, including fast ones, would add the queue's overhead (serialization, a round trip through the queue backend, a worker picking it up on its own schedule rather than immediately) to calls that were already fast enough to just execute inline and return a result in the same request. For a tool that completes in milliseconds, this overhead can easily dominate the actual work being done -- turning a sub-100ms operation into one that takes as long as the queue's polling interval or worker availability allows, purely for architectural uniformity that provides no real benefit here. The SLOW_TOOLS check exists specifically to apply the async-queue pattern only where it earns its cost: tools whose execution time is long enough that BLOCKING the caller on it would be a real problem (per section 1's photo-shop analogy) benefit from being handed off; tools that finish quickly don't have that problem in the first place, so forcing them through the same indirection just adds latency and complexity without solving anything. This mirrors a broader principle worth stating directly: introducing async/queueing infrastructure is a trade-off, not a free win -- it should be applied where blocking is actually costly, not uniformly to every operation regardless of how fast it already is.
Problem 2 · Tracing the exact backoff delays for a specific job

Using section 2's code (BASE_DELAY_SECONDS = 2, MAX_ATTEMPTS = 4), a job fails on its first 3 attempts and succeeds on the 4th. What are the exact delays before each retry, and how long does the job take in total (ignoring actual execution time)?

Show solution
Using delay = BASE_DELAY_SECONDS * (2 ** (attempts - 1)): After attempt 1 fails (job["attempts"] becomes 1): delay = 2 * 2^0 = 2 seconds before attempt 2. After attempt 2 fails (attempts becomes 2): delay = 2 * 2^1 = 4 seconds before attempt 3. After attempt 3 fails (attempts becomes 3): delay = 2 * 2^2 = 8 seconds before attempt 4. Attempt 4 succeeds -- no further delay, the job completes. Total elapsed time waiting between attempts: 2 + 4 + 8 = 14 seconds (plus whatever each attempt's actual execution time was, and note attempts == MAX_ATTEMPTS (4) is checked BEFORE this success -- had attempt 4 also failed, job["attempts"] would reach 4, matching MAX_ATTEMPTS, and the job would move to the dead-letter queue instead of getting a 5th attempt). This exponential growth (2, 4, 8, ...) is exactly what gives a struggling downstream dependency increasingly more room to recover between attempts, rather than hammering it at a constant retry rate the whole time.
Problem 3 · Diagnosing a DLQ that quietly fills up unnoticed

A team implements the dead-letter queue from section 2 correctly, but nobody ever looks at it or alerts on its size. Six months later, thousands of failed jobs sit there, none reprocessed. Is the DLQ "working" in this scenario? What's actually missing?

Show solution
Mechanically, yes, the DLQ is doing exactly what section 2 describes -- preserving failed jobs' full payload and failure history rather than losing them, and freeing worker capacity from retrying jobs that can never succeed. But section 2's stated PURPOSE of the DLQ was "so a human can inspect it later, understand why it failed, fix the root cause, and potentially reprocess it" -- and none of that is actually happening here. The DLQ has become a place where failed work goes to be technically preserved but functionally forgotten, which is barely better than silently dropping it in terms of actual business outcomes (the underlying tasks those jobs represented are still not getting done), even though it's strictly better in terms of not having LOST the information about what failed. What's missing is the operational half of the DLQ pattern, not the storage half: monitoring/alerting on DLQ size or growth rate (so a spike in failures gets noticed close to when it happens, not six months later), and an actual process -- automated or human -- for periodically reviewing DLQ contents and either fixing the root cause and reprocessing, or deciding the jobs are genuinely unrecoverable and can be discarded. A DLQ without this operational loop is a data structure, not a reliability mechanism -- the reliability benefit only materializes if something actually acts on what accumulates there.
Problem 4 · Choosing a backpressure strategy for a specific failure mode

A queue backing an agent's tool-call jobs is fed by many different agent instances simultaneously, and the downstream tool (a third-party API) has a hard, fixed rate limit regardless of how many workers you run. Which backpressure strategy from section 3's table fits best, and why does "scale workers horizontally" specifically NOT help here?

Show solution
"Reject past a queue-depth threshold" (or throttling the producer side) fits best here; "scale workers horizontally" is specifically the WRONG lever for this scenario. Section 3's table already flags this exact limitation: scaling workers only helps when the bottleneck is worker PROCESSING CAPACITY -- more workers genuinely drain the queue faster when what's limiting throughput is CPU/IO capacity to do the work. But here the bottleneck is an external, fixed constraint (the third-party API's rate limit) that doesn't budge no matter how many workers are asking it to do work -- adding a 10th worker doesn't make the third-party API accept requests any faster; it just means 10 workers are now contending for the same fixed-rate resource, likely making things WORSE by triggering more 429/rate-limit errors (feeding directly back into section 2's retry logic, potentially compounding the problem) rather than better. The right response is to accept that throughput is capped by the downstream rate limit regardless of internal architecture, and apply backpressure UPSTREAM of that constraint: reject or delay new jobs once the queue depth suggests the backlog already exceeds what the rate-limited downstream can drain in a reasonable time, rather than accepting jobs the system has no realistic path to completing promptly. This is a good illustration of why "backpressure" isn't one universal fix -- the right mechanism depends on WHERE the actual bottleneck is, and applying the wrong one (more workers, when the bottleneck is external and fixed) can waste effort or actively worsen the situation.
Problem 5 · Connecting job queue backpressure to the agent that's enqueueing work

Section 1's handle_tool_call enqueues a job and returns immediately with a job ID. If the queue rejects the enqueue attempt due to backpressure (section 3), what should the CALLING agent actually do with that rejection, and why is silently retrying forever not a good default?

Show solution
The calling agent should treat a backpressure rejection as a real, first- class outcome to reason about -- not something to paper over by blindly retrying the enqueue call in a tight loop until it succeeds. A reasonable response mirrors the graceful-error-handling lesson from mcp_client_basics.html: surface the rejection as a structured result (e.g. "the job queue is currently at capacity, try again shortly" or "this particular request couldn't be queued right now") that the agent's own reasoning loop -- if it's running something like the ReAct loop from react_pattern.html -- can incorporate into its next Thought, potentially deciding to wait and retry after a delay, try a different (faster, inline) approach if one exists, or tell the user directly that the system is currently overloaded rather than silently appearing to hang. Silently retrying forever is a bad default for the same reason unbounded retries were flagged as a problem in section 2's job-processing logic generally: it can turn a single overloaded moment into sustained, compounding pressure on the very queue that's already struggling -- every rejected-then-immediately-retried enqueue attempt is itself extra load on a system section 3 already established is past its comfortable capacity. A bounded retry with backoff (the SAME pattern section 2 already uses for job execution failures, just applied one level up, to the enqueue attempt itself) is the more defensible default: give the queue a real chance to drain before hammering it again, and eventually surface a clear failure rather than retrying indefinitely with no visible signal that anything is wrong.
