01 — A budget that refills itself over time

Token bucket: refilling and draining, live

Start here, before any code. Think of a subway fare card that automatically adds one ride's worth of credit every few minutes, up to a maximum of 10 rides stored at once. If you haven't ridden in a while, you can burn through several stored rides back-to-back right now — the card doesn't care that you're "supposed" to only need one ride per refill period, it just checks whether you have credit available at all. But once you've drained it, you're stuck waiting for the next refill tick, same as anyone else.

A token bucket holds up to some maximum number of tokens (the burst capacity), refilling at a fixed rate (e.g. 2 tokens per second) up to that cap. Each incoming request consumes exactly one token if any are available; if the bucket is empty, the request is rejected (or queued, depending on design). This design explicitly ALLOWS bursts — a client that's been idle can spend its entire accumulated bucket in one instant — while still enforcing a strict long-run average rate once the bucket runs dry.

Interview-ready definition: a token bucket rate limiter maintains a counter capped at a maximum burst capacity, refilling at a fixed rate over time; each request consumes one token if available and is rejected otherwise. It permits short bursts up to the full bucket capacity (useful for clients with naturally bursty-but-bounded traffic) while still enforcing a hard long-run average rate equal to the refill rate once accumulated tokens are exhausted — the key design lever is choosing capacity (how large a burst to tolerate) independently from refill rate (the sustained long-run limit).
02 — Counting requests "in the last N seconds" is trickier than it sounds

Sliding window vs fixed window, and the boundary flaw

Start here, before the demo. Imagine a rule "no more than 5 coffees per calendar hour" versus "no more than 5 coffees in any rolling 60-minute stretch." The calendar-hour rule has an exploit: order 5 coffees at 8:59am (still within the 8am hour) and another 5 at 9:01am (now within the 9am hour) — that's 10 coffees in 2 minutes, technically obeying the calendar-hour rule the whole time. The rolling-60-minute rule has no such exploit — it always looks back exactly 60 minutes from RIGHT NOW, no matter where that lands relative to any clock boundary.

Fixed window

Counts requests within rigid clock-aligned buckets (e.g. 9:00:00-9:00:59). Simple and cheap, but a client can send a full limit's worth of requests in the last instant of one window and another full limit's worth in the first instant of the next — doubling the effective rate right at the boundary.

Sliding window

Counts requests within a continuously moving window measured back from the current instant (e.g. "the last 60 seconds, right now"). No fixed boundary to exploit — the count at any moment reflects exactly what happened in the immediately preceding window, regardless of clock alignment.

The trap, made concrete: with a fixed 60-second window and a limit of 5, a client can send 5 requests at 9:00:59 and 5 more at 9:01:00 — 10 requests in roughly 1 second, yet each 60-second bucket individually shows exactly 5, satisfying the rule as literally written. A true sliding window looking back 60 seconds from 9:01:00 would see all 10 of those requests within its lookback range and correctly reject the excess.
Interview-ready definition: fixed-window rate limiting counts requests in rigid, clock-aligned time buckets and resets the count to zero at each boundary, which allows up to roughly 2x the intended rate for requests clustered around a boundary crossing. Sliding-window rate limiting counts requests within a continuously moving lookback interval measured from the current moment, eliminating the boundary exploit at the cost of needing to track individual request timestamps (or a weighted approximation blending the current and previous fixed windows) rather than a single resettable integer.
03 — The counter that works fine until you add a second server

Distributed rate limiting

Start here, before the diagram. Picture 3 separate cashiers at 3 separate registers, each keeping their OWN private tally of how many items a particular customer has bought today, with no way to compare notes. That customer can simply visit a different register each time and, from each cashier's individual perspective, never exceed the limit — even though their TOTAL across all three registers is way over. The limit was real, but it was only ever being enforced per-register, not per-customer.

An in-memory counter (a plain variable in your application process) works perfectly on a single server — but the moment you run multiple instances behind a load balancer, each instance has its OWN separate copy of that counter, with no visibility into what the others have counted. A client hitting 3 different instances round-robin can consume 3x its intended limit, because each instance independently believes the client is well within bounds.

Interview-ready definition: distributed rate limiting requires every server instance to check and update a SHARED counter (typically in a fast in-memory store like Redis) rather than an independent in-process counter, because per-instance counters cannot see traffic hitting sibling instances and collectively under-enforce the true limit by roughly a factor of the instance count. The shared store's increment operation must be atomic (a single indivisible read-modify-write, like Redis's INCR) to avoid a race condition where two instances both read the same pre-increment value concurrently and both allow a request that, combined, exceeds the limit.
04 — Not every spike is abuse

Handling burst traffic

Start here, before the table. A legitimate user opening an app after being offline for an hour might fire off a dozen requests in the first second (syncing everything they missed) — that's a burst, not an attack. A rate limiter that treats ALL bursts as violations equally, with zero tolerance, ends up punishing normal usage patterns just as harshly as actual abuse.

ApproachHow it handles burstsTrade-off
Token bucketExplicitly tolerates bursts up to bucket capacity, independent of refill rateRequires tuning two separate parameters (capacity and refill rate) instead of one
Sliding windowTolerates bursts only within the limit for that rolling window — no special burst allowanceSimpler mental model, but less forgiving of legitimately bursty-but-bounded clients
Fixed windowUnintentionally over-tolerates bursts at window boundaries (the flaw covered above)The "burst tolerance" here is an accidental bug, not a deliberate design choice

In practice, many production rate limiters layer multiple limits together: a short-window limit (e.g. 20 requests per second, catching abusive bursts) combined with a longer-window limit (e.g. 1000 requests per hour, catching sustained overuse that trickles in slowly enough to dodge the short-window check). This gives a legitimate bursty client room to breathe on the short window while still bounding their total consumption over time.

Why this matters in practice: a rate limiter that's too strict on bursts causes real users to see errors during completely normal usage (a mobile app reconnecting after being backgrounded, a batch UI action that fires several requests at once) — this is a genuine product regression, not just an edge case. Choosing token bucket over a bare sliding window specifically because it tolerates bounded bursts is often the right call for user-facing APIs, while strict sliding-window enforcement is more appropriate for protecting genuinely scarce backend resources (a downstream service that truly cannot handle spikes at all, regardless of legitimacy).
Interview-ready definition: burst traffic is a legitimate, temporary spike in request rate from a single client that doesn't represent sustained overuse or abuse — a well-designed rate limiter distinguishes tolerable bursts from actual abuse by choosing an algorithm (token bucket) or a layered set of limits (short-window plus long-window) that explicitly allows short-term spikes while still capping the long-run average rate, rather than treating every momentary spike as a violation.

Problem 1 · Tracing a token bucket by hand

A token bucket has capacity 5, refills 1 token/second, and starts full. A client sends 5 requests instantly at t=0, then 1 request at t=0.5s, then 1 request at t=1.2s. Which requests succeed, and why?

Show solution
The 5 requests at t=0 all succeed, draining the bucket from 5 tokens to 0 (it started full, at capacity). The request at t=0.5s FAILS -- only 0.5 seconds have passed since the bucket hit empty, and at a refill rate of 1 token/second, only 0.5 tokens have accumulated (not yet a full token), so there's nothing available to consume. The request at t=1.2s SUCCEEDS -- by then, 1.2 seconds have passed since the bucket was emptied, meaning slightly more than 1 full token has refilled (capped at capacity 5, but here well under that cap), so exactly 1 token is available and gets consumed, bringing the bucket back to roughly 0.2 tokens remaining.
Problem 2 · The fixed-window boundary exploit, quantified

A fixed-window rate limiter allows 100 requests per 60-second window. What is the maximum number of requests a client could send in any 1-second real-world interval while technically never exceeding the stated limit in any single window, and how?

Show solution
Up to 200 requests in roughly 1 second. The exploit: send 100 requests in the final second of one window (e.g. 9:00:59), which is fully within that window's 100-request allowance, then send another 100 requests in the very first second of the NEXT window (9:01:00), which is fully within THAT window's separate 100-request allowance. From the fixed-window limiter's perspective, two entirely separate buckets each correctly recorded exactly 100 -- no individual window was ever exceeded -- but a real 1-2 second slice of wall-clock time actually saw 200 requests, double the intended sustained rate. This is exactly the boundary flaw a sliding window eliminates, since it would see all 200 requests within its continuously-moving 60-second lookback and correctly flag the excess.
Problem 3 · Diagnosing under-enforcement across instances

A service is meant to enforce a limit of 100 requests/minute per API key, using a simple in-process counter, and runs behind a load balancer with 4 instances using round-robin routing. What is the effective, actually-enforced limit per client, and why?

Show solution
The effective enforced limit is roughly 400 requests/minute per client -- 4 times the intended 100 -- because each of the 4 instances maintains its OWN independent in-process counter with no visibility into the other 3. With round-robin routing spreading a client's requests evenly across all 4 instances, each instance individually sees only about 1/4 of that client's total traffic, so each instance's local counter stays under 100 even when the client's TRUE total across all instances is 4x that. The limit was never actually broken from any single instance's narrow point of view -- it was simply never being measured against the client's real, cross-instance total at all. Fixing this requires a shared counter (e.g. in Redis) that every instance reads from and atomically increments, so the count reflects the client's true aggregate usage regardless of which instance happened to handle each request.
Problem 4 · Why the increment must be atomic

A team implements distributed rate limiting by having each instance run: (1) GET the current count from Redis, (2) check in application code if count < limit, (3) if so, SET count+1 back to Redis. Under concurrent requests from the same client hitting two different instances at nearly the same moment, what can go wrong?

Show solution
This is a classic race condition (a check-then-act pattern that isn't atomic). Suppose the current count is 99 and the limit is 100. Instance A reads count=99, checks 99 < 100 (true), and prepares to write 100 back. Before Instance A's write completes, Instance B ALSO reads count=99 (A hasn't written yet), also checks 99 < 100 (true), and also prepares to write 100. Both instances independently concluded their request should be ALLOWED based on the same stale read of 99, and both write back 100 -- meaning 2 requests were let through when only 1 slot (99 -> 100) actually remained, silently allowing the client to exceed the limit by however many requests race in this way. The fix is to use a genuinely atomic operation like Redis's INCR, which performs the read-increment-write as a single indivisible step server-side -- there's no window between reading and writing where a second concurrent caller could read the same stale value, because the increment and the return of the new value happen together, atomically, for every caller.
Problem 5 · Choosing token bucket vs sliding window for a real scenario

A mobile app syncs data with the server, sending nothing while the app is backgrounded and then a flurry of catch-up requests the moment the user reopens it. Meanwhile, a separate internal service must never send more than a strictly bounded rate to a fragile downstream dependency, no exceptions. Which algorithm fits each scenario, and why?

Show solution
The mobile app sync scenario fits TOKEN BUCKET well. The "nothing while backgrounded, then a burst on reopen" pattern is exactly what a bucket's accumulated-capacity model is built to tolerate -- tokens quietly build up while idle, and the burst on reopen simply spends that built-up allowance, which is legitimate usage, not abuse. Rejecting that burst with a strict, non-bursty limiter would create a poor user experience for completely normal behavior. The fragile-downstream-dependency scenario fits SLIDING WINDOW (or an even stricter fixed-rate approach) better. Here the goal is a hard, consistent ceiling on instantaneous rate with no tolerance for bursts at all, because the downstream system genuinely cannot absorb a burst regardless of whether it's "legitimate" -- token bucket's core feature (deliberately allowing bursts) is precisely the property this scenario needs to AVOID. A tightly-scoped sliding window with a low limit gives the most consistent, predictable request pacing with no burst allowance baked in.
