BACKEND & APIS LAB · RAW ASYNC DRIVERS

An ORM writes SQL for you. Sometimes that's exactly the problem.

Every ORM trades some performance and control for convenience — object hydration, an identity map, and a SQL-generation layer standing between your code and the database. Most of the time that trade is worth it. This lab digs into the three places it stops being worth it: raw drivers like asyncpg talking the wire protocol almost directly, prepared statements that are both faster AND safer than string-built SQL, and the N+1 query trap that a JOIN quietly avoids.

01 — Convenience has a CPU cost, and sometimes a correctness cost too

When raw drivers outperform an ORM

Start here, before any code. Imagine ordering food through a translator who has to convert your request into the restaurant's native language, relay it, wait for the kitchen's answer, translate that back, and also keep a running notebook of every dish you've ordered all night in case you ask about it again. Most of the time that's genuinely helpful — you don't speak the language, and the notebook saves you re-explaining yourself. But if you're placing the exact same simple order a thousand times a minute, all that translating and note-keeping starts to visibly slow the kitchen down, and you'd rather just shout the order directly to the cook in a language they already understand.

An ORM (Object-Relational Mapper) sits between your application code and the database, and that translation layer does real, measurable work on every query:

  • Object hydration — every row that comes back from the database gets turned into a full Python object, with attribute descriptors, type coercion, and often lazy-loading machinery attached, even if you only needed two of its twelve columns.
  • Identity map / unit-of-work bookkeeping — the ORM tracks every object it has loaded in this session so that fetching the "same" row twice returns the same Python object and edits get batched into a single flush. That tracking has memory and CPU overhead on every load.
  • SQL generation through an abstraction layer — your query.filter(...).join(...) chain has to be walked and compiled into SQL text at runtime, which costs cycles the raw driver never spends because you already wrote the SQL yourself.
  • Often genuinely worse SQL — for a specific, tricky query (a complex aggregate, a recursive CTE, a query that needs a particular index hint or join order) a human who knows the schema can frequently hand-write something more efficient than what a general-purpose query builder produces, because the ORM has to stay correct for the general case, not your specific one.

A raw driver like asyncpg skips essentially all of this. It speaks PostgreSQL's binary wire protocol almost directly, returns rows as lightweight record-like objects (not full tracked ORM entities), and executes exactly the SQL text you wrote — nothing is being generated, tracked, or hydrated into a rich object graph on your behalf.

Interview-ready definition: raw async drivers outperform an ORM by skipping object hydration (materializing rows as rich, tracked Python objects), identity-map/unit-of-work bookkeeping, and runtime SQL-generation overhead — talking the database's wire protocol nearly directly and executing exactly the SQL text you wrote. This matters most on hot, high-throughput query paths, in bulk data pipelines that don't need a live object graph, and for tricky queries where a hand-written statement is more efficient than what a general-purpose query builder would generate. It is a genuine trade-off, not a free win: you give up the ORM's convenience (automatic object mapping, relationship traversal, database-agnostic code) in exchange for raw performance and exact control.
02 — Parse once, plan once, execute many times

Prepared statements: the actual mechanism

Start here, before the pipeline. Think of a chef who, the first time a particular dish is ordered, has to read the recipe, figure out the best order to prep ingredients, and decide which pans and burners to use — that's real up-front thinking. But once they've done that thinking once, every future order of the SAME dish just plugs in different quantities or spice levels into a workflow they've already worked out; they don't re-read the recipe or re-plan the kitchen layout from scratch every single time.

A SQL statement like SELECT * FROM users WHERE id = $1 goes through two distinct phases the first time the database sees it: it is PARSED (checked for syntax, resolved against the schema) and PLANNED (the query optimizer decides HOW to execute it — which index to use, what join strategy, etc.), producing a reusable query plan. A prepared statement is exactly this: parse and plan done ONCE, then the resulting plan is EXECUTED MANY TIMES with different bound parameter values ($1 = 7, then $1 = 812, then $1 = 44...), skipping the re-parse and re-plan on every subsequent call.

First call: parse + plan + execute. Every call after: execute only, reusing the cached plan.
Why this is faster: parsing and query planning are not free — the planner has to consider index choices, estimate row counts, and pick a join strategy, which takes real CPU time. A prepared statement pays that cost exactly ONCE, no matter how many times you execute it afterward with different parameter values, instead of paying it fresh on every single call. For a query executed thousands of times per second, this is the difference between doing real optimizer work thousands of times per second and doing it once, ever.

Why this is also safer: SQL injection

The other half of the story is security, not just speed. When a query is built by concatenating a user-supplied value directly into the SQL text, that value becomes part of the SQL the database parses — which means a malicious value can inject its OWN SQL syntax into the statement. A parameterized query never does this: the parameter value is sent to the database separately from the SQL text, as pure data, and the database substitutes it into the already-parsed plan without ever re-parsing it as code. A malicious string like 1; DROP TABLE users;-- is treated as a literal parameter value — never as executable SQL — because by the time the parameter is bound, parsing is already over.

Interview-ready definition (be precise here, not just "it's safer"): prepared statements prevent SQL injection because the parameter value and the SQL command text travel to the database through two SEPARATE channels and are never combined before parsing happens. The SQL text (SELECT * FROM users WHERE id = $1) is parsed and planned first, with $1 as an unfilled placeholder — parsing is fully complete before any user-supplied value is even sent. Only afterward is the parameter value bound into that already-fixed plan as inert data. Since the malicious value never passes through the SQL parser at all, it has no opportunity to be interpreted as SQL syntax — it can only ever be treated as the literal contents of one parameter, no matter what characters it contains. String concatenation has no such separation: the user's value becomes part of the text handed to the parser, so any SQL-meaningful characters inside it (quotes, semicolons, comment markers) are parsed as real SQL syntax, exactly as if the attacker had typed them into the query themselves.
03 — The trade-off made concrete: less abstraction, more control

Abstraction vs control: the N+1 problem

Start here, before any queries. Imagine asking an assistant for a list of 5 book titles, and then, for each book, separately asking "who wrote this one?" one at a time — that's 1 trip to get the list plus 5 more trips, one per book, when you could have just asked "give me the 5 books AND their authors" in a single request and gotten everything back at once. The naive approach doesn't feel wrong in the moment (each individual question is simple and correct), but the total number of round trips scales directly with how many books you asked about.

This is exactly what happens with naive ORM lazy-loading. Fetching a list of posts is 1 query. Then looping over each post and accessing post.author.username triggers a SEPARATE query per post the first time that relationship is accessed, because the ORM didn't know up front that you'd need every post's author — it fetches each one lazily, on demand, the moment your code asks for it. For N posts, that's 1 query for the posts plus N queries for the N authors: N+1 total queries.

# Naive ORM version -- looks completely innocent posts = await session.execute(select(Post)) posts = posts.scalars().all() # query 1: fetch all posts for post in posts: print(post.author.username) # query 2, 3, 4, ... N+1: one SELECT per post's author

A raw driver (or a properly written ORM query) avoids this entirely with a single JOIN:

-- Raw driver / hand-written version -- ONE query total SELECT posts.id, posts.title, users.username AS author_username FROM posts JOIN users ON posts.author_id = users.id;

Interview-ready definition: the N+1 problem occurs when fetching a list of N parent records triggers 1 initial query, followed by N additional queries — one per parent — to lazily fetch a related child or parent record for each item individually, for a total of N+1 queries where a single JOIN (or an ORM's eager-loading feature) could have fetched everything in exactly 1 query. It is the sharpest concrete example of the ORM's abstraction/control trade-off: the convenience of writing post.author.username as if it were just a normal attribute access hides the fact that, without explicit eager loading, each access is a full separate round trip to the database.
04 — Same operation, three ways to write it

Side-by-side: ORM (naive vs eager) vs raw driver

Start here, before the code. Three cooks can be asked for "the same finished dish" and produce wildly different amounts of kitchen activity to get there — one makes a dozen small trips to the pantry as they go, one plans ahead and grabs everything in one trip, and one just knows the recipe well enough to skip straight to plating. Same requested outcome, very different amounts of underlying work.

The task: get all posts along with each post's author's username. Here it is written three ways.

ORM — naive (N+1)

result = await session.execute( select(Post) ) posts = result.scalars().all() for post in posts: print(post.author.username) # lazy-loads author, # 1 query per post

ORM — eager-loaded (fixed)

from sqlalchemy.orm import selectinload result = await session.execute( select(Post).options( selectinload(Post.author) ) ) posts = result.scalars().all() for post in posts: print(post.author.username) # no extra query -- # already loaded

Raw driver — hand-written JOIN

rows = await conn.fetch( """ SELECT p.id, p.title, u.username AS author FROM posts p JOIN users u ON p.author_id = u.id """ ) for row in rows: print(row["author"])

selectinload fixes the N+1 by issuing exactly 2 queries total: one for all the posts, and one more that fetches all of their authors in a single WHERE id IN (...) batch — still more than the raw driver's 1 query, but a huge improvement over N+1. joinedload instead folds everything into a single query using a SQL JOIN, much like the raw driver version, at the cost of the result set repeating post columns once per row.

Interview-ready definition: the same logical fetch can compile down to a wildly different number of database round trips depending entirely on HOW the ORM (or hand-written SQL) is told to load related data — naive lazy-loading defaults to N+1 queries, explicit eager-loading strategies like selectinload or joinedload collapse that to 1-2 queries while keeping ORM ergonomics, and a raw hand-written JOIN collapses it to exactly 1 query with the least abstraction and the most control. Choosing between them is a real engineering decision, not a "raw is always better" rule — it depends on how hot the code path is and how much you value keeping the ORM's object-mapping convenience.

Problem 1 · Spotting N+1 in given ORM code

A code reviewer sees this:
orders = await session.execute(select(Order)); orders = orders.scalars().all()
for o in orders: print(o.customer.email)
Is there an N+1 problem here? How would you confirm it, and how would you fix it?

Show solution
Yes, this is a textbook N+1. The first line issues one query to fetch all orders. Inside the loop, "o.customer.email" accesses a relationship (customer) that was never eagerly loaded, so on the FIRST access for each distinct order, SQLAlchemy lazily issues a fresh SELECT to fetch that order's customer row. For N orders, that is 1 query for the orders plus up to N more queries for their customers. To confirm it, you would turn on SQL echo logging (e.g. engine created with echo=True) or attach a query-counting listener and watch the query count scale linearly with the number of orders returned -- 10 orders should produce roughly 11 queries if this is really happening. The fix is to eager-load the relationship up front: add ".options(selectinload(Order.customer))" (or joinedload) to the initial select, so the customer data is fetched in 1-2 total queries instead of lazily, one per order, inside the loop.
Problem 2 · Why prepared statements prevent SQL injection, precisely

A junior engineer says "prepared statements are safer because the database sanitizes the input." Is that the correct mechanism? Explain precisely why prepared statements actually prevent injection.

Show solution
"Sanitizing input" is not the correct mechanism, and describing it that way hides what's actually happening. The real mechanism is a SEPARATION between the SQL text and the parameter values, in time and in channel. With a prepared statement, the SQL text (e.g. "SELECT * FROM users WHERE id = $1") is sent to the database and fully PARSED AND PLANNED first, with $1 left as an unfilled placeholder in the resulting plan -- this happens before the actual parameter value is even provided. Only afterward is the parameter value bound into that already-fixed, already-parsed plan, purely as inert data to be compared or inserted -- it is never re-submitted to the SQL parser at all. Because the malicious value never passes through the parser, characters that would normally have special SQL meaning (a closing quote, a semicolon, a comment marker like "--") are not interpreted as syntax -- they are just the literal bytes of one parameter's value, no matter what they contain. This is categorically different from "sanitizing" (which implies scanning and possibly modifying/escaping dangerous characters in the input) -- a prepared statement doesn't need to detect or strip anything dangerous, because the value was never in a position to be parsed as code in the first place.
Problem 3 · Calculating total query count for N+1

A page lists 40 products, and for each product the naive ORM code lazily loads that product's category name and its seller's display name (two separate relationships per product, both lazily loaded). How many total queries fire, and what would eager-loading both relationships bring it down to?

Show solution
Naive: 1 query for the 40 products, plus 40 queries for each product's category (one per product, lazily triggered), plus another 40 queries for each product's seller (also one per product) = 1 + 40 + 40 = 81 total queries. This is really "N+1" applied twice over, once per lazily-loaded relationship -- more precisely it's 1 + 2N for N products and 2 lazy relationships per product. With both relationships eager-loaded (e.g. ".options(selectinload(Product.category), selectinload(Product.seller))"), each relationship collapses to 1 additional batched query total (a single "WHERE category_id IN (...)"-style query for all categories, and a single similar query for all sellers), bringing the total down to 1 + 1 + 1 = 3 queries -- independent of how many products (N) there are, versus the naive version's cost scaling linearly with N.
Problem 4 · Choosing eager loading vs raw driver for a scenario

Two teams both need "list of posts with author username." Team A is building an internal admin dashboard viewed by a handful of employees, occasionally, with existing SQLAlchemy models already in place. Team B is building the main public API endpoint that serves this exact data to hundreds of thousands of requests per minute. What should each team choose, and why?

Show solution
Team A (internal admin dashboard, low traffic, existing ORM models) should use the ORM with eager loading (selectinload or joinedload). The traffic volume is low enough that the ORM's per-request overhead is completely irrelevant to user experience or infrastructure cost, and staying in the ORM keeps the code consistent with the rest of the codebase, gets automatic object mapping, and avoids maintaining a second, separate raw-SQL code path for something used rarely. Team B (hot public endpoint, hundreds of thousands of req/min) should strongly consider the raw driver with a hand-written JOIN, or at minimum benchmark eager-loaded ORM against it before deciding. At that request volume, even a small per-request overhead difference (object hydration, identity-map bookkeeping, extra query round trips) gets multiplied by an enormous number of requests, translating directly into real latency and infrastructure cost. The precise control over exactly what SQL executes, and the lower per-request overhead, are worth the loss of ORM convenience specifically because this is the hottest possible path in the system.
Problem 5 · When ORM overhead genuinely doesn't matter

Explain, in terms of actual request volume and latency budgets, why "always use a raw driver, ORMs are slow" is bad advice -- give a concrete scenario where the ORM's overhead is the right trade to make.

Show solution
"ORMs are slow, always avoid them" ignores that the ORM's overhead is typically single-digit milliseconds per query -- often far smaller than network latency, downstream API calls, or business logic elsewhere in the same request. For a low-traffic internal tool (say, a handful of requests per minute, viewed by employees who are fine waiting an extra 20-50ms), that overhead is completely imperceptible to the end user and utterly insignificant to infrastructure cost -- optimizing it away by hand-writing raw SQL trades real developer time and code-maintainability risk for a performance gain nobody will ever notice or benefit from. The right trade genuinely reverses only once request volume and per-query frequency get high enough that the overhead is (a) multiplied by a large number of requests per second, turning milliseconds into meaningful aggregate infrastructure cost and queueing latency, or (b) sitting directly on a latency-sensitive hot path where every millisecond shaved measurably improves p99 latency for real users -- a checkout flow, a search-as-you-type endpoint, a feed that must render instantly. Blanket advice in either direction ("always ORM" or "always raw") ignores that this is a genuine cost/benefit trade that depends on traffic volume and how hot the specific path actually is, not a universal rule.
