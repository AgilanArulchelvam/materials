BACKEND & APIS LAB · WEBSOCKETS

A WebSocket connection starts life as an ordinary HTTP request, then never goes back.

WebSockets don't replace HTTP — they hijack a single HTTP request into something entirely different via a one-time "upgrade" handshake, after which both sides can send messages to each other at any moment, independently, with no request/response turn-taking at all. This lab shows the real upgrade headers, animates true full-duplex messaging, and walks the connection lifecycle as a state machine.

01 — One HTTP request that asks to stop being HTTP

The upgrade handshake, header by header

Start here, before any headers. Think of calling a company's automated phone line and, partway through, asking to be transferred to a live human on an open line that stays connected until either of you hangs up — no more pressing 1 for this and 2 for that, just a continuous conversation. That transfer request itself still has to go through the normal phone system to initiate, but once it succeeds, the nature of the call has fundamentally changed.

A WebSocket connection begins as a completely normal HTTP request — the same TCP connection, same HTTP framing — but with special headers asking the server to upgrade the connection to a different protocol entirely. If the server agrees, it responds with status 101 Switching Protocols, and from that point forward, the SAME underlying TCP connection stops speaking HTTP and starts speaking the WebSocket framing protocol instead.

THE REAL HANDSHAKE HEADERS
GET /chat HTTP/1.1 Host: example.com Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== Sec-WebSocket-Version: 13 HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Click to see exactly how the server proves it understood the upgrade request.

The Sec-WebSocket-Key is a random, client-generated base64 value — it isn't a secret or a credential, it exists purely to prove the server actually understood the WebSocket handshake protocol (and to help defend against certain caching proxies mistakenly treating this as a cacheable plain HTTP response). The server proves it understood by taking that key, appending a fixed "magic" GUID string defined by the WebSocket spec, SHA-1 hashing the result, and base64-encoding that hash into Sec-WebSocket-Accept. Any client can verify this computation locally to confirm the response came from a real WebSocket-aware server.

The mistake this trips people into: Sec-WebSocket-Key looks like it should be a security credential (it's random, it's in a header called "Key"), but it provides no actual security — anyone can compute the matching Accept value, since the transformation algorithm and magic GUID are public and fixed by the spec. Its purpose is protocol confirmation, not authentication; any real auth (session cookies, a token in the initial URL or a subprotocol) has to be handled separately, typically during this same initial HTTP handshake before the upgrade completes.
Interview-ready definition: the WebSocket handshake is a single HTTP/1.1 request containing Upgrade: websocket and Connection: Upgrade headers plus a randomly generated Sec-WebSocket-Key; a server that supports the upgrade responds with 101 Switching Protocols and a Sec-WebSocket-Accept header computed deterministically from the key, confirming both sides understood the handshake. After this single exchange, the same underlying TCP connection is repurposed entirely for WebSocket framing — it is no longer an HTTP connection at all.
02 — Both sides can talk whenever they want

Full-duplex communication vs request/response

Start here, before the demo. Ordinary HTTP is like a customer service call where you can only speak after you've pressed a button to ask a question, and the agent only ever responds to what you just asked — the agent can never call you out of the blue to tell you something on their own initiative. A WebSocket connection is like an open phone line where either party can start talking at literally any moment, independent of whether the other side just said something, and both can even talk at exactly the same time.

This property is called full-duplex: after the handshake, either the client or the server can send a message at any time, with no requirement that a message be "in response to" anything. This is fundamentally different from HTTP's request/response model, where the server can only ever speak when spoken to (a client sends a request, and only then does a response come back).

Why this matters in practice: full-duplex is what makes WebSockets the right fit for genuinely bidirectional, low-latency use cases — live chat (either party can type at any time), multiplayer games (both the local player's actions and other players' state updates arrive independently), and collaborative editing (any collaborator's keystroke needs to reach everyone else immediately, not on some polling schedule). Simulating this over plain HTTP requires ugly workarounds like long-polling, where the client repeatedly asks "anything new?" and the connection just hangs open until there's an answer.
Interview-ready definition: full-duplex communication means both parties can transmit data independently and concurrently over the same connection, with no turn-taking requirement — contrasted with HTTP's half-duplex request/response model, where the server may only send data in direct reply to a client-initiated request and can never push data unprompted. WebSockets provide true full-duplex messaging over a single persistent TCP connection once the upgrade handshake completes.
03 — What a WebSocket connection goes through, start to finish

Connection lifecycle: open, message, close, error

Start here, before the diagram. Any long-lived phone call has a shape: it gets connected, conversation happens (possibly for a long time), and eventually it ends — either because someone hangs up normally, or because the line just drops unexpectedly. A WebSocket connection, as an object in your client-side code, exposes exactly this shape as four events you can listen for.

Pick a scenario to watch the client-side WebSocket events fire in order.
const ws = new WebSocket("wss://example.com/chat"); ws.onopen = function(event) { // fires once, when the 101 handshake completes -- safe to send now ws.send("hello from client"); }; ws.onmessage = function(event) { // fires every time a message arrives, in any order relative to sends console.log("received:", event.data); }; ws.onerror = function(event) { // fires on a connection-level failure -- the socket is unusable now console.error("WebSocket error", event); }; ws.onclose = function(event) { // fires exactly once, whether closed cleanly or after an error console.log("closed:", event.code, event.reason); };
The ordering detail worth remembering: onerror does NOT replace onclose — a connection that errors out still transitions to CLOSED and still fires the close event afterward. This means cleanup logic that needs to run whenever a connection ends (regardless of whether it ended cleanly or via an error) belongs in onclose, not duplicated into both handlers.
Interview-ready definition: a WebSocket connection moves through four states — CONNECTING (handshake in flight), OPEN (handshake succeeded, full-duplex messaging active, onopen fired), CLOSING (a close handshake has started), and CLOSED (connection fully terminated, onclose fired with a status code and reason). An error event can fire while OPEN to signal an abnormal failure, but it always precedes an eventual close event rather than replacing it — client code should treat onclose as the single reliable place to detect "this connection is now over," for any reason.

Problem 1 · What Sec-WebSocket-Key actually proves

A developer argues that since Sec-WebSocket-Key is randomly generated per connection, it must be providing some security guarantee (like proving the client isn't malicious). Is this correct?

Show solution
No. Sec-WebSocket-Key provides protocol confirmation, not security. Its randomness exists mainly to prevent certain caching proxies from incorrectly treating the 101 response as a cacheable, generic HTTP response for that URL (since the accept value differs every time). The transformation from key to Sec-WebSocket-Accept (append a fixed public GUID, SHA-1 hash, base64 encode) is entirely public and specified by the WebSocket RFC -- any client, malicious or not, can compute the correct Accept value for any Key. It proves the SERVER implements the WebSocket handshake correctly, not anything about the trustworthiness of the client. Actual authentication (verifying who the client is) has to be handled separately, typically via a cookie or token sent during the same initial HTTP request.
Problem 2 · Recognizing when polling should become a WebSocket

An app currently polls a REST endpoint every 2 seconds asking "any new chat messages?" Explain concretely what problem this causes and why WebSockets are a better fit.

Show solution
Polling every 2 seconds means: (1) up to 2 seconds of latency between a message being sent and the recipient seeing it, even when the recipient is actively online and ready, and (2) constant wasted requests during the much more common case where there's NO new message yet -- every single poll that returns "nothing new" was pure overhead (a full HTTP request/response round trip, connection overhead, server load) for zero useful information. A WebSocket connection flips this: the server can PUSH a new message to the client the instant it exists, with no polling interval determining the worst-case latency, and no wasted round trips when nothing has happened -- the connection just sits open, idle, and costs nothing extra until there's actually something to send. This is exactly the full-duplex, server-can- speak-first property that plain HTTP request/response cannot provide.
Problem 3 · Tracing the state machine under a network drop

A user's WiFi drops mid-conversation while a WebSocket connection is OPEN. Which events fire, in what order, and does the client's cleanup logic in onclose still run?

Show solution
The sequence is: OPEN -> error event fires (onerror) because the underlying transport failed abnormally -> the connection transitions to CLOSED -> close event fires (onclose), typically with a non-normal close code (e.g. 1006, "abnormal closure") since no clean closing handshake occurred. Yes, onclose still runs. The error event does not replace or skip past onclose -- every WebSocket connection that reaches CLOSED fires onclose exactly once, whether it got there via a clean, intentional close or via an abnormal failure. This is precisely why any cleanup that must run regardless of HOW the connection ended (releasing resources, updating UI state, attempting reconnection) belongs in onclose rather than being duplicated into onerror.
Problem 4 · Upgrade request rejected

A client sends a WebSocket upgrade request to a server that doesn't support WebSockets at all. What does the server most likely respond with, and what does the client-side WebSocket object do as a result?

Show solution
A server with no WebSocket support simply doesn't recognize the Upgrade header as anything special -- it responds like it would to any other request it can't fulfill as asked, typically with a normal HTTP status (commonly 400 Bad Request, or whatever status the route would normally return, since from the server's perspective this just looked like a regular GET request with some unusual headers it ignored). It will NOT respond with 101 Switching Protocols, because that requires explicit WebSocket support to send. On the client side, since the handshake didn't succeed with 101, the WebSocket object never transitions to OPEN -- onopen never fires. Instead, it fires onerror (the handshake failed) followed by onclose, and the application never gets a usable full-duplex connection.
Problem 5 · Why the handshake has to be HTTP at all

Why does the WebSocket protocol bother starting as an HTTP request instead of just being its own completely separate protocol with its own port and handshake from the start?

Show solution
Starting as a normal HTTP request lets WebSocket connections travel through the exact same infrastructure that already exists for HTTP traffic -- the same port (80/443), the same TLS termination points, the same reverse proxies, load balancers, and corporate/network firewalls that are already configured to allow and route HTTP(S) traffic. If WebSockets required an entirely separate protocol and port from scratch, every one of those intermediary systems would need explicit new configuration to allow it through, and many restrictive networks (corporate firewalls, some mobile carriers) that only permit standard web ports would block it outright. By beginning as a request that looks completely ordinary to any intermediary that doesn't specifically understand the Upgrade header, WebSocket traffic can piggyback on infrastructure built for HTTP, and only diverges into its own framing protocol after both endpoints have explicitly agreed to it -- any middlebox that doesn't understand the upgrade just sees a request it can't fulfill and responds accordingly, rather than mysteriously breaking or blocking traffic on some unfamiliar port.
