BACKEND & APIS LAB · HTTP/1.1 VS HTTP/2

One slow request on HTTP/1.1 blocks everything behind it. On HTTP/2, it just finishes last.

HTTP/1.1 and HTTP/2 speak the same request/response semantics, but their wire-level connection handling is completely different: HTTP/1.1 sends responses back in the SAME order requests went out on a given connection, while HTTP/2 interleaves independent streams over one connection and lets each finish whenever it's actually ready. This lab animates the exact same 4 requests racing down both protocols side by side.

01 — Why one slow thing stalls everything behind it

Head-of-line blocking in HTTP/1.1

Start here, before any code. Picture a single checkout lane at a grocery store, one register, one line. If the person at the front has a cart full of coupons that need manual price checks, EVERYONE behind them waits — it doesn't matter that the next three people each have exactly one item and could be through in seconds. The register can only serve one customer at a time, strictly in line order, and a slow customer at the front delays every faster customer behind them.

A single HTTP/1.1 connection works the same way. Without pipelining (which browsers effectively never use in practice due to its own ordering problems), each connection sends one request, waits for its FULL response, then sends the next. Browsers work around this by opening multiple parallel TCP connections to the same host (historically 6 per origin) — but on any ONE of those connections, requests are still strictly serialized: if request #1 is slow, requests #2, #3, and #4 queued on that same connection cannot even start until #1 finishes.

The trap in the term "head-of-line blocking": it doesn't mean the slow request itself is the problem — a 3.5-second API call is just... a 3.5-second API call. The actual damage is that two genuinely fast requests (a tiny JSON config, a small icon) that could have completed in milliseconds are forced to wait the ENTIRE 3.5 seconds too, purely because of queue position on a shared connection, not because they're slow themselves.
Interview-ready definition: head-of-line (HOL) blocking on an HTTP/1.1 connection occurs because responses must be delivered in the same order their requests were sent on that connection — a slow response at the front of the queue delays every faster response queued behind it on the same connection, even though those later responses may already be ready. Opening multiple parallel connections per origin mitigates this in practice but doesn't eliminate it, and each additional connection carries its own TCP/TLS setup cost.
02 — One connection, many independent conversations

Multiplexing, header compression & server push

Start here, before any code. Now picture a restaurant kitchen with several chefs working off ONE shared ticket rail, each chef free to grab any ticket and start cooking, and each dish gets plated and sent out the moment IT is done — not necessarily in the order tickets came in. A slow dish for table 4 doesn't stop table 7's quick order from going out first. Same shared resource (the kitchen), but no single-file queue forcing strict ordering.

HTTP/2 introduces streams: each request/response pair gets its own independent stream ID, and many streams share ONE underlying TCP connection, with their data frames physically interleaved on the wire. The server can send stream 2's response chunks, then stream 4's, then more of stream 2's, in whatever order data becomes ready — no stream has to wait for an earlier one to fully finish. HTTP/2 also compresses headers with HPACK (avoiding re-sending identical header sets like cookies and user-agent strings on every single request) and supports server push (the server proactively sends a resource it knows the client will need next, like a CSS file referenced by the HTML it just served, before the client even asks for it).

// HTTP/1.1: request line + headers, sent as plain text, once per request GET /style.css HTTP/1.1 Host: example.com Cookie: session=abc123; theme=dark; lang=en-US // resent on EVERY request User-Agent: Mozilla/5.0 ... // resent on EVERY request // HTTP/2: headers pass through HPACK compression -- repeated header // fields across requests on the same connection are referenced from a // shared dynamic table instead of being retransmitted as literal text
Why server push mostly faded: server push sounded great in theory — why make the client wait to even ask for the CSS file it obviously needs? — but in practice it often pushed resources the client already had cached, wasting bandwidth, and was hard for servers to get right. Most major browsers deprecated support for it; the far more common modern approach is the server hinting resources via a <link rel="preload"> tag or a 103 Early Hints response, letting the client decide whether to actually fetch.
Interview-ready definition: HTTP/2 multiplexes many independent request/response streams over a single TCP connection, allowing frames from different streams to interleave and each stream to complete as soon as its data is ready, eliminating connection-level head-of-line blocking. HPACK header compression avoids retransmitting repeated header fields (cookies, user-agent) as literal text on every request. Server push let a server proactively send resources before the client requested them, but has been widely deprecated in practice due to cache-awareness problems and is being replaced by client-driven hints like preload and Early Hints.

Interview-ready definition: under identical request timing, an HTTP/1.1 connection's total time-to-last-response is bounded by the SUM of requests queued ahead of the slowest one that must go first in order, while HTTP/2's multiplexed connection lets each stream finish independently — the fast requests finish quickly regardless of the slow one's position, and only the slow request itself determines when its own stream completes.
04 — Real trade-offs, not just "HTTP/2 is strictly better"

When the difference actually matters — and when it doesn't

Start here, before the table. A protocol upgrade doesn't magically fix everything — it removes ONE specific bottleneck. If your app was never bottlenecked on connection-level HOL blocking in the first place (say, it makes exactly one request per page load), switching protocols buys you very little. The skill worth having in an interview isn't "HTTP/2 good, HTTP/1.1 bad" — it's recognizing which workloads actually hit the bottleneck each protocol addresses.

Where HTTP/1.1's limits genuinely bite

Pages that fire off many small, independent requests concurrently (a dashboard loading a dozen widgets, a page with many small images/icons/API calls) — connection-level queuing and the overhead of opening multiple parallel connections both add real, measurable latency.

Where it barely matters

A simple server-rendered page with one HTML request and a handful of cacheable static assets already sitting in the browser cache, or a backend service that makes one request at a time to another single backend — there's no queue of concurrent requests for HOL blocking to affect in the first place.

ScenarioDoes the HTTP/1.1 → HTTP/2 switch help?
Modern web app, dozens of concurrent API/asset requests per pageYes, often substantially — this is the textbook case multiplexing was built for
Single large file download (one long request)Barely — there's nothing else queued behind it to unblock
Server-to-server call, one request at a time, sequential by designNo — no concurrent queue exists for HOL blocking to affect
Poor network conditions with packet lossCan actually get WORSE — see the TCP-level caveat below
The caveat worth knowing for an interview: HTTP/2 solves HOL blocking at the HTTP layer, but it still runs over a single TCP connection underneath, and TCP itself guarantees in-order byte delivery — so if ONE packet is lost, TCP holds up delivery of every subsequent byte on that connection until the lost packet is retransmitted, effectively re-introducing head-of-line blocking at the TRANSPORT layer, something HTTP/2 cannot see or fix. This is precisely the motivation behind HTTP/3, which replaces TCP with QUIC (built on UDP) so that a lost packet only stalls the one stream it belonged to, not the entire connection.
Interview-ready definition: HTTP/2's multiplexing benefit is proportional to how many genuinely concurrent, independent requests an application actually issues over one connection — workloads with little or no request concurrency see little benefit, and on lossy networks, HTTP/2's reliance on a single TCP connection can reintroduce head-of-line blocking at the transport layer (fixed only by HTTP/3's QUIC-based transport, which multiplexes independently at the packet level too).

Problem 1 · Predicting HTTP/1.1 completion order

Four requests are sent, in order, on one HTTP/1.1 connection: A (0.2s), B (2s), C (0.1s), D (0.3s). In what order do their responses actually complete, and why?

Show solution
They complete in the exact order they were SENT: A, then B, then C, then D -- regardless of each one's individual duration. Even though C is the fastest request of all (0.1s), it cannot even START until B has fully finished, because a single HTTP/1.1 connection processes requests strictly in order. C's actual wall-clock completion time is roughly 0.2 + 2 + 0.1 = 2.3s from the start, not 0.1s -- its own speed is irrelevant to when it finishes; only its position in the queue and the requests ahead of it matter.
Problem 2 · Same requests over HTTP/2

Using the same 4 requests from Problem 1 (A=0.2s, B=2s, C=0.1s, D=0.3s), but now multiplexed as 4 streams on one HTTP/2 connection, what order do they complete in?

Show solution
C, then A, then D, then B -- each stream completes based on its OWN duration, independent of send order or the other streams' progress. C (0.1s) finishes first even though it's the fewest-priority-looking request in the batch and was sent third, because nothing forces it to wait behind B. This is the concrete, measurable benefit of multiplexing: total time-to-last-byte is bounded by the slowest individual request (2s for B), not by the sum of everything queued ahead of the fastest one.
Problem 3 · Why more parallel connections isn't the real fix

A team "fixes" HTTP/1.1 head-of-line blocking by opening 12 parallel connections to the same origin instead of the typical 6. What problems does this create, and why is HTTP/2 multiplexing a fundamentally different kind of fix rather than just "more of the same trick"?

Show solution
Opening more parallel connections is a workaround, not a real fix, and it has real costs: each additional TCP connection requires its own handshake (and, over HTTPS, its own TLS handshake), consuming more client and server resources, more memory for connection state, and more competition for limited bandwidth via TCP's per-connection congestion control -- more connections doesn't mean more effective throughput past a point, and many servers/browsers cap how many connections per origin they'll allow specifically because of this overhead. It also doesn't eliminate HOL blocking, it just spreads it across more, smaller queues -- a slow request on any ONE of those 12 connections still blocks everything else scheduled onto that specific connection. HTTP/2 multiplexing is fundamentally different because it solves the problem WITHOUT adding connections at all -- one single connection, one TCP handshake, one TLS handshake, and streams share that one pipe with no inherent ordering constraint between them. It removes the need for the workaround entirely rather than scaling the workaround up.
Problem 4 · Recognizing a workload where it doesn't matter

A backend microservice calls exactly one downstream API, waits for the full response, then calls a second downstream API using the response from the first. Would migrating this call chain from HTTP/1.1 to HTTP/2 meaningfully reduce its total latency? Explain.

Show solution
No, not meaningfully. This call chain is inherently SEQUENTIAL by design -- the second call depends on the result of the first, so there is no concurrency for multiplexing to exploit even if it were available. HOL blocking specifically hurts workloads that COULD be concurrent but get serialized anyway by the connection; here, the requests couldn't run concurrently regardless of protocol, since call 2 needs call 1's output. HTTP/2 might still offer small, secondary benefits (marginally cheaper connection reuse, header compression if many such calls share a connection), but the core latency bottleneck -- two sequential round trips that must happen one after another -- is unaffected by the protocol choice.
Problem 5 · The transport-layer caveat

A mobile app over a flaky cellular connection is migrated from HTTP/1.1 (6 parallel connections) to HTTP/2 (1 multiplexed connection), expecting a straightforward improvement. Under what condition could this migration actually make perceived performance WORSE, and why?

Show solution
If the cellular connection experiences meaningful packet loss, the migration can make things worse. HTTP/2 concentrates ALL traffic onto a SINGLE TCP connection, and TCP guarantees in-order byte delivery -- so a single lost packet stalls delivery of every stream multiplexed on that one connection until the lost packet is retransmitted and TCP's ordering requirement is satisfied, even though the lost packet may have belonged to just one of many streams. This is head-of-line blocking reappearing at the TRANSPORT layer, invisible to and unfixable by HTTP/2 itself. With HTTP/1.1's 6 separate connections, a lost packet on ONE of those connections only stalls the requests riding that particular connection -- the other 5 connections are unaffected, since each has its own independent TCP state. Under lossy conditions, that isolation can end up outperforming HTTP/2's single shared connection. This exact problem is what motivated HTTP/3, which runs over QUIC (UDP-based) instead of TCP, so that packet loss on one stream no longer blocks the others sharing the same connection.
