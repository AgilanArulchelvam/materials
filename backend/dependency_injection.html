A dependency is resolved once per request, no matter how many times it's asked for.

This lab traces exactly how a dependency chain resolves, in what order, and why a dependency used by two different parts of the same request is only ever computed once.

01 — What Depends() actually does

Depends() mechanics

Start here, before any code. Think of a restaurant kitchen ticket that says "needs: chopped onions." The cook doesn't personally grow, harvest, and chop the onions from scratch every single time — there's a prep station upstream whose entire job is producing "chopped onions," and the cook just declares that dependency and receives the finished result. If two different dishes on the same ticket both need chopped onions, the prep station doesn't chop two separate batches — it made one batch for this ticket, and both dishes draw from it.

A FastAPI dependency is just a regular function (often called a "provider") that FastAPI calls FOR you before your route runs, then passes its return value into your route as an argument. You declare this by giving a route parameter a default value of Depends(some_function). Crucially, dependencies can themselves depend on OTHER dependencies — Depends() chains arbitrarily deep, and FastAPI resolves the whole tree automatically.

from fastapi import Depends, FastAPI app = FastAPI() def get_db(): db = DBSession() try: yield db # hands the session to the route finally: db.close() # runs AFTER the response is sent def get_current_user(db = Depends(get_db), token: str = ""): # get_current_user itself DEPENDS on get_db -- a dependency chain return db.lookup_user_by_token(token) @app.get("/profile") async def read_profile(user = Depends(get_current_user), db = Depends(get_db)): # this route asks for get_current_user AND get_db directly. # get_current_user ALSO needs get_db internally. # FastAPI resolves get_db only ONCE for this whole request -- see next section. return {"user": user.name}
Interview-ready definition: Depends() declares that a route (or another dependency) requires the return value of a given callable, resolved by FastAPI before the dependent function executes. Dependencies can be plain functions (return a value directly) or generator functions (using yield, splitting into setup code before the yield and teardown code after — teardown runs once the response has been generated). FastAPI builds and resolves the full dependency graph for a request automatically, including dependencies-of-dependencies, without the route needing any knowledge of how a dependency is internally constructed.
02 — Order matters, and repetition doesn't cost anything

Resolution order and per-request caching

Start here, before the demo. Back to the kitchen: if "plated dessert" needs "baked cake," and "baked cake" needs "mixed batter," the kitchen obviously can't bake before mixing, or plate before baking — dependencies must be resolved from the deepest, most upstream one outward, working toward whatever actually asked for them. And if the SAME prep item is needed by two different steps on one ticket, a well-run kitchen makes it once and shares it — it does not duplicate the work for each consumer.

FastAPI works the same way: for a single incoming request, it resolves dependencies depth-first — a dependency's own dependencies are resolved before the dependency itself runs — and it caches the result of each unique dependency callable for the lifetime of that one request. If get_db is required both directly by a route AND indirectly through get_current_user, FastAPI calls get_db exactly once and reuses that same return value everywhere it's needed in that request — this is the single most common point of confusion for people new to FastAPI's DI system.

The core rule of thumb: within a single request, each unique dependency callable is resolved AT MOST ONCE, no matter how many routes or other dependencies ask for it. This is what makes it safe to have both a route and several nested dependencies all declare Depends(get_db) — you get one shared database session for the whole request, not one per declaration, which matters enormously for correctness (all reads/writes in that request see a consistent session) and performance.
03 — What per-request caching is actually for

Sharing a DB session or config object via DI

Start here, before any code. Imagine if every function that touched a shopping cart got its own SEPARATE, disconnected copy of the cart — one function adds an item, but the next function's copy never sees it. That's obviously broken; you need everyone touching "this request's cart" to be looking at the SAME cart. A per-request-cached dependency is exactly how FastAPI guarantees that: every part of handling one request that asks for get_db gets the identical session object, so a row inserted by one dependency is visible to a route handler that runs afterward in the same request.

Database session

One Session per request, shared across every dependency and the route handler, then closed (and often committed/rolled-back) automatically after the response is built — via a yield-based dependency's teardown code.

Config / settings object

A Settings object (env vars, API keys, feature flags) is often built ONCE at app startup and reused across every request via a cached dependency — the same underlying pattern, applied to app-lifetime state instead of per-request state.

from functools import lru_cache class Settings(BaseModel): database_url: str debug: bool = False @lru_cache # cached across the WHOLE APP lifetime, not just one request def get_settings() -> Settings: return Settings(database_url=os.environ["DATABASE_URL"]) @app.get("/health") async def health(settings: Settings = Depends(get_settings)): return {"debug": settings.debug}
A subtle distinction: FastAPI's built-in dependency caching is PER-REQUEST by default — it does not persist across different requests. @lru_cache above is a separate, deliberate choice to cache get_settings's result across the entire application's lifetime, appropriate because config genuinely doesn't change between requests. Using @lru_cache on something like get_db would be a serious bug — it would hand out the SAME database session to every request forever, defeating per-request isolation entirely.
04 — Swapping real dependencies for fakes

Overriding dependencies for testing

Start here, before any code. A flight simulator doesn't fly a real plane — it swaps out the real engines, real weather, and real air traffic control for controlled, predictable stand-ins, while the pilot's controls and training experience stay identical. Testing a FastAPI app works the same way: you don't want a test hitting a real production database or calling a real external API — you want to swap those dependencies for fast, predictable fakes, while the route code under test doesn't change at all.

Because dependencies are just callables referenced by Depends(), FastAPI's test client lets you replace any dependency function with a different one via app.dependency_overrides — a dictionary mapping the original callable to a replacement, active for the lifetime of the override (commonly the whole test session).

from fastapi.testclient import TestClient def override_get_db(): db = FakeInMemoryDB() # no real database connection at all try: yield db finally: pass app.dependency_overrides[get_db] = override_get_db # swap it in client = TestClient(app) response = client.get("/profile") # uses FakeInMemoryDB, never touches real DB # cleanup after the test: app.dependency_overrides.clear()
Interview-ready definition: app.dependency_overrides is a dictionary FastAPI checks before resolving any dependency — if the original dependency callable is a key in this dictionary, FastAPI calls the override callable instead, anywhere in the dependency graph that original would have been used. This lets tests substitute fakes/mocks (an in-memory database, a stubbed authentication check) for real infrastructure without modifying a single line of route or dependency code, because the route only ever declared a dependency on "get_db," not on any specific implementation of it.

Problem 1 · Caching within one request

A route depends on both get_current_user and get_db directly, and get_current_user itself depends on get_db. How many times does get_db actually execute for one incoming request, and why?

Show solution
Exactly once. FastAPI caches the result of each unique dependency callable for the duration of a single request -- the first time get_db is needed (whichever consumer asks for it first in resolution order), FastAPI calls it and stores the result. Every subsequent place in that same request's dependency graph that also declares Depends(get_db) receives the ALREADY- COMPUTED result rather than triggering a second call. This is deliberate: it's what guarantees the route handler and get_current_user share the exact same database session/connection for that request.
Problem 2 · Resolution order

Given the chain route → get_current_user → get_db, in what order do these three actually execute, and why can't it be any other order?

Show solution
get_db executes first, then get_current_user, then the route handler itself. This is forced by data dependency: get_current_user's own code needs the database session as an argument to do its job (looking up a user by token), so get_db MUST have already produced a value before get_current_user can even be called. Likewise the route handler needs get_current_user's return value as an argument, so get_current_user must finish first. FastAPI resolves dependency trees depth-first, from the most upstream (fewest unmet dependencies) outward to the thing that ultimately requested them.
Problem 3 · lru_cache vs per-request caching

Why would putting @lru_cache directly on get_db (instead of just relying on FastAPI's normal per-request dependency caching) be a serious bug?

Show solution
@lru_cache caches across the ENTIRE application's lifetime, not per request -- the first request to call get_db would create one database session, and @lru_cache would then hand that exact same session object to EVERY future request forever, since the function's arguments (none) never change. This breaks per-request isolation completely: concurrent requests would all share one session (a serious correctness and thread-safety problem for most database drivers), and the yield-based teardown (closing the session) would only ever run once, if at all, rather than once per request as intended. FastAPI's built-in dependency caching is deliberately scoped to a single request specifically to avoid this failure mode; @lru_cache is only appropriate for things that are genuinely safe to share for the whole app's lifetime, like static configuration.
Problem 4 · Testing without touching the real database

Explain, mechanically, how app.dependency_overrides lets a test avoid connecting to a real database, without changing any route code.

Show solution
Route code never references a specific database implementation directly -- it only declares Depends(get_db), a reference to a callable. FastAPI resolves that callable at request time by looking it up (checking dependency_overrides first). When a test sets app.dependency_overrides[get_db] = override_get_db, every future request made through that app (including ones nested many dependencies deep) will have FastAPI substitute override_get_db wherever get_db would have been called, without the route or any intermediate dependency knowing or caring that a substitution happened. Since override_get_db can yield a fake in-memory object instead of a real connection, the real database is never touched, and no route source code needed to change.
Problem 5 · Generator dependency teardown timing

A get_db dependency uses `yield` and closes the session in a finally block after the yield. If the route handler raises an unhandled exception, does the finally block still run? What does this guarantee for resource cleanup?

Show solution
Yes, the finally block still runs. FastAPI drives yield-based dependencies using the same exception-propagation semantics as a normal Python try/finally -- if an exception occurs anywhere downstream of the yield (inside the route handler, or in another dependency that ran after this one), that exception propagates back through the generator at the yield point, and Python guarantees the finally block executes regardless of whether the code after yield succeeded or raised. This is precisely why yield-based dependencies are the standard way to manage resources like database sessions or file handles in FastAPI: cleanup (closing the connection, releasing a lock) is guaranteed to happen exactly once per request, success or failure, without every route needing its own manual try/finally.
