BACKEND & APIS LAB · JWT & OAUTH2

A JWT isn't encrypted — anyone can read the payload. Its signature only proves it wasn't tampered with.

JSON Web Tokens and OAuth2 solve two different but related problems: JWT is a compact, self-contained way to represent claims about a user, verifiably signed; OAuth2's password flow is the actual request/response choreography for exchanging credentials for a token. This lab decodes a real-looking JWT part by part, walks the OAuth2 password flow request by request, and covers why refresh tokens and safe storage aren't just extra complexity for its own sake.

01 — Three parts, and only one of them is a secret

JWT structure: header, payload, signature

Start here, before any code. Think of a wax-sealed letter with the text written in plain, ordinary handwriting — anyone who intercepts the letter can read every word of it without any special key. What the wax seal actually proves is narrower: that the letter came from whoever holds the matching stamp, and that nobody altered the text after it was sealed. A JWT is exactly that kind of letter: its contents are NOT secret or encrypted (just base64url-encoded, which is trivially reversible by anyone), and its signature exists purely to prove authenticity and integrity — not confidentiality.

A JWT is three base64url-encoded segments joined by dots: a header (declares the token type and signing algorithm), a payload (the actual claims — user ID, roles, expiry — as a JSON object), and a signature (a cryptographic signature over the header and payload, computed with a secret or private key the server holds).

The mistake this trips people into: because a JWT LOOKS like an opaque random string, it's easy to assume it's encrypted and safe to stuff sensitive data into. It is not — anyone holding the token (a browser extension, a proxy log, a curious user with devtools open) can base64url-DEcode the payload instantly and read every claim in plain text. Never put secrets (passwords, raw API keys, sensitive PII) directly in a JWT payload; put only what's safe for the token holder themselves to see.
Interview-ready definition: a JWT (JSON Web Token) is a compact, URL-safe token format consisting of three base64url-encoded, dot-separated segments — a header specifying the algorithm and token type, a payload containing claims (arbitrary JSON data about the subject, plus standard claims like expiry), and a signature computed over the header and payload using a server-held key. The signature allows any party with the corresponding verification key to confirm the token's contents haven't been altered since issuance (integrity and authenticity), but the header and payload themselves are NOT encrypted and are trivially readable by anyone holding the token.
02 — The actual sequence of requests

OAuth2 password flow, conceptually

Start here, before any diagram. Think of checking into a hotel: you show ID and pay at the front desk ONCE, and in exchange you get a keycard. For the rest of your stay, you show the KEYCARD to get into your room — nobody re-checks your ID and payment on every single door you open. The keycard is a stand-in credential, scoped (it only opens your room, not every room), and it can be deactivated or expire without needing to redo the entire check-in process.

OAuth2's password flow (technically the "Resource Owner Password Credentials" grant) is that check-in process: the client collects the user's username and password directly, sends them ONCE to an authorization/token endpoint, and receives back an access token to use on every subsequent request instead of resending credentials each time.

Why this flow is increasingly discouraged: the password flow requires the CLIENT itself to directly handle the user's raw username and password, which only makes sense when the client is fully trusted (a first-party app). It's a poor fit for third-party integrations, which is why the authorization code flow (redirecting to a login page the third-party app never sees) is preferred in most modern OAuth2 usage — the password flow is still worth understanding conceptually because it's the simplest illustration of "trade credentials for a token, then use the token."
Interview-ready definition: the OAuth2 password grant is a flow where a client submits a resource owner's username and password directly to an authorization server's token endpoint, receives back an access token (and often a refresh token), and then authenticates all subsequent API requests by presenting that token (typically via an Authorization: Bearer <token> header) instead of resending credentials — decoupling "proving who you are" (done once) from "proving you're still authorized" (done on every request, cheaply, via the token).
03 — Tokens don't live forever, and where they live matters

Token expiry, refresh tokens, and safe storage

Start here, before any code. A hotel keycard that worked forever, even after checkout, would be a real security problem — anyone who ever held one could keep using it indefinitely. That's why keycards (and access tokens) are time-limited. But making guests re-do the entire check-in desk process every hour would be miserable — so hotels sometimes offer an easy re-issue process for returning guests without repeating the full ID check. That's what a refresh token is for.

An access token is deliberately short-lived (minutes to a couple hours) — if it leaks, the exposure window is small. A refresh token is longer-lived and used ONLY to obtain a new access token from the auth server, without re-sending the username and password again — trading "how often do I need real credentials" against "how long is a leaked access token dangerous for."

// Access token: short-lived, sent on every API request { "access_token": "eyJhbGciOi...", "expires_in": 900 } // 15 minutes // When it expires, the client uses the refresh token to get a new one -- // no password re-entry needed: POST /token { "grant_type": "refresh_token", "refresh_token": "def502..." } // Response: a brand new access_token (and often a rotated refresh_token) { "access_token": "eyJhbGciOi_NEW...", "expires_in": 900 }

Storing a JWT in localStorage

JavaScript on the page can read localStorage directly. If the site has ANY cross-site scripting (XSS) vulnerability — a single unsanitized field rendering attacker-controlled script — that malicious script can read the token straight out of localStorage and exfiltrate it, no special privilege needed.

Storing a token in an httpOnly cookie

An httpOnly cookie is deliberately INVISIBLE to JavaScript — document.cookie simply cannot read it. Even a successful XSS injection can't directly steal the token this way, though httpOnly cookies bring their own concern (CSRF) that needs separate mitigation (e.g. SameSite cookie attributes, CSRF tokens).

Why this matters in practice: "where do I store the token" is not a minor implementation detail — it's a real security boundary decision. XSS vulnerabilities are common enough in real applications that "assume XSS will eventually happen somewhere" is a reasonable defensive posture, which is why httpOnly cookies are generally recommended over localStorage for storing tokens in browser-based apps, despite localStorage being simpler to use from ordinary JavaScript.
Interview-ready definition: access tokens are intentionally short-lived to limit the damage window if one is stolen, while refresh tokens are longer-lived credentials used solely to obtain new access tokens without re-authenticating with a password — allowing a system to keep sessions convenient for users while keeping the actively-used bearer token's exposure window small. Storing tokens in browser localStorage exposes them to theft via any XSS vulnerability (since page JavaScript can read localStorage), while httpOnly cookies are inaccessible to JavaScript entirely, making them the generally safer default for browser-based token storage, at the cost of needing separate CSRF protections.

Problem 1 · What the signature does and doesn't prove

An attacker intercepts a valid JWT and, without the server's signing secret, changes the payload's "role" claim from "user" to "admin," re-encodes it, and sends the modified token to the server. What happens, and why?

Show solution
The server rejects the token. The signature was computed over the ORIGINAL header and payload using the server's secret key -- changing even one character of the payload produces a completely different expected signature. When the server re-verifies the token, it recomputes the signature over the (now-modified) header and payload and compares it against the signature the attacker sent, which still reflects the OLD, unmodified payload. These won't match, so verification fails and the server rejects the token as tampered. This is exactly what the signature is FOR -- proving the payload hasn't changed since a party holding the secret signed it -- even though the payload itself was always readable in plain text.
Problem 2 · Confidentiality vs integrity

A developer stores a user's full home address directly in a JWT payload, reasoning "it's fine, the token is signed." Explain what's wrong with this reasoning.

Show solution
Signing provides INTEGRITY (proof the data wasn't tampered with) and authenticity (proof it came from whoever holds the signing key) -- it does NOT provide CONFIDENTIALITY. The payload is only base64url-encoded, which is a reversible encoding scheme, not encryption; anyone who obtains the token (through a browser extension, a server log, a network proxy, or simply opening devtools) can decode the payload and read the home address in plain text instantly. "Signed" and "encrypted" are different properties, and conflating them is a common and genuinely dangerous mistake -- sensitive data needs actual encryption (or simply shouldn't be placed in a JWT payload at all), not just a signature.
Problem 3 · Tracing the password flow

In the OAuth2 password flow, after the client receives an access token, does it need to send the username/password again on subsequent API requests? What does it send instead, and why is this a meaningful improvement?

Show solution
No, the client does not resend the username/password on subsequent requests -- it sends the access token instead, typically as an Authorization: Bearer header. This is a meaningful improvement for several reasons: the raw password is transmitted only ONCE (at initial login), minimizing how often the most sensitive credential travels over the network at all; verifying a token (checking a signature and an expiry timestamp) is far cheaper for the server than re-validating a password against a user store (which often involves an expensive hash comparison); and if a token needs to be revoked or expires, that doesn't require changing the user's actual password.
Problem 4 · Why refresh tokens exist at all

Why not just issue access tokens with a very long expiry (say, 30 days) and skip refresh tokens entirely?

Show solution
A long-lived access token is dangerous specifically BECAUSE it's the token sent on every single API request -- it's exposed far more often (every request, potentially logged by proxies, visible in network traffic inspection tools) than a refresh token, which is only sent occasionally (when actually refreshing). If a long-lived access token leaks, an attacker has a full 30 days of access with no further action needed. The refresh token pattern splits this risk: the frequently-exposed access token has a short leak-exposure window (minutes to hours), while the rarely-exposed refresh token can safely be longer-lived, since it's used far less often and can be more tightly protected (e.g. stored only in a secure httpOnly cookie, checked against a revocation list server-side). This gets you both convenience (users don't re-login constantly) and a much smaller blast radius if the token that's actually in constant circulation gets stolen.
Problem 5 · localStorage vs httpOnly cookie under XSS

A site has a stored XSS vulnerability (an attacker can get arbitrary JavaScript to run on other users' pages). Compare what the attacker can do if the access token is stored in localStorage versus in an httpOnly cookie.

Show solution
If stored in localStorage: the attacker's injected JavaScript can directly call localStorage.getItem(...) and read the token, then send it to an attacker-controlled server -- full token theft, trivially, the moment the XSS payload executes on a victim's page. If stored in an httpOnly cookie: the injected JavaScript CANNOT read the cookie's value at all -- document.cookie simply omits httpOnly cookies by browser design. The attacker's script could still potentially make requests that ride along with the cookie automatically (since browsers attach cookies to same-origin requests without JS needing to touch them), which is a CSRF-shaped risk, not direct token theft -- but the attacker cannot exfiltrate the actual token value to use it independently elsewhere (e.g. from their own machine, outside the victim's browser), which is the specific threat direct localStorage access enables. This is exactly why httpOnly cookies are considered meaningfully safer against XSS specifically, while still needing separate CSRF defenses.
