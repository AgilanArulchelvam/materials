01 — Cold recall, no notes

MCP gateway design, re-derived

Do this before opening anything below. Set a timer for 5-8 minutes. On paper or out loud, answer every bullet below as if you were in an actual interview, with nobody to check your work until you're done.

Prompt — attempt cold first

Without looking anything up, sketch an MCP gateway design:

  • What does the gateway's routing table actually map, and why does tools/list need special handling that tools/call doesn't?
  • Why does centralizing auth at the gateway reduce security surface area, specifically — not just "make it tidier"?
  • What has to be true about a gateway instance before you can safely run several of them behind a load balancer?
  • Walk through what breaks if a permission revocation only updates one gateway instance's local memory.
Reveal the answer (only after you've actually attempted it)
ROUTING TABLE AND tools/list: the routing table maps tool (or resource/ prompt) names to the backend MCP server address that actually implements each one -- a client sends every request to ONE gateway address, and the gateway forwards tools/call requests to whichever specific backend owns the named tool. tools/list needs special handling because it's a DISCOVERY query, not a routing decision -- the gateway has to MERGE every backend's individual tool catalog into one combined list so the client sees all available tools as if from a single server. WHY CENTRALIZING AUTH REDUCES SECURITY SURFACE AREA: with per-server auth, N independently-implemented checks means N independent chances for a bug. Centralizing means exactly ONE place enforces authentication and per-client permission scope, before any request reaches a backend -- backend servers can trust that anything reaching them was already authorized. The surface area shrinks from N implementations to one. WHAT MUST BE TRUE BEFORE SCALING HORIZONTALLY: gateway instances must be STATELESS with respect to routing tables and per-client permissions -- that data lives in a shared external store every instance reads from, not duplicated per-instance memory. WHAT BREAKS ON A STALE REVOCATION: a compromised client's next request might land on an instance that hasn't picked up the revocation, and that instance incorrectly continues allowing access that was supposed to be cut off immediately -- a security-relevant inconsistency, not a cosmetic one.
What "re-derive cold" is testing: whether you can explain WHY centralizing auth actually reduces risk, and whether "must be stateless" connects to a concrete consequence (a stale revocation) rather than a buzzword.
02 — Cold recall, no notes

Async tool job queue design, re-derived

Do this before opening anything below. Same rules: timer, full attempt, no peeking until you're done.

Prompt — attempt cold first

Without looking anything up, sketch an async tool job queue design:

  • Walk through the enqueue → worker → result-store flow. What exactly makes the caller's path non-blocking?
  • Trace the exact backoff delays across several failed attempts, and explain what happens once MAX_ATTEMPTS is hit.
  • Name the two distinct problems a dead-letter queue solves.
  • Name at least two backpressure strategies, and describe a scenario where applying the wrong one makes things worse.
Reveal the answer (only after you've actually attempted it)
ENQUEUE -> WORKER -> RESULT-STORE FLOW: a slow tool call is represented as a job (tool name, arguments, job ID) written to a queue rather than awaited directly. The caller returns IMMEDIATELY with a job ID once enqueued. A separate worker dequeues jobs on its own schedule, executes them, and writes results to a store the caller reads from afterward. What makes it non-blocking: the enqueue write is fast and returns right away -- the SLOW work happens entirely on the worker's own timeline. BACKOFF DELAYS AND MAX_ATTEMPTS: delay = BASE_DELAY_SECONDS * (2 ** (attempts - 1)), BASE_DELAY_SECONDS=2: 2s, 4s, 8s across three failed attempts, doubling each time. At MAX_ATTEMPTS (commonly 4), the job stops retrying and moves to the dead-letter queue instead of a 5th attempt. TWO PROBLEMS A DLQ SOLVES: first, stops a permanently-failing job from consuming worker retry capacity forever. Second, avoids silently dropping the job -- its full payload and failure history are preserved for later human inspection and possible reprocessing. BACKPRESSURE STRATEGIES AND THE WRONG-STRATEGY TRAP: (1) reject new enqueues past a queue-depth threshold; (2) throttle the producer; (3) scale workers horizontally. The trap: scaling workers does NOT help when the bottleneck is an EXTERNAL, FIXED constraint (a third-party API's hard rate limit) -- more workers just means more requests contending for the same fixed-rate resource, making things worse, not better.
What "re-derive cold" is testing: the exact exponential-backoff arithmetic, BOTH problems a DLQ solves, and correctly identifying a scenario where "just add more workers" is the wrong answer.
03 — This week's new material: weaving security into the SAME architecture

Securing the system end to end

Start here, before the diagram. Sections 1 and 2 each describe a component working correctly under NORMAL conditions. This section asks a different question entirely: assuming a client's request might be adversarial, or an agent might be manipulated via injected content it processes along the way, where in THIS SAME gateway-plus-queue architecture does each of this week's security mechanisms actually have to sit? Walking the request's journey with security explicitly in view: the gateway (section 1) is where authentication and coarse authorization already live — that doesn't change this week. What's NEW is that the content the routed agent subsequently reads (a webpage, a tool's own output) might carry a prompt_injection_risks.html-style payload trying to redirect the agent's next action — the gateway has no visibility into this at all, because it happens entirely downstream of routing, inside the agent's own reasoning over content it fetched.

The next layer is where this week's other two labs earn their place, and they earn it specifically because the injection mitigations from prompt_injection_risks.html (delimiting, data-only instructions) are NOT guaranteed to hold — the honest conclusion that lab reached. So even if an agent IS successfully manipulated into generating a harmful tool call, permission_scoping.html's scope check and tool_call_sandboxing.html's resource boundary both still have to run before that call ever executes — one asking "is this agent even authorized to attempt this OPERATION," the other asking "can this call physically REACH what it's asking for." Both checks are mechanical and don't need to know an injection happened.

Finally, the job queue (section 2) doesn't get a pass just because it's downstream and async — a job enqueued from a manipulated agent call still carries whatever arguments the agent generated, so the scope and sandbox checks need to have ALREADY happened before enqueueing (or be re-verified by the worker at execution time, not merely trusted from enqueue time onward) — async execution doesn't shrink the attack surface, it just moves WHEN the check needs to happen relative to when the user sees a result.

A trap worth naming directly: it's tempting to think "we added prompt injection mitigations, so the system is secure." Section 3's own table shows why that's incomplete: injection mitigations reduce the FREQUENCY of a successful manipulation, but permission scoping and sandboxing are what bound the DAMAGE when a mitigation is bypassed anyway — dropping either layer because "the injection defenses should have caught it" reintroduces exactly the single-point-of-failure risk this month's security labs, taken together, were built to avoid.
Interview-ready definition: securing this system end to end means recognizing that no single layer covers every failure mode: gateway authentication and routing (Week 1) establish who is allowed to reach the system at all; prompt injection mitigations (this week) reduce, but do not eliminate, the chance an agent is manipulated by untrusted content it processes downstream of the gateway; permission scoping and tool call sandboxing (this week) bound the damage even when a manipulation succeeds, by constraining respectively which operations and which resources a tool call can reach, independent of why the call was generated; and the async job queue (Week 2) must preserve these guarantees across the enqueue/execute boundary rather than treating async execution as an implicit trust boundary of its own. Real security here is the composition of all of these layers, each covering a gap the others don't.

Problem 1 · Deciding where the scope check belongs relative to enqueueing

Using section 3's reasoning, should permission_scoping.html's authorize_tool_call check run BEFORE a job is enqueued, AT worker execution time, or both? Justify using the async job queue's own timing.

Show solution
Both, and they check different things. Checking BEFORE enqueue is necessary because there's no reason to pay the queue's storage and worker-scheduling cost for a request that was never going to be authorized anyway -- failing fast, before any resources are committed, mirrors the same "reject invalid input as early as possible" principle json_schema_tool_specs.html applied to malformed tool calls. But checking ONLY before enqueue and then blindly trusting the job at execution time has a real gap: async_tool_job_queue_design.html's own retry/backoff logic means a job can sit in the queue or be retried across a MEANINGFUL time window (seconds to minutes, per section 2's backoff arithmetic) -- if the agent's grant could change in that window (a revocation, exactly like section 1's stale-revocation scenario, just applied to a queued job instead of a live gateway request), executing the job later without re-checking would honor a permission that may no longer be valid by execution time. Re-checking at worker execution time closes this gap, at the cost of a small amount of redundant work for the common case where nothing changed. This mirrors section 1's own statelessness argument extended one hop further: just as gateway instances can't rely on a permission decision cached indefinitely in local memory, a queued job can't rely on an authorization decision made once at enqueue time remaining valid forever, either.
Problem 2 · Tracing a specific injected-then-sandboxed failure

An agent is manipulated (via injected content) into generating a call to a correctly-SCOPED tool (it does hold the right operation-level permission) requesting a file path outside its allowed directory. Using this lab's layered table, which specific layer stops this, and why do the earlier layers (gateway auth, permission scoping) not catch it?

Show solution
Sandboxing (tool_call_sandboxing.html) is the layer that stops this, and specifically NOT the earlier ones, because each earlier layer is checking a genuinely different question that this scenario doesn't violate. Gateway auth already passed -- this is a legitimately authenticated, authorized client's session; the gateway has no visibility into content the agent reads downstream anyway. Permission scoping also passes -- the problem statement specifies the tool call is CORRECTLY scoped, meaning the agent does hold whatever operation-level permission (e.g. a generic "file:read" scope) this call requires; scope checks only ask "is this OPERATION allowed," not "is this specific PATH allowed." Only the sandboxing layer's specific job -- checking the RESOLVED resource (the file path) against an allowlist of directories -- catches this, because it's the only layer asking about the resource itself rather than the client's identity or the operation category. This is precisely section 3's point made concrete: an injected instruction can successfully manipulate the agent into generating a call that is authenticated, authorized at the operation level, and STILL dangerous, because none of the earlier layers were ever designed to catch a resource-level boundary violation -- that's sandboxing's job alone, and it's why dropping any one layer leaves a specific, identifiable gap the others don't cover.
Problem 3 · Evaluating a proposal to only sandbox, skip scoping

A candidate argues "sandboxing already restricts what a tool call can touch, so permission scoping is redundant — just sandbox everything tightly enough." Using permission_scoping.html's Problem 4 reasoning, what's a scenario where sandboxing alone doesn't help?

Show solution
Sandboxing constrains WHICH RESOURCES a call can reach (a filesystem path, a network host) -- it says nothing about which OPERATIONS are permitted on a resource the call IS allowed to reach. Consider a delete_event tool correctly sandboxed to only touch the user's OWN calendar (never someone else's) -- sandboxing is working exactly as designed here, the resource boundary (this user's calendar data) is correctly enforced. But if this agent was only ever supposed to READ events, not delete them, sandboxing provides zero protection against a manipulated agent calling delete_event on the user's OWN, entirely in-bounds calendar -- the delete succeeds, sandboxing never objects, because the resource being touched (this user's own data) was always within the sandbox's allowed boundary. This is exactly permission_scoping.html's core distinction: sandboxing answers "can this call reach that RESOURCE" while scoping answers "is this OPERATION even allowed at all," and a call can be simultaneously in-bounds on the first question and entirely unauthorized on the second. "Sandbox everything tightly enough" cannot substitute for scoping because tightening a sandbox only ever narrows WHICH resources are reachable -- it has no mechanism for restricting WHICH VERBS (read vs write vs delete) are permitted against a resource that's already correctly in-bounds. The two checks are answering genuinely non-overlapping questions, which is why section 3's table lists them as separate rows with separate "does NOT defend against" columns.
Problem 4 · Reasoning about gateway statelessness applied to a security incident

A prompt injection is discovered live, in production, and the fix requires immediately revoking one agent's calendar:delete scope. Using section 1's stale-revocation reasoning, what architectural property does the permission-scope STORE need to have for this revocation to take effect immediately across every gateway instance and every queue worker?

Show solution
The same property section 1 required of gateway instances themselves -- statelessness with respect to policy, backed by a SHARED, externally consistent store every consumer reads from live, rather than each component (gateway instances, AND now also queue workers) caching its own private copy of the agent's granted_scopes with no mechanism to learn about a change. If either gateway instances or workers were reading a locally-cached copy of the permission grant that only refreshes on some slow interval (or never, until restart), the revocation would take effect at wildly inconsistent times across the fleet -- exactly section 1's stale-revocation scenario, now extended to cover not just gateway routing/auth decisions but also every queue worker's authorize_tool_call check at execution time (per Problem 1 above, which already established workers need to re-check scope at execution, not just trust enqueue-time state). The practical requirement: authorize_tool_call's grant lookup needs to read from a shared, low-latency, consistently-updated store (a fast cache backed by a database, invalidated the moment a revocation is written) that BOTH gateway instances and queue workers query against, rather than either component holding its own independently-refreshed copy. This is the same lesson section 1 already taught for gateway routing tables, generalized to now also cover permission grants consumed by a second, independent component (the worker pool) that didn't exist in section 1's original scope.
Problem 5 · Writing your own end-to-end security trace for a new scenario

Using this lab's layered-defense framing, write (in words) a full trace for a DIFFERENT scenario: a legitimate, non-malicious agent request that nonetheless gets denied at the sandboxing layer due to an overly narrow allowlist — distinguishing this from an actual attack being stopped.

Show solution
A reasonable trace: the client authenticates and is routed correctly by the gateway (section 1) -- nothing adversarial here. The agent, with no injection involved at all, generates a completely legitimate tool call (e.g. read_file("/data/reports/q4/summary.pdf")) in direct response to a real user request. The call IS correctly scoped (the agent legitimately holds file:read). But the sandbox's ALLOWED_DIRECTORIES was configured too narrowly during setup (say, only ["/data/reports/q1", "/data/ reports/q2", "/data/reports/q3"] -- someone forgot to add q4 when the new quarter's directory was created), so the resolved path falls outside every allowed directory and tool_call_sandboxing.html's wrapper denies it, exactly as it would deny an actual attack. The key distinction this trace surfaces: sandboxing (and permission scoping) can't tell the DIFFERENCE between "this request is denied because it's a security threat" and "this request is denied because our configuration is stale or too narrow for a legitimate, evolving need" -- both produce the identical {"status": "denied"} result, because the check is purely mechanical (per permission_scoping.html's Problem 3 reasoning about the check having "no idea an injection occurred"). This is precisely why loop_termination_logic.html and permission_scoping.html's own Problem 4 both argued for a graceful, informative denial response fed back to the agent/user rather than a silent hard failure -- a human reviewing "why was this legitimate request denied" needs the SAME structured denial information (which scope or boundary was missing) that a security team investigating an actual attack attempt would need, and distinguishing the two cases is a job for a HUMAN reviewing the denial log, not something the mechanical check itself needs to (or can) do.
