SYSTEMS FUNDAMENTALS LAB · LATENCY, THROUGHPUT & SCALING

Latency is how long one thing takes. Throughput is how much gets done.

They sound like the same idea — "system speed" — but they measure different axes, and pushing one often costs you the other. This lab makes both concrete with a live request pipe, then builds up to why "just scale it" has two very different meanings and three very different reasons to reach for it.

01 — Two different rulers

Definitions of latency and throughput

Latency is the time between when a single request starts and when it finishes — measured in time units (milliseconds, seconds). It answers: "how long did I personally wait?"

Throughput is the number of requests a system completes per unit of time — measured in a rate (requests/second, jobs/minute). It answers: "how much total work got done?"

These are not opposites and not the same thing — a system can have low latency and low throughput (a single very fast checkout lane, nobody else in line), or high latency and high throughput (a slow-but-massively-parallel batch pipeline still finishing thousands of jobs a minute).

Little's Law (a useful anchor): on average, concurrent requests in flight = throughput × latency. If your service handles 200 req/s and each takes 50ms (0.05s), you should expect roughly 200 × 0.05 = 10 requests in flight at any moment. This single formula ties all three quantities together.
02 — The batching tradeoff

Why optimizing one can hurt the other

A common way to boost throughput is batching: instead of processing each request the moment it arrives, wait to collect several, then process them together (fewer round trips, better use of fixed per-batch overhead like a disk write or a network call). This raises throughput — but every individual request now waits for the batch to fill, which raises its latency.

# no batching: handle immediately — low latency, but throughput capped by per-request overhead def handle_one(req): write_to_disk([req]) # fixed overhead paid on EVERY single request # batching: collect N requests, flush together — throughput up, per-request latency up def handle_batch(queue, batch_size=10): if len(queue) >= batch_size: write_to_disk(queue) # overhead paid ONCE for all 10 — but request #1 waited for #2..#10 queue.clear()

04 — Three different reasons to scale

What "scaling" actually solves for

"We need to scale" can mean three genuinely different problems. Naming which one you have changes the right fix entirely.

⚡ Load

▁▂▃▅█

Traffic exceeds what current capacity can handle — requests start queuing or getting dropped. Both scaling directions add capacity to absorb more concurrent load.

🛡 Availability

●  ●  ●

One machine failing shouldn't take the whole system down. This is inherently a horizontal-scaling win — redundant copies mean a failure degrades capacity instead of causing a full outage.

💰 Cost

$ → $$$

Big single machines get disproportionately expensive near the top of their range. Many smaller machines are often cheaper per unit of capacity, and can be added/removed to match demand instead of paying for peak capacity all the time.

Why this framing matters: a vertically-scaled single powerful server can absolutely solve a load problem — but it does nothing for availability (still one point of failure) and often loses on cost at the high end. If the real problem is "one bad deploy or one hardware failure takes us down," more horizontal capacity is the fix, not more vertical.

Practice problems

Work each one out before expanding the solution.

Problem 1 · Definitions check

A video call has 120ms of latency per audio packet, and the service handles 50,000 concurrent calls. Is 50,000 a throughput number, a latency number, or neither? Explain.

Show solution
Neither, strictly speaking. 50,000 concurrent calls is a CONCURRENCY / capacity number (how many are in flight right now), not a rate of completed work over time. Throughput would be something like "packets processed per second across all calls." Concurrency, latency, and throughput are three distinct measurements that Little's Law relates, but they're not interchangeable.
Problem 2 · Little's Law

A service has an average latency of 200ms per request and needs to support 25 requests in flight at any given moment on average. What throughput does that imply?

Show solution
125 requests/second Little's Law: concurrency = throughput × latency 25 = throughput × 0.2s throughput = 25 / 0.2 = 125 req/s
Problem 3 · Spotting the tradeoff

A team increases their database write batch size from 10 to 500 to reduce disk I/O overhead. Throughput improves 4x. What's the most likely cost, and why?

Show solution
Per-request latency for individual writes increases significantly — a write now has to wait for up to 499 other writes to accumulate before the batch flushes (or wait for a timeout). The system does more total work per second, but any single request's "how long did MY write take" number gets worse and more variable, especially under low traffic when the batch fills slowly.
Problem 4 · Vertical vs horizontal, pick one

A single-machine app occasionally has a spike that overwhelms it, and last month a hardware fault took the whole service down for 40 minutes. Which scaling direction addresses BOTH issues, and which addresses only one?

Show solution
Horizontal scaling addresses both: more machines absorb the traffic spike (load) AND mean one hardware fault only removes a fraction of capacity instead of the whole service (availability). Vertical scaling (a bigger single machine) could absorb the spike (load) but does nothing for the hardware-fault outage — it's still one machine, so one fault still takes everything down.
Problem 5 · Cost reasoning

A company runs one very large server sized for their Black-Friday peak traffic, all year round. What's the cost problem here, and how would horizontal scaling change it?

Show solution
They're paying for peak capacity 365 days a year even though peak load only happens for a few days. That's the cost problem: a fixed vertical size can't shrink when demand is low. Horizontal scaling (with autoscaling) lets them run a small number of machines most of the year and add more only during the traffic spike, paying roughly in proportion to actual demand instead of worst-case demand.
Problem 6 · Applying both concepts together

A checkout API currently: single server, no batching, 40ms latency, 25 req/s throughput, and goes down completely about once a month. Propose one change and predict its effect on latency, throughput, availability, and cost — including any tradeoff.

Show solution
One reasonable answer: switch to horizontal scaling with 4 identical servers behind a load balancer. Latency: roughly unchanged per request (~40ms) — each server still handles one request the same way it did before; latency isn't primarily what horizontal scaling improves. Throughput: roughly 4x (up to ~100 req/s), since 4 servers can process requests in parallel. Availability: much improved — losing one server now costs ~25% capacity, not 100% downtime. Cost: goes up, since you're now paying for 4 servers instead of 1 — the tradeoff for the availability and throughput gains. (A follow-up optimization would be autoscaling so you don't pay for all 4 during low traffic.)
