01 — Where we left off

Quick recap: 1NF and 2NF

Before 3NF makes sense, a 30-second refresher on the two rules before it, in the same everyday-then-technical style as the previous lab:

FormEveryday versionTechnical rule
1NFEvery cell holds one thing, not a list crammed into one box.Every column holds a single, atomic value — no repeating groups or comma-packed lists in one field.
2NFIf your ID card is actually two numbers glued together, every fact on file has to depend on BOTH, not just one.Already in 1NF, and every non-key column depends on the entire primary key — not just part of a composite key.

Both of those rules are about a column's relationship to the key. 3NF asks a different question entirely: is there a non-key column that depends on another non-key column, rather than on the key at all?

02 — The last kind of redundancy

Third Normal Form: no transitive dependency

Start here, before any code. Imagine a company directory that lists, for every employee: their name, their department ID, AND their department's manager's name. If Priya manages the Engineering department, her name is copied onto the row of every single engineer. Priya gets a new title? You now have to hunt down and edit every engineer's row, not just one record about the Engineering department itself. The manager's name isn't really a fact about the EMPLOYEE — it's a fact about the DEPARTMENT, riding along on the wrong table.

That's a transitive dependency: employee_id → dept_id → dept_manager. dept_manager doesn't depend on employee_id directly — it depends on dept_id, which itself depends on employee_id. It's a dependency chained through another non-key column instead of anchored directly to the key. Third Normal Form requires a table already be in 2NF, with every non-key column depending on the key, the whole key, and nothing but the key — that last clause is what rules out transitive dependencies specifically.

-- VIOLATES 3NF: dept_manager depends on dept_id, not on id (the actual key) CREATE TABLE employees ( id INTEGER PRIMARY KEY, name TEXT, dept_id INTEGER, dept_manager TEXT -- transitive: id → dept_id → dept_manager ); -- FIXED: split off the transitively-dependent fact into its own table CREATE TABLE employees ( id INTEGER PRIMARY KEY, name TEXT, dept_id INTEGER, FOREIGN KEY (dept_id) REFERENCES departments(id) ); CREATE TABLE departments ( id INTEGER PRIMARY KEY, manager TEXT -- now lives exactly once, where it actually belongs );
WATCH THE ANOMALY, THEN THE FIX
How to spot it fast: ask of every non-key column, "if I know the PRIMARY KEY value, do I directly know this, or do I only know it because I first look up some OTHER non-key column?" If it's the second case, that column belongs on a different table, keyed by whatever it actually depends on.
Interview-ready definition: a relation is in Third Normal Form if it is already in Second Normal Form and contains no transitive functional dependency of a non-key attribute on another non-key attribute — informally, every non-key column must depend on the key, the whole key, and nothing but the key. Violating 3NF causes update anomalies (a single logical fact, like a department's manager, must be edited in many rows to stay consistent) and insertion/deletion anomalies (you can't record a department's manager until it has an employee, and deleting the last employee in a department loses the manager fact entirely).
03 — Breaking the rules on purpose

Denormalization as a deliberate trade-off

Start here, before any code. A fully-normalized filing system is beautiful for accuracy — one true copy of every fact, filed exactly once. But if you need to answer "how many total orders has this customer placed?" a hundred times a second, recomputing that by walking through every order record every single time is slow. Sometimes it's worth keeping a duplicate, pre-computed answer taped to the customer's folder — accepting that it might occasionally go slightly stale — purely for speed.

Denormalization is deliberately reintroducing redundancy that normalization would remove — usually to avoid expensive joins or repeated aggregation on read-heavy paths. It's not "doing normalization wrong"; it's a conscious trade of some write-side complexity (keeping the duplicate in sync) for read-side speed, made only after the normalized design is understood and a real performance need is measured, not guessed at.

-- normalized: order_count must be computed by counting rows every time SELECT COUNT(*) FROM orders WHERE customer_id = 42; -- denormalized: a redundant cached column, updated whenever an order is placed CREATE TABLE customers ( id INTEGER PRIMARY KEY, name TEXT, order_count INTEGER -- redundant: derivable from orders, kept here for speed ); -- now reading it is instant, but every INSERT into orders must also -- remember to run: UPDATE customers SET order_count = order_count + 1 ...
NormalizedDenormalized
Data integrityOne source of truth — hard to get inconsistentRedundant copies can drift out of sync if an update is missed
Read performanceMay require joins or aggregation at read timeFast — the answer is already sitting there
Write complexitySimple — write the fact once, in one placeEvery write path touching the source must also update the redundant copy
When it's the right callDefault — start hereMeasured, read-heavy hot path where join/aggregation cost is a proven bottleneck
Interview-ready definition: denormalization is the deliberate, selective reintroduction of redundant or derived data into a schema that would otherwise satisfy a higher normal form, undertaken to reduce read-time computation (joins, aggregations) at the cost of increased write-path complexity and a risk of data drift if the redundant copy isn't kept transactionally consistent with its source. It is a targeted optimization applied after understanding the fully normalized design — not a substitute for understanding normalization in the first place.
04 — Designing before you normalize

ER modeling: entities, attributes, relationships, cardinality

Start here, before any code. Before an architect draws precise blueprints with exact measurements, they sketch a bubble diagram: "here's the kitchen, here's the living room, they connect through this doorway." An Entity-Relationship (ER) diagram is that bubble sketch for a database — a picture of what THINGS exist, what FACTS describe each thing, and how the things connect — drawn before you commit to specific tables and columns.

An entity is a distinct kind of thing worth tracking (Customer, Order, Product) — it becomes a table. An attribute is a fact describing one entity (a Customer's email, an Order's date) — it becomes a column. A relationship connects two entities (a Customer PLACES an Order) — it becomes a foreign key or a join table. Cardinality states how many of one entity can relate to how many of the other (one Customer places MANY Orders; one Order belongs to exactly ONE Customer) — it determines whether you need a simple foreign key or a full join table, exactly as covered in the tables & keys lab.

Interview-ready definition: Entity-Relationship modeling is a conceptual database design technique that identifies entities (distinct object types to be tracked), their attributes (descriptive properties), the relationships between entities, and each relationship's cardinality (one-to-one, one-to-many, many-to-many) — independent of any specific database engine — as a design step performed before translating the model into normalized relational tables, so that structural decisions (which things are separate entities, how they connect) are made deliberately before implementation details are chosen.

Practice problems

Work each one out before expanding the solution.

Problem 1 · Spot the transitive dependency
students(student_id PK, name, zip_code, city, state) -- city and state are fully determined by zip_code

Is this table in 3NF? If not, what's the transitive dependency, and how would you fix it?

Show solution
Not in 3NF. The dependency chain is: student_id → zip_code → city, state. city and state depend on zip_code (a non-key column), not directly on student_id (the actual key) — that's the transitive dependency. Fix: split off a zip_codes table. students(student_id PK, name, zip_code FK → zip_codes.zip_code) zip_codes(zip_code PK, city, state) Now city/state are stored exactly once per zip code, not duplicated across every student who happens to share one.
Problem 2 · Update anomaly from a 3NF violation

Using the ungrouped students table from Problem 1 (city and state stored directly, not split out), the city of zip code 10001 is renamed in the database. What has to happen for the data to stay consistent, and what could go wrong?

Show solution
Every row where zip_code = 10001 needs its city column updated — if even one row is missed (a common risk with a manual or partial UPDATE statement), the table now contains TWO different city values for the same zip code, which is a direct contradiction with no way for the database itself to know which one is "right." This is the classic update anomaly 3NF prevents: after normalizing (Problem 1's fix), the city is stored in exactly ONE row of the zip_codes table, so a single UPDATE is guaranteed to keep everything consistent.
Problem 3 · Justify a denormalization

A social media app's normalized schema requires joining posts, likes, and users to display "1,204 likes" on every post view, and this page is viewed millions of times per day. Propose a denormalization and name its specific cost.

Show solution
Add a redundant like_count INTEGER column directly on the posts table, incremented/decremented whenever a like row is inserted/deleted, instead of running COUNT(*) on the likes table joined to posts on every single page view. Cost: like_count can drift out of sync with the true count in the likes table if an increment/decrement is ever missed (e.g. a failed write, a race condition under high concurrency, or a bug that deletes a like row without updating the counter) — the system now has two "sources of truth" for the same fact that must be kept manually consistent, which is exactly the integrity risk normalization exists to eliminate, accepted here deliberately for read speed at massive scale.

An ER diagram shows: DOCTOR --- (1 : many) --- APPOINTMENT --- (many : 1) --- PATIENT, plus a separate many-to-many between DOCTOR and SPECIALTY. Sketch the tables this becomes.

Problem 5 · 2NF vs 3NF, side by side

Explain the difference between a 2NF violation and a 3NF violation in one sentence each, using the phrase "depends on."

Show solution
2NF violation: a non-key column depends on only PART of a composite primary key, rather than the whole key (e.g. in a composite key (student_id, course_id), a column like student_name depends only on student_id, not on the pair together). 3NF violation: a non-key column depends on ANOTHER NON-KEY COLUMN, rather than depending directly on the primary key (e.g. dept_manager depends on dept_id, which depends on the actual key, employee_id — a chain rather than a direct link). Both are about what a column "depends on" — 2NF is about depending on only PART of the key; 3NF is about depending on something that ISN'T the key at all.
