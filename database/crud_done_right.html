01 — Telling "retry" apart from "do it again"

Idempotency keys for safe retries

Start here, before any code. Imagine mailing a signed check to pay a bill, and the postal tracking page just stops updating — no "delivered," no "lost," nothing. You don't know if the check arrived or vanished. Do you mail a second check? If you do and the first one WAS delivered, you've now paid twice and have to fight to get the extra payment back. What you actually want is to write "for July's bill" on both checks, so that if the biller ever receives a check already marked "for July's bill" that they've already cashed, they just shred the duplicate instead of cashing it again.

That's exactly what an idempotency key does over HTTP. The client generates one unique key per logical operation — "charge this customer $50 for this specific order" — typically a UUID, and sends it with every attempt at that same logical operation as a header, e.g. Idempotency-Key: 7c1e-...-b402. Crucially, the SAME key is reused across retries of the same intent — a fresh key is only generated for a genuinely new, different operation. The server keeps a store (a table, a cache) of keys it has already processed. When a request arrives, the server checks that store first: if the key is new, it processes the operation normally and records the key with its result; if the key has already been seen, the server skips re-executing the operation entirely and just returns the CACHED result from the first time — no second charge, no second row inserted, nothing re-run.

POST /charge HTTP/1.1 Idempotency-Key: 7c1e2f90-...-b402 -- body: { "amount": 50, "order_id": "ord_991" } -- server logic, roughly: SELECT result FROM idempotency_keys WHERE key = '7c1e2f90-...-b402'; -- found? -> return the STORED result, do not charge again -- not found? -> charge the card, INSERT the key + result, return it

Without the key: two attempts, two charges

The client sends the charge request. The server actually processes it — the card IS charged $50 — but the response carrying that "success" confirmation is dropped by the network before it reaches the client. From the client's point of view, this looks identical to the request never having been received at all, so it does the only reasonable thing: it retries, sending a plain new charge request. The server has no way to know this is "the same $50 charge, attempted again" versus "a genuinely new $50 charge" — so it processes it again. Two charges land. The customer is out $100 for something that should have cost $50.

With the key: the retry is recognized and short-circuited

Same dropped response, same retry — but this time the retry carries the exact same Idempotency-Key as the original attempt, because the client generated ONE key for this logical charge and reused it on every retry. The server looks up that key, finds it already marked as processed (with the original result: "charged $50, succeeded"), and returns that cached result directly — without touching the card a second time. The client gets its confirmation. The customer is charged exactly once.

Interview-ready definition: an idempotency key is a client-generated unique identifier, sent with a request, that scopes a single LOGICAL operation (not a single HTTP attempt) so the server can detect and safely no-op duplicate retries of that same operation by returning the previously-computed result instead of re-executing the side effect. It solves the specific problem that a network failure can occur on the response path AFTER a write already succeeded — leaving the client unable to distinguish "my request never arrived" from "it arrived and worked, but I never heard back."
02 — Two ways to stop two writers from stepping on each other

Optimistic vs pessimistic locking

Start here, before any code. Imagine two roommates editing the same shared shopping list. The pessimistic approach: whoever picks up the list first physically holds onto it — the other person just stands there waiting until it's put back down before they can even look at it, guaranteeing no one ever writes over the other's edit, but one person is always stuck waiting. The optimistic approach: both roommates take a photo of the list, edit their own copy, and whoever writes their changes back FIRST wins; the second person, when they go to write back, checks if the list has changed since their photo was taken — if it has, their edit is rejected and they have to look at the new list and redo their edit.

In a database, that "version check" is a real column. Optimistic locking reads a row along with its current version number, does no locking at all while the application computes its change, and then writes with UPDATE ... SET version = version + 1 WHERE id = ? AND version = <the version read earlier>. If nobody else touched the row in between, the version still matches, one row is updated, and the version bumps. If someone else already committed a change (and therefore already bumped the version), the WHERE clause matches zero rows — the update silently affects nothing, and the application must check the affected-row count, detect the conflict, and either retry against the fresh row or surface the conflict to the user.

Pessimistic locking takes the lock immediately, at read time, with something like SELECT ... FOR UPDATE — this tells the database "I intend to write this row, so hold a lock on it for the rest of my transaction." Any other transaction that tries to write (or in stricter modes, even read) that same row must BLOCK — it simply waits — until the first transaction commits or rolls back and releases the lock. This guarantees no conflicting concurrent write can ever happen, but it comes at the cost of real contention: transactions sit blocked, throughput drops under load, and if two transactions ever lock rows in different orders and then wait on each other, you get a deadlock, which the database has to detect and resolve by forcibly aborting one of the transactions.

Optimistic — fast under low contention

No blocking while reading or computing. Cheap when conflicts are rare. But when a conflict DOES happen, the loser's read and computed update are simply thrown away — wasted work that must be redone from a fresh read.

Pessimistic — guarantees no conflict, ever

The lock physically prevents a conflicting write from ever landing. But the waiting transaction is genuinely blocked — real contention under load, plus a real risk of deadlock if lock orders differ across transactions.

Interview-ready definition: optimistic locking allows concurrent reads with no locking, and detects conflicts only at write time via a version/timestamp column checked in the UPDATE's WHERE clause — a stale version means zero rows updated, and the application must detect and retry. Pessimistic locking acquires a lock at read time (e.g. SELECT ... FOR UPDATE) and forces any conflicting concurrent writer to block until the lock is released, guaranteeing no conflicting write can occur but introducing real blocking and deadlock risk. Optimistic wins under low contention (rare conflicts, no blocking overhead); pessimistic wins under high contention on the same rows (guarantees correctness without repeated wasted retries).
03 — "Deleted" doesn't always mean "gone"

Soft deletes vs hard deletes

Start here, before any code. Think about a document shredder versus moving a file to your computer's Trash folder. Shredding is final — the paper is gone, no undo, nothing to audit later. Trash just marks the file as "not currently visible in your normal folders" — it's still sitting on disk, recoverable, and if some OTHER program doesn't know to skip the Trash folder when it scans your files, it'll still find and list that "deleted" file. Soft delete and hard delete map onto exactly that distinction.

A hard delete executes DELETE FROM users WHERE id = 42; — the row is physically removed from the table immediately, storage and index space are reclaimed, and there is nothing left to query, undo, or audit unless you kept a separate backup or audit log elsewhere.

A soft delete adds a nullable deleted_at TIMESTAMP column. "Deleting" a row means UPDATE users SET deleted_at = NOW() WHERE id = 42; — the row physically still exists, with all its data intact, but is treated as gone by convention. NULL means not deleted; a timestamp means deleted (and records exactly when).

-- hard delete: gone, immediately, no trace DELETE FROM users WHERE id = 42; -- soft delete: row still physically present UPDATE users SET deleted_at = NOW() WHERE id = 42; -- every query touching this table must now remember this filter -- SELECT * FROM users WHERE deleted_at IS NULL; -- forget it ONCE, anywhere, and "deleted" rows silently reappear

A concrete forgotten-filter bug: a user soft-deletes their account — their row gets deleted_at = NOW(), and the row physically stays put. Two things can now go wrong. First, an unrelated admin analytics query that was written before soft deletes existed (or just forgot the filter) does SELECT * FROM users with no WHERE deleted_at IS NULL — and that "deleted" user shows right back up in a report, looking active. Second, if email has a uniqueness constraint, a brand-new signup with that SAME email address will fail — the database sees the value as already taken, because the old "deleted" row still physically occupies it, even though from the product's perspective that account is gone.
Interview-ready definition: a soft delete marks a row as logically removed via a nullable deleted_at timestamp column (NULL = active) without physically removing it, preserving history, enabling undo, and supporting audit/compliance needs — at the cost that every query against that table must consistently apply a WHERE deleted_at IS NULL filter (or go through a view/ORM default scope that applies it automatically), and forgetting that filter anywhere is a real, easy-to-introduce bug. A hard delete physically removes the row via DELETE, reclaiming storage immediately and requiring no filter anywhere, but is unrecoverable without a separate backup or audit-log mechanism.

Problem 1 · Tracing the idempotency demo with different timing

Suppose instead the network drops the ORIGINAL REQUEST itself (never reaches the server at all), not the response, and the client retries with the same idempotency key. What happens, and how is this different from the "response dropped" scenario in the lab?

Show solution
If the original request never reached the server, the server never processed it and never recorded that idempotency key. So when the retry arrives carrying that key, the server looks it up, finds nothing, and processes the charge for the FIRST time -- exactly as intended, exactly once. This is functionally identical in outcome to the "response dropped" case in the lab (exactly one charge lands) but for a different reason: in the lab's scenario the server had already processed the original and the idempotency key store is what prevented a SECOND charge on retry; here there was never a first processing at all, so the retry simply becomes the one-and-only real attempt. Either way, the idempotency key makes the retry safe -- the client does not need to know or care which of these two timings actually happened, which is exactly the point.
Problem 2 · Optimistic vs pessimistic for a flash sale

A flash sale has 5,000 buyers concurrently trying to purchase the last 3 units of a limited item. Separately, a low-traffic internal admin tool lets exactly one or two employees edit a shared config row per day. Which locking strategy fits each scenario, and why?

Show solution
Flash sale (very high contention on the SAME row/small set of rows): neither approach is free of pain here, but this is actually a case where you want the STRONGEST correctness guarantee on the critical stock decrement -- pessimistic locking (or an equivalent atomic decrement-with-check) is usually preferred, because with optimistic locking under this much contention, an enormous fraction of the 5,000 concurrent write attempts would read a version, compute a decrement, and then get rejected at write time because thousands of others already beat them to it -- leading to a storm of wasted work and retries hammering the same row repeatedly. Pessimistic locking (or a single atomic UPDATE statement with a WHERE stock > 0 guard) avoids that retry storm, at the cost of serializing access to that specific hot row, which is an acceptable, expected cost given how contended it already is. Internal admin tool (very low contention, essentially never concurrent): optimistic locking is the right fit. Conflicts are rare to the point of being nearly theoretical, so paying any locking/blocking overhead for guarantees you'll almost never need is wasted cost. A version column and a conditional UPDATE is simple, requires no held locks, and the rare conflict (two admins editing the same config within the same minute) is cheap to detect and ask one of them to retry.
Problem 3 · Diagnosing a forgotten deleted_at filter

A support engineer reports: "A customer says they deleted their account three months ago, but our fraud-detection job just flagged their (deleted) account for suspicious login activity, and the login actually succeeded." What's the likely root cause, and what are two different places the bug could be hiding?

Show solution
The likely root cause is a soft delete: the account row still physically exists with deleted_at set to three months ago, and at least one part of the system is not filtering on deleted_at IS NULL. Two plausible locations for the bug: 1. The LOGIN path itself -- if the authentication query that checks credentials doesn't filter out soft-deleted accounts, a "deleted" account can still successfully log in, which is exactly what's reported here (a real security/product bug, not just a cosmetic reporting issue). 2. The FRAUD-DETECTION job's query -- if it scans "all users" without excluding soft-deleted ones, it will keep evaluating and flagging an account that should be considered gone. Both are instances of the same root problem: nothing in the schema itself prevents a query from omitting the deleted_at filter, so each new query written against this table is a fresh opportunity to reintroduce the bug. The systemic fix is to centralize the filter -- a view, an ORM default scope, or a wrapped query helper that applies WHERE deleted_at IS NULL automatically -- so individual developers don't have to remember it every single time.
Problem 4 · Why idempotency keys are scoped to the logical operation

Explain concretely why an idempotency key must be generated once per LOGICAL operation and reused across retries, rather than generated fresh for every individual HTTP attempt. What would go wrong if the client generated a new key on every retry?

Show solution
The entire mechanism depends on the server being able to recognize "this is the same intent I've possibly already handled" -- and that recognition works ONLY because the key stays constant across retries of one logical operation. If the client instead generated a brand new key for every retry attempt, then from the server's point of view, the retry would look like a completely new, never-before-seen operation every single time -- because it WOULD be a never-before-seen key. The idempotency-key lookup would never find a match, the server would process each "retry" as an original request, and you'd be back to the exact double-charge bug the mechanism exists to prevent -- just with extra header plumbing and false confidence that it's handled. The key must identify "charge this customer $50 for THIS order," a single durable intent, not "this specific attempt number 2 of possibly several" -- the retries are re-attempts at delivering the SAME intent, and the key has to reflect that sameness for the deduplication to work at all.
Problem 5 · Choosing soft vs hard delete under stated requirements

A healthcare records system must be able to prove, for regulatory audits, exactly which patient records existed and when any were removed, and must support restoring a record if a removal is later found to be in error. A separate internal cache table stores precomputed dashboard aggregates that are cheap to regenerate and have zero compliance requirements. Which delete strategy fits each, and why?

Show solution
Healthcare records: soft delete is essentially required here, not just preferred. The stated requirements are exactly what soft delete provides and hard delete cannot: an auditable trail of what was removed and when (the deleted_at timestamp, plus ideally who removed it and why, in a related audit log), and the ability to UNDO a mistaken removal by simply clearing deleted_at back to NULL -- the data was never actually destroyed. A hard delete would make both requirements impossible to satisfy after the fact, since the row and its history would be permanently gone the moment it was deleted. Internal cache/aggregates table: hard delete is the right choice. There is explicitly no compliance requirement, no need for history, and the data is cheap to regenerate from source if ever needed again -- so none of soft delete's benefits apply, while its costs (every query must remember the deleted_at filter, storage isn't reclaimed) are pure downside for a table like this. Simplicity wins: DELETE FROM cache_aggregates WHERE ... with no filter to forget anywhere else in the codebase.
