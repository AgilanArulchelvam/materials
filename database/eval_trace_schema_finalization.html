01 — From "a pointer to a trace" to "the trace itself, queryable"

Extending the schema with real trace tables

Start here, before any DDL. Think about a library that used to keep a card catalog with just a note — "full case file available at the courthouse" — for every legal case it referenced. That's usable, but every time someone actually needs the case details, they have to leave the library entirely. Now imagine the library decides to bring PHOTOCOPIES of the actual case files into its own shelves, properly indexed and cross-referenced to the existing catalog cards — without removing or renumbering a single existing card. That's exactly what this lab does to eval_results_schema.html's design: trace_id stays exactly where it is on eval_result, but now a real eval_span table lives in the SAME database, holding the actual span data that trace_id used to only point at externally.

Why do this at all, given eval_results_schema.html's own Problem 3 argued FOR keeping the trace in a separate observability backend? Because that argument was about the LIVE, production trace pipeline — high-volume, short-retention, OpenTelemetry-shaped. This schema extension is narrower and more durable: specifically capturing the spans belonging to EVAL RUNS, which are lower-volume, need longer retention (an eval run from a month ago is still worth debugging), and benefit from being queryable with the same SQL joins as eval_run/eval_result rather than requiring a second query language against a separate observability system every time.

-- unchanged from eval_results_schema.html -- not touched by this migration CREATE TABLE eval_run ( /* run_id, started_at, model_version, dataset_id, suite_name, triggered_by */ ); CREATE TABLE eval_result ( /* result_id, run_id, test_case_id, eval_type, score, passed, details, trace_id, evaluated_at */ ); -- NEW: one row per SPAN belonging to the trace an eval_result references. -- Mirrors opentelemetry_basics.html's nesting model exactly, as real rows. CREATE TABLE eval_span ( span_id TEXT PRIMARY KEY, -- matches the OTel span_id format trace_id TEXT NOT NULL, -- same trace_id value already on eval_result parent_span_id TEXT REFERENCES eval_span(span_id), -- NULL for the root span span_name TEXT NOT NULL, -- e.g. "call_llm", "call_database" started_at TIMESTAMPTZ NOT NULL, ended_at TIMESTAMPTZ NOT NULL, duration_ms NUMERIC GENERATED ALWAYS AS (EXTRACT(EPOCH FROM ended_at - started_at) * 1000) STORED, attributes JSONB -- e.g. {"llm.model": "...", "llm.output_tokens": 142} ); CREATE INDEX idx_eval_span_trace ON eval_span(trace_id); CREATE INDEX idx_eval_span_parent ON eval_span(parent_span_id);

Notice what makes this a genuine EXTENSION rather than a redesign: eval_run and eval_result's own column lists are completely untouched — not one column added, removed, or retyped on either table. eval_span.trace_id is deliberately the SAME kind of value already stored on eval_result.trace_id, so the join between them is immediate and requires no new mapping table. And parent_span_id as a self-referencing foreign key is exactly opentelemetry_basics.html's nesting model, now expressed as a real, queryable relational constraint instead of an implicit "current span" context that only exists at instrumentation time.

Referential integrity across the new relationship is worth being precise about: eval_span.trace_id is NOT a formal foreign key to eval_result.trace_id — the same reasoning eval_results_schema.html's Problem 3 gave for why trace_id itself isn't a true FK applies here too, but for a subtly different reason now: eval_result.trace_id isn't even guaranteed UNIQUE (a single trace could, in principle, back multiple eval_result rows if several test cases were scored from the same execution), so it can't serve as a REFERENCES target the way a primary key can. The join between eval_result and eval_span is enforced at the QUERY level (JOIN eval_span ON eval_span.trace_id = eval_result.trace_id), exactly like the original external trace_id link — just now joining two tables in the SAME database instead of reaching into a separate system.

Interview-ready definition: finalizing an eval/trace schema means extending the existing header/detail pair (eval_run, eval_result) with a genuinely new table (eval_span) capturing trace-specific structure — span_id, trace_id, parent_span_id for nesting, start/end timing, and attributes — without altering a single existing column on the tables already in production. The new table's trace_id matches the value already stored on eval_result, making the two joinable directly, while parent_span_id's self-referencing foreign key gives OpenTelemetry's nesting model a real, relationally-enforced structure instead of an externally-inferred one.
02 — Additive, reversible, and safe to run against a live table with existing rows

Writing the migration

Start here, before the SQL. Think about renovating a house that people are still living in. A destructive rewrite would mean tearing the whole house down and rebuilding — nobody can live there during that, and everything inside is lost unless separately backed up first. A responsible renovation instead adds a new room onto the existing structure: the people living there are never displaced, everything that already existed keeps working exactly as before, and if the new room turns out to have a problem, it can be sealed back off without touching the rest of the house. A schema migration for a table already holding production data needs to be built the second way, always.

-- migrations/0007_add_eval_span.sql -- ADDITIVE, backward-compatible -- Up migration: pure addition. Does not touch eval_run or eval_result -- at all -- no ALTER TABLE against either existing table, no data rewrite. CREATE TABLE eval_span ( span_id TEXT PRIMARY KEY, trace_id TEXT NOT NULL, parent_span_id TEXT REFERENCES eval_span(span_id), span_name TEXT NOT NULL, started_at TIMESTAMPTZ NOT NULL, ended_at TIMESTAMPTZ NOT NULL, duration_ms NUMERIC GENERATED ALWAYS AS (EXTRACT(EPOCH FROM ended_at - started_at) * 1000) STORED, attributes JSONB ); CREATE INDEX idx_eval_span_trace ON eval_span(trace_id); CREATE INDEX idx_eval_span_parent ON eval_span(parent_span_id); -- Down migration (rollback plan): drop only what this migration added. -- eval_run and eval_result are never referenced here because they were -- never touched -- rollback is exactly as safe as the up migration was. DROP TABLE IF EXISTS eval_span;

Three properties make this migration genuinely safe to run against a live table with existing rows, and each is worth naming explicitly because each is a real way a migration can go wrong if skipped:

PropertyWhy it matters here
AdditiveCREATE TABLE for a brand-new table never locks, rewrites, or risks corrupting eval_run or eval_result's EXISTING rows, because it doesn't touch those tables at all. Every eval_result row written before this migration still reads back exactly as it did before.
Backward-compatibleAny application code that was written against the OLD schema (only knowing about eval_run/eval_result) keeps working unmodified after this migration runs — it simply doesn't know eval_span exists yet. This means the migration can be deployed BEFORE the application code that populates eval_span, with zero downtime window where old code breaks against the new schema.
Has a rollback planThe down migration is symmetric and safe — DROP TABLE eval_span removes exactly what the up migration added, nothing more, meaning a bad rollout of the span-writing feature can be reverted without any risk to the eval_run/eval_result data that predates it.

Compare this against the destructive alternative a less careful migration might attempt: altering eval_result to REPLACE its plain trace_id column with a foreign key into a redesigned trace table, or worse, dropping and recreating eval_result entirely to "clean up" the schema. Either would require a data migration step to preserve every existing row's data, introduce real downtime or locking while the rewrite runs, and — critically — leaves NO safe rollback path once existing rows have been transformed, because reversing a destructive rewrite means reconstructing the exact prior row shapes, which is error-prone and sometimes not even fully possible if any information was lost in the transform.

What "locking a schema" actually means: it does not mean the schema can never change again — database/migrations_and_sql_vs_nosql_revisited.html already established that schemas evolve. It means committing to a stable CORE (here, eval_run and eval_result's existing columns) that future work builds ON TOP OF via additive migrations like this one, rather than a core that gets rewritten out from under existing consumers every time a new requirement appears.

Problem 1 · Deciding whether parent_span_id needs a NOT NULL constraint

Section 1's DDL defines parent_span_id as nullable. A teammate proposes making it NOT NULL for data-quality reasons. Evaluate this proposal using opentelemetry_basics.html's nesting model.

Show solution
The proposal is wrong, and section 1's own design already reflects why: opentelemetry_basics.html's nesting model requires exactly one ROOT span per trace -- the span representing the entire request (e.g. handle_request) that has no parent of its own, by definition, since nothing else in the trace contains it. If parent_span_id were NOT NULL, there would be no valid way to represent that root span's row at all -- every single span, including the root, would be forced to reference SOME other span as its parent, which is structurally false for the root and would require either fabricating a fake self-referencing or sentinel parent (corrupting the data to satisfy a constraint that shouldn't exist) or refusing to ever write the root span row (losing exactly the span most likely to be queried first, since it holds the overall request-level duration). The correct constraint is exactly what section 1 already has: nullable, with NULL meaning "this is the root span of its trace." This is the same NULL-as-meaningful-value pattern used elsewhere in this schema family -- eval_result.score being nullable for eval types that don't produce a numeric score is a comparable case -- NULL isn't "missing data," it's a legitimate, meaningful state (here, "has no parent") that a NOT NULL constraint would make impossible to express.
Problem 2 · Reasoning about why duration_ms is a generated column, not a stored, independently-written value

Section 1 defines duration_ms as GENERATED ALWAYS AS (...) STORED rather than a plain column the application writes directly. What specific data-integrity problem does this prevent, connecting to opentelemetry_basics.html's Practice Problem 3?

Show solution
A GENERATED column is computed by the database itself FROM started_at and ended_at, and can never be written directly or independently by application code -- it's mechanically impossible for duration_ms to disagree with (ended_at - started_at), because the database recomputes it from those two columns every time, rather than trusting whatever value application code happened to calculate and send separately. The specific integrity problem this prevents: if duration_ms were instead a plain column the application computed and wrote independently alongside started_at/ended_at, a bug in that application-side calculation (a timezone handling error, an off-by-one in unit conversion, or simply forgetting to update duration_ms after a started_at/ended_at correction) could leave a row where duration_ms doesn't actually match the real gap between started_at and ended_at -- silently wrong data with no mechanism to catch or prevent it. This connects directly to opentelemetry_basics.html's Practice Problem 3, which established that a parent span's duration is an INDEPENDENTLY MEASURED quantity, not derivable by simply summing children -- but within a SINGLE span, duration is always exactly (ended_at - started_at) by definition, with no such ambiguity, which is precisely why it's safe and correct to enforce that relationship mechanically via a generated column here, even though the cross-span relationship (parent vs sum of children) that Problem 3 discussed is NOT something a database constraint could enforce the same way.
Problem 3 · Diagnosing a migration that looks additive but isn't

A teammate's draft migration adds eval_span exactly as section 2 describes, but also includes ALTER TABLE eval_result ALTER COLUMN trace_id SET NOT NULL; (trace_id was previously nullable). Is this still a safe, additive migration? What could break?

Show solution
No -- this line breaks section 2's "additive and backward-compatible" guarantee, even though it looks like a minor addition (just a constraint, not a new column). ALTER COLUMN ... SET NOT NULL is a DESTRUCTIVE-STYLE change with respect to EXISTING rows specifically: if even one existing eval_result row currently has trace_id = NULL (a realistic possibility -- eval_results_schema.html's original design never required every result to have a trace_id, e.g. a deterministic eval_type check might never have needed a traced execution at all), this ALTER statement will FAIL outright when run, because Postgres validates the NOT NULL constraint against every existing row at migration time -- the migration doesn't silently succeed and corrupt data, it just refuses to run, which is at least loud rather than silent, but still breaks section 2's "safe to run against a live table with existing rows" guarantee. Even setting aside whether it fails outright, this line also breaks BACKWARD COMPATIBILITY the way section 2 defined it: any existing application code path that currently writes an eval_result row WITHOUT a trace_id (again, plausible for eval types with no traced execution) would start failing immediately after this migration runs, with no grace period -- exactly the "old code breaks against the new schema" failure mode section 2's backward-compatibility property was designed to avoid. The fix: either leave trace_id nullable (it's a legitimate, pre-existing state, same as Problem 1's parent_span_id reasoning), or if NOT NULL is genuinely desired going forward, handle it as its own carefully staged migration -- first backfilling or auditing existing NULL rows, THEN adding the constraint -- rather than bundling it silently into what's supposed to be a purely additive migration for an unrelated new table.
Problem 4 · Extending the retention policy to cover the new table

Using eval_results_schema.html's Problem 4 retention tiering (full detail for 30-90 days, then summarized), propose a retention rule for eval_span specifically, and explain whether it should match eval_result's retention window exactly or differ from it.

Show solution
eval_span rows should follow the SAME retention window as the eval_result rows whose trace_id they belong to, not an independently-set window -- and the reason is a direct consequence of section 1's join mechanism. eval_span only has VALUE in this schema as evidence supporting a specific eval_result's scored outcome (per eval_results_schema.html's core argument: "an eval result with no trace is a number nobody can trust"). Once the eval_result row itself has aged past its own retention window and been rolled into a coarser per-run summary (per that lab's Problem 4), the SPECIFIC eval_span rows tied to its trace_id no longer have anything to attach evidentiary value TO -- keeping them around independently past that point preserves span data with no result row left to explain what it was evidence FOR. Concretely: when an eval_run (and its eval_result rows) crosses the 30-90 day full-detail retention boundary and gets summarized, the CASCADE should extend to eval_span as well -- either a scheduled cleanup job deletes eval_span rows whose trace_id no longer matches any still-full-detail eval_result row, or (cleaner, and worth setting up directly rather than relying on a separate cleanup job matching by value) an ON DELETE CASCADE-style relationship could be considered if eval_result rows are themselves eventually hard-deleted rather than just summarized -- though note section 1 established trace_id isn't a formal FK between the two tables, so true cascading delete isn't mechanically available without adding one, meaning in practice this is most likely enforced by an explicit cleanup job matching trace_id values, run immediately after eval_result's own retention job, rather than a database-level cascade. Either way, the key design decision is that eval_span's retention should be COUPLED to eval_result's, not set as an independent, possibly-longer or possibly-shorter window of its own.
Problem 5 · Writing the query the CI/CD eval gate needs against the finalized schema

Using this lab's eval_span table and latency_and_tracing_integration.html's p95 definition, write a query that computes p95 REQUEST-LEVEL latency (the root span's duration) across every scenario in a specific eval run — exactly the number cicd_eval_gating_survival_exercise.html needs to gate on.

Show solution
SELECT percentile_cont(0.95) WITHIN GROUP (ORDER BY s.duration_ms) AS p95_latency_ms FROM eval_result r JOIN eval_span s ON s.trace_id = r.trace_id WHERE r.run_id = :target_run_id AND s.parent_span_id IS NULL; -- root span only, per Problem 1's -- NULL-means-root convention The WHERE clause's second condition is the whole point, and connects directly to latency_and_tracing_integration.html's section 1 distinction: this query needs REQUEST-LEVEL latency specifically (one number per scenario, representing the full end-to-end duration a user or gate actually cares about), not span-level latency for every individual child span in every trace -- joining eval_span without filtering to parent_span_id IS NULL would instead be aggregating a mix of root spans AND every nested child span together into one meaningless blended percentile, conflating "how long did the whole request take" with "how long did one specific database call inside it take," which is a different question entirely. percentile_cont(0.95) WITHIN GROUP (ORDER BY ...) is Postgres's native continuous-percentile aggregate -- it computes the same percentile concept latency_and_tracing_integration.html's Problem 1 worked out with nearest-rank by hand, but interpolating between the two nearest ranks rather than snapping to a single one, which is the standard, more statistically defensible approach a real production query would use rather than hand-implementing nearest-rank in application code. This is exactly the query cicd_eval_gating_survival_exercise.html's gate stage runs immediately after an eval run completes, comparing its result against the configured p95 threshold to decide whether to block the deploy.
