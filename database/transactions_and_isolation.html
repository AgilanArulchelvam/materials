Isolation levels don't ask "is this correct" — they ask "which specific ways of being wrong are you willing to tolerate."

ACID gives transactions their guarantees on paper, but "isolated" is a sliding scale, not a boolean — every level below Serializable trades a specific, well-defined class of anomaly for better concurrency. This lab traces dirty reads, non-repeatable reads, and phantom reads statement by statement across two concurrent transactions, and pins down exactly which isolation level closes each door.

01 — Four separate promises, not one vague one

ACID properties, one clear sentence each

Start here, before the definitions. Think about a bank transfer: money leaves account A and lands in account B. You want the WHOLE thing to happen or NONE of it (not half-transferred if the system crashes mid-way), you want the balances to always add up correctly before and after (no money created or destroyed), you want a second transfer that's checking balances at the same moment to not see some weird half-done in-between state, and you want the transfer to survive a power outage the instant after it completes. Those four wants map directly onto ACID.

A

Atomicity

A transaction's operations all happen, or none of them do — there is no partial completion visible to anyone.

C

Consistency

A transaction moves the database from one valid state to another, never violating declared constraints (foreign keys, uniqueness, checks).

I

Isolation

Concurrent transactions produce the same result as if they had run one at a time, to a degree controlled by the chosen isolation level.

D

Durability

Once a transaction commits, its changes survive any subsequent crash — they are written somewhere that outlives a power loss.

Interview-ready definition: ACID is the set of guarantees a database transaction provides: Atomicity (all-or-nothing execution), Consistency (the database moves between states that satisfy its declared integrity constraints), Isolation (concurrent transactions don't observe each other's uncommitted or partial intermediate states, to a degree set by the isolation level), and Durability (a committed transaction's effects persist even through a subsequent crash). This lab focuses specifically on Isolation — the other three are largely binary guarantees, while isolation is a deliberately configurable spectrum with real, named trade-offs at each level.
02 — Same guarantee name, very different actual behavior

Isolation levels: Read Uncommitted → Serializable

Start here, before the table. Isolation level is a dial, not a switch — turning it up (toward Serializable) buys stronger correctness guarantees at the cost of more locking/blocking and lower concurrency; turning it down (toward Read Uncommitted) buys higher throughput at the cost of tolerating specific, well-understood kinds of "wrong" reads. The interview-relevant skill is knowing exactly WHICH kind of wrongness each level still permits, not just memorizing the level names in order.

*Some databases (notably PostgreSQL's MVCC-based Repeatable Read) prevent phantom reads too as an implementation detail beyond the SQL standard's minimum requirement — but the standard only guarantees phantom-read prevention at Serializable.

Interview-ready definition: the SQL standard defines four isolation levels forming a strictly increasing guarantee ladder — Read Uncommitted (weakest, permits all three anomalies), Read Committed (prevents dirty reads only), Repeatable Read (additionally prevents non-repeatable reads), and Serializable (strongest, prevents all three, behaving as if transactions ran one at a time). Each step up trades concurrency/throughput for correctness — stronger isolation typically means more locking, more blocking, or more transaction aborts/retries under contention.
03 — Watching exactly when each anomaly happens

Dirty reads, non-repeatable reads, and phantom reads — traced live

Start here, before any trace. All three anomalies share a shape: Transaction 1 sees something that Transaction 2 is in the middle of changing, and the exact TIMING of what T1 sees relative to T2's commit is what determines whether the read is "dirty," "non-repeatable," or a "phantom." Watching the two transactions interleave statement by statement — not just reading a definition — is what actually makes the distinction between these three stick.

TWO-TRANSACTION TRACE: WATCH EACH ANOMALY HAPPEN
Pick an anomaly and run the trace — each step highlights exactly when the anomaly occurs.

Dirty read — seeing data that never actually committed

Transaction 1 reads a value that Transaction 2 has written but NOT yet committed. If Transaction 2 then rolls back, Transaction 1 acted on data that, from the database's permanent record, never actually existed. Prevented starting at Read Committed — Read Committed guarantees a transaction only ever sees already-committed data.

Non-repeatable read — the same row, two different answers

Transaction 1 reads a row, Transaction 2 commits a change to that SAME row, and Transaction 1 reads it again within the same transaction — getting a different value the second time, even though it never wrote anything itself in between. Prevented starting at Repeatable Read — that level guarantees any row you've already read stays consistent for the rest of your transaction.

Phantom read — the same query, a different set of rows

Transaction 1 runs a query matching a set of rows (e.g. "all orders over $100"), Transaction 2 commits a NEW row that would now match that same condition, and Transaction 1 re-runs the identical query — seeing a row that "phantom-ly" appeared, even though no single row Transaction 1 already read was altered. Prevented starting at Serializable (per the standard) — this is subtly different from a non-repeatable read because it's about the SET of matching rows changing, not an existing row's value changing.

The distinction that trips people up in interviews: non-repeatable read and phantom read sound almost identical, but the difference is precise: a non-repeatable read is the SAME row returning a different value on a second read; a phantom read is the SAME query returning a DIFFERENT SET of rows (new rows appearing or existing ones disappearing from the result) on a second execution. Repeatable Read isolation locks/versions rows it has already read to prevent the former, but by default doesn't prevent brand-new rows from satisfying the query's condition and showing up — that gap is exactly what Serializable closes.
Interview-ready definition: a dirty read observes another transaction's uncommitted, possibly-to-be-rolled-back writes. A non-repeatable read observes a different value for the SAME previously-read row because another transaction committed a change to it in between. A phantom read observes a different SET of rows matching the same query condition because another transaction committed a row insertion or deletion that changes which rows satisfy that condition. Each is prevented by a specific minimum isolation level: Read Committed prevents dirty reads, Repeatable Read additionally prevents non-repeatable reads, and Serializable additionally prevents phantom reads.

Problem 1 · Classifying an anomaly from a trace

T1 runs `SELECT COUNT(*) FROM orders WHERE status='pending'` and gets 12. Before T1 commits, T2 inserts a new pending order and commits. T1 re-runs the exact same COUNT query and gets 13. Which anomaly is this, and what is the minimum isolation level that prevents it?

Show solution
This is a phantom read. No previously-read ROW changed value -- T1 never read any individual order row and had its value change underneath it. Instead, the SET of rows matching the query's condition (status='pending') changed, because T2 committed a brand-new row that now satisfies that condition. The minimum isolation level that prevents this per the SQL standard is Serializable -- Repeatable Read specifically guards against already-read ROWS changing value, not against new rows appearing that would now match a previously-run query's WHERE clause.
Problem 2 · Dirty read consequences

Under Read Uncommitted, T1 reads a bank balance that T2 just updated (but hasn't committed) to reflect a $500 deposit, and T1 uses that value to approve a withdrawal. T2 then rolls back due to an unrelated error. What's the concrete problem?

Show solution
T1 made a real, consequential decision (approving a withdrawal) based on a balance that INCLUDED a $500 deposit that, after T2's rollback, never actually happened as far as the permanent database record is concerned. T1's decision is now based on data that is provably wrong -- the approved withdrawal may leave the account with a balance the account holder never actually had, since the $500 that justified the withdrawal was rolled back. This is exactly why dirty reads are considered dangerous enough that essentially no production system defaults to Read Uncommitted for anything involving real business decisions -- acting on uncommitted, potentially transient data can produce results that are impossible to reconcile after the fact, since the "phantom" $500 leaves no trace once rolled back.
Problem 3 · Choosing an isolation level for a report

A nightly reporting job runs several SELECT queries against the same set of tables over several minutes, and needs every query in the job to see a perfectly consistent snapshot — no row it already looked at should appear to change mid-report, though it doesn't specifically need protection from brand-new unrelated rows appearing in a completely different, unrelated query. Which isolation level is the minimum sufficient choice, and why not weaker or stronger?

Show solution
Repeatable Read is the minimum sufficient choice. The stated requirement is specifically "a row I've already read shouldn't appear to change value mid-report" -- that is precisely what Repeatable Read guarantees (it prevents non-repeatable reads), no more and no less than what's actually needed here. Read Committed would be insufficient -- it only prevents dirty reads, so a row read early in the report could still show a different, newly-committed value if read again later in the same long-running job, producing an internally inconsistent report. Serializable would work too (it's strictly stronger) but is more than necessary given the stated requirement explicitly doesn't care about phantom rows from unrelated queries -- and Serializable's stronger guarantee typically comes with more locking overhead or a higher chance of transaction conflicts/retries, a real cost you'd be paying for a guarantee this specific job doesn't need.
Problem 4 · Tracing a non-repeatable read by hand

Write out, statement by statement, a concrete 2-transaction sequence under Read Committed isolation that produces a non-repeatable read on an `accounts.balance` column.

Show solution
T1: BEGIN; T1: SELECT balance FROM accounts WHERE id=7; -- returns 1000 T2: BEGIN; T2: UPDATE accounts SET balance = 800 WHERE id=7; T2: COMMIT; -- T2's change is now committed T1: SELECT balance FROM accounts WHERE id=7; -- returns 800 -- DIFFERENT from the first read! T1: COMMIT; Under Read Committed, T1's first SELECT sees 1000 (T2 hasn't started yet). T2 then updates the SAME row and commits. T1's SECOND SELECT of the exact same row, still within the same transaction, now sees 800 -- a different value for a row T1 already read once, with no write by T1 itself in between. This is a non-repeatable read specifically because it's the SAME row (id=7) returning two different values across two reads within one transaction. Repeatable Read isolation would prevent this by ensuring T1's second read still returns 1000, either by holding a read lock on the row or by giving T1 a consistent snapshot as of when its transaction (or first read, depending on the exact MVCC implementation) began.
Problem 5 · Serializable's cost

If Serializable prevents all three anomalies and is therefore "the most correct" isolation level, why isn't every transaction in every system just run at Serializable by default?

Show solution
Serializable's stronger guarantee has to be enforced SOMEHOW at runtime, and that enforcement carries real costs. Depending on the database's implementation, this typically means either much more aggressive locking (transactions block each other far more often, reducing how many can genuinely run concurrently, which directly hurts throughput under contention) or, in optimistic/MVCC-based implementations, a higher rate of transaction ABORTS -- the database detects, at commit time, that two concurrent transactions' actual execution wasn't equivalent to some serial ordering, and forces one of them to roll back and retry, which costs wasted work and adds application-level complexity (you now need retry logic for a class of failure that lower isolation levels wouldn't have triggered nearly as often). Most real workloads don't need protection against ALL three anomalies for every single transaction -- many transactions are fine with Read Committed (the common default in systems like PostgreSQL and Oracle) because they either don't re-read the same row twice, don't run range queries sensitive to phantom rows, or the specific anomaly simply doesn't matter for that particular business operation. Choosing the isolation level per-workload, rather than blanket-defaulting to the strongest option everywhere, is a deliberate cost/correctness trade-off, not an oversight.
