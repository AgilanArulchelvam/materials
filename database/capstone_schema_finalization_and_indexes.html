01 — Everything this week accumulated, in one place

The finalized capstone schema

Start here, before any index. Think about moving from a set of sticky notes tracking a project to one properly organized binder — the sticky notes (this week's separate labs: eval_results_schema.html's original design, eval_trace_schema_finalization.html's span extension, capacity_estimation_practice.html's growth assumptions) each captured something true, but scattered. Finalizing means bringing all of it into ONE schema, stated once, that every other capstone lab — the orchestrator's instrumentation (capstone_dashboard_integration.html), the tool-call tracking implied by mcp-and-agents/capstone_orchestrator_integration.html — writes into and reads from.

-- migrations/0009_finalize_capstone_schema.sql -- Four tables: the complete capstone data model. -- agent_run and eval_run are UNCHANGED from eval_results_schema.html; -- tool_call is NEW this lab; eval_span is UNCHANGED from -- eval_trace_schema_finalization.html. Nothing here rewrites an -- existing column -- pure extension, per section 3's migration. CREATE TABLE agent_run ( run_id UUID PRIMARY KEY, agent_id TEXT NOT NULL, started_at TIMESTAMPTZ NOT NULL, ended_at TIMESTAMPTZ, status TEXT NOT NULL -- 'running' | 'done' | 'error' ); CREATE TABLE tool_call ( call_id UUID PRIMARY KEY, run_id UUID NOT NULL REFERENCES agent_run(run_id), sequence_number INTEGER NOT NULL, -- ordered position within the run tool_name TEXT NOT NULL, arguments JSONB NOT NULL, result JSONB, latency_ms NUMERIC, status TEXT NOT NULL, -- 'success' | 'error' | 'timeout' called_at TIMESTAMPTZ NOT NULL ); CREATE TABLE eval_run ( eval_run_id UUID PRIMARY KEY, started_at TIMESTAMPTZ NOT NULL, model_version TEXT NOT NULL, dataset_id TEXT, suite_name TEXT NOT NULL ); CREATE TABLE eval_result ( result_id UUID PRIMARY KEY, eval_run_id UUID REFERENCES eval_run(eval_run_id), run_id UUID REFERENCES agent_run(run_id), -- links a score to the actual run eval_type TEXT NOT NULL, score NUMERIC, passed BOOLEAN, trace_id TEXT NOT NULL, evaluated_at TIMESTAMPTZ NOT NULL ); CREATE TABLE eval_span ( span_id TEXT PRIMARY KEY, trace_id TEXT NOT NULL, -- matches eval_result.trace_id, joined at query time parent_span_id TEXT REFERENCES eval_span(span_id), -- NULL = root span span_name TEXT NOT NULL, started_at TIMESTAMPTZ NOT NULL, ended_at TIMESTAMPTZ NOT NULL, duration_ms NUMERIC GENERATED ALWAYS AS (EXTRACT(EPOCH FROM ended_at - started_at) * 1000) STORED, attributes JSONB );

Notice tool_call is the one genuinely NEW table here, filling a gap the earlier labs named but didn't build: capstone_capacity_estimation_practice.html's entity list assumed tool calls as a distinct, sizeable entity, and mcp-and-agents/capstone_orchestrator_integration.html's orchestrator dispatches tool calls that need to be durably recorded somewhere beyond the ephemeral span data — tool_call is that durable, queryable record, complementary to (not a duplicate of) the trace-level eval_span rows the same dispatch also produces.

Interview-ready definition: "finalizing" a schema means consolidating every table designed across separate, earlier design passes into one coherent, currently-accurate reference — adding the one genuinely missing table the earlier work implied but never built (tool_call, here) — without silently rewriting anything already in production, and without leaving any table's purpose ambiguous relative to the others (agent_run = the run itself, tool_call = each dispatched action, eval_run/eval_result = scoring, eval_span = trace structure).
02 — Every index earns its place by naming a real query

Indexes, each tied to an actual query pattern

Start here, before adding an index "to be safe." Think about a book's index (the paper kind) — a good one lists exactly the terms readers actually look up, not every word in the book. An index on every word would be enormous, slow to maintain, and mostly useless, because most words aren't things anyone searches for. A database index is the same trade: each one costs write overhead and storage FOREVER, in exchange for speeding up ONE specific access pattern — so each index proposed below is justified by naming the actual query it serves, not offered as a blanket "index the foreign keys" habit.

-- idx 1: "give me the full ordered call sequence for run Y" -- -- ORDER BY sequence_number is the whole point of this table; -- this composite index makes that scan free instead of a sort. CREATE INDEX idx_tool_call_run_seq ON tool_call(run_id, sequence_number); -- idx 2: "what's tool X's failure rate over the last 24 hours" -- -- filters by tool_name AND a time range together, so a composite -- index in this column order serves both predicates in one scan. CREATE INDEX idx_tool_call_name_time ON tool_call(tool_name, called_at); -- idx 3: "show me every span for the trace behind eval_result X" -- -- the exact join eval_trace_schema_finalization.html's own demo runs; -- without this, every trace lookup is a full table scan of eval_span. CREATE INDEX idx_eval_span_trace ON eval_span(trace_id); -- idx 4: "walk the child spans of a given parent, for waterfall rendering" -- -- serves capstone_dashboard_integration.html's detail-view expansion. CREATE INDEX idx_eval_span_parent ON eval_span(parent_span_id); -- idx 5: "every eval_result for a given agent run" -- links a run's -- outcome back to its scores, needed by the dashboard's per-run row. CREATE INDEX idx_eval_result_run ON eval_result(run_id); -- idx 6: "runs currently in 'running' state, oldest first" -- lets an -- ops query find stuck/long-running orchestrator runs cheaply, per -- capstone_orchestrator_integration.html's loop-termination concerns. -- A PARTIAL index -- only rows matching status='running' are indexed -- -- since most rows will eventually be 'done', and indexing those would -- be pure overhead for a query that never looks at them. CREATE INDEX idx_agent_run_running ON agent_run(started_at) WHERE status = 'running';
IndexQuery pattern it servesWhy this column order
idx_tool_call_run_seqOrdered call sequence for one runrun_id first (equality filter), sequence_number second (range/order) — the standard equality-then-range composite index rule
idx_tool_call_name_timeFailure rate for tool X, last 24htool_name first (equality), called_at second (range) — same rule, different columns
idx_eval_span_traceAll spans for one trace_idSingle column — the join key itself, no compound need
idx_eval_span_parentChildren of a given span, waterfall renderingSingle column — self-referencing FK lookups need their own index, not implied by the PK
idx_eval_result_runAll eval scores for one agent runSingle column FK lookup, same reasoning as idx_eval_span_parent
idx_agent_run_runningFind stuck/long-running runsPartial index — smaller, cheaper to maintain, since only a small fraction of rows are ever 'running' at once
Interview-ready definition: a defensible index proposal always states the query pattern FIRST, then the index — never the reverse. Composite indexes put equality-filtered columns before range-filtered or sorted columns; single-column indexes are for direct FK/join-key lookups; and a partial index (WHERE status = 'running') is worth naming explicitly whenever a query only ever cares about a small, identifiable subset of rows, since indexing the excluded majority would be pure overhead with no matching query to justify it.
03 — Additive, with a real rollback, exactly like the labs it builds on

The migration script

Start here, before running anything against a real database. Same renovation-not-demolition principle eval_trace_schema_finalization.html section 2 already established: this migration only CREATEs — new tables, new indexes — and touches nothing already holding production rows.

-- migrations/0009_finalize_capstone_schema.sql -- UP: pure addition. tool_call is new; every index is new; -- agent_run, eval_run, eval_result, eval_span keep their existing -- column definitions from earlier migrations, untouched. BEGIN; CREATE TABLE IF NOT EXISTS tool_call ( /* full definition, section 1 */ ); CREATE INDEX IF NOT EXISTS idx_tool_call_run_seq ON tool_call(run_id, sequence_number); CREATE INDEX IF NOT EXISTS idx_tool_call_name_time ON tool_call(tool_name, called_at); CREATE INDEX IF NOT EXISTS idx_eval_span_trace ON eval_span(trace_id); CREATE INDEX IF NOT EXISTS idx_eval_span_parent ON eval_span(parent_span_id); CREATE INDEX IF NOT EXISTS idx_eval_result_run ON eval_result(run_id); CREATE INDEX IF NOT EXISTS idx_agent_run_running ON agent_run(started_at) WHERE status = 'running'; COMMIT; -- DOWN: drop exactly what this migration added, nothing more. -- agent_run, eval_run, eval_result, eval_span are never referenced -- here because they were never touched by the UP migration either. BEGIN; DROP INDEX IF EXISTS idx_agent_run_running; DROP INDEX IF EXISTS idx_eval_result_run; DROP INDEX IF EXISTS idx_eval_span_parent; DROP INDEX IF EXISTS idx_eval_span_trace; DROP INDEX IF EXISTS idx_tool_call_name_time; DROP INDEX IF EXISTS idx_tool_call_run_seq; DROP TABLE IF EXISTS tool_call; COMMIT;

One detail worth naming explicitly: CREATE INDEX (without CONCURRENTLY) takes a lock that blocks writes to the indexed table for the duration of the build. On tool_call — brand new, empty at migration time — this is instant and harmless. On eval_span and eval_result, which may already hold real rows by the time this migration runs, a large enough table makes that lock duration genuinely disruptive — the production-safe version of this migration would use CREATE INDEX CONCURRENTLY for any index on a table that already has meaningful data, accepting a slower index build in exchange for not blocking writes.

What "safe to run against a live table" actually requires: additive DDL alone isn't sufficient once tables have real rows — CREATE INDEX without CONCURRENTLY is additive in the schema sense but still takes a write-blocking lock, which is a real production risk on eval_span/eval_result specifically (both already populated by capstone_dashboard_integration.html's live instrumentation), even though it's a non-issue on the brand-new, empty tool_call table.
04 — An index that isn't used is pure overhead

Verifying an index is actually being used

Start here, before trusting that a CREATE INDEX statement did its job. Think about installing a new highway exit ramp and never actually confirming any cars use it — you've paid the construction cost either way. Same with a database index: it costs write overhead and storage the moment it exists, whether or not the query planner ever chooses to use it. Confirming usage isn't optional polish — it's the only way to know section 2's indexes are earning their cost.

-- The standard verification tool: EXPLAIN (or EXPLAIN ANALYZE to -- actually execute and report real timing, not just the plan). EXPLAIN ANALYZE SELECT span_name, started_at, duration_ms FROM eval_span WHERE trace_id = '7f3a9c' ORDER BY started_at; -- What a HEALTHY plan looks like (index in use): -- Index Scan using idx_eval_span_trace on eval_span -- Index Cond: (trace_id = '7f3a9c') -- -> the planner went STRAIGHT to matching rows via the index, -- never touched rows for any other trace_id -- What an UNHEALTHY plan looks like (index NOT used): -- Seq Scan on eval_span -- Filter: (trace_id = '7f3a9c') -- -> the planner read EVERY row in the table and checked each -- one against the filter -- idx_eval_span_trace exists but -- was never consulted at all

Reasoning about WHY a planner skips an index it has available, even when one exists exactly matching the query, is worth being able to explain without needing to actually reproduce it against a live database:

Reason the planner skips the indexWhat it means
The table is smallFor a tiny table, a sequential scan can be CHEAPER than an index lookup (fewer total pages to read either way) — this is correct planner behavior, not a bug, and disappears naturally as the table grows toward realistic capstone volume per capacity_estimation_practice.html's projections
Stale table statisticsThe planner estimates cost using statistics (ANALYZE output) about row counts and value distributions; if those are stale (e.g. right after a large bulk load with no ANALYZE run since), the planner can badly misjudge whether the index is worth using
A function or cast wraps the indexed columnWHERE LOWER(tool_name) = 'search' against a plain index on tool_name can't use that index at all — the index is built on the raw column values, not the transformed ones, unless a matching functional index is created
The query filters on a different column than expectedA query filtering primarily on eval_type with only a secondary check on trace_id won't benefit from idx_eval_span_trace the way this section's example query does — the index has to match what the query ACTUALLY filters on first
Interview-ready definition: declaring an index and confirming it's used are two separate steps — EXPLAIN ANALYZE against the actual query pattern the index was built for is how you confirm the planner chose an Index Scan over a Seq Scan; an index that exists but never appears in any real query's plan is dead weight, worth periodically auditing for and dropping, not assumed correct just because the CREATE INDEX statement ran without error.

Problem 1 · A missing index the schema doesn't have yet

The capstone dashboard (capstone_dashboard_integration.html) needs to answer "show me the 20 most recent agent runs with their overall eval pass/fail status" — a query joining agent_run and eval_result, ordered by started_at descending, limited to 20. None of section 2's six indexes serve this directly. Design the index that does.

Show solution
The query's access pattern is: no equality filter at all (it wants ALL recent runs, not runs matching a specific value), just an ORDER BY started_at DESC with a LIMIT. This is a different shape from every index in section 2 -- those all lead with an equality-filtered column. Here, the right index is a single-column index directly on the ORDER BY column, matching DESCENDING order explicitly (some databases build ascending by default and can still use it for a DESC scan by reading backwards, but stating it explicitly is the more defensible answer): CREATE INDEX idx_agent_run_started_at ON agent_run(started_at DESC); With this index, "20 most recent runs" becomes an index scan that reads exactly 20 rows in already-sorted order and stops -- rather than a full table scan followed by an expensive sort of every row just to take the top 20. The join to eval_result for each of those 20 runs then uses idx_eval_result_run (already in section 2) to find that run's scores efficiently, one indexed lookup per row rather than a second full scan. This is worth naming as a DISTINCT index-design case from section 2's examples: those were all "find matching rows by equality, optionally ordered within the match" (composite, equality-then-range); this one is "no equality filter, order the WHOLE table and take the top N" -- a pure ORDER BY + LIMIT pattern, which wants a single-column index on exactly the sort column, in the exact sort direction the query uses.
Problem 2 · Justifying idx_agent_run_running as a partial index over a full one

Section 2's idx_agent_run_running is a PARTIAL index (WHERE status = 'running'). Quantify, using capacity_estimation_practice.html's assumptions, roughly how much smaller this partial index is than a full index on agent_run(started_at) covering every row, and explain why that size difference matters beyond just disk space.

Show solution
Using capacity_estimation_practice.html's own growth assumptions as a rough basis: agent runs accumulate continuously, and at any given moment, the number of runs actually IN the 'running' state (mid-flight, not yet done or errored) is bounded by current concurrent traffic -- plausibly a few dozen to a few hundred at once for a capstone-scale system, versus potentially tens of thousands of historical run_id rows accumulated over weeks/months of total operation. A partial index covering only 'running' rows could realistically be two to three orders of magnitude smaller than a full index covering every historical row, and that ratio only grows more favorable to the partial index over time as more completed runs accumulate. Why this matters beyond disk space: every INSERT and UPDATE against agent_run has to maintain every index defined on that table, including updating each index's internal structure. A full index on started_at gets touched (and must be updated) on every single row write, including writes for a run that finished and moved OUT of 'running' status three months ago and will never again match this index's purpose. A partial index only needs maintenance work for rows that currently match its WHERE clause -- once a run's status flips from 'running' to 'done', it's REMOVED from the partial index's working set implicitly, keeping the index's ongoing write overhead proportional to CURRENT concurrent load rather than to the ever-growing total history. This is a genuinely different scaling behavior, not just a smaller constant-factor win -- the full index's write overhead grows without bound as history accumulates, while the partial index's stays roughly flat, bounded by concurrent traffic.
Problem 3 · A composite index built in the wrong column order

A teammate proposes building idx_tool_call_name_time (section 2) as (called_at, tool_name) instead of (tool_name, called_at). Using the "what's tool X's failure rate over the last 24 hours" query this index is meant to serve, explain concretely why the column order matters and isn't just a cosmetic choice.

Show solution
Column order in a composite (multi-column) B-tree index determines which QUERY SHAPES the index can serve efficiently, and it's not symmetric -- (tool_name, called_at) and (called_at, tool_name) are genuinely different indexes with different capabilities, not the same index in two notations. A B-tree composite index is effectively sorted first by the leading column, then by the second column WITHIN each value of the first. With (tool_name, called_at): all rows for tool_name = 'hybrid_search' are grouped together and, within that group, sorted by called_at -- so "failure rate for hybrid_search in the last 24h" becomes: jump directly to the 'hybrid_search' group (via the leading column), then scan only the recent portion of that already-sorted-by-time sub-range. Both the equality filter (tool_name) and the range filter (called_at) are served by ONE efficient index traversal. With (called_at, tool_name) reversed: rows are grouped by TIME first, and within each time slice, sorted by tool_name. To answer the same query, the database would have to scan every row in the last 24 hours (fine, that's the range part) but then, for EACH of those rows, check whether tool_name matches 'hybrid_search' -- it can't jump directly to just the matching tool's rows within that time range the way the correct ordering can, because tool_name isn't the leading sort key. For a system with many distinct tools, this means scanning through rows for irrelevant tools mixed into the same time range, doing much more filtering work than necessary. The general rule this confirms: composite index column order should put the EQUALITY-filtered column(s) first, then the RANGE-filtered column(s) — exactly the ordering rationale table in section 2 already states for both idx_tool_call_run_seq and idx_tool_call_name_time, and reversing it doesn't just make the index "slightly less optimal," it can make the query fall back to scanning far more rows than the correctly-ordered version ever would.
