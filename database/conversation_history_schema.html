DATABASE FUNDAMENTALS LAB · CONVERSATION HISTORY SCHEMA

A conversation isn't always a straight line. Sometimes it branches — and the schema has to survive that.

agent_memory_schemas.html already covered the base conversation_turns table — one row per message, roles, tool-call pairs. This lab goes deeper into what that base schema doesn't handle on its own: a user editing a past message and forking the conversation from that point, multiple parallel agent sessions sharing the same underlying history, and — critically — the exact index shape that makes "give me the last N turns" fast at real scale.

01 — Editing a past message doesn't overwrite history, it forks it

Schema for branching conversations and edited messages

Start here, before any DDL. Think about editing a sent email in a thread everyone's already replied to — you can't actually rewrite what people already read and responded to. What editing tools really do instead is create a NEW version of that message, and everything that happens after the edit builds on the new version, while the OLD version and its own replies still exist, just no longer part of the "current" thread. A conversation history schema needs the same idea: editing turn 5 of a 10-turn conversation doesn't erase turns 6-10 — it forks the conversation, creating a new branch from turn 5 onward, while the original branch remains intact underneath.

agent_memory_schemas.html's conversation_turns table modeled a conversation as a strictly linear sequence, ordered by created_at. That linear model breaks the moment a message can be edited after later turns already exist — it has no way to represent "two different possible turn 6's" for the same conversation. Branching support adds exactly that:

CREATE TABLE conversation_turns ( turn_id BIGSERIAL PRIMARY KEY, conversation_id UUID NOT NULL REFERENCES conversations(conversation_id), parent_turn_id BIGINT REFERENCES conversation_turns(turn_id), -- NULL only for the first turn branch_id UUID NOT NULL, -- which branch this turn belongs to role TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'tool')), content TEXT, is_edited_from BIGINT REFERENCES conversation_turns(turn_id), -- the turn this one supersedes, if an edit turn_number INT NOT NULL, -- position within ITS branch, not global created_at TIMESTAMPTZ NOT NULL DEFAULT now() ); -- editing turn 5 does NOT update its row. It inserts a NEW row: INSERT INTO conversation_turns (conversation_id, parent_turn_id, branch_id, role, content, is_edited_from, turn_number) VALUES ('conv-88a1', 4, gen_random_uuid(), 'user', 'Actually, what about Berlin instead?', 5, 5); -- parent_turn_id=4 (same parent as the ORIGINAL turn 5) -- this is the fork point -- is_edited_from=5 -- traceable link back to what this replaces -- new branch_id -- everything built on THIS turn belongs to the new branch -- the original turn 5, and turns 6-10 built on it, are untouched and still exist
ONE CONVERSATION, ONE EDIT, TWO BRANCHES
Turn 5 gets edited after turns 6-7 already existed on the original branch — notice the original branch is untouched, not deleted.

The fork point is exactly where parent_turn_id matters: the edited turn 5 shares the SAME parent_turn_id (turn 4) as the original turn 5 — both are valid continuations of turn 4, just on different branches. is_edited_from is a separate, orthogonal link: it doesn't affect the conversation's tree structure at all, it's purely a traceability pointer saying "this turn is an edited version of that one," useful for showing a user an edit history or for the extraction pipeline from agent_memory_schemas.html to know not to treat both versions as independently meaningful facts.

Interview-ready definition: a branching conversation schema replaces a single linear turn order with a tree: each turn has a parent_turn_id pointing to the turn it continues from, and a branch_id identifying which line of the tree it belongs to. Editing a past message doesn't update or delete existing rows — it inserts a new turn sharing the edited turn's parent_turn_id (creating a sibling, and therefore a fork) with an is_edited_from pointer back to the turn it replaces, so both the original branch and the new one remain fully intact and independently reconstructable.
02 — Several agent sessions, one underlying history, not several copies of it

Multiple parallel agent sessions referencing shared history

Start here, before the schema. Think about several people editing shared meeting notes at once, each scrolled to a different section — they're all working against the SAME underlying document, not private copies of it, and a change one person makes is visible to the others without anyone needing to manually sync files. A multi-agent or multi-session system wants the same property for conversation history: several agent SESSIONS (maybe different specialized sub-agents, per multi_agent_delegation.html, or the same user resuming from two devices) reading and appending to ONE shared history, rather than each maintaining its own disconnected copy.

CREATE TABLE agent_sessions ( session_id UUID PRIMARY KEY, conversation_id UUID NOT NULL REFERENCES conversations(conversation_id), branch_id UUID NOT NULL, -- which branch THIS session is currently reading/writing on agent_role TEXT, -- e.g. 'coordinator', 'research_subagent' -- see multi_agent_delegation last_read_turn_id BIGINT REFERENCES conversation_turns(turn_id), -- this session's read position started_at TIMESTAMPTZ NOT NULL DEFAULT now(), last_active_at TIMESTAMPTZ NOT NULL DEFAULT now() ); -- two sessions, same conversation, same branch -- both see every turn either writes SELECT * FROM conversation_turns WHERE conversation_id = 'conv-88a1' AND branch_id = 'branch-main' ORDER BY turn_number ASC; -- session A's coordinator and session B's research sub-agent both run this -- same query against the same rows -- there is exactly ONE copy of this -- conversation's turns, not one private copy per session

The key design decision here: agent_sessions is a thin table tracking WHO is participating and WHERE each session currently is in the shared history (last_read_turn_id) — it does NOT duplicate any turn content. This mirrors a principle already established for long-term memory in agent_memory_schemas.html: keep exactly one authoritative copy of the actual data (there, memories scoped by user; here, turns scoped by conversation+branch), and let multiple consumers (sessions, sub-agents) reference it rather than each maintaining redundant copies that could drift out of sync with each other.

Interview-ready definition: supporting multiple parallel sessions against shared conversation history means sessions are tracked in a separate, lightweight table recording which conversation/branch each session is reading or writing (and its current read position), while the actual turn content lives in exactly one place — conversation_turns — that every session queries directly rather than copies. This avoids the consistency problem of N sessions maintaining N independent copies of the same conversation that could diverge; every session sees writes from every other session because there is only ever one underlying set of rows being read.
03 — "Give me the last N turns" has to stay fast as history grows

Efficient retrieval of recent context

Start here, before the index. database/indexing.html established the leftmost-prefix rule for composite indexes: an index on (A, B) serves queries that filter on A alone, or on A AND B together, efficiently — but not a query that filters on B alone. The dominant query against this lab's schema is "give me the last N turns of THIS conversation's THIS branch" — an equality filter on (conversation_id, branch_id) combined with sorting by turn_number (or created_at) descending. That's exactly the shape a composite index needs to be built around.

CREATE INDEX idx_turns_conv_branch_recency ON conversation_turns (conversation_id, branch_id, turn_number DESC); -- leftmost-prefix: conversation_id filters first, branch_id narrows -- within it, turn_number DESC means the index is ALREADY in the exact -- order "most recent turn first" needs -- no separate sort step required SELECT * FROM conversation_turns WHERE conversation_id = 'conv-88a1' AND branch_id = 'branch-main' ORDER BY turn_number DESC LIMIT 20; -- EXPLAIN ANALYZE shows: Index Scan using idx_turns_conv_branch_recency -- (not a Seq Scan) -- Postgres narrows directly to this conversation's -- this branch's rows, already sorted, and stops after 20 -- it never -- touches rows from OTHER conversations or OTHER branches at all
WHY (conversation_id, branch_id, turn_number DESC) IS THE RIGHT SHAPE
Index shapeWhat happens for this queryWhy
(conversation_id, branch_id, turn_number DESC)Direct index scan, narrows to exact rows needed, already sortedMatches the query's equality filters (leftmost columns) AND its sort order (trailing DESC column) in one structure — database/indexing.html's leftmost-prefix rule applied to 2 filter columns plus a sort column
(turn_number DESC) aloneIndex technically usable for the sort, but can't narrow to one conversation/branch first — still touches far more rows than needed, or Postgres may just seq scan insteadAn index with no leading equality columns can't answer "which conversation" at all — it only helps with global ordering, which isn't the actual access pattern
No indexFull table scan of every turn ever written, across every conversation, filtering and sorting in memory afterwardCost grows linearly with TOTAL rows in the table, not with the size of one conversation — exactly the difference the indexing lab measured directly for range queries

This is the same reasoning agent_memory_schemas.html applied to its simpler (conversation_id, created_at) index, extended one level further: branching (section 1) means conversation_id alone is no longer enough to identify "the current thread" — a conversation with 3 branches has 3 different valid "last 20 turns" answers depending on which branch is being read, so branch_id has to be part of the equality-filter prefix too, not bolted on afterward as a filter applied to an already-fetched result set.

A trap worth naming directly: it's tempting to index (conversation_id, turn_number DESC) and filter branch_id in application code after fetching — this technically "works" but throws away exactly the narrowing the index was supposed to provide: the database still has to scan every branch's turns for that conversation (not just the one branch actually needed) before the application can discard the irrelevant ones. For a conversation with many branches (frequent edits, many forks), this can mean fetching several times more rows than necessary on every single retrieval — the fix is including branch_id IN the index's leftmost-prefix columns, not filtering it out afterward.
Interview-ready definition: efficient retrieval of recent conversation context requires a composite index whose leftmost columns match the query's equality filters (conversation_id, and — once branching is supported — branch_id) followed by the sort column in the same direction the query needs it (turn_number DESC for "most recent first"), letting the database satisfy both the filter and the ordering from one index structure without a separate sort step or a scan of irrelevant rows. Omitting a necessary equality column from the index's prefix — even if it's still applied as a filter afterward — forces the database to scan more rows than the query logically needs, silently degrading exactly the "give me the last N turns" access pattern this schema exists to serve fast.

Problem 1 · Distinguishing a fork from a plain new turn

Using section 1's schema, how would you write a query to determine whether a given turn_id is a fork point (i.e. has more than one child turn) versus a normal, non-branching turn?

Show solution
A fork point is exactly a turn_id that appears as parent_turn_id for MORE THAN ONE row in conversation_turns -- section 1 established that an edit creates a new row sharing the edited turn's ORIGINAL parent_turn_id, meaning two turns (the original and its edited replacement) both point back to the same parent. A query like: SELECT parent_turn_id, COUNT(*) AS child_count FROM conversation_turns WHERE parent_turn_id = ? GROUP BY parent_turn_id HAVING COUNT(*) > 1; If this returns a row, the given turn_id is a fork point -- more than one valid continuation exists from it, meaning more than one branch_id has a turn whose parent is this turn. A turn with exactly one child is a normal, non-branching link in the chain; a turn with zero children is simply the current tip of whichever branch it belongs to. This is a genuinely useful query for UI purposes too -- it's exactly what you'd run to decide whether to show a user "this message has alternate versions" affordance.
Problem 2 · Reconstructing one branch's full history in order

Given section 1's schema, why is WHERE conversation_id = ? AND branch_id = ? ORDER BY turn_number ASC sufficient to reconstruct one branch's full conversation in order — without needing to walk parent_turn_id pointers one at a time the way you might reconstruct a generic tree?

Show solution
Because branch_id is assigned to EVERY turn that belongs to that branch at write time (section 1's edit example gives the new forked turn a NEW branch_id, and by extension every subsequent turn built on it would inherit or reference that same branch_id) -- meaning branch_id already encodes "which single line of the tree this turn belongs to" directly as a column value, not something that has to be DERIVED by walking parent_turn_id links at read time. Combined with turn_number (this turn's position specifically within its own branch, as section 1 notes turn_number is "position within ITS branch, not global"), a simple filter-plus-sort query reconstructs the full ordered sequence directly. This is a deliberate schema design choice, not an accident: many tree structures (e.g. a raw parent-pointer-only tree with no branch_id) DO require walking parent links recursively to reconstruct a path, which is considerably more expensive as a query (often a recursive CTE) than a single indexed filter-and-sort. Materializing branch_id as its own column at write time trades a small amount of write-time bookkeeping (deciding and storing the correct branch_id when a turn is inserted) for a much cheaper, more directly indexable read pattern -- exactly the kind of trade section 3's indexing discussion is built around: paying a cost where writes happen once, to save cost on reads that happen far more often.
Problem 3 · Diagnosing a stale read across two sessions

Two sessions (per section 2's agent_sessions table) are both active on conversation_id = 'conv-88a1', branch_id = 'branch-main'. Session A writes a new turn. Should session B automatically see it on its next read, and what — if anything — has to be true about the schema for that to hold?

Show solution
Yes, session B should see session A's new turn on its very next SELECT against conversation_turns for that same conversation_id/branch_id -- this is exactly the property section 2 establishes: because there is only ONE authoritative copy of the turn data (not one private copy per session), any query session B runs is reading from the same underlying rows session A just wrote to, with no synchronization step required between them. This is a direct consequence of NOT duplicating turn content per session, unlike the shared-agent-history problem section 2 explicitly frames in contrast to per-session private copies. What has to be true for this to actually hold in practice, beyond just the schema shape: the database's isolation level (transactions_and_isolation.html) needs to guarantee session A's committed write is visible to a subsequently-issued query from session B -- true under any standard isolation level for a plain committed INSERT followed by a fresh SELECT, so this isn't usually a real risk with a normal relational database. Where it COULD go wrong: if session B is instead reading from a STALE CACHE of the conversation's turns (e.g. an in-memory copy fetched once at session start and never refreshed) rather than querying conversation_turns directly on each read -- that's not a schema problem, it's an application- layer caching decision that would need its own explicit invalidation strategy, similar to the cache-freshness trade-offs the caching_layer_design lab covered generally.
Problem 4 · Choosing the right index when branch_id wasn't in the equality filter

A team indexes conversation_turns as (branch_id, conversation_id, turn_number DESC) — same three columns as section 3's recommended index, but with branch_id listed FIRST instead of second. Using the leftmost-prefix rule, does this index serve the "last 20 turns of this conversation's this branch" query just as well?

Show solution
In practice, yes for THIS specific query, because both conversation_id and branch_id are used as EQUALITY filters together (WHERE conversation_id = ? AND branch_id = ?) -- the leftmost-prefix rule cares about which columns are the LEADING equality-filtered columns as a SET when they're all present with equality conditions, and Postgres's planner can use a composite index efficiently regardless of which of the two equality columns is listed first, as long as both appear before the sort column in the index definition. So (branch_id, conversation_id, turn_number DESC) and (conversation_id, branch_id, turn_number DESC) perform comparably for this exact query. Where the choice of ORDER between the two equality columns WOULD matter: if there's ALSO a common query that filters by branch_id alone (unlikely here, since branch_id isn't meaningful without knowing which conversation it belongs to) or by conversation_id alone (section 3's earlier, pre-branching index actually was exactly this: (conversation_id, created_at) with no branch_id at all) -- in THAT case, whichever column is listed first is the one a single-column-equivalent query can still use via the leftmost-prefix rule, while the second column would NOT help a query filtering only on itself. Since conversation_id alone (without branch_id) is a much more plausible standalone query pattern than branch_id alone (a UUID that's meaningless without its conversation), putting conversation_id first, as section 3 does, is the safer choice for supporting BOTH the full two-column filter and a plausible conversation_id-only fallback query -- not because the two-column query itself cares about the order.
Problem 5 · Extending agent_memory_schemas's extraction pipeline for branches

agent_memory_schemas.html's extraction pipeline reads recent turns from conversation_turns to populate long-term memory. With branching now in the schema, what does the extraction step need to decide that it didn't before, and why does getting this wrong risk polluting long-term memory?

Show solution
With branching, extraction needs to decide WHICH branch's turns to read from -- a conversation with multiple branches (e.g. an original path plus an edited fork) has multiple, genuinely DIFFERENT possible histories, and naively reading ALL turns for a conversation_id regardless of branch_id would mix content from mutually exclusive alternate versions of the conversation together, as if they all actually happened, when in reality only ONE branch represents what the user actually ended up seeing/saying. Concretely, using section 1's edit example: the ORIGINAL turn 5 ("what about the weather in Lisbon") and the edited turn 5 ("actually, what about Berlin instead") are alternate, mutually exclusive versions of the SAME point in the conversation -- a user never said BOTH; they said one, then changed it to the other. If extraction reads turns from BOTH branches without distinguishing them, it risks generating a long-term memory entry like "user asked about Lisbon and Berlin weather" as if both were genuinely part of one continuous exchange, when the more accurate fact is "user initially asked about Lisbon, then corrected themselves to Berlin" -- information the branch_id and is_edited_from columns preserve precisely, but only if the extraction query actually filters to ONE branch (typically whichever branch_id currently represents the "live," most recently active line of conversation) rather than pulling from conversation_turns for a conversation_id with no branch_id filter at all. This is a direct, concrete consequence of adding branching to the schema: every downstream consumer that assumed "conversation_id uniquely identifies one linear history" -- including agent_memory_schemas's own extraction pipeline -- now needs to be updated to also filter by branch_id, or it will silently produce corrupted or misleading results once branching data actually exists in the table.
