DATABASE FUNDAMENTALS LAB · AUDIT TRAIL SCHEMA

If a tool call goes wrong at 3am, the audit trail is the only witness that was there.

Every lab this month has trusted tool calls to just work: deterministic_parsing.html validates them, loop_termination_logic.html bounds them, but nothing yet has recorded them permanently. This lab builds the schema that logs every single tool call's inputs, outputs, and outcome — not for the agent's benefit, but for a HUMAN's, debugging a failure hours or days after the fact, with nothing to go on except what got written down.

01 — A summary tells you something happened. Full inputs and outputs tell you WHY.

Logging every tool call's inputs and outputs

Start here, before any DDL. Think about an airplane's black box. It doesn't record "the flight was mostly normal, with one minor anomaly around minute 40" — it records literally every instrument reading, every control input, every radio transmission, continuously, for the entire flight. The reason isn't paranoia: when something goes wrong, investigators don't know in advance which detail will turn out to matter, so a summary written by someone who didn't yet know what would go wrong is exactly the wrong thing to have. An audit trail for tool calls needs the same posture — record the actual data, not someone's guess at what might later seem relevant.

Here's the core table, one row per tool call:

CREATE TABLE tool_call_audit ( call_id UUID PRIMARY KEY DEFAULT gen_random_uuid(), agent_id UUID NOT NULL, -- which agent/session made this call conversation_id UUID REFERENCES conversations(conversation_id), tool_name TEXT NOT NULL, input_params JSONB NOT NULL, -- the FULL arguments object, exactly as validated output_result JSONB, -- the FULL result, or NULL if the call never completed status TEXT NOT NULL CHECK (status IN ('success', 'tool_error', 'validation_error', 'timeout')), error_detail TEXT, -- populated only when status != 'success' started_at TIMESTAMPTZ NOT NULL, duration_ms INT NOT NULL ); -- one real row, a validation failure caught before execution INSERT INTO tool_call_audit (agent_id, conversation_id, tool_name, input_params, output_result, status, error_detail, started_at, duration_ms) VALUES ( 'agent-77f2', 'conv-88a1', 'search_flights', '{"origin": "SFO", "destination": "JFK", "cabin_class": "luxury"}'::jsonb, NULL, 'validation_error', "'luxury' is not one of ['economy','business','first'] at $.cabin_class", '2026-08-19 14:02:11+00', 4 );

Notice input_params and output_result are JSONB, storing the entire arguments object and the entire result — not a truncated string, not a hand-picked subset of "the fields that seemed important." This directly mirrors json_schema_tool_specs.html and deterministic_parsing.html's own approach: those labs validate and parse the FULL structured object, never a lossy summary of it — and the audit trail's whole job is to preserve exactly what those steps actually saw, unmodified.

Storing a summary ("called search_flights, failed")

Tells you something happened, roughly when, and roughly what kind of thing it was. Does NOT tell you which specific argument was wrong, what value was actually passed, or what the tool's exact error message said — every one of which might be exactly what a debugging session six hours later needs, and none of which can be recovered after the fact if it was never written down.

Storing the full input_params and output_result

Preserves the EXACT arguments object that was validated (or that failed validation) and the EXACT result (or error) the tool produced — nothing paraphrased, nothing dropped. A debugging session later can see precisely what happened, because the row IS what happened, not someone's earlier guess at what would matter about it.

Why store the full objects rather than just a summary column like notes TEXT? Because at write time — the moment a tool call happens — nobody yet knows which detail will turn out to matter for a debugging session that might happen hours, days, or never. A summary is a decision made too early, by someone (or some code) that doesn't yet know what the eventual question will be. The full input_params/output_result objects defer that decision: whatever ends up mattering is already there, because everything is there.

Interview-ready definition: an audit trail schema for tool calls logs one row per call containing the caller's identity (agent_id), the tool invoked, the FULL input_params and output_result as structured JSON (not a truncated or hand-summarized version of either), an explicit status distinguishing different failure kinds, and timing data. Storing complete inputs and outputs rather than a summary is a deliberate choice to defer the "what matters" decision away from write time — when nobody yet knows what a future debugging session will actually need — to read time, when the full data is still there to answer whatever question actually comes up.
02 — A log you can only READ is different from a log you can RUN

Schema supporting replay and debugging

Start here, before the schema extension. Think about the difference between a restaurant's handwritten note "the soufflé collapsed" and a chef's actual RECIPE with exact measurements and timing — the note tells you a fact; the recipe lets you literally attempt the dish again, this time watching for where it goes wrong. A log that tells you a tool call failed is the note. A log precise enough that you could feed its input_params back into the SAME tool and watch it fail (or now succeed, if the underlying cause was fixed) the same way — that's the recipe. Replay support is exactly the difference between those two.

Section 1's schema already has almost everything needed for this — the discipline is making sure nothing is missing. A row supports replay only if it captures EVERYTHING that could have influenced the outcome:

What's needed for replayWhere it lives in section 1's schemaWhat breaks if it's missing
The exact call that was madetool_name + input_params (full JSONB)Without the FULL arguments, you can't re-issue the identical call — you'd be guessing at what was actually passed, defeating the entire point of a replay
What the tool actually returned or failed withoutput_result + status + error_detailWithout knowing the ORIGINAL outcome, you have nothing to compare a replay attempt's result against — "did it fail the same way, or differently?" is unanswerable
Ordering relative to other calls in the same sessionconversation_id + started_atA tool call rarely happens in isolation — if an earlier call in the same session changed some external state (e.g. created a booking) that this call then depended on, replaying THIS call alone, out of order, could behave completely differently than it did originally
Which agent/session context was activeagent_idDifferent agents (or the same agent with different configuration) might handle identical arguments differently — without knowing WHO made the call, a replay might use the wrong logic entirely

This connects directly to a broader idea worth naming, even briefly: storing a complete, ordered sequence of exactly what happened — rather than only the current state something ended up in — is the same underlying principle behind event sourcing (storing state as a sequence of events, so any past state can be reconstructed by replaying events from the beginning). This audit trail isn't a full event-sourced system in its own right, but it borrows event sourcing's central insight: if you record the actual sequence of things that happened, in enough detail and in the right order, you can reconstruct — or literally re-attempt — what happened later, in a way a system that only ever stored "current state" fundamentally cannot.

ONE SESSION'S TOOL CALLS, IN ORDER — ENOUGH TO REPLAY THE FAILURE
A trap worth naming directly: it's tempting to log output_result only on success and skip it entirely on failure ("there's no result, so why store anything?"). But a FAILED call often has genuinely useful output too — a partial response before a timeout, an HTTP status code and response body from a downstream API that rejected the call, or the specific validation error from deterministic_parsing.html's pipeline. error_detail exists specifically to capture this — leaving it null on every failure throws away exactly the detail a debugging session needs most, on exactly the rows where debugging is most likely to happen.
Interview-ready definition: an audit trail schema supports replay and debugging when its rows capture not just that a call happened, but everything needed to reconstruct or re-attempt it: the complete input arguments, the complete result or error, the calling agent's identity, and the call's position in a larger ordered sequence (via conversation_id and started_at) relative to other calls that may have changed relevant external state beforehand. This mirrors event sourcing's core principle at a smaller scale — a detailed, ordered record of what actually happened lets you reconstruct or replay past behavior in a way a system that only stores current state cannot, without requiring the audit trail itself to be a full event-sourced system.

Problem 1 · Writing a query to find every call that failed validation in the last hour

Using section 1's schema, write a query that finds every validation_error call in the last hour, and explain why an index on (status, started_at) — not just started_at alone — would make this query efficient at scale, using the leftmost-prefix reasoning from database/indexing.html.

Show solution
SELECT * FROM tool_call_audit WHERE status = 'validation_error' AND started_at >= now() - INTERVAL '1 hour' ORDER BY started_at DESC; An index on started_at ALONE would let Postgres narrow to the last hour efficiently, but it would still have to scan every row in that window and check status = 'validation_error' against each one individually -- if validation errors are a small fraction of total call volume (which they typically are), most of the rows scanned in that time window get discarded after the check, wasted work. An index on (status, started_at) matches the query's EQUALITY filter (status) as the leading column, followed by the RANGE filter (started_at) -- exactly the leftmost-prefix shape database/indexing.html established: Postgres narrows directly to just the validation_error rows first, then range-scans only WITHIN that already-narrow set for the last hour, touching far fewer rows overall than scanning the full time window and filtering status afterward. This is the same principle conversation_history_schema.html applied to (conversation_id, branch_id, turn_number DESC) -- put the equality-filtered column(s) first, the range/sort column after, so the index does the narrowing instead of the database doing it in application-visible filtering after the fact.
Problem 2 · Deciding what NOT to log

Section 1 argues for storing FULL inputs and outputs. Does this mean literally every field of every argument should always be stored verbatim, with no exceptions? Name one realistic case where storing the full, raw value would be a mistake, and what you'd do instead.

Show solution
No -- "store the full input/output" is the right DEFAULT, but it has a real exception: fields containing sensitive data (a credit card number, a password, a government ID number passed as a tool argument) shouldn't be stored in plaintext in an audit table that may be read by many engineers debugging unrelated issues, retained indefinitely, and potentially included in backups or replicated to less-secured environments. Storing raw sensitive values here would trade one real problem (losing debugging fidelity) for a different, often worse one (a data-security and compliance liability sitting in a table specifically designed to be broadly readable for debugging purposes). What to do instead: redact or tokenize specific known-sensitive fields before writing input_params (e.g. store "**** **** **** 4242" instead of a full card number, or a reference token that can be looked up separately under stricter access control if truly needed), while still storing everything ELSE in that same call's arguments in full. This preserves section 1's core benefit (full context for debugging almost everything about the call) while not turning the audit trail itself into a sensitive-data exposure. The general principle: "store everything" is the right default for data whose future debugging value is genuinely unknown at write time, but it's not a blanket rule that overrides every other constraint (security, compliance, storage cost at extreme scale) -- those are separate, real considerations layered on top of the default, not disproofs of it.
Problem 3 · Diagnosing an audit trail that looks complete but can't actually replay

A team implements section 1's schema correctly — full input_params, full output_result, accurate status — but omits conversation_id and started_at entirely, reasoning "each row is already self-contained, why do we need ordering?" Using section 2's replay requirements, what specifically breaks?

Show solution
Each ROW is self-contained in the sense that you can see exactly what that ONE call's arguments and result were -- but replay often isn't about one call in isolation, it's about reproducing a SEQUENCE of calls where an earlier one changed state a later one depends on. Section 2's table names this directly: without conversation_id and started_at, you can't tell WHICH other calls happened in the same session, or in what ORDER -- so if a booking-confirmation call failed specifically because an earlier seat-selection call in the SAME session had already consumed the last available seat, that causal relationship is invisible. Each row on its own looks like an unexplained failure; only the ORDERED SEQUENCE of calls in that specific session reveals why. Concretely: imagine two DIFFERENT sessions both called search_flights with identical input_params and got different output_results, because one session's earlier calls had changed some shared external state (e.g. available seat inventory) between the two searches. Without conversation_id grouping calls into sessions and started_at ordering them within a session, there's no way to distinguish "these two identical- looking calls behaved differently because of unrelated global state changes over time" from "the tool is nondeterministic" -- the omitted columns are exactly what would let you tell those two very different explanations apart. Self-contained rows answer "what happened in THIS call" perfectly; they cannot answer "why did this call's outcome depend on what came before it" without ordering and session-grouping data.
Problem 4 · Connecting duration_ms to loop_termination_logic's timeout mechanism

Using loop_termination_logic.html's per-step timeout mechanism, how would a status = 'timeout' row's duration_ms value relate to that lab's step_timeout_seconds parameter, and why is logging the actual duration still useful even though you already know it hit the timeout?

Show solution
A status = 'timeout' row's duration_ms should be very close to (at or just past) step_timeout_seconds * 1000 -- since loop_termination_logic's asyncio.wait_for(..., timeout=step_timeout_seconds) is precisely what determined the call was abandoned, the recorded duration reflects approximately that same budget having elapsed before the call was cut off, not the tool's true (unknown, since it never got to finish) completion time. Logging the actual duration is still useful for a few real reasons even though "it timed out" is already known from status alone: (1) it lets you distinguish a call that timed out almost immediately (duration_ms much smaller than the configured budget, suggesting something OTHER than a hung external call, e.g. a bug that immediately blocks) from one that ran right up against the full budget (suggesting a genuinely slow or hung downstream dependency, matching loop_termination_logic's original motivating scenario); (2) it lets you audit whether step_timeout_seconds itself is well-tuned across many rows -- if timeouts consistently fire at exactly 90% of the configured budget across hundreds of calls to the SAME tool, that's a strong, data-backed signal the budget might be set too tight for that tool's normal (non-hung) behavior, which is a genuinely different, more actionable finding than "this tool sometimes times out" alone would tell you.
Problem 5 · Reasoning about the trade-off between granularity and storage growth

A system logs one tool_call_audit row per call and runs millions of calls per day. Using the reasoning from database/time_series_schema.html's retention/downsampling pattern, propose a retention strategy that keeps full replay fidelity for RECENT calls without keeping every row forever at full detail.

Show solution
This is structurally the same trade-off time_series_schema.html covered for sensor data: keep full-fidelity raw rows for a bounded RECENT window (where replay/debugging value is highest -- most debugging happens within hours or days of an incident, not months later), and age older rows into a coarser, smaller-footprint form rather than deleting them outright or keeping every row at full detail forever. A concrete strategy: keep tool_call_audit rows at full fidelity (complete input_params and output_result JSONB) for, say, 30 days -- long enough to cover the overwhelming majority of real debugging requests, which reference recent activity. Past 30 days, roll rows into a coarser SUMMARY table (call counts per tool per day, error-rate percentages, average duration_ms) that preserves AGGREGATE trends (useful for "has this tool's error rate been rising over the last 6 months" questions) without keeping every individual call's full JSONB payload indefinitely -- exactly time_series_schema.html's raw-to-per-minute-to-per-hour downsampling pattern, applied here to audit rows instead of sensor readings, aging from "every call in full detail" to "an hourly/daily rollup" rather than to progressively coarser TIME buckets of the same metric. The trade-off being made explicit: this deliberately sacrifices full REPLAY capability for calls older than the retention window (you can no longer literally re-attempt a specific 4-month-old call, since its exact input_params are gone) in exchange for bounded storage growth -- a reasonable trade specifically because section 2's replay use case is overwhelmingly a RECENT-past concern in practice, not a need to replay arbitrary historical calls indefinitely. Whether 30 days is the right window (versus 7, or 90) is a product/compliance decision, not something the schema itself dictates -- but SOME bounded full-fidelity window, with a coarser fallback beyond it, is the general shape any audit-trail-at-scale needs.
