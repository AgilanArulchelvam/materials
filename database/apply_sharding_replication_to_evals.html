01 — Every sharding and replication decision starts from how the data is actually used

The eval data access pattern, first

Start here, before any shard key candidates. database/sharding_and_partitioning.html's core lesson was that a shard key's quality depends entirely on the QUERIES a system actually runs, not on the data's shape in isolation — a shard key that avoids hot shards but forces every real query to fan out across all shards anyway hasn't actually solved anything useful. So before picking a shard key or a replication mode for eval_run/eval_result, the access pattern needs to be pinned down precisely, using database/eval_results_schema.html's own section 3 queries as ground truth for how this data really gets used.

Two facts about eval data's access pattern, both directly from eval_results_schema.html: it is written once, read many times — an eval_result row is inserted exactly once when a run completes and essentially never updated afterward, but then read repeatedly by dashboards, CI gates, and engineers investigating a regression. And it is overwhelmingly queried by RECENT time range or by a SPECIFIC run — eval_results_schema.html's own Q1 ("pass rate across the last 5 runs"), Q2 ("failing results from the MOST RECENT run"), and Q3 ("does test case tc-882 fail across recent runs") are all either scoped to one specific run_id, or bounded to a RECENT window, ordered by started_at DESC. Nobody in that lab's queries ever asked "give me every eval result for dataset X across all history" as a primary access pattern — which turns out to matter enormously for section 2's decision.

Interview-ready definition: before choosing a shard key or replication mode for any dataset, the actual read/write access pattern has to be established first — write frequency and update frequency (does this data change after being written), and which columns real queries filter or order by. For eval data specifically: written once per result, read many times, and the dominant read patterns are "one specific run_id" (CI gates, drill-down debugging) and "recent time range" (dashboards, trend queries) — never "one dataset_id across all of history" as a primary pattern. Every decision in this lab follows directly from these two established facts, not from sharding or replication theory in the abstract.
02 — run_id, dataset_id, or time period: which one actually serves the real queries?

Choosing a shard key for eval_result

Start here, before the comparison. sharding_and_partitioning.html's core interview-ready definition named two things a good shard key needs: even distribution (no hot shard) AND minimizing how often real queries have to cross shard boundaries at all. Applied to eval_result, three candidates are worth weighing against BOTH of those criteria, using section 1's established access pattern as the test.

Candidate shard keyDistributionServes "one run_id" queries (Q2)?Serves "recent time range" queries (Q1, Q3)?
run_idGood — a UUID per run, naturally high-cardinality, no real-world skewYes, perfectly — every row for one run_id lives on exactly one shard, so Q2 ("failing results from the most recent run") never crosses a shard boundaryNo — recent runs are spread evenly across ALL shards (since run_id has no correlation with time), so a "last 5 runs" query (Q1) has to fan out to potentially every shard
dataset_idRisky — a small number of popular, frequently-used datasets could concentrate a large share of eval_result rows and traffic onto very few shards, the exact sharding_and_partitioning.html hot-shard patternNo — a single run_id's results, if that run spans one dataset, land on one shard, but results are also often queried WITHOUT knowing dataset_id up front (Q2 doesn't filter by dataset at all)No — same fan-out problem as run_id, recent runs across many datasets still scatter across shards
Time period (e.g. month of evaluated_at)Good NOW, but same signup_date-style skew risk sharding_and_partitioning.html warned about — the MOST RECENT time-period shard absorbs nearly all current write AND read traffic (dashboards querying "recent" data), while older shards sit comparatively idleNo — one run's results could straddle a period boundary if the run happens near a boundary, and even when they don't, nothing about run_id correlates with a clean partition edgeYes, well — a time-range query lands on exactly the shard(s) covering that range, often just one, avoiding fan-out for exactly the dashboards' dominant access pattern

Neither run_id nor time period alone serves BOTH dominant access patterns well — this is the genuine trade-off, not a case where one obviously dominates. Sharding by run_id makes Q2-style "one run" queries perfectly single-shard, but scatters Q1/Q3-style "recent time range" queries across every shard. Sharding by time period makes the opposite trade: recent-range dashboard queries stay single-shard (or close to it), but a single run's own results are still trivially findable within that one time-period shard anyway, since run_id is still indexed WITHIN each shard — a "get results for run_id=X" query still only has to search the ONE shard covering that run's started_at, which the application layer can determine directly from the run's own timestamp without needing to fan out at all.

This tips the decision toward time period as the primary shard key, with the caveat that it inherits the exact same recency-skew risk sharding_and_partitioning.html's signup_date example warned about — the shard covering the current month absorbs almost all live write traffic (every CI run writing fresh eval_result rows) AND almost all live read traffic (every dashboard querying "recent" data), while shards covering last year sit nearly idle. The mitigation database/time_series_schema.html already established for exactly this shape of data applies directly here: use a rolling window of active, writable shards (e.g. one shard per month, only the current 1-2 months actively serving both reads and writes) with OLDER shards effectively becoming read-mostly, lower-priority storage — accepting the skew as an intrinsic, expected property of time-partitioned data rather than something a cleverer shard key could avoid, because the recency skew is a property of the WORKLOAD itself (eval runs happen now, not evenly across all of history), not an artifact of a poorly chosen key.

Interview-ready definition: for eval_result data — written once, read predominantly by recent time range (dashboards) or by a specific run_id (CI gates, drill-downs) — sharding by TIME PERIOD best serves the dominant "recent" access pattern, keeping most dashboard queries single-shard, while a run_id lookup remains cheap within a time-sharded scheme because the run's own timestamp identifies which shard to query directly, no fan-out needed. This comes at the cost of inheriting the same recency-driven hot-shard risk sharding_and_partitioning.html's signup_date example demonstrated — the current period's shard absorbs disproportionate live traffic — which is mitigated the same way time_series_schema.html mitigates it for any time-series-shaped data: treat recency skew as an expected, structural property of the workload, not a shard-key design flaw to be engineered away entirely.
03 — Does an eval dashboard reading a few seconds behind the truth ever actually hurt anyone?

Sync or async replication for this data

Start here, before the trade-off. database/replication.html's core distinction: synchronous replication waits for a follower to confirm a write before telling the client "success" (safer, slower); asynchronous replication confirms immediately and lets followers catch up in the background (faster, with a real replication-lag window where a follower can serve stale data). Which one fits eval data comes down to a single, concrete question: is an eval_result read ever in the CRITICAL PATH of a live, user-facing request, the way a financial transaction or an inventory check would be?

Why financial data needs SYNCHRONOUS

A payment system reading a stale balance from a lagging follower could let a user overdraw an account or double-spend funds — the read's staleness directly causes an incorrect, consequential DECISION made right now, in the critical path of the request. Synchronous replication's slower writes are a worthwhile trade to guarantee every read sees the true, current state.

Why eval data is fine with ASYNCHRONOUS

Per section 1, eval_result reads serve dashboards and CI gate checks — genuinely important, but not something a LIVE USER's request is blocked on in real time. A dashboard showing a pass-rate number that's 2 seconds (or even a minute) behind the true latest write causes no incorrect action to be taken RIGHT NOW — nobody's transaction gets double-processed, no money moves incorrectly. This is precisely the same "trend dashboard tolerates staleness" reasoning database/read_replicas_and_dashboard_caching.html already established for observability dashboards generally, now confirmed for eval-results dashboards specifically.

The one case worth checking carefully before committing to asynchronous replication fully: backend/cicd_gating_system_design.html's CI/CD gate reads the JUST-COMPLETED eval_run's results to decide whether to block a deploy — is THAT read in a critical path sensitive enough to need synchronous replication instead? Working through it: the gate's read happens moments after the SAME eval_run's write completed, from the SAME pipeline that triggered the run — if that read is routed to a replica that hasn't caught up yet (replication lag, per replication.html's section 1), the gate could see an incomplete or stale result set and make the WRONG blocking decision. This is genuinely a case where either (a) the CI gate's specific read should be routed to the PRIMARY rather than a replica — exactly read_replicas_and_dashboard_caching.html's "route reads that need the latest committed row back to primary" pattern, applied to this one specific, sensitive read — or (b) the gate should simply wait for write confirmation from the SAME connection that performed the writes (which, on a single primary connection, already guarantees read-your-own-write consistency without needing synchronous REPLICATION at all). Either fix is cheaper than making ALL eval data replication synchronous just to cover this one specific read.

Interview-ready definition: eval_result data is a strong candidate for ASYNCHRONOUS replication because its dominant reads — dashboards, trend queries — are never in the critical path of a live user-facing request the way financial transaction data is; a dashboard reading a few seconds stale causes no incorrect real-time decision. The one exception worth naming explicitly is the CI/CD gate's own read of its own just-completed run's results (per backend/cicd_gating_system_design.html), which needs read-your-own-write consistency — solved narrowly by routing that ONE specific read to the primary (or the same connection that wrote it), exactly read_replicas_and_dashboard_caching.html's targeted fix — rather than by making the entire dataset's replication synchronous just to cover this one sensitive read path.

Problem 1 · Justifying why eval_run and eval_result should share the same shard key

Section 2 settles on time period as eval_result's shard key. Using eval_results_schema.html's header/detail relationship (eval_run to eval_result), should eval_run be sharded the SAME way, by the same time period? What would go wrong if eval_run were sharded differently — say, by triggered_by?

Show solution
Yes, eval_run should be sharded by the SAME time period as eval_result -- specifically, co-locating a run and its own results on the SAME shard, keyed by consistent logic (e.g. both keyed off started_at's time period). This directly reuses sharding_and_partitioning.html's cross- shard-query warning: eval_results_schema.html's Q1 query JOINs eval_run and eval_result together (to get pass rate per run, ordered by started_at). If the two tables were sharded independently by DIFFERENT keys, that JOIN would almost always become a cross-shard operation -- paying the fan-out-and-merge cost sharding_and_partitioning.html's section 3 described as strictly more expensive, on what should be one of the schema's most common queries. Sharding eval_run by triggered_by ('ci_pipeline' vs 'manual' vs 'scheduled') would be actively worse: that column has very low cardinality (only 3 real values) and almost certainly skews heavily toward 'ci_pipeline' in practice (most eval_run rows come from automated CI, not manual or scheduled triggers) -- a textbook hot-shard setup per sharding_and_partitioning.html's section 2, AND it would decouple eval_run from eval_result's own time-based sharding entirely, turning every single Q1-style JOIN into a cross-shard query regardless of which specific run is being looked up. The general principle: two tables in a header/detail relationship that are ALWAYS queried together (via JOIN) should be sharded by a CONSISTENT, co-locating key, so their join stays within one shard for the common case -- exactly the "shard key chosen so most real queries stay within a single shard" criterion sharding_and_partitioning.html's section 3 established generally.
Problem 2 · Deciding what changes if the dominant access pattern shifts

Suppose a new product requirement emerges: a "dataset health" dashboard that shows aggregate pass rates PER DATASET across all of history, becoming a heavily-used, primary query pattern (not just an occasional one). Would this change section 2's shard key recommendation? Explain using the same criteria section 2 applied.

Show solution
This is exactly the kind of access-pattern shift that should trigger RE-EVALUATING the shard key decision, not just adding an index and moving on -- section 1's entire premise was that the shard key follows from the actual, CURRENT dominant access pattern, and that pattern has now genuinely changed. Under the CURRENT time-period sharding, "pass rate per dataset across all of history" is now the worst possible query shape -- it has to fan out across EVERY time-period shard ever created (since a popular dataset's eval runs are scattered across every week of history) and merge partial aggregates from each, exactly the expensive cross-shard coordination sharding_and_partitioning.html's section 3 described, now happening on every load of this new, HEAVILY-USED dashboard rather than as a rare exception. If this dataset-health pattern truly becomes a PRIMARY, high-frequency access pattern (not just occasional), the honest answer is that sharding by dataset_id starts looking more attractive despite section 2's original hot-shard concern -- OR, more likely in practice, this argues for NOT re-sharding the primary table at all, but instead maintaining a separate, precomputed AGGREGATE table (per-dataset rolled-up pass rates, updated incrementally as new eval_result rows land) that serves this specific new dashboard directly, without forcing either shard key to serve two genuinely conflicting dominant access patterns at once. This mirrors read_replicas_and_dashboard_caching. html's own principle: an expensive, frequently-repeated aggregate query is often better served by precomputing/caching its answer than by trying to make the PRIMARY schema's sharding equally good at every possible query shape simultaneously.
Problem 3 · Tracing exactly why the CI gate's read-your-own-write problem is a replication issue, not a sharding issue

Section 3 identifies the CI/CD gate's read as needing special handling. Is this specifically a REPLICATION concern, a SHARDING concern, or both? Justify by explaining what would (and wouldn't) happen if the gate's read were routed to the correct SHARD but a lagging REPLICA of that shard.

Show solution
Purely a replication concern, not a sharding one -- and separating these two is exactly the point worth being precise about. Sharding determines WHICH shard a given row lives on; replication determines which COPY of that shard (primary vs a given follower) a specific read is served from. The CI gate's read for its own just-completed run is trivially routed to the CORRECT shard -- per section 2, the run's own started_at timestamp identifies its time-period shard directly, no ambiguity, no fan-out needed, sharding is doing its job correctly here. The actual problem is entirely on the REPLICATION side: even having found the right SHARD, if that read gets served from a REPLICA of that shard rather than the shard's own PRIMARY, and that replica hasn't yet caught up to the write the CI pipeline just performed moments earlier (section 3's replication.html-sourced lag concern), the gate could see an incomplete eval_result set for that run and make an incorrect blocking decision -- purely because of WHICH COPY was read, with the correct shard having been identified successfully throughout. This confirms section 3's fix (route this one read to the shard's primary, or use the same connection that wrote it) is a replication-routing fix, completely independent of and unaffected by whatever shard key section 2 chose -- the two concerns compose but don't interact here, exactly the way database/read_replicas_and_dashboard_caching.html's Problem 5 established that replication lag and (in that lab's case) cache TTL are independent, STACKING sources of staleness, each needing its own separate fix.
Problem 4 · Evaluating a proposal to shard eval_result by test_case_id instead

A teammate proposes sharding eval_result by test_case_id instead, arguing it would make eval_results_schema.html's Q3 ("does tc-882 fail consistently across runs") a single-shard query. Evaluate this proposal against section 1's established DOMINANT access pattern, not just Q3 in isolation.

Show solution
The teammate is locally correct about Q3 specifically -- sharding by test_case_id WOULD make "all history for one specific test case" a single-shard lookup, genuinely improving that one query. But evaluating it against section 1's actual DOMINANT pattern (not just Q3 in isolation) reveals a worse overall trade: Q1 and Q2 -- arguably the more operationally CRITICAL queries, since Q2 is what a CI gate runs on EVERY SINGLE deploy, and Q1 is what most dashboards show by default -- both become WORSE under test_case_id sharding than under time-period sharding. Q2 ("failing results from the most recent run") would now have to fan out across potentially every test_case_id shard, since a single run's results span MANY different test cases scattered across however many shards those test_case_ids hash to -- exactly the kind of regression sharding_and_partitioning.html's section 3 warned a bad shard key produces even when it happens to serve ONE query type well. The general lesson, directly connecting back to section 1's opening principle: evaluating a shard key against a single query in isolation (here, Q3) without weighing it against the FULL set of real, frequently -run queries is a common mistake -- optimizing for a comparatively rare "trace one test case's history" investigation at the cost of degrading the CI gate's every-single-deploy query and the default dashboard's every-single-load query would be a bad trade in practice, even though the proposal isn't WRONG about the one specific query it targets. A better fix for Q3 specifically, without resharding the whole table, is simply a good secondary INDEX on (test_case_id, run_id) within each time-period shard -- exactly the indexing strategy eval_results_schema. html's own section 3 already recommended -- giving Q3 reasonable performance WITHIN whichever shard(s) it needs to touch, without sacrificing the dominant patterns' single-shard performance to do it.
Problem 5 · Designing the failover story for a lost eval-data shard's primary

Using replication.html's failover/split-brain reasoning and this lab's asynchronous replication decision, what happens to the CURRENT month's eval-data shard if its primary crashes, and is any eval data at risk of being permanently lost?

Show solution
Per replication.html's failover mechanics, the surviving followers of that ONE shard (not the whole system -- sharding means only that specific shard's primary/follower set is affected, per section 2's per-shard replication topology) coordinate to promote one follower to become the new primary for that shard, typically favoring whichever follower has the LEAST replication lag to minimize data loss -- identical mechanics to replication.html's general case, just scoped to one shard rather than a single, whole-database primary. Is any data at risk? Yes, genuinely, and this is the direct, honest cost of section 3's asynchronous replication choice: because writes are confirmed to the CI pipeline the moment they land on the PRIMARY, without waiting for any follower to acknowledge, any eval_result rows written to the old primary but NOT YET replicated to the promoted follower at the moment of the crash are lost -- they existed on the crashed primary's disk, potentially momentarily, but never made it to any surviving copy. This is precisely the trade-off section 3's argument accepted deliberately: eval data isn't in the critical path of a live user request, so this small, bounded risk of losing a handful of very-recently-written rows during a rare primary crash is an acceptable cost in exchange for not paying synchronous replication's write-latency tax on EVERY eval_result insert, unlike financial transaction data where that same risk would be unacceptable. The practical mitigation isn't switching to synchronous replication for all eval data -- it's making sure the CI/CD gate (section 3) treats a just-crashed-and- failed-over shard's very recent history as suspect and, if a gate decision genuinely can't be made confidently right after such a failover, erring toward blocking the deploy rather than assuming missing rows mean the eval suite passed.
