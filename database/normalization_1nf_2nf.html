01 — What problem normalization is even solving

Why normalize a table at all

Start here, before any tables. Imagine a school keeps one single master spreadsheet listing every student, alongside their teacher's name, that teacher's office number, and a comma-separated list of the student's courses, all crammed into one row per student. It works fine for reading — until a teacher moves offices, and now you have to hunt down and edit dozens of rows, one for every student that teacher has, all saying the same thing. Miss even one row, and now your spreadsheet is quietly lying — it says the same teacher has two different office numbers depending on which row you look at.

That's the entire problem normalization exists to solve: every fact should be stored in exactly one place. When "Ms. Lee's office is Room 204" is copy-pasted into fifty different rows instead of stored once, you've created fifty separate opportunities for that fact to become inconsistent with itself. Database designers gave this problem a name and a fix: normalization — a series of rules, called normal forms, that each catch a specific way a table can end up with duplicated or tangled facts, and each tell you exactly how to split the table to fix it.

1NF and 2NF are the first two rules in that series — the foundational ones almost every other rule builds on top of. This lab covers exactly those two, deeply, with tables you can watch get restructured.

The three anomalies normalization prevents

Before the rules themselves, it helps to know exactly what a badly-organized table costs you in practice. Un-normalized data causes three specific, well-known problems:

Update anomaly

The same fact is duplicated in multiple rows. Update it in one row but miss another, and the table now contradicts itself — like the teacher's office number example above.

Insertion anomaly

You can't record a fact until an unrelated fact also exists. E.g. you can't add a new course to the catalog until at least one student has enrolled in it, because "course" data only exists attached to a student row.

Deletion anomaly

Deleting one fact accidentally deletes another, unrelated fact along with it. E.g. the last student drops a course, and the only record that course ever existed disappears too.

The throughline: every anomaly above traces back to the same root cause — a fact that should have exactly one home instead has zero, one-of-many, or none at all, depending on unrelated data. Normalization is the systematic fix: identify where a table is mixing together facts that don't actually belong together, and split them into separate tables connected by keys.
02 — Rule one: one value per cell

First Normal Form (1NF): atomic values, no repeating groups

Start here, before any tables. Picture a single mailbox slot meant to hold exactly one letter. If you try to cram three separate letters into that one slot, the mail carrier can't tell where one letter ends and the next begins, addresses get confused, and eventually something gets lost or misdelivered. A database cell has exactly the same expectation: it's a slot meant to hold one value, not a bundle of several values squeezed together.

First Normal Form (1NF) is the rule that enforces this. A table satisfies 1NF when two conditions both hold:

  • Atomic values — every cell holds exactly one indivisible value, never a list or a combination of several values jammed together (like "Math, Art, History" in a single "courses" cell).
  • No repeating groups — there isn't a set of columns that repeats itself to hold a variable number of similar things (like course1, course2, course3 columns, which fall apart the moment a student takes a 4th course).

Why this matters: the non-atomic "courses" column can't be searched, filtered, indexed, or joined by a single course cleanly — the database has no idea "Math, Art" secretly contains two separate facts, so WHERE courses = 'Art' would need to become a fragile string-matching hack (LIKE '%Art%'), which also wrongly matches something like "Arts and Crafts." Splitting into one row per (student, course) pair makes every value a single, clean, searchable fact — this is the atomicity 1NF requires.

Spotting the "repeating columns" violation

The same underlying problem shows up in a second disguise — instead of comma-separating values into one cell, some designs add numbered columns instead:

students (repeating group)
idnamecourse_1course_2course_3
1AmyMathArt
2RaviArtHistoryGym
Why this is just as bad: this table technically has one value per cell — but course_1, course_2, course_3 is a repeating group: the same kind of fact ("a course this student takes") spread sideways across multiple columns instead of down multiple rows. It breaks the moment a student takes a 4th course — you'd need to alter the table's structure itself to add a course_4 column, and any query asking "does this student take X" has to check three separate columns instead of one. The 1NF-compliant fix is identical to before: one row per (student, course) pair.
03 — Rule two: every non-key column depends on the WHOLE key

Second Normal Form (2NF): no partial dependency on part of a composite key

Start here, before any tables. Imagine a hotel's guest ledger where each row is identified by the pair (room number, guest name) — because the same room hosts different guests over time. Now suppose you also store "hotel's swimming pool hours" in that same table. The pool hours have nothing to do with which guest is in the room — they only depend on the room's floor, or really, they don't depend on the room or guest at all. Storing them in a table keyed by (room, guest) means the exact same pool hours get copied into every single guest row, and if the pool hours change, you have to update every row that ever mentioned them.

That's exactly the shape of problem Second Normal Form (2NF) catches. But first, 2NF only applies to tables with a composite key — a primary key made of more than one column together (like our (room, guest) pair). If a table's primary key is a single column, it automatically satisfies 2NF as long as it's already in 1NF — there's no "part of the key" to depend on partially.

2NF's actual rule: every non-key column must depend on the entire composite key — not just part of it. A column that only needs part of the composite key to determine its value has what's called a partial dependency, and that's the violation.

Interview-ready definition: a partial dependency exists when a non-key attribute depends on only a subset of a composite primary key, rather than the whole key. 2NF requires a table to already be in 1NF, and additionally requires every non-key attribute to be fully functionally dependent on the entire primary key. The fix is always the same shape: move each partially-dependent attribute, together with the part of the key it actually depends on, into its own separate table.
04 — Diagnosing a table you're handed cold

Spotting a 1NF / 2NF violation in a sample table

Start here, before the checklist. When you're handed an unfamiliar table — in an interview, a legacy codebase, or a real migration — you need a repeatable process, not a vague gut feeling of "this looks messy." Here's the exact two-question sequence to run through, in order:

  1. 1NF check: does any single cell hold more than one value (comma-separated, or otherwise combined)? Is there a set of numbered columns standing in for a variable-length list? If yes to either, it's not in 1NF — fix that first, since 2NF assumes 1NF already holds.
  2. 2NF check: does the table have a composite primary key (more than one column)? If not, it's automatically in 2NF. If so, look at every non-key column and ask: "to know this value, do I need the WHOLE key, or would part of the key already tell me?" Any column answerable from just part of the key is a 2NF violation.

Practice problems

Work each one out before expanding the solution — try sketching the fixed table structure on paper first.

Problem 1 · Spot the 1NF violation

A recipes table has columns (recipe_id, name, ingredients) where ingredients stores a value like "flour, sugar, eggs". Explain the violation and redesign it into 1NF-compliant tables.

Show solution
Violation: `ingredients` is not atomic -- it packs multiple separate facts (each individual ingredient) into one cell as a comma-separated string. Fix: split into two tables -- recipes(recipe_id, name) recipe_ingredients(recipe_id, ingredient) Now each row of recipe_ingredients holds exactly one (recipe, ingredient) pair, and "does this recipe contain flour" becomes a simple, indexable equality check instead of a fragile string search.
Problem 2 · Full key or partial key?

A table order_items(order_id, item_id, quantity, item_price, warehouse_location) has composite key (order_id, item_id). item_price is the price of that specific item (same regardless of which order it's in). warehouse_location is which warehouse the item ships from (also fixed per item, regardless of order). Which columns violate 2NF, and why?

Show solution
quantity: depends on BOTH order_id and item_id (how many of this item were ordered, in this specific order) -- full dependency, OK. item_price: depends on item_id ALONE -- the price doesn't change based on which order it appears in. Partial dependency -- 2NF violation. warehouse_location: depends on item_id ALONE, same reasoning. Partial dependency -- 2NF violation. Both item_price and warehouse_location should move into a separate items(item_id, item_price, warehouse_location) table, leaving order_items(order_id, item_id, quantity) holding only what truly needs both halves of the key.
Problem 3 · Does 2NF even apply here?

A table users(user_id, email, signup_country) has a single-column primary key, user_id. A teammate claims this table might have a 2NF violation because signup_country "doesn't really depend on the whole thing." Are they right?

Show solution
No -- 2NF violations are specifically about PARTIAL dependency on a COMPOSITE key. This table's primary key is a single column (user_id), so there is no "part of the key" for a column to depend on partially -- every non-key column either depends on the full key (the only option available) or it doesn't belong in this table at all (which would be a different issue, not a 2NF violation). Any table whose primary key is a single column automatically satisfies 2NF, as long as it's already in 1NF.
Problem 4 · Diagnose and fully redesign

You're handed bookings(booking_id, guest_id, guest_phone, room_number, room_type, nights_booked) with composite key (booking_id, room_number) — one row per room booked within a booking, since a single booking can include several rooms. Diagnose every 1NF and 2NF issue, then write out the corrected set of tables.

Show solution
1NF: no violation here -- every cell already holds a single atomic value, and there's no repeating group. (This one only has a 2NF problem.) 2NF check, column by column: - nights_booked: depends on BOTH booking_id and room_number (a booking might book room 101 for 2 nights and room 102 for 4 nights) -- full dependency, OK. - guest_phone: depends on booking_id ALONE, since a booking has one associated guest, and the phone number doesn't change per room -- partial dependency, VIOLATION. (guest_id itself is fine to keep in this table, since it's the other half of describing "whose booking is this," but guest_phone is a fact ABOUT the guest, not about the booking-room pair.) - room_type: depends on room_number ALONE, since a given room's type doesn't change depending on which booking it's part of -- partial dependency, VIOLATION. Corrected tables: bookings(booking_id, guest_id) guests(guest_id, guest_phone) rooms(room_number, room_type) booking_rooms(booking_id, room_number, nights_booked) Each fact -- guest phone, room type, nights for this specific booking+room -- now lives in exactly one place.
