01 — Five steps, applicable to any system before you've written a line of schema

The general capacity estimation method

Start here, before any numbers. Think about estimating how much luggage space a moving truck needs for a house move, versus just guessing "big truck" or "small truck." You wouldn't guess — you'd count the rooms (entities), estimate roughly how many boxes each room produces (rows per entity), estimate how big an average box is (bytes per row), multiply it out, and then round UP because you know you're forgetting things and moving trucks come in fixed sizes anyway (headroom). Capacity estimation for a database is the exact same five-step process, just with rows and bytes instead of rooms and boxes.

The five steps

  1. Identify the entities — what are the actual "nouns" the system needs to store? (Not columns yet — just the tables/collections themselves.)
  2. Estimate row/event counts and growth rate — how many of each entity gets created per day/second, and does that rate grow over time (more users, more traffic) or stay roughly flat?
  3. Estimate bytes per row — a rough average size per record, including any large fields (JSON blobs, text) that dominate the estimate.
  4. Multiply out to storage over time — rows/day × bytes/row × days = storage at 1 year, 5 years. This is where you find out if the answer is "fits on a laptop" or "needs a distributed store."
  5. Estimate read/write QPS from usage assumptions, sized for PEAK — not the average request rate, the busiest moment you'd realistically need to survive without falling over. Section 4 makes this concrete.
Interview-ready definition: capacity estimation is the five-step process of identifying entities, estimating their growth rate, estimating bytes per row, multiplying out to total storage over a defined time horizon (typically 1 and 5 years), and estimating read/write throughput sized for peak load rather than average — done BEFORE detailed schema design, because the resulting order-of-magnitude numbers (megabytes vs. terabytes, tens vs. thousands of QPS) decide fundamental architectural choices — a single Postgres instance vs. a sharded cluster, a normalized schema vs. a denormalized read-optimized one — that are expensive to reverse after the fact.

04 — The average QPS number will pass code review and then fall over in production

Sizing for peak, not average

Start here, before the formula. A restaurant that sizes its kitchen staff for the AVERAGE number of customers across a full 24-hour day would be catastrophically understaffed at 7pm on a Friday — the average smooths right over the exact moment that actually determines whether the kitchen survives. The same is true for a database's write throughput: the AVERAGE requests/sec across a full day is almost always a wildly misleading number to provision for, because real traffic is never flat — it clusters around specific hours, specific days, or specific events (a capstone demo day, an incident causing retry storms).

# The calculator above computes avg QPS as: avg_write_qps = (runs_per_day + toolcalls_per_day + spans_per_day) / 86400 # But a realistic usage pattern concentrates most activity into a # working-hours window, not spread evenly across 24 hours -- and on # top of that, bursts (batch evals kicking off, a demo, a retry storm # after a downstream failure) spike well above even the busy-hour rate. # The peak-to-average multiplier in the calculator (default 4x) is a # standard planning heuristic: provision write capacity for AVERAGE # QPS times that multiplier, not average QPS alone. peak_write_qps = avg_write_qps * peak_multiplier

Where does a defensible peak multiplier come from in practice? Three real sources, worth naming explicitly rather than picking a number arbitrarily: (1) TIME-OF-DAY concentration — if usage clusters into an 8-hour working window instead of spreading over 24, that alone is a 3x multiplier before any burst behavior; (2) EVENT-DRIVEN spikes — a batch eval run (per evals-and-observability/pytest_evals_practice.html) kicking off hundreds of agent runs at once; (3) FAILURE-INDUCED bursts — a downstream MCP server failing and every caller retrying simultaneously, exactly the kind of burst systems/enterprise_mcp_agent_gateway_design.html's circuit breaker was designed to contain on the SERVING side, but which still shows up as a write burst on the telemetry/audit side.

Interview-ready definition: sizing for peak means provisioning write/read capacity for the busiest realistic moment the system must survive without degrading, not the 24-hour average — computed as average throughput times a peak multiplier derived from time-of-day concentration, known event-driven spikes (batch jobs, demos), and failure-induced retry bursts. A system provisioned only for average QPS will pass every load test that uses average traffic and then fail during the exact moments (a demo, an incident) when failing is most visible and most costly.

Problem 1 · A "light usage" assumption set

Set DAU=50, runs/user/day=3, tools/run=2, spans/run=6, retention=30 days, peak multiplier=3x. By hand, compute agent runs/day and total storage over the retention window (assume the same per-row byte estimates from section 2: ~800B/run, ~2KB/tool call, ~500B/span). Then check against the calculator.

Show solution
Agent runs/day = 50 * 3 = 150 runs/day. Tool calls/day = 150 * 2 = 300 tool calls/day. Spans/day = 150 * 6 = 900 spans/day. Storage/day = (150 * 800B) + (300 * 2000B) + (900 * 500B) = 120,000B + 600,000B + 450,000B = 1,170,000B ≈ 1.17MB/day Storage @ 30 days = 1.17MB * 30 ≈ 35MB. This is a genuinely tiny number -- comfortably "fits on a laptop, Postgres with no special tuning is more than sufficient." The exercise here isn't the arithmetic itself, it's recognizing that at THIS scale, essentially none of the distributed-systems machinery from this week's design mocks (sharding, tail-based sampling, circuit breakers) is justified yet -- correctly identifying "this doesn't need that yet" is as much a real skill as knowing how to design the distributed version when the numbers actually call for it.
Problem 2 · A "demo day" burst on top of light usage

Using Problem 1's light-usage numbers, the capstone is being demoed to 40 evaluators simultaneously, each firing off 5 agent runs in a tight 2-minute window (in addition to normal background usage). Estimate the write QPS during that 2-minute window, and compare it to Problem 1's average QPS. Does the 3x peak multiplier from Problem 1 actually cover this?

Show solution
Demo burst: 40 evaluators * 5 runs = 200 runs compressed into 2 minutes (120 seconds). Each run also produces ~2 tool calls and ~6 spans (same ratios as Problem 1), so total rows in that window: runs: 200 tool calls: 200 * 2 = 400 spans: 200 * 6 = 1,200 total rows: 1,800 over 120 seconds = 15 rows/sec during the burst Problem 1's average, spread over a full day: (150 + 300 + 900) rows / 86,400 sec ≈ 0.0156 rows/sec. 15 / 0.0156 ≈ 960x Problem 1's average QPS -- FAR beyond the 3x peak multiplier used in Problem 1's provisioning. This is exactly the "event-driven spike" category section 4 named explicitly, and it's a realistic, not contrived, scenario for a capstone specifically: a demo day is precisely the kind of concentrated, short-window, human- triggered burst that a smooth "3x the daily average" heuristic completely fails to capture, because the heuristic was modeling DIFFUSE time-of-day concentration, not a literally simultaneous multi-user event. The practical fix isn't raising the general peak multiplier to 960x (wildly over-provisioning for the 99.9% of days that aren't demo day) -- it's recognizing that KNOWN, SCHEDULABLE events like a demo deserve their own explicit capacity check ("can the system handle 40 concurrent evaluators for 2 minutes") separate from the general day-to-day peak multiplier, exactly the same reasoning that led enterprise_mcp_agent_gateway_design.html to size its gateway's instance count off a stated burst assumption rather than a single blended average.
Problem 3 · A "5-year retention" compliance requirement

Set DAU=200, runs/user/day=6, tools/run=4, spans/run=8 (the calculator's defaults) with retention pushed to 1825 days (5 years). Using the calculator, what's the resulting storage figure, and what does that number suggest about whether "one Postgres instance, unmodified" remains a reasonable architecture?

Show solution
Working the defaults by hand first: runs/day = 200*6 = 1,200. tool calls/day = 1,200*4 = 4,800. spans/day = 1,200*8 = 9,600. Storage/day = (1,200*800) + (4,800*2000) + (9,600*500) = 960,000 + 9,600,000 + 4,800,000 = 15,360,000B ≈ 15.4MB/day At 5 years (1,825 days): 15.4MB * 1,825 ≈ 28GB. 28GB is still comfortably within a single well-resourced Postgres instance's capabilities on modern hardware -- this is NOT yet a "you need sharding" number the way distributed_telemetry_ingester_design.html's 180TB unsampled estimate was. The more relevant architectural question at 28GB over 5 years isn't storage CAPACITY at all -- it's whether querying 5 years of unaggregated span-level data efficiently needs something beyond a single un-tuned table: appropriate indexing (database/indexing.html), and likely PARTITIONING the traces/spans table by time range (month or quarter) so that a query scoped to "recent" data doesn't have to scan 5 years of rows to find it, even though the raw byte count alone doesn't force sharding or a distributed store. This is a genuinely different lesson from Problem 2: Problem 2 showed a SHORT BURST can demand real architecture even at otherwise-tiny scale; Problem 3 shows a LARGE TIME HORIZON can demand query-shape changes (partitioning, indexing) well before it demands a fundamentally different storage architecture (sharding). Both are real capacity findings; neither shows up if you only ever check the raw total-bytes number in isolation.
