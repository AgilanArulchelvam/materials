DATABASE FUNDAMENTALS LAB · TIME-SERIES SCHEMA DESIGN

Every row has a timestamp, almost nothing ever gets updated, and yesterday's precision isn't worth keeping forever.

Time-series data — sensor readings, metrics, logs — has a write pattern that looks nothing like a typical transactional table: overwhelmingly append-only, rarely if ever updating an old row, queried mostly by time range. This lab animates the same sensor data laid out narrow (one row per metric reading) versus wide (one row per timestamp, a column per metric), builds a retention/downsampling pipeline that gets coarser the older data gets, and works through exactly why this access pattern demands a different schema shape than an OLTP table.

01 — One row per fact, or one row per moment — the same data, laid out two ways

Wide vs narrow table design for time-series data

Start here, before any schema. Imagine logging a room's conditions every minute: temperature, humidity, and CO2 level. You could keep a single notebook page per minute, with three columns filled in side by side — or you could keep one long list where every single reading gets its own line: "10:01, temperature, 21.3", "10:01, humidity, 44", "10:01, CO2, 512", "10:02, temperature, 21.4"... The second approach writes three times as many lines for the same information, but it never needs to change its page layout no matter how many new things you start measuring — a fourth sensor just adds more lines, not a redesigned notebook.

A narrow (also called "long" or "tall") time-series table stores one row per (timestamp, metric_name, value) triple — every individual reading of every individual metric is its own row. A wide table stores one row per timestamp, with a separate column for each metric being tracked (temperature, humidity, co2, each its own column). The exact same underlying data, laid out two structurally different ways.

Narrow

Flexible: adding a new metric is just more ROWS with a new metric_name value — no schema change required at all. Cost: far more total rows for the same data (N timestamps × M metrics = N×M rows), and querying "all metrics at one timestamp" requires filtering/grouping across many rows instead of reading one.

Wide

Compact: N timestamps = N rows regardless of metric count, and "all metrics at this timestamp" is a single-row read. Cost: adding a new metric requires an actual schema change (ALTER TABLE to add a column) — and existing rows get a NULL/default in that new column for all the timestamps before the metric existed.

Interview-ready definition: a narrow (long) time-series schema stores one row per individual (timestamp, metric_name, value) reading, trading a much larger row count for complete schema flexibility — adding a new metric never requires a schema migration, just new rows. A wide schema stores one row per timestamp with a dedicated column per tracked metric, trading that flexibility for a far smaller row count and cheaper "give me every metric at this moment" queries — at the cost of requiring an actual ALTER TABLE (and backfilling NULLs into every prior row) whenever a genuinely new metric needs to be tracked. Neither is universally correct; the choice depends on how often the metric set actually changes and how queries are shaped.
02 — You cannot keep every raw data point forever, and mostly you don't need to

Retention and downsampling strategies

Start here, before the tiers. Imagine a security camera that records in full HD forever — the storage cost grows without bound, but nobody actually needs frame-by-frame detail from footage recorded three years ago. A much more practical policy: keep full-resolution footage for a recent window (say, the last week), then keep only a lower-resolution highlight reel for the month after that, and just a daily summary snapshot for anything older still. You lose precision on old footage, but you were extremely unlikely to need frame-level detail from a year-old Tuesday afternoon anyway — and you never run out of storage.

Downsampling applies this same idea to time-series data: keep raw, full-precision data points only for a short recent window, and progressively AGGREGATE (average, min/max, sum — whatever's appropriate for the metric) older data into coarser and coarser time buckets the further back it goes. A common concrete tiering: raw per-second (or per-reading) data for the last 24 hours, per-minute aggregates for the last month, per-hour aggregates beyond that. This keeps total storage roughly bounded even as the time series grows forever, because old data occupies dramatically fewer rows once it's been aggregated down.

Note the row-count difference: keeping a full YEAR of raw per-second data for one metric would be over 31 million rows; the same year, downsampled per this tiering (1 day raw + 29 days per-minute + the rest per-hour), is under 50,000 rows — several orders of magnitude smaller, while still preserving a genuinely useful (if coarser) picture of everything beyond the last day.

What's lost, and why it's usually an acceptable trade: downsampling is lossy — once raw per-second data has aged out and only the per-hour aggregate remains, a brief anomaly (a 3-second spike) that occurred 6 months ago and got averaged into an hour-long bucket is genuinely no longer recoverable at its original resolution. This is an acceptable trade specifically because time-series queries over OLD data overwhelmingly ask for trends and patterns over long ranges ("what did average CPU load look like across Q2"), not "the exact reading at 3:14:07am six months ago" — and for the rare case where forensic-level historical precision truly matters, some systems keep raw data in cold, cheap archival storage even after it's aged out of the queryable downsampled tiers, just at a cost and latency that make it unsuitable for routine queries.
Interview-ready definition: retention and downsampling is the practice of keeping full-precision raw time-series data only for a short recent window, then replacing older data with progressively coarser time-bucketed aggregates (e.g. raw per-second for the last day, per-minute for the last month, per-hour beyond that) rather than retaining every raw point forever. This keeps total storage bounded despite the time series growing without limit, trading fine-grained precision on old data (which is usually not needed — most queries over old data ask about trends across long ranges, not exact individual readings) for dramatically reduced row counts and storage cost.
03 — Append-only and read-by-range vs update-heavy and read-by-key

Why time-series schemas differ from transactional schemas

Start here, before the comparison. A typical OLTP (transactional) table — an e-commerce order, a user profile, a bank account balance — gets both read AND updated constantly: a customer's shipping address changes, an order's status field gets updated a dozen times as it moves through fulfillment, an account balance updates on every transaction. A time-series row, once written, essentially never changes again — a sensor reading from 10:03am is a historical fact about what the sensor reported at that instant, and there's no future event that would ever legitimately "correct" that row after the fact. This is a fundamentally different write pattern, and it changes what the schema and storage engine should actually be optimized for.

DimensionTime-series schemaTypical OLTP (transactional) schema
Write patternAppend-only — new rows constantly, old rows essentially never updatedFrequent updates to existing rows (status changes, balance updates, profile edits)
Query patternMostly range scans over time ("last 24 hours," "this quarter") and aggregationMostly point lookups by primary/foreign key ("this specific order," "this user")
Row lifespanA row is a historical fact — write once, read many times, essentially immutableA row represents current state — actively mutated over its lifetime
Volume growthUnbounded, constant — every second/minute produces more rows indefinitelyGrows with business activity (new users, new orders), typically much slower
What the engine optimizes forFast sequential/bulk writes, fast time-range scans, compression of similar consecutive valuesFast point lookups by key, fast in-place updates, strong single-row consistency guarantees

This is exactly why specialized time-series databases exist as a distinct category (rather than everyone just using a general-purpose OLTP database for everything): a storage engine optimized for time-series workloads can exploit the append-only, rarely-updated, range-scanned access pattern in ways a general OLTP engine's B-tree-per-row design doesn't — for example, storing consecutive readings of the same metric physically together (favoring the time-range-scan access pattern) and applying aggressive compression on consecutive similar values (since sensor readings often change gradually, not randomly, between adjacent timestamps).

Interview-ready definition: time-series schemas differ from transactional (OLTP) schemas because their access pattern is fundamentally different: time-series writes are overwhelmingly append-only with old rows essentially never updated after being written, and queries are dominated by time-range scans and aggregation rather than point lookups by key — versus OLTP's frequent in-place updates to individual rows and predominantly key-based point-lookup queries. This difference in access pattern is why time-series-optimized storage engines make different design trade-offs than general-purpose OLTP engines (favoring sequential write throughput, time-range scan speed, and compression of similar consecutive values, over the fast point-update and strong per-row consistency guarantees an OLTP engine prioritizes), and why treating a genuinely time-series workload as if it were a typical OLTP table often performs poorly at scale.

Problem 1 · Choosing narrow vs wide for a specific scenario

A fleet-monitoring platform tracks a rapidly growing, frequently-changing set of metrics per vehicle (new sensor types get added to the fleet every few weeks as new hardware ships), and most queries ask for a single specific metric's trend over time, rarely "give me every metric for this vehicle at this instant." Which layout — narrow or wide — fits better, and why?

Show solution
Narrow is the better fit here, and the scenario is built around two details that both point that way. First, "new sensor types get added every few weeks" is exactly the case where wide's cost (requiring an actual ALTER TABLE plus NULL-backfilling existing rows every time a new metric appears, per section 1) becomes a recurring operational burden rather than a rare event -- narrow's flexibility (a new metric is just new rows, no schema change) directly avoids paying that cost on a biweekly cadence. Second, "most queries ask for a single specific metric's trend over time, rarely every metric at one instant" plays against wide's actual strength (a single-row read for "everything at this timestamp") and neutralizes what would otherwise be wide's main advantage -- if you're rarely doing the query wide is good at, and you're constantly paying the schema-change cost wide has, narrow's flexibility wins on both axes for this specific access pattern. Wide would be the better answer if the metric set were stable and "all metrics at once" queries were common -- neither of which describes this scenario.
Problem 2 · Computing storage savings from a retention/downsampling policy

Using section 2's tiering (raw per-second for 1 day, per-minute for the next 29 days, per-hour beyond that), compute the total row count for ONE metric over exactly 1 year (365 days), and compare it to keeping raw per-second data for the full year.

Show solution
Raw tier (last 1 day): 86,400 rows (1 reading/second x 86,400 seconds/ day). Per-minute tier (next 29 days): 29 days x 1,440 minutes/day = 41,760 rows. Per-hour tier (remaining 365 - 1 - 29 = 335 days): 335 days x 24 hours/ day = 8,040 rows. Total under the tiered policy: 86,400 + 41,760 + 8,040 = 136,200 rows. Compare to keeping raw per-second data for the FULL year: 365 days x 86,400 seconds/day = 31,536,000 rows. 136,200 / 31,536,000 ≈ 0.43% -- the tiered retention policy uses well under 1% of the row count that full-year raw retention would require, roughly a 230x reduction, while still preserving a genuinely useful (if coarser) view of the full year via the per-hour tier. This concretely demonstrates section 2's claim that downsampling keeps storage bounded despite the underlying time series growing without limit -- the OLDEST data (365 - 30 = 335 days' worth) contributes only 8,040 of the 136,200 total rows, i.e. it barely adds to storage at all despite being the largest TIME SPAN in the policy.
Problem 3 · Diagnosing a wide-table design breaking under a metric-set change

A team built a wide time-series table with one column per metric. Six months in, a new hardware revision reports 12 new metrics the old hardware didn't have, and the team needs to backfill 6 months of history for devices that never reported these metrics at all. What does this require under a wide schema, and how would this same situation have played out under a narrow schema?

Show solution
Under the wide schema: this requires an ALTER TABLE to add 12 new columns, and -- critically -- every one of the millions of EXISTING rows across the prior 6 months now has NULL (or some sentinel) in all 12 new columns, since those readings genuinely never happened for devices running the old hardware. This isn't a bug to fix; it's an accurate reflection of reality (those metrics didn't exist yet for those rows) -- but it does mean the table now has a large, genuinely sparse region (12 columns x 6 months of old-hardware rows, all NULL), which is exactly the kind of storage inefficiency wide tables are prone to when the metric set isn't stable, per section 1's trade-off description. The schema migration itself (adding 12 columns to a massive, actively-written table) can also be a nontrivial operational event depending on the database engine. Under the narrow schema: no schema change is needed at all -- the 12 new metrics simply start appearing as new rows with new metric_name values once the new hardware starts reporting them, and there is no backfill problem for old rows, because narrow's structure was never committed to a fixed, enumerated set of metrics to begin with. Old devices simply never produce rows for those 12 metric_names, which requires no special representation (no NULL columns) -- their absence is just the absence of rows, not a NULL value sitting in a column that exists for every row regardless of relevance. This is the concrete, recurring cost section 1 warned about: a genuinely evolving metric set is one of the strongest arguments for narrow over wide, and this problem is that argument playing out at real scale.
Problem 4 · Explaining why an OLTP-style index strategy underperforms on a time-series table

A team puts a time-series table on a general-purpose relational database and indexes it exactly the way they'd index an OLTP table — a B-tree primary key index on an auto-incrementing row ID. Query performance for "give me the last 24 hours of readings for sensor X" is poor. Using section 3's reasoning, explain why, and what indexing/storage approach would fit better.

Show solution
A B-tree index on an auto-incrementing row ID optimizes for exactly the access pattern section 3 describes as TYPICAL OLTP: fast POINT lookups by a specific key value. But the actual query here -- "the last 24 hours of readings for sensor X" -- is a RANGE query over time, filtered by sensor, which is precisely the time-series access pattern section 3 contrasts against OLTP's point-lookup pattern. An auto-incrementing row ID has no relationship to either "this specific sensor" or "this specific time range" -- rows for sensor X's readings across a day are scattered arbitrarily throughout the table in insertion order interleaved with every OTHER sensor's readings, so answering the query requires scanning and filtering a large, non-contiguous swath of the table rather than reading one contiguous chunk. A better fit: index (or physically partition/cluster) the data by (sensor_id, timestamp) rather than by an arbitrary row ID -- this keeps one sensor's readings physically or logically contiguous and ordered by time, so "sensor X, last 24 hours" becomes a genuinely efficient contiguous range scan instead of a scattered filter over the whole table. This is exactly the kind of design choice section 3 attributes to purpose-built time-series storage engines: optimizing physical layout and indexing around time-range-scan-by-series access, rather than around the point-lookup-by-arbitrary-key pattern a default OLTP indexing strategy assumes.
Problem 5 · Reasoning about why time-series rows are treated as immutable

A junior engineer proposes adding UPDATE support to "correct" old sensor readings retroactively when a calibration error is discovered — e.g. "every reading from sensor Y between March 1-15 was actually 2 degrees higher than recorded, update those rows." Using section 3's framing, is this a natural fit for a time-series schema's design, and what's a more idiomatic alternative?

Show solution
This is NOT a natural fit for a time-series schema's design, per section 3: time-series schemas and storage engines are built around the assumption that a row, once written, is essentially immutable -- optimized for append-only writes and range-scan reads, not for in-place updates to arbitrary historical rows. Retroactively UPDATING a two-week window of historical rows fights directly against that design assumption -- it requires locating and modifying a large range of already-written, already-downsampled (per section 2) historical data, which may not even exist anymore at full raw resolution if enough time has passed for it to have been aggregated into coarser tiers -- you can't cleanly "correct" 2 degrees onto an already-averaged per-hour bucket that blended those readings with others. A more idiomatic alternative, consistent with time-series's append-only nature: write NEW rows recording the correction as its own event, rather than mutating the old ones -- e.g. a correction record noting "readings from sensor Y, March 1-15, should be adjusted +2 degrees, applied [today's date]," and have queries/downstream aggregation account for that correction at READ time (or apply it during the next scheduled downsampling pass, while raw data for that window still exists). This preserves the append-only write pattern the whole schema and storage engine are optimized around, keeps a transparent history of WHEN and WHY a correction was made (which retroactively overwriting old rows would destroy), and avoids fighting the storage engine's fundamental design assumption that historical rows don't need to support efficient in-place mutation.
