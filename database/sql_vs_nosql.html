DATABASE FUNDAMENTALS LAB · SQL vs NoSQL

The real question isn't which database is better — it's which one lies about your data less.

The normalization work in the previous labs assumed a relational schema was the right starting point. This lab asks when that assumption is even correct: schema-on-write vs. schema-on-read, where ACID and joins actually earn their cost, and where flexible schemas and horizontal scale win instead — with the real consistency and query-flexibility trade-offs made concrete, not just asserted.

01 — When does "the shape of the data" get decided?

Schema-on-write vs. schema-on-read

Start here, before any code. Think about two different ways to organize a filing cabinet. One approach: before you file a single sheet of paper, you design labeled folders with fixed categories — "invoices," "receipts," "contracts" — and every new document must be trimmed, stamped, and slotted to fit one of those folders, or it gets rejected at the door. The other approach: you just throw every document into one big box as it arrives, however it's shaped, and only when someone actually needs to find something do they dig through the box and figure out on the spot what category a given paper falls into.

That's schema-on-write versus schema-on-read. A relational database enforces its schema at write time — the moment you try to insert a row, the database checks it against the table's fixed columns and types (from the tables-and-keys lab) and rejects anything that doesn't fit. A document database (like MongoDB) or key-value store typically enforces little to no schema at write time — you can insert wildly differently-shaped documents into the same collection — and any "shape" gets imposed later, at read time, by whatever code is doing the reading and deciding how to interpret each document's fields.

TRY INSERTING MISMATCHED DATA INTO BOTH MODELS

SQL table (schema-on-write): users(id, name, email)

{id: 1, name: "Ada", email: "ada@example.com"}

Document collection (schema-on-read): users

{_id: 1, name: "Ada", email: "ada@example.com"}
Try inserting a document with a completely different shape (no email, has phone instead) into both models and see what each one does.
Interview-ready definition: schema-on-write means the data's structure (columns, types, constraints) is validated and enforced by the database at the moment of insertion, guaranteeing every stored record conforms to a known shape. Schema-on-read means the database imposes little or no structure at write time, storing data in a flexible format (commonly JSON-like documents), and structural assumptions are instead applied by application code whenever the data is later read and interpreted.
02 — Where the relational model earns its cost

Where relational (ACID, joins) wins

Start here, before any code. Imagine a bank transferring $100 from your checking account to your savings account. This absolutely must NOT be allowed to half-happen — money leaving checking without arriving in savings (or vice versa) would either destroy value or create it from nothing. You need an operation that is truly all-or-nothing, and that stays correct even if the power goes out mid-transfer, and that behaves correctly even if a thousand other transfers are happening on the same accounts at the same instant.

That's exactly what relational databases are built to guarantee via ACID transactions: Atomicity (all-or-nothing — the transfer either fully happens or fully doesn't), Consistency (the database moves between valid states — you never see a checking account debited with no matching savings credit), Isolation (concurrent transactions don't see each other's half-finished work), and Durability (once committed, it survives a crash). Multi-table transactions with strong ACID guarantees are the relational model's signature strength — exactly the strength financial systems, inventory systems, and anything else where correctness beats raw throughput lean on.

The other relational strength is joins — the ability to combine normalized tables (recall the normalization labs: splitting data to eliminate redundancy) back together on demand, flexibly, for whatever query you need right now. A relational schema doesn't commit up front to exactly how data will be queried later; joins let you ask new questions across the same normalized data without restructuring anything.

BEGIN TRANSACTION; UPDATE accounts SET balance = balance - 100 WHERE id = 1; -- checking UPDATE accounts SET balance = balance + 100 WHERE id = 2; -- savings COMMIT; -- If anything fails between BEGIN and COMMIT, the ENTIRE transaction rolls -- back — the database guarantees you never end up in a state where only -- one of the two UPDATEs took effect.
Interview-ready definition: ACID (Atomicity, Consistency, Isolation, Durability) is the set of guarantees a relational transaction provides: a transaction's operations either all succeed or all roll back together, the database only ever transitions between valid states, concurrent transactions are isolated from each other's intermediate states, and committed changes survive subsequent failures. This makes relational databases the strong default for workloads requiring strict multi-row/multi-table correctness, such as financial transfers or inventory adjustments.
03 — Where flexibility and scale matter more than joins

Where document/key-value wins: flexible schema, horizontal scale

Start here, before any code. Imagine a product catalog for an online marketplace selling everything from books to bicycles to houseplants. A book has an ISBN and a page count; a bicycle has a frame size and a wheel diameter; a houseplant has a light requirement and a watering schedule. Forcing all of these into one rigid relational table means either a table with fifty mostly-NULL columns, or a maze of sub-tables joined together for every single product type. A document database just lets each product be its own self-contained JSON-like document with whatever fields actually apply to it — no schema migration needed every time a new product category is added.

The other major NoSQL strength is horizontal scalability by design. Because most document/key-value stores don't need cross-document joins or multi-row ACID transactions as their primary access pattern, individual documents can be partitioned ("sharded") across many machines with minimal coordination between them — reading or writing document #47291 only ever needs to talk to whichever single shard holds it. Relational databases can be sharded too, but joins across shard boundaries and cross-shard transactions are expensive and awkward precisely because the relational model assumes related data might need to be queried together.

EMBED-DON'T-JOIN: THE DOCUMENT-MODEL DEFAULT

Relational: normalized, joined at query time

-- orders and order_items are separate tables SELECT * FROM orders JOIN order_items ON order_items.order_id = orders.id WHERE orders.id = 42;

Document: embedded, one read, no join needed

{ _id: 42, customer: "Ada", items: [ {product: "Widget", qty: 3}, {product: "Gadget", qty: 1} ] }
Interview-ready definition: document and key-value stores prioritize flexible, per-record schemas (each record can have a different shape without a database-level migration) and horizontal scalability (partitioning data across many machines by key, since most access patterns don't require cross-partition joins or transactions). This makes them a strong fit for high-volume, high-variability data where write throughput and horizontal scale matter more than complex multi-entity consistency guarantees.
04 — What you actually give up

The real trade-offs: consistency models and query flexibility

Many distributed NoSQL systems relax strict consistency in exchange for availability and partition tolerance (the CAP theorem's central trade-off) — offering eventual consistency instead of the immediate, strict consistency a single-node relational database naturally provides. Eventual consistency means: after a write, different replicas of the data might briefly disagree, but will converge to the same value given enough time with no further writes. This is a real, felt trade-off — a user could write a value and, for a brief window, read back a stale one from a different replica.

strict / immediateeventual / relaxed

Query flexibility is the other side of the same coin: SQL's declarative query language plus joins let you ask essentially any question across your normalized schema after the fact, without redesigning storage. Most NoSQL systems trade that away for speed and scale — queries often need to be at least partially anticipated by how you chose to shard/partition and structure documents up front (denormalizing, embedding related data together specifically because you expect to read it together). Asking an unanticipated cross-document question later can be significantly harder or require a separate analytics pipeline.

Interview-ready definition: the SQL-vs-NoSQL decision is fundamentally a trade-off between the relational model's strong consistency, rich transactional guarantees, and flexible ad hoc query power on one side, and NoSQL's flexible per-record schema, simpler horizontal partitioning, and often-relaxed (eventual) consistency on the other — with the right choice determined by which set of guarantees the actual workload needs, not by which technology is newer or more fashionable.

Practice problems

Work each one out before expanding the solution.

Problem 1 · Identifying schema timing

A team stores JSON blobs in a database with no fixed columns, and their application code checks if "phone" in record before using that field. Is this schema-on-write or schema-on-read, and where does the "schema" actually live?

Show solution
Schema-on-read. The database itself enforces essentially no structure at insert time — any shape of JSON is accepted. The "schema" — the assumptions about what fields exist and what they mean — lives entirely in the application code that reads and interprets the records, which is exactly why that code has to defensively check `if "phone" in record` rather than trusting the field is always present.
Problem 2 · Choosing for a banking ledger

You're building the core ledger for a banking app: transfers between accounts must never partially apply, and you need historical reporting that joins transactions against accounts, customers, and branches. Which model, and why?

Show solution
Relational (SQL). Two requirements point directly at it: "must never partially apply" is exactly what ACID atomicity guarantees, and joining across transactions/accounts/customers/branches for reporting is exactly what the relational model's joins are built for. A document store would require either denormalizing (duplicating data across documents, risking inconsistency) or expensive application-level joins to answer the same reporting questions.
Problem 3 · Choosing for a product catalog

You're building a catalog for a marketplace with wildly different product types (electronics, clothing, furniture, digital downloads), expecting rapid addition of new product categories with different attributes, and needing to scale to tens of millions of listings. Which model, and why?

Show solution
Document (NoSQL). The core pain point — wildly varying attributes per product type, with new categories added frequently — is exactly what schema-on-read flexibility solves without constant migrations. The scale requirement (tens of millions of listings) also favors a model designed for horizontal partitioning by key (e.g. product ID) from the start, without needing cross-product joins as the primary access pattern.
Problem 4 · Eventual consistency in practice

A user updates their profile picture on a distributed document database. Two seconds later, a friend viewing their profile from a different region briefly still sees the old picture. Is this a bug? Explain using the vocabulary from this lab.

Show solution
Not necessarily a bug — this is the expected, documented behavior of eventual consistency. The write was applied to one replica (or a subset) immediately, but it takes some time to propagate to every replica across regions. Given enough time with no further writes, all replicas converge to the same value ("eventual" consistency) — the friend briefly reading a stale value from a different, not-yet-updated replica is the trade-off the system deliberately made in exchange for availability and horizontal scale across regions, not an error condition.
Problem 5 · Query flexibility trade-off

A team stores user activity as one document per user, embedding their entire event history as a nested array, because their app almost always reads "give me everything for user X." Six months later, a new requirement appears: "find every user who did event type Y in the last hour, across ALL users." Why is this suddenly hard, and what does it reveal about the trade-off made earlier?

Show solution
The original design optimized specifically for "read everything for ONE user" by embedding and partitioning by user — which is fast and simple for exactly that access pattern. But "find all users who did event Y" is a cross-document query cutting against the partitioning key entirely; it either requires scanning every user's document (slow, doesn't scale) or a separate index/analytics system built specifically for this new access pattern. This reveals the core query-flexibility trade-off from this lab: NoSQL's performance and scale advantages come from anticipating access patterns up front in the data model, and un-anticipated query shapes are exactly where that choice is repaid with difficulty — a relational schema with proper indexes could have answered the new question without a redesign, at the cost of the original "read everything for one user" query being relatively more expensive (a join) instead of a single document fetch.
Problem 6 · Hybrid reasoning

A large e-commerce company uses a relational database for orders/payments and a document database for the product catalog and session data. Justify this hybrid approach rather than picking one system for everything.

Show solution
Different subsystems have genuinely different requirements. Orders and payments need strict ACID transactions (a payment must never partially apply) and benefit from joins across customers/orders/inventory for reporting and correctness checks — a strong fit for relational. The product catalog has highly variable per-product attributes and needs to scale to huge read volume with mostly single-item lookups — a strong fit for a flexible-schema, horizontally-scaled document store. Session data is high-volume, short-lived, simple key-value shaped data with no need for joins or strict multi-row transactions — another strong fit for a key-value/document store. Using one database technology for every subsystem regardless of its actual access pattern would mean accepting unnecessary trade-offs somewhere; the hybrid approach lets each subsystem's storage match its actual consistency and query needs.
