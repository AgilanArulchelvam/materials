DATABASE FUNDAMENTALS LAB · SHARDING & PARTITIONING

One table stops fitting on one machine — so you cut it, and the cut matters.

A single database server eventually runs out of disk, memory, or write throughput for one giant table. Partitioning splits that table apart; sharding spreads the pieces across multiple servers. This lab animates both ways to cut the SAME table (by rows vs by columns), then shows a bad shard key producing a lopsided hot shard next to a good one producing an even spread, and closes with why a query spanning multiple shards has to fan out and merge — the same scatter-gather shape a distributed search faces.

01 — Two different ways to cut the same table

Horizontal vs vertical partitioning

Start here, before any diagrams. Imagine a single massive filing cabinet holding every customer's full paper folder. One way to split the load across two cabinets: keep every folder intact, but put customers A-M in cabinet 1 and N-Z in cabinet 2 — each cabinet holds fewer, but COMPLETE, folders. Another way entirely: keep all customers in both cabinets, but tear each folder in half — cabinet 1 gets the frequently-referenced summary page for every customer, cabinet 2 gets the rarely-touched, bulky attachments (old correspondence, scanned documents) for every customer. Both approaches genuinely split the data across two cabinets, but they cut along completely different axes.

Horizontal partitioning splits a table by ROWS: some rows live in one partition (or shard, or server), other rows live in another, but every partition has the SAME columns — a partition holding "users A-M" has the exact same schema as the partition holding "users N-Z," just a different subset of the actual user records. This is the far more common meaning of "sharding" in a distributed-systems context: spreading rows of one logical table across multiple physical servers by some partitioning key.

Vertical partitioning splits a table by COLUMNS instead: every row still exists in some form in every partition, but different COLUMNS live in different partitions. A common real pattern: frequently-accessed, small columns (id, name, status) live in one table/partition that's read constantly and cheaply, while rarely-accessed, large columns (a big text bio, a JSON blob, an old audit history) live in a separate table/partition that's only touched when specifically needed — keeping the "hot" table smaller and faster to scan without those large columns bloating every row read.

Horizontal partitioning

Solves: one table has too many ROWS for one server (disk, memory, or write throughput limits). Every shard has the full schema, a subset of the records. This is what "sharding" usually means.

Vertical partitioning

Solves: one table has some columns that are read constantly and others that are large but rarely touched, bloating every scan. Every partition has all rows, a subset of the columns.

Interview-ready definition: horizontal partitioning (often called sharding) splits a table's ROWS across multiple partitions or servers based on some partitioning/shard key, with every partition sharing the identical schema — used to distribute total data volume and write/read throughput across machines when the row count itself is the scaling constraint. Vertical partitioning splits a table's COLUMNS across multiple tables or storage locations, with every partition covering all (or most) rows but only a subset of columns — used to separate frequently-accessed columns from large, rarely-accessed ones so that hot-path queries don't pay the I/O cost of columns they never needed, which directly echoes the row-vs-columnar storage trade-off from the storage engines labs, just applied at the schema-design level rather than the physical storage-engine level.
02 — The one decision that determines whether sharding actually helps

Shard key selection and distribution

Start here, before the animation. Imagine splitting a huge crowd into 4 lines by the first letter of their last name, versus splitting them into 4 lines by which MONTH they were born. Both are valid ways to divide people into 4 groups, but if you know that a disproportionate number of last names in this crowd start with S, the last-name split leaves one line enormously longer than the others — while birth month tends to spread people roughly evenly across 12 buckets (and therefore roughly evenly across 4 lines grouped by quarter), because birth month has no similar skew. The SAME splitting mechanism (4 buckets) produces wildly different outcomes purely based on which attribute you chose to split by.

A shard key is the column (or combination of columns) used to decide which shard a given row belongs to. The entire value of sharding — spreading load evenly across multiple servers — depends on the shard key actually distributing data (and, more importantly, TRAFFIC) roughly evenly across shards. A hot shard is what happens when the chosen key doesn't distribute evenly: one shard ends up holding a disproportionate share of the data or, often worse, a disproportionate share of the READ/WRITE traffic, turning that one shard into a bottleneck that defeats the entire point of having spread the data across multiple servers in the first place.

Sharding by signup_date in a growing product is a classic bad-shard-key example: because most users signed up RECENTLY (a growing product has more signups this month than a year ago), a date-range-based shard scheme concentrates a disproportionate share of both the DATA and, critically, the ONGOING WRITE TRAFFIC (new signups, and typically higher activity from newer/more-engaged users) onto whichever shard covers the most recent date range — while shards covering older date ranges sit comparatively idle. Sharding by a hashed user_id instead spreads both data and traffic roughly uniformly, since a good hash function has no correlation with time or any other skewed real-world attribute.

Interview-ready definition: a hot shard occurs when the chosen shard key does not distribute data and traffic evenly across shards, concentrating a disproportionate load onto one or a few shards while others remain comparatively idle — the shard key is the single decision that determines whether horizontal partitioning actually achieves its goal of spreading load, and a shard key correlated with a real-world skew (like signup recency, geographic concentration, or a small number of very popular keys) reliably produces a hot shard even though the sharding mechanism itself is working exactly as designed. The general fix is choosing a shard key with better distributional properties — often a hash of a naturally high-cardinality, low-skew field like user_id — rather than a raw field that happens to correlate with time or popularity.
03 — The cost sharding doesn't advertise up front

Cross-shard query complexity

Start here, before the mechanics. Back at the split filing cabinets: if someone asks "how many total customers do we have whose last name starts with any letter," and customers are split across 2 cabinets by last name, you can't answer by looking in just one cabinet — you have to check BOTH cabinets, count each one's matches separately, and add the two counts together yourself. That extra step — going to multiple places, then combining what you found — didn't exist when everything lived in one cabinet.

A query that can be satisfied entirely within ONE shard (e.g. "fetch this exact user by their shard key") is cheap and fast — exactly as fast as an unsharded query, since the application (or a routing layer) can compute which single shard holds the answer and go straight there. But a query that needs data spanning MULTIPLE shards (e.g. "how many total users signed up this week, across the whole system" when users are sharded by user_id, not date) cannot be answered by any single shard alone. The application has to fan out — send the same query to every shard that might hold relevant data — wait for each shard's partial result, and then merge those partial results into one final answer (summing counts, re-sorting a combined result set, deduplicating, etc.).

# Cross-shard query: fan out to every shard, then merge async def count_signups_this_week(shards): # fan out -- query EVERY shard concurrently, since the answer # could involve rows on any of them partial_results = await asyncio.gather(*[ shard.query("SELECT COUNT(*) FROM users WHERE signup_date >= ?", this_week) for shard in shards ]) # merge -- combine each shard's partial answer into one final answer return sum(partial_results)
This is the same shape as scatter-gather: fanning a query out to multiple independent shards and merging their partial results is structurally identical to the scatter-gather pattern used by distributed search systems — a query is scattered (sent) to every relevant partition/node in parallel, each returns its own partial results, and a coordinating layer gathers and merges them into one final response. Cross-shard database queries and distributed search across partitioned data are the same underlying coordination problem: no single node has the full answer, so the cost of correctness is real network fan-out plus a merge step that didn't exist when everything lived on one machine.

Cross-shard queries are strictly more expensive and more complex than single-shard queries along several dimensions: latency is bounded by the SLOWEST shard's response (not the average), partial failures become a real concern (what happens if one of N shards times out — return an incomplete answer, or fail the whole query?), and some operations that are trivial on one machine (a JOIN across two tables, a globally unique auto-increment ID, a multi-row transaction) become genuinely hard or require entirely different mechanisms once the relevant rows might live on different shards. This is exactly why shard key selection (section 2) matters so much beyond just avoiding hot shards: a shard key chosen so that MOST real queries stay within a single shard (e.g. sharding a multi-tenant SaaS product by tenant_id, when almost every query is already scoped to one tenant) avoids paying the cross-shard fan-out/merge cost on the common path entirely.

Interview-ready definition: a cross-shard query is one that cannot be answered by a single shard alone and must fan out (send the query to every relevant shard concurrently) and then merge (combine each shard's partial results into one final answer) — the same scatter-gather coordination pattern used by distributed search. This is strictly more expensive than a single-shard query: latency is bounded by the slowest responding shard, partial shard failures must be handled explicitly, and operations trivial on one machine (joins, global uniqueness, multi-row transactions) become genuinely harder across shard boundaries. A well-chosen shard key minimizes how often real queries need to cross shard boundaries at all, which is often as important a selection criterion as avoiding a hot shard.

Problem 1 · Classifying a split as horizontal or vertical

A team splits their products table into products_core (id, name, price, in_stock) and products_media (id, full_description, image_urls, video_url), joined by id, because product listing pages only need the core fields but product DETAIL pages need everything. Is this horizontal or vertical partitioning, and why?

Show solution
This is vertical partitioning. Every product still has a row (or a matching pair of rows, joined by id) present in BOTH resulting tables -- nothing about WHICH rows exist in which table has changed, only WHICH COLUMNS live in which table. products_core holds the small, frequently-accessed columns (used on every listing page load); products_media holds the larger, less-frequently-accessed columns (only needed when a user opens a specific product's detail page). This matches the exact pattern described in section 1's "hot columns / cold columns" vertical split -- separating columns by access frequency and size, not separating rows by any key.
Problem 2 · Predicting the hot-shard outcome for a stated shard key

A ride-sharing app shards its "active rides" table by city_id. One city (a huge, dense metro area) accounts for 40% of all rides company-wide; the other 200+ cities split the remaining 60%. Will this shard key produce a hot shard? Explain using section 2's reasoning.

Show solution
Yes, this will produce a hot shard, for exactly the reason section 2 describes: the shard key (city_id) correlates with a real-world skew -- ride volume is heavily concentrated in one dense metro area rather than spread evenly across cities. Whichever shard holds that one city's rides will handle roughly 40% of all active-ride traffic company-wide, while the remaining shards split the other 60% across 200+ cities each, meaning most other shards handle a tiny fraction of the load that the one hot shard does. This is structurally the same failure mode as the signup_date example in section 2 (recent dates get disproportionate traffic) -- a shard key can be a perfectly reasonable, meaningful business dimension (city_id makes intuitive sense for a ride-sharing app, since most queries are probably city-scoped anyway) and STILL produce a hot shard if the underlying real-world distribution of that key's values is skewed rather than uniform. The fix isn't necessarily abandoning city_id entirely (it may still be the right choice for keeping most queries single-shard, per section 3) -- it might instead mean giving the dominant city its own DEDICATED shard (or multiple shards, further sub-partitioned) rather than co-locating it with much smaller cities on a shard sized for average, not peak, city volume.
Problem 3 · Choosing a shard key to minimize cross-shard queries

A multi-tenant B2B SaaS product has almost every query scoped to one customer organization (tenant) at a time — "show tenant X's dashboard," "list tenant X's users." A small number of internal admin queries need data across ALL tenants. Which shard key minimizes cross-shard query cost for the COMMON case, and what does this mean for the rare admin queries?

Show solution
Shard by tenant_id. Since the overwhelming majority of real queries are already naturally scoped to exactly one tenant, sharding by tenant_id means the application can route each of those common queries directly to the ONE shard holding that tenant's data -- no fan-out, no merge, full single-shard-query speed, exactly matching section 3's point that a well-chosen shard key minimizes how often real queries cross shard boundaries. This is a case where the "natural" query pattern of the business domain directly suggests the right shard key, rather than needing to guess. The trade-off this creates: the rare cross-tenant ADMIN queries (e.g. "total active users across all tenants") now unavoidably become cross-shard queries requiring the fan-out-and-merge pattern from section 3, since no single shard has the full picture across every tenant. This is an acceptable trade specifically because those queries are rare and typically not latency-sensitive (an internal admin dashboard can tolerate a slower, fan-out query far better than a customer-facing dashboard could) -- the shard key was chosen to optimize the COMMON, latency- sensitive path at the deliberate cost of the RARE, latency-tolerant path, which is usually the correct prioritization.
Problem 4 · Diagnosing which failure mode is occurring from symptoms

A system sharded across 8 servers by user_id (hashed, uniform) is reported as "slow." On investigation: CPU and disk usage look roughly even across all 8 shards, but the dashboard's "total revenue this month across all users" query takes 12 seconds. Is this a hot-shard problem or a cross-shard-query problem? Justify from the given evidence.

Show solution
This is a cross-shard-query problem, not a hot-shard problem -- and the evidence given directly distinguishes the two. A hot shard would show up as UNEVEN load across shards (one or a few shards pegged at high CPU/ disk usage while others sit comparatively idle), which is explicitly ruled out here ("CPU and disk usage look roughly even across all 8 shards" -- this is exactly what a well-chosen, uniformly-hashed shard key like hashed user_id is supposed to produce, per section 2). The slow query itself -- "total revenue this month across ALL users" -- is inherently a query that spans every shard, since revenue data for different users lives on different shards by design (that's the whole point of sharding by user_id). This forces the fan-out-and-merge pattern from section 3 on every single run: query all 8 shards, wait for the slowest one to respond, sum the partial results. The 12-second latency is consistent with cross-shard fan-out/merge overhead (bounded by the slowest shard, plus merge cost) rather than any one shard being overloaded. The fix here isn't re-sharding by a different key (that would likely just move the cross-shard cost to a DIFFERENT set of queries, per Problem 3's trade-off) -- it's more likely to pre-aggregate this specific cross-tenant metric on a schedule (a materialized rollup table) rather than computing it live via an 8-way fan-out on every dashboard load.
Problem 5 · Combining horizontal and vertical partitioning in one system

Design a partitioning scheme for a users table that needs to: (a) scale past what one server can hold as the user base grows into the tens of millions, and (b) keep hot-path login queries (id, email, password_hash, status) fast, separate from a large, rarely-touched profile_json blob column. Use both concepts from this lab.

Show solution
This calls for BOTH horizontal and vertical partitioning applied together, addressing two genuinely different problems: Horizontal (addresses requirement a — total row count/volume): shard the users table by a hash of user_id across N servers, so that as the user base grows into the tens of millions, no single server has to hold every user's data -- each shard holds a roughly even subset of the total users, per section 2's reasoning about uniform hash-based distribution avoiding hot shards. Vertical (addresses requirement b — hot vs cold columns): WITHIN each shard, split the users table itself into two tables -- a small users_auth table (id, email, password_hash, status) that login queries hit constantly and needs to stay fast and compact, and a separate users_profile table (id, profile_json) holding the large, rarely- accessed blob, joined back by id only when a full profile is actually needed (e.g. viewing a user's full profile page, not every login check). The result: horizontal partitioning solves the "too much total data for one server" problem, and vertical partitioning (applied independently, within each horizontal shard) solves the "one frequently-hit query path shouldn't have to read past a large rarely-needed column" problem. These two techniques address orthogonal problems and combine cleanly -- neither one substitutes for the other, which is exactly why real large-scale systems often use both simultaneously rather than treating "partitioning" as a single decision.
