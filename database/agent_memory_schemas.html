DATABASE FUNDAMENTALS LAB · AGENT MEMORY SCHEMAS

An agent that forgets everything between requests isn't an agent — it's a stateless function with extra steps.

Every agentic system needs somewhere to put what happened: the literal back-and-forth of a conversation, including tool calls and their results, and — separately — the facts and preferences worth remembering long after that specific conversation is over. This lab designs the schema for both: a conversation-turns table with roles and timestamps, and the short-term vs long-term memory split that decides what gets kept in full versus summarized into a vector-indexed store.

01 — Every message, who said it, and when, including the tool in the middle

Schema for conversation turns with roles and timestamps

Start here, before any DDL. Imagine a call-center transcript: every line is timestamped, and every line is attributed to a specific speaker — the customer, the agent, or (in a modern setup) an automated lookup the agent triggered mid-call ("checking your account balance now... it's $412"). An agent conversation's log needs exactly this same shape: not just "what was said," but WHO said it (a role) and WHEN (a timestamp), with tool invocations treated as their own first-class kind of turn, not squeezed into the same bucket as plain conversational text.

CREATE TABLE conversation_turns ( turn_id BIGSERIAL PRIMARY KEY, conversation_id UUID NOT NULL REFERENCES conversations(conversation_id), role TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'tool')), content TEXT, -- the actual message text, NULL for pure tool-call turns tool_call_id TEXT, -- links a 'tool' turn back to the assistant turn that requested it tool_name TEXT, -- e.g. 'get_weather' -- NULL unless role='tool' or this turn triggered one tool_arguments JSONB, -- the arguments the assistant passed, e.g. {"city": "Lisbon"} tool_result JSONB, -- the tool's actual output, NULL until the tool call resolves created_at TIMESTAMPTZ NOT NULL DEFAULT now() ); CREATE INDEX idx_turns_conv_time ON conversation_turns (conversation_id, created_at); -- composite index: the dominant query is "this conversation's turns, -- in time order" -- exactly the leftmost-prefix pattern from the -- indexing lab, letting a range scan serve both filter and order

A tool call becomes THREE things in this schema, not one: (1) an assistant-role turn where tool_name and tool_arguments are populated (the model deciding to call a tool, per the mcp_fundamentals_jsonrpc lab's tools/call shape), (2) a separate tool-role turn carrying tool_result and a tool_call_id linking it back to turn (1), and (3) typically a following assistant turn where the model incorporates that result into its actual reply to the user. This mirrors exactly how the underlying JSON-RPC exchange works — a request and a correlated response, here persisted as two separate rows joined by an id rather than two JSON-RPC messages joined by id.

ONE REAL CONVERSATION, ROW BY ROW
Every row is one turn — notice the tool call splits into an assistant turn (requesting it) and a separate tool turn (the result), joined by tool_call_id.
Interview-ready definition: a conversation-turns schema stores one row per message in an agent conversation, keyed by a conversation_id foreign key and ordered by a created_at timestamp, with a role column distinguishing user, assistant, and tool turns. Tool calls are represented as a pair of linked rows rather than one — an assistant turn carrying the requested tool name and arguments, and a separate tool turn carrying the result, joined by a shared tool_call_id — which preserves the request/response structure of the underlying tool-calling exchange directly in the schema, rather than collapsing it into a single ambiguous row.
02 — Not every fact deserves to live forever, and not every fact should be forgotten

Short-term vs long-term memory schema

Start here, before the split. Think about how you personally handle a single meeting versus a running friendship. During the meeting, you remember the last few things said, verbatim, in order — that's short-term, full-detail, and it evaporates once the meeting's context stops mattering. But you don't remember every meeting you've ever had verbatim — instead, you retain a compressed sense of who this friend is, what they like, what's been true about them across MANY past conversations. That compressed, cross-conversation residue is long-term memory, and it's a genuinely different kind of storage than "the last few things said."

Short-term memory

The section 1 conversation_turns table itself, queried by conversation_id and recency — the current conversation's actual turns, kept in full detail, no compression.

  • Query pattern: WHERE conversation_id = ? ORDER BY created_at DESC LIMIT N
  • Scoped to ONE conversation — doesn't span across a user's other, separate conversations
  • No information loss — this IS the actual transcript
  • Naturally bounded by context-window limits (this connects to storage-and-rag/token_budget_management.html from Month 3 — eventually the full history has to be trimmed or summarized to fit)

Long-term memory

A SEPARATE table: summarized or extracted facts/preferences that persist ACROSS conversations, often embedded and vector-indexed for semantic retrieval, exactly like the storage-and-rag/vector_db_schema_design.html lab's embeddings-plus-metadata pattern.

  • Query pattern: semantic similarity search — "what do we know that's relevant to THIS query," not a time-ordered scan
  • Scoped to a USER (or entity) — spans every conversation that user has ever had
  • Lossy by construction — a summarized fact loses the exact original wording, deliberately, in exchange for being retrievable without replaying an entire history
CREATE TABLE agent_long_term_memory ( memory_id BIGSERIAL PRIMARY KEY, user_id UUID NOT NULL REFERENCES users(user_id), source_conversation_id UUID REFERENCES conversations(conversation_id), -- where this fact was learned, if traceable memory_text TEXT NOT NULL, -- e.g. "User prefers window seats on flights" embedding VECTOR(1536) NOT NULL, -- for semantic retrieval, per vector_db_schema_design memory_type TEXT NOT NULL CHECK (memory_type IN ('preference', 'fact', 'summary')), created_at TIMESTAMPTZ NOT NULL DEFAULT now(), last_confirmed_at TIMESTAMPTZ -- updated if this fact gets re-observed/re-confirmed later ); CREATE INDEX idx_ltm_user ON agent_long_term_memory (user_id); -- the embedding column additionally gets an HNSW or IVF index (per the -- storage-and-rag indexing labs) for the actual similarity search -- -- retrieval here is "semantically relevant to the current query," not -- "recent," which is the fundamental query-pattern difference from -- short-term memory's time-ordered scan

Notice long-term memory is scoped by user_id, not conversation_id — a preference learned in one conversation ("prefers window seats") needs to be retrievable in a COMPLETELY DIFFERENT, LATER conversation with the same user, which is exactly the cross-conversation persistence short-term memory structurally cannot provide (it's scoped to one conversation by design). source_conversation_id is kept as a traceability link back to where the fact was learned, but the retrieval query itself never filters by it.

Interview-ready definition: short-term memory is the current conversation's own turns (section 1's schema), queried by conversation_id and recency, kept in full unsummarized detail but bounded by context-window limits. Long-term memory is a separate table scoped by user/entity rather than conversation, holding summarized or extracted facts and preferences with a vector embedding for semantic retrieval — deliberately lossy (an extracted fact discards the original conversation's exact wording) in exchange for being retrievable across every future conversation with that user, not just the one it was learned in, via similarity search rather than a time-ordered scan.
03 — Neither table works alone — an agent needs both, feeding each other

How short-term and long-term memory actually connect

Start here, before the pipeline. These two schemas aren't independent choices — they're two stages of one pipeline. As a conversation happens, it's written into conversation_turns (short-term). At some point — end of conversation, or a periodic background job — an extraction step reads recent turns, identifies durable facts worth keeping, and writes THOSE into agent_long_term_memory (long-term). Later, at the START of a brand new conversation, the agent can query long-term memory by the user's id to pull in "what we already know about this person" before the first message is even sent.

WALK THE PIPELINE: CONVERSATION → EXTRACTION → LONG-TERM → NEXT CONVERSATION
StageWhat happensWhich table
1. Live conversationEvery message and tool call written as a row, in orderconversation_turns
2. ExtractionA summarization/extraction step (often an LLM call itself) scans recent turns for durable facts, filtering out anything conversation-specific/irrelevant laterReads from conversation_turns
3. PersistenceExtracted facts get embedded and written as new rows, scoped to the user, not the conversationWrites to agent_long_term_memory
4. RecallA NEW, unrelated conversation starts; the agent runs a similarity search against long-term memory to retrieve relevant prior facts before respondingReads from agent_long_term_memory
The mistake this schema split prevents: a naive design might try to make ONE table do both jobs — e.g. querying conversation_turns directly for "everything we know about this user" by scanning across every conversation they've ever had. This breaks down exactly the way the Month 3 RAG lab's context-window discussion predicted: a long-time user might have thousands of turns across dozens of conversations, and neither a time-ordered scan nor an unsummarized dump of all of it fits in a prompt's token budget, nor is most of it still relevant. The extraction step (stage 2) is what actually solves this — it's a deliberate compression step, not an optional nicety, and it's exactly why long-term memory needs its OWN schema rather than just being "a bigger query" against short-term memory's table.

Problem 1 · Choosing which table a new fact belongs in

During a conversation, a user says "actually, let's cancel that — I changed my mind about the flight." Should this sentence itself ever be written directly into agent_long_term_memory? Why or why not, using section 3's pipeline?

Show solution
No -- this sentence, as literal conversational text, belongs in conversation_turns (short-term) as a normal 'user' role turn, not directly in agent_long_term_memory. Per section 3's pipeline, long-term memory is never written to directly from raw conversation text -- it's populated by the EXTRACTION step (stage 2), which reads recent turns and decides what, if anything, is durable enough to persist across future conversations. This specific sentence is a good example of something that should generally NOT survive extraction into long-term memory at all: "changed my mind about a flight, mid-conversation" is conversation-specific context (relevant to resolving THIS booking, right now) rather than a durable fact or preference about the user that would still be useful in some unrelated future conversation. Compare to "prefers window seats" -- that DOES generalize usefully to future conversations and is exactly the kind of thing extraction should surface. The extraction step's whole job is distinguishing these two categories -- section 3's warning about naively treating short-term as "just a bigger long-term query" applies in reverse here too: not everything said deserves to be promoted to long-term storage, and an extraction step that promoted every sentence verbatim would just recreate the short-term table's bloat problem inside the long-term table instead.
Problem 2 · Diagnosing a broken tool-call join

A team's conversation_turns table has a tool-role row with a populated tool_result, but its tool_call_id doesn't match ANY assistant-role row's tool_call_id in the same conversation. What does this break, using section 1's schema design?

Show solution
This breaks the ability to reconstruct WHICH tool call this result actually belongs to, and WHY the tool was even invoked in the first place (what arguments were passed, per the assistant turn's tool_arguments column) -- per section 1, the whole point of tool_call_id is linking the pair of rows (the assistant's request, the tool's result) together as one logical exchange, mirroring the request/id/response correlation from the JSON-RPC fundamentals lab. An orphaned tool-role row with no matching assistant-role row is a result with no traceable request -- functionally, the schema can no longer answer "what did the agent ask for that produced THIS specific output," which matters concretely for debugging (why did the agent get this weather data?) and for replay/audit purposes (a later lab this month, audit trail schema, depends on exactly this kind of request/result traceability being intact). Likely causes: an application bug generating a tool_call_id inconsistently between the write that inserts the assistant turn and the write that inserts the tool-result turn (e.g. regenerating a new id instead of reusing the original one), or a partial write where the assistant turn's insert failed/rolled back after the tool_call_id was already used downstream. The fix is enforcing this relationship structurally rather than just by convention -- e.g. a foreign-key-style constraint or application-level invariant check that a tool-role row's tool_call_id must reference an existing assistant-role row's tool_call_id in the same conversation before the write is considered valid.
Problem 3 · Reasoning about index choice for the two different query patterns

Section 1 indexes conversation_turns on (conversation_id, created_at), a standard B-tree composite index. Section 2 indexes agent_long_term_memory's embedding column with an HNSW/IVF-style index instead. Why can't the SAME kind of index serve both tables well?

Show solution
These two tables have fundamentally different QUERY PATTERNS, and each index type is built to exploit a different one -- this is exactly the same reasoning the storage_engine_consolidation lab from Month 3 applied across row-store, columnar, HNSW, and IVF. conversation_turns' dominant query is "give me this conversation's turns, in time order" -- an equality filter (conversation_id = ?) combined with a range/order operation (created_at). A B-tree composite index on (conversation_id, created_at) is built exactly for this: it can narrow directly to the matching conversation_id's contiguous range of index entries, already sorted by created_at, satisfying both the filter AND the ordering in one structure -- precisely the leftmost-prefix pattern from the indexing lab. agent_long_term_memory's dominant query is entirely different: "find memories whose MEANING is closest to this query's meaning" -- a nearest- neighbor search over high-dimensional embedding vectors, where there's no meaningful notion of one embedding being "less than" another the way a B-tree's ordering requires. A B-tree fundamentally cannot answer "what's approximately closest in 1536-dimensional space" -- that's exactly the problem HNSW/IVF-style indexes (Month 3's storage-and-rag labs) are built to solve instead, trading exact results for approximate nearest-neighbor search at usable speed. Using a B-tree on the embedding column would either not work at all for similarity queries, or force a full table scan computing similarity against every single row -- the same brute- force cost the HNSW lab's day-1 exercise measured directly and found prohibitive at scale.
Problem 4 · Handling a conflicting long-term memory update

A user's long-term memory already has a row: "User prefers aisle seats" (from 6 months ago). In a new conversation, they say "actually I always take window seats now." Using section 2's schema, what should happen — insert a new row, update the existing one, or something else — and what column matters most here?

Show solution
The most defensible approach is inserting a NEW row for the updated preference rather than silently overwriting the old one in place, at least initially -- but the exact right answer depends on whether the schema is meant to track "current believed state" or "history of what was ever told to us," and section 2's last_confirmed_at column is specifically what supports the "current state, but with a memory of how we got here" middle ground. A reasonable concrete approach: insert the new "prefers window seats" row (new memory_id, new embedding, current timestamp), and separately either (a) mark the old "prefers aisle seats" row as superseded/inactive via a status column (not shown in this simplified schema, but a natural extension), or (b) simply leave both rows present and rely on RECENCY (comparing created_at / last_confirmed_at) at retrieval time to prefer the more recent, contradicting fact when both surface in a similarity search for "seat preference." What matters most: the timestamp columns (created_at, last_confirmed_at) are what let a later retrieval step detect and resolve this exact kind of conflict -- two memories that are both plausibly relevant to the same query but actually contradict each other. Blindly UPDATING the old row in place (overwriting "aisle" with "window") loses the fact that the preference ever changed at all, which can matter for understanding user behavior over time -- whereas keeping both rows with reliable timestamps preserves that history while still letting retrieval logic prefer the more recent, presumably more accurate fact. This is a genuine design choice with no universally correct answer, but the schema needs to support WHICHEVER choice is made, which is exactly what the timestamp columns are there for.
Problem 5 · Estimating storage growth and connecting to retention

A product has 100,000 active users, each averaging 20 conversations/month, each conversation averaging 15 turns. Using section 1's schema, roughly how many rows does conversation_turns accumulate per month, and — connecting to the Month 3 time_series_schema lab's retention/downsampling idea — what would you actually want to do about unbounded growth here?

Show solution
Rows per month: 100,000 users x 20 conversations/user x 15 turns/ conversation = 30,000,000 rows/month -- 360 million rows/year, growing without bound exactly like the append-only, ever-growing time-series data the time_series_schema lab described, since conversation_turns rows are also essentially write-once and never updated after being written (section 1's schema has no meaningful "edit a past turn" operation any more than a sensor reading gets retroactively corrected). What to actually do: this is a direct application of the time-series lab's retention/downsampling reasoning, adapted to conversational data rather than sensor data. A reasonable policy: keep FULL, raw conversation_turns rows for some recent window (e.g. the last 30-90 days, covering "still-active or recently-referenced conversations" and supporting features like "resume an old conversation"), then for older conversations, either (a) archive the raw rows to cheaper, colder storage (mirroring the time-series lab's "cold archival storage" option for old raw data that's rarely queried but occasionally needed), or (b) rely on the fact that anything DURABLE from those older conversations should already have been captured by the extraction pipeline (section 3) into agent_long_term_memory, which is FAR smaller per user than the full raw transcript, meaning the raw turns for very old conversations can often be deleted or archived without losing anything the agent actually still needs day-to-day -- the extraction step isn't just a memory-retrieval mechanism, it doubles as the thing that makes it SAFE to eventually downsample/archive the much larger raw conversation_turns table, exactly as the time-series lab's downsampling accepted losing raw precision on old data because coarser aggregates already captured what mattered.
