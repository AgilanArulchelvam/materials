01 — Narrowing down instead of checking everything

B-Tree index structure and range queries

Start here, before any code. Think about looking up a word in a printed dictionary versus reading a random, unsorted list of words front to back. In the dictionary, you flip to roughly the middle, see you've overshot or undershot alphabetically, and narrow your search by half again and again — a handful of flips gets you to any word. In an unsorted list, there's no shortcut: you must check words one by one until you happen to find it, or confirm it isn't there by checking literally everything.

A B-tree index is the database's version of the dictionary. It's a balanced, sorted tree structure where each internal node holds a small number of key values that guide you toward the right branch, and the actual row locations live in the leaf nodes at the bottom — all leaves at the same depth, which is what keeps every lookup roughly the same speed regardless of which value you're searching for. Because the tree is SORTED, it doesn't just answer "does this exact value exist?" — it also answers range queries (WHERE age BETWEEN 25 AND 35) efficiently, by finding one boundary and then walking sequentially along the leaf level until the other boundary is passed.

Interview-ready definition: a B-tree index is a balanced, sorted tree structure (internal nodes hold guide keys, leaf nodes hold pointers to actual row locations, all leaves at equal depth) that lets both exact-match and range lookups be resolved in O(log n) node visits instead of scanning every row — the sortedness of the leaf level is specifically what makes range queries (BETWEEN, <, >, ORDER BY on the indexed column) efficient, not just single-value equality lookups.
02 — Column order isn't just a style choice

Composite indexes and column-order sensitivity

Start here, before any code. A phone book is sorted by last name FIRST, then first name within each last name — "Smith, Alice" comes right before "Smith, Bob," but "Alice" entries are scattered across every letter of the alphabet depending on THEIR last name, not grouped together anywhere. If you want everyone named "Smith," the sort order helps enormously — they're all adjacent. If you want everyone named "Alice" regardless of last name, the phone book's sort order gives you no shortcut at all — you'd still have to check every single page.

A composite (multi-column) index behaves exactly like that phone book: an index on (last_name, first_name) physically sorts entries by last_name first, and only sorts by first_name as a tiebreaker WITHIN each last_name group. This has a direct, asymmetric consequence for which queries the index can actually help.

WHERE first_name = 'Alice'

Index does NOT help. first_name is only sorted WITHIN each last_name group — "Alice" values are scattered across every last_name bucket in the tree, so this index gives no shortcut; it typically falls back to a full scan.

CREATE INDEX idx_lastname_firstname ON employees (last_name, first_name); -- USES the index efficiently: last_name is the leftmost column SELECT * FROM employees WHERE last_name = 'Smith'; -- ALSO uses it efficiently: both columns present, in order SELECT * FROM employees WHERE last_name = 'Smith' AND first_name = 'Alice'; -- Does NOT use this index (falls back to a full scan): first_name alone -- is not the leftmost column, so the sort order provides no shortcut SELECT * FROM employees WHERE first_name = 'Alice';
The classic interview trap, stated plainly: a composite index on (A, B) can serve queries filtering on A alone, or on A AND B together, but generally CANNOT serve a query filtering on B alone — the "leftmost prefix rule." This asymmetry is not a bug or a limitation of any one database; it's a direct, unavoidable consequence of how the multi-column sort itself works. If both single-column filters need to be fast independently, you generally need two separate indexes, not one composite index in either order.
Interview-ready definition: the leftmost-prefix rule states that a composite index on columns (A, B, C) can be used to accelerate a query only if that query filters on a contiguous prefix of the index's column list starting from the left — filters on (A), (A, B), or (A, B, C) can use the index, but a filter on (B) alone, (C) alone, or (B, C) without A generally cannot, because the index's physical sort order only guarantees adjacency for values sharing the same leading column(s).
03 — Reading what the database actually decided to do

Reading EXPLAIN ANALYZE: seq scan vs index scan

Start here, before any output. A GPS app doesn't just tell you the destination — it shows you the route it actually chose and how long each leg took. EXPLAIN ANALYZE is that for a SQL query: it runs the query for real and shows you the actual execution plan the database chose, including which scan strategy it used for each table and how much time and how many rows were involved at each step.

The two numbers to watch closely: estimated rows (the planner's guess, from table statistics, before running) versus actual rows (what really came back) — a huge mismatch between them is a common sign of stale statistics misleading the planner. And the total time reported for each node, read from the innermost/lowest node outward, shows exactly where the query's time is actually being spent.

Signal in the planSeq ScanIndex Scan
What it doesReads every row in the table, checking each against the filterWalks the index tree to the matching range, then fetches only those rows
Cost scalingGrows linearly with table size, regardless of how selective the filter isGrows roughly with the LOG of table size plus the number of matching rows
When the planner picks it anywayFilter matches a large fraction of the table — reading everything sequentially can beat many scattered index lookupsFilter is selective (matches a small fraction) — the index avoids reading rows that would just be discarded
A subtlety worth remembering: a sequential scan showing up in a plan isn't automatically a problem — for a query that matches a large percentage of a table's rows, a straightforward sequential read can genuinely be FASTER than jumping around an index fetching scattered individual rows (a phenomenon sometimes called "index scan isn't always the query planner's friend"). The planner is choosing based on estimated selectivity and cost, not blindly preferring one strategy — the interview-relevant skill is recognizing WHEN each choice is actually the right one, not just recognizing the words.
Interview-ready definition: EXPLAIN ANALYZE executes a query and reports its real execution plan, including the scan method chosen for each table (sequential scan reads every row; index scan uses an index to jump directly to matching rows), estimated vs. actual row counts at each step, and timing per plan node. A sequential scan's cost scales linearly with table size regardless of filter selectivity, while an index scan's cost scales primarily with the number of matching rows plus a small, roughly logarithmic tree-traversal cost — making index scans dramatically cheaper specifically when a filter is selective (matches few rows out of many).

Problem 1 · Leftmost prefix, applied

Given an index on (country, city, zip_code), which of these queries can use the index efficiently: (a) WHERE country = 'US', (b) WHERE city = 'Austin', (c) WHERE country = 'US' AND city = 'Austin', (d) WHERE zip_code = '78701'?

Show solution
(a) YES -- country is the leftmost column, so filtering on it alone uses the index. (b) NO -- city alone skips the leftmost column (country); city values are only sorted WITHIN each country group, so there's no useful adjacency for a city-only filter. (c) YES -- country, then city, is a contiguous prefix starting from the left (country first, then city), so this uses the index efficiently. (d) NO -- zip_code alone skips both leading columns, same reasoning as (b) but one level deeper.
Problem 2 · Designing two indexes instead of one

An application frequently runs both `WHERE last_name = ?` alone AND `WHERE first_name = ?` alone as independent, equally common queries. Can a single composite index serve both efficiently? What should you do instead?

Show solution
No single composite index can serve both efficiently, regardless of which column comes first -- whichever column you put second will not be usable for a query filtering on it alone, by the leftmost-prefix rule. If both single-column filters genuinely need to be fast independently, the correct design is to create TWO separate single-column indexes: one on last_name and one on first_name. This costs more in write overhead and storage (every index must be updated on every insert/update) but is the only way to make both single-column filters use an index, since a composite index's column order can only favor one direction.
Problem 3 · Range queries and B-tree sort order

Explain why a B-tree index can efficiently serve `WHERE age BETWEEN 30 AND 40`, but a hash index (which maps each value to a bucket via a hash function, with no inherent ordering between buckets) generally cannot.

Show solution
A B-tree's leaf level is fully SORTED by the indexed column's value, so "find everything between 30 and 40" reduces to: find the leaf position for 30 (a single O(log n) tree descent), then walk sequentially forward along the sorted leaf level until you pass 40 -- all the matching rows are physically adjacent in the structure. A hash index has no such ordering by design -- it deliberately scrambles values across buckets specifically to make single-value equality lookups O(1) average case. There's no relationship between the hash bucket for 30 and the hash bucket for 31, so there's no way to "walk forward" toward 40 -- answering a range query with a hash index would require checking values individually or falling back to a full scan, since the structure itself carries no information about which values are numerically close to each other.
Problem 4 · Reading a mismatch between estimated and actual rows

An EXPLAIN ANALYZE output shows "rows=50" estimated but "rows=48,000" actual for an index scan step. What does this mismatch typically indicate, and why might it cause the planner to make a bad decision elsewhere in the same query?

Show solution
This large mismatch typically indicates STALE TABLE STATISTICS -- the query planner estimates row counts using statistics gathered the last time the table was analyzed (e.g. via ANALYZE/auto-analyze), and if the data has changed significantly since then (many new rows matching that condition, or a changed data distribution), the estimate can be badly wrong even though the actual query still executes and returns correct results. This matters beyond just being a "wrong number in a report": the planner uses these ESTIMATES, not the actual counts (which aren't known until the query runs), to choose the whole execution plan -- including whether to use an index scan at all, what join order to use, and what join algorithm to pick. An estimate of 50 rows might lead the planner to choose a plan that's efficient for a small result set (e.g. nested loop joins), but if the true count is 48,000, that same plan can perform far worse than an alternative the planner would have chosen with accurate statistics (e.g. a hash join). The fix is typically to run ANALYZE (or ensure auto-analyze is keeping up) so the planner's row estimates reflect current reality.
Problem 5 · When a seq scan is the right choice

A table has an index on `status`, but a query filtering `WHERE status = 'active'` matches 95% of the table's rows, and EXPLAIN ANALYZE shows the planner chose a sequential scan instead of using the index. Is this a bug, or the planner working correctly? Explain.

Show solution
This is the planner working correctly, not a bug. An index scan's benefit comes from AVOIDING reads of rows that don't match the filter -- but if 95% of rows match, an index scan would still end up fetching almost every row anyway, PLUS pay the extra cost of tree traversal and (for many storage engines) scattered/random-access reads back to the table's heap for each matching row, which is often slower per-row than a straightforward sequential read. A sequential scan reads the whole table in one efficient, mostly-sequential pass -- for a filter with low selectivity (matches a large fraction of the table), this is frequently faster overall than the index-scan alternative, and a well-functioning query planner is expected to make exactly this cost-based trade-off rather than always preferring whichever index technically exists.
