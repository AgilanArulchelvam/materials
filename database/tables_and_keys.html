01 — The basic unit

What a relational table is: rows, columns, schema

A relational table is a grid. Each column is a named, typed field that every row shares — the schema is that fixed set of columns and types, decided up front. Each row is one record — one concrete instance of that schema, filled in with actual values.

CREATE TABLE books ( id INTEGER PRIMARY KEY, title TEXT NOT NULL, author_id INTEGER, published INTEGER ); -- this CREATE TABLE statement IS the schema: 4 columns, each with a fixed type
BUILD A TABLE FROM ITS SCHEMA
books — schema: id (INTEGER), title (TEXT), author_id (INTEGER), published (INTEGER)
idtitleauthor_idpublished
The schema (column names + types) is fixed. Every row you insert must match that shape — same columns, compatible types.
Schema vs. data: the schema changes rarely and deliberately (a migration). The rows — the actual data — change constantly as the application runs. Keeping that distinction clear is most of what "database design" means.
02 — Every row needs an address

Primary key: uniqueness, why every table needs one

A primary key is one column (or a small combination of columns) guaranteed to be unique across every row in the table — no two rows can ever share the same value. It's how you unambiguously point at "this exact row" from anywhere else, including from other tables.

Without a primary key, "update the book called Dune" is ambiguous the moment two books happen to share a title. With a primary key, "update the book with id=1" can never be ambiguous — that's the entire point.

Common choice — surrogate keys: instead of relying on a "natural" unique value (which can turn out not to be unique — two people really can share a name), most schemas use a meaningless auto-incrementing integer or UUID as the primary key, generated by the database itself. It has no business meaning; its only job is to be a stable, permanent, unique address for the row.
03 — Pointing at another table's primary key

Foreign key: referential integrity between tables

A foreign key is a column in one table that holds the primary key value of a row in another table — it's a pointer between tables. Referential integrity is the guarantee the database enforces: a foreign key value must either be NULL or match an actual, existing primary key in the referenced table. It can never point at nothing.

CREATE TABLE books ( id INTEGER PRIMARY KEY, title TEXT, author_id INTEGER, FOREIGN KEY (author_id) REFERENCES authors(id) ); -- author_id in "books" must match an id that actually exists in "authors"

What the database refuses, on your behalf: without this constraint, nothing stops a typo or a bug from inserting author_id = 99 when no author 99 exists — you'd have a "book" pointing at nothing, discovered only later when some query tries to join it and gets silence. Referential integrity turns that into an immediate, loud error at insert time instead of a silent data-quality bug discovered months later.
04 — How tables connect

One-to-many vs. many-to-many, and join tables

RelationshipMeaningHow it's modeled
One-to-manyOne row in table A relates to many rows in table B, but each row in B relates to only one row in A.A single foreign key column on the "many" side (table B).
Many-to-manyMany rows in A can relate to many rows in B, in any combination.A separate join table with two foreign keys, one to each side.
TOGGLE THE RELATIONSHIP SHAPE

Why many-to-many needs a join table

A single foreign key column can only point at one row. If a student can be in many courses, and a course can have many students, neither table can hold a plain foreign key to the other — there's nowhere to put "student 3 is in courses 1, 2, and 5" as a single column value. The fix is a third table where each row represents one connection:

CREATE TABLE enrollments ( -- the join table student_id INTEGER, course_id INTEGER, PRIMARY KEY (student_id, course_id), -- composite key: this PAIR must be unique FOREIGN KEY (student_id) REFERENCES students(id), FOREIGN KEY (course_id) REFERENCES courses(id) ); -- one row per (student, course) pairing — a student in 3 courses = 3 rows here

The join table's primary key is usually the combination of both foreign keys — a "composite key" — which naturally prevents the same student from being enrolled in the same course twice, while still allowing any student/course combination overall.

Practice problems

Work each one out before expanding the solution.

Problem 1 · Schema vs data

A users table has columns id, email, created_at. Someone signs up. Is that event a schema change or a data change? What about adding a new phone_number column later?

Show solution
Someone signing up = a data change (a new ROW is inserted; the columns stay the same). Adding a phone_number column = a schema change (a migration) — the shape every row must conform to has changed, and existing rows now need a value (or NULL) in that new column.
Problem 2 · Choosing a primary key

A table of employees has columns: ssn, email, full_name, employee_number (auto-incrementing, assigned by the company). Which would you use as the primary key, and why not the others?

Show solution
employee_number is the best choice — it's a surrogate key, generated purely to be unique, with no external meaning to change or collide. full_name: not guaranteed unique (two employees can share a name). email: usually unique in practice, but can change (someone gets married, company rebrands domains) — primary keys should ideally never need to change, since other tables may reference them. ssn: technically unique, but it's sensitive personal data — using it as a key means it ends up copied into every table that references this one, which is a privacy/security liability best avoided.
Problem 3 · Foreign key violation
-- authors table has rows with id = 1, 2, 3 INSERT INTO books (id, title, author_id) VALUES (10, 'Ghost Story', 7);
Show solution
This INSERT fails with a foreign key constraint violation. author_id = 7 doesn't exist in the authors table (only 1, 2, 3 do), so the foreign key constraint (books.author_id REFERENCES authors.id) rejects the insert — referential integrity means a foreign key can't point at a row that doesn't exist.
Problem 4 · Identify the relationship

For each pair, is it one-to-many or many-to-many? (a) A blog post and its comments. (b) Products and the tags applied to them (a product can have several tags; a tag can apply to many products). (c) A country and its capital city.

Show solution
(a) One-to-many: one post has many comments, each comment belongs to exactly one post. Modeled with a post_id foreign key on the comments table. (b) Many-to-many: a product can have many tags AND a tag can apply to many products. Needs a join table, e.g. product_tags(product_id, tag_id). (c) One-to-one (a special, tighter case of one-to-many where each side is capped at exactly one): one country has exactly one capital, and that city is the capital of exactly one country. Often modeled as a foreign key with a UNIQUE constraint on top of it.
Problem 5 · Design a join table

Design the table(s) for: actors can appear in many movies, and movies have many actors. Write the CREATE TABLE statements (columns only, types can be simplified).

Show solution
CREATE TABLE actors ( id INTEGER PRIMARY KEY, name TEXT ); CREATE TABLE movies ( id INTEGER PRIMARY KEY, title TEXT ); CREATE TABLE movie_actors ( -- join table movie_id INTEGER, actor_id INTEGER, PRIMARY KEY (movie_id, actor_id), FOREIGN KEY (movie_id) REFERENCES movies(id), FOREIGN KEY (actor_id) REFERENCES actors(id) ); -- one row per (movie, actor) appearance — a cast of 5 in one movie = 5 rows
Problem 6 · Reading a schema

Given: orders(id PK, customer_id FK→customers.id, order_date) and order_items(id PK, order_id FK→orders.id, product_id FK→products.id, quantity) — describe the relationship between customers and orders, and between orders and products.

Show solution
customers → orders: one-to-many. Each order has exactly one customer_id, but a customer can place many orders — a single foreign key on the "many" side (orders) is enough. orders ↔ products: many-to-many, modeled through order_items as the join table. One order can contain many products (many rows in order_items with the same order_id), and one product can appear in many different orders (many rows with the same product_id across different orders). order_items also carries its own extra data (quantity) — a common and useful pattern: the join table isn't just two foreign keys, it can hold facts ABOUT that specific pairing.
