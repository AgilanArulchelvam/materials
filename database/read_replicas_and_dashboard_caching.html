DATABASE FUNDAMENTALS LAB · READ REPLICAS & DASHBOARD CACHING

Every dashboard query is a favor the primary database didn't ask to do.

An observability dashboard — the exact kind trace_dashboard_practice.html builds — runs expensive aggregate queries (p99 latency over an hour, error rate by service) that have nothing to do with serving real users, yet compete for the SAME primary database connection pool and disk I/O as production traffic. This lab routes those dashboard reads to a read replica instead, then layers a short-TTL cache on top for the identical queries many viewers ask at once — reusing replication.html's leader-follower model and caching_layer_design.html's write/eviction reasoning, applied to one concrete, very common workload.

Primary — production writes AND reads, never dashboard reads
Read replica — isolates dashboard load entirely
Short-TTL cache — the same query, asked by 40 viewers, computed once

01 — Dashboard queries and production queries are different customers of the same database

Offloading dashboard queries from primary

Start here, before any diagrams. Imagine a small bakery's single register also has to handle a researcher who walks in once an hour and asks the cashier to manually count every receipt from the past week to compute average sale size — while paying customers are standing in line. Even if the researcher is polite and infrequent, that manual count TIES UP the same cashier and register that paying customers need for their (much faster, much more time-sensitive) transactions. The fix isn't to tell the researcher to stop asking questions — it's to give the researcher a SEPARATE, synced copy of the week's receipts to comb through, so the register stays free for actual sales the whole time.

An observability dashboard is exactly this researcher. Queries like "p99 latency for call_llm spans over the last hour" or "error rate by service, last 24 hours" — the kind trace_dashboard_practice.html's dashboard runs — are typically expensive AGGREGATE queries: scanning, grouping, and computing statistics over potentially millions of rows, very different from a production query's typical shape (fetch one row by primary key, or a small filtered set). Running these aggregate queries against the primary database — the same one handling live production reads and writes — means dashboard load competes directly with production traffic for the primary's connection pool (connection_pooling.html's exact concern) and disk I/O, potentially slowing down or even destabilizing the actual production workload just because someone opened a dashboard.

The fix reuses replication.html's leader-follower model directly: dashboard queries get routed to a read replica instead of the primary. The replica receives the same writes as the primary (with the same replication lag replication.html's section 1 already established — dashboard data can be a few seconds to minutes stale, which is almost always an acceptable trade-off for an aggregate trend dashboard, unlike a production read that needs the LATEST committed row). Because the replica is a physically separate machine, however much load the dashboard's expensive queries generate, it can never directly compete with the primary's own connection pool or I/O capacity — the isolation is structural, not just a scheduling hope.

# routing dashboard reads to a replica, production reads/writes to primary def get_db_connection(query_type: str): if query_type == "production_write" or query_type == "production_read": # writes always go to primary; production reads too, since they # need the freshest committed data, no tolerance for replication lag return primary_pool.get_connection() elif query_type == "dashboard_aggregate": # dashboard queries tolerate a few seconds/minutes of lag just fine -- # route to the replica, isolating this load entirely from primary return replica_pool.get_connection() # example: the p99-latency dashboard query from opentelemetry_basics.html's # Problem 2 scenario, now correctly routed def get_p99_latency_last_hour(service: str): conn = get_db_connection("dashboard_aggregate") # -> replica, not primary return conn.execute( "SELECT percentile_cont(0.99) WITHIN GROUP (ORDER BY duration_ms) " "FROM spans WHERE service = %s AND start_time > NOW() - INTERVAL '1 hour'", [service] )
Interview-ready definition: offloading dashboard queries to a read replica routes expensive, aggregate-heavy observability queries away from the primary database entirely, so dashboard load can never directly compete with production reads/writes for the primary's connection pool or disk I/O. This works because dashboard queries — unlike production reads that need the latest committed row — tolerate the replica's normal replication lag (replication.html section 1) just fine; a trend dashboard being a few seconds or minutes behind real-time is an acceptable trade-off for structurally isolating the load, whereas a production read serving an actual user transaction generally is not.
02 — Ten people looking at the same hour of data shouldn't mean ten identical expensive queries

Caching strategy for frequent queries

Start here, before the mechanics. Imagine a museum tour guide who, every single time a NEW visitor asks "how old is this painting," walks all the way to the archive room, pulls the physical records, and reads the answer back out loud — even though the last five visitors asked the EXACT SAME question about the EXACT SAME painting in the last ten minutes. The obviously better approach: after answering once, jot the answer on a sticky note taped right next to the painting, and just read the sticky note for the next several visitors — only walking back to the archive again once the note's information might plausibly be stale.

Even after section 1's replica offload, a real observability dashboard has a SECOND, independent inefficiency: many different viewers (or the same viewer refreshing repeatedly) very often ask for the SAME time range and SAME aggregate query within a short window — "p99 latency for the last hour" doesn't meaningfully change between one viewer's request and another's thirty seconds later. Re-running that expensive aggregate query, even against a replica specifically isolated for this load (section 1), is still wasted work if the answer would be IDENTICAL to a query that already ran seconds ago. This is exactly caching_layer_design.html's territory, applied to this specific workload: cache the query's result for a short TTL (time-to-live) — long enough to absorb the burst of near-simultaneous identical requests, short enough that the dashboard still feels close to real-time.

# short-TTL cache on top of the replica-routed dashboard query CACHE_TTL_SECONDS = 30 # tune per caching_layer_design.html's consistency/staleness trade-off def get_p99_latency_cached(service: str): cache_key = f"dash:p99:{service}:{current_minute_bucket()}" cached = redis_client.get(cache_key) if cached is not None: return cached # cache hit -- no query against the replica at all # cache miss -- compute it once, against the replica (section 1), then cache result = get_p99_latency_last_hour(service) redis_client.setex(cache_key, CACHE_TTL_SECONDS, result) return result

Two design choices worth being precise about, both direct applications of caching_layer_design.html's framework. First: this is a read-through, short-TTL cache, not write-through/write-back at all — there's no "write" happening here in the caching-layer sense, since the underlying data (the spans/traces) is written elsewhere, by the production system, not by this dashboard read path. Second: the TTL itself is the entire consistency/staleness knob — a 30-second TTL means up to 30 seconds of staleness on a dashboard number, which for a TREND view ("is p99 rising over the last hour") is an entirely acceptable trade-off, the same reasoning caching_layer_design.html's section 3 applied to cache consistency generally, now with a very concrete, very defensible use case: nobody needs sub-second freshness on an aggregate that's already averaging over the past hour.

Interview-ready definition: caching frequent dashboard queries means storing a short-TTL cached copy of an expensive aggregate query's result, keyed by the specific query parameters (service, time range), so that many viewers requesting the SAME aggregate within the TTL window get served the cached result instead of each triggering an independent, identical, expensive query — even against an already-isolated read replica. The TTL is chosen as a direct trade-off between staleness (how out-of-date the cached number can be) and load reduction (how long a burst of identical requests gets absorbed by one cached value), following caching_layer_design.html's general consistency-vs-cost framework, applied here to a workload where a data point already representing an hour-long trend can easily tolerate tens of seconds of additional staleness.

Problem 1 · Deciding which query type goes to primary vs replica

Using section 1's routing function, classify each of the following as production_read (primary) or dashboard_aggregate (replica), and justify each: (a) fetching a single trace's full span tree by trace_id for trace_dashboard_practice.html's waterfall view, (b) checking whether a specific order exists before processing a refund, (c) computing average trace duration by hour for the past week.

Show solution
(a) Fetching one trace's full span tree by trace_id -- this is genuinely ambiguous and worth reasoning through explicitly: if it's being viewed moments after that exact trace was captured (e.g. someone debugging a request that JUST failed), replication lag could mean the replica doesn't have it yet, arguing for primary. But if it's a dashboard feature browsing HISTORICAL traces (as trace_dashboard_ practice.html's list-then-drill-in UI implies -- traces already sitting in the "recent traces" list), the data is already at least a few seconds old by the time it's clicked, so the replica's normal lag is a non-issue -- route to replica. The general rule this illustrates: it's not "read vs write" alone that decides the routing, it's whether the read can tolerate the replica's lag GIVEN how fresh the underlying data needs to be for this specific use case. (b) Checking whether a specific order exists before processing a refund -- PRIMARY, unambiguously. This is a production read gating a write with real consequences (processing a refund incorrectly because the replica hadn't yet replicated a very recent order creation would be a genuine correctness bug, not just a stale dashboard number) -- exactly why section 1 routes production reads to primary by default, not just production writes. (c) Computing average trace duration by hour for the past week -- REPLICA, unambiguously. A classic dashboard_aggregate query: expensive (scanning/grouping over a week of data), and a trend over an entire week tolerates the replica's seconds-to-minutes lag with zero meaningful impact on the answer's usefulness.
Problem 2 · Picking a TTL for a specific dashboard panel

Using section 2's TTL reasoning, would you set a LONGER or SHORTER cache TTL for a "current active agent sessions" panel (meant to show what's happening RIGHT NOW) compared to the "p99 latency, last hour" panel this lab used? Justify with the staleness-vs-load trade-off.

Show solution
SHORTER TTL for "current active agent sessions" -- possibly even no caching at all, or a TTL of just a few seconds. The entire VALUE of that panel is showing what's happening RIGHT NOW -- a viewer looking at "active sessions" wants near-real-time truth, and 30 seconds of staleness (this lab's example TTL) could mean showing sessions that already ended, or missing ones that just started, undermining the panel's actual purpose. This directly mirrors caching_layer_design.html's section 3 point: the TTL choice is a bet on how wrong a stale answer is allowed to be, and "what's happening right now" tolerates almost no staleness by definition. By contrast, "p99 latency, last hour" is already, by its own definition, an aggregate SMOOTHED over 60 minutes of data -- a data point that's already averaging over an hour genuinely doesn't change in any meaningful way between one 30-second window and the next, so a 30 (or even 60+) second TTL costs essentially nothing in perceived freshness while meaningfully reducing repeated-query load (section 2's core trade-off). The general principle: TTL should scale with how "already smoothed over time" the underlying metric is -- point-in-time state tolerates almost no caching; long-window aggregates tolerate comparatively generous caching.
Problem 3 · Explaining why the cache key needs the time bucket, not just the service name

Section 2's cache_key includes current_minute_bucket(), not just the service name. What would go wrong if the cache key were just f"dash:p99:{service}" with no time component, and the TTL were set to 30 seconds?

Show solution
Without a time bucket in the key, the FIRST time this query ever runs for a service, its result gets cached under a key that never changes -- and every subsequent call within the 30-second TTL correctly reuses it, which is fine SHORT-term. But once that entry EXPIRES and gets recomputed, it recomputes for "the last hour AS OF right now" -- a DIFFERENT actual time window than the previous cached value, even though the key is identical. This isn't wrong per se (each fresh computation IS correctly "the last hour as of now"), but it does mean the cache key alone gives no way to distinguish "this specific hour's p99" from "whatever hour happened to be current when this entry was last computed" -- which becomes a real problem the moment you want to cache MULTIPLE distinct time-bucketed views simultaneously (e.g. "p99 for 2-3pm" and "p99 for 3-4pm" as two separate, independently cacheable, non-overlapping dashboard panels a user might view side by side). Including current_minute_bucket() in the key means each distinct time bucket gets its OWN cache entry, so two different time-range panels never collide or overwrite each other's cached value, and repeated requests for the SAME bucket within the TTL still correctly hit the same cached entry. This is the same key-design discipline database/ time_series_schema.html's retention/bucketing logic already established -- the bucket boundary is part of the query's actual identity, not an incidental detail.
Problem 4 · Diagnosing what happens if the cache is skipped but the replica offload isn't

Suppose section 1's replica routing is correctly implemented but section 2's caching layer is accidentally disabled. 40 dashboard viewers all load the same panel within the same 10-second window. What happens, and is production traffic still protected?

Show solution
Production traffic IS still protected -- this is the key thing section 1's replica routing guarantees on its own, independent of caching. All 40 of these dashboard queries hit the REPLICA, not the primary, so however much load 40 near-simultaneous expensive aggregate queries generate, it lands entirely on the replica's own connection pool and I/O capacity -- production reads/writes against the primary remain completely unaffected, exactly section 1's isolation guarantee, which doesn't depend on caching at all. However, the REPLICA itself is now doing 40x more work than necessary -- the exact inefficiency section 2 exists to eliminate. All 40 viewers are asking for the IDENTICAL query (same service, same time bucket), so 39 of those 40 executions are pure waste: recomputing an answer that was already computed moments earlier by request #1. If the replica's own capacity is limited, this could cause the DASHBOARD itself to become slow or start timing out for viewers, even though production is fine -- a real, if less severe, problem than section 1's original concern, and precisely the gap section 2's caching layer closes. The two techniques are complementary, not redundant: replica routing protects PRODUCTION from dashboard load; caching protects the REPLICA (and the dashboard's own responsiveness) from redundant dashboard load.
Problem 5 · Designing the interaction between cache invalidation and replication lag

A viewer complains that a dashboard number stayed wrong for 90 seconds after a burst of new traces should have changed it, even though the cache TTL is only 30 seconds. Using both section 1's replication lag and section 2's TTL together, what's the worst-case total staleness this system can produce, and is 90 seconds consistent with that?

Show solution
The two staleness sources STACK, they don't cancel out: replication lag (section 1) is however long it takes a write to propagate from primary to replica -- say, up to some bound X seconds under normal conditions. Cache TTL (section 2) then adds UP TO another 30 seconds on top, in the worst case (a viewer's request lands the INSTANT after a fresh cache entry was populated with slightly-stale replica data, right before the underlying replica data itself updates). Worst case total staleness ≈ replication lag (X) + cache TTL (30s). If replication lag under some real load spike is, say, 60 seconds (well within replication.html's own established range of "milliseconds to seconds, occasionally worse under load"), then worst-case total staleness could indeed approach 60 + 30 = 90 seconds -- meaning the complained-about 90 seconds is entirely consistent with normal system behavior under a replication lag spike, not necessarily a bug. The actionable takeaway: when diagnosing "why is this dashboard number stale," you have to check BOTH layers independently -- is the cache TTL itself the dominant factor (check cache entry timestamp vs now), or is the underlying REPLICA itself behind the primary (check replication lag directly, exactly as replication.html's own live demo visualizes)? Treating "the dashboard is stale" as a single, one-cause problem misses that this system has two independent, stacking sources of staleness, each requiring a different fix (lowering the TTL helps one; addressing replica lag/capacity helps the other).
