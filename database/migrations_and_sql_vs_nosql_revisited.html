01 — A schema change that can be applied, and un-applied

Writing and running an Alembic migration

Start here, before any code. Think of a schema migration like a single step in a hiking trail with trail markers pointing both directions — one set of arrows says "this is how you got here from the last checkpoint," and a separate, equally maintained set says "this is exactly how to walk back to the last checkpoint if you need to." A migration file isn't just "here's the new schema" — it's a pair of directions, forward and backward, both of which have to actually work, not just the forward one.

Alembic is SQLAlchemy's migration tool. Every migration is a Python file with two functions: upgrade(), which applies the change, and downgrade(), which undoes it. Alembic tracks which migrations have already been applied to a given database (in a small table it manages itself, typically alembic_version), so it always knows exactly which direction to run and how far.

# alembic/versions/a1b2c3d4e5f6_add_last_login_to_users.py # Generated by: alembic revision --autogenerate -m "add last_login to users" from alembic import op import sqlalchemy as sa # identifiers used by Alembic to order and chain migrations revision = "a1b2c3d4e5f6" down_revision = "f9e8d7c6b5a4" # the migration this one comes directly after branch_labels = None depends_on = None def upgrade() -> None: op.add_column( "users", sa.Column("last_login", sa.DateTime(timezone=True), nullable=True) ) def downgrade() -> None: op.drop_column("users", "last_login")

The revision and down_revision identifiers form a linked list: Alembic follows that chain to figure out exactly which migrations need to run, and in what order, to get a database from wherever it currently is to wherever you're asking it to go — whether that's "latest," a specific revision, or "one step back."

# The actual commands, in the order you'd run them alembic revision --autogenerate -m "add last_login to users" # -> creates the migration file above by diffing your SQLAlchemy models # against the current database schema alembic upgrade head # -> runs upgrade() for every migration not yet applied, in order, # up through the newest ("head") revision alembic downgrade -1 # -> runs downgrade() for just the most recently applied migration, # reverting the database by exactly one step

Interview-ready definition: an Alembic migration is a versioned Python file exposing upgrade() and downgrade(), chained to adjacent migrations via revision/down_revision identifiers, so Alembic can deterministically compute the exact ordered sequence of forward or backward steps needed to move a database between any two points in that chain. alembic upgrade head applies every unapplied migration's upgrade() in order; alembic downgrade -1 runs only the most recently applied migration's downgrade(), reverting exactly one step — the reversibility is the entire point: a migration that only knows how to move forward isn't safely deployable, because a bad deploy has no clean way back.
02 — What the diff tool actually sees, and what it can't

Autogenerate vs hand-written migrations

Start here, before the examples. Imagine a proofreading tool that compares two drafts of a document and highlights every added or deleted sentence — genuinely useful, and it'll never miss a sentence that was fully added or fully removed. But now imagine a sentence was just REWORDED, moved to a different paragraph, and slightly repurposed. The tool sees that as "one sentence deleted here, one unrelated new sentence added there" — technically not wrong about the characters on the page, but it has completely missed the actual intent: this wasn't two unrelated edits, it was one rename-and-move. Alembic's --autogenerate has exactly this blind spot, and it's a specific, well-understood one, not a vague "sometimes it's wrong."

alembic revision --autogenerate works by diffing your current SQLAlchemy model definitions against the database's actual current schema (introspected via reflection), then generating op.* calls for whatever differences it finds. It's genuinely reliable for a specific, narrow class of changes, and genuinely unreliable — sometimes silently wrong — for others.

What autogenerate handles well

Structural changes with a clean, unambiguous before/after: adding a column, dropping a column, adding or dropping a table, adding a straightforward single-column index or constraint. These all show up as an unambiguous structural diff between "what the models say" and "what the database currently has" — there's exactly one reasonable interpretation of the change, so Alembic generates it correctly essentially every time.

Renames look like drop-then-add, not a rename

This is the single most common autogenerate trap. If you rename a model's username column to handle, Alembic's diff sees "a column called username that no longer exists" and "a new column called handle that didn't exist before" — it has no way to know these are actually the SAME logical column, just renamed, rather than two unrelated changes. Left unedited, the generated migration does exactly what it detected:

# What autogenerate produces for a RENAME, by default -- WRONG def upgrade() -> None: op.drop_column("users", "username") # destroys every existing value! op.add_column("users", sa.Column("handle", sa.String(), nullable=True)) # What you actually need to hand-write instead -- CORRECT def upgrade() -> None: op.alter_column("users", "username", new_column_name="handle") # -- preserves every existing row's value, just under the new name

The drop-then-add version isn't just cosmetically different — it's destructive. Every existing user's username value is gone the moment that migration runs, replaced by a brand-new, entirely empty handle column. Nothing about running alembic upgrade head would warn you; the migration "succeeds" and the schema ends up looking correct, while the actual data silently didn't survive.

Data migrations: autogenerate can't see this at all

Autogenerate only diffs schema STRUCTURE — column names, types, constraints — by comparing model definitions to the reflected database schema. It has no concept of transforming existing row VALUES, because there's no "before" and "after" model definition to diff for that; the models look identical whether or not the data inside matches them. Backfilling a new non-nullable column with a computed default for existing rows, splitting one column's data into two, or normalizing inconsistent existing values — all of these require hand-written op.execute() calls with real SQL (or batched Python), because there is nothing in your model definitions for autogenerate to diff against in the first place.

# A hand-written DATA migration -- autogenerate would never produce this def upgrade() -> None: op.add_column("orders", sa.Column("status", sa.String(), nullable=True)) # backfill existing rows based on other columns' current values -- # this is business logic, not a structural diff, so it has to be # written by hand op.execute("UPDATE orders SET status = 'completed' WHERE shipped_at IS NOT NULL") op.execute("UPDATE orders SET status = 'pending' WHERE shipped_at IS NULL") op.alter_column("orders", "status", nullable=False) # now safe to enforce NOT NULL
The workflow this implies: always read a generated migration before running it, never trust it blindly, especially for renames, composite index changes, or anything touching a column that already has production data in it. Autogenerate is a first draft, not a final answer — it correctly detects "the schema differs," but it cannot know your INTENT (was this a rename, or a genuine drop-and-add?), and it never knows anything about the values already living in the affected rows.
Interview-ready definition: alembic revision --autogenerate generates a migration by diffing SQLAlchemy model metadata against the database's reflected schema, and is reliable for unambiguous structural changes (column/table/simple-index add or drop) but is not intent-aware: a column rename is detected as an unrelated drop-plus-add (destroying existing data unless hand-corrected to op.alter_column(..., new_column_name=...)), and it cannot generate data migrations at all, since backfilling or transforming existing row values has no corresponding "before/after" difference in model structure for the diff to detect. Every autogenerated migration should be read and, where needed, hand-edited before being trusted — treat it as a draft, not a guarantee.
03 — Not "which is better," but "which fits THIS service's actual access pattern"

SQL vs NoSQL, revisited with a concrete service

Start here, before the decision. The Month 1 SQL vs NoSQL lab covered the abstract trade-offs — schema-on-write vs schema-on-read, ACID guarantees vs horizontal scale, joins vs denormalized documents. This section does something different: it applies that framework to one real, specific decision this month's own notification service design has to make, using the actual read/write pattern of that specific system rather than a generic example.

The question: where should notification delivery history live — Postgres, or a document store? Every time a notification is sent (or attempted, or retried, or DLQ'd), that event needs to be recorded somewhere durable, queryable, and auditable.

The actual access pattern for this specific service

Recall the notification service's shape from earlier this month: one logical event fans out to multiple channels (email, push, SMS), each channel attempt can retry with backoff, and a failed attempt eventually lands in a dead-letter queue with its full failure history preserved. What does the delivery-history record for ONE notification attempt actually need to hold?

Most of that row is a clean, fixed relational shape: an ID, a channel name, an integer attempt number, a status enum, a timestamp. But provider_response is genuinely different — its shape varies by channel and even by provider (SendGrid's error payload looks nothing like Twilio's, which looks nothing like APNs's), it's write-once and rarely queried by its internal fields (mostly read back whole, for a human debugging one specific failure), and new fields can appear in it any time a vendor changes their API without warning.

WEIGH THE ACTUAL ACCESS PATTERN
Pick a framing to see how the access pattern drives the storage decision.

All-Postgres (relational, with a JSONB column)

Use Postgres for everything: a normal relational table for the fixed fields (notification_id, channel, status, timestamps) with proper indexes for the actual query patterns ("show me all failed attempts for notification X," "count failures per channel this week"), and a JSONB column for provider_response to hold the variable, vendor-specific payload without needing a schema migration every time a new provider is added or a vendor changes their response shape.

Separate document store

Push the entire delivery log into a document database (e.g. MongoDB or DynamoDB), reasoning that the record is "mostly unstructured anyway." This trades away Postgres's transactional guarantees and its ability to JOIN delivery-log rows against the rest of the relational schema (e.g. the notifications table, the users table) in a single query, in exchange for schema flexibility this specific case doesn't actually need as much as it looks like it does.

The right call here is the all-Postgres approach with a JSONB column, and the reasoning matters more than the conclusion: the WRITE pattern (one row per delivery attempt, append-only, never updated after the fact) and the READ pattern (mostly structured queries — "attempts for notification X," "failure rate per channel," "everything currently in the DLQ" — occasionally a human reading one row's full provider_response for debugging) are both patterns relational databases handle well, AS LONG AS the one genuinely variable field is isolated into a JSONB column rather than forcing the whole record into a rigid, brittle fixed schema. Reaching for a full separate NoSQL document store here would mean giving up transactional consistency with the rest of the relational schema (can this delivery-log write and a corresponding notifications-table status update ever need to be atomic together? — yes, plausibly) for a flexibility need that a single JSONB column already satisfies.

The mistake this revisits from Month 1: "this data has some unstructured parts" is not, by itself, a reason to leave a relational database. Modern relational databases (Postgres in particular) support a JSONB column right alongside strictly-typed columns in the SAME row, which handles exactly this "mostly structured, one field genuinely variable" shape without paying the cost of a second storage system, a second connection pool, a second set of migrations, and the loss of transactional consistency with the rest of the schema. The decision should follow the ACTUAL proportion and criticality of the unstructured part, not just its presence.
Interview-ready definition: the SQL vs NoSQL decision for a specific service should be driven by that service's actual read/write access pattern — not a generic "structured data → SQL, unstructured data → NoSQL" heuristic. For the notification delivery log specifically: the majority of fields are fixed and relational (IDs, enums, timestamps), the query patterns are structured (filter by notification, channel, or status), and cross-table consistency with the rest of the relational schema matters — all of which favor Postgres. The one genuinely variable field (vendor-specific provider responses) is handled by a single JSONB column rather than justifying a wholesale move to a document store, since a hybrid relational-plus-JSONB design captures the schema flexibility benefit without sacrificing joins, transactions, or a single unified storage system.

Problem 1 · Tracing a migration chain by hand

A database is currently at migration c3. The chain is c1 → c2 → c3 → c4 → c5 (each arrow meaning "down_revision points back to the previous one"). Someone runs alembic upgrade head. Which migrations' upgrade() functions run, and in what order?

Show solution
c4's upgrade() runs first, then c5's upgrade() runs second. c1, c2, and c3 do NOT run again -- they're already applied (the database is currently AT c3, meaning everything up through and including c3 has already run). Alembic tracks the current revision in its own version table, walks the down_revision chain to find every migration between the current position and "head" (the newest revision, c5), and applies each one's upgrade() in order from oldest-not-yet-applied to newest -- here, that's exactly c4 then c5.
Problem 2 · Fixing an autogenerated rename before it runs

You rename a model field from email_addr to email and run alembic revision --autogenerate. The generated file contains op.drop_column("users", "email_addr") followed by op.add_column("users", sa.Column("email", sa.String())). What's wrong, and what's the corrected version?

Show solution
Running this as generated would DELETE every existing user's email address -- the drop_column destroys the column and all its data, and the subsequent add_column creates a brand new, entirely empty "email" column with no relationship to what used to be in "email_addr". Autogenerate detected this as two unrelated changes (one column disappeared, a different one appeared) because it has no way to infer that a rename was the actual intent behind those two changes. Corrected version, replacing both generated lines with a single alter_column call: def upgrade() -> None: op.alter_column("users", "email_addr", new_column_name="email") def downgrade() -> None: op.alter_column("users", "email", new_column_name="email_addr") This preserves every existing row's value under the new column name in both directions, instead of destroying and recreating the column.
Problem 3 · Deciding whether a change needs a hand-written data migration

Which of these three changes can autogenerate handle correctly on its own, and which need a hand-written migration: (a) adding a nullable phone_number column to users, (b) adding a NOT NULL country_code column to a table with 2 million existing rows, (c) splitting an existing full_name column into separate first_name and last_name columns?

Show solution
(a) Autogenerate handles this fine on its own. A nullable column add is exactly the unambiguous structural change autogenerate is reliable for -- existing rows simply get NULL in the new column, no data transformation needed. (b) Needs a hand-written migration. A NOT NULL column with no default cannot be added to a table that already has 2 million rows without SOME value for every existing row -- autogenerate will generate the add_column call, but naively adding it as NOT NULL with no default would fail against existing data. The real migration needs to: add the column as nullable first, backfill a value for all 2 million existing rows (op.execute(...) with real logic, or a default derived from other data), THEN alter the column to NOT NULL once every row has a value -- a three-step hand-written sequence autogenerate cannot produce on its own. (c) Needs a hand-written migration. This is a data transformation (parsing "full_name" into two parts for every existing row), not a structural rename -- autogenerate would only see "full_name disappeared, first_name and last_name appeared" as an unrelated drop+add, and even a corrected non-destructive version still requires hand-written logic (likely op.execute() with a string-splitting UPDATE, or a Python-level batch operation) to actually populate first_name/last_name from each existing full_name value before dropping the old column.
Problem 4 · Applying the notification-service reasoning to a different service

Using the same reasoning framework from section 3 (majority field shape, actual query pattern, need for joins/transactions with other tables), would you store a URL shortener's click-analytics data (one row per click: short_code, timestamp, referrer, user_agent, rough geolocation) in Postgres or a document/columnar store? Justify using the specific access pattern, not a general preference.

Show solution
This one genuinely leans toward NOT plain Postgres, or at least not the SAME Postgres instance serving the shortener's core redirect lookups -- and the reasoning is the interesting part, since it differs from the notification-log case despite looking superficially similar (also "one row per event"). Key differences in the actual access pattern: click-analytics data is extremely high VOLUME and WRITE-heavy (every single redirect potentially generates a row, at whatever scale the shortener's read traffic already runs at), it is rarely if ever JOINed against the shortener's core short_code -> long_url table in a single transactional query, and it is typically queried in AGGREGATE ("clicks per day for code X over the last month") rather than row-by-row. That access pattern -- high write volume, rarely joined transactionally with core relational data, mostly queried in bulk/aggregate -- is a much better fit for either a columnar/analytics- oriented store or a NoSQL store optimized for high-throughput appends and aggregation, kept SEPARATE from the core relational database serving the actual redirect lookups, so that a click-analytics write storm never risks degrading the latency-critical redirect path. Contrast with the notification log: lower relative volume, frequently queried by structured filters (notification_id, channel, status), and plausibly needs transactional consistency with the rest of the relational schema -- which is why Postgres+JSONB was the right call there. Same framework, different answer, because the actual access pattern differs.
Problem 5 · Writing the downgrade() for a hand-written data migration

For the backfill migration in section 1's data-migration example (adding orders.status, backfilling it from shipped_at, then setting it NOT NULL), write a reasonable downgrade(). What's the fundamental limitation of any downgrade() for a migration like this?

Show solution
A reasonable downgrade(): def downgrade() -> None: op.alter_column("orders", "status", nullable=True) op.drop_column("orders", "status") The fundamental limitation: this downgrade can cleanly reverse the STRUCTURAL part (removing the column), but it cannot truly "undo" the migration in the sense of restoring the exact pre-migration state, because the backfill in upgrade() was a lossy computation -- it derived status from shipped_at, but nothing about that process is reversible in the other direction (there was no "status" column before this migration to derive shipped_at FROM). Once this migration's upgrade() has run and the status column is later used for OTHER purposes -- say, a support agent manually overrides a specific order's status -- running downgrade() still just drops the whole column, silently losing that override along with everything else, with no way to recover it. This is a general, important truth about data migrations: downgrade() for a structural change (add/drop a column) is almost always cleanly reversible, but downgrade() for a DATA migration is frequently only a partial or best-effort reversal, since real information can be created, derived, or overwritten between the upgrade and any later downgrade. This is exactly why production teams treat "can we roll this back" as a real design question for data migrations specifically, not an assumption that downgrade() always makes you whole again.
