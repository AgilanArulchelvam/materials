DATABASE FUNDAMENTALS LAB · EVENT SOURCING VS. CRUD

A row that gets UPDATEd forgets what it used to be. A sequence of events never does.

audit_trail_schema.html already borrowed one piece of this idea — recording what happened, not just the current state, so a failure could be replayed later. This lab names that idea directly: event sourcing stores state as a sequence of immutable events and derives current state by replaying them, trading query simplicity for full historical replayability. Most systems don't need this — knowing exactly when to reach for it, versus when a normal CRUD table is simply the right, simpler default, is the actual skill.

01 — Store what HAPPENED, not just what's true right now

Storing state as a sequence of events

Start here, before any DDL. Think about a bank statement versus a bank balance. A balance is a single number that gets silently overwritten every time money moves — look at it right now and you know how much is there, but you have no idea HOW it got there unless something else recorded that separately. A statement, by contrast, is a list of every individual transaction, in order — each deposit and withdrawal preserved forever as its own line. You can still compute the current balance from a statement (sum every line), but you can ALSO answer questions a bare balance never could: when exactly did this money arrive, what was the balance after any specific past transaction, did a specific transaction get reversed later. Event sourcing is a database applying the "statement" approach to ALL of an entity's state, not just its money.

Concretely: instead of an orders table with a single status column that gets UPDATEd in place every time the order's status changes — overwriting whatever the previous status was — event sourcing stores every status CHANGE as its own immutable row, appended to an events table, never updated or deleted once written:

-- CRUD approach: one mutable row, overwritten on every change CREATE TABLE orders ( order_id UUID PRIMARY KEY, status TEXT NOT NULL, -- overwritten in place by every UPDATE updated_at TIMESTAMPTZ NOT NULL ); -- after 3 status changes, this row shows ONLY the current status -- -- "shipped" -- with zero trace that it was ever "created" or "paid" -- Event sourcing approach: an APPEND-ONLY log of every state change CREATE TABLE order_events ( event_id UUID PRIMARY KEY DEFAULT gen_random_uuid(), order_id UUID NOT NULL, event_type TEXT NOT NULL, -- 'OrderCreated', 'PaymentReceived', 'OrderShipped' payload JSONB NOT NULL, -- whatever data THIS event carries occurred_at TIMESTAMPTZ NOT NULL -- NOTE: no status column, no UPDATE ever runs against this table -- -- every row, once written, is permanent and never modified ); -- one order's full history, as three separate, permanent rows INSERT INTO order_events (order_id, event_type, payload, occurred_at) VALUES ('ord-501', 'OrderCreated', '{"items": ["sku-42"], "total": 89.00}', '2026-08-01 09:00'), ('ord-501', 'PaymentReceived', '{"amount": 89.00, "method": "card"}', '2026-08-01 09:02'), ('ord-501', 'OrderShipped', '{"carrier": "ups", "tracking": "1Z..."}', '2026-08-03 14:30');

To find the order's CURRENT status under event sourcing, you don't read a status column at all — there isn't one. You derive it by replaying (or "folding") every event for that order, in order, applying each one's effect on top of the last: start with no order, apply OrderCreated → status is "created"; apply PaymentReceived → status becomes "paid"; apply OrderShipped → status becomes "shipped". The final status is a COMPUTED result of walking the whole event sequence, not a value that was ever directly stored anywhere.

Interview-ready definition: event sourcing stores an entity's state as a sequence of immutable, append-only events — each representing one discrete state CHANGE (OrderCreated, PaymentReceived, OrderShipped) — rather than storing only the entity's current state in a row that gets overwritten on each update. Current state is derived, not stored directly: it's computed by replaying (folding) every event for that entity, in order, from the beginning, applying each event's effect on top of the last. Nothing is ever updated or deleted from the event log — the full history is the source of truth, and "current state" is just one particular, derivable VIEW of that history.
02 — Full history is not free — it's traded for something real

Replayability vs. query complexity

Start here, before the trade-off table. Section 1's bank-statement analogy already hints at the cost: a statement is strictly MORE informative than a balance, but nobody actually wants to compute "what's my balance right now" by re-adding every transaction since the account opened, every single time they check it at an ATM. A statement's completeness comes at the cost of making the single most common question ("what's true right now") more work to answer than it would be if that answer were just sitting in a column somewhere.

What event sourcing gives you

Full history, always. You can answer "what was this order's status at 9:01am on Aug 1st" (a moment BETWEEN two events) by replaying only the events that occurred before that timestamp. You can answer "how many orders were cancelled after payment but before shipping, in the last quarter" by scanning the event log for that exact pattern. This directly extends audit_trail_schema.html's replay concept from last week — that lab's tool_call_audit log borrowed exactly this principle at a smaller scale (a detailed, ordered record of what happened, not just a final state) to support debugging a failed session after the fact.

What it costs you

Query complexity for "what's true right now." "Show me every order currently in 'shipped' status" can't be a simple WHERE status = 'shipped' against a column that doesn't exist — it requires either replaying every order's full event history on every query (prohibitively slow at scale) or maintaining a separate, continuously-updated PROJECTION table that mirrors what a plain CRUD status column would have given you for free.

That second cost has a standard mitigation, worth naming precisely because it reveals the real shape of the trade-off: a projection (or "materialized view" / "read model") is a normal, CRUD-shaped table — e.g. an order_current_state table with a plain status column — that gets kept up to date by replaying new events onto it AS they arrive, rather than replaying the entire history from scratch on every read. This gives you fast, simple "what's true right now" queries again, but now you're maintaining TWO things instead of one: the immutable event log (the source of truth) AND at least one projection (a derived, disposable cache of one particular VIEW of that log) — and the projection has to be kept correctly in sync with the log as new events arrive, which is real, ongoing engineering work a plain CRUD table never required in the first place.

-- a PROJECTION: a normal, fast-to-query table, kept in sync by replaying -- new events onto it -- this is what makes "current state" queries fast -- again, at the cost of maintaining this table as a second, derived thing CREATE TABLE order_current_state ( order_id UUID PRIMARY KEY, status TEXT NOT NULL, -- the FOLDED result of that order's events so far total NUMERIC, last_event_at TIMESTAMPTZ NOT NULL ); -- CRUD-shaped and fast: exactly the query event sourcing alone can't do cheaply SELECT * FROM order_current_state WHERE status = 'shipped';
QuestionPlain CRUD tableEvent log aloneEvent log + projection
"What's this order's status right now?"Trivial — SELECT statusRequires replaying every event for that orderTrivial again — SELECT status from the projection
"What was this order's status at 9:01am on Aug 1st?"Impossible — the prior value was overwritten and is goneReplay events up to that timestamp — fully answerableAnswerable via the log (the projection alone can't answer this either — it only reflects NOW)
Ongoing maintenance burdenNone beyond the table itselfNone beyond appending eventsMust keep the projection's replay logic correct and current as new events arrive
The trade-off, stated precisely: event sourcing doesn't make "what's true right now" queries impossible — it makes them require either a replay (slow, but always correct) or a maintained projection (fast, but now a second artifact that has to be kept in sync). A plain CRUD table gives you the "right now" answer for free, permanently, because that's the ONLY thing it was ever designed to answer — it never had a "what was true at 9:01am" question to answer in the first place, so it isn't giving anything up by not being able to answer it.
Interview-ready definition: the core trade-off between event sourcing and CRUD is replayability versus query simplicity. Event sourcing preserves the full history of every state change, enabling reconstruction of state at any past point in time and rich queries over the sequence of changes itself — directly extending the replay-for-debugging value audit_trail_schema.html established for tool call logs — but answering "what's true right now" requires either replaying the full event history on every read or maintaining a separately-updated projection table, which is genuine additional complexity a plain CRUD table's single, always-current row never has to pay.

04 — Most systems should just use CRUD. Really.

When CRUD is simpler and sufficient

Start here, before deciding. Section 2 and 3 made event sourcing look appealing — full history, replayable state, nothing ever silently lost. It's tempting to conclude "this is strictly better, why wouldn't every table work this way?" The answer is the same one audit_trail_schema.html's own Practice Problem 5 already reached from the other direction: event sourcing is a DELIBERATE trade, made specifically by systems that actually need historical replay or a full audit trail — not a universal upgrade. If you don't need that, a normal CRUD table with a plain UPDATE is simpler, and simpler should be the default absent a specific reason not to.

SignalFavors event sourcingFavors plain CRUD
Does the business genuinely need "what was true at time T in the past"?Yes — e.g. financial ledgers, order lifecycle disputes, compliance audit requirementsNo — most CRUD entities (a user's display name, a product's current price) only ever need to answer "what's true right now"
Is there real value in replaying history to debug or reconstruct behavior?Yes — audit_trail_schema.html's tool-call debugging case is exactly thisNo — if nobody would ever ask "how did this get to its current value," the history has no consumer to justify the extra complexity
Engineering capacity to build and maintain projections correctlyTeam has the capacity and the need justifies itTeam doesn't want to own projection-consistency bugs for a benefit nobody's asking for
"What's true right now" is the overwhelmingly dominant query patternStill fine with event sourcing + a projection, but that projection IS basically just a CRUD table anywayJust use a CRUD table directly — you'd be building the event log's own escape hatch as your primary design

Notice the last row's implication directly: if "what's true right now" is nearly everything your system needs, and you build event sourcing anyway, you typically end up building a CRUD-shaped projection table as your PRIMARY way of answering the overwhelming majority of your real queries — at which point you're paying event sourcing's full complexity cost (the event log, the replay/fold logic, projection-consistency maintenance) for a benefit (full history) that isn't actually being used. This is the same "don't reach for a more complex tool than the workload requires" reasoning sql_vs_nosql.html and migrations_and_sql_vs_nosql_revisited.html apply elsewhere this system's design has to reckon with — event sourcing is a real, valuable pattern for the RIGHT workload, and unnecessary, pure overhead for the wrong one.

Interview-ready definition: CRUD (a plain table with rows that get created, read, updated, and deleted directly) remains the correct default whenever a system doesn't have a genuine, specific need for historical replay, point-in-time reconstruction, or a full audit trail of every state change — which describes most tables in most systems. Event sourcing is a deliberate trade made BY systems that specifically need that history (financial ledgers, compliance-audited workflows, systems like audit_trail_schema.html's tool-call log that exist explicitly to support later replay) — not a strictly-better default, because it introduces real, ongoing complexity (maintaining projections, replay logic) that a system without that specific need would be paying for no corresponding benefit.

Problem 1 · Deriving state at a PAST point in time, not just "now"

Using section 1's order_events schema, write the query logic (in words or pseudo-SQL) to determine order ord-501's status as of 2026-08-02 (a date AFTER payment but BEFORE shipping). Could a plain CRUD orders table with only a status column ever answer this same question?

Show solution
SELECT event_type, payload, occurred_at FROM order_events WHERE order_id = 'ord-501' AND occurred_at <= '2026-08-02' ORDER BY occurred_at ASC; Then fold these results in order: OrderCreated (status becomes "created") -> PaymentReceived (status becomes "paid"). OrderShipped's occurred_at (2026-08-03) is AFTER the cutoff, so it's excluded by the WHERE clause and never applied -- the folded result as of 2026-08-02 is "paid", correctly reflecting that the order hadn't shipped yet at that point in time. A plain CRUD orders table with only a status column could NOT answer this at all -- by the time you're asking the question, the table's single status column has already been overwritten to "shipped" (the CURRENT value), and the "paid" value that was true on 2026-08-02 was destroyed the moment the UPDATE to "shipped" ran. This is section 2's trade-off made completely concrete: the event log answers a question (state as of a specific past moment) that a CRUD table's design makes structurally unanswerable, not just inconvenient -- the data needed to answer it was deleted by the CRUD table's own normal operation.
Problem 2 · Diagnosing a projection that's fallen out of sync

A system's order_current_state projection shows ord-501 as status "paid", but the order_events log has an OrderShipped event for it from an hour ago. Using section 2's projection-maintenance reasoning, what's the most likely cause, and why is this a NEW category of bug that plain CRUD tables don't have?

Show solution
The most likely cause: the process responsible for replaying new events onto the projection (the "keep the projection in sync" logic section 2 describes) either failed silently on the OrderShipped event specifically, is running behind (a queue or worker lag, similar in spirit to async_tool_job_queue_design.html's worker-processing delay), or has a bug that doesn't correctly handle this particular event_type. The event log itself (the source of truth) is NOT wrong -- it correctly has the OrderShipped event; the projection (a derived, secondary artifact) has simply failed to catch up to what the log already contains. Why this is a NEW category of bug plain CRUD doesn't have: a plain CRUD orders table has exactly ONE place status lives -- there's no "source of truth" and "derived copy" to fall out of sync with each other, because there's only ever one copy. Event sourcing's two-artifact design (immutable log + derived projection) introduces an entirely new failure mode -- projection staleness or corruption -- that simply cannot occur in a system with only one place any given piece of state is stored. This is exactly section 2's "ongoing maintenance burden" row made concrete: the projection isn't free to maintain, and "the projection disagrees with the log" is a genuinely new class of bug this architecture invites that a CRUD table's design makes impossible by construction.
Problem 3 · Deciding between event sourcing and CRUD for a specific new feature

A team is building a simple "user's display name" feature — just a name shown next to their posts, changeable anytime, with no requirement to ever show "what name did this user have when they made THIS specific post." Using section 4's table, which approach is correct here, and what would change your answer?

Show solution
Plain CRUD is correct here -- a users table with a display_name column that gets UPDATEd directly whenever the user changes it. Checking section 4's signals: there's no stated need to reconstruct "what was true at time T" (the problem explicitly says there's no requirement to show historical names per-post), no audit/compliance driver mentioned, and "what's the user's CURRENT display name" is clearly the dominant, essentially only, query pattern this feature needs. Building an event-sourced name_change_events log plus a projection for this would be pure unnecessary complexity -- paying event sourcing's maintenance cost (section 2's projection-sync burden, Problem 2's new failure mode) for a capability (point-in-time name reconstruction) nobody asked for and the product explicitly doesn't need. What WOULD change the answer: if a later requirement emerged that posts should display the name the user had AT THE TIME they posted (a genuinely common real feature, actually -- many platforms preserve the poster's name-at-post-time) -- that's precisely the kind of point-in-time reconstruction need section 4's first row names as favoring event sourcing. Even then, a simpler middle ground often suffices before reaching for full event sourcing: just DENORMALIZE the display name directly onto each post row at post-creation time (posts.author_name_at_ post_time), a plain CRUD technique that captures the one specific historical fact actually needed without building a general-purpose event log for a single, narrow requirement -- worth naming because "we need SOME history" doesn't automatically mean "we need full event sourcing"; sometimes a targeted CRUD-shaped solution to the SPECIFIC historical need is simpler than a general-purpose event log built for open-ended future questions nobody has asked yet.
Problem 4 · Connecting event sourcing to audit_trail_schema's replay argument, precisely

audit_trail_schema.html argued its tool_call_audit table "borrows event sourcing's core principle... without requiring the audit trail itself to be a full event-sourced system." Using this lab's definitions, name the ONE specific thing that audit trail is missing that would be required for it to count as TRUE event sourcing of the underlying entity (e.g. an agent's session state).

Show solution
The audit trail logs EVERY tool call as an immutable, ordered row -- genuinely borrowing event sourcing's "record what happened, in order, never overwritten" principle. What it's missing to count as TRUE event sourcing of, say, an agent's session or conversation state specifically: there's no defined FOLD/REPLAY function that reconstructs a meaningful CURRENT STATE of the underlying entity (the agent's session) FROM those rows -- audit_trail_schema.html's rows exist purely for human debugging and replay-of-individual-calls, not to be replayed and folded into an authoritative "here is the agent's current state" the way section 1's order_events rows fold into an order's current status. Concretely: tool_call_audit has no equivalent of section 1's event_type-driven state transitions (OrderCreated -> status="created", etc.) -- there's no code anywhere that says "replay every tool_call_audit row for this agent_id, in order, and the fold result IS this agent's current, authoritative state," because nothing in the system actually derives the agent's live state that way; the audit trail is a side log for debugging, not the primary source of truth the system reads from to know what's currently true. That's the specific gap audit_trail_schema.html's own phrasing ("without requiring... a full event-sourced system") was already flagging -- it borrows the RECORDING discipline of event sourcing without adopting the REPLAY-AS- SOURCE-OF-TRUTH discipline that would make it the real thing.
Problem 5 · Reasoning about indexing an event log for replay performance

Using the leftmost-prefix indexing reasoning from database/indexing.html and audit_trail_schema.html's Problem 1, what index would make replaying a single order's events (section 3's live demo) efficient at scale, and why does column ORDER in that index matter here specifically?

Show solution
An index on (order_id, occurred_at) -- order_id LEADING, occurred_at second. Replaying a single order's history is fundamentally: filter to exactly one order_id (an EQUALITY filter), then read its events in chronological ORDER (occurred_at ASC). Per indexing.html and audit_trail_schema.html's Problem 1's shared leftmost-prefix reasoning, the equality-filtered column belongs FIRST in the index so Postgres can narrow directly to just that one order's rows, with the sort/range column (occurred_at) second so those already-narrowed rows come back pre-ordered for the replay fold to consume directly, without a separate sort step. Column order matters specifically here because reversing it -- an index on (occurred_at, order_id) -- would be far less useful for THIS query pattern: it would let Postgres quickly find events in a given TIME range across ALL orders, but replaying one specific order's history would still require scanning through every order's events within whatever time range, filtering out all the OTHER orders' events along the way -- exactly the wasted-scan problem audit_trail_schema.html's Problem 1 described for a status-only index versus a (status, started_at) composite. Since section 3's replay pattern is fundamentally "give me ONE order's full history, in order," not "give me all events in a time window," (order_id, occurred_at) is the index shape that actually matches how this data gets queried in practice.
