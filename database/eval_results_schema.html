DATABASE FUNDAMENTALS LAB · EVAL RESULTS SCHEMA

An eval score with no trace behind it is a number nobody can trust.

This week built three families of eval checks — deterministic, model-graded, trajectory-based — and Thursday's observability_pipeline_design.html built the trace/metric/log pipeline those evals need to actually run against. This lab is where they meet: a schema for eval runs, eval results, and how a result links back to the specific trace_id of the exact execution that produced the behavior being scored — the same "link the record back to what actually happened" discipline audit_trail_schema.html established for tool calls, applied here to eval scoring.

eval_run — one batch execution of a test suite against a model/dataset
eval_result — one test case's score within that run
trace_id — the link back to the actual execution being scored

01 — Two tables, one relationship, and a link to the execution that actually happened

Schema for eval runs, scores, and trace records

Start here, before any DDL. Think about a school's report card system. A "run" is one exam sitting — a specific date, a specific test version, a specific group of students taking it together. A "result" is one student's one score on one question within that sitting. And critically, if a student disputes their score, the school doesn't just have the number — it has the ACTUAL ANSWER SHEET that student submitted, so a grader can go back and verify exactly what happened, not just trust the recorded score in isolation. eval_run, eval_result, and the trace link are exactly this trio.

-- one row per BATCH execution of an eval suite -- e.g. "run the full -- deterministic + trajectory suite against agent v2.3 on the standard dataset" CREATE TABLE eval_run ( run_id UUID PRIMARY KEY DEFAULT gen_random_uuid(), started_at TIMESTAMPTZ NOT NULL, completed_at TIMESTAMPTZ, model_version TEXT NOT NULL, -- which agent/model build was under test dataset_id TEXT NOT NULL, -- which fixed set of test cases was used suite_name TEXT NOT NULL, -- e.g. "deterministic_v1", "trajectory_v1" triggered_by TEXT NOT NULL -- 'ci_pipeline', 'manual', 'scheduled' ); -- one row per TEST CASE's outcome within a given eval_run CREATE TABLE eval_result ( result_id UUID PRIMARY KEY DEFAULT gen_random_uuid(), run_id UUID NOT NULL REFERENCES eval_run(run_id), test_case_id TEXT NOT NULL, -- which fixed test case this result is for eval_type TEXT NOT NULL CHECK (eval_type IN ('deterministic', 'model_graded', 'trajectory')), score NUMERIC, -- e.g. 1.0/0.0 for pass/fail, or a 1-5 judge score passed BOOLEAN NOT NULL, details JSONB, -- e.g. which sub-check failed, judge's justification trace_id TEXT, -- links to the EXACT execution being scored evaluated_at TIMESTAMPTZ NOT NULL );

Notice the shape mirrors audit_trail_schema.html's own core table almost exactly: a header/detail split (eval_run is the "session," eval_result is the "one call" — the same relationship conversation_history_schema.html used for conversations and turns), a full JSONB details column rather than a lossy summary, and — most importantly for this lab — a trace_id column that isn't just metadata, it's the actual LINK back to observability_pipeline_design.html's trace pipeline: the specific spans, tool calls, and timing of the exact execution that produced the output this eval_result row is scoring.

Why trace_id is a plain TEXT/string column here rather than a foreign key with a full REFERENCES constraint: the trace itself typically lives in a SEPARATE observability backend (per observability_pipeline_design.html's architecture — spans, metrics, and logs usually live in purpose-built time-series storage, not the same relational database as this eval schema). trace_id here is a REFERENCE by value into that other system, the same pattern agent_memory_schemas.html and conversation_history_schema.html already used for cross-system references that a single database's foreign key mechanism can't span — the two systems agree on an ID format, and joining across them happens at query time in application code, not via a database-enforced constraint.

Interview-ready definition: an eval results schema splits into a header/detail pair — eval_run (one batch execution: which model version, which dataset, which suite, when) and eval_result (one test case's score within that run: eval type, score, pass/fail, and structured details) — plus a trace_id column on each result linking it back to the specific execution (spans, tool calls, timing) that produced the behavior being scored. That link is what turns "this test failed" into "this test failed, and here's exactly what the agent did, in what order, that caused it" — without it, an eval result is just an isolated number with no path back to the actual evidence behind it, the same gap audit_trail_schema.html identified for tool calls logged without ordering or session context.

03 — What this schema is actually FOR, in practice

Real queries against this schema

Start here, before the SQL. A schema earns its shape by what it makes easy to ask. Three real questions a team running evals continuously actually needs to answer, and how this schema answers each:

-- Q1: "Has our pass rate for trajectory evals regressed across the last 5 runs?" SELECT r.run_id, r.started_at, r.model_version, COUNT(*) FILTER (WHERE res.passed) * 1.0 / COUNT(*) AS pass_rate FROM eval_run r JOIN eval_result res ON res.run_id = r.run_id WHERE res.eval_type = 'trajectory' GROUP BY r.run_id, r.started_at, r.model_version ORDER BY r.started_at DESC LIMIT 5; -- Q2: "Show me every failing result from the most recent run, with a path to its trace" SELECT res.result_id, res.test_case_id, res.eval_type, res.details, res.trace_id FROM eval_result res WHERE res.run_id = (SELECT run_id FROM eval_run ORDER BY started_at DESC LIMIT 1) AND res.passed = FALSE; -- Q3: "Does test case tc-882 fail consistently across recent runs, or is it flaky?" SELECT r.started_at, res.passed, res.score FROM eval_result res JOIN eval_run r ON r.run_id = res.run_id WHERE res.test_case_id = 'tc-882' ORDER BY r.started_at DESC LIMIT 10;

Q1 and Q3 both depend on the SAME structural fact: eval_result rows across MANY runs, for the SAME test_case_id, are directly comparable over time, because run_id and test_case_id together give every result a stable identity across runs. This is precisely why a leftmost-prefix index on (test_case_id, run_id) — or, depending on which query pattern dominates, (run_id, eval_type) — matters here exactly the way database/indexing.html and audit_trail_schema.html's Problem 1 established: put the equality-filtered column first, letting the database narrow directly instead of scanning and filtering after the fact.

Interview-ready definition: this schema's real value shows up in queries that track a metric OVER TIME (pass rate trend across runs) and queries that trace a SPECIFIC failure back to evidence (a failing result's trace_id). Both depend on the header/detail relationship (eval_run to eval_result) giving every result a stable, comparable identity across runs via test_case_id, and on the trace_id link giving every result a path to the actual execution evidence behind it — a schema that only stored aggregate pass/fail counts per run, without per-test-case rows or trace links, could answer "is our pass rate trending down" but could never answer "which SPECIFIC test case is regressing" or "WHY did it fail," which are usually the more actionable questions in practice.

Problem 1 · Deciding what belongs in eval_run vs eval_result

A team wants to add a judge_model_version field (which specific judge model scored a model-graded result). Does it belong on eval_run or eval_result? Justify using the header/detail relationship section 1 established.

Show solution
eval_result, not eval_run. eval_run captures properties of the BATCH as a whole (which model version is under TEST, which dataset, when the batch started) -- properties that are the same across every result in that run. judge_model_version is a property of ONE SPECIFIC result row's SCORING mechanism, and critically, it can legitimately differ WITHIN the same eval_run: a single run might include deterministic results (no judge at all -- judge_model_version would be NULL for those rows), model_graded results possibly scored by different judge model versions if a judge was upgraded mid-rollout, and trajectory results (also no judge). Putting judge_model_version on eval_run would force one single value to apply to every result in the batch, which is factually wrong the moment a run mixes eval types or judge versions -- exactly the same header/detail reasoning conversation_history_schema.html and audit_trail_schema.html both apply: a field describing ONE row's specific circumstances belongs on the DETAIL table, not the header, even when it happens to be constant across most rows in practice.
Problem 2 · Diagnosing a schema that can't distinguish a flaky test from a real regression

A team's eval_result table has no run_id column at all — just test_case_id, passed, and evaluated_at. Using section 3's Q3 query, explain specifically what becomes impossible to answer, and why.

Show solution
Without run_id, there's no way to group results into the BATCH they came from, which breaks two related things at once. First, Q1's per-run pass-rate aggregation becomes impossible to compute correctly -- "what was the pass rate for THIS SPECIFIC run" requires knowing which rows belong to that run, and evaluated_at timestamps alone are a weak, error-prone substitute (concurrent runs, or a run that takes a while to complete, would make timestamp-based grouping ambiguous or wrong in a way an explicit run_id foreign key never is). Second, and more subtly connecting to this problem's actual question: without run_id, you can still see individual pass/fail history for tc-882 ordered by evaluated_at (Q3's basic shape survives), but you lose the ability to correlate ITS failure with what ELSE failed or passed in the SAME batch -- e.g. "did tc-882 fail on a run where EVERYTHING else also failed (suggesting an infrastructure problem, not a real regression in tc-882 specifically) or did it fail in isolation while everything else in that same run passed (suggesting a genuine, specific regression for that test case)." That distinction is exactly what separates "this is probably flaky infrastructure" from "this is a real regression," and it requires being able to ask "what ELSE was in the SAME run as this failure" -- a question that has no answer at all without run_id linking results back to a shared batch identity.
Problem 3 · Reasoning about trace_id as a cross-system reference

Section 1 argues trace_id is a plain TEXT column, not a real foreign key, because the trace lives in a different system. What's the concrete downside of this design choice compared to a true foreign key, and why is it still the right trade-off here?

Show solution
The concrete downside: the database can no longer ENFORCE referential integrity on trace_id the way a real FOREIGN KEY REFERENCES constraint would for an in-database relationship. Nothing stops an eval_result row from being written with a trace_id that doesn't actually exist in the observability backend (a typo, a trace that was already pruned by observability_pipeline_design.html's retention policy, or a race condition where the eval_result is written before the trace finishes being ingested) -- the database has no mechanism to reject or flag this at write time the way it would reject an eval_result with a nonexistent run_id. Why it's still the right trade-off: the trace lives in a fundamentally different kind of storage system (a time-series/observability backend, per observability_pipeline_design.html's section 3, likely NOT even the same relational database engine at all) -- a true cross-database foreign key constraint isn't something most database engines can even enforce in the first place, since FK constraints only work within a single database's own schema. This is the same trade-off agent_memory_schemas.html and conversation_history_schema.html already accepted for other cross-system references: accept a referentially- unenforced pointer (with the small risk of a dangling reference) in exchange for NOT forcing every eval result and its trace data into the same storage system, which would be a far worse trade given how different observability data's storage/query shape (Thursday's lab) is from this schema's OLTP-like relational shape. The mitigation isn't a database constraint -- it's application-level tooling that surfaces a dangling trace_id as a data-quality issue to investigate, not something the schema itself can prevent from ever happening.
Problem 4 · Designing a retention policy for eval_result at scale

Using database/time_series_schema.html's retention reasoning and audit_trail_schema.html's Problem 5, a team runs the full eval suite on every CI commit — thousands of eval_result rows per day. Propose a retention strategy, distinguishing what should be kept in full detail versus summarized.

Show solution
The same tiered shape both referenced labs already established, applied to eval results specifically: keep full-detail eval_result rows (including the full JSONB details column and trace_id links) for a bounded RECENT window -- say 30-90 days, long enough to cover the overwhelming majority of "did my recent change break something, and why" investigations, which are almost always about recent commits, not commits from 8 months ago. Beyond that window, roll individual eval_result rows into a coarser per-run SUMMARY (pass count, fail count, pass rate, broken out by eval_type) rather than either deleting everything or keeping every row's full detail (including trace_id links, which are increasingly likely to be DANGLING anyway past that window, per Problem 3, since the observability backend's OWN retention window -- per observability_pipeline_design.html's section 3, 7-30 days for raw traces -- is typically much SHORTER than 90 days, meaning the trace_id link for an old eval_result is often already unusable regardless of whether the eval_result row itself survives). This last point is worth naming explicitly: eval_result's own retention window for FULL trace-linkable detail is naturally bounded by the SHORTER of (a) how long eval_result itself is worth keeping in full detail, and (b) how long the linked trace actually still exists in the observability backend -- keeping an eval_result row's trace_id "forever" past the point the trace itself has been pruned doesn't actually preserve any real debugging capability, just a pointer to nothing.
Problem 5 · Extending the schema for CI/CD gating

Week 2's roadmap calls for a "CI/CD gating system" that blocks deploys on eval thresholds. Using this schema, sketch (in words or SQL) the query a CI/CD pipeline would run against eval_run/eval_result to decide "should this deploy be blocked," and name one column this schema is MISSING that such a gate would need.

Show solution
The query: for the eval_run just completed against the candidate build (model_version = the new build being considered), compute the pass rate per eval_type (Q1's shape from section 3) and compare each against a configured threshold -- e.g. "deterministic pass rate must be >= 99%, trajectory pass rate must be >= 90%." If ANY threshold isn't met, the gate blocks the deploy; a pipeline would run this as an automated check immediately after the eval_run completes, before promoting the build. SELECT eval_type, COUNT(*) FILTER (WHERE passed) * 1.0 / COUNT(*) AS pass_rate FROM eval_result WHERE run_id = :new_run_id GROUP BY eval_type; -- pipeline logic: if any pass_rate < configured threshold for that -- eval_type, block the deploy and report which eval_type failed the gate One column this schema is missing for that purpose: a way to mark WHICH run corresponds to a specific CANDIDATE BUILD/deploy attempt being gated, distinct from routine scheduled or ad-hoc runs. triggered_by ('ci_pipeline' vs 'manual' vs 'scheduled') gets partway there, but a gating system specifically needs to correlate one eval_run with one SPECIFIC deploy/commit SHA it's gating -- a deploy_candidate_id or commit_sha column on eval_run, so the CI/CD pipeline can query "give me the eval_run for commit abc123" directly rather than relying on approximate matching by timestamp or model_version alone. This is exactly the kind of schema gap Week 4's "finalize eval/trace schema" checkpoint exists to catch before it's locked in -- a real, missing requirement that only became obvious once a concrete downstream USE (CI/CD gating) was worked through against the schema as originally designed.
