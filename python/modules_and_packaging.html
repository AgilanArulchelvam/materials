PYTHON INTERNALS LAB · MODULES & PACKAGING

An import is just Python searching a list of folders until it finds a match.

There's no magic lookup table — import foo walks sys.path, a plain list of directory strings, checking each one in order until it finds something named foo. Once that's concrete, absolute vs. relative imports, __init__.py, pyproject.toml, and virtual environments all stop being folklore and become one consistent mental model.

import foo
searches ⟶
sys.path[0], sys.path[1], sys.path[2]...

01 — Where Python actually looks

The module search path: sys.path

Start here, before any code. Imagine you ask a friend to find your keys. They don't magically know where keys live — they check your pocket, then the counter, then the drawer by the door, in that specific order, and stop as soon as they find a set. If two rooms both have keys, the first room checked wins, even if the "real" set is in the second room.

That's exactly what import foo does. Python doesn't have some global registry of every module on your machine. It holds a plain Python list, sys.path, and walks it in order: the directory of the script being run, then PYTHONPATH entries, then the standard library location, then site-packages (where installed packages live). The first directory containing a matching foo.py or foo/ package wins — checking stops immediately.

import sys print(sys.path) ['/home/user/myproject', # 1. script's own directory '/usr/lib/python3.11', # 2. standard library '/usr/lib/python3.11/lib-dynload', '/home/user/myproject/.venv/lib/python3.11/site-packages'] # 3. installed packages
WATCH import requests SEARCH sys.path
[0] /home/user/myproject (script's own directory)
[1] /usr/lib/python3.11 (standard library)
[2] /usr/lib/python3.11/lib-dynload
[3] .venv/lib/python3.11/site-packages (installed packages — requests lives here)
Why "no module named X" sometimes lies to you: if you have a local file named requests.py in your own project directory, it sits at sys.path[0] — before site-packages — so import requests silently imports YOUR file instead of the real library, and then fails with confusing errors about missing attributes. This is the single most common "why is my import broken" bug: never name a file the same as a package you depend on.
Interview-ready definition: the module search path is the ordered list sys.path — script directory, then PYTHONPATH, then standard library, then site-packages — that Python's import system walks left to right, returning the first module or package matching the requested name and caching the result in sys.modules so subsequent imports of the same name are free.
02 — Turning a folder into a package

Packages and __init__.py

Start here, before any code. A folder full of loose papers isn't a "file" — but put them in a labeled binder with a cover page, and now it's one thing you can hand someone as a unit. __init__.py is that cover page: it's what tells Python "treat this directory as one importable package," and its code runs once, automatically, the moment anything imports the package.

A directory containing an __init__.py file is a package — a namespace that can contain modules (.py files) and sub-packages (more directories with their own __init__.py). The file can be completely empty; its mere presence is the signal. It can also actively re-export names to shape the package's public API.

myapp/ __init__.py # can be empty, or re-export things models/ __init__.py user.py order.py utils/ __init__.py formatting.py
# myapp/__init__.py — re-exporting for a cleaner public API from .models.user import User from .models.order import Order # now callers can do the short form instead of the deep path: from myapp import User # works, because __init__.py re-exported it # instead of forcing: from myapp.models.user import User

Namespace packages (the exception): since Python 3.3, a directory without __init__.py can still be imported as a "namespace package" if nothing else claims that name — but it behaves subtly differently (no single __init__.py to run setup code, contents can be spread across multiple directories). In interviews and in practice, assume you need an explicit __init__.py unless you have a specific reason for the namespace-package behavior.
03 — Two ways to name a neighbor

Absolute vs. relative imports

Start here, before any code. Giving someone directions, you can say "123 Main Street, Springfield" (works from anywhere, same words every time) or "the house two doors down" (only makes sense if you're already standing at a specific spot). Absolute imports are the full address; relative imports are "two doors down from here."

Absolute imports spell out the full path from the top of the package: from myapp.models.user import User. They work identically no matter which file writes them. Relative imports use dots to mean "relative to my own location": from .user import User (same directory) or from ..utils import formatting (up one level, then into utils). Relative imports only work inside a package — never in a top-level script run directly.

Absolute

from myapp.models.order import Order from myapp.utils.formatting import money

Relative

from .order import Order # same dir from ..utils.formatting import money # up 1, then in

Interview-ready definition: an absolute import names a module by its full dotted path from a top-level entry on sys.path; a relative import (from . import x / from .. import y) names a module by its position relative to the importing module's own package, resolved via that module's __name__ and __package__ — which is exactly why relative imports fail when a file is executed directly as a script rather than imported as part of a package.
04 — The project's single source of truth

pyproject.toml basics

Start here, before any code. Think of a shipping label on a package: it states what's inside, who it's from, and what carrier should handle it — all in one standard place, so anyone in the chain can read it the same way. pyproject.toml is that label for a Python project: one file, one standard format (TOML), that any tool — pip, build backends, linters — can read to understand the project.

It replaced a scattered mess of setup.py, setup.cfg, and tool-specific config files with one standardized file split into a few key tables (TOML sections).

# pyproject.toml [build-system] # what tool builds this into a distributable package requires = ["setuptools>=68"] build-backend = "setuptools.build_meta" [project] # the metadata label itself name = "myapp" version = "0.1.0" description = "A demo application" requires-python = ">=3.10" dependencies = [ "requests>=2.31", # what myapp needs to RUN "pydantic>=2.0", ] [project.optional-dependencies] dev = ["pytest>=7.0", "mypy>=1.5"] # only needed for development/testing

Click a section above to see its purpose explained.
Interview-ready definition: pyproject.toml is the PEP 518/PEP 621 standardized project descriptor — it declares the build backend needed to package the project ([build-system]), the project's own metadata and runtime dependencies ([project]), and optionally tool-specific configuration (e.g. [tool.mypy], [tool.pytest.ini_options]) — all in one file any PEP-517-compliant tool can parse identically, replacing the older setup.py/setup.cfg split.
05 — Why every project gets its own sandbox

Virtual environments and why isolation matters

Start here, before any code. Imagine two roommates sharing one closet, and both need "the black jacket" — but they need different sizes. There's no way to hang two things with the same label in the same closet without one shadowing the other. A virtual environment gives each project its own closet: same package name, independently chosen version, no collision.

A virtual environment is an isolated Python installation — its own site-packages directory and its own copy of (or link to) the interpreter — separate from the system Python and from every other project's environment. Activating one changes sys.path so installs and imports resolve inside that isolated directory instead of globally.

python -m venv .venv # create an isolated environment in ./.venv source .venv/bin/activate # (Linux/Mac) — now `pip install` writes HERE, not globally .venv\Scripts\activate # (Windows) pip install requests==2.28 # this project's copy — other projects are untouched
TWO PROJECTS, TWO ISOLATED ENVIRONMENTS

Project A — .venv

  • python 3.10
  • requests==2.28
  • django==4.1

Project B — .venv

  • python 3.12

Both projects depend on requests, but at different pinned versions — and both are satisfied simultaneously because each environment's site-packages is a completely separate directory. Without isolation, installing Project B's requests would silently upgrade (or break) Project A's.
Without isolationWith a virtual environment per project

Interview-ready definition: a virtual environment is a self-contained directory holding an interpreter reference and an isolated site-packages, created so that per-project dependencies (and their exact versions) don't collide with the system interpreter's packages or with another project's requirements — enabling reproducible, conflict-free dependency management across multiple projects on one machine.

Practice problems

Problem 1 · Shadowing the standard library

A developer creates a file named json.py in their project's root directory to experiment with JSON parsing. Afterward, every import json anywhere in the project starts failing with AttributeError: module 'json' has no attribute 'loads'. Why?

Show solution
Their own json.py sits in the script's own directory, which is sys.path[0] — checked BEFORE the standard library entry. So `import json` finds their empty/experimental file first and stops searching (first match wins), never reaching the real standard library json module. The fix is simply renaming the file to something that doesn't collide, like json_experiment.py.
Problem 2 · Package or not?

A directory helpers/ contains math_utils.py and string_utils.py, but no __init__.py. On Python 3.11, will from helpers.math_utils import square work?

Show solution
Likely yes, via "implicit namespace packages" (PEP 420, since Python 3.3) — a directory without __init__.py can still be treated as an importable namespace package as long as no __init__.py-based package of the same name exists elsewhere on sys.path first. However, it behaves slightly differently (no package-level __init__.py code runs, and namespace packages can be split oddly across multiple directories). In a real project, adding an explicit __init__.py is the safer, more predictable choice and is what almost every style guide recommends.
Problem 3 · Relative import failure
# myapp/models/user.py from .order import Order # run directly: python myapp/models/user.py
Show solution
This raises: ImportError: attempted relative import with no known parent package. Running a file directly makes its __name__ equal to "__main__", with no __package__ context — Python has no idea what "." is relative TO, because the file isn't being imported as part of a package, it's the entry point itself. Relative imports only work when the module is imported (e.g. via `python -m myapp.models.user` or from another module doing `from myapp.models import user`), not when run as a standalone script.
Problem 4 · Reading pyproject.toml
[project] name = "reportgen" version = "1.2.0" dependencies = ["pandas>=2.0", "click>=8.0"] [project.optional-dependencies] dev = ["pytest", "mypy"]

A teammate runs plain pip install reportgen. Will pytest and mypy get installed? What command would install them too?

Show solution
No — plain `pip install reportgen` only installs the required dependencies (pandas, click), not the optional "dev" extra. To also get pytest and mypy, they'd run: pip install "reportgen[dev]" — the bracket syntax explicitly requests the named optional-dependencies group. This split exists so end users installing the tool don't pull in testing tools they'll never use.
Problem 5 · Diagnosing a dependency conflict

Two projects on the same laptop, both installed with plain pip install directly into the system Python (no virtual environments). Project A needs requests==2.20 for a legacy API quirk; Project B needs requests>=2.31 for a security fix. What breaks, and what's the fix?

Show solution
There's only ONE site-packages directory (the system one), so only one version of requests can be installed at a time — installing 2.31 for Project B silently uninstalls/overwrites 2.20, breaking Project A's legacy API quirk (or vice versa, whichever was installed last "wins"). Fix: give each project its own virtual environment (python -m venv .venv inside each project directory, then pip install its own pinned requests version there). Each venv's site-packages is independent, so both pinned versions can coexist on the same machine without conflict.
