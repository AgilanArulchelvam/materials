PYTHON INTERNALS LAB · EXCEPTIONS & ERROR HANDLING

Every exception is a class instance, and catching it is just matching that instance against a type.

There's no separate "error system" bolted onto Python — raise ValueError("bad") creates an ordinary object and throws it up the call stack; except ValueError: catches it because isinstance() says yes. Once that's concrete, the exception hierarchy, custom exceptions, try/except/else/finally, and raise X from Y all click into one coherent system.

01 — Every error is a class, and classes have parents

The exception hierarchy: Exception → ValueError, KeyError, etc.

Start here, before any code. Think of a company's org chart for handling complaints: a generic "Customer Complaint" role sits above more specific roles like "Billing Complaint" and "Shipping Complaint." If you're willing to handle ANY complaint, you register for the generic role; if you only care about billing issues specifically, you register narrower. Catching exceptions works the same way — except Exception catches everything below it in the tree, while except ValueError only catches that branch.

Every built-in exception inherits from BaseException, and almost everything you'd ever want to catch inherits specifically from Exception (a narrower branch — SystemExit and KeyboardInterrupt deliberately sit outside it so a broad except Exception doesn't accidentally swallow a deliberate program exit). except SomeType: catches that type AND every subclass of it, because it's implemented as an isinstance() check.

Why SystemExit and KeyboardInterrupt are special: they inherit directly from BaseException, not Exception — deliberately, so that a broad except Exception: (a very common pattern for "catch anything that went wrong") does NOT accidentally intercept a user pressing Ctrl+C or a deliberate sys.exit() call. Only a bare except: (catching literally everything) would swallow those too — one of several reasons bare except: is considered dangerous.
Interview-ready definition: Python's exception hierarchy is a class inheritance tree rooted at BaseException, with Exception as the branch covering ordinary error conditions. except SomeExceptionType: catches any raised instance for which isinstance(instance, SomeExceptionType) is true — meaning it catches that exact type and every subclass beneath it in the tree, which is exactly why catching a broader ancestor type (like Exception) is a strictly wider net than catching one specific leaf type (like KeyError).
02 — When the built-ins aren't specific enough

Defining custom exceptions and when it's warranted

Start here, before any code. A generic "something went wrong" sticky note is useless to whoever finds it later — "insufficient funds, account #4471, tried to withdraw $200 with $50 available" is something they can actually act on. Custom exceptions are that specific sticky note: a named, purpose-built signal that carries exactly the information a caller needs to respond correctly.

Defining a custom exception is just subclassing Exception (or a more specific built-in, if your error genuinely IS a specialization of one). It's warranted when: (1) callers need to distinguish YOUR specific failure mode from generic ValueErrors elsewhere in a large codebase, (2) you want to attach structured data (an account ID, a validation field name) to the error object itself, or (3) you're building a library and want callers to be able to catch "any error from this library" via one common base class.

class InsufficientFundsError(Exception): """Raised when a withdrawal exceeds the available balance.""" def __init__(self, balance: float, requested: float): self.balance = balance self.requested = requested super().__init__( f"Cannot withdraw ${requested}: only ${balance} available" ) def withdraw(balance, amount): if amount > balance: raise InsufficientFundsError(balance, amount) return balance - amount try: withdraw(50, 200) except InsufficientFundsError as e: print(f"Blocked: needed ${e.requested}, had ${e.balance}") # structured data, not just a string

Interview-ready definition: a custom exception is a user-defined subclass of Exception (or an appropriate built-in) that names a specific, meaningful failure mode and can carry structured contextual data via its own attributes. It is warranted when generic built-in exception types can't be reliably distinguished by callers, when callers need programmatic access to failure details beyond a message string, or when establishing a shared base exception class for an entire module or library's error surface.
03 — Four blocks, four distinct jobs

try/except/else/finally semantics

Start here, before any code. Think of cooking a recipe: you attempt the dish (try), have a backup plan if something burns (except), only plate it nicely if nothing went wrong (else), and clean the kitchen no matter what happened either way (finally). Each block runs under a different, precise condition.

try: result = risky_call() # the code that MIGHT raise except ValueError as e: handle_error(e) # runs ONLY if a ValueError was raised in try else: use_result(result) # runs ONLY if try raised NOTHING at all finally: cleanup() # ALWAYS runs — success, caught error, or uncaught error

Interview-ready definition: try delimits code that may raise; a matching except clause runs exactly when a raised exception is an instance of its declared type; else runs exactly when the try block completes with no exception raised at all (making it the right place for code that should NOT be wrapped in the same try, to avoid accidentally catching its own errors); finally runs unconditionally — after success, after a caught exception, or even after an uncaught exception propagates further up the stack — making it the correct place for guaranteed cleanup like closing a file or releasing a lock.
04 — Precision vs. a wide, dangerous net

Catching specific exceptions vs. bare except

Start here, before any code. A smoke detector that only reacts to actual smoke is useful. One so sensitive it also goes off for steam from a shower, sunlight, and dust just trains everyone to ignore every alarm — including the real fire. A bare except: is that oversensitive detector: it catches everything, including bugs you'd actually want to know about, and silently hides them.

# BAD: bare except — catches EVERYTHING, including typos and Ctrl+C try: process(data) except: pass # a NameError from a typo now silently vanishes too # BETTER: catch the specific thing you know how to handle try: process(data) except ValueError as e: log.warning(f"Skipping malformed record: {e}") # anything else (a real bug) still propagates and gets noticed

The real cost of bare except: it doesn't just risk missing bugs — it actively destroys the evidence needed to find them. A NameError from a typo, silently caught and ignored, means the program keeps running in some half-broken state with no error message pointing at the actual mistake, often surfacing as a much more confusing failure much later.
05 — Preserving the original cause

Raising with context: raise X from Y

Start here, before any code. If a translator mistranslates a sentence, the useful bug report says both "the translation was wrong" AND "here's the original sentence that caused the confusion" — not just the garbled output on its own. raise X from Y keeps both: the new, more meaningful exception, and a visible link back to the low-level exception that actually caused it.

def load_config(path): try: with open(path) as f: return json.load(f) except FileNotFoundError as e: raise ConfigError(f"Missing config at {path}") from e # the traceback shows BOTH: ConfigError, AND # "The above exception was the direct cause of" FileNotFoundError

Compare this to plain raise ConfigError(...) written inside an except block without from e — Python still shows the original exception (as "during handling of the above exception, another exception occurred"), but from e makes the causal relationship explicit and intentional rather than incidental. raise ConfigError(...) from None deliberately suppresses the chain entirely, when the original is genuinely irrelevant noise.

Interview-ready definition: raise X from Y sets the new exception's __cause__ attribute to Y, producing an explicit exception chain that Python's default traceback formatter renders as "the above exception was the direct cause of." This preserves the original low-level failure for debugging while letting code raise a higher-level, more meaningful exception at each layer of abstraction — a common pattern when translating a library's internal errors into a caller-facing error type.

Problem 1 · Hierarchy matching
try: d = {"a": 1} print(d["b"]) except LookupError: print("caught it")
Show solution
caught it d["b"] raises KeyError. KeyError is a SUBCLASS of LookupError (both KeyError and IndexError inherit from it), so "except LookupError:" catches it via the same isinstance() logic that lets any ancestor type in the hierarchy catch its descendants. Catching the parent class is intentional here if you want to handle "any kind of lookup failure" the same way.
Problem 2 · Custom exception with data
class ValidationError(Exception): def __init__(self, field, reason): self.field = field self.reason = reason super().__init__(f"{field}: {reason}") try: raise ValidationError("email", "missing @ symbol") except ValidationError as e: print(e.field) print(str(e))
Show solution
email email: missing @ symbol e.field accesses the structured attribute directly (useful for programmatic handling — e.g. highlighting the specific form field). str(e) returns whatever was passed to super().__init__(...), which is the formatted message. This dual access — structured data AND a readable message — is exactly why custom exceptions beat raising a plain string-only ValueError when a caller needs to act on WHICH field failed, not just read a message.
Problem 3 · else vs finally
def process(n): try: result = 10 / n except ZeroDivisionError: print("cannot divide by zero") return None else: print(f"got {result}") return result finally: print("done processing") process(2) print("---") process(0)
Show solution
got 5.0 done processing --- cannot divide by zero done processing process(2): try succeeds (no exception) → else runs, printing "got 5.0" and returning 5.0 → finally STILL runs before the function actually returns, printing "done processing". process(0): try raises ZeroDivisionError → except catches it, prints "cannot divide by zero", returns None → else is SKIPPED entirely (it only runs when try raises nothing) → finally still runs regardless, printing "done processing" before the None actually returns to the caller.
Problem 4 · Bare except hides a real bug
def get_discount(price, user): try: return price * user.discount_rate except: return price get_discount(100, None)
Show solution
Returns 100 — silently, with no error or warning anywhere. user is None, so user.discount_rate raises AttributeError: 'NoneType' object has no attribute 'discount_rate' — a genuine bug (probably a missing user lookup upstream). The bare except: swallows it completely and falls back to price, masking the real problem. If this had instead been `except (ZeroDivisionError, TypeError):` scoped to whatever the function actually anticipates, the AttributeError would propagate and get noticed immediately instead of silently returning a wrong-but-plausible-looking value.
Problem 5 · Exception chaining
class OrderError(Exception): pass def charge_card(order): try: return payment_gateway.charge(order.total) except ConnectionError as e: raise OrderError(f"Could not process order {order.id}") from e charge_card(some_order)
Show solution
If payment_gateway.charge() raises ConnectionError, the resulting traceback shows OrderError as the exception that propagates out of charge_card, with __cause__ set to the original ConnectionError — printed as "The above exception was the direct cause of the following exception." This lets calling code catch just OrderError (a clean, meaningful, order-level abstraction) without needing to know or care that the underlying transport used ConnectionError specifically — while a developer reading the full traceback during debugging still sees exactly which low-level network failure triggered it, instead of that detail being lost.
