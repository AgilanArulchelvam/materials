PYTHON INTERNALS LAB · THE GLOBAL INTERPRETER LOCK

Only one thread may touch Python objects at a time — no exceptions.

The GIL is a single lock that every thread must hold before running any Python bytecode. It exists to protect the exact reference-counting machinery from the previous lab from getting corrupted by two threads racing to update the same object's refcount. That one fact explains why threading barely helps CPU-bound Python, why it helps I/O-bound Python enormously, and why multiprocessing exists at all.

01 — One lock, guarding everything

What the GIL is, and why it exists

Start here, before any code. Imagine a single microphone at a crowded meeting, and a strict house rule: nobody may speak unless they are physically holding the microphone. Even if ten people all have something to say at once, only one voice actually comes out of the speakers at any given moment — the microphone itself is the bottleneck, by design. It isn't there because people can't talk simultaneously in principle; it's there because the sound system can only mix one clean signal at a time without garbling everything into noise.

The GIL — Global Interpreter Lock — is that microphone. It's a single mutex inside the CPython interpreter, and the rule is simple: no thread may execute Python bytecode unless it currently holds the GIL. Even on an 8-core machine running 8 Python threads, only one of them is ever actually running Python code at any given instant.

Why build it this way at all? Recall the previous lab: every object's refcount gets incremented and decremented constantly, by ordinary code, all the time. If two threads could run Python bytecode truly simultaneously, two threads could both try to increment (or one increment while another decrements) the same object's refcount at the exact same instant — a classic race condition. Depending on timing, an update could get lost, leaving the refcount permanently wrong: too high (a leak — the object never gets freed) or too low (freed too early, while something still needs it — a crash or corrupted memory). The GIL sidesteps this entire class of bug with a blunt but effective rule: only one thread ever touches Python objects (and their refcounts) at a time, full stop.

One increment was silently lost — this is # exactly the kind of bug the GIL exists to make structurally impossible.
Interview-ready definition: the Global Interpreter Lock is a mutex internal to CPython that must be held by a thread in order for that thread to execute Python bytecode or safely manipulate Python object internals such as reference counts. It serializes execution of Python code across threads within a single process, which prevents race conditions on CPython's non-thread-safe reference-counting and object-management internals, at the cost of preventing true parallel execution of Python bytecode on multiple CPU cores within that process.
02 — Why the GIL matters differently depending on the workload

CPU-bound vs. I/O-bound multithreading under the GIL

Start here, before any code. Picture one cashier working two registers side by side. If both lines need the cashier actively ringing up items non-stop, alternating registers doesn't speed anything up — the cashier is still doing one thing at a time, just switching who benefits from that one thing moment to moment; the total number of items rung up per minute doesn't change. But if half of "checking someone out" is spent waiting for their card to process — time where the cashier is doing nothing — then the cashier absolutely can hop to the other register during that dead time and get real extra work done. The difference is entirely about whether the wait is a genuine wait (nothing useful the cashier could be doing) or continuous active work.

CPython's threads release the GIL periodically to give other threads a turn — either after running for a while, or, crucially, whenever a thread is about to block on something outside the interpreter (a network call, a disk read, time.sleep()). This single behavior explains both cases:

  • CPU-bound work (tight number-crunching loops, image processing, parsing) constantly wants the GIL back the instant it's released — threads just take turns holding the "microphone," and since only one is ever actually computing, total wall-clock time for N threads doing CPU work is roughly the same as (often slightly worse than) doing it all sequentially in one thread, due to the overhead of switching the GIL back and forth.
  • I/O-bound work (network requests, file reads, database calls) releases the GIL while waiting on the operating system to finish the actual I/O — and during that wait, another thread can pick up the GIL and make real progress. Threading genuinely helps here: the waits overlap instead of stacking up.

The core rule of thumb: threading in Python helps enormously when threads spend most of their time waiting (I/O-bound), and helps little-to-not-at-all when threads spend most of their time computing (CPU-bound) — because only one thread can compute at a time regardless of how many exist.
03 — Two different ways to get concurrency

Threading vs. multiprocessing, given the GIL

Multiprocessing sidesteps the GIL entirely rather than working around it — because the GIL belongs to a single interpreter process. Spin up multiple OS processes, and each one gets its own completely separate Python interpreter, its own memory space, and its own GIL. Nothing is shared, so nothing needs a lock to protect it from other processes — they genuinely run in parallel on separate CPU cores.

from multiprocessing import Process from threading import Thread def crunch_numbers(): return sum(i*i for i in range(10_000_000)) # Threads: share memory, but only one runs Python bytecode at a time (the GIL). # For CPU-bound crunch_numbers(), 4 threads ≈ same wall time as 1. threads = [Thread(target=crunch_numbers) for _ in range(4)] # Processes: separate memory, separate interpreter, separate GIL each. # For CPU-bound crunch_numbers(), 4 processes ≈ 1/4 the wall time (up to core count). procs = [Process(target=crunch_numbers) for _ in range(4)]

Interview-ready definition: given the GIL, threading provides concurrency (interleaved progress on multiple tasks) but not parallelism (simultaneous execution) for CPU-bound Python code, because only one thread can hold the GIL and execute bytecode at any instant. Multiprocessing achieves true parallelism for CPU-bound work by running entirely separate OS processes, each with its own independent Python interpreter and therefore its own independent GIL, at the cost of higher memory overhead and the need for explicit inter-process communication instead of shared memory.
04 — What changes if you remove the lock

--disable-gil and free-threaded builds (PEP 703)

PEP 703 introduced an official, optional build of CPython (available starting around Python 3.13) that can run without the GIL — a "free-threaded" build. At a high level: since a single global lock is what made refcounting safe across threads, removing it means CPython needs a different, more fine-grained thread-safety mechanism for its internals (more sophisticated per-object or biased reference counting schemes, essentially trading one big lock for many smaller, faster ones). The payoff is that CPU-bound multithreading could finally get real parallelism within a single process, without needing multiprocessing's memory-copying overhead.

This is a genuinely large, ongoing change to CPython's internals — not a simple flag flip — and it comes with real costs: single-threaded performance can regress somewhat (the more careful, per-object thread-safety bookkeeping isn't free even when there's only one thread running), and the C-extension ecosystem (numpy, etc.) needs updates to be safe under free-threading. As of this writing it's an opt-in experimental build, not the default interpreter most people run.

Why this connects back to everything above: free-threading doesn't change what threading vs. multiprocessing are for conceptually — I/O-bound work still overlaps waits, CPU-bound work still needs genuine parallelism to speed up. What changes is that, under a free-threaded build, threading itself could eventually deliver that CPU-bound parallelism too, closing part of the gap that used to require multiprocessing.

Problem 1 · Why the GIL exists

Explain in one or two sentences, using the refcounting lab from before, exactly what would go wrong in CPython's internals if the GIL were simply removed with nothing to replace it.

Show solution
Two threads could execute Python bytecode simultaneously and both try to increment or decrement the SAME object's refcount at the same instant. This is a classic read-modify-write race: both threads could read the same old value, compute the same new value, and one update gets silently lost — the refcount ends up wrong. A refcount that's too high leaks the object forever; one that's too low can free an object while something still references it, causing a crash or memory corruption. The GIL exists specifically to make this race structurally impossible by ensuring only one thread ever touches Python objects at a time.
Problem 2 · Predict the speedup

A function does pure CPU-bound math with no I/O and takes 4 seconds single-threaded. You run it on 4 threads simultaneously. Roughly how long does the whole thing take wall-clock, and why?

Show solution
Roughly 16 seconds total work still gets done (4 threads x 4 seconds each of CPU work), but since only one thread can hold the GIL and run bytecode at a time, the wall-clock time to finish ALL 4 is still roughly 16 seconds (possibly a bit worse due to GIL hand-off/context-switch overhead) — NOT 4 seconds. Threading gives no real speedup for CPU-bound work under the GIL; each thread's 4 seconds of work still has to happen one at a time.
Problem 3 · I/O-bound speedup

A function makes a network call that takes 2 seconds of pure waiting (no CPU work) and takes 2 seconds single-threaded. You run it on 4 threads simultaneously, each making its own independent network call. Roughly how long does the whole thing take wall-clock?

Show solution
Roughly 2 seconds total, not 8. Each thread releases the GIL the instant it starts waiting on the network (blocking I/O), so all 4 threads can be "waiting" on their own network calls at the same time — the waits overlap almost completely. Only the tiny slivers of actual Python bytecode (issuing the request, handling the response) are serialized by the GIL, and those are a small fraction of the 2 seconds compared to the wait itself.
Problem 4 · Choosing the right tool

You need to (a) resize 10,000 images (pure CPU work, no I/O) as fast as possible, and (b) fetch 500 URLs from an API as fast as possible. Which concurrency approach fits each, and why?

Show solution
(a) Image resizing: multiprocessing. It's CPU-bound, so you need genuine parallel execution across cores, which requires separate processes (each with its own GIL) — threading would give no real speedup here. (b) Fetching 500 URLs: threading (or asyncio) — this is I/O-bound. The threads spend almost all their time waiting on network responses, during which the GIL is released, so many requests can be "in flight" waiting simultaneously. Multiprocessing would work too but is needlessly heavy (500 processes would be wasteful) for what is fundamentally a waiting problem, not a computing problem.
Problem 5 · Mixed workload

A single task both makes a network call AND does meaningful CPU-bound parsing of the response. If you run many of these tasks concurrently with threading, which part benefits from the concurrency and which part doesn't?

Show solution
The network-call portion benefits — while one thread is waiting on its network response, other threads can run (their own waits, or brief bursts of parsing). The CPU-bound parsing portion does NOT get parallelized — when multiple threads are all in their parsing phase at once, they're back to taking turns holding the GIL, so that part of the total work still executes serially regardless of thread count. This is why "I/O-bound" and "CPU-bound" is really a description of where a task spends its TIME, not a strict either/or category — many real tasks are a mix, and threading only helps proportionally to the I/O-bound share.
Problem 6 · Free-threaded builds

Why can't a free-threaded (--disable-gil) build just delete the GIL and change nothing else in CPython's internals?

Show solution
Because the GIL is precisely what made the existing simple refcounting scheme thread-safe. Deleting the lock with no replacement reintroduces the exact race condition from Problem 1 — concurrent increments/decrements on the same object's refcount could corrupt it. Free-threaded builds replace the single global lock with different, more fine-grained thread-safety mechanisms for reference counting and other interpreter internals (PEP 703), which is why it's a substantial internal redesign rather than a one-line flag change, and why it can carry single-threaded performance costs and requires the C-extension ecosystem to adapt.
