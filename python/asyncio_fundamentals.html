01 — The single dispatcher

The event loop: single-threaded, cooperative multitasking

Start here, before any code. Picture one air-traffic controller managing many planes with a single radio. The controller never actually flies more than one radio conversation at once — but planes spend most of their time cruising on autopilot, not needing the radio at all. The controller's job is to notice the instant a plane needs attention, handle that one exchange quickly, then move on to whichever other plane needs something next. Nothing is happening in true parallel — there's one controller, one radio — but by never sitting idle waiting on any single plane, an enormous number of flights get managed smoothly by that one person.

The event loop is that controller. It runs on a single thread, and its entire job is to repeatedly ask "which of my registered tasks is ready to make progress right now?", run that task until it voluntarily pauses (at an await), then move to the next ready task. This is called cooperative multitasking because tasks aren't forcibly interrupted the way an OS scheduler interrupts threads — each coroutine has to voluntarily yield control back at an await point for anything else to get a turn. If it never awaits anything, it runs to completion uninterrupted, blocking the whole loop the entire time.

import asyncio async def main(): print("start") await asyncio.sleep(1) # yields control back to the loop for 1 second print("end") asyncio.run(main()) # creates the event loop, runs main() on it, closes the loop when done
Interview-ready definition: the asyncio event loop is a single-threaded scheduler that manages a set of coroutines/tasks and repeatedly selects one that is ready to run, executes it until it suspends at an await expression (typically because it is waiting on I/O or another awaitable), and then resumes a different ready task — achieving concurrency through voluntary, cooperative yielding rather than preemptive OS-level thread or process scheduling.
02 — The three building blocks

Coroutines, Tasks, and Futures

Start here, before any code. Think of a coroutine as a recipe card — written instructions for something to do, but nobody is cooking yet just because the card exists. A Task is handing that recipe to an actual cook and saying "start on this now, I'll come check on it" — it's the recipe PLUS someone actively working through it concurrently with other cooks. A Future is simply a claim ticket for a dish that isn't ready yet — "come back later and I'll have your food," with no recipe attached at all, just a promise of an eventual result.

ConceptWhat it is
CoroutineThe result of calling an async def function — a paused, not-yet-started computation. Calling it does nothing until it's awaited or scheduled.
TaskA coroutine wrapped and scheduled to run concurrently on the event loop right now, via asyncio.create_task(). This is what lets multiple coroutines actually make interleaved progress instead of running one at a time in sequence.
FutureA lower-level object representing a result that doesn't exist yet — a placeholder that will eventually be filled in (or fail with an exception). A Task is actually a subclass of Future, specifically one driven by running a coroutine.
async def fetch(name, delay): await asyncio.sleep(delay) return f"{name} done" async def main(): coro = fetch("A", 2) # just a coroutine object — nothing running yet task = asyncio.create_task(fetch("B", 2)) # scheduled NOW — starts running concurrently result_a = await coro # starts running coro only now, and waits for it result_b = await task # task was ALREADY running this whole time — likely already done

This distinction matters enormously: awaiting a bare coroutine directly runs it to completion before moving to the next line — sequential. Wrapping it in create_task() first schedules it to start running concurrently with whatever else the loop is doing, and you only pay for the actual wait when you later await the task to collect its result.

03 — The single most common asyncio bug

Why awaiting a blocking call defeats the entire point

Start here, before any code. Back to the air-traffic controller: the entire system works because the controller only ever holds the radio for brief exchanges before releasing it. Now imagine the controller gets on the radio with one plane and, instead of a quick exchange, falls asleep holding the mic key down for ten minutes. Every other plane is now completely locked out — not because they aren't ready, but because the ONE controller, the shared resource everything depends on, is unavailable to anyone. This is exactly what a blocking call inside a coroutine does to the entire event loop.

✗ Accidentally blocking

import time async def broken(): print("working...") time.sleep(3) # BLOCKS the OS thread — # never yields to the loop! print("done")
Every other coroutine is frozen for 3 full seconds — the single thread running the loop is stuck inside time.sleep(), unable to do anything else at all.

✓ Correctly cooperative

import asyncio async def fixed(): print("working...") await asyncio.sleep(3) # YIELDS control back # to the loop for 3s print("done")
Other coroutines run freely during these 3 seconds — asyncio.sleep() hands control back to the loop instead of holding the thread hostage.
WATCH ONE BLOCKING COROUTINE FREEZE EVERYTHING ELSE
The rule this teaches: inside an async def, anything that can block the thread (time.sleep, a synchronous requests.get(), heavy CPU work with no await points) freezes the ENTIRE event loop, not just that one coroutine — because there is only one thread, and it's now stuck. Always use the async-native equivalent (asyncio.sleep, an async HTTP client) or run genuinely blocking work in a separate thread/process via asyncio.to_thread() / an executor.

Problem 1 · Coroutine vs. running it
async def greet(): print("hello") g = greet() print(type(g))
Show solution
<class 'coroutine'> Calling greet() does NOT run the function body — "hello" is never printed. It creates a coroutine object, a paused computation waiting to be driven forward by await or by being scheduled as a Task. Only awaiting it (or running it via asyncio.run()) actually executes the body.
Problem 2 · Sequential await vs create_task
import asyncio async def work(name, seconds): await asyncio.sleep(seconds) return name async def main(): a = await work("A", 2) b = await work("B", 2) return a, b # roughly how long does asyncio.run(main()) take?
Show solution
Roughly 4 seconds. Each `await work(...)` runs that coroutine to completion before moving to the next line — this is sequential, not concurrent. work("A", 2) fully finishes (2s) before work("B", 2) even starts (another 2s) = 4s total. Using asyncio.create_task() for both BEFORE awaiting either would let them run concurrently, taking roughly 2s total instead.
Problem 3 · Fixing the concurrency

Rewrite the main() from Problem 2 so both calls to work() run concurrently instead of sequentially.

Show solution
async def main(): task_a = asyncio.create_task(work("A", 2)) task_b = asyncio.create_task(work("B", 2)) a = await task_a b = await task_b return a, b Both create_task() calls schedule their coroutines to start running immediately/concurrently. By the time we await task_a, task_b has already been running in the background too — both sleeps overlap, so the whole thing takes roughly 2 seconds instead of 4. (asyncio.gather(work("A", 2), work("B", 2)) achieves the same result more concisely.)
Problem 4 · Spotting the blocking bug
import time import asyncio async def fetch_data(): print("fetching...") time.sleep(2) return "data" async def heartbeat(): while True: print("heartbeat") await asyncio.sleep(0.5) async def main(): asyncio.create_task(heartbeat()) result = await fetch_data() print(result) # What goes wrong here, concretely?
Show solution
The heartbeat task never gets to print during fetch_data()'s 2-second "wait" — you'd expect ~4 heartbeat prints during that window, but you get ZERO, because time.sleep(2) blocks the entire single thread the event loop runs on. heartbeat()'s await asyncio.sleep(0.5) can only resume once the loop gets control back, and the loop can't do anything at all while stuck inside fetch_data()'s time.sleep(). The fix: replace time.sleep(2) with await asyncio.sleep(2) (if it's genuinely just a wait) or run the real blocking work via `await asyncio.to_thread(blocking_function)` so it executes on a separate thread instead of freezing the loop's thread.
Problem 5 · Task vs Future

Explain the relationship between a Task and a Future in one or two sentences — is a Task a kind of Future, or the other way around?

Show solution
A Task IS a kind of Future — asyncio.Task is a subclass of asyncio.Future. A plain Future is just a placeholder for a result that will show up later (often set manually by lower-level code, e.g. callback-based APIs). A Task is a Future that is specifically driven by running a coroutine on the event loop to completion, automatically resolving itself with that coroutine's return value (or exception) once it finishes.
Problem 6 · Predicting scheduling order
import asyncio async def task(name, delay): print(f"{name} start") await asyncio.sleep(delay) print(f"{name} end") async def main(): await asyncio.gather( task("A", 1), task("B", 0.5), ) # In what order do the four print statements appear?
Show solution
A start B start B end A end asyncio.gather schedules both coroutines to start running essentially together. Both print their "start" message immediately (no await has happened yet in either), then both call await asyncio.sleep(...) and yield control back to the loop. B's 0.5s sleep finishes first, so "B end" prints before A's 1s sleep finishes and prints "A end". This ordering — both starts immediately, then completions in delay order — is a direct consequence of cooperative scheduling: nothing preempts A or B mid-flight, they only hand off control at their own await points.
