A method call is just a function call with the object smuggled in as the first argument.

Everything about classes — self, instance vs. class attributes, dunder methods, even @dataclass — is built on that one substitution. Once obj.method(x) and Class.method(obj, x) feel like the same statement, the "magic" behind Python objects stops being magic.

01 — The blueprint and the instances

Class syntax, __init__

A class is a blueprint. __init__ is the method Python calls automatically right after a new, empty object is created — its job is to set up that specific object's starting state by attaching attributes to it.

class Dog: def __init__(self, name, age): self.name = name # attach 'name' to THIS specific object self.age = age rex = Dog("Rex", 3) # Python creates a blank object, then calls __init__(rex, "Rex", 3) mia = Dog("Mia", 5) # a completely separate object, its own name/age rex.name → 'Rex' mia.name → 'Mia'
WATCH __init__ BUILD EACH INSTANCE
02 — Why Python spells it out

self and why it's explicit in Python

In many languages, "the current object" (this) is implicit inside a method — you never see it as a parameter. Python does the opposite: every instance method takes the object as its first parameter, and you name it yourself (by convention, self).

This isn't decoration — obj.method(args) is syntax sugar for Class.method(obj, args). The dot-call automatically slots the object in as the first argument; writing self in the method definition is just naming that slot so the method body can refer to it.

TWO WAYS TO CALL THE SAME METHOD
class Dog: def bark(self, volume): return f"{self.name} says WOOF ({volume})" rex = Dog(); rex.name = "Rex" rex.bark("loud")
Both calls run the exact same method body with the exact same arguments — self=rex, volume="loud". The dot syntax is just shorthand.
Why this design: making self explicit means there's no hidden, special-cased mechanism for "the current object" — it's an ordinary parameter, following ordinary parameter rules (LEGB scoping applies to it exactly like any other name). It's more visible in exchange for zero magic.
03 — Where the value actually lives

Instance vs. class attributes

A class attribute is defined directly in the class body — it lives on the class object itself, and every instance shares the exact same one (until an instance shadows it). An instance attribute is set via self.x = ..., usually inside __init__ — it lives in that specific instance's own namespace.

class Dog: species = "Canis familiaris" # CLASS attribute — one copy, shared def __init__(self, name): self.name = name # INSTANCE attribute — separate per object rex = Dog("Rex") mia = Dog("Mia") rex.species → 'Canis familiaris' (found on the class, both instances see it) mia.species → 'Canis familiaris' (SAME string object, shared) Dog.species = "Updated" rex.species → 'Updated' (changing the CLASS attribute affects every instance that hasn't shadowed it)
SHARED vs. PER-INSTANCE, LIVE
The classic trap: a mutable class attribute (like tricks = [] in the class body) is ONE shared list — appending to it through any instance mutates the same object every instance sees, exactly like the mutable-default-argument trap. Mutable state that should be per-instance belongs in __init__ as self.tricks = [], not in the class body.
04 — Generating the boilerplate

@dataclass: what it auto-generates, field() for defaults

Plain data-holding classes usually need the same handful of methods written by hand: __init__, __repr__, __eq__. @dataclass generates them for you from type-annotated class attributes.

✗ Written by hand

class Point: def __init__(self, x, y): self.x = x self.y = y def __repr__(self): return f"Point(x={self.x}, y={self.y})" def __eq__(self, other): return (self.x, self.y) == (other.x, other.y)

✓ With @dataclass

from dataclasses import dataclass @dataclass class Point: x: int y: int # __init__, __repr__, __eq__ all generated # automatically from the annotated fields.
Point(1, 2) → Point(x=1, y=2) # __repr__ generated Point(1, 2) == Point(1, 2) → True # __eq__ generated, compares field values

For a mutable default (like a list), a plain tags: list = [] annotation is actually rejected by @dataclass at class-definition time — it refuses to let you make that mistake. Use field(default_factory=list) instead, which builds a fresh list per instance, just like the None-sentinel fix from the default-argument lesson:

from dataclasses import dataclass, field @dataclass class Dog: name: str tricks: list = field(default_factory=list) # fresh [] per instance rex = Dog("Rex") mia = Dog("Mia") rex.tricks.append("sit") mia.tricks → [] # untouched — separate list, unlike a shared mutable default

05 — Hooking into Python's built-in syntax

Common dunders: __repr__, __eq__, __len__, __iter__, __hash__

Dunder ("double underscore") methods are how a class opts into Python's built-in syntax and functions — print(), ==, len(), for, and hashing all check for a specific dunder method on the object's class before falling back to a default.

__repr__(self)
triggered by: repr(obj), the console/debugger, print() as a fallback

Should return an unambiguous string, ideally one that looks like valid code to recreate the object: Point(x=1, y=2) not "a point".

__eq__(self, other)
triggered by: ==

Without it, == falls back to identity (is) — two objects with identical data would compare unequal.

__len__(self)
triggered by: len(obj)

Must return a non-negative int. Also makes the object "truthy/falsy" by size if __bool__ isn't defined — an empty container becomes falsy.

__iter__(self)
triggered by: for x in obj, list(obj), unpacking

Should return an iterator (something with __next__). This is what makes for item in my_object: work at all.

__hash__ and its relationship with __eq__

__hash__ lets an object be used as a dict key or set member. Python enforces a rule: if two objects are equal (==), they must have the same hash — otherwise dicts and sets silently misbehave (two "equal" objects could end up in different buckets and never be recognized as duplicates).

class Point: def __init__(self, x, y): self.x, self.y = x, y def __eq__(self, other): return (self.x, self.y) == (other.x, other.y) def __hash__(self): return hash((self.x, self.y)) # must agree with __eq__'s notion of equality
A gotcha worth knowing: defining __eq__ without also defining __hash__ makes Python set the class's __hash__ to None automatically — the object becomes unhashable, and {obj} or {obj: val} raises a TypeError. @dataclass does this by default too (regular dataclasses are unhashable) unless you pass @dataclass(frozen=True), which generates a matching __hash__ for you.

Problem 1 · __init__ basics
class Counter: def __init__(self): self.count = 0 def increment(self): self.count += 1 a = Counter() b = Counter() a.increment() a.increment() b.increment() print(a.count, b.count)

Problem 2 · self desugaring

Given class Dog: def bark(self, vol): return f"{self.name}: {vol}" and an instance rex with rex.name = "Rex", write the equivalent call to rex.bark("loud") using the class directly instead of the dot syntax.

Show solution
Dog.bark(rex, "loud") rex.bark("loud") is syntax sugar for Dog.bark(rex, "loud") — the dot call automatically supplies rex as the first argument (self); calling through the class requires passing it explicitly.
Problem 3 · The mutable class attribute trap
class Dog: tricks = [] # class attribute — NOT inside __init__ def __init__(self, name): self.name = name def learn(self, trick): self.tricks.append(trick) rex = Dog("Rex") mia = Dog("Mia") rex.learn("sit") print(mia.tricks)
Show solution
['sit'] tricks is a CLASS attribute — one shared list. self.tricks.append(...) doesn't create an instance attribute (append mutates in place, it doesn't assign), so both rex and mia are reading/writing the exact same list object. mia sees "sit" even though only rex.learn() was called — same bug family as the mutable default argument trap.
Problem 4 · @dataclass equality
from dataclasses import dataclass @dataclass class Point: x: int y: int p1 = Point(1, 2) p2 = Point(1, 2) print(p1 == p2) print(p1 is p2)
Show solution
True False @dataclass generates __eq__ that compares FIELD VALUES, so p1 == p2 is True even though they're two separate objects in memory (p1 is p2 is False — identity check, same as the mutability lab's `is` vs `==` distinction). Without @dataclass (or a hand-written __eq__), a plain class would fall back to identity comparison and p1 == p2 would be False.
Problem 5 · field(default_factory=...)
from dataclasses import dataclass, field @dataclass class Team: name: str members: list = field(default_factory=list) a = Team("Alpha") b = Team("Beta") a.members.append("Sam") print(a.members, b.members)
Show solution
['Sam'] [] default_factory=list calls list() FRESH for every new Team instance, so a.members and b.members are two independent list objects from the start. This is the dataclass-safe equivalent of the None-sentinel fix for mutable default arguments — @dataclass would actually raise an error if you tried `members: list = []` directly, specifically to prevent this trap.
Problem 6 · __len__ and truthiness
class Basket: def __init__(self, items): self.items = items def __len__(self): return len(self.items) b = Basket([]) if b: print("has items") else: print("empty") print(len(b))
Show solution
empty 0 Without a __bool__ method, Python falls back to __len__ to decide truthiness: an object is falsy if len(obj) == 0. b.items is [], so len(b) is 0, so `if b:` takes the else branch.
Problem 7 · __eq__ without __hash__
class Point: def __init__(self, x, y): self.x, self.y = x, y def __eq__(self, other): return (self.x, self.y) == (other.x, other.y) p = Point(1, 2) s = {p}
Show solution
TypeError: unhashable type: 'Point' Defining __eq__ without also defining __hash__ makes Python set __hash__ to None automatically on that class (Python won't let a hash exist that might disagree with equality). Trying to put p into a set requires hashing it, which fails. Fix: add a __hash__ method that agrees with __eq__, e.g. `def __hash__(self): return hash((self.x, self.y))`.
