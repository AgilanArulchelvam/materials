01 — "has-a" vs "is-a"

Composition vs. inheritance

Start here, before any code. Think about how you'd describe a person. You might say "a manager is an employee" — a manager is fundamentally a kind of employee, just with extra responsibilities. But you'd never say "a manager is a laptop" — a manager just has a laptop, uses it, and could swap it for a different one tomorrow without stopping being a manager. Those are two completely different kinds of relationship, and object-oriented code has a name and a tool for each one.

The test is simple: does the relationship describe what the object fundamentally is, or what the object merely has, and uses?

  • "is-a" → inheritance. A Duck is an Animal. In Python, class Duck(Animal): — the parentheses after the class name mean "Duck inherits from Animal."
  • "has-a" → composition. A Car has an Engine. In Python, Car simply stores an Engine object as one of its own attributes, the same way you'd store any other value.

Mixing these two up — reaching for inheritance when you really just mean "has a" — is one of the most common design mistakes in object-oriented code, and a question interviewers like to probe specifically because it reveals whether you're modeling relationships deliberately or just copying a pattern you've seen before.

is-a — Inheritance

class Animal: def speak(self): return "..." class Duck(Animal): def speak(self): return "quack" # Duck IS an Animal — usable # anywhere an Animal is expected.
  • Shares code through a class hierarchy
  • Tight coupling to the parent's internals
  • Fixed at class-definition time

has-a — Composition

class Engine: def start(self): return "vroom" class Car: def __init__(self): self.engine = Engine() def start(self): return self.engine.start()
  • Assembles behavior from independent parts
  • Loose coupling — swap parts via their interface
  • Can change which part is held at runtime
SWAP THE ENGINE AT RUNTIME — INHERITANCE CAN'T DO THIS
car = Car(300) car.start()→ 'Engine roars to life (300 hp)'
Car doesn't inherit from Engine — it just holds one. Click the button to swap the part it delegates to.
Why this matters: imagine adding an ElectricCar. If Car inherited from GasEngine, you'd either duplicate the whole class or contort the hierarchy. With composition, ElectricCar just holds a different engine object that implements the same start() — no hierarchy redesign. This is the practical meaning of "favor composition over inheritance": reach for inheritance only for genuine taxonomies where you need to share a big, stable interface; reach for composition whenever you're assembling capabilities.
Interview-ready definition: inheritance models an is-a relationship — a subclass automatically gains its parent's interface and implementation, and can be used anywhere the parent is expected (this substitutability is formalized as the Liskov Substitution Principle). It creates tight coupling: subclasses depend on their parent's internal implementation details, and that dependency is fixed at class-definition time. Composition models a has-a relationship — an object holds a reference to another object and delegates work to it through that object's public interface. This is loose coupling: the held object can be swapped for any other object satisfying the same interface, including at runtime. The standard industry guidance, "favor composition over inheritance," means: default to composition for flexibility, and reserve inheritance for genuine, stable taxonomies.
02 — How Python resolves the diamond

Multiple inheritance and MRO

Start here, before any code. Suppose you inherited character traits from both of your parents, and both of them happen to be excellent cooks — but they cook completely differently. If someone asks "how do you cook pasta?", whose method do you use? You need some consistent rule for which side of the family "wins" when there's a conflict, or the question has no sensible answer.

Python has exactly this problem when a class inherits from more than one parent class at once — this is called multiple inheritance. If two parent classes both define a method with the same name, Python needs a fixed, predictable rule for which one gets used. That rule is called the Method Resolution Order, or MRO for short: it's simply the exact order Python checks classes in, from most specific to least specific, when looking for a method.

The rule Python actually uses to build that order is an algorithm called C3 linearization — you will almost never need to compute it by hand, but knowing the name matters for interviews, since it's the standard term for "how Python decides the search order." The everyday intuition behind it is simple, though: a class is always checked before its parents, and if a class has multiple parents, they're checked left-to-right in the exact order they were written in the class definition.

class Animal: def speak(self): return "..." class Swimmer(Animal): def speak(self): return "blub" class Flyer(Animal): def speak(self): return "screech" class Duck(Swimmer, Flyer): # note the order: Swimmer listed first pass Duck().speak() → 'blub' — Swimmer wins, not Flyer or Animal

Interview-ready definition: the MRO is the linear order Python searches through a class's ancestors when resolving an attribute or method lookup — accessible directly as ClassName.__mro__ or ClassName.mro(). It is computed once, when the class is defined, using the C3 linearization algorithm, which guarantees two properties: a subclass always precedes its parents in the order (local precedence), and the relative order of parents as listed in the class definition is preserved (monotonicity). If no ordering can satisfy both properties simultaneously — a genuine contradiction in the hierarchy — Python raises TypeError at class-definition time rather than silently picking one.

super() follows the MRO, not "the parent"

Here's the part almost everyone gets wrong the first time: it's tempting to assume super().__init__() means "go call my parent's __init__." That's true in simple, single-parent inheritance — but with multiple inheritance, it's not quite right. super() doesn't mean "my parent." It means "whoever comes next in the MRO" — and in a multi-parent hierarchy, that "next" class can actually be a sibling class, not an ancestor at all.

This matters because it's exactly what makes multi-parent hierarchies work correctly: if every class in the chain calls super() instead of naming a specific parent, Python can walk through the entire MRO and make sure each class's code runs exactly once, in the right order — even in a "diamond" shape where two different paths both eventually lead back to the same shared ancestor.

class Swimmer(Animal): def speak(self): return "blub + " + super().speak() class Flyer(Animal): def speak(self): return "screech + " + super().speak() class Duck(Swimmer, Flyer): def speak(self): return "quack + " + super().speak() Duck().speak() → 'quack + blub + screech + ...' Duck.speak calls super() → Swimmer.speak (NOT Animal — the next MRO slot) Swimmer.speak calls super() → Flyer.speak Flyer.speak calls super() → Animal.speak
Core foundation: super() means "the next stop on this instance's MRO," not "my parent." That's the only way a diamond hierarchy guarantees Animal.__init__ runs exactly once even though two subclasses both lead to it. Design mixins so every one calls super().__init__(**kwargs), and let the MRO handle the chaining.
03 — Attributes that run code

@property and @x.setter

Start here, before any code. Imagine a thermostat display. You just look at the number on the screen and set a new target temperature by turning a dial — you never open the thermostat up and directly rewire its internal sensor. Behind that simple dial, though, the thermostat is quietly checking your requested temperature is actually reasonable (not -900 degrees) before it accepts it. From the outside, it looks like you're just "setting a number." Underneath, real logic is running.

A Python property lets a class attribute work exactly like that thermostat dial. You write obj.value and obj.value = 25 — completely ordinary-looking attribute syntax — but underneath, a method is quietly running every time, checking or computing things before anything actually happens. This is Python's approach to encapsulation: instead of forcing every class to expose ugly get_value() / set_value() methods everywhere (as some other languages do), you write plain attribute access, and the class itself decides — invisibly — whether that access should validate the value, compute it fresh, or log it.

class Temperature: def __init__(self, celsius): self._celsius = celsius # real storage, "private" by convention @property def celsius(self): return self._celsius @celsius.setter def celsius(self, value): if value < -273.15: raise ValueError("Below absolute zero") self._celsius = value

Why this matters: you can ship a class with a plain public attribute (self.celsius = 25) and later convert it into a property without breaking any caller — obj.celsius and obj.celsius = x still work syntactically the same. Python doesn't need getFoo()/setFoo() conventions the way Java does: add validation only when you actually need it, with zero API changes for callers.
Interview-ready definition: @property is a built-in descriptor — an object implementing __get__, and optionally __set__/__delete__ — that Python's attribute-lookup machinery checks before falling back to an instance's own __dict__. Decorating a method with @property turns attribute reads (obj.x) into calls to that method. @x.setter registers a second method to handle attribute writes (obj.x = value) on the same property name. If no setter is defined, the property is read-only and assignment raises AttributeError. This is the standard mechanism behind Python encapsulation: it achieves the same goal as explicit getters/setters without changing the calling syntax.

Computed and read-only properties

A property with no setter is read-only from outside the class — assigning to it raises AttributeError. This is the idiomatic way to expose a derived value without letting callers overwrite it directly.

@property def fahrenheit(self): return self._celsius * 9/5 + 32 # no @fahrenheit.setter defined here → t.fahrenheit = 100 raises AttributeError @property def area(self): return self.width * self.height # computed fresh every access — no separate storage to keep in sync
04 — Making a promise enforceable

Abstract base classes: abc.ABC, @abstractmethod

Start here, before any code. Think of a job application form that says "all fields marked required must be filled in." If that's just a note at the top written in plain English, nothing stops someone from submitting the form with a required field left blank — the mistake only gets caught later, by whoever processes the form, possibly much too late. Now imagine the form is a website that simply refuses to submit until every required field has something in it. Same rule, but now it's actually enforced, automatically, the moment it matters.

An abstract base class is Python's version of that enforced form. It lets you define a set of methods that say "every subclass of me is required to provide this," and — unlike a comment or a docstring saying the same thing — Python actually checks the promise and refuses to let you create a broken object at all.

from abc import ABC, abstractmethod class Shape(ABC): @abstractmethod def area(self): ... @abstractmethod def perimeter(self): ... def describe(self): # concrete methods CAN live on an ABC — they can call the abstract ones return f"area={self.area():.2f}, perimeter={self.perimeter():.2f}" class Circle(Shape): def __init__(self, radius): self.radius = radius def area(self): return 3.14159 * self.radius ** 2 def perimeter(self): return 2 * 3.14159 * self.radius
TRY INSTANTIATING EACH CLASS
Why this matters: without ABC, "every Shape must implement area()" is just a comment — nothing stops a subclass from forgetting it, and the bug surfaces at the worst time, deep inside a call to .area() on a shape you didn't write. With abc.ABC, the bug surfaces the moment the broken subclass is instantiated, naming exactly which methods are missing. This is fail-fast applied to interface design: the promise is enforced by the language, not by discipline.
Interview-ready definition: abc.ABC is a base class (built on the metaclass ABCMeta) that enables abstract method enforcement. Marking a method with @abstractmethod registers it as required; Python then refuses to instantiate any class — the ABC itself, or any subclass — that hasn't overridden every abstract method, raising TypeError at the moment of instantiation and naming the specific missing methods. Concrete (non-abstract) methods are allowed on an ABC and may freely call the abstract ones, since by the time any instance exists, those abstract methods are guaranteed to be implemented. This pattern — defining a contract once, enforced everywhere — is what allows client code (like a function that calls .area() on "any Shape") to safely stay agnostic about which concrete subclass it's actually holding, a technique known as polymorphism.

Composition + ABC + property, together

Real code usually combines all three tools. Order never needs to know which payment method it holds — only that it satisfies the interface. The ABC guarantees the shape of the contract; composition lets the concrete implementation vary freely; the property validates state before it's used.

class PaymentMethod(ABC): @abstractmethod def charge(self, amount): ... class PayPal(PaymentMethod): def charge(self, amount): return f"Charged ${amount:.2f} via PayPal" class Order: def __init__(self, method: PaymentMethod): self._method = method # composition: Order HAS-A PaymentMethod self._total = 0.0 @property def total(self): return self._total @total.setter def total(self, value): if value < 0: raise ValueError("Total can't be negative") self._total = value def checkout(self): return self._method.charge(self.total) # delegate to the swappable part order = Order(PayPal()); order.total = 49.99 order.checkout() → 'Charged $49.99 via PayPal'

Problem 1 · Composition refactor

You're given class FlyingCar(Car, Airplane). It's grown unmanageable — Car and Airplane both define fuel_level and conflict. Rewrite it using composition: FlyingCar should hold a drive_mode and a fly_mode object, each with its own move(), and pick which to delegate to based on a mode attribute.

Show solution
class DriveMode: def move(self): return "driving" class FlyMode: def move(self): return "flying" class FlyingCar: def __init__(self): self.drive_mode = DriveMode() self.fly_mode = FlyMode() self.mode = "drive" def move(self): if self.mode == "drive": return self.drive_mode.move() return self.fly_mode.move() No inheritance from Car/Airplane at all — FlyingCar HAS a DriveMode and a FlyMode, and simply forwards to whichever is active. Adding a third mode means adding a third held object, not restructuring a hierarchy.
Problem 2 · Trace an MRO by hand
class A: pass class B(A): pass class C(A): pass class D(B, C): pass print(D.__mro__)

Then explain in one sentence why class D(C, B): pass would produce a different order.

Show solution
(D, B, C, A, object) C3 linearization keeps each parent's own MRO intact and merges left-to-right by the order bases were listed, so D, B, C, A, object. Swapping the base list to D(C, B) swaps B and C in the result: D, C, B, A, object — the search order always mirrors the order the parent classes were listed in.
Problem 3 · A validated property

Write a BankAccount class with a balance property. The setter should reject negative values with ValueError. Add a read-only is_overdrawn property (no setter) computed from the stored balance.

Show solution
class BankAccount: def __init__(self, balance=0): self.balance = balance # goes through the setter immediately @property def balance(self): return self._balance @balance.setter def balance(self, value): if value < 0: raise ValueError("Balance can't be negative") self._balance = value @property def is_overdrawn(self): return self._balance < 0 Because the setter always rejects negatives, is_overdrawn will always read False here — which is itself the point: it demonstrates that a read-only property can safely expose a derived fact without ever risking a caller setting it directly.
Problem 4 · Design an abstract interface

Define an abstract Notifier(ABC) with an abstract send(message). Implement EmailNotifier and SMSNotifier. Write notify_all(notifiers, message) that calls .send() on each without caring which concrete class any of them are. What happens if you try Notifier() directly?

Show solution
from abc import ABC, abstractmethod class Notifier(ABC): @abstractmethod def send(self, message): ... class EmailNotifier(Notifier): def send(self, message): return f"Email: {message}" class SMSNotifier(Notifier): def send(self, message): return f"SMS: {message}" def notify_all(notifiers, message): for n in notifiers: print(n.send(message)) Notifier() # TypeError: Can't instantiate abstract class Notifier with abstract method send notify_all loops and calls .send() polymorphically — it never checks which concrete class it has. That safety is guaranteed by the ABC contract, not by convention.
Problem 5 · Combine everything

Build a small ConnectionPool: an abstract Connection(ABC) with execute(query), two concrete implementations, a Pool that composes a list of connections and exposes a validated max_size property. What ABC guarantee lets Pool stay agnostic about which concrete connection type it holds?

Show solution
from abc import ABC, abstractmethod class Connection(ABC): @abstractmethod def execute(self, query): ... class PostgresConnection(Connection): def execute(self, query): return f"[postgres] {query}" class SQLiteConnection(Connection): def execute(self, query): return f"[sqlite] {query}" class Pool: def __init__(self, max_size): self.connections = [] # composition: Pool HAS-A list of Connection self.max_size = max_size # goes through the validated setter @property def max_size(self): return self._max_size @max_size.setter def max_size(self, value): if value <= 0: raise ValueError("max_size must be positive") self._max_size = value def add(self, conn: Connection): if len(self.connections) >= self.max_size: raise RuntimeError("Pool is full") self.connections.append(conn) Because every Connection subclass is guaranteed (by ABC) to implement execute(), Pool.add() and any code that later calls conn.execute() never needs an isinstance check or a branch per database type — the abstract contract is what makes the composition safe to leave generic.
