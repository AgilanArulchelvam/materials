01 — Annotating what's already true

Basic type hints: variables, signatures, return types

Start here, before any code. A type hint is like a label on a storage bin — it doesn't stop you from throwing in the wrong item, but it tells everyone (including future-you) what's supposed to go there, and a separate inspector can walk around checking every bin against its label without you having to remember the rule yourself.

A hint after a variable or parameter name (x: int) states the intended type; an arrow before the function body (-> str) states the intended return type. None of this is enforced when the code actually runs — Python's runtime behavior is completely unaffected by hints. They exist purely for static analysis tools, IDEs, and human readers.

def greet(name: str, times: int = 1) -> str: return (f"Hi, {name}! " * times).strip() age: int = 30 name: str = "Ada" # Python happily runs this even though it violates the hint: greet(123, "two") → crashes at runtime (str * str is invalid) — NOT because of the hint, the hint was never checked; it crashed for its own normal reasons
WHO ACTUALLY ENFORCES THE HINT?
Click to see what actually happens when hints are "violated" at runtime.
Interview-ready definition: a type hint (PEP 484) is a static annotation — stored in __annotations__, readable via introspection — that declares the intended type of a variable, parameter, or return value. It is not enforced by the Python interpreter at runtime; enforcement is the job of an external static type checker such as mypy, pyright, or an IDE's inline analysis.
02 — Containers that remember what's inside

Generics: list[int], dict[str, int], TypeVar

Start here, before any code. A plain box just says "box." A labeled box says "box of screws" — now you know what to expect without opening it, and if someone tries to drop in a nail, the label makes that visibly wrong even before you look inside. Generics are labeled containers: list[int] isn't just "a list," it's "a list, specifically of integers."

list[int], dict[str, int], and similar bracket syntax (built into the language since Python 3.9, no import needed) tell a type checker what's inside a container, not just its outer shape. TypeVar goes one step further — it lets a function's input and output types stay linked without committing to one specific type up front.

scores: dict[str, int] = {"Ada": 95, "Grace": 98} names: list[str] = ["Ada", "Grace"] from typing import TypeVar T = TypeVar("T") def first(items: list[T]) -> T: # whatever T is going IN is what comes OUT return items[0] first([1, 2, 3]) # T = int here → mypy infers return type int first(["a", "b"]) # T = str here → mypy infers return type str

Interview-ready definition: a generic type parameterizes a container or function over another type, letting a checker verify contents (list[int] vs. list[str]) rather than just outer shape. TypeVar declares a placeholder type that mypy solves per call-site, preserving the relationship between a function's input type and its output type without hardcoding either — this is what lets one generic function be correctly type-checked across many different concrete types.
03 — "If it walks like a duck..." made type-safe

Protocol: structural typing

Start here, before any code. Two job applicants might have completely different resumes — different schools, different past titles — but if both can genuinely do the job being interviewed for, a good hiring manager cares about what they can DO, not what family of resume template they used. Protocol lets you require "can do this," not "is officially descended from this class."

Normal type hints check nominal typing — isinstance(x, Duck) cares about the declared class hierarchy. Protocol (from typing) instead checks structural typing — "does this object have the right methods/attributes with the right signatures?" — regardless of what class it claims to inherit from. This matches Python's long-standing duck-typing culture, but makes it statically checkable.

from typing import Protocol class Quacks(Protocol): def quack(self) -> str: ... class Duck: # doesn't inherit from Quacks at all def quack(self) -> str: return "Quack!" class RubberDuckToy: # also doesn't inherit from Quacks def quack(self) -> str: return "Squeak (pretending)" def make_it_quack(thing: Quacks) -> None: print(thing.quack()) make_it_quack(Duck()) ✓ mypy OK — has a matching quack() method make_it_quack(RubberDuckToy()) ✓ mypy OK — ALSO has a matching quack() method, no inheritance needed
NOMINAL vs. STRUCTURAL — WHICH TYPES ARE ACCEPTED?

Nominal (isinstance / inheritance)

def make_it_quack(thing: Duck):
  ...

Only accepts objects that ARE-A Duck (inherit from it). RubberDuckToy would be REJECTED, even with an identical quack() method, because it doesn't inherit from Duck.

Structural (Protocol)

def make_it_quack(thing: Quacks):
  ...

Accepts ANY object with a matching quack() method — Duck, RubberDuckToy, or anything else you write later. No shared base class required.
Interview-ready definition: typing.Protocol defines a structural type — a set of method/attribute signatures an object must satisfy to be considered compatible, checked by shape rather than declared ancestry. It formalizes duck typing for static analysis: a class needs no explicit inheritance relationship to the Protocol to satisfy it, only matching members. This is Python's version of what Go calls interfaces and TypeScript calls structural interfaces.
04 — Reading the checker's output

Running mypy and reading its errors

Start here, before any code. A spell-checker doesn't stop you from typing nonsense — it runs after the fact and underlines what it thinks is wrong, with a specific line number and reason, and you decide whether to fix it. Running mypy is exactly that pass over your code, except for types instead of spelling.

mypy filename.py reads every type hint in the file (and any it can infer), cross-checks every assignment, call, and return against those hints, and prints one line per mismatch: file, line number, the mismatch, and an error code in brackets you can search for.

def add(a: int, b: int) -> int: return a + b result = add(5, "3") # passing a str where int is expected

Common trap: mypy only checks what it can see. A function with no annotations at all is checked loosely by default (depending on config strictness), so an unannotated helper function can hide real bugs from mypy entirely. --strict mode (or disallow_untyped_defs) forces every function to be annotated, which is what most production codebases eventually turn on.
05 — Naming "might not be there"

Optional / Union and None handling

Start here, before any code. A locker that's sometimes empty needs a sign that says "may be empty" — not just "contains a backpack" — so nobody reaches in expecting something and gets surprised. Optional[str] is that sign: it tells both mypy and the next reader "this might be None, check before you use it."

Optional[X] is shorthand for Union[X, None] — "either an X, or None." Union[A, B] more generally means "either an A or a B." Modern Python (3.10+) allows the shorter X | None and A | B syntax instead of importing from typing. Critically, mypy will not let you call a method on an Optional value without first narrowing it — proving to the checker that the None case has been ruled out.

def find_user(user_id: int) -> str | None: return DB.get(user_id) # might legitimately not be found user = find_user(42) print(user.upper()) ✗ mypy error: Item "None" of "str | None" has no attribute "upper" if user is not None: # narrowing: mypy now KNOWS user is str inside this block print(user.upper()) ✓ mypy OK — None case has been eliminated
NARROW THE TYPE BEFORE USING IT
user: str | None
if user is not None:
user: str (narrowed)
Interview-ready definition: Optional[X] (equivalently X | None) is Union[X, None] — a type that may hold either a value of type X or the sentinel None. Static checkers require narrowing (an explicit is None/is not None check, an assert, or equivalent control flow) before permitting operations valid only on X, preventing an entire class of AttributeError: 'NoneType' object has no attribute ... bugs before the code ever runs.

Practice problems

Work each one out before expanding the solution.

Problem 1 · Hints don't stop execution
def double(n: int) -> int: return n * 2 print(double("ab"))
Show solution
abab Python's runtime never checks the hint "n: int" — it just runs `n * 2`, and str * int is valid Python (string repetition), so it executes fine and prints "abab". mypy WOULD flag this call as a type error (passing str where int is expected), but nothing about running the plain interpreter enforces that — only a separate static-analysis pass would catch it.
Problem 2 · Generic container mismatch
def total(numbers: list[int]) -> int: return sum(numbers) total([1, 2, "3"])
Show solution
mypy reports an error at the call site: List item 2 has incompatible type "str"; expected "int" — because list[int] means EVERY element should be int, and "3" (a string) breaks that. At runtime, this actually crashes too: sum() would raise TypeError: unsupported operand type(s) for +: 'int' and 'str' So here mypy would have caught a real bug before ever running the code — this is the case type hints are specifically good for.
Problem 3 · TypeVar identity
from typing import TypeVar T = TypeVar("T") def last(items: list[T]) -> T: return items[-1] x = last([1, 2, 3]) y = last(["a", "b"])
Show solution
mypy infers x: int and y: str. TypeVar binds T independently for each call: in `last([1,2,3])`, the argument is list[int], so T=int for that call, making the return type int. In `last(["a","b"])`, T=str for that call. Without TypeVar, the signature would have to be `def last(items: list) -> object` (or Any), losing the precise return type — the caller would then have to manually re-cast the result to use it as a str or int.
Problem 4 · Protocol satisfaction without inheritance
from typing import Protocol class Sized(Protocol): def __len__(self) -> int: ... def describe(thing: Sized) -> str: return f"has {len(thing)} items" describe([1, 2, 3]) describe("hello") describe({"a": 1})
Show solution
All three calls type-check successfully under mypy, and all three print correctly at runtime: "has 3 items", "has 5 items", "has 1 items". list, str, and dict none of them inherit from a class called "Sized" you wrote — they satisfy the Protocol purely structurally, because each implements __len__(self) -> int. This is exactly why built-in types can satisfy Protocols you define yourself: Protocol checks shape, not declared ancestry.
Problem 5 · Optional narrowing
from typing import Optional def get_nickname(name: str) -> Optional[str]: nicknames = {"Robert": "Bob", "William": "Bill"} return nicknames.get(name) def shout(name: str) -> str: nick = get_nickname(name) return nick.upper()
Show solution
mypy error on `return nick.upper()`: Item "None" of "Optional[str]" has no attribute "upper" get_nickname returns Optional[str] — dict.get() returns None when the key isn't found (e.g. get_nickname("Ada") has no entry). Calling .upper() directly on nick, without first checking `if nick is not None:` (or providing a default via nicknames.get(name, name)), is exactly the bug Optional exists to catch: at runtime, shout("Ada") would raise AttributeError: 'NoneType' object has no attribute 'upper' — mypy catches it before that ever happens.
