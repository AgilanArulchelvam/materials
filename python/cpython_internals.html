PYTHON INTERNALS LAB · CPYTHON MEMORY MODEL

Every Python object carries its own body count of who's pointing at it.

CPython decides when to free an object almost entirely by counting references to it. That single idea — reference counting — explains why deleting a variable doesn't always free memory, why two objects can leak forever by only pointing at each other, and why CPython bothers running a second, smarter garbage collector on top.

01 — CPython's default memory strategy

Reference counting and object lifetime

Start here, before any code. Imagine a library book with a little card in the back listing everyone currently checked out on it — not one person, but a shared count of how many people currently have it borrowed simultaneously (imagine unlimited photocopied cards floating around, each one a "hold" on the same physical book). Every time someone else creates a hold on the book, the librarian bumps the number on the card up by one. Every time someone returns their hold, it goes down by one. The instant that number hits zero — nobody, anywhere, still holds the book — the librarian pulps it and reuses the paper. Nobody has to remember to check; the count itself is the signal.

That is exactly what CPython does with every object in memory. Every object has a hidden integer field — its reference count — tracking how many places currently refer to it: variables, list elements, dict values, other objects' attributes, function argument bindings, all of it. Assigning a name creates a reference and bumps the count. Deleting a name, reassigning it, letting a function's local variables go out of scope, or removing something from a container all drop a reference and decrement the count. The moment an object's refcount reaches zero, CPython frees it immediately — not on some later pass, not eventually, right then, deterministically.

import sys x = [1, 2, 3] sys.getrefcount(x) → 2 (one for the name "x", one for the temporary argument reference getrefcount() itself creates while it's running) y = x # y now ALSO refers to the same list object sys.getrefcount(x) → 3 (x, y, and the temporary call argument) del y # drop y's reference sys.getrefcount(x) → 2 (back down — y is gone) del x # refcount drops to 0 (ignoring the temporary call ref) → list freed immediately

sys.getrefcount(obj) is the direct, observable window into this mechanism — it's always at least 1 higher than you'd naively expect, because passing obj into getrefcount() itself creates one more temporary reference for the duration of the call.

Interview-ready definition: reference counting is a memory-management scheme in which every object stores a count of the references currently pointing to it; the count is incremented on each new binding and decremented on each removal, and the object is deallocated deterministically the instant the count reaches zero. CPython's implementation is Py_INCREF/Py_DECREF on the object's ob_refcnt field, called automatically by the interpreter around essentially every operation that creates or destroys a reference.
02 — The hole in pure refcounting

Reference cycles: the case refcounting alone can never solve

Start here, before any code. Picture two people, each holding the other's IOU. Person A owes person B, and person B owes person A — the exact same amount, cancelling out. Nobody outside this pair owes either of them anything, and neither owes anything to anyone outside the pair. In any sane accounting, this debt should just be torn up: it nets to nothing. But if your only rule is "a debt gets forgiven when the last outstanding IOU against you is cleared," these two IOUs will point at each other forever — each one keeps the other "not yet forgiven," even though, from the outside, the whole arrangement is completely irrelevant and could vanish with zero consequence.

That's a reference cycle. Two (or more) objects hold references to each other, and nothing outside the group holds a reference to any of them. Refcounting only asks "does my count equal zero" for each object in isolation — and in a cycle, it never does, because each object is still being kept "alive" by the other member of the cycle, even though the whole group together is garbage.

class Node: def __init__(self, name): self.name = name self.partner = None a = Node("A") # a.refcount = 1 (the name "a") b = Node("B") # b.refcount = 1 (the name "b") a.partner = b # b.refcount = 2 (name "b" AND a.partner) b.partner = a # a.refcount = 2 (name "a" AND b.partner) del a # a.refcount drops to 1 — NOT zero, b.partner still points to it del b # b.refcount drops to 1 — NOT zero, a.partner still points to it # both names are gone. Nothing in the entire rest of the program can reach # either object anymore. But each object's refcount is 1, not 0 — each is # kept alive purely by the other half of the cycle. Pure refcounting will # NEVER free these two objects; they leak for the life of the process.

Why this genuinely can't be fixed by "better" refcounting: the problem isn't a bug in the algorithm — it's structural. Refcounting only ever asks a purely local question ("is my own count zero?"), and a cycle is a case where the true answer requires a global question ("is this whole connected group of objects reachable from anything outside itself?"). No amount of per-object bookkeeping can answer a question about the whole graph's shape — you need something that can walk the graph and look for cycles unreachable from the outside. That something is a separate garbage collector.
03 — The cycle-detector on top of refcounting

The generational garbage collector, conceptually

Start here, before any code. Think about how a busy inbox actually behaves: the overwhelming majority of emails that will ever be deleted get deleted within the first day or two of arriving — a promo, a one-time code, a "your order shipped" notice. Emails that survive a full month tend to keep surviving for a very long time after that — they're the ones you actually kept on purpose. If you had to re-scan your entire inbox history every single day looking for things to clean up, you'd waste enormous effort re-checking old mail you already decided to keep, over and over. It's far more efficient to check the newest stuff constantly (that's where the deletions are happening) and only occasionally sweep through the old, already-vetted stuff.

CPython's cycle-detecting garbage collector is built on exactly that observed pattern, sometimes called the "generational hypothesis": most objects die young. Short-lived temporaries, loop variables, intermediate results — the vast majority of objects are created and become garbage within a very short time. Objects that survive one collection pass are statistically far more likely to keep living a long time (a module-level constant, a long-lived cache, a class definition). So instead of scanning every live object on every pass, CPython groups objects into three generations — 0 (newest), 1, and 2 (oldest) — and scans generation 0 far more often than generation 1, and generation 1 far more often than generation 2. Any object that survives a collection of its current generation gets "promoted" up to the next one.

This generational GC's actual job is narrow and specific: it only exists to find and break reference cycles among container-like objects (things that can hold other objects — lists, dicts, class instances, etc.). It periodically walks these objects looking for groups that reference each other but are unreachable from anywhere outside the group — exactly the Node-A/Node-B situation above — and frees the whole unreachable group at once. Everything else, the vast majority of memory management, is still handled the instant it happens by plain reference counting; the generational GC is a periodic safety net specifically for cycles, not the primary mechanism.

import gc gc.get_threshold() → (700, 10, 10) # gen 0 collected after ~700 new allocations since the last gen-0 sweep # gen 1 collected after 10 gen-0 sweeps have happened # gen 2 collected after 10 gen-1 sweeps have happened gc.collect() # force a full collection right now — this is what finally frees a-b's cycle

Interview-ready definition: the generational garbage collector is a cycle-detecting collector that operates on top of (not instead of) reference counting. It partitions tracked container objects into three generations based on survival count, and collects younger generations more frequently than older ones under the generational hypothesis that most objects become garbage shortly after creation. It exists specifically to reclaim reference cycles, which are unreachable-but-nonzero-refcount object graphs that pure reference counting can never free on its own.

Problem 1 · Basic refcount tracing
import sys a = {"x": 1} b = a c = [a] print(sys.getrefcount(a)) del b print(sys.getrefcount(a))
Show solution
4 3 After a, b=a, c=[a]: references are the name "a", the name "b", the list element inside c, plus the temporary argument reference getrefcount() itself creates — that's 4. After `del b`, one binding is removed, dropping it to 3 (a, c's element, and the temporary call reference).
Problem 2 · Spotting a cycle
class Parent: def __init__(self): self.child = None class Child: def __init__(self, parent): self.parent = parent parent.child = self p = Parent() c = Child(p) del p del c
Show solution
This is a reference cycle. Child holds self.parent pointing at the Parent object, and Parent.__init__ was never called with a chance to set self.child — but Child's __init__ sets parent.child = self, so the Parent object ends up pointing back at the Child. After `del p` and `del c`, neither object's refcount reaches zero (each is still referenced by the other), even though nothing outside the pair can reach either one anymore. This exact "parent points at child, child points back at parent" shape is one of the most common real-world reference cycles — e.g. in tree/GUI widget hierarchies with back-pointers to a parent node.
Problem 3 · Why isn't this a cycle
class Node: def __init__(self, value): self.value = value self.next = None a = Node(1) b = Node(2) a.next = b del a
Show solution
Not a cycle — this is a normal, refcounting-solvable chain. a.next points at b (so b.refcount = 2: the name "b" and a.next). When `del a` runs, a.refcount drops to 0 immediately (nothing else pointed at a), so a is freed right away. Freeing a also removes a.next's reference to b, dropping b.refcount from 2 to 1 (just the name "b" remains). b is still reachable and correctly still alive. Nothing points back from b to a, so there's no cycle and no need for the generational GC here at all.
Problem 4 · Generational promotion

A module-level cache dictionary is created when your program starts and lives for the entire run of the program. After the program has been running a while, which generation is it most likely sitting in, and why does that matter for GC performance?

Show solution
Generation 2 (the oldest). Every time it survives a collection pass of its current generation, it gets promoted upward — gen 0 to gen 1, gen 1 to gen 2. Since it lives for the whole program, it eventually survives enough passes to land in gen 2, which is scanned the least often. This matters because it means CPython isn't wasting cycles repeatedly re-scanning this long-lived, clearly-still-needed object on every gen-0 pass — the generational design specifically avoids that waste by trusting that objects which have already proven long-lived will likely keep being long-lived.
Problem 5 · gc.collect() and __del__

Two objects in a cycle each define a __del__ method that prints a message. You call gc.collect(). Will the messages print immediately, in a predictable order relative to each other, and why might this matter in practice?

Show solution
Yes, gc.collect() will find the unreachable cycle and finalize both objects, so both __del__ messages will print. But the ORDER between the two is not guaranteed to be meaningful/predictable the way it would be for a simple non-cyclic chain, because the collector has to break the cycle somehow before either object can be safely finalized, and which one "goes first" is an implementation detail of how the cycle is unwound. This is exactly why relying on __del__ side effects (like releasing a lock or closing a file) is risky for objects that might end up in cycles — prefer explicit cleanup (context managers, `close()` methods) over depending on finalization order.
Problem 6 · Refcount vs is-alive

True or false: "if an object's refcount is greater than zero, something in my program can still reach it." Explain using the cycle example from this lab.

Show solution
False. A refcount greater than zero only means SOMETHING holds a reference — it says nothing about whether that something is itself reachable from your program's actual roots (global names, the call stack, etc). In the Node A / Node B cycle, after deleting both outside names, each node's refcount is 1 — not zero — but neither is reachable from anywhere your running program could actually get to. "Refcount > 0" means "not provably garbage by the cheap local check"; it does not mean "definitely still useful." This exact gap between the two is the entire reason the generational GC needs to exist.
